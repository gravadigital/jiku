# Installation

The short path. Every operational detail — the four setup steps, the SQL for the read-only
role, the troubleshooting — lives in [deploy/README.md](../deploy/README.md), which is where you
will spend the time.

## What you need

| | |
|---|---|
| **Node.js 24** | see [`.nvmrc`](../.nvmrc) |
| **Docker** | for the stack, and for the `api` and `core` test suites, which start an ephemeral PostgreSQL |
| **An OIDC identity provider** | Jiku does not manage users. Zitadel is what it is built against. |
| **A database dump** | the migrations cannot build the schema from empty — see below |

That last one is the sharpest edge in adopting Jiku today, and it is worth knowing before you
start: the 95 migrations under `api/db-upgrade/migrations/` assume an existing schema and only
alter it. Against an empty database the api fails to start. See
[known-limitations.md](known-limitations.md).

## Development

```sh
npm install     # compiles the shared packages under packages/ too
npm run build
npm test
```

A fresh clone works with a single `npm install`: a `postinstall` hook builds `packages/*`, which
`api` and `core` consume from `dist/`.

## Running the stack

Three composes, for three situations:

| Compose | For | Identity provider |
|---|---|---|
| `docker-compose.dev.yml` | working with no external dependencies | the callout's `mock` mode |
| `docker-compose.local.yml` | the full stack on your machine, via `./local.sh` | real |
| `docker-compose.yml` | a server; pulls published images | real |

On your machine, after the one-time setup in [deploy/README.md](../deploy/README.md):

```sh
cd deploy
./local.sh up
```

| | |
|---|---|
| web | http://localhost:3000 |
| opus-web | http://localhost:3001 |
| api | http://localhost:3100 |

Three things have to exist before the first start, and all three are one-time: a filled-in
`deploy/.env`, a service user key per service, and the NATS identity generated by
`deploy/nats/bootstrap.sh`. [deploy/README.md](../deploy/README.md) walks through each.

## On a server

Published images, no building:

```sh
docker compose pull
docker compose up -d
```

Images are `gravadigital/jiku-{api,core,web,opus-web}`, pinned per service in `deploy/.env`.
They carry **no configuration** — one image works for any installation, everything is passed at
runtime. See [configuration.md](configuration.md).

Two differences from local: two external Docker networks are required, and the read-only
database role has to be created by hand — `local.sh` does it for you, the production compose
does not.
