# Story Plan: S-019 (web) - La marca de identidad automática en los frontends

## Status

**Status:** Completed

---

## Story Reference

- **Story:** [S-019](../stories/S-019.la-marca-de-identidad-automatica-en-los-frontends.md)
- **Service:** `web`
- **Summary:** `web` gana un badge `"Automático"` que marca al autor que **no es una persona** —una
  identidad de servicio— en los **6 puntos** de las 3 pantallas que exponen autoría. Es **un solo
  componente** reusado en los seis lugares, y se renderiza **solo** cuando `identityType === 'service'`.

> **La api ya está hecha (S-019 · `api` · Done).** Los payloads de autoría que esta story consume ya
> traen `identityType`. Esta story es **tipos + un componente + seis inserciones + tests**: no toca
> ninguna Server Action, ningún hook, ningún route handler y ninguna query key.

**Patrones que aplican a esta story:**

- **Server Components por defecto.** `'use client'` es una decisión de hoja: se marca el componente
  más chico que lo necesita, no el padre. **El badge no necesita `'use client'`**: no tiene estado,
  ni efectos, ni handlers.
- **Un módulo `.scss` por componente**, adyacente al `.tsx`, con `index.ts` de barrel.
- **Los tipos de dominio viven en `features/{módulo}/types/`**; los transversales se re-exportan por
  `shared/types/index.ts`.
- **Error handling:** `error.tsx` por ruta + `ApiError` normalizado + toasts. **Esta story no agrega
  ningún camino de error**: la ausencia del dato es render vacío, no error.

### Relevant ADRs

#### ADR-010: Sass + CSS Modules sin librería de componentes

**Decisión:** los estilos son Sass + CSS Modules + custom properties, sin librería de componentes ni
framework utilitario.

**Implementation Rules (verbatim):**

- Los estilos de un componente **DEBEN** vivir en su `*.module.scss` adyacente. **NO SE DEBE**
  usar CSS global salvo en `globals.scss` y en la capa de tokens.
- Los valores de color, espaciado y tipografía **DEBEN** referenciar custom properties de
  `_variables.scss`. **NO SE DEBEN** hardcodear valores hexadecimales ni píxeles sueltos.
- Los patrones visuales repetidos (tipografía, botones, inputs, tags, focus rings) **DEBEN** usar
  los mixins de `_mixins.scss`.
- Los breakpoints **DEBEN** declararse con los mixins de `_mixins.scss`. **NO SE DEBEN** escribir
  `@media` crudas con valores literales — hoy hay 14 en `web` con 8 valores distintos, y es deuda
  reconocida (NFR-U03).
- **NO SE DEBE** agregar una librería de componentes ni un framework CSS utilitario sin un ADR que
  lo reemplace.
- En `opus-web`, las variantes de componente **DEBEN** expresarse con atributos `data-*`, no con
  nombres de clase compuestos.
- Un valor de token **DEBE** declararse en un solo lugar. Hoy `globals.scss` y `_variables.scss`
  declaran el mismo `:root` con los mismos valores: es duplicación a resolver, no un patrón.

> **Lo que esto obliga en esta story:** el badge usa el mixin **`tag-base`** (existe) y tokens de
> `_variables.scss`. **Cero hex, cero px suelto, cero `@media`.**

#### ADR-011: TanStack Query como cache de servidor

**Decisión:** todo dato de la api se maneja con TanStack Query; el estado de UI con `useState` local.

**Implementation Rules (verbatim):**

- Todo dato que venga de la api **DEBE** manejarse con TanStack Query. **NO SE DEBE** copiar una
  respuesta a `useState` ni a un store global.
- Las query keys **DEBEN** seguir el patrón por dominio: `['<dominio>', <identificador o filtros>]`.
- Tras una mutación exitosa **DEBE** invalidarse la key afectada. Al invalidar por prefijo, hay que
  verificar que el prefijo cubra lo que se pretende.
- Las mutations **DEBEN** mantener `retry: 0`. Reintentar una escritura sin idempotencia
  garantizada duplicaría datos (ADR-002).
- El update optimista **DEBE** usarse solo donde el rollback sea trivial y la latencia se note. **NO
  SE DEBE** aplicar por default.
- El estado propio de la interfaz **DEBE** usar `useState` local. Un Context nuevo **DEBE**
  justificarse por tener consumidores reales.
- En listados paginados por categoría, **DEBE** evaluarse el costo de montar N queries en paralelo:
  el tablero del portal monta 7 y su `isLoading` es un `some`, así que la pantalla espera a la más
  lenta.

> **Lo que esto obliga en esta story:** **nada nuevo.** `identityType` llega en la misma respuesta
> que ya se cachea. **NO SE DEBE** agregar una query, un hook ni una key para traer el tipo de
> identidad: viaja en el payload que la pantalla ya pide.

#### ADR-009: El access token confinado al servidor

**Decisión:** el navegador nunca ve el access token; toda llamada de dominio de `web` va por Server
Action con `apiClient`.

**Implementation Rules (las que aplican acá, verbatim):**

- El access token **NO DEBE** llegar al navegador por ningún camino: ni en el bundle, ni en una
  respuesta, ni en una cookie legible por JS.
- La URL de la api **DEBE** leerse de `API_URL` **en el servidor, en runtime**. **NO SE DEBE**
  usar `NEXT_PUBLIC_API_URL` ni ninguna variable horneada en build.
- En `web`, toda llamada de dominio **DEBE** ir por un Server Action (`'use server'`) con
  `apiClient`. Un route handler en `app/api/` **DEBE** justificarse por una capacidad que el Server
  Action no tenga (streaming, headers de respuesta, llamada desde componente cliente).
- Un 401 de la api **DEBE** redirigir el navegador a `/login`.

> **Lo que esto obliga en esta story:** **ninguna capa de datos se toca.** Si en algún momento
> parece que hace falta un fetch nuevo para saber si un autor es un servicio, la implementación se
> fue por el camino equivocado: el dato ya está en la respuesta.

#### ADR-006: Dos frontends, una api

**Decisión:** `web` (interno) y `opus-web` (portal) son dos aplicaciones sobre la misma api; el
aislamiento del portal es **de datos**, no de renderizado.

**Lo único que esto obliga acá:** el componente del badge de `web` **no se comparte con
`opus-web`** — son dos servicios sin paquete común, y CA-12 pide *"un componente **por
superficie**"*. Duplicar la implementación entre superficies es lo correcto y está decidido; lo que
CA-12 prohíbe es duplicarla **dentro** de una superficie.

### API Context

**Todos los endpoints de esta story ya existen y ya devuelven el campo (S-019 · `api` · Done).**
`web` **no** llama a ninguno nuevo. Lo que sigue es el contrato exacto que los tipos de Task 1 deben

#### El schema de autoría: `AuthorUser`

```yaml
AuthorUser:
  type: object
  properties:
    id: { type: string }
    name: { type: string }
    email: { type: string, format: email }
    identityType:
      type: string
      enum: [person, service]
```

`description` de `identityType`, verbatim de `docs/apis/api.yaml`:

> Marca de identidad automática en la interfaz. `service` es una identidad de servicio —un conector
> externo, no una persona—, y el front renderiza la marca **solo** si el valor es exactamente
> `service`. Los dos valores están en inglés porque no los elige el producto: son el `type` de
> `deploy/nats/auth-callout/rules.yaml`. **La palabra que ve el usuario la elige el front.**

> **`roles` NO sale en ninguna respuesta HTTP, en ningún schema.** No hay nada que leer en `web`, y
> nada que agregar a ningún tipo. Si aparece `roles` en un payload, es un bug de la api, no un dato
> a consumir.

#### Los tres endpoints que alimentan las 3 pantallas

**1. `GET /api/requirements/{reqid}` → `RequirementWithRelations`** — alimenta `detalle-requisito`

```yaml
RequirementWithRelations:
  allOf:
    - $ref: '#/components/schemas/Requirement'
    - type: object
      properties:
        project: { $ref: '#/components/schemas/ProjectSummary' }
        creator: { $ref: '#/components/schemas/AuthorUser' }        # ← punto de inserción 1
        activity:
          type: array
          items:
            allOf:
              - $ref: '#/components/schemas/RequirementActivity'
              - type: object
                properties:
                  changedBy: { type: string }
                  previousValue: { type: string }
                  newValue: { type: string }
                  changedByUser: { $ref: '#/components/schemas/AuthorUser' }   # ← punto 2
        responsiblePeople: [...]
```

Nota de la spec, verbatim: *"El feed del requisito. **El handler la rebautiza:** la asociación es
`requirementActivities` y la clave de la respuesta es `activity` (`requirements-id-get.ts:43-44`).
Solo la devuelve `GET /requirements/{reqid}`."*

**2. `GET /api/projects/{id}`** — alimenta `detalle-proyecto`

```yaml
'200':
  schema:
    allOf:
      - $ref: '#/components/schemas/Project'
      - type: object
        properties:
          creator: { $ref: '#/components/schemas/AuthorUser' }      # ← punto de inserción 3
```

`description` del endpoint, verbatim: *"Devuelve `creator` y `client` embebidos. `creator` es un
`AuthorUser`: alimenta la fila "Creado por" de `detalle-proyecto` (S-019, CA-4)."*

**3. `GET /api/objectives/{id}` → `ObjectiveWithWorkedTime`** — alimenta `detalle-tarea`

```yaml
ObjectiveWithWorkedTime:
  allOf:
    - $ref: '#/components/schemas/Objective'
    - type: object
      properties:
        project: { $ref: '#/components/schemas/Project' }
        creator: { $ref: '#/components/schemas/AuthorUser' }        # ← punto de inserción 4
        ObjectiveActivity:
          type: array
          items:
            allOf:
              - $ref: '#/components/schemas/ObjectiveActivity'
              - type: object
                properties:
                  changedBy: { type: string }
                  previousValue: { type: string }
                  newValue: { type: string }
                  user: { $ref: '#/components/schemas/AuthorUser' } # ← puntos 5 y 6
```

`description` de la lista, **verbatim y crítica para Task 5**:

> **La clave es literalmente `ObjectiveActivity`**: es el nombre de la asociación, sin alias. De esta
> única lista salen las DOS listas de `detalle-tarea` —el historial y los comentarios—: el front las
> parte filtrando por `typeOfActivity === 'comment'` (S-019, CA-5).

> **Por eso los puntos 5 y 6 son dos y no uno:** el mismo `user` alimenta el historial y el
> comentario, y son dos componentes distintos (`ObjectiveHistoryList` y `ObjectiveComment`).

#### Endpoints que NO cambian, y de los que NO hay que leer `identityType`

| Endpoint | Por qué |
|---|---|
| `GET /api/projects` (listado) | Su `creator` **no** es `AuthorUser`: `projects-get.ts:31` mantiene `['id','name','email']`. `listado-proyectos` quedó fuera por CA-15 |
| `GET /api/requirements` (listado) | No tiene el `include` de `creator`. `listado-requisitos` **no tiene columna de autor** (CA-15) |
| `GET /api/requirements/report` | Devuelve `items: { type: object }` y `web` lo tipa a mano como `RequirementReportItem` con **`createdBy: string`** — no hay `AuthorUser` ni `identityType`. Ver *Hallazgos* |
| `GET /api/persons`, `GET /api/projects/{projid}/persons` | Leen `people`, no `users`. Un service user **no puede** aparecer ahí |

**Formato de error / autenticación / validación:** sin cambios. Esta story no agrega ni un status
nuevo, ni un código de error nuevo, ni un campo de request.

### Database Context

**Ninguno.** Esta story no toca la base. Las columnas `identity_type` y `roles` las creó S-015;
`web` **ni las lee directo ni sabe que existen**: consume `identityType` de una respuesta HTTP.

Para contexto del dato (informativo, no accionable en `web`):

- `users.identity_type` — `enum('person','service')`, **default `'person'`** (S-015 CA-6).
- El valor `'service'` lo escribe **solo** el consumidor del evento de autenticación (S-016), desde
  el `type` de `deploy/nats/auth-callout/rules.yaml`.
- `users.roles` — JSONB. **No sale en ninguna respuesta HTTP.**

> **Consecuencia para el front:** cualquier valor **ausente, nulo o inesperado no marca nada**,
> porque la condición es `=== 'service'`. Es la degradación segura de CA-10: se pierde una marca,
> **nunca se marca a una persona**.

**Decisiones y descartes de REQ-005 para esta pantalla, verbatim:**

- **Un autor que no es una persona se marca, no se oculta.** Se descartó **filtrarlo**: es el
  comportamiento que REQ-001 buscó a propósito (*"el publicador externo es el autor"*), y esconderlo
  dejaría el requisito sin autor visible. Se descartó también **no hacer nada**: el usuario leería el
  `name` de un service user creyendo que es alguien del equipo.
- **`"Automático"`, no `"Servicio"` ni `"Integración"`.** `"Servicio"` nombra el `identityType` de la
  base, un concepto que la interfaz nunca expuso. `"Integración"` está peor: REQ-003 dio de baja la
  integración con sistemas externos **como capacidad**, y reintroducir la palabra en la UI sugeriría
  que volvió.
- **La marca acompaña al nombre y no lo reemplaza.** El `name` del service user sigue siendo el dato
  más útil para saber **qué** lo creó; la marca solo dice **qué clase** de autor es.
- **No se marca a las personas.** Se descartó un par simétrico (`"Persona"` / `"Automático"`): el
  caso normal no necesita etiqueta y etiquetarlo sumaría ruido a cada entrada del feed, **que es el
  bloque de mayor densidad de la pantalla**.
- **No se agregó componente al Design System.** `badge` no tiene spec en `web` v0.1.0 pero **es un
  tipo que esta pantalla ya usa** en `codigo-requisito` y `badge-resultado`: el gap es previo y la
  marca no suma un compromiso nuevo.
- **Pregunta abierta:** el `name` de un service user lo define su plantilla del auth-callout y hoy
  nadie lo revisa como microcopy. Si llega vacío o con un identificador técnico, **esta pantalla lo
  muestra tal cual**. El fallback no se decide acá porque el dato es de despliegue.

#### Flujo de usuario afectado: `web` · Flujo 2 — Avanzar un requisito por su workflow

**JTBD:** *"Cuando el trabajo sobre un pedido avanza, quiero reflejarlo para que el cliente y el
equipo vean el mismo estado sin que yo tenga que avisarles."*
**Audiencia:** equipo-interno. **Trigger:** el usuario abre un requisito desde el listado o desde el
detalle de su proyecto.

**Happy path (sin cambios):**

1. `listado-requisitos` → filtra y abre uno → `detalle-requisito`
2. El **stepper de workflow** muestra dónde está: `analisis → planificacion → en_cola → desarrollo → revision`
3. El usuario completa los campos del **acordeón** que corresponden al estado actual
4. Avanza el estado desde el stepper
5. El cambio se registra como **actividad pública** automáticamente y aparece en el feed

**Camino alternativo NUEVO que esta story implementa, verbatim:**

> **Leer una entrada del feed que no la escribió una persona** — Camino de lectura **nuevo desde
> REQ-005**. Una identidad de servicio —el conector externo— tiene fila en `users` y puede figurar
> como autor de una actividad o como `created_by` del requisito. En el feed y en la fila
> `"Creado por"` el nombre viene acompañado de un badge **`"Automático"`**, que es lo único que
> distingue a ese autor de un compañero de equipo. **No hay acción asociada:** el usuario no puede
> responderle, y el comentario de un servicio no es editable como no lo es ningún comentario ajeno
> (RF-3, RF-10).

**Criterio de éxito NUEVO del flujo, verbatim:**

> - El usuario debería poder distinguir **qué escribió una persona y qué escribió un servicio** sin
>   tener que reconocer nombres — **se cumple desde REQ-005** con la marca de autoría automática

**Errores y recuperación del flujo (sin cambios, copiados para contexto):** `resolution_required` al
resolver una incidencia sin conclusión; el salto de estado inválido que **el stepper previene pero la
api no valida**; adjunto de otra persona; adjunto cuyo contenido nunca llegó; falla del bus separada
en `503` (no ocurrió, reintentar es seguro) y `504` (pudo haber ocurrido, refrescar antes de
repetir). **Esta story no agrega ni modifica ningún error de este flujo.**

**Flujos 1, 3 y 4 de `web`: sin cambios** — no exponen autoría.

#### Flujos cross-surface afectados (`docs/ux/cross-surface-flows.md`)

**Flujo 1 — Del pedido del cliente al trabajo del equipo**, verbatim:

> **Y desde REQ-005 el pedido puede tener un tercer origen.** Hasta ahora un requisito lo creaba un
> cliente en `opus-web` o alguien del equipo en `web`. Desde REQ-005 toda identidad que se autentica
> en el bus tiene fila en `users`, así que el **conector externo** de REQ-001 puede crear requisitos
> de verdad —antes no podía: sin fila en `users` la escritura violaba la FK— y aparece como autor en
> las dos superficies. Ese tercer origen **sí se distingue**: donde el producto muestra autor, el
> nombre viene con un badge *"Automático"* — en el detalle del requisito de `web` y en la columna
> "AUTOR" del tablero de `opus-web`. **Donde no muestra autor no hay nada que marcar**, y el paso 3
> de este recorrido es justamente uno de esos casos: **listado-requisitos** no tiene columna de
> autor, así que ahí el pedido del conector sigue siendo indistinguible del resto (RF-3, RF-10).
>
> **La ironía vale registrarla:** el origen que nadie pidió distinguir —el del servicio— quedó
> marcado, y el que el criterio de éxito de este flujo pide desde el relevamiento —el del cliente
> contra el del equipo— **sigue sin marca**.

**Criterio de éxito, verbatim:** *"**Nuevo:** el equipo y el cliente deberían poder distinguir lo que
creó un **servicio** de lo que creó una persona — **se cumple desde REQ-005** en el detalle de las
dos superficies y en el tablero de `opus-web`; **no se cumple** en `listado-requisitos` de `web` (sin
columna de autor) ni en el tablero mobile de `opus-web`."*

**Flujo 3 — Conversación sobre un requisito**, verbatim:

> **Lo que sí cruza distinto es la autoría.** El mismo feed que las dos superficies leen puede tener
> entradas de un autor que no es una persona, y **las dos lo marcan con la misma palabra**:
> `"Automático"`. `opus-web` suma una segunda señal que `web` no necesita —el avatar del comentario,
> que en vez de iniciales muestra un icono— porque su tarjeta de comentario **tiene** avatar.

**Criterio de éxito, verbatim:** *"Las dos partes deberían leer **la misma marca** para un autor que
no es una persona — **se cumple desde REQ-005**: el mismo badge `"Automático"` en las dos
superficies."*

> **Consecuencia dura para la implementación: el texto es `"Automático"`, exacto, en las dos
> superficies.** Un sinónimo en `web` rompe un criterio de éxito cross-surface.

## Hallazgos de la planificación

Cosas que aparecieron al cruzar los screen.md con el código. **Ninguna bloquea la story**; se anotan
para que el implementador no las descubra en el medio y las "arregle" fuera de alcance.

1. **`web` sí tiene avatar de iniciales en el feed de `detalle-requisito`, y el doc cross-surface
   dice que no.** `cross-surface-flows.md` justifica que la variant de avatar con icono sea solo de
   `opus-web` porque *"su tarjeta de comentario **tiene** avatar"* — pero
   `RequirementActivityFeed.tsx` **también** renderiza un avatar con iniciales y color derivado del
   nombre (`getInitials`, `getAvatarColor`, `AVATAR_COLORS`). O sea: **`"Conector Portal"` → `"CP"`

   **Resolución para esta story: el badge y nada más.** Los tres screen.md de `web` dicen
   `Icono: nada` y ninguno declara una variant de avatar; extenderla sería diseñar sin revisión UX.
   **Queda anotado como pregunta para UX**, no como trabajo de este plan.

2. **`reporte-requisitos` tiene una columna `"Creado por"` y queda afuera con razón, pero la razón
   registrada es imprecisa.** El REQ lo descarta junto a las pantallas que *"no exponen ningún
   `Usuario`"*, y `RequirementsReportTable.tsx:38,54` sí muestra un autor — pero muestra
   **`item.createdBy`, un `string`**, no un `AuthorUser`. Y la api lo respalda:
   `GET /requirements/report` declara `items: { type: object }` y **no devuelve `creator`**.
   **Conclusión: correctamente fuera de alcance** —no hay `identityType` que leer y marcarlo
   requeriría un cambio de api que CA-1 no incluye—, **pero la razón es "el payload no trae
   `AuthorUser`", no "no expone autor".**

3. **`ProjectDetails.tsx` es código muerto y tiene un bug en su fila `"Creado por"`.**

   (`overview.md` lo lista entre los 11 componentes muertos), y el que sí se renderiza es
   `ProjectGeneralInfo`. **No se toca: arreglar código muerto no es alcance de esta story**, y
   agregarle el badge lo haría parecer vivo.

4. **`ProjectGeneralInfo` no tiene ningún test hoy.** Es el único de los 6 puntos de inserción sin
   archivo de test vecino. Task 4 **crea** `ProjectGeneralInfo.test.tsx`.

5. **`web` no maneja `creator: null`, y esta story no lo introduce ni lo arregla.** La tabla de
   errores de la story dice que *"los tipos de los frontends ya lo declaran nullable
   (`requirement.types.ts:18,37,72`)"* — **pero esas líneas son de `opus-web`**. En `web`,
   `RequirementCreator`, `Project.creator` y `Objective.creator` son **no nullable**, y las 6 lecturas
   hacen `.name` sin guarda: un `creator: null` **ya crashea hoy**. Es preexistente.
   **Mitigación de diseño adoptada:** el badge recibe **solo `identityType`**, no el objeto usuario.
   Así **no agrega ni una lectura nueva** sobre un objeto potencialmente nulo, y el comportamiento
   ante `creator: null` queda **exactamente igual que antes** de esta story.

6. **`ObjectiveComment` usa el antipatrón de template string para clases condicionales.** La
   convención `styling` lo nombra explícitamente como bug latente. **No se corrige en esta story**
   (fuera de alcance), pero **el código nuevo que se agregue ahí debe usar `cn()`**.

### Task 1: El tipo de autoría suma `identityType`

**Status:** Completed

#### Description

Declarar en los tipos de `web` el campo que la api **ya devuelve**. Sin esto no hay nada que leer: el
front no tiene con qué decidir cuándo renderizar la marca, y la única alternativa —inferirlo del
nombre o del dominio del email— es el **riesgo alto** que la story nombra explícitamente
(*"Todas producen falsos positivos sobre personas reales, que es el peor error posible acá"*).

Es la tarea que existe porque **`web` no consume `@jiku/models`**: sus tipos de dominio están escritos
a mano y **no se enteran solos** de que la api cambió.

**cinco** campos de autoría que las 3 pantallas leen. El campo es **opcional** a propósito: es el

  name: string;
  email: string;

}

export function AutomatedIdentityBadge({ identityType }: AutomatedIdentityBadgeProps) {

}
