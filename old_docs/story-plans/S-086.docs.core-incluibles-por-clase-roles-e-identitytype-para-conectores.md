### Lo implementado: el código que hay que documentar (commit `8dcd5be`)

#### `ResourceSpec.includableByClass` (`core/src/queries/types.ts`)

```ts
/**
 * INCLUIBLES VISIBLES SOLO PARA UNA CLASE DE CALLER (S-086). Los suma `resolveForClass()`
 * (`engine/spec.ts`) antes de validar, ejecutar y describir.
 *
 * SOLO INCLUIBLES: filtros y orden por clase no son representables por tipo, así que un nombre
 * declarado acá NUNCA es filtrable ni ordenable, y tampoco entra en `q`. Su ausencia —o la de la
 * clase— significa "nada extra", jamás "todo": para las demás clases el nombre no existe
 * (`invalid_fields`, ADR-008).
 */
readonly includableByClass?: Readonly<
  Partial<Record<CallerClass, Readonly<Record<string, IncludableSpec>>>>
>;
```

`Query.validate` cambió de firma:

```ts
validate(payload: unknown, callerClass: CallerClass): { value: TPayload } | { error: Reply<never> };
```

con el JSDoc: *"`callerClass` llega YA RESUELTA por la compuerta 2 del despachador: es lo que
permite que la ficha sume los incluibles declarados para esa clase (`includableByClass`). Una
consulta que no la necesita (`meta.describe`, `requirements.tags`) puede ignorarla."*

#### `resolveForClass` (`core/src/queries/engine/spec.ts`)

```ts
export function resolveForClass(resource: ResourceSpec, callerClass?: CallerClass): ResourceSpec {
  const extra = callerClass ? resource.includableByClass?.[callerClass] : undefined;
  if (!extra) {
    return resource;
  }
  const includable = { ...resource.includable, ...extra };
  return {
    ...resource,
    includable,
    includableNames: Object.keys(includable),
    fieldNames: [...Object.keys(resource.base), ...Object.keys(includable)],
  };
}
```

- Mismo molde que `resolveVariant`: **fusiona** el mapa y **re-deriva** `includableNames` y
  `fieldNames` con `Object.keys`, sin copiarlos.
- Orden: primero la ficha y después la clase (`email, person, roles, identityType`). Es el orden que
  viaja en `errorDetails.allowed` y en `meta.describe`.
- **Devuelve la misma referencia** si la ficha no tiene `includableByClass`, si no llega clase o si
  la clase no tiene entrada. Sin clase **falla cerrado** (ADR-008).
- No toca `filterable`, `sortable` ni `enums`.

#### Dónde se aplica (siempre **antes** que `resolveVariant`)

| Punto | Archivo | Cambio |

#### La ficha de `users` (`core/src/queries/users/users-spec.ts`)

```ts
const INCLUDABLE_BY_CLASS: Record<string, Record<string, IncludableSpec>> = {
  connector: {
    roles: { kind: 'field', column: 'roles' },
    identityType: { kind: 'field', column: 'identity_type' },
  },
};
// ...
includableByClass: INCLUDABLE_BY_CLASS,
// Ningún enum: `identity_type` NO se declara porque `enums` se publica a todas las clases en
// `meta.describe` y filtraría el nombre a las personas.
enums: {},
```

Cabecera vigente (resumen fiel): para una persona (interna o externa), `roles` **no existe**, porque
publicarlo le permitiría enumerar quién es admin. Existen **solo** en `includableByClass.connector`
(S-086, D-10 de REQ-017). `roles` viaja tal cual, **incluidos los roles desconocidos como `docs`**.
**Riesgo conocido (R-2): todo `internal-app` ve los roles de todos.** Para ninguna clase son
filtrables, ordenables ni entran en `q`.

Sin `transform`: `pg` entrega el `jsonb` como array y el enum como string.

### Relevant ADRs

#### ADR-008: Autorización deny-by-default por path, no por ruta

- **Decisión:** `validateToken` global con lista explícita de exenciones; un endpoint nuevo queda
  protegido sin que su autor haga nada. Lo no declarado no existe. El plano de consultas de core cita
  este ADR para sus listas blancas (`users-spec.ts`: *"PARA LAS PERSONAS 'NO ESTÁ DECLARADO PARA TU
  CLASE' ES 'NO EXISTE' (ADR-008)"*).
- **Implementation Rules (verbatim):**
  - `validateToken` **DEBE** instalarse globalmente en `app.ts`. **NO SE DEBE** declarar
    autenticación ruta por ruta.
  - Un endpoint público **DEBE** agregarse explícitamente a `api/lib/config/public.ts`. Cualquier
    cambio en ese archivo es un **cambio de seguridad** y debe revisarse como tal.
  - Un endpoint público **DEBE** validar por su cuenta lo que corresponda. El caso vigente
    (`GET /api/opus/attachments/:id/public`) verifica que el adjunto esté marcado público, responde
    403 en cualquier otro caso, y manda `X-Content-Type-Options: nosniff` con CSP de sandbox.
  - Un endpoint que requiere rol **DEBE** declarar `hasAnyRole([...])` explícitamente. La
    autenticación global no implica autorización.
  - Un endpoint accesible a `external-user` **DEBE** además verificar permiso de proyecto: el rol
    solo no alcanza ([ADR-006](ADR-006-dos-frontends-una-api.md)).
  - Un tipo de entidad nuevo con adjuntos **DEBE** agregarse a la resolución de proyecto de
    `attachments-access.ts`. Un tipo no contemplado **no se autoriza**, que es el comportamiento
    correcto.
  - Al leer un archivo de ruta, **NO SE DEBE** concluir que está desprotegido por no ver el
    middleware: la protección es global.
- **Estructura vigente del final del archivo:** `## Referencias` y después
  `## Revisión: una nueva exención, /p/docs/* (REQ-016 / S-085, 2026-10-24)`. Precedente (DP-4 de
  S-085): las revisiones **se agregan al final**, sin reescribir texto existente.
