# Story Plan: S-042 (web) - Total real y paginador unificado en el listado de requisitos

## Status

**Status:** Completed

## Story Reference

- **Story:** [S-042](../stories/S-042.total-real-y-paginador-unificado-en-el-listado-de-requisitos.md)
- **Service:** `web`
- **Summary:** Reemplazar el paginador inline de `RequirementList` por el componente unificado
  `Pagination` (S-037), alimentado con el total real del conjunto filtrado que devuelve
  `useRequirementsCount` (S-036). El paginador deja de adivinar si hay página siguiente comparando
  `requirements.length >= limit` y pasa a calcular la cantidad exacta de páginas.

**Patrones clave:**

- **Las tres capas de datos.** Ningún componente cliente saltea capas:
  `componente cliente → useQuery(hook) → Server Action → apiClient (axios, interceptor Bearer) → api`.
  El token nunca llega al navegador.
- **El estado de los filtros vive en la URL.** Los listados escriben `searchParams` con
  `router.push` y la página de servidor los lee. No hay estado local de filtros.
- **`Suspense` con `key`.** `requirements/page.tsx:44` usa `key={JSON.stringify(filters)}`, así que
  todo cambio de filtro remonta el subárbol.
- **Error handling:** `useRequirements` se desestructura con default `[]` e ignora `isError`. Es
  deuda conocida de la pantalla; **esta story no la cierra** y debe mantener ese comportamiento
  (no introducir un tratamiento de error nuevo que cambie el empty state existente).
- **Testing:** Vitest + Testing Library. Los mocks de módulo se declaran con `vi.mock` a nivel de
  archivo; `next/navigation` se mockea con `useRouter`/`useSearchParams` falsos.

### API Context

**No hay cambios de API.** El contrato ya existe y está documentado en `docs/apis/api.yaml`.

`GET /requirements` — parámetro `count`:

```yaml
- name: count
  in: query
  description: |
    Si es `true`, devuelve la cantidad de requisitos que satisfacen los mismos filtros en vez
    del listado. `page` y `limit` se ignoran.
  schema: { type: boolean }
responses:
  '200':
    content:
      application/json:
        schema:
          oneOf:
            - type: array
              items: { $ref: '#/components/schemas/RequirementWithRelations' }
            - type: integer
              description: Cantidad de requisitos que satisfacen los filtros. Solo con `count=true`.
```

**Consecuencia de contrato:** con `count=true` la respuesta es un **entero desnudo**, no un objeto.
`getRequirementsCount` devuelve `response.data` tal cual, tipado como `Promise<number>`.

**Filtros que viajan:** los mismos que el listado. `state` viaja como CSV
(`state=planificacion,en_cola,desarrollo,revision`) y el backend lo resuelve con `[Op.or]` en su
`buildWhere` (S-040, Completed). El `count` **no lleva `include`**, así que es una query barata
sobre el mismo índice `idx_requirements_state_created_id`.

**Autenticación:** transparente para esta story. El interceptor de `lib/axios.ts` inyecta el
`Bearer` llamando a `auth()` dentro de la Server Action.

### Flow Context

La story declara explícitamente: **"Flujos Afectados: Ninguno"**. La interacción es
`web → api → PostgreSQL` dentro de un único servicio de lectura; no cruza el bus ni a `core`. No

### Database Context

**Sin cambios de base de datos.** El `count` se apoya en el índice ya existente

ni migraciones.

### Integration Points

- **api (HTTP):** `GET /requirements?...&count=true`, vía la Server Action `getRequirementsCount`.
  Es el único punto de integración nuevo desde esta pantalla, y es un endpoint ya en producción.

### Code Conventions

- **Query keys:** `['requirements', filters]` para el listado, `['requirements-count', filters]`
  para el conteo. Las keys incluyen el objeto de filtros completo, así que un cambio de filtro
  invalida ambas queries por identidad estructural.
- **Componentes cliente:** `'use client'` al tope. `RequirementList` ya lo tiene.
- **Imports:** desde los barrels (`@/shared/components/ui`), no desde rutas profundas.
- **Nombres:** `handleXxx` para callbacks de evento, `useCallback` con el array de dependencias
  explícito (patrón ya presente en el archivo).
- **CSS Modules:** clases en camelCase, consumidas como `styles.xxx`.

**Contrato exacto de `Pagination` (copiado del código):**

```tsx
interface PaginationBaseProps {
  readonly totalItems: number;
  readonly limit: number;
}

type PaginationUrlProps = PaginationBaseProps & {
  /** Ruta base a la que navegar; el resto de los searchParams se preservan. */
  readonly basePath: string;
  readonly currentPage?: never;
  readonly onPageChange?: never;
};

type PaginationControlledProps = PaginationBaseProps & {
  readonly currentPage: number;
  readonly onPageChange: (page: number) => void;
  readonly basePath?: never;
};
```

Comportamiento relevante:

- `totalPages = Math.ceil(totalItems / limit)`.
- **`if (totalItems === 0) return null;`** — con conteo 0 el paginador no renderiza nada. Esto es
  exactamente lo que CA-2 exige ("no ofrece páginas navegables").
- En modo URL deriva la página de `searchParams.get('page')` y navega con
  `router.push(\`${basePath}?${createQueryString('page', String(newPage))}\`)`, **preservando el
  resto de los searchParams**.
- Renderiza `<nav aria-label="Paginación" role="navigation">`; el botón activo lleva
  `data-active` + `aria-current="page"` y está `disabled`.

- `RequirementDetail.tsx:230` — modo controlado (S-039).

#### Contenido — bloques que esta story toca

**`paginacion`** (texto/label: flechas con `aria-label="Página anterior"` y `"Página siguiente"`,
más los números de página):

- **Deja de ser una reimplementación inline y pasa al paginador unificado** del producto (el mismo
  bloque que ya usan `listado-tareas`, la card de requisitos del detalle de proyecto y la tabla de
  tareas del requisito), en su modo URL.
- **Conoce el total del conjunto filtrado:** la cantidad de páginas se calcula sobre el total de
  requisitos que cumplen los estados seleccionados y los demás filtros, en vez de adivinar si hay
  una página siguiente porque la actual vino llena [REQ-009 RF-9, AC-6].
- Con 32 requisitos en los cuatro estados por default y 15 por página, ofrece **3 páginas** — no 4
  ni las que resultarían del total sin filtrar [REQ-009 AC-6].
- Muestra como máximo **10 números en una ventana deslizante** centrada en la página actual, como
  el resto de las tablas del producto.
- **El total corresponde siempre al conjunto filtrado**, así que cambiar los estados cambia el
  total y la cantidad de páginas, y cualquier cambio de la selección devuelve a la página 1
  [REQ-009 RF-8, RF-9].

**`selector-tamano-pagina`**: opciones `"15 por página"` · `"20 por página"` · `"25 por página"`.
Default 15. **Se conserva tal cual**, incluido su `aria-label="Elementos por página"` y el reseteo
de `page` a 1 al cambiar el límite.

**`vacio-requisitos`**: `"No se encontraron requisitos"`, en un `<td colSpan={8}>`; los encabezados
de la tabla quedan visibles. **No cambia.**

#### Estados

**`empty`** — Aplica: Sí. Mensaje: `"No se encontraron requisitos"`.
- vacio-requisitos: solo visible en este estado, como una fila con `colSpan={8}`.
- Los encabezados de la tabla quedan visibles.
- **Alcanzable por una combinación de estados sin resultados.** En ese caso el total informado es 0
  y el paginador no ofrece páginas navegables [REQ-009 AC-13].

**`loading`** — Aplica: Sí. `"Cargando..."` en el primer render (fallback del `<Suspense key>`) y
`"Cargando requisitos..."` en los refetch (dentro del cuerpo de la tabla).

**`última página conocida`** — Aplica: Sí — **pasa a estar implementado** [REQ-009 RF-9, AC-6].
- paginacion: la última página es la real del conjunto filtrado. La flecha "siguiente" queda
  deshabilitada en ella, y **ya no se puede navegar a una página vacía cuando el total es múltiplo
  exacto del límite**.
- El total del conjunto filtrado deja de ser desconocido para la pantalla, y por lo tanto la
  cantidad de páginas es exacta en vez de inferida.
- Antes: habilitaba "siguiente" comparando `requirements.length >= limit` — "vino una página llena,
  asumo que hay más".

**`error de sistema`** — Aplica: No, no implementado. `useRequirements` ignora `isError` y el
default `[]` hace que un fallo se vea como `"No se encontraron requisitos"`. **Deuda preexistente;
esta story no la cierra** — y el mismo criterio aplica al conteo: un `count` fallido no debe romper
el render.

#### Interacciones

- flecha de `paginacion` · on click → `params.set('page', ...)` + `router.push`.
- `selector-tamano-pagina` · on change → setea `limit` y **resetea `page` a 1**.
- `updateFilter` → borra `page` y hace `router.push`. `state` es la excepción al borrado del
  sentinel: `state=all` se conserva (S-041).

#### Accesibilidad de la pantalla (lo que cambia y lo que no)

- **Mejora que trae el cambio:** hoy la paginación es un `<div>` sin `aria-label`. `Pagination`
  renderiza `<nav aria-label="Paginación" role="navigation">`, así que el bloque pasa a ser un
  landmark correcto.
- **`selector-tamano-pagina`** conserva su `aria-label="Elementos por página"`.
- **Gap que NO se cierra acá:** el resultado del filtrado no se anuncia (sin `aria-live`). Con el
  total ya disponible en la pantalla, la ausencia de región live pasa de consecuencia a carencia
  propia — **queda registrado como gap; este requerimiento no lo cierra** (decisión explícita de la
  Revisión UX de REQ-009). No agregar `aria-live` en esta story.
- **Gap que NO se cierra acá:** las filas de la tabla siguen fuera del orden de foco
  (`<tr onClick>` sin `role`/`tabIndex`).

#### Decisiones registradas (REQ-009) que gobiernan esta story

- **El paginador se migra al componente unificado y se alimenta con el total real.** No estaba en el
  pedido: es un hallazgo del diseño. El paginador inline adivinaba las páginas comparando si la
  página vino llena, y con un filtro que recorta el conjunto eso pasa de ser impreciso a ser
  visiblemente incorrecto. **Descartado** dejarlo como estaba [REQ-009 RF-9, AC-6, riesgo R2].
- **No se agrega desglose por estado en el listado global.** El paginador informa el total de la
  selección, que es lo que se necesita para navegar [REQ-009, clarificación de negocio].
- **La card de requisitos del detalle de proyecto no se toca** [AC-8]. **`opus-web` no se modifica**
  [AC-15].

`surfaces/web/user-flows.md` — **Flujo 2 (Avanzar un requisito por su workflow), paso 1:** el

## Tarea 1: Consumir `useRequirementsCount` en `RequirementList`

**Status:** Completed
**Categoría:** Data

### Descripción

Traer el total real del conjunto filtrado al componente, invocando el hook `useRequirementsCount`
ya existente (S-036) con **los mismos filtros** que ya recibe `useRequirements`. Hoy el componente
no lo usa: es la pieza de datos que falta para que el paginador deje de adivinar.

### Acceptance Criteria

- `RequirementList` invoca `useRequirementsCount(filters)` con el mismo objeto `filters` que llega
  por props y que ya alimenta a `useRequirements`.
- El total se expone en el componente como un número con default `0` cuando la query todavía no
  resolvió o falló (`const { data: count = 0 } = useRequirementsCount(filters)`).
- No se agrega ninguna Server Action ni hook nuevo: se reutiliza lo que ya existe.
- No se modifica `useRequirementsCount`, `getRequirementsCount` ni `requirementsApi.ts`.

### Technical Details

**Archivo:** `web/src/features/requirements/components/RequirementList/RequirementList.tsx`

**Referencias del Architectural Context:**
- *Reusable Code* → `useRequirementsCount`, `getRequirementsCount`.
- *API Context* → `GET /requirements?...&count=true` devuelve un **entero desnudo**.
- *Code Conventions* → query key `['requirements-count', filters]`; el hook ya la declara.

**Import a agregar:**

```ts

```

**Uso, junto al hook que ya está en la línea 74:**

```ts
const { data: requirements = [], isLoading } = useRequirements({ filters });
const { data: count = 0 } = useRequirementsCount(filters);
```

**Por qué el default `0` y no un `undefined` propagado:** `Pagination` devuelve `null` con
`totalItems === 0`, así que el default hace que durante la carga y ante un fallo del conteo la
pantalla simplemente no muestre paginador, en vez de romper o mostrar páginas inventadas. Es
consistente con cómo el componente ya trata `requirements = []` (deuda documentada: `isError` se
ignora; **no cambiarla en esta story**).

**Cuidado con la identidad del objeto de filtros:** `filters` llega por props desde un Server
Component que lo reconstruye en cada render de la ruta. La query key es `['requirements-count',
filters]` y TanStack Query la serializa estructuralmente, así que no hace falta memoizar; pasar el
mismo objeto que recibe `useRequirements` garantiza que ambas queries se invaliden juntas.

Un mock de fábrica **reemplaza el módulo entero**: cualquier export no declarado queda `undefined`.

```ts
vi.mock('../../services/requirementsApi', () => ({
  getRequirements: vi.fn(),
  getRequirementsCount: vi.fn(),
}));
```

```ts
beforeEach(() => {
  vi.clearAllMocks();
  mockSearchParams = new URLSearchParams();
  vi.mocked(requirementsApi.getRequirements).mockResolvedValue([mockRequirement]);
```

serializa como `data-active="true"`) al botón de la página actual, pero **solo renderiza si
`totalItems > 0`**. Un default de `32` con `limit: 10` (el de `filters` en la suite) deja 4 páginas
y el test sigue pasando sin tocarlo.

**Cómo consultar el paginador en los tests:**

```ts
const nav = document.querySelector('nav[aria-label="Paginación"]');
const pageButtons = nav ? within(nav as HTMLElement).getAllByLabelText(/^Página \d+$/) : [];
```

Las flechas tienen `aria-label="Página anterior"` / `"Página siguiente"`, que **no** matchean
`/^Página \d+$/`, así que la regex separa números de flechas limpiamente.

```ts
mockSearchParams = new URLSearchParams('page=3');
render(<RequirementList filters={{ ...filters, page: 3, limit: 15 }} />, { wrapper: createWrapper() });
```
