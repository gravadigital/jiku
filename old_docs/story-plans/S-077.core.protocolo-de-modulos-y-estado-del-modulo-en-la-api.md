## Story Reference

- **Story:** [S-077](../stories/S-077.protocolo-de-modulos-y-estado-del-modulo-en-la-api.md)
- **Service:** `core`
- **Summary:** `generateUlid` se mudó de `core/src/ulid.ts` a `@jiku/nats-protocol` (plan
  `S-077.nats-protocol.*`, ya completado) porque desde REQ-016 lo necesitan dos servicios: core
  (`eventId` y `correlationId`) y la api (altas de docs, DD-8). Este plan cierra la mudanza del lado
  de core: **re-apunta los dos imports** al paquete y **retira la copia local** (`core/src/ulid.ts` y
  su test, cuyos casos ya están portados al paquete como TS-201..TS-204). Ningún comportamiento
  observable cambia.

**Lo que este plan NO hace (y no hay que "completar"):**

- **No** cambia la implementación de `generateUlid`: la del paquete es una copia byte a byte de la de
  core (verificado por TS-200 del paquete, que fija los prefijos de tiempo calculados con
  `core/src/ulid.ts`). Si algo del paquete parece distinto, es un bug del plan del paquete, no de este.
- **No** agrega la dependencia npm `ulid` (D-2 de REQ-014, conservada por REQ-016).
- **No** toca ningún comando, consulta, evento, ni la base. Ningún criterio de aceptación de la story
  (CA-2..CA-8, CA-S2) se implementa en core: todos viven en la api.
- **No** toca `docs/flows/*.md` (S-085) ni `packages/nats-protocol` (ya hecho).

### Firma en el paquete (fuente: `packages/nats-protocol/src/index.ts:1143`)

```ts
export function generateUlid(now: number = Date.now()): string;
```

- Misma firma que la local. **No hay `export default`** en el paquete (el `export default generateUlid`
  de `core/src/ulid.ts` no se copió): se importa siempre **nombrado**.
- El `dist/index.d.ts` del paquete ya lo exporta. Core consume el paquete **compilado**, así que antes
  de compilar o testear core hay que correr `npm run build:packages` desde la raíz.

### Relevant ADRs

- **ADR-012: Monorepo npm con contexto de build en la raíz**
  - Decisión: un único monorepo npm con workspaces; las imágenes se construyen con contexto en la raíz.
  - Implementation Rules (verbatim):
    - Todo servicio y paquete **DEBE** ser un workspace declarado en el `package.json` de la raíz.
    - Un Dockerfile **DEBE** construirse con contexto en la **raíz del monorepo**, no en la carpeta del
      servicio. **NO SE DEBE** usar `docker build .` desde la carpeta del servicio: falla al no
      alcanzar `packages/`.
    - Los Dockerfiles **DEBEN** copiar los manifiestos antes del código fuente, para preservar el cacheo
      de `npm ci`.
    - Los frontends **DEBEN** instalar con `--ignore-scripts`: no consumen `packages/*` compilados.
    - El gestor de paquetes **DEBE** ser **npm** con workspaces. **NO SE DEBEN** usar yarn, pnpm ni bun.
    - Un cambio en `packages/*` **DEBE** ejecutarse con los tests de **todos** los servicios que lo
      consumen antes de mergear.
    - Los cuatro servicios **DEBEN** correr sobre `node:24.12-alpine3.23` con usuario no-root, y usar
      build multi-stage.
    - Una imagen **NO DEBE** hornear configuración: sin `ARG` de entorno ni `NEXT_PUBLIC_*` funcional
      ([ADR-009](ADR-009-token-confinado-al-servidor.md)).
  - Aplicación acá: `core/Dockerfile` ya copia y compila `packages/nats-protocol` (líneas 14, 24, 39,
    49), así que la imagen no necesita cambios. La regla de "tests de todos los consumidores" es la que
    cierra la story: con este plan, core pasa a consumir un símbolo nuevo del paquete.

### Integration Points

### Code Conventions (de `docs/architectures/core/conventions/_base.md`)

- **Imports relativos** para el propio servicio; los paquetes del workspace se importan **por nombre**
  (`@jiku/nats-protocol`), consumidos compilados.
- Orden de imports: `joi` → `sequelize` → `@jiku/models` → `@jiku/nats-protocol` → relativos. Por eso
  `generateUlid` entra en el import de `@jiku/nats-protocol` **ya existente** de cada archivo, no como
  una línea suelta al final.
- `strict: true` + `noUnusedLocals`: si queda un import huérfano, `tsc` falla. Es la red que confirma
  que no quedó ningún consumidor de `../ulid`.
- Comentarios en español, que explican el por qué. Si se deja un comentario en el import, dice por qué
  vive en el paquete (lo usan core y la api), no qué hace.

### Reusable Code

- **`generateUlid`** — ahora en `@jiku/nats-protocol` (`packages/nats-protocol/src/index.ts`). 26
  caracteres Crockford base32 (10 de timestamp en ms + 16 aleatorios vía `crypto.randomBytes`).
  Alimenta `DomainEvent.eventId` (uno por evento, en `emitEvents`) y `correlationId` (uno por
  `dispatch()`, compartido por todos los eventos de ese comando — CA-9 de S-063).
- El catálogo `docs/reusable-code/core/` todavía lo lista en `core/src/ulid.ts`
  (`index.md:37`, `utils.md:663-692`): queda desactualizado con este plan y se corrige en la Tarea 2.

## Tasks

### Task 1: Re-apuntar `generateUlid` al paquete y retirar la copia de core

**Status:** Completed

#### Description

Los dos únicos consumidores de `core/src/ulid.ts` pasan a importar `generateUlid` de
`@jiku/nats-protocol`. Después se borran `core/src/ulid.ts` y `core/tests/ulid.test.ts`: la función y
sus tests ya viven en el paquete (TS-199..TS-204), y mantener dos copias es exactamente lo que la
mudanza vino a evitar — dos implementaciones de un mismo identificador terminan divergiendo.

#### Acceptance Criteria

1. `core/src/bus/emit-events.ts` importa `generateUlid` dentro de su import de `@jiku/nats-protocol`
   existente: `import { DomainEvent, EVENTS_VERSION, eventSubject, generateUlid } from '@jiku/nats-protocol';`.
   La línea `import { generateUlid } from '../ulid';` desaparece.
2. `core/src/bus/dispatcher.ts` agrega `generateUlid` al bloque multilínea
   `import { Actor, ErrorCode, Reply, callerFromSubject, commandFromSubject, failure } from '@jiku/nats-protocol';`
   (manteniendo el orden alfabético existente del bloque) y elimina `import { generateUlid } from '../ulid';`
   (línea 23).
3. Las llamadas `eventId: generateUlid(),` y `const correlationId = generateUlid();` no cambian.
4. `core/src/ulid.ts` y `core/tests/ulid.test.ts` están borrados.
5. TS-1, TS-2, TS-3, TS-4 y TS-5 pasan.

#### Technical Details

**Architectural Context References:**
- Imports y su orden: *Code Conventions* (paquete por nombre, en el import existente).
- Firma y ausencia de `export default`: *Firma en el paquete*.
- Equivalencia de tests: tabla de *Tests existentes que hacen de regresión*.

**Files to Create/Modify:**
- `src/bus/emit-events.ts` (modificar import)
- `src/bus/dispatcher.ts` (modificar import)
- `src/ulid.ts` (borrar)
- `tests/ulid.test.ts` (borrar)

**Implementation Notes:**
- Usar `git rm` para los dos borrados, así el historial deja explícito que el archivo se retiró.
- No dejar un `core/src/ulid.ts` que re-exporte del paquete "por compatibilidad": no hay otros
  consumidores (TS-1) y un re-export es una segunda puerta al mismo símbolo.
- Antes de compilar: `npm run build:packages` en la raíz (core consume el `dist/` del paquete).
- Si `tsc` reporta `Module '"@jiku/nats-protocol"' has no exported member 'generateUlid'`, el `dist`
  del paquete está viejo: rebuildear el paquete, no tocar el código de core.

**Dependencies:**
- Interna: `@jiku/nats-protocol` (ya en `dependencies`).

#### Testing Requirements

**Unit Tests:**
- No se escriben tests nuevos: el comportamiento no cambia y los tests de la función viven en el

**Integration Tests:**

**Manual Testing:**
