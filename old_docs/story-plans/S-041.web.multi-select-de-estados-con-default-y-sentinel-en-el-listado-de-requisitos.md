# Story Plan: S-041 (web) - Multi-select de estados con default y sentinel en el listado de requisitos

## Status

**Status:** Completed

## Story Reference

- **Story:** [S-041](../stories/S-041.multi-select-de-estados-con-default-y-sentinel-en-el-listado-de-requisitos.md)
- **Service:** `web`
- **Summary:** El filtro de estado del listado global de requisitos (`/requirements`) pasa de
  selección única a selección múltiple, con un default de cuatro estados de trabajo en curso al
  entrar sin `state` en la URL y un sentinel `all` —persistido en la URL— que significa "todos los
  estados". Replica el mecanismo ya en producción en el listado de tareas.

**Origen:** [REQ-009](../requests/REQ-009.filtro-multi-estado-en-el-listado-de-requisitos.md)

### Alcance: qué NO entra en esta story

El documento de pantalla `listado-requisitos.md` (v1.1) describe **dos** cambios de REQ-009: el
filtro multi-estado y la migración de `paginacion` al paginador unificado con total real. **Esta
story implementa solo el primero.** El paginador es alcance de **S-042** (misma REQ, story
separada), que toca la zona de paginación del mismo `RequirementList.tsx`.

Consecuencia práctica para el implementador: **no tocar** el bloque `pagination` de
`RequirementList.tsx:196-246` ni `getRequirementsCount` / `useRequirementsCount`. Si un test de esta
story parece pedir el total real del conjunto filtrado, está mal derivado — el total es de S-042.

**Secuenciación:** S-042 sigue en `Ready` y sin plan, así que `RequirementList.tsx` está intacto.
S-041 va primero, como recomienda la nota de secuenciación de la story, para evitar el conflicto de
merge en ese archivo.

### Service Architecture

**Regla central del servicio:** el access token nunca llega al navegador. Los `services/*Api.ts`
llevan `'use server'` y el interceptor de `apiClient` llama a `auth()`, que solo corre en el
servidor.

**Las tres capas de lectura** (convención `data-fetching`):

```
componente cliente
      │   useRequirements({ filters })              features/requirements/hooks/useRequirements.ts
      ▼
  useQuery({ queryKey: ['requirements', filters] }) ← cache
      │   queryFn
      ▼
  getRequirements(filters)                          features/requirements/services/requirementsApi.ts
      │   'use server'
      ▼
  apiClient.get('/requirements?...')                lib/axios.ts (interceptor → Bearer)
      ▼
  api
```

Ninguna capa se saltea desde un componente cliente. Una página **de servidor** sí puede llamar a la
Server Action directamente.

**Estructura de carpetas relevante** (dentro de `web/src/`):

```
app/(loggedin)/requirements/
├── page.tsx                  ← Server Component: lee searchParams y arma `filters`
├── page.test.tsx
└── requirements.module.scss

features/requirements/
├── components/
│   ├── RequirementFilters/   ← la barra de filtros (Client Component)
│   └── RequirementList/      ← tabla + paginación + dueño de la URL (Client Component)
├── hooks/useRequirements.ts
├── services/requirementsApi.ts
└── types/requirement.types.ts

shared/components/ui/InputMultipleSelect/  ← el multi-select reutilizable
```

**Manejo de errores** (convención `error-handling`): el interceptor de respuesta de axios normaliza
todo fallo a `ApiError { code, message, status }`. El error que llega a un hook es **siempre** un
`ApiError`, nunca un `AxiosError`. El `401` redirige a `/login` en un solo lugar (el interceptor).

> Nota relevante para esta pantalla: `useRequirements` se desestructura hoy como
> `{ data: requirements = [], isLoading }` — `isError` se ignora y un fallo se ve como
> `"No se encontraron requisitos"`. **Es un gap preexistente, no lo abre esta story y no se cierra
> acá.** No agregarlo al alcance.

### Relevant ADRs

**ADR-011 — TanStack Query** (`docs/adrs/ADR-011-tanstack-query.md`): el cache de servidor vive en
TanStack Query, con la query key incluyendo los filtros. La consecuencia directa para esta story:
`queryKey: ['requirements', filters]` ya incluye `state`, así que **cambiar el CSV de estados
invalida la key y re-pide sola**. No hay que invalidar nada a mano.

### Convención `state-management` (la que gobierna esta story)

Árbol de decisión vigente:

```
¿De dónde viene el dato?
├── De la api  ─────────────────> TanStack Query. NUNCA copiarlo a useState
├── Define qué se ve en la
│   pantalla y querés que sea
│   compartible / navegable  ───> searchParams (router.push)
├── Sesión ─────────────────────> useSession() / auth()
└── Solo le importa a este
    componente y a sus hijos ───> useState / useReducer
```

**Reglas del estado de URL (verbatim de la convención):**

- Partir de los params actuales (`new URLSearchParams(searchParams?.toString())`), no de vacío:
  cambiar un filtro no debe borrar los otros.
- El valor `'all'` **borra** el parámetro en vez de escribirlo. Es el sentinel de "sin filtro".
- Al cambiar cualquier filtro, **resetear `page` a 1**.
- El destino del `push` es la ruta actual, escrita literal.
- Los defaults se aplican en la página de servidor, en un solo lugar, no en cada componente.

> ### ⚠️ Esta story introduce una excepción explícita a la segunda regla
>
> La convención dice que `'all'` borra el parámetro. **Para `state` en `/requirements`, eso deja de
> valer**: `state=all` se escribe y se conserva en la URL. La razón es que con un default de cuatro
> estados, una URL sin `state` ya no significa "sin filtro" sino "el default", así que "sin filtro"
> necesita su propia representación explícita. Los demás filtros (`projectId`, `sort`, `search`)
> **mantienen** el borrado actual. Es exactamente lo que ya hace el listado de tareas, que sí
> escribe `state=all`.

### API Context

Contrato ya ampliado por **S-040** (`Completed`). Esta story **no modifica `docs/apis/api.yaml`**.

```yaml
  /requirements:
    get:
      tags: [requirements]
      summary: Lista requisitos
      x-roles: [user, admin]
      parameters:
        - name: projectId
          in: query
          schema: { type: integer }
        - name: state
          in: query
          description: |
            Uno o varios estados separados por coma. Devuelve los requisitos que estén en
            **cualquiera** de ellos (OR). Un valor fuera del enum `RequirementState` invalida el
            parámetro completo y responde 400 `invalid_fields`.
          schema: { type: string }
          example: planificacion,en_cola,desarrollo,revision
        - name: type
          in: query
          schema: { $ref: '#/components/schemas/RequirementType' }
        - name: priority
          in: query
          schema: { type: string }
        - name: createdBy
          in: query
          schema: { type: string }
        - name: estimatedFinishDate
          in: query
          schema: { type: string, format: date }
        - name: tag
          in: query
          schema: { type: string }
        - name: search
          in: query
          description: Búsqueda parcial sobre el título (`ILIKE`)
          schema: { type: string }
        - $ref: '#/components/parameters/Page'
        - name: limit
          in: query
          schema: { type: integer, minimum: 1, maximum: 100, default: 20 }
        - name: sort
          in: query
          description: Aceptado por el esquema pero **no usado**; el orden es siempre `createdAt DESC`
          schema: { type: string }
        - name: count
          in: query
          schema: { type: boolean }
      responses:
        '200': OK  (array de RequirementWithRelations, o integer si count=true)
        '400': InvalidFields
        '401': Unauthorized
        '403': AccessDenied
        '500': InternalError
```

**Semántica que importa para esta story:**

- Los estados se combinan con **OR** entre sí; el filtro de estado se combina con **AND** contra
  `projectId`, `search`, etc.
- Un estado fuera del enum invalida el parámetro entero → `400 invalid_fields`. No alcanzable desde
  la UI, porque las opciones están cerradas al enum.
- **Ausencia del parámetro `state`** = sin condición de estado = los siete estados.

**Services:**

- **`getRequirements`** — `web/src/features/requirements/services/requirementsApi.ts`
  ```ts
  const cleanFilters = (filters: object): Record<string, string> => {
    return Object.fromEntries(
      Object.entries(filters).filter(([, value]) => value && value !== 'all')
    ) as Record<string, string>;
  };

  export const getRequirements = async (filters: RequirementFilters = {}): Promise<Requirement[]> => {
    const nonEmptyFilters = cleanFilters(filters);
    const queryParams = new URLSearchParams(nonEmptyFilters).toString();
    const response = await apiClient.get(`/requirements?${queryParams}`);
    return response.data;
  };
  ```
  **`cleanFilters` ya descarta el literal `'all'`.** El sentinel está contemplado en el
  serializador: **este archivo no se toca en esta story.** Es la pieza que hace que `state=all` en la
  URL salga como una request **sin** `state`.

**Types:**

- **`RequirementState`** — `web/src/features/requirements/types/requirement.types.ts`
  ```ts
  export type RequirementState =
    'analisis' | 'planificacion' | 'en_cola' | 'desarrollo' | 'revision' | 'resuelto' | 'cancelado';
  ```
- **`RequirementFilters`** — mismo archivo. `state?: RequirementState | string | null` — **ya admite
  un string arbitrario**, así que el CSV entra sin cambiar el tipo.

**Precedente a replicar (no es reutilizable directo, es el patrón):**

`web/src/features/objectives/components/ObjectiveSearchFilters/ObjectiveSearchFilters.tsx` — el
filtro de estado del listado de tareas. Las tres piezas que esta story copia:

```tsx
// 1. Serialización de la selección: vacío → sentinel 'all'
if (Array.isArray(value)) {
  formattedValue = value.length === 0 ? 'all' : value.map((item) => item.value).join(',');
}

// 2. Derivación del valor seleccionado desde la URL, parseando el CSV
value={
  searchParams?.get('state') === 'all'
    ? []
    : searchParams?.get('state')?.split(',')
        .map((state) => ({ label: getStateLabel(state), value: state })) || [{ label: 'Activo', value: 'activo' }]
}

// 3. El default vive en la página de servidor
state: resolvedSearchParams.state || 'activo',   // objectives/page.tsx:25
```

**Diferencia arquitectónica que hay que respetar:** `ObjectiveSearchFilters` es dueño de la URL (usa
`useRouter`/`useSearchParams` directamente). **`RequirementFilters` NO**: recibe `filters` y un
callback `onChange(key, value)`, y quien escribe la URL es `RequirementList.updateFilter`. Esta
story **mantiene esa separación**: el filtro deriva su valor de la prop `filters.state` (no de
`useSearchParams`) y emite un string por `onChange`.

#### Estados aplicables

**default** — estado base, query resuelta con al menos un requisito.

**empty** — mensaje `"No se encontraron requisitos"`; `vacio-requisitos` visible como fila con
`colSpan={8}`; los pills ocultos; los encabezados de la tabla quedan visibles. Disparado por
`requirements.length === 0`.
**Alcanzable por una combinación de estados sin resultados.** Con el default de cuatro estados, un
listado que solo tenga requisitos en `analisis`, `resuelto` o `cancelado` abre vacío aunque existan
requisitos — el empty no lo explica, porque el mensaje es el mismo para "no hay nada" y "no hay nada
con estos filtros" [REQ-009 AC-13].

**loading** — `"Cargando..."` en el primer render (fallback del `<Suspense key>`) y
`"Cargando requisitos..."` en los refetch. Esta pantalla **sí usa `key` en el `<Suspense>`**
(`requirements/page.tsx:39`), así que al cambiar un filtro el fallback vuelve a aparecer.

**error de sistema** — No implementado (gap preexistente): `isError` se ignora y un fallo se ve como
el empty. **No se cierra en esta story.**

#### Interacciones (verbatim, las que esta story cambia)

- filtro-estado · on change → serializa la selección múltiple a lista separada por comas →
  `onChange('state', csv)` inmediato → `router.push`. **Con la selección vacía emite el sentinel
  `'all'`, que se escribe en la URL en vez de borrarse** [REQ-009 RF-6, RF-7, AC-4]
- `updateFilter` → borra `page` y hace `router.push` · `RequirementList.tsx:82-89`. **`state` es la
  excepción al borrado del sentinel:** los demás filtros siguen quitando el parámetro de la URL
  cuando el valor es vacío o `'all'`, pero `state=all` se conserva, porque una URL sin `state`
  significa el default de cuatro estados [REQ-009 RF-6, riesgo R1]

#### Accesibilidad de la pantalla (estado y gaps)

- **Orden de foco:** boton-nuevo-requisito → buscador-requisito → filtro-estado → filtro-proyecto →
  filtro-orden → paginacion → selector-tamano-pagina.
- **Gap que esta story roza y NO cierra:** los labels de los filtros son `<label className=...>` sin
  `htmlFor`. Con `InputMultipleSelect`, **el filtro de estado pasa a tener `htmlFor` propio** (el

#### Decisiones y descartes (de REQ-009, verbatim de la pantalla)

- **El filtro de estado pasa a selección múltiple, replicando el de `listado-tareas` en vez de
  inventar un mecanismo.**
- **El default es de cuatro estados y no "todos".** El listado abre en lo que se está haciendo; el
  histórico se pide explícitamente.
- **El default vive en el servidor de la página, no en el componente de filtros.** Así el primer
  render ya trae el recorte correcto y no hay parpadeo de "todos y después cuatro".
- **Deseleccionar todo muestra todo, y no vacía la tabla ni vuelve al default.** **Descartado**
  vaciar la tabla (leería como "no hay requisitos", que es falso) y **descartado** devolver al
  default de cuatro (haría imposible ver los siete estados juntos).
- **El sentinel `all` se conserva en la URL en vez de borrarse.**
- **La opción `"Todos los estados"` de valor `''` se elimina de la lista.** Mantenerla habilitaría el
  estado contradictorio de tener "todos" elegido junto a dos estados concretos.
- **La card de requisitos del detalle de proyecto no se toca.** Sigue con sus siete tabs.
- **`opus-web` no se modifica.**

#### Description

### Task 3: Conservar `state=all` en la URL (excepción al borrado del sentinel)

**Status:** Completed

#### Description

Este es **el punto de riesgo de la story** (riesgo R1 del diseño técnico).

`RequirementList.updateFilter` (`RequirementList.tsx:82-86`) hoy hace:

```tsx
if (!value || value === 'all') {
  params.delete(key as string);
} else {
  params.set(key as string, value);
}
```

Es decir, borra el parámetro cuando el valor es `'all'`. Con el default de la Tarea 1, borrar `state`
de la URL **significa volver a los cuatro estados por default**, que es exactamente lo que CA-4
prohíbe: deseleccionar todo tiene que mostrar los siete estados, no volver al default.

La solución es tratar `state` como excepción: **conservarlo en la URL como `state=all`**, mientras el
resto de los filtros mantiene el borrado actual. Es lo que ya hace el listado de tareas, que sí
escribe `state=all`.

Del otro lado del circuito no hay nada que hacer: `cleanFilters` en `requirementsApi.ts:17` **ya**
descarta el literal `'all'`, así que la request sale sin `state` y la api devuelve los siete estados.
**Ese archivo no se toca.**

#### Acceptance Criteria

1. `updateFilter('state', 'all')` produce una URL que **contiene** `state=all`.
2. `updateFilter('state', '<csv>')` produce una URL con ese CSV.
3. `updateFilter('projectId', 'all')` sigue **borrando** `projectId` de la URL.
4. `updateFilter('search', '')` sigue borrando `search` de la URL.
5. Cualquier cambio de filtro sigue borrando `page` (vuelta a la página 1).
6. Cambiar el filtro de estado no borra los demás parámetros de la URL.
7. `getRequirements({ state: 'all' })` emite una request **sin** el parámetro `state`.

#### Technical Details

**Architectural Context References:**

- Convención `state-management` → regla "El valor `'all'` **borra** el parámetro". **Esta tarea
  introduce la excepción documentada para `state` en esta ruta** — ver el recuadro de advertencia en
  el Architectural Context. Dejar un comentario en el código explicando por qué, para que no se
  "corrija" más adelante.
- Interacciones de la pantalla: "`state` es la excepción al borrado del sentinel: los demás filtros
  siguen quitando el parámetro de la URL cuando el valor es vacío o `'all'`, pero `state=all` se
  conserva".
- Reusable Code → `cleanFilters`: ya contempla `'all'`; **no modificar** `requirementsApi.ts`.

**Files to Create/Modify:**
