### Convenciones activas relevantes

#### `styling` — Sass + CSS Modules + custom properties

- **Un módulo por componente.** Nombre del módulo = nombre del componente. Las páginas usan
  `styles.module.scss` (sin prefijo) porque el archivo ya es `page.tsx`.
- **Clases en `camelCase`**, no `kebab-case`: CSS Modules las expone como propiedades de un objeto y
  `styles.buttonContainer` es válido mientras `styles.button-container` no.
- El módulo empieza con `@use '@/styles' as *;` cuando necesita mixins. Sin eso los `@include` no
  resuelven.
- **Composición de clases con `cn()`** (`src/shared/utils/cn.ts`), nunca template strings: el patrón
  `` `${styles.a} ${cond && styles.b}` `` escribe el string `"false"` en el `class` cuando la
  condición no se cumple. Acepta `{ clase: condición }`.
- **No hex literales: usar tokens.** No `@media` cruda: usar los mixins. No estilos inline salvo
  valores calculados en runtime (`style={{ width: \`${pct}%\` }}`).
- Los overrides de terceros van en `globals.scss`, no en un módulo (un módulo hashea la clase y no
  matchea lo que renderiza la librería).

> **La convención `styling.md` describe todavía la capa de tokens vieja** (`--color-button`
> `#DA2C6A`, `--radius-items`, tipografía Archivo). **S-052 ya la reemplazó en código** por la capa
> de tres tiers (`_reference.scss` / `_semantic.scss` / `_component.scss`). Al migrar se consume el
> tier semántico; el documento de convención queda desactualizado y su corrección es trabajo de
> `/product-change-technical-definition`, fuera de esta story.

#### `testing-unit` — Vitest + Testing Library

- Tests **junto al archivo que testean**, como `{Nombre}.test.tsx`. No hay carpeta `__tests__/`;
  `tests/` en la raíz tiene solo el setup.
- **Nombres de test en español**, describiendo comportamiento observable, no implementación.
- **`getByRole` con nombre accesible antes que clase o `data-testid`.** `userEvent` antes que
  `fireEvent`. `queryBy*` para aserciones de ausencia.
- Se mockea la **capa de servicios o de hooks**, nunca `fetch` ni `apiClient`.
- `next/navigation` (`useRouter`, `useSearchParams`) se mockea cuando el componente navega.
- Las páginas de servidor async se testean invocando el componente como función async y
  renderizando lo que devuelve.
- **`TZ: 'UTC'` no se toca.** Un alias nuevo en `tsconfig.json` hay que replicarlo en
  `vitest.config.mts`.
- Comandos: `npm test --workspace web`, `npm run lint --workspace web`.

> **Cobertura previa:** `features/clients` **no tiene ningún test**. `features/projects` y
> `features/objectives` sí tienen algunos. Los tests existentes en el alcance son
> `projects/new/page.test.tsx`, `projects/edit/[id]/page.test.tsx`, `projects/[id]/page.test.tsx`,
> `objectives/page.test.tsx`, `objectives/new/page.test.tsx`, `objectives/edit/[id]/page.test.tsx`,
> `objectives/by-project/page.test.tsx`, `objectives/by-responsible/page.test.tsx` y
> `ProjectActiveObjectives.test.tsx`. **Varios consultan por `<button>` crudo y van a romperse con
> la migración** — actualizarlos es parte del trabajo, no un daño colateral.

#### `data-fetching` / `mutations` / `state-management`

**No cambian.** La story es visual: Server Action → axios → TanStack Query queda intacto, y la
mecánica de cada formulario se preserva. El REQ deja explícitamente fuera de alcance la decisión de
unificar formularios (`react-hook-form`/yup vs `useState`).

#### `forms`

Tres enfoques conviven. **Esta story no elige uno**: migra el aspecto visual conservando la mecánica
de submit de cada formulario tal como está.

#### Componentes del DS a usar — API real en código

**`Button`** — `web/src/shared/components/ui/Button/Button.tsx`

```tsx
type ButtonVariant = 'primary' | 'secondary-nav' | 'secondary-dismiss' | 'session' | 'flow';

interface ButtonProps {
  readonly children?: React.ReactNode;   // label — NO hay prop `label`
  readonly variant?: ButtonVariant;      // default 'primary'
  readonly disabled?: boolean;
  readonly loading?: boolean;            // reemplaza el label por <Loader inline/>, aria-busy
  readonly icon?: string;
  readonly iconTrailing?: boolean;
  readonly onClick?: MouseEventHandler<HTMLButtonElement>;
  readonly href?: string;                // extensión local: navega con useRouter().push
  readonly ariaDescribedBy?: string;
  readonly fab?: boolean;                // requiere 'aria-label'
}
```

> **`Button` NO tiene prop `type`.** Nunca es un submit nativo. Es la razón de CA-3: cada botón
> dentro de un `<form>` hay que verificarlo antes de migrarlo.
> **`size` no existe** — el caso de `size="small"` se resuelve con `Badge` o pill.

Clasificación semántica de variants (la distinción **no es decorativa**):

| Variant | Cuándo | Ejemplo en el alcance |
|---|---|---|
| `primary` | Acción principal de la vista | «Nuevo proyecto», «Guardar» |
| `secondary-nav` | **Navega** — borde verde agua | «Volver» |
| `secondary-dismiss` | **Descarta** — borde claro | «Cancelar», «Borrar propiedad» |
| `session` | Entrada/salida de sesión | *(no aplica en este alcance)* |
| `flow` | Avance de estado de flujo, icono → | *(no aplica en este alcance)* |

> **No hay variant `destructive`, y es una decisión tomada.** El rojo `#F72C25` está reservado a
> estados de vencimiento, no a acciones. Un borrado se confirma con `ConfirmDialog`, donde **ambas
> acciones van como `secondary-dismiss`** y la advertencia la carga el texto.
> **Un solo botón primario por vista.**

**`Input`** — cinco variants sobre una caja de 44 px / radio 10 px

```tsx
type InputVariant = 'text' | 'textarea' | 'date' | 'search' | 'locked';

interface InputProps {
  readonly variant?: InputVariant;
  readonly label: string;         // requerido — no hay campos solo-placeholder
  readonly required?: boolean;
  readonly placeholder?: string;
  readonly error?: string;        // STRING, no boolean: su presencia pinta el error y alimenta aria-describedby
  readonly disabled?: boolean;
  readonly icon?: string;
  readonly value: string;
  readonly onChange: (value: string) => void;
}
```

`date` y `search` traen su propio icono inline (calendario / lupa). `locked` renderiza `readOnly`
sobre niebla, sin anillo de foco. Los ids se generan con `useId()`.
**`date-picker` y `search-bar` no son componentes propios: son `Input` variant `date` / `search`.**

**`Select`** — el selector único; combobox propio, **sin `react-select`**

```tsx
interface SelectOption { readonly value: string; readonly label: string; }

interface SelectSingleProps {                 // single | locked | inline
  readonly variant?: 'single' | 'locked' | 'inline';
  readonly value: string;
  readonly onChange: (value: string) => void;
}
interface SelectMultipleProps {
  readonly variant: 'multiple';
  readonly value: string[];
  readonly onChange: (value: string[]) => void;
}
type SelectProps = (SelectSingleProps | SelectMultipleProps) & {
  readonly label?: string;        // requerido salvo en `inline`
  readonly options: SelectOption[];
  readonly placeholder?: string;
  readonly required?: boolean;
  readonly error?: string;
  readonly disabled?: boolean;
};
```

`multiple` renderiza el trigger como `<div role="combobox" tabIndex={0}>` (hospeda un `<button>` por
chip y un `<button>` no puede anidar contenido interactivo); el resto renderiza `<button
role="combobox">`. Cada chip expone `aria-label="Quitar {label}"`.

> **NO SE DEBE usar `react-select` con estilos propios.** El `selectStyles` duplicado es la razón
> por la que este spec existe.

**`Card`** — contenedor único, radio 14 px, fluido

```tsx
type CardVariant = 'project' | 'task' | 'task-overdue' | 'panel' | 'metric';

interface CardProps {
  readonly variant?: CardVariant;              // default 'panel'
  readonly title?: string;
  readonly href?: string;                      // su presencia hace la card navegable
  readonly status?: { family: BadgeFamily; label: string };
  readonly tags?: { label: string; family?: BadgeFamily }[];
  readonly metrics?: { label: string; value: string; overdue?: boolean }[];
  readonly headingLevel?: 'h2' | 'h3' | 'h4';  // default 'h3' — nunca hardcodear
  readonly children?: React.ReactNode;         // slot de contenido de `panel`
  readonly header?: React.ReactNode;
  readonly footer?: React.ReactNode;
}
```

Una card navegable expone **exactamente un** destino accesible: el título como heading envolviendo
un `<Link>`, expandido a toda la superficie con `::after`. **NO SE DEBEN anidar controles dentro de
un contenedor clickeable.** El ancho y la igualación de alto por fila son trabajo de la grilla que
la contiene, no de la card. El pie se tiñe **sólo** cuando está vencida.

**`Table`** — tabla única, `<table>` real, fila de 48 px

```tsx
interface TableColumn { key: string; label: string; sortable?: boolean; scope?: 'row'; }
interface TableSort { key: string; direction: 'asc' | 'desc'; }
interface TableRow { [key: string]: React.ReactNode; _overdue?: readonly string[]; }
interface TableProps {
  readonly variant?: 'light' | 'dense' | 'matrix';   // default 'light'
  readonly columns: readonly TableColumn[];
  readonly rows: readonly TableRow[];
  readonly sort?: TableSort;
  readonly onSortChange?: (sort: TableSort) => void;
  readonly emptyState?: React.ReactNode;
  readonly loading?: boolean;
  readonly ariaLabel?: string;
}
```

Densidades: `light` (cabecera niebla — **listados navegables**), `dense` (cabecera azul oscuro —
**tablas densas de seguimiento**), `matrix` (cruce de dos dimensiones). La elección no es estética:
la cabecera oscura señala que la tabla es para mirar mucho de un vistazo, no para navegar.
**DEBE** usarse `<table>` real con `<th scope="col">`; una grilla de `div`s no expone la relación
fila–columna. **NO SE DEBE teñir la fila completa** con un color de sistema: el estado va en badge.

> El catálogo de código reusable dice explícitamente: «Nine ad-hoc `<table>` implementations existed
> in the product before this component — none of them are migrated to `Table` yet; that is the job of
> stories S-056 to S-058.»

**`Badge`** — pill de estado/etiqueta

```tsx
type BadgeVariant = 'state' | 'outline' | 'area' | 'editable' | 'card-tag';
type BadgeFamily = 'resolved' | 'in-progress' | 'review' | 'urgent' | 'analysis' | 'neutral';

// presentacional: variant?: Exclude<BadgeVariant,'editable'>; family?; label (requerido)
// editable:       variant: 'editable'; family?; label; options: BadgeOption[]; onChange
declare const STATE_TO_FAMILY: Record<string, BadgeFamily>;
```

**El componente recibe una `family`, nunca un string de estado de dominio.** `STATE_TO_FAMILY` se
exporta junto a `Badge` y es la tabla de mapeo del spec: **reusarla, no reimplementarla.** El color
va en el punto y en el borde; el punto es `aria-hidden` y **nunca porta el estado solo**.

Mapeo estado → familia: Planificación `analysis` · En cola `neutral` · Desarrollo `in-progress` ·
Revisión `review` · Resuelto `resolved` · Cancelado `neutral`.
Prioridad: Alta `urgent` · Media `review` · Baja `neutral` · Sin prioridad `neutral` (tinte grafito).

> **«En curso» en una tarjeta usa verde agua pleno**, porque marca el elemento activo de interfaz.
> **Los estados en tabla y listado usan `#1B998B`**, no verde agua.

**`Loader`** — indicador único (absorbió `Loader` + `Spinner`)

```tsx
interface LoaderProps {
  readonly variant?: 'block' | 'inline';  // default 'block'
  readonly size?: 'md' | 'sm';
  readonly label?: string;                // default 'Cargando…'
}
```

`block` ocupa el lugar del contenido y muestra label; `inline` acompaña contenido ya en pantalla, sin
label visible. `role="status"` + `aria-live="polite"` siempre. **Es retrocompatible** con el
`<Loader label="..." />` viejo.

**`Pagination`** — dos modos, nunca se oculta

```tsx
type PaginationProps =
  | { totalItems: number; limit: number; basePath: string;      pageSizeOptions?; onPageSizeChange? }
  | { totalItems: number; limit: number; currentPage: number; onPageChange: (p:number)=>void; pageSizeOptions?; onPageSizeChange? };
```

**Nunca hardcodea una ruta** (era el bug de S-037). Con una sola página o 0 ítems **igual renderiza**
el `<nav>` con las flechas genuinamente `disabled`. La divergencia spec/implementación
(`totalItems`/`limit` en vez de `page`/`totalPages`) **se mantiene a propósito**, y migrar a la API
del spec pertenece explícitamente a S-056–S-058 — **pero esta story no la cambia**: usar
`totalItems`/`limit`, que es lo que el componente expone hoy.

**`Tabs`** — tablist ARIA completo con roving tabindex

```tsx
interface TabItem { key: string; label: string; count: number; }
interface TabsProps { tabs: readonly TabItem[]; activeKey: string; onChange: (k:string)=>void; children?; }
```

**Una tab con count 0 nunca se oculta ni se deshabilita** — es información.

**`EmptyState`**

```tsx
interface EmptyStateProps {
  readonly variant?: 'list' | 'filtered' | 'scoped';  // default 'list'
  readonly message: string;
  readonly action?: ButtonProps;                       // sólo se renderiza en `list`
}
```

`list` invita a crear; `filtered` invita a **cambiar el filtro**, nunca a crear. `filtered` lleva
`aria-live="polite"`; el componente **nunca** usa `role="alert"` porque la ausencia de datos no es un
error.

**`ViewHeader`**

```tsx
interface ViewHeaderProps {
  readonly variant?: 'list' | 'breadcrumb' | 'detail';
  readonly title: string;
  readonly parent?: { label: string; href: string };
  readonly badges?: readonly { variant?: BadgeVariant; family?: BadgeFamily; label: string }[];
  readonly action?: Pick<ButtonProps,'children'|'onClick'|'variant'|'disabled'|'loading'>;
}
```

El título es siempre el `<h1>` real de la vista, nunca un `<div>` estilado. En `breadcrumb` el nivel
actual va **en caja baja** con `aria-current="page"`. `action` renderiza **exactamente un** `Button`.

**`Tooltip`** — `content` / `placement` / `delay`; aparece en **hover y foco de teclado**, cierra con
`Esc` sin mover el foco.

**`ConfirmDialog`** — ambas acciones como `secondary-dismiss` (sin primario, sin rojo); la
advertencia vive en el texto. `<dialog>` nativo, foco inicial en Cancelar.

#### Accesibilidad

`docs/design-system/web/guidelines/accessibility.md` está **en estado `placeholder` (v0.1.0)** — es

y son las que aplican:

- Texto sobre fondo ≥ 4.5:1; texto grande ≥ 3:1; bordes interactivos ≥ 3:1.
- **No comunicar estado sólo con color:** los estados combinan punto de color + texto.
- Foco visible: `0 0 0 3px rgba(97,204,185,.22)`. **NO SE DEBE** suprimir con `outline: none` sin
  reemplazo.

### Task 1: Auditoría de botones y clasificación de variants

**Status:** Completed

#### Description

Antes de tocar una sola pantalla, producir la tabla de clasificación de **los 31 `<button>` crudos**
y de todos los usos de `Button` ya existentes en el alcance, asignando a cada uno su variant
semántico y registrando si vive dentro de un `<form>`.

Esto es CA-3 en su forma literal: «se verificó cada uso dentro de un `<form>` antes de migrarlo, dado
que el `Button` nuevo no tiene prop `type`». Hacerlo como tarea propia y primera evita el modo de
falla real de esta migración: reemplazar botón por botón mientras se está pensando en colores, y
romper un submit sin notarlo hasta que alguien no puede guardar un proyecto.

El relevamiento inicial ya encontró que **ningún submit del alcance depende del `type="submit"`
implícito** — los cuatro `<form onSubmit>` tienen sus botones de guardado fuera del form, con
`type="button"` y `onClick` explícito. **Esta tarea lo verifica archivo por archivo en vez de
asumirlo**, y deja el resultado escrito para que las tareas 2 a 7 lo apliquen sin volver a razonarlo.

#### Acceptance Criteria

1. Existe una tabla que cubre los 31 `<button>` crudos del alcance, con: archivo, línea, texto o
   propósito del botón, variant asignada, y si está dentro de un `<form>`.
2. Cada botón queda clasificado en exactamente una de: `primary`, `secondary-nav`,
   `secondary-dismiss`, o `fab`. Ningún botón queda como «a decidir».
3. La tabla registra, para cada uno de los 4 `<form onSubmit>` del alcance, cuál es su mecanismo de
   envío real y qué botón lo dispara.
4. Los usos de `Button` ya existentes (`objectives/new`, `objectives/edit/[id]`, y los que haya en
   `features/`) quedan revisados: los que usen una variant que no corresponda a su intención se
   listan para corrección.
5. Se identifica, por pantalla, cuál es **el único** botón `primary` — el DS prohíbe apilar dos
   primarios en una misma vista.
6. La tabla se deja en el propio Story Plan o en un archivo de trabajo referenciado, disponible para
   las tareas siguientes.
7. Los `<button>` que pertenecen a los **seis componentes muertos** quedan marcados como «se borra,
   no se migra» y no consumen tiempo de clasificación semántica.
8. Se confirma, con `grep` del identificador excluyendo su propia carpeta y los `*.test.tsx`, que los
   seis componentes listados como muertos efectivamente no tienen consumidor.
