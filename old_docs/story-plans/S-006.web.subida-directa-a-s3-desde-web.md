# Story Plan: S-006 (web) - Subida directa a S3 desde `web`

## Status

**Status:** Completed

**Progress:** 8/8 tareas completadas

## Story Reference

- **Story:** [S-006](../stories/S-006.subida-directa-a-s3-desde-web.md)
- **Service:** `web`
- **Summary:** El navegador deja de mandar el binario al BFF: pide un ticket a `POST /api/attachments`
  (contra la `api`, vía Server Action), hace el `PUT` **directo a la URL prefirmada de S3** con
  `XMLHttpRequest` y progreso real, de a un archivo por vez. Se elimina el route handler
  `POST /api/attachments` del BFF y `bodySizeLimit`; los handlers de `/preview` y `/download` pasan a
  propagar el 302 en lugar de proxear el binario. Los formularios pasan `fileIds` en lugar de
  `attachmentIds`.

**Forma interna de un módulo de dominio:** `components/`, `hooks/`, `services/`, `types/` y, cuando
hace falta, `utils/`. El barrel `index.ts` es la superficie pública; las rutas importan de ahí.

**La regla central del servicio: el access token nunca llega al navegador.** Los
`services/*Api.ts` llevan `'use server'` y el interceptor de `apiClient` llama a `auth()`, que solo
corre en el servidor. **`API_URL` es variable de servidor, no `NEXT_PUBLIC_*`.**

> **Esta story introduce la única excepción declarada a esa regla, y es deliberada** (ADR-009, D-23):
> la **URL prefirmada de S3 sí llega al navegador**, porque el `PUT` lo hace el navegador. Llega **por
> la respuesta de la api**, nunca por `NEXT_PUBLIC_*`: la topología del bucket no entra al bundle y el
> access token sigue confinado al servidor.

### Relevant ADRs

#### ADR-009: Token confinado al servidor

- **Decisión:** el access token de Zitadel nunca llega al navegador. Todo el tráfico de datos sale del
  proceso de Next.js; el navegador solo tiene la cookie de sesión de NextAuth.
- **Implementation Rules:**
  - Los `services/*Api.ts` llevan `'use server'`. `apiClient` **no se importa jamás desde un componente
    cliente**: `auth()` no corre ahí.
  - `API_URL` se lee en runtime como variable de servidor. **No** usar prefijo `NEXT_PUBLIC_`.
  - Un route handler del BFF que hable con la api resuelve el token con `decodedToken()` y lo pasa a
    mano como `Bearer`. **No** devuelve el token ni ninguna parte de él en la respuesta.
- **Excepción que esta story ejerce:** la `uploadUrl` prefirmada viaja al navegador en el cuerpo del
  `UploadTicket`. Es una URL de un solo objeto y TTL corto (300 s por default), firmada por `core`. No
  es una credencial reutilizable ni revela la topología interna del bucket al bundle.

#### ADR-001: Separación lectura/escritura

- **Decisión:** la `api` lee de la base y publica comandos al bus para escribir; `core` escribe. El
  storage entra al alcance del ADR con REQ-001: **la `api` pierde las credenciales de S3**.
- **Consecuencia para `web`:** el binario ya no atraviesa ningún servicio del producto. Sube del
  navegador a S3 y baja de S3 al navegador. `web` deja de ser un proxy de bytes.

#### ADR-011: TanStack Query

- **Decisión:** TanStack Query es el único cache de datos de servidor. La invalidación es **explícita
  y por query key**, no por tag de Next.
- **Implementation Rules:**
  - Invalidar en el `onSuccess` **del hook**, no en el componente.
  - Invalidar la colección (prefijo plural) y, si aplica, `[recurso, id]`.
  - **No** usar `revalidatePath` / `revalidateTag`: no hay ningún uso en el servicio.
  - **No** poner `retry` en una mutación. El default es `0` a propósito: reintentar una escritura que
    ya pudo aplicarse duplica registros.
  - **No** copiar datos de query a `useState`.

#### ADR-010: Sass + CSS Modules sin librería

- **Decisión:** un módulo `.scss` por componente, junto al `.tsx`. Tokens como custom properties.
- **Implementation Rules:**
  - Clases en `camelCase` (CSS Modules las expone como propiedades).
  - `@use '@/styles' as *;` al inicio del módulo cuando se necesitan mixins.
  - **Usar el token, nunca el hex literal.**
  - **No** `@media` cruda: usar los mixins de `_mixins.scss`.
  - **No** template strings para clases condicionales: usar `cn()` de `@/shared/utils`.
  - Estilos inline **solo** para valores calculados en runtime — la barra de progreso
    (`style={{ width: \`${pct}%\` }}`) es el caso legítimo y el que esta story usa.

### API Context

Todo el contrato del lado del servidor ya está cerrado por S-004 y S-005. **Esta story no cambia
ningún endpoint: cambia quién los consume y cómo.**

#### `POST /api/attachments` — pedir permiso de subida (contra la `api`)

**Ya NO recibe el binario.** Content-Type `application/json`. **Un archivo por request** (D-07): tres
archivos son tres requests independientes, y el fallo de uno no arrastra a los otros.

**Request body:**
```json
{
  "fileName": "informe.pdf",
  "mimeType": "application/pdf",
  "fileSize": 4194304,
  "checksum": null
}
```

| Campo | Tipo | Requerido | Notas |
|---|---|---|---|
| `fileName` | string, maxLength 255 | Sí | Nombre original |
| `mimeType` | string, maxLength 100 | Sí | |
| `fileSize` | integer, minimum 1 | Sí | |
| `checksum` | string \| null | No | sha256 declarado por el cliente. **Nadie lo verifica** (D-25) |

**Campos ELIMINADOS del contrato:** `files` (el binario, D-09), `entityType` (D-12), `entityId`,
`description`. **Subir no menciona la entidad.**

**Autorización:** solo el JWT. `canUserAccessEntity` deja de aplicar porque no hay entidad; el control
por entidad se corre al momento de vincular.

**Response `201` (`UploadTicket`):**
```json
{
  "fileId": 1234,
  "uploadUrl": "https://bucket.example/grava-gestion/f/9c1e.../abcd.pdf?X-Amz-...",
  "expiresIn": 300
}
```

| Campo | Tipo | Notas |
|---|---|---|
| `fileId` | integer | Id de `files`. **Es lo que viaja en `fileIds`** al guardar la entidad |
| `uploadUrl` | string | URL prefirmada de **PUT**, de un solo objeto y TTL corto |
| `expiresIn` | integer | Segundos de validez, leídos de `system_settings` |

> **Lo que se pierde respecto de hoy: el `Attachment` completo.** Hoy la respuesta trae `fileName`,
> `fileSize` y `mimeType`, que el frontend usa para el preview embebido. **No se pierde nada**: esos
> tres valores salen del objeto `File` del input del navegador, o sea que se tienen **antes** de
> llamar. Lo único que hace falta de vuelta es el `fileId` y la URL.

**Errores:**

| Status | `code` | Cuándo |
|---|---|---|
| 400 | `file_type_not_allowed` | Extensión o MIME fuera de la allowlist de `core` |
| 400 | `file_too_large` | Supera `file-max-size-bytes` de `system_settings` |
| 400 | `invalid_fields` | Joi corta la forma del body antes de publicar |
| 401 | — | Sin JWT válido |
| 503 | `bus_unavailable` | Timeout del bus (5 s) |

#### `PUT {uploadUrl}` — el byte, directo a S3

- **Método:** PUT · **Endpoint:** la `uploadUrl` del ticket, tal cual · **Body:** el binario crudo
- **No lleva `Authorization`**: la autorización va firmada en la query string de la URL
- Se hace con `XMLHttpRequest` para tener `upload.onprogress`. **`fetch` no da progreso de subida**
- **No pasa por la `api`, ni por el BFF, ni por el bus**
- Respuesta de éxito: `200` de S3, sin cuerpo útil
- **Precondición de infraestructura (S-008):** CORS en el bucket acotado al origen del frontend, y una
  URL del bucket alcanzable desde el navegador. **Sin CORS el síntoma es un error de red opaco que no
  señala la causa** — si aparece un fallo de red inexplicable al probar, es lo primero a verificar

**Errores del `PUT`:**

| Condición | Qué llega | Qué hace el front |
|---|---|---|
| URL vencida | `403` de S3 | Falla visible + el usuario **puede pedir un ticket nuevo** (CA-11) |
| Falla de red / CORS | `error` del XHR, sin status | Error de subida en el bloque de progreso, con reintento |
| Falla en silencio | — | **No hay compensación.** La fila de `files` queda `byte_status: 'pending'` y el error se descubre al leer (`file_not_available`) |

#### `GET /api/attachments/{id}/preview` y `/download` (de la `api`) — ahora **302**

**Responden `302` con `Location` a la prefirmada de `GetObject`, no el binario.** El
`Content-Disposition` con el nombre original viaja **firmado en la URL**.

- `Content-Type` y `Content-Disposition` van en el `GET` **y** en el `HEAD`
- **`Content-Length` va SOLO en el `HEAD`**: en un `GET` prometería un cuerpo que un 302 no tiene, y el
  cliente se quedaría esperando bytes que no llegan
- Errores: `401`, `403`, `404` (`not_found` | `file_not_found` | `file_not_available`), `500`, `503`

#### `GET /api/files/{id}/preview` — preview de archivo **SIN vínculo** (camino nuevo, S-005)

- Recibe **`fileId`** (id de `files`), **no** el id del vínculo. Ruta propia a propósito: dos espacios
  de identificadores distintos merecen dos rutas distintas
- **Autorización: solo el JWT.** Sin vínculo no hay entidad contra la que validar permiso de proyecto
- Responde igual: **302** a la prefirmada
- **No existe `/api/files/{id}/download`.** La descarga siempre ocurre sobre un adjunto ya vinculado
- **Es el camino que hace posible CA-7:** previsualizar lo recién subido, antes de guardar la entidad

#### Endpoints de dominio: `fileIds` reemplaza a `attachmentIds`

`fileIds` aparece en el body de:

| Endpoint | Método |
|---|---|
| `/api/requirements` | POST |
| `/api/requirements/{reqid}` | PATCH |
| `/api/requirements/{reqid}/comments` | POST |
| `/api/objectives/{id}/comments` | POST |

**Schema `FileIds`:**
```yaml
type: array
maxItems: 10
items: { type: integer, minimum: 1 }
```

- Ids de **`files`**, no de `attachments`. **Reemplaza a `attachmentIds`**
- Cada uno tiene que existir, estar vivo, y **haber sido subido por el actor de este comando** (RF-12).
  Si alguno no cumple → **403 `file_not_owned`**, y se descarta toda la escritura: ni la entidad ni un
  solo vínculo. **Los `files` sí sobreviven, sin vínculo, que es un estado válido**
- **La titularidad no tiene excepción por rol** (RF-13): un `admin` tampoco puede vincular un archivo
  que no subió
- El tope de **10 es regla fija, no configurable** (D-20)
- **`attachmentScope` desaparece** del contrato

**Códigos de error de dominio que el front tiene que distinguir:**

| `code` | Status | Mensaje al usuario |
|---|---|---|
| `file_not_owned` | 403 | `"No podés adjuntar un archivo que subió otra persona"` |
| `file_not_available` | 404 | `"El archivo no está disponible"` |
| `file_too_large` | 400 | `"El archivo supera el tamaño máximo permitido"` |
| `file_type_not_allowed` | 400 | `"Ese tipo de archivo no está permitido"` |

> **El error llega normalizado como `ApiError` (`{ code, message, status }`)** cuando pasa por
> `apiClient`, o como `Error` cuando viene de un `ClientApi`. Por eso el `onError` de los componentes
> hace un cast defensivo.

### Flow Context

#### Flujo `subida-de-archivos` — el plano del byte para `web`

Los pasos que esta story implementa, copiados del flujo:

**Paso 1 — Validación en el cliente (conveniencia).** El frontend valida tipo y tamaño **antes** de
pedir el ticket, para fallar rápido. **Dejó de ser autoritativa:** la fuente de verdad es `core`, que
lee la política de `system_settings` **en caliente**. Por eso el microcopy **no puede** nombrar los
límites — cambian por SQL sin redespliegue (CA-12).

**Paso 2 — El cliente pide permiso.** `POST /api/attachments` con JSON, **un request por archivo**.

**Paso 6 — La api traduce el reply:** `201 UploadTicket { fileId, uploadUrl, expiresIn }`.

**Paso 7 — El byte va directo a S3.** `PUT {uploadUrl}` con `XMLHttpRequest`. **No pasa por la `api`
ni por el bus.**

> **El progreso que se muestra es el del `PUT`, no la confirmación de que el byte llegó y quedó
> íntegro.** El sistema **no verifica el byte** (D-13): `byte_status` sigue en `'pending'` hasta que el
> vínculo lo pase a `'uploaded'`. **Por eso la UI bloquea el envío mientras la subida está en curso**
> (CA-14): vincular un archivo incompleto crea un adjunto ilegible que el usuario descubre después.

**Paso 8 — Vista previa antes de guardar (opcional).** Entre el `PUT` y el guardado, el usuario puede
previsualizar lo que subió. Todavía no hay vínculo, así que la lectura entra **por `fileId`**:
`GET /api/files/{fileId}/preview`.

**Paso 9 — El vínculo.** Al guardar, el cliente manda `fileIds: [1234, 1235, 1236]`. Ahí `core` valida
titularidad, hace `UPDATE files SET byte_status = 'uploaded'` y crea las filas de `attachments`.

> **El rollback de S3 desapareció y no se reemplaza.** Hoy la `api` borra del bucket lo ya subido si un
> lote falla a mitad. Con el byte directo a S3 ese rollback **no puede existir**: quien escribe el
> objeto es el navegador. Está en Riesgos Asumidos del REQ. **No inventar una compensación en el
> frontend.**

#### Flujo `lectura-de-archivos` — los dos route handlers que se mantienen

Los handlers de `web` existen porque **el navegador no puede mandar el `Authorization` cuando la URL va
en un `src`/`href`**, y esa razón no cambia. Lo que cambia es que **ya no proxean el binario**: lo que
reciben de la `api` es un **302**, así que **dejan de propagar `Content-Length`** y solo siguen la
redirección o la devuelven al navegador.

Camino completo hoy (post S-005):

1. navegador → `web` `GET /api/attachments/{id}/preview` (sin `Authorization`)
2. `web` → `api`, con el Bearer de la sesión
3. `api` autoriza (`canUserViewEntity`), resuelve el `file_id`, publica `files.{file_id}.request-download`
4. `core` valida `retention_status` y `byte_status`, firma `GetObject`
5. `api` responde **302** `Location: {downloadUrl}` + `nosniff`
6. navegador → S3, directo

> **El `HEAD` al preview sigue funcionando, pero por otro mecanismo.** Los metadatos vienen en el reply
> del comando en vez de leerse del stream. `useAttachmentMeta` hace `HEAD` sobre el handler del BFF
> para resolver nombre, tamaño y mime — **hay que verificar que ese `HEAD` siga devolviendo
> `Content-Type`, `Content-Disposition` y `Content-Length`** al atravesar el handler nuevo. Es el
> riesgo concreto de esta story en el lado de lectura, y se descubre en runtime porque los tipos de
> `web` están escritos a mano.

#### Flujo `adjuntos` (el viejo) — qué queda y qué se va

- Su **paso 1** (validación en el cliente) se conserva **como conveniencia**, no como autoridad
- Su **paso 2** (subida multipart a la api) **queda eliminado**

### Database Context

**Ninguno.** `web` no accede a base de datos. Los conceptos que importan son de contrato:

| Concepto | Qué es | Espacio de ids |
|---|---|---|
| `File` | El archivo. Existe por sí solo. `byte_status: pending \| uploaded` | `files.id` → **`fileId`** |
| `Attachment` | El **vínculo** entre un `File` y una entidad | `attachments.id` |

**Un archivo sin vínculo es un estado válido** (RF-1, CA-7). **El borrador desapareció del modelo**:
ya no hay `requirement_draft`, `comment_draft`, `objective_comment_draft` ni
`requirement_comment_draft`.

> **Los dos espacios de ids conviven en el frontend y no se pueden confundir.** El markdown embebido
> usa `[attach:N]` con id de **vínculo** para lo ya guardado, y necesita id de **archivo** para lo
> recién subido. Es la decisión de diseño más delicada de esta story y está resuelta en la Tarea 5.

### Integration Points

- **`api`** — vía Server Action (`apiClient`, con Bearer inyectado por el interceptor) para el ticket y
  los guardados de dominio; vía route handler del BFF (con `fetch` nativo y Bearer a mano) para
  preview y download.
- **Storage S3-compatible** — **directo desde el navegador**, sin ninguna credencial propia: la
  autorización va firmada en la query string de la `uploadUrl`. Requiere CORS en el bucket (S-008).
- **Bus NATS** — `web` no lo toca. Nunca.

### Code Conventions

**Route handlers del BFF** (`conventions/api-routes.md`):

- El criterio: un handler se justifica solo si **el navegador tiene que iniciar la llamada** y una
  Server Action no sirve. **Con el byte directo a S3, `POST /api/attachments` deja de cumplirlo** — su
  única justificación era el progreso incremental (CA-3).
- Preámbulo obligatorio, idéntico en todos:
  ```ts
  const token = await decodedToken();
  if (!token?.accessToken) {
    return NextResponse.json({ error: 'Unauthorized' }, { status: 401 });
  }
  ```
  `decodedToken()` de `@/shared/utils/decoded-token`, **no** `auth()` directo. El cuerpo del 401 es
  `{ error: 'Unauthorized' }` y no filtra el motivo.
- La URL se arma como `` `${process.env.API_URL}api/...` `` — **sin `/` entre medio**, porque
  `API_URL` termina en `/` en el deploy. Es la asimetría con `lib/axios.ts`, que sí normaliza el
  trailing slash.
- `fetch` nativo, **no** `apiClient`: el token ya se tiene y se pasa a mano.
- Params dinámicos son promesa en Next 15+: tipar `Promise<{ id: string }>` y hacer `await`.
- El `.catch()` en el parseo del error del upstream es obligatorio: sin él, un 502 con HTML hace que el
  handler responda 500 en lugar del status real.

**Nombres de archivos de servicio:**
```
features/attachments/services/
├── attachmentsApi.ts         'use server'  → apiClient → api
└── attachmentsClientApi.ts   navegador     → fetch / XHR contra rutas relativas
```
El `ClientApi` **no** lleva `'use server'` y **no** importa `apiClient`.

**Mutaciones** (`conventions/mutations.md`): un hook por operación en
`features/{módulo}/hooks/use{Verbo}{Recurso}.ts`, invalidación en el `onSuccess` del hook, toasts y
navegación en el componente.

**Formularios** (`conventions/forms.md`): enfoque 2 — `useState` + yup con errores por campo, schema a
nivel de módulo, `abortEarly: false`, `transformYupErrors`.

**Mensajes de error establecidos:** `"Hubo un error al {infinitivo}"`. De éxito:
`"{Entidad} {participio} con éxito"`. El mensaje **prioriza el de la api** (`err.message`) y cae a un
texto propio en español. **Nunca** se muestra un error crudo.

**Tests** (`conventions/testing-unit.md`):

- Junto al archivo que testean, como `{Nombre}.test.tsx`. **No hay carpeta `__tests__/`**
- Nombres de test **en español**, describiendo comportamiento observable
- `getByRole` antes que clase o `data-testid`; `userEvent` antes que `fireEvent`;
  `queryBy*` para ausencia
- **Mockear la capa de servicios o de hooks, NO `fetch` ni `apiClient`**
- `TZ: 'UTC'` no se toca

### Task 2: El `PUT` directo a S3 con progreso real

**Status:** Completed

#### Description

Reescribir `attachmentsClientApi.ts` para que el binario viaje **del navegador a la URL prefirmada de
S3**, con `XMLHttpRequest` y progreso real, y componer el flujo completo de un archivo:
**ticket → `PUT` → `fileId`**.

Es el corazón de la story: es lo que hace que el byte deje de atravesar el BFF y que el porcentaje
que ve el usuario sea el de la transferencia real y no el de una request cuyo final solo se sabe
cuando llega.

Por qué es necesaria: CA-1 y CA-11.

#### Acceptance Criteria

1. Existe `putFileToStorage({ uploadUrl, file, onProgress, signal? }): Promise<void>` que hace
   `xhr.open('PUT', uploadUrl)` y `xhr.send(file)`.
2. **No** setea el header `Authorization`. **No** usa `FormData`. **No** apunta a ninguna ruta
   relativa `/api/...`.
3. `onProgress` recibe un entero 0-100 calculado como
   `Math.round((event.loaded * 100) / event.total)`, solo cuando `event.lengthComputable`.
4. Un status fuera de `2xx` rechaza con un `Error` de mensaje legible en español; el `403` (URL
   vencida) se distingue para que el consumidor pueda ofrecer reintento.
5. El evento `error` del XHR rechaza con `Error('Error de red al subir el archivo')`.
6. Existe `uploadFile(file, { onProgress }): Promise<number>` que compone
   `requestUploadTicket` → `putFileToStorage` y resuelve con el `fileId`.
7. `uploadAttachments` (la función vieja, con `FormData` contra `/api/attachments`) **queda
   eliminada**.
8. `getPreviewUrl` y `getDownloadUrl` se mantienen; se agrega `getFilePreviewUrl(fileId)` que devuelve
   `/api/files/{fileId}/preview`.

#### Technical Details

**Architectural Context References:**

- Seguir **API Context → `PUT {uploadUrl}`**: sin `Authorization`, body = el binario crudo, `XHR` para
  tener `upload.onprogress` (**`fetch` no da progreso de subida** — es la razón técnica de usar XHR y
  no hay alternativa).
- Seguir **Flow Context → paso 7**: el byte no pasa por la `api` ni por el BFF ni por el bus.
- Seguir **Code Conventions**: `attachmentsClientApi.ts` **no** lleva `'use server'` y **no** importa
  `apiClient`.
- **Precondición de infraestructura (S-008):** sin CORS en el bucket el `PUT` falla con un error de red
  opaco. Si aparece un fallo inexplicable al probar, es lo primero a verificar — **no es un bug del
  código**.
- **Reusable Code:** el bloque de `XMLHttpRequest` con `upload.addEventListener('progress', ...)` ya
  existe en `uploadAttachments` y es exactamente el patrón a conservar; lo que cambia es el destino, el
  método y el body.

**Files to Create/Modify:**

- `src/features/attachments/services/attachmentsClientApi.ts` — reescribir
- `src/features/attachments/services/attachmentsClientApi.test.ts` — crear

**Implementation Notes:**

- **`uploadFile` es una Server Action llamando desde el cliente para el ticket, y XHR crudo para el
  byte.** Esa mezcla es correcta y deliberada: el ticket necesita el token (servidor), el byte no
  (la firma va en la URL).
- El `403` de S3 por URL vencida **no trae body JSON útil**: distinguirlo por `xhr.status === 403` y no
  por el cuerpo.
- **No implementar reintento automático dentro de `putFileToStorage`.** El reintento es una decisión
  de la UI (el usuario aprieta), y un reintento silencioso con una URL ya vencida falla igual. Lo que

  nuevo.
- **No agregar compensación ante fallo del `PUT`.** El rollback de S3 desapareció por diseño y no se
  reemplaza (Flow Context). La fila de `files` queda `pending` y el error se descubre al leer.

  tareas 4-6, dejarlo fuera antes que dejarlo muerto.

### Task 3: El BFF deja de mover bytes — eliminar el handler de subida y propagar el 302

**Status:** Completed

#### Description

Retirar del BFF todo lo que existía para transportar binarios: eliminar el route handler
`POST /api/attachments`, convertir los handlers de `/preview` y `/download` en propagadores de la
redirección, y sacar `bodySizeLimit` de `next.config.js`.

Por qué es necesaria: CA-3, CA-4 y CA-13. El handler de subida tenía **una sola** justificación —el
progreso incremental vía `XHR` + `duplex: 'half'`— y con el byte directo a S3 la pierde. Los de
lectura conservan la suya (el navegador no puede mandar el `Authorization` cuando la URL va en un
`src`/`href`), pero dejan de proxear.

#### Acceptance Criteria

1. `src/app/api/attachments/route.ts` **está eliminado**.
2. Ningún módulo de `src/` hace un `POST` contra `'/api/attachments'`.
3. El handler de `/preview` hace el `fetch` a la api con `redirect: 'manual'` y, ante un `302`,
   responde `302` con el mismo `Location`.
4. El handler de `/download`, idem.
5. Ninguno de los dos setea `Content-Length` en la respuesta del `GET`.
6. El `HEAD` sigue propagando `Content-Type`, `Content-Disposition` y `Content-Length`.
7. El preámbulo de auth se conserva idéntico en ambos: `decodedToken()` y
   `401 { error: 'Unauthorized' }`.
8. Un `404` de la api con `{ code: 'file_not_available' }` se propaga con ese status y ese body.
9. `next.config.js` no contiene `experimental.serverActions.bodySizeLimit`.

#### Technical Details

**Architectural Context References:**

- Seguir **Code Conventions → route handlers**: `decodedToken()` (no `auth()`), cuerpo del 401 exacto,
  URL como `` `${process.env.API_URL}api/...` `` **sin `/` entre medio**, `fetch` nativo (no
  `apiClient`), params como `Promise<{ id: string }>` con `await`, `.catch()` obligatorio en el parseo
  del error del upstream.
- Seguir **Flow Context → `lectura-de-archivos`, pasos 1-2**: el handler ya no proxea el binario; lo
  que recibe es un 302 y **deja de propagar `Content-Length`**.
- Seguir **API Context → preview/download**: `Content-Length` va **solo en el `HEAD`**. En un `GET`
  prometería un cuerpo que un 302 no tiene y el cliente se quedaría esperando bytes que no llegan.
- **Reusable Code:** `decodedToken()` de `@/shared/utils/decoded-token`.

**Files to Create/Modify:**

- `src/app/api/attachments/route.ts` — **ELIMINAR**
- `src/app/api/attachments/[id]/preview/route.ts` — reescribir
- `src/app/api/attachments/[id]/preview/route.test.ts` — actualizar
- `src/app/api/attachments/[id]/download/route.ts` — reescribir
- `src/app/api/attachments/[id]/download/route.test.ts` — actualizar
- `next.config.js` — retirar `experimental.serverActions.bodySizeLimit`

**Implementation Notes:**

- **`redirect: 'manual'` es el detalle que hace toda la diferencia.** Sin él, `fetch` sigue la
  redirección por su cuenta y el handler termina bufferizando el binario desde S3 — exactamente lo que
  esta story elimina, pero de forma invisible: los tests de contrato pasarían y el proxy seguiría ahí.
- La respuesta se arma con `NextResponse.redirect(location, 302)` o
  `new NextResponse(null, { status: 302, headers: { Location } })`. **No** pasar `response.body`.
- **Decidir explícitamente si el handler devuelve el 302 al navegador o lo sigue.** Devolverlo es lo
  correcto y lo más barato: el navegador sigue redirecciones de forma transparente, y así el byte
  nunca toca el proceso de Next. Seguirlo desde el servidor reintroduciría el proxy.
- **`bodySizeLimit` no es solo limpieza:** refleja que ningún binario atraviesa el BFF. Retirarlo hace
  que un intento accidental de reintroducir el proxy falle rápido en lugar de funcionar en silencio.
- **El `HEAD` es el riesgo real de esta tarea.** `useAttachmentMeta` depende de él para resolver
  nombre, tamaño y mime de cada adjunto embebido, y los tipos de `web` están escritos a mano: si el
  `HEAD` deja de traer `Content-Disposition`, ningún compilador lo avisa y los adjuntos embebidos
  aparecen como `"Adjunto 42"` en producción. **Cubrirlo con TS-14 y verificarlo a mano.**

**Dependencies:**

- Librerías externas: ninguna
- Módulos internos: `@/shared/utils/decoded-token`
- Servicios: `api` (preview y download, que ya responden 302 desde S-005)

#### Testing Requirements

## Notas de Planificación

### Precondiciones de prueba que NO son del código

**S-008 es precondición dura para probar esta story en cualquier instalación.** Sin CORS en el bucket
acotado al origen del frontend, y sin una URL del bucket alcanzable desde el navegador, el `PUT`
directo **falla con un error de red opaco que no señala la causa**. Si al implementar aparece un fallo
de red inexplicable en el paso del `PUT`, verificar el bucket antes de buscar el bug en el código.

**S-004 y S-005 tienen que estar desplegadas.** Sin S-004 el endpoint no devuelve el ticket; sin S-005
los handlers de lectura reciben un stream en lugar de un 302 y el preview por `fileId` (CA-7) no
existe. Ambas figuran como completadas en `docs/story-plans/`.

**Puede correr en paralelo con S-007** (`opus-web`): son dos frontends independientes contra el mismo
contrato ya cerrado.

### Riesgos asumidos que el implementador no tiene que resolver

- **El rollback de S3 desapareció y no se reemplaza.** Quien escribe el objeto es el navegador. **No
  inventar una compensación en el frontend.**
- **El sistema no verifica que el byte llegue** (D-13). El progreso es el del `PUT`, no una
  confirmación de integridad. La mitigación es CA-14 (bloquear el envío), no una verificación.
- **Los archivos sin vínculo se acumulan sin techo.** El barrido está fuera de alcance. **No agregar
  limpieza desde el frontend.**

### El punto de mayor riesgo técnico

**Los dos espacios de identificadores en el markdown embebido** (Tareas 5 y 6). Un archivo recién
subido tiene `fileId`; un adjunto guardado tiene id de vínculo. Confundirlos no rompe la compilación
—los tipos de `web` están escritos a mano— y se manifiesta como un preview vacío o, peor, como el
preview de **otro** adjunto que casualmente tenga ese id. Es el fallo que hay que cubrir con tests
explícitos (TS-26, TS-27) y coordinar entre las dos tareas antes de escribir código.

**El segundo:** el `HEAD` al preview (Tarea 3). `useAttachmentMeta` depende de él y ningún compilador
avisa si deja de traer `Content-Disposition`.
