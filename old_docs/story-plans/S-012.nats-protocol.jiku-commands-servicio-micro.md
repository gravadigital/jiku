### Service Architecture

`packages/nats-protocol` es un **paquete compartido**, no un servicio desplegable. No tiene
`docs/architectures/`, y eso es correcto: no hay manifest porque no hay servicio. El contexto
técnico sale de las convenciones de sus **dos consumidores** (`core` y `api`), del contrato
`docs/apis/core.yaml`, y de los ADR 002 y 012. Precedente exacto del mismo patrón:
`docs/story-plans/S-011.nats-protocol.contrato-del-bus-renombrado.md`.

**Estado actual del paquete — el árbol completo, son 9 archivos:**

```
packages/nats-protocol/
├── package.json          name @jiku/nats-protocol, main dist/index.js, scripts build + test + lint
├── tsconfig.json         strict, declaration, outDir ./dist, rootDir ./src, include src/**/*.ts
├── eslint.config.js      module.exports = require('../../eslint.config.base.js')
├── .mocharc.json         require ts-node/register, timeout 10000, exit, recursive
├── src/
│   └── index.ts          282 líneas — TODO el código del paquete vive acá
└── tests/                abierta por S-011; hoy 93 casos, todos verdes
    ├── helpers/reload.ts recarga el módulo con un entorno controlado
    ├── protocol.test.ts  26 casos — nombres de servicio, subjects, grupo
    ├── endpoints.test.ts 56 casos — derivación de endpoints y methodFromSubject
    └── inbox.test.ts     11 casos — hash del inbox, superficie pública, envelope
```

**Baseline verificado al escribir este plan:** `npm run test --workspace @jiku/nats-protocol` →
**93 passing (165ms)**. Sin base de datos, sin red.

**Cómo se consume:** `package.json` apunta a `dist/`, así que los consumidores lo usan
**compilado**. `npm run build:packages` (postinstall de la raíz) lo compila antes que `api` y
`core`. Un borrado en `src/index.ts` **no llega a los consumidores sin rebuild** — y a la inversa:
un `core` que compila contra un `dist/` viejo daría un falso verde. De ahí que la Tarea 5 corra
`npm run build` completo antes de las suites.

**Patrón del archivo (respetarlo, es la convención de facto del paquete):**
- Un solo archivo, sin subcarpetas ni capas.
- Constantes de entorno **al tope**, leídas con `process.env.X || 'default'` **al importar**.
- Funciones puras exportadas, una por concepto, con un docblock en español que explica **el por
  qué**, no el qué.
- Los helpers privados (`base32`, `USER_ID_HASH_LEN`, `BASE32_ALPHABET`) van **después** de las
  funciones públicas que los usan, sin `export`.

**Manejo de errores:** el paquete **no lanza y no loguea**. Es un constructor de strings y un
catálogo de constantes.

**Estrategia de testing:** Mocha + `should` + `ts-node`, corriendo contra `src/` (no contra
`dist/`), sin base de datos y sin red. No hay `global-setup`: el paquete es puro. Todo lo que
dependa del entorno pasa por `reload()` (ver "El patrón de recarga").

### Relevant ADRs

#### ADR-002: Toda mutación es un comando NATS request/reply, sin JetStream

**Decisión:** NATS en modo request/reply, sin JetStream. La api publica un comando y espera la
respuesta con un timeout; core valida, escribe en una transacción y responde.

**Implementation Rules (verbatim del ADR):**

- Todo comando **DEBE** publicarse con el subject `{instance}.{user-id}.gestion.v1.{comando}`,
  usando la gramática de `@jiku/nats-protocol`. **NO SE DEBE** construir el subject a mano.
- El cliente NATS **DEBE** fijar `inboxPrefix` explícitamente al conectar, con el hash del user id
  que calcula `@jiku/nats-protocol`. Sin esto las respuestas no llegan.
- El `userId` con el que publica la api **DEBE** salir de la key del service user, **NO** de una
  variable de entorno: tiene que coincidir exactamente con el `sub` que el auth-callout lee del
  token para autorizar el subject.
- Toda respuesta **DEBE** tener el formato `{ status: 'success', data }` o
  `{ status: 'failure', errorCode, errorMessage }`. **NO SE DEBEN** inventar otros formatos.
- Los comandos de creación **DEBEN** devolver únicamente `{ id }`. Las ediciones y borrados, nada.
- Todo `errorCode` nuevo **DEBE** agregarse al mapa de `api/lib/utils/bus/protocol.ts` con su
  status HTTP. Un código sin mapeo cae en un 500 genérico.
- El timeout de la request es `NATS_REQUEST_TIMEOUT_MS` (default **5000 ms**); al expirar la api
  **DEBE** responder **503**.
- **NO SE DEBE** transportar datos estructurados dentro de `errorMessage`. El caso actual de
  `daily_limit_exceeded` —que la api recupera parseando el mensaje con un regex— es deuda
  explícita, no un patrón a imitar.
- Core **NO DEBE** publicar mensajes: solo responde el `Reply` de la request que recibe.

**Cómo aplica a este plan.** La primera regla es la que **justifica el borrado**: si la gramática
vive en el paquete y nadie arma un subject a mano, un símbolo que ya no tiene callers es superficie
muerta que invita a reusarse. El texto del ADR todavía cita `gestion` en el subject y "17 comandos";
esa corrección es **RF-23**, no de este plan.

> **Nota:** el ADR cita `core/src/bus/consumer.ts:69-70` como implementación de la suscripción con
> queue group. **Ese archivo ya no existe** — lo reemplazaron `core/src/bus/host.ts` y
> `core/src/bus/service.ts` en `S-012.core.*`. Actualizar la referencia es parte de RF-23/RF-24, no
> de este plan.

#### ADR-012: Monorepo npm con contexto de build en la raíz

**Decisión:** un único repo con npm workspaces (`packages/*`, `api`, `core`, `web`, `opus-web`),
Dockerfiles con contexto en la raíz, y los paquetes compartidos consumidos compilados.

**Implementation Rules (verbatim del ADR):**

- Todo servicio y paquete **DEBE** ser un workspace declarado en el `package.json` de la raíz.
- Un Dockerfile **DEBE** construirse con contexto en la **raíz del monorepo**, no en la carpeta del
  servicio. **NO SE DEBE** usar `docker build .` desde la carpeta del servicio: falla al no
  alcanzar `packages/`.
- Los Dockerfiles **DEBEN** copiar los manifiestos antes del código fuente, para preservar el cacheo
  de `npm ci`.
- Los frontends **DEBEN** instalar con `--ignore-scripts`: no consumen `packages/*` compilados.
- El gestor de paquetes **DEBE** ser **npm** con workspaces. **NO SE DEBEN** usar yarn, pnpm ni bun.
- Un cambio en `packages/*` **DEBE** ejecutarse con los tests de **todos** los servicios que lo
  consumen antes de mergear.
- Los cuatro servicios **DEBEN** correr sobre `node:24.12-alpine3.23` con usuario no-root, y usar
  build multi-stage.
- Una imagen **NO DEBE** hornear configuración: sin `ARG` de entorno ni `NEXT_PUBLIC_*` funcional
  (ADR-009).

**Cómo aplica a este plan.** La sexta regla es **la Tarea 5 completa**, y no es opcional: borrar un
`export` de un paquete es un cambio de API que solo el compilador de los consumidores puede
declarar seguro. `api/lib/utils/bus/protocol.ts`:10 hace `export * from '@jiku/nats-protocol'`, así
que la superficie del paquete es también la superficie de la api.

### API Context

#### La gramática del bus — el contrato, verbatim de `docs/apis/core.yaml`:114-137

```
#   {instance}.{user-id}.{svc}.{version}.{method}
#   dev.323332022539911171.jiku-commands.v1.clients.new
#
#   instance   deployment: dev / prod              (NATS_INSTANCE)
#   user-id    WHO publishes: the token's `sub`, RAW
#   svc        jiku-commands                       (NATS_COMMAND_SERVICE)
#              jiku-queries                        (NATS_QUERY_SERVICE)
#   version    protocol version: `v1`              (NATS_PROTOCOL_VERSION)
#   method     clients.new, requirements.{id}.edit, ...
#
# THE GRAMMAR DID NOT CHANGE — the set of values of the `{svc}` token went from one to two.
#
# Core registers the group `{instance}.*.{svc}.{version}` per service and subscribes one endpoint
# per method, with queue group `jiku-commands` for the commands and `jiku-queries` for the
# queries. The wildcard covers any caller and several replicas share the messages between them.
```

**Nada de esto cambia en este plan.** Se cita porque es lo que hace que el borrado sea seguro: el
prefijo de grupo que el framework micro necesita lo produce `groupSubject(service)`, que **ya
existe y ya se usa** (`core/src/bus/service.ts`). `subscriptionSubject()` producía el mismo prefijo
**con un `.>` final** —la forma vieja, de `subscribe()` a pelo— y no tiene ningún consumidor.

**Bloque 2 — líneas 86-97** (docblock + función):

```ts

 * Subject con wildcard que atiende core: cubre a cualquier caller.
 *
 * @deprecated Usá `groupSubject(COMMAND_SERVICE)`, que devuelve el mismo prefijo sin el `.>`
 * final —la forma que pide el framework micro—. El cuerpo quedó sin tocar a propósito: el
```

**Los dos docblocks declaran su propia fecha de vencimiento: "Desaparece en S-012".** Este plan es
ese vencimiento. La regla de `_base` que lo pedía —*"un comentario que marca deuda dice cuándo
desaparece"*— es la que hace que este borrado sea mecánico y no una investigación.

**Lo que NO se borra del vecindario, y es fácil confundir:**

```ts
/**
 * @deprecated Usá `methodFromSubject`: con dos servicios en el bus, el quinto segmento es un
 * método (comando o consulta), no siempre un comando. Es el MISMO símbolo, no una copia: se
 * mantiene para no tocar `core/src/bus/dispatcher.ts`. Se elimina cuando su caller se repunte.

export const commandFromSubject = methodFromSubject;
```

`commandFromSubject` es el **tercer** `@deprecated` del archivo y **se queda** (CA-15, verbatim:
*"`commandFromSubject` **sí se mantiene** como alias de `methodFromSubject`, porque su caller es el
despachador y el despachador no se toca"*). Borrar los tres de una pasada es el error fácil de esta
story, y rompe el build de `core` (`core/src/bus/dispatcher.ts`:4 lo importa).

### El patrón de recarga — cómo se testea un módulo que lee `process.env` al importar

Es la única decisión técnica no obvia del paquete, y condiciona cómo se escriben las aserciones
nuevas de este plan.

**El problema.** `COMMAND_SERVICE`, `QUERY_SERVICE`, `INSTANCE` y `PROTOCOL_VERSION` se evalúan
**una sola vez, al importar el módulo**. Un test que haga `process.env.NATS_COMMAND_SERVICE = 'x'`
después del `import` no cambia nada. Y un test que afirme el default (`'jiku-commands'`) **falla en
la máquina de cualquiera que tenga esa variable exportada en su shell**.

**La solución, ya instalada por S-011** (`tests/helpers/reload.ts`, verbatim del estado actual):

```ts
type Protocol = typeof import('../../src/index');

/** Las cinco variables que el módulo lee al importarse. Se resetean SIEMPRE. */
const PROTOCOL_ENV_KEYS = [
  'NATS_INSTANCE',
  'NATS_PROTOCOL_VERSION',
  'NATS_COMMAND_SERVICE',
  'NATS_QUERY_SERVICE',
  'NATS_SERVICE_NAME',
] as const;

export function reload(env: Partial<Record<ProtocolEnvKey, string>> = {}): Protocol {
  const saved = new Map<string, string | undefined>();
  for (const key of PROTOCOL_ENV_KEYS) {
    saved.set(key, process.env[key]);
    delete process.env[key];
  }
  for (const [key, value] of Object.entries(env)) {
    process.env[key] = value;
  }

  const modulePath = require.resolve('../../src/index');
  delete require.cache[modulePath];
  const loaded = require('../../src/index') as Protocol;

  for (const [key, value] of saved) {
    if (value === undefined) { delete process.env[key]; } else { process.env[key] = value; }
  }
  // Que el módulo cargado con entorno de test no quede cacheado para el próximo `reload`.
  delete require.cache[modulePath];

  return loaded;
}
```

**Lo que este plan le cambia:** `'NATS_SERVICE_NAME'` sale de `PROTOCOL_ENV_KEYS` (quedan cuatro), y
el docblock pasa de "las cinco variables" a "las cuatro variables". **Es seguro:** después del
borrado **ningún símbolo del paquete lee esa variable**, así que resetearla no protege de nada. Y
tampoco quedó definida en ningún lado del repo: `S-011.deploy.*` la sacó de los tres
`docker-compose*.yml`, de `deploy/bus-inspect.sh`, de `deploy/.env`, de `deploy/.env.dist` y de
`core/.env.test` (verificado por grep al escribir este plan: **cero apariciones** fuera de
`packages/nats-protocol/`).

**El detalle que hace posible el test-first de un borrado.** Una aserción escrita como
`p.SERVICE_NAME.should.be.undefined()` **no compila** después del borrado: `p` está tipado como
`typeof import('../../src/index')` y la propiedad deja de existir. La forma que compila **en los dos
estados** —antes del borrado (rojo) y después (verde)— es el cast que la suite ya usa en TS-48:

```ts
const surface = reload({}) as unknown as Record<string, unknown>;
(surface.SERVICE_NAME === undefined).should.be.true();
```

Esa es la forma **obligatoria** para las aserciones nuevas de la Tarea 2. Al revés, los cinco tests
existentes que ejercitan los símbolos con acceso **tipado** (`p.SERVICE_NAME.should.equal(...)`,
