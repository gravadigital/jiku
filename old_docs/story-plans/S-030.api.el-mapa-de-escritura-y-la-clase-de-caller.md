## Story Reference

- **Story:** [S-030](../stories/S-030.el-mapa-de-escritura-y-la-clase-de-caller.md)
- **Service:** `api`
- **Summary:** La api agrega **una sola clave** a `STATUS_BY_ERROR_CODE`: `access_denied` → **403**.
  Es el **tercero de los tres lugares** que exige la convención de errores para un código nuevo, y
  los otros dos ya están escritos (`packages/nats-protocol` y `docs/apis/core.yaml`, entregados con
  `S-030.core` y `S-030.nats-protocol`). Sin este tercero el código cae en el `|| 500` de
  `httpStatusFor()` y el frontend trata un rechazo de permisos como error de servidor.

> **Esta story no elimina ninguna regla de la api, y eso es CA-14 textual.** Ni un `hasAnyRole`,
> ni un `validateProjectPermissions`, ni un `canUserAccessEntity`, ni una regla de negocio. **La
> duplicación transitoria es la red** mientras dure la migración: las eliminaciones son **S-034**.
> Si un test de autorización se pone rojo, el alcance se desbordó.

> **Criterios de este plan:** **CA-9** (el único enteramente de la api), **CA-11** y **CA-14**;
> **CA-10** por el lado del contrato HTTP —los dos códigos comparten el 403 y **no se fusionan**—;
> **CA-3** y **CA-7** verificados solo en su traducción a HTTP.
> **No son de este plan:** CA-1, CA-2, CA-4, CA-5, CA-6, CA-8, CA-12, CA-13, CA-15 — todos de la
> compuerta de `core`, **ya entregados** (`S-030.core`, Completed 8/8).

### H-3 — La api **hoy no puede recibir** `access_denied` de `core`, y eso es CA-14 funcionando

Es la parte contraintuitiva del plan, y define entera la estrategia de test.

`core` derivó su mapa `COMMAND_ENTITY` **de qué ruta de escritura aplica hoy la capa 3 de la api**,
verificado con `grep` sobre `api/lib/routes/` (`core/src/entity-project.ts:236`). El resultado es
que, para **cada uno de los 8 comandos con descriptor de entidad**, la ruta HTTP que lo publica ya
lleva `validateProjectPermissions` o `canUserAccessEntity` **antes** del `sendCommand`:

| Comando con chequeo en `core` | Ruta que lo publica | Capa 3 de la api |
|---|---|---|
| `requirements.new` | `lib/routes/opus-requirements-post.ts:85` | `validateProjectPermissions` |
| `requirements.{id}.edit` | `lib/routes/opus-requirements-*` | `validateProjectPermissions` |
| `requirements.{id}.comment` | `lib/routes/opus-requirements-id-comments-post.ts:54` | `validateProjectPermissions` |
| `requirements.{id}.subscriptors.new` | `lib/routes/opus-requirements-id-subscriptors-post.ts:75` | `validateProjectPermissions` |
| `requirements.{id}.subscriptors.{userId}.delete` | `lib/routes/opus-requirements-id-subscriptors-userid-delete.ts:53` | `validateProjectPermissions` |
| `requirements.{id}.resolve` | **ninguna ruta HTTP lo publica** | — |
| `attachments.{id}.delete` | `lib/routes/attachments-delete.ts` | `canUserAccessEntity` |
| `files.{fileId}.request-download` | las cuatro rutas de lectura de archivo | `canUserViewEntity` |

Y las dos capas evalúan **la misma tabla con el mismo criterio**: la api restringe
`if (req.decodedTokenRoles.includes('external-user'))`; `core` restringe
`if (callerClass === 'external')`, que con la precedencia de CA-5 es el mismo conjunto. **Coinciden
por construcción, y la api decide primero.**

> **Consecuencias, y las tres importan:**
>
> 1. **No intentes construir un test donde `core` emita el código a través de una ruta real.** Para
>    lograrlo habría que desactivar un middleware de la api, y eso es **S-034**, no esto.
> 2. **El instrumento honesto es `fakeBus.reply(...)`**, exactamente lo que hizo `S-017.api` con
>    `caller_not_authorized` (*"en la práctica esta api nunca lo recibe"*). No es un atajo: es la
>    única forma de cubrir el camino sin fabricar un estado que la api no permite.
> 3. **Y por eso los tests son lo único que sostiene la entrada del mapa.** Sin ellos, el próximo
>    que lea *"la api nunca lo recibe"* la borra por código muerto — y el día que S-034 elimine
>    `validateProjectPermissions`, **todos** esos rechazos salen 500.

### H-4 — `errorBody` no reenvía `errorDetails`, y acá no hace falta

`Reply` tiene `errorDetails?: Record<string, unknown>` desde S-020
(`packages/nats-protocol/src/index.ts:257`), pero `errorBody` arma solo `{ code, message }`
(`api/lib/utils/bus/protocol.ts`). **No es un problema para esta story:** el rechazo de `core` es
`failure(ErrorCode.ACCESS_DENIED, ACCESS_DENIED_MESSAGE)` **sin details**
(`core/src/entity-project.ts:504`), deliberadamente, porque el mensaje no puede llevar el proyecto,
la entidad ni el subject (CA-32 del REQ).

> **No agregues el reenvío de `errorDetails` en este plan.** Es un cambio de contrato con los dos
> frontends y no lo pide ningún CA de S-030.

**Estrategia de errores:** sin clases de error y sin handler global. Cada punto responde
`res.status(n).json({ code, message })` y corta. Para los errores que vienen del bus, quien responde
es `sendCommand`, con `httpStatusFor(reply.errorCode)` y `errorBody(reply)`.

**Estrategia de testing:** Mocha con `should`, PostgreSQL real levantado por los fixtures globales,
y el `FakeBus` ya instalado para toda la corrida (`tests/setup-env.ts:31`), con `reset()` por root
hook. **No llames a `setBus` en un archivo de test.**

### Relevant ADRs

#### ADR-002: Comandos NATS sin JetStream

**Decisión:** toda mutación es un request/reply sincrónico sobre NATS core, sin cola, sin
persistencia y sin reintento.

**Implementation Rules (verbatim):**

- Todo comando **DEBE** publicarse con el subject `{instance}.{user-id}.gestion.v1.{comando}`,
  usando la gramática de `@jiku/nats-protocol`. **NO SE DEBE** construir el subject a mano.
- El cliente NATS **DEBE** fijar `inboxPrefix` explícitamente al conectar, con el hash del user id
  que calcula `@jiku/nats-protocol`. Sin esto las respuestas no llegan.
- El `userId` con el que publica la api **DEBE** salir de la key del service user, **NO** de una
  variable de entorno: tiene que coincidir exactamente con el `sub` que el auth-callout lee del
  token para autorizar el subject.
- Toda respuesta **DEBE** tener el formato `{ status: 'success', data }` o
  `{ status: 'failure', errorCode, errorMessage }`. **NO SE DEBEN** inventar otros formatos.
- Los comandos de creación **DEBEN** devolver únicamente `{ id }`. Las ediciones y borrados, nada.
- **Todo `errorCode` nuevo DEBE agregarse al mapa de `api/lib/utils/bus/protocol.ts` con su status
  HTTP. Un código sin mapeo cae en un 500 genérico.**  ← **es la regla que este plan cumple**
- El timeout de la request es `NATS_REQUEST_TIMEOUT_MS` (default **5000 ms**); al expirar la api
  **DEBE** responder **503**.
- **NO SE DEBE** transportar datos estructurados dentro de `errorMessage`. El caso actual de
  `daily_limit_exceeded` —que la api recupera parseando el mensaje con un regex— es deuda
  explícita, no un patrón a imitar.
- Core **NO DEBE** publicar mensajes: solo responde el `Reply` de la request que recibe.

#### ADR-008: Autorización deny-by-default

**Decisión:** `validateToken` global para todo path, exenciones como lista explícita, y sobre esa
base dos capas más: por rol (`hasAnyRole`) y por entidad (`validateProjectPermissions` /
`canUserAccessEntity` / `canUserViewEntity`, que resuelven el proyecto desde **9 tipos de entidad**).

**Implementation Rules (verbatim):**

- `validateToken` **DEBE** instalarse globalmente en `app.ts`. **NO SE DEBE** declarar
  autenticación ruta por ruta.
- Un endpoint público **DEBE** agregarse explícitamente a `api/lib/config/public.ts`. Cualquier
  cambio en ese archivo es un **cambio de seguridad** y debe revisarse como tal.
- Un endpoint público **DEBE** validar por su cuenta lo que corresponda. El caso vigente
  (`GET /api/opus/attachments/:id/public`) verifica que el adjunto esté marcado público, responde
  403 en cualquier otro caso, y manda `X-Content-Type-Options: nosniff` con CSP de sandbox.
- Un endpoint que requiere rol **DEBE** declarar `hasAnyRole([...])` explícitamente. La
  autenticación global no implica autorización.
- Un endpoint accesible a `external-user` **DEBE** además verificar permiso de proyecto: el rol
  solo no alcanza (ADR-006).
- Un tipo de entidad nuevo con adjuntos **DEBE** agregarse a la resolución de proyecto de
  `attachments-access.ts`. Un tipo no contemplado **no se autoriza**, que es el comportamiento
  correcto.
- Al leer un archivo de ruta, **NO SE DEBE** concluir que está desprotegido por no ver el
  middleware: la protección es global.

> **Cómo se lee ADR-008 en esta story:** las tres capas de la api **siguen intactas** (CA-14). Lo
> que cambia es que ahora existen **también** del lado de `core`. ADR-008 no se relaja acá.

#### ADR-006: Dos frontends, una api

Relevante por una sola línea, y es la que hace que este plan valga: **`access_denied` es el código
que `web` y `opus-web` ya conocen** para *"no podés tocar esto"*, y ya lo reciben con **403**.
Mantener el par `(403, access_denied)` es lo que permite mover el rechazo a `core` **sin tocar una
línea de UI** (CA-11).

### API Context

#### El archivo que se toca: `api/lib/utils/bus/protocol.ts`

Estado actual del mapa (extracto verbatim de lo relevante):

```ts
const STATUS_BY_ERROR_CODE: Record<string, number> = {
  invalid_fields: 400,
  client_not_found: 400,
  // … 14 códigos de 400 más …
  requirement_not_found: 400,
  user_not_found: 404,
  subscription_not_found: 404,
  file_not_found: 404,
  file_not_available: 404,
  file_type_not_allowed: 400,
  file_too_large: 400,

  // `file_not_owned` es 403 y NO 400, y ES LA ENTRADA MÁS FÁCIL DE MAPEAR MAL. […]
  file_not_owned: 403,

  // `caller_not_authorized` es 403 por LA MISMA RAZÓN que `file_not_owned` […]
  caller_not_authorized: 403,

  unknown_command: 500,
  internal_error: 500,
};

export function httpStatusFor(errorCode: string | undefined): number {
  return (errorCode && STATUS_BY_ERROR_CODE[errorCode]) || 500;
}
```

**El fallback `|| 500` es el modo de falla exacto que CA-9 describe.** No es un error de
compilación: `access_denied` sin entrada compila, corre, y devuelve 500.

`errorBody` (mismo archivo) arma el cuerpo que esperan los fronts:

```ts

    message: reply.errorMessage || 'Internal error',

  if (reply.errorCode === 'daily_limit_exceeded') { /* remainingMinutes por regex */ }
  return body;
}
```

### Flow Context

#### `escritura-por-el-bus` — Manejo de Errores (copiado verbatim)

Es la tabla que este plan hace verdadera del lado HTTP. **Las dos filas de 403 son el corazón de
CA-10.**

| Situación | Reply | HTTP equivalente | Dónde se decide |
|---|---|---|---|
| `external-user` publicando un comando | *(violación de permisos del servidor NATS, en el momento)* | — | **Paso 1** — el mensaje no llega a `core` |
| Ídem, si la plantilla se equivocara | `caller_not_authorized` | 403 | **Paso 2d** — la segunda capa |
| Identidad en el payload de un caller no confiable | `invalid_fields` | 400 | Paso 2a |
| Sin fila en `users` / `roles: []` / roles desconocidos | `caller_not_authorized` | 403 | Paso 2c' |
| El rol no habilita el método | `caller_not_authorized` | 403 | Paso 2d |
| **Modo externo sin permiso sobre la entidad** | **`access_denied`** | **403** | **Paso 3** |
| Regla de dominio incumplida | el código de la regla | 400 / 403 | Paso 4 |
| Sobre y campo de dominio que difieren | `invalid_fields` + `errorDetails` | 400 | Paso 3 |
| El cliente no fijó `inboxPrefix` | *(timeout)* | 504 | **Paso 1** — el error más caro de diagnosticar |
| `core` caído | *(sin suscriptor / timeout)* | 503 / 504 | ADR-002 |

Y el párrafo que fija el criterio, verbatim del mismo flujo:

> **`access_denied` y `caller_not_authorized` responden preguntas distintas** y no se fusionan: el
> primero es *"¿podés tocar ESTA entidad?"* y lo decide el comando con la fila delante; el segundo
> es *"¿tu rol habilita este método?"* y lo decide el mapa antes de tocar el dominio. **Es además el
> código que los dos frontends ya conocen** para este caso, que es lo que hace que el contrato HTTP
> no cambie.

**Qué modifica este plan del flujo:** nada de los pasos 1 a 5 —son de `core`—. Modifica **el paso
donde la api traduce el reply**, que es la columna *"HTTP equivalente"*: hoy la fila
`access_denied` daría **500**, y al terminar da **403**.

#### `alta-requisito-desde-portal` — el paso 4 y su tabla de errores (extracto)

| Paso | Situación | HTTP | Cuerpo | Nota |
|---|---|---|---|---|
| 4 | Rol no autorizado | 403 | `{ code: access_denied }` | La api rechaza sin publicar |
| 4 | **Sin permiso sobre el proyecto** | 403 | `{ code: access_denied }` | **La capa que aísla un cliente de otro.** Rechaza sin publicar |
| 6 | `File.uploaded_by` ≠ el actor resuelto | **403** | `{ code: file_not_owned }` | Rollback total igual |

> **Las dos primeras filas siguen vigentes tal cual, y por eso H-3 es cierto:** *"la api rechaza sin
> publicar"* es exactamente lo que impide que `core` emita `access_denied` a través de una ruta
> real. Esas filas se mueven en **S-034**, no acá. Lo que este plan garantiza es que **cuando se
> muevan, el status no cambie**.

### Integration Points

- **NATS** (`nats@^2.29.3`), request/reply sin JetStream. Subject:

  devuelve el reply fijo sin llegar a `core`.

### Code Conventions

- **`kebab-case`** en archivos; `camelCase` en funciones y variables; `SCREAMING_SNAKE_CASE` en
  constantes de módulo (`STATUS_BY_ERROR_CODE` ya lo es).
- **Imports relativos.** Nada de paths de `tsconfig` ni de los alias de `module-alias` en TS. Los
  paquetes del monorepo, por nombre: `@jiku/nats-protocol`.
