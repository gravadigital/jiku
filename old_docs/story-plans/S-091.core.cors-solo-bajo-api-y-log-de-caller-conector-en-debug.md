# Story Plan: S-091 (core) - CORS solo bajo /api y log de caller conector en debug

## Status

**Status:** Completed

**Progress:** 3/3 tareas completadas

## Story Reference

- **Story:** [S-091](../stories/S-091.cors-solo-bajo-api-y-log-de-caller-conector-en-debug.md)
- **Service:** `core`
- **Origen:** [REQ-020](../requests/REQ-020.arreglos-chicos-de-pruebas-e2e-y-relevamiento-de-pantallas.md) (DD-3, DD-4)
- **Summary:** el despachador de comandos pasa la clase del caller (`callerClass`, la misma que ya
  calcula con `resolveCallerClass` desde S-030) al `CommandContext`, y la rama externa de
  `resolveActor` loguea en `debug` cuando el caller es de clase `connector` (jiku-docs, el camino
  normal) y sigue en `warn` para cualquier otra clase. Así un `warn` vuelve a significar algo
  anómalo: un `CORE_TRUSTED_PUBLISHER_ID` mal configurado o una persona publicando directo al bus.

> **Alcance de este plan:** solo el servicio `core` (CA-4, CA-5, CA-6). CA-1 a CA-3 (CORS bajo
> `/api`) son del servicio `api` y ya están completos en su propio plan. Los documentos
> (`docs/architectures/core/conventions/commands.md` —que copia la interfaz `CommandContext`—,
> el flujo `escritura-por-el-bus`, ADR-015, etc.) son del servicio `docs`.

> **Precondición verificada sobre el árbol (2026-10-26, `5e51de8`):**
>
> - `core/src/bus/dispatcher.ts` declara `let callerClass: CallerClass;` (línea ~272), lo asigna
>   dentro del `try` de la compuerta (líneas ~365-382: `resolveCallerClass(roles)`, o
>   `'connector'` para el exento directo, o `throw`) y hoy **solo lo usa** para el chequeo de
>   entidad (`if (callerClass === 'external')`, línea ~446). El contexto del comando se arma en
>   **dos** lugares: `command.execute(validated.value, { caller, params, transaction, actor, roles, actorName })`
>   (línea ~460) y `writeNotifications(reply.notifications, { ...mismo objeto... })` (línea ~495).
>   La story cita `:272` y `:367-373`; los puntos donde se **arma el objeto** son estos dos.
> - Ningún test arma un `CommandContext` a mano: `tests/commands/notifications.test.ts:127` solo
>   **tipa** el parámetro de un `execute` doble que recibe el contexto del despachador. Hacer el
>   campo obligatorio no rompe la compilación de ningún test.
> - **Hay un test que la story no listó y que se rompe con el cambio:** `requirements.test.ts`
>   TS-37 (línea ~3319, *"la rama externa loguea en warn sin filtrar el payload"*) despacha con
>   `EXTERNAL`, que en ese archivo tiene `roles: ['internal-app']` → clase `connector`. Hoy afirma
>   `warn.callCount === 1`; después del cambio ese log sale en `debug`. Se ajusta en Task 3.

**`CallerClass` y su resolución (`src/caller-class.ts`, sin cambios):**

```ts
export type CallerClass = 'connector' | 'internal' | 'external';
const PRECEDENCE: readonly CallerClass[] = ['external', 'internal', 'connector'];
export const CLASS_BY_ROLE: Readonly<Record<string, CallerClass>> = {
  'external-user': 'external',
  user: 'internal',
  admin: 'internal',
  'internal-app': 'connector',
};
export function resolveCallerClass(roles: readonly string[]): CallerClass | null { ... }
```

**Cómo resuelve el despachador `callerClass` hoy (`dispatcher.ts`, extracto, sin cambios de lógica):**

```ts
let callerClass: CallerClass;
let roles: readonly string[];
let actorName: string | undefined = actor?.name;
const actorIdentity = actor ? actor.id : caller;
try {
  const exemptDirect = !actor && caller === getTrustedPublisherId();
  if (actor) { roles = actor.roles; }
  else if (exemptDirect) { roles = []; }
  else { const identity = await readCallerIdentity(caller); roles = identity.roles; ... }
  ...
  const denied = authorizeWithRoles(actorIdentity, roles, name, 'commands', channel);
  if (denied) { return denied; }
  const resolved = resolveCallerClass(roles);
  if (resolved) { callerClass = resolved; }
  else if (exemptDirect) { callerClass = 'connector'; }
  else { throw new Error(`rol con comandos y sin clase de caller: ${roles.join(',')}`); }
} catch (error: any) { ... return failure(ErrorCode.INTERNAL_ERROR, 'Internal error'); }
...
if (callerClass === 'external') { ...authorizeEntityAccess... }
const transaction = await sequelize.transaction();
try {
  const reply = await command.execute(validated.value, {
    caller, params, transaction, actor, roles, actorName,
  });
  if (reply.status === 'success' && reply.notifications?.length) {
    await writeNotifications(reply.notifications, {
      caller, params, transaction, actor, roles, actorName,
    });
  }
  ...
```

**Qué clase llega a la rama externa de `resolveActor`** (la que loguea): solo callers **sin sobre**
y cuyo `caller !== CORE_TRUSTED_PUBLISHER_ID`, es decir, el canal **directo**. Ahí `roles` sale de
`users.roles` del caller, y:

| Roles del caller directo | `callerClass` | Rama de `resolveActor` | Log después del cambio |
|---|---|---|---|
| `['internal-app']`, `['internal-app','docs']` (jiku-docs, conectores) | `connector` | externa | **`debug`** |
| `['user']`, `['admin']` (persona publicando directo) | `internal` | externa | **`warn`** (sin cambios) |
| `['external-user']` | `external` | — | no llega: `commands: []` en canal directo → `caller_not_authorized` antes del comando |
| exento (`CORE_TRUSTED_PUBLISHER_ID`, sin sobre) | `connector` | api (rama 2) | ninguno (sin cambios) |
| cualquiera **con sobre** | la del actor | sobre (rama 1) | ninguno (sin cambios) |

`user` tiene `files.request-upload` en `INTERNAL_COMMANDS` (canal directo), así que un caller con
`roles: ['user']` llega al comando y a la rama externa: es el vehículo de CA-5.

**Código actual de la rama externa (`src/commands/resolve-actor.ts`):**

```ts
  // `warn` y no `error`: la rama externa no es un fallo, es el caso raro de hoy (RF-11). Su
  // ausencia haría que un CORE_TRUSTED_PUBLISHER_ID mal configurado se manifieste SOLO como
  // `file_not_owned` en S-003, que parece un problema de permisos y no de configuración.
  //
  // Se loguea el `caller` —un identificador de servicio— pero NUNCA el payload: la convención
  // `logging` prohíbe loguear datos de negocio fuera de LOG_COMMANDS.
  logger.warn(
    `[${component}] comando publicado por un caller externo: ${ctx.caller}. ` +
    'El actor se resuelve del subject y se ignora lo declarado en el cuerpo.'
  );

  return ctx.caller;
```

La rama del sobre (`if (ctx.actor) return ctx.actor.id;`) y la de la api
(`if (ctx.caller === getTrustedPublisherId()) return declaredActor;`) **no loguean** y no cambian.

**Comandos que comparten `resolveActor`** (once): `files.request-upload`, los seis que vinculan
archivos vía `link-files.ts` (`requirements.new`, `requirements.{id}.edit`,
`requirements.{id}.comment`, `tasks.new`, `tasks.{id}.edit`, `tasks.{id}.comment`) y los cuatro de
tiempos. Todos reciben el `ctx` del despachador, así que el cambio de nivel los cubre a todos sin
tocarlos.

### Relevant ADRs

- **ADR-007 (identidad del subject):** el `user-id` del subject es el `sub` del service user que
  publica; la api usa un único service user. Es la razón de las tres ramas de `resolveActor`. No
  cambia.
- **ADR-003 (el despachador nunca lanza / es dueño del contexto):** el contexto lo arma el
  despachador; los comandos no calculan la clase por su cuenta. `callerClass` se pasa **sin
  ninguna consulta nueva**, igual que `roles` (S-031) y `actorName` (S-070).
- **ADR-008 (deny-by-default, `CLASS_BY_ROLE` cerrado):** no se agrega lógica de clasificación;
  se reusa el valor ya calculado. Un gate en los tests verifica que `CLASS_BY_ROLE` y `PRECEDENCE`
  estén declarados una sola vez en `core/src/` — no duplicar.

### API Context

Ningún cambio en el contrato del bus (`docs/apis/core.yaml`, `packages/nats-protocol`): ni
subjects, ni payloads, ni replies, ni códigos de error. `CommandContext` es un tipo **interno** de
core. Comando usado por los tests:

- `files.request-upload` — payload `{ fileName: string, mimeType: string, fileSize: number, uploader?: string }`;
  responde `success` con `UploadTicket` (`data.id` = id de la fila en `files`). Con caller externo
  `files.uploaded_by = ctx.caller`.
- `requirements.{id}.comment` — payload `{ author, comment, fileIds? }`.
- `attachments.{id}.delete` — payload `{}`; no resuelve actor.

### Database Context

Sin cambios de esquema. Los tests siembran filas en `users` (`id`, `name`, `username`, `email`,
`roles`, `identityType`) y leen `files.uploaded_by`.

### Flow Context

**escritura-por-el-bus** (`docs/flows/escritura-por-el-bus.md`, Paso 3), texto actual:

```
2. resolveActor(ctx, payload):
   if hay sobre                                       -> actor.id
   else if ctx.caller == CORE_TRUSTED_PUBLISHER_ID    -> payload.author/creator/editor/uploader
   else                                               -> ctx.caller
```

Cambio de esta story: la rama `else` loguea `debug` si `ctx.callerClass === 'connector'` y `warn`
para cualquier otra clase. El valor devuelto no cambia. (La edición del flujo es del servicio `docs`.)

Escenario de la story (CA-4 a CA-6):

1. **[core / despachador]** `resolveCallerClass(['internal-app'])` → `connector`; arma el contexto
   con `callerClass`.
2. **[core / `resolveActor`]** sin sobre y caller ≠ `CORE_TRUSTED_PUBLISHER_ID` → rama externa →
   `debug` si `connector`, `warn` si no; devuelve `ctx.caller`. Sobre o api sin sobre → sin log.

### Integration Points

- Sin integraciones nuevas. jiku-docs no se modifica: sigue publicando `files.request-upload` por
  el canal directo con su service user (`roles: ['internal-app', 'docs']`).

### Code Conventions

- **`_base`:** comentarios en español y del **por qué**; un archivo por responsabilidad; imports
  relativos.
- **`logging`:** logger único importado de `../logger`; prefijo de componente entre corchetes
  (`[${component}]`); **nunca** el payload fuera de `LOG_COMMANDS`; niveles: `warn` = entrada
  inválida/anómala que el servicio maneja; `debug` = diagnóstico. En producción la consola está en
  `info`, así que el `debug` del conector no aparece — es el objetivo.
- **`commands`:** los comandos no se tocan; el contexto lo arma el despachador.
- **`testing`:** los tests entran por el despachador (`dispatch()`), sobre base real; `sinon.spy`
  / `sinon.stub` sobre `logger`, `sinon.restore()` en `afterEach`.
- Documentar el campo nuevo en `CommandContext` con el mismo estilo que `roles`: de dónde sale en
  cada canal y por qué no es opcional.

### Task 1: `callerClass` en el `CommandContext` y nivel por clase en `resolveActor`

**Status:** Completed

#### Description

DD-3 y DD-4 de la story. Agregar `callerClass: CallerClass` (obligatorio, como `roles`) a
`CommandContext`, pasarlo en los dos objetos de contexto que arma el despachador, y en la rama

#### Acceptance Criteria

1. `src/commands/types.ts`: `CommandContext` tiene `callerClass: CallerClass` (importado de
   `../caller-class`), **no opcional**, con docblock que explique: es la misma clase de
   `resolveCallerClass` (S-030) ya calculada por la compuerta; de dónde sale en cada canal (sobre →
   la del actor; directo → la de `users.roles` del caller; exento → `'connector'`); que existe para

   el despachador).
2. `src/bus/dispatcher.ts`: los dos objetos `{ caller, params, transaction, actor, roles, actorName }`
   (el de `command.execute` y el de `writeNotifications`) pasan a incluir `callerClass`. Sin
   consultas nuevas, sin cambiar cómo se calcula.
3. `src/commands/resolve-actor.ts`: la rama externa usa `logger.debug` si
   `ctx.callerClass === 'connector'` y `logger.warn` en otro caso, con **el mismo texto** de hoy.

4. El comentario de la rama externa (y el docblock de la función donde corresponda) explica: para

5. No se tocan `caller-class.ts`, `authorize-caller.ts`, `write-notifications.ts` ni ningún comando.
6. `npm run build --workspace @jiku/core` y `npm run lint --workspace @jiku/core` pasan.
