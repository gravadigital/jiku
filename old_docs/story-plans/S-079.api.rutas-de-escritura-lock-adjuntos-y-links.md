### Relevant ADRs

**ADR-002: Toda mutación es un comando NATS request/reply, sin JetStream** — reglas que aplican
(verbatim):
- *"Todo comando **DEBE** publicarse con el subject `{instance}.{user-id}.gestion.v1.{comando}`,
  usando la gramática de `@jiku/nats-protocol`. **NO SE DEBE** construir el subject a mano."*
- *"Un bus caído **DEBE** responder **503**."*
- *"**NO SE DEBE** transportar datos estructurados dentro de `errorMessage`."*
- Aplicación: el subject lo arma `moduleCommandSubject` / `moduleQuerySubject` dentro del bus con el
  `serviceName` del registro; la ruta solo pasa el **método** (`documents.new`,
  `documents.${id}.update`). **Corolario de seguridad (mismo que S-078):** en las rutas 9-14, 16 y
  20 el `{id}` **entra al subject**, así que se valida con `isUlid` **antes** de llamar al embudo;
  un `.`, `*` o `>` (Express entrega `req.params` decodificado) inyectaría tokens NATS. El
  `version_conflict` / `document_locked` llegan con sus datos en `errorDetails`, no en
  `errorMessage`, y así se propagan (DD-7).

**ADR-008: Autorización deny-by-default** — reglas (verbatim):
- *"`validateToken` **DEBE** instalarse globalmente en `app.ts`. **NO SE DEBE** declarar
  autenticación ruta por ruta."*
- *"Un endpoint que requiere rol **DEBE** declarar `hasAnyRole([...])` explícitamente. La
  autenticación global no implica autorización."*
- *"Al leer un archivo de ruta, **NO SE DEBE** concluir que está desprotegido por no ver el
  middleware: la protección es global."*
- Aplicación: **H-3** (REQ-016, verbatim): *"`config/public.ts` no declara `put`, así que `app.ts`
  no instala `validateToken` para ese método; hoy el único `PUT` (`week-assigned-times-put.ts`) lo
  declara en su propia cadena. ADR-008 prohíbe autenticar ruta por ruta. **Decisión:** se agrega
  `put` al mecanismo global (lista vacía + `app.put(...)`) y se quita la declaración redundante de
  `week-assigned-times-put.ts`. Cierra la trampa para siempre en vez de repetirla."* Las doce rutas
  declaran `hasAnyRole(['admin', 'user'])`.

**ADR-001 / DD-17 (excepción):** la ruta 18 (`shares.list`) es una **consulta** al bus, no a la
base: es la misma excepción de S-078 (la documentación no está en la base de la api). El JSDoc de
`client.ts` ya lo explica; la ruta no lo repite.

**ADR-006 / DD-3:** el portal es **solo lectura**. Ninguna ruta de escritura se monta bajo
`/opus/*`, y `/docs/*` queda en `hasAnyRole(['admin', 'user'])` (un `external-user` recibe 403).

**DD-1:** *"La api llama a jiku-docs **siempre** en nombre de la persona con `actor: { id }` — **solo
`id`**"*. Lo inyecta el embudo; el handler no lo arma.

**DD-2:** *"La api **no autoriza el dominio de documentación** […] jiku-docs es la autoridad (ACL de
carpetas, visibilidad, clase de caller)"*. Ninguna ruta decide si la persona tiene `write` o
`manage`: lo responde jiku-docs (`permission_denied` → 403).

**DD-7:** *"Cuerpo de error de las rutas de docs: `{ code, message, details? }` — `code` es el
`errorCode` de jiku-docs **sin traducir** y `details` es su `errorDetails` verbatim […] **En
CA-17/CA-18, "errorCode" y "errorDetails" se leen como `code` y `details` del cuerpo HTTP**"*. Ya lo
hace `docsErrorBody`; este plan solo lo verifica con 409.

**DD-8 (verbatim):** *"La api genera los ULID de alta (`documents.new`, `attachments.request-upload`,
`shares.new`) si el cliente no manda `id`, y calcula el `checksum` del contenido de texto; la web
genera el `sessionId` del lock y el `checksum` del binario del adjunto."*

**DD-9 (verbatim):** *"`via` lo fija la api: `human` en escrituras y locks. Toda escritura por HTTP
es una persona en la web. `agent` es de jiku-go."*

**DD-14 (verbatim):** *"`POST /docs/documents/{id}/shares` responde **404 `sharing_not_configured`**
si la api no tiene `JIKU_PUBLIC_URL`. jiku-docs arma la `url` con su propio `JIKU_PUBLIC_URL`: crear
un link que la api después no sirve es entregar un link roto."*

### API Context

#### Cadena común de middlewares

Todas: (global) `validateToken` → `requireModule('docs')` → `hasAnyRole(['admin', 'user'])` →
`validateBodyFields(SCHEMA)` o `validateQueryParams(SCHEMA)` → handler (que primero valida el id de
path con `isUlid` y responde `respondDocsNotFound` sin llamar al bus).

> **`requireModule` va primero, antes del rol** (orden fijado por S-077, TS-44 de S-078): con el
> módulo `not_installed`, un `external-user` recibe **404 `module_not_installed`**, no 403, y un body
> inválido tampoco llega a Joi. **`validateToken` global va antes que todo**: sin token, 401 aunque
> el módulo no esté instalado.

#### Bodies HTTP y esquemas Joi (forma, no dominio)

Regla de este plan (P-3): **Joi valida la forma** —tipos, obligatorios, ids ULID, claves no
declaradas— y **deja las reglas de dominio a jiku-docs**, para que el código específico llegue a la
web sin traducir: el patrón de `fileName` (`file_name_invalid`), el tamaño de `content`
(`content_too_large`), el rango de `expiresAt` (`share_expiry_invalid`), `version` obligatoria con
`mode: pinned` (`invalid_fields`). Si Joi los replicara, la web recibiría `invalid_fields` donde
jiku-docs da un código propio.

**Todos los esquemas de body son `joi.object({...}).strict()`**: el body es JSON, así que los tipos
llegan exactos; `strict` impide que `"6"` pase como `6` y deja `expiresAt` sin convertir. Como
`validateBodyFields` no convierte, **el payload se arma con `req.body` ya validado** (con
`pickDefined` de `lib/modules/docs/query.ts` para no mandar claves ausentes). Ninguno usa
`.unknown(true)`: una clave no declarada es **400 `invalid_fields`** — así se rechazan `via`,
`checksum` (rutas 8/9), `force`, `documentId` en el body de la 19, `contentUploadId`, `actor`.

```ts
// import { joiUlid } from '../modules/docs/ids';
const version = () => joi.number().integer().min(1);

// 8  POST /docs/documents
joi.object({ id: joiUlid(), folderId: joiUlid().required(), fileName: joi.string().required(),
  content: joi.string().allow('').required(), message: joi.string() }).strict()
// 9  PUT /docs/documents/:id
joi.object({ baseVersion: version().required(), content: joi.string().allow('').required(),
  sessionId: joiUlid(), message: joi.string() }).strict()
// 10 POST /docs/documents/:id/move   (DocumentsMove: anyOf folderId | fileName)
joi.object({ baseVersion: version().required(), folderId: joiUlid(), fileName: joi.string(),
  sessionId: joiUlid() }).or('folderId', 'fileName').strict()
// 11 DELETE /docs/documents/:id — QUERY (validateQueryParams, convierte: N llega como número)
joi.object({ baseVersion: version().required() })
// 12 POST /docs/documents/:id/restore
joi.object({ fromVersion: version().required(), baseVersion: version().required() }).strict()
// 13 POST /docs/documents/:id/lock   (DocumentsLock.ttlSeconds: 30..300)
joi.object({ sessionId: joiUlid().required(), ttlSeconds: joi.number().integer().min(30).max(300) }).strict()
// 14 POST /docs/documents/:id/unlock
joi.object({ sessionId: joiUlid().required() }).strict()
// 15 POST /docs/attachments   (AttachmentUploadRequest; Checksum del contrato)
joi.object({ id: joiUlid(), documentId: joiUlid().required(), fileName: joi.string().required(),
  mimeType: joi.string().required(), fileSize: joi.number().integer().min(1).required(),
  checksum: joi.string().pattern(/^sha256:[0-9a-f]{64}$/).required() }).strict()
// 16 POST /docs/attachments/:id/confirm — sin cuerpo (Express 5: req.body undefined) o {}
joi.object({}).strict()
// 18 GET /docs/documents/:id/shares — QUERY
joi.object({ status: joi.string().valid('active', 'revoked', 'expired'),
  limit: joi.number().integer().min(1).max(PAGE_LIMIT_MAX).default(50), cursor: joi.string().max(500) })
// 19 POST /docs/documents/:id/shares
joi.object({ id: joiUlid(), mode: joi.string().valid('latest', 'pinned').required(), version: version(),
  expiresAt: joi.string().isoDate().required(), includeAttachments: joi.boolean(),
  note: joi.string(), acknowledgeSecretWarning: joi.boolean() }).strict()
// 20 DELETE /docs/shares/:id — sin cuerpo ni query (no lleva validador)
```

- Rutas 11 y 18 (query): el handler toma los valores tipados con `SCHEMA.validate(req.query).value`
  (patrón de S-078: `validateQueryParams` valida pero no convierte, y `req.query` es de solo lectura
  en Express 5).
- `joi.string()` sin `.allow('')` rechaza `''` en `fileName`, `mimeType`, `message`, `note` (el
  contrato tiene `minLength: 1` en `fileName`/`mimeType` del adjunto; para `message`/`note` vacíos
  no hay motivo para mandarlos). `content: ''` **sí** se acepta (el contrato no fija mínimo).
- Rutas 16 y 20: Express 5 deja `req.body` en `undefined` sin cuerpo; `joi.object({}).validate(undefined)`
  no da error. La 20 no lleva validador (como `DELETE` de S-078 no hay; el path es todo su input).

#### Checksum del texto (DD-8, CA-S7)

```ts
// lib/modules/docs/checksum.ts
import { createHash } from 'crypto';

/** `Checksum` de jiku-docs (`^sha256:[0-9a-f]{64}$`) del contenido que la api envía (DD-8). */
export function contentChecksum(content: string): string {
  return 'sha256:' + createHash('sha256').update(content, 'utf8').digest('hex');
}
```

Fórmula del story (verbatim): `checksum = "sha256:" + hex(sha256(utf8(content)))`. Se calcula
**sobre el mismo string que va en `content`** (el de `req.body`, sin normalizar finales de línea ni
espacios): describe los bytes que la api envía. Vectores verificados con `node:crypto`:

| `content` | `checksum` |
|---|---|
| `''` | `sha256:e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855` |
| `'abc'` | `sha256:ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad` |
| `'# Acta\n\nKickoff con Acme.\n'` | `sha256:56ef0169a0ce1c72ce999efd5044f748c00da07d58ec73958f2b9057ab7c87c5` |
| `'# Acta v2\n'` | `sha256:1071fceb411ffa95f20a102482770ef3f419ea029e4296f3ac3aae7aa362d2ee` |
| `'Año\n'` (UTF-8) | `sha256:af8a9a5924d037f8b26da7db93567aef77b6d7a77299d476e3812ff5f8436fd2` (en `latin1` daría `6329568f…`: el test lo distingue) |

#### ULID de alta (DD-8, CA-S7)

`generateUlid()` de `@jiku/nats-protocol` (movido desde core en S-077; firma
`generateUlid(now: number = Date.now()): string`). Rutas 8, 15 y 19: `id: req.body.id ??
generateUlid()`. Si el cliente lo manda, se valida con `joiUlid()` y se envía **tal cual** (es lo que
hace idempotente un reintento: jiku-docs responde `already_exists` al segundo alta con el mismo id).
El `sessionId` **no** lo genera la api (DD-8: lo genera la web) y es obligatorio en lock/unlock.

#### Ids de path

Mismo criterio que S-078 (P-1 de su plan): **forma** con `isUlid`, y un id malformado responde 404
con el `*_not_found` del recurso, **sin llamar al bus** (idéntico a un id inexistente):

#### Ruta 19 — `sharing_not_configured` (DD-14, CA-S9)

```ts

  return res.status(404).json({ code: 'sharing_not_configured', message: 'Los links compartidos no están configurados' });

```

- `docsFeatures()` (`lib/modules/docs/features.ts`, S-077) lee `process.env.JIKU_PUBLIC_URL` en cada
  llamada: ausente o en blanco → `sharing: false`. **Se reusa, no se relee el env a mano**: es la
  misma regla que `GET /modules` informa como `features.sharing` (DD-13), y así las dos no pueden
  divergir.
- Orden en el handler: `isUlid(id)` → `sharing` → `moduleCommand`. Sin llamada al bus.

- **Solo la 19.** Listar (18) y revocar (20) funcionan sin `JIKU_PUBLIC_URL`: revocar un link

- **`token` y `url` nunca se loguean** (story, *Seguridad*): el handler no loguea `data`; el único
  `logger.error` es el del `catch`, con `error.message`. Lo mismo para `uploadUrl` (15) y `content`
  (8, 9).

#### Ruta 13 — lock idempotente (CA-S8)

La api **no** guarda estado del lock: repetir `POST …/lock` con el mismo `sessionId` publica
**exactamente el mismo payload** (`{ sessionId, via: 'human', ttlSeconds? }`), y jiku-docs lo renueva
(especificación §5, *Idempotencia*: *"Tomar un lock que la misma sesión ya tiene lo renueva"*). La
respuesta es el `data` tal cual: `200 { id, sessionId, expiresAt }` con el `expiresAt` nuevo.

Estructura del handler (patrón de `docs-attachments-id-get.ts`, adaptado a escritura):

```ts
async function updateDocument(req: Request, res: Response) {
  const id = String(req.params.id);
  // El `id` entra al subject (`documents.{id}.update`): se valida antes del bus (ADR-002).
  if (!isUlid(id)) return respondDocsNotFound(res, 'document_not_found');

  const { content } = req.body;
  try {
    const data = await moduleCommand(res, 'docs', `documents.${id}.update`, {
      ...pickDefined(req.body, ['baseVersion', 'content', 'sessionId', 'message']),
      checksum: contentChecksum(content),
      via: 'human',                 // DD-9: lo fija la api
    });
    if (!data) return;              // el embudo ya respondió el error (409 incluido)
    return res.status(200).json(data);
  } catch (error: any) {
    // Nunca se loguea `content` ni el payload.
    logger.error(`PUT /api/docs/documents/:id updateDocument error: ${error.message}`);
    return res.status(500).json({ code: 'internal_error', message: 'Internal error' });
  }
}

router.put('/docs/documents/:id', requireModule('docs'), hasAnyRole(['admin', 'user']), validateBodyFields(UPDATE_SCHEMA), updateDocument);
```

> El orden de claves del payload no importa para `deepEqual` de should, pero el **conjunto** sí:
> ninguna clave `undefined` (`pickDefined`), y `via`/`checksum` siempre presentes en 8 y 9.

### Flow Context

Los flujos `documentos-desde-la-web` (nuevo) y las notas de `escritura-por-el-bus` /
`subida-de-archivos` los escribe S-085. Se copian los escenarios del REQ-016 que este plan
implementa (lado api):

> **Escenario C: edición con lock y versión base (CA-17, CA-18, CA-29, CA-30)**
> 1. **[web]** genera `sessionId` (ULID) y llama `POST /api/docs/documents/{id}/lock { sessionId }`.
>    - `409 document_locked` → solo lectura con "{holder} lo está editando hasta {expiresAt}".
> 2. **[api]** `documents.{id}.lock { actor, sessionId, via: "human" }` → `{ id, sessionId,
>    expiresAt }` (TTL default 120 s).
> 3. **[web]** renueva cada 60 s repitiendo el lock con el mismo `sessionId` mientras el editor está
>    abierto (CA-29).
> 4. **[web → api]** guardar: `PUT /api/docs/documents/{id} { baseVersion: 6, content, sessionId }`.
> 5. **[api]** calcula `checksum = "sha256:" + hex(sha256(utf8(content)))` y publica
>    `documents.{id}.update { actor, baseVersion: 6, content, checksum, sessionId, via: "human" }`.
>    - Éxito → `200 { id, version: 7 }`; la web libera con `POST …/unlock { sessionId }`.
>    - **`version_conflict`** → `409 { code, message, details: { currentVersion: 7 } }` (CA-17).
>    - **`document_locked`** → `409 { …, details: { holder, via, expiresAt } }` (CA-18).
> 6. **[web]** cancelar o salir: `unlock`. Cierre de pestaña: `pagehide` → BFF de la web con
>    `keepalive`. Si nada de eso llega, el lock vence a los 120 s.

> **Escenario D — subida (CA-19, CA-33), lado api**
> El editor pide `POST /api/docs/attachments { documentId, fileName, mimeType, fileSize, checksum }`
> (checksum SHA-256 calculado en el navegador con `crypto.subtle`), hace `PUT` a `uploadUrl` con el
> `putFileToStorage` existente, llama `…/confirm` e inserta `![nombre]({link})`. Por dentro
> jiku-docs delega en `files.request-upload` / `files.{fileId}.request-download` de core (D-3): el
> archivo **nunca** se vincula (RF-11, CA-15).

> **Escenario E: link compartido (CA-20 a CA-24, CA-31, CA-32), pasos de la api autenticada**
> 1. **[web]** botón "Compartir" visible solo si `features.sharing` y `folder.effectivePermission ===
>    'manage'` (CA-32). Diálogo: vencimiento (default 30 días, máx. 180), nota, adjuntos sí/no.
> 2. **[api]** `POST /docs/documents/{id}/shares` → `shares.new { actor, id: ulid, documentId, mode:
>    "latest", expiresAt, includeAttachments, note }`.
>    - `secret_warning_not_acknowledged` → la web pide confirmación explícita y reenvía con
>      `acknowledgeSecretWarning: true`.
> 3. **[web]** muestra `url` **una vez** con "Copiar"; la lista (`GET …/shares`) muestra estado,
>    vencimiento, nota, accesos y último acceso, **nunca** el token (CA-31). "Revocar" →
>    `DELETE /docs/shares/{id}`.
> (Pasos 4-8, la página pública, son S-080.)

- **Un archivo por endpoint**, nombre = path con `-` + verbo (`docs-documents-id-lock-post.ts`),

  `@jiku/nats-protocol`.
- **Comentarios en español, el porqué**, citando REQ-016 / DD-x / CA-x / H-3.
- **JSDoc de ruta** como `docs-attachments-id-get.ts`: `@name`, `@description`, `@route {VERBO} /api/...`,

## Hallazgos y decisiones de este plan

Lo que la story deja abierto y este plan fija, para que la implementación no lo improvise:

| # | Punto | Decisión |
|---|---|---|
| P-1 | Id de path malformado | 404 `*_not_found` sin llamar al bus (criterio de S-078). Obligatorio donde el id entra al subject (9-14, 16, 20) |
| P-2 | Status de éxito de 10, 11, 12, 14, 16, 18, 20 | 200 con el `data` sin transformar (el REQ fija solo 8, 9, 13, 15 y 19) |
| P-3 | Qué valida Joi | Forma (tipos estrictos, obligatorios, ULID, claves no declaradas → 400). Las reglas de dominio (patrón de `fileName`, tamaño de `content`, rango de `expiresAt`, `version` con `pinned`) las valida jiku-docs para que su código llegue sin traducir |
| P-4 | Mensaje de `share_not_found` local | `'Link compartido no encontrado'` |
| P-5 | Mensaje de `sharing_not_configured` | `'Los links compartidos no están configurados'` |
| P-6 | `id` opcional en el body de la 19 | Se acepta (DD-8 nombra `shares.new` entre las altas cuyo id genera la api *"si el cliente no manda `id`"*), aunque la tabla de forma del REQ no lo liste |
| P-7 | `sharing_not_configured` en 18 y 20 | No: listar y revocar funcionan sin `JIKU_PUBLIC_URL` |

**Resolución de los puntos abiertos (decisión delegada por el dueño del producto en la corrida de implementación):**

1. **Límite del body JSON — RESUELTO en esta story.** `app.ts` monta, **antes** del `express.json()`
   global, un `express.json({ limit: '768kb' })` que se aplica solo a `POST` y `PUT` bajo `/api/docs`
   (`DOCS_WRITE_BODY_LIMIT`). Al dejar el body leído, el parser global lo saltea: el resto de la api
   conserva los 100 kb por defecto de body-parser. 768 KiB = 256 KiB de `content` con 2x de expansión por
   el escapado de JSON (un `\n` ocupa dos bytes) y holgura para el sobre; lo que supere eso sigue siendo
   413. Fijado por tests: `docs-documents-post.test.ts` y `docs-documents-id-put.test.ts` (contenido de
   262144 caracteres y de 262144 saltos de línea pasan; 900 KiB es 413) y `docs-body-limit.test.ts`
   (`PUT /week-assigned-times` y `POST /clients` con 150 kb siguen en 413).
2. **Alta sin `id` no es idempotente — LIMITACIÓN CONOCIDA.** Si el cliente no manda `id`, cada reintento
   tras un 504 genera un ULID nuevo. Recomendación para S-082/S-083: que la web mande siempre `id` en las
   altas. Queda dicho en la descripción de `ModuleGatewayTimeout` y de la operación `POST /docs/documents`.
3. **Documentos > 256 KiB — LIMITACIÓN CONOCIDA.** No se pueden crear ni editar por estas rutas: el REQ no
   expone `contentUploadId` / `documents.request-content-upload`. Coherente con el supuesto de la captura
   (la web los abre en solo lectura). Anotado para que no se lea como omisión.
