# Story Plan: S-033 (core) - El workflow de estados del requisito nace en `core`

## Status

**Status:** Completed

**Progress:** 6/6 tareas completadas

## Story Reference

- **Story:** [S-033](../stories/S-033.el-workflow-de-estados-del-requisito.md)
- **Service:** `core`
- **Summary:** La secuencia `analisis → planificacion → en_cola → desarrollo → revision` —con las
  incidencias salteando `en_cola`— nace como **tabla de transiciones declarada en `core`**,
  validada en `requirements.{id}.edit` y en `requirements.{id}.resolve` compartiendo el mismo
  validador. El mismo validador aplica C-17 (tipo y conclusión obligatorios al resolver).

## Hallazgos que hay que leer antes de escribir código

### H-1 · Un test existente hoy queda en rojo con la tabla nueva

`core/tests/commands/requirements.test.ts:180-185`, test **`'completa las marcas de tiempo al
cambiar de estado'`**, dentro de `describe('requirements.{id}.edit')`:

```ts
beforeEach(async () => {
  const requirement = await Requirement.create({
    title: 'Original', description: 'Descripción original', projectId,
    createdBy: CREATOR,
  });               // sin `state` explícito -> default del modelo: 'analisis'
  requirementId = requirement.id;
});

it('completa las marcas de tiempo al cambiar de estado', async () => {
  await dispatch(`requirements.${requirementId}.edit`, {
    editor: CREATOR, state: 'desarrollo',      // analisis -> desarrollo, SALTEANDO planificacion y en_cola
  });
  const requirement = await Requirement.findByPk(requirementId);
  (requirement!.inProgressAt === null).should.be.false();
});
```

Esta transición es exactamente el caso que **CA-2 exige rechazar**: `analisis → desarrollo`
saltea `planificacion` y `en_cola`, y el requisito no tiene `type: 'incidencia'` (default del
modelo es `undefined`/sin tipo — no aplica la excepción de CA-3, que exige `type === 'incidencia'`
explícito). Con el validador nuevo, este test falla con `invalid_state_transition` en vez de
`success`.

**Tarea 5 lo corrige**: el `beforeEach` de este `describe` necesita crear el requisito ya en un
estado desde el que `desarrollo` sea alcanzable en un paso (`en_cola`), o el test tiene que hacer
la secuencia completa. La forma más simple y menos invasiva: crear el fixture con
`state: 'en_cola'` en ese test puntual (no en el `beforeEach` compartido, que otros tests del
mismo describe usan con el default `analisis` a propósito — ver el test de arriba,
`'registra actividad de title, description y state'`, que hace `analisis -> planificacion` y sigue
siendo válido).

**Antes de tocar código:** correr `npm test` en `core/` y confirmar que este es el único rojo
preexistente relacionado. Si aparece otro, es una regresión distinta y hay que entenderla antes.

### H-2 · `requirements.{id}.resolve` necesita el mismo rechazo de estados terminales, y el contrato no lo declara todavía

`docs/apis/core.yaml:1129` — el canal `RequirementsResolve` declara:

```yaml
x-error-codes: [invalid_fields, requirement_not_found, resolution_required, internal_error, access_denied]
```

**Falta `invalid_state_transition`.** CA-7 exige que `resuelto` y `cancelado` sean terminales
—ninguna transición sale de ahí, tampoco hacia `resuelto` de nuevo por el camino de resolución— y
CA-11 exige que `.resolve` comparta **el mismo validador** que `.edit`. Si el validador se aplica
también en `.resolve` (como debe), un intento de resolver un requisito que ya está en `resuelto` o
`cancelado` tiene que devolver `invalid_state_transition`, y ese código hoy no está en la lista
blanca del canal.

**Esta tarea agrega el código a `x-error-codes` de `RequirementsResolve`** en `docs/apis/core.yaml`
(Tarea 4) — es un ajuste de documentación descubierto al planificar, no un cambio de diseño: la
story ya pide "el mismo validador" y esto es la consecuencia literal en el contrato.

### H-3 · El validador compartido no es el mismo código que hoy exige conclusión en `.resolve`

`requirements-resolve.ts:43-50` ya tiene una validación de conclusión, pero es **local al
comando** y **no lee la tabla de transiciones** (no rechaza un `resuelto → resuelto` ni valida que
el estado de origen sea válido para resolver). La tarea 2 reemplaza esta validación ad-hoc por una
llamada al validador compartido (`validateStateTransition`, Tarea 1), que:

1. Verifica que la transición de origen hacia `resuelto` esté permitida por la tabla (siempre lo
   está desde cualquier estado no terminal, CA-6 declara terminal solo `resuelto`/`cancelado`).
2. Aplica C-17 (tipo + conclusión) cuando el destino es `resuelto`.

El código de error para ambos casos ya existe: `invalid_state_transition` y `resolution_required`.

### H-4 · El `type` que decide la excepción de CA-3 se lee de la fila, nunca del payload

Ni `.edit` ni `.resolve` reciben `type` como parte de la transición: el payload de `.edit` sí
declara `type` como campo editable independiente (cambiar la clasificación del requisito), pero
**la decisión de si `planificacion → desarrollo` está permitida usa el `type` ya persistido en la
fila ANTES de aplicar los `changes` de este mismo payload** — igual que hace hoy
`requirements-resolve.ts:44` con `requirement.type`. Si el payload trae `type` Y `state` en el
mismo edit, la tabla evalúa contra el `type` viejo (pre-cambio); es una decisión de diseño
razonable (evita que alguien cambie el tipo y el estado en el mismo request para colarse por la
excepción) y no está probada hoy — la Tarea 6 agrega el escenario.

## Architectural Context

### Tech Stack

- **Lenguaje:** TypeScript, `strict: true` (`core/tsconfig.json`)
- **Runtime:** Node.js, worker sin HTTP — consumidor NATS puro
- **Validación:** Joi 18.0
- **ORM:** Sequelize (usuario dueño de la base, `@jiku/models`)
- **Testing:** Mocha 11.7 + `should` 13.2 + `sinon` 21.0, contra PostgreSQL real (sin mocks)
- **Bus:** NATS request/reply sin JetStream, `@jiku/nats-protocol` para el envelope `Reply`

### Arquitectura del servicio

```
core/src/
├── bus/dispatcher.ts        # abre transacción, ejecuta comando, decide commit/rollback por status
├── commands/
│   ├── index.ts              # registro único de los 21 comandos
│   ├── types.ts               # interfaz Command<TPayload, TData>
│   ├── validate.ts            # validateWith (Joi), pickPresent (edición parcial)
│   └── requirements/
│       ├── requirements-edit.ts       # A MODIFICAR (Tarea 2)
│       ├── requirements-resolve.ts    # A MODIFICAR (Tarea 2)
│       ├── requirements-new.ts        # sin cambios: crear siempre entra en 'analisis' o el
│       │                              #   estado que declare el payload; no hay transición que
│       │                              #   validar en una creación (no hay "estado previo")
│       ├── requirements-comment.ts    # sin cambios
│       └── requirements-subscriptors.ts  # sin cambios
```

**El comando NO abre ni cierra transacciones** (`commands.md`). El validador de transición se
llama dentro de `execute()`, después de leer la fila (`findByPk`) y antes de escribir — es una
"regla de negocio" en el orden canónico de `execute` (paso 3 de la lista: *"Validar las reglas de
negocio"*).

### La interfaz `Command` (convención `commands`)

```ts
// core/src/commands/types.ts
export interface Command<TPayload = any, TData = unknown> {
  readonly pattern: string;
  validate(payload: unknown): { value: TPayload } | { error: Reply<never> };
  execute(payload: TPayload, ctx: CommandContext): Promise<Reply<TData>>;
}

export interface CommandContext {
  caller: string;
  params: Record<string, string>;
  transaction: Transaction;
}
```

**Orden dentro de `execute` (los 20 comandos existentes lo siguen):**
1. Buscar la entidad del `params`, responder `*_not_found` si no está.
2. Validar las referencias del payload.
3. **Validar las reglas de negocio** (tope diario, conclusión de incidencia) — **acá va el
   validador de transición**.
4. Calcular lo que necesita el estado anterior.
5. Escribir, siempre con `{ transaction: ctx.transaction }`.
6. `success()` o `success({ id })`.

### El patrón module-constant (precedente: S-030, `ROLE_METHODS`)

La story pide explícitamente la misma forma que el mapa rol → comando de S-030
(`core/src/authorize-caller.ts`): **una constante de módulo, deny-by-default, dato y no código**.
Forma de referencia (adaptada; ver `authorize-caller.ts` completo para el precedente real):

```ts
// forma general del precedente: un Record<clave, valor[]> como tabla exhaustiva
const ROLE_PERMISSIONS: Record<Role, RolePermissions> = {
  admin: { commands: ALL },
  user: { commands: [...] },
  'external-user': { commands: [] },   // deny-by-default: lo que no está, no se autoriza
  // ...
};
```

Este mismo criterio aplica a la tabla de transiciones de esta story: un `Record` de estado de
origen a los estados de destino permitidos, consultado con una función pura, sin condicionales
repartidos.

### Reply / manejo de errores (convención `error-handling`)

```ts
export interface Reply<T = unknown> {
  status: 'success' | 'failure';
  errorCode?: string;
  errorMessage?: string;
  data?: T;
}
export function success<T>(data?: T): Reply<T>;
export function failure(errorCode: string, errorMessage: string): Reply<never>;
```

- **Nunca se lanza** para señalar un error esperado: se devuelve `failure(...)`.
- Se usa la **constante** `ErrorCode.X`, no el literal — la convención documenta como deuda
  conocida que `resolution_required` se emite hoy como literal en
  `requirements-resolve.ts:49`; **esta story lo corrige al tocar ese archivo** (pasar a
  `ErrorCode.RESOLUTION_REQUIRED`), siguiendo la instrucción explícita de la convención: *"Al
  tocar ese archivo, pasalo a la constante."*
- `invalid_state_transition` y `resolution_required` **ya existen** en el catálogo de
  `@jiku/nats-protocol` (`packages/nats-protocol/src/index.ts:375,377`):
  ```ts
  INVALID_STATE_TRANSITION: 'invalid_state_transition',
  RESOLUTION_REQUIRED: 'resolution_required',
  ```
  **No hay que agregar nada al paquete.**
- Los mensajes van en **español**, sin datos internos. El mensaje existente para
  `resolution_required` sirve de referencia: `'Se requiere tipo y conclusión para resolver una
  incidencia'`. Para `invalid_state_transition`, sugerido: `'Transición de estado no permitida'`
  (sin exponer la tabla completa en el mensaje).

### Validación (convención `validation`, Joi)

- `validate` **no toca la base**: corre antes de la transacción. La tabla de transiciones consulta
  el `state` **de la fila**, así que **no puede vivir en `validate`** — vive en `execute`, después
  de `findByPk`.
- El esquema Joi de `.edit` y `.resolve` no cambia de forma (siguen aceptando los mismos campos);
  el validador de transición es una regla de negocio adicional dentro de `execute`, no una regla
  de esquema.

### API Context — los dos canales a modificar

**`requirements.{id}.edit`** — `docs/apis/core.yaml:535-590` (contrato YA actualizado con la tabla
como documentación; el código todavía no la aplica):

```yaml
x-error-codes:
  - invalid_fields
  - requirement_not_found
  - invalid_responsible_person
  - file_not_owned
  - invalid_state_transition      # YA declarado en el contrato
  - resolution_required           # YA declarado en el contrato
  - internal_error
  - access_denied
```

La tabla de transiciones documentada en `core.yaml` (sección `x-req-007-state-workflow` del
canal), copiada verbatim porque es la especificación exacta a implementar:

```
analisis  ->  planificacion  ->  en_cola  ->  desarrollo  ->  revision
                     └──────── incidencia ────────┘
```

| Desde | Hacia (permitido) |
|---|---|
| `analisis` | `planificacion` |
| `planificacion` | `en_cola`, **`desarrollo` solo si `type === 'incidencia'`** |
| `en_cola` | `desarrollo` |
| `desarrollo` | `revision` |
| `revision` | `resuelto` |
| *cualquier estado no terminal* | `cancelado` |
| *cualquier estado no terminal* | `resuelto` **por el camino de resolución** (exige tipo + conclusión, C-17) |
| `resuelto`, `cancelado` | *(terminales — ninguna transición sale de acá)* |
| *un paso hacia atrás en la secuencia* | permitido |

Cualquier otra combinación: `invalid_state_transition`. Una transición a `resuelto` sin tipo o sin
conclusión: `resolution_required`.

**`type` se lee de la FILA, no del payload** — un caller no puede declararse `incidencia` para
saltear `en_cola` (ver H-4 arriba sobre el orden de lectura cuando `type` y `state` llegan juntos).

**`requirements.{id}.resolve`** — `docs/apis/core.yaml:593-620`:

```yaml
x-error-codes: [invalid_fields, requirement_not_found, resolution_required, internal_error, access_denied]
# + invalid_state_transition (Tarea 4, ver H-2)
```

Nota **"DEAD SURFACE" YA REESCRITA** en el documento (no hay que tocar la prosa, solo agregar el
código a `x-error-codes`):

> **NO HTTP ROUTE PUBLISHES IT — but the rule IS enforced (REQ-007, S-033).** [...] Both channels
> now share the SAME validator — the state transition table (C-15) and the mandatory type +
> conclusion (C-17) — so the rule applies **whichever way the change arrives**.

### Flow Context — `alta-requisito-desde-portal.md`

Del flujo (`docs/flows/alta-requisito-desde-portal.md`), la nota que esta story invierte:

> **El requisito nace siempre en `analisis`.** El portal lo muestra como chip fijo y core lo
> valida por default, pero **la secuencia posterior del workflow solo se valida en `web`**
> (NFR-S07): por esta misma superficie se puede llevar un requisito a cualquier estado.

Después de esta story, esa nota queda invertida: la secuencia se valida en `core`, sea cual sea el
cliente. **Paso 6 del flujo** (`requirements.new`) no cambia — la creación no valida transición
(no hay estado previo) — el cambio afecta a `requirements.{id}.edit`, que es un flujo distinto no
detallado paso a paso en este documento (la story no referencia un flujo de edición dedicado).

### Reusable Code

Del catálogo de `core` (`docs/reusable-code/core/index.md`) — nada directamente reusable para
una tabla de transiciones nueva; el precedente relevante es código de servicio
(`authorize-caller.ts`, S-030), ya citado arriba como forma de referencia, no como función a
importar (vive en otro dominio: autorización de caller, no de estado del dominio).

### Code Conventions aplicables

- Archivos: `kebab-case.ts`. Constantes de módulo: `SCREAMING_SNAKE_CASE`.
- Comentarios **en español**, explican el **por qué**, no el qué.
- Imports relativos, sin alias.
- Un comando nuevo son tres pasos (archivo + registro + tests) — **no aplica acá**: no hay comando
  nuevo, se modifican dos existentes.
- La ubicación natural para la tabla y la función de validación: un archivo nuevo
  `core/src/commands/requirements/state-transitions.ts` (helper del módulo, mismo patrón que
  `projects/properties.ts` o `tasks/priority.ts` citados en la convención `contract-translation`
  para helpers de un dominio).
