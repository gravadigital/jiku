### Fuera de alcance (declarado, para no improvisarlo)

- **Los dos handlers finales de `app.ts` (fallback 404, líneas 78-89) no se tocan.** H-6 de REQ-017 los
  declara defecto previo fuera de alcance. El manejador nuevo va **después** de ellos y delega el
  objeto `{ status: 404 }` que arma el primero con `next(err)`: una ruta inexistente sigue terminando en
  el 404 por defecto de Express (cuerpo HTML), igual que hoy (CA-3).
- **No se declara `413` fuera de las nueve escrituras de `/docs/*`** aunque el manejador aplique a toda
  la api (R-5). Es un desfase previo; lo anota el plan `S-088.docs` en ADR-015.
- **No se cambia `DOCS_WRITE_BODY_LIMIT`** (`'768kb'`) ni el límite global (100 kb de body-parser), ni el
  orden de los parsers.
- **No se toca `docs-shares-id-delete.ts`**: DD-4 corrige el contrato, no el handler.
- **Ningún otro error cambia de forma**: un JSON malformado (`entity.parse.failed`, 400), un charset no
  soportado, etc. siguen yendo al `finalhandler` como hoy.
- **Sin cambios de base de datos, variables de entorno, dependencias npm ni bus.**
- **`README.md`, `documentation/*`, `docs/prd/architecture.md`, ADR-015 y los flujos** son del plan
  `S-088.docs`.

### El estado actual de `api/app.ts` (lo relevante, verbatim)

```ts
export const DOCS_WRITE_BODY_LIMIT = '768kb';
const docsJsonParser = express.json({ limit: DOCS_WRITE_BODY_LIMIT });
function docsWriteJson(req: Request, res: Response, next: NextFunction) {
  return req.method === 'POST' || req.method === 'PUT' ? docsJsonParser(req, res, next) : next();
}
// ...
  app.use(publicHostOnly);
  app.use(cors());
  app.use('/api/docs', docsWriteJson);   // línea 46
  app.use(express.json());               // línea 47 (100 kb por defecto)
  app.use(express.urlencoded({ extended: true }));
  app.use(express.static(path.join(__dirname, 'public')));
  app.use(expressWinston.logger({ ... }));
  app.get(publicPaths('get'), validateToken);   // ... y patch/post/put/delete
  app.use(publicRoutes);
  for (const key of Object.keys(routes)) {
    app.use('/api', routes[key as keyof typeof routes]);
  }

  app.use(function (_req, _res, next) {           // línea 78
    const err = { message: 'Not Found', status: 404, stack: {}, };
    next(err);
  });

  app.use((res: Response) => {                    // línea 83 — un argumento: no es error handler
    console.error('Not Found');
    return res.status(400).json({ status: 'not_found', message: 'Not Found' });
  });
  return app;                                     // línea 90
```

**Cómo viaja el error hoy (H-6):** el parser lanza `PayloadTooLargeError` con `next(err)`. Express salta
toda capa de aridad distinta de 4 — validateToken, los routers del barrel (`Router` es una función de 3
argumentos), el fallback de la línea 78 y el de la 83 — y, como no hay ningún manejador de cuatro
argumentos a nivel app, el error llega al `finalhandler`, que responde `413 text/html` ("Payload Too
Large", con el stack fuera de producción). El `multerErrorHandler` de `attachments-post.ts` está montado
**dentro** de su router, que no se invoca en modo error, así que no intercepta.

**Lo que cambia:** un `app.use(payloadTooLargeHandler)` justo antes de `return app;`. Como es la última
capa y la única de cuatro argumentos a nivel app, recibe:
- el `PayloadTooLargeError` de cualquiera de los dos parsers JSON (o del `urlencoded`) → responde 413 JSON;
- el `{ message: 'Not Found', status: 404, stack: {} }` del fallback de la línea 78 → `next(err)` → el
  `finalhandler` responde 404 como hoy;
- cualquier otro error (p. ej. `entity.parse.failed`) → `next(err)` → sin cambio.

### Convenciones activas que aplican (extracto)

**`error-handling`** (custom), reglas verbatim que aplican:
- Respondé con `res.status(n).json({ code, message })`. No introduzcas clases de error ni `throw` en handlers.
- `code` es `snake_case` y estable: los fronts hacen `switch` sobre él.
- `message` es texto de interfaz. Nuevos mensajes de usuario, en español.
- Un middleware que responde **no** llama a `next()`.
- Un error handler de Express lleva **cuatro** argumentos y delega lo que no reconoce con `next(err)`.
- Usá `logger`, nunca `console`.

El modelo explícito de la convención es el `multerErrorHandler` (`lib/routes/attachments-post.ts:138-150`):
*"cuatro argumentos, tratá lo que reconocés, delegá el resto con `next(err)`"*.

> **Sobre "si tocás el manejo de 404, arreglá los dos handlers juntos":** este plan **no** toca el manejo
> de 404. El manejador nuevo solo reconoce `entity.too.large`; el 404 lo delega intacto. La convención
> no se dispara (y H-6 lo deja fuera de alcance).

**`logging`:** el manejador **no loguea**. Un 413 es un error del cliente, no un error inesperado (la regla
"todo error inesperado se loguea con contexto" no aplica), y la línea tendría que llevar la URL, que en
`/p/docs/*` contiene el token del link (el logger de `express-winston` excluye esas rutas por eso). Además
el 413 ocurre antes de que se monte `expressWinston.logger`, así que hoy tampoco queda registro: no
cambia.

**`http-server` / `_base`:** comentarios en español, imports relativos, la función con nombre en el
mismo archivo (precedente: `docsWriteJson`, también en `app.ts`).

**`testing`** (custom), reglas verbatim que aplican:
- No llames a `setBus`: el doble ya está instalado y se resetea por root hook.
- Aserciones con `should`. No mezcles `assert` ni `expect`.
- Un test no depende del orden de ejecución ni del estado que dejó otro.
- Los tests de contrato (`tests/utils/api-contract.test.ts`) **leen líneas, no parsean YAML** (no se
  agrega `js-yaml`): mismo molde que los `describe` existentes.

api, `{ code, message }`, y `PayloadTooLarge` referencia `#/components/schemas/Error`, no `ModuleError`.

**Status:** Completed

#### Description

`return app;`, después de los dos handlers del fallback 404, que no se tocan).

#### Acceptance Criteria

- `err?.type === 'entity.too.large'` y `!res.headersSent` → `res.status(413).json({ code: 'payload_too_large', message: 'El cuerpo de la solicitud supera el límite permitido' })`, sin llamar a `next`.
- Cualquier otro caso → `return next(err);` (incluye el `{ status: 404 }` del fallback y `entity.parse.failed`).
- No loguea (ver *logging* en el Architectural Context). No usa `console`.
- Nada más de `app.ts` cambia: ni el orden de los parsers, ni `DOCS_WRITE_BODY_LIMIT`, ni los handlers de las líneas 78-89.

#### Technical Details

```ts
/**
 * DD-3 de REQ-017: el 413 de body-parser (`entity.too.large`, de cualquiera de los parsers: el de
 * /api/docs con 768 KiB o el global con 100 kb) sale con la forma de error de toda la api en lugar del
 * HTML del finalhandler. Cuatro argumentos, y todo lo que no reconoce sigue su camino con next(err): el
 * 404 del fallback de arriba y cualquier otro error no cambian. No loguea: es un error del cliente, y en
 * /p/docs/* la URL lleva el token del link.
 */
function payloadTooLargeHandler(err: any, _req: Request, res: Response, next: NextFunction) {
  if (err?.type === 'entity.too.large' && !res.headersSent) {
    return res.status(413).json({
      code: 'payload_too_large',
      message: 'El cuerpo de la solicitud supera el límite permitido',
    });
  }
  return next(err);
}
```

```ts
  // ... fallback 404 (líneas 78-89, sin cambios)
  // DD-3: AL FINAL de la cadena, para recibir el error de cualquier parser sin interceptar nada más.
  app.use(payloadTooLargeHandler);
  return app;
```

- Ubicación de la función: en `app.ts`, junto a `docsWriteJson` (mismo precedente de función con nombre en
  el archivo). Los tipos `Request`, `Response`, `NextFunction` ya están importados (línea 1).
- `any` en `err`: borde con una librería (body-parser), permitido por `_base`; el comentario lo justifica.
- **Architectural Context References:** convención `error-handling` (reglas de cuatro argumentos y

## Hallazgos y decisiones de este plan

- **H-1 — El yaml va en el plan de la api.** La fila `docs` de la story incluye `api.yaml`, pero el test de
  contrato de la api afirma `los 88 endpoints` en dos lugares: si el plan `docs` cambia el encabezado solo,
  rompe la suite de la api (CA-7). Precedente: `S-078.api` Tarea 8 y `S-087.api` Tarea 3.
- **H-2 — El 413 corta antes que todo.** `docsWriteJson` está montado antes de `validateToken` y de
  `requireModule`: una escritura grande responde 413 aunque el módulo no esté instalado (TS-3) o falte el
  token. No es un cambio de este plan (el orden ya era así); el manejador solo cambia la forma del cuerpo.
- **H-3 — El manejador también cubre el resto de la api** (límite global de 100 kb y `urlencoded`), como
  anticipa DD-3 / R-5. Los dos tests existentes de S-079 (TS-4, TS-5) lo pasan a afirmar. El contrato no lo
  declara fuera de `/docs` (pendiente para ADR-015, plan `S-088.docs`).
- **H-4 — `docs/architectures/api/conventions/error-handling.md` ("Los dos handlers finales de `app.ts`")
  queda incompleta**: después de este plan hay un tercer handler, el primero de cuatro argumentos a nivel
  app. La story no la lista en "Documentación a actualizar"; **NOT DOCUMENTED - needs verification**: se
  sugiere sumarla al plan `S-088.docs` (agregar el manejador del 413 y `payload_too_large` a la tabla
  "Códigos por situación").
- **H-5 — R-4 sigue aceptado.** Si jiku-docs respondiera `invalid_fields` a `shares.{id}.revoke`, saldría
  un 400 no declarado. Se mantiene DD-4.
