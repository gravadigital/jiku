### Fuera de alcance (declarado, para no improvisarlo)

- **`validateToken`, `api/config/public.ts` y `getRolesFromToken` no se tocan** (CA-11). Ninguna ruta nueva es pública.
- **`buildActor` y el embudo `call()` no se tocan**: las rutas nuevas usan `moduleQuery`/`moduleCommand` y heredan el
  `actor` completo.
- **La api no autoriza el dominio** (DD-2): no valida `visibility: restricted`, ni si un `user` puede asignar
  relaciones. Lo decide jiku-docs (`permission_denied`, lista vacía).
- **Sin cambios de base de datos, migraciones, modelos (`packages/models`), variables de entorno, dependencias npm ni
  `@jiku/nats-protocol`.** Solo lecturas con el Sequelize de solo lectura.
- **Sin chequeo de versión de jiku-docs en runtime** (el registro no publica versión menor). Se documenta como
  requisito de instalación.
- `GET /docs/folders`, `GET /docs/folders/{id}`, `POST /docs/documents/{id}/move`, `PUT /docs/documents/{id}`,
  `POST .../lock`, `POST .../restore`, `GET /docs/topics`, `GET /docs/documents/{id}/versions`: **sin cambios de
  código** (los campos 1.3.0 pasan verbatim; `restore` gana `version_pruned` 404 por el mapa). Solo se actualiza su
  documentación (esquemas) en la Tarea 10.
- `folderId` y `pathPrefix` del listado se **conservan** (no rompen; la web deja de usarlos).
- **CHANGELOG raíz:** no se escribe acá (se arma al cortar la release). La entrada de publicación de
  `docs/changelog/` sí (Tarea 10), porque es la fuente que usa el procedimiento de release.

### Convenciones aplicables (extracto)

**`_base`:**
- No hay `src/`: el código va en `lib/`. Un endpoint = un archivo en `lib/routes/` + una línea en
  `lib/routes/index.ts`. Nombre del archivo `{recurso}-{path}-{método}` (`docs-documents-id-relations-post.ts`), export
  del barrel en `PascalCase` (`DocsDocumentsIdRelationsPost`).
- Imports relativos sin extensión; `@jiku/models` por nombre. Orden: express, externos, `@jiku/*`, relativos.
- Constantes de módulo `SCREAMING_SNAKE_CASE`. Comentarios en español, el **por qué**.
- `any` permitido en los bordes con payloads del bus y con Sequelize.
- Lint antes de terminar: `npm run lint --workspace @jiku/api`.

**`http-server`:** el prefijo `/api` lo pone el montaje (`router.get('/docs/suggestions', ...)` responde en
`GET /api/docs/suggestions`). `app.ts` no se toca. JSDoc con `@name`, `@description`, `@route`, `@response` en cada
ruta (patrón de los `docs-*.ts` existentes).

**`validation`:** Joi inline en el archivo de ruta. `validateQueryParams(SCHEMA)` / `validateBodyFields(SCHEMA)`
**validan pero no convierten**: el handler vuelve a correr `SCHEMA.validate(req.query).value` para obtener los valores
tipados (patrón de `docs-documents-get.ts`). Error → `400 { code: 'invalid_fields', message: 'Invalid field - ...' }`.
Las claves no declaradas son 400. Los bodies de escritura van con `.strict()` (sin conversión de tipos).

**`bus-modules` (reglas, verbatim):**
- Una ruta que habla con un módulo declara `requireModule('<módulo>')` **antes** de `hasAnyRole`.
- Usá `moduleQuery` / `moduleCommand` / `runModuleCommand`. Después de la llamada, `if (!data) return;` (o `if (!ok) return;`): la respuesta ya salió.
- **Nunca** armes el `actor` a mano, ni lo tomes del cuerpo, ni le agregues campos: lo inyecta el embudo con `buildActor(res.req)` entero.
- **Nunca** llames a un módulo sin identidad verificada: el embudo responde 401 y no publica.
- **Nunca** loguees `payload`, `options`, el token de un link ni el contenido de un documento. El error de bus se loguea como `[modules] {module} {method}: {error.message}`.
- El cuerpo de error de módulo conserva `code` y `details` tal cual vienen. No traduzcas el `code`.
- Un id de path con forma inválida es 404 `*_not_found` **sin llamar al bus**.
- El estado del módulo se lee de memoria. No consultes el KV ni hagas ping en el request.
- `upstream_unavailable` no se traduce a `unavailable`: no marques el módulo por eso.

**`orm` (reglas, verbatim):**
- No escribas con el modelo.
- `attributes` explícito en los `include`. No traigas relaciones completas.
- `as` explícito cuando la asociación tiene alias.
- Búsqueda de texto con `Op.iLike`, nunca `Op.like`.
- Filtros condicionales con el patrón `reduce`.
- `sequelize.literal` solo cuando no hay operador equivalente, y **nunca** con input del usuario sin escapar.

**`error-handling`:** el `catch` del handler loguea `{MÉTODO} /api/{ruta} {handler} error: ${error.message}` y
responde `500 { code: 'internal_error', message: 'Internal error' }` (patrón de todos los `docs-*.ts`).

**`testing` (reglas, verbatim):**
- Un archivo de ruta nuevo lleva `tests/routes/{mismo-nombre}.test.ts`.
- No mockees Sequelize ni la base. Los tests corren contra PostgreSQL real.
- No prepares el esquema en un archivo de test: lo hacen los fixtures globales.
- Toda mutación se testea con el `FakeBus`, verificando **comando y payload**, no solo el status.
- No llames a `setBus`: el doble ya está instalado y se resetea por root hook.
- Limpiá los datos que creaste en `after` / `afterEach` con `Model.destroy({ where: {} })`. Un test que deja filas contamina al siguiente.
- Todo endpoint con `hasAnyRole` lleva un test por rol rechazado.
- Toda ruta de un módulo opcional usa `itRespectsModuleState` y verifica que el `actor` publicado sea exactamente `expectedActor(<token>)` (el de `buildActor`, entero).
- Toda regla de negocio se testea **en su límite**, no en el centro del rango válido.
- Aserciones con `should`. No mezcles `assert` ni `expect`.
- Un test no depende del orden de ejecución ni del estado que dejó otro.

> Nota: espiar `Client.findAll` / `Project.findAll` con `sinon.spy` para **contar** consultas (TS-12) no es mockear la
> base: la consulta corre igual contra PostgreSQL. Restaurar el spy en `afterEach`.

### ADRs relevantes

**ADR-015: Módulos opcionales del bus** — *Implementation Rules* (verbatim, las aplicables):

- Toda llamada a un módulo **DEBE** pasar por `api/lib/modules/client.ts` (`moduleQuery`/`moduleCommand`/`runModuleCommand`, o `sendToModule` en las rutas que responden HTML). **NO SE DEBE** hablar con un módulo desde un handler con `bus()` directo.
- **NO SE DEBE** usar `sendCommand` ni `withActor` con un módulo: `withActor` sin identidad publica sin `actor` (falla abierto), y para jiku-docs un llamado sin `actor` es el propio servicio (REQ-019).
- El `actor` **DEBE** ser el de `buildActor(res.req)` sin transformar (`{ id, roles, name?, username?, email? }`, el mismo que recibe core; REQ-019) y **DEBE** inyectarlo el embudo, después del spread del payload. **NO SE DEBE** agregarle campos (ni `identityType`) ni armarlo a mano. Sin identidad verificada el embudo **DEBE** fallar cerrado (401 sin publicar). **NO SE DEBE** llamar a un módulo sin `actor` salvo en una ruta pública deliberada (`shares.resolve`/`shares.attachment`).
- Toda ruta de módulo **DEBE** llevar `requireModule('<módulo>')` **antes** de `hasAnyRole`.
- El mapa de errores **DEBE** ser **por módulo** (`docs/errors.ts`); **NO SE DEBE** mezclar con `STATUS_BY_ERROR_CODE` de core. El cuerpo **DEBE** ser `{ code, message, details? }` con `code` sin traducir y `details` verbatim.
- La api **NO DEBE** autorizar el dominio de un módulo (ACL, visibilidad): solo autentica, rutea por superficie y traduce errores.
- Cualquier cambio en `api/config/public.ts` es un **cambio de seguridad** (ADR-008).

Decisiones que esta story **revisa** (se anota como sección "Revisión" en el ADR, Tarea 10):
- *"`GET /docs/documents/{id}` compone dos consultas en serie (`documents.get` + `folders.get` con
  `include: ['effectivePermission']`)"* → se elimina; la composición pasa a ser la de **referencias con nombre**
  (`clientRefs`, `projectRefs`, `requirementRefs`, `taskRefs`) resueltas desde la base, que también se aplica al
  listado y a la búsqueda.
- DD-3 (portal) se mantiene: `visibility: 'public'` forzado y 404 si no es `public`. Con `fields` explícitos,
  **`visibility` tiene que estar en `fields`** o el detalle fallaría cerrado para todos (404 siempre).

**ADR-001 (lectura directa de la base):** "Proyectos, clientes y personas salen de core" se resuelve leyendo la base
de la api (modelo de lectura de core). No se agregan consultas a `jiku-queries`.

**ADR-008 (deny-by-default):** las tres rutas nuevas son `hasAnyRole(['admin','user'])`; `external-user` y un token
sin roles → 403.

### API Context

#### Cadena común

```ts
router.<verb>('<path>', requireModule('docs'), hasAnyRole(['admin', 'user']), validate…(SCHEMA), handler);
```

Errores locales: 404 `module_not_installed`, 503 `module_unavailable`, 504 `gateway_timeout`, 401 `unauthorized`
(sin identidad, sin publicar), 400 `invalid_fields` (Joi), 403 `access_denied` (`hasAnyRole`), 404 `*_not_found`
para id de path no ULID (sin bus).

#### Mapa de errores de jiku-docs (`DOCS_STATUS_BY_ERROR_CODE`), estado final tras esta story

| Status | Códigos |
|---|---|
| 400 | `invalid_fields`, `invalid_cursor`, `file_name_invalid`, `frontmatter_invalid`, `invalid_relation`, `content_too_large`, `checksum_mismatch`, `upload_not_found`, `attachment_type_not_allowed`, `attachment_too_large`, `share_expiry_invalid`, `secret_warning_not_acknowledged`, `semantic_search_not_configured` |
| 403 | `permission_denied`, `sharing_blocked`, `unknown_caller`, `caller_not_authorized` |
| 404 | `document_not_found`, `folder_not_found`, `attachment_not_found`, `share_not_found`, **`version_pruned` (nuevo)** |
| 409 | `version_conflict`, `document_locked`, `lock_not_held`, `already_exists`, `folder_not_empty` |
| 503 | `upstream_unavailable`, `attachments_not_configured` |
| 504 | `query_timeout` |
| 500 | `internal_error` y cualquier código desconocido |

`version_pruned` trae `errorDetails: { requestedVersion, previousAvailable, nextAvailable }` → `details` verbatim.

#### Composición nueva: referencias con nombre (reemplaza `folder`)

| Campo agregado | Dónde | Origen (ids) | Tabla / modelo | Forma |
|---|---|---|---|---|
| `clientRefs` | ítems de `GET /docs/documents`, hits de `GET /docs/search`, `GET /docs/documents/{id}` | `item.clients` | `clients` / `Client` | `[{ id: integer, name: string \| null }]` |
| `projectRefs` | ídem | `item.projects` | `projects` / `Project` | `[{ id: integer, name: string \| null, code: string \| null, clientId: integer \| null }]` |
| `requirementRefs` | solo `GET /docs/documents/{id}` | `document.relations.requirements` | `requirements` / `Requirement` | `[{ id: integer, title: string \| null, projectId: integer \| null }]` |
| `taskRefs` | solo `GET /docs/documents/{id}` | `document.relations.tasks` | `objectives` / `Objective` | `[{ id: integer, title: string \| null, projectId: integer \| null }]` |

Reglas: una consulta `IN` **por tipo y por respuesta** (nunca por ítem); ninguna consulta si no hay ids de ese tipo;
orden = el de la lista de jiku-docs; un id desconocido va con `name`/`title`/`code`/`clientId`/`projectId` en `null`;
un ítem sin la clave (`clients` ausente) produce `[]`; **los campos de jiku-docs no se modifican** (solo se agregan
claves). Deduplicar ids antes del `IN`.

#### `GET /api/docs/documents` — query final

| Param | Joi | → payload de `documents.list` |
|---|---|---|
| `projectId` | entero > 0 o lista (repetido), máx 20 | `filter.projectId: number[]` |
| `requirementId`, `taskId` | entero > 0 (sin cambios) | `filter.requirementId` / `filter.taskId` |
| `clientId` | entero > 0 o lista, máx 20 | `filter.clientId: number[]` |
| `topic` | string 1..500 o lista, máx 20 | `filter.topic: string[]` |
| `folderId` | ULID (sin cambios) | `filter.folderId` |
| `pathPrefix` | string 1..500 (sin cambios) | `filter.pathPrefix` |
| `hasProject`, `hasClient`, `hasTopic` | boolean | `filter.hasProject` / `hasClient` / `hasTopic` |
| `person` | string 1..200 (`sub`) o lista, máx 10 | `filter.or: [{ createdBy: [...] }, { updatedBy: [...] }]` |
| `visibility` | `internal` \| `public` \| `restricted` | `filter.visibility` |
| `myActiveProjects` | boolean; **excluyente con `projectId`** (`.oxor`) | `filter.projectId` = proyectos activos de la persona |
| `count` | boolean | `count: true` **solo** si `true` (la clave no existe si es `false` o falta) |
| `sort` | sin cambios (default `-updatedAt`) | `sort: [sort]` |
| `limit` | 1..200, default 50 | `page.limit` |
| `cursor` | string ≤ 500 | `page.cursor` |

Payload fijo: `include: ['lock', 'topics']`. Response `200 { items: [...item, clientRefs, projectRefs], page }` (el
`page` de jiku-docs sin transformar, con `total` si hubo `count`).

`myActiveProjects=true` sin proyectos → `200 { items: [], page: { limit, returned: 0 } }` **sin llamar al bus** (con
`count=true` se agrega `total: 0` — mismo significado que `PageInfo.total`, decisión de este plan para que la web no
tenga un caso especial). `myActiveProjects=false` no filtra (equivale a ausente).

> **Normalización de listas:** `projectId`, `clientId`, `topic` y `person` se normalizan **siempre a array**
> (Joi `.single()`): `projectId=12` → `filter.projectId: [12]`. Es equivalente para el contrato (`IntOrList` /
> `StrOrList`) y deja un solo camino. Los tests existentes que esperan `projectId: 12` se actualizan a `[12]`.

#### `GET /api/docs/search` — query final

`q` (2..1000, requerido), `projectId` / `clientId` / `topic` (valor o lista, máx 20), `requirementId`, `taskId`,
`pathPrefix`, `hasProject`, `hasClient`, `hasTopic`, `person` (máx 10), `visibility`, `limit` (1..50, default 20).
Sin `cursor`, sin `count`, sin `myActiveProjects`, sin `mode`. Payload `documents.search`:
`{ query: q, mode: 'text', filter: buildDocumentsFilter(query), limit }`. Response `200 { items: [...hit, clientRefs,
projectRefs] }`.

#### `GET /api/docs/documents/{id}`

Una sola consulta: `documents.get { id, version?, include: ['content','relations','topics','lock','attachments'] }`.
Response `200 { ...document, clientRefs, projectRefs, requirementRefs, taskRefs }` — **sin `folder`**. Pasan verbatim:
`prunedVersionsCount`, `createdByName`, `updatedByName`, `lock.holderName`, `visibility: 'restricted'`,
`clients`, `projects`. `version_pruned` → 404 con `details`.

#### `POST /api/docs/documents`

Body Joi `.strict()`: `id?` (ULID), `folderId?` (ULID), `fileName?` (string), `content` (string, admite `''`,
requerido), `message?` (string). Payload `documents.new`: `{ id: body.id ?? generateUlid(), ...pickDefined(body,
['folderId','fileName','content','message']), checksum: contentChecksum(content), via: 'human' }`. Response `201`
con el `data` verbatim: `{ id, version, path, folderId, fileName, warnings? }`.

#### `POST /api/docs/documents/{id}/relations` (nuevo)

- Comando `documents.{id}.relations.update` (subject `…jiku-docs-commands.v1.documents.{id}.relations.update`).
- Body Joi `.strict()`, `.or('add','remove')`:
  ```
  baseVersion: integer >= 1, requerido
  add:    { clients?: int[1..]≤100, projects?: …, requirements?: …, tasks?: … }   (sin otras claves)
  remove: { idem }
  sessionId: ULID, opcional
  ```
- Payload: `pickDefined(body, ['baseVersion','add','remove','sessionId'])`. **Sin `via`** (el contrato lo deriva de
  la clase del caller) y **sin `checksum`**.
- Response `200` con `data` verbatim: `{ id, version, relations: { clients, projects, requirements, tasks },
  warnings? }` (`DocsRelationsResult`).
- Errores: 409 `version_conflict` (`details.currentVersion`) / `document_locked` (`details: { holder, holderName,
  via, expiresAt }`); 400 `invalid_relation` / `invalid_fields` / `frontmatter_invalid`; 403 `permission_denied`;
  404 `document_not_found` (también id no ULID, sin bus); 503 `upstream_unavailable`.
- La regla fina ("un id en add y remove a la vez", "al menos un id") la valida jiku-docs (`invalid_fields`): la api
  solo valida forma.

#### `GET /api/docs/documents/{id}/suggested-relations` (nuevo)

- Consulta `documents.suggest-relations { id }`.
- Response `200 { items: [{ projectId, clientId, score, reason, projectName, projectCode, clientName }] }`: los
  cuatro primeros verbatim; `projectName`/`projectCode` de `projects` por `projectId` (null si `projectId` es null o
  desconocido); `clientName` de `clients` por `clientId` (null si `clientId` es null o desconocido). Orden de jiku-docs.
- Errores: 404 `document_not_found` (también id no ULID, sin bus); 403 `permission_denied`; 503
  `upstream_unavailable`; 400 `invalid_fields`.

#### `GET /api/docs/suggestions` (nuevo)

- Query: `q` (string 1..100, requerido, se usa recortado con `trim()`), `clientId` (entero > 0, opcional), `limit`
  (1..10, default 5, tope **por grupo**).
- Response `200`:
  ```json
  {
    "projects": [{ "id": 12, "name": "Videoconferencia", "code": "VID", "clientId": 4, "clientName": "EXO", "mine": true }],
    "clients":  [{ "id": 4, "name": "EXO" }],
    "persons":  [{ "userId": "zitadel-sub-02", "name": "Victor Vidal" }],
    "topics":   [{ "topic": "video", "documents": 7 }]
  }
  ```
- Reglas:
  - **projects:** `name ILIKE '%q%' OR code ILIKE '%q%'` (+ `client_id = clientId` si vino). Orden: primero los
    **activos de la persona** (`mine: true`), después `status = 'activo'`, después el resto; dentro de cada grupo por
    `name` ascendente. `clientName` del cliente del proyecto (`null` si no tiene). `mine` es `true` solo si el
    proyecto está en `activeProjectIdsOf(sub)`.
  - **clients:** `name ILIKE '%q%'`, orden `name`.
  - **persons:** `people` con `enabled = true` y `user_id IS NOT NULL`, `first_name ILIKE '%q%' OR last_name ILIKE
    '%q%'`, orden `first_name, last_name`; `name = "{firstName} {lastName}"`, `userId = user_id` (el `sub`, lo que
    guardan `createdBy`/`updatedBy`).
  - **topics:** `topics.list { filter: { prefix: q }, page: { limit } }` → `items` verbatim (`{ topic, documents }`).
    El contrato solo ofrece **prefijo** ("vid" encuentra "video", no "pedido-video").
  - `clientId` limita **solo** proyectos (clientes, personas y temas no).
  - Los comodines de `ILIKE` en `q` (`%`, `_`, `\`) se **escapan** (`q='%'` no devuelve todo). Decisión de este plan:
    la sugerencia busca texto, no patrones.
  - Orden de ejecución: primero la base, después el bus. Si `topics.list` falla, la ruta responde el error del módulo
    (el embudo ya respondió): no se devuelven sugerencias parciales.
  - "Buscar «q»" y "Sin proyecto / Sin cliente / Sin tema" los arma la web: la api no los devuelve.

#### `GET /api/opus/docs/documents` y `GET /api/opus/docs/documents/{id}`

- Listado: agrega `fields: ['id', 'title', 'version', 'visibility', 'createdAt', 'updatedAt']` al payload de
  `documents.list` (el resto igual: `filter: { projectId | requirementId, visibility: 'public' }`, `sort:
  ['-updatedAt']`, `page`).
- Detalle: `documents.get { id, include: ['content', 'attachments'], fields: [mismos seis] }`. El chequeo DD-3
  (`visibility !== 'public'` → 404) se mantiene: **por eso `visibility` está en `fields`**.
- Ninguno incluye `path`, `folderId` ni `fileName`. Los nombres de campo existen en `documentFields` de jiku-docs
  (`internal/service/specs.go:67`); un nombre no declarado sería `invalid_fields`.
- La descripción en `api.yaml` deja de mencionar `externalBlocked`.

### Flow Context

**Flujo `documentos-desde-la-web` (vigente, extracto verbatim de lo que esta story cambia):**

> **Paso 1: panel de documentos en una ficha (web)** — Request `GET /api/docs/documents`; Query: `projectId`,
> `requirementId`, `taskId`, `clientId`, `folderId`, `pathPrefix`, `topic`, `sort` (default `-updatedAt`), `limit`
> (1..`PAGE_LIMIT_MAX`, default 50; el panel pide 10), `cursor`. Cadena: `requireModule('docs')` →
> `hasAnyRole(['admin','user'])` → Joi → handler. Subject `{instance}.{apiUserId}.jiku-docs-queries.v1.documents.list`;
> Payload `{ filter, sort: [sort], page, include: ['lock'], actor: { id, roles, name?, username?, email? } }`.
> Response `200` con el `data` de jiku-docs **sin transformar** (`{ items, page }`).
>
> **Paso 2: visor de un documento (web)** — `GET /api/docs/documents/{id}` (query opcional `version`). La api valida
> que `{id}` sea un ULID antes de tocar el bus. Después compone dos consultas en serie, la única composición de la api:
> 1. `documents.get { id, include: ['content','relations','topics','lock','attachments'] }`
> 2. `folders.get { id: document.folderId, include: ['effectivePermission'] }`
> Response `200 { ...document, folder: { id, path, effectivePermission, sharingBlocked } }`.
>
> **Paso 9: lectura desde el portal (opus-web)** — Listar: `GET /api/opus/docs/documents`, query `projectId` o
> `requirementId`; `filter.visibility: 'public'` lo fuerza el handler. Detalle: `documents.get { id, include:
> ['content','attachments'] }`; 404 `document_not_found` si `visibility !== 'public'`.
>
> **Manejo de errores** (fila que cae): "1-8 | Sin permiso sobre la carpeta | 403 | `permission_denied`".

**Qué cambia (lo actualiza la Tarea 10 en el documento):**
- Paso 1: query nueva (listas, `hasProject`, `hasClient`, `hasTopic`, `person`, `visibility`, `myActiveProjects`,
  `count`), `include: ['lock','topics']`, `count: true` opcional, ítems con `clientRefs`/`projectRefs`.
- Paso 2: se elimina `folders.get`; la composición pasa a ser `clientRefs`/`projectRefs`/`requirementRefs`/`taskRefs`
  desde la base.
- Nuevo paso: alta sin carpeta (`documents.new` sin `folderId`/`fileName`, respuesta con `folderId`/`fileName`).
- Nuevo paso: historial (`versions` con `authorName`/`kind`/`protected`, `version_pruned` 404, `restore`).
- Paso 4/5: `document_locked` trae `details.holderName`.
- Paso 9: `fields` sin `path`/`folderId`/`fileName`; se quita `externalBlocked` de la regla de externos.
- Errores: `version_pruned` 404, `sharing_blocked` 403 para `restricted`; se quita "Sin permiso sobre la carpeta".

**Flujo `lectura-por-link-compartido` (cambia solo en documentación):** un `restricted` no admite links
(`sharing_blocked`), pasar a `restricted` revoca los activos (`revokeReason: restricted`), `shares.resolve` de un
`restricted` responde `share_not_found` → el mismo 404 de la página pública. Sin cambios de código.

**Flujo nuevo `buscador-de-documentacion`** (lo crea la Tarea 10), con los escenarios del REQ:
1. web → `GET /api/docs/suggestions?q=vid&clientId=4` → api: base (proyectos del cliente 4 que coinciden, los de la
   persona primero; clientes; personas) + `topics.list { filter: { prefix: 'vid' }, page: { limit: 5 }, actor }` →
   `200 { projects, clients, persons, topics }`.
2. web → `GET /api/docs/documents?clientId=4&projectId=12&sort=-updatedAt&limit=20&count=true` → api:
   `documents.list { filter: { clientId: [4], projectId: [12] }, sort: ['-updatedAt'], page: { limit: 20 }, include:
   ['lock','topics'], count: true, actor }` + `clients`/`projects` `WHERE id IN (...)` → `200 { items: [{ ...,
   projectMatch, clientRefs, projectRefs }], page: { limit, returned, cursor?, total } }`.
3. "Sin proyecto": `GET /api/docs/documents?hasProject=false&limit=20&count=true`; por fila
   `GET /api/docs/documents/{id}/suggested-relations`; "Asignar" → `POST /api/docs/documents/{id}/relations
   { baseVersion: item.version, add: { projects: [12] } }` → `documents.{id}.relations.update { baseVersion, add,
   actor }` → `200 { id, version, relations }`. Errores: 409 `version_conflict` / `document_locked` (con
   `details.holderName`), 400 `invalid_relation`.
4. Errores comunes: 404 `module_not_installed`, 503 `module_unavailable`, 400 `invalid_fields`.

### Integration Points

**jiku-docs 1.3.0 (`conectores/jiku-docs/docs/apis/`), por el bus, vía el embudo. Lo que esta story usa:**

- `documents.list` — `DocumentsListQuery { actor, filter: DocumentsFilter, sort, page: { limit, cursor }, fields,
  include: [relations|topics|lock], count: boolean | 'only' }`. Reply `{ items: Document[], page: { limit, returned,
  cursor?, total? } }`.
- `DocumentsFilter` (`additionalProperties: false`): `id`, `folderId`, `path`, `pathPrefix`, `clientId` (IntOrList),
  `projectId` (IntOrList; incluye documentos vinculados por requisito o tarea), `requirementId`, `taskId` (IntOrList),
  `topic` (StrOrList), `visibility` (`internal|public|restricted`; `restricted` pedido por quien no lo lee → lista
  vacía, nunca `invalid_fields`), `createdBy`, `updatedBy` (StrOrList), `createdAt`, `updatedAt` (DateRange),
  `fileName`, `deleted`, `hasProject` (`false` = sin relación con proyecto, ni por requisito ni por tarea),
  `hasClient`, `hasTopic`, `or` (array ≤ 10, un nivel, cada elemento con los mismos filtros sin `or`).
  `IntOrList` / `StrOrList`: valor o array ≤ 200.
- `documents.search` — `SearchQuery { actor, query (2..1000), mode: 'text', filter: DocumentsFilter, limit (1..50,
  default 20) }`. Reply `{ items: SearchHit[] }`. `SearchHit`: `documentId, version, title, path, headingPath, snippet,
  score, updatedAt, updatedBy, updatedByName, createdBy, createdByName, visibility, clients, projects, projectMatch`.
- `documents.get` — `{ actor, id, version?, fields?, include: [content|relations|topics|lock|attachments] }`. Fields
  válidos: `id, title, path, folderId, fileName, version, checksum, sizeBytes, visibility, createdAt, createdBy,
  createdByName, updatedAt, updatedBy, updatedByName, deletedAt, clients, projects, prunedVersionsCount`. Errores:
  `invalid_fields`, `document_not_found`, `version_pruned` (`errorDetails { requestedVersion, previousAvailable,
  nextAvailable }`).
- `Document` (1.3.0): `id, title, path, folderId, fileName, version, checksum, sizeBytes, visibility
  (internal|public|restricted), createdAt, createdBy, createdByName (string|null), updatedAt, updatedBy,
  updatedByName (string|null), deletedAt, clients: int[], projects: int[], projectMatch (direct|indirect, solo con
  filter.projectId), prunedVersionsCount (solo get), content, contentUrl, relations { clients, projects,
  requirements, tasks }, topics: string[], lock { sessionId, holder, holderName (string|null), via, expiresAt } | null,
  attachments`.
- `documents.suggest-relations` — `{ actor, id }`. Reply `{ items: [{ projectId: int|null, clientId: int|null,
  score: 0..1, reason: string }] }` (≤ 5; `projectId: null` en candidato solo de cliente, nunca 0). Errores:
  `invalid_fields`, `document_not_found`, `permission_denied` (externo), `upstream_unavailable`.
- `topics.list` — `{ actor, filter: { prefix }, page }`. Reply `{ items: [{ topic, documents }], page }`.
- `documents.new` (comando) — `{ actor, id (ULID, req), checksum (req), content | contentUploadId, folderId?,
  fileName?, via?, message? (≤ 500) }`. Sin `folderId` la carpeta sale de las relaciones del frontmatter
  (`/clientes/<cliente>/<proyecto>/`, `/clientes/<cliente>/general/` o `/general/`); sin `fileName`, el título en
  kebab-case `.md`, único en la carpeta. Reply `{ id, version, path, folderId, fileName, warnings? }`. Un `user` con
  `visibility: restricted` en el frontmatter → `permission_denied`.
- `documents.{id}.relations.update` (comando, write) — `RelationsUpdate { actor, baseVersion (int ≥ 1, req), add?:
  RelationSet, remove?: RelationSet, sessionId?: ULID }`; `RelationSet { clients?, projects?, requirements?, tasks? }`
  (cada uno int ≥ 1, ≤ 100, `additionalProperties: false`). "Al menos un id en add o remove (si no, invalid_fields);
  un id en los dos es invalid_fields. Resultado = (actuales ∪ add) \ remove, más el cliente de cada proyecto
  agregado. Sin via: el origen sale de la clase del caller." Reescribe solo el bloque `jiku:` del frontmatter y crea
  una versión (`kind: update`) con mensaje automático. Sin cambios: `success` con la versión actual. Reply `{ id,
  version, relations: { clients, projects, requirements, tasks }, warnings? }`. Errores: `document_not_found`,
  `version_conflict`, `document_locked`, `frontmatter_invalid`, `invalid_relation`, `invalid_fields`,
  `permission_denied`, `upstream_unavailable`.
- `document_locked` trae `errorDetails { holder, holderName, via, expiresAt }`.
- `Version` (1.3.0) suma `authorName`, `kind` (`create|update|restore`), `protected`. `Share.revokeReason` suma
  `restricted`.
