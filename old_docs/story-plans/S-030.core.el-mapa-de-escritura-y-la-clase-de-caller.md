### H-1 (BLOQUEANTE) · La lectura literal de CA-3 rompe el portal, y hay evidencia

**Lo que dice CA-3:**

> **DADO** una identidad con rol `external-user`, **venga por el sobre o por el subject** …
> **ENTONCES** el mapa **no autoriza ninguno** → `caller_not_authorized` → **403**

**Lo que pasa si se implementa así, literal:**

La api **ya manda el sobre con los roles de la persona**, en las 27 llamadas, desde S-029:

```ts
// api/lib/utils/bus/actor.ts:50
const actor: Actor = { id, roles: req?.decodedTokenRoles ?? [] };
// api/lib/utils/bus/send-command.ts:54  — va en el embudo, no en las rutas
return { ...payload, actor };
```

Y hay **seis endpoints del portal** que un `external-user` alcanza hoy y que publican un comando:

| Endpoint | `x-roles` | Comando publicado |
|---|---|---|
| `POST /api/opus/requirements` | `[user, external-user]` | `requirements.new` |
| `POST /api/opus/requirements/{reqid}/comments` | `[user, external-user]` | `requirements.{id}.comment` |
| `POST /api/opus/requirements/{reqid}/subscriptors` | `[external-user]` | `requirements.{id}.subscriptors.new` |
| `DELETE /api/opus/requirements/{reqid}/subscriptors/{userId}` | `[external-user]` | `requirements.{id}.subscriptors.{userId}.delete` |
| `POST /api/opus/attachments` | `[user, external-user]` | `files.request-upload` |
| `GET /api/opus/attachments/{id}/preview` | `[user, external-user]` | `files.{fileId}.request-download` |

Con `external-user: { commands: [] }` y CA-2 aplicado (decide `actor.roles`), **los seis empiezan a
responder 403**. Eso contradice, en este orden:

1. **RF-1 del REQ-007:** *"Los `external-user` siguen escribiendo únicamente por el portal vía
   HTTP."* Si `core` los rechaza, **dejan de escribir por el portal también**.
2. **§20 del REQ:** *"`external-user` **no obtiene comandos por el bus**"* — *por el bus*, no *por
   la api*. La tabla de riesgos del REQ (línea 954) lo dice todavía más claro: las dos defensas son
   *"el callout no le da permiso de publicación"* y *"si existiera **por un error de plantilla**, el
   mapa no autoriza su rol"*. Las dos hablan del caller directo.
3. **CA-11 de esta story:** *"el status y el contrato de error son los mismos… **sin tocar una
   línea de UI**"*.
4. **CA-14:** *"la duplicación transitoria es la red"* — la api sigue autorizando, así que esta
   story **no puede** cambiar el resultado de una request que hoy funciona.

**La evidencia dura: el `FakeBus` de la api ejecuta `core` REAL** (`api/tests/mocks/bus.ts:22` —
*"los ejecuta contra core con la misma base de datos"*). Estos archivos usan
`token_04_external_user` **sin** `fakeBus.reply()`, así que se ponen en rojo:

- `api/tests/routes/opus-attachments-post.test.ts:55` — *"devuelve 201 con el UploadTicket para un
  external-user y publica el comando"*, con `actor: { id: 'zitadel-sub-04', roles: ['external-user'] }`
- `api/tests/routes/opus-requirements-post.test.ts:52`
- `api/tests/routes/opus-requirements-id-comments-post.test.ts:60`
- `api/tests/routes/opus-requirements-id-subscriptors-post.test.ts:60`
- `api/tests/routes/opus-requirements-id-subscriptors-userid-delete.test.ts:60`

**Y el Escenario 2 de la story no lo contradice**: arranca con *"`opus-web → api` publica
`requirements.{id}.edit`"*, pero `PATCH /api/opus/requirements/{reqid}` declara
`hasAnyRole(['user','admin'])` — **sin `external-user`** (`api/lib/routes/opus-requirements-id-patch.ts:30`).
Un cliente del portal **no alcanza ese endpoint hoy**, así que el escenario es ilustrativo y no
describe ningún camino vivo.

**Cómo lo resuelve este plan:** ver **D-1**. En una línea: el mapa distingue el **canal directo**
(sin sobre) del **canal del sobre**. `external-user` autoriza **cero comandos por el bus** —CA-3
intacta, la segunda defensa en pie— y **exactamente los seis de arriba cuando el comando llega con
sobre**, que es literalmente lo que su `hasAnyRole` ya autoriza. Cero ampliación respecto de hoy.

> **Si el dueño de producto prefiere la lectura literal**, es un cambio de una línea (`external-user:
> { commands: [], envelopeCommands: [] }`) **más** el arreglo de los cinco tests de la api **más**
> una decisión explícita de que el portal deja de escribir. Este plan no la toma por su cuenta
> porque rompe RF-1.

**Patrones que gobiernan este cambio:**

- **La transacción es del despachador, nunca del comando** (ADR-003). Commit si el reply es
  `success`, rollback en cualquier otro caso.
- **El despachador nunca lanza.** Todo error inesperado se traduce a un `Reply` de falla.
- **La compuerta corre ANTES de `registry.resolve()` y ANTES de `sequelize.transaction()`**
  (S-017 CA-6), y no abre transacción — es una **excepción deliberada** a la convención `orm`.
- **Una compuerta que no puede decidir DENIEGA.** Ante lo inesperado, `internal_error`, nunca
  `null`.
- **El registry matchea por SEGMENTOS, no por regex** (`commands/registry.ts:9-17`): los ids pueden
  ser números (`clients.7.edit`) o strings de Zitadel con puntos.

### Code Conventions (`_base`, `error-handling`, `validation`, `orm`, `logging`, `testing`)

- Archivos `kebab-case.ts`; clases `PascalCase`; constantes de módulo `SCREAMING_SNAKE_CASE`.
- **Imports relativos**, sin alias ni paths de `tsconfig`. Orden en un archivo de comando:
  `joi` → `sequelize` → `@jiku/models` → `@jiku/nats-protocol` → relativos.
- **Comentarios en español**, y explican **el por qué**, no el qué. Un comentario que marca algo
  transitorio dice **cuándo desaparece**.
- **`success()` / `failure()` se construyen con los helpers** de `@jiku/nats-protocol`, nunca a
  mano. Se usa **la constante** `ErrorCode.X`, no el literal.
- **Un código nuevo va en tres lugares**: el paquete, `docs/apis/core.yaml`, y el mapa a HTTP de la
  api (ver H-4).
- **Los mensajes nuevos van en español** y **no llevan datos internos**: ni ids de otras entidades,
  ni nombres de columna, ni detalle de excepción. **Ni el subject**, que transporta el user id
  (CA-32 del REQ).
- **Nada de `console.log`.** Prefijo `[auth]` para **todo** rechazo de autorización de los dos
  planos: es lo que lo hace grepeable con una línea.
- **`warn` y no `error`** para una entrada inválida que el servicio maneja bien; `error` para lo
  inesperado.
- **Los tests entran por `dispatch()`**, nunca llamando a `execute()` directamente. **No se mockea
  Sequelize ni la base.**

### Relevant ADRs

#### ADR-008: Autorización deny-by-default por path, no por ruta

**Decisión:** `validateToken` global + lista explícita de exenciones. Sobre esa base, dos capas
más: **por rol** (`hasAnyRole`) y **por entidad** (`validateProjectPermissions`,
`canUserAccessEntity`/`canUserViewEntity`, *"que resuelven el proyecto desde 9 tipos de entidad y
verifican `user_project_permissions`"*).

**Implementation Rules (verbatim):**

- `validateToken` **DEBE** instalarse globalmente en `app.ts`. **NO SE DEBE** declarar
  autenticación ruta por ruta.
- Un endpoint público **DEBE** agregarse explícitamente a `api/lib/config/public.ts`. Cualquier
  cambio en ese archivo es un **cambio de seguridad** y debe revisarse como tal.
- Un endpoint público **DEBE** validar por su cuenta lo que corresponda. El caso vigente
  (`GET /api/opus/attachments/:id/public`) verifica que el adjunto esté marcado público, responde
  403 en cualquier otro caso, y manda `X-Content-Type-Options: nosniff` con CSP de sandbox.
- Un endpoint que requiere rol **DEBE** declarar `hasAnyRole([...])` explícitamente. La
  autenticación global no implica autorización.
- Un endpoint accesible a `external-user` **DEBE** además verificar permiso de proyecto: el rol
  solo no alcanza (ADR-006).
- **Un tipo de entidad nuevo con adjuntos DEBE agregarse a la resolución de proyecto de
  `attachments-access.ts`. Un tipo no contemplado NO SE AUTORIZA, que es el comportamiento
  correcto.**
- Al leer un archivo de ruta, **NO SE DEBE** concluir que está desprotegido por no ver el
  middleware: la protección es global.

> **La regla en negrita es la que gobierna el mapa comando → entidad de la Tarea 5:** el mapa es
> **cerrado**, y un comando ausente **no se autoriza en modo externo**.

#### ADR-003: La transacción es del despachador, nunca del comando

**Decisión:** la transacción la abre y la cierra el **despachador**. Los comandos la reciben pero
**no tienen acceso a `commit` ni `rollback`**.

**Implementation Rules (verbatim):**

- Un comando **DEBE** recibir la transacción por su contexto y usarla en todas sus operaciones de
  base de datos. **NO DEBE** abrir una transacción propia.
- Un comando **NO DEBE** llamar a `commit()` ni a `rollback()`. Si el código de un comando los
  invoca, está mal escrito.
- Un comando **DEBE** señalar el fallo devolviendo un `Reply` con `status: 'failure'` y su
  `errorCode`. **NO DEBE** lanzar una excepción para señalar un fallo de negocio esperado.
- El despachador **DEBE** hacer commit **solo** si el reply es `success`, y rollback en todos los
  demás casos, incluidas las excepciones inesperadas.
- El despachador **NO DEBE** lanzar nunca: todo error se traduce a un `Reply` de falla.
- Los tests de comandos **DEBEN** entrar por el despachador (helper `dispatch()`), no llamando a
  `execute()` directamente: es lo único que verifica el comportamiento transaccional, incluido el
  rollback.

> **Consecuencia para la Tarea 6:** el chequeo de entidad **NO abre transacción** y corre **antes**
> de `sequelize.transaction()`. Es el mismo criterio con que la compuerta de S-017 y la validación
> Joi corren antes: un caller sin permiso no consume una conexión del pool de escritura.

#### ADR-001: Separación lectura / escritura

`core` es **el único que escribe** y conecta con el usuario dueño; la api conecta con un rol sin
`INSERT`/`UPDATE`/`DELETE`. **La compuerta lee por la conexión del DUEÑO también en el plano de
consultas** (`authorize-caller.ts:29-35`), porque `models/read.ts` no registra los modelos: es una
lectura **por PK**, sin escritura posible, así que la garantía de ADR-001 no está en juego. **El
chequeo de entidad de este plan sigue exactamente ese precedente.**

```ts
/** Los dos planos con caller en el subject. El de eventos no tiene: no hay a quién autorizar. */
export type Plane = 'commands' | 'queries';

/** TODOS los métodos del plano. Válido en los DOS planos — ver el comentario del mapa. */
const ALL = '*';

interface RolePermissions {
  readonly commands: readonly string[] | typeof ALL;
  readonly queries: readonly string[] | typeof ALL;
}

export const ROLE_METHODS: Readonly<Record<string, RolePermissions>> = {
  'internal-app': { commands: ALL, queries: ALL },
  admin: { commands: [], queries: ALL },            // ← CAMBIA
  user: { commands: [], queries: ALL },             // ← CAMBIA
  'external-user': { commands: [], queries: ALL },  // ← CAMBIA (D-1)
  core: { commands: [], queries: [] },
  'bus-observer': { commands: [], queries: [] },
};

const DENIED_MESSAGE = 'El caller no está autorizado a ejecutar este método';

export function rolesAuthorize(roles: readonly string[], method: string, plane: Plane): boolean {
  for (const role of roles) {
    const permissions = ROLE_METHODS[role];
    if (!permissions) { continue; }                 // deny-by-default: un rol desconocido se SALTEA
    const allowed = permissions[plane];
    if (allowed === ALL) { return true; }
    if (allowed.some((pattern) => matchesPattern(pattern, method))) { return true; }
  }
  return false;                                     // UNIÓN, no precedencia
}

export async function readCallerRoles(caller: string): Promise<readonly string[]> {
  const user = await User.findByPk(caller);         // SIN transacción, POR PK
  return Array.isArray(user?.roles) ? user.roles : [];   // JSONB sin CHECK: falla cerrado
}

export function authorizeWithRoles(
  caller: string, roles: readonly string[], method: string, plane: Plane
): Reply<never> | null {
  if (caller === getTrustedPublisherId()) { return null; }      // ← la exención del `sub`
  if (rolesAuthorize(roles, method, plane)) { return null; }
  logger.warn(`[auth] ${plane}: caller no autorizado: ${caller} -> ${method}`);
  return failure(ErrorCode.CALLER_NOT_AUTHORIZED, DENIED_MESSAGE);
}

export async function authorizeCaller(
  caller: string, method: string, plane: Plane
): Promise<Reply<never> | null> {
  try {
    if (caller === getTrustedPublisherId()) { return null; }    // corta ANTES de leer
    const roles = await readCallerRoles(caller);
    return authorizeWithRoles(caller, roles, method, plane);
  } catch (error: any) {
    logger.error(`[auth] ${plane}: no se pudo autorizar ${method}: ${error.message}`);
    return failure(ErrorCode.INTERNAL_ERROR, 'Internal error');   // falla CERRADA
  }
}
```

const PRECEDENCE: readonly CallerClass[] = ['external', 'internal', 'connector'];

/** El mapa rol → clase. CERRADO (ADR-008): un rol ausente no produce clase. */

  'external-user': 'external',
  user: 'internal',
  admin: 'internal',
  'internal-app': 'connector',

#### `core/src/bus/dispatcher.ts` — el orden de hoy, verbatim (lo que la Tarea 4 y la 6 tocan)

```ts
async dispatch(subject: string, raw: unknown): Promise<Reply> {
  const name = commandFromSubject(subject);
  const caller = callerFromSubject(subject);

  // 1. EL SOBRE VA ANTES QUE LA COMPUERTA (S-029). No toca la base, no resuelve el método,
  //    no abre transacción: es una comparación de strings sobre el cuerpo.
  const extracted = extractActor(caller, raw);
  if ('error' in extracted) { return extracted.error; }
  const { actor, payload } = extracted;

  // 2. EL ESPEJO, ANTES DE AUTORIZAR (CA-8, RF-9) y en su PROPIA transacción, que commitea
  //    antes de que se abra la del comando. Sin sobre no hay espejo.
  if (actor) { await mirrorActor(actor); }

  // 3. LA COMPUERTA, antes de `registry.resolve()` y de `sequelize.transaction()`.   ← TAREA 4
  const denied = await authorizeCaller(caller, name, 'commands');
  if (denied) { return denied; }

  // 4. El registry
  const resolved = this.registry.resolve(name);
  if (!resolved) {
    logger.warn(`[dispatch] comando desconocido: ${name}`);
    return failure(ErrorCode.UNKNOWN_COMMAND, `Unknown command: ${name}`);
  }
  const { command, params } = resolved;

  if (process.env.LOG_COMMANDS === 'true') { logger.info(`[cmd] ${name} <- ${JSON.stringify(payload)}`); }

  // 5. La validación Joi, ANTES de abrir la transacción
  const validated = command.validate(payload);
  if ('error' in validated) { return validated.error; }

  //                    ← TAREA 6: EL CHEQUEO DE ENTIDAD VA ACÁ, todavía SIN transacción

  // 6. La transacción
  const transaction = await sequelize.transaction();
  try {
    const reply = await command.execute(validated.value, { caller, params, transaction, actor });
    if (reply.status === 'success') { await transaction.commit(); } else { await transaction.rollback(); }
    if (process.env.LOG_COMMANDS === 'true') { logger.info(`[cmd] ${name} -> ${JSON.stringify(redactReply(reply))}`); }
    return reply;
  } catch (error: any) {
    await transaction.rollback();
    logger.error(`[dispatch] ${name}: ${error.message}`);
    return failure(ErrorCode.INTERNAL_ERROR, 'Internal error');
  }
}
```

## Decisiones que este plan toma (y que la story no fija)

### D-1 · El mapa distingue el canal DIRECTO del canal del SOBRE

**El problema:** H-1. CA-3 (*"venga por el sobre o por el subject"*) y RF-1 del REQ (*"los
`external-user` siguen escribiendo únicamente por el portal vía HTTP"*) no pueden ser las dos
verdaderas con un solo campo.

**La decisión:** `RolePermissions` gana **un** campo opcional, y **un solo rol lo declara**:

```ts
interface RolePermissions {
  /** Comandos autorizados cuando el comando llega DIRECTO al bus, sin sobre. */
  readonly commands: readonly string[] | typeof ALL;
  /**
   * Comandos autorizados cuando el comando llega CON SOBRE, o sea publicado por la api en
   * nombre de una persona. AUSENTE = los mismos que `commands`.
   *
   * LO DECLARA UN SOLO ROL, `external-user`, y la asimetría ES la decisión del producto:
   * un `external-user` NO ESCRIBE POR EL BUS (REQ-007 §20, CA-3) — su plantilla del callout
   * no le da permiso de publicación y este mapa es la segunda defensa — pero SÍ ESCRIBE POR
   * EL PORTAL, y desde S-029 esa escritura llega acá con `actor.roles: ["external-user"]`.
   * Con un solo campo hay que elegir entre romper el portal o abrir el bus. Con dos, no.
   *
   * DESAPARECE si algún día `external-user` deja de escribir por el portal, o si su plantilla
   * del callout gana publicación (que es un cambio de seguridad por ADR-007, no un renglón acá).
   */
  readonly envelopeCommands?: readonly string[] | typeof ALL;
  readonly queries: readonly string[] | typeof ALL;
}
```

**Por qué no las dos alternativas:**

| Alternativa | Por qué no |
|---|---|
| `external-user: { commands: [] }` a secas (lectura literal de CA-3) | **Rompe cinco caminos de escritura del portal** y pone en rojo cinco archivos de test de la api. Contradice RF-1, CA-11 y CA-14 (H-1) |
| `external-user: { commands: [<los 6>] }` en un solo campo | **Pierde la segunda defensa independiente** que CA-3 del REQ exige: si la plantilla del callout se equivocara y le diera publicación, el mapa lo autorizaría |

**Cómo se implementa la selección del campo:** el plano de comandos ya sabe si hay sobre —
`extractActor` devuelve `actor` o no. Ese booleano viaja a la compuerta. **El plano de consultas no
cambia**: no tiene sobre (REQ-006 §19), así que siempre lee `commands`/`queries`.

### D-2 · La regla de derivación de la enumeración, escrita para que un test la pueda correr

Un rol `R ∈ {admin, user, external-user}` autoriza el comando `C` **si y solo si**:

- **(a)** algún endpoint con `x-bus-command: C` declara `x-roles` que contiene `R`; **o**
- **(b)** algún endpoint que publica `C` **no declara `x-roles`** *y* `R ∈ {admin, user}`; **o**
- **(c)** `C` **no tiene ningún endpoint que lo publique** *y* `R ∈ {admin, user}`.

**Por qué (b) recorta a `external-user`.** Un endpoint sin `hasAnyRole` *"es alcanzable por
cualquier usuario autenticado, incluido un `external-user`"*, y el propio spec lo llama **deuda**:
*"La ausencia no es una convención, es deuda."* Traducir esa deuda a un permiso **declarado** del
bus le daría a `external-user` escritura sobre `clients`, `projects`, `objectives`, horas y
ausencias — trece comandos que ninguna pantalla del portal usa. **Se traduce la intención, no la
deuda.**

**Por qué (c).** Es H-5, y solo alcanza a `requirements.{id}.resolve`.

**El resultado, que es LO QUE HAY QUE ESCRIBIR EN EL MAPA:**

| `clients.{id}.edit` | ✅ | ✅ | — | (b) |
| `projects.new` | ✅ | ✅ | — | (b) |
| `projects.{id}.edit` | ✅ | ✅ | — | (b) |
| `tasks.new` | ✅ | ✅ | — | (b) |
| `tasks.{id}.edit` | ✅ | ✅ | — | (b) |
| `tasks.{id}.comment` | ✅ | ✅ | — | (b) |
| `requirements.new` | ✅ | ✅ | **✅** | (a) `[user,admin]` ∪ `[user,external-user]` |
| `requirements.{id}.edit` | ✅ | ✅ | — | (a) `[user,admin]` ∪ `[user,admin]` |
| `requirements.{id}.resolve` | ✅ | ✅ | — | (c) — H-5 |

> **`admin` y `user` reciben LOS MISMOS 18, y no es un error.** Hoy **ningún** endpoint distingue
> `admin` de `user` entre las escrituras que ya pasan por el bus: la única combinación
> `['admin']` sola es `PUT /week-assigned-times`, que publica el **comando 21** y **es S-032**. La
> distinción entre los dos roles nace ahí, no acá. Es exactamente el mismo criterio con que
> `CLASS_BY_ROLE` los mete en la misma clase (`internal`).
>
> **Los dos comandos de suscriptores no los tiene ningún rol interno**, y tampoco es un error: sus
> dos endpoints son de la superficie opus y declaran `hasAnyRole(['external-user'])`. Un `admin` no
> puede suscribir a nadie por HTTP hoy, así que dárselo por el bus **sería ampliar**, no migrar.
> Está anotado como observación para S-034/S-035.

### D-3 · `caller-class.ts` sube a `src/`, y es un movimiento, no una copia

**El *"Riesgo medio"* de la story pide reusar la función de S-023 en vez de copiar la tabla.** Pero
importar `queries/caller-class` desde `bus/dispatcher.ts` acopla el plano de comandos al módulo de
consultas — exactamente el acoplamiento que `authorize-caller.ts` evitó subiendo un nivel:

> **VIVE EN `src/` Y NO EN `bus/` NI EN `queries/`** por lo mismo que `config.ts` y `logger.ts`: la
> comparten módulos distintos y no pertenece a ninguno.

**Decisión:** `core/src/queries/caller-class.ts` → **`core/src/caller-class.ts`**, y el tipo
`CallerClass` se muda con él. `core/src/queries/types.ts` lo **re-exporta**
(`export type { CallerClass } from '../caller-class';`) para que **ninguno de los ~30 archivos del
plano de consultas cambie un import**.

**Los importadores reales son tres** (verificado con `grep`):

1. `core/src/queries/dispatcher.ts:11` — `from './caller-class'` → `from '../caller-class'`
2. `core/tests/queries/caller-class.test.ts:5` — la ruta del import
3. `core/tests/queries/caller-class.test.ts:72` — **la ruta que el gate estructural LEE del disco**
   para verificar que no hay cache. **Si no se actualiza, el gate lee un archivo inexistente y
   explota con `ENOENT`, no con una aserción legible.**

**El comportamiento no cambia en un carácter.** El archivo de test se queda donde está
(`tests/queries/`): su sujeto sigue siendo el mismo mapa y moverlo no agrega información.

### D-4 · El chequeo de entidad va en el despachador, DESPUÉS de `validate()` y ANTES de la transacción

**Dónde exactamente:** entre el `command.validate(payload)` y el `await sequelize.transaction()`.

**Por qué ahí y no antes:** el chequeo necesita **el `{id}` del subject** (que sale de
`registry.resolve()` como `params`) y **campos del payload ya validados** (`projectId`). Ponerlo
antes obligaría a re-implementar la extracción de params y a leer un payload sin validar.

**Qué se conserva y qué no:**

| Propiedad | ¿Se conserva? |
|---|---|
| El **mapa** y la **clase** corren antes de `registry.resolve()` (CA-12) | **Sí** — la Tarea 4 no los mueve |
| Un caller sin permiso **no consume una conexión del pool de escritura** (S-017 CA-6) | **Sí** — sigue antes de `sequelize.transaction()` |
| Un caller sin permiso **no se entera de si el comando existe** | **No, para el caso externo**: un `external-user` con un método inexistente recibe `unknown_command` en vez de `access_denied`. **Es correcto**: la compuerta de método ya corrió y lo autorizó, así que el caller **ya sabe** que su rol habilita ese patrón |
| Ningún `execute()` cambia (CA-15) | **Sí** |

**La consecuencia de rendimiento, acotada:** en modo externo el chequeo cuesta entre **1 y 3
`SELECT`** (permiso; +1 si hay que resolver la entidad; +1 más si hay salto al dueño). **En modo
interno y conector cuesta CERO**, que es el 100% del tráfico de hoy.

### D-5 · `core` espeja la **correspondencia entidad → proyecto**, no las reglas finas de `canUserAccessObjective`

`canUserAccessEntity` aplica, **solo para `objective`**, reglas más finas: `admin` siempre; un
interno pasa por permiso **o** por ser creador **o** por estar asignado; un `external-user` necesita
permiso **y además** ser creador o estar asignado.

**CA-8 pide *"la misma correspondencia entidad → proyecto"***, y CA-7 pide *"resuelve el proyecto
desde el tipo de entidad"* + fila en `user_project_permissions`. **Eso es la forma de
`canUserViewEntity`, no la de `canUserAccessObjective`.**

**Decisión:** `core` implementa **proyecto + fila**. Las reglas finas de objetivo **se quedan en la
api**, que sigue aplicándolas (CA-14: no se elimina nada).

**Consecuencia, y hay que escribirla:** para `attachments.{id}.delete` sobre un `objective`, el
chequeo de `core` es **más permisivo** que el de la api. **Nada se abre**, porque la api sigue
corriendo delante. **Queda anotado como pendiente de S-034**: el día que la api deje de autorizar,
alguien tiene que decidir si esas reglas finas se mudan o se resignan.

### D-6 · El mapa comando → entidad es CERRADO, y `null` significa *"no hay entidad que chequear"*

Dos valores distintos, y confundirlos es un bug de seguridad en cualquiera de las dos direcciones:

- **`null` explícito** = *"este comando no toca una entidad de proyecto"*. **Pasa** en modo externo.
  Es la paridad exacta con la api: `POST /api/opus/attachments` **no** aplica capa 3 —
  *"`canUserAccessEntity` no tiene sobre qué operar"* (`attachments-post.ts:44`) — y su test afirma
  *"acepta a un external-user sin permiso sobre ningún proyecto"*
  (`api/tests/routes/opus-attachments-post.test.ts:141`).
- **Ausente del mapa** = **deniega** con `access_denied`. Es ADR-008 (*"Un tipo no contemplado no se
  autoriza"*) aplicado a un comando futuro que nadie declaró.
- **Declarado pero sin proyecto resoluble** (`stage`, una entidad borrada, un `entityId` nulo) =
  **deniega**. Es el precedente literal de `hasProjectPermission`: `if (!projectId) return false`.

**El mapa, derivado de qué ruta aplica hoy la capa 3** (ver *API Context*):

| Comando | Descriptor | De dónde sale el id |
|---|---|---|
| `requirements.new` | **`project`** (no `requirement`: todavía no existe) | `payload.projectId` |
| `requirements.{id}.edit` | `requirement` | `params.id` |
| `requirements.{id}.resolve` | `requirement` | `params.id` — gemelo de `.edit` (H-5) |
| `requirements.{id}.comment` | `requirement` | `params.id` |
| `requirements.{id}.subscriptors.new` | `requirement` | `params.id` |
| `requirements.{id}.subscriptors.{userId}.delete` | `requirement` | `params.id` |
| `attachments.{id}.delete` | **polimórfico** | la fila `attachments` de `params.id` → `entity_type` + `entity_id` |
| `files.{fileId}.request-download` | **polimórfico** | los vínculos vivos del `params.fileId` |
| **los otros 12** | **`null`** | — ninguna ruta les aplica capa 3 hoy |

Los 12 con `null`: `clients.new`, `clients.{id}.edit`, `projects.new`, `projects.{id}.edit`,
`tasks.new`, `tasks.{id}.edit`, `tasks.{id}.comment`, `files.request-upload`, `worked-times.new`,
`worked-times.{id}.delete`, `unworked-times.new`, `unworked-times.{id}.delete`.

> **`projects.{id}.edit`, `tasks.*` y `worked-times.*` llevan `null` aunque SÍ tocan un proyecto**, y
> es deliberado: **ninguna de sus rutas aplica `validateProjectPermissions` hoy**. Declararlo acá
> sería **endurecer**, y esta story migra reglas, no las inventa. Si alguien quiere endurecerlas, es
> una decisión de producto con su propio REQ.

**Para `files.{fileId}.request-download`** se replica la doctrina del recorte `bridge` que el
recurso `files` del plano de lectura ya usa (S-027): la fila es visible **por sus vínculos vivos**
o, **si no tiene ninguno**, por ser propia (`files.uploaded_by = caller`). **La rama huérfana NO es
un `orSelfColumn`**: entra **solo** cuando el `EXISTS` positivo está vacío, así que un archivo
vinculado a una entidad que el caller no puede ver **no se le filtra a quien lo subió**.

`rolesAuthorize` gana un parámetro para elegir el campo. La forma que **no** duplica el mapa:

```ts
/** Por qué canal llegó el método. Solo el plano de COMANDOS tiene sobre (REQ-006 §19). */
export type Channel = 'direct' | 'envelope';

function allowedFor(permissions: RolePermissions, plane: Plane, channel: Channel) {
  if (plane === 'queries') { return permissions.queries; }
  // `?? commands` y no un `if`: la ausencia de `envelopeCommands` SIGNIFICA "los mismos",
  // así que cinco de los seis roles no declaran nada y el mapa no tiene seis líneas repetidas.
  return channel === 'envelope' ? (permissions.envelopeCommands ?? permissions.commands)
                                : permissions.commands;
}
```

**El default de `channel` es `'direct'`.** Es la elección segura: un llamador que se olvide del
parámetro obtiene la lista **más restrictiva**, nunca la del sobre.

**El comentario del mapa tiene que decir, como mínimo:**

- de dónde sale la enumeración (`x-roles` de `docs/apis/api.yaml`, endpoint por endpoint) y **que

## Notas de Cierre

### Corrección a D-2 encontrada durante la implementación: los COMANDOS SECUNDARIOS

**La regla D-2, tal como estaba escrita, tenía un punto ciego, y costó tres tests de la api.**

D-2 deriva la enumeración de los endpoints que declaran `x-bus-command`. Pero **una ruta puede
publicar más de un comando**, y `x-bus-command` documenta la correspondencia **1:1** endpoint →
comando, así que el segundo **no aparece en ninguna parte del spec**.

El caso concreto: `POST /api/opus/requirements` (`hasAnyRole(['user','external-user'])`) publica
`requirements.new` **y después** `requirements.{id}.subscriptors.new`, porque el creador queda
suscripto siempre (`opus-requirements-post.ts`). Con la tabla de D-2 tal cual, `user` no recibía
ese segundo comando y **todo `user` dejaba de poder crear un requisito por el portal**: tres tests
de `opus-requirements-post.test.ts` en rojo (`201` → `403`).

**Es exactamente el "Riesgo crítico — una enumeración incompleta" de la story**, y lo atrapó la
mitigación (b): *la api sigue autorizando y su `FakeBus` ejecuta `core` real*. La mitigación (c) —el
test de paridad— **no** lo atrapó, porque tenía el mismo punto ciego que la regla.

**Lo que se corrigió, y en qué CANAL:**

| Rol | Canal directo | Canal del sobre |
|---|---|---|
| `admin` | **18** (como D-2) | los mismos 18 |
| `user` | **18** (como D-2) | **19** — los 18 + `requirements.{id}.subscriptors.new` |
| `external-user` | 0 | **6** (como D-2) |

**La tabla de D-2 era correcta para el canal DIRECTO.** El comando secundario solo afecta al canal
del sobre, y ahí es donde se agregó: `user` lo alcanza **únicamente** porque la api lo publica en su
nombre al crear el requisito. Su endpoint propio
(`POST /api/opus/requirements/{reqid}/subscriptors`) es **`external-user` only**, así que ponerlo en
`commands` le daría a cualquier `user` conectado al bus la capacidad de **suscribir a cualquiera a
cualquier requisito** — más de lo que su superficie HTTP permite. Eso es **ampliar**, y es
exactamente lo que el propio plan advierte que no hay que hacer.

**Consecuencia de forma:** `envelopeCommands` ya no lo declara un solo rol sino **dos**, y TS-11
pasa a afirmar `['external-user', 'user']`. La razón de los dos es la misma —hay comandos que una
persona alcanza solo porque la api los publica en su nombre— así que el campo no cambió de
significado.

`admin` **no** lo recibe por ningún canal, y es correcto: no alcanza `POST /api/opus/requirements`
(su `hasAnyRole` no lo incluye) y la ruta interna `POST /api/requirements` **no** publica el comando
de suscripción.

`requirements.{id}.subscriptors.{userId}.delete` **sigue sin tenerlo ningún rol interno**: su único
endpoint declara `hasAnyRole(['external-user'])` y ninguna ruta lo publica como secundario.

**El test de paridad ahora declara los comandos secundarios como dato**, junto a los cuatro
publicadores que salen del código, con el comentario de por qué el spec no puede expresarlos.

### Corrección a la forma de la Tarea 4: la identidad que evalúa la compuerta de método

El snippet de la Tarea 4 pasaba `caller` a `authorizeWithRoles`. Con sobre, `caller` es el
publicador de confianza, así que **la exención del `sub` cortaba antes de mirar `actor.roles`** y el
canal del sobre quedaba en un no-op: cualquier rol publicado por la api habría quedado autorizado en
los 20 comandos, y CA-2 no se cumplía. Lo detectan TS-28/29/30.

**Lo implementado:** la identidad que se evalúa es **la del actor** (`actor.id` con sobre, `caller`
sin sobre). Así la exención se conserva entera para el publicador directo (S-017 CA-1) y desaparece
—como corresponde— cuando la api publica **en nombre de otro**. Es la misma identidad que después
usa el chequeo de entidad.

### Otras dos precisiones de implementación

- **El exento sin sobre no lee `users`.** El snippet de la Tarea 4 leía siempre en el canal directo,
  lo que rompía TS-38 y S-017 CA-1. Se conserva el cortocircuito.
- **La clase sin resolver falla CERRADA.** En vez del `null as never` del snippet, un caller que no
  es el exento y no tiene clase **lanza**, y el `catch` lo traduce a `internal_error`. Es la lectura
  literal de *"revienta acá"* del plan, y evita que un rol nuevo con comandos y sin clase caiga
  silenciosamente en `connector`, que es la clase MENOS restrictiva.
