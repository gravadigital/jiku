## Story Reference

- **Story:** [S-101](../stories/S-101.web-reconocer-a-la-persona-y-contrato-api-1-3-0.md)
- **Service:** `api`
- **Origen:** [REQ-022](../requests/REQ-022.arreglos-e2e-documentacion-sin-carpetas.md)
- **Summary:** Alinear `docs/apis/api.yaml` con lo que las rutas de documentación devuelven de verdad
  con jiku-docs 1.3.0. El portal (`/opus/docs/documents*`) pasa a un esquema propio,
  `DocsPortalDocument`, sin `path`, `folderId` ni `fileName`; los esquemas de la web (`DocsDocument`,
  `DocsVersion`, `DocsSearchHit`, `DocsWriteResult`) se describen como pass-through de jiku-docs 1.3.0,
  con `lock.holder`, `createdBy`, `updatedBy` y `author` documentados como el `sub` de Zitadel.
  **Sin cambios de código en `api/lib/`.** El cambio se blinda con tests de documentación en
  `api/tests/utils/api-contract.test.ts`, el mismo molde que ya sostiene el resto del contrato.

> **Alcance de este plan:** solo el servicio `api`, es decir **CA-4 y CA-5**. CA-1, CA-2 y CA-3
> (`useCurrentUser.zitadelId`, `features/docs`, `DocumentRow`) son del servicio `web` y ya están
> implementados (`b09fd28`, plan `S-101.web.*`). opus-web no cambia: sus tipos ya coinciden con el
> esquema nuevo del portal (ver Integration Points).

> **Contexto UX / Design System:** la story tiene `affects_ui: true` por el lado `web`. Este plan es
> del servicio `api` (`type: api` en su `manifest.yaml`), que no tiene UI: no se copia contexto de
> pantallas ni de Design System.

> **Precondición verificada sobre el árbol (2026-10-26, rama
> `feature/S-101_web-reconocer-a-la-persona-y-contrato-api-1-3-0`, `ff901f9`):**

## Architectural Context

### Tech Stack

- Node.js + TypeScript (`strict` apagado, a propósito — ver `_base`).
- Express 5.2, un archivo por endpoint (no se toca ninguno en esta story).
- Contrato HTTP en `docs/apis/api.yaml` (OpenAPI 3, `info.version: 1.0.0`). **El yaml es la fuente de
  verdad**: donde código y documento discrepan, gana el documento, y la story prohíbe cambiar la api
  para ajustarse al yaml.

  parser de YAML** (ver Reusable Code).

### Relevant ADRs

- **ADR-015 / REQ-016 (módulos del bus, DD-2 y DD-3)** — aplica como contexto, no se modifica:
  - La api no autoriza el dominio de documentación: jiku-docs resuelve el ACL con el `actor` (el `sub` del token).
  - DD-3: el portal solo muestra documentos `public`; `visibility: 'public'` lo fuerza la api y el
    detalle responde 404 `document_not_found` si `visibility !== 'public'` (falla cerrado). Por eso
    `visibility` **tiene que** estar en `PORTAL_DOC_FIELDS` y en el `required` de `DocsPortalDocument`.
- **REQ-021, decisión 12:** el portal no recibe la ruta (`path`, `folderId`, `fileName`). Ya está
  implementado en las rutas con `PORTAL_DOC_FIELDS`; esta story lo lleva al contrato.

No hay ADR que cambie: es una corrección de documentación del contrato.

### API Context

**Hoy (portal):**

```yaml

'200':
  description: OK
  content:
    application/json:
      schema: { $ref: '#/components/schemas/DocsDocumentPage' }    # <- pasa a DocsPortalDocumentPage

# /opus/docs/documents/{id} → get → responses
'200':
  description: OK
  content:
    application/json:
      schema: { $ref: '#/components/schemas/DocsDocument' }        # <- pasa a DocsPortalDocument
```

Las descripciones de las dos operaciones del portal **ya** dicen "sin `path`, `folderId` ni
`fileName`": no cambian.

**Esquemas nuevos (verbatim de la story, se insertan junto a los demás `Docs*`, p. ej. después de `DocsDocumentPage`):**

```yaml
    DocsPortalDocument:
      type: object
      description: Documento `public` para el portal. Sin `path`, `folderId` ni `fileName` (REQ-021); los `fields` los fija la api
      required: [id, title, version, visibility, createdAt, updatedAt]
      properties:
        id: { type: string, pattern: '^[0-9A-HJKMNP-TV-Z]{26}$' }
        title: { type: string }
        version: { type: integer }
        visibility: { type: string, enum: [public] }
        createdAt: { type: string, format: date-time }
        updatedAt: { type: string, format: date-time }
        content: { type: string, description: "Solo en el detalle, hasta 256 KiB" }
        contentUrl: { type: string, description: "Solo en el detalle, en lugar de `content` por encima de 256 KiB; vence a los 300 s" }
        attachments: { type: array, items: { $ref: '#/components/schemas/DocsAttachment' }, description: "Solo en el detalle" }

    DocsPortalDocumentPage:
      type: object
      required: [items, page]
```

### Flow Context

**`docs/flows/documentos-desde-la-web.md`** — ya actualizado por el servicio `web` en esta story:

> **Identidad en la documentación (REQ-022, S-101):** la web reconoce la reserva y las versiones propias
> comparando `lock.holder`, `createdBy`, `updatedBy` y `author` con `session.user.zitadelId` (el `sub`),

**Paso 3 (reserva):** `POST /api/docs/documents/{id}/lock` → `documents.{id}.lock { sessionId, ttlSeconds?, via: 'human', actor }`; jiku-docs guarda `holder = actor.sub`. Esto es lo que el contrato pasa a decir en `lock.holder`.

### Integration Points

- **jiku-docs 1.3.0** (`conectores/jiku-docs/internal/service/specs.go`):
  - `documentFields` (todos los pedibles): `id, title, path, folderId, fileName, version, checksum, sizeBytes, ...`
  - Base del listado: `id, title, path, folderId, version, visibility, updatedAt, updatedBy, updatedByName, ...`
  - El `holder` de un lock y el `author`/`createdBy`/`updatedBy` son el `actor.sub` que manda la api (el `sub` del token de Zitadel).
- **opus-web** (consumidor del portal, no cambia): `opus-web/src/features/docs/types/docs.types.ts`
  declara `DocsDocument { id, title, version?, visibility?, createdAt?, updatedAt, content?, contentUrl?, attachments? }`
  y `DocsDocumentPage { items, page }`. El esquema nuevo del portal describe exactamente eso.
- **web** (consumidor de los esquemas de la web, ya implementado en S-101/web): compara contra el `sub`.
- Sin colas ni comandos nuevos.

### Code Conventions

- Esquemas de componentes con 4 espacios de indentación (`    DocsPortalDocument:`), propiedades con 8,
  propiedades en formato flow (`{ type: string, ... }`) en una sola línea, como el resto de la sección
  `# ---- documentación ...`.
- Los `$ref` en una sola línea: los tests de contrato cuentan líneas.
- Los tests nuevos van en un `describe` propio al final de `api-contract.test.ts`, titulado
  `docs/apis/api.yaml — contrato de documentos 1.3.0 (S-101)`, con un comentario que explique **por qué**
  existe (test de documentación: CA-4/CA-5 se enuncian sobre el yaml) y con los IDs `S-101 · TS-N` en el `it`.

### Reusable Code

- **`api/tests/utils/api-contract.test.ts`** — el molde a copiar:
  - `SPEC_PATH = path.join(__dirname, '../../../docs/apis/api.yaml')`.
  - `pathBlock(spec, name)`: bloque de un path (`  /ruta:`) hasta el siguiente path. Está **dentro** del
