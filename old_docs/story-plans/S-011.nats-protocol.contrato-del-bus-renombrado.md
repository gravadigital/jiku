### Service Architecture

`packages/nats-protocol` es un **paquete compartido**, no un servicio desplegable. No tiene
`docs/architectures/`, y eso es correcto: no hay manifest porque no hay servicio. El contexto
técnico de este plan sale de las convenciones de sus **dos consumidores** (`core` y `api`), del
contrato `docs/apis/core.yaml`, y de los ADR 002, 004 y 012. Precedente del mismo patrón:
`docs/story-plans/S-001.base.separar-file-de-attachment.md` y
`S-010.base.baja-integracion-sistemas-externos.md`, que planifican `base` sin arquitectura propia.

**Estado actual del paquete — el árbol completo, son 4 archivos:**

```
packages/nats-protocol/
├── package.json          name @jiku/nats-protocol, main dist/index.js, scripts build + lint
├── tsconfig.json         strict, declaration, outDir ./dist, rootDir ./src, include src/**/*.ts
├── eslint.config.js      module.exports = require('../../eslint.config.base.js')
└── src/
    └── index.ts          180 líneas — TODO el paquete vive acá
```

**No hay carpeta `tests/`, ni `.mocharc.json`, ni script `test`.** Ningún paquete bajo `packages/`
los tiene. Este plan abre esa carpeta para `nats-protocol` (Tarea 1).

**Cómo se consume:** `package.json` apunta a `dist/`, así que los consumidores lo usan
**compilado**. `npm run build:packages` (postinstall de la raíz) lo compila antes que `api` y
`core`. Un cambio en `src/index.ts` **no** llega a los consumidores sin rebuild.

**Patrón del archivo (respetarlo, es la convención de facto del paquete):**
- Un solo archivo, sin subcarpetas ni capas.
- Constantes de entorno **al tope**, leídas con `process.env.X || 'default'` **al importar**.
- Funciones puras exportadas, una por concepto, con un docblock en español que explica **el por
  qué**, no el qué.
- Los helpers privados (`base32`, `USER_ID_HASH_LEN`, `BASE32_ALPHABET`) van **después** de las
  funciones públicas que los usan, sin `export`.

**Manejo de errores:** el paquete **no lanza y no loguea**. Es un constructor de strings y un
catálogo de constantes. Las funciones nuevas de esta story son igual de puras: no validan su
entrada ni tiran. Si le llega un patrón mal formado, produce un string mal formado — la detección
de duplicados que falla el arranque es de **S-012**, no de acá.

**Estrategia de testing (la que este plan instaura):** Mocha + `should` + `ts-node`, corriendo
contra `src/` (no contra `dist/`), sin base de datos y sin red. Es el mismo runner que `core` y
`api`, con dos diferencias que importan:
- **No hay `global-setup`**: no hay base que levantar. El paquete es puro.
- **Hay que controlar `process.env` antes de importar**: ver "El patrón de recarga", abajo.

### Relevant ADRs

#### ADR-002: Toda mutación es un comando NATS request/reply, sin JetStream

**Decisión:** NATS en modo request/reply, sin JetStream. La api publica un comando y espera la
respuesta con un timeout; core valida, escribe en una transacción y responde.

Gramática del subject declarada por el ADR (texto del ADR, **con el valor viejo del token**):
```
{instance}.{user-id}.{svc}.{version}.{comando}
dev.323332022539911171.gestion.v1.clients.new
```

**Implementation Rules (verbatim del ADR):**

- Todo comando **DEBE** publicarse con el subject `{instance}.{user-id}.gestion.v1.{comando}`,
  usando la gramática de `@jiku/nats-protocol`. **NO SE DEBE** construir el subject a mano.
- El cliente NATS **DEBE** fijar `inboxPrefix` explícitamente al conectar, con el hash del user id
  que calcula `@jiku/nats-protocol`. Sin esto las respuestas no llegan.
- El `userId` con el que publica la api **DEBE** salir de la key del service user, **NO** de una
  variable de entorno: tiene que coincidir exactamente con el `sub` que el auth-callout lee del
  token para autorizar el subject.
- Toda respuesta **DEBE** tener el formato `{ status: 'success', data }` o
  `{ status: 'failure', errorCode, errorMessage }`. **NO SE DEBEN** inventar otros formatos.
- Los comandos de creación **DEBEN** devolver únicamente `{ id }`. Las ediciones y borrados, nada.
- Todo `errorCode` nuevo **DEBE** agregarse al mapa de `api/lib/utils/bus/protocol.ts` con su
  status HTTP. Un código sin mapeo cae en un 500 genérico.
- El timeout de la request es `NATS_REQUEST_TIMEOUT_MS` (default **5000 ms**); al expirar la api
  **DEBE** responder **503**.
- **NO SE DEBE** transportar datos estructurados dentro de `errorMessage`. El caso actual de
  `daily_limit_exceeded` —que la api recupera parseando el mensaje con un regex— es deuda
  explícita, no un patrón a imitar.
- Core **NO DEBE** publicar mensajes: solo responde el `Reply` de la request que recibe.

**Cómo aplica a esta story — leer con cuidado, dos reglas están en tensión aparente:**

1. La primera regla fija el subject **con `gestion` embebido**. Esta story cambia exactamente ese
   valor. **No es una violación**: RF-1 y RF-23 del REQ-004 declaran que el ADR se corrige, y
   `docs/apis/core.yaml` —que el propio ADR nombra como contrato completo— **ya está actualizado**
   con `jiku-commands` (ver API Context). La corrección del texto del ADR se tramita por
   `/product-change-technical-definition` y **está fuera del alcance de esta story** (ver
   "Fuera de alcance").
2. La segunda mitad de esa misma regla —**"NO SE DEBE construir el subject a mano"**— es la que
   esta story tiene que honrar al pie de la letra, y es la que hace que el rename sea un cambio de
   un archivo. Toda función nueva de este plan existe para que ningún consumidor concatene.
3. El timeout de 5000 ms y el 503 **no se tocan acá**: la separación 503/504 es de **S-014**.
4. `Reply`, `success()`, `failure()` y el catálogo `ErrorCode` (26 miembros) **no se tocan**:
   RF-11 los declara intactos.

#### ADR-004: El vocabulario nuevo es del contrato, no del almacenamiento

**Decisión:** el bus adopta el vocabulario del producto y `core` traduce al escribir. El nombre
nuevo es del contrato, no del almacenamiento.

**Implementation Rules (verbatim):**

- Un comando nuevo **DEBE** usar el vocabulario del producto en su contrato (`task`, no
  `objective`). La traducción a nombres de tabla vive **dentro** del comando.
- **NO SE DEBE** renombrar una tabla ni una columna existente para alinearla con el contrato. La
  base se cambia solo cuando hay una razón propia, no por vocabulario.
- Toda traducción contrato ↔ base **DEBE** vivir en `core`, en el comando o en un helper del
  módulo. **NO DEBE** filtrarse a `@jiku/models`, que describe la base tal como es.
- El contrato HTTP de la api **NO DEBE** cambiar de vocabulario sin coordinarlo con los dos
  frontends: es el contrato público del producto.
- `priorityValue` es un escape transitorio: **NO SE DEBE** replicar el patrón de mandar un campo
  paralelo para esquivar una traducción con pérdida. Cuando la web mande nombres de prioridad,
  el campo se elimina.
- Al agregar un valor a un enum del bus, **DEBE** verificarse que la traducción a la base sea
  biyectiva. Si no lo es, la traducción es el problema, no el enum.

**Cómo aplica:** es el ADR que **autoriza** esta story. El producto se llama Jiku; el token decía
`gestion`. Cambiar el nombre del contrato sin tocar la base es exactamente el criterio del ADR. Y
es también la razón del nombre `methodFromSubject`: el token `{svc}` ahora tiene dos valores, así
que el quinto segmento ya no es siempre "un comando" — es un **método**, que puede ser un comando
o una consulta. La segunda regla es la que prohíbe arrastrar el rename a la base (ver CA-12).

#### ADR-012: Monorepo npm con contexto de build en la raíz

**Decisión:** un monorepo npm con workspaces: `api`, `core`, `web`, `opus-web` y `packages/*`.

**Implementation Rules (verbatim):**

- Todo servicio y paquete **DEBE** ser un workspace declarado en el `package.json` de la raíz.
- Un Dockerfile **DEBE** construirse con contexto en la **raíz del monorepo**, no en la carpeta del
  servicio. **NO SE DEBE** usar `docker build .` desde la carpeta del servicio: falla al no
  alcanzar `packages/`.
- Los Dockerfiles **DEBEN** copiar los manifiestos antes del código fuente, para preservar el cacheo
  de `npm ci`.
- Los frontends **DEBEN** instalar con `--ignore-scripts`: no consumen `packages/*` compilados.
- El gestor de paquetes **DEBE** ser **npm** con workspaces. **NO SE DEBEN** usar yarn, pnpm ni bun.
- Un cambio en `packages/*` **DEBE** ejecutarse con los tests de **todos** los servicios que lo
  consumen antes de mergear.
- Los cuatro servicios **DEBEN** correr sobre `node:24.12-alpine3.23` con usuario no-root, y usar
  build multi-stage.
- Una imagen **NO DEBE** hornear configuración: sin `ARG` de entorno ni `NEXT_PUBLIC_*` funcional
  ([ADR-009](../adrs/ADR-009-token-confinado-al-servidor.md)).

**Cómo aplica — es la regla operativa más importante de este plan:** *"Un cambio en `packages/*`
**DEBE** ejecutarse con los tests de **todos** los servicios que lo consumen antes de mergear."*
Los consumidores son `core` y `api`, y los dos tienen suite. La Tarea 6 existe solo por esta regla,
y es también la verificación de CA-6. **Ningún Dockerfile cambia** (RF-6): el paquete no agrega
deployable.

### API Context

#### La gramática del bus — el contrato ya está escrito con el nombre nuevo

`docs/apis/core.yaml` (AsyncAPI 2.6) es la fuente de verdad del bus, y **ya fue actualizado**
durante la creación de las stories del REQ-004. Copia verbatim de su sección de gramática:

```
#   {instance}.{user-id}.{svc}.{version}.{method}
#   dev.323332022539911171.jiku-commands.v1.clients.new
#
#   instance   deployment: dev / prod              (NATS_INSTANCE)
#   user-id    WHO publishes: the token's `sub`, RAW
#   svc        jiku-commands                       (NATS_COMMAND_SERVICE)
#              jiku-queries                        (NATS_QUERY_SERVICE)
#   version    protocol version: `v1`              (NATS_PROTOCOL_VERSION)
#   method     clients.new, requirements.{id}.edit, ...
#
# THE GRAMMAR DID NOT CHANGE — the set of values of the `{svc}` token went from one to two.
#
# Core registers the group `{instance}.*.{svc}.{version}` per service and subscribes one endpoint
# per method, with queue group `jiku-commands` for the commands and `jiku-queries` for the
# queries. The wildcard covers any caller and several replicas share the messages between them.
#
# WHY THE SEPARATION LIVES IN `{svc}` AND NOT NESTED UNDER THE COMMANDS SERVICE. The commands
# subscription used to be `{instance}.*.{svc}.v1.>`, and that `>` would also swallow the queries
# if they shared the `{svc}` token. Two different queue groups over overlapping subjects means the
# message is delivered to BOTH subscriptions and TWO replies reach the same inbox; a plain
# `request()` returns the first and DISCARDS THE SECOND SILENTLY. Sharing the process does not
# avoid it: the overlap is in the subject. With a distinct `{svc}` the problem cannot happen,
# because subject tokens are compared whole.
```

**Consecuencia práctica para este plan:** el spec **ya declara** que los nombres y subjects de
endpoint se derivan con `endpointName()` / `endpointSubject()` de `@jiku/nats-protocol`. Este plan
implementa esas dos funciones. El spec no es una aspiración: es el contrato contra el que se
verifica CA-5.

**Las dos reglas de forma, y por qué son así:**

- **El nombre no lleva puntos.** Micro valida el nombre del endpoint contra `/^[-\w]+$/`
  (`nats@2.29.3`, `jetstream/jsutil.js`:67-82; ADR-32 de NATS: solo `A-Z a-z 0-9 - _`). El subject
  con puntos y `*` va aparte, en `opts.subject`.
- **El `{param}` se vuelve `*`.** Un token de subject no puede llevar llaves, y el despachador ya
  extrae los params del subject completo con el registry por segmentos — **no los necesita del
  endpoint**.
- **El `{param}` se ELIMINA del nombre, no se reemplaza.** `tasks.{id}.edit` -> `tasks-edit`, no
  `tasks-any-edit`. Es la fuente del único bug plausible de la derivación: dejar el param produce
  `requirements-id-subscriptors-userId-delete`, que es un nombre válido para micro y por lo tanto
  **no falla en ningún lado** — solo queda mal en `nats micro info`.

### Flow Context

La story lista dos flujos afectados. **Ninguno se toca en este plan**: los dos son documentos de
`docs/flows/` que describen permisos del auth-callout, y van con el plan de `deploy`.

- **`autenticacion-y-entrada`** (`docs/flows/autenticacion-y-entrada.md`:179) — *"permiso de
  publicación sobre `{instance}.{user-id}.gestion.v1.>`"* pasa a **dos** permisos. Es el flujo que
  refleja el cambio de la plantilla `api` del callout. **Plan de `deploy`.**
- **`subida-de-archivos`** (`docs/flows/subida-de-archivos.md`:211) — la nota sobre la plantilla del
  publicador externo, que hay que corregir en dos cosas: el nombre nuevo **y** que esa plantilla
  **no** autoriza `>` sino 9 subjects enumerados. **Plan de `deploy`.**

Lo que sí importa de los flujos para **este** plan es el escenario 1 de la story, porque es lo que
la Tarea 6 verifica. Copiado con el detalle que hace falta:

**Escenario: un comando de escritura después del rename, con `core` sin modificar (CA-6)**

1. **[`web`]** `POST /api/clients` con `{name, description}`. **Sin cambios.**
2. **[`api` — `lib/routes/clients-post.ts`]** `sendCommand(res, 'clients.new', {...})` ->
   `bus().request('clients.new', payload)`. El subject lo arma
   `commandSubject('clients.new', userId)` en `api/lib/utils/bus/index.ts`:75 ->
   `dev.<uid>.jiku-commands.v1.clients.new` **(MODIFICADO)**. **El archivo de ruta no cambia**: el
   subject sale del paquete. Espera en `_INBOX.<hash(uid)>` — `inboxPrefix()` **intacto**.
3. **[auth-callout]** La plantilla `api` autoriza el prefijo nuevo -> la publicación pasa.
   **(Plan de `deploy`.)** Sin ese cambio, este mismo código es rechazado por permisos.
4. **[NATS]** Matchea `dev.*.jiku-commands.v1.>`, la suscripción que `consumer.ts`:69 armó con
   `subscriptionSubject()` — que ahora resuelve al nombre nuevo **porque `SERVICE_NAME` es alias de
   `COMMAND_SERVICE`**. Queue group `jiku-commands`, del **mismo** símbolo (`consumer.ts`:70):
   **una** réplica atiende.
5. **[`core` — `bus/consumer.ts`, SIN TOCAR]** `for await` -> `void dispatcher.dispatch(subject, payload)`.
6. **[`core` — `bus/dispatcher.ts`, SIN TOCAR]** `commandFromSubject(subject)` (alias de
   `methodFromSubject`) -> `'clients.new'`; `registry.resolve()`; `validate`; transacción;
   `execute`; commit si `success` (ADR-003) -> `success({ id })`.
7. **[`api`]** Recibe el envelope, relee la base y responde `201` (ADR-001).

**La verificación que sostiene toda la story, comprobada en el código:**

```ts
// core/src/bus/consumer.ts:69-70  — SIN TOCAR en esta story
const subject = subscriptionSubject();
this.subscription = this.connection.subscribe(subject, { queue: SERVICE_NAME });
```

El subject **y** el queue group salen del **mismo símbolo**. Aliasar `SERVICE_NAME` mueve las dos
cosas a la vez, que es exactamente lo que hace falta. Si salieran de fuentes distintas, el alias no
alcanzaría y `core` tendría que tocarse acá.

### Integration Points

**Ninguna integración externa.** `docs/references/` no existe en este producto, y esta story no
suma ningún tercero. Las referencias que el REQ cita (ADR-32 y ADR-6 de NATS) son documentación de
una dependencia ya instalada, y lo único que aportan a este plan es la regla de caracteres del
nombre de endpoint, ya copiada arriba.

### El patrón de recarga — cómo se testea un módulo que lee `process.env` al importar

Es la única decisión técnica no obvia del plan, y sin ella los tests son frágiles o directamente
imposibles.

**El problema.** `COMMAND_SERVICE`, `QUERY_SERVICE`, `INSTANCE` y `PROTOCOL_VERSION` se evalúan
**una sola vez, al importar el módulo**. Un test que haga `process.env.NATS_COMMAND_SERVICE = 'x'`
después del `import` no cambia nada. Y un test que afirme el default (`'jiku-commands'`) **falla en
la máquina de cualquiera que tenga esa variable exportada en su shell**, o si mañana el paquete se
testea en un entorno donde el compose la define.

**La solución, verificada empíricamente en este repo (ts-node + Mocha, funciona):** un helper que
fija el entorno, limpia la entrada del `require.cache` del módulo, lo re-requiere, y **restaura el
entorno**. Todas las aserciones dependientes del entorno pasan por él, así la suite es **hermética**
sin importar el shell del desarrollador.

```ts
// packages/nats-protocol/tests/helpers/reload.ts
type Protocol = typeof import('../../src/index');

/** Las cinco variables que el módulo lee al importarse. Se resetean SIEMPRE. */
const PROTOCOL_ENV_KEYS = [
  'NATS_INSTANCE',
  'NATS_PROTOCOL_VERSION',
  'NATS_COMMAND_SERVICE',
  'NATS_QUERY_SERVICE',
  'NATS_SERVICE_NAME',
] as const;

/**
 * Re-importa el paquete con un entorno controlado.
 *
 * El módulo lee `process.env` AL IMPORTARSE, así que no hay forma de cambiar una constante
 * después del import: hay que volver a importarlo. Y las cinco variables se resetean siempre,
 * no solo las que el test pisa, para que la suite no dependa del shell de quien la corre.
 */
export function reload(env: Partial<Record<(typeof PROTOCOL_ENV_KEYS)[number], string>> = {}): Protocol {
  const saved = new Map<string, string | undefined>();
  for (const key of PROTOCOL_ENV_KEYS) {
    saved.set(key, process.env[key]);
    delete process.env[key];
  }
  for (const [key, value] of Object.entries(env)) {
    process.env[key] = value;
  }

  const modulePath = require.resolve('../../src/index');
  delete require.cache[modulePath];
  // eslint-disable-next-line @typescript-eslint/no-require-imports
  const loaded = require('../../src/index') as Protocol;

  for (const [key, value] of saved) {
    if (value === undefined) { delete process.env[key]; } else { process.env[key] = value; }
  }
  // Que el módulo cargado con entorno de test no quede cacheado para el próximo `reload`.
  delete require.cache[modulePath];

  return loaded;
}
```

**Verificado antes de escribir este plan** (probe descartado, no quedó en el árbol):
- `ts-node` compila y corre archivos de `tests/` **aunque estén fuera del `rootDir: ./src`** del
  `tsconfig.json`. No hace falta un `tsconfig` de test ni tocar `rootDir` (tocarlo movería
  `dist/index.js` a `dist/src/index.js` y rompería el `main` del `package.json`).
- El ciclo `delete require.cache` -> `require` -> restaurar entorno **devuelve el valor correcto en
  las dos direcciones** (override y default), en corridas sucesivas dentro del mismo proceso.
- `eslint ./tests` pasa con `eslint.config.base.js` **sin agregar globals de Mocha**: la config no
  activa `no-undef`, así que `describe`/`it` no dan error.
- `should`, `mocha`, `ts-node` y `@types/mocha` **ya resuelven** desde
  `packages/nats-protocol/` por hoisting de npm workspaces.

**Regla para los tests, derivada de todo esto:** las funciones puras que **no** dependen del
entorno (`endpointName`, `endpointSubject`, `methodFromSubject`, `callerFromSubject`, `hashUserId`,
`inboxPrefix`, `success`, `failure`) pueden importarse normal con `import`. Todo lo que involucre
`INSTANCE`, `PROTOCOL_VERSION`, `COMMAND_SERVICE`, `QUERY_SERVICE` o `SERVICE_NAME` **DEBE** pasar
por `reload()`.

### Task 3: Los subjects de comandos y consultas, y el prefijo de grupo

**Status:** Completed

#### Description

Repuntar `commandSubject()` a `COMMAND_SERVICE`, y sumar `querySubject()` y `groupSubject()`.

`commandSubject()` **mantiene su firma exacta** y solo cambia el valor del token `{svc}` que
produce. Es la razón por la que ningún caller cambia una línea: los dos que existen
(`api/lib/utils/bus/index.ts`:75 y `api/tests/mocks/bus.ts`:93) siguen llamándola igual.

`groupSubject(service)` es el reemplazo estructural de `subscriptionSubject()`: devuelve el prefijo
del grupo micro **sin** el `.>` final, porque el framework micro pide el grupo y arma los subjects
de endpoint por su cuenta. `subscriptionSubject()` queda marcado `@deprecated` con el cuerpo
intacto — sigue funcionando y ahora devuelve el nombre nuevo, que es lo que renombra la suscripción
de `core`.

La decisión de fondo que estas tres funciones materializan: la separación va en el token `{svc}` y
no anidada bajo el servicio de comandos, porque la suscripción de comandos termina en `>` y ese `>`
se comería también las consultas. Dos queue groups sobre subjects solapados entregan el mensaje a
**las dos** suscripciones, llegan **dos** respuestas al mismo inbox, y un `request()` devuelve la
primera y **descarta la segunda en silencio**. Con `{svc}` distinto el problema no existe, porque
los tokens se comparan enteros.

#### Acceptance Criteria

1. `commandSubject(command, userId)` conserva su firma `(string, string) => string` y devuelve
   `` `${INSTANCE}.${userId}.${COMMAND_SERVICE}.${PROTOCOL_VERSION}.${command}` ``.
2. Con la configuración por defecto, `commandSubject('clients.new', '323332022539911171')` devuelve

## Notas de Cierre

**Al terminar este plan, el producto queda funcionando end-to-end.** `core` se renombró solo, sin
una línea modificada en `core/src/`, y `api` publica en el subject nuevo sin cambiar un archivo de
ruta. Es lo que hace que esta story sea desplegable por sí sola — **siempre que el plan de `deploy`
haya aplicado el estado final del auth-callout antes o junto con el código.**

**Deuda que esta story crea a propósito, y quién la paga:**

| Deuda | La paga |
|---|---|
| `SERVICE_NAME` deprecado pero vivo, con dos callers (`core/src/bus/consumer.ts`, `core/tests/helpers/dispatch.ts`:21) | **S-012** (elimina el símbolo y repunta el helper) |
| `subscriptionSubject()` deprecado pero vivo, un caller | **S-012** |
| `commandFromSubject` alias, un caller (`core/src/bus/dispatcher.ts`:50) | S-012 o después: el despachador no cambia en el REQ-004 |
| `NATS_SERVICE_NAME` inerte en los compose y en `core/.env.test`:16 | **`S-011.deploy.*`** |
| `endpointName()` / `endpointSubject()` exportados sin consumidor | **S-012** (los registra como endpoints micro) |
| `querySubject()` / `QUERY_SERVICE` exportados sin consumidor | **S-013** (registro) y **S-014** (cliente de la api) |
| ADR-002, `bus-consumer.md` y `bus-commands.md` describiendo el nombre viejo | `/product-change-technical-definition` (RF-23, RF-24), fuera de las cuatro stories |

**Riesgo latente que esta story descubre y NO resuelve** (queda anotado porque es el momento en que
alguien está leyendo esto): `PROTOCOL_VERSION` es variable en el código y **literal** en las
plantillas del callout. `templates/core.yaml`:29 tiene `v1` hardcodeado, igual que los 9 subjects
del `external-publisher`, y `templates/observer.yaml`:17 **omite el segmento de versión por
completo**. Subir `NATS_PROTOCOL_VERSION` a `v2` dejaría al callout autorizando `v1`. Está **fuera
de alcance** —el REQ-004 no cambia la versión del protocolo (RF-11)— pero es una trampa latente, y
el REQ pide anotarla en el ADR nuevo (RF-25).
