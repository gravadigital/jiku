  cliente, proyecto (limitado al cliente; elegir proyecto completa el cliente), temas libres con

  desconocidas, comentarios y estilo) y se manda **un solo `PUT`** con `message` opcional ("Mensaje de
  la versión", que la protege). Frontmatter ilegible → edición del contenido completo con aviso.

### Fuera de alcance (declarado, para no improvisarlo)

- **Editar requisitos y tareas por campos**: la UX los conserva tal cual (pregunta abierta en
  `documento.md`). Solo viajan en el alta cuando llegan precargados (`initial.requirement`/`initial.task`).
- **Proyectos o clientes secundarios por campos**: los selectores son `single` y editan el **principal**
  (el primero de la lista, que es el que jiku-docs usa para ubicar). Los demás ids se conservan (ver
  Decisiones 6).
- **Mover el documento**: la ubicación la genera jiku-docs a partir del frontmatter; la web no la muestra.
- **"Origen HedgeDoc"**: descartado por la UX (no hay fuente en el contrato).

### Convenciones activas que aplican (extracto)

**`_base` (Next.js):** TypeScript strict, sin `any` salvo bordes; componentes con estado llevan
`'use client'`; el token nunca en el cliente; imports absolutos `@/…`; comentarios solo del **porqué**.

**`data-fetching` (custom):**
- Tres capas: componente cliente → hook `useQuery` → Server Action `'use server'` → `apiClient`.
  "Ninguna capa se saltea desde un componente cliente."
- Server Action con tipo de retorno explícito; devuelve `response.data`.
- **`features/docs/` usa `DocsResult`**: las Server Actions no lanzan, devuelven `{ ok: true; data } |
  { ok: false; error }` (`toResult`) y los hooks re-lanzan con `unwrap`.
- Hooks: un objeto `options` con defaults, `enabled` siempre expuesto, el hook no transforma datos.
- Toda consulta de docs va envuelta en `withModuleInvalidation` y usa `retry: shouldRetryDocsQuery`.
- Query keys del módulo: temas `['docs', 'topics', prefix]` (nueva); documento `['docs-document', id]`;
  listados `['docs', 'documents', …]`, `['docs', 'search', …]`, `['docs-documents', …]` (cards).

**`mutations` (custom):** invalidar **en el hook** (`onSuccess`); el hook no navega ni muestra toasts;
`retry: 0`; `isPending` alimenta `loading`/`disabled`. Alta y guardado no se reintentan (un 504 "pudo
haberse aplicado").

**`state-management` (custom):** borrador, campos y versión base del editor son **estado de interfaz**
(no se derivan del query, que se refresca en plena edición). La intención `?editar=1` va en la URL y se
consume una vez. No copiar datos de query a estado salvo como valor inicial explícito.

**`forms` (custom):** formularios chicos de la feature con estado controlado (`useState`) y componentes
del DS (`Input`, `Select`, `ToggleGroup`); la validación de dominio la hace el módulo y su `code` se
traduce en un util de la feature.

**`styling` (custom, ADR-010):** Sass + CSS Modules por componente (`@use '@/styles' as *;`), custom
properties del DS (`var(--space-*)`, `var(--space-grid-gap)`, `var(--z-modal)`, `var(--radius-surface)`,
`var(--elevation-raised)`), sin librería de componentes. Viewport único desktop: grilla de 12 columnas
**sin `@media`** (`display: grid; grid-template-columns: repeat(12, minmax(0, 1fr)); gap: var(--space-grid-gap);`).

**`error-handling` (custom):** avisos inline con `DocsNotice` (`intent` + `role`), toasts con
`react-toastify`, mensaje por `code` en `utils/docsErrors.ts`.

**`testing-unit` (custom):** tests junto al archivo, partidos por tema (`NewDocumentDialog.relations.test.tsx`);
mockear **hooks** al testear componentes y **services** al testear hooks; `vi.mock('@/lib/axios')` al
testear Server Actions; mockear `next/navigation` (`useRouter`, `useSearchParams`), `next-auth/react`
(`useSession`) y `@/hooks/use-current-user`; `getByRole` antes que `data-testid`; `userEvent`;
`queryBy*` para ausencia; TZ fijada en UTC. Comandos: `npm test --workspace web`,
`npm run lint --workspace web`, `npm run build --workspace web`.

### API Context

Todas las rutas son de la api (`{API_URL}/api`), las llama una Server Action con el Bearer de la sesión.
Cadena: `requireModule('docs') → hasAnyRole(['admin','user']) → Joi`. Errores comunes: `404
module_not_installed`, `503 module_unavailable`, `504 gateway_timeout`, `400 invalid_fields`, `403
permission_denied`. Cuerpo de error `{ code, message, details? }` → interceptor → `ApiError { code,
message, status, details? }` → `toResult` → `DocsError`.

**`POST /docs/documents`** (`api.yaml:2181`) — body `additionalProperties: false`, `required: [content]`:
```json
{ "id": "ULID opcional", "folderId": "ULID opcional (jiku-docs >= 1.3.0)", "fileName": "opcional",
  "content": "Markdown, hasta 256 KiB", "message": "opcional, minLength 1" }
```
"Sin `folderId` la carpeta sale de las relaciones del frontmatter (`/clientes/<cliente>/<proyecto>/`,
`/clientes/<cliente>/general/` o `/general/`); sin `fileName`, del título (kebab-case `.md`, único en la
carpeta). La respuesta trae `folderId` y `fileName`. Un `user` con `visibility: restricted` en el
frontmatter recibe 403 `permission_denied` (lo decide jiku-docs)." "Reenviar el mismo `id` tras un 504 es
seguro (`already_exists`); **un alta sin `id` no es idempotente**."
Response `201 DocsWriteResult { id, version, path?, folderId?, fileName?, warnings? }`.
Errores: `400 frontmatter_invalid` / `invalid_relation` / `invalid_fields` / `content_too_large`,
`403 permission_denied`, `409 already_exists`, `413 payload_too_large`, `503`, `504`.

**`PUT /docs/documents/{id}`** (`api.yaml:2254`) — body `required: [baseVersion, content]`:
`{ baseVersion: integer ≥ 1, content: string, sessionId?: ULID, message?: string minLength 1 }`.
Response `200 DocsWriteResult`. Errores: `409 version_conflict` (`details.currentVersion`), `409
document_locked` (`details.holder`, `holderName`, `via`, `expiresAt`), `400 frontmatter_invalid` /
`invalid_relation` / `content_too_large`, `403 permission_denied` (un `user` que pone o quita
`restricted`), `413`, `503`, `504`.

**`GET /docs/topics`** (`api.yaml:2384`) — query `prefix` (1..200), `limit` (1..200, default 50),
`cursor` (≤ 500). "Llama a `topics.list`. Responde el `data` de jiku-docs sin transformar."
Response `200 DocsTopicPage { items: DocsTopic[]; page: DocsPageInfo }`, `DocsTopic { topic: string;
documents: integer }`. El contrato ofrece **solo prefijo** ("vid" encuentra "video", no "pedido-video").

**`POST /docs/documents/{id}/lock`** — body `{ sessionId }` → `200 { id, sessionId, expiresAt }`;
`409 document_locked` con `details.holderName`. Sin cambios (lo usa `useEditSession`).

**`GET /clients`** y **`GET /projects`** (módulos `clients` y `projects`, existentes) — los consumen
`useClients()` (`@/features/clients`) y `useProjects()` (`@/features/projects/hooks/useProjects`, vía
`ProjectPicker`). `Client { id, name, … }`; `Project { id, name, client?: { id, name } , … }`.

**Formato del frontmatter** (jiku-docs `especificacion-v1.md` §3, verbatim):
```markdown
---
title: Acceso al servidor de staging
visibility: internal
topics: [infra, accesos]
jiku:
  clients: [4]
  projects: [12, 31]
  requirements: [812]
  tasks: []
---
```
- "`title`: si falta, se toma el primer encabezado `#`; si tampoco hay, el nombre de archivo sin extensión."
- "`visibility`: `internal`, `public` o `restricted`. Otro valor es error `frontmatter_invalid`."
- "`topics`: lista de strings; se normalizan a kebab-case sin acentos. Los temas se crean al usarse."
- "`jiku`: bloque estricto. Solo acepta `clients`, `projects`, `requirements` y `tasks`, con listas de ids
  numéricos. Cada id se valida contra `core`; uno inexistente o no visible para quien escribe es error
  `invalid_relation`."
- "Otras claves de primer nivel se conservan en el contenido y se ignoran."
- "`restricted`: solo `admin` y servicios. … Solo un `admin` (o un servicio) lo pone o lo quita, en `new`,
  `update`, `restore` y `relations.update`; un `user` recibe `permission_denied`. No admite links, y pasar
  un documento a `restricted` revoca los activos."
- (`p1/servicio.md`) "El primero de la lista" es el primero **tal como está escrito** en el frontmatter.

### Flow Context

**`documentos-desde-la-web`** (verbatim, pasos que toca esta story):

- **Paso 2b: alta sin carpeta (web)** — "`POST /api/docs/documents { id?, folderId?, fileName?, content,
  message? }`. Desde jiku-docs 1.3.0 `folderId` y `fileName` son opcionales: sin `folderId` la carpeta sale
  de las relaciones del frontmatter … y sin `fileName` del título. **Comando:** `documents.new { id,
  content, checksum, via: 'human', folderId?, fileName?, message?, actor }`. **Response:** `201 { id,
  version, path, folderId, fileName, warnings? }`. Un `user` con `visibility: restricted` en el frontmatter
  recibe 403 `permission_denied`."
- **Paso 3: tomar la reserva** — `POST /api/docs/documents/{id}/lock { sessionId }` (`useEditSession`).
- **Paso 5: guardar con versión base (web)** — `PUT /api/docs/documents/{id} { baseVersion, content,
  sessionId?, message? }` → "`documents.{id}.update { baseVersion, content, sessionId?, message?,
  checksum, via: 'human', actor }`". "Al guardar bien, la web libera la reserva (Paso 6). **Sin reintento
  automático**: un 504 significa 'pudo haberse aplicado'." **Cambio de REQ-021 a documentar (Task 9):**
  "`message` opcional que protege la versión; el frontmatter se reescribe por campos."
- **Errores (tabla del flujo):** `2b | visibility: restricted de un user en el alta | 403 | permission_denied
  | Error en el alta`; `5 | Frontmatter o vínculo inválido | 400 | frontmatter_invalid / invalid_relation |
  Mensaje bajo el editor`; `3, 5 | Reserva en poder de otra sesión | 409 | document_locked …`;
  `3-5 | Alta con nombre repetido, o nombre inválido | 409 / 400 | already_exists / file_name_invalid |
  Error junto al campo en el alta` (**queda sin uso en la web**: se corrige en Task 9).

**Escenario web de la story (verbatim):**
1. **[web — `NewDocumentDialog`]** arma el frontmatter y el título. Output: `POST /api/docs/documents
   { content }` (sin `folderId`/`fileName`).
2. **[api]** `documents.new` con `via: 'human'` y `actor`. Output: `201 { id, version: 1, path, folderId, fileName }`.
3. **[web]** `router.push('/docs/{id}?editar=1')`; `DocumentView` carga, `session.start()` → `POST
   .../lock { sessionId }` → fase `editing`; luego `history.replaceState`.
- **Outcome:** documento abierto en edición con el lock tomado, sin recarga completa.
- **Errores:** 403 `permission_denied` → error junto al selector; 400 `frontmatter_invalid` /
  `invalid_relation` → error en el diálogo; falla el lock → toast actual y queda en lectura.

**Escenario de REQ-021 "guardar con mensaje":** `PUT /api/docs/documents/{id} { baseVersion, content,
sessionId, message: "Cierre de sprint" }` → `documents.{id}.update` → versión protegida.

### Decisiones de este plan sobre la story

1. **Selectores de cliente y proyecto con las rutas de siempre, no con `/docs/suggestions`.** La story
   nombra `GET /docs/suggestions` "proyectos y clientes para el selector", pero esa ruta exige `q` (≥ 1
   carácter) y tope de 10 por grupo: no sirve para un `Select` `searchable` que lista y filtra en memoria.
   `ProjectPicker` (S-095, `useProjects`) ya es el selector compartido que nombra REQ-021 ("`ProjectPicker`
   (alta, 05)"); el de cliente usa `useClients()` igual. Sin llamadas a `/docs/suggestions` en esta story.
2. **Frontmatter del alta (`buildNewDocumentContent`):** siempre `title` y `visibility`; `topics` solo si
   hay; `jiku` solo con las listas no vacías (y se omite entero si no hay ninguna). Listas en estilo flujo
   (como el ejemplo de la especificación). Cuerpo: línea vacía + `# {título}` + `\n`. Ejemplo exacto en
   TS-1.
3. **Edición: solo se escriben las claves cuyo campo cambió.** `composeContent` compara los valores
   iniciales con los actuales; si nada cambió, el bloque de frontmatter original se conserva **byte a
   byte** (incluido un cierre `...`). Si algo cambió, se reescribe con `yaml` mutando el nodo existente
   (`scalar.value`, `seq.items`) para conservar comentarios, comillas y estilo flujo/bloque; una clave
   ausente se agrega con `setIn` (listas en flujo). El bloque reescrito se delimita con `---` y `---`.
4. **Frontmatter ilegible** (`parseContent → { readable: false }`): bloque que abre con `---` y no
   cierra; YAML con errores (`doc.errors.length > 0`, incluye claves duplicadas); raíz que no es un mapa;
   `title` que no es string; `visibility` fuera de `internal|public|restricted`; `topics` que no es lista de
   strings; `jiku` que no es mapa, o `jiku.clients|projects|requirements|tasks` que no son listas de
   enteros. En ese caso: aviso `aviso-frontmatter-ilegible`, sin campos, y el editor muestra **el contenido
   completo** (se guarda tal cual). Sin frontmatter → legible (`frontmatter: null`).
5. **Valores iniciales de los campos en edición:** `title` = el del frontmatter o, si falta, `doc.title`
   (el servicio lo derivó del `#` o del archivo); `visibility` = el del frontmatter o `doc.visibility`;
   `topics` = el del frontmatter o `[]`; `clients`/`projects` = los de `jiku` o `[]`. Como solo se escribe lo
   que cambió (Decisión 3), un título derivado que no se toca **no** se agrega al frontmatter.
6. **Cliente y proyecto editan el principal** (`relationFields.ts`), conservando los demás ids en su orden:
   - `setPrincipal(list, id)`: `id` `null` → `list.slice(1)`; si no → `[id, ...list.slice(1).filter(x => x !== id)]`.
   - Elegir proyecto `p` (de cliente `c`): `projects = setPrincipal(projects, p)`; si `c !== null`,
     `clients = setPrincipal(clients, c)` ("elegir un proyecto completa el cliente").
   - Elegir cliente `c`: `clients = setPrincipal(clients, c)`; si el proyecto principal no es de `c`,
     `projects = setPrincipal(projects, null)` ("cambiar el cliente vacía el proyecto si no es de ese cliente").
   - "Sin cliente": quita el cliente principal **y** el proyecto principal (un proyecto siempre es de un
     cliente). "Sin proyecto": quita solo el proyecto principal.
   - El proyecto del selector se filtra por el cliente elegido (`clientId` de `ProjectPicker`).
7. **Temas libres (`TopicsInput`):** cada tema se normaliza al agregarlo con `normalizeTopic` (minúsculas,
   sin acentos, `[^a-z0-9]+` → `-`, sin guiones en los bordes), igual que jiku-docs, así el chip muestra lo
   que se va a guardar; vacío tras normalizar → no se agrega; repetido → no se duplica. Sugerencias con
   `GET /docs/topics?prefix={normalizado}&limit=10` (debounce 200 ms), sin los ya elegidos. Enter con una
   sugerencia activa la agrega; Enter sin opción activa agrega el texto escrito; Backspace con el campo vacío
   quita el último; Escape cierra la lista. "1 documento" en singular (la UX fija `"{n} documentos"`).
8. **Visibilidad (`VisibilityField`):** `ToggleGroup` `segmented`. "Restringido" se renderiza si
   `canRestrict` (`admin`) **o** si el valor actual es `restricted`; en el segundo caso, para un `user`,
   **todas** las opciones quedan `disabled` (ve la opción marcada y no puede cambiar). Debajo, la ayuda de la
   opción elegida (`aria-describedby` vía la prop aditiva de `ToggleGroup`); en edición, si se pasa a
   `restricted` desde otro valor, además `"Al guardar, los links compartidos de este documento dejan de
   funcionar."`.
9. **`permission_denied` (CA-9):** en el alta, el mensaje `"Solo la conducción puede crear un documento
   restringido."` va en `aviso-error-alta`, que el layout pone **inmediatamente debajo** de
   selector-visibilidad, y el `ToggleGroup` lo referencia con `aria-describedby`. En la edición, si la
   visibilidad cambió y el valor inicial o el nuevo es `restricted`: toast `"Solo la conducción puede
   restringir un documento."` **y** el mismo texto como error debajo del selector; el editor sigue editable.
   Cualquier otro `permission_denied` conserva el comportamiento actual (toast + solo lectura).
10. **Alta idempotente:** el diálogo genera el `id` (ULID) al abrir y lo reusa en reintentos. Un
    `409 already_exists` con ese `id` significa que el intento anterior (tras un 504) sí creó el documento:
    se trata como éxito y se navega a `/docs/{id}?editar=1`.
11. **Carrera de "Crear y editar":** el diálogo hace `router.push('/docs/{id}?editar=1')` y **después**
    `onClose()`. `DocumentView` consume `?editar=1` una vez (ref), llama `startEditing()` y **recién al
    resolverse** (éxito o fallo) limpia la URL con `window.history.replaceState(null, '', '/docs/{id}')` — sin
    `router.replace`, que dispara una navegación de Next y re-renderiza el segmento. Documento grande o
    bloqueado: limpia sin tomar la reserva.
12. **Guardar sobre un conflicto:** el próximo `PUT` compone sobre el frontmatter de la **versión actual**
    (la ajena, ya cargada para el panel) aplicando solo las claves que la persona cambió; si esa versión no
    se pudo cargar o es ilegible, compone sobre el original. Así no se revierten en silencio cambios ajenos
    de propiedades que la persona no tocó.
13. **Toast de guardado:** con `possible_secret_detected` gana el aviso de secreto (`toast.warning`); si no,
    con mensaje `"Guardaste la versión {n}. Quedó protegida."`; sin mensaje `"Guardaste la versión {n}."`.
14. **Botones Guardar/Cancelar quedan en la fila de acciones**, a la derecha de campo-mensaje (como hoy),
    no en la cabecera: la story pide el mensaje "junto a Guardar" y el orden de foco de la UX termina en
    `campo-mensaje → boton-cancelar → boton-guardar` (ver Hallazgos).

boton-guardar." "al entrar en edición el foco va a editor-markdown; al guardar o cancelar vuelve a
boton-editar."

**Decisiones (verbatim, REQ-021):** "Propiedades por campos en la edición y el editor sobre el cuerpo. Así
título, visibilidad, temas y vínculos cambian en la misma versión que el texto, y nadie tiene que escribir
YAML para cambiar un proyecto. Si el frontmatter no se puede leer, se vuelve al texto completo en vez de
arriesgarse a perder claves." "Requisitos y tareas no se editan desde los campos." "'Restringido' visible
para todos, elegible solo por `admin`." "El mensaje de la versión explica que protege." "Sin 'Origen HedgeDoc'."

**Navegación de la superficie (product-map, extracto):** sidebar fija con "Documentación" (solo con el módulo
instalado). O-07 (menú de `Select` con búsqueda) — triggers nuevos de REQ-021: "O-11 y documento en edición
(cliente y proyecto)". O-11 — "Crear un documento con título, cliente, proyecto, temas y visibilidad —sin
carpeta— y entrar directo a editarlo". O-02 — confirmación de descartar cambios.

**User flows aplicables (verbatim, Flujo 5):**
- Happy path 3-6: "Pulsa **'Editar'** → la web toma la reserva y abre la edición: propiedades por campos
  (título, visibilidad, temas, cliente y proyecto) arriba, editor del cuerpo con vista previa al lado; la
  reserva se renueva sola" · "Opcionalmente escribe un **'Mensaje de la versión'**, que la protege de la
  compactación" · "**'Guardar'** → versión nueva (propiedades y texto juntos), reserva liberada, vuelta a la
  lectura con `"Guardaste la versión {n}."`"
- Alternativo: "**Crear un documento** — **'Nuevo documento'** (O-11) desde documentacion, o **'+'** desde la
  card de una ficha con el proyecto ya elegido: título, cliente, proyecto, temas y visibilidad; **'Crear y
  editar'** abre el editor con la reserva tomada, sin recargar."
- Error: "**Propiedades inválidas o vínculo inexistente** — El mensaje del módulo debajo del campo o del
  editor. Si el frontmatter no se puede leer, la edición por campos se desactiva y se edita el texto completo."
- **Cross-surface:** Flujo 4 (la visibilidad la decide el documento; `restricted` no cruza al portal) — sin
  trabajo en `web` para esta story más allá de escribir `visibility` en el frontmatter.

### Design System Context — `web`

- **Versión fijada:** `4.3.0` (`docs/design-system/web/README.md`).
- **Accent de la superficie:** verde agua `#61CCB9` (`color.brand.primary`) — acento, foco e ítem activo,
  **nunca fondo de página**. Texto/enlace verde sobre claro: `color.brand.primary-deep` `#12897A`.
- **Grid:** `desktop` 1440 px, único, 12 columnas; `display: grid` con `gap: var(--space-grid-gap)`, sin `@media`.
- **Elevación:** `elevation.card` en cards; el diálogo usa `var(--elevation-raised)` y `z-index: var(--z-modal)`.
- **Mono:** el DS no tiene token de familia monoespaciada (gap previo): el textarea usa el stack que ya usa
  `DocumentEditor.module.scss` (`--fontStack-monospace, ui-monospace, …, monospace`).

**Componentes usados (extractos normativos verbatim):**
- **Input** (`text`, `textarea`) — "Todo campo **DEBE** tener `<label for>` asociado — no basta el
  placeholder." "`aria-invalid="true"` + `aria-describedby` apuntando al mensaje cuando hay error." "**Error:**
  se comunica con **borde + icono + texto**, nunca sólo con color." "**NO SE DEBE** usar el placeholder como
  label." API: `variant`, `label`, `hideLabel`, `ariaLabel`, `required`, `placeholder`, `error` (string),
  `disabled`, `icon`, `value`/`onChange`.
- **Select** (`single` `searchable`) — "Rol `combobox` con `aria-expanded` y `aria-controls` sobre el listado."
  "**El menú DEBE ser operable sin puntero.**" "Las flechas y `Enter` **DEBEN** operar sobre las opciones
  **visibles**." "**«Sin resultados» DEBE ser texto**." "`searchable` … **obligatorio cuando las opciones vienen
  de la api**." "**NO SE DEBE** crear un cuarto selector." API: `variant`, `label`, `options {value,label}[]`,
  `value`, `onChange`, `placeholder`, `required`, `error`, `disabled`, `searchable`. Con `value: ''` muestra el
  placeholder.
- **ToggleGroup** (`segmented`) — "**DEBE** implementarse como grupo de radios (`role="radiogroup"` con
  `role="radio"` y `aria-checked`)." "Flechas mueven la selección dentro del grupo; `Tab` entra y sale." "El
  grupo **DEBE** tener nombre accesible." "**NO SE DEBE** dejar el grupo sin ninguna opción elegida cuando el
  valor es obligatorio." API: `variant`, `label`, `options { value, label, disabled? }[]`, `value`, `onChange`.
- **Button** — `primary` ("Crear y editar", "Guardar"), `secondary-dismiss` ("Cancelar"). "**NO SE DEBEN**
  apilar dos botones primarios en una misma vista." API: `variant`, `disabled`, `loading` (spinner +
  `aria-busy`), `icon`, `onClick`, `ariaDescribedBy` (extensión local).
- **Card** (`panel`) — fila de propiedades; "**NO SE DEBEN** anidar tarjetas".
- **ConfirmDialog** (O-02, descartar cambios) — sin cambios. "**DEBE** llevar `role="dialog"` con
  `aria-modal="true"` y `aria-labelledby`." "El foco DEBE atraparse dentro del diálogo… y volver al elemento
  que lo abrió." "`Esc` DEBE cerrar el diálogo cancelando la acción."
- **Badge** (`outline`, `neutral`) — chips de `TopicsInput` (el × es un `<button>` aparte, no el badge):
  "**NO SE DEBE** usar un badge como botón".
- **Loader** (`inline`) — dentro de `Button` `loading`.
- **ViewHeader** (`detail`) — "El breadcrumb **DEBE** ser un `<nav aria-label="Ruta">` con una lista, y el
  nivel actual **DEBE** llevar `aria-current="page"`." API: `parent: { label, href }` (**un solo nivel**: ver gap nuevo).

**Accesibilidad (guideline `web`, extracto aplicable):** WCAG 2.2 AA. "NO comunicar estado solo con color."
"Todo elemento interactivo es accesible vía teclado. Foco visible. ESC cierra modales / popovers. Enter /
Space activan controles. Sin keyboard traps." "Cada componente declara su rol ARIA correcto. Iconos puramente
decorativos: `aria-hidden="true"`. Live regions para feedback dinámico (`aria-live="polite"`)."

**DS Gaps — `web`:**
- *Aceptados* (REQ-021 → "Dejar anotado"):
  - **campo-temas** (`text-input` con chips) — "`Select` `multiple` `searchable` no acepta valores nuevos;
    temas libres necesita alta con Enter. Componente de la feature (`TopicsInput`), compartido por los dos
    usos". Combobox propio con la anatomía de chips y el teclado de `Select` `multiple` (mismo patrón ARIA
    que `DocsSearchBar`).
  - **modal-nuevo-documento** (`modal`) — gap previo: `<dialog>` nativo con el armazón de `ConfirmDialog`.
  - **aviso-error-alta, aviso-frontmatter-ilegible, indicador-reserva** (`alert`) — gap previo: `DocsNotice`.
  - **toast-resultado** (`toast`) — gap previo: `react-toastify` sin spec.
  - **selector-visibilidad** (`toggle`), **selectores de cliente/proyecto** (`dropdown`) — **cubiertos** por
    `ToggleGroup` y `Select` `searchable`.
- *Nuevos* (aparecieron al planificar; **no bloquean**, se resuelven inline y quedan reportados):
  - **`ViewHeader` con un solo nivel de breadcrumb**: el breadcrumb de edición `"Documentación / {título} /
    Editando"` tiene tres niveles. En edición `DocumentView` pasa `ViewHeader` **sin `parent`** y renderiza
    encima su propio `<nav aria-label="Ruta">` (mismo armazón que el `RouteNav` del not found) con
    `"Documentación"` (enlace a `/docs`), `"{título}"` (texto) y `"Editando"` (`aria-current="page"`).
  - **`ToggleGroup` sin `aria-describedby`**: la ayuda por opción y el error de visibilidad tienen que quedar
    asociados. Se agrega la prop **aditiva** `ariaDescribedBy?: string` (va al `role="radiogroup"`), como la
    extensión local que ya tiene `Button`. Candidata a sumarse a la spec vía `/product-design-system-update`.
  - **`Select` `single` sin "limpiar"**: para "Sin cliente"/"Sin proyecto" se agrega una primera opción
    explícita con `value: ''` (con `''` el `Select` muestra el placeholder).
  - **`Input` sin texto de ayuda asociado**: la ayuda de campo-mensaje (`"Con mensaje, esta versión queda
    protegida…"`) y la de selector-proyecto (`"Solo los proyectos de {cliente}"`) van como `<p>` visibles
    inmediatamente debajo del campo; no se toca `Input`/`Select`.

**Implementation Notes:**
- Separación: `content.match(FRONTMATTER)`; si matchea, `raw = match[0]`, `frontmatter` = lo que queda entre
  la primera línea y la línea de cierre, `body = content.slice(raw.length)`. Si **no** matchea pero el
  contenido empieza con `/^---[ \t]*\r?\n/` → ilegible (abre y no cierra). Si no empieza así → legible sin
  frontmatter (`raw: null`, `frontmatter: null`, `body: content`, `values: {}`).
- Lectura con `parseDocument(frontmatter)`: `errors.length > 0` → ilegible; `contents === null` → `values: {}`;
  `!isMap(contents)` → ilegible. Luego `doc.toJS()` y validar tipos (Decisión 4). Las listas de `jiku` deben
  ser enteros (`Number.isInteger`).
- `composeContent`: si `title`, `visibility`, `topics` (comparación por orden y valor), `clients`, `projects`
  no cambiaron → `(parsed.raw ?? '') + body`. Si alguno cambió: `doc = parseDocument(parsed.frontmatter ?? '')`;
  por cada clave cambiada:
  - escalar (`title`, `visibility`): `node = doc.getIn([k], true)`; `isScalar(node)` → `node.value = v`; si no
    existe → `doc.setIn([k], v)`.

## Hallazgos (para revisar fuera de esta story)

1. **La story nombra `GET /docs/suggestions` para los selectores**, pero la ruta exige `q` y tope de 10: el plan
   usa `useClients`/`useProjects` (Decisión 1). Sin impacto en el contrato.
2. **`documento.md` ubica Guardar/Cancelar en la cabecera (col 4/12)** pero su orden de foco termina en
   `campo-mensaje → boton-cancelar → boton-guardar` y la story pide el mensaje "junto a Guardar": el plan los deja
   en la fila de acciones (Decisión 14). Conviene alinear el layout del screen.md.
3. **Varios proyectos o clientes**: los selectores editan solo el principal y conservan el resto sin mostrarlo en
   la edición (lo muestra "Vinculado a" en lectura). La UX no dice qué hacer con los secundarios; queda como
   pregunta abierta junto a la de requisitos y tareas.
4. **DS**: cuatro gaps nuevos no bloqueantes (ViewHeader de un nivel, `ToggleGroup.ariaDescribedBy`, `Select`
   sin limpiar, `Input` sin ayuda asociada). `ariaDescribedBy` en `ToggleGroup` y en `Button` son extensiones
   locales que la spec del DS todavía no documenta: candidatas a `/product-design-system-update`.
5. **`"{n} documentos"`** en las sugerencias de temas: la UX no fija el singular; el plan usa `"1 documento"`.
6. **Guardar sobre un conflicto** compone sobre el frontmatter de la versión ajena aplicando solo las claves
   tocadas (Decisión 12). Las claves que ambos cambiaron quedan con el valor propio, que es la semántica explícita
   de "Guardar sobre la versión {n}".
