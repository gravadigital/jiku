# Story Plan: S-070 (api) - `requirements.new` acepta suscriptores

## Status

**Status:** Completed

## Story Reference

- **Story:** [S-070](../stories/S-070.requirements-new-acepta-suscriptores.md)
- **Service:** `api`
- **Summary:** Las dos rutas HTTP que dan de alta un requisito aprovechan el campo
  `subscriberUserIds` que `core` ya acepta en `requirements.new`. `POST /requirements` lo pasa sin
  transformar (campo nuevo, opcional, aditivo). `POST /opus/requirements` deja de publicar N+1
  comandos —un `requirements.new` más un `requirements.{id}.subscriptors.new` por suscriptor— y
  publica **uno solo**, armando el set con el creador incluido.

> **Este plan cubre SOLO `api`.** La story afecta también a `core`, cuyo trabajo —validar contra
> `users`, deduplicar e insertar en `requirement_subscriptors` dentro de la transacción— es del plan
> [`S-070.core.*`](./S-070.core.requirements-new-acepta-suscriptores.md) y ya está **Completed**.
> Acá se cubren **CA-5, CA-6 y CA-7**; CA-1, CA-2, CA-3 y CA-4 son de `core`.

> **`core` ya está implementado y desplegable.** Esa es la precondición de la story
> ("Orden de despliegue: `core` primero") y **está satisfecha**: `core/src/commands/requirements/requirements-new.ts`
> ya valida, deduplica e inserta los suscriptores, y `docs/apis/core.yaml` ya declara
> `subscriberUserIds` en `RequirementsNewPayload` y `user_not_found` en el `x-error-codes` de
> `RequirementsNew`. **No hay ventana de incompatibilidad**: el campo es aditivo y el despliegue del
> monorepo es conjunto.

> **Es la única modificación de contrato de todo REQ-015, y es aditiva.** Un cliente que hoy publica
> `requirements.new` sin el campo sigue funcionando exactamente igual (CA-2, verificada del lado de
> `core`). Del lado de la api, el equivalente es que un `POST /requirements` sin `subscriberUserIds`
> se comporta idéntico al de hoy.

> **Esta story NO agrega notificaciones.** El `Reply` de `requirements.new` no declara
> notificaciones todavía —eso lo agrega S-072— y esta story no toca `notification_outbox`, así que
> es independiente de S-069 y puede implementarse en paralelo.

### Service Architecture

`api` es el **servicio HTTP**: expone `/api/*` a `web` y `/api/opus/*` al portal de clientes
(`opus-web`). **No escribe en la base**: conecta a PostgreSQL con un rol de solo lectura, así que
toda mutación se publica como comando NATS a `core`, y después el handler **relee** con Sequelize
para armar la respuesta.

```
handler ──sendCommand(res, 'requirements.new', payload)──▶ bus().request()
                                                               │
                              NATS request/reply ──────────────┤──▶ core ──escribe──▶ PostgreSQL
                                                               │
                              Reply { status, errorCode?, data? }
                                                               │
       success → data          failure → res.status(httpStatusFor(errorCode)).json(errorBody(reply))
                                                               │
       handler relee la base con Sequelize y arma la respuesta completa
```

**Estructura relevante para esta story (no hay `src/`; el código vive en `lib/`):**

```
api/
├── app.ts                          Express, middleware global, monta el barrel bajo /api
├── lib/
│   ├── routes/
│   │   ├── index.ts                el barrel (NO se toca: las dos rutas ya están exportadas)
│   │   ├── requirements-post.ts              ← ARCHIVO DE ESTA STORY (Task 1)
│   │   └── opus-requirements-post.ts         ← ARCHIVO DE ESTA STORY (Task 2)
│   ├── utils/
│   │   ├── validate-body-fields.ts           el middleware Joi
│   │   └── bus/
│   │       ├── send-command.ts               sendCommand / runCommand / actorId / withActor
│   │       └── protocol.ts                   STATUS_BY_ERROR_CODE, httpStatusFor, errorBody
│   └── logger.ts
└── tests/
    ├── mocks/bus.ts                          el FakeBus — ejecuta los comandos contra core REAL
    └── routes/
        ├── requirements-post.test.ts         ← TESTS DE ESTA STORY (Task 1)
        └── opus-requirements-post.test.ts    ← TESTS DE ESTA STORY (Task 2)
```

**Cómo se escribe un archivo de ruta** (convención `http-server`): esquema Joi arriba, middlewares
locales, handler, y el `router.{verb}(` al final con la cadena en orden de ejecución. **Ambos
archivos de esta story ya existen y ya siguen esa forma**: la story no crea rutas nuevas, modifica
dos existentes.

**Orden de la cadena de middlewares** (fijo, y las dos rutas ya lo respetan):

1. Rol — `hasAnyRole([...])`, si el endpoint lo acota
2. **Forma del input** — `validateBodyFields(schema)`
3. Existencia de la entidad — `validateProject` (acá es **local** en los dos archivos, porque el
   proyecto viene en el **cuerpo** y no en el path; está comentado en ambos y es la razón válida de
   duplicar)
4. Permiso sobre esa entidad
5. Visibilidad en la superficie
6. Reglas de negocio
7. Handler

**Manejo de errores** (convención `error-handling`): **no hay clases de error ni `throw`**. Cada
punto responde `res.status(n).json({ code, message })` y corta. Los errores que vienen del bus los
traduce y responde `sendCommand`/`runCommand`; el handler solo corta con `if (!data) return;`.

**Logging:** Winston, nunca `console`. **Esta story no agrega ningún log**: no hay rama nueva que lo
amerite — los dos caminos de error (Joi y el reply de `core`) ya loguean donde corresponde.

**Testing:** Mocha contra **PostgreSQL real** y con el `FakeBus`, que por default **ejecuta los
comandos contra el `core` real con la misma base**. Un solo test verifica a la vez qué comando se
publicó y con qué payload, cómo se tradujo la respuesta a HTTP, y que la escritura ocurrió.

### Relevant ADRs

#### ADR-001 / ADR-002 (la decisión estructural, recogida en la convención `bus-commands`)

**Decisión:** la api **no escribe en la base**. Conecta con un rol de solo lectura, y toda mutación
se publica como comando NATS a `core`.

**Implementation Rules (verbatim de la convención `bus-commands`):**

- Ninguna mutación nueva usa el modelo: publicá un comando. Las dos escrituras que quedan
  (`Attachment.create()` y `PUT /api/week-assigned-times`) son deuda, no precedente.
- Después de `sendCommand`, chequeá `if (!data) return;`. Después de `runCommand`, `if (!ok) return;`.
  Sin eso se responde dos veces.
- Usá `runCommand` cuando el comando no devuelve datos, y `sendCommand` cuando sí.
- **La identidad viaja en el sobre**, y lo inyecta `sendCommand`: no la agregues a mano. Los campos
  de dominio (`creator` / `author` / `editor`) se siguen llenando con `actorId(req)`. Nunca tomes la
  identidad del cuerpo de la request.
- Un `errorCode` nuevo en core se agrega a `STATUS_BY_ERROR_CODE`, o sale 500.
- **Los campos opcionales van con spread condicional, no con `undefined` explícito.**
- Las traducciones de nombres o formatos van en `lib/utils/bus/`, no en el handler.
- Si el comando necesita el rol, el usuario final o la fecha de hoy para validarse, **eso ya no lo
  deja en la api**: el criterio es **de quién es la regla**. Si decide si la operación puede ocurrir
  sobre estos datos y tiene que dar el mismo resultado por HTTP y por el bus, **va al comando de
  `core`**; si es del transporte HTTP —la forma del input, la traducción de nombres de contrato, el
  404 de la entidad del path— se queda acá.
- No agregues reintento automático: los comandos no son idempotentes.
- En los tests, usá el `FakeBus`.

> **Por qué importa acá, y mucho:** la regla "la validación de existencia de `userId` es del
> escritor" es **exactamente** lo que decide el diseño de esta story. La api **NO** valida que cada
> `subscriberUserIds` exista: eso lo hace `core` dentro de la transacción, y llega como
> `user_not_found` en el reply. Agregar un `User.findAll()` en la api sería una segunda definición
> de la misma regla —lo que REQ-007 (S-031) desarmó— y además no podría ser atómica con el insert.

#### ADR-003: La transacción es del despachador, nunca del comando (efecto en la api)

**Decisión:** la transacción la abre y la cierra el **despachador de `core`**.

**Consecuencia que esta story consume:** el rollback de un `user_not_found` es **completo y
automático** — no queda ni el requisito ni ninguna suscripción. La api no tiene nada que deshacer y
**no debe** intentar compensar: solo corta y deja que `sendCommand` responda. Es la diferencia
concreta con el N+1 que se elimina, donde una suscripción fallida dejaba el requisito ya creado y
sin sus suscriptores.

#### ADR-008: middleware global de autenticación (efecto en la api)

`validateToken` se instala **globalmente en `app.ts`**, no por ruta, para que el modo de fallo por
omisión desaparezca. Por eso `req.user.id` está siempre disponible en los handlers de las dos rutas,
y por eso `withActor` puede inyectar el sobre en el embudo.

### Flow Context

**Flujo: alta de un requisito público con suscriptores desde el portal (CA-6, CA-7).**

**Trigger:** un `external-user` crea un requisito desde el portal con `subscriberUserIds: [U2, U3]`,
siendo U1 el creador.

**HOY (N+1 comandos) — `opus-requirements-post.ts:40-61`:**

```
1. [opus-web] POST /api/requirements → proxy catch-all → POST /opus/requirements de la api
2. [api]      valida Joi, valida el proyecto del cuerpo
3. [api]      sendCommand('requirements.new', { creator: U1, title, description, projectId, ... })
                                                    ↑ SIN subscriberUserIds
4. [core]     crea el requisito → { id: 412 }
5. [api]      const subscribers = new Set([req.user.id, ...(subscriberUserIds || [])])
              for (const userId of subscribers) {
                runCommand(`requirements.412.subscriptors.new`, { userId })   ← 3 comandos más
                if (!ok) return;
              }
6. [api]      Requirement.findByPk(412) → 201
```

**DESPUÉS (un solo comando) — lo que implementa Task 2:**

```
1. [opus-web] POST /api/requirements → proxy catch-all → POST /opus/requirements de la api
2. [api]      valida Joi, valida el proyecto del cuerpo
3. [api]      sendCommand('requirements.new', {
                creator: U1, title, description, projectId, ...,
                subscriberUserIds: [...new Set([req.user.id, U2, U3])]    ← MODIFICADO
              })
4. [core · dispatcher]     compuerta de autorización, sequelize.transaction()
5. [core · requirements-new] DENTRO de la transacción:
              INSERT requirements → id 412
              INSERT people_requirements
              linkFiles
              valida que cada subscriberUserIds exista en `users` → user_not_found si no
              deduplica
              INSERT requirement_subscriptors (412,U1), (412,U2), (412,U3)
              → success({ id: 412 })
6. [api]      Requirement.findByPk(412) → 201
```

**Outcome:** el requisito y sus tres suscripciones existen **atómicamente**.

**Manejo de errores del flujo nuevo:**
- `user_not_found` en cualquier suscriptor → `failure`, **rollback completo** en `core`: no queda ni
  el requisito ni ninguna suscripción. La api responde **404** `user_not_found` y **no tiene nada
  que compensar**.
- Bus caído → 503; timeout → 504. Igual que hoy.

> **El beneficio de corrección que trae la unificación**, más allá de eliminar la carrera: hoy, si el
> requisito se crea y una suscripción posterior falla, **el requisito queda creado y sin sus
> suscriptores**, y el cliente ve un error de algo que sí ocurrió a medias. Con un solo comando la
> atomicidad la da la transacción.

**Reglas de validación (convención `validation`) que aplican a esta story:**

- El esquema vive **en el mismo archivo** que la ruta. No lo muevas a un módulo compartido.
- Esquema largo → constante nombrada arriba del archivo (`requirements-post.ts` usa `createSchema`).
  Corto → inline en la cadena (`opus-requirements-post.ts` lo tiene inline).
- **Los ids de usuario son `joi.string()`**; los de entidad, `joi.number().integer()`. Los
  `subscriberUserIds` son `sub` de Zitadel: **strings, no números**.
- Patrón canónico para un array de ids de usuario, ya usado en `opus-requirements-post.ts:75`:
  `joi.array().items(joi.string()).optional()`
- La validación de forma va **antes** de buscar entidades en la base.
- No cambies el contrato de error: `400` con `{ code: 'invalid_fields', message: 'Invalid field - ...' }`.

**Regla de `bus-commands` que decide la forma del payload:**

```ts
...(subscriberUserIds !== undefined ? { subscriberUserIds } : {}),
```

**Spread condicional, nunca `undefined` explícito.** El protocolo usa semántica de edición parcial:
un `undefined` explícito no es lo mismo que la ausencia del campo. Es como están los otros once
campos opcionales de `requirements-post.ts:67-77`.

### Reusable Code

- **`httpStatusFor(errorCode)` / `errorBody(reply)`** (`api/lib/utils/bus/protocol.ts:153,168`) — los

**Middlewares / validación:**

- **`validateBodyFields(schema)`** (`api/lib/utils/validate-body-fields.ts`) — valida `req.body` con

### Task 1: `POST /requirements` acepta y pasa `subscriberUserIds`

**Status:** Completed

#### Description

Agregar el campo opcional `subscriberUserIds` al esquema Joi de `requirements-post.ts` y pasarlo
**sin transformar** al payload de `requirements.new`, con spread condicional.

Es el cambio más chico de la story y el que habilita CA-5: sin él, la ruta interna nunca puede
disparar un alta con suscriptores, y solo el portal tiene acceso a la funcionalidad nueva que `core`
ya soporta.

**Sin transformar** es literal: la api **no** deduplica, **no** agrega el creador, **no** valida que
los ids existan. Esta ruta no tiene el comportamiento de auto-suscripción del portal (eso es
específico de `opus`), y la validación de existencia es del escritor (`core` la hace dentro de la
transacción y responde `user_not_found`, que ya sale 404 por el mapa).

#### Acceptance Criteria

1. `createSchema` de `api/lib/routes/requirements-post.ts` declara

2. `subscriberUserIds` se desestructura de `req.body` en `createRequirement`.
3. El payload de `sendCommand(res, 'requirements.new', ...)` incluye
   `...(subscriberUserIds !== undefined ? { subscriberUserIds } : {})` — **spread condicional**, con
   la clave **ausente** del payload cuando el cuerpo no la trae.
4. El valor se pasa **tal cual llegó**: sin deduplicar, sin agregar `req.user.id`, sin ordenar.
5. Nada más del archivo cambia: ni la cadena de middlewares, ni el `validateProject` local, ni la

### Task 2: `POST /opus/requirements` publica un solo comando

**Status:** Completed

#### Description

Reemplazar el N+1 de `opus-requirements-post.ts` por un comando único: el `Set` de suscriptores que
hoy se arma **después** del alta para publicar un `requirements.{id}.subscriptors.new` por cada uno,
pasa a armarse **antes** y a viajar dentro del payload de `requirements.new`.

Es CA-6, y trae CA-7 pegado: el auto-suscribir al creador **no se toca**, solo se mueve de lugar —
el mismo `new Set([req.user.id, ...(subscriberUserIds || [])])` que ya existe, ahora como campo del
comando en vez de como bucle de comandos.

Además del beneficio pedido (eliminar la carrera), la unificación **corrige un bug**: hoy, si el
requisito se crea y una suscripción posterior falla, el requisito queda creado y sin sus
suscriptores, y el cliente recibe un error de una operación que ocurrió a medias. Con un solo
comando la atomicidad la da la transacción de `core`.

#### Acceptance Criteria

1. El handler `createRequirement` arma `const subscribers = [...new Set([req.user.id, ...(subscriberUserIds || [])])]`
   **antes** de publicar, y lo pasa como `subscriberUserIds` en el payload de `requirements.new`.
2. El campo se pasa **siempre** (no con spread condicional), porque el set **nunca está vacío**: el
   creador siempre está. Es la diferencia deliberada con Task 1, y hay que dejarla comentada.
3. El creador queda **primero** en el array (`[req.user.id, ...]`), preservando la semántica del `Set`
   de hoy.
4. **Se elimina el bucle completo** (`opus-requirements-post.ts:54-61`): el `for (const userId of subscribers)`
   con su `runCommand(...)` y su `if (!ok) return;`.
5. Si `runCommand` queda sin usar en el archivo, **se elimina del import** (`import { sendCommand }`,
   sin `runCommand`). ESLint marca el import muerto y el build falla.
6. El comentario `// Las suscripciones son comandos aparte. El creador queda suscripto siempre.` se
   **reemplaza** por uno que explique la unificación y por qué el creador va primero.
7. El JSDoc del handler (`opus-requirements-post.ts:26-33`) se actualiza: la frase "acá el creador
   puede suscribir a otros usuarios de una" sigue siendo verdad, pero conviene decir que ahora viaja
   en el mismo comando.
8. Nada más cambia: ni el esquema Joi (ya declara `subscriberUserIds`), ni el `validateProject`
   local, ni la relectura `Requirement.findByPk`, ni el status 201.
9. **Ningún** `requirements.{id}.subscriptors.new` se publica desde esta ruta después del cambio.

#### Technical Details

**Architectural Context References:**

- **Flow Context** → el diagrama "HOY (N+1 comandos)" vs "DESPUÉS (un solo comando)" es la
  especificación exacta de esta tarea.
- **ADR-003 → efecto en la api**: el rollback de `user_not_found` es completo y automático. **No
  agregues compensación**: el handler solo corta con `if (!data) return;`.
- **`bus-commands` — `runCommand` vs `sendCommand`**: esta tarea elimina el único `runCommand` del
  archivo. El `sendCommand` que queda ya trae el `if (!data) return;`.
- **`bus-commands` — el sobre**: `withActor` inyecta `actor` solo. `req.user.id` se sigue usando como
  campo **de dominio** `creator`, y **también** —esto es nuevo— como primer elemento del set de
  suscriptores. Son dos usos distintos del mismo dato y los dos son correctos.
- **`bus-commands` — sin reintento**: los comandos no son idempotentes. Un 504 significa que la
  operación **pudo** haber ocurrido; no reintentes ni publiques nada de compensación.
- **API Context → `POST /api/opus/requirements`**: su contrato HTTP **no cambia**.
- **Reusable Code → `fakeBus`**: `failWithNoResponders()` y `failWithTimeout()` para TS-15 y TS-16.

**Files to Create/Modify:**

- `lib/routes/opus-requirements-post.ts` — modificar (handler + imports + comentarios)

**Implementation Notes:**

- La forma del cambio, concretamente:

  ```ts
  // El creador queda suscripto siempre, y el set viaja DENTRO del comando: `requirements.new`
  // crea el requisito y sus suscripciones en la misma transacción (S-070). Antes esto eran N+1
  // comandos —uno por suscriptor, después del alta—, y si uno fallaba el requisito quedaba
  // creado y sin suscriptores. Con un solo comando la atomicidad la da la transacción de core.
  //
  // Va SIN spread condicional, a diferencia de la ruta interna: acá el array NUNCA está vacío,
  // porque el creador siempre está. Y va primero, que es el orden que ya tenía el Set.
  const subscribers = [...new Set([req.user.id, ...(subscriberUserIds || [])])];

  const data = await sendCommand<{ id: number }>(res, 'requirements.new', {
    creator: req.user.id,
    title,
    description,
    projectId,
    subscriberUserIds: subscribers,
    ...(priority !== undefined ? { priority } : {}),
    ...(type !== undefined ? { type } : {}),
    ...(estimatedFinishDate !== undefined ? { estimatedFinishDate } : {}),
    ...(fileIds !== undefined ? { fileIds } : {}),
  });
  if (!data) {
    return;
  }

  const requirement = await Requirement.findByPk(data.id);
  return res.status(201).json(requirement);
  ```

- **`[...new Set(...)]`, no `new Set(...)` a secas.** Hoy el código deja el `Set` como `Set` porque
  lo itera con `for...of`; ahora tiene que ser un **array**, porque va serializado en JSON al bus y
  un `Set` serializa como `{}`. **Es el error más fácil de cometer en esta tarea** y el test que lo
  atrapa es TS-9.
- `core` deduplica igual por su cuenta, pero **el `Set` de la api se conserva**: es el que garantiza
  que el creador repetido en el cuerpo no duplique (TS-11), y es el comportamiento que ya existe.
  Quitarlo sería delegar en `core` algo que esta capa ya resuelve.
- Después de borrar el bucle, verificá que `runCommand` no se use en ninguna otra parte del archivo
  antes de sacarlo del import.
- **No toques** el bloque de archivos (`fileIds`) ni la respuesta.

**Dependencies:**

- Librerías externas: **ninguna nueva**.
- Módulos internos: `sendCommand` de `../utils/bus/send-command` (ya importado; se le quita
  `runCommand`).
- Servicios: `core` (ya soporta el campo).
