**Los cinco archivos de `nats/auth-callout/` son el entregable central de este plan.** Los otros
cambios (compose, `.env`, scripts, docs) son la periferia que los hace efectivos y consistentes.

#### Patrón de organización de las plantillas del callout

Cada plantilla es un YAML con tres claves y **comentarios en castellano que explican el porqué**:

```yaml
pub:
  allow:
    - "<subject o patrón>"     # qué puede publicar
sub:
  allow:
    - "<subject o patrón>"     # qué puede escuchar
response:
  max: 1                       # respuestas implícitas permitidas por request recibida
  ttl: 45s
```

**Placeholders que el callout expande** (idénticos en las cuatro plantillas):

| Placeholder | Qué es |
|---|---|
| `{{instance}}` | La instancia de deploy (`CALLOUT_INSTANCE`, que el compose ata a `NATS_INSTANCE`) |
| `{{user_id}}` | El `sub` del token, **crudo**. Guion **BAJO**, no `{{user-id}}` |
| `{{user_id_hash}}` | Hash estable del user id — **solo** para el prefijo de inbox |
| `{{service}}` | El campo `service` de la regla de `rules.yaml` que matcheó. **Es un solo valor** |

**`{{service}}` es la razón de la mitad de este plan.** Ahora hacen falta **dos** prefijos de
suscripción (`jiku-commands` y `jiku-queries`) y el placeholder solo puede llevar uno. No hay forma
de expresarlo con la variable, así que en `core.yaml` y en `observer.yaml` los dos prefijos van
**escritos literalmente**. Es también la razón por la que esas dos plantillas son el lugar donde se
olvida `$SRV.>`: se dejan de leer como "una línea con una variable" y pasan a ser una lista.

#### Convención de estilo, que acá es contenido y no cosmética

Los comentarios de `rules.yaml` y de las cuatro plantillas **explican decisiones de seguridad**:
por qué `external-publisher` va arriba de `internal-app` en el orden de evaluación, por qué el
inbox va bajo el hash y no bajo el user id crudo, por qué no hay catch-all. Un comentario que queda
diciendo `gestion` después de este plan **no es un detalle de formato**: es documentación de
seguridad que contradice el archivo en el que vive, y la próxima persona que lo lea va a creerle al
comentario. **Los comentarios se actualizan con las mismas ganas que las líneas de permiso**, y
cada tarea de este plan enumera los suyos.

Lo mismo con `.env.dist`: es la plantilla que alguien copia para instalar el producto. Un bloque de
comentario que describe una variable que ya no existe es una instrucción para configurar algo que
no hace nada.

### Relevant ADRs

#### ADR-002: Comandos por NATS sin JetStream

**Decisión:** los comandos van por NATS core en request/reply, sin JetStream, sin persistencia. Las
réplicas de `core` escalan con **queue group**. El subject lleva el user id del caller con wildcard
para que sumar un publicador nuevo no requiera tocar código.

**Implementation Rules (verbatim de `docs/adrs/ADR-002-comandos-nats-sin-jetstream.md`:63-82):**

- Todo comando **DEBE** publicarse con el subject `{instance}.{user-id}.gestion.v1.{comando}`,
  usando la gramática de `@jiku/nats-protocol`. **NO SE DEBE** construir el subject a mano.
- El cliente NATS **DEBE** fijar `inboxPrefix` explícitamente al conectar, con el hash del user id
  que calcula `@jiku/nats-protocol`. Sin esto las respuestas no llegan.
- El `userId` con el que publica la api **DEBE** salir de la key del service user, **NO** de una
  variable de entorno: tiene que coincidir exactamente con el `sub` que el auth-callout lee del
  token para autorizar el subject.
- Toda respuesta **DEBE** tener el formato `{ status: 'success', data }` o
  `{ status: 'failure', errorCode, errorMessage }`. **NO SE DEBEN** inventar otros formatos.
- Los comandos de creación **DEBEN** devolver únicamente `{ id }`. Las ediciones y borrados, nada.
- Todo `errorCode` nuevo **DEBE** agregarse al mapa de `api/lib/utils/bus/protocol.ts` con su
  status HTTP. Un código sin mapeo cae en un 500 genérico.
- El timeout de la request es `NATS_REQUEST_TIMEOUT_MS` (default **5000 ms**); al expirar la api
  **DEBE** responder **503**.
- **NO SE DEBE** transportar datos estructurados dentro de `errorMessage`. El caso actual de
  `daily_limit_exceeded` —que la api recupera parseando el mensaje con un regex— es deuda
  explícita, no un patrón a imitar.
- Core **NO DEBE** publicar mensajes: solo responde el `Reply` de la request que recibe.

> **La primera regla todavía dice `gestion` — y NO se corrige en esta story.** El REQ-004 saca los

#### ADR-007: Identidad en Zitadel con auth-callout

**Decisión:** una sola fuente de identidad (Zitadel) para los cuatro servicios y los dos frontends.
Los servicios se autentican al bus con el token de un service user; el **auth-callout** intercepta
la conexión, valida el token, lee el rol y **mintea los permisos de subject** para esa conexión.
La autorización del bus es dinámica y por identidad, no un secreto compartido.

**Implementation Rules (verbatim de `docs/adrs/ADR-007-identidad-zitadel-auth-callout.md`:59-75):**

- Todo servicio que se conecte al bus **DEBE** autenticarse con el token de un service user
  obtenido vía `@jiku/zitadel-auth`, con auto-refresh. **NO SE DEBE** usar un token de larga
  duración por variable de entorno.
- El `userId` para publicar **DEBE** derivarse de la key del service user, **NO** de una variable
  de entorno.
- El cliente NATS **DEBE** fijar `inboxPrefix` con el hash de `@jiku/nats-protocol`.
- La api **DEBE** validar los tokens de usuario contra el JWKS de Zitadel, con resincronización
  ante `kid` desconocido (`KEY_SYNC_ATTEMPS` reintentos).
- Los roles **DEBEN** leerse del claim `urn:zitadel:iam:org:project:{PROJECT_ID}:roles`.
  **NO SE DEBEN** almacenar roles en la base ni derivarlos de otra fuente.
- `AUTH_BYPASS=true` **DEBE** seguir siendo opt-in explícito, **prohibido con
  `NODE_ENV=production`** (el arranque debe fallar) y exigir `DEV_USER_ID`. **NO SE DEBE**
  activar por ausencia de otra variable.
- El producto **NO DEBE** escribir la tabla `users` para modificar identidad: es espejo del
  proveedor. (El alta de la fila local es otro asunto — ver FG-1.)
- **Un cambio en `rules.yaml` del auth-callout DEBE tratarse como cambio de seguridad: es lo que
  define quién puede escribir en el producto.**

> **La última regla aplica a la Tarea 1 de este plan, literalmente.** El diff se revisa como un
> cambio de seguridad, no como configuración: quién puede escribir en el producto es exactamente lo
> que se está tocando.

#### ADR-008: Autorización deny-by-default

**Decisión:** el default es denegar, y las excepciones se **enumeran explícitamente** en un archivo
cuyo único propósito es enumerarlas — un cambio que sí salta en revisión. El ADR está escrito sobre
la capa HTTP de la api (`validateToken` global + `api/lib/config/public.ts`), pero el principio es
el que gobierna las plantillas del callout, y la story lo invoca por eso.

**Cómo se materializa en este plan:**

- `rules.yaml` **no tiene catch-all**: un token válido de Zitadel con un rol que no está declarado
  **no conecta**. Los roles `user` y `external-user` no tienen regla, y eso es lo que mantiene a las
  personas fuera del bus. **No agregues un catch-all.**
- `templates/external-publisher.yaml` **enumera** sus subjects en vez de abrirse a `>`. Es la
  plantilla más restrictiva del sistema **a propósito**, y este plan la renombra **sin aflojarla**
  (CA-9). Abrirla a `jiku-commands.v1.>` sería una línea menos y una regresión de seguridad.
- `templates/core.yaml` y `templates/observer.yaml` **enumeran** los dos prefijos en vez de
  abrirse a `{{instance}}.*.>`. Enumerar es más largo y es el punto.
- **Regla derivada, para este plan:** si en algún momento la salida más corta parece ser ampliar un
  patrón, **es la salida equivocada**. La forma correcta de agregar un permiso acá es agregar una
  línea a una lista.

**Regla de ADR-008 que aplica textualmente:** *"Cualquier cambio en ese archivo es un cambio de
seguridad y debe revisarse como tal."* Vale para `rules.yaml` y para las cuatro plantillas.

### API Context

`deploy/` no expone HTTP y este plan no cambia ningún endpoint. La "API" acá es **la gramática de
subjects del bus** y **el contrato de la imagen del callout**.

#### La gramática del bus — no cambia; cambia el conjunto de valores de `{svc}`

**Estado actual del contrato** (verbatim de `docs/apis/core.yaml`:115-124 — **ya actualizado por el
plan de `nats-protocol`**, no hay nada que hacer ahí):

```
  {instance}.{user-id}.{svc}.{version}.{method}
  dev.323332022539911171.jiku-commands.v1.clients.new

  instance   deployment: dev / prod              (NATS_INSTANCE)
  user-id    WHO publishes: the token's `sub`, RAW
  svc        jiku-commands                       (NATS_COMMAND_SERVICE)
             jiku-queries                        (NATS_QUERY_SERVICE)
```

Suscripciones, antes y después:

```
{instance}.*.gestion.v1.>        queue group: gestion         - ELIMINADO
{instance}.*.jiku-commands.v1.>  queue group: jiku-commands   + NUEVO
{instance}.*.jiku-queries.v1.>   queue group: jiku-queries    + NUEVO
```

**Por qué la separación va en `{svc}` y no anidada bajo el servicio actual** — esto importa para
entender por qué las plantillas enumeran y no usan `>`: la suscripción de comandos es
`{instance}.*.{svc}.v1.>`, y ese `>` **se come también las consultas** si comparten el token
`{svc}`. Con dos queue groups distintos sobre subjects solapados el mensaje se entrega a **las dos**
suscripciones y salen **dos respuestas al mismo inbox**; un `request()` devuelve la primera y
**descarta la segunda en silencio**. El síntoma serían respuestas correctas la mitad de las veces,
sin ningún error. Con `{svc}` distinto el problema no existe: **NATS compara los tokens enteros**,
así que `jiku-queries` no matchea un patrón que dice `jiku-commands`. Esa comparación entera es
también todo el mecanismo de CA-8.

**Lo que NO cambia:** el envelope `Reply`, el catálogo de `ErrorCode`, la semántica de los 20
comandos, el inbox hasheado, `v1`.

#### El contrato de la imagen del auth-callout

La imagen se configura por variables con prefijo `CALLOUT_*` (es el contrato de la imagen publicada,
no una convención del producto). Lo relevante para este plan, tal como está en los tres compose:

| Variable | Valor en los compose | Qué implica acá |
|---|---|---|
| `CALLOUT_SERVER_MODE` | `operator` | El árbol de creds de `bootstrap.sh` es la raíz de confianza |
| `CALLOUT_RULES_PATH` | `/etc/auth-callout/rules.yaml` | `./nats/auth-callout` se monta **read-only**; el callout lee `rules.yaml` y las plantillas de ahí |
| `CALLOUT_INSTANCE` | `${NATS_INSTANCE}` | Es el `{{instance}}` de las plantillas |
| `CALLOUT_IDP_MODE` | `${GESTION_IDP_MODE}` (`zitadel`) / `${GESTION_IDP_MODE:-mock}` en `dev` | **`mock` decodifica la identidad del texto del token (`mock:<sub>:<user>:<roles>`), sin secretos ni red.** Es lo que hace verificables CA-7 a CA-9 en local |
| `CALLOUT_ZITADEL_PROJECT_ID` | `${GESTION_ZITADEL_PROJECT_ID}` | Proyecto del claim de roles |

**No hay ninguna variable `CALLOUT_*` que nombre el servicio.** El nombre del endpoint sale del
campo `service` de la regla que matcheó en `rules.yaml`. Por eso el auth-callout **no cambia en los
compose**: todo su cambio está en los cinco archivos YAML montados.

> **`CALLOUT_IDP_MODE=mock` es la herramienta de verificación de este plan.** Permite conectar con
> un token de texto plano que declara el rol que uno quiera (`mock:<sub>:<user>:core`), y el callout
> mintea los permisos de la plantilla de ese rol. Sin Zitadel, sin secretos, sin red. Es lo que
> convierte CA-7, CA-8 y CA-9 de "verificable por lectura" en "verificable por ejecución", que es la
> diferencia que importa: **un permiso mal escrito falla al conectar, no al revisar.**

#### Escenario 1: un comando de escritura después del rename (CA-6)

El flujo end-to-end que este plan tiene que dejar funcionando. Los pasos marcados **[este plan]** son
los que dependen de estos cambios:

1. **[`web`]** `POST /api/clients` con `{name, description}`. Sin cambios.
2. **[`api` — `lib/routes/clients-post.ts`]** `sendCommand(res, 'clients.new', {...})`. El subject lo
   arma `commandSubject('clients.new', userId)` → `dev.<uid>.jiku-commands.v1.clients.new`
   **(ya MODIFICADO por el plan de `nats-protocol`)**. El archivo de ruta no cambia. Espera en
   `_INBOX.<hash(uid)>`.
3. **[auth-callout] ← ESTE PLAN.** La plantilla `api` autoriza el prefijo nuevo → la publicación
   pasa. **Sin este cambio, el mismo código es rechazado por permisos.** Es el paso que hoy está
   roto en cualquier entorno que corra el código nuevo.
4. **[NATS]** Matchea `dev.*.jiku-commands.v1.>` — la suscripción que `consumer.ts`:69 armó con
   `subscriptionSubject()`, que resuelve al nombre nuevo porque `SERVICE_NAME` es alias de
   `COMMAND_SERVICE`. Queue group `jiku-commands`, del **mismo** símbolo (`consumer.ts`:70): **una**
   réplica atiende.
5. **[auth-callout] ← ESTE PLAN.** La plantilla `core` autoriza esa suscripción. Sin el cambio,
   `core` no puede suscribirse y **no hay quien atienda**.
6. **[`core` — `bus/consumer.ts`, SIN TOCAR]** `for await` → `void dispatcher.dispatch(...)`.
7. **[`core` — `bus/dispatcher.ts`, SIN TOCAR]** `commandFromSubject` (alias de `methodFromSubject`),
   `validate`, transacción, `execute`, commit si `success` (ADR-003) → `success({ id })`.
8. **[`api`]** Recibe el envelope, relee la base y responde `201` (ADR-001).

**Outcome:** comportamiento **idéntico** al de antes del rename. `core` sin una línea modificada.

**Manejo de errores:** si la plantilla del callout no autoriza el prefijo nuevo, la publicación o la
suscripción se rechazan por permisos (`Authorization Violation`). **Es la razón por la que el callout
y el paquete van en la misma story:** separarlos produce exactamente la ventana en la que estamos hoy.

#### Escenario 2: un consumidor con permiso de solo lectura (CA-8)

1. **[consumidor]** Conecta; el callout mintea sus permisos desde la regla de su rol, al que se le

2. Publica en `{instance}.{uid}.jiku-queries.v1.tasks.list` → **autorizado**.
3. Publica en `{instance}.{uid}.jiku-commands.v1.clients.new` → **rechazado**: el token `{svc}` no

**Outcome:** lectura sin escritura, expresado como un permiso de prefijo. Con las consultas anidadas
bajo el servicio de comandos no habría forma de acotarlo sin enumerar recursos uno por uno.

**Hoy no existe ningún rol con ese permiso** (no hay consumidor de consultas). CA-8 es una propiedad
del diseño, y su verificación está resuelta en TS-24 con una regla **efímera y no commiteada** en el
stack `dev` con IdP mock.

#### Escenario 3: el publicador externo (CA-9)

1. **[externo]** Conecta con rol `external-publisher`; el callout mintea sus **9** subjects
   enumerados, ya con el nombre nuevo.
2. Publica `{instance}.{uid}.jiku-commands.v1.files.request-upload` → autorizado.
3. Publica cualquier comando fuera de la lista → **rechazado**.

**Outcome:** el rol más restrictivo del sistema sigue siéndolo. **Su plantilla no se abre a `>`.**

> El rol `external-publisher` **sigue vigente** después de S-010: lo que S-010 dio de baja fue el

### Integration Points

- **NATS** (`nats:2.10-alpine`, modo operator). El árbol de operador/cuentas/creds lo generó
  `bootstrap.sh` y **no se regenera**: nada de este plan lo requiere, y RF-22 lo prohíbe. Las creds
  del sentinel (`NATS_CREDS`) **no conceden permisos por sí solas** — es el token de Zitadel el que
  dispara el callout que los mintea.
- **auth-callout** (imagen externa). Lee `rules.yaml` y las plantillas del volumen **read-only**
  `./nats/auth-callout:/etc/auth-callout:ro`. **Consecuencia operativa que hay que conocer: un
  cambio en estos archivos requiere reiniciar el contenedor del callout** (`docker compose restart
  auth-callout`) para que los relea. Un cambio aplicado sin reinicio se ve en el archivo y no en el
  bus, y el síntoma es un permiso viejo que "no se actualizó".
- **Zitadel** (`GESTION_ZITADEL_*`). **Nada que hacer acá:** no hay rol nuevo ni service user nuevo
  (RF-20). Los dos servicios micro de S-012/S-013 usan el service user y el rol `core` que ya
  existen. Si en algún momento se separan a deployables distintos, ahí sí hace falta un rol nuevo —
  y `templates/core.yaml` es el único archivo que se parte.
- **PostgreSQL.** Solo declaración de variables; ninguna conexión nueva se abre en esta story.

### Code Conventions

**Variables de entorno** (`.env` / `.env.dist`):
- `SCREAMING_SNAKE_CASE`, una por línea, `CLAVE=valor` sin espacios alrededor del `=`.
- Cada variable o grupo va precedido de un comentario en castellano que dice **qué es y qué pasa si
  falta o si se cambia mal**. Los `.env` de este repo son documentación además de configuración.
- Secciones separadas por `# ====` con un título.
- **`.env.dist` no lleva secretos**; los campos sensibles quedan vacíos (`API_SERVICE_USER_KEY_B64=`).
- **`.env` y `.env.dist` se editan en paralelo y con el mismo contenido no sensible.** Un valor
  nuevo que va solo en uno de los dos es el bug más común de este archivo: `.env.dist` es lo que
  alguien copia para instalar, `.env` es lo que corre en la máquina de quien edita, y los compose
  leen `.env`. Sacar una variable del compose pero no del `.env` la deja definida y sin uso; agregarla
  al compose pero no al `.env` la deja resolviendo a **cadena vacía**, sin error.

**Docker Compose:**
- Variables inyectadas como lista: `- CLAVE=${VARIABLE_DEL_ENV}`.
- El nombre de la variable **dentro** del contenedor puede diferir del nombre en `.env` cuando el
  valor se reusa: es el patrón que ya usa `POSTGRESQL_USER=${DATABASE_READONLY_USER}`.
- Los comentarios explican **por qué** un servicio recibe una credencial y no otra.
- Los tres compose se mantienen consistentes entre sí en el bloque de cada servicio, aunque difieran
  en imagen, red y puertos.

**Plantillas y reglas del callout:** ver "Patrón de organización" y "Convención de estilo" arriba.

**Scripts bash:** `set -euo pipefail`, `cd "$(dirname "$0")"`, defaults con
`${VARIABLE:-default}`.

**Documentos de `docs/flows/`:** castellano, subjects entre backticks con los tokens variables entre
llaves (`{instance}.{user-id}.jiku-commands.v1.clients.new`).

### Reusable Code

**No aplica.** No existe `docs/reusable-code/deploy/` y no tiene sentido que exista: `deploy/` no
tiene código de aplicación, ni módulos, ni funciones que reusar. Los catálogos que sí existen
(`api`, `core`, `nats-protocol`, `web`, `opus-web`) documentan servicios de código.

Lo más cercano a "código reutilizable" acá son **los patrones de los archivos que ya están en
`deploy/`**, y la regla es: **copiar la forma del vecino**. Una variable nueva en `.env.dist` se
escribe como las que ya están (comentario que explica el modo de falla + `CLAVE=valor`); una línea
de permiso nueva se escribe como las que ya están. **No inventes un estilo nuevo en un archivo que
ya tiene uno.**

### 3. `deploy/nats/auth-callout/templates/core.yaml`

**El archivo central del plan.** Dos apariciones de `gestion` en comentarios (8, 12) y la línea de
suscripción (29).

**Objetivo del bloque `sub`** — de dos entradas a cuatro:

```yaml
sub:
  allow:
    # Los comandos dirigidos a su endpoint de escrituras, de cualquier caller.
    - "{{instance}}.*.jiku-commands.v1.>"
    # Las consultas, ídem. Todavía no hay servicio que las atienda (es S-013).
    - "{{instance}}.*.jiku-queries.v1.>"
    # Discovery y stats de micro. SIN ESTO LOS SERVICIOS LEVANTAN Y SON INVISIBLES para
    # `nats micro ls`: no hay error, no hay log, solo desaparece la observabilidad.
    # No expone payloads de negocio, solo metadata del protocolo de servicios.
    - "$SRV.>"
    # Inbox propio (respuestas de los servicios que llame), bajo el hash de su user id.
    # Es POR RÉPLICA, no por endpoint: dos réplicas con distinto service user no se roban
    # las respuestas.
    - "_INBOX.{{user_id_hash}}.>"
```

**El orden importa para la legibilidad, no para el funcionamiento:** comandos, consultas, `$SRV.>`,
inbox. Es el orden del REQ-004 §10.5 y es el que agrupa los dos prefijos del protocolo antes de los
dos permisos de infraestructura.

**`$SRV.>` no lleva `{{instance}}`** y es correcto: es un subject del protocolo de servicios de NATS,

**Declararlas todas ahora es deliberado**, y la razón es asimétrica: la configuración de despliegue
es el **estado final** y se toca una vez. Una variable declarada sin consumidor **no hace nada**;
una variable que falta cuando el código la busca **tira el arranque** (o peor: resuelve a cadena
vacía y no tira nada). El costo de adelantarse es cero y el de atrasarse es un deploy roto.

##### Decisión: `POSTGRESQL_READ_USER` / `_PASSWORD` no son claves nuevas de `.env`

Se cablean en el compose a las claves que **ya existen**:

```yaml
      - POSTGRESQL_READ_USER=${DATABASE_READONLY_USER}
      - POSTGRESQL_READ_PASSWORD=${DATABASE_READONLY_PASSWORD}
```

**Por qué.** El REQ-004 §10.6 es explícito: *"`POSTGRESQL_READ_USER` puede ser el mismo rol que ya
usa la api: es de solo lectura y no hay razón para crear otro. Lo que no puede es ser el usuario
dueño."* Y ese rol ya está en `.env` (`DATABASE_READONLY_USER=grava_readonly`) y ya lo consume la api
en los tres compose. Crear un par de claves nuevas con el mismo valor sería **duplicar una
credencial en dos lugares**, que es el tipo de cosa que se desincroniza en la primera rotación de
contraseña — y el síntoma sería `core` leyendo con una contraseña vieja mientras la api lee bien.

Esto satisface CA-11: las variables quedan **declaradas** en la configuración de despliegue, que es
donde vive el contrato del contenedor. Es además el patrón que el repo ya usa
(`POSTGRESQL_USER=${DATABASE_READONLY_USER}` en el bloque de la api).

**Si S-013 necesita un rol distinto** (por ejemplo con `statement_timeout` fijado a nivel de rol),
ahí se agregan las claves propias. No es una deuda de este plan: es una decisión que corresponde a
la story que escribe el código que abre la conexión.

##### La invariante que no es una coincidencia de defaults

```
POSTGRESQL_STATEMENT_TIMEOUT_MS (8000)  <  NATS_QUERY_TIMEOUT_MS (10000)
```

**Estrictamente menor.** No es que "quedaron distintos": es un requisito. Si el timeout de la
sentencia fuera mayor o igual, una consulta lenta agotaría primero el timeout del bus y el caller se
quedaría esperando **sin saber por qué**. Con la sentencia venciendo primero, la base corta, `core`
la convierte en un `failure` con código, y el caller recibe un error **explicable**. Es el mismo
principio de "fallar ruidoso" de todo el REQ.

**Los comentarios de las dos variables en `.env.dist` tienen que decirlo, y referenciarse
mutuamente.** Es la única forma de que alguien que suba una de las dos se entere de que hay otra.

##### `SERVICE_VERSION` tiene que ser SemVer estricto

Micro valida la versión con la regex oficial de SemVer y **rechaza cualquier otra cosa**. Un `latest`
o un `1.0` ahí es un **arranque fallido** en S-012. El comentario en `.env.dist` tiene que advertirlo,
y los compose **no** deben sobreescribirlo con un tag de imagen (la tentación es
`SERVICE_VERSION=${CORE_VERSION}`, que hoy vale `1.0.0` y funcionaría, pero ata la versión anunciada
en el bus al tag de la imagen — dos cosas que no tienen por qué moverse juntas). **Va como variable
propia.**
