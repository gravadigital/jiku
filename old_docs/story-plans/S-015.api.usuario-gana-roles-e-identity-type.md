### Relevant ADRs

#### ADR-001: Separación lectura/escritura por credenciales de base de datos

**Decisión:** separar lectura y escritura en dos servicios, y hacer que la separación **la imponga
PostgreSQL por permisos**, no una convención de código. La `api` conecta con un rol **sin
`INSERT`/`UPDATE`/`DELETE`**; `core` conecta con el usuario dueño y es el único que escribe.

**Implementation Rules (verbatim):**

- Toda escritura de dominio nueva **DEBE** implementarse como comando en `core`. **NO SE DEBE**
  agregar escritura con el ORM en `api`.
- La conexión de `api` **DEBE** usar credenciales sin `INSERT`/`UPDATE`/`DELETE`. Si un endpoint
  nuevo requiere escribir, la respuesta correcta es un comando, no ampliar los permisos del rol.
- La conexión de `core` **DEBE** usar el usuario dueño de la base.
- Las migraciones **DEBEN** correr desde `api` con `POSTGRESQL_MIGRATION_USER`, nunca desde `core`.
- Después de publicar un comando de creación, la api **DEBE** releer la base para armar la
  respuesta: core devuelve solo `{ id }` y el contrato con los frontends es el recurso completo con
  sus relaciones.
- Un endpoint que lee **NO DEBE** pasar por el bus: la lectura va directo a PostgreSQL desde la api.
  **Excepción declarada desde REQ-001 (S-005): la lectura de archivos.**

**Cómo aplica acá:** la migración de la Tarea 1 es la **primera de las tres excepciones que el ADR
ya declara** ("las migraciones corren al arrancar la api con credenciales propias. Es intencional:
la api es la dueña del esquema"). **No hay decisión nueva.** Y el filtro de la Tarea 2 es una
lectura: va directo a PostgreSQL, no por el bus.

#### ADR-005: Modelos compartidos en `@jiku/models`

**Implementation Rules (verbatim):**

- Los modelos Sequelize **DEBEN** vivir en `@jiku/models`. **NO SE DEBE** definir un modelo dentro
  de `api/` o de `core/`.
- `@jiku/models` **NO DEBE** abrir una conexión ni leer variables de entorno de base de datos.
  Exporta clases; la instancia la crea cada servicio.
- Cada servicio **DEBE** registrar las clases en su propio `Sequelize` con sus credenciales.
- Un cambio de esquema **DEBE** hacerse en dos lugares en el mismo cambio: la migración en
  `api/db-upgrade/migrations/` y el modelo en `@jiku/models`. Uno sin el otro deja el código y la
  base desalineados.
- Los hooks que van en el modelo son los que pertenecen **al dato**. Los que dependen del caso de
  uso o del rol **DEBEN** ir en el comando de core o en la api.
- Los nombres en `@jiku/models` **DEBEN** ser los reales de la base. La traducción de vocabulario
  es responsabilidad de core.
- Al agregar un modelo, **DEBE** registrarse en el índice del paquete.

**Cómo aplica acá:** la cuarta regla es la que obliga a que este plan y el de `models` se
**despliegen juntos**. El ADR declara como riesgo, sin mitigación: *"`sequelize.sync()` corre en
testing y development, mientras producción se construye con las migraciones: dos fuentes de
verdad"*. Ese riesgo **es** la razón de existir de esta story.

#### ADR-013: Tests contra base real

**Implementation Rules (verbatim):**

- Los tests de `api` y `core` **DEBEN** correr contra PostgreSQL real. **NO SE DEBEN** mockear los
  modelos de Sequelize.
- Los tests de comandos de `core` **DEBEN** entrar por el despachador (`dispatch()`), **NO** por
  `execute()` directamente.
- Un test de escritura de la api **DEBE** verificar las tres capas: comando publicado, traducción
  de la respuesta a HTTP, y que la fila quedó escrita. **NO SE DEBE** asertar solo el status HTTP.
- `reply()` / `failWith()` **DEBEN** usarse solo para cubrir caminos de error. El camino feliz
  **DEBE** ejecutar core de verdad.
- Cada archivo de test **DEBE** poder correr solo: el esquema y el mock de auth se preparan en
  fixtures globales de Mocha.
- `TZ=UTC` **DEBE** estar fijado en la configuración de test de todo servicio.
- La limpieza entre corridas **DEBE** ser `TRUNCATE ... RESTART IDENTITY CASCADE`, para que los ids
  autoincrementales sean predecibles.
- **NO SE DEBE** depender del orden de ejecución entre archivos de test.

**Cómo aplica acá, y es la trampa central de este plan:** los tests corren contra el esquema que
produce `sync()`, donde `identity_type` es un **`VARCHAR(255)` sin CHECK**. Consecuencia directa:
**no escribas un test de Mocha que afirme que un valor inválido es rechazado** — pasaría en
producción y fallaría en `testing`, por una razón que no es un bug del producto. La verificación
del ENUM nativo va por SQL contra una base migrada (Tarea 5), no por la suite.

#### ADR-008: Autorización deny-by-default

Aplica de fondo: el filtro de la Tarea 2 **es defensa, no corrección**. Hoy un service user tampoco
aparecería en el listado (sale de `user_project_permissions` y no tiene fila ahí). Se agrega para
que **conceder un permiso de proyecto a un service user por error no lo meta en un selector de
personas**.

Spec actual (`docs/apis/api.yaml`, verbatim):


Implementación actual (`api/lib/routes/opus-projects-projid-users-get.ts`, verbatim):

```ts
function getProjectUsers(req: Request, res: Response) {
  const project = req.project;

  return UserProjectPermission.findAll({
    where: { projectId: project.id },
    include: [{
      model: User,
      as: 'user',
      attributes: ['id', 'name', 'email']
    }],
    order: [[{ model: User, as: 'user' }, 'name', 'ASC']]
  })
    .then((permissions) => {
      const users = permissions.map((permission) => permission.user);
      return res.status(200).json(users);
    })
    .catch((error) => {
      logger.error(`[GET /opus/projects/:projid/users] getProjectUsers error: ${error.message}`);
      return res.status(500).json({
        code: 'internal_error',
        message: 'Internal server error',
      });
    });
}

router.get('/opus/projects/:projid/users',
  validateProject,
  hasAnyRole(['user', 'external-user']),
  validateProjectPermissions,
  getProjectUsers
);
```

**El contrato HTTP no cambia:** mismo path, mismos middlewares, mismos `attributes`, mismo `order`,
mismo schema de respuesta, mismos códigos de error. **Cambia qué filas entran.**

**Ojo con el `where` dentro de un `include` sin `required`.** Sequelize convierte un `include` con
`where` en un **`INNER JOIN` implícito**, que es exactamente lo que se busca: la fila de permiso sin
usuario `person` **no** tiene que aparecer. Si fuera `LEFT JOIN`, el `.map(p => p.user)` de la línea
siguiente produciría `undefined` en el array de respuesta. **No pongas `required: false`.**

### Database Context

#### `users` — estado actual (DBML verbatim de `docs/db-schemas/jiku.md`)

El documento de esquema **ya fue actualizado** por el plan de `models`, así que declara las dos
columnas nuevas. La **base de producción todavía no las tiene**: eso es lo que hace esta migración.

```dbml
Table users {
  id varchar(100) [pk, note: 'sub de Zitadel']
  name varchar [not null]
  username varchar [not null]
  email varchar [not null]
  roles jsonb [not null, default: `'[]'::jsonb`, note: 'lista de strings, sin validacion de contenido']
  identity_type identity_type [not null, default: 'person', note: 'el modelo lo declara DataType.STRING a proposito']
  created_at timestamp
  updated_at timestamp
}

Enum identity_type { person service }
```

#### Las dos columnas a crear

| Columna | Tipo | Restricciones | Por qué así |
|---|---|---|---|
| `roles` | `JSONB` | `NOT NULL DEFAULT '[]'::jsonb` | La convención del esquema fija **JSONB para datos semiestructurados**. `NOT NULL` con default hace que "roles vacíos o ausentes" sea el **mismo caso** que una fila preexistente: lista vacía, sin autorización. Un `NULL` obligaría a una rama extra en la compuerta de S-017 y a un `?? []` en cada lectura |
| `identity_type` | ENUM nativo `identity_type` (`'person'`, `'service'`) | `NOT NULL DEFAULT 'person'` | La convención declara *"Enums: Tipos `ENUM` de PostgreSQL"* |

**Valores en inglés**, contra la convención *"ENUM con valores en español (son los que viajan al
front)"*: estos **no viajan al front** (CA-9) y **no los elige el producto** — son el `type` de
`deploy/nats/auth-callout/rules.yaml`, un contrato con un componente externo. Precedente en el mismo
esquema: `Enum visibility_level { public internal }`.

**Índices: ninguno.** Los dos accesos a estas columnas son **por PK** (`User.findByPk` en S-016 y
S-017) y el filtro de `opus` se aplica sobre un `include` ya acotado por `user_project_permissions`,
con cardinalidad de unidades. Un índice acá sería costo de escritura sin lectura que lo use. `roles`
es JSONB leído entero en el mismo `SELECT` de la fila: **no hay consulta por contenido, así que no
hay índice GIN que justificar.**

#### `DataType.STRING` y NO `DataType.ENUM` en el modelo — el precedente

El modelo (ya escrito, `packages/models/src/user.model.ts`:66-71) declara:

```ts
  @Column({
    type: DataType.STRING,
    allowNull: false,
    defaultValue: IdentityType.Person,
  })
    identityType!: IdentityType;
```

Declararlo `ENUM` haría que `sequelize.sync()` cree el tipo con la convención de nombre de Sequelize
—`enum_users_identity_type`— **distinto del `identity_type` que crea esta migración**. Las dos
fuentes divergirían y **ningún test lo vería**. Es el precedente documentado y deliberado de
`byte_status` / `retention_status`.

#### Comparación campo por campo (CA-11) — insumo del plan de `models`

El DDL que `sync()` emite, capturado con evidencia por la Tarea 3 de ese plan:

```
"roles" JSONB NOT NULL DEFAULT '[]'
"identity_type" VARCHAR(255) NOT NULL DEFAULT 'person'
```

| Campo | `sync()` (FUENTE 1, tests) | Migración (FUENTE 2, producción) | ¿Coincide? |
|---|---|---|---|
| Nombre de columna | `roles` | `roles` | **Sí** |
| Nombre de columna | `identity_type` | `identity_type` | **Sí** |
| Tipo de `roles` | `JSONB` | `JSONB` | **Sí** |
| Nulabilidad de `roles` | `NOT NULL` | `NOT NULL` | **Sí** |
| Default de `roles` | `'[]'` | `'[]'::jsonb` | **Sí** — mismo valor, distinta anotación de tipo |
| Nulabilidad de `identity_type` | `NOT NULL` | `NOT NULL` | **Sí** |
| Default de `identity_type` | `'person'` | `'person'` | **Sí** |
| **Tipo de `identity_type`** | **`VARCHAR(255)`** | **ENUM nativo `identity_type`** | **NO — y es la divergencia deliberada** |

> **CA-11 se cierra con esta tabla, no a pesar de ella.** Leer la última fila como un fallo lleva al
> error exacto que la story quiere prevenir: "arreglar" el modelo a `DataType.ENUM`, que crea
> `enum_users_identity_type` y convierte una divergencia **conocida, precedentada y sin
> consecuencia** en una **desconocida**. La divergencia correcta es `STRING` ↔ ENUM nativo. La
> incorrecta es `enum_users_identity_type` ↔ `identity_type`.

**`sync()` no pelea con la migración en runtime.** `api/lib/models/index.ts`:58 y
`core/src/models/index.ts` llaman `sequelize.sync()` **sin opciones** — ni `alter` ni `force`— así
que solo emiten `CREATE TABLE IF NOT EXISTS` y **no alteran una `users` existente**. En un entorno de
desarrollo donde las migraciones ya corrieron, el ENUM nativo sobrevive intacto. La divergencia
aparece únicamente en **cómo se construyó la base**: `sync()` desde cero (tests) → `VARCHAR(255)`;
migrada (producción) → ENUM nativo.

#### Estrategia y convenciones de migración

- Van en `api/db-upgrade/migrations/`, en **JavaScript** (requisito de `sequelize-cli`; es la única
  excepción a "no se escribe JavaScript nuevo" de `_base`).
- Nombre: `YYYYMMDD_NN_descripcion.js`. Tabla de control: `sequelize_meta`.
- Se esperan **aditivas**.
- `up`/`down` dentro de `queryInterface.sequelize.transaction(async (transaction) => { ... })`, con
  `{ transaction }` en **cada** `query`.
- **Comentario de bloque en español al principio del archivo, explicando el POR QUÉ y declarando si
  es reversible.** Es la convención de las migraciones recientes (`20260819_01`..`20260819_05`).
- La migración más reciente es `20260820_01_drop_external_integration.js`. La de esta story,
  `20260824_01_...`, **no colisiona**.

**Precedente 1 — ENUM nativo + columna que lo usa** (`20260819_01_create_files_table.js`):

```js
      await queryInterface.sequelize.query(
        "CREATE TYPE file_byte_status AS ENUM ('pending', 'uploaded');",
        { transaction }
      );
      // ... y la columna lo referencia citando el tipo entre comillas dobles:
          byte_status: {
            type: '"file_byte_status"',
            allowNull: false,
            defaultValue: 'pending',
          },
      // ... y el down:
      await queryInterface.sequelize.query(
        'DROP TYPE IF EXISTS "file_byte_status";',
        { transaction }
      );
```

**Precedente 2 — un solo `ALTER` con varios `ADD COLUMN` por SQL crudo**
(`20260820_01_drop_external_integration.js`:128-135):

```js
        ALTER TABLE objectives
          ADD COLUMN external_project_id integer REFERENCES external_project(id) ON UPDATE CASCADE ON DELETE SET NULL,
          ADD COLUMN external_issue_id varchar(255),
          ADD COLUMN external_issue_key varchar(100),
          ADD COLUMN external_url text,
          ADD COLUMN external_raw_data jsonb,
          ADD COLUMN last_synced_at timestamp with time zone;
```

> **Por qué SQL crudo y no `queryInterface.addColumn` dos veces.** CA-3 exige **un solo `ALTER` con
> dos `ADD COLUMN`**, y `addColumn` emite **un `ALTER` por llamada**: no puede expresarlo. El
> precedente de arriba es la forma que la casa ya usa para eso. `addColumn` sigue siendo correcto

#### Credenciales de la migración

## Tasks

### Task 1: La migración `20260824_01_users_roles_identity_type.js`

**Status:** Completed

#### Description

Crear la única migración de la story: el ENUM nativo `identity_type` y las dos columnas de `users`,
con sus defaults, dentro de una transacción y con un `down` reversible.

Es **la mitad de producción** del par modelo/migración que esta story existe para escribir y revisar
en un solo diff. El modelo ya está (plan de `models`); esto es lo que hace que la base de producción
lo respalde. **Sin esta migración, desplegar `@jiku/models` rompe toda lectura de `users`** con
`column users.identity_type does not exist`, porque Sequelize incluye las columnas nuevas en el
`SELECT` de cualquier `include` sin `attributes`.

Cubre TS-1 a TS-8.

**Es puramente aditiva y no cambia ningún comportamiento.** Al terminar, las dos columnas existen,
**todas** las filas dicen `identity_type = 'person'` y `roles = '[]'`, y **nada las escribe**.

#### Acceptance Criteria

1. El archivo se llama exactamente
   `api/db-upgrade/migrations/20260824_01_users_roles_identity_type.js`, en formato `.js` con
   `'use strict';` al principio.
2. **TS-1:** el `up` ejecuta `CREATE TYPE identity_type AS ENUM ('person', 'service');`, **sin
   `IF NOT EXISTS`**, y los dos valores quedan en ese orden.
3. **TS-2, TS-3:** el `up` ejecuta **un solo `ALTER TABLE` con dos `ADD COLUMN`** (no dos
   sentencias `ALTER`), que crea `roles JSONB NOT NULL DEFAULT '[]'::jsonb` e
   `identity_type "identity_type" NOT NULL DEFAULT 'person'`.
4. Las dos sentencias del `up` corren dentro de
   `queryInterface.sequelize.transaction(async (transaction) => {...})`, con `{ transaction }` en
   cada `query`.
5. **TS-4:** **no hay ningún `UPDATE`** en el archivo. El backfill lo dan los defaults.
6. **TS-5:** **no hay ningún `ALTER COLUMN ... DROP DEFAULT`**. Los defaults se conservan.
7. **TS-7:** el `down` hace `DROP COLUMN` de las dos columnas **y después** `DROP TYPE`, en ese
   orden, también dentro de una transacción.
8. **TS-8:** una re-corrida del `up` falla y la transacción deja el esquema **exactamente** como
   estaba.
9. El archivo abre con un **comentario de bloque en español** que explica: que es aditiva y sin
   cambio de comportamiento; por qué un solo `ALTER`; por qué no hay `UPDATE` y por qué `'person'` /
   `'[]'` son correctos para toda fila; por qué los defaults se conservan; por qué el ENUM es nativo

```js
 * Agrega `users.roles` y `users.identity_type`: las dos columnas donde S-016 va a espejar la
 * identidad que el auth-callout autentica en el bus.

 * PURAMENTE ADITIVA Y SIN CAMBIO DE COMPORTAMIENTO. Al terminar, las dos columnas existen,
 * TODAS las filas dicen `identity_type = 'person'` y `roles = '[]'`, y NADA las escribe: el
 * consumidor del evento es S-016 y la compuerta de autorizacion es S-017.
 *
 * UN SOLO ALTER CON DOS ADD COLUMN, no dos sentencias: es un solo pase sobre el catalogo, y con
 * defaults no volatiles PostgreSQL >= 11 no reescribe la tabla. Por eso no hace falta ventana de
 * mantenimiento. `queryInterface.addColumn` emite un ALTER por llamada, asi que no puede
 * expresarlo; el precedente de SQL crudo es 20260820_01.
 *
 * SIN BACKFILL EXPLICITO: los DEFAULT ya dejan toda fila preexistente en 'person' / '[]'.
 * 'person' es correcto para todas porque hoy `users` se puebla a mano con las personas del
 * equipo y ningun service user tiene fila. '[]' es la opcion conservadora: no inventa
 * autorizacion que nadie concedio. La fila se corrige en la proxima autenticacion de esa
 * identidad al bus, una vez que S-016 exista.
 *
 * LOS DEFAULT SE CONSERVAN (no hay ALTER COLUMN ... DROP DEFAULT). Son la garantia de que un
 * INSERT que no las mencione -los 127 puntos de siembra de los tests, el que produce sync()- no
 * falle.
 *
 * EL ENUM ES NATIVO (`identity_type`) pero el modelo declara DataType.STRING. La divergencia es
 * deliberada: declararlo ENUM en el modelo haria que sync() cree el tipo con la convencion de
 * nombre de Sequelize (`enum_users_identity_type`), distinto de este, y las dos fuentes del
 * esquema divergirian sin que ningun test lo vea. Es el precedente de byte_status /
 * retention_status.
 *

 * el producto, son el `type` de deploy/nats/auth-callout/rules.yaml.
 *
 * SIN `IF NOT EXISTS` en el CREATE TYPE: una re-corrida indica un problema de estado de
 * migraciones que conviene ver, no absorber. La transaccion garantiza que no quede a medias.
 *
 * SIN INDICES: los dos accesos a estas columnas son por PK (findByPk en S-016 y S-017) y el
 * filtro de opus se aplica sobre un include ya acotado por user_project_permissions.
 *
 * REVERSIBLE: el `down` dropea las dos columnas y DESPUES el tipo, en ese orden. Invertirlo hace
 * fallar el DROP TYPE con `cannot drop type identity_type because other objects depend on it`,
 * un error que no nombra la columna que lo retiene.
 */
module.exports = {
  up: (queryInterface) => {
    return queryInterface.sequelize.transaction(async (transaction) => {
      await queryInterface.sequelize.query(
        "CREATE TYPE identity_type AS ENUM ('person', 'service');",
        { transaction }
      );

      await queryInterface.sequelize.query(
        `
        ALTER TABLE users
          ADD COLUMN roles         JSONB           NOT NULL DEFAULT '[]'::jsonb,
          ADD COLUMN identity_type "identity_type" NOT NULL DEFAULT 'person';
        `,
        { transaction }
      );
    });
  },

  down: (queryInterface) => {
    return queryInterface.sequelize.transaction(async (transaction) => {
      // El orden importa: el tipo no se puede borrar mientras una columna lo use.
      await queryInterface.sequelize.query(
        'ALTER TABLE users DROP COLUMN identity_type, DROP COLUMN roles;',
        { transaction }
      );

      await queryInterface.sequelize.query(
        'DROP TYPE IF EXISTS "identity_type";',
        { transaction }
      );
    });
  },
};
```

- **`"identity_type"` entre comillas dobles en el `ADD COLUMN`.** Es la forma que usa
  `20260819_01` (`type: '"file_byte_status"'`) y evita cualquier ambigüedad entre el nombre del
  tipo y el de la columna, que en este caso **son el mismo string**. Postgres lo permite; las
  comillas lo dejan explícito para quien lee.
- **`DROP TYPE IF EXISTS` en el `down`, pero `CREATE TYPE` sin `IF NOT EXISTS` en el `up`.** No es
  una inconsistencia: es el patrón de la casa (`20260819_01`). El `up` quiere fallar ruidosamente
  ante un estado inesperado; el `down` quiere ser idempotente para poder desenredar un rollback a
  medias.
- **No uses `queryInterface.addColumn`** para este caso: emitiría dos `ALTER`, y CA-3 pide uno.
- **No agregues `NODE_ENV` ni ninguna rama por entorno.** La migración es la misma en todos.

### 1. CA-12 y CA-13 se contradicen en un punto exacto, y la story no lo ve

`tests/routes/projects-id-get.test.ts`:101-106 afirma `creator: { id, name, username, email }`.
Acotar ese `include` a `['id','name','email']` —que es literalmente lo que CA-12 ordena— hace
desaparecer `username` de la respuesta y **rompe esa aserción**. CA-13 dice que *"ningún test
existente cambia una aserción"*.

**No es un error de la story: es un caso que su autor no verificó.** Los otros dos sitios usan
`creator: {name: 'User 01'}` con `containDeep`, que es permisivo; este es el único que enumera los
cuatro campos.

**Resuelto en la Tarea 3 (AC 9):** gana CA-12, se quita `username` de la aserción, y queda
registrado en el changelog como la **única** excepción a CA-13 de todo el plan, con su razón.
Rechazado explícitamente: poner `['id','name','username','email']` solo en esa ruta, que evitaría el
cambio de aserción a cambio de una cuarta variante de la lista de `attributes` en el servicio.

**Evidencia de que es seguro:** ningún componente de `web` ni de `opus-web` lee `username` de un
usuario embebido — solo `name` e `id` (`ProjectGeneralInfo.tsx`:36, `ProjectDetails.tsx`:74,
`ObjectiveDetails.tsx`:98, `RequirementDetail.tsx`:354, `ObjectiveHistoryList.tsx`:41 y :79-80,
`useCanEditObjective.ts`:14).

### 4. El spec sobredeclara `creator`, y esta story lo empeora sin poder arreglarlo

`docs/apis/api.yaml` declara `creator: { $ref: '#/components/schemas/User' }` en dos lugares
(líneas 292 y 2700) y `User` tiene cuatro propiedades, `username` incluida. Después de la Tarea 3,
esas respuestas devuelven **tres**.

**La deriva es preexistente, no la introduce esta story:** `requirements-id-get.ts`:14 y
`opus-projects-projid-requirements-get.ts`:49-53 ya devolvían tres campos contra el mismo `$ref`.
Esta story suma tres endpoints más al mismo desfasaje.

**El arreglo correcto es un `UserSummary`** (`id`, `name`, `email`) en `components/schemas`, y que
los `$ref` de `creator`, `uploader`, `user` y `changedByUser` apunten ahí, dejando `User` para donde
efectivamente se devuelve el usuario completo. **No se hace en este plan**: es un cambio de
definición técnica y va por `/product-change-technical-definition`. La Tarea 4 lo prohíbe
explícitamente para que no se cuele.

**Y el mismo desfasaje existe del lado de `web`:**
`web/src/features/auth/types/auth.types.ts`:14-19 declara `username: string` **requerido** en el

material para una story de `web`: un `UserSummary`/`Creator` propio, o `username?: string`. El
patrón correcto ya existe en el mismo repo: `RequirementCreator`
(`requirement.types.ts`:56-60) declara exactamente `id`, `name`, `email`.
