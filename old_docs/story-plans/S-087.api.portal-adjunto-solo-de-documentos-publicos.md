# Story Plan: S-087 (api) - El adjunto del portal solo de documentos públicos

## Status

**Status:** Completed

**Progress:** 4/4 tareas completadas

## Story Reference

- **Story:** [S-087](../stories/S-087.portal-adjunto-solo-de-documentos-publicos.md)
- **Service:** `api`
- **Origen:** [REQ-017](../requests/REQ-017.roles-de-usuarios-para-conectores-y-cierre-de-brechas-de-docs.md)
- **Summary:** Cierra la brecha F-13. La ruta del adjunto del portal deja de ser
  `GET /api/opus/docs/attachments/{id}` (que entregaba el adjunto de un documento `internal` a un
  usuario interno que conociera el id) y pasa a `GET /api/opus/docs/documents/{documentId}/attachments/{id}`:
  antes de pedir la descarga, la api lee el documento con `documents.get`, exige `visibility: 'public'`
  y que el adjunto pertenezca a ese documento. Se suman tests con usuario interno en las tres rutas
  `/opus/docs/*`.

> **Precondición verificada sobre el árbol (2026-10-24):** existen `lib/routes/opus-docs-attachments-id-get.ts`,
> `opus-docs-documents-get.ts`, `opus-docs-documents-id-get.ts`, sus tests en `tests/routes/`, el barrel
> `lib/routes/index.ts` (líneas 72-74), `lib/modules/docs/ids.ts`, `lib/modules/docs/download.ts`,
> `lib/modules/client.ts` y `tests/helpers/docs-module.ts`. Sin dependencias de otras stories (la story
> declara *Prerequisitos: Ninguno*; S-086 es independiente).

### Convenciones activas que aplican (extracto)

**`http-server`** (custom):
- Agregar un endpoint son **dos pasos**: crear el archivo y exportarlo en `lib/routes/index.ts`. `app.ts`
  no se toca. Quitar uno es lo inverso: borrar el archivo y su línea del barrel.
- El path en el archivo va **sin** `/api`. Método y path **en la misma línea** del `router.get(`.
- Orden de la cadena: **0. Módulo** (`requireModule('docs')`, antes del rol) → 1. Rol (`hasAnyRole`) →
  2. Forma del input → 3. Existencia de la entidad → 4. Permiso → 5. Visibilidad en la superficie →
  6. Negocio → 7. Handler.
- Estilo de declaración: el **directo** (`router.get('/path', mw1, mw2, handler)`).
- Todo endpoint nuevo lleva su archivo de test en `tests/routes/{mismo-nombre}.test.ts`.
- Con la ruta vieja borrada, una petición a `/api/opus/docs/attachments/{id}` cae en el fallback de
  `app.ts:78-81` (`next({ status: 404, ... })`), que termina en el **404 por defecto de Express** (cuerpo
  HTML). La story lo acepta así: *"la petición vieja responde el 404 genérico de Express"*.

**`bus-modules`** (custom), reglas verbatim:
- Una ruta que habla con un módulo declara `requireModule('<módulo>')` **antes** de `hasAnyRole`.
- Usá `moduleQuery` / `moduleCommand` / `runModuleCommand`. Después de la llamada, `if (!data) return;`
  (o `if (!ok) return;`): la respuesta ya salió.
- **Nunca** armes el `actor` a mano ni lo tomes del cuerpo: lo inyecta el embudo, solo con `id`.
- **Nunca** loguees `payload`, `options`, el token de un link ni el contenido de un documento.
- El cuerpo de error de módulo conserva `code` y `details` tal cual vienen. No traduzcas el `code`.
- Un id de path con forma inválida es 404 `*_not_found` **sin llamar al bus**.
- El estado del módulo se lee de memoria. No consultes el KV ni hagas ping en el request.
- Una ruta puede encadenar varias llamadas (precedente: `GET /api/docs/documents/:id` compone
  `documents.get` + `folders.get`).

**`testing`** (custom), reglas verbatim que aplican:
- Un archivo de ruta nuevo lleva `tests/routes/{mismo-nombre}.test.ts`.
- Todo endpoint con `hasAnyRole` lleva un test por rol rechazado.
- Toda ruta de un módulo opcional usa `itRespectsModuleState` y verifica que el `actor` publicado sea
  `{ id }` y nada más.
- No llames a `setBus`: el doble ya está instalado y se resetea por root hook (y `docsModule.stop()` también).
- Aserciones con `should`. No mezcles `assert` ni `expect`.
- Un test no depende del orden de ejecución ni del estado que dejó otro.

**`error-handling` / `logging`:** el `catch` del handler loguea `logger.error(\`GET /api/opus/docs/... error: ${error.message}\`)`
y responde `500 { code: 'internal_error', message: 'Internal error' }` (patrón de las tres rutas del
portal). La `downloadUrl` **nunca** se loguea.

**`_base`:** comentarios en español, imports relativos, `kebab-case` en archivos.

### Relevant ADRs

**ADR-015: Módulos opcionales del bus** — Implementation Rules (verbatim, las que aplican):
- Toda llamada a un módulo **DEBE** pasar por `api/lib/modules/client.ts`
  (`moduleQuery`/`moduleCommand`/`runModuleCommand`, o `sendToModule` en las rutas que responden
  HTML). **NO SE DEBE** hablar con un módulo desde un handler con `bus()` directo.
- **NO SE DEBE** usar `sendCommand` ni `withActor` con un módulo: su sobre (`roles`, `name`…) es
  `invalid_fields` para jiku-docs.
- El `actor` **DEBE** ser solo `{ id }` y **DEBE** inyectarlo el embudo, después del spread del
  payload. Sin identidad verificada el embudo **DEBE** fallar cerrado (401 sin publicar). **NO SE
  DEBE** llamar a un módulo sin `actor` salvo en una ruta pública deliberada
  (`shares.resolve`/`shares.attachment`).
- Toda ruta de módulo **DEBE** llevar `requireModule('<módulo>')` **antes** de `hasAnyRole`.
- El mapa de errores **DEBE** ser **por módulo** (`docs/errors.ts`); **NO SE DEBE** mezclar con
  `STATUS_BY_ERROR_CODE` de core. El cuerpo **DEBE** ser `{ code, message, details? }` con `code`
  sin traducir y `details` verbatim.
- La api **NO DEBE** autorizar el dominio de un módulo (ACL, visibilidad): solo autentica, rutea
  por superficie y traduce errores.
- **NO DEBE** loguearse la `downloadUrl` ni el `htmlUrl`.

> **Nota sobre "la api NO DEBE autorizar ... visibilidad":** el recorte por `visibility: 'public'` del
> portal es una regla de **superficie** (DD-3 de REQ-016, ya aplicada en `GET /opus/docs/documents/{id}`),
> no de dominio: no mira ACL ni rol. Esta ruta aplica la misma regla. No es una desviación nueva.

**F-13 (ADR-015, texto actual que este plan cierra):** *"Ruta 23 del portal sin recorte para internos.
`GET /opus/docs/attachments/{id}` no puede aplicar DD-3, porque el reply de `request-download` no trae la
visibilidad. Para `external-user` lo cubre jiku-docs; un usuario interno que use el portal recibe el
adjunto de un documento `internal` si conoce el id."* (La edición del ADR es del plan `S-087.docs`.)

**ADR-006: Dos frontends, una api** — reglas verbatim que aplican:
- Todo endpoint de cara al cliente **DEBE** vivir bajo `/api/opus/*`. **NO SE DEBE** exponer un
  endpoint interno al portal agregándole un filtro por rol.
- Todo endpoint bajo `/api/opus/*` **DEBE** verificar el permiso de proyecto con
  `validateProjectPermissions` o equivalente. El rol solo no alcanza.
- Aplicación: la ruta nueva **mantiene la excepción anotada DD-4** de la que reemplaza: no hay
  `validateProjectPermissions` porque el proyecto no se conoce antes de pedir el documento; el
  equivalente es la regla de externos de jiku-docs (`public` + proyecto en sus `project-permissions` +
  carpeta sin `externalBlocked`) más el recorte de visibilidad de la api. El JSDoc de la ruta lo dice.

**ADR-002** — corolario ya vigente: el `{id}` de `attachments.{id}.request-download` **entra al subject
NATS**, por eso se valida con `isUlid` **antes** del bus. Lo mismo vale para `documentId` (viaja en el
payload, pero se valida por consistencia y para no gastar un round-trip).

### API Context

**Ruta que se ELIMINA** (`docs/apis/api.yaml`, bloque actual):

```yaml
  /opus/docs/attachments/{id}:
    get:
      tags: [opus]
      summary: Descarga un adjunto (portal)
      x-jiku-module: docs
      x-roles: [external-user, admin, user]
      description: |
        Igual que `GET /docs/attachments/{id}`: `attachments.{id}.request-download` y **302** a la `downloadUrl`.
        **Limitación conocida:** el reply no trae la visibilidad del documento, así que para un usuario interno
        que use el portal la api no puede recortar el adjunto de un documento `internal`; el recorte es el de
        jiku-docs para `person-external`.
      parameters:
        - { name: id, in: path, required: true, description: "Id del adjunto (ULID)", schema: { type: string, pattern: '^[0-9A-HJKMNP-TV-Z]{26}$' } }
      responses:
        '302':
          description: |
            Redirección a la `downloadUrl` de jiku-docs, sin cuerpo y sin `Content-Type` ni
            `Content-Disposition` (el reply de jiku-docs no trae metadatos de archivo). La URL
            nunca se loguea. `HEAD` responde igual.
          headers:
            Location:
              schema: { type: string }
              description: '`downloadUrl` prefirmada'
            X-Content-Type-Options:
              schema: { type: string, enum: [nosniff] }
        '401': { $ref: '#/components/responses/Unauthorized' }
        '403': { $ref: '#/components/responses/ModuleForbidden' }
        '404': { $ref: '#/components/responses/ModuleNotFound' }
        '500': { $ref: '#/components/responses/InternalError' }
        '503': { $ref: '#/components/responses/ModuleUnavailable' }
        '504': { $ref: '#/components/responses/ModuleGatewayTimeout' }
```

La ruta **no está en ningún tag publicado** (`v1.6.0` es el último): reemplazarla no rompe un contrato
publicado (story).

**Ruta NUEVA** (diseño de la story, verbatim):

**`GET /opus/docs/documents/{documentId}/attachments/{id}`**
- **Servicio:** api (`api/lib/routes/opus-docs-documents-id-attachments-id-get.ts`)
- **Cadena:** `requireModule('docs')` -> `hasAnyRole(['external-user', 'admin', 'user'])` -> handler
- **Descripción:**
  1. `documentId` o `id` sin forma ULID -> 404 (`document_not_found` / `attachment_not_found`) sin bus.
  2. `documents.get { id: documentId, include: ['attachments'] }` como `actor`. Error del módulo -> el mapa de siempre (`docsHttpStatusFor`).
  3. `visibility !== 'public'` (o ausente) -> 404 `document_not_found`, para todo rol.
  4. `attachments` sin un elemento con `id === id` -> 404 `attachment_not_found`.
  5. `attachments.{id}.request-download` -> `redirectToModuleDownload` (302, `Location`, `X-Content-Type-Options: nosniff`; la URL nunca se loguea).
- **Request:** sin cuerpo. Path: `documentId` (ULID), `id` (ULID).
- **Response:** `302`; `401, 403, 404, 500, 503, 504` con las mismas `$ref` (`Unauthorized`, `ModuleForbidden`, `ModuleNotFound`, `InternalError`, `ModuleUnavailable`, `ModuleGatewayTimeout`).
- **Errores:** nunca 403 por visibilidad: el portal no revela que existe un documento interno.

**Rutas sin cambio de comportamiento (solo tests nuevos):**
- `GET /opus/docs/documents` — llama a `documents.list` con `filter: { projectId | requirementId, visibility: 'public' }`; **`visibility: public` lo fuerza la api** y la query no lo acepta (400). Test nuevo: con token `admin`, el payload lleva `visibility: 'public'`.
- `GET /opus/docs/documents/{id}` — `documents.get` con `include: ['content', 'attachments']`; si `visibility` no es `public` (o falta), 404 `document_not_found`. Test nuevo: documento `internal` con token `admin` -> 404.

        uploadedBy: { type: string }

    DocsDocument:   # (extracto)

### Flow Context

**`docs/flows/documentos-desde-la-web.md` — Paso 9: lectura desde el portal (opus-web)** (estado actual, verbatim de la tabla):

| Operación | Endpoint | Detalle |
|---|---|---|
| Listar | `GET /api/opus/docs/documents` | Query `projectId` **o** `requirementId` (uno solo); `limit`, `cursor`. Cadena: `requireModule` → `hasAnyRole(['external-user','admin','user'])` → forma → `loadDocsScope` → `validateProjectPermissions` → `validateRequirementIsPublic` (solo si filtra por requisito) → handler. **`filter.visibility: 'public'` lo fuerza el handler**; la query no puede pisarlo |
| Detalle | `GET /api/opus/docs/documents/{id}` | `documents.get { id, include: ['content','attachments'] }`; **404 `document_not_found` si `visibility !== 'public'`** (falla cerrado) |
| Adjunto | `GET /api/opus/docs/attachments/{id}` | 302 a la URL prefirmada |

**Lo que cambia (story, "Flujo de Interacción"):** la fila **Adjunto** pasa a
`GET /api/opus/docs/documents/{documentId}/attachments/{id}`:

1. **[opus-web — visor]** `docsUrlTransform(doc.id)` reescribe el enlace → `/api/docs/documents/{docId}/attachments/{attId}`.
2. **[opus-web — route handler]** valida sesión y los dos ULID → `GET {API_URL}/api/opus/docs/documents/{docId}/attachments/{attId}` con `Authorization: Bearer <token>` y `redirect: 'manual'`.
3. **[api — este plan]** `requireModule('docs')` → `hasAnyRole` → `documents.get { id: docId, include: ['attachments'] }` → `visibility !== 'public'` → 404 `document_not_found`; `attId` ausente en `attachments[].id` → 404 `attachment_not_found`; OK → `request-download` → 302 `Location`.
4. **[opus-web — route handler]** propaga el 302; el navegador baja del storage.

**Manejo de errores:** módulo no instalado → 404 `module_not_installed`; no disponible → 503; timeout → 504.
`external-user` sin acceso en jiku-docs → `document_not_found` / `permission_denied` traducido por el mapa (sin cambio).

(La edición del documento de flujo es del plan `S-087.docs`.)

### UX (la story declara `affects_ui: true`, pero no por este servicio)

La UI afectada es `opus-web` (pantalla 6 "documento", `docs/ux/surfaces/opus-web/screens/documento.md`
v1.1): **sin cambio de layout**, solo la URL del proxy. La revisión de Design System de REQ-017 dice
*"Sin gaps: el delta no introduce tipos de bloque nuevos"* — ningún `pendiente-DS`, nada que bloquee.
Lo que importa para la api, de esa pantalla (verbatim de la anotación de `contenido-documento`):
*"Un enlace o imagen que apunta al adjunto de **otro** documento se renderiza igual, pero no abre: el
proxy responde 404 (enlace que no descarga, imagen rota) [REQ-017 R-3]."* — es CA-5 en el lado de la api
(404 `attachment_not_found`). No hay wireframes, DS ni UI Preview en este plan: `api` es `type: api`.

```ts
async function downloadPortalAttachment(req: Request, res: Response) {
  const documentId = String(req.params.documentId);
  const id = String(req.params.id);
  // Los dos ids se validan antes del bus; el del adjunto entra al subject de NATS (ADR-002).
  if (!isUlid(documentId)) return respondDocsNotFound(res, 'document_not_found');
  if (!isUlid(id)) return respondDocsNotFound(res, 'attachment_not_found');

  try {
    const document = await moduleQuery(res, 'docs', 'documents.get', { id: documentId, include: ['attachments'] });
    if (!document) return;

    // DD-3 de REQ-016 aplicado al adjunto (cierra F-13): para todo rol, y sin revelar que existe.
    if (document.visibility !== 'public') return respondDocsNotFound(res, 'document_not_found');

    const belongs = Array.isArray(document.attachments) && document.attachments.some((a: any) => a?.id === id);
    if (!belongs) return respondDocsNotFound(res, 'attachment_not_found');

    const ticket = await moduleCommand<ModuleDownloadTicket>(res, 'docs', `attachments.${id}.request-download`, {});
    if (!ticket) return;
    return redirectToModuleDownload(res, ticket);
  } catch (error: any) {
    logger.error(`GET /api/opus/docs/documents/:documentId/attachments/:id downloadPortalAttachment error: ${error.message}`);
    return res.status(500).json({ code: 'internal_error', message: 'Internal error' });
  }
}
```

- **El test de contrato acopla api y docs.** `tests/utils/api-contract.test.ts` nombra la ruta del portal
  por su path en `api.yaml`; por eso la Tarea 3 edita el bloque del yaml desde este plan (precedente
  `S-078.api`). El plan `S-087.docs` queda con la prosa y la verificación.
- **El 404 de la ruta vieja es el de Express** (HTML), no `{ code, message }`: es lo que la story acepta.
  TS-17 asserta solo status y que no se llamó al módulo.
- **La 403 de jiku-docs se respeta**: un `permission_denied` en `documents.get` sale como 403 por el mapa
  (TS-11). La regla "nunca 403 por visibilidad" se refiere al recorte de la api, no a los errores del módulo
  (story: *"traducido por el mapa (sin cambio)"*).
- **Costo:** un round-trip extra a jiku-docs (`documents.get`) por descarga; aceptado en la story.
