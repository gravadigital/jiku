# Story Plan: S-076 (core) - core reconoce `docs` como rol de servicio

## Status

**Status:** Completed

---

## Story Reference

- **Story:** [S-076](../stories/S-076.core-reconoce-docs-como-rol-de-servicio.md)
- **Service:** `core`
- **Summary:** El machine user de jiku-docs llega a core con `matched_role: "docs"` y sin `email`.
  Hoy `docs` no está en `SERVICE_ROLES`, así que el evento de autenticación se **descarta**
  (`"email" is required`), no se crea la fila en `users` y core le responde `caller_not_authorized`
  / `unknown_caller` a todo (hallazgo H-1 de REQ-016). El cambio de código es **una línea**: `docs`
  entra a `SERVICE_ROLES`. El resto de la story son **tests** que fijan los tres criterios: el alta
  de la identidad (CA-14b), la clase conector para `[internal-app, docs]` (CA-14) y la descarga de
  un archivo sin vínculo subido por ese servicio (CA-15).

**Lo que esta story NO hace (y no hay que "completar"):**

- **No** agrega `docs` a `ROLE_METHODS` ni a `CLASS_BY_ROLE`. Para la autorización y la clase de
  caller, `docs` es un rol **desconocido que se saltea**; `internal-app` es el que autoriza
  (REQ-016 D-1). Los gates `TS-20` ("el mapa declara EXACTAMENTE 6 roles") y
  `(gate) el mapa es CERRADO: exactamente los cuatro roles que consultan` **no cambian** y tienen
  que seguir verdes.
- **No** toca `docs/flows/*.md` (se documenta en S-085), ni `rules.yaml` (S-075, ya hecho), ni la
  base (sin migración: `users.roles` es JSONB sin CHECK).
- **No** cambia ningún comando ni consulta.

**Estrategia de manejo de errores:** los despachadores **nunca lanzan**. El de eventos, ante un
payload inválido, loguea `warn` `[events] descartado: <mensaje de Joi>` y retorna sin abrir
transacción. Los de comandos/consultas devuelven un `Reply` de falla con `errorCode`
(`caller_not_authorized`, `unknown_caller`, `file_not_found`, `invalid_fields`, ...).

**Logging:** Winston; nunca el payload (trae `email`, `client_ip`, sesión). El handler de auth
loguea `info` `[events] {id}: created|updated`.

**Testing:** contra base real, entrando por el despachador (`dispatch()`, `dispatchQuery()`,
`new EventDispatcher(syncUser).dispatch(...)`). Fixtures propios en el `before` de cada archivo.
Limpieza: cada archivo borra **solo sus ids** (el `TRUNCATE` es al arrancar la corrida).

### Relevant ADRs

#### ADR-007 — Identidad: Zitadel + auth-callout

- **Decisión:** las identidades del bus vienen de Zitadel vía el auth-callout; `users` es un espejo
  del proveedor que core mantiene a partir del evento de autenticación.
- **Implementation Rules (verbatim):**
  - Todo servicio que se conecte al bus **DEBE** autenticarse con el token de un service user
    obtenido vía `@jiku/zitadel-auth`, con auto-refresh. **NO SE DEBE** usar un token de larga
    duración por variable de entorno.
  - El `userId` para publicar **DEBE** derivarse de la key del service user, **NO** de una variable
    de entorno.
  - El cliente NATS **DEBE** fijar `inboxPrefix` con el hash de `@jiku/nats-protocol`.
  - La api **DEBE** validar los tokens de usuario contra el JWKS de Zitadel, con resincronización
    ante `kid` desconocido (`KEY_SYNC_ATTEMPS` reintentos).
  - Los roles **DEBEN** leerse del claim `urn:zitadel:iam:org:project:{PROJECT_ID}:roles`.
    **NO SE DEBEN** almacenar roles en la base ni derivarlos de otra fuente.
  - `AUTH_BYPASS=true` **DEBE** seguir siendo opt-in explícito, **prohibido con
    `NODE_ENV=production`** (el arranque debe fallar) y exigir `DEV_USER_ID`. **NO SE DEBE**
    activar por ausencia de otra variable.
  - El producto **NO DEBE** escribir la tabla `users` para modificar identidad: es espejo del
    proveedor. (El alta de la fila local es otro asunto — ver FG-1.)
  - Un cambio en `rules.yaml` del auth-callout **DEBE** tratarse como cambio de seguridad: es lo que
    define quién puede escribir en el producto.

#### ADR-008 — Autorización deny-by-default

- **Decisión:** lo no declarado no se autoriza. En core: `ROLE_METHODS` y `CLASS_BY_ROLE` son
  mapas **cerrados**; un rol ausente no autoriza nada ni produce clase.
- **Aplicación en esta story:** `docs` **no** entra a ninguno de los dos mapas. Un usuario con
  `roles: ['docs']` solo (sin `internal-app`) sigue sin autorizar nada y sin clase — hay un test
  que lo fija (TS-9 de este plan).

#### ADR-013 — Tests contra base real

- **Implementation Rules (verbatim):**
  - Los tests de `api` y `core` **DEBEN** correr contra PostgreSQL real. **NO SE DEBEN** mockear los
    modelos de Sequelize.
  - Los tests de comandos de `core` **DEBEN** entrar por el despachador (`dispatch()`), **NO** por
    `execute()` directamente.
  - Un test de escritura de la api **DEBE** verificar las tres capas: comando publicado, traducción de
    la respuesta a HTTP, y que la fila quedó escrita. **NO SE DEBE** asertar solo el status HTTP.
  - `reply()` / `failWith()` **DEBEN** usarse solo para cubrir caminos de error. El camino feliz
    **DEBE** ejecutar core de verdad.
  - Cada archivo de test **DEBE** poder correr solo: el esquema y el mock de auth se preparan en
    fixtures globales de Mocha.
  - `TZ=UTC` **DEBE** estar fijado en la configuración de test de todo servicio.
  - La limpieza entre corridas **DEBE** ser `TRUNCATE ... RESTART IDENTITY CASCADE`, para que los ids
    autoincrementales sean predecibles.
  - **NO SE DEBE** depender del orden de ejecución entre archivos de test.

### API Context

No hay cambios de contrato. Lo relevante, tal como está hoy:

#### `SERVICE_ROLES` y la derivación (`core/src/events/auth/identity-type.ts`)

```ts
export const SERVICE_ROLES = ['internal-app', 'core'] as const;   // línea 36 — pasa a tres
const SERVICE_ROLE_SET: ReadonlySet<string> = new Set(SERVICE_ROLES);

export function identityTypeFromMatchedRole(matchedRole: string | undefined): IdentityType {
  if (!matchedRole) {
    return IdentityType.Person;
  }
  return SERVICE_ROLE_SET.has(matchedRole) ? IdentityType.Service : IdentityType.Person;
}
```

Comparación **exacta** (sin `trim`, sin `toLowerCase`): `Docs` no es `docs`.

#### El esquema del evento (`core/src/events/dispatcher.ts`) — se consume, no se toca

```ts
email: joi.string().when('matched_role', {
  is: joi.string().valid(...SERVICE_ROLES).required(),
  then: joi.string().allow(null).empty('').default(null),
  otherwise: joi.string().required(),
}),
roles: joi.array().items(joi.string()).default([]),
```

Al sumar `docs` a `SERVICE_ROLES`, **la misma constante** vuelve opcional el `email` y clasifica la
identidad como `service`: las dos decisiones no pueden discrepar.

#### Clase del caller (`core/src/caller-class.ts`) — se consume, no se toca

```ts
const PRECEDENCE: readonly CallerClass[] = ['external', 'internal', 'connector'];
export const CLASS_BY_ROLE = {
  'external-user': 'external', user: 'internal', admin: 'internal', 'internal-app': 'connector',
};
export function resolveCallerClass(roles: readonly string[]): CallerClass | null {
  const classes = new Set(roles.map((role) => CLASS_BY_ROLE[role]).filter(Boolean));
  return PRECEDENCE.find((candidate) => classes.has(candidate)) ?? null;
}
```

`resolveCallerClass(['internal-app', 'docs'])` → `'connector'` (la clase que **no recorta filas**).

#### `files.request-upload` / `files.{fileId}.request-download` — se consumen, no se tocan

- Subida, payload: `{ uploader?, fileName, mimeType, fileSize, checksum? }` → `{ id, uploadUrl, expiresIn }`.
  Crea la fila en `files` con `byteStatus: 'pending'`, `retentionStatus: 'active'`.
  `uploader` se resuelve con `resolveActor`: si el caller **no** es `CORE_TRUSTED_PUBLISHER_ID`,
  el uploader es **el caller del subject** (y se loguea un `warn` de rama externa).
- Descarga, payload: `{ disposition?: 'inline' | 'attachment' }` (default `inline`) →
  `{ downloadUrl, expiresIn, fileName, mimeType, fileSize }`. Solo firma si
  `retentionStatus === 'active'`; si no, `file_not_found`. **No exige vínculo ni titularidad**
  (TS-36 y TS-41 existentes). `byteStatus: 'pending'` firma igual.

### Flow Context

#### `sincronizacion-de-identidades` — Paso 3 (nota vigente, verbatim)

> **`identity_type` YA NO VIAJA EN EL PAYLOAD (v2, S-069).** [...] su valor se **deriva de
> `matched_role`** —el rol que efectivamente ganó la regla, leído del token— en
> `core/src/events/auth/identity-type.ts`: `internal-app` y `core` dan `service`, todo lo demás (y
> la ausencia del campo) da `person`.
>
> **Si se agrega un rol de servicio a `rules.yaml`, hay que agregarlo también a `SERVICE_ROLES`.**
> Si no, esa identidad se espeja como `person` y nada falla; hay un test que cuenta la lista.

`rules.yaml` (S-075) ya tiene la regla `docs` **por encima** de `internal-app`:

```yaml
rules:
  - match: docs
    template: templates/docs.yaml
  - match: internal-app
    template: templates/connector.yaml
  - match: core
    template: templates/core.yaml
  - match: admin
    template: templates/person-internal.yaml
  - match: user
    template: templates/person-internal.yaml
  - match: external-user
    template: templates/person-external.yaml
```

Son **seis** reglas; los roles de servicio pasan a ser **tres**: `docs`, `internal-app`, `core`.

|---|---|---|
| `type` | `=== 'authenticated'` | descarta + `warn` |

#### `sincronizacion-de-identidades` — Paso 6

`User.findByPk(id)` → no existe: `User.create({ id, name, username, email, roles, identityType })`;
existe: `update` de los cinco campos (reemplazo total). Log `[events] {id}: created|updated`.

**Lo que esta story cambia del flujo:** en el Paso 3/5, `docs` pasa a ser rol de servicio. La
documentación del flujo se actualiza en S-085, **no acá**.

#### `lectura-de-archivos` — Camino E

Archivo sin vínculo, por `fileId`: `files.{fileId}.request-download` firma un archivo `active` aunque
no tenga fila en `attachments` y aunque el byte esté `pending`. Con jiku-docs deja de ser hipotético
(documentación en S-085).

#### Secuencia de la primera conexión del machine user de jiku-docs (de la story)

1. **[auth-callout]** aplica la regla `docs`; el evento lleva `matched_role: "docs"` sin `email`.
2. **[core — dispatcher]** `email` opcional porque `docs` está en `SERVICE_ROLES`; deriva
   `identity_type = service`.
3. **[core]** crea la fila en `users` con `roles: [internal-app, docs]`.
4. **[core — caller-class / authorize-caller]** rol `docs` desconocido se saltea; `internal-app` da
   clase `connector` y `commands/queries: ALL`.
