- **Resumen:** Construir en `core` el **motor de consulta genérico** del plano `jiku-queries` —gramática
  completa de `filter` / `sort` / `page` / `fields` / `include` / `count`, ficha de recurso **como dato**,

### Service Architecture

`core` es un **worker**: consumidor de bus, sin puerto ni endpoints HTTP. Desde S-013 el proceso monta
**dos servicios micro** sobre una sola conexión NATS (`jiku-commands` y `jiku-queries`) más una
suscripción plana al evento de autenticación.

```
core/
├── src/
│   ├── index.ts              # arranque: loadConfig, initializeDb, BusHost.start()
│   ├── config.ts             # CORE_TRUSTED_PUBLISHER_ID, validado al arrancar
│   ├── logger.ts             # Winston
│   ├── authorize-caller.ts   # la compuerta ROLE_METHODS (S-017)
│   ├── bus/
│   │   ├── host.ts           # UNA conexión, N servicios micro + consumidor de eventos
│   │   ├── service.ts        # registerService(): endpoints micro, handle() que nunca lanza
│   │   └── dispatcher.ts     # despachador de COMANDOS (abre transacción)
│   ├── commands/             # los 20 comandos de escritura
│   │   └── tasks/priority.ts # la traducción priority enum <-> entero
│   ├── events/               # el consumidor del evento de auth
│   ├── models/
│   │   ├── index.ts          # Sequelize con el usuario DUEÑO, registra @jiku/models
│   │   └── read.ts           # readDb: SOLO LECTURA, SIN modelos registrados
│   └── queries/              # <-- EL MÓDULO DE ESTA STORY
│       ├── index.ts          # registro único de las 6 consultas
│       ├── registry.ts       # QueryRegistry: Map exacto, sin {param}
│       ├── dispatcher.ts     # QueryDispatcher: SIN transacción, nunca lanza
│       ├── types.ts          # Query, QueryContext
│       ├── pending.ts        # pendingContract(): el stub sin contrato
│       ├── tasks/            # tasks-list.ts, tasks-get.ts
│       ├── projects/         # projects-list.ts, projects-get.ts (siguen pending)
│       └── comments/         # comments-list.ts, comments-get.ts (siguen pending)
└── tests/
    ├── setup-env.ts          # levanta PostgreSQL efímero ANTES de que Mocha cargue los tests
    ├── global-setup.ts       # sync() + TRUNCATE + CREATE ROLE readonly + GRANT SELECT
    ├── helpers/dispatch.ts   # dispatch() y dispatchQuery()
    ├── commands/             # un archivo por módulo de dominio
    └── queries/              # dispatcher.test.ts, registry.test.ts
```

**Patrones clave:**

- **Tres capas sin solapamiento:** `NATS -> service.ts (handle) -> QueryDispatcher -> Query`.
- **El despachador de consultas NO abre transacción** y **no tiene `params`**: los patrones de consulta
  no llevan `{param}` porque el id del recurso viaja en el payload (cache de subjects del server).
- **Ningún despachador lanza.** Todo error se traduce a un `Reply` de falla.
- **Sin capa de repositorio ni de servicio.** La consulta es la unidad completa: valida, arma SQL, lee y
  proyecta.
- **Manejo de errores:** un error esperado es un **valor de retorno** (`failure(...)`), nunca una
  excepción. Se usa la **constante** `ErrorCode.X`, jamás el literal.
- **Logging:** Winston, prefijo `[query]` en este módulo. **Nada de `console.log`.** El detalle del error
  va al log; el mensaje que cruza el bus es genérico y **nunca lleva el subject completo** (tiene el user
  id).
- **Testing:** Mocha + base real, **entrando por el despachador** (`dispatchQuery()`), nunca llamando al
  `execute` de una consulta directamente. Sin mocks de Sequelize.

#### Convenciones activas del servicio (resueltas desde `manifest.yaml`)

`service: core` · `type: worker` · `language: node`. **Todas las convenciones son CUSTOM**, ninguna del
catálogo: `_base`, `bus-consumer`, `commands`, `contract-translation`, `orm`, `validation`,
`error-handling`, `logging`, `testing`, `env-config`, `dockerfile`, `ci-github`.

**De `_base` (lo que aplica a este módulo):**

- Archivos en `kebab-case.ts`. Clases `PascalCase`. Constantes de módulo `SCREAMING_SNAKE_CASE`.
- **Imports relativos**, sin alias ni paths de `tsconfig`: `../types`, `./ficha`. Los paquetes del
  workspace por nombre: `@jiku/models`, `@jiku/nats-protocol`.
- Orden de imports: `joi` -> `sequelize` -> `@jiku/models` -> `@jiku/nats-protocol` -> relativos.
- Interfaces de payload: `{Consulta}Payload`.
- Cada archivo de consulta exporta **nombrado y también como `default`**; `index.ts` importa el default.
- **Comentarios en español**, y explican **el por qué**, no el qué. Lo que amerita comentario: una
  decisión que parece un error y no lo es, una traducción entre contrato y base, un escape transitorio
  (que además dice **cuándo desaparece**).
- `any` se tolera en dos bordes: los payloads del bus **antes** de validar y el acceso dinámico a campos.
- Fechas: `objectives.estimated_finish_date` es **STRING `YYYY-MM-DD`**, no DATE. Los tests fijan `TZ=UTC`.

**De `validation`:**

- Joi con `validateWith`-style: `schema.validate(payload, { convert: true, abortEarly: true })`.
- `joi.object()` **sin `.unknown()`**: un campo desconocido se rechaza. **No agregues `.unknown(true)`**.
- Un fallo de esquema es **siempre `invalid_fields`**.
- `validate` **no toca la base**: solo forma. Corre antes de `execute`.
- La interfaz `{X}Payload` se escribe **a mano**, no se infiere del esquema.

**De `error-handling`:**

- `success()` / `failure()` se construyen **con los helpers de `@jiku/nats-protocol`**, nunca a mano.
- Se usa la **constante** `ErrorCode.X`.
- Los mensajes nuevos van en **español** y **no llevan datos internos** (ids de otras entidades, nombres
  de columna, detalle de excepción, fragmentos de SQL, el subject).
- **No uses el mensaje como canal de datos estructurados.** Para eso está `errorDetails` (S-020).
- Todo mensaje del bus se responde. Nunca se descarta en silencio.

**De `contract-translation`:**

- La base **no se toca** para acomodar un nombre del contrato: **core traduce**.
- Una traducción vive en **un helper del módulo**, no repetida en cada consulta.
- **No renombres los modelos de `@jiku/models`**: los comparte `api`. La traducción **no se filtra** al
  paquete.
- **No construyas nada nuevo sobre `priorityValue`**: es un escape con fecha de vencimiento. En esta
  story se **expone en lectura** porque el contrato lo exige (CA-21), no se extiende su patrón.

**De `orm` (lo que aplica acá, y lo que NO):**

- `readDb` es una instancia de Sequelize **sin modelos registrados**. En este módulo se usa
  **exclusivamente** como transporte de SQL explícito: `db.query<Row>(sql, { type: QueryTypes.SELECT, replacements })`.
- **NO** se registran modelos en `readDb`, **NO** se usa `Objective.findAll()`, **NO** se importa
  `@jiku/models` para leer.
- Las reglas de transacción de la convención **no aplican**: este plano no tiene transacción.

**De `testing`:**

- Un archivo de test por módulo, en `tests/queries/{módulo}.test.ts`.
- Los fixtures se crean en el `before` del propio archivo, con los modelos directamente (la **escritura**
  de fixtures sí usa `@jiku/models` sobre la conexión de escritura; la **lectura** bajo test va por
  `readDb`).
- No dependas de la zona horaria local: `TZ=UTC` está fijado.
- No dejes datos entre archivos: el truncado es al arrancar la corrida, no entre tests.

### Relevant ADRs

#### ADR-001: Separación lectura/escritura por credenciales de base de datos

**Decisión:** la separación entre lectura y escritura **la impone PostgreSQL por permisos**, no una
convención de código. `api` conecta con un rol sin `INSERT`/`UPDATE`/`DELETE`; `core` conecta con el
usuario dueño. Desde S-013 `core` tiene además una **segunda** conexión, `readDb`, con
`POSTGRESQL_READ_USER` (solo `SELECT`).

**Implementation Rules (verbatim):**

- Toda escritura de dominio nueva **DEBE** implementarse como comando en `core`. **NO SE DEBE** agregar
  escritura con el ORM en `api`.
- La conexión de `api` **DEBE** usar credenciales sin `INSERT`/`UPDATE`/`DELETE`. Si un endpoint nuevo
  requiere escribir, la respuesta correcta es un comando, no ampliar los permisos del rol.
- La conexión de `core` **DEBE** usar el usuario dueño de la base.
- Las migraciones **DEBEN** correr desde `api` con `POSTGRESQL_MIGRATION_USER`, nunca desde `core`.
- Después de publicar un comando de creación, la api **DEBE** releer la base para armar la respuesta:
  core devuelve solo `{ id }` y el contrato con los frontends es el recurso completo con sus relaciones.
- Un endpoint que lee **NO DEBE** pasar por el bus: la lectura va directo a PostgreSQL desde la api.
  **Excepción declarada desde REQ-001 (S-005): la lectura de archivos.**

> **Lo que esta story no puede aflojar (CA-28):** `core/src/models/read.ts` **no recibe `models`**. Dos
> instancias de Sequelize en el mismo proceso se pelean las clases del paquete: la segunda que registre
> el índice las **reasigna**, y las escrituras empiezan a salir por la conexión equivocada — rompiendo
> ADR-001 **sin un solo síntoma**. Es la primera de 18 tentaciones de "usar el ORM que ya está ahí".

#### ADR-003: La transacción es del despachador

**Decisión:** el despachador de **comandos** abre la transacción y decide commit/rollback por el `status`
del reply. El despachador de **consultas** no abre ninguna, y la ausencia es el contrato (RF-9).

**Implementation Rules (verbatim):**

- Un comando **DEBE** recibir la transacción por su contexto y usarla en todas sus operaciones de base de
  datos. **NO DEBE** abrir una transacción propia.
- Un comando **NO DEBE** llamar a `commit()` ni a `rollback()`. Si el código de un comando los invoca,
  está mal escrito.
- Un comando **DEBE** señalar el fallo devolviendo un `Reply` con `status: 'failure'` y su `errorCode`.
  **NO DEBE** lanzar una excepción para señalar un fallo de negocio esperado.
- El despachador **DEBE** hacer commit **solo** si el reply es `success`, y rollback en todos los demás
  casos, incluidas las excepciones inesperadas.
- El despachador **NO DEBE** lanzar nunca: todo error se traduce a un `Reply` de falla.
- Los tests de comandos **DEBEN** entrar por el despachador (helper `dispatch()`), no llamando a
  `execute()` directamente: es lo único que verifica el comportamiento transaccional, incluido el
  rollback.

> **Aplicación a esta story (CA-31):** `QueryContext` **sigue sin `transaction` y sin `params`**. Si una
> consulta necesitara consistencia entre varias lecturas, abre una `READ ONLY` explícita **dentro de sí
> misma** — en `tasks` no hace falta.

#### ADR-004: El vocabulario del producto vive en el contrato del bus, no en el esquema

**Decisión:** *"la base no se toca: el nombre nuevo es del contrato, no del almacenamiento"*. El bus dice
`task`; la base dice `objectives`. **Core traduce.**

**Implementation Rules (verbatim):**

- Un comando nuevo **DEBE** usar el vocabulario del producto en su contrato (`task`, no `objective`). La
  traducción a nombres de tabla vive **dentro** del comando.
- **NO SE DEBE** renombrar una tabla ni una columna existente para alinearla con el contrato. La base se
  cambia solo cuando hay una razón propia, no por vocabulario.
- Toda traducción contrato ↔ base **DEBE** vivir en `core`, en el comando o en un helper del módulo.
  **NO DEBE** filtrarse a `@jiku/models`, que describe la base tal como es.
- El contrato HTTP de la api **NO DEBE** cambiar de vocabulario sin coordinarlo con los dos frontends: es
  el contrato público del producto.
- `priorityValue` es un escape transitorio: **NO SE DEBE** replicar el patrón de mandar un campo paralelo
  para esquivar una traducción con pérdida. Cuando la web mande nombres de prioridad, el campo se elimina.
- Al agregar un valor a un enum del bus, **DEBE** verificarse que la traducción a la base sea biyectiva.
  Si no lo es, la traducción es el problema, no el enum.

#### ADR-005: Modelos compartidos en `@jiku/models`

**Implementation Rules (verbatim):**

- Los modelos Sequelize **DEBEN** vivir en `@jiku/models`. **NO SE DEBE** definir un modelo dentro de
  `api/` o de `core/`.
- `@jiku/models` **NO DEBE** abrir una conexión ni leer variables de entorno de base de datos. Exporta
  clases; la instancia la crea cada servicio.
- Cada servicio **DEBE** registrar las clases en su propio `Sequelize` con sus credenciales.
- Un cambio de esquema **DEBE** hacerse en dos lugares en el mismo cambio: la migración en
  `api/db-upgrade/migrations/` y el modelo en `@jiku/models`. Uno sin el otro deja el código y la base
  desalineados.
- Los hooks que van en el modelo son los que pertenecen **al dato** (mantener `finishedAt` consistente
  con `state`). Los que dependen del caso de uso o del rol **DEBEN** ir en el comando de core o en la api.
- Los nombres en `@jiku/models` **DEBEN** ser los reales de la base. La traducción de vocabulario es
  responsabilidad de core.
- Al agregar un modelo, **DEBE** registrarse en el índice del paquete: los dos servicios lo importan
  desde ahí.

> **Esta story NO toca `@jiku/models`.** Es deliberado y es un criterio de aceptación.

#### ADR-002: Comandos NATS sin JetStream (lo que aplica al envelope)

**Implementation Rules relevantes (verbatim):**

- Toda respuesta **DEBE** tener el formato `{ status: 'success', data }` o
  `{ status: 'failure', errorCode, errorMessage }`. **NO SE DEBEN** inventar otros formatos.
- Todo `errorCode` nuevo **DEBE** agregarse al mapa de `api/lib/utils/bus/protocol.ts` con su status HTTP.
  Un código sin mapeo cae en un 500 genérico.
- **NO SE DEBE** transportar datos estructurados dentro de `errorMessage`.
- Core **NO DEBE** publicar mensajes: solo responde el `Reply` de la request que recibe.

> **Excepción declarada de REQ-006 a la regla del mapa HTTP:** los cinco códigos nuevos
> (`unknown_caller`, `query_timeout`, `invalid_cursor`, `comment_not_found`, `task_not_found`)
> **NO se agregan** a `api/lib/utils/bus/protocol.ts`: al cerrar REQ-006 `bus.query()` sigue sin caller,
> así que ninguno llega a una respuesta HTTP y el mapa sería código muerto. **Esta story no toca `api`.**

#### ADR-008: Autorización deny-by-default

Lo que aplica: `ROLE_METHODS` en `core/src/authorize-caller.ts` es **cerrado y deny-by-default**. Esta
story **no lo toca**. Hoy autoriza `queries: ALL` a `admin`, `user` y `external-user`; el recorte por
clase de caller llega en S-023.

### API Context

El contrato de esta story es **el del bus**, no HTTP.

- `docs/apis/api.yaml` **no cambia**.
- `docs/apis/core.yaml` (AsyncAPI de los 20 comandos) **no cambia**: enumera lo que devuelve un

- `docs/apis/core-queries.yaml` **NO EXISTE TODAVÍA** — lo crea **S-028**. No lo crees en esta story.

#### Gramática del subject (de `@jiku/nats-protocol`)

```
{instance}.{user-id}.{svc}.{version}.{método}
dev.323332022539911171.jiku-queries.v1.tasks.list
```

- `querySubject(query, userId)` arma el subject; **no se concatena a mano**.
- `methodFromSubject(subject)` -> `tasks.list` (`slice(4).join('.')`).
- `callerFromSubject(subject)` -> **segundo token**, y de ningún otro lugar. Es infalsificable: el
  auth-callout solo autoriza publicar bajo el id propio (ADR-007).
- Los patrones de consulta **no llevan `{param}`**. El id del recurso viaja en el payload.
- `QUERY_SERVICE = 'jiku-queries'`, `PROTOCOL_VERSION = 'v1'`, `INSTANCE = 'dev'` (por env).

#### El envelope (`@jiku/nats-protocol`, con `errorDetails` desde S-020)

```ts
export interface Reply<T = unknown> {
  status: 'success' | 'failure';
  errorCode?: string;
  errorMessage?: string;
  errorDetails?: Record<string, unknown>;   // S-020. AUSENTE por default
  data?: T;
}

export function success<T>(data?: T): Reply<T>;
export function failure(
  errorCode: string,
  errorMessage: string,
  details?: Record<string, unknown>,
): Reply<never>;
```

- **`errorDetails` solo aparece si se pasa el tercer argumento.** `failure(code, msg)` produce un
  envelope **sin la clave**, byte a byte igual al de siempre — por eso los 20 comandos no cambian.
- La comparación en `failure()` es contra `undefined` **explícitamente**: un `{}` es un detalle legítimo
  y viaja.
- **Acá adentro van DATOS DEL CONTRATO:** qué campo, qué valor, qué se aceptaba. **Nunca** stack traces,
  nombres de columna de la base, fragmentos de SQL, ni el subject completo.

#### Códigos de error disponibles (todos **ya declarados** en `ErrorCode`, S-020)

| Constante | Valor | Uso en esta story |
|---|---|---|
| `ErrorCode.INVALID_FIELDS` | `invalid_fields` | Nombre no declarado, `or` anidado, `limit` inválido, identidad en el payload, `get` mal formado |
| `ErrorCode.INVALID_CURSOR` | `invalid_cursor` | Cursor malformado, de otra `v`, o con `h` que no coincide |
| `ErrorCode.QUERY_TIMEOUT` | `query_timeout` | `statement_timeout` de PostgreSQL (8000 ms) |
| `ErrorCode.TASK_NOT_FOUND` | `task_not_found` | `tasks.get` de un id inexistente |
| `ErrorCode.INTERNAL_ERROR` | `internal_error` | Cualquier otra cosa (lo captura el despachador) |
| `ErrorCode.UNKNOWN_COMMAND` | `unknown_command` | Lo que sigue devolviendo `pendingContract` para los otros cuatro endpoints |

> `ErrorCode.OBJECTIVE_NOT_FOUND` **se queda en los comandos**. En consultas es `TASK_NOT_FOUND`.
> `ErrorCode.UNKNOWN_CALLER` existe pero **lo emite S-023**, no esta story.

#### La forma del payload — `list`

```jsonc
{
  "filter":  { "projectId": 12, "state": ["backlog", "activo"],
               "createdAt": { "gte": "2026-08-01T00:00:00.000Z" },
               "or": [ { "state": "activo" },
                       { "state": "finalizado", "finishedAt": { "gt": "2026-08-16T00:00:00.000Z" } } ] },
  "sort":    ["-createdAt"],
  "page":    { "limit": 50, "cursor": null },
  "fields":  ["id", "title", "state"],
  "include": ["description", "project"],
  "count":   false
}
```

**Todo opcional.** Las claves de `filter` se combinan **con AND**; **el valor decide el operador**:

| Se escribe | Significa |
|---|---|
| `"campo": valor` | Igualdad |
| `"campo": [v1, v2]` | `IN (v1, v2)` |
| `"campo": null` | `IS NULL` |
| `"campo": {"not": valor}` | Distinto |
| `"campo": {"gte": a, "lte": b}` | Rango; también `gt` y `lt`, **combinables entre sí** |
| `"q": "texto"` | Búsqueda sobre los campos que declara el recurso (`title`, `description` en `tasks`) |

- `filter.or` admite **un solo nivel**. Un `or` dentro de otro `or` -> `invalid_fields`.
- `sort` es un array aplicado en orden, `-` para descendente; el servicio **agrega `id` al final siempre**.
- `page.limit`: default **50**, máximo **200** (mayor se recorta **sin avisar**), `0` = default, negativo
  o no entero = `invalid_fields`.
- `count`: `false` (o ausente) | `true` | `"only"`.

#### La forma del payload — `get`

```jsonc
{ "id": 8140, "fields": [], "include": [] }
```

`id` obligatorio. `filter`, `sort`, `page` y `count` **no aplican**: si vienen, `invalid_fields`.

#### El envelope de respuesta

```jsonc
// list
{ "status": "success",
  "data": { "items": [ … ],
            "page": { "limit": 200, "returned": 173, "cursor": "eyJ…", "total": 128 } } }

// get   — `data` ES el recurso, sin envoltorio de colección
{ "status": "success", "data": { "id": 8140, "title": "…" } }

// error
{ "status": "failure", "errorCode": "invalid_fields",
  "errorMessage": "…",
  "errorDetails": { "field": "sort", "value": "estimatedFinishDate", "allowed": [ … ] } }
```

- `items` **siempre presente**; `[]` **no es un error**.
- `page.limit` es el **efectivamente aplicado**, que puede ser menor al pedido.
- `page.returned` es explícito para que el recorte por bytes sea **visible**.
- **La ausencia de `page.cursor` es la ÚNICA señal de fin.** `returned < limit` **no significa nada**.
- `page.total` **solo** si se pidió `count`. Exacto, no estimado.

#### La ficha de `tasks` (el dato que esta story define)

En la base la tabla es `objectives`. En el contrato es `task`, **siempre**.

| Grupo | Contenido |
|---|---|
| **Base** | `id` `title` `state` `area` `priority` `priorityValue` `estimatedFinishDate` `finishedAt` `visibilityLevel` `projectId` `requirementId` `createdBy` `createdAt` `updatedAt` |
| **Includable (field)** | `description` |
| **Includable (relation)** | `project` -> `{id,name,code,status}` · `requirement` -> `{id,title,state}` · `responsiblePersons` -> `[{id,firstName,lastName,isLeader}]` (**solo `active = true`**) · `comments` (tope **10**, marca `commentsTruncated`) · `subscriptors` -> `[userId]` |
| **Filterable** | `id` `projectId` `requirementId` `state` `area` `priority` `priorityValue` `visibilityLevel` `createdBy` `responsiblePersonId` `finishedAt` `createdAt` `updatedAt` `q`(sobre `title`, `description`) |
| **Sortable** | `title` `state` `priority` `finishedAt` `createdAt` `updatedAt` — default `["-createdAt"]` |
| **Recorte externo** | proyectos permitidos **y** `visibilityLevel = public` — **se DECLARA acá y lo APLICA S-023** |

**Enums del contrato:**

- `state`: `backlog` · `activo` · `en_revision` · `finalizado` · `cancelado`
- `area`: `diseño` · `desarrollo` · `gestion` · `investigacion`
- `priority`: `sin_prioridad` · `baja` · `media` · `alta` · `urgente`

**Notas que la ficha tiene que dejar escritas:**

#### Los índices del keyset (S-021, ya aplicados)

> **Un campo del contrato de consultas se declara ordenable SOLO si tiene índice compuesto terminado en
> `id`.** No es una recomendación de performance: es lo que hace posible la paginación keyset, que
> resuelve la página siguiente con `WHERE (sort…, id) > (k…)` en vez de `OFFSET`. Sin el índice, cada
> página degrada a `Seq Scan` + `Sort` y el `statement_timeout` de 8000 ms empieza a devolver
> `query_timeout` bajo carga normal.
>
> **La dirección de cada columna importa.** PostgreSQL recorre un índice hacia atrás, pero un compuesto
> con direcciones **mixtas** solo sirve al orden que declara y a su inverso exacto. Los índices de
> `objectives` llevan `DESC` en `created_at` e `id`.

Los tres que sostienen los `sortable` de `tasks`:
`idx_objectives_project_created_id`, `idx_objectives_priority_created_id`, `idx_objectives_state_created_id`.

> **⚠️ PUNTO ABIERTO — requiere verificación antes de implementar la ficha.**
> La ficha declara `sortable = [title, state, priority, finishedAt, createdAt, updatedAt]`, pero S-021
> entregó índices compuestos terminados en `id` solo para `(project_id, created_at, id)`,
> `(priority, created_at, id)` y `(state, created_at, id)`. **`title`, `finishedAt` y `updatedAt` no
> tienen índice compuesto propio**, y la regla de `docs/db-schemas/jiku.md` ("Los índices del keyset")
> dice que un campo se declara ordenable **solo** si lo tiene. La story reconoce la tensión
> (sección Dependencias enumera exactamente esos tres índices) pero **no la resuelve**.
> **No la resuelvas por tu cuenta:** implementá la ficha **tal como la story la declara** y dejá
> registrada la discrepancia. Las dos salidas posibles —agregar índices (otra story, toca `api/`) o
> recortar el `sortable`— son decisiones de producto, no de implementación.

> **⚠️ Segundo punto abierto — el esquema de test no tiene estos índices.**
> `core/tests/global-setup.ts` construye el esquema con `sequelize.sync()` sobre `@jiku/models`, y
> **`@jiku/models` no declara los índices de REQ-006** (viven solo en la migración de `api/`). La
> **corrección** del keyset no depende del índice, así que los tests pasan igual; la **performance** no
> queda cubierta por la suite. No agregues los índices a `@jiku/models` en esta story: ADR-005 exige
> migración + modelo en el mismo cambio, y la migración ya la posee S-021.

#### El presupuesto de bytes y `nc.info.max_payload` — plumbing que hay que construir

**Estado actual:** `nc.info` **no se usa en ningún lado** del codebase. `ServiceSpec.handle` tiene la
firma `(subject: string, payload: unknown) => Promise<Reply>` y no recibe la conexión; `BusHost` guarda
la conexión en un campo privado (`core/src/bus/host.ts`).

**Lo que la story exige (CA-14 y el riesgo declarado):**

- El presupuesto es `floor(nc.info.max_payload * 0.5)`.
- **Se resuelve POR REQUEST y no se cachea al arranque:** una reconexión a un server con otra
  configuración cambiaría el número.
- **Necesita un valor por defecto razonable si `nc.info` no está disponible.**
- **Tiene que poder inyectarse en los tests:** depender del `max_payload` real del server hace el test
  frágil.

**Camino recomendado (no inventes otro sin razón):** un proveedor perezoso `() => number`.

1. `BusHost` expone `maxPayload(): number | undefined` leyendo `this.connection?.info?.max_payload`.
2. `QueryDispatcher` recibe un tercer argumento opcional `payloadBudget?: () => number` y lo evalúa **en
   cada `dispatch()`**, pasando el resultado en `QueryContext`.
3. `src/index.ts` le pasa `() => budgetFrom(host.maxPayload())`. La closure referencia `host`, que se
   declara después: es válido porque se **invoca** después de `start()`.
4. El default cuando `nc.info` no está: `max_payload` de NATS por defecto es **1 MiB (1048576)**, así que
   el presupuesto por defecto es **524288**. Declaralo como constante de módulo con un comentario que
   explique de dónde sale el número.
5. `tests/helpers/dispatch.ts` construye su `QueryDispatcher` con un presupuesto **fijo e inyectable**,
   para que los tests de CA-14/CA-15 no dependan de ningún server.

**No agregues la conexión a `ServiceSpec`:** cambiaría la firma que también usa `jiku-commands`, que esta
story declara intacto.

### Flow Context

**Flujo nuevo que esta story estrena:** `docs/flows/consulta-por-el-bus.md` (status `Draft`,
stories S-022…S-028).

> **El Paso 3.4 (clase del caller) y el Paso 5 (recorte del modo externo) están descritos en el flujo
> pero los implementa S-023.** En esta story el motor construye SQL **sin recorte de filas**.

#### Paso 1 — El caller publica la consulta

- Subject: `{instance}.{user-id}.jiku-queries.v1.{recurso}.{operación}`, ej.
  `dev.323332022539911171.jiku-queries.v1.tasks.list`
- **Sin `*` en el subject** (RF-4): el id del recurso viaja **en el payload**, para no inutilizar el
  cache de subjects de 1024 entradas del server.
- El segundo token es el `sub` de Zitadel de quien publica, **infalsificable** (ADR-007).
- **El payload NO lleva identidad.** Un campo de identidad en el cuerpo responde `invalid_fields`.
- Timeout del caller: `NATS_QUERY_TIMEOUT_MS` = **10000 ms**.

#### Paso 2 — `bus/service.ts` decodifica y delega

- `msg.json()`. **Cuerpo vacío = `{}`.**
- Un payload no-JSON se contesta con un `failure` bien formado: el endpoint **nunca deja de contestar**.
- -> `QueryDispatcher.dispatch(subject, payload)`

#### Paso 3 — Identidad y autorización (ya implementado, S-017)

- `caller = callerFromSubject(subject)` -> **segundo token**.
- `authorizeCaller(caller, method, 'queries')`. `CORE_TRUSTED_PUBLISHER_ID` pasa **sin consultar la base**.
- `ROLE_METHODS` es cerrado y deny-by-default: `admin`, `user` y `external-user` tienen `queries: ALL`.
- Sin autorización -> `failure` `caller_not_authorized`.
- **La compuerta VA ANTES de resolver el método**, y esta story **no altera ese orden**.
- **Paso 3.4 (clase del caller -> `unknown_caller`) es S-023. NO lo implementes acá.**

#### Paso 4 — Validación contra las listas blancas del recurso  **← esta story**

- Un nombre no declarado en `filter`, `sort`, `fields` o `include` responde `invalid_fields`, con
  `errorDetails: { field, value, allowed }`. **Nunca se ignora en silencio**: un filtro ignorado devuelve
  **datos de más**.
- `filter.or` admite **un solo nivel**.
- `page.limit`: default 50, máximo 200 (mayor se recorta **sin avisar**), `0` = default, negativo o no
  entero = `invalid_fields`.
- `sort`: array en orden, `-` para descendente. El servicio **agrega `id` como último criterio siempre**.
- Conjunto devuelto: `( fields ?? base ) ∪ include ∪ { id }`.
- Cursor: base64url de `{"v":1,"k":[…],"h":<hash(filter+sort)>}`; se verifica `h` contra el `filter`+`sort`
  **de esta request**. No coincide, malformado o de otra `v` -> `invalid_cursor`. **Cambiar solo el
  `limit` sí es válido.**
- **La misma estructura que valida es la que `meta.describe` proyecta** (S-028): la descripción del
  contrato no puede desactualizarse porque **no hay una segunda copia**.

#### Paso 5 — El recorte del modo externo  **← S-023, NO esta story**

Se **declara** en la ficha de `tasks` (proyectos permitidos + `visibilityLevel = public`) y **no se
aplica**. Ver Riesgos.

#### Paso 6 — El SQL sobre la conexión de solo lectura  **← esta story**

- **Conexión:** `readDb` — `POSTGRESQL_READ_USER`, pool propio, `statement_timeout` = **8000 ms**
- **SQL explícito** (`db.query(...)`), **nunca el ORM**
- **Sin transacción** (ADR-003)

```sql
-- tasks.list, filtro por proyecto, sort default, primera página
SELECT … FROM objectives
 WHERE project_id = $1 AND state = ANY($2)
 ORDER BY created_at DESC, id DESC
 LIMIT 201;                       -- limit + 1, para saber si hay página siguiente SIN un COUNT

-- página siguiente: keyset sobre el índice, no OFFSET
 WHERE project_id = $1 AND state = ANY($2) AND (created_at, id) < ($3, $4)
```

**Dos reglas duras del armado:**

1. **Los nombres** de tabla, columna y dirección de orden salen **exclusivamente de las listas blancas**
   del recurso — **nunca del payload**. Un nombre no declarado **no llega al SQL**: responde
   `invalid_fields` en el Paso 4.
2. **Los valores** van **siempre** como parámetros (`replacements`).

**Traducciones que esta story implementa** (todas en el servicio de consultas, ADR-004; **ninguna se
filtra a `@jiku/models`**):

| Contrato | Base |
|---|---|
| `tasks` | tabla `objectives` |
| `priority` (enum) + `priorityValue` (entero) | `objectives.priority` `INTEGER` 0-5 |
| `body` (en `comments` incluidos) | `objective_activity.new_value` |
| `authorId` (en `comments` incluidos) | `objective_activity.changed_by` |

**Exclusión permanente:** `ticket_slug` **nunca se expone** ni se acepta como filtro.

#### Paso 7 — Proyección, presupuesto de bytes y cursor  **← esta story**

- **Traduce por fila** al vocabulario del contrato.
- **Serializa item por item midiendo bytes** hasta `floor(nc.info.max_payload * 0.5)`. Si se pasa, **corta
  ahí** y devuelve cursor **aunque falten items del `limit` pedido**.
- **Un item que solo no entra se devuelve igual**, con el campo de texto truncado y marcado
  (`"<campo>Truncated": true`). **Nunca una página vacía con cursor**, que para el cliente es un bucle
  infinito.
- **Cursor** = base64url de `{"v":1,"k":[<clave de orden>,<id>],"h":<hash(filter+sort normalizados)>}`.
  **No autoriza nada**: identidad y filtros **se reaplican en cada página**.

#### Paso 8 — El caller recorre la colección

```ts
let cursor: string | null = null;
do {
  const res = await bus.query('tasks.list', { filter, sort, page: { limit: 200, cursor } });
  procesar(res.data.items);
  cursor = res.data.page.cursor ?? null;
} while (cursor);
```

**Entre página y página, `filter` y `sort` tienen que ir idénticos** o la respuesta es `invalid_cursor`.
**`limit` sí puede cambiar.**

#### Catálogo de errores del flujo (el subconjunto que esta story implementa)

| Situación | Código | Dónde se decide |
|---|---|---|
| Nombre no declarado en `filter`/`sort`/`fields`/`include` | `invalid_fields` + `errorDetails: {field, value, allowed}` | validación contra la ficha |
| `or` anidado dentro de otro `or` | `invalid_fields` | parser del filtro |
| `limit` negativo o no entero | `invalid_fields` | validación de `page` |
| Campo de identidad en el payload | `invalid_fields` | validación transversal |
| `get` sin `id`, o con `filter`/`sort`/`page`/`count` | `invalid_fields` | validación de la forma `get` |
| Cursor malformado, de otra `v`, o con `h` que no coincide | `invalid_cursor` | decodificador del cursor |
| `tasks.get` de un id inexistente | `task_not_found` | el `get` |
| `tasks.list` que no matchea nada | **`items: []`**, no un error | motor |
| `statement_timeout` de 8000 ms | `query_timeout` | captura del error de PostgreSQL |
| Cualquier otra cosa | `internal_error`, con detalle en el log y **sin el subject completo** | `catch` del despachador |

**La garantía dura: toda request obtiene respuesta.** La sostienen tres redes que esta story **no
debilita**: el `try/catch` de `QueryDispatcher.dispatch` (`core/src/queries/dispatcher.ts:60-68`), el
`try/catch` de `handle()` en `bus/service.ts:70-77`, y la invariante 8000 < 10000.

### Task 3: El validador de la gramática contra la ficha

**Status:** Completed

#### Description

El validador genérico que traduce un payload crudo del bus a una **especificación de consulta validada**,
o a un `failure` `invalid_fields` con `errorDetails`. Es la compuerta que hace que **un nombre no
declarado no llegue nunca al SQL**.

Cubre: las dos formas (`list` y `get`), los seis operadores del filtro, `filter.or` de un solo nivel, la
normalización de `sort` con el desempate por `id`, la fórmula del conjunto devuelto, las reglas de
`page.limit`, los tres valores de `count`, y el rechazo de campos de identidad en el payload.

#### Acceptance Criteria

1. Un nombre no declarado en `filter`, `sort`, `fields` o `include` responde
   `failure(ErrorCode.INVALID_FIELDS, <mensaje en español>, { field, value, allowed })`.
2. `allowed` sale **de la ficha**, no de una copia: la lista devuelta es la misma estructura que la ficha
   declara.
3. **Nunca se ignora en silencio.** Ningún nombre desconocido produce `success`.
4. Los seis operadores se reconocen por la **forma del valor**: escalar = igualdad, array = `IN`,
   `null` = `IS NULL`, `{not}` = distinto, `{gte|gt|lte|lt}` = rango (**combinables entre sí**),
   `q` = búsqueda sobre las columnas que declara la ficha.
5. Una clave de operador desconocida dentro de un objeto (por ejemplo `{ like: 'x' }`) es
   `invalid_fields`.
6. `filter.or` admite **un solo nivel**: un `or` dentro de un elemento de `or` es `invalid_fields` con
   `errorDetails.field === 'filter.or'`.
7. `sort` sin especificar usa `defaults.sort` de la ficha; en los dos casos se **agrega `id` como último
   criterio**, con la misma dirección que el último criterio declarado.
8. `sort` respeta el orden del array y el prefijo `-` para descendente.
9. Conjunto devuelto = `( fields ?? base ) ∪ include ∪ { id }`, con `id` **siempre** presente.
10. `page.limit`: ausente o `0` -> `50`; `> 200` -> `200` **sin error**; negativo o no entero ->
    `invalid_fields` con `errorDetails.field === 'page.limit'`.
11. `count` acepta `false`, `true` y `"only"`; cualquier otro valor es `invalid_fields`.
12. Un campo de identidad en el payload (`userId`, `caller`, `callerId`, `sub`, …) es `invalid_fields`.
    La lista de nombres prohibidos es una constante de módulo con comentario.
13. La forma `get` exige `id` y **rechaza** `filter`, `sort`, `page` y `count`, con el nombre de la
    palanca ofensora en `errorDetails.value`.
14. La forma `get` acepta `fields` e `include` y les aplica la misma fórmula del punto 9.
15. Ningún `errorMessage` contiene el subject, nombres de columna de la base ni fragmentos de SQL.
16. El validador **no toca la base**.

#### Technical Details

**Architectural Context References:**

- Convención **`validation`** — Joi con `convert: true`, `abortEarly: true`; `joi.object()` **sin

### Task 4: El cursor keyset — codec, normalización y hash

**Status:** Completed

#### Description

El cursor opaco que sostiene la paginación keyset: lo **codifica** el motor al cerrar una página y lo
**decodifica** al abrir la siguiente, verificando que corresponde a **esta** consulta.

Es `base64url` de `{"v":1,"k":[<clave de orden…>,<id>],"h":<hash(filter+sort normalizados)>}`. La pieza
delicada es la **normalización**: si el hash se calculara sobre el JSON tal como llegó, un caller que
reordene las claves del mismo filtro recibiría `invalid_cursor` sin haber cambiado nada.

#### Acceptance Criteria

1. `encodeCursor(keys, filter, sort)` devuelve un string `base64url` (sin padding, seguro en JSON).
2. `decodeCursor(cursor, filter, sort)` devuelve las claves de orden, o un error de cursor.
3. `v` es una constante de módulo `CURSOR_VERSION = 1`. Un cursor con otra `v` -> `invalid_cursor`.
4. Un cursor malformado (no base64url, JSON inválido, sin `k` o sin `h`) -> `invalid_cursor`. **Nunca
   lanza**, nunca `internal_error`.
5. `h` se calcula sobre una **normalización** del `filter` y del `sort`: claves de objeto ordenadas
   alfabéticamente en todos los niveles, listas en orden estable, `undefined` omitido.
6. **Reordenar las claves del mismo filtro NO invalida el cursor.**
7. Cambiar el `filter` o el `sort` **sí** invalida el cursor.
8. Cambiar **solo el `limit`** NO invalida el cursor: el `limit` **no participa** del hash.
9. `k` contiene los valores de las claves de orden **más el `id`**, en el mismo orden que el `ORDER BY`.
10. El cursor **no transporta** identidad, ni caller, ni conjunto de resultados: solo `v`, `k` y `h`.
11. El hash es de longitud fija y no reversible (sha256 truncado alcanza; **no es un secreto**, es un
    detector de cambio).

#### Technical Details

**Architectural Context References:**

- **API Context → "El envelope de respuesta"** y las reglas de `page.cursor`.
- **Flow Context → Paso 4 (cursor) y Paso 7 (emisión)**.
- Convención **`error-handling`** — `ErrorCode.INVALID_CURSOR`, y el decodificador **no lanza**.
- **Riesgos de la story** — "el hash del cursor cambia con la serialización del `filter`" y "el cursor no
  autoriza nada".
- `hashUserId` de `@jiku/nats-protocol` es un **precedente de estilo** (sha256 -> codificación corta), no
  una función a reusar: aquel hash tiene que coincidir con el del auth-callout, este no.

**Files to Create/Modify:**

- `src/queries/engine/cursor.ts`
- `tests/queries/cursor.test.ts`

**Implementation Notes:**

- Usá `node:crypto` (`createHash('sha256')`), que ya se usa en el monorepo. Truncar a 16 caracteres hex o
  base64url alcanza: es un detector de cambio, no una defensa criptográfica.
- `base64url`: `Buffer.from(json).toString('base64url')` está disponible en el Node de este proyecto.
- **El `limit` no entra en el hash, y es un requisito, no un olvido** (CA-17). Dejá el comentario: sin
  él, la próxima persona lo "arregla" agregándolo y rompe TS-31.

### Task 7: Presupuesto de bytes, armado de la página y emisión del cursor

**Status:** Completed

#### Description

Cerrar la página: serializar item por item midiendo bytes hasta el presupuesto, decidir si hay página
siguiente, emitir el cursor, y armar el objeto `page` de la respuesta.

Acá vive la regla que evita el peor modo de fallo del contrato: **un item que solo no entra se devuelve
igual, truncado y marcado — nunca una página vacía con cursor**, que para el cliente es un bucle infinito.

#### Acceptance Criteria

1. Los items se serializan **de a uno**, acumulando bytes, hasta el presupuesto de `ctx.budgetBytes`.
2. Si el presupuesto se alcanza, la página **corta ahí**: devuelve **menos items que el `limit`** y
   entrega `cursor`.
3. `page.returned` refleja **lo efectivamente devuelto**, siempre.
4. `page.limit` es el **efectivamente aplicado** tras el recorte silencioso de 200, **no** el recortado
   por bytes.
5. Si el **primer** item por sí solo excede el presupuesto, se devuelve **igual**, con el campo de texto
   truncado y marcado `"<campo>Truncated": true`. **Nunca una página vacía con cursor.**
6. El cursor se emite **solo** si hay página siguiente: por la fila extra del `LIMIT limit + 1` o por
   corte de presupuesto.
7. La última página **no trae `cursor`**.
8. `data.items` **siempre presente**; `[]` no es un error y no lleva cursor.
9. `page.total` aparece **solo** si se pidió `count`.
10. Con `count: 'only'`, `items` es `[]`, `total` está presente y **no** hay cursor.
11. El presupuesto se lee de `ctx.budgetBytes` (T1) y **no** de `nc.info` directamente: el motor no conoce
    la conexión.

#### Technical Details

**Architectural Context References:**

- **API Context → "El envelope de respuesta"** — las cinco reglas de `page`.
- **Flow Context → Paso 7** — verbatim.
- **Riesgos de la story** — "un item que solo no entra produciría una página vacía con cursor" y
  "`max_payload` se lee del server y puede no estar disponible".
- **Integration Points → "El presupuesto de bytes"** — por qué se resuelve por request.
- **T1** — de dónde viene `budgetBytes`; **T4** — el codec del cursor.

**Files to Create/Modify:**

- `src/queries/engine/paginate.ts` — presupuesto, armado de `page`, emisión del cursor
- `tests/queries/paginate.test.ts`

**Implementation Notes:**

- Medir bytes con `Buffer.byteLength(JSON.stringify(item), 'utf8')`, **no** con `.length` del string:
  la diferencia aparece con acentos y con la `ñ` de `diseño`, que están en los datos reales.
- Contabilizá también el **overhead del envelope** (las llaves de `data`, `items`, `page` y el cursor):
  el presupuesto es del mensaje completo, no de la suma de items. Un margen fijo pequeño y documentado
  alcanza.
- El truncado del item que solo no entra **elige el campo de texto sin cota** (en `tasks`,
  `description`). Si el item sigue sin entrar tras truncar, se devuelve igual: la regla de "nunca una

- El `page.limit` de la respuesta es el **pedido efectivo** (tras el tope de 200), no `items.length`.

## Notas de Riesgo para el Implementador

Cuatro cosas que la story marca como riesgos y que se deciden **durante** la implementación, no después:

1. **No despliegues S-022 sola a un entorno con callers `external-user`.** `ROLE_METHODS` ya autoriza
   `queries: ALL` a `admin`, `user` **y `external-user`**, y este motor **no recorta filas**: un caller
   externo vería tareas de proyectos que no le corresponden. **S-022 y S-023 se despliegan juntas.** La
   separación entre las dos es de **desarrollo y verificación**, no de despliegue independiente.

2. **El motor es UNO, la ficha es DATO.** Si al terminar T9 los dos archivos de `tasks` tienen lógica de
   armado de SQL, la story entregó el primero de 18 motores divergentes. La verificación real llega en
   S-024, cuando tres recursos más se agregan **sin tocar el motor**.

3. **No registres los modelos de `@jiku/models` en `readDb`.** Funciona perfecto y rompe ADR-001 en
   silencio: la segunda instancia de Sequelize **reasigna** las clases del paquete y las escrituras
   empiezan a salir por la conexión equivocada. Es la primera de 18 tentaciones de "usar el ORM que ya
   está ahí". TS-51 es la red.

4. **La migración de índices de S-021 tiene que estar aplicada en el entorno** antes de desplegar este
   `core`. En la suite de tests **no lo está** (ver el segundo punto abierto de *Database Context*): la
   corrección se verifica igual, la performance no.
