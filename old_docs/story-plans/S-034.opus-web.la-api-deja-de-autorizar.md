# Story Plan: S-034 (opus-web) - La api deja de autorizar y de exigir fila en `users`

## Status

**Status:** Completed

---

## Story Reference

- **Story:** [S-034](../stories/S-034.la-api-deja-de-autorizar.md)
- **Service:** `opus-web`
- **Summary:** Del lado de `opus-web` esta story **no toca ningún endpoint ni regla de negocio**:
  rediseña el estado `empty` de `proyectos-redireccion`, que deja de ser un borde inalcanzable
  (bloqueado hasta ahora por el 401 `user_not_found` que la api eliminó) para convertirse en la
  primera pantalla de todo cliente nuevo sin permisos (CA-14, CA-15). Suma un encabezado
  (`titulo-sin-acceso`), reescribe el microcopy corrigiendo el voseo, y agrega una salida
  (`boton-cerrar-sesion`) que en mobile es la única que existe porque el sidebar no se renderiza
  bajo 768px. También corrige el JTBD documentado de `login-entrada`, que ya no da de alta a nadie
  (CA-17) — sin cambio de código, solo de comentario/intención.

**Patrón dominante de la pantalla:** `if` temprano con retorno — el componente devuelve una
pantalla completa por estado, antes del render principal, en el orden `loading` → `error` →
`empty` → contenido. Ver [error-handling](#error-handling) más abajo.

**Convención de estilos:** CSS Modules con Sass, un módulo por componente/página
(`page.module.scss`), clases en `camelCase`, tokens en `_variables.scss` vía custom properties.
Responsive con `@include mobile` (`max-width: 767px`), **nunca** `@media` cruda.

**Convención de testing:** Vitest + Testing Library. Los tests de este archivo viven en
`__tests__/app/projects/page.test.tsx` (ubicación existente — no junto al código, porque ya está
así y la convención dice "no reubicar tests existentes al tocarlos", solo agregar ahí).
`getByRole`/`getByText`, no `getByTestId` cuando hay rol o texto accesible.

### Flow Context

**Flujo `autenticacion-y-entrada`** (paso relevante para `login-entrada`): el paso 3
(*"el paso que no hace nada"*) sigue siendo un no-op — `POST /api/auth/present` sigue llamándose
igual — pero **su razón de ser desaparece**: ya no hay fila que crear ni 401 que evitar. No hay
cambio de código en `presentInApi`, solo de comentario/intención (ver Task 2).

**User Flow 1 de `opus-web`** (`docs/ux/surfaces/opus-web/user-flows.md`), camino alternativo
*"Primera entrada de un cliente al que todavía no le dieron acceso"* — **nuevo desde REQ-007**:

> Hasta acá, una identidad autenticada sin fila en `users` chocaba contra un 401
> `user_not_found` y no entraba; ese 401 desapareció de las 61 rutas de la api, así que ahora
> **entra** y la api le devuelve `200 []` porque no tiene ninguna fila en
> `user_project_permissions` (CA-12, CA-13 del REQ). Recorre
> `login → login-entrada → proyectos-redireccion` y **se queda ahí**: es el estado `empty`, que
> dejó de ser un borde para ser la pantalla de bienvenida de todo cliente nuevo. Ve *"Todavía no
> tenés acceso a ningún proyecto"*, un texto que le dice que el acceso lo concede el equipo y a
> quién escribirle, y un botón de **Cerrar sesión** —que en mobile es la única salida que existe,
> porque el sidebar no se renderiza. **El happy path arranca recién cuando alguien le concede el
> permiso desde afuera del portal**, y el cliente lo descubre en su próxima visita: no hay
> notificación ni polling.

Sección "Errores y recuperación" del mismo flujo, entrada relevante:

> **Sin proyectos asignados** — Ya no es un error: es el estado de entrada de todo cliente nuevo.
> [...] De las tres lecturas ambiguas que tenía el mensaje anterior, **"tu alta falló" dejó de
> existir** —con REQ-007 no hay alta que fallar, `core` espeja la identidad desde el comando—; las
> otras dos, "no te asignaron ninguno todavía" y "perdiste el permiso", siguen sin distinguirse **a
> propósito**: el portal no le confirma a un externo qué existe del otro lado (REQ-006 §22). El
> cliente ahora sí tiene una acción posible: **cerrar sesión**. Lo que no tiene es forma de pedir
> el acceso desde el producto — `user_project_permissions` no tiene interfaz de administración
> (FG-1) y no hay canal de notificación (FG-2).

**Criterio de éxito nuevo agregado por REQ-007 a este flujo:**

> Un cliente que entra por primera vez y todavía no tiene acceso debería entender **que el
> producto funciona y que le falta un permiso**, no creer que se rompió.
