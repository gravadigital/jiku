# Story Plan: S-002 (core) - Módulo `files` en `core`: los dos comandos de storage

## Status

**Status:** Completed

## Story Reference

- **Story:** [S-002](../stories/S-002.modulo-files-en-core.md)
- **Service:** `core` (el worker consumidor de NATS, en `core/`)
- **Summary:** Abrir el **sexto módulo de dominio de `core`** (`src/commands/files/`) con los dos
  comandos de storage: `files.request-upload` y `files.{fileId}.request-download`. Es la primera vez
  que `core` habla con un sistema externo (S3) y la primera vez que lee configuración de negocio en
  caliente desde `system_settings`. **No tiene consumidores todavía**: se prueba de punta a punta por
  el despachador, sin tocar ninguna ruta HTTP.

> **`core` pasa a ser el único dueño del storage.** Hoy consume *"PostgreSQL, NATS, Zitadel"*
> (`overview.md`). Esta story le suma el cliente de S3 con credenciales de firma de **lectura y
> escritura**. Quitarle las variables a la `api` es lo que completa la garantía estructural, pero eso
> ocurre en **S-005**, no acá.

```
│   ├── commands/
│   │   ├── index.ts          # el registro único: agregar un comando es sumarlo a esta lista
│   │   ├── registry.ts       # matching por segmentos, extracción de params
│   │   ├── types.ts          # la interfaz Command y CommandContext
│   │   ├── validate.ts       # validateWith (Joi) y pickPresent (edición parcial)
│   │   ├── clients/ projects/ tasks/ requirements/ times/     # los 5 módulos actuales
│   │   └── files/            # <-- EL MÓDULO NUEVO DE ESTA STORY
│   └── models/index.ts       # registra los modelos de @jiku/models con las credenciales del dueño
└── tests/

    ├── global-setup.ts       # crea el esquema y trunca; apaga el contenedor al final
    ├── helpers/dispatch.ts   # despacha un comando como si viniera del bus
    └── commands/             # un archivo por módulo de dominio
```

**Tres capas, sin solapamiento:**

```
NATS ──> Consumer ──> Dispatcher ──> Command ──> base de datos
         (conexión)   (transacción)  (valida y escribe)
```

**Patrones clave del servicio:**

- **No hay capa de repositorio ni de servicio.** Un comando habla directo con los modelos. El comando
  **es** la unidad completa: valida, consulta y escribe. **No agregues una capa nueva.**
- **Un archivo por comando**, nombrado `{entidad}-{acción}.ts`. Los helpers de un dominio van en un
  archivo propio dentro de su carpeta, **sin prefijo de entidad** (`projects/properties.ts`,
  `tasks/priority.ts`, `tasks/activity.ts`).
- **Imports relativos**, sin alias ni paths de `tsconfig`. Los paquetes del workspace por nombre.
- **Orden de imports en un archivo de comando:** `joi` → `sequelize` si hace falta → `@jiku/models`
  → `@jiku/nats-protocol` → relativos.
- **Cinco partes en un archivo de comando, siempre en este orden:** imports → interfaz del payload →
  esquema Joi → el objeto `Command` → `export default`.
- **Cada archivo de comando exporta el comando nombrado Y como `default`.** El `index.ts` importa el
  default.

**Estrategia de errores:** un error es un **valor de retorno**, nunca una excepción. `failure(code, msg)`
de `@jiku/nats-protocol`. El `status` decide la transacción.

**Estrategia de logging:** un logger único importado de `../logger`. **Nunca `console.log`.** Todo
mensaje empieza con el prefijo del componente entre corchetes.

**Estrategia de testing:** Mocha contra PostgreSQL real, entrando por `dispatch()`. **Sin mocks de
Sequelize.**

### Relevant ADRs

#### ADR-002: Toda mutación es un comando NATS request/reply, sin JetStream

**Decisión:** NATS en modo request/reply, **sin JetStream**. La api publica un comando y espera la
respuesta con un timeout; core valida, escribe en una transacción y responde.

**Gramática del subject:**
```
{instance}.{user-id}.{svc}.{version}.{comando}
dev.323332022539911171.gestion.v1.clients.new
```

Core se suscribe a `{instance}.*.gestion.v1.>` con **queue group `gestion`**.

**Implementation Rules (verbatim):**

- Todo comando **DEBE** publicarse con el subject `{instance}.{user-id}.gestion.v1.{comando}`,
  usando la gramática de `@jiku/nats-protocol`. **NO SE DEBE** construir el subject a mano.
- El cliente NATS **DEBE** fijar `inboxPrefix` explícitamente al conectar, con el hash del user id
  que calcula `@jiku/nats-protocol`. Sin esto las respuestas no llegan.
- El `userId` con el que publica la api **DEBE** salir de la key del service user, **NO** de una
  variable de entorno: tiene que coincidir exactamente con el `sub` que el auth-callout lee del
  token para autorizar el subject.
- Toda respuesta **DEBE** tener el formato `{ status: 'success', data }` o
  `{ status: 'failure', errorCode, errorMessage }`. **NO SE DEBEN** inventar otros formatos.
- Los comandos de creación **DEBEN** devolver únicamente `{ id }`. Las ediciones y borrados, nada.
- Todo `errorCode` nuevo **DEBE** agregarse al mapa de `api/lib/utils/bus/protocol.ts` con su
  status HTTP. Un código sin mapeo cae en un 500 genérico.
- El timeout de la request es `NATS_REQUEST_TIMEOUT_MS` (default **5000 ms**); al expirar la api
  **DEBE** responder **503**.
- **NO SE DEBE** transportar datos estructurados dentro de `errorMessage`. El caso actual de
  `daily_limit_exceeded` —que la api recupera parseando el mensaje con un regex— es deuda
  explícita, no un patrón a imitar.
- Core **NO DEBE** publicar mensajes: solo responde el `Reply` de la request que recibe.

> **Dos reglas de ADR-002 tienen tratamiento especial en esta story:**
>
> 1. **"Los comandos de creación DEBEN devolver únicamente `{ id }`"** — `files.request-upload` es
>    una **excepción declarada y documentada** en `docs/apis/core.yaml`
>    (`ReplyWithUploadTicket`) y en la story. No hay alternativa: la URL prefirmada la genera `core`,
>    es de un solo uso y de vida corta, y la `api` no puede reconstruirla releyendo la base sin
>    duplicar la política de la clave y montar su propio firmador de escritura. **Es una excepción,
>    no un patrón nuevo.**
> 2. **"Todo `errorCode` nuevo DEBE agregarse al mapa de `api/lib/utils/bus/protocol.ts`"** — el
>    mapeo a HTTP de los cinco códigos nuevos **NO es de esta story**: va en **S-004/S-005**, cuando
>    la `api` los consume. Esta story los agrega al **paquete** y ya están en `docs/apis/core.yaml`.
>
> **El timeout de 5 s es la razón de dos decisiones de diseño de esta story:** la firma es local (sin
> red) y el byte **no se verifica** con `headObject`.

#### ADR-003: La transacción es del despachador, nunca del comando

**Decisión:** **Invertir la propiedad de la transacción**: la abre y la cierra el **despachador**, no
el comando. El despachador abre la transacción, ejecuta el comando pasándole la transacción en su
contexto, y hace **commit si el reply es `success`**, **rollback en cualquier otro caso**.

Los comandos reciben la transacción pero **no tienen acceso a `commit` ni a `rollback`**.

**Implementation Rules (verbatim):**

- Un comando **DEBE** recibir la transacción por su contexto y usarla en todas sus operaciones de
  base de datos. **NO DEBE** abrir una transacción propia.
- Un comando **NO DEBE** llamar a `commit()` ni a `rollback()`. Si el código de un comando los
  invoca, está mal escrito.
- Un comando **DEBE** señalar el fallo devolviendo un `Reply` con `status: 'failure'` y su
  `errorCode`. **NO DEBE** lanzar una excepción para señalar un fallo de negocio esperado.
- El despachador **DEBE** hacer commit **solo** si el reply es `success`, y rollback en todos los
  demás casos, incluidas las excepciones inesperadas.
- El despachador **NO DEBE** lanzar nunca: todo error se traduce a un `Reply` de falla.
- Los tests de comandos **DEBEN** entrar por el despachador (helper `dispatch()`), no llamando a
  `execute()` directamente: es lo único que verifica el comportamiento transaccional, incluido el
  rollback.

**Código del despachador (`core/src/bus/dispatcher.ts`, ya existente):**
```ts
const transaction = await sequelize.transaction();
try {
  const reply = await command.execute(validated.value, {
    caller: callerFromSubject(subject),
    params,
    transaction,
  });

  if (reply.status === 'success') await transaction.commit();
  else await transaction.rollback();

  return reply;
} catch (error: any) {
  await transaction.rollback();
  logger.error(`[dispatch] ${name}: ${error.message}`);
  return failure(ErrorCode.INTERNAL_ERROR, 'Internal error');
}
```

> **Consecuencia directa para esta story:** si `files-request-upload` hace el `INSERT INTO files` y
> **después** falla la firma de S3, el `INSERT` se pierde solo. No hay que compensar nada. Por eso el
> orden interno del comando puede validar tarde sin riesgo — pero **no conviene**: las validaciones
> de política van antes del `INSERT` para que ni siquiera se consuma un id de la secuencia.
>
> **Y la advertencia más importante:** una escritura que se olvide `{ transaction: ctx.transaction }`
> **corre fuera de la transacción y sobrevive al rollback**. Es el error más fácil de cometer y el
> más difícil de ver en este codebase.

#### ADR-007: Identidad Zitadel + auth-callout (revisión por REQ-001)

**Lo que aporta a esta story:**

- El `user-id` del subject es el **`sub` del service user del SERVICIO que publica**, no el de la
  persona. La `api` usa **un único service user para todas sus personas**.
- La autorización del bus (auth-callout de Zitadel) es la **única** defensa: `core` no tiene segunda
  línea.
- **Revisión que introduce REQ-001, a registrar:** `files.{fileId}.request-download` recibe un
  `fileId`, así que **quien pueda publicar en el bus puede pedir la URL de cualquier archivo del
  catálogo**, salteando la autorización de la `api`. Es el mismo modelo de confianza que ADR-007 ya
  declara para toda la **escritura**, pero ahora cubre la **lectura**, y la superficie es el catálogo
  entero de archivos, no el de vínculos autorizables. Se evaluó un `attachmentId` opcional que `core`
  validara y **se descartó** por simetría con `request-upload`; queda como mitigación aditiva
  disponible.
- **`CORE_TRUSTED_PUBLISHER_ID` cubre un modo de fallo que ADR-007 registra sin mitigación para
  `ZITADEL_PROJECT_ID`.** Acá **sí** se puede cubrir: el arranque falla sin la variable.

#### ADR-013: Tests contra base real

Los tests de `core` corren contra un PostgreSQL de verdad, con el esquema real, y **entran por el
despachador**. Es lo único que verifica el comportamiento transaccional.

**Aplicado a esta story:** los tests de `files` van en `core/tests/commands/files.test.ts` y entran
por `dispatch('files.request-upload', {...})` / `dispatch('files.1234.request-download', {...})`.
**El doble es solo el de S3**, nunca el de la base.

#### Canal 1 — `files.request-upload`

- **Pattern del comando:** `files.request-upload` (2 segmentos)
- **Archivo:** `core/src/commands/files/files-request-upload.ts`
- **Message:** `FilesRequestUpload` · **Reply:** `ReplyWithUploadTicket`
- **`x-error-codes`:** `[invalid_fields, file_type_not_allowed, file_too_large, internal_error]`

**Payload (`FilesRequestUploadPayload`) — verbatim del contrato:**

```yaml
FilesRequestUploadPayload:
  type: object
  required: [uploader, fileName, mimeType, fileSize]
  properties:
    uploader:
      allOf:
        - $ref: '#/components/schemas/IdentityUserId'
      description: |
        Who uploads. For the api it is the end user authenticated by JWT.
        **An external publisher omits it: core resolves it from the subject's `caller`.** And
        if it sends one, it is **ignored**. See `x-resolve-actor`.
        It is optional on purpose: it is the lever of D-26.
    fileName:
      type: string
      maxLength: 255
      description: 'The original name. It is **not** the key — core builds the key.'
    mimeType:
      type: string
      maxLength: 100
      description: |
        Declared by the client. Validated against `file-allowed-mime-types`, **and the
        extension of `fileName` is validated against `file-allowed-extensions` as well**: a
        new type has to be added to both lists (RF-17, D-18).
    fileSize:
      type: integer
      minimum: 1
      description: 'Declared by the client. Validated against `file-max-size-bytes`.'
    checksum:
      type: [string, 'null']
      description: |
        Hexadecimal sha256 declared by the client. **NOBODY verifies it** (D-25), the same way
        nobody verifies `mimeType` or `fileSize` against the actual byte.
```

> **Tensión del contrato a resolver en la implementación, y está resuelta a propósito:**
> `uploader` figura en `required: [uploader, ...]` **pero su descripción dice que un publicador
> externo lo omite**. La resolución correcta —la que hacen coincidir la story (CA-9), el flujo
> (paso 4: *"Payload: `{ fileName, mimeType, fileSize }`. **No manda `uploader`**"*) y el contrato
> (*"It is optional on purpose"*)— es: **el esquema Joi lo declara `.optional()`**, porque el canal
> externo no lo manda. Lo que hace `resolveActor` con él es lo que decide su valor. Si el esquema lo
> exigiera, el canal del bus directo (RF-11) sería imposible y **CA-9 no se podría cumplir**.
>
> El `required` del YAML describe el **canal de la `api`**, que sí lo manda siempre. Dejá un
> comentario en el esquema Joi explicando exactamente esto, porque a primera vista parece que el
> código contradice al documento.

```yaml

      type: object
      required: [id, uploadUrl, expiresIn]
```

#### `resolveActor` — el bloque `x-resolve-actor` del contrato, verbatim

```
resolveActor(ctx, payload):
  if ctx.caller == CORE_TRUSTED_PUBLISHER_ID   (the api's service user, from config)
     -> the actor is payload.author / creator / editor / uploader
        (the api ALREADY authenticated that person against Zitadel by JWT)
  else
     -> the actor is ctx.caller
        (an external publisher has no person behind it: its identity IS the subject's,
         vouched by the auth-callout and unforgeable. Whatever it declares is IGNORED)
```

Y después, uniforme en los dos canales:
`if File.uploaded_by != resolveActor(ctx, payload) -> failure(file_not_owned)`
— **esa comparación es de S-003**, no de esta story. Acá `resolveActor` solo **produce** el valor que
va a `files.uploaded_by`.

**Del contrato, verbatim:**

- **`files.request-upload` and the six domain commands MUST use the same function.** If uploading and
  linking resolved identity differently, nobody could link what they uploaded.
- **No exception by role** (RF-13): core knows nothing about roles, so the rule is uniform by
  construction.
- **`CORE_TRUSTED_PUBLISHER_ID` is configuration, not a literal**, and **core MUST fail to start
  without it**: an empty default would send every `caller` down the external branch and break the web
  silently. The external branch should log at `warn`, since today it is the rare case.

**Los cinco a agregar (ya declarados en el enum de `docs/apis/core.yaml`):**

> Los cinco se agregan al paquete **en esta story** (CA-19 exige que el catálogo los tenga), aunque
> `FILE_NOT_OWNED` solo lo use S-003. Un código declarado y no usado no rompe nada; uno usado y no
> declarado obliga al literal a mano, que es la deuda que el catálogo ya arrastra tres veces.

**Deuda conocida del catálogo, para no imitarla:** `resolution_required`, `worked_time_not_found` y
`unworked_time_not_found` se emiten como **literal** en vez de la constante. **En `files` se usa
siempre la constante.**

**Mensajes de error:** el `errorMessage` **llega al usuario final** a través de la api. Para un
mensaje nuevo, **español**, y **sin datos internos** (ids de otras entidades, nombres de columna,
detalle de excepción). **No uses el mensaje como canal de datos estructurados.**

#### Validación (Joi)

```ts
// core/src/commands/validate.ts — ya existente
export function validateWith<T>(schema: joi.Schema, payload: unknown):
  { value: T } | { error: Reply<never> } {
  const result = schema.validate(payload, { convert: true, abortEarly: true });
  if (result.error) return { error: failure(ErrorCode.INVALID_FIELDS, result.error.message) };
  return { value: result.value as T };
}
```

- **`convert: true`** — Joi normaliza tipos. Un `fileSize` que llega como string queda como número.
- **`abortEarly: true`** — se responde el primer error.
- **`validate` NO toca la base.** Corre **antes** de abrir la transacción, así que un payload inválido
  no consume una conexión del pool. Todo lo que necesite una consulta va en `execute`.
- **Los defaults del contrato van en el esquema**, no en el `execute`: `disposition` con
  `.default('inline')`.
- **Campos desconocidos se rechazan por defecto** (`joi.object()` sin `.unknown()`), y eso se
  mantiene. Hay un test que lo cubre en `clients.test.ts:52`.
- **La interfaz `{Comando}Payload` se escribe a mano**, no se infiere del esquema. Es duplicación
  deliberada: la interfaz documenta el contrato, el esquema lo hace cumplir.

### Flow Context

> Los dos flujos son **nuevos** y los crea esta story en su plano de *permiso* / *firma*. Copiados
> con los pasos que le tocan a `core`.

#### Flujo `subida-de-archivos` — Paso 5 (el de `core`), verbatim

**Origen:** `core` (`src/commands/files/files-request-upload.ts`) · **Destino:** PostgreSQL + S3 (firma)

El despachador abre la transacción (ADR-003).

**1. Lee la política de `system_settings`** — `file-max-size-bytes`, `file-allowed-extensions`,
`file-allowed-mime-types`, `upload-url-ttl-seconds`. **Cada clave ausente cae a su default de
código** (RF-16, CA-7): el seed es conveniencia, el default es la garantía.

**2. Valida:**

| Regla | Código de error |
|---|---|
| Tamaño sobre `file-max-size-bytes` | `file_too_large` |
| Extensión fuera de `file-allowed-extensions` | `file_type_not_allowed` |
| MIME fuera de `file-allowed-mime-types` | `file_type_not_allowed` |

**Las dos listas, no una** (RF-17, D-18): un `.exe` renombrado a `.pdf` se rechaza porque el MIME
declarado no coincide. Lo que se valida es **lo declarado**, y eso nunca fue una garantía sobre el
byte (D-25).

**3. Resuelve el actor:**
```
resolveActor(ctx, payload):
  si ctx.caller == CORE_TRUSTED_PUBLISHER_ID   -> el actor es payload.uploader
  si no                                        -> el actor es ctx.caller
```
Es **la misma función** que usan los seis comandos de dominio al vincular (S-003).

**4. Construye la clave** — **quien sube no la elige** (D-08):
```
{STORAGE_S3_KEY_PREFIX}/f/{uuid}{ext}
```
Sin `entityType` ni `entityId` (D-02). El namespace `/f/` separa lo nuevo del legado.

**Operación de BD:**
- **Tabla:** `files` · **Operación:** INSERT
- **Campos:** `file_name`, `file_size`, `mime_type`, `storage_key`, `storage_bucket`,
  `storage_region`, `checksum`, `byte_status` (`'pending'`), `uploaded_by` (el actor resuelto),
  `retention_status` (`'active'`)

**5. Firma `PutObject`** con `expiresIn` = `upload-url-ttl-seconds`.

> **Es una llamada de firma local, sin red.** El SDK firma con las credenciales sin contactar el
> bucket, así que no arriesga el timeout de 5 s de ADR-002. Es la misma razón por la que **no se
> verifica que el byte llegue** con un `headObject` (D-13).

**Reply:** `{ status: 'success', data: { id, uploadUrl, expiresIn } }` → **commit**

**Manejo de errores del flujo (fila de `core`):**

| Error | Código | Comportamiento |
|---|---|---|
| Extensión fuera de la allowlist | `file_type_not_allowed` | Rollback del comando. **No queda fila de `files`** |
| MIME fuera de la allowlist, **aunque la extensión esté** | `file_type_not_allowed` | Idem |
| Supera `file-max-size-bytes` | `file_too_large` | Idem |
| Forma inválida del payload | `invalid_fields` | Joi corta **antes** de la transacción |
| Falla de la firma o de la base | `internal_error` | Rollback del despachador |

**Lo que NO pasa en esta story:** los pasos 1, 2, 3, 6, 7, 8 y 9 del flujo son de `web`/`opus-web`
(S-006, S-007), de la `api` (S-004) y del vínculo (S-003). **`core` no los ve.**

#### Flujo `lectura-de-archivos` — Paso 5 (el de `core`), verbatim

**Origen:** `core` (`src/commands/files/files-request-download.ts`) · **Destino:** PostgreSQL + S3

El despachador abre la transacción (ADR-003) — **es de solo lectura, pero el despachador la abre
igual**.

1. Busca el `File` por el `id` del subject → **`file_not_found`** si no está o su `retention_status`
   no es `active`
2. Verifica `byte_status` → **`file_not_available`** si es `'pending'`. **Sin llamar a S3**
3. Lee `download-url-ttl-seconds` de `system_settings`, con su default de código
4. Firma `GetObject` sobre `storage_key`, con `response-content-disposition` según `disposition` y el
   `file_name` original. **Firma local, sin red**

**Reply (éxito):** `{ downloadUrl, expiresIn, fileName, mimeType, fileSize }`

Los tres campos de metadatos van en el reply **a propósito**: la `api` los necesita para armar los
headers de su respuesta sin volver a consultar la base, y el `HEAD` al preview que los frontends ya
usan para resolver nombre y tamaño sigue funcionando.

> **`core` no conoce el vínculo ni la entidad.** La autorización ya la hizo la `api`. **Lo que `core`
> NO valida en este comando es el permiso sobre la entidad**, porque `core` no conoce roles ni
> usuarios finales: `core` es dueño **del storage**, la `api` es dueña **de la autorización**.
>
> **`file_not_available` se resuelve por `byte_status`, sin tocar S3.** `core` responde con lo que ya
> tiene en la fila, sin una llamada de red dentro de la transacción del despachador — justo lo que
> ADR-002 y ADR-003 no toleran. El `NoSuchKey` queda como red de seguridad para el objeto borrado del
> bucket por fuera del producto.

**Manejo de errores del flujo (filas de `core`):**

| Condición | Reply de core | HTTP destino |
|---|---|---|
| Archivo borrado (`retention_status` no `active`) | `file_not_found` | 404 |
| **`byte_status: 'pending'` — el byte nunca llegó** | `file_not_available` | **404** con mensaje entendible |
| Objeto borrado del bucket por fuera del producto | *(el 302 lleva a un `NoSuchKey` de S3)* | 403/404 de S3 — caso residual |

**Por qué la lectura NO distingue archivos viejos de nuevos** (nota del flujo, importante para no
introducir una rama que no debe existir):

| Origen | `storage_key` |
|---|---|
| Migrado | `{prefix}/{entityType}/{entityId ?? 'draft'}/{uuid}{ext}` |
| Nuevo (D-02) | `{prefix}/f/{uuid}{ext}` |

**Y nada lee esa forma.** Ningún código parsea la clave: `core` la pasa **opaca** al firmador de S3, y
es el único que la toca. **No hay rama, ni `if`, ni fallback.** El `/f/` no está para distinguirlos al
leer: está para que el backfill **no pueda colisionar** con una clave existente.

**Referencia de implementación — `api/lib/utils/storage-service.ts`, ya existente.** Es el patrón que
`core` replica **acotado a lo que necesita**. Fragmentos relevantes:

```ts
// api/lib/utils/storage-service.ts
export const STORAGE_KEY_PREFIX = process.env.STORAGE_S3_KEY_PREFIX || 'grava-gestion';

constructor() {
  const endpoint = process.env.STORAGE_S3_ENDPOINT;
  const accessKeyId = process.env.STORAGE_S3_CREDENTIALS_ACCESSKEY;
  const secretAccessKey = process.env.STORAGE_S3_CREDENTIALS_SECRETKEY;
  const bucket = process.env.STORAGE_S3_BUCKETNAME;
  const region = process.env.STORAGE_S3_REGION;
  const forcePathStyle = process.env.STORAGE_S3_FORCEPATHSTYLE === 'true';

  // Sin defaults: el bucket y la región dependen del proveedor de cada instalación
  // (AWS S3, MinIO, Spaces, R2). Un default acá apuntaría a la infraestructura de
  // otro, y el error recién aparecería al subir el primer archivo.
  if (!endpoint || !accessKeyId || !secretAccessKey || !bucket || !region) {
    throw new Error('Missing S3 storage configuration: ...');
  }

  this.s3Client = new S3Client({
    endpoint, region: this.region,
    credentials: { accessKeyId, secretAccessKey },
    forcePathStyle,
  });
}

async getPresignedUrl(key: string, expiresIn: number = 60): Promise<string> {
  const command = new GetObjectCommand({ Bucket: this.bucket, Key: key });
  return getSignedUrl(this.s3Client, command, { expiresIn });
}
```

**Diferencias deliberadas del firmador de `core` respecto del `StorageService` de la `api`:**

| Aspecto | `api` (hoy) | `core` (esta story) |
|---|---|---|
| Superficie | 6 operaciones: upload, stream, delete, list, presign GET, head | **2 operaciones: firmar PUT y firmar GET.** Nada más |
| Red | Sí (`send()` real contra el bucket) | **Nunca.** Solo `getSignedUrl`, que firma local |
| `getSignedUrl` de PUT | No existe | **Nuevo**: `PutObjectCommand` |
| `response-content-disposition` | No lo usa | **Sí**, va firmado en la URL de GET |
| Instanciación | `export default new StorageService()` — **al importar el módulo** | Ver nota abajo |

> **Ojo con `export default new StorageService()`.** En la `api` el constructor lanza si falta una
> variable, y el módulo se instancia **al importarse**. Si `core` copiara ese patrón tal cual, el
> firmador se construiría al cargar el módulo del comando — y en el entorno de **tests**, que no tiene
> credenciales reales, **cualquier import de la cadena rompería la suite entera** aunque el test no
> toque S3. Instanciá el cliente de forma **perezosa** (al primer uso) o inyectable, para que el doble
> de tests pueda reemplazarlo. Es la decisión que hace testeable la story y merece un comentario que
> lo explique.

**Firma de `PutObject` — forma esperada:**
```ts
const command = new PutObjectCommand({ Bucket: bucket, Key: key, ContentType: mimeType });
const url = await getSignedUrl(client, command, { expiresIn });
```

**Firma de `GetObject` con disposition — forma esperada:**
```ts
const command = new GetObjectCommand({
  Bucket: bucket,
  Key: key,
  ResponseContentDisposition: `${disposition}; filename="${fileName}"`,
});
const url = await getSignedUrl(client, command, { expiresIn });
```

> **`ResponseContentDisposition` es lo que hace que el nombre original viaje FIRMADO en la URL** y S3
> lo devuelva sin que nadie proxee el byte ni arme el header (CA-13).
>
> **Escapá el `fileName`.** Un nombre con comillas dobles o con caracteres no-ASCII rompe el header
> `Content-Disposition` que S3 va a emitir. Es entrada del usuario que termina en un header HTTP: no
> la concatenes cruda.

### Code Conventions (reglas duras, resumidas para revisión)

**De `_base`:**
- `strict: true` no se apaga.
- **Un comando nuevo son tres pasos: el archivo, el registro en `commands/index.ts`, y sus tests. Los
  tres o ninguno.**
- El `pattern` de un comando tiene que coincidir con el subject de `docs/apis/core.yaml`. **Ante una
  discrepancia, manda el documento.**
- Un comando nunca abre ni cierra transacciones.
- **Un comando nunca lee `process.env`.** La configuración se lee al arrancar; las constantes de
  negocio son constantes de módulo.
- Nada de `console.log`.
- Imports relativos; no agregues alias al `tsconfig`.
- **No agregues una capa de repositorio ni de servicio: un comando es la unidad completa.**

**De `commands`:**
- **Toda escritura pasa `{ transaction: ctx.transaction }`. Sin excepción.**
- `validate` no toca la base: solo forma.
- Las creaciones devuelven solo `{ id }` — **con la excepción declarada de `files.request-upload`**.
- No agregues campos a la respuesta de un comando *(salvo la excepción documentada de esta story)*.

**De `env-config`:**
- **Una variable nueva se documenta en tres lugares:** la convención `env-config`, `core/README.md` y
  `deploy/.env.dist`.
- Una variable nueva que el servicio necesita para funcionar va también en el `environment` de
  `deploy/docker-compose.yml`. *(El compose es de la story de deploy; ver "Lo que NO es de esta
  story".)*
- **No pongas secretos en `deploy/.env.dist`**: va con el valor vacío o un placeholder.
- Los defaults van donde se lee la variable, con `||`. **No dupliques un default en dos archivos.**
- **No metas configuración de negocio en variables de entorno.** *(Por eso las 5 claves de archivos
  van en `system_settings` y no en `env`.)*

> **Nota sobre "sin validación al arrancar":** la convención `env-config` declara que `core` **no
> tiene asserts de arranque**, y lo señala como deuda: *"si se agregan asserts, los candidatos por
> impacto son `NATS_INSTANCE` y `ZITADEL_SERVICE_USER_KEY_B64`"*. **Esta story agrega el primer
> assert de arranque de `core`**, para `CORE_TRUSTED_PUBLISHER_ID` (CA-10). Es un cambio deliberado
> de la convención, justificado en la story y en el contrato, y **hay que actualizar
> `docs/architectures/core/conventions/env-config.md`** para que deje de decir que no hay ninguno.

**De `logging`:**
- Un solo logger, importado de `../logger`.
- Todo mensaje empieza con el prefijo del componente entre corchetes.
- **Un `failure` esperado no se loguea como `error`.** Una entidad que no existe es una respuesta
  normal del protocolo.
- **Nunca loguees tokens, keys ni credenciales.** *(Y para esta story: **nunca loguees la URL
  prefirmada** — lleva la firma y da acceso al contenido sin credencial.)*
- Niveles: `error` = algo falló y hay que mirarlo · `warn` = **entrada inválida que el servicio maneja
  bien** · `info` = hitos del ciclo de vida · `debug` = diagnóstico.

> **CA-11 usa `warn` a propósito**: la rama externa de `resolveActor` no es un error, es el caso raro,
> y su ausencia haría que un `CORE_TRUSTED_PUBLISHER_ID` mal configurado se manifieste **solo** como
> `file_not_owned` en S-003 — que parece un problema de permisos y no de configuración.

```ts
// core/tests/helpers/dispatch.ts — ya existente
export function dispatch<T = unknown>(
  command: string,
  payload: unknown,
  caller = 'api'
): Promise<Reply<T>> {
```

#### Anatomía de un comando (plantilla del codebase)

```ts
// core/src/commands/clients/clients-new.ts — el patrón a seguir
import joi from 'joi';
import { Client } from '@jiku/models';
import { Reply, success } from '@jiku/nats-protocol';
import { Command, CommandContext } from '../types';
import { validateWith } from '../validate';

export interface ClientsNewPayload { name: string; description?: string; }

const schema = joi.object({
  name: joi.string().required(),
  description: joi.string().optional().allow(''),
});

export const clientsNew: Command<ClientsNewPayload, { id: number }> = {
  pattern: 'clients.new',
  validate(payload: unknown) { return validateWith<ClientsNewPayload>(schema, payload); },
  async execute(payload, ctx: CommandContext): Promise<Reply<{ id: number }>> {
    const client = await Client.create({ ... }, { transaction: ctx.transaction });
    return success({ id: client.id });
  },
};

export default clientsNew;
```

### Task 3: `resolveActor` compartido y el arranque estricto de `CORE_TRUSTED_PUBLISHER_ID`

**Status:** Completed

#### Description

Implementar la resolución de identidad por canal, y hacer que **`core` falle al arrancar** si le
falta `CORE_TRUSTED_PUBLISHER_ID`.

Es la pieza más delicada de la story y **la que S-003 va a compartir**. Si subir y vincular
resolvieran la identidad distinto, **nadie podría vincular lo que subió** — por eso el contrato dice
que tiene que ser **la misma función**, no dos implementaciones equivalentes.

El arranque estricto no es defensivo de más: un default vacío haría que **todo** `caller` caiga en la
rama externa, `uploaded_by` pase a ser el service user de la `api`, y ningún usuario pueda vincular lo
que subió — con `file_not_owned` como único síntoma, que parece un problema de permisos y no de
configuración. **La web se rompería en silencio.**

Esta tarea introduce **el primer assert de arranque de `core`**, algo que la convención `env-config`

4. La rama externa emite **un** log de nivel `warn` con el prefijo de componente y el `caller` (CA-11)

6. `core` **falla al arrancar** si `CORE_TRUSTED_PUBLISHER_ID` está ausente (CA-10)

### Task 4: Cliente S3 de `core` — el firmador local de PUT y GET

**Status:** Completed

#### Description

Crear el cliente de S3 de `core`: **dos operaciones y nada más**, firmar un `PutObject` y firmar un
`GetObject`. Es la primera integración de `core` con un sistema externo.

**No hace red.** El SDK de S3 firma **localmente** con las credenciales, sin contactar el bucket, y
eso es lo que permite que la firma ocurra dentro de la transacción del despachador sin arriesgar el
timeout de 5 s de ADR-002 (CA-18). Es también la razón por la que **no se verifica el byte** con un
`headObject`: eso **sí** sería red.

Incluye la construcción de la clave de S3, que es política de `core` y **no del cliente que sube**
(D-08, CA-2).

#### Acceptance Criteria

1. Expone una operación para firmar un `PutObject` sobre una `key`, con `expiresIn` parametrizado, y
   devuelve la URL
2. Expone una operación para firmar un `GetObject` sobre una `key`, con `expiresIn` y con
   `ResponseContentDisposition` armado a partir de `disposition` y `fileName`
3. **Ninguna de las dos hace una llamada de red al bucket** (CA-18): no se invoca `s3Client.send()`
4. Construye la clave con la forma `{STORAGE_S3_KEY_PREFIX}/f/{uuid}{ext}`, sin `entityType` ni
   `entityId` (CA-2)
5. La extensión se deriva del `fileName` del payload y se normaliza a minúsculas
6. El `fileName` que va al `ResponseContentDisposition` está **escapado**: comillas dobles y
   caracteres no-ASCII no rompen el header (TS-35)
7. Expone el `bucket` y la `region` configurados, para poblar `files.storage_bucket` y
   `files.storage_region`
8. **No se instancia al importar el módulo**: el cliente se construye de forma perezosa o inyectable,
   para que la suite de tests pueda doblarlo sin credenciales reales
9. La configuración falta → error claro que nombra las variables faltantes, igual que en la `api`
10. Las variables `STORAGE_S3_*` están documentadas en `env-config`, `core/README.md` y
    `deploy/.env.dist`

#### Technical Details

**Architectural Context References:**
- **Integration Points → S3**: la tabla de variables, el fragmento de referencia de
  `api/lib/utils/storage-service.ts`, la tabla de diferencias deliberadas y la advertencia sobre
  `export default new StorageService()`.
- **Integration Points → firma de `PutObject` / `GetObject`**: las formas esperadas de llamada.
- **ADR-002 → el timeout de 5 s**: la razón de que la firma no haga red.
- **Flow Context → paso 5 de `subida-de-archivos`**, punto 4: la forma de la clave y por qué el `/f/`.
- **Flow Context → `lectura-de-archivos`, nota final**: **nadie parsea la clave**; `core` la pasa
  opaca al firmador. **No introduzcas ninguna rama por formato de clave.**
- **`conventions/env-config`**: las credenciales de S3 **sí** son `env` — son infraestructura, no
  negocio.

**Files to Create/Modify:**

- `docs/architectures/core/conventions/env-config.md` — las filas de las variables nuevas

**Implementation Notes:**
- **La instanciación perezosa es la decisión que hace testeable la story.** El `StorageService` de la
  `api` se instancia al importarse y lanza si falta configuración; copiar eso haría que **cualquier
  import de la cadena rompa la suite entera** de `core`, aunque el test no toque S3. Construilo al
  primer uso, o exponé un punto de inyección. **Dejá el comentario explicando por qué difiere de la
  `api`** — es justo el tipo de diferencia deliberada que la convención `_base` pide comentar.
- **El `uuid`:** Node 18+ trae `crypto.randomUUID()` en el módulo `crypto` del runtime. No agregues
  una dependencia para esto.
- **La extensión:** derivala del `fileName` con `path.extname()`, normalizada a minúsculas. Un

- **El `fileName` no participa de la clave** (solo su extensión). Es lo que hace que TS-6 sea seguro:

### Task 5: Comando `files.request-upload`

**Status:** Completed

#### Description

El primero de los dos comandos: valida la política de subida, resuelve el actor, construye la clave,
crea la fila de `files` con el byte **sin verificar**, y firma la URL de PUT.

Es lo que cierra la excepción 2 de ADR-001: la `api` deja de escribir la base al subir adjuntos.

**El byte no se verifica y es deliberado** (D-13): un `headObject` dentro de la transacción del
despachador sería una llamada de red que arriesgaría el timeout de 5 s de ADR-002. La falla aparece
**al descargar**, como `file_not_available`, en vez de como una fila corrupta.

#### Acceptance Criteria

1. `pattern: 'files.request-upload'`, coincidente con `docs/apis/core.yaml`
2. Esquema Joi que refleja `FilesRequestUploadPayload`: `fileName` (string, max 255, requerido),
   `mimeType` (string, max 100, requerido), `fileSize` (integer, min 1, requerido), `uploader`
   (string, **opcional** — ver nota), `checksum` (string o `null`, opcional)
3. Rechaza campos desconocidos con `invalid_fields` (TS-52)
4. Lee la política con el helper de la Tarea 2, **dentro de la transacción**
5. Orden de validación: **tamaño → extensión → MIME**, y cada uno con su código
6. `file_too_large` cuando `fileSize > maxSizeBytes`; el límite es **inclusivo** (TS-14)
7. `file_type_not_allowed` si la extensión no está en la allowlist
8. `file_type_not_allowed` si el MIME no está en la allowlist, **aunque la extensión sí esté** (CA-4)
9. Ninguna validación fallida deja fila en `files` (CA-3)
10. Resuelve el actor con `resolveActor` de la Tarea 3
11. `INSERT INTO files` con `byte_status: 'pending'`, `retention_status: 'active'`, `uploaded_by` = el
    actor resuelto, y `storage_bucket` / `storage_region` del firmador
12. Toda escritura pasa `{ transaction: ctx.transaction }`
13. Firma un `PutObject` con `expiresIn = upload-url-ttl-seconds`
14. Devuelve `success({ id, uploadUrl, expiresIn })` — **exactamente esas tres claves**
15. Registrado en `src/commands/index.ts`
16. El archivo exporta el comando **nombrado y como `default`**

**Implementation Notes:**
- **El `uploader` va `.optional()` en Joi**, no `.required()`, con un comentario que explique por qué
  el YAML dice `required` y el esquema no: el `required` describe el canal de la `api`; el canal
  externo (RF-11, CA-9) **lo omite a propósito**, y exigirlo lo haría imposible. Sin ese comentario,

### Task 6: Comando `files.{fileId}.request-download`

## Riesgos y puntos de atención de esta implementación

1. **La escritura sin `{ transaction: ctx.transaction }`.** Es el error más fácil de cometer en este
   codebase y el más difícil de ver: el test pasa, y la inconsistencia aparece cuando otra validación
   falla más adelante. Revisá cada operación de Sequelize del módulo.
2. **El firmador instanciado al importar.** Si se copia el patrón de la `api`, la suite entera de
   `core` deja de arrancar sin credenciales de S3. Ver Tarea 4.
3. **`SystemSetting.value` en `STRING(255)`.** Sin el cambio de la Tarea 1, la base de tests trunca la
   lista de MIME y TS-21 falla con un error que no señala la causa.
4. **`uploader` `.required()` en Joi.** Rompería CA-9 y el canal externo entero. El comentario que lo
   explica es parte del entregable, no un extra.
5. **`CORE_TRUSTED_PUBLISHER_ID` con `|| ''`.** Es exactamente el bug que CA-10 previene, y el patrón
   `|| default` es la convención en todo el resto del servicio. Hay que romperla acá a propósito.
6. **La cuenta de MIME (12 vs 13).** Verificá contra la migración `20260819_05` antes de escribir la
   constante de default; la documentación dice 13 y el código de la `api` tiene 12.
7. **Loguear la URL prefirmada.** Da acceso al contenido sin ninguna credencial. No va al log ni al
   `errorMessage`, ni siquiera bajo `LOG_COMMANDS`.
