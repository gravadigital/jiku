### Service Architecture — `web`

`type: frontend`, `language: nextjs`. Convenciones activas relevantes para esta story:
`styling`, `testing-unit`, `state-management`. Todas son **custom**
(`docs/architectures/web/conventions/`), no del catálogo.

**Estructura de un componente de UI** (convención `styling`, "Un módulo por componente"):

```
web/src/shared/components/ui/Table/
├── Table.tsx              ← el componente
├── Table.module.scss      ← su módulo de estilos
├── Table.test.tsx         ← su test (convención testing-unit: junto al código)
└── index.ts               ← re-export nombrado
```

**Reglas de estilado que aplican a los ocho componentes:**

- Nombre del módulo = nombre del componente.
- **Clases en `camelCase`**, no `kebab-case`: CSS Modules las expone como propiedades de un objeto
  y `styles.tableHeader` es válido mientras `styles.table-header` no.
- El módulo empieza con `@use '@/styles' as *;` cuando necesita mixins. Sin eso los `@include` no
  resuelven. `next.config.js:17-24` agrega `styles/` a los `includePaths` de Sass.
- **Usar el token, nunca el hex literal.**
- Clases condicionales con `cn()`, **nunca** template strings: el patrón
  `` `${styles.a} ${cond && styles.b}` `` escribe el string `"false"` en el `class` cuando la
  condición no se cumple. Es un bug latente que existe en el código (`NavItem.tsx:48-51`,
  `NavSubItem.tsx:49-52`), no el patrón a seguir.
- El mixin `focus-ring` de `_mixins.scss` **NO SE USA**: emite el `outline` violeta viejo. El foco
  nuevo es `box-shadow: var(--focus-ring)` (verde agua al 22 %, 3 px).

#### `Pagination` — ya es agnóstica de la ruta (CA-1 está parcialmente satisfecha)

`web/src/shared/components/ui/Pagination/Pagination.tsx` **ya no hardcodea `/objectives`**. S-037
la reescribió con dos modos discriminados por unión de tipos:

```ts
type PaginationUrlProps = PaginationBaseProps & {
  readonly basePath: string;              // ← la ruta la manda quien lo usa
  readonly currentPage?: never;
  readonly onPageChange?: never;
};

type PaginationControlledProps = PaginationBaseProps & {
  readonly currentPage: number;
  readonly onPageChange: (page: number) => void;   // ← callback, no ruta interna
  readonly basePath?: never;
};
```

Ya tiene: `<nav aria-label="Paginación">`, `aria-current="page"` en la página actual,
`aria-label="Página anterior"` / `"Página siguiente"` en las flechas, ventana deslizante de 10
números (`getPageWindow.ts`, función pura con test propio) y **26 test scenarios** en
`Pagination.test.tsx`, incluido un grep de control que verifica que `/objectives` no vuelva.

**Lo que le falta contra el spec `Pagination` v1.0.0:**

| Regla del spec | Estado hoy |
|---|---|
| Selector de cantidad por página («5 por página ⌄», `Select` variant `inline`) | **No existe.** No hay `pageSize`, `pageSizeOptions` ni `onPageSizeChange` |
| «NO SE DEBE ocultar la paginación cuando hay una sola página: se muestra deshabilitada» | **Lo viola**: `if (totalItems === 0) return null;` y con una sola página se dibuja un solo número |
| El cambio de página se anuncia en región `aria-live` | **No existe** |
| Los extremos `disabled` de verdad | Cumple |
| Tokens del DS (`--pagination-*`, radio 8 px, borde `#DFE1E7`) | **No cumple**: usa `--color-general-background`, `--color-button`, `border-radius: 5px` y `@include focus-ring` (el violeta viejo) |
| API del spec: `page`, `pageSize`, `totalPages` | **Difiere**: el componente recibe `totalItems` + `limit` y deriva `totalPages` |

> **Decisión de alcance, y hay que respetarla:** el modo URL (`basePath`) y `totalItems`/`limit`
> **se conservan**. Hay consumidores en pantalla que los usan y **esta story no toca pantallas**.
> Lo que se agrega es el selector de cantidad, la región viva y la capa visual del DS. Cambiar la
> API a `page`/`totalPages` rompería los usos existentes y es trabajo de S-056–S-058.

#### `Stepper` — hoy es código inline dentro de `RequirementStatusCard`

No existe un componente `Stepper`. El stepper vive en
`web/src/features/requirements/components/RequirementStatusCard/RequirementStatusCard.tsx`, y su
comportamiento —el que S-050 dejó y que **no debe cambiar**— es:

```ts
const INLINE_STEPS: StepDefinition[] = [
  { label: 'Análisis', value: 'analisis' },
  { label: 'Planificación', value: 'planificacion' },
  { label: 'En cola', value: 'en_cola' },
  { label: 'Desarrollo', value: 'desarrollo' },
  { label: 'Revisión', value: 'revision' },
];

// El stepper muestra siempre los cinco pasos de trabajo, para cualquier tipo: es
// cómo el equipo lee dónde está el requisito. Desde REQ-012 ya no recorta a dónde se
// puede ir — eso lo decide la pill de estado, no el stepper.
const visibleSteps = INLINE_STEPS;
```

Reglas de render que hoy están en `renderStep` y que el componente nuevo tiene que poder expresar:

- `isCurrent`: `state === step.value` → `aria-current="step"` en el nodo.
- `isDone`: `stepIdx < currentIdx`, **o** `reachedTerminal` (`resuelto`/`cancelado` marcan los
  cinco pasos como superados, porque para llegar ahí se recorrió todo el flujo).
- `skippedOnCancel`: si terminó `cancelado` y un paso "superado" no tiene actividad real en el
  historial (`hasStepActivity`), se dibuja **`×` en vez de `✓`**, para no sugerir que se completó.
- Contenido del nodo: `×` si `skippedOnCancel`, `✓` si `isDone`, el **número** (`stepIdx + 1`) si
  no.
- `data-testid="step-dot"` en el nodo — hay tests de `RequirementDetail` y de
  `RequirementStatusCard` que lo consultan.

> **Alcance de esta story sobre el stepper (CA-2):** se **crea** el componente `Stepper` con la API
> del spec y se lo cubre con test propio. **`RequirementStatusCard` no se toca**: la sustitución del
> stepper inline por el componente es de S-057 (migración de las pantallas de requisitos). Lo que
> CA-2 exige verificar acá es que el componente nuevo **pueda expresar** los cinco estados de nodo
> de arriba sin alterar conducta — si algo del spec obligara a cambiar comportamiento, se reporta
> antes de continuar, no se "corrige" silenciosamente.

#### `Table` v1.0.0 — lo normativo

**Tres variants, y la elección no es estética:**

| Variant | Cabecera | Uso |
|---|---|---|
| `light` | **Niebla `#F6F6F9`** con borde claro, texto secundario | **Listados navegables** — requisitos |
| `dense` | **Azul oscuro `#0B1934`**, texto niebla | **Tablas densas de seguimiento** — tareas |
| `matrix` | Niebla, con agrupadores en versalitas | **Cruce de dos dimensiones** — matriz de asignación |

- **Un solo alto de fila: 48 px** en las tres variants. La `matrix` puede comprimir el ancho de
  columna, **nunca el alto**.
- Padding de celda: `space.2` (8 px) vertical, `space.4` (16 px) horizontal. Borde 1 px `#DFE1E7`
  entre filas. Interlínea de datos 1,5.
- **States:** `default` (`bg.surface`), `row-hover` (`bg.surface.sunken`), `row-focus`
  (`focus.ring`), `sorted` (indicador en la cabecera), `overdue` (`state.urgent.text` + texto
  «vencido hace 1 día»).
- **Accesibilidad (normativa):** `<table>` real con `<th scope="col">`; la `matrix` **DEBE** llevar
  además `<th scope="row">` («sin eso, una celda de "0 %" no dice de quién ni de qué proyecto»); el
  orden de columna **DEBE** exponerse con `aria-sort`; el estado va en badge con **punto + texto**;
  una tabla con scroll horizontal debe poder desplazarse con teclado y anunciar su región.
- **Don't:** NO teñir la fila completa con un color de sistema; NO usar `<div>` en lugar de
  `<table>`; NO mezclar las dos cabeceras en una misma vista.
- **Contenido:** cabeceras en sustantivo corto sentence case; celda sin dato **«N/D» o «0 h», nunca
  vacía**; sufijo «+N» para responsables extra en `text.secondary`.
- **API:** `variant`, `columns: { key, label, sortable?, scope? }[]`, `rows: object[]`,
  `sort: { key, direction }`, `onSortChange`, `emptyState: ReactNode`.

#### `Stepper` v1.1.0 — lo normativo

- **Cinco pasos fijos**, para cualquier tipo de requisito: Análisis · Planificación · En cola ·
  Desarrollo · Revisión. **Resuelto y Cancelado NO son nodos**: son estados de cierre.
- **«En cola» se muestra también para incidencias.** El stepper **no recorta por tipo**.
- **Reparto de responsabilidades** (la sección central del spec):

  | Control | Qué hace | Alcance |
  |---|---|---|
  | **Stepper** | Leer **dónde está** el requisito | Los **cinco** pasos de trabajo |
  | **Badge editable** en el `ViewHeader` | Decidir **a dónde va** | Los **siete** estados, sin recorte |
  | **Card de resolución** | Cerrar y reabrir | Resolver · Cancelar · Reabrir |

- **Tres estados de nodo:** *Recorrido* = **verde agua pleno** + `✓` en azul oscuro
  (`--stepper-active-bg`); *Actual* = **anillo** de 3 px (mismo grosor que `focus.ring` pero **no es
  foco, es estado**); *Pendiente* = borde claro + número, texto `text.disabled`.
- Es el único lugar del sistema donde el verde agua se usa **pleno como fondo**, y funciona porque
  el `✓` va en azul oscuro (9.8:1).
- **Accesibilidad (normativa):** **DEBE** ser una lista ordenada `<ol>`; cada nodo **DEBE** anunciar
  su estado en texto («Análisis, completada» / «Desarrollo, etapa actual» / «Revisión, pendiente») —
  **el `✓` y el anillo son visuales y no alcanzan**; la etapa actual **DEBE** llevar
  `aria-current="step"`; **el stepper informativo NO DEBE ser focusable** (si `interactive` es
  `false`, que es el default, no entra en el orden de foco y se expone como lista, no como grupo de
  controles); el estado **NO se comunica sólo con color** (`✓` / número / anillo distinguen por
  forma).
- **Don't:** NO usar color de sistema en los nodos; NO rellenar el nodo actual (el anillo es lo que
  lo distingue); **NO convertir el stepper en el selector de estado**; NO agregar Resuelto y
  Cancelado como nodos; NO recortar los cinco pasos por tipo.
- **API:** `steps: { key, label }[]`, `currentKey: string`, `interactive?: boolean` (default
  `false`), `onStepChange?: (key) => void`.

#### `Avatar` v1.0.0 — lo normativo

- **Variants:** `person` (**iniciales** en niebla sobre azul oscuro) y `app` (**símbolo de Jiku** al
  **62 % del diámetro** — regla de marca, no de componente). *El símbolo nunca se usa para una
  persona y las iniciales nunca para la app.*
- **Sizes:** `sm` 24 px (dentro de fila de tabla) · `md` 32 px (cabecera, pie del sidebar).
- **Radio 999 px.** Fondo `avatar.bg` → **azul oscuro `#0B1934`**; texto `avatar.text` → **niebla
  `#F6F6F9`**, dos iniciales en mayúscula. Gap avatar–nombre `space.2` (8 px).
- **El fondo NO varía por persona.** No hay colores asignados por usuario.
- **Accesibilidad (normativa):** es **decorativo cuando el nombre está visible al lado**
  (`aria-hidden="true"`, para que el lector no diga «AV, Andrés Vandoni»); **sin** el nombre al
  lado **DEBE** llevar el nombre completo como `aria-label` — las iniciales solas no identifican a
  nadie; el sufijo «+N» **DEBE** ser accesible: «y 1 responsable más», no «+1». Contraste 14.6:1.
- **Estado único, no interactivo por sí mismo:** si abre un menú, el control es el botón que lo
  contiene, no el avatar.
- **Don't:** NO asignar color por persona; NO usar el símbolo como avatar de persona; NO recolorear
  ni rotar el símbolo; **NO mostrar una sola inicial**.
- **API:** `variant: "person" | "app"`, `name: string`, `size: "sm" | "md"`,
  `nameVisible?: boolean`.

#### `SidebarNav` v1.0.0 — lo normativo

- **Una sola variant: sidebar de 300 px fijo. No hay estado colapsado ni drawer en esta versión.**
- **Medidas:** ancho 300 px · alto de ítem **48 px** · sangrado de subítem **44 px** · icono de
  ítem **22 px** · icono de subítem **19 px** · firma **26 px** de alto.
- **States:** `default` (icono grafito `#626C78`) · `hover` (`bg.surface.sunken`) · `focus`
  (`focus.ring`) · **`active` = tarjeta blanca + barra verde agua de 3 px + `elevation.raised`,
  icono en `#12897A`** · `subitem-active` = tinte verde agua al 8 %.
- El activo se marca con **tres señales a la vez** —superficie, barra y color de icono— y por eso
  no depende del color.
- **Accesibilidad (normativa):** `<nav>` con `aria-label` («Navegación principal»); la lista de
  secciones **DEBE** ser `<ul>`/`<li>` real; el ítem activo **DEBE** llevar `aria-current="page"`
  (la barra verde agua es visual y no llega al lector); los subítems **DEBEN** anidarse en una lista
  dentro de su ítem padre; `Tab` recorre en orden visual y **NO SE DEBE atrapar el foco**; el icono
  del ítem es decorativo (`aria-hidden`) porque el label está visible; la firma lleva texto
  alternativo «Jiku».
- **Don't:** NO usar verde agua como fondo del ítem activo (es tarjeta blanca con barra); **NO teñir
  el icono activo con el verde agua de marca sobre fondo claro (1.9:1)** — va `#12897A`; NO repetir
  la firma en el pie.
- **Contenido:** labels con el término de dominio en plural («Actores», «Proyectos», «Requisitos»,
  «Tareas»), sentence case.
- **API:** `items: { key, label, icon, href, children? }[]`, `activeKey: string`,
  `user: { name, initials }`, `onLogout: () => void`.

#### `ViewHeader` v1.1.0 — lo normativo

- **Variants:** `list` (cabecera de listado) · `breadcrumb` (vista con nivel padre) · `detail`
  (detalle de entidad, con badges editables — el de estado ofrece los **siete**).
- **Título:** `text.view-title` = **Sora 30/700**, tracking −0,035 em, interlínea 1,05–1,15.
- **Breadcrumb:** el nivel padre en `text.secondary` («Tareas /»); **el nivel actual en caja baja**
  y `text.primary` («crear»). El nivel actual en caja baja es deliberado.
- **Spacing:** gap breadcrumb–título `space.1` (4 px) · gap título–badges `space.2` (8 px) · acción
  principal alineada a la derecha, al centro vertical del título · divisor inferior 1 px `#DFE1E7`.
- **Accesibilidad (normativa):** el título **DEBE** ser el **`<h1>`** de la vista; el breadcrumb
  **DEBE** ser `<nav aria-label="Ruta">` con una lista, y el nivel actual **DEBE** llevar
  `aria-current="page"`; **NO SE DEBE** usar un `<div>` de 30 px en lugar de un encabezado real.
- **Don't:** NO usar Sora en otros títulos (los de card van en Gabarito 16/700); **NO poner dos
  botones primarios** en la cabecera; NO repetir el nombre de la sección en el título si ya está en
  el breadcrumb.
- **API:** `variant`, `title: string`, `parent: { label, href }`, `badges: Badge props[]` (sólo
  `detail`), `action: Button props`.

#### `Tabs` v1.0.0 — lo normativo

- **Una sola variant:** tabs horizontales **con contador**.
- **`empty`: un tab con contador 0 NO se oculta ni se deshabilita.** «Backlog 0» informa que no hay
  nada en backlog, y eso es información. Ocultarlo obligaría al usuario a recordar qué estados
  existen.
- **States:** `default` (`tab.text`) · `hover` · `focus` (`focus.ring`) · `active`
  (`tab.text.active` + indicador verde agua de 2 px).
- **Spacing:** padding `space.2` / `space.4` · gap label–contador `space.1` · indicador 2 px de alto
  con el ancho del tab · contador en pill de radio 999 px sobre `bg.tint.neutral`.
- **Accesibilidad (normativa):** **DEBE** implementar el patrón ARIA de tabs — `role="tablist"`,
  `role="tab"` con `aria-selected`, `role="tabpanel"` con `aria-labelledby`; **teclado: flechas
  ← → mueven entre tabs, `Home`/`End` van a los extremos, y `Tab` entra y sale del tablist**, no
  recorre los tabs uno por uno; el contador **DEBE** formar parte del nombre accesible del tab («En
  curso, 3 elementos»); el tab activo **no se distingue sólo por la barra**, también por el peso del
  texto.
- **Don't:** NO ocultar un tab con 0 elementos; NO usar tabs para navegar entre secciones del
  producto; NO poner más tabs de los que caben sin scroll horizontal.
- **API:** `tabs: { key, label, count }[]`, `activeKey: string`, `onChange: (key) => void`.

#### `Pagination` v1.0.0 — lo normativo

- **Anatomía:** `‹` anterior · indicador de página · `›` siguiente · **selector de cantidad** («5
  por página ⌄», un `Select` variant `inline`).
- **States:** `default` · `hover` · `focus` (`focus.ring`) · **`current` = fondo verde agua + texto
  azul oscuro** (`--pagination-active-*`) · `disabled` (`‹` en la primera, `›` en la última) — «los
  controles en el extremo **DEBEN** estar `disabled` de verdad, no sólo atenuados».
- **Sizes:** la zona clickeable de cada control **nunca baja de 32 px**. Radio 8 px, gap `space.1`
  (4 px), borde 1 px `#DFE1E7`, separación con el selector de cantidad `space.4` (16 px).
- **Accesibilidad (normativa):** `<nav aria-label="Paginación">`; la página actual con
  `aria-current="page"`; `‹` y `›` con nombre accesible («Página anterior», «Página siguiente») —
  **el glifo no es un nombre**; **el cambio de página DEBE anunciarse en una región `aria-live`**, o
  mover el foco al inicio del listado.
- **Contenido:** cantidad **con unidad explícita**: «5 por página», no «5».
- **Don't:** **NO hardcodear una ruta dentro del componente** («es lo que rompió al anterior»); NO
  reimplementar la paginación inline en una pantalla; **NO ocultar la paginación cuando hay una sola
  página: se muestra deshabilitada**, para que el pie no cambie de alto.
- **API del spec:** `page`, `pageSize`, `pageSizeOptions` (default `[5, 10, 25]`), `totalPages`,
  `onPageChange` (**callback, no ruta interna**), `onPageSizeChange`. *«No hay prop de ruta. El
  componente notifica y quien lo usa decide qué hacer con el cambio.»*

#### `WeekNav` v1.0.0 — lo normativo

- **Anatomía:** «‹ Anterior» · rango visible · **«Esta semana»** · «Siguiente ›».
- **`current`: «Esta semana» NO se oculta cuando ya estás en la semana actual: se marca.** Ocultarlo
  haría que el control aparezca y desaparezca según dónde estés.
- **Sizes:** zona clickeable no menor a **32 px** de alto. Radio 999 px en «Esta semana», 8 px en
  las flechas. Gap `space.2` (8 px).
- **Accesibilidad (normativa):** `<nav aria-label="Navegación de semana">`; **el cambio de semana
  DEBE anunciarse en una región `aria-live`** («el rango cambia y con él todo el contenido»); el
  rango **DEBE** ser texto legible **con mes y año** — no «24/08–28/08» a secas; si las flechas se
  reducen a sólo glifo, **DEBEN** llevar `aria-label`.
- **Contenido:** «Semana del 24 al 28 de agosto 2026» · atajo nombrado **«Esta semana», no «Hoy»**
  (el recorte es semanal) · flechas con palabra.
- **API:** `weekStart: Date`, `onChange: (weekStart) => void`, `isCurrentWeek: boolean`.
