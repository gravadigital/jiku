### Fuera de alcance (declarado, para no improvisarlo)

- **Distinguir "no existe" de "sin permiso".** La api los iguala a propósito (`api.yaml:2989-2991`) y
  DD-7 los clasifica igual. Un solo estado, un solo texto.
- **Unificar "Volver al listado" del error de sistema** con "Volver al tablero": la UX lo descarta
  (*"no se unificó el texto ahí para no tocar un estado que el REQ no cambia"*).
- **Cambiar el layout mobile del modal en los estados de excepción.** Hoy loading y error del modal se
  renderizan con `styles.overlay`/`styles.container` también en mobile; el estado nuevo ocupa el mismo
  contenedor. O-01 no tiene screen.md ni wireframe (Revisión UX de REQ-020).
- **`not-found.tsx` de Next** y cualquier otra pantalla de la superficie.
- **El 401**: lo sigue resolviendo el interceptor de `lib/axios.ts` (redirige a `/login`).

### Convenciones activas que aplican (extracto)

**error-handling (custom de opus-web):**

- Todo error de red sale del interceptor como `ApiError` plano (`src/lib/axios.ts`):
  ```ts
  export interface ApiError { code: string; message: string; status: number; }
  // errorInterceptor:
  code: error.response?.data?.code ?? 'unknown_error',
  message: error.response?.data?.message ?? 'Error desconocido',
  status: error.response?.status ?? 500,
  ```
- *"Un `catch` nunca recibe un `AxiosError`. Recibe un `ApiError` plano."* → tipar con
  `error as unknown as ApiError`.
- Un fallo de red sin respuesta da `{ code: 'unknown_error', message: 'Error desconocido', status: 500 }`
  → `system`.
- *"El 401 no llega al componente como un error a mostrar"*: el interceptor redirige a `/login`.
- El proxy catch-all `/api/opus/[...path]` reenvía `status` y cuerpo de la api tal cual: el 403/404 y
  su `code` llegan al interceptor.

**testing-unit (custom de opus-web):**

- **Regla para código nuevo:** tests junto al código (`Componente.test.tsx` al lado).
- **Mockear los hooks de datos, no la red** (`vi.mock('@/features/requirements/hooks/useRequirement')`
  o `vi.mock('../../hooks/useRequirement')`).
- **Los hooks se testean con `renderHook` dentro de un `QueryClientProvider` propio**, un `QueryClient`
  nuevo por test (patrón de `src/features/docs/hooks/useDocument.test.tsx`, que mockea el servicio con
  `vi.mock('../services/docsApi')`).
- **Mockear `useIsMobile`** (`vi.mock('@/shared/hooks', () => ({ useIsMobile: () => … }))`): *"un
  componente que ramifica por `useIsMobile` necesita un test por rama"*.
- Aserciones por rol y texto (`getByRole`, `getByText`); clases solo para variantes visuales.
- `next/navigation` se mockea como en `BoardHeader.test.tsx`:
  `vi.mock('next/navigation', () => ({ useRouter: () => ({ push: mockPush, replace: mockReplace }), useSearchParams: () => ({ get: () => 'list' }), useParams: () => (...) }))`.

**styling (custom de opus-web):** CSS Modules + custom properties; cambio de **acomodo** por viewport
con `@include mobile` en CSS, no con `useIsMobile` (que decide árbol, `grid.md`: *"El corte de 768 es de
árbol de componentes, no de CSS"* — acá no hay cambio de árbol).

### API Context

**Sin cambios de API.** opus-web consume los status y `code` que la api ya devuelve.

`GET /opus/requirements/{reqid}` (de `docs/apis/api.yaml:2982-3018`, extracto verbatim):

```yaml
/opus/requirements/{reqid}:
  get:
    tags: [opus]
    summary: Detalle de un requisito en el portal
    description: |
      **Responde 404 `requirement_not_found` si el requisito es `internal`**, para todo rol.
      El 404 es idéntico al de un id inexistente, a propósito: distinguirlos confirmaría que
      el requisito existe (mismo criterio que el recorte externo de `core`).
    x-roles: [user, external-user]
    responses:
      '200': { RequirementWithRelations }
      '401': { $ref: '#/components/responses/Unauthorized' }
      '403': { $ref: '#/components/responses/AccessDenied' }
      '404': { $ref: '#/components/responses/RequirementNotFound' }
      '500': { $ref: '#/components/responses/InternalError' }
```

Cuerpos (verbatim de `components/responses`):

```yaml
AccessDenied:        # 403 — Autenticado, pero el rol o el permiso de proyecto no alcanzan
  example: { code: access_denied, message: Access denied }
RequirementNotFound: # 404 — El requisito no existe
  example: { code: requirement_not_found, message: Requirement not found }
InternalError:       # 500 — Error inesperado
  example: { code: internal_error, message: Internal error }
```

Desde el navegador se llama `GET /api/opus/requirements/{id}` (route handler same-origin que agrega el
token), vía `requirementsApi.getById(id: number): Promise<RequirementDetail>`.

**Regla de clasificación (DD-7, verbatim de la story):** `status` 403 o 404, o `code`
`requirement_not_found` / `access_denied` → `not_found`; cualquier otro (5xx, red: el interceptor deja
`status: 500`, `code: 'unknown_error'`) → `system`.

**Regla de reintento (DD-9, verbatim):**
`retry: (count, error) => classifyRequirementError(error) === 'system' && count < 1`.

### Flow Context

La story no referencia flujos de sistema ("Flujos Afectados: Ninguno"). Flujo de interacción de la
story (verbatim):

1. **[opus-web / `useRequirement`]** `GET /api/opus/requirements/{id}` → 404 `requirement_not_found` o
   403 `access_denied`.
2. **[opus-web]** `classifyRequirementError` → `not_found`; sin reintento de TanStack → 
   `RequirementUnavailable` con "Volver al tablero", sin "Reintentar".

Manejo de errores: red o 5xx → `system` → un reintento automático → "Error al cargar el requisito" +
"Reintentar".

## Hallazgos y decisiones de este plan

- **Cabecera mínima como prop de `BoardHeader`.** La story pide "cabecera mínima" sin decir con qué
  componente; el screen.md dice que `encabezado-detalle` *"es el mismo `BoardHeader`"* y que en este
  estado *"queda como cabecera mínima"*. Se agrega `minimal` en lugar de un header nuevo para conservar
  los 61 px, los estilos del breadcrumb y el botón "Requisitos" existente.
- **Query sin datos y id no numérico.** Ambos caen en "no disponible" (DD-8 lo pide para el primero; el
  segundo —`/requirements/abc`, query deshabilitada— hoy caía en "Requisito no encontrado", que este
  estado reemplaza). Fijado por TS-21 y TS-22.
- **`<h1>` también en el modal.** La accesibilidad del screen.md fija `<h1>` para la página; O-01 no
  tiene screen.md. Se usa el mismo componente sin prop de nivel, para no inventar una variante: en ese
  estado el modal no tiene otro encabezado.
- **Modal en mobile.** Los estados de excepción del modal ya usan el contenedor desktop también en
  mobile (comportamiento actual); no se agrega rama por `useIsMobile` (fuera de alcance, TS-32).
- **"Cerrar" en el error de sistema del modal.** DD-8 dice *"texto actual + Reintentar (`refetch`) +
  cerrar"* sin texto; se usa `"Cerrar"` (secondary). No está en ningún screen.md porque O-01 no tiene uno.
- **Catálogo de código reutilizable.** La story asigna `docs/reusable-code/opus-web/` al servicio
  `docs` (y el plan de S-092 · docs lo dejó explícitamente para esta story). Este plan no lo toca:
  `classifyRequirementError`, `RequirementUnavailable`, `BoardHeader.minimal` y el `retry` de
  `useRequirement` quedan para el plan de `docs`.
- **Gap de DS `empty-state`** — aceptado en la Revisión UX de REQ-020 ("Dejar anotado"); se implementa
  como componente de feature.
