# Story Plan: S-004 (api) - La `api` deja de escribir y de recibir el byte

## Status

**Status:** Completed

**Progress:** 6/6 tareas completadas

## Story Reference

- **Story:** [S-004](../stories/S-004.api-deja-de-escribir-y-recibir-el-byte.md)
- **Service:** `api`
- **Summary:** Los dos endpoints de subida de adjuntos (`POST /api/attachments` y
  `POST /api/opus/attachments`) pasan de multipart a JSON y publican `files.request-upload` en vez de
  escribir la base; `DELETE /api/attachments/{id}` pasa a publicar `attachments.{id}.delete`. Con eso
  desaparecen `multer`, `storageService` y `Attachment.create()` de la `api`, y se cierra la
  **excepción 2 de ADR-001**.

### Service Architecture

**No hay `src/`.** El código vive en `lib/`, y el dominio **no está en carpetas: está en el prefijo
del nombre del archivo de ruta**.

```
api/
├── app.ts                    Express, middleware global, montaje automático de rutas
├── bin/index.ts              entry point: assertAuthConfig → initializeDb → initialize → listen
├── config/public.ts          exenciones de autenticación
├── lib/
│   ├── routes/               61 archivos, uno por endpoint, + index.ts (barrel)
│   ├── models/index.ts       Sequelize de SOLO LECTURA
│   ├── interfaces/           augmentación de Express.Request (user, decodedTokenRoles, ...)
│   ├── logger.ts             Winston
│   └── utils/
│       ├── bus/              cliente NATS, sendCommand/runCommand, protocol.ts, download-ticket.ts
│       ├── middlewares/      7 compartidos: auth, roles, entidades del path, semana
│       └── *.ts              validate-body-fields, attachments-access, storage-service, ...
├── db-upgrade/migrations/    95+ migraciones (.js), corren al arrancar
└── tests/
    ├── routes/               un archivo por archivo de ruta
    ├── utils/                unitarios, sin base
    └── mocks/bus.ts          el FakeBus
```

**El montaje es automático.** `app.ts:35-37` itera los exports del barrel:

```ts
for (const key of Object.keys(routes)) {
  app.use('/api', routes[key as keyof typeof routes]);
}
```

Agregar/quitar un endpoint son **dos pasos**: el archivo en `lib/routes/` y su línea en
`lib/routes/index.ts`. **`app.ts` no se toca.** El prefijo `/api` lo pone el montaje: en el archivo
de ruta el path va **sin** él.

**Nombres:**

| Elemento | Convención | Ejemplo |
|---|---|---|
| Archivos | `kebab-case` | `attachments-post.ts` |
| Archivos de ruta | `{recurso}-{path}-{método}` | `attachments-delete.ts` |
| Exports del barrel | `PascalCase` | `AttachmentsPost` |
| Funciones y variables | `camelCase` | `requestUpload` |
| Constantes de módulo | `SCREAMING_SNAKE_CASE` | `MAX_FILE_SIZE` |
| Tipos e interfaces | `PascalCase`, sin prefijo `I` | `UploadTicket` |

**Imports: relativos.** No hay paths de `tsconfig` en el código fuente. Desde `lib/routes/` es
`../utils/...` y `../logger`. Los `_moduleAliases` de `package.json` (`@models`, `@logger`) aplican al
JavaScript **compilado**, no al TypeScript. Los paquetes del monorepo se importan por nombre.

**Comentarios: en español, y explican el POR QUÉ, no el qué.** Cuando toques algo con una razón no
obvia, dejala escrita — es la única documentación de la decisión que viaja con el código.

**Orden de la cadena de middlewares** (importa y es siempre el mismo):

1. **Rol** — `hasAnyRole([...])`
2. **Forma del input** — `validateBodyFields(schema)` / `validateQueryParams(schema)`
3. **Existencia de la entidad del path** — `validateProject` / `validateRequirement` / `validateObjective`
4. **Permiso sobre esa entidad** — `validateProjectPermissions`
5. **Reglas de negocio** — validadores locales del endpoint
6. **Handler**

**Manejo de errores: sin clases, sin `throw` en handlers, sin handler global que traduzca.** Cada
punto responde `res.status(n).json({ code, message })` y **corta**. Un middleware que responde **no**
llama a `next()`.

| Status | Código | Cuándo |
|---|---|---|
| 400 | `invalid_fields` | falló Joi. Mensaje: `Invalid field - {primer error}` |
| 401 | `unauthorized` / `user_not_found` | autenticación |
| 403 | `access_denied` | rol o permiso de proyecto insuficiente |
| 404 | `{entidad}_not_found`, `not_found` | la entidad del path no existe |
| 500 | `internal_error` | cualquier error inesperado |
| 503 | `service_unavailable` | el bus no responde |

`message` **es texto de interfaz** (los fronts lo muestran tal cual). Mensajes nuevos, **en español**.
Nunca devuelvas el detalle de un error interno: va al log con endpoint y función.

**Logging:** `logger` de Winston, **nunca `console`**. Todo error inesperado se loguea con contexto
antes de responder.

### Relevant ADRs

#### ADR-001: Separación lectura/escritura por credenciales de base de datos

**Decisión:** La `api` conecta con un rol de PostgreSQL **sin `INSERT`/`UPDATE`/`DELETE`**; `core`
conecta con el usuario dueño y es el único que escribe. La separación **la impone PostgreSQL por
permisos**, no una convención de código.

**Estado de las excepciones al empezar esta story:**

| # | Excepción | Estado |
|---|---|---|
| 1 | Las migraciones (`POSTGRESQL_MIGRATION_USER`) | **Deliberada**, se queda |
| 2 | **La fila de `attachments`** (`attachments-post.ts:96-108`) | **Deuda — ESTA STORY LA CIERRA** |
| 3 | `PUT /api/week-assigned-times` | Deuda, fuera de alcance. Queda como **la única excepción viva** |

**Implementation Rules (verbatim del ADR):**

- Toda escritura de dominio nueva **DEBE** implementarse como comando en `core`. **NO SE DEBE**
  agregar escritura con el ORM en `api`.
- La conexión de `api` **DEBE** usar credenciales sin `INSERT`/`UPDATE`/`DELETE`. Si un endpoint
  nuevo requiere escribir, la respuesta correcta es un comando, no ampliar los permisos del rol.
- La conexión de `core` **DEBE** usar el usuario dueño de la base.
- Las migraciones **DEBEN** correr desde `api` con `POSTGRESQL_MIGRATION_USER`, nunca desde `core`.
- Después de publicar un comando de creación, la api **DEBE** releer la base para armar la
  respuesta: core devuelve solo `{ id }` y el contrato con los frontends es el recurso completo
  con sus relaciones.
- Un endpoint que lee **NO DEBE** pasar por el bus: la lectura va directo a PostgreSQL desde la api.
  **Excepción declarada desde REQ-001 (S-005): la lectura de archivos.**

> **La regla de la relectura NO aplica a `files.request-upload`, y es una excepción declarada, no un
> descuido.** La URL prefirmada la genera `core`, es de un solo objeto y de vida corta, y **no está
> en la base**: releer no la produciría. Está registrado como excepción en `docs/apis/core.yaml`
> (`ReplyWithUploadTicket`). No intentes releer para "cumplir" la regla.

#### ADR-002: Toda mutación es un comando NATS request/reply, sin JetStream

**Decisión:** NATS en **modo request/reply, sin JetStream**. La api publica y **espera la respuesta**
con timeout; core valida, escribe en una transacción y responde.

**Gramática del subject:** `{instance}.{user-id}.{svc}.{version}.{comando}`
→ `dev.323332022539911171.gestion.v1.files.request-upload`

**Formato de respuesta**, igual para todos los comandos:
```json
{ "status": "success", "data": { "id": 7 } }
{ "status": "failure", "errorCode": "project_not_found", "errorMessage": "Project not found" }
```

**Implementation Rules (verbatim del ADR):**

- Todo comando **DEBE** publicarse con el subject `{instance}.{user-id}.gestion.v1.{comando}`,
  usando la gramática de `@jiku/nats-protocol`. **NO SE DEBE** construir el subject a mano.
- El cliente NATS **DEBE** fijar `inboxPrefix` explícitamente al conectar, con el hash del user id
  que calcula `@jiku/nats-protocol`. Sin esto las respuestas no llegan.
- El `userId` con el que publica la api **DEBE** salir de la key del service user, **NO** de una
  variable de entorno.
- Toda respuesta **DEBE** tener el formato `{ status: 'success', data }` o
  `{ status: 'failure', errorCode, errorMessage }`. **NO SE DEBEN** inventar otros formatos.
- Los comandos de creación **DEBEN** devolver únicamente `{ id }`. Las ediciones y borrados, nada.
- **Todo `errorCode` nuevo DEBE agregarse al mapa de `api/lib/utils/bus/protocol.ts` con su status
  HTTP. Un código sin mapeo cae en un 500 genérico.**
- El timeout de la request es `NATS_REQUEST_TIMEOUT_MS` (default **5000 ms**); al expirar la api
  **DEBE** responder **503**.
- **NO SE DEBE** transportar datos estructurados dentro de `errorMessage`.
- Core **NO DEBE** publicar mensajes: solo responde el `Reply` de la request que recibe.

> **La regla en negrita es CA-7 y CA-13 de esta story.** Los tres códigos que faltan mapear son
> `file_type_not_allowed`, `file_too_large` y `file_not_owned`.

#### ADR-013: Tests contra base real

Los tests corren contra un PostgreSQL de verdad y el `FakeBus` **ejecuta los comandos contra el core
real** con la misma base. Es lo que hace que el corrimiento de la validación de la `api` a `core`
quede cubierto de punta a punta **con los tests que ya existen**.

  '401': Unauthorized
  '403': AccessDenied
  '404': NotFound

#### Schema `UploadTicket` (nuevo, ya en `docs/apis/api.yaml:2788`)

```yaml
UploadTicket:
  type: object
  required: [fileId, uploadUrl, expiresIn]
  properties:
    fileId:    { type: integer }   # id de `files`. Viaja como `fileIds` al guardar la entidad
    uploadUrl: { type: string }    # prefirmada de PUT, un solo objeto, TTL corto (D-10)
    expiresIn: { type: integer }   # segundos, de `system_settings` (upload-url-ttl-seconds, default 300)
```

> **El campo se llama `id` en el bus y `fileId` en HTTP.** No es un descuido: en el bus `id` es la
> convención de todas las creaciones, y en HTTP `fileId` dice de qué id se trata, que importa porque
> el contrato HTTP de adjuntos maneja **dos** espacios de ids (el del vínculo y el del archivo). **La
> `api` traduce**, que es lo que ya hace en sus cinco traducciones de contrato documentadas.

### Bus / Integration Points

#### Cómo se publica un comando

```ts
import { sendCommand, runCommand, actor } from '../utils/bus/send-command';

// Con datos de vuelta
const data = await sendCommand<UploadTicket>(res, 'files.request-upload', payload);
if (!data) return;         // OBLIGATORIO: la respuesta de error ya salió

// Sin datos de vuelta
const ok = await runCommand(res, `attachments.${id}.delete`, {});
if (!ok) return;
```

`sendCommand` (`lib/utils/bus/send-command.ts`) ya hace, por dentro:
- `bus().request(command, payload)` con el subject armado por `@jiku/nats-protocol`
- **timeout / bus caído → responde `503 { code: 'service_unavailable', message: 'El servicio no está disponible en este momento' }` y devuelve `null`** (esto es **CA-13 gratis**, no lo reimplementes)
- `reply.status !== 'success'` → `res.status(httpStatusFor(reply.errorCode)).json(errorBody(reply))` y devuelve `null`
- éxito → devuelve `reply.data`

#### `files.request-upload` — contrato del comando (core, ya implementado en S-002)

**Subject:** `{instance}.{api-service-user}.gestion.v1.files.request-upload`

**Payload (`FilesRequestUploadPayload`)** — de `docs/apis/core.yaml:1053` y
`core/src/commands/files/files-request-upload.ts`:

```json
{
  "uploader": "IdentityUserId — el zitadel `sub` del usuario final autenticado por JWT",
  "fileName": "string, maxLength 255",
  "mimeType": "string, maxLength 100",
  "fileSize": 4194304,
  "checksum": "string|null — sha256 hex declarado por el cliente. NADIE lo verifica (D-25)"
}
```

Requeridos por el canal de la api: `uploader`, `fileName`, `mimeType`, `fileSize`.

> **`uploader` DEBE ir siempre desde la api.** El esquema Joi de `core` lo declara `.optional()` a
> propósito —para el canal del bus directo, donde no hay persona detrás y `core` resuelve el actor del
> `caller` del subject—, pero **el contrato del canal HTTP lo pone en `required`**. Si la api lo
> omitiera, `resolveActor` caería en la rama externa, `uploaded_by` pasaría a ser el service user de
> la api y **ningún usuario podría vincular lo que subió**, con `file_not_owned` como único síntoma.
> Sale de `req.user.id` (nunca del cuerpo de la request).

**Reply de éxito (`ReplyWithUploadTicket`):**

```json
{
  "status": "success",
  "data": {
    "id": 1234,
    "uploadUrl": "https://bucket.example/grava-gestion/f/9c1e.../abcd.pdf?X-Amz-...",
    "expiresIn": 300
  }
}
```

**`x-error-codes`:** `invalid_fields`, `file_type_not_allowed`, `file_too_large`, `internal_error`.

#### `attachments.{id}.delete` — contrato del comando

**Subject:** `{instance}.{api-service-user}.gestion.v1.attachments.{id}.delete`

- **`{id}` es el id de `attachments`** — el **vínculo**, no el archivo. Es **al revés** que
  `files.{fileId}.request-download`, que lleva el id del archivo. El nombre es deliberado.
- **Payload:** vacío (`EmptyPayload`).
- **Reply:** `ReplyEmpty` — `{ status: 'success' }`, sin `data`. **Por eso se usa `runCommand`, no
  `sendCommand`.**
- **`x-error-codes`:** `invalid_fields` (vínculo inexistente), `internal_error`.

> ✅ **RESUELTO AL IMPLEMENTAR (S-004 core ya está Done).** El comando
> `attachments.{id}.delete` **existe y está registrado** en `core`
> (`core/src/commands/attachments/attachments-delete.ts`, registrado en
> `core/src/commands/index.ts`). La advertencia original —que no existía— quedó obsoleta.
> **Consecuencia: TS-30 y TS-31 NO se saltean**: se escribieron dejando que el `FakeBus`
> ejecute el comando real, que es la cobertura más fuerte. No los debilites para volver al
> `reply()` fijo. El párrafo de abajo se conserva como registro de la advertencia original:
>
> El comando `attachments.{id}.delete` no existía al planificar: no había
> `core/src/commands/attachments/` y `core/src/commands/index.ts` no lo registraba. La story lo asigna
> al servicio **`core`**, que se planifica y se implementa por separado
> (`/service-planify-story S-004 core`).
>
> **Consecuencia práctica:** los tests de la Tarea 5 que dejan ejecutar el `FakeBus` contra core real
> fallarían con `unknown_command`. Mientras el comando de `core` no exista, esos tests se cubren con
> `fakeBus.reply('attachments.{id}.delete', { status: 'success' })`, que es exactamente para lo que
> la convención de testing reserva `reply()`. La Tarea 5 lo detalla.

### Flow Context

#### Flujo `subida-de-archivos` — pasos 2, 3 y 6 (los que implementa esta story)

**Paso 2 — El cliente pide permiso de subida** *(navegador → `api`, REST)*

- **Método:** POST · **Endpoint:** `/api/attachments` (o `/api/opus/attachments`)
- **Content-Type:** `application/json` — **ya no es `multipart/form-data`**
- **Body:**
  ```json
  {
    "fileName": "string — nombre original, maxLength 255",
    "mimeType": "string — maxLength 100",
    "fileSize": "integer — minimum 1",
    "checksum": "string|null — sha256 hexadecimal declarado por el cliente"
  }
  ```
- **Un request por archivo (D-07).** Tres archivos son tres requests independientes: el fallo de uno
  no arrastra a los otros.
- Desaparecen del contrato `files` (el binario), `entityType`, `entityId` y `description`: **subir no
  menciona la entidad** (D-12).
- **Autorización:** solo el JWT.

**Paso 3 — La api publica el comando** *(`api` → `core`, NATS request/reply)*

La `api` valida el JWT y **la forma con Joi**. **No valida tipo ni tamaño** —eso es de `core` ahora
(D-08)— y **no toca la base**.

- **Subject:** `{instance}.{api-service-user}.gestion.v1.files.request-upload`
- **Payload:** `{ uploader, fileName, mimeType, fileSize, checksum }`
- **Timeout:** 5000 ms (ADR-002)

**Paso 6 — La api traduce el reply** *(`api` → navegador)*

**No relee la base**: la URL prefirmada no está en la base y no es reconstruible desde afuera de
`core`.

- **Status:** 201
- **Body (`UploadTicket`):** `{ fileId, uploadUrl, expiresIn }` — donde `fileId` **es** el `id` del
  reply del bus.

**Manejo de errores del flujo (los que le tocan a la `api`):**

| Paso | Error | Código | Response |
|---|---|---|---|
| 2 | Sin JWT válido | 401 | La `api` rechaza sin publicar |
| 2 | Forma del body inválida | 400 | `{ code: invalid_fields }` — Joi corta **antes de publicar** |
| 5 (core) | Extensión fuera de la allowlist | 400 | `{ code: file_type_not_allowed }` |
| 5 (core) | MIME fuera de la allowlist, **aunque la extensión esté** | 400 | `{ code: file_type_not_allowed }` |
| 5 (core) | Supera `file-max-size-bytes` | 400 | `{ code: file_too_large }` |
| 3 | Timeout del bus | **503** | La operación no ocurrió |

**Pasos del flujo que esta story NO implementa:** el paso 1 (validación de conveniencia en el
cliente), el 4 (canal del bus directo), el 5 (`core`, ya hecho en S-002), el 7 (el `PUT` a S3, que es
de S-006/S-007) y el 8/9 (preview y vínculo).

#### Flujo `vinculacion-de-archivos` — paso 6, Desvinculación

1. **[navegador]** `DELETE /api/attachments/{id}` — el id es el del **vínculo**
2. **[`api`]** Autoriza sobre la **entidad** del vínculo. Si falla, **403 sin publicar**
3. **[`api`]** Publica `{instance}.{api-service-user}.gestion.v1.attachments.{id}.delete`
   - **Request:** sin payload propio
4. **[`core`]** Borra la fila de `attachments`. **No toca `files` ni el bucket**
   - **Reply:** `success` · **Errores:** `invalid_fields`, `internal_error`
5. **[`api`]** Traduce el reply y responde

> **Es la tercera escritura implícita de la `api`, y también se convierte en comando.** Dejarla afuera
> dejaría a la `api` escribiendo `attachments` por otra puerta, reabriendo la excepción que este
> rediseño cierra.

#### Flujos que esta story deja obsoletos / desactualizados

- **`adjuntos.md`** — sus pasos 2, 3 y 4 (subida multipart, validación y rollback en la api,
  escritura de la fila sin pasar por core) quedan **eliminados**. El documento ya está marcado como
  reemplazado por `subida-de-archivos` + `lectura-de-archivos` + `vinculacion-de-archivos`.
- **`alta-requisito-desde-portal.md`** — su paso 3 ya está actualizado a
  `POST /api/opus/attachments (application/json)`.
- **`asignacion-semanal.md`** — ya corregido: `PUT /api/week-assigned-times` queda como **la única
  excepción viva** de ADR-001.

### Code Conventions (resumen operativo para esta story)

**Validación (Joi, inline en la ruta):**

```ts
import joi from 'joi';
import validateBodyFields from '../utils/validate-body-fields';

const uploadTicketSchema = joi.object({
  fileName: joi.string().max(255).required(),
  mimeType: joi.string().max(100).required(),
  fileSize: joi.number().integer().min(1).required(),
  checksum: joi.string().allow(null).optional(),
});

router.post('/attachments', validateBodyFields(uploadTicketSchema), requestUpload);
```

`validateBodyFields` responde **400 con el PRIMER error**:
`{ code: 'invalid_fields', message: 'Invalid field - {mensaje de Joi}' }`. **Se devuelve un error, no
la lista** — es el contrato que los fronts ya manejan.

- Esquema largo → constante nombrada arriba del archivo. Corto → inline en la cadena.
- La validación de forma va **antes** de buscar entidades en la base.
- Los ids de usuario son `joi.string()` (son `sub` de Zitadel); los de entidad, `joi.number().integer()`.

**Reglas del bus que aplican acá:**

- Ninguna mutación nueva usa el modelo: **publicá un comando**.
- Después de `sendCommand`, `if (!data) return;`. Después de `runCommand`, `if (!ok) return;`. **Sin
  eso se responde dos veces.**
- El usuario que actúa va **en el cuerpo del comando**, tomado de `req.user.id`. **Nunca del cuerpo de
  la request.**
- Un `errorCode` nuevo de core se agrega a `STATUS_BY_ERROR_CODE`, o sale 500.
- Los campos opcionales van con **spread condicional**, no con `undefined` explícito:
  `...(checksum !== undefined ? { checksum } : {})`.
- Las traducciones de nombres o formatos van en `lib/utils/bus/`, **no en el handler**.

#### Patrón de referencia: `attachments-preview.ts` (S-005)

**Es el modelo más cercano a lo que hay que escribir**, en particular para el DELETE: autoriza
primero, publica después.

```ts
// lib/routes/attachments-preview.ts — abreviado
async function previewAttachment(req: Request, res: Response) {
  const attachmentId = parseInt(req.params.id as string);
  if (isNaN(attachmentId)) {
    return res.status(400).json({ code: 'invalid_id', message: 'Attachment ID must be a valid integer' });
  }

  const attachment = await Attachment.scope('active').findByPk(attachmentId, {
    include: [{ model: File, as: 'file' }],
  });
  if (!attachment) return res.status(404).json({ code: 'not_found', message: 'Attachment not found' });

  const hasAccess = await canUserViewEntity(req.user.id, req.decodedTokenRoles,
                                            attachment.entityType, attachment.entityId);
  if (!hasAccess) return res.status(403).json({ code: 'access_denied', message: '...' });

  const data = await sendCommand<DownloadTicket>(res, `files.${attachment.fileId}.request-download`, { disposition: 'inline' });
  if (!data) return;

  return redirectToPresigned(req, res, data, 'inline');
}
```

Su comentario de cabecera enuncia la regla que esta story reusa para el DELETE:

> **EL ORDEN ES EL CRITERIO DE ACEPTACIÓN, no un detalle de estilo:** el 404 y el 403 tienen que
> ocurrir **ANTES** de publicar. Un handler que publique primero y autorice después pasaría los tests
> de status igual, pero le habría pedido a core una operación sobre algo que el usuario no puede tocar.

#### Aplanado de la respuesta (`lib/routes/attachments-get.ts`, S-005)

`flattenAttachment(attachment)` es lo que sostiene **CA-11**. No lo modifiques en esta story; la Tarea
6 solo verifica que sigue intacto.

### Task 5: `DELETE /api/attachments/{id}` autoriza y publica `attachments.{id}.delete`

**Status:** Completed

#### Description

Reescribir `lib/routes/attachments-delete.ts`: deja de hacer `softDelete()` (un `UPDATE` con el ORM) y
pasa a **autorizar sobre la entidad del vínculo y publicar un comando**.

**Dos cambios de comportamiento observables**, los dos deliberados:

1. **Qué se borra.** Antes marcaba la fila y —según el contrato viejo— también borraba el objeto del
   bucket. Ahora **borra solo el vínculo; el archivo se retiene** (D-04). Con 0..N vínculos por
   archivo, borrar el objeto rompería los otros.
2. **Quién autoriza y cómo.** Antes: `isAdmin || uploadedBy === req.user.id`, o sea **titularidad sobre
   el adjunto**. Ahora: `canUserAccessEntity` sobre **la entidad del vínculo**, que es lo que el flujo
   `vinculacion-de-archivos` (paso 6.2) y la story (CA-9) especifican.

> ⚠ **El criterio de autorización cambia, y hay que entenderlo antes de escribirlo.** `attachments`
> **ya no tiene columna `uploaded_by`**: la migración `20260819_05` la dropeó. El `uploadedBy` que hoy
> lee el handler solo funciona porque el modelo todavía declara la columna y `sync()` la crea en el
> esquema de tests. Contra producción, ese `attachment.uploadedBy` es `undefined`. O sea que el
> criterio viejo **ya está roto** y esta tarea no lo degrada: lo reemplaza por el que el diseño pide.
>
> Si querés conservar la titularidad como control adicional, la fuente correcta es **`file.uploadedBy`**
> (vía el `include`), no la del vínculo. **No lo agregues en esta story:** ningún CA lo pide, y sumar
> un control que el diseño no especificó haría que un caso legítimo (alguien del proyecto desvincula un
> archivo que subió otro) empiece a dar 403 sin que ningún test lo declare como esperado.

#### Acceptance Criteria

1. El handler resuelve el vínculo con `Attachment.scope('active').findByPk(id)` **antes** de publicar.
2. Id no numérico → `400 { code: 'invalid_id' }` sin publicar.
3. Vínculo inexistente → `404 { code: 'not_found' }` sin publicar.
4. Autoriza con `canUserAccessEntity(req.user.id, req.decodedTokenRoles, attachment.entityType,
   attachment.entityId)`. Sin acceso → `403 { code: 'access_denied' }` **sin publicar**.
5. Con acceso, publica **exactamente** `attachments.{id}.delete`, donde `{id}` es el id del **vínculo**.
6. Usa **`runCommand`**, no `sendCommand`: el reply no trae `data`.
7. El payload del comando es un objeto vacío.
8. Éxito → `200` con un cuerpo `{ code, message }` (forma `Acknowledgement`), con `message` en español.
9. **No existe ninguna llamada a `attachment.softDelete()`**, `Attachment.update()`, `Attachment.destroy()`
   ni ninguna otra escritura con el ORM en el archivo.
10. El archivo **no importa** `storage-service`: la api no toca el bucket.
11. `invalid_fields` de core → 400. Timeout del bus → 503.
12. El export del barrel sigue llamándose `AttachmentsDeleteDelete` y la ruta sigue siendo
    `router.delete('/attachments/:id', ...)`.

#### Technical Details

**Architectural Context References:**

- **ADR-001 → Implementation Rules:** *"NO SE DEBE agregar escritura con el ORM en `api`."* Ésta era la
  **tercera escritura implícita**; dejarla afuera reabriría por otra puerta la excepción que el REQ
  cierra.
- **ADR-002:** `runCommand` para comandos sin `data`; timeout → 503.
- **Bus / Integration Points → `attachments.{id}.delete`:** el `{id}` es el del **vínculo**, payload
  vacío, reply sin `data`, errores `invalid_fields` / `internal_error`. **Y la advertencia de que el
  comando todavía no existe en `core`.**

- **Reusable Code → patrón `attachments-preview.ts`:** *"EL ORDEN ES EL CRITERIO DE ACEPTACIÓN: el 404 y
  el 403 tienen que ocurrir ANTES de publicar."*

**Implementation Notes:**

  ```ts
  async function deleteAttachment(req: Request, res: Response) {
    const attachmentId = parseInt(req.params.id as string);
    if (isNaN(attachmentId)) {
      return res.status(400).json({ code: 'invalid_id', message: 'Attachment ID must be a valid integer' });
    }

    // Se resuelve el vínculo para AUTORIZAR sobre su entidad. El orden importa: el 404 y el
    // 403 tienen que salir ANTES de publicar, o le habríamos pedido a core que borre algo
    // que el usuario no puede tocar.
    let attachment: Attachment | null;
    try {
      attachment = await Attachment.scope('active').findByPk(attachmentId);
    } catch (error: any) {
      logger.error(`Delete failed: id=${attachmentId}, error=${error.message}`, { userId: req.user.id });
      return res.status(500).json({ code: 'internal_error', message: 'Failed to delete attachment' });
    }

    if (!attachment) {
      return res.status(404).json({ code: 'not_found', message: 'Attachment not found' });
    }

    const hasAccess = await canUserAccessEntity(
      req.user.id, req.decodedTokenRoles, attachment.entityType, attachment.entityId
    );
    if (!hasAccess) {
      return res.status(403).json({ code: 'access_denied', message: 'No tenés permiso para desvincular este archivo' });
    }

    // Borra SOLO el vínculo. El archivo y el objeto del bucket se retienen (D-04): con
    // 0..N vínculos por archivo, borrar el objeto rompería los otros.
    const ok = await runCommand(res, `attachments.${attachmentId}.delete`, {});
    if (!ok) return;

    return res.status(200).json({ code: 'attachment_unlinked', message: 'Archivo desvinculado' });
  }
  ```
