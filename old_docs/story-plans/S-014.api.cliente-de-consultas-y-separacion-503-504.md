### Service Architecture

No es MVC ni Clean Architecture: es **un archivo por endpoint**, con la validación, los permisos y el
handler colocados juntos. No hay `src/`; el código vive en `lib/`.

```
api/
├── app.ts                    Express, middleware global, montaje de rutas
├── bin/index.ts              entry point; valida la config de auth ANTES de escuchar
├── lib/
│   ├── routes/               61 archivos, uno por endpoint, + index.ts (barrel)
│   ├── logger.ts             Winston
│   └── utils/
│       ├── bus/              <- TODO EL CÓDIGO DE ESTA STORY VIVE ACÁ
│       │   ├── index.ts          cliente NATS: interfaz `Bus`, `NatsBus`, setBus/bus()
│       │   ├── protocol.ts       USER_ID, STATUS_BY_ERROR_CODE, httpStatusFor, errorBody
│       │   ├── send-command.ts   sendCommand / runCommand / actor  <- el catch 503/504
│       │   ├── download-ticket.ts, upload-ticket.ts, priority.ts, properties.ts
│       └── middlewares/      7 compartidos
└── tests/
    ├── mocks/bus.ts          el FakeBus     <- CA-8, CA-9
    ├── routes/               61 archivos, uno por archivo de ruta
    └── utils/                unitarios, SIN base de datos (npm run test:unit)
```

**Manejo de errores:** sin clases de error, sin `throw` en handlers, sin handler global que traduzca.
Cada punto responde `res.status(n).json({ code, message })` y corta.

**Logging:** `logger` de `lib/logger.ts`, nunca `console`. Prefijo de origen: `[bus]` en el cliente
del bus. Se loguea `error.message`, no el error completo. **Un error que se responde al cliente se
loguea antes de responder.**

### Relevant ADRs

#### ADR-002: Toda mutación es un comando NATS request/reply, sin JetStream

**Decisión:** la api no escribe en la base; publica un comando y espera la respuesta, con
request/reply directo sobre NATS core (sin JetStream, sin cola, sin reintento, sin idempotencia).

**Implementation Rules (copiadas verbatim del ADR):**

- Todo comando **DEBE** publicarse con el subject `{instance}.{user-id}.gestion.v1.{comando}`,
  usando la gramática de `@jiku/nats-protocol`. **NO SE DEBE** construir el subject a mano.
- El cliente NATS **DEBE** fijar `inboxPrefix` explícitamente al conectar, con el hash del user id
  que calcula `@jiku/nats-protocol`. Sin esto las respuestas no llegan.
- El `userId` con el que publica la api **DEBE** salir de la key del service user, **NO** de una
  variable de entorno: tiene que coincidir exactamente con el `sub` que el auth-callout lee del
  token para autorizar el subject.
- Toda respuesta **DEBE** tener el formato `{ status: 'success', data }` o
  `{ status: 'failure', errorCode, errorMessage }`. **NO SE DEBEN** inventar otros formatos.
- Los comandos de creación **DEBEN** devolver únicamente `{ id }`. Las ediciones y borrados, nada.
- Todo `errorCode` nuevo **DEBE** agregarse al mapa de `api/lib/utils/bus/protocol.ts` con su
  status HTTP. Un código sin mapeo cae en un 500 genérico.
- El timeout de la request es `NATS_REQUEST_TIMEOUT_MS` (default **5000 ms**); al expirar la api
  **DEBE** responder **503**.
- **NO SE DEBE** transportar datos estructurados dentro de `errorMessage`. El caso actual de
  `daily_limit_exceeded` —que la api recupera parseando el mensaje con un regex— es deuda
  explícita, no un patrón a imitar.
- Core **NO DEBE** publicar mensajes: solo responde el `Reply` de la request que recibe.

> **DOS DE ESAS REGLAS ESTÁN DESACTUALIZADAS Y EL ADR NO SE TOCA EN ESTA STORY.** Léelas así:

#### ADR-001: Separación lectura / escritura

**Decisión:** la api conecta a PostgreSQL con un rol de **solo lectura** y toda mutación va por el
bus. La garantía la impone PostgreSQL por permisos, no una convención de código.

**Lo que aporta a esta story:** **los endpoints HTTP de lectura NO migran al bus** (RF-14). `query()`
se agrega como cliente disponible, **no** como camino de lectura de la api. `jiku-queries` nace para
**otros** consumidores y **no es una excepción a ADR-001**.

### API Context

#### El contrato HTTP que esta story cambia — un status nuevo

**Estado actual, verbatim de `api/lib/utils/bus/send-command.ts`:24-34:**

```ts
  try {
    reply = await bus().request<T>(command, payload);
  } catch (error: any) {
    // Timeout o bus caído. Sin JetStream no hay reintento: la operación no ocurrió.
    logger.error(`[bus] ${command}: ${error.message}`);
    res.status(503).json({
      code: 'service_unavailable',
      message: 'El servicio no está disponible en este momento',
    });
    return null;
  }
```

**Estado objetivo — se separan dos fallas que hoy colapsan en una:**

| Causa | Actual | Nuevo | Cuerpo |
|---|---|---|---|
| No hay **ningún suscriptor** del subject | 503 `service_unavailable` | **503** (sin cambio) | `{code:'service_unavailable', message:'El servicio no está disponible en este momento'}` |
| La respuesta **no llegó a tiempo** | 503 `service_unavailable` | **504 `gateway_timeout`** → MODIFICADO | `{code:'gateway_timeout', message:'La operación tardó demasiado'}` |
| Cualquier otra excepción | 503 `service_unavailable` | **503** (sin cambio) | Ídem 503 |

**Los dos mensajes están aprobados tal cual por la Revisión UX del REQ-004 y NO se cambian**
(ver "Contexto UX" más abajo).

#### `STATUS_BY_ERROR_CODE` — el mapa que NO cambia (CA-5)

Vive en `api/lib/utils/bus/protocol.ts`:30-87 y traduce el `errorCode` **de un `Reply` de core** al
status HTTP. Su fallback:

```ts
export function httpStatusFor(errorCode: string | undefined): number {
  return (errorCode && STATUS_BY_ERROR_CODE[errorCode]) || 500;
}
```

**`gateway_timeout` NO entra en este mapa.** No es un `errorCode` de core: no viene en un `Reply`, lo
genera la api en el `catch`. Es un `code` de respuesta HTTP directa, **igual que
`service_unavailable`, que tampoco está en el mapa**. Los dos mapas son distintos y **confundirlos es
el error fácil de esta story**: un `errorCode` sin entrada sale 500, así que meter `gateway_timeout`
ahí sería declarar que core lo emite, que es falso.

#### La interfaz `Bus` — estado actual y objetivo

**Actual, verbatim de `api/lib/utils/bus/index.ts`:7-17 y :70-83:**

```ts
const REQUEST_TIMEOUT_MS = Number(process.env.NATS_REQUEST_TIMEOUT_MS) || 5000;

export interface Bus {
  request<T = any>(command: string, payload: unknown): Promise<Reply<T>>;
}

// ... en class NatsBus implements Bus:
  async request<T = any>(command: string, payload: unknown): Promise<Reply<T>> {
    if (!this.connection) {
      throw new Error('Bus no conectado');
    }

    const subject = commandSubject(command, this.userId);
    const message = await this.connection.request(
      subject,
      new TextEncoder().encode(JSON.stringify(payload)),
      { timeout: REQUEST_TIMEOUT_MS }
    );

    return JSON.parse(new TextDecoder().decode(message.data)) as Reply<T>;
  }
```

**Objetivo (CA-6):**

```
interface Bus {
  request(command, payload): Promise<Reply>   // NATS_REQUEST_TIMEOUT_MS (5000)
  query(query, payload):     Promise<Reply>   // NATS_QUERY_TIMEOUT_MS  (10000)  <- NUEVO
}
```

- Subject: `querySubject(query, this.userId)`, del paquete. **Nada se concatena a mano** (RF-18).
- **Una sola conexión, el mismo inbox, el mismo service user.** No se abre una segunda conexión ni se
  pide identidad nueva: la separación es de **timeout y de subject**, no de transporte.
- **Timeout propio y más largo**, porque el perfil es opuesto: lecturas largas con joins contra
  escrituras cortas y transaccionales.
- **Sin ningún caller** (CA-7). Hasta que exista `jiku-queries` (S-013), `query()` devuelve el 503 de
  *no responders* — que es correcto, y es la prueba de que compila y publica sin nadie del otro lado.

**Solo hay dos implementadores de `Bus` en todo el servicio** (verificado con grep):
`NatsBus` (`lib/utils/bus/index.ts`:19) y `FakeBus` (`tests/mocks/bus.ts`:35). Ampliar la interfaz
**rompe el build de los tests** hasta que `FakeBus` implemente `query()`.

### Integration Points

#### `@jiku/nats-protocol` — lo que S-011 ya dejó disponible (verificado en el código)

`packages/nats-protocol/src/index.ts`, verbatim:

```ts
export const COMMAND_SERVICE = process.env.NATS_COMMAND_SERVICE || 'jiku-commands';
export const QUERY_SERVICE = process.env.NATS_QUERY_SERVICE || 'jiku-queries';
export const PROTOCOL_VERSION = process.env.NATS_PROTOCOL_VERSION || 'v1';
export const INSTANCE = process.env.NATS_INSTANCE || 'dev';

/** Arma el subject de un comando saliente. `userId` es el `sub` de quien publica. */
export function commandSubject(command: string, userId: string): string {
  return `${INSTANCE}.${userId}.${COMMAND_SERVICE}.${PROTOCOL_VERSION}.${command}`;
}

export function querySubject(query: string, userId: string): string {
  return `${INSTANCE}.${userId}.${QUERY_SERVICE}.${PROTOCOL_VERSION}.${query}`;
}
```

Gramática: `{instance}.{user-id}.{svc}.{version}.{método}`. Ejemplo de consulta:
`dev.323332022539911171.jiku-queries.v1.tasks.list`.

> **El orden de los parámetros de `querySubject` es el mismo que en `commandSubject` a propósito**
> (lo dice su comentario): las dos toman dos strings, así que invertirlo sería un bug que el
> compilador no atrapa.

`api/lib/utils/bus/protocol.ts` hace `export * from '@jiku/nats-protocol'`, así que **`querySubject`
se importa desde `./protocol`**, igual que `commandSubject` hoy. No importes el paquete directo en
`bus/index.ts`: seguí el import que ya está en la línea 5.

#### La API de errores de `nats` 2.29 — **leé esto antes de escribir el `catch`**

Verificado ejecutando el paquete instalado durante la planificación. Es la parte de la story donde la
intuición falla:

```ts
import { ErrorCode, NatsError } from 'nats';
```

| Símbolo | Disponible en `nats` 2.29.3 | Notas |
|---|---|---|
| `ErrorCode` | **Sí** (tipos y runtime) | `ErrorCode.Timeout === 'TIMEOUT'` · `ErrorCode.NoResponders === '503'` |
| `NatsError` | **Sí** (tipos y runtime) | Clase con `.code`. Estática: `NatsError.errorForCode(code, chainedError?)` |
| `isNatsError` | **NO.** No lo exporta la superficie pública | Está en el `.d.ts` **interno** (`nats-base-client/internal_mod.d.ts`), pero `nats-base-client/mod.d.ts` no lo re-exporta. `import { isNatsError } from 'nats'` **no compila**: `TS2724: '"nats"' has no exported member named 'isNatsError'`. Y en runtime `require('nats').isNatsError` es `undefined` |

**Formas exactas de los tres errores que el `catch` puede recibir** (medidas, no supuestas):

| Error | `code` | `message` | `instanceof NatsError` |
|---|---|---|---|
| `NatsError.errorForCode(ErrorCode.NoResponders)` | `'503'` | `'503'` | `true` |
| `NatsError.errorForCode(ErrorCode.Timeout)` | `'TIMEOUT'` | `'TIMEOUT'` | `true` |
| `new Error('timeout')` | `undefined` | `'timeout'` | `false` |

**Dónde los produce el cliente real** (`node_modules/nats/lib/nats-base-client/`):
`msg.js:29` y `nats.js:206-207` construyen el de *no responders* cuando el server contesta con el
header de status `503`; `muxsubscription.js:90` y `util.js:82` construyen el de *timeout* al vencer el
`{ timeout }` de la request.

**Consecuencias prácticas para el `catch`:**

1. La discriminación se escribe como `error instanceof NatsError && error.code === ErrorCode.Timeout`.
   `instanceof` es seguro acá porque **hay una sola copia de `nats` instalada** (verificado:
   `find . -path "*node_modules/nats/package.json"` → 1, hoisted en la raíz del monorepo).
2. **No hace falta detectar *no responders* explícitamente**, y no conviene: cae en el default 503
   junto con cualquier otra excepción, que es exactamente lo que piden CA-1 y CA-4 (*"el `catch` gana
   una rama, no se reescribe"*). Una rama propia que devuelve el mismo cuerpo sería código muerto.
3. **`ErrorCode.NoResponders` y `ErrorCode.JetStreamNotEnabled` son el mismo string `'503'`.**
   Irrelevante acá porque no se usa JetStream (ADR-002) — y es una razón más para discriminar **solo**
   por `Timeout`.
4. **El log ya distingue las dos causas sin tocarlo:** el `message` de un `NatsError` **es su código**,
   así que ``logger.error(`[bus] ${command}: ${error.message}`)`` sale como
   `[bus] requirements.new: TIMEOUT` o `[bus] requirements.new: 503`. No cambies la línea del log.

### Contexto UX / Design System

`affects_ui: false`. **No se cargó contexto UX ni Design System**: la story no toca ninguna pantalla,
overlay, bloque ni transición, y `web` / `opus-web` **no cambian ni una línea** (RF-16, CA-12).

**Pero el copy que esta story emite es literalmente lo que ve la persona**, así que la Revisión UX del
REQ-004 (`ux_review: done`) dejó tres decisiones que **condicionan** la implementación:

**1. Los dos mensajes están aprobados tal cual y NO se cambian sin volver a pasar por revisión UX:**

| Falla | Mensaje aprobado | Qué pasó | Qué debería hacer el usuario |
|---|---|---|---|
| `503 service_unavailable` | *"El servicio no está disponible en este momento"* | La operación **no ocurrió** | Reintentar es seguro |
| `504 gateway_timeout` | *"La operación tardó demasiado"* | **Pudo haber ocurrido** | Verificar antes de reintentar — el reintento a ciegas duplica |

comandos **no son idempotentes**, ADR-002) y **el de timeout no afirma que la operación no ocurrió**.
Lo que **no** hacen es guiar la recuperación, y eso **se descartó a propósito**.

**2. El estado de error del timeout no recibe tratamiento distinto, y es un descarte explícito.**
Darle un estado propio significa diseñar UI, y el REQ deja los frontends sin cambios.

**3. Tres hallazgos de la revisión que NO son alcance de esta story** (anotados acá porque es donde se
leen, no para que se arreglen):

- **`alta-proyecto` de `web` descarta el `message` de la api** y muestra un literal fijo. Con dos
  mensajes de recuperación **opuesta**, es pérdida de información. Es código de `web` (RF-16). **No se
  arregla acá.**
- **Los toasts de `web` cierran en 2 segundos** (`autoClose: 2000`), antes de que se lea el mensaje que
  ahora es la única guía de recuperación. **Tampoco se arregla acá.**
- **`web` y `opus-web` no tienen ni un test ni una línea que enumere códigos de error**, así que la
  separación no les rompe nada. Confirmado en `web/src/lib/axios.ts`:41-49 y
  `opus-web/src/lib/axios.ts`:26-30: los dos normalizan cualquier `{code,message}` y propagan
  `message` tal cual; solo el 401 tiene rama propia.

**Design System: 0 gaps.** La Revisión UX del REQ-004 lo verifica explícitamente: *"el delta no
introduce ni un bloque"*, así que **no hay ningún componente pendiente de crear** y nada que abortar.

> **Registrado sin resolver (decisión aceptada, no un hallazgo de esta story):** ninguno de los dos
> catálogos de DS tiene un componente de feedback (toast, alert, inline error) pese a que las dos
> superficies dependen de uno para todo su manejo de errores. **No es un gap de este delta** y el REQ
> decidió no convertirlo en "crear componente": sería alcance nuevo. No lo re-abras acá.

## Tasks

### Task 1: `query()` en la interfaz `Bus`, en `NatsBus` y en `FakeBus`

**Status:** Completed

#### Description

Ampliar la interfaz `Bus` con `query()` —un método de consulta con su propio timeout y su propio token
`{svc}` de subject— e implementarla en sus **dos** implementadores.

**Va todo en una tarea, y no es pereza: `FakeBus implements Bus` es una declaración explícita
(`tests/mocks/bus.ts`:35), así que en el instante en que la interfaz suma un método, la suite de tests
DEJA DE COMPILAR.** Separar la interfaz de su doble dejaría el árbol roto entre dos tareas. Los dos
cambios son una sola unidad.

`query()` **queda sin ningún caller** (CA-7). Es deliberado: se construye por adelantado para el REQ
que defina el contrato de consultas (RF-10). Hasta que exista `jiku-queries` (S-013) devolvería el 503
de *no responders*, lo cual es correcto y es la prueba de que compila y publica sin nadie del otro
lado. **Los endpoints HTTP de lectura NO migran al bus** (RF-14, ADR-001).

#### Acceptance Criteria

1. La interfaz `Bus` de `lib/utils/bus/index.ts` declara
   `query<T = any>(query: string, payload: unknown): Promise<Reply<T>>`, además de `request()`.
2. `NatsBus.query()` arma el subject con **`querySubject(query, this.userId)`**, importado desde
   `./protocol`. **Nada se concatena a mano.**
3. `NatsBus.query()` pasa `{ timeout: QUERY_TIMEOUT_MS }`, donde
   `QUERY_TIMEOUT_MS = Number(process.env.NATS_QUERY_TIMEOUT_MS) || 10000`, **separado** de
   `REQUEST_TIMEOUT_MS` (5000).
4. `QUERY_TIMEOUT_MS` y `REQUEST_TIMEOUT_MS` se **exportan** desde `lib/utils/bus/index.ts`, para que
   TS-10 pueda afirmar la separación sin levantar un NATS.
5. `NatsBus.query()` usa `this.connection` — **la misma** conexión, **el mismo** inbox
   (`inboxPrefix` ya fijado en `connect()`) y **el mismo** service user. **No** se abre una segunda
   conexión, **no** se pide identidad nueva, **no** se toca `connect()`.
6. `NatsBus.query()` lanza `new Error('Bus no conectado')` si no hay conexión, igual que `request()`.
7. `FakeBus` implementa `query()` y **rechaza explícitamente** con un error cuyo mensaje **nombra la
   razón** (que no hay contrato de consultas), **antes** de registrar nada en `sent`.
8. `FakeBus.request()` **no se modifica en ninguna línea**, y en particular no se toca la `:93` que
   arma el subject con `commandSubject()` (CA-9).
9. `FakeBus` suma `failWithNoResponders(): this` y `failWithTimeout(): this`, que fijan el `failure`
   con el `NatsError` correspondiente. `failWith(error)` **se conserva** tal cual, para la excepción
   genérica de CA-4.
10. `grep -rn "\.query(" api/lib` no devuelve **ningún** caller de `bus().query()` (CA-7).
11. `npm run lint --workspace @jiku/api` pasa y `npm test --workspace @jiku/api` **compila**.

### Task 2: Separar 503 de 504 en el `catch` de `send-command.ts`

**Status:** Completed

#### Description

Agregar **una** rama al `catch` de `sendCommand` que devuelva **504 `gateway_timeout`** cuando el
cliente NATS señala un **timeout**, dejando el **503 `service_unavailable`** como comportamiento por
defecto para *no responders* y para cualquier otra excepción.

**Es una rama, no una reescritura.** Perder el default cambiaría el comportamiento de casos que el REQ
no toca (CA-4).

**La rama se elige por la SEÑAL del error del cliente NATS, no por el tiempo transcurrido** (CA-3):
*no responders* llega **en milisegundos** —el server lo contesta, no vence el timeout— y un timeout que
vence antes de lo esperado seguiría siendo un timeout.

**Y `gateway_timeout` NO va a `STATUS_BY_ERROR_CODE`** (CA-5). Es el error fácil de esta story: ese
mapa traduce `errorCode` **de un `Reply` de core**, y `gateway_timeout` lo genera la api en el `catch`.
Meterlo ahí declararía que core lo emite, que es falso.

#### Acceptance Criteria

1. El `catch` de `sendCommand` (`lib/utils/bus/send-command.ts`:26-34) responde **504** con
   `{ code: 'gateway_timeout', message: 'La operación tardó demasiado' }` **si y solo si** el error es
   un `NatsError` con `code === ErrorCode.Timeout`.
2. Cualquier otro error —**incluido** el de *no responders* (`code === ErrorCode.NoResponders`)—
   responde **503** con `{ code: 'service_unavailable', message: 'El servicio no está disponible en este momento' }`,
   **byte por byte el mismo cuerpo que hoy**.
3. La discriminación **no** mira el tiempo transcurrido, ni el `message` del error, ni ninguna
   heurística de texto. Solo `error instanceof NatsError && error.code === ErrorCode.Timeout`.
4. **No se agrega una rama explícita para *no responders***: cae en el default, que devuelve el mismo
   cuerpo. Una rama que duplica la respuesta es código muerto y viola *"el `catch` gana una rama"*.
5. ``logger.error(`[bus] ${command}: ${error.message}`)`` **se conserva sin cambios**, y sigue
   ejecutándose **antes** de responder (convención `logging`).
6. `STATUS_BY_ERROR_CODE` en `lib/utils/bus/protocol.ts` **no gana ninguna entrada**. Ni
   `gateway_timeout`, ni `service_unavailable`.
7. `errorBody()` y `httpStatusFor()` **no se modifican**: arman la respuesta de un `Reply` de core, no
   la del `catch`.
8. `runCommand()` **no se modifica**: delega en `sendCommand` y devuelve `!res.headersSent`, así que
   hereda el 504 sin una línea.
9. Los mensajes son **exactamente** los aprobados por la Revisión UX. Ni una coma distinta.

#### Technical Details

**Architectural Context References:**

- **La API de errores de `nats` 2.29** (Integration Points) es la referencia de esta tarea. En
  particular: **`isNatsError` no se puede importar de `nats`** (`TS2724`), así que la forma es
  `error instanceof NatsError && error.code === ErrorCode.Timeout`; `instanceof` es seguro porque hay
  **una sola copia** de `nats` instalada; y `ErrorCode.NoResponders` es el string `'503'`, que colisiona
  con `ErrorCode.JetStreamNotEnabled` — una razón más para discriminar **solo** por `Timeout`.
- **API Context › El contrato HTTP que esta story cambia**: la tabla de las tres causas con sus cuerpos
  exactos.
- **API Context › `STATUS_BY_ERROR_CODE`**: por qué `gateway_timeout` no entra (CA-5).
- **ADR-002, Implementation Rules**: *"al expirar la api DEBE responder 503"* es **la regla que esta
  tarea cambia**; *"Todo `errorCode` nuevo DEBE agregarse al mapa"* **sigue vigente y no aplica acá**,
  porque `gateway_timeout` no es un `errorCode`.
- **Convención `error-handling`**: `res.status(n).json({ code, message })`; `code` en `snake_case` y
  **estable**; `message` es **texto de interfaz** y va en español; nunca el detalle del error en la
  respuesta (va al log).
- **Convención `logging`**: prefijo `[bus]`, `error.message`, loguear **antes** de responder.
- **Contexto UX**: los dos mensajes están **aprobados tal cual** y no se cambian sin volver a pasar por
  revisión UX.

**Implementation Notes:**

## Notas de planificación

### Hallazgos de la planificación que corrigen o precisan la story

1. **Son 11 archivos de test, no ~8.** La story estimó *"~8 archivos"* y listó 8. El grep completo de
   `api/tests/` devuelve **11**: faltaban `projects-patch`, `opus-attachments-preview` y
   `files-preview`. Los tres están en la tabla de Task 3.

2. **Los 11 simulan la falla con un `Error` pelado, no con un error de NATS.** Todos usan
   `failWith(new Error('timeout'))` o `new Error('TIMEOUT')`. Con la rama de Task 2 eso cae en el
   default y sale 503 — así que **sin tocar nada la suite pasaría en verde afirmando 503 por la razón
   equivocada**. La story anticipó que *"algunos siguen esperando 503 y otros pasan a 504"*; lo que la
   planificación agrega es que **los 11 hay que tocarlos**, incluidos los que no cambian de status,
   porque la simulación misma es lo que está mintiendo.

3. **`isNatsError` NO se puede importar de `nats` 2.29.3.** Está en el `.d.ts` **interno** del paquete
   pero la superficie pública no lo re-exporta: `import { isNatsError } from 'nats'` falla con
   `TS2724`, y en runtime `require('nats').isNatsError` es `undefined`. La forma correcta es
   `error instanceof NatsError && error.code === ErrorCode.Timeout`. **Es el detalle que más tiempo
   habría costado descubrir escribiendo el `catch` de memoria.**

4. **CA-11 ya está cumplido.** `docs/apis/api.yaml` tiene las 26 referencias de 503, las 26 de 504, los
   dos componentes de respuesta y la cabecera con los tres modos de falla. Task 4 no escribe el spec:
   lo **blinda** con un test. La "Nota de planificación" de la story lo anticipaba (*"ya está aplicada"*)
   y se verificó línea por línea.

5. **`NATS_QUERY_TIMEOUT_MS` ya está cableada al contenedor de la api** por S-011 (`deploy/.env.dist`:125
   y los tres `docker-compose*.yml`). No hay nada que agregar en `deploy`. Y **`api/.env.dist` no
   declara ninguna variable `NATS_*`**: las de la api llegan por el compose. No inaugures esa sección
   por una variable.

6. **ADR-002 tiene dos Implementation Rules desactualizadas y NO se tocan acá.** La del subject con
   `gestion` embebido quedó obsoleta con S-011 y sigue sin corregir; la del *"503 al expirar"* es
   justamente la que esta story cambia. REQ-004 las manda a
   `/product-change-technical-definition` (RF-23). Lo mismo con
   `docs/architectures/api/conventions/bus-commands.md`, `error-handling.md` y `env-config.md` (RF-24).
   **Están citadas en el Architectural Context con su estado real** para que el implementador no las
   siga a ciegas.
