# Story Plan: S-003 (core) - Titularidad y `fileIds` en los comandos de dominio

## Status

**Status:** Completed

## Story Reference

- **Story:** [S-003](../stories/S-003.titularidad-y-fileids-en-comandos-de-dominio.md)
- **Service:** `core`
- **Summary:** Los seis comandos de dominio que reciben archivos pasan de `attachmentIds` (drafts que
  se reanclan) a `fileIds` (archivos que ya existen y se vinculan), validando titularidad con el
  **mismo** `resolveActor` que usa `files.request-upload`. `attachmentScope` desaparece; el vínculo se
  crea con `INSERT INTO attachments` contra una entidad que ya existe, en la misma transacción.

**Patrones clave (convención `commands`):**

- Tres capas sin solapamiento: `Consumer → Dispatcher → Command → base`.
- Un archivo por comando, bajo `src/commands/{entidad}/`. Imports **relativos**.
- Cinco partes en cada archivo, siempre en este orden: imports → interfaz del payload → esquema Joi →
  el objeto `Command` → `export default`.
- **Orden dentro de `execute`** (consistente en los 17 comandos):
  1. Buscar la entidad del `params` → `*_not_found` si no está.
  2. Validar las referencias del payload (proyecto, personas, requisito) → su código.
  3. Validar las reglas de negocio.
  4. Calcular lo que necesita el estado anterior (historial), **antes** de escribir.
  5. **Escribir, siempre con `{ transaction: ctx.transaction }`.**
  6. `success()` o `success({ id })`.
- Las creaciones devuelven **solo `{ id }`**; ediciones y borrados, nada.
- Un comando **no** valida permisos ni roles, **no** abre transacciones, **no** lanza, **no** lee
  `process.env`, **no** loguea el flujo normal, **no** notifica.
- Agregar un comando son tres pasos: el archivo, el registro en `commands/index.ts`, y sus tests.
- **No agregues capa de repositorio ni de servicio**: el comando es la unidad completa.

**Manejo de errores (convención `error-handling`):**

- Un comando **nunca lanza** para señalar un error esperado: devuelve `failure(...)`.
- `success()` / `failure()` se construyen con los helpers de `@jiku/nats-protocol`, nunca a mano.
- Se usa la **constante** `ErrorCode.X`, nunca el literal.
- **Devolver `failure` descarta toda la escritura del comando.** No esperes conservar parte del trabajo.
- Los mensajes nuevos van en **español** y no llevan datos internos (ids de otras entidades, nombres
  de columna, detalle de excepción).
- Un código nuevo se agrega en **tres** lugares: el paquete `@jiku/nats-protocol`, `docs/apis/core.yaml`,
  y el mapa a HTTP de la api. **`file_not_owned` ya existe en el paquete y en el YAML** (S-002); el
  mapa de la api es de **S-004**, no de esta story.

**Logging (convención `logging`):**

- Winston. **No se loguea el flujo normal** de un comando; el despachador ya traza con `LOG_COMMANDS`.
- **Nunca se loguea el payload** ni datos de negocio fuera de `LOG_COMMANDS`. `resolve-actor.ts` loguea
  el `caller` (identificador de servicio) y nada más — respetá ese límite.

**Testing (convención `testing` + ADR-013):**

- Mocha, contra **PostgreSQL real**, sin mocks de Sequelize.
- Los tests entran por `dispatch()`, **nunca** llamando a `execute()` directamente.
- Un archivo por módulo: `tests/commands/{módulo}.test.ts`.
- Los fixtures se crean en el `before` del propio archivo. No hay factories compartidas.
- `TZ=UTC` está fijado en `tests/setup-env.ts`.

### Relevant ADRs

#### ADR-003: La transacción es del despachador, nunca del comando

**Decisión:** Invertir la propiedad de la transacción. La abre y la cierra el **despachador**
(`core/src/bus/dispatcher.ts:42-54`): abre, ejecuta el comando pasándole la transacción en su contexto,
y hace **commit si el reply es `success`, rollback en cualquier otro caso**. Los comandos reciben la
transacción pero **no tienen acceso a `commit` ni a `rollback`**.

**Implementation Rules (verbatim):**

- Un comando **DEBE** recibir la transacción por su contexto y usarla en todas sus operaciones de
  base de datos. **NO DEBE** abrir una transacción propia.
- Un comando **NO DEBE** llamar a `commit()` ni a `rollback()`. Si el código de un comando los
  invoca, está mal escrito.
- Un comando **DEBE** señalar el fallo devolviendo un `Reply` con `status: 'failure'` y su
  `errorCode`. **NO DEBE** lanzar una excepción para señalar un fallo de negocio esperado.
- El despachador **DEBE** hacer commit **solo** si el reply es `success`, y rollback en todos los
  demás casos, incluidas las excepciones inesperadas.
- El despachador **NO DEBE** lanzar nunca: todo error se traduce a un `Reply` de falla.
- Los tests de comandos **DEBEN** entrar por el despachador (helper `dispatch()`), no llamando a
  `execute()` directamente: es lo único que verifica el comportamiento transaccional, incluido el
  rollback.

**Por qué es EL ADR de esta story:** es lo que hace segura la **validación tardía**. `core` crea la
entidad y **después** valida los archivos; si la titularidad falla, el rollback descarta la entidad
entera. CA-4 y CA-7 dependen enteramente de esta regla.

```ts
// core/src/bus/dispatcher.ts
const transaction = await sequelize.transaction();
try {
  const reply = await command.execute(validated.value, { caller, params, transaction });
  if (reply.status === 'success') await transaction.commit();
  else await transaction.rollback();
  return reply;
} catch (error: any) {
  await transaction.rollback();
  logger.error(`[dispatch] ${name}: ${error.message}`);
  return failure(ErrorCode.INTERNAL_ERROR, 'Internal error');
}
```

#### ADR-013: Tests contra base real

**Decisión:** los tests de `api` y `core` corren contra un PostgreSQL efímero real, con el esquema
construido por `sequelize.sync()`, entrando por el despachador.

**Implementation Rules (verbatim, las que aplican):**

- Los tests de `api` y `core` **DEBEN** correr contra PostgreSQL real. **NO SE DEBEN** mockear los
  modelos de Sequelize.
- Los tests de comandos de `core` **DEBEN** entrar por el despachador (`dispatch()`), **NO** por
  `execute()`.
- Cada archivo de test **DEBE** poder correr solo: el esquema y el mock de auth se preparan en el
  arranque de la corrida.
- `TZ=UTC` **DEBE** estar fijado en la configuración de test de todo servicio.
- La limpieza entre corridas **DEBE** ser `TRUNCATE ... RESTART IDENTITY CASCADE`, para que los ids
  arranquen desde 1.
- **NO SE DEBE** depender del orden de ejecución entre archivos de test.

**Consecuencia crítica para esta story:** el esquema de test lo construye **`sequelize.sync()` a partir
de los modelos**, no las migraciones. Lo que vale en los tests es lo que declara el **modelo**
`Attachment`, no lo que dropea la migración `20260819_05`. Ver "Database Context → El obstáculo del
modelo `Attachment`".

#### ADR-007: Identidad Zitadel con auth-callout

**Decisión (lo que importa acá):** el `user-id` del subject es el `sub` del **service user del
servicio** que publica, no el de la persona. La `api` usa **un único service user para todas sus
personas**. El auth-callout de Zitadel mintea los permisos de publicación según el rol del token, así
que el `caller` del subject es **avalado por el bus y no falsificable**.

**Consecuencia directa:** `File.uploaded_by == ctx.caller` **rompe la web** (uploaded_by es un usuario
de Zitadel, caller es el service user de la api: nunca coinciden), y `File.uploaded_by ==
payload.author` **no cumple RF-14**. De ahí `resolveActor`.

#### ADR-002: Comandos NATS sin JetStream

**Decisión (lo que importa acá):** request/reply sincrónico con timeout de 5000 ms
(`NATS_REQUEST_TIMEOUT_MS`). **No hay cola, ni reintento, ni idempotencia.** No metas llamadas de red
dentro de la transacción del despachador: arriesgan el timeout. Esta story **no hace ninguna llamada
de red** — solo lecturas y escrituras de la base ya conectada.

#### ADR-005: Modelos compartidos

**Decisión (lo que importa acá):** `@jiku/models` es compartido entre `api` y `core`. Un cambio al
paquete afecta a los dos y obliga a desplegarlos juntos. **Esta story no debería necesitar tocar
`@jiku/models`** — y si el implementor cree que sí, ver la nota de riesgo en "El obstáculo del modelo
`Attachment`" antes de hacerlo.

#### ADR-001: Separación lectura/escritura

**Decisión (lo que importa acá):** `core` es el único servicio que escribe. `api` conecta con un rol
sin `INSERT`/`UPDATE`/`DELETE`. Toda escritura de `attachments` y `files` de esta story es de `core`.

### API Context

**El contrato es AsyncAPI, no OpenAPI.** `core` no expone HTTP: su único contrato es
`docs/apis/core.yaml`. **Ante discrepancia entre el código y el documento, manda el documento.**

**Estado actual del YAML: ya fue actualizado por REQ-001 para esta story.** El esquema `FileIds` ya
existe, los seis payloads ya declaran `fileIds`, y `attachmentScope` ya está eliminado del YAML. **Lo
que falta en el YAML es una sola cosa: los `x-error-codes`** (ver Tarea 7).

**Esquema `FileIds` (verbatim de `docs/apis/core.yaml`):**

```yaml
FileIds:
  type: array
  maxItems: 10
  description: |
    Ids from `files` to link. Each one has to exist, be alive (`retention_status: 'active'`)
    and have been uploaded by the actor of this command (REQ-001 RF-12). If any of them does
    not comply, the reply is `file_not_owned` or `invalid_fields` and **the whole write is
    discarded**.

    **Replaces `AttachmentIds`** (REQ-001, S-003). There are no drafts any more: the file
    already exists on its own and the link is created against the entity, which by then
    exists too.

    **Ownership is resolved per channel** — see `x-resolve-actor` below. It has **no
    exception by role**: an administrator cannot link a file they did not upload either
    (RF-13). Core knows nothing about roles, so the rule is uniform by construction.

    `maxItems: 10` moves the 10-file cap from `multer` to **the bus contract** (D-20): it
    stops being a transport limit and becomes a domain rule, validated by Joi.
  items:
    type: integer
    minimum: 1
```

> es la tarea con más superficie de las siete.

**`x-resolve-actor` (verbatim del `info.description` del YAML):**

```
resolveActor(ctx, payload):
  if ctx.caller == CORE_TRUSTED_PUBLISHER_ID   (the api's service user, from config)
     -> the actor is payload.author / creator / editor / uploader
        (the api ALREADY authenticated that person against Zitadel by JWT)
  else
     -> the actor is ctx.caller
        (an external publisher has no person behind it: its identity IS the subject's,
         vouched by the auth-callout and unforgeable. Whatever it declares is IGNORED)
```

Y después, uniforme para los dos canales:
`if File.uploaded_by != resolveActor(ctx, payload) -> failure(file_not_owned)`.

**Formato de `Reply` (`@jiku/nats-protocol`):**

```ts
export interface Reply<T = unknown> {
  status: 'success' | 'failure';
  errorCode?: string;
  errorMessage?: string;
  data?: T;
}
export function success<T>(data?: T): Reply<T>;
export function failure(errorCode: string, errorMessage: string): Reply<never>;
```

**Códigos de error relevantes (constantes de `@jiku/nats-protocol`, `packages/nats-protocol/src/index.ts`):**

| Constante | Valor | Cuándo en esta story |
|---|---|---|
| `ErrorCode.INVALID_FIELDS` | `invalid_fields` | Falla Joi (incluye `maxItems: 10`), o un `fileId` no existe / no está `active` → **400** |
| `ErrorCode.FILE_NOT_OWNED` | `file_not_owned` | `File.uploaded_by != resolveActor(...)` → **403** |
| `ErrorCode.PROJECT_NOT_FOUND` | `project_not_found` | Ya en uso por `requirements.new` / `tasks.new` |
| `ErrorCode.REQUIREMENT_NOT_FOUND` | `requirement_not_found` | Ya en uso |
| `ErrorCode.OBJECTIVE_NOT_FOUND` | `objective_not_found` | Ya en uso por `tasks.{id}.comment` |
| `ErrorCode.INVALID_RESPONSIBLE_PERSON` / `PERSON_NOT_FOUND` | — | Ya en uso |
| `ErrorCode.INVALID_ATTACHMENT_ID` | `invalid_attachment_id` | **Deja de emitirse por los seis comandos.** El código sigue existiendo en el paquete (no se retira: no hay CA que lo pida y el paquete es compartido) |

> `FILE_NOT_OWNED` **ya está declarado** en `packages/nats-protocol/src/index.ts:175` con un comentario
> que dice literalmente *"lo emite S-003 al vincular"*. **No lo agregues de nuevo.** Y no lo reuses
> como `invalid_attachment_id`: el YAML lo declara explícitamente **403, no 400**, porque hacer
> indistinguible *"el archivo no existe"* de *"el archivo no es tuyo"* borra la regla nueva del REQ.

#### El obstáculo del modelo `Attachment` — leé esto antes de escribir la primera línea

**El modelo `Attachment` de `@jiku/models` NO fue reducido por S-001.** El plan de S-001, Tarea 6,
lo dice literal:

> *"Esta tarea agrega `fileId` y la asociación al modelo `Attachment`, pero **no le quita** las 10
> columnas que la migración 5 dropea (...). Motivo: la `api` y `core` siguen leyendo y escribiendo
> esos campos hasta S-004/S-005, y `sequelize.sync()` los recrea en los tests. Quitarlos acá rompería
> los dos servicios y toda la suite (...). La reducción de `Attachment` pertenece a la story que corta
> sus últimos consumidores."*

Y está verificado que esos consumidores **siguen vivos**: `api/lib/routes/attachments-preview.ts`,
`attachments-download.ts`, `attachments-delete.ts`, `opus-attachments-preview.ts`,
`attachments-post.ts:96` y `opus-attachments-post.ts:210` leen y escriben `attachment.storageKey`,
`.mimeType`, `.fileName`, `.uploadedBy`. **Bajarlos es S-004/S-005, no esta story.**

**Consecuencia concreta y no negociable:** hoy el modelo declara `allowNull: false` en `fileName`,
`fileSize`, `mimeType`, `storageKey`, `storageBucket`, `storageRegion` y `uploadedBy`. Un
`Attachment.create({ entityType, entityId, fileId })` **a secas falla la validación de Sequelize** con
`notNull Violation`, el despachador lo traduce a `internal_error`, y ningún test de esta story pasa.

**Cómo se resuelve, y por qué así:** al insertar el vínculo, **copiá del `File` ya leído** los siete
campos que el modelo todavía exige:

```ts
await Attachment.create(
  {
    entityType: AttachmentEntityType.Requirement,
    entityId: requirement.id,
    fileId: file.id,
    // Transitorio: el modelo todavía declara estas columnas NOT NULL porque las rutas de
    // adjuntos de la api las leen hasta S-004/S-005. La migración 20260819_05 ya las dropeó en
    // producción, pero el esquema de TESTS lo construye sequelize.sync() desde el modelo
    // (ADR-013), así que acá siguen siendo obligatorias. Se copian del File, que es la fuente.
    // CUANDO S-004/S-005 REDUZCAN EL MODELO, ESTE BLOQUE SE BORRA ENTERO.
    fileName: file.fileName,
    fileSize: file.fileSize,
    mimeType: file.mimeType,
    storageKey: file.storageKey,
    storageBucket: file.storageBucket,
    storageRegion: file.storageRegion,
    uploadedBy: file.uploadedBy,
  },
  { transaction: ctx.transaction }
);
```

**No "arregles" esto quitándole los `allowNull: false` al modelo.** `@jiku/models` es compartido
(ADR-005) y las rutas de la api dependen de esos campos; aflojarlos rompe `api` en una story que no
declara tocarla. La copia es **fea a propósito y transitoria por diseño** — dejá el comentario, es lo
que hace que S-004/S-005 sepan qué borrar.

> **Ojo con `storage_key` UNIQUE.** La columna es UNIQUE en `attachments` y el valor se copia del
> `File`. Con **0..N vínculos por archivo** (CA-13), dos vínculos del mismo archivo intentarían
> insertar el mismo `storageKey` y el segundo violaría la UNIQUE. **CA-13 es el test que expone
> esto.** Si aparece, la salida NO es dejar de copiar (viola el NOT NULL) ni desactivar la UNIQUE en
> producción (donde la columna ya no existe): es **quitar solo `unique: true` de `storageKey` en el
> modelo `Attachment`**, que es un aflojamiento de una restricción sobre una columna que la migración
> ya dropeó, no toca a la `api` (ninguna ruta depende de esa unicidad) y desaparece con el resto del
> bloque en S-004/S-005. Registralo en el changelog de la story si lo hacés.

#### Operaciones SQL que esta story ejecuta

```sql
-- 1) leer los archivos referenciados (PK + índice (uploaded_by, byte_status))
SELECT * FROM files WHERE id IN (1234, 1235, 1236);

-- 2) el cliente reportó el PUT y se le cree (D-13)
UPDATE files SET byte_status = 'uploaded' WHERE id IN (1234, 1235, 1236);

-- 3) el vínculo, una fila por archivo, contra la entidad que YA existe
INSERT INTO attachments (entity_type, entity_id, file_id, ...) VALUES ('requirement', 412, 1234, ...);

-- 4) SOLO en los comandos de edición: desvincular lo que ya no viene
DELETE FROM attachments WHERE id = <id del vínculo>;
```

**Ninguna tabla se crea ni se altera en esta story.** No hay migraciones nuevas.

> **La desvinculación de los comandos de edición es un `DELETE` real, no un `softDelete()`.**
> `requirements-edit.ts:150-153` hoy hace `attachment.softDelete(payload.editor, ...)`, que escribe
> `retentionStatus` y `deletedAt` — dos columnas que **la migración 05 ya dropeó de `attachments`**
> (`retention_status` está en la lista de las 10 que se van; el ciclo de retención vive ahora en
> `files.retention_status`, D-04). Seguir usándolo funcionaría en tests (`sync()` recrea la columna) y
> **fallaría en producción**. El schema es explícito: *"El borrado del **vínculo** es real; el ciclo
> de retención del **archivo** vive en `files.retention_status`"*, y *"Desvincular es borrar la fila
> de `attachments`"*. Usá `Attachment.destroy({ where: { id }, force: true, transaction })` — el
> `force: true` es obligatorio, porque el hook `@BeforeDestroy` del modelo lanza sin él.

### Flow Context

Flujo **nuevo**, creado por esta story: `docs/flows/vinculacion-de-archivos.md` (status `Draft`,
stories `[S-003, S-004]`). Los pasos que corresponden a `core` en esta story son 4 y 5. El **paso 6
(desvinculación vía `attachments.{id}.delete`) es de S-004** y **no** se implementa acá.

**Paso 4 — Core resuelve el actor** (verbatim):

> Es la pieza central del flujo, y lo que ADR-007 declaró irrealizable y este rediseño convierte en
> requisito.
>
> **El problema, exacto:** `CommandContext.caller` es *"el SERVICIO que publicó, del subject"*. Para la
> `api`, el `user-id` del subject es **su service user, el mismo para todas las personas**. Entonces:
> - Validar `File.uploaded_by == ctx.caller` **rompe la web**.
> - Validar `File.uploaded_by == payload.author` **no cumple RF-14**.
>
> **Es la misma función que usa `files.request-upload`** para poblar `File.uploaded_by`. Si subir y
> vincular resolvieran la identidad distinto, nadie podría vincular lo que subió.

**Paso 5 — Core valida titularidad y escribe, todo en una transacción** (verbatim):

> El despachador abre **una** transacción (ADR-003).
>
> `core` crea la entidad y **después** valida los archivos — **validación tardía, segura por ADR-003**,
> que es el patrón que `requirements-new.ts` ya usa:
>
> 1. Cada `fileId` **existe** y tiene `retention_status: 'active'` → si no, `invalid_fields`
> 2. `File.uploaded_by == resolveActor(ctx, payload)` → si no, **`file_not_owned`** (RF-12)
>
> `entity_type` sale de los **5 valores** que quedan del enum. `entity_id` es **NOT NULL** (D-01): no
> hay draft.
>
> **La entidad y sus vínculos, juntos o ninguno** (RF-4, CA-5). Si un solo `fileId` falla la
> titularidad, **no queda ni la entidad ni un solo vínculo**. Lo que **sí queda** son los `File`, sin
> vínculo, que es un estado válido (RF-1, CA-7).

**Las cuatro combinaciones de titularidad** (verbatim del flujo):

| Subió | Vincula | Resultado |
|---|---|---|
| Usuario de la web | El mismo usuario | ✓ |
| Usuario de la web | Servicio externo | `file_not_owned` — el `uploaded_by` es un `sub` de persona; el actor resuelto es un service user |
| Servicio externo A | Servicio externo B | `file_not_owned` — dos service users distintos |
| Usuario de la web | **Un `admin`** | `file_not_owned` — **sin excepción por rol** |

**Manejo de errores del flujo, tramo `core`:**

| Condición | Reply de core | HTTP destino (S-004) |
|---|---|---|
| `fileId` inexistente o `retention_status != active` | `invalid_fields` | 400 |
| `File.uploaded_by` ≠ actor | `file_not_owned` | **403** |
| Más de 10 `fileIds` | `invalid_fields` (Joi, `maxItems: 10`) | 400 |
| Sin permiso sobre el proyecto | *(la api corta antes de publicar — CA-16, no es de core)* | 403 |

### Code Conventions

- Archivos en **`kebab-case`**, un archivo por comando: `src/commands/{entidad}/{entidad}-{accion}.ts`.
- Imports **relativos** (no paths absolutos de `tsconfig`).
- Comentarios que explican **el por qué**, en **español**. El codebase lo hace consistentemente y es lo
  que hace legible una decisión rara meses después.
- La interfaz `{Comando}Payload` se escribe **a mano** y se mantiene en sincronía con el esquema Joi.
  Es duplicación deliberada: la interfaz documenta el contrato, el esquema lo hace cumplir.
- Los esquemas Joi viven en el archivo del comando, como `const schema`, **arriba** del objeto `Command`.
- **No agregues `.unknown(true)`**: un campo de más es una discrepancia de contrato y tiene que verse.
- Los enums se derivan del modelo (`Object.values(...)`) siempre que existan ahí.
- Las reglas entre campos del payload van en el esquema (`oxor`, `and`, `with`); las que dependen de la
  base, en `execute`.
- Las columnas se declaran en **camelCase** en los modelos; Sequelize las mapea a `snake_case`.

### Reusable Code

#### Utils

**`resolveActor`** — `core/src/commands/files/resolve-actor.ts`

La pieza que esta story **comparte, no reimplementa**. Su docstring lo dice literal:

> *"S-003 COMPARTE ESTA FUNCIÓN para los seis comandos de dominio (`author` / `creator` / `editor`).
> **NO la dupliques ni la bifurques**: si subir y vincular resolvieran la identidad distinto, nadie
> podría vincular lo que subió. Por eso recibe el valor declarado en vez de leer un campo con nombre
> fijo del payload."*
>
> *"VIVE EN `commands/files/` PORQUE ES DONDE NACE. Cuando llegue S-003 y la compartan seis comandos
> de otros módulos, **conviene subirla a `commands/`**; es un rename de una línea y no hay motivo
> para anticiparlo."*

**Firma:**

```ts
export function resolveActor(
  ctx: CommandContext,
  declaredActor: string | undefined,  // payload.uploader / author / creator / editor
  component: string                   // prefijo del log, p.ej. 'requirements.new'
): string | undefined;
```

**Comportamiento:** si `ctx.caller === getTrustedPublisherId()` devuelve `declaredActor` (rama api);
si no, loguea en `warn` con el `component` y devuelve `ctx.caller` (rama externa, ignorando el cuerpo).
Devuelve `undefined` solo si la rama api recibió un `declaredActor` ausente.

**Uso de referencia** (`files-request-upload.ts:83-90`):

```ts
const actor = resolveActor(ctx, payload.uploader, COMPONENT);
if (!actor) {
  return failure(ErrorCode.INVALID_FIELDS, 'Falta el uploader del archivo');
}
```

> En los seis comandos de esta story, `creator` / `author` / `editor` son **`.required()`** en sus
> esquemas Joi, así que la rama `!actor` es inalcanzable por el canal de la api. Aun así se maneja:
> es más legible que un `internal_error` opaco, y cuesta tres líneas.

**`readFileSettings`** — `core/src/commands/files/settings.ts`. Lee las cinco claves de política desde
`system_settings` dentro de la transacción. **Esta story NO lo usa**: el tope de 10 archivos es
**regla fija, no configurable** (D-20, CA-12) y vive en el esquema Joi como `maxItems: 10`. No lo
muevas a `system_settings`.

**`buildStorageKey`, `contentDisposition`** — `core/src/commands/files/storage.ts`. **No se usan en
esta story**: no se crea ningún objeto ni se firma ninguna URL.

### Task 1: `resolveActor` compartido y el helper de vinculación

**Status:** Completed

#### Description

Crear la pieza que los seis comandos comparten, **antes** de tocar ninguno de ellos. Son dos cosas:

1. **Subir `resolveActor` de `commands/files/` a `commands/`.** Su propio docstring lo anticipa:
   *"Cuando llegue S-003 y la compartan seis comandos de otros módulos, conviene subirla a `commands/`;
   es un rename de una línea"*. Dejarla en `files/` haría que `requirements/` y `tasks/` importen desde
   el módulo de archivos, que es exactamente el acoplamiento raro que el comentario previene.
2. **Un helper `linkFiles`** que concentre la secuencia que los seis repiten: resolver el actor, leer
   los `File`, validar existencia + vida + titularidad, marcar `byte_status` y crear los `Attachment`.

Sin este helper, la regla de titularidad queda escrita seis veces y **las seis pueden divergir** — que
es el mismo modo de fallo que el docstring de `resolveActor` describe para la identidad. Es la tarea
que hace que las cinco siguientes sean casi mecánicas.

**Ojo con el límite de la convención `commands`:** *"No agregues capa de repositorio ni de servicio: el
comando es la unidad completa"*. Esto **no** es una capa: es un helper de módulo, del mismo tipo que
`pickPresent`, `validateWith`, `resolvePriority` (`tasks/priority.ts`) o `activityVisibilityLevel`
(`tasks/activity.ts`), que ya existen y son el patrón del codebase. Mantenelo como función pura +
llamadas a modelo, sin clase ni estado.

#### Acceptance Criteria

1. `core/src/commands/resolve-actor.ts` existe con **la misma función**, sin cambios de comportamiento,
   y `core/src/commands/files/resolve-actor.ts` deja de existir.
2. `files-request-upload.ts` importa desde la ubicación nueva y **su comportamiento no cambia**: los
   tests TS-22, TS-23, TS-24 de `files.test.ts` siguen pasando sin editarlos.
3. El docstring de `resolveActor` se actualiza: la nota *"VIVE EN `commands/files/` PORQUE ES DONDE
   NACE... conviene subirla"* se reemplaza por una que diga que ya vive en `commands/` y **la comparten
   siete comandos** (los seis de dominio + `files.request-upload`).
4. `core/src/commands/link-files.ts` exporta `linkFiles(...)` con esta firma:
   ```ts
   export async function linkFiles(params: {
     fileIds: number[];
     declaredActor: string | undefined;
     entityType: AttachmentEntityType;
     entityId: number;
     component: string;
     ctx: CommandContext;
   }): Promise<Reply<never> | null>;
   ```
   Devuelve `null` si vinculó bien, y un `Reply` de falla listo para retornar si no.
5. `linkFiles` ejecuta, **en este orden**:
   a. `resolveActor(ctx, declaredActor, component)`; si devuelve `undefined` → `failure(INVALID_FIELDS, 'Falta el actor del comando')`.
   b. `File.findAll({ where: { id: fileIds }, transaction: ctx.transaction })`.

   d. Si algún `File` tiene `retentionStatus !== RetentionStatus.Active` → `failure(INVALID_FIELDS, ...)`.
   e. Si algún `File` tiene `uploadedBy !== actor` → **`failure(ErrorCode.FILE_NOT_OWNED, ...)`**.
   f. `File.update({ byteStatus: ByteStatus.Uploaded }, { where: { id: fileIds }, transaction })`.
   g. Un `Attachment.create(...)` por archivo, con `{ transaction: ctx.transaction }`.
6. **El orden c → d → e es obligatorio y se documenta con un comentario**: existencia y vida se
   chequean antes que titularidad, para que un archivo inexistente dé `invalid_fields` (400) y no
   `file_not_owned` (403). TS-14, TS-15 y TS-16 lo verifican.
7. Los `Attachment.create` copian del `File` los siete campos que el modelo todavía declara NOT NULL,
   con el comentario "transitorio hasta S-004/S-005" que explica por qué (ver "El obstáculo del modelo
   `Attachment`" en el Architectural Context).
8. Los mensajes de error van en **español** y **no incluyen el `fileId`** ni ningún dato interno
   (convención `error-handling`: *"No pongas datos internos en el mensaje: ids de otras entidades..."*).
9. `linkFiles` **no abre ni cierra transacción**, no llama a `commit`/`rollback`, y **no lanza** para

10. Se decide y **se documenta con un comentario** qué pasa con un `fileId` repetido en el mismo array

11. Existe un helper hermano para la semántica de conjunto completo de los comandos de edición —

   mencionado en el documento de la story. Si el implementor escribe

5. **`noUnusedLocals` está activo.** Cada bloque de draft que se borre deja imports muertos (`Op`,

   asumiendo que es simétrica a las otras.
7. **El orden de chequeo existencia → vida → titularidad decide el código de error**, y CA-11 pide
   explícitamente que `invalid_fields` (400) y `file_not_owned` (403) sean distinguibles. Un `findAll`
   con `where: { retentionStatus: Active }` los colapsaría a los dos en "no existe". Leé sin filtrar y
   validá en memoria.
8. **La `api` sigue mandando `attachmentIds` hasta S-004.** Los tests de la `api` que ejercitan la ruta
   completa con adjuntos **van a fallar** al terminar esta story, porque el `FakeBus` ejecuta `core` de
   verdad (ADR-013). Es esperado y es de S-004 arreglarlo — pero verificá cuáles son antes de cerrar,
   para que S-004 sepa qué la espera.
