## Status

**Status:** Completed

## Story Reference

- **Story:** [S-045](../stories/S-045.columna-y-card-de-horas-trabajadas-en-el-listado-y-el-detalle.md)
- **Service:** `web`
- **Summary:** Agregar la columna "Hs. Trab." al listado de requisitos (novena columna, alimentada

## Architectural Context

### Tech Stack

- **Lenguaje:** TypeScript 5.9.3 (`strict`, target ES2017, JSX `react-jsx`)
- **Framework:** Next.js 16.1.1 (App Router) + React 19.2.3
- **Runtime:** Node.js >= 24
- **Path en el monorepo:** `web/` (workspace npm `@jiku/web`)
- **Datos:** axios (cliente de servidor, `src/lib/axios.ts`) + TanStack Query (cache)
- **Estilos:** Sass + CSS Modules + custom properties (sin librería de componentes)
- **Tests:** Vitest + Testing Library, jsdom, `TZ=UTC`, tests junto al código

`web` **no consume ningún paquete del monorepo** (`@jiku/models` incluido): sus tipos de dominio
están escritos a mano en `src/features/*/types/`. Consecuencia relevante para esta story: el tipo
`Requirement` puede divergir del schema real sin fallar en compilación, así que `totalMinutes` se
declara opcional y la UI tiene que tolerar su ausencia.

**Patrón central (data-fetching):** las tres capas, ninguna se saltea desde un componente cliente.

```
componente cliente
      │   useRequirementWorkedHours(reqid)          features/requirements/hooks/
      ▼
  useQuery({ queryKey: ['requirement-worked-hours', reqid] })   ← cache
      │   queryFn
      ▼
  getRequirementWorkedHours(reqid)                 features/requirements/services/requirementsApi.ts
      │   'use server'
      ▼
  apiClient.get('/requirements/{reqid}/worked-hours')   lib/axios.ts (interceptor → Bearer)
      ▼
  api
```

**Manejo de errores:** `error.tsx` por ruta + `ApiError` normalizado en el interceptor de respuesta
+ toasts. **La ruta `/requirements` NO tiene `error.tsx`** (es la única ruta de listado del producto
sin él) — dato relevante para CA-3/AC-3: la columna no introduce un modo de falla propio y esa
carencia no se cierra en esta story.

**Testing:** Vitest + Testing Library, archivos `*.test.tsx` junto al componente. Ya existen
`RequirementList.test.tsx`, `RequirementDetail.test.tsx` y `requirementsApi.test.ts`.

### Relevant ADRs

**ADR-011 — Query keys de TanStack Query** (recogido en `conventions/data-fetching.md`, que es la
convención custom activa del servicio):

- **Decisión:** el cache de servidor vive entero en TanStack Query. Convención de keys: `[recurso]`
  para la colección, `[recurso, id]` para el ítem, y los filtros como segundo elemento cuando
  aplican.
- **Reglas de implementación (verbatim de la convención activa):**
  - Un archivo por query en `features/{módulo}/hooks/use{Recurso}.ts`, con `'use client'`.
  - Un solo objeto `options` con defaults, no parámetros posicionales.
  - `enabled` siempre expuesto.
  - El hook **no transforma datos**. El mapeo a etiquetas y el agrupamiento van en el componente o
    en `features/{m}/utils/`.
  - Tipo de retorno explícito en la Server Action. Es el único contrato con la api que el compilador
    conoce.
  - Devolver `response.data`, nunca la respuesta de axios: el objeto de axios no es serializable a
    través del límite servidor/cliente.
  - El `baseURL` ya incluye `/api`. Las rutas que se pasan a `apiClient` empiezan en `/`.
  - **Nunca importar `apiClient` desde un componente cliente.**
  - No poner `staleTime` por query sin motivo escrito: el default de 30 s es la línea base.
  - **Los filtros vacíos y los `'all'` se descartan antes de armar el query string** (`cleanFilters`).

  Query keys ya en uso en el módulo: `['requirements', filters]`, `['requirements-count', filters]`,
  `['requirement', reqid]`. **La key nueva de esta story:** `['requirement-worked-hours', reqid]`
  (singular = ítem, según la convención).

**Convención `state-management` (custom, activa):**
- Todo dato de la api vive en TanStack Query. **Regla dura: no copiar datos de query a `useState`.**
- Los filtros de pantalla van a la URL; `include=totalMinutes` **no es un filtro de usuario** y por
  eso NO va a `searchParams`: es parte de la pantalla, se fija en el Server Component.

**Convención `styling` (custom, activa):**
- Un módulo `.scss` por componente, junto al `.tsx`. Clases en `camelCase`.
- Usar tokens (`--spacing-*`, `--font-size-*`, `--color-*`), nunca hex literal.
- `cn()` para clases condicionales, no template strings.
- **Para código nuevo: usar los mixins de breakpoint, no `@media` cruda.**

### API Context

Los dos endpoints ya están desplegados (S-043 y S-044, ambas `Completed`). `web` **no cambia el
contrato**: lo consume.

#### `GET /requirements` — el `include` de S-044

Parámetro nuevo que esta story usa:

```yaml
- name: include
  in: query
  description: |
    Lista de campos calculados adicionales, separados por coma. Único valor aceptado:
    `totalMinutes`. Ausente, la respuesta no lo trae y las subconsultas no se ejecutan.
    Un valor fuera de la lista responde 400 `invalid_fields`.

    **`count=true` lo ignora:** el conteo devuelve un entero y no hay dónde poner el
    campo, así que las subconsultas no se arrastran a un `COUNT`.
  schema: { type: string }
  example: totalMinutes
```

Respuesta `200`: `array` de `RequirementWithRelations`. Campo relevante del schema:

```yaml
totalMinutes:
  type: integer
  description: |
    Minutos imputados al requisito más los de sus tareas. **Solo presente con
    `include=totalMinutes` en `GET /requirements`**: son dos subconsultas
    correlacionadas por fila y no se pagan si no se piden. Misma gradación que el
    incluible homónimo de `core-queries.yaml`. Mismo valor que devuelve
    `GET /requirements/{reqid}/worked-hours`.
```

**Consecuencia de contrato:** `totalMinutes` es **opcional** en el tipo de `web`. Contra una api
vieja el campo no llega y la celda tiene que pintar `'—'` igual que con un 0 (CA-2).

#### `GET /requirements/{reqid}/worked-hours` — el desglose de S-043

```yaml
/requirements/{reqid}/worked-hours:
  get:
    tags: [requirements]
    summary: Horas trabajadas imputadas a un requisito
    x-roles: [user, admin]
    parameters:
      - $ref: '#/components/parameters/ReqIdPath'
    responses:
      '200':
        description: OK
        content:
          application/json:
            schema:
              type: object
              required: [requirementId, totalMinutes, byPerson]
              properties:
                requirementId: { type: integer }
                totalMinutes:
                  type: integer
                  description: |
                    Suma de todos los minutos imputados al requisito: los cargados directamente
                    más los de sus tareas. Es exactamente la suma de los `minutes` de `byPerson`.
                byPerson:
                  type: array
                  description: |
                    Desglose de minutos por persona. **Siempre presente**: vale `[]` cuando el
                    requisito no tiene horas imputadas, nunca se omite. Una fila por persona,
                    sumando las horas directas y las de tareas. Ordenado por `minutes`
                    descendente, con desempate por `personId` ascendente. Incluye personas
                    deshabilitadas, dadas de baja y sin `User` vinculado: el desglose es por
                    `Person`, no por `User`.
                  items:
                    type: object
                    required: [personId, firstName, lastName, minutes]
                    properties:
                      personId: { type: integer }
                      firstName: { type: string }
                      lastName: { type: string }
                      minutes: { type: integer }
      '401': { $ref: '#/components/responses/Unauthorized' }
      '403': { $ref: '#/components/responses/AccessDenied' }
      '404': { $ref: '#/components/responses/RequirementNotFound' }
      '500': { $ref: '#/components/responses/InternalError' }
```

**Dos garantías del contrato que la UI puede dar por ciertas y NO tiene que re-implementar:**

1. **`byPerson` viene ya ordenado de mayor a menor** (`minutes` descendente, desempate por
   `personId` ascendente). El componente **NO ordena**: renderiza en el orden que llega (CA-4).
2. **`byPerson` siempre está presente**, vale `[]` cuando no hay horas. La condición de vacío es
   `byPerson.length === 0`, no `byPerson == null` (CA-5).

**Autenticación:** el interceptor de `apiClient` inyecta el `Bearer` desde `auth()`. La restricción
de acceso vive en `api` (`x-roles: [user, admin]`); `web` no agrega ni relaja ningún control.

  `app/(loggedin)/requirements/error.tsx`.

**Interacciones (lo que esta story define):**

- encabezado `"Hs. Trab."` de tabla-requisitos · **sin evento**: no ordena ni filtra. Es la única
  columna que se declara explícitamente no accionable, para que no se lea como un `<th>` ordenable
  que no responde [REQ-010 RF-6, AC-12].

**Accesibilidad — gaps propios de la columna (registrados, NO se cierran en esta story):**

- **La columna "Hs. Trab." se lee como texto plano y su encabezado abreviado no se expande.**
  `"Hs. Trab."` es una abreviatura que un lector de pantalla deletrea o pronuncia mal, y no hay
  `abbr`, `title` ni texto accesible que dé la forma larga "Horas trabajadas". El valor de la celda
  (`"2h 30m"`) sí se lee bien. Queda registrado como gap propio de la columna; este requerimiento no
  lo cierra [REQ-010 RF-7].
- **El `"—"` de una fila sin horas no se distingue del `"—"` de un proyecto vacío.** Preexistente en
  la columna Proyecto y la de horas lo replica [REQ-010 AC-9].

**Decisiones y descartes relevantes (REQ-010, verbatim):**

- **La columna va última, después de "Creación", y no entre las de clasificación.** Es un dato de
  consulta ocasional, no de identificación.
- **El ancho sale del título (42% → 34%), no de las columnas compactas.** **Descartado** dar scroll
  horizontal a la tabla: el `body` tiene `overflow-x: hidden`.
- **El encabezado no ordena.** El motivo es de costo, no de diseño: `totalMinutes` es un calculado
  que ordenar obligaría a evaluar sobre todo el conjunto y no solo sobre la página. La consecuencia
  de UX es que el `<th>` tiene que **no parecer** ordenable —sin cursor de mano, sin flecha, sin
  hover de columna ordenable— porque un encabezado que invita al click y no responde se lee como un
  bug.
- **El cero se muestra como `"—"` y no como `"0h 0m"`.** Un cero formateado ocupa el mismo espacio
  que un valor real y obliga a leerlo para descartarlo. **Descartado** dejar la celda en blanco: una
  celda vacía se confunde con un dato que no cargó.
- **La columna es parte de la pantalla, no un filtro opcional del usuario.** No hay toggle de
  "mostrar horas". Que en la api sea opt-in es una decisión de costo del contrato.
- **Una sola request para la página entera.** Con 50 requisitos serían 50 requests para un dato
  secundario.
- **El listado no muestra el desglose por persona.** El desglose vive en el card del detalle.

- **`card-horas-trabajadas`**
  - Texto/label: título **`"Horas Trabajadas"`**
  - Annotation: card de la columna derecha, **última**, después de `"Resolución"`. Se carga por su
    cuenta, con una consulta propia y no con el payload del requisito: **si falla o tarda, el resto
    del detalle se renderiza igual** [REQ-010 RF-8, Escenario B]

- **`total-horas-trabajadas`**
  - Texto/label: el total formateado como `Xh Ym` — **`"5h 0m"` para 300 minutos**
  - Annotation: suma las horas imputadas directamente al requisito **más** las de sus tareas, sin
    doble conteo. Es el mismo número que muestra la columna `"Hs. Trab."` del listado, y siempre es
    igual a la suma del desglose de abajo [REQ-010 RF-3, AC-6, AC-10]

- **`desglose-horas-persona`**
  - Texto/label: una fila por persona — **`"{Nombre} {Apellido}"`** a la izquierda y sus horas
    formateadas `Xh Ym` a la derecha. Ejemplo: `"Ana García"` · `"3h 0m"` / `"Beto Ruiz"` · `"2h 0m"`
  - Annotation: **de mayor a menor**, la persona que más cargó primero [REQ-010 RF-1, AC-10]. Cada
    persona aparece **una sola vez**, con lo que imputó al requisito y a sus tareas ya sumado: no se
    separan las dos fuentes [REQ-010 RF-2, AC-2]. **Es un desglose histórico:** quien cargó horas
    aparece siempre, incluso si ya no está en el equipo o está deshabilitado [REQ-010 RF-3, AC-4, AC-18]

- **`vacio-horas-trabajadas`**
  - Texto/label: **`"Sin horas cargadas"`**
  - Annotation: reemplaza al total y al desglose cuando el requisito no tiene ninguna hora imputada.
    **La card sigue estando**, no desaparece: que no haya horas es en sí un dato de gestión
    [REQ-010 RF-8, AC-11]

- **`cargando-horas-trabajadas`**
  - Texto/label: **`"Cargando horas..."`**
  - Asset: imagen del componente `<Loader>`
  - Annotation: ocupa el cuerpo de la card mientras la consulta está en vuelo. Es el único loader de
    la pantalla que no depende de una mutación: la card se carga sola, después del primer render del
    detalle [REQ-010 Escenario B]

**Estados nuevos de esta story (verbatim del screen.md):**

- **`sin horas cargadas`** (parent_state: default) — **estado nuevo con REQ-010** (RF-8)
  - Mensaje: `"Sin horas cargadas"`
  - Cambios: `vacio-horas-trabajadas` solo visible en este estado; `total-horas-trabajadas` y
    `desglose-horas-persona` **ausentes** — no se muestra `"0h 0m"` ni una lista vacía;
    `card-horas-trabajadas` **presente, con su título. La card no desaparece.**
  - Disparado por un requisito sin ninguna hora imputada, ni directa ni en sus tareas: **la respuesta
    trae el total en cero y el desglose vacío** [REQ-010 RF-8, AC-3, AC-11]

- **`horas cargando`** (parent_state: default) — **estado nuevo con REQ-010** (Escenario B)
  - Mensaje: `"Cargando horas..."`
  - Cambios: `cargando-horas-trabajadas` solo visible en este estado; `total-horas-trabajadas`,
    `desglose-horas-persona` y `vacio-horas-trabajadas` ausentes. **El resto de la pantalla se
    renderiza completo y es operable**: el header, el workflow, las tareas y el feed no esperan a las
    horas.
  - **Es el primer loading de esta pantalla que no viene de una mutación.**

- **`horas no disponibles`** (parent_state: default) — **estado nuevo con REQ-010** (Escenario B)
  - Mensaje: **`"No se pudieron cargar las horas"`**
  - Cambios: `card-horas-trabajadas` presente, con el mensaje en el cuerpo en lugar del total y el
    desglose; `total-horas-trabajadas`, `desglose-horas-persona`, `vacio-horas-trabajadas` ausentes.
    **El resto del detalle no se ve afectado.** Ninguna otra sección cambia y ninguna acción se bloquea.
  - **Por qué existe como estado propio y no como toast:** es la contrapartida de que la card tenga su
    propia consulta. Sin este estado la falla se vería como `"Sin horas cargadas"` —un requisito con
    horas parecería no tenerlas—, que es el modo de falla peor: silencioso y con un dato falso en
    pantalla. Distinguir "no hay horas" de "no pude traerlas" es la razón de que el estado esté
    declarado [REQ-010 RF-8, AC-11]

**Interacciones:**

- `card-horas-trabajadas` · **sin eventos de usuario**: es una card de lectura. Ni el total ni las
  filas del desglose son clickeables — no llevan a un reporte, a la persona ni a las horas de una
  tarea [REQ-010 RF-8].

**Feedback:**

- La card de horas tiene **su propio ciclo de carga y su propio error**, separados de los del
  requisito: se revalida sola y una falla suya no toca al resto de la pantalla [REQ-010 Escenario B].

**Accesibilidad:**

- **`card-horas-trabajadas` no agrega paradas al orden de foco**: es de solo lectura y no tiene
  controles [REQ-010 RF-8].
- **El título `"Horas Trabajadas"` hereda el problema de jerarquía de las demás cards:** como los
  otros siete títulos de sección, no es un encabezado sino un `div`, así que la card nueva **no**
  agrega un punto de navegación por secciones. La carencia es de la pantalla entera y este
  requerimiento no la cierra, pero la card la agrava en un grado: son ocho secciones sin jerarquía en
  vez de siete [REQ-010 RF-8]. **Implicación para el implementador:** seguir el patrón existente
  (`<div className={styles.cardTitle}>`), NO introducir un `<h3>` que rompa la consistencia con las
  otras cuatro cards. El bloque UX lo tipa como `heading h3` en referencia al *total*, no al título
  de la card.
- **Ni la carga ni el resultado de las horas se anuncian:** el card pasa de `"Cargando horas..."` a
  mostrar el total sin región `aria-live`. Es un gap que el estado de carga propio introduce y queda
  registrado **sin cerrarse acá** [REQ-010 Escenario B].

**Decisiones y descartes relevantes (REQ-010, verbatim):**

- **El desglose vive en el detalle y el total en el listado, no al revés.**
- **La card se carga sola, con su propia consulta, y no cuelga del payload del requisito.** Es la
  decisión de UX más consecuente del cambio: si el desglose viajara con el requisito, se recargaría
  en cada edición inline del header —que son muchas— y una falla suya rompería el detalle entero.
- **`"No se pudieron cargar las horas"` es un estado declarado y no un toast.**
- **La card se queda cuando no hay horas, con `"Sin horas cargadas"`.** **Descartado** ocultarla.
- **El total se muestra además del desglose, aunque sea la suma de lo que está debajo.** La
  redundancia es deliberada.
- **Una fila por persona, con las dos fuentes ya sumadas.** **Descartado** separar "directas" y "de
  tareas".
- **El desglose es histórico y no filtra a nadie.**
- **La card va última en la columna derecha.**
- **Nada de esto llega a `opus-web`.**

### Task 2: `include=totalMinutes` fijo en la request del listado

**Status:** Completed

**Categoría:** Data

#### Description

Hacer que el listado pida `totalMinutes` en la request que ya hace, **sin agregar un round-trip**.
El `include` es parte de la pantalla, no un filtro que el usuario elija: se fija en el Server
Component junto a los defaults, y **no va a `searchParams`**.

Hay un detalle que es la razón por la que esta tarea existe aparte: `getRequirementsCount` comparte
el mismo objeto de filtros y **no debe** llevar `include`. El contrato dice que `count=true` lo
ignora, pero mandarlo igual arrastraría un parámetro sin efecto y confundiría el próximo cambio.
Además `useRequirementsCount` recibe hoy el mismo `filters` que `useRequirements`, así que hay que
recortarlo explícitamente.

#### Acceptance Criteria

1. `app/(loggedin)/requirements/page.tsx` arma `filters` con `include: 'totalMinutes'` fijo, junto a
   los defaults ya existentes.
2. `include` **no** se lee de `searchParams` ni se escribe en la URL: no es un filtro de usuario.
3. `getRequirements` serializa `include=totalMinutes` en la query string (vía `cleanFilters`, sin
   tocar el helper).
4. La request del listado sigue siendo **una sola** para la página entera: no se agrega ninguna
   llamada por fila.
5. La request de conteo (`getRequirementsCount`) **no** lleva `include`.
6. `RequirementList` sigue llamando a `useRequirementsCount` con el mismo conjunto de filtros que la
   api necesita para contar, pero sin `include`.

#### Technical Details

**Architectural Context References:**
- **ADR-011 / convención `data-fetching`** → `cleanFilters` descarta falsy y `'all'`;
  `'totalMinutes'` es truthy y distinto de `'all'`, así que sobrevive sin modificar el helper.
- **Convención `state-management`** → "si el filtro identifica la pantalla, va a la URL". `include`
  **no** identifica la pantalla: es parte de qué datos la pantalla necesita, no de qué recorte está
  viendo el usuario. Por eso NO va a la URL.
- **API Context** → `GET /requirements`, parámetro `include`: *"`count=true` lo ignora: el conteo
  devuelve un entero y no hay dónde poner el campo"*.
- **Reusable Code** → `cleanFilters` (`requirementsApi.ts:15-19`).

**Files to Create/Modify:**
- `src/app/(loggedin)/requirements/page.tsx` (modificar)
- `src/features/requirements/components/RequirementList/RequirementList.tsx` (modificar — recorte del
  `include` antes de pasar a `useRequirementsCount`)

**Implementation Notes:**
- En `page.tsx`, agregar la línea junto a `DEFAULT_STATE_FILTER`, con un comentario que explique **el
  porqué** (la columna es parte de la pantalla, no una opción del usuario) — es exactamente el tipo
  de "por qué no obvio" que la convención `_base` pide comentar.
- El `include` entra en el objeto `filters`, y por lo tanto en la **query key**

- **No** tocar `getRequirements` ni `getRequirementsCount`: el mecanismo de serialización ya

### Task 5: El componente `RequirementWorkedHoursCard`

**Status:** Completed

**Categoría:** UI

#### Description

El card "Horas Trabajadas" con sus cuatro cuerpos posibles: total + desglose, vacío, cargando y
error. **El título está siempre**, en los cuatro: la card no desaparece nunca, porque que un
requisito no tenga horas es en sí un dato de gestión.

La distinción que más importa de las cuatro es entre **vacío** y **error**. Sin un estado de error
propio, una falla se vería como `"Sin horas cargadas"` — un requisito con horas mostrando que no las
tiene, que es el modo de falla peor: silencioso y con un dato falso en pantalla.

#### Acceptance Criteria

1. El card siempre renderiza el título `"Horas Trabajadas"`, en los cuatro estados.
2. Con datos y `byPerson.length > 0`: muestra el total con `formatMinutes(totalMinutes)` y una fila
   por persona con `"{firstName} {lastName}"` y `formatMinutes(minutes)`.
3. Las filas se renderizan **en el orden en que llegan**: el componente no ordena.
4. Con `byPerson.length === 0`: muestra `"Sin horas cargadas"` y **no** muestra el total ni la lista.
5. Con `isLoading`: muestra `<Loader label="Cargando horas..." />` y nada más en el cuerpo.
6. Con `isError`: muestra `"No se pudieron cargar las horas"` y **no** muestra `"Sin horas cargadas"`.
7. El card no tiene ningún control interactivo: ni el total ni las filas son clickeables, y no agrega
   paradas al orden de foco.
8. El título usa el mismo patrón que las otras cuatro cards (`<div className={styles.cardTitle}>`),
   no un `<h3>`.
9. Reutiliza las clases `.card`, `.cardTitle` y `.emptyText` existentes; no introduce hex literales.
