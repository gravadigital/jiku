### Tech Stack / convenciones del directorio

| Aspecto | Valor |
|---|---|
| Idioma | `deploy/nats/auth-callout/README.md` y comentarios de plantillas: **castellano**. `deploy/README.md`: **inglés**. Respetar el idioma de cada archivo |

### La política final del bus (verbatim de `deploy/nats/auth-callout/`)

**`rules.yaml`** (orden): `docs → docs.yaml`, `internal-app → connector.yaml`, `core → core.yaml`,
`admin → person-internal.yaml`, `user → person-internal.yaml`, `external-user → person-external.yaml`.
Sin catch-all.

`KV_READ_WATCH` (idéntico en `connector`, `docs`, `person-internal`, `person-external`):

```yaml
- "$JS.API.INFO"
- "$JS.API.STREAM.INFO.KV_JIKU_MODULES"
- "$JS.API.DIRECT.GET.KV_JIKU_MODULES.>"
- "$JS.API.CONSUMER.CREATE.KV_JIKU_MODULES"
- "$JS.API.CONSUMER.CREATE.KV_JIKU_MODULES.>"
- "$JS.FC.KV_JIKU_MODULES.>"
```

**`connector.yaml`** (`internal-app`): pub `{{instance}}.{{user_id}}.jiku-commands.v1.>`,
`…jiku-queries.v1.>`, `…jiku-docs-commands.v1.>`, `…jiku-docs-queries.v1.>`, `$SRV.PING.>`, las
cinco formas de consumo de `JIKU_EVENTS` y de `JIKU_DOCS_EVENTS` (más `$JS.API.INFO`), y
`KV_READ_WATCH`. Sub `{{instance}}.events.v1.>`, `_INBOX.{{user_id_hash}}.>`. `response.max: 0`.

**`docs.yaml`** (`docs`): todo `connector.yaml` + pub `{{instance}}.docs-events.v1.>`,
`{{instance}}.*.docs-notify.v1.>`, `$JS.API.STREAM.*.JIKU_DOCS_EVENTS`, `$KV.JIKU_MODULES.docs`; sub
además `{{instance}}.*.jiku-docs-commands.v1.>`, `{{instance}}.*.jiku-docs-queries.v1.>`, `$SRV.>`.
`response: { max: 1, ttl: 45s }`.

**`core.yaml`**: sin cambios desde antes de REQ-016. **Su comentario de encabezado dice**:

```yaml
# El servicio `core`: atiende los dos planos y publica eventos de dominio. Ver README.md.
#
# Es el ÚNICO que recibe requests por el bus (el único con `sub.allow` de servicio).
```

Falso desde S-075: `docs.yaml` también tiene `sub.allow` de servicio. Anotado como "inconsistencia
conocida" en las notas de implementación del plan S-075 deploy ("queda para un ajuste de comentario
aparte").

**`person-internal.yaml`** (`admin`, `user`): pub `…jiku-queries.v1.>`, `…jiku-commands.v1.>`,
`…jiku-docs-queries.v1.>`, `…jiku-docs-commands.v1.>` (todos bajo `{{instance}}.{{user_id}}`) +
`KV_READ_WATCH`. Sub `_INBOX.{{user_id_hash}}.>`, `{{instance}}.{{user_id}}.docs-notify.v1.>`. **Sin
`response`.**

**`person-external.yaml`** (`external-user`): pub `…jiku-queries.v1.>`, `…jiku-docs-queries.v1.>` +
`KV_READ_WATCH`. Sub `_INBOX.{{user_id_hash}}.>`. **Sin `response`.**

Ninguna plantilla de persona tiene `$SRV.PING` (H-P5 de S-075: el estado del módulo lo da el
registro, no el ping).

### Hallazgos de este planeamiento (lo que falta)

**H-1 · El README del callout dice que el bucket "ya está versionado".** Sección "Habilitar el módulo
de documentación", texto vigente:

> **Nada de este directorio hay que tocar**: la regla `docs`, su plantilla y el bucket del registro
> ya están versionados.

La regla y la plantilla sí; **el bucket no**: es estado de JetStream de cada instalación y lo crea
`../create-modules-kv.sh` (en local lo invoca `local.sh up`; en un servidor, a mano). La propia
sección "El registro de módulos" del mismo README lo dice bien ("el bucket es infraestructura"). Un
operador que siga la lista de "Habilitar…" literal se queda sin registro y el módulo figura
`not_installed` para siempre (la api reintenta cada 30 s sin error visible más que su log, DD-6 —
`api/lib/modules/registry.ts`, `open()`).

**H-2 · El cierre del README del callout atribuye `response.max: 0` a plantillas que no lo
declaran.** Texto vigente:

> Todos los demás solo emiten y escuchan su propio inbox, y por eso sus plantillas llevan
> `response.max: 0`.

Solo `connector.yaml` declara `response.max: 0`; `person-internal.yaml` y `person-external.yaml` no
tienen bloque `response`. Además, desde S-075 la persona interna escucha **dos** cosas (su inbox y
`docs-notify` bajo su id), no "solo su propio inbox".

**H-3 · La "Verificación manual" del README del callout no menciona la sonda de S-075.** Existe
`deploy/nats/bus-policy-probe.sh` (+ `core/tests/tools/bus-policy-probe.ts`): se conecta al bus real
como una identidad real (sentinel + token de Zitadel), recorre la matriz allow/deny de un perfil
(`docs | connector | person-internal | person-external`) y usa el log del servidor NATS como
oráculo (cuenta líneas `Publish Violation|Subscription Violation` antes y después); exit 0 solo si
todo coincide. Precondiciones (encabezado del script): stack local arriba, `JIKU_MODULES` creado, el
auth-callout reiniciado tras editar plantillas; las keys de service user se pasan por `--key` y viven
fuera del repo. Uso: `./bus-policy-probe.sh --profile <perfil> --key <service-user.json>`. La
checklist manual (3 pasos) solo cubre el plano de comandos de core.
**Límite conocido, a no sobredocumentar:** el QA de S-075 registró que la sonda todavía no cubre el
alta/consumo/ack de `JIKU_DOCS_EVENTS`, la relectura de `docs`, el `request` a core ni la escritura
durante el watch, y que **nunca se corrió contra el bus real** (Task 6 de S-075 pendiente; H-P4,
`$JS.ACK.JIKU_DOCS_EVENTS`, sin veredicto). El README describe la herramienta y qué verifica, sin
afirmar cobertura que no tiene.

**H-4 · `deploy/README.md` — el árbol de `nats/` no lista `bus-policy-probe.sh`.** Lista
`events-test-consumer.sh` (la sonda análoga de S-067) pero no la de S-075.

**H-5 · `deploy/README.md` — "Letting an external service publish" describe el `connector.yaml`
anterior.** "Mind how much this grants" dice que `internal-app` publica bajo `jiku-commands.v1.>` y
`jiku-queries.v1.>`; no menciona que ahora también publica comandos y consultas **de docs** bajo su
id, hace ping (`$SRV.PING.>`), consume `JIKU_DOCS_EVENTS` y lee/observa `JIKU_MODULES`, ni R-3:
jiku-docs trata a todo `internal-app` como clase `service` y **le deja leer toda la documentación**
(aceptado en D-2). Ampliar `connector.yaml` amplía a todos los `internal-app`.

**H-6 · `deploy/README.md` — "Letting a person write to the bus" afirma algo que S-075 volvió
falso.** Texto vigente sobre `person-external.yaml`:

> authorises **only** `{instance}.{user-id}.jiku-queries.v1.>` plus the same inbox — the exact
> permission the old shared template granted, unchanged.

Hoy suma `jiku-docs-queries.v1.>` y `KV_READ_WATCH`. El bullet de `person-internal.yaml` tampoco
menciona `jiku-docs-*`, `docs-notify` ni `KV_READ_WATCH`. La tabla de callers no tiene el plano de
docs ni la fila `docs`. La checklist manual no incluye los dos chequeos de docs que separan a
`external-user` (no publica `jiku-docs-commands`, no escucha `docs-notify`).
"Neither template declares `$SRV.>` discovery or a service subscription" **sigue siendo cierto**
(`docs-notify` bajo su id no es suscripción de servicio) y se conserva, sumando que tampoco tienen
`$SRV.PING` (H-P5).

**H-7 · `deploy/README.md` — Notes: "JetStream is enabled, but scoped to domain events only".** El
bullet dice que JetStream respalda **solo** `JIKU_EVENTS`. Desde REQ-016 hay dos más:
`JIKU_DOCS_EVENTS` (lo crea y administra jiku-docs, solo si el módulo está instalado) y
`KV_JIKU_MODULES` (el bucket del registro, lo crea `create-modules-kv.sh`). Lo de core (sin
`$JS.API`) sigue vigente y no se toca.

**H-8 · `deploy/README.md` — "On a server": los dos `create-*` no funcionan como están escritos.**
El bloque corre `./create-events-stream.sh` y `./create-modules-kv.sh` **antes** de
`docker compose up -d` y **sin** `NATS_DOCKER_NETWORK`. Los dos scripts hablan con NATS por
`docker run --network "${NATS_DOCKER_NETWORK:-jiku-local_jiku}"` + `nats://nats:4222`: en producción
(a) NATS todavía no está arriba y (b) la red es `jiku_jiku-bus`, no `jiku-local_jiku`. La línea de
`create-events-stream.sh` es anterior a REQ-016 (S-061); la de `create-modules-kv.sh` la agregó
S-075 copiando la forma. `NATS_DOCKER_NETWORK` no está documentada en ningún lado.
**Corrección:** igual que `local.sh` (que invoca `create-modules-kv.sh` después de `up` y del
`healthz`), en "On a server" los dos scripts van **después** de `docker compose up -d`, con
`NATS_DOCKER_NETWORK=jiku_jiku-bus`, y una nota que explique la variable. Es seguro para la api: si
el registro no existe al arrancar, `ModuleRegistry.open()` no rechaza y se reintenta cada 30 s
(DD-6), así que el módulo aparece solo cuando el bucket existe.
**No se cambia ningún script** (cambiar el default rompería local). Si `STAGE`/`name:` del compose
se cambiaran, la red cambia con ellos: la nota dice cómo verla (`docker network ls | grep jiku-bus`).
