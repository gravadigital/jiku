# Story Plan: S-034 (api) - La api deja de autorizar y de exigir fila en `users`

## Status

**Status:** Completed

## Story Reference

- **Story:** [S-034](../stories/S-034.la-api-deja-de-autorizar.md)
- **Service:** `api`
- **Summary:** `validateToken` deja de exigir una fila en `users` y arma `req.user` desde el claim ya
  verificado; el 401 `user_not_found` y su excepción de `/api/auth/present` desaparecen. Las rutas de
  escritura pierden `hasAnyRole` y el chequeo de entidad —ya viven en `core` (S-030/S-031/S-032/S-033)—;
  las 28 rutas `GET` **no se tocan**. Se retira además la validación de URI de `projects-*` (ya
  implementada en `core`) y se verifica que no quede residuo de límites de archivo. Es un diff de solo
  eliminaciones (CA-12): si algo agrega una regla nueva, se pasó de alcance.

## Architectural Context

### Tech Stack

- **Lenguaje:** TypeScript (sin `strict`), Node.js.
- **Framework HTTP:** Express 5, un archivo por endpoint bajo `api/lib/routes/`, montaje automático
  vía barrel (`api/lib/routes/index.ts` + `app.ts:35-37`).
- **ORM:** Sequelize, conectado con un rol de PostgreSQL de **solo lectura**
  (`api/lib/models/index.ts:19-31`). La api no escribe salvo las tres excepciones documentadas
  (migraciones, `Attachment.create()` legado ya eliminado por S-004/S-005, y
  `PUT /api/week-assigned-times`).
- **Validación:** Joi 18, esquema declarado inline en el archivo de la ruta.
- **Bus:** `nats` 2.29 + `@jiku/nats-protocol`, request/reply síncrono contra `core`.
- **Auth:** `jsonwebtoken` 9 contra el JWKS de Zitadel, con reintento por `kid` desconocido.
- **Testing:** Mocha 11.7 + `should` + `sinon`, PostgreSQL real efímero, `FakeBus` que ejecuta
  `core` real por default.

No hay `src/`; el dominio vive en el **prefijo del nombre del archivo de ruta**
(`{recurso}-{path}-{método}.ts`). Imports relativos, sin paths de `tsconfig`.

**Errores:** sin clases, `res.status(n).json({ code, message })` directo en cada punto. `code` es
`snake_case` estable (los fronts hacen `switch`). `message` es texto de interfaz, en español para
mensajes nuevos.

**Testing:** Mocha + base real (el contenedor de test usa un rol con permisos completos, no el de
producción). El `FakeBus` está instalado globalmente (`tests/setup-env.ts:31`, `setBus(fakeBus)`) y se
resetea antes de cada test por root hook — **no llamar `setBus` en un archivo de test**.

### Convención `auth-jwt` (`docs/architectures/api/conventions/auth-jwt.md`)

**El flujo actual de `validateToken`** (`api/lib/utils/middlewares/validate-token.ts`):

```
Authorization: Bearer <jwt>
  ▼
decodeAuthToken(token)                          jwt.verify con getKey + resync por kid desconocido
  ▼
req.decodedToken, req.decodedTokenRoles         roles del claim urn:zitadel:iam:org:project:roles
  ▼
User.findByPk(decodedToken.sub)                 ← ESTO SE ELIMINA (D-6)
  │  no existe → 401 user_not_found  (excepto /api/auth/present)   ← ESTO SE ELIMINA
  ▼
req.user   →   next()
```

**El flujo objetivo** (D-6 de la story): `req.user` se arma **del claim ya verificado**, sin consultar
la base:

```
req.user = { id: decodedToken.sub, name, username, email, roles: decodedTokenRoles }
```

- `name` sale de `decodedToken.name` (opcional).
- `username` sale de `decodedToken.preferred_username` (opcional; el claim OIDC se llama distinto
  que el campo del sobre — la traducción ya existe en `buildActor`, mismo criterio a replicar acá).
- `email` sale de `decodedToken.email` (opcional).
- `roles` sale de `decodedTokenRoles` (siempre presente, `[]` si no hay claim de roles).

**`DecodedToken` ya declara estos tres campos como opcionales** (`api/lib/interfaces/decoded-token.ts`),
con el comentario: *"Los tres son OPCIONALES porque el access token los trae SOLO si la instancia de
Zitadel los emite con los scopes `profile`/`email`... Su ausencia no rechaza nada: el espejo de core es
best-effort en los campos de perfil (CA-11)"*. No hace falta tocar esta interfaz.

**Reglas de la convención que aplican a esta story:**
- No agregues `validateToken` a la cadena de una ruta: ya está global. Es redundante (varias rutas
  igual lo declaran explícito hoy — `week-assigned-times-put.ts`, `unworked-times-post.ts`,
  `unworked-times-id-delete.ts`, `attachments-delete.ts` — y **eso no se toca**, es ortogonal).
- Los errores de autenticación son 401 con `unauthorized`. `user_not_found` desaparece.
- El id del usuario que actúa se toma de `req.user.id`, nunca del cuerpo — **esto no cambia**: el
  claim también trae `sub` como `id`.

### Convención `authorization` (`docs/architectures/api/conventions/authorization.md`)

Las tres capas:
```
1. Autenticación global   app.ts → validateToken           ¿hay un usuario válido?
2. Rol                    hasAnyRole(['user','admin'])      ¿su rol alcanza esta ruta?
3. Entidad                validateProjectPermissions        ¿puede tocar ESTE proyecto?
                          canUserAccessEntity / canUserViewEntity
```

- Capa 2 se **elimina de las rutas de escritura** (CA-5), se **conserva en las 28 `GET`** (CA-6).
- Capa 3 (`validateProjectPermissions` / `canUserAccessEntity`) se **elimina de las rutas de
  escritura** (CA-7) — con la excepción documentada más abajo para `attachments-delete.ts`.
  `canUserViewEntity` en las rutas de lectura de adjuntos **no se toca**.

### Convención `bus-commands` — el criterio ya fue aplicado por S-031/S-032/S-033

> *"Si el comando necesita el rol, el usuario final o la fecha de hoy para validarse, ESO YA NO LO
> DEJA EN LA API... si decide si la operación puede ocurrir sobre estos datos y tiene que dar el
> mismo resultado por HTTP y por el bus, va al comando de core; si es del transporte HTTP —la forma
> del input, la traducción de nombres de contrato, el 404 de la entidad del path, un código que el

Este es el criterio que ya se aplicó a `worked-times-post.ts`, `worked-times-id-delete.ts`,

Esta story lo termina de aplicar a lo que falta: rol y entidad en el resto de las rutas de escritura.

### El sobre de identidad (S-029) — ya en producción, no se toca

`api/lib/utils/bus/actor.ts` (`buildActor`) arma el sobre `actor` **desde `req.decodedToken`**, nunca
desde `req.user`, y ya está inyectado por `sendCommand`/`withActor` en el embudo (`send-command.ts`)
para las 27 publicaciones. Esta pieza **no cambia con esta story** — ya lee el claim directamente y es
el precedente exacto del patrón que `validateToken` va a aplicar para `req.user`.

```ts
// api/lib/utils/bus/actor.ts — ya existe, no se toca
export function buildActor(req: Request | undefined): Actor | undefined {
  const decoded = req?.decodedToken;
  const id = claimString(decoded?.sub);
  if (!id) return undefined;
  const actor: Actor = { id, roles: req?.decodedTokenRoles ?? [] };
  const name = claimString(decoded?.name);
  if (name) actor.name = name;
  const username = claimString(decoded?.preferred_username);   // OIDC → username, traducción acá
  if (username) actor.username = username;
  const email = claimString(decoded?.email);
  if (email) actor.email = email;
  return actor;
}
```

`actorId(req)` (`send-command.ts:150`) sigue siendo `req.user.id` — con el claim, `req.user.id` va a
seguir siendo el mismo valor (`decodedToken.sub`), así que las 19 llamadas a `actorId(req)` **no se
tocan**.

`core/src/commands/projects/properties.ts` ya valida `documentacion`, `diseño` y `board_de_tareas`

### Riesgo crítico detectado en el análisis — `attachments-delete.ts` NO puede perder su chequeo de entidad sin abrir un hueco

**Esto es una excepción a CA-7 que hay que declarar explícitamente, no una tarea de eliminación
más.** El análisis de esta story encontró que `core/src/entity-project.ts` (S-030) **documenta la
brecha de punta a punta**, con esta nota literal en el código:

> *"LO QUE NO SE ESPEJA, Y ES UNA DECISIÓN (D-5): las reglas finas de `canUserAccessObjective`
> —`admin` siempre, o ser creador, o estar asignado a la tarea—. CA-8 pide la correspondencia a
> proyecto y CA-7 pide la fila en `user_project_permissions`: eso es la forma de `canUserViewEntity`,
> no la de `canUserAccessObjective`. Las reglas finas SIGUEN EN LA API, que las aplica delante
> (CA-14: esta story no elimina nada). LA CONSECUENCIA HAY QUE ESCRIBIRLA: para
> `attachments.{id}.delete` sobre un `objective`, el chequeo de `core` es MÁS PERMISIVO que el de la
> api. Nada se abre, porque la api sigue corriendo primero. EL DÍA QUE LA API DEJE DE AUTORIZAR
> (S-034) alguien tiene que decidir si esas reglas se mudan o se resignan."*

**El detalle concreto:** `attachments-delete.ts` llama a `canUserAccessEntity(userId, roles,
entityType, entityId)`. Para `entityType === 'objective'`, esa función (`canUserAccessObjective` en
`api/lib/utils/attachments-access.ts`) exige, para un `user` interno (no `admin`): tener permiso en el
proyecto, **o** ser el creador de la tarea, **o** estar asignado a ella. `core`'s
`authorizeEntityAccess` (`core/src/entity-project.ts`) **solo corre en modo externo**
(`callerClass === 'external'`); para `admin`/`user` no hay ningún chequeo de fila — coincide con
`validateProjectPermissions`, pero **no** con `canUserAccessObjective`, que sí restringe a `user`.

**Consecuencia si se elimina sin más:** cualquier `user` autenticado podría desvincular un archivo de
**cualquier** tarea de **cualquier** proyecto, sin ser su creador, sin estar asignado y sin permiso de
proyecto — porque `core` no tiene esa regla y la api dejaría de aplicarla.

**Decisión para esta story (mínimo viable, sin ampliar alcance):** `attachments-delete.ts`
**conserva** su llamada a `canUserAccessEntity` como **excepción declarada** a CA-7, documentada en el
propio archivo con la referencia a `core/src/entity-project.ts` (D-5) y a esta story. Mudar la regla
fina a `core` es trabajo nuevo (un comando que hoy no tiene esa validación empieza a tenerla) y CA-12
exige que el diff de esta story sea **solo de eliminaciones** — agregarla en `core` violaría eso. La
alternativa (eliminar sin más) abre un hueco de autorización real. Ninguna de las dos es "terminar
CA-7 tal cual está escrito", así que la Tarea 5 dedicada a `attachments-delete.ts` deja el código
como está y **documenta por qué**, en vez de tocarlo — que es la lectura correcta de H-4 ("verificar,
no construir") aplicada a un caso donde la verificación dio un resultado inesperado. **Este punto se
reporta al usuario en el resumen final de la story, para que decida si abre una story de seguimiento
que mude la regla fina a `core`.**

### Tests a actualizar

`token_01_user`/`token_02_user`/`token_03_admin`/`token_04_external_user` **no** traen claims de

### Documentación técnica del servicio (fuera del código, referencia)

`documentation/known-limitations.md` (sección *"Users are only created for identities that connect to
the bus"*) describe el comportamiento que esta story deroga: *"a person who authenticates but is not
in `users` gets 401 `user_not_found` from every route"*. **No es parte del entregable de código de
esta story** (es documentación de producto, no de `docs/architectures/api/`), pero el hallazgo se
reporta en el resumen final para que se actualice junto con el cierre del REQ (Step 5 del
procedimiento de release, o antes si el usuario lo pide).

### Task 1: `validateToken` arma `req.user` del claim y elimina el 401 `user_not_found`

**Status:** Completed

#### Description

Es el corazón de la story (D-6, H-5). `validateToken` deja de consultar `users` para autenticar:
construye `req.user` directamente desde `req.decodedToken` y `req.decodedTokenRoles`, ya verificados
contra el JWKS. Esto elimina un `SELECT` por request en las 61 rutas (CA-19) y hace que una identidad
sin fila previa opere desde la primera pantalla (CA-1, CA-2). La excepción de `/api/auth/present`
deja de tener sentido porque ya no hay chequeo del que eximirla (CA-4).

#### Acceptance Criteria

1. `validate-token.ts` ya no importa ni llama a `User.findByPk`.
2. En la rama sin bypass, tras `decodeAuthToken`, `req.user` se arma con

   base.
3. El branch `if (!user && req.path !== '/api/auth/present') { 401 user_not_found }` se elimina
   completo.
4. `req.user.id` sigue siendo el `sub` del token — cualquier código que use `req.user.id` (61 rutas,
   `actorId()`, `validate-project-permission.ts`) sigue funcionando sin tocarlo.
5. El 401 `unauthorized` (sin token, token inválido, fallo de `decodeAuthToken`) no cambia.
6. La rama de `AUTH_BYPASS` (`validate-token.ts:66-90`) **no se toca**: sigue haciendo
   `User.findByPk(DEV_USER_ID)` — es una herramienta de desarrollo local con su propio candado
   (`assertAuthConfig`), no la ruta de producción que esta story ataca. Modificarla está fuera de
   alcance.
7. `auth-present-post.ts` sigue respondiendo `200 {}` sin tocar la base; se actualiza su comentario
   para reflejar que ya no hay 401 del que eximirla.
8. `docs/apis/api.yaml` **ya está actualizado** con el contrato objetivo — no requiere cambios en
   esta tarea, solo verificar que el código termine coincidiendo (ya lo revisó el planning: el spec
   documenta exactamente este comportamiento en `securitySchemes.bearerAuth`, `POST /auth/present` y
   `components/responses/Unauthorized`).
