# REQ-017: Roles de usuarios para conectores y cierre de brechas de docs (seguimiento de REQ-016)

## Requerimiento Original

> Seguimiento de REQ-016, que ya está implementado y mergeado en `feat/jiku-docs`:
>
> 1. **core expone `roles` e `identityType` de `users` solo a la clase `connector`.** Es la decisión
>    D-10 de `conectores/jiku-docs/docs/decisiones-integracion.md`.
>    - jiku-docs clasifica a quien lo llama con
>      `users.list {filter:{id:[...]}, include:["roles","identityType"]}`. Hoy
>      `core/src/queries/users/users-spec.ts` los excluye a propósito (CA-7). Sin ellos, jiku-docs
>      responde `upstream_unavailable` a cualquier persona, y bloquea la integración.
>    - Quedan como incluibles solo para callers de clase `connector` (roles `internal-app`, y por lo
>      tanto `docs`), sin filtro ni orden.
>    - Para personas internas y externas siguen sin existir: responden `invalid_fields` y
>      `meta.describe` no los muestra. Así CA-7 se mantiene para quien importa.
>    - Tests de ambos lados, más la actualización de `docs/apis/core-queries.yaml` y su test de
>      paridad si existe.
>    - Si la ficha no admite "incluible por clase", diseñá el mecanismo mínimo y consistente con
>      ADR-008.
> 2. **Cerrar la brecha de `GET /opus/docs/attachments/{id}`.** Hoy un usuario interno que entra al
>    portal opus-web y conoce el id de un adjunto de un documento `internal` puede descargarlo. Por
>    el portal solo se sirven adjuntos de documentos `public`, sin importar el rol de quien pida.
>    Revisá también las demás rutas `/opus/docs/*` con el mismo criterio.
> 3. **Correcciones en `docs/apis/api.yaml` que quedaron reportadas en ADR-015:**
>    - el conteo de endpoints del encabezado;
>    - el 400 que declara `DELETE /docs/shares/{id}` y que el handler no produce;
>    - el 413 que falta en las escrituras de docs con cuerpo grande.
>
>    Actualizá también los conteos desactualizados en `README.md`,
>    `documentation/api-reference.md`, `docs/architectures/api/conventions/_base.md`,
>    `documentation/installation.md` y `documentation/known-limitations.md`.

## Clarificaciones

### Supuestos (modo automático)

El dueño del producto delegó todas las decisiones; no se hicieron preguntas. Cada ambigüedad se
resolvió así:

- **[Qué significa "incluible por clase"]:** → **Supuesto tomado:** `roles` e `identityType` se
  agregan a la ficha de `users` como campos **incluibles restringidos a la clase `connector`**. Para
  un caller `connector` se comportan como cualquier incluible (se piden en `include`, salen en
  `meta.describe` y se devuelven); para `person-internal` y `person-external` **no existen**: pedirlos
  en `include`, `fields`, `filter` o `sort` responde `invalid_fields` exactamente igual que un nombre
  inexistente, y `meta.describe` no los lista. Si el motor no soporta esa restricción, el diseño agrega
  el mecanismo mínimo **declarativo en la ficha** (un dato, no código en el handler), consistente con
  ADR-008: "no está declarado para tu clase" es la única forma de "no se puede pedir".
- **[Filtro y orden]:** → **Supuesto tomado:** ni filtrables ni ordenables, ni para la clase
  `connector`. Tampoco entran en `q`.
- **[Forma de los valores]:** → **Supuesto tomado:** `roles` sale como lista de strings tal como está
  en la tabla (incluye roles que core no conoce, como `docs`) e `identityType` como string con los
  valores de la columna (`person` / `service`). El diseño fija la forma exacta según el esquema real.
- **[Quién es `connector`]:** → **Supuesto tomado:** la clase que core ya calcula (S-023): un usuario
  con rol `internal-app`, con o sin roles adicionales desconocidos. jiku-docs (`[internal-app, docs]`)
  y la api quedan dentro. Un `admin` o `user` humano **no** es `connector`.
- **[Contrato de core]:** → **Supuesto tomado:** `docs/apis/core-queries.yaml` documenta los dos
  incluibles con su restricción de clase; si existe un test de paridad entre la ficha y el contrato,
  se actualiza para que entienda la restricción.
- **[Cómo se cierra la brecha del portal]:** el reply de `attachments.{id}.request-download` no trae
  la visibilidad del documento (F-13). → **Supuesto tomado:** la api **no sirve un adjunto por el
  portal sin haber verificado que pertenece a un documento `public`**, para cualquier rol. El diseño
  elige el mecanismo con lo que el contrato de jiku-docs ya ofrece (por ejemplo, exigir el id del
  documento y comprobar visibilidad y pertenencia con `documents.get` / `attachments.list`); si eso
  cambia lo que manda opus-web, opus-web se ajusta en la misma entrega. Jiku-docs no se modifica.
- **[Cuando no es `public`]:** → **Supuesto tomado:** 404 `attachment_not_found` (o
  `document_not_found` si el error es del documento), indistinguible de un adjunto inexistente. Nunca
  403: el portal no revela que existe un documento interno.
- **[Las demás rutas `/opus/docs/*`]:** → **Supuesto tomado:** se revisan `GET /opus/docs/documents` y
  `GET /opus/docs/documents/{id}` con el mismo criterio (solo `public`, sin importar el rol). Si
  alguna deja pasar algo no `public` para algún rol, se corrige en la misma entrega; si ya cumplen,
  se agrega el test que lo prueba para usuarios internos.
- **[400 de `DELETE /docs/shares/{id}`]:** → **Supuesto tomado:** se corrige el contrato, no el
  handler: se quita el `400` (el id mal formado responde 404 `share_not_found`). Si jiku-docs llegara
  a responder `invalid_fields`, el mapa de errores lo traduce igual que en el resto de las rutas.
- **[413 en las escrituras de docs]:** → **Supuesto tomado:** se declara `413` en todas las
  operaciones `POST`/`PUT` de `/docs/*` sujetas a `DOCS_WRITE_BODY_LIMIT` (768 KiB). El contrato
  describe el cuerpo **real** que produce body-parser hoy (no es `{code, message}`); el diseño decide si
  conviene además un manejador que lo convierta a `{code, message}`, siempre que el contrato y el
  código queden alineados.
- **[Conteos]:** → **Supuesto tomado:** el conteo correcto se obtiene contando las operaciones de
  `docs/apis/api.yaml` después de los cambios de este REQ (si se agrega o cambia una ruta, cuenta), y
  todos los documentos citados quedan con el mismo número. Si alguno de esos documentos no tiene
  conteo, no se le agrega uno.
- **[Ruta `/docs/documents/{id}` de la web (F-31)]:** D-10 la menciona junto con este cambio, pero el
  pedido no la incluye. → **Supuesto tomado:** **fuera de alcance**; queda como pendiente.
- **[Versión del producto]:** → **Supuesto tomado:** este REQ no versiona; la release es otra

## Requerimientos Funcionales

### core: `roles` e `identityType` para conectores
1. Un caller de clase `connector` puede pedir `roles` e `identityType` en el `include` de
   `users.list` y recibirlos en cada usuario.
2. Para un caller `person-internal` o `person-external`, `roles` e `identityType` no existen: pedirlos
   por cualquier palanca (`include`, `fields`, `filter`, `sort`) responde `invalid_fields`.
3. `meta.describe` de `users` lista `roles` e `identityType` como incluibles solo para la clase
   `connector`; para personas no los muestra.
4. Ninguno de los dos es filtrable ni ordenable para ninguna clase.
5. La restricción vive declarada en la ficha del recurso (ADR-008), no en código del handler.
6. `docs/apis/core-queries.yaml` documenta los dos incluibles y su restricción de clase.

### api: portal de documentación
7. `GET /opus/docs/attachments/{id}` (o la ruta que lo reemplace) solo entrega adjuntos de
   documentos `public`, para cualquier rol que use el portal (`external-user`, `admin`, `user`).
8. Un adjunto de un documento no `public` responde 404, indistinguible de uno inexistente.
9. `GET /opus/docs/documents` y `GET /opus/docs/documents/{id}` solo devuelven documentos `public`
   para cualquier rol, con test que lo pruebe para usuarios internos.
10. Si el cambio de la ruta de adjuntos altera lo que manda el portal, opus-web se adapta y los
    adjuntos de documentos `public` se siguen viendo en el visor del portal.

### Contrato y documentación
11. El encabezado de `docs/apis/api.yaml` declara el número real de operaciones.
12. `DELETE /docs/shares/{id}` no declara un `400` que el handler no produce.
13. Las escrituras de `/docs/*` con límite de cuerpo declaran el `413` con el cuerpo que realmente
    se devuelve.
14. `README.md`, `documentation/api-reference.md`, `docs/architectures/api/conventions/_base.md`,
    `documentation/installation.md` y `documentation/known-limitations.md` dicen el mismo conteo que
    `api.yaml` donde citan uno, y `known-limitations.md` deja de declarar la brecha F-13.
15. ADR-015 registra como resueltos F-12, F-13, F-30, B-1, B-2, B-3 y B-4.

## Criterios de Aceptacion

1. DADO un caller de clase `connector` (roles `[internal-app, docs]`)
   CUANDO pide `users.list {filter:{id:[<id de una persona>]}, include:["roles","identityType"]}`
   ENTONCES recibe al usuario con `roles` (lista) e `identityType` (`person`/`service`).

2. DADO un caller de clase `connector` con solo `internal-app`
   CUANDO pide los mismos incluibles
   ENTONCES también los recibe.

3. DADO un caller `person-internal` (rol `admin` o `user`)
   CUANDO pide `users.list` con `include:["roles"]` o `include:["identityType"]`
   ENTONCES recibe `invalid_fields`, igual que con un nombre inexistente.

4. DADO un caller `person-external`
   CUANDO pide `users.list` con `include:["roles","identityType"]`
   ENTONCES recibe `invalid_fields`.

5. DADO cualquier caller, incluido un `connector`
   CUANDO pide `users.list` con `filter:{roles:...}`, `filter:{identityType:...}` o `sort:["roles"]`
   ENTONCES recibe `invalid_fields`.

6. DADO un caller `connector`
   CUANDO pide `meta.describe` de `users`
   ENTONCES ve `roles` e `identityType` entre los incluibles.

7. DADO un caller `person-internal` o `person-external`
   CUANDO pide `meta.describe` de `users`
   ENTONCES no ve `roles` ni `identityType` en ninguna lista.

8. DADO un usuario interno (`admin` o `user`) en el portal opus-web
   CUANDO pide un adjunto de un documento `internal` por la ruta de adjuntos del portal, conociendo
   su id
   ENTONCES recibe 404 y no se genera ninguna URL de descarga.

9. DADO un usuario externo con permiso sobre el proyecto
   CUANDO pide un adjunto de un documento `public` vinculado a su proyecto por el portal
   ENTONCES recibe la redirección 302 a la descarga, como hoy.

10. DADO un usuario interno en el portal
    CUANDO lista documentos o abre un documento `internal` por `/opus/docs/*`
    ENTONCES no lo ve en la lista y la ficha responde 404.

11. DADO el visor del portal con un documento `public` que embebe adjuntos
    CUANDO se renderiza
    ENTONCES los adjuntos se ven (las URLs reescritas apuntan a la ruta del portal vigente).

12. DADO `docs/apis/api.yaml`
    CUANDO se cuentan sus operaciones
    ENTONCES el número coincide con el del encabezado y con los citados en README y `documentation/`.

13. DADO un `POST`/`PUT` de `/api/docs` con un cuerpo mayor a 768 KiB
    CUANDO llega a la api
    ENTONCES responde 413 tal como lo declara el contrato.

14. DADO `DELETE /docs/shares/{id}` en el contrato
    CUANDO se revisan sus respuestas
    ENTONCES no declara `400`.

15. DADO el monorepo con los cambios
    CUANDO se corre `npm run build && npm run lint && npm test`
    ENTONCES todo pasa.

#### Hallazgos que precisan supuestos del pedido

- **H-1 — El motor no soporta "incluible por clase".** `Query.validate(payload)` corre en el
  despachador **sin** la clase del caller (`dispatcher.ts`, `query.validate(raw)`), aunque la clase
  ya está resuelta en ese punto (la compuerta 2 va antes). `validateList` / `validateGet` y
  `runList` / `runGet` solo conocen la ficha. Hace falta el mecanismo mínimo (ver DD-1).
- **H-2 — `meta.describe` es hoy idéntico para todo caller, y es una decisión escrita.**
  `meta-describe.ts` ignora `ctx.callerClass` a propósito (CA-14 de S-028), `core-queries.yaml` lo
  promete (líneas 128 y 712) y `meta-describe.test.ts` TS-70 lo fija para externo contra interno. El
  RF-3 de este REQ lo cambia **solo para la clase `connector`**: para personas internas y externas la
  descripción sigue byte a byte igual (TS-70 sigue valiendo tal cual); la promesa se reformula como
  "idéntica para todas las personas; un conector ve además lo declarado para su clase".
- **H-3 — Las rutas de documentos del portal ya cumplen.** `GET /opus/docs/documents` fuerza
  `filter.visibility: 'public'` en el handler y la query no puede pisarlo (TS-34 de S-078); `GET
  /opus/docs/documents/{id}` responde 404 si `visibility !== 'public'` sin mirar el rol (TS-39/TS-40).
  Lo que falta es el test **con usuario interno** (RF-9). No cambia código.
- **H-4 — La ruta del adjunto del portal no puede verificar nada con lo que recibe.** El path solo trae
  el id del adjunto y el reply de `attachments.{id}.request-download` es `{ id, downloadUrl,
  expiresIn }`. El contrato de jiku-docs sí ofrece la verificación: `documents.get { id, include:
  ['attachments'] }` devuelve `visibility` y la lista de `Attachment` del documento. Para usarlo la api
  necesita **el id del documento** (DD-2).
- **H-5 — La ruta del portal no está publicada.** `/opus/docs/attachments/{id}` nació en REQ-016 y no
  está en ningún tag (`v1.6.0` es el último; REQ-016 solo está en `feat/jiku-docs`). Reemplazarla no
  rompe un contrato HTTP publicado.
- **H-6 — El 413 de hoy es HTML.** La api no tiene manejador de errores con cuatro argumentos: el
  `PayloadTooLargeError` de body-parser llega al `finalhandler` de Express, que responde `text/html`
  ("Payload Too Large", o con el stack fuera de producción). El fallback 404 de `app.ts`
  (`app.use((res: Response) => ...)`) tampoco es un manejador de errores válido (un solo argumento):
  defecto previo, fuera de alcance.
- **H-7 — Conteos.** `api.yaml` declara **89** operaciones (72 internas, 15 del portal, 2 públicas) y
  este REQ las deja en 89 (una ruta del portal se reemplaza por otra). Citan conteo: `README.md`
  (línea 83: 62), `documentation/api-reference.md` (línea 3: 62), `docs/prd/architecture.md`
  (líneas 78 y 141: 61; línea 462: la nota "todavía dice 88") y `docs/architectures/api/overview.md`
  (línea 10: 89, ya correcto). **No citan conteo** `docs/architectures/api/conventions/_base.md`,
  `documentation/installation.md` ni `documentation/known-limitations.md`: según el supuesto, no se
  les agrega uno (`known-limitations.md` sí cambia, por F-13).
- **H-8 — `api-reference.md` no lista las rutas de documentación.** Sus tablas enumeran 62 rutas y
  ninguna de `/api/docs/*`, `/api/opus/docs/*`, `/api/modules`, `/api/opus/modules` ni `/p/docs/*`.
  Cambiar el "62" por "89" sin las filas haría mentir al documento. **Decisión:** se agregan las
  filas que faltan para que el conteo sea verificable con su propia receta de `grep` (sección
  "Regenerating this list").

### Decisiones de diseño

- **DD-1 — Incluibles por clase, declarados en la ficha.** `ResourceSpec` gana un campo opcional
  `includableByClass?: Partial<Record<CallerClass, Record<string, IncludableSpec>>>`. Una función
  nueva de `engine/spec.ts`, `resolveForClass(resource, callerClass)`, devuelve la ficha efectiva
  para esa clase: fusiona `includable` con lo declarado para la clase y **deriva** `includableNames` y
  `fieldNames` (igual que `resolveVariant`, nunca copiados). Sin `includableByClass`, o sin entrada
  para la clase, devuelve **la misma referencia**: las otras quince fichas no cambian un byte.
  - **Solo incluibles, por tipo.** El campo no admite filtros ni orden: "filtrable u ordenable por
    clase" no es representable, y eso cumple RF-4 sin una regla aparte. Tampoco entra en `q`.
  - **Se aplica antes que `resolveVariant`**, en los cuatro puntos donde hoy se resuelve la ficha:
    `validateList`, `validateGet`, `runList` y `runGet`. Para un caller sin la clase, un nombre que no
    está declarado para él cae en la rama de siempre (`invalid_fields` con `errorDetails.allowed` sin
    el nombre): **"no está declarado para tu clase" es la única forma de "no se puede pedir"**
    (ADR-008).
  - **La clase llega a `validate`.** `Query.validate(payload, callerClass)`; el despachador ya la
    tiene resuelta antes de validar y la pasa. `validateList` / `validateGet` reciben `callerClass`
    como tercer parámetro **opcional**: ausente, no se suma nada (falla cerrado). Todas las consultas
    `list`/`get` registradas lo reenvían (cambio mecánico de una línea por archivo), así el mecanismo
    vale para cualquier ficha futura y ningún handler decide nada. Los 48 llamados de los tests a
    `validateList`/`validateGet` siguen compilando.
  - **`meta.describe` deriva por clase.** `describeResource(resource, callerClass)` aplica
    `resolveForClass` antes de describir; `meta-describe.ts` deja de ignorar `ctx.callerClass`. Sigue
    siendo derivado (CA-12 de S-028): lo que describe es exactamente lo que el validador acepta para
    esa clase.
  - **Alternativa descartada:** chequear la clase dentro de `users-list.ts`. Es código en el handler
    (contra RF-5) y deja a `meta.describe` con una segunda copia de la regla.
- **DD-2 — El adjunto del portal se pide bajo su documento.** `GET /opus/docs/attachments/{id}` se
  **reemplaza** por `GET /opus/docs/documents/{documentId}/attachments/{id}`. La api llama a
  `documents.get { id: documentId, include: ['attachments'] }`, verifica `visibility === 'public'` y
  que `id` esté en `attachments[].id`, y solo entonces pide `attachments.{id}.request-download`.
  - **Por qué un path anidado y no `?documentId=`:** el documento es parte de la identidad del
    recurso que el portal sirve (la autorización depende de él), y un parámetro de query opcional
    invitaría a omitirlo. La ruta vieja **se elimina** (H-5): conservarla dejaría la brecha abierta.
  - **Cierra también una brecha lateral:** un documento `public` que enlaza el adjunto de **otro**
    documento ya no lo sirve por el portal, aunque ese otro sea `public` (404). Es el
    comportamiento correcto para una superficie compartida con el cliente, y es el único cambio
    visible (ver Evaluación de Impacto UX).
  - **Alternativa descartada:** `attachments.list { filter: { documentId } }` más `documents.get`.
    Son dos round-trips donde `documents.get` con `include: ['attachments']` resuelve las dos
    preguntas en uno, y es la misma consulta que ya hace `GET /opus/docs/documents/{id}`.
- **DD-3 — El 413 pasa a ser `{ code, message }`.** Se agrega en `api/app.ts`, **al final de la
  cadena**, un manejador de errores de cuatro argumentos que solo atiende
  `err.type === 'entity.too.large'` y responde `413 { "code": "payload_too_large", "message":
  "El cuerpo de la solicitud supera el límite permitido" }`; cualquier otro error sigue con
  `next(err)` (sin cambio de comportamiento). Así el contrato declara un cuerpo con la forma del
  resto de la api en vez de documentar HTML. Aplica a toda la api (body-parser corre en todas las
  rutas), pero el contrato lo declara **solo donde el pedido lo exige**: las nueve escrituras de
  `/docs/*` (RF-13). Que el resto de las rutas no lo declare es un desfase previo, se anota como
  pendiente.
- **DD-4 — Se corrige el contrato, no el handler, en `DELETE /docs/shares/{id}`.** Se quita el
  `400`. El handler no tiene más input que el path (un id malformado es 404 `share_not_found` sin
  bus) y el payload a `shares.{id}.revoke` es `{}`.

### Flujo de Interacción

#### Escenario A: jiku-docs clasifica a quien lo llama (CA-1, CA-2, CA-5, CA-6)

**Trigger:** una persona llama a jiku-docs; jiku-docs necesita sus roles.

1. **[jiku-docs]** (machine user, roles `[internal-app, docs]`)
   - Publica `{instance}.{jiku-docs-sub}.jiku-queries.v1.users.list`
   - Payload: `{ "filter": { "id": ["<sub de la persona>"] }, "include": ["roles", "identityType"] }`
2. **[core — despachador]**
   - `readCallerRolesForQueries(caller)` -> `["internal-app","docs"]`
   - Compuerta 1: `authorizeWithRoles(..., 'queries')` -> `internal-app` tiene `queries: ALL`
   - Compuerta 2: `resolveCallerClass` -> `connector`
   - `usersList.validate(raw, 'connector')` -> `validateList(usersSpec, raw, 'connector')` ->
     `resolveForClass` suma `roles` e `identityType` -> la proyección es válida
3. **[core — motor]**
   - `runList(usersSpec, query, ctx)` -> `resolveForClass(usersSpec, ctx.callerClass)` -> SQL
     `SELECT t.id, t.name, t.username, t.created_at, t.updated_at, t.roles, t.identity_type FROM users t WHERE t.id IN (...)`
   - Reply: `{ "success": true, "data": { "items": [{ ..., "roles": ["user"], "identityType": "person" }], "page": {...} } }`
4. **[jiku-docs]** clasifica a la persona con esos roles.

**Errores:**
- `filter: { roles: ... }`, `filter: { identityType: ... }` o `sort: ["roles"]`, para **cualquier**
  clase -> `invalid_fields` (no son filtrables ni ordenables; `errorDetails.allowed` = los cuatro
  filtros / los dos ordenables de siempre).
- Fila del caller ausente -> `unknown_caller` (sin cambio).

#### Escenario B: una persona pide los incluibles (CA-3, CA-4, CA-7)

1. **[api o jiku-go]** con identidad `admin` / `user` / `external-user` publica `users.list` con
   `include: ["roles"]`.
2. **[core]** compuerta 2 -> `internal` o `external`; `validateList(usersSpec, raw, clase)` ->
   `resolveForClass` devuelve la ficha sin cambios -> `invalid_fields`, `details.field: "include"`,
   `allowed: ["email","person"]` — idéntico a pedir un nombre inexistente.
3. `meta.describe { resources: ["users"] }` -> `includable: { email, person }`, byte a byte como hoy.

#### Escenario C: adjunto desde el portal (CA-8, CA-9, CA-11)

**Trigger:** el visor del portal renderiza un documento `public` con un enlace
`/docs/attachments/{attId}`, o el usuario hace click en la lista de adjuntos.

1. **[opus-web — visor]** `docsUrlTransform(doc.id)` reescribe a
   `/api/docs/documents/{docId}/attachments/{attId}`.
2. **[opus-web — route handler]** valida sesión y los dos ULID -> `GET {API_URL}/api/opus/docs/documents/{docId}/attachments/{attId}`
   con `Authorization: Bearer <token>` y `redirect: 'manual'`.
3. **[api]** `requireModule('docs')` -> `hasAnyRole(['external-user','admin','user'])` ->
   `documents.get { id: docId, include: ['attachments'] }` (con `actor`).
   - `visibility !== 'public'` -> **404 `document_not_found`** (CA-8: interno con documento
     `internal`; no se pide ninguna URL de descarga).
   - `attId` no está en `attachments[].id` -> **404 `attachment_not_found`**.
   - OK -> `attachments.{attId}.request-download` -> **302** `Location: <downloadUrl>` (CA-9).
4. **[opus-web — route handler]** propaga el 302; el navegador baja del storage.

**Errores:** módulo no instalado 404 `module_not_installed`; no disponible 503; timeout 504; para
`external-user` sin acceso jiku-docs responde `document_not_found` / `permission_denied` en el paso 3
y el mapa lo traduce (sin cambio).

#### Escenario D: escritura de docs con cuerpo grande (CA-13)

1. **[web]** `PUT /api/docs/documents/{id}` con un cuerpo de más de 768 KiB.
2. **[api]** `docsWriteJson` (body-parser, `limit: '768kb'`) lanza `PayloadTooLargeError`
   (`type: 'entity.too.large'`) -> el manejador nuevo -> **413**
   `{ "code": "payload_too_large", "message": "El cuerpo de la solicitud supera el límite permitido" }`.
   No llega a la ruta ni al bus.

### Consideraciones Técnicas

#### Riesgos
- **R-1 — Fuga de `roles` a una persona por un error de plumbing.** Si una consulta no reenviara la
  clase a `validate`, el parámetro ausente **falla cerrado** (no suma nada). El riesgo real es el
  inverso: que `runList` use la ficha de una clase distinta a la validada. Mitigación: las dos
  resoluciones salen de la misma clase (la del despachador) y hay un test que pide `roles` como
  persona y verifica `invalid_fields` y que el SQL no nombra la columna.
- **R-2 — Cualquier identidad `internal-app` ve los roles de todos.** Es la consecuencia de D-10: la
  clase `connector` ya lee los 16 recursos sin recorte. Se documenta en `known-limitations.md`
  junto al punto "Every connector can read all documentation".
- **R-3 — Enlaces entre documentos en el portal.** Un documento `public` que enlaza el adjunto de
  otro documento deja de mostrarlo (404). Aceptado por diseño (DD-2); se registra en
  `known-limitations.md`.
- **R-4 — `DELETE /docs/shares/{id}` sin `400`.** Si jiku-docs llegara a responder `invalid_fields`
  a `shares.{id}.revoke` (payload `{}`), el mapa produciría un 400 no declarado. Improbable; se
  mantiene la decisión del pedido.
- **R-5 — El 413 JSON aplica a toda la api** y solo las escrituras de docs lo declaran. Se anota como
  desfase previo en ADR-015 (pendiente fuera de este REQ).

#### Dependencias
- La story de core es independiente de las de api.
- La story de contrato y conteos va después de la del portal: el conteo final y las filas de
  `api-reference.md` dependen de la ruta del adjunto que quede.
- jiku-docs (otro repo) desbloquea su integración cuando la story de core esté desplegada; no hay
  cambio coordinado de versión del protocolo (no se agrega ni quita ningún canal).

#### Performance
- El adjunto del portal suma un round-trip a jiku-docs (`documents.get`) antes del
  `request-download`. Es la misma consulta que ya hace el visor, por id; despreciable frente a la
  descarga.
- `resolveForClass` es una fusión de objetos por request solo para fichas con `includableByClass`
  (hoy, una); para las demás devuelve la referencia.

#### Seguridad
- Cierra F-13: ningún rol obtiene por el portal un adjunto que no pertenezca a un documento `public`.
- CA-7 se mantiene para personas; el modelo de autorización solo se publica a conectores.
- El 404 del portal no distingue "documento interno" de "inexistente" (nunca 403).
