## Clarificaciones

### Supuestos (modo automático)

El dueño del producto delegó las decisiones de detalle; no se hicieron preguntas. Cada ambigüedad se resolvió así:

- **[Cliente de cada proyecto]:** → **Supuesto tomado:** `GET /api/projects` agrega el cliente del proyecto como objeto
  `client` (`id`, `name`) además de lo que ya devuelve; es un cambio aditivo y no rompe a los otros consumidores. Si el
  diseño encuentra que el cliente ya llega por otra vía, la web se corrige para leerlo de ahí. Un proyecto sin cliente
  devuelve `client: null`.
- **[Relación Cliente → Proyecto]:** → **Supuesto tomado:** se conserva la regla de REQ-021: con un cliente elegido, el
  selector de Proyecto ofrece solo los proyectos de ese cliente (más "Sin proyecto"); elegir un proyecto completa su
  cliente; cambiar el cliente vacía el proyecto solo si no es de ese cliente; "Sin cliente" lo vacía siempre.
- **["+" de la card de proyecto]:** → **Supuesto tomado:** el diálogo abre con el cliente y el proyecto visibles en los
  selectores (no solo en el payload). Lo mismo aplica al editor de un documento existente que ya tiene proyecto.
- **[Listado "Sin cliente · Proyecto"]:** → **Supuesto tomado:** la etiqueta muestra el cliente del documento cuando el
  ítem lo trae en `clients`. Si el documento no tiene cliente propio pero sí un proyecto, se muestra "Sin cliente" (no se
  infiere el cliente del proyecto en la etiqueta), porque refleja las relaciones reales del documento. El diseño
  confirma si el caso de la e2e era un documento sin cliente (consecuencia de JIKU-WEB-3) o un error de la etiqueta, y
  corrige la etiqueta solo si es lo segundo.
- **[Identidad del usuario actual en docs]:** → **Supuesto tomado:** en el módulo de documentación, "yo" es
  `session.user.zitadelId` (el `sub` que jiku-docs guarda en `lock.holder`, `createdBy`, `updatedBy` y `author`). No se
  cambia el criterio de otros módulos (comentarios de requisitos y objetivos siguen con `session.user.id`). Si
  `zitadelId` no está en la sesión, nada se reconoce como propio (se muestra el nombre o "—", nunca "vos" por error).
- **[Alcance de la revisión]:** → **Supuesto tomado:** se revisan todos los componentes y utilidades de
  `web/src/features/docs` que comparan con el usuario actual (lock en lectura, editor y filas; cabecera "Versión N ·
  actualizado …"; "Editado por" en listados; autor en el historial).
- **[Contrato `api.yaml`]:** → **Supuesto tomado:** se alinean los schemas de respuesta de documentos de la web y del
  portal con lo que devuelven las rutas hoy (contrato 1.3.0): sin `path`, `folderId` ni `fileName` en el documento;
  con `clients`, `projects`, `topics`, `visibility` (`internal | public | restricted`), `createdByName`,
  `updatedByName`, `authorName` donde corresponda, `lock` con `holderName`. Los parámetros y cuerpos de rutas que ya no
  usa la web (filtro `folderId`, `move`, carpetas) se documentan tal como están implementados en la api; si una ruta
  sigue existiendo, no se borra del contrato. No se cambia comportamiento de la api para ajustarse al yaml.
- **[Tamaño]:** → **Supuesto tomado:** una o dos stories (api + web para JIKU-WEB-3, web para JIKU-WEB-4 y contrato).

## Criterios de Aceptación

1. DADO "Nuevo documento" abierto
   CUANDO la persona elige el cliente EXO y abre Proyecto
   ENTONCES ve los proyectos de EXO (además de "Sin proyecto").

2. DADO "Nuevo documento" sin cliente elegido
   CUANDO la persona elige el proyecto "EXO - Videoconferencia"
   ENTONCES el selector de Cliente muestra EXO.

3. DADO un proyecto de EXO elegido
   CUANDO la persona elige el cliente EXO
   ENTONCES el proyecto se conserva; si elige otro cliente, el proyecto se vacía.

4. DADO el detalle de un proyecto de EXO
   CUANDO la persona toca "+" en la card de Documentación
   ENTONCES el alta muestra EXO / {proyecto} precargados y al guardar manda ambos.

5. DADO un documento existente con proyecto y cliente
   CUANDO la persona lo edita
   ENTONCES los selectores muestran su cliente y su proyecto.

6. DADO un consumidor existente de `GET /api/projects`
   CUANDO pide la lista
   ENTONCES recibe los mismos campos que antes más el cliente de cada proyecto.

7. DADO un documento con cliente y proyecto
   CUANDO aparece en un listado
   ENTONCES la columna Cliente · Proyecto muestra el nombre del cliente, no "Sin cliente".

8. DADO un documento con el lock de la persona actual (humano)
   CUANDO lo abre en otra pestaña
   ENTONCES ve "Lo estás editando en otra pestaña o ventana.", no "Otra persona lo está editando…".

9. DADO un documento cuya última versión guardó la persona actual
   CUANDO ve la cabecera, la fila del listado o el historial
   ENTONCES ve "vos" como autor.

10. DADO una sesión sin `zitadelId`
    CUANDO se muestra un lock o un autor
    ENTONCES no se muestra "vos" ni "Lo estás editando…" por error.

11. DADO `docs/apis/api.yaml`
    CUANDO se leen los schemas de documentos de la web y del portal
    ENTONCES no declaran `path`, `folderId` ni `fileName` en el documento y sí los campos del contrato 1.3.0.

**Diagnóstico confirmado:**

1. **JIKU-WEB-3 — causa confirmada.** `projects-get.ts:31` incluye solo `creator`; el JSON trae `clientId` (columna)
   pero **no** el objeto `client`. `ProjectPicker.tsx:36-41`, `ClientProjectFields.tsx:28-31` y
   `NewDocumentDialog.tsx:98-107` leen `p.client?.id` / `project.client.id`, siempre `undefined`. Con un cliente
   elegido el filtro `p.client?.id === clientId` deja la lista vacía (solo "Sin proyecto"); elegir un proyecto manda
   `clientId: null` a `chooseProject`, que no completa el cliente; `chooseClient` ve `projectClientOf(id) === null` y
   vacía el proyecto. En el "+" (W8) el diálogo recibe `clientId` y `projectId`, pero como el proyecto no está entre
   las opciones filtradas el `Select` no lo puede mostrar ("EXO / Sin proyecto") aunque el estado sí lo tiene (por eso
   el guardado manda `projects [43] clients [1]`). `GET /projects/{id}` sí incluye `client`, por eso el detalle de
   proyecto funciona. La lógica de `relationFields.ts` (`chooseProject`, `chooseClient`) es correcta: no se toca.
2. **Etiqueta "Sin cliente · EXO - Videoconferencia" — no es un error de la etiqueta.** El documento de W3
   (`01M5VXS000HW8JBQN8654SBJED`) quedó con `clientes []` porque el proyecto no completó el cliente (consecuencia de
   JIKU-WEB-3). `ClientProjectLabel` muestra `clientRefs[0].name` cuando existe. Se agrega un test de no regresión
   (AC-7) y no se cambia el componente.
3. **JIKU-WEB-4 — causa confirmada.** Todos los puntos de `features/docs` pasan `currentUser?.id` (uuid de Jiku) a
   `lockedMessage` y `editorLabel`, que lo comparan con `lock.holder`, `updatedBy` y `author` (el `sub` de Zitadel).
   Además, la fila del listado (`DocumentRow.tsx:94-111`) muestra "Otra persona lo está editando" aun cuando el lock
   es propio: tampoco reconoce a la persona.
4. **Contrato `api.yaml` — la premisa es parcialmente cierta.** El **portal** ya no recibe `path`/`folderId`/`fileName`
   (`PORTAL_DOC_FIELDS = ['id','title','version','visibility','createdAt','updatedAt']`), pero `/opus/docs/documents*`
   referencian el `DocsDocument` compartido, que los declara: eso sí está desalineado. Las rutas **de la web**
   (`/docs/documents`, `/docs/documents/{id}`, `/docs/search`, alta) **siguen devolviéndolos** porque pasan la
   respuesta de jiku-docs 1.3.0 verbatim y jiku-docs los conserva para el CLI y el sync. El supuesto del REQ dice
   "no se cambia comportamiento de la api para ajustarse al yaml" y CLAUDE.md dice que el yaml es la fuente de verdad:
   borrarlos del `DocsDocument` de la web haría que el contrato mienta. **Decisión:** el portal pasa a esquemas propios
   sin esos campos; en la web se conservan, marcados como pass-through de jiku-docs que la UI no muestra. Ver
   "Desvío respecto del AC-11" en Consideraciones Técnicas.

### Flujo de Interacción

#### Escenario: elegir cliente y luego proyecto (AC-1, AC-3)

**Trigger:** la persona abre "Nuevo documento" (o "Editar") y elige el cliente EXO.

1. **[web]** `useProjects()` → Server Action `getProjects` → `GET /api/projects` (cache TanStack `['projects', {}]`).
2. **[api]** `Project.findAll({ include: [creator, client(id,name)] })` → `200 [{ id: 43, name: "EXO -
   Videoconferencia", clientId: 1, client: { id: 1, name: "EXO" }, creator: {...}, ... }]`.
3. **[web]** `ClientProjectFields` → `chooseClient(value, 1, projectClientOf)`; `ProjectPicker` con `clientId=1`
   filtra `projectClientId(p) === 1` → opciones "Sin proyecto" + proyectos de EXO, hint "Solo los proyectos de EXO".
4. **[web]** elegir el proyecto 43 → `chooseProject(value, { id: 43, clientId: 1 })` → `{ clients: [1], projects:
   [43] }`. Volver a elegir EXO conserva el proyecto (`projectClientOf(43) === 1`); elegir otro cliente lo vacía.

**Outcome:** al guardar, `POST /api/docs/documents` manda `relations: { clients: [1], projects: [43] }` (sin cambios).

#### Escenario: proyecto primero (AC-2)

Elegir "EXO - Videoconferencia" sin cliente → `chooseProject(value, { id: 43, clientId: 1 })` → el selector de
Cliente muestra EXO.

#### Escenario: "+" de la card de proyecto y edición (AC-4, AC-5)

**Trigger:** `DocsPanel` del proyecto 43 → `NewDocumentDialog initial={{ projectId: 43, clientId: 1 }}` (o el editor
con `relations` del documento).

1. **[web]** estado `{ clients: [1], projects: [43] }`; `ProjectPicker` filtra por cliente 1 y ahora el 43 **está**
   entre las opciones → el `Select` muestra "EXO - Videoconferencia · EXO". Si `initial` trae solo `projectId`, el
   efecto `clientPending` completa el cliente con `projectClientId`.

**Outcome:** el alta muestra EXO / EXO - Videoconferencia y guarda ambos.

#### Escenario: reconocer el lock propio (AC-8, AC-9, AC-10)

**Trigger:** la persona edita en la pestaña A y abre el mismo documento en la pestaña B.

1. **[web A]** `POST /api/docs/documents/{id}/lock` → jiku-docs guarda `holder = actor.sub` (flujo
   `documentos-desde-la-web`, paso 3).
2. **[web B]** `GET /api/docs/documents/{id}` → `lock: { sessionId, holder: "<sub>", holderName, via: "human",
   expiresAt }`; `sessionId` distinto → `isLockActive` true.
3. **[web B]** `lockedMessage(doc.lock, currentUser.zitadelId)` → `holder === zitadelId` → "Lo estás editando en
   otra pestaña o ventana.". En la fila del listado: "Lo estás editando".
4. Cabecera (`metaVersionLabel`), "Editado por" (`editorLabel` con `updatedBy`) e historial (`author`) → "vos".

**Manejo de errores:** sin `zitadelId` en la sesión → `currentUserSub = null` → nunca "vos" ni "Lo estás
editando…"; se muestra `holderName`/nombre o el texto genérico (AC-10).

### Consideraciones Técnicas

#### Riesgos

- **Desvío respecto del AC-11.** El AC pide que los esquemas de documentos "de la web y del portal" no declaren
  `path`, `folderId` ni `fileName`. Para el **portal** se cumple (esquema propio). Para la **web** no se cumple a
  propósito: las rutas los devuelven (jiku-docs 1.3.0 los conserva para el CLI y el sync, `servicio.md:68`) y el
  supuesto del REQ prohíbe cambiar la api para ajustarse al yaml. Se documentan como pass-through que la UI no usa.
  Si el dueño prefiere que la web no los reciba, es un cambio de comportamiento aparte (pedir `fields` explícitos en
  `documents.list`/`get`), no parte de este REQ. La story de contrato reformula el AC-11 en este sentido.
- **Límite del listado de proyectos.** `useProjects()` sin filtros usa el `limit` por defecto (200 por el `default`
  de Joi, que no se valida contra el `max(30)`). Con más proyectos, alguno no aparecería en el selector. Preexistente;
  se anota, no se cambia.
- **`useCurrentUser` lo usan otros módulos.** El cambio es aditivo (`zitadelId` nuevo); `id` no cambia.

#### Dependencias

- La story web depende de la de api solo para la e2e; el respaldo `clientId` permite implementarlas en paralelo.

#### Performance

- Un `LEFT JOIN clients` por consulta de `GET /api/projects`, sobre `client_id` indexado (`20260724_01`). Despreciable.

#### Seguridad

- `client` expone solo `id` y `name`, que ya son visibles para los mismos roles en `GET /projects/{id}`. Sin cambios
  de autenticación ni de `getRolesFromToken`.
