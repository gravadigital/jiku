# S-053: Componentes base: Button, Input, Select, Loader, Badge, Card

**Status:** Completed
**Created:** 2026-09-02
**Source:** REQ-013

## Historia de Usuario

**Como** desarrollador que va a migrar las pantallas de `web` a la identidad nueva,
**quiero** disponer de los seis componentes fundacionales (`Button`, `Input`, `Select`,
`Loader`, `Badge`, `Card`) con las variants y la API que declara cada spec del Design System,
**para** que el resto de los componentes y todas las pantallas tengan un destino único al que
migrar cada elemento construido a mano.

## Criterios de Aceptación

### CA-1: `Button` expone los cinco variants más FAB, sin `size`

**DADO** que `Button` hoy expone `variant="primary" | "secondary"` + `size="normal" | "small"`
**CUANDO** se migra al spec nuevo
**ENTONCES** expone los cinco variants (`primary`, `secondary-nav`, `secondary-dismiss`,
`session`, `flow`) más FAB, `size` desaparece de la API, el spec usa `children` como slot en vez
de `label: string`, no existe prop `type` (por lo que no puede ser submit nativo de un
`<form>`), y tiene `aria-label` obligatorio en el FAB y `aria-busy` en el estado cargando

### CA-2: Existe un único `Select` con 4 variants, sin `react-select` directo ni `selectStyles` duplicado

**DADO** que hoy conviven `InputSelect` (12 archivos), `Select` y `react-select` directo (13
archivos) con `selectStyles` duplicado
**CUANDO** se crea el `Select` nuevo
**ENTONCES** implementa los 4 variants que declara `components/select.md`, ningún import directo
de `react-select` queda en el componente nuevo, y no hay ninguna copia de `selectStyles` dentro
de él (la migración de los usos existentes en pantallas es responsabilidad de las stories de
migración de pantallas, S-056 a S-058)

### CA-3: Existe un único `Loader` con `block`/`inline`

**DADO** que hoy conviven `Loader` y `Spinner` sin regla de cuándo usar cada uno
**CUANDO** se crea el `Loader` nuevo
**ENTONCES** implementa las variantes `block` e `inline` que declara su spec, con
`aria-label="Cargando"` cuando no hay label visible en la variante inline

### CA-4: `Input` cubre las variantes `date` y `search`

**DADO** que la Revisión UX de REQ-013 resolvió los bloques `date-picker` y `search-bar` como
`Input` variant `date` y variant `search` respectivamente
**CUANDO** se construye `Input`
**ENTONCES** incluye la variant `date` con su icono de calendario y la variant `search` con
lupa y placeholder configurable, además de las variantes base que declara `components/input.md`

### CA-5: `Badge` y `Card` existen con la API de sus specs

**DADO** que `Badge` (badge editable de estado) y `Card` deben existir como componentes
reutilizables nuevos, y que `Card` colisionaba con el componente muerto ya eliminado en S-051
**CUANDO** se crean
**ENTONCES** `Badge` implementa las variants de su spec, incluyendo su rol de control de estado
editable con las 7 opciones (ver preservación de comportamiento en S-057), y `Card` reemplaza
toda tarjeta armada con `div` que la migración de pantallas encuentre

### CA-6: Cada componente nuevo tiene test y usa el anillo de foco del DS

**DADO** que `Button`, `Loader` no tenían test antes de esta story
**CUANDO** se entregan los seis componentes
**ENTONCES** cada uno se entrega con su propio `.test.tsx`, y todos usan el anillo de foco verde
agua al 22% que define `foundations/elevation.md`

## Diseño Técnico

### Servicios Afectados

| Servicio | Impacto | Cambios Necesarios | Estado |
|----------|---------|---------------------|--------|
| `web` | Alto | Crear/reescribir `Button`, `Input`, `Select`, `Loader`, `Badge`, `Card` en `shared/components/ui/`, exportados desde el barrel, cada uno con test propio | Done |

### Cambios de API

Ninguno a nivel HTTP/bus. Cambia la API interna (props) del componente `Button` de forma
breaking dentro del propio servicio `web` — ver Consideraciones Técnicas.

### Cambios de Base de Datos

Ninguno.

### Flujo de Interacción

#### Escenario: Construcción de los componentes base sobre la capa de tokens

**Trigger:** S-052 (capa de tokens) está completa.

**Flujo:**

1. **[web · `shared/components/ui/Button/`]**
   - Acción: Reescribir con los 5 variants + FAB, `children` como slot, sin `size` ni `type`.
   - Output: Componente exportado desde el barrel, con test.

2. **[web · `shared/components/ui/Select/`]**
   - Acción: Crear el `Select` único con 4 variants, absorbiendo la superficie de API que hoy
     cubren `InputSelect`, `Select` viejo y los usos directos de `react-select`.
   - Output: Componente exportado, sin `react-select` importado directamente ni
     `selectStyles` propio.

3. **[web · `shared/components/ui/Loader/`]**
   - Acción: Crear `Loader` con `block`/`inline`, absorbiendo la superficie de `Spinner`.
   - Output: Componente exportado, con test.

4. **[web · `shared/components/ui/Input/`, `Badge/`, `Card/`]**
   - Acción: Crear cada uno según su spec del DS.
   - Output: Los seis componentes fundacionales completos y exportados desde el barrel.

5. **[web · clasificación de usos de `Button`]**
   - Acción: Se releva cada uno de los 14 usos existentes de `Button` (más los 104 `<button>`
     crudos que se migran en las stories de pantallas) para asignar el variant semántico según
     intención — "Volver" es `secondary-nav`, "Cancelar" es `secondary-dismiss`. Esta story
     define el criterio de clasificación; la migración masiva de los usos en pantalla ocurre en
     S-056, S-057 y S-058.
   - Output: Criterio de clasificación documentado para las stories siguientes.

**Outcome:** Los seis componentes base están disponibles en el barrel, listos para que los
componentes compuestos (S-054, S-055) y las migraciones de pantalla los consuman.

**Manejo de errores:**
- Ninguno propio a nivel de runtime; los `error` de `Input` y `Select` se expresan como string
  para alimentar `aria-describedby`, según ya resolvió la Revisión UX del REQ para el bloque
  `alert` de formulario.

### Consideraciones Técnicas

**Seguridad:**
- Anillo de foco verde agua al 22% obligatorio en todos los controles (`foundations/elevation.md`).
- `aria-label` obligatorio en el FAB, `aria-busy` en `Button` cargando, `aria-label="Cargando"`
  en `Loader` inline sin label visible.
- Contraste: verificar que `secondary-nav`/`secondary-dismiss` (outline sobre fondo claro, texto
  `#0B1934`) alcanzan AA — el spec registra que el `secondary` viejo sobre `#D9D9D9` era el
  candidato más probable a no alcanzarlo.

**Performance:**
- No aplica cambio relevante; son componentes de presentación sin fetch propio.

**Dependencias:**
- **Depende de S-052** (capa de tokens): estos componentes derivan su apariencia de los
  tokens de componente (`--button-primary-bg`, etc.).
- **Riesgo señalado por el REQ:** "hay muchísimo más botón crudo que `Button`": 104 `<button>`
  sin componente en 48 archivos. Esta story solo construye el componente; la clasificación y
  reemplazo masivo en pantallas es de las stories de migración (S-056 a S-058).
- **Riesgo señalado por el REQ:** verificar cada uso de `Button` dentro de un `<form>` antes de
  migrarlo, porque el componente nuevo no tiene prop `type` y no puede ser submit nativo.
- Habilita S-054 y S-055 (componentes de datos/navegación y de feedback/contenido), que
  componen sobre estos seis.

## Dependencias
