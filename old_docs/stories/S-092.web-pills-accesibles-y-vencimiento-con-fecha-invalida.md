# S-092: Web: pills accesibles y vencimiento con fecha inválida

**Status:** Completed
**Created:** 2026-10-26
**Source:** REQ-020

## Historia de Usuario

**Como** usuario de la web interna (incluido quien usa lector de pantalla),
**quiero** que cada pill del detalle de requisito anuncie su propio atributo y que el listado de tareas no muestre vencimientos absurdos,
**para** entender qué estoy editando y confiar en las fechas de cierre que veo.

## Criterios de Aceptación

### CA-1: Pills con nombre accesible propio

**DADO** el detalle de un requisito en la web
**CUANDO** un lector de pantalla recorre las pills
**ENTONCES** anuncia "Estado: …", "Tipo: …" y "Prioridad: …" respectivamente

### CA-2: Fecha nula, vacía o inválida

**DADO** una tarea con fecha estimada de fin nula, vacía o inválida
**CUANDO** se renderiza el listado de tareas
**ENTONCES** no aparece texto "Vencido hace" ni "Falta", ni marca de cercanía al vencimiento

### CA-3: Fecha válida vencida

**DADO** una tarea con fecha estimada de fin válida vencida hace 3 días y no cerrada
**CUANDO** se renderiza el listado
**ENTONCES** muestra "Vencido hace: 3 día(s)"

### Decisiones de diseño

- **DD-5 — `Badge` editable con nombre de atributo.** Prop nueva solo en `BadgeEditableProps`: `attributeLabel?: string`, default `'Estado'`; `aria-label={`${attributeLabel}: ${label}`}` (`Badge.tsx:141`). `RequirementHeader` (línea 110-152) pasa `attributeLabel="Tipo"` y `"Prioridad"`; el de estado queda con el default. `StateTag` no cambia. Tests: `Badge.test.tsx` (default y prop) y `RequirementHeader.test.tsx` (los tres nombres accesibles con `canEdit`). Cualquier otro uso no-estado del editable también pasa el nombre correcto si el cambio es trivial.
- **DD-6 — "Fecha válida" = la forma del contrato.** Helper nuevo en `web/src/shared/utils/`: `parseFinishDate(value: Date | string | null | undefined): Date | null`.
  - Devuelve `null` si el valor es nulo, vacío, un `Date` inválido, o un string que no empieza con `YYYY-MM-DD`.
  - Un `YYYY-MM-DD` se construye como fecha local (`new Date(y, m - 1, d)`), no con `new Date('YYYY-MM-DD')` (UTC; en UTC-3 cae el día anterior).
  - `ObjectivesTable` (línea 28-63) lo usa en `getFinishDateText` (inválida → "No definida"), `getDaysLeftText` (inválida → `''`) e `isCloseToDeadline` (inválida → `false`). `isOverdue` (`objectiveHelpers.ts:34-41`) y `ObjectiveCard` usan el mismo helper.
  - `calculateDaysLeft` no cambia de firma ni semántica: cuenta días hábiles. 32 666 días hábiles son ~125 años: una fecha cercana a 1900 producida por texto heredado no ISO. La story reproduce el caso con el valor real del entorno e2e y lo fija en un test; si resultara ser un `YYYY-MM-DD` válido, se reporta como dato y no se esconde.
  - Tests: `parseFinishDate` (null, `''`, `'abc'`, `'31/12/2026'`, `Invalid Date`, `'2026-10-23'`, ISO con hora) y `ObjectivesTable` con reloj fijo (vencida hace 3 días hábiles y abierta → "Vencido hace: 3 día(s)"; nula/inválida → ni "Vencido hace" ni "Falta" ni clase `closeToDeadline`).

### Flujo de Interacción

#### Escenario: pills del detalle (CA-1)

**Trigger:** un usuario con `canEdit` abre el detalle de requisito con lector de pantalla.

**Flujo:**

1. **[web / `RequirementHeader`]**
   - Acción: renderiza tres `Badge` editables con `attributeLabel` Estado (default), Tipo, Prioridad
   - Output: `aria-label` "Estado: …", "Tipo: …", "Prioridad: …"

#### Escenario: columna de cierre en Tareas (CA-2, CA-3)

**Trigger:** el usuario abre `/objectives`.

**Flujo:**

1. **[web / `ObjectivesTable`]**
   - Acción: `parseFinishDate(estimatedFinishDate)`
   - Output: `Date` local o `null`

2. **[web / `ObjectivesTable`]**
   - Acción: `null` → "No definida", sin texto de vencimiento ni `closeToDeadline`; válida → cálculo actual
   - Output: texto de la columna

**Manejo de errores:**
- Texto heredado no ISO → tratado como inválido ("No definida")
