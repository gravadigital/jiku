# S-032: La asignación semanal se convierte en comando

**Status:** Completed
**Created:** 2026-08-25
**Source:** REQ-007

## Historia de Usuario

**Como** producto que quiere que **la misma operación produzca el mismo resultado por los dos
caminos**,
**quiero** el **comando 21** —`week-assigned-times.replace`— con C-38 resuelto por el mapa y C-36
dentro del comando, y que `PUT /api/week-assigned-times` pase a **comando + relectura**,
**para** que deje de existir la única escritura de dominio que no pasa por `core`, y que las dos
reglas de la grilla tengan **dónde** vivir del lado del escritor.

> **Es la story que el requerimiento no vio (H-1).** `PUT /api/week-assigned-times` es **la única
> escritura de dominio que no pasa por `core`**: la api la ejecuta con el ORM (`destroy` +
> `bulkCreate` en una transacción propia, `week-assigned-times-put.ts:39-78`), y
> `docs/flows/asignacion-semanal.md` la documenta aparte por eso mismo — *"`core`: **No participa.**
> Este flujo no lo involucra"*. **No hay dónde poner C-36 y C-38 sin crear el comando.**

> **Es la única story del REQ que crea un comando, así que su riesgo es distinto al de las otras dos
> de reglas: no es mover una regla, es mover una escritura entera de servicio.**

> **El contrato HTTP no cambia.** Mismo verbo, mismo cuerpo, mismo status. Lo que cambia es quién
> valida y quién escribe.

## Criterios de Aceptación

### CA-1: `week-assigned-times.replace` existe y es el comando 21

**DADO** el registro de comandos de `core`
**CUANDO** termina esta story
**ENTONCES** existe el canal `week-assigned-times.replace` en el módulo `times`, y
**`nats micro info jiku-commands` pasa a listar 21 endpoints**. El registro es automático desde
`commands/index.ts` (`endpointName()`/`endpointSubject()`): **sumar el comando es sumar el endpoint**

### CA-2: Reemplaza la semana completa

**DADO** `week-assigned-times.replace` con `dateFrom` y una lista de `assignments`
**CUANDO** se ejecuta
**ENTONCES** **borra y recrea la semana entera** dentro de la transacción del despachador — que es la
semántica que la entidad ya tiene: *"es la única entidad que se **reemplaza por semana completa**"*

### CA-3: Solo `admin` — y lo decide el mapa, no el comando

**DADO** una persona con rol `user`
**CUANDO** publica `week-assigned-times.replace`
**ENTONCES** `core` la rechaza con **`caller_not_authorized`** → **403**: C-38 **no depende del
payload**, así que se resuelve en el **mapa rol → comando** de S-030, antes de tocar el dominio
(CA-20 del REQ)

### CA-4: No se modifican semanas pasadas

**DADO** un `admin`
**CUANDO** reemplaza una semana **ya pasada**
**ENTONCES** `core` la rechaza con **`invalid_date_range`** → **400**: `validateWeekNotPast` deja de
ser una regla de la api (C-36, CA-21 del REQ)

### CA-5: `dateFrom` tiene que ser lunes

**DADO** `week-assigned-times.replace`
**CUANDO** `dateFrom` no es un lunes
**ENTONCES** `core` lo rechaza con `invalid_fields`: la semana se identifica por su lunes, y aceptar
cualquier día dejaría dos semanas solapadas

### CA-6: `internal` se deriva de `projects.type`, como hoy

**DADO** una asignación sobre un proyecto con `type = 'interno'`
**CUANDO** el comando la persiste
**ENTONCES** **deriva** `internal` de `projects.type`, sin recibirlo del payload — exactamente como lo
hace hoy la api

### CA-7: Las asignaciones con `minutes: 0` se descartan

**DADO** un payload con asignaciones de `minutes: 0`
**CUANDO** el comando las procesa
**ENTONCES** **no se insertan**, igual que hoy: una celda vacía de la grilla no es una fila

### CA-8: El reply es `ReplyEmpty`

**DADO** un reemplazo exitoso
**CUANDO** `core` responde
**ENTONCES** devuelve `{ "status": "success" }` — **es un reemplazo, no una creación: no hay `id` que
devolver**

### CA-9: `PUT /api/week-assigned-times` publica el comando y relee

**DADO** la ruta HTTP
**CUANDO** termina esta story
**ENTONCES** declara `x-bus-command: week-assigned-times.replace`, publica el comando con el sobre, y
**relee la base con Sequelize** para responder — el patrón comando + relectura del resto de las rutas
(ADR-001)

### CA-10: La api pierde su escritura con el ORM y sus middlewares de transacción

**DADO** el diff de la api
**CUANDO** termina esta story
**ENTONCES** `- ELIMINADO` el `destroy` + `bulkCreate` de `week-assigned-times-put.ts:39-78`, `-
ELIMINADO` el middleware `validateWeekNotPast`, `- ELIMINADO` el `hasAnyRole(['admin'])`, y
`- ELIMINADO` el uso de los **middlewares de transacción de la api, que es la única ruta que los
usa** — con lo que esos middlewares quedan **sin ningún consumidor**

### CA-11: El contrato HTTP no cambia

**DADO** los dos frontends
**CUANDO** guardan la grilla
**ENTONCES** ven **el mismo verbo, el mismo cuerpo y los mismos status**: `403` para un `user`, `400`
para una semana pasada, `200`/`204` en el éxito. **Ninguna línea de UI cambia** (CA-8 del REQ)

### CA-12: El mapa gana la entrada del comando 21

**DADO** el mapa rol → método de S-030
**CUANDO** termina esta story
**ENTONCES** `week-assigned-times.replace` está enumerado **solo para `admin`** y para `internal-app`;
`user` y `external-user` **no lo tienen**

### CA-13: La escritura pasa al usuario dueño de la base

**DADO** la conexión con que se escribe la grilla
**CUANDO** termina esta story
**ENTONCES** escribe **`core` con el usuario dueño**, y **no** la api con su rol. Es la primera vez que
la promesa de ADR-001 se puede cumplir de verdad para esta tabla

### CA-14: El test de paridad cubre las dos reglas

**DADO** C-36 y C-38
**CUANDO** se las ejerce por HTTP (con `FakeBus`) y por `dispatch()` directo
**ENTONCES** los dos caminos producen **el mismo reply** (CA-5 del REQ)

### Cambios de API

#### Nuevos canales necesarios

**`week-assigned-times.replace`** — **el comando 21**
- **Servicio:** `core`, módulo `times`
- **Descripción:** reemplaza **la semana completa** de asignación (borrar + recrear)
- **Request:**
  ```json
  {
    "actor": { "id": "3233…", "roles": ["admin"], "name": "…", "username": "…", "email": "…" },
    "dateFrom": "2026-08-24",
    "assignments": [
      { "projectId": 12, "personId": 7, "minutes": 480 }
    ]
  }
  ```
  `dateFrom` (DateOnly, req, **lunes**) · `assignments` (array, req) con `projectId` (integer, req),
  `personId` (integer, req), `minutes` (integer, req)
- **Response:** `ReplyEmpty` — `{ "status": "success" }`
- **Reglas que aplica:**
  - **solo `admin`** (C-38) — resuelta por el **mapa rol → comando**, no dentro del comando, porque
    **no depende del payload**
  - **no se modifican semanas pasadas** (C-36) → `invalid_date_range`
  - `dateFrom` tiene que ser lunes → `invalid_fields`
  - `internal` se **deriva** de `projects.type === 'interno'`
  - las asignaciones con `minutes: 0` se **descartan**
- **Errores:** `caller_not_authorized` (403), `invalid_date_range` (400), `invalid_fields` (400),
  `project_not_found` / `person_not_found` (400) según referencias inválidas

> **`nats micro info jiku-commands` pasa a listar 21 endpoints.** Toda frase del corpus que diga *"los
> 20 comandos"* —`core/manifest.yaml`, `core/overview.md`, la cabecera de `docs/apis/core.yaml`, S-012,
> S-017 CA-1— queda desactualizada. **Se corrige por `/product-change-technical-definition`, no por
> esta story**, salvo la cabecera de `core.yaml`, que es contrato y se actualiza acá.

#### Endpoints existentes a modificar — contrato HTTP

**`PUT /api/week-assigned-times`** (ref: `docs/apis/api.yaml`)
- **Cambio:** `-> MODIFICADO` de escritura con ORM a **comando + relectura**. Gana
  `x-bus-command: week-assigned-times.replace`. `- ELIMINADO` el middleware `validateWeekNotPast` y el
  `hasAnyRole(['admin'])`; `- ELIMINADO` el uso de los middlewares de transacción, **que es la única
  ruta que los usa**
- **Justificación:** H-1, RF-4, RF-17. **El contrato HTTP no cambia**

#### El cambio de credenciales que sí importa

`PUT /api/week-assigned-times` es hoy *"la única ruta que escribe con el ORM"* de la api, y funciona
**porque el rol de la instalación se lo permite** — el propio `api/overview.md` advierte que *"contra
un rol estrictamente `SELECT` fallarían"*. Al convertirla en comando, esa escritura pasa al usuario
dueño de la base.

**Consecuencia operativa:** después de esta entrega, el rol de PostgreSQL de la api **puede
endurecerse a `SELECT` puro** para la escritura de dominio. Queda **una sola** excepción pendiente
(las migraciones, que ya usan `POSTGRESQL_MIGRATION_USER` propio). **No se endurece en esta story** —es
un cambio de infraestructura con su propio riesgo— **pero hay que registrarlo o se pierde**.

### Flujo de Interacción

#### Escenario 1: Un `admin` reemplaza la semana (CA-2, CA-6, CA-7, CA-9)

**Trigger:** un `admin` guarda la grilla proyecto × persona en `web`.

**Flujo:**

1. **[web]** → `PUT /api/week-assigned-times` con la grilla completa de la semana

2. **[api · `week-assigned-times-put.ts`]**
   - **`- ELIMINADO`** `hasAnyRole(['admin'])`, `validateWeekNotPast` y los middlewares de transacción
   - **`- ELIMINADO`** el `destroy` + `bulkCreate` con el ORM
   - Publica `week-assigned-times.replace` con el sobre de S-029
   - Timeout `NATS_REQUEST_TIMEOUT_MS` (5000 ms)

3. **[core · compuerta]** — el mapa autoriza `week-assigned-times.replace` **solo a `admin`** (C-38).
   Un `user` → `caller_not_authorized` → **403**

4. **[core · comando]**
   - `dateFrom` es lunes → si no, `invalid_fields`
   - `dateFrom` no puede ser una semana pasada (C-36) → `invalid_date_range` → **400**
   - Deriva `internal` de `projects.type`, descarta `minutes: 0`
   - **Borra y recrea dentro de la transacción del despachador** (ADR-003)
   - → `success` → **commit**

5. **[api]** — relee la base con Sequelize y responde

**Outcome:** el mismo contrato HTTP, la misma grilla, **y por primera vez la escritura pasa por el
único servicio que puede escribir**. `docs/flows/asignacion-semanal.md` deja de ser el flujo
excepcional.

**Manejo de errores:**

| Situación | Status HTTP | Comportamiento |
|---|---|---|
| Rol `user` | **403** `caller_not_authorized` | Antes lo cortaba `hasAnyRole` en la api |
| Semana pasada | **400** `invalid_date_range` | Antes `validateWeekNotPast` |
| `dateFrom` no es lunes | **400** `invalid_fields` | Regla explícita del contrato nuevo |
| `core` caído | **503** tras 5000 ms | **La operación no ocurrió** (ADR-002). **Es un desenlace nuevo para esta ruta** |
| Respuesta perdida | **504** | **Pudo haber ocurrido.** Riesgo asumido de ADR-002. **También nuevo para esta ruta** |

#### Escenario 2: Un `user` intenta reemplazar la semana (CA-3, CA-12)

**Trigger:** una persona con rol `user` publica `week-assigned-times.replace`, por HTTP o por el bus.

**Flujo:**

1. **[core · compuerta de método]** — el mapa **no** tiene el comando para `user` →
   **`caller_not_authorized`**
2. **No se abre transacción, no se toca la grilla**

**Outcome:** rechazado **antes de tocar el dominio**, que es exactamente por qué C-38 va en el mapa y
no dentro del comando: no depende del payload.

### Flujos Afectados

#### Flujos existentes modificados

- **`asignacion-semanal`** (ref: `docs/flows/asignacion-semanal.md`) — **cambia de naturaleza**
  - Hoy se describe como ***"el flujo excepcional del producto […] la única escritura de dominio que
    no pasa por `core`"***, con `core` marcado *"**No participa**"*. **Deja de ser excepcional**
  - El diagrama de secuencia se rehace: `api → NATS → core → PostgreSQL`, con **la transacción del
    despachador** en vez de la de la api
  - `core` entra en la tabla de servicios involucrados; la api pasa de *"Procesador **y escritor**"* a
    **Procesador**
  - C-36 y C-38 se mueven de la api a `core`
  - Aparecen los desenlaces **503** y **504** de ADR-002, que este flujo **nunca tuvo**

#### Flujos nuevos

**Ninguno.**

### Consideraciones Técnicas

#### Decisiones de diseño

**C-38 va en el mapa, C-36 va en el comando.** El criterio es si la regla depende del payload:
*"solo `admin` edita la grilla"* no lo hace —es una pregunta sobre el rol, y se responde antes de
tocar el dominio—; *"no se modifican semanas pasadas"* sí, porque necesita `dateFrom`. Es el mismo
corte que S-030 estableció entre `caller_not_authorized` y `access_denied`.

**El reemplazo total se conserva tal cual.** La semántica *borrar + recrear la semana entera* ya es la
de la entidad, y esta story **la mueve de servicio, no la rediseña**. Un comando incremental
(`upsert` por celda) sería un contrato distinto y un cambio de UI.

**`ReplyEmpty` y no un `id`.** No hay entidad creada: hay una semana reemplazada.

#### Riesgos

- **Riesgo alto — la ruta gana dos desenlaces que nunca tuvo: 503 y 504.** Hasta hoy esta escritura era
  local a la api y no podía fallar por el bus. Con el comando hereda el desdoblamiento de ADR-002, y
  **504 significa *"pudo haberse guardado"*** sobre una grilla entera.
  - **Mitigación:** el REQ lo registra como **gap de UX declarado**: en `asignacion-tiempo` (`web`) la
    recuperación correcta es **recargar la semana antes de reintentar**, y **nada en la pantalla lo
    dice**. No se resuelve en esta story —el REQ declara las superficies sin cambios de UI— pero **el
    gap queda escrito y no descubierto**.

- **Riesgo alto — los middlewares de transacción quedan sin consumidor.** Esta es su **única** ruta.
  Eliminar su uso los deja huérfanos: borrarlos es tentador y **cambia el alcance de la story**.
  - **Mitigación:** esta story **elimina el uso**, no los middlewares. Su eliminación, si corresponde,
    va con las de S-034, que es *"un diff de solo eliminaciones"*.

- **Riesgo medio — la transacción cambia de dueño y de forma.** Hoy el `destroy` + `bulkCreate` corre
  en una transacción de la api; pasa a correr en **la del despachador** (ADR-003: commit si `success`,
  rollback en cualquier otro caso). Una semana a medio reemplazar es el peor resultado posible.
  - **Mitigación:** un test que falle **después** del `destroy` y verifique que la semana quedó intacta.

- **Riesgo medio — `dateFrom` no-lunes hoy no se valida explícitamente.** La api asume el lunes porque
  el frontend lo manda. Un caller del bus no tiene esa garantía.
  - **Mitigación:** CA-5 lo convierte en regla del contrato. Hay que verificar que **el frontend
    efectivamente manda el lunes**, o la ruta se rompe en producción con un `invalid_fields`.

- **Riesgo medio — H-1: la story no estaba en el requerimiento.** Planificar *"mudar dos reglas"* sin
  ver que hay que **crear un comando, convertir una ruta y quitar los únicos middlewares de
  transacción de la api** subestima esta parte por un factor grande.
  - **Mitigación:** es una story propia, paralelizable, y su alcance está acotado porque la semántica
    de reemplazo total ya está definida en la entidad.

- **Riesgo bajo — el conteo "20 comandos" queda desactualizado en cinco documentos.**
  - **Mitigación:** se tramita por `/product-change-technical-definition` al cierre del REQ; la cabecera
    de `core.yaml` —que es contrato— se actualiza acá (CA-1).

#### Performance

- **La escritura pasa de una transacción local a un request al bus.** Suma el round-trip de NATS y el
  timeout de 5000 ms, contra una escritura que hoy es local. **Es el único costo real de la story**, y
  es el mismo que ya pagan las otras 20 escrituras del producto.
- **La relectura con Sequelize** es el patrón que el resto de las rutas ya usa (ADR-001).
- **El borrado + inserción no cambia de forma:** las mismas dos operaciones, en la otra transacción.

#### Seguridad

- **C-38 pasa a ser una regla del escritor.** Hasta hoy, nadie del lado de `core` impedía escribir la
  grilla — no había comando. Esta story cierra ese hueco **al mismo tiempo que lo abre**, que es por
  qué CA-12 (la entrada del mapa) es parte del entregable y no un detalle.
- **La escritura pasa al usuario dueño de la base** (CA-13): el rol de la api deja de necesitar
  `INSERT`/`DELETE` sobre `week_assigned_times`.
- **Ningún permiso nuevo en el auth-callout.** La publicación por personas es S-035.

#### Testing

- **`core` entra por el despachador** (`tests/helpers/dispatch.ts`): la transacción y el rollback del
  reemplazo se prueban ahí, no en el `execute` aislado.
- **El test del rollback a mitad de reemplazo** (fallar después del `destroy`) es el más importante de
  la story.
- **El test de paridad de CA-14**: C-36 y C-38 por HTTP y por `dispatch()`.
- **La api se prueba con `FakeBus`, que ejecuta `core` real**, así que `PUT /api/week-assigned-times`
  se verifica de punta a punta sin mockear el comando.
- **Los casos de borde de la semana:** semana actual (acepta), semana siguiente (acepta), semana
  anterior (rechaza), `dateFrom` martes (rechaza).

#### Dependencias

- **S-029 es prerequisito duro:** el rol viaja en el sobre, y sin él la compuerta no puede decidir C-38
  por el rol de la persona.
- **S-030 es prerequisito duro:** C-38 **es una entrada del mapa**, y el mapa nace ahí.
- **Ninguna dependencia nueva de npm.**
