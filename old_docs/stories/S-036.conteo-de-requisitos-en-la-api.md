# S-036: Conteo de requisitos en la api

**Status:** Completed
**Created:** 2026-08-31
**Source:** REQ-008

## Historia de Usuario

**Como** frontend (`web`) que necesita mostrar totales reales por estado,
**quiero** que `GET /requirements` acepte un parámetro `count` que devuelva la cantidad de
requisitos que satisfacen los mismos filtros,
**para** dejar de calcular totales sobre datos parciales ya traídos y replicar el contrato que
ya expone `GET /objectives?count=true`.

## Criterios de Aceptación

### CA-1: Conteo respeta los mismos filtros que el listado

**DADO** un proyecto con 12 requisitos en estado `desarrollo`
**CUANDO** se llama `GET /requirements?projectId={id}&state=desarrollo&count=true`
**ENTONCES** la respuesta es `200` con el número `12`, respetando los mismos filtros que el
listado — el mismo contrato que ya expone `GET /objectives`

### CA-2: Sin `count`, la respuesta no cambia

**DADO** una llamada `GET /requirements` sin el parámetro `count`
**CUANDO** se ejecuta
**ENTONCES** devuelve el array de requisitos como hoy, sin cambios para ningún consumidor
existente

### CA-3: Valor no booleano en `count`

**DADO** un valor no booleano en el parámetro `count` (ej. `count=quizas`)
**CUANDO** se llama `GET /requirements?count=quizas`
**ENTONCES** la respuesta es `400` con el error de campos inválidos, coherente con el resto de
los parámetros del endpoint

### CA-4: `limit` fuera de rango

**DADO** un `limit` fuera del rango aceptado por el endpoint (mínimo 1, máximo 100)
**CUANDO** se llama el listado con ese valor
**ENTONCES** la api responde `400`

### CA-5: Sin sesión válida

**DADO** un usuario **sin sesión válida**
**CUANDO** se llama `GET /requirements` con o sin `count=true`
**ENTONCES** la respuesta es `401`, sin filtrar el conteo — el conteo no es una superficie más
permisiva que el listado

### CA-6: Rol `external-user` sin acceso

**DADO** un usuario autenticado con rol `external-user`
**CUANDO** intenta llegar a `GET /requirements` (con o sin `count`)
**ENTONCES** no obtiene acceso: el endpoint es `[user, admin]` y el portal externo lee por
`/opus/*`. El conteo no abre una vía nueva para el modo externo ni expone requisitos `internal`
a un cliente

## Diseño Técnico

### Servicios Afectados

| Servicio | Impacto | Cambios Necesarios | Estado |
|----------|---------|-------------------|--------|
| `api` | Bajo | `GET /requirements` acepta `count` (boolean) y, en `true`, devuelve el número crudo con los mismos filtros. Un solo archivo de ruta. | Done |

### Cambios de API

#### Endpoints Existentes a Modificar

**`GET /requirements`** (ref: `docs/apis/api.yaml`:468-523; código `api/lib/routes/requirements-get.ts`)

- **Cambio:** agregar el query param opcional `count` (boolean). Con `count=true` la respuesta es
  el número crudo de requisitos que satisfacen los mismos filtros; sin el parámetro, la respuesta
  no cambia.
- **Justificación:** RF-11 y RF-12 del request; CA-1 y CA-2 de esta story.

Contrato actual (verbatim del spec, líneas 473-519 de `docs/apis/api.yaml`):

```
parameters:
  - name: projectId    in: query   schema: { type: integer }
  - name: state        in: query   schema: { $ref: '#/components/schemas/RequirementState' }
  - name: type         in: query   schema: { $ref: '#/components/schemas/RequirementType' }
  - name: priority     in: query   schema: { type: string }
  - name: createdBy    in: query   schema: { type: string }
  - name: estimatedFinishDate  in: query  schema: { type: string, format: date }
  - name: tag          in: query   schema: { type: string }
  - name: search       in: query   schema: { type: string }
  - $ref: '#/components/parameters/Page'
  - name: limit        in: query   schema: { type: integer, minimum: 1, maximum: 100, default: 20 }
  - name: sort         in: query   schema: { type: string }
responses:
  '200': array de RequirementWithRelations
  '400' InvalidFields · '401' Unauthorized · '403' AccessDenied · '500' InternalError
```

Contrato resultante:

```
parameters:
  ... todos los anteriores SIN CAMBIOS ...
  + NUEVO  - name: count
             in: query
             description: Si es true, devuelve la cantidad de requisitos que satisfacen los
                          mismos filtros en vez del listado. `page` y `limit` se ignoran.
             schema: { type: boolean }
responses:
  '200':
    -> MODIFICADO  oneOf:
         - array de RequirementWithRelations   (sin count)
         - { type: integer }                   (con count=true)
  '400' / '401' / '403' / '500'  SIN CAMBIOS
```

**Forma de implementación** (fijada por la convención `http-server` del propio servicio):

`requirements-get.ts` **no usa** `parseGetParams()` — lee `req.query` directo, a diferencia de
`objectives-get.ts`. Por eso el count se implementa como un middleware local en el mismo archivo,
espejando la estructura de `getObjectivesCount` (`objectives-get.ts`:147-175) pero leyendo de
`req.query`:

- Nuevo middleware `getRequirementsCount(req, res, next)` que hace `if (!count) return next();`.
- La construcción del `where` (hoy en `getRequirements`, líneas 30-43) se **extrae a un helper
  compartido** `buildWhere(query)` para que listado y conteo apliquen filtros idénticos por
  construcción — es la garantía del CA-1 y el mismo patrón que `buildWhereClauses` en
  `objectives-get.ts`:19-51.
- `Requirement.count({ where })`. **Sin `include`**: los filtros no dependen de las relaciones
  (`project` y `responsiblePeople` se incluyen solo para armar la respuesta del listado), así que
  no hace falta el `distinct: true` que sí necesita objectives.
- Cadena del router: `hasAnyRole(['user','admin'])` → `validateQueryParams(querySchema)` →
  `getRequirementsCount` → `getRequirements`.
- Joi: `count: joi.boolean().optional()` en el `querySchema` (línea 12-24). Joi rechaza
  `count=quizas` con 400 `invalid_fields` sin código extra (CA-3), y `limit` ya trae
  `.min(1).max(100)` (CA-4).
- Errores: `logger.error` y `500 internal_error`, idéntico al listado (líneas 73-76).

### Cambios de Base de Datos

#### Tablas Existentes a Modificar

Ninguna. El requerimiento no altera el esquema.

#### Nuevas Tablas

Ninguna.

#### Índices

**No se requieren índices nuevos.** Los de REQ-006 (`docs/db-schemas/jiku.md`:693-697) cubren el
acceso del conteo:

- `idx_requirements_project_created_id` sobre `(project_id, created_at, id)` — sirve al conteo
  filtrado solo por proyecto.
- `idx_requirements_state_created_id` sobre `(state, created_at, id)` — sirve al filtro por
  estado.

El conteo por tab es `WHERE project_id = ? AND state = ?`: lo resuelve el primero con filtro
adicional sobre un conjunto ya acotado al proyecto. Con los volúmenes del producto (decenas de
requisitos por proyecto) es irrelevante.

### Flujo de Interacción

#### Escenario: conteo con filtros

**Trigger:** `web` pide `GET /requirements?projectId={id}&state=desarrollo&count=true`.

**Flujo:**

1. **[api]**
   - Acción: `hasAnyRole(['user','admin'])` → `validateQueryParams(querySchema)` (Joi valida
     `count` como boolean) → `getRequirementsCount` construye `where` con `buildWhere(query)` y
     ejecuta `Requirement.count({ where })`.
   - Output: `200` con el número crudo, ej. `12`.

**Outcome:** el consumidor recibe un entero que respeta exactamente los mismos filtros que el
listado.

**Manejo de errores:**
- `count=quizas` (no booleano) → `400 invalid_fields`, mismo mecanismo que el resto de los
  parámetros del endpoint.
- `limit` fuera de `[1,100]` → `400` (validación ya existente, no cambia).
- Sin sesión → `401`.
- Rol `external-user` → sin acceso (el endpoint es `[user, admin]`).
- Error de BD → `500 internal_error`, idéntico al listado.

### Consideraciones Técnicas

**Seguridad:**
- El conteo entra **detrás** de `hasAnyRole(['user','admin'])`, igual que el listado: no es una
  superficie más permisiva (CA-5 y CA-6).
- El conteo **no filtra por `visibilityLevel`** — igual que el listado actual, que tampoco lo
  hace. El endpoint no es alcanzable desde el portal externo (`opus-web` usa `/opus/*`,
  ADR-006), así que el conteo no expone requisitos `internal` a un cliente. No se cambia el
  comportamiento existente; solo se hace explícito que el conteo lo hereda tal cual.
- Sin datos nuevos en la respuesta: un entero.

**Performance:**
- `SELECT COUNT(*) FROM requirements WHERE project_id = ? AND state = ?`, servido por
  `idx_requirements_project_created_id`. Coste despreciable.

**Dependencias:**
- Ninguna hacia atrás. Esta story es la base: S-038 (card de requisitos) depende de que este
  endpoint exista para pedir sus 7 totales reales.

**Deuda documental que se salda en esta story:**
- `count=true` funciona en `GET /objectives` desde antes y nunca se documentó en
  `docs/apis/api.yaml` (verificado: `grep "name: count"` no devuelve nada en el archivo). Esta
  story documenta el parámetro `count` en **los dos** endpoints — `/requirements` (nuevo) y
  `/objectives` (código preexistente, spec desalineado) — dejando el contrato HTTP alineado con
  el código en ambos casos.
