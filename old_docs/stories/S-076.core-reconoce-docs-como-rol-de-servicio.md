# S-076: core reconoce `docs` como rol de servicio

**Status:** Completed
**Created:** 2026-10-24
**Source:** REQ-016

## Historia de Usuario

**Como** operador de una instalación con el módulo de documentación,
**quiero** que core trate al machine user de jiku-docs como un servicio más,
**para** que su identidad se espeje en `users` y pueda consultar y operar sin ser rechazado.

## Criterios de Aceptación

### CA-14: Clase conector para `[internal-app, docs]` (RF-10)

**DADO** un usuario con `roles: [internal-app, docs]` e `identityType: service`
**CUANDO** consulta por `jiku-queries` y publica un comando
**ENTONCES** core le da la clase conector, sin recorte de filas, igual que a `[internal-app]`

### CA-14b: El evento de autenticación sin `email` se acepta (H-1, R-2)

**DADO** un evento de autenticación con `matched_role: 'docs'` y sin `email`, y sin fila previa en `users`
**CUANDO** core lo procesa
**ENTONCES** crea la fila con `identity_type = service` y el usuario deja de recibir `caller_not_authorized` / `unknown_caller`

### CA-15: Archivo sin vínculo descargable (RF-11)

**DADO** un archivo subido por el machine user de jiku-docs y nunca vinculado
**CUANDO** el mismo servicio pide `files.{id}.request-download`
**ENTONCES** recibe la URL prefirmada, y el archivo no es purgado mientras esté activo

### Cambios de Base de Datos

### Hallazgo H-1 (por qué core sí cambia)

Con la regla `docs` por encima de `internal-app`, el `matched_role` del evento de autenticación del machine user es `docs`. `identityTypeFromMatchedRole('docs')` devuelve `person` (no está en `SERVICE_ROLES`) y el esquema exige `email`, que un machine user de Zitadel no tiene. El evento se descarta, no se crea la fila y core rechaza todo. **Corrección:** `docs` entra a `SERVICE_ROLES` (`core/src/events/auth/identity-type.ts:36`, hoy `['internal-app', 'core']`); el test TS-7 de `core/tests/events/identity-type.test.ts` pasa a tres. La nota de `docs/flows/sincronizacion-de-identidades.md` ya advertía esto.

### Flujo de Interacción

#### Escenario: primera conexión del machine user de jiku-docs

**Trigger:** jiku-docs se autentica en el bus por primera vez.

1. **[auth-callout]** aplica la regla `docs`; el evento de autenticación lleva `matched_role: "docs"` sin `email`.
2. **[core — dispatcher]** `email` opcional porque `docs` está en `SERVICE_ROLES`; deriva `identity_type = service`.
3. **[core]** crea la fila en `users` con `roles: [internal-app, docs]`.
4. **[core — caller-class / authorize-caller]** rol `docs` desconocido se saltea; `internal-app` da clase `connector` y `commands/queries: ALL`.

**Outcome:** jiku-docs consulta y publica comandos como cualquier conector.

**Manejo de errores:**
- Si `docs` no estuviera en `SERVICE_ROLES` → evento descartado (el caso que el test de CA-14b prohíbe).

### Flujos Afectados

- **sincronizacion-de-identidades** (ref: docs/flows/sincronizacion-de-identidades.md) — Paso 3/5: `docs` es rol de servicio (se documenta en S-085).
- **lectura-de-archivos** (ref: docs/flows/lectura-de-archivos.md) — Camino E deja de ser hipotético (S-085).

### Consideraciones Técnicas

**Seguridad:**
- No se agrega ninguna entrada de autorización para `docs`: para core es un `internal-app` más.

**Performance:**
- Sin impacto.

**Dependencias:**
- Verificado en el diseño: `core/src/` no tiene barrido de archivos sin vínculo, y `files.{id}.request-download` no exige vínculo ni titularidad. Si el test de CA-15 fallara, ajuste mínimo en core.
- El test de CA-14b parte de un evento sin fila previa, no de una fila existente (R-2).
