> de ese plan. Ver **Frontera con el plan de `api`** al final.

> **Este plan corre PRIMERO.** No es una preferencia de orden: la Tarea 3 produce el **DDL exacto
> que `sync()` emite**, y ese texto es el objetivo contra el que la migración del plan de `api` se

### Service Architecture

`packages/models` es un **paquete compartido**, no un servicio desplegable. No tiene
`docs/architectures/`, y eso es correcto: no hay manifest porque no hay servicio. El contexto
técnico de este plan sale de las convenciones `orm` y `_base` de sus **dos consumidores**
(`api` y `core`), del esquema `docs/db-schemas/jiku.md`, y de los ADR 001, 005, 012 y 013.
Precedentes del mismo patrón: `S-001.base.separar-file-de-attachment.md`,
`S-010.base.baja-integracion-sistemas-externos.md` y
`S-011.nats-protocol.contrato-del-bus-renombrado.md`.

**Estado actual del paquete — 28 archivos de `src/`, 26 modelos:**

```
packages/models/
├── package.json        name @jiku/models, main dist/index.js, scripts: build + lint
│                       NO tiene script `test` (ver "Testing" más abajo)
├── tsconfig.json       strict: true, decoradores, declaration, outDir ./dist
├── eslint.config.js    module.exports = require('../../eslint.config.base.js')
└── src/
    ├── index.ts                    barrel: 26 re-exports + `allModels`
    ├── retention-status.enum.ts    el ÚNICO enum en archivo propio (razón abajo)
    └── *.model.ts                  26 modelos, uno por archivo
```

**Cómo se consume:** `package.json` apunta a `dist/`, así que los dos backends lo usan
**compilado**. `npm run build:packages` (postinstall de la raíz) compila `@jiku/models`,
`@jiku/nats-protocol` y `@jiku/zitadel-auth` **antes** que `api` y `core`. **Un cambio en `src/`
no llega a los consumidores sin rebuild** — es el paso que más se olvida en este paquete.

**El paquete no abre la conexión, a propósito.** Exporta clases; cada servicio las registra en su
propio `Sequelize` con sus credenciales:

```ts
// api/lib/models/index.ts:16-26  — SOLO LECTURA
export const sequelize = new Sequelize({ /* ... */ models: allModels, logging: false });

// core/src/models/index.ts:17-27 — usuario DUEÑO de la base
export const sequelize = new Sequelize({ /* ... */ models: allModels, logging: false });
```

**Las dos fuentes del esquema — el hecho central de esta story:**

```ts
// core/src/models/index.ts:54-65
function initializeDb() {
  return connectToDatabase().then(() => {
    if (['testing', 'development'].includes(NODE_ENV)) {
      return sequelize.sync().then(/* ... */);   // <-- FUENTE 1
    }
    return null;                                  // producción: solo migraciones

}
```

`sync()` en `testing`/`development`; las 101 migraciones de `api/db-upgrade/migrations/` en
producción (FUENTE 2). **Los tests corren contra la FUENTE 1** (ADR-013), así que una divergencia
entre las dos **no produce ningún fallo en CI**.

**Testing del paquete: no tiene, y este plan no lo abre.**

`@jiku/models` no tiene `tests/`, ni `.mocharc.json`, ni script `test`, y **el `npm test` de la raíz
no lo incluye**:

```json
"test": "npm run test --workspace @jiku/nats-protocol --workspace @jiku/api --workspace @jiku/core --workspace @jiku/web --workspace @jiku/opus-web"
```

Y no hace falta abrirlo: **los modelos se testean desde `api/tests/00-configurations/`**, que es
donde vive la infraestructura que los ejercita contra PostgreSQL real. Ese directorio ya tiene
`attachment-model.test.ts`, `file-model.test.ts`, `inbound-mail-thread-model.test.ts` y
`external-integration-removal.test.ts` — los dos últimos **creados por planes del lado del esquema**
(S-062 y S-010 respectivamente), no por planes de `api`. La Tarea 2 sigue ese precedente.

> **Por qué importa la aclaración:** un implementador que lea "plan de `packages/models`" puede
> concluir que no puede tocar archivos fuera del paquete y terminar abriendo infraestructura de test
> nueva en `packages/models/` para no salirse. Sería trabajo desperdiciado y una segunda forma de
> testear modelos. El precedente es explícito: `S-010.base` Tarea 3 creó
> `api/tests/00-configurations/external-integration-removal.test.ts`.

### Relevant ADRs

#### ADR-005: Modelos compartidos en `@jiku/models`, sin abrir la conexión

**Decisión:** extraer los modelos a un paquete del workspace que exporta las **clases** pero
**deliberadamente no abre la conexión**. Cada servicio registra las clases en su propio `Sequelize`
con sus credenciales.

**Implementation Rules (verbatim, completas):**

- Los modelos Sequelize **DEBEN** vivir en `@jiku/models`. **NO SE DEBE** definir un modelo dentro
  de `api/` o de `core/`.
- `@jiku/models` **NO DEBE** abrir una conexión ni leer variables de entorno de base de datos.
  Exporta clases; la instancia la crea cada servicio.
- Cada servicio **DEBE** registrar las clases en su propio `Sequelize` con sus credenciales.
- Un cambio de esquema **DEBE** hacerse en dos lugares en el mismo cambio: la migración en
  `api/db-upgrade/migrations/` y el modelo en `@jiku/models`. Uno sin el otro deja el código y la
  base desalineados.
- Los hooks que van en el modelo son los que pertenecen **al dato** (mantener `finishedAt`
  consistente con `state`). Los que dependen del caso de uso o del rol **DEBEN** ir en el comando
  de core o en la api.
- Los nombres en `@jiku/models` **DEBEN** ser los reales de la base. La traducción de vocabulario
  es responsabilidad de core.
- Al agregar un modelo, **DEBE** registrarse en el índice del paquete: los dos servicios lo
  importan desde ahí.

> **La cuarta regla es la que esta story tensiona.** Dice que el modelo y la migración van *en el
> mismo cambio*. El split de REQ-005 los pone en **dos planes**, y eso es deliberado —`packages/models`
> y `api` son servicios distintos y el skill genera un plan por servicio—, pero significa que
> **ninguno de los dos planes solo cumple la regla**. La cumple el par. Es la razón de que la Tarea 3
> publique el DDL como contrato y de que los dos planes se desplieguen juntos.

**Riesgo declarado por el propio ADR, textual:** *"`sequelize.sync()` corre en testing y
development, mientras producción se construye con las migraciones: **dos fuentes de verdad** para el
mismo esquema. Mitigación: ninguna hoy. Registrado en NFR-R07 y en el feature group FG-6."*

#### ADR-013: Tests contra base de datos real

**Decisión:** los tests corren contra PostgreSQL real, sin mocks de Sequelize. **El esquema de test
lo construye `sequelize.sync()`**, no las migraciones.

**Implementation Rules (verbatim, completas):**

- Los tests de `api` y `core` **DEBEN** correr contra PostgreSQL real. **NO SE DEBEN** mockear los
  modelos de Sequelize.
- Los tests de comandos de `core` **DEBEN** entrar por el despachador (`dispatch()`), **NO** por
  `execute()` directamente.
- Un test de escritura de la api **DEBE** verificar las tres capas: comando publicado, traducción de
  la respuesta a HTTP, y que la fila quedó escrita. **NO SE DEBE** asertar solo el status HTTP.
- `reply()` / `failWith()` **DEBEN** usarse solo para cubrir caminos de error. El camino feliz
  **DEBE** ejecutar core de verdad.
- Cada archivo de test **DEBE** poder correr solo: el esquema y el mock de auth se preparan en
  fixtures globales de Mocha.
- `TZ=UTC` **DEBE** estar fijado en la configuración de test de todo servicio.
- La limpieza entre corridas **DEBE** ser `TRUNCATE ... RESTART IDENTITY CASCADE`, para que los ids
  autoincrementales sean predecibles.
- **NO SE DEBE** depender del orden de ejecución entre archivos de test.

**Consecuencia negativa declarada, textual:** *"El esquema de test lo construye `sequelize.sync()`,
no las migraciones. Es una **segunda fuente de verdad** del esquema: los tests podrían pasar contra
un esquema que las migraciones nunca producirían (NFR-R07, FG-6)."*

> **Traducido a esta story:** el test de la Tarea 2 corre contra un `identity_type` que es
> **`VARCHAR(255)`**, no el ENUM nativo. Todo lo que ese test puede afirmar sobre el tipo es lo que
> `sync()` produce. Lo que la migración produce se verifica a mano, en el plan de `api`.

#### ADR-001: Separación lectura / escritura

**Decisión:** `core` es el único que escribe; `api` conecta con un rol sin `INSERT`/`UPDATE`/`DELETE`.
Relevante acá por **la primera de sus tres excepciones declaradas**: las migraciones las corre la
api con `POSTGRESQL_MIGRATION_USER`. No hay decisión nueva en esta story; la escritura de esquema
cae en una excepción que ya existe.

**Consecuencia que esta story prepara:** a partir de S-016, `users` deja de ser la única tabla que
nadie escribe. Este plan **no** documenta ese cambio (no hay escritor todavía).

#### ADR-012: Monorepo con contexto en la raíz

Los paquetes del workspace se importan por nombre (`@jiku/models`) y los Dockerfiles se construyen
con contexto en la raíz. Relevante acá solo por una consecuencia operativa: **un cambio en
`packages/models/src/` obliga a reconstruir el paquete y a desplegar `api` y `core` juntos.**

#### Las dos columnas nuevas

| Columna | Tipo en el modelo | Tipo en la base | Restricciones | Por qué así |
|---|---|---|---|---|
| `roles` | `DataType.JSONB` | `JSONB` | `NOT NULL DEFAULT '[]'::jsonb` | La convención del esquema fija **JSONB para datos semiestructurados** (`jiku.md`:40). `NOT NULL` con default hace que "roles vacíos o ausentes" sea el **mismo caso** que una fila preexistente: lista vacía, sin autorización. Un `NULL` obligaría a una rama extra en la compuerta de S-017 y a un `?? []` en cada lectura |
| `identity_type` | **`DataType.STRING`** | ENUM nativo `identity_type` (`'person'`, `'service'`) | `NOT NULL DEFAULT 'person'` | La convención declara *"Enums: Tipos `ENUM` de PostgreSQL"* (`jiku.md`:39). El modelo lo declara `STRING` a propósito — ver abajo |

#### `DataType.STRING` y NO `DataType.ENUM` — el precedente, textual

`docs/db-schemas/jiku.md`:466-470, verbatim:

> **`byte_status` y `retention_status` son ENUM nativos en la base** (`file_byte_status` y
> `retention_status`) aunque el modelo los declare `DataType.STRING`. La divergencia es deliberada:
> declararlos `ENUM` en el modelo haría que `sync()` cree tipos con la convención de nombre de
> Sequelize (`enum_files_byte_status`), distintos de los que crea la migración.

El mismo razonamiento ya está escrito **en el código**, en el docblock de `file.model.ts`:28-31:

```
 * `byteStatus` y `retentionStatus` se declaran `DataType.STRING`, NO `DataType.ENUM`, igual
 * que `Attachment` hace con `entityType`: declararlos ENUM haría que `sync()` cree tipos con
 * la convención de nombre de Sequelize (`enum_files_byte_status`), distintos de los que la
 * migración crea (`file_byte_status`), agravando la divergencia sync()<->migraciones.
```

**Aplicado a esta story:** `DataType.ENUM` haría que `sync()` cree `enum_users_identity_type`,
distinto del `identity_type` que crea la migración. Las dos fuentes divergirían **y ningún test lo
vería**. La Tarea 2 incluye el escenario que fija esa ausencia como contrato (TS-13).

**Los tres enums de columna que ya existen en el paquete y cómo se ubican:**

|---|---|---|
| `ByteStatus` | dentro de `file.model.ts` | patrón por defecto: el enum vive con su modelo |
| `AttachmentEntityType` | dentro de `attachment.model.ts` | ídem |
| `RetentionStatus` | en `retention-status.enum.ts`, archivo propio | **excepción con causa**: `Attachment` y `File` se importan mutuamente, y leer un valor del otro módulo *en tiempo de decoración* rompe con "Cannot read properties of undefined". Sacarlo del ciclo es lo que lo evita |

`IdentityType` va **dentro de `user.model.ts`** (patrón por defecto). No aplica la excepción de
`RetentionStatus`: nadie lo lee en tiempo de decoración desde otro módulo del paquete.

#### `underscored: true` → `identity_type` (CA-2), verificado

`@Table` de `User` ya declara `underscored: true`, así que el atributo `identityType` mapea a la
columna `identity_type` **sin declarar `field` a mano**. Verificado empíricamente con
Sequelize 6.37.8:

```
idType.field : identity_type
roles.field  : roles
```

`roles` es una sola palabra: `underscored` no la altera.

**Los tres nombres conviven y no hay que "normalizarlos"**: `identity_type` en el payload del evento
del bus y en la base, `identityType` en el modelo y en el código.

#### El DDL que `sync()` emite — el contrato para la migración del plan de `api`

Verificado con el query generator de Sequelize 6.37.8 sobre la definición objetivo:

```
"roles"         JSONB NOT NULL DEFAULT '[]'
"identity_type" VARCHAR(255) NOT NULL DEFAULT 'person'
```

El DDL que la migración del plan de `api` va a crear (CA-3 de la story):

```sql
CREATE TYPE identity_type AS ENUM ('person', 'service');

ALTER TABLE users
  ADD COLUMN roles         JSONB           NOT NULL DEFAULT '[]'::jsonb,
  ADD COLUMN identity_type "identity_type" NOT NULL DEFAULT 'person';
```

**Comparación campo por campo (CA-11):**

| Campo | `sync()` (FUENTE 1, tests) | Migración (FUENTE 2, producción) | ¿Coincide? |
|---|---|---|---|
| Nombre de columna | `roles` | `roles` | **Sí** |
| Nombre de columna | `identity_type` | `identity_type` | **Sí** |
| Tipo de `roles` | `JSONB` | `JSONB` | **Sí** |
| Nulabilidad de `roles` | `NOT NULL` | `NOT NULL` | **Sí** |
| Default de `roles` | `'[]'` | `'[]'::jsonb` | **Sí** — mismo valor, distinta anotación de tipo. `jsonb_in('[]')` y `'[]'::jsonb` producen el mismo `[]` |
| Nulabilidad de `identity_type` | `NOT NULL` | `NOT NULL` | **Sí** |
| Default de `identity_type` | `'person'` | `'person'` | **Sí** |
| **Tipo de `identity_type`** | **`VARCHAR(255)`** | **ENUM nativo `identity_type`** | **NO — y es la divergencia deliberada** |

> **CA-11 se cierra con esta tabla, no a pesar de ella.** El criterio dice *"coinciden en nombre de
> columna, tipo, nulabilidad y default"*, y en el tipo de `identity_type` **no coinciden**. Leerlo
> como un fallo lleva al error exacto que la story quiere prevenir: "arreglar" el modelo a
> `DataType.ENUM`, que es lo que crea `enum_users_identity_type` y convierte una divergencia
> **conocida, precedentada y sin consecuencia** en una **desconocida**. La divergencia correcta es
> `STRING` ↔ ENUM nativo, exactamente la de `byte_status` y `retention_status`. La incorrecta es
> `enum_users_identity_type` ↔ `identity_type`. La Tarea 3 registra cuál de las dos hay.

**Lo que la divergencia cuesta, dicho explícitamente:** en `testing` la columna es un `VARCHAR(255)`
sin CHECK, así que **un test puede insertar `identityType: 'banana'` y va a pasar**, mientras
producción lo rechazaría con `invalid input value for enum identity_type`. Consecuencia práctica:
**no escribas un test que afirme que un valor inválido es rechazado** — fallaría en `testing` por
una razón que no es un bug del producto. La validación del valor vive en el consumidor (S-016), no
en la columna.

#### `defaultValue: []` no comparte el array entre instancias

Es el footgun obvio de un default mutable, y **en Sequelize 6.37.8 no aplica**: los defaults se
clonan en profundidad al inicializar cada instancia (`node_modules/sequelize/lib/model.js`:125-127,
`_.cloneDeep(value)`). Verificado:

```
i1.roles: ["x"]   i2.roles: []   shared reference?: false
```

Así que `defaultValue: []` es correcto y no hay que envolverlo en una función ni usar
`DataType.JSONB` con un default de string.

#### Índices: ninguno

Los dos accesos a estas columnas son **por PK** — la compuerta de S-017 hace
`User.findByPk(caller)` y el upsert de S-016 hace `findByPk(payload.id)`— y el filtro de `opus` se
aplica sobre un `include` ya acotado por `user_project_permissions`, con cardinalidad de unidades.
`roles` es JSONB con acceso por PK: se lee entera en el mismo SELECT de la fila, no hay consulta por
contenido, **no hay índice GIN que justificar**. Un índice acá sería costo de escritura sin lectura
que lo use.

#### Conteo de modelos: sigue en 26

Esta story **no agrega un modelo**, solo dos columnas. `allModels.length === 26` no cambia. (Nota:
ADR-005 dice "28 definiciones" en su texto — es un conteo desactualizado del ADR, no de esta story.
No lo toques acá.)

### API Context

**Esta story no toca HTTP, y el plan de `packages/models` menos que nada.** El paquete no conoce
Express ni rutas. Se registran las dos consecuencias que el cambio de modelo tiene sobre la api,
para que el implementador sepa **por qué no las resuelve en este plan**:

- **CA-9 — el schema `User` de `docs/apis/api.yaml`:2563 NO gana las columnas.** Es una decisión de
  seguridad (D-12 del REQ): ese schema es alcanzable por `external-user` vía
  `/api/opus/projects/:id/users`. → **plan de `api`**.
- **CA-12 — los `include` de `User` sin `attributes` empiezan a devolver las columnas nuevas.** Una
  columna nueva en un modelo compartido aparece **sola** en toda respuesta cuyo `include` no esté
  acotado. → **plan de `api`**.

> **La regla general que sale de acá, y que este plan es el lugar natural para registrar:** en este
> producto, **agregar una columna a un modelo de `@jiku/models` obliga a revisar los `include` de ese
> modelo en `api/lib/`**, porque el default de Sequelize es devolver todo y no hay cambio de spec que
> lo delate.

**`core` no expone nada de esto.** Su único uso de `User` es
`core/src/commands/requirements/requirements-subscriptors.ts`:36, un `findByPk` usado **solo como
chequeo de existencia** (`if (!user) return failure(...)`); la respuesta es
`success({ id: subscription.id })` y el objeto `user` nunca sale del comando. **Verificado: no hay
fuga por el bus.** Confirma la afirmación de la story de que `core` no cambia.

### Code Conventions

Del `_base` de los consumidores y del patrón de facto del paquete:

- **Archivos:** `kebab-case`. Los modelos son `{entidad}.model.ts`; un enum en archivo propio es
  `{nombre}.enum.ts`.
- **Enums:** `PascalCase` en nombre y miembros. **El valor va en español** por convención general
  (`RequirementState.Resuelto = 'resuelto'`) — **`IdentityType` es una excepción declarada**, con la
  razón escrita arriba y precedente en `visibility_level`, `ByteStatus` y `RetentionStatus`, cuyos
  valores también están en inglés.
- **Tipos e interfaces:** `PascalCase`, sin prefijo `I`.
- **Columnas:** se declaran en `camelCase`; `underscored: true` las mapea a `snake_case`.
- **`@Table`:** `timestamps: true`, `underscored: true`, `tableName` explícito. Ya están en `User`.
- **Comentarios:** en español, y comentan **el por qué, no el qué**. Es la convención más
  load-bearing de esta story: el docblock de `file.model.ts`:28-31 es la única razón de que alguien
  que abra el archivo entienda por qué no es `DataType.ENUM`. **Sin un comentario equivalente en
  `user.model.ts`, el próximo desarrollador lo "arregla".**
- **`strict: true`** en este paquete (a diferencia de `api`). El atributo se declara con `!`
  (definite assignment): `identityType!: IdentityType;`.
- **Lint:** `npm run lint --workspace @jiku/models` (cubre `./src`).

### 3. `IdentityType` como enum de TypeScript es una decisión de este plan, no de la story

Ni la story ni REQ-005 piden un enum: CA-1 dice `DataType.STRING`, `allowNull: false`,
`defaultValue: 'person'`, y S-016 escribe los valores como literales (`identityType: 'person'`).

Este plan **sí** declara `export enum IdentityType`, y la razón es que CA-1 invoca explícitamente el
precedente de `byte_status` / `retention_status` — y ese precedente **incluye el enum de TypeScript**:
las tres columnas de tipo enum del paquete (`ByteStatus`, `RetentionStatus`, `AttachmentEntityType`)
se declaran `DataType.STRING` **con** un enum exportado que tipa el atributo. Declarar la columna
`STRING` y tipar el atributo como `string` seguiría la mitad del precedente.

**Es una decisión reversible y contenida.** Si el equipo la rechaza, la alternativa es:

```ts
  @Column({ type: DataType.STRING, allowNull: false, defaultValue: 'person' })
    identityType!: string;
```

y quitar el re-export del barrel. Los valores en la base son idénticos en los dos casos, así que
S-016 y S-017 interoperan con cualquiera de las dos formas: el enum les da autocompletado, el
`string` les deja los literales que ya escribieron. Lo que **no** es opcional es `DataType.STRING`
sobre `DataType.ENUM`, que es lo que CA-1 fija.
