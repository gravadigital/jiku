# Story Plan: S-091 (api) - CORS solo bajo /api y log de caller conector en debug

## Status

**Status:** Completed

**Progress:** 2/2 tareas completadas

## Story Reference

- **Story:** [S-091](../stories/S-091.cors-solo-bajo-api-y-log-de-caller-conector-en-debug.md)
- **Service:** `api`
- **Origen:** [REQ-020](../requests/REQ-020.arreglos-chicos-de-pruebas-e2e-y-relevamiento-de-pantallas.md) (F-18, DD-1, DD-2)
- **Summary:** `cors()` deja de ser global y pasa a montarse solo bajo `/api`
  (`app.use('/api', cors())`), **en la misma posición** de la cadena de `api/app.ts`. Así los links
  compartidos `/p/docs/*` dejan de emitir `Access-Control-Allow-Origin: *` (cierra F-18: el HTML de un
  link no es legible por JavaScript de otro origen) y todo lo que está bajo `/api` responde
  exactamente igual que hoy, preflight incluido. Un test nuevo con la app real lo blinda.

> **Alcance de este plan:** solo el servicio `api` (CA-1, CA-2, CA-3). CA-4 a CA-6 (`callerClass` y
> nivel de log en `resolveActor`) son del servicio `core` y van en su propio plan. Los documentos
> (`http-server.md`, `api/overview.md`, `api/index.md`, ADR-015, flujos) son del servicio `docs`.

> **Precondición verificada sobre el árbol (2026-10-26, `561e85a`):** `api/app.ts` monta
> `app.use(cors())` global, entre `publicHostOnly` y `app.use('/api/docs', docsWriteJson)`. Ningún
> test de `api/tests/` menciona `cors` ni `access-control` (grep vacío), así que el cambio no rompe
> aserciones existentes. `cors` es la versión 2.8.6, con defaults `methods: 'GET,HEAD,PUT,PATCH,POST,DELETE'`,
> `preflightContinue: false`, `optionsSuccessStatus: 204`. `api/public/` (el `express.static`) no
> existe en el árbol.

### Service Architecture

**Estructura relevante:**

```
api/
├── app.ts                         Express, middleware global, montaje  <- se modifica
├── config/public.ts               exenciones de validateToken (NO se toca)
├── lib/public-routes/index.ts     router de /p/docs/* montado en la raíz (NO se toca)
├── lib/utils/middlewares/
│   ├── public-docs.ts             publicHostOnly, publicDocsHeaders, requirePublicHost, ... (NO se toca)
│   └── validate-token.ts          (NO se toca)
└── tests/
    ├── mocks/app.ts               start() = initialize()
    ├── helpers/public-docs.ts     PUBLIC_URL, PUBLIC_HOST, TOKEN, RESOLVED, publicGet, ...
    ├── helpers/docs-module.ts     docsAvailable, success, failure, ...
    └── routes/                    <- test nuevo
```

**Orden actual de la cadena en `api/app.ts` (de `http-server` y ADR-015):**

1. `app.set('trust proxy', ...)` si `API_TRUST_PROXY` viene.
2. **`publicHostOnly` — primer middleware** (DD-10): en el host de `JIKU_PUBLIC_URL` solo pasan
   `GET`/`HEAD` de `/p/docs/<algo>`; todo lo demás recibe el 404 genérico (`sendPublicNotice(res, 404)`).
3. **`cors()`** — HOY global. Por eso `Access-Control-Allow-Origin: *` llega también a `/p/docs/*` (F-18).
4. `app.use('/api/docs', docsWriteJson)` (768kb), `express.json()`, `express.urlencoded`,
   `express.static`, logger de requests con `ignoreRoute` para `/p/docs/*`.
5. `validateToken` global para `get`, `patch`, `post`, `put`, `delete` (**no** para `options`).
6. `app.use(publicRoutes)` en la raíz y luego el barrel de `lib/routes` bajo `/api`.
7. Fallback 404 y `payloadTooLargeHandler`.

**Código actual (`api/app.ts`, extracto):**

```ts
  // DD-10: PRIMER middleware. En el host público la api no sirve nada que no sea /p/docs/*; va antes
  // de validateToken y del logger para que esos 404 no revelen la api ni ensucien el log.
  app.use(publicHostOnly);
  app.use(cors());
  // Las escrituras de /docs llevan `content` inline de hasta 256 KiB (contrato de jiku-docs): ...
  app.use('/api/docs', docsWriteJson);
```

**Cadena de `/p/docs/*` (`lib/public-routes/index.ts`, sin cambios):**

```ts
router.use('/p/docs', publicDocsHeaders, publicDocsAccessLog, requirePublicHost, publicDocsRateLimit);
router.use(PublicDocsGet);
router.use(PublicDocsAttachmentsGet);
router.use('/p/docs', publicDocsNotFound);
```

`publicDocsHeaders` pone las cinco cabeceras de `PUBLIC_DOCS_HEADERS` en toda respuesta;
`requirePublicHost` responde `sendPublicNotice(res, 404)` si el `Host` no es el de `JIKU_PUBLIC_URL`
(o la variable no está). `sendPublicNotice` también setea `PUBLIC_DOCS_HEADERS` y responde HTML.

**Comportamiento esperado de `OPTIONS /p/docs/{token}` después del cambio** (deducido de la cadena,
es lo que el test fija):

- **Host público:** `publicHostOnly` corta con 404 (solo pasan `GET`/`HEAD`). Igual que hoy (hoy
  `publicHostOnly` ya va antes de `cors()`), sin cabeceras CORS.
- **Otro host:** hoy `cors()` responde **204 con cabeceras CORS**. Después: no hay CORS fuera de
  `/api`; `validateToken` no corre para `OPTIONS`; el router público lo lleva a `requirePublicHost`
  → **404** genérico con `PUBLIC_DOCS_HEADERS` y **sin** cabeceras CORS. Este es el caso que cambia
  de verdad para el preflight.

**Logging:** el cambio no agrega logs. `/p/docs/*` no se loguea con el token (`ignoreRoute`), sin cambios.

**Testing:** un archivo en `tests/routes/` contra la app real; aserciones `should`; nada de mocks de
Express ni de `cors`.

### Relevant ADRs

- **ADR-015: Módulos opcionales del bus** — la ruta pública `/p/docs/*` y el orden de `app.ts`.
  - Decision (punto pertinente): `publicHostOnly` es el primer middleware; `/p/docs/*` se monta en
    la raíz, fuera de `/api`. La consecuencia negativa registrada es exactamente F-18:
    *"`Access-Control-Allow-Origin: *` llega a `/p/docs/*`: `cors()` corre antes del router público.
    No amplía la exposición (la ruta ya es pública y de solo lectura), pero está."* Esta story la cierra.
  - Implementation Rules (las que aplican a esta story, verbatim):
    - `/p/docs/*` **NO DEBE** loguearse con el token en la URL (`ignoreRoute` en el logger de requests;
      línea propia con `jds_…` enmascarado). **NO DEBE** loguearse la `downloadUrl` ni el `htmlUrl`.
    - El host público **NO DEBE** servir nada más que `GET`/`HEAD` de `/p/docs/*`
      (`publicHostOnly` va primero en `app.ts`). La comparación **DEBE** hacerse contra el `Host` crudo,
      nunca contra `X-Forwarded-Host`.
    - Toda respuesta de `/p/docs/*` **DEBE** llevar las cinco cabeceras de `PUBLIC_DOCS_HEADERS` y el
      404 **DEBE** ser el mismo para cualquier link inválido.
    - Cualquier cambio en `api/config/public.ts` es un **cambio de seguridad** (ADR-008).
  - La revisión fechada de ADR-015 (F-18 resuelto) la escribe el servicio `docs`, no este plan.

- **ADR-007 / ADR-008: identidad y autorización deny-by-default** — la autenticación **no cambia**.
  No se toca `validateToken`, `config/public.ts` ni `getRolesFromToken` (DD-1 de la story).

## Tasks

### Task 1: Montar `cors()` solo bajo `/api` en `app.ts`

**Status:** Completed

#### Description

Cambiar `app.use(cors())` por `app.use('/api', cors())` **en la misma posición** de la cadena
(después de `publicHostOnly`, antes de `app.use('/api/docs', docsWriteJson)` y, por lo tanto, antes de
`validateToken`). Es DD-1 de la story: cierra F-18 sin tocar la autenticación. Bajo `/api` el
comportamiento queda idéntico (incluido el preflight que `cors()` responde con 204 antes de
`validateToken`); fuera de `/api` no queda ningún middleware CORS.

#### Acceptance Criteria

1. `api/app.ts` no contiene `app.use(cors())`; contiene `app.use('/api', cors())` inmediatamente
   después de `app.use(publicHostOnly)`.
2. `cors()` se invoca sin opciones (misma configuración que hoy).
3. Un comentario en español junto a la línea explica el por qué (F-18 / REQ-020: el HTML de un link
   compartido no tiene que ser legible por JavaScript de otro origen) y por qué la posición (antes de
   `validateToken`, para que el preflight y los 401 de `/api` sigan llevando CORS).
4. No cambian `config/public.ts`, `lib/utils/middlewares/validate-token.ts`,
   `lib/utils/middlewares/public-docs.ts`, `lib/public-routes/` ni `getRolesFromToken`.
5. `npm run build --workspace @jiku/api` y `npm run lint --workspace @jiku/api` pasan.

#### Technical Details

**Architectural Context References:**
- Orden de la cadena de `app.ts` (Service Architecture) y ADR-015 (`publicHostOnly` primero).
- DD-1 de la story; ADR-007/ADR-008 (autenticación sin cambios).

**Files to Create/Modify:**
- `app.ts`

**Implementation Notes:**

```ts
  app.use(publicHostOnly);
  // F-18 (REQ-020): CORS solo bajo /api. El HTML de un link compartido (/p/docs/*) no tiene que ser
  // legible por JavaScript de otro origen aunque se conozca el token. Va en esta posición, antes de
  // validateToken, para que el preflight de /api lo siga respondiendo cors() con 204 y los 401 lleven
  // Access-Control-Allow-Origin como hasta ahora.
  app.use('/api', cors());
```

- Montar en `'/api'` hace que Express le pase a `cors()` el `req.path` sin prefijo; `cors()` no mira
  el path, así que el resultado bajo `/api` es el mismo.

**Dependencies:**
- Ninguna nueva (`cors` ya es dependencia).

#### Testing Requirements

**Unit Tests:**
- No aplica (es configuración de la app; se cubre en Task 2 con la app real).

**Integration Tests:**
- Los de Task 2.

**Manual Testing:**
- `curl -si -H 'Origin: https://otro.example' -H 'Host: <host público>' http://localhost:<port>/p/docs/<token>` → sin `Access-Control-Allow-Origin`.
- `curl -si -X OPTIONS -H 'Origin: https://otro.example' -H 'Access-Control-Request-Method: GET' http://localhost:<port>/api/modules` → `204` con `Access-Control-Allow-Origin: *`.

#### Task Dependencies
