# Story Plan: S-017 (api) - El segundo plano: `core` autoriza a los callers del bus por `roles`

## Status

**Status:** Completed

**Progress:** 4/4 tareas completadas

## Story Reference

- **Story:** [S-017](../stories/S-017.core-autoriza-a-los-callers-del-bus-por-roles.md)
- **Service:** `api`
- **Summary:** Agregar **una entrada** al mapa `STATUS_BY_ERROR_CODE` de
  `api/lib/utils/bus/protocol.ts` —`caller_not_authorized: 403`— con el comentario que deja escrito
  por qué es 403 y no 400, y por qué **la api nunca lo va a recibir** y se mapea igual. Es todo el
  alcance de CA-13 punto 3 y de CA-14. Y verificar, con dos tests que hoy no existen, que **el plano
  HTTP no cambió**: la autorización sigue saliendo del claim de Zitadel y **no** del campo
  `users.roles` que S-015 creó (CA-16).

> **Es el más chico de los tres planes de S-017 y el que va último.** Una línea de código, un
> comentario, y el resto es verificación. La desproporción entre el tamaño del cambio y el tamaño
> de este documento es deliberada: **la entrada de un mapa es exactamente el tipo de cambio que se
> hace mal en treinta segundos** —el status equivocado, el bloque equivocado, o directamente
> olvidado— y el modo de fallo es silencioso: el usuario ve un 500 genérico donde el contrato
> promete un 403.

> **Los otros dos planes ya están cerrados.** `S-017.nats-protocol.*` (Completed) declaró
> `ErrorCode.CALLER_NOT_AUTHORIZED`; `S-017.core.*` (Completed) instaló la compuerta en los dos
> despachadores. **Este plan cierra el tercero de los tres lugares que exige la convención**, y
> mientras no se implemente, un rechazo de la compuerta que llegara a la api saldría **500**.

### Fuera de alcance (declarado, para no improvisarlo)

- **Ninguna lógica de autorización nueva en la api.** La compuerta es de `core` (CA-5). Si al
  implementar aparece la tentación de "chequear roles también acá", **no**: consultar
  `users.roles` del service user sería autorizar dos veces la misma cosa por dos fuentes distintas,
  con la peor de las dos decidiendo (CA-16).
- **Ningún archivo de `api/lib/routes/`.** Los 61 endpoints no cambian. Si el diff toca un archivo
  de ruta, el alcance se desbordó (TS-18).
- **`validate-token.ts`, `has-any-role.ts` y `validate-project-permission.ts` no se tocan.** Las
  tres capas de `authorization.md` siguen resolviéndose con el claim (TS-19).
- **`send-command.ts` no se toca.** El 503/504 de S-014 y la traducción por `httpStatusFor` ya
  están; el código nuevo entra por el mapa, no por una rama nueva.
- **El plano de consultas de la api no gana nada.** `bus().query()` existe desde S-014 y **no tiene
  ni un caller** en `api/lib` (verificado). No hay `sendQuery`, así que no hay una segunda
  traducción de errores donde agregar la entrada. CA-12 (que `external-publisher` no pueda
  consultar) se verifica en `core`, no acá.
- **Ninguna dependencia nueva de npm.**
- **Documentación de producto:** los cuatro flujos, ADR-007, ADR-008, `docs/prd/architecture.md` y
  las convenciones de `core` quedan desactualizados por S-017 y **se corrigen con
  `/product-change-technical-definition`**, no desde acá. El plan de `core` ya dejó ese pendiente
  registrado; este plan no lo amplía.
- **`api/README.md` no cambia.** No documenta el mapa de errores (verificado: no tiene ninguna
  sección de errores), así que no hay nada que actualizar ahí.
- **`docs/reusable-code/api/` no cambia.** Este plan no crea ningún símbolo reusable: agrega una
  clave a un objeto que es una **constante privada de módulo** (`const STATUS_BY_ERROR_CODE`, sin
  `export`). `httpStatusFor` ya existía y no cambia de firma.

### Service Architecture

No hay `src/`. El código vive en `lib/`, y el dominio está en el **prefijo del nombre del archivo de
ruta**. Lo que importa para este plan:

```
api/
├── lib/
│   ├── routes/               61 archivos, uno por endpoint (NINGUNO cambia acá)
│   └── utils/
│       ├── bus/
│       │   ├── index.ts          cliente NATS: request() y query()
│       │   ├── protocol.ts       <-- EL ÚNICO ARCHIVO QUE CAMBIA
│       │   └── send-command.ts   sendCommand/runCommand; llama a httpStatusFor
│       └── middlewares/      validate-token, has-any-role, ... (NO cambian)
└── tests/
    ├── routes/               61 archivos de rutas (uno nuevo acá, para CA-16)
    └── utils/                unitarios, SIN base de datos
        └── protocol.test.ts  <-- los tests del mapa
```

**Patrones y estrategia:**

- **Errores:** sin clases, sin `throw`, sin handler global. Se responde y se corta:
  `res.status(n).json({ code, message })`. La traducción `errorCode` del bus → status HTTP vive
  **exclusivamente** en `httpStatusFor` (`lib/utils/bus/protocol.ts`), y el cuerpo lo arma
  `errorBody`.
- **Logging:** Winston vía `logger`, nunca `console`. Este plan no agrega ningún log: el log del
  rechazo lo emite `core`.
- **Testing:** Mocha. `tests/utils/` corre **sin base** (`npm run test:unit`); `tests/routes/` corre
  contra un PostgreSQL real levantado por `tests/setup-env.ts`. El `FakeBus` ya está instalado para
  toda la corrida y se resetea por root hook: **no llames a `setBus`**.

### Relevant ADRs

#### ADR-002: Comandos NATS sin JetStream

**Decisión:** toda mutación se publica como comando request/reply a `core`, sin JetStream. Sin cola,
sin reintento, sin persistencia.

**Implementation Rules (verbatim, completas):**

- Todo comando **DEBE** publicarse con el subject `{instance}.{user-id}.gestion.v1.{comando}`,
  usando la gramática de `@jiku/nats-protocol`. **NO SE DEBE** construir el subject a mano.
- El cliente NATS **DEBE** fijar `inboxPrefix` explícitamente al conectar, con el hash del user id
  que calcula `@jiku/nats-protocol`. Sin esto las respuestas no llegan.
- El `userId` con el que publica la api **DEBE** salir de la key del service user, **NO** de una
  variable de entorno: tiene que coincidir exactamente con el `sub` que el auth-callout lee del
  token para autorizar el subject.
- Toda respuesta **DEBE** tener el formato `{ status: 'success', data }` o
  `{ status: 'failure', errorCode, errorMessage }`. **NO SE DEBEN** inventar otros formatos.
- Los comandos de creación **DEBEN** devolver únicamente `{ id }`. Las ediciones y borrados, nada.
- Todo `errorCode` nuevo **DEBE** agregarse al mapa de `api/lib/utils/bus/protocol.ts` con su
  status HTTP. Un código sin mapeo cae en un 500 genérico.
- El timeout de la request es `NATS_REQUEST_TIMEOUT_MS` (default **5000 ms**); al expirar la api
  **DEBE** responder **503**.
- **NO SE DEBE** transportar datos estructurados dentro de `errorMessage`. El caso actual de
  `daily_limit_exceeded` —que la api recupera parseando el mensaje con un regex— es deuda
  explícita, no un patrón a imitar.
- Core **NO DEBE** publicar mensajes: solo responde el `Reply` de la request que recibe.

> **La sexta regla es este plan entero.** Y la última quedó matizada por S-016 (core sí publica el
> consumo del evento de autenticación), pero eso no toca nada de acá.

#### ADR-008: Autorización deny-by-default por path, no por ruta

**Decisión:** `validateToken` global para todo path, con exenciones enumeradas en
`api/lib/config/public.ts`. Sobre esa base, `hasAnyRole([...])` por rol —**sobre los roles del claim
de Zitadel**— y `validateProjectPermissions` por entidad.

**Implementation Rules (verbatim, completas):**

- `validateToken` **DEBE** instalarse globalmente en `app.ts`. **NO SE DEBE** declarar
  autenticación ruta por ruta.
- Un endpoint público **DEBE** agregarse explícitamente a `api/lib/config/public.ts`. Cualquier
  cambio en ese archivo es un **cambio de seguridad** y debe revisarse como tal.
- Un endpoint público **DEBE** validar por su cuenta lo que corresponda.
- Un endpoint que requiere rol **DEBE** declarar `hasAnyRole([...])` explícitamente. La
  autenticación global no implica autorización.
- Un endpoint accesible a `external-user` **DEBE** además verificar permiso de proyecto: el rol
  solo no alcanza (ADR-006).
- Un tipo de entidad nuevo con adjuntos **DEBE** agregarse a la resolución de proyecto de
  `attachments-access.ts`. Un tipo no contemplado **no se autoriza**, que es el comportamiento
  correcto.
- Al leer un archivo de ruta, **NO SE DEBE** concluir que está desprotegido por no ver el
  middleware: la protección es global.

> **Para este plan la ADR importa por dos cosas.** Primero: *"sobre los roles del claim de
> Zitadel"* es **exactamente** CA-16, y el mapa cerrado deny-by-default de `core` es esta misma
> decisión aplicada al otro plano. Segundo: la consecuencia declarada —*"un archivo de ruta puede
> parecer desprotegido y estar cubierto"*— es la razón por la que la verificación de CA-16 tiene que
> ser **un test de ruta de punta a punta** y no la lectura de un handler.

#### ADR-007: Identidad en Zitadel con auth-callout

**Lo que importa acá:** la limitación estructural que la story cita. El `user-id` del **subject**
identifica al *service user* de la api, **no a la persona**, y por eso la "Alternativa 3" de esa ADR
—que core verifique al caller— se había descartado por **irrealizable**. S-017 la vuelve realizable
**para todo caller que no sea la api**, y el hueco que queda es el que la ADR ya declara: dentro del
canal de la api, `core` sigue confiando en el `creator` / `author` / `editor` del cuerpo. **Este plan
no cierra ese hueco y no pretende cerrarlo.**

#### ADR-013: Tests contra base real

**Lo que importa acá:** no se mockea Sequelize ni la base. Los tests de `tests/routes/` corren contra
un PostgreSQL real; el esquema se crea **una vez por corrida** con `sequelize.sync()` en
`mochaGlobalSetup`. En los tests la base **no** es de solo lectura (usuario `test`), así que un test
puede sembrar su propio estado con `Model.create()` y limpiarlo con `Model.destroy({ where: {} })`.
Es lo que hace posible el test de CA-16: sembrar una fila de `users` con `roles` **contradiciendo**
el claim del token.

### API Context

#### El único archivo que cambia: `api/lib/utils/bus/protocol.ts` (estado actual, verbatim)

```ts
/**
 * Traduce el error de core al status HTTP que espera cada front.
 *
 * Es lo que sostiene el contrato con web y opus-web: cada código de error sale con el
 * status que esas pantallas manejan.
 *
 * El catálogo definitivo de errores está pendiente (ver el protocolo); mientras tanto,
 * estos son los códigos que las rutas usan hoy.
 */
const STATUS_BY_ERROR_CODE: Record<string, number> = {
  invalid_fields: 400,
  client_not_found: 400,
  project_not_found: 400,
  objective_not_found: 400,
  person_not_found: 400,
  invalid_responsible_person: 400,
  requirement_project_mismatch: 400,
  daily_limit_exceeded: 400,
  invalid_date_range: 400,
  invalid_attachment_id: 400,
  resolution_required: 400,
  already_subscribed: 400,
  invalid_state_transition: 400,
  stage_not_found: 400,
  worked_time_not_found: 400,
  unworked_time_not_found: 400,

  // Ojo: `requirement_not_found` sale 400 porque las rutas que lo reciben lo usan como
  // validación de entrada (worked-times). La única que responde 404 —PATCH
  // /requirements/:reqid, cuando no existe el requisito del path— lo resuelve por su
  // cuenta antes de publicar.
  requirement_not_found: 400,
  user_not_found: 404,
  subscription_not_found: 404,

  // Los dos códigos de `files.{fileId}.request-download` son 404 y NO 400 porque describen
  // el ESTADO DEL RECURSO PEDIDO, no un problema con la entrada: el id llegó bien formado y
  // la api ya autorizó. `file_not_found` es el archivo borrado (retention_status != active);
  // `file_not_available`, el byte que nunca llegó al storage (byte_status = 'pending'), que
  // es el caso probable del PUT que falló en silencio. Sin estas dos entradas caerían en el
  // `|| 500` de abajo y el usuario vería un error genérico donde el contrato promete un 404
  // entendible (REQ-001, S-005).
  file_not_found: 404,
  file_not_available: 404,

  // Los dos rechazos de la política de subida (`files.request-upload`, core S-002) son 400
  // porque describen una ENTRADA rechazada: el nombre o el MIME están fuera de la allowlist,
  // o el tamaño supera el máximo. La política vive en `system_settings` y core la lee en
  // caliente, así que la api no puede anticiparlos: llegan como reply y se traducen acá
  // (REQ-001, S-004).
  file_type_not_allowed: 400,
  file_too_large: 400,

  // `file_not_owned` es 403 y NO 400, y ES LA ENTRADA MÁS FÁCIL DE MAPEAR MAL. Describe un
  // PERMISO —el archivo existe y está bien formado, pero lo subió otra persona (RF-12)—, no
  // una entrada inválida. Reusar `invalid_attachment_id`, que ya está mapeado a 400, haría
  // INDISTINGUIBLE "el archivo no existe" de "el archivo no es tuyo", y la segunda es
  // justamente la regla nueva que RF-12 introduce.
  //
  // No lo emite ningún comando que esta story publique: lo emiten los seis comandos de
  // dominio al vincular (S-003). Se mapea igual porque el mapa es DEL SERVICIO, no del
  // endpoint, y sin la entrada ese 403 saldría 500.
  file_not_owned: 403,

  unknown_command: 500,
  internal_error: 500,
};

export function httpStatusFor(errorCode: string | undefined): number {
  return (errorCode && STATUS_BY_ERROR_CODE[errorCode]) || 500;
}
```

> **El comentario de `file_not_owned` es el precedente literal que CA-14 manda seguir**, y ya
> contiene las dos mitades del argumento: *"describe un PERMISO, no una entrada inválida"* y *"se
> mapea igual porque el mapa es DEL SERVICIO, no del endpoint"*. La entrada nueva va **junto a esa**,
> no en el bloque de los 400 ni al final entre los 500.

#### `errorBody` — no cambia, pero define el cuerpo que sale

```ts
export function errorBody(reply: Reply): Record<string, unknown> {
  const body: Record<string, unknown> = {
    code: reply.errorCode || 'internal_error',
    message: reply.errorMessage || 'Internal error',
  };

  if (reply.errorCode === 'daily_limit_exceeded') {
    const match = /Minutos disponibles: (-?\d+)/.exec(reply.errorMessage || '');
    if (match) {
      body.remainingMinutes = Number(match[1]);
    }
  }

  return body;
}
```

Con el código nuevo, un reply `{ status: 'failure', errorCode: 'caller_not_authorized',
errorMessage: 'No autorizado' }` sale como `403 { code: 'caller_not_authorized', message: 'No
autorizado' }` — **sin** `remainingMinutes`, porque el `if` no aplica.

#### Quién llama a `httpStatusFor` (inventario completo, verificado)

Un solo caller de producción: `api/lib/utils/bus/send-command.ts:70`.

```ts
  if (reply.status !== 'success') {
    res.status(httpStatusFor(reply.errorCode)).json(errorBody(reply));
    return null;
  }
```

Y el `catch` de arriba, que **no** pasa por el mapa (S-014): 504 `gateway_timeout` si venció el
timeout, 503 `service_unavailable` en cualquier otro caso. El comentario que ya está en ese archivo
lo dice explícito: *"Ninguno de estos dos `code` va a STATUS_BY_ERROR_CODE: ese mapa traduce el
`errorCode` de un reply de core, y acá no hubo reply — los genera la api."*

> **Esa distinción es la trampa del plan.** `caller_not_authorized` **sí** viene en un reply de core,
> así que **sí** va al mapa. `gateway_timeout` y `service_unavailable` **no** vienen en un reply, así
> que **no** van — y `tests/utils/protocol.test.ts` ya tiene dos tests (TS-7 y TS-8 de S-014) cuya
> aserción es que ambos devuelven **500**, con un comentario que grita que **no se arreglen**
> agregándolos. No los toques.

#### `docs/apis/core.yaml` — el bloque de `ErrorCode`, ya escrito (verbatim)

```
        > **REQ-005 adds one code, and it is the first one emitted by the DISPATCHER rather than
        > by a command**: `caller_not_authorized` → **403**. Core now authorises the CALLER of the
        > subject against the roles persisted in `users.roles`, before resolving the method and
        > before opening the transaction.
        >
        > **One code for two situations, deliberately.** "No row in `users`" and "there is a row
        > but the role does not allow this method" answer **the same thing**. Telling them apart
        > would leak to an unauthorised caller whether an identity exists in the database — a free
        > oracle. `user_not_found` is **not** reused for the same reason, and because it is already
        > mapped to **404**, which is the wrong status for a permissions refusal.
        >
        > **403 and not 400:** it describes a permission, not malformed input — the same argument
        > already written next to `file_not_owned`. **In practice the api never receives it** (its
        > channel is exempt from the gate, see `info.description`); it is mapped anyway because
        > **the map belongs to the service, not to the endpoint**.
```

**Es la fuente de verdad del valor, del status y de la justificación.** Este plan no decide nada:
copia. El `enum` del mismo schema ya trae `- caller_not_authorized` como cuarto valor, junto a
`invalid_fields`, `internal_error` y `unknown_command` — la familia de los que no vienen de un
`execute()`.

#### `docs/apis/core.yaml` › `info.description` — la compuerta y la exención (verbatim, extracto)

````
    **Authorisation gate on the caller (REQ-005).** Both dispatchers — commands and queries —
    check the caller of the subject **before resolving the method and before opening the
    transaction**:

    ```
    caller == CORE_TRUSTED_PUBLISHER_ID  -> passes WITHOUT touching the database
    otherwise                            -> User.findByPk(caller)
                                              no row                        -> caller_not_authorized
                                              row, no role allows the method -> caller_not_authorized
    ```

    **Why the api's channel is exempt, and why it is not a shortcut.** Without the exemption there
    is a **silent total write outage**: if the api connects to the bus before core is subscribed,
    its authentication event is lost (core NATS, no retry, no record), the api stays connected and
    functional **without a row in `users`**, and core refuses **all 20 commands** with a 403 — until
    the api reconnects, which with a hot-renewed ~1 h token may not happen for days. The api also
    already authorises by role before publishing (`hasAnyRole`), so consulting `users.roles` for its
    service user would be authorising the same thing twice from two sources, with the worse of the
    two deciding.
````

> **La última oración es CA-16 escrita desde el otro lado del bus.** El contrato ya declara que la
> api **no** consulta `users.roles`. La Tarea 3 lo convierte en un test.

#### El plano de consultas de la api: nada que hacer

**Quién la lee, verificado archivo por archivo:**

| Consumidor | Lee `users.roles`? |
|---|---|
| `core` › los dos despachadores (S-017) | **Sí.** Es la compuerta |
| `api` › `validate-token.ts` | **No.** Hace `User.findByPk(sub)` para verificar que la fila exista y cargar `req.user`; los roles salen de `getRolesFromToken(req.decodedToken)` → `req.decodedTokenRoles` |

**La otra barrera que S-015 dejó y que conviene no romper:** los `include` de `User` en `api/lib`

respuestas HTTP **sin ningún cambio de spec que lo delate**. Este plan no agrega ningún `include`;
si al escribir el test de CA-16 hiciera falta uno, declarale esos `attributes`.

#### `autenticacion-y-entrada` › Paso 4 y Paso 5 (verbatim, extracto)

```
3. **Usuario:** busca la fila en `users` por el `sub`.

### Paso 5 (paralelo): Autenticación de los servicios en el bus
```

### Integration Points

- **NATS (→ core), request/reply sin JetStream.** La api publica en
  `{instance}.{user-id}.jiku-commands.v1.{comando}`; core responde un `Reply`. El `errorCode` de un
  `Reply` de falla se traduce con `httpStatusFor`. **Es el único punto de integración que este plan
  toca, y lo toca en la traducción, no en el transporte.**
- **El canal de la api está exento de la compuerta de core.** El `caller` que core lee del subject es
  el `sub` del service user de la api, que coincide con `CORE_TRUSTED_PUBLISHER_ID`. Por eso, en
  producción, `caller_not_authorized` **nunca llega a esta api**. La entrada del mapa existe porque
  el mapa es del servicio: si algún día el service user rota y la variable de core queda
  desalineada, el 403 aparecería — y con la entrada puesta, aparece como un 403 legible en lugar de
  un 500 genérico.
- **Zitadel.** JWKS con reintentos para validar el token; los roles salen del claim
  `urn:zitadel:iam:org:project:roles`. **No cambia.**
- **PostgreSQL, solo lectura** (ADR-001). **No cambia.** Este plan no agrega ni una consulta.
- **Sin dependencias externas nuevas.**

### Code Conventions

Lo que aplica a un cambio de este tamaño:

- **Comentar el por qué, en español.** Es la convención `_base` del servicio, y acá es el 90% del
  trabajo: la línea de código es trivial, el comentario es el entregable.
- **`printWidth: 100`** (Prettier). El comentario nuevo es largo: es el error más probable de todo el
  plan. Corré `npx prettier --check api` antes de cerrar.
- **Claves del mapa en `snake_case`**, exactamente como el valor que viaja por el bus. Un typo acá
  sale 500 en producción y **ningún test de `core` lo atrapa**, porque `core` usa la constante del
  paquete y la api indexa por string.
- **`code` es estable: los fronts hacen `switch` sobre él.** No renombres nada de lo existente.
- **No introduzcas clases de error ni `throw`.**
- **Imports relativos**, sin los alias de `module-alias`.
- **Tests con `should`**, sin mezclar `assert` ni `expect`. Un test no depende del orden de ejecución
  ni del estado que dejó otro; lo que crea, lo destruye en `after`.
- **No llames a `setBus`** en un archivo de test: el `FakeBus` ya está instalado y se resetea por
  root hook.
- **Lint antes de cerrar:** `npm run lint --workspace @jiku/api` (cubre solo `./lib`).

### Task 3: El gate de CA-16 — el plano HTTP sigue autorizando por el claim

## Notas de cierre para el implementor

1. **`npm run build:packages` antes de todo.** No porque este plan lo necesite para compilar —la
   clave del mapa es un string, no la constante— sino porque la Tarea 1 verifica contra el `dist/`
   del paquete y una copia vieja daría un falso negativo.

2. **La entrada del mapa es un string, no la constante, y está bien.** `STATUS_BY_ERROR_CODE` es un
   `Record<string, number>` y sus 26 claves ya son literales. **No** lo "mejores" indexando con
   `[ErrorCode.CALLER_NOT_AUTHORIZED]: 403`: sería el único de los 27 escrito distinto, y el archivo
   ya hace `export * from '@jiku/nats-protocol'` sin importar `ErrorCode` por nombre. El precio es
   que **un typo en la clave no lo atrapa `tsc`** — lo atrapa TS-5, que es por lo que ese test existe.

3. **Si `httpStatusFor('caller_not_authorized')` sigue devolviendo 500** después de la Tarea 2, el
   orden de diagnóstico es: (a) ¿la clave está en `snake_case` exacto, sin typo?; (b) ¿está **dentro**
   del objeto y no debajo del `};`?; (c) ¿estás corriendo el `protocol.ts` que editaste, o un `dist/`
   viejo?

4. **No agregues `gateway_timeout` ni `service_unavailable` al mapa.** Vas a ver dos tests cuya
   aserción es que devuelven **500** y un comentario que grita que no se arreglen. Es correcto: ese
   mapa traduce el `errorCode` **de un reply de core**, y esos dos los genera la api cuando **no
   hubo** reply. Son dos mapas distintos y confundirlos es el error fácil.

5. **"La api nunca lo recibe" no es un argumento para no mapearlo.** Es el argumento del comentario, y
   el precedente ya está escrito para `file_not_owned` —que tampoco lo emite ningún comando que la api
   publique— cuatro líneas más arriba. El mapa es **del servicio**. Y el día que aparezca —una
   rotación del service user que deje `CORE_TRUSTED_PUBLISHER_ID` desalineada— la diferencia es entre
   un 403 legible y un 500 genérico en cada escritura del producto.

6. **Si un test de la Tarea 3 se pone rojo en el futuro, no lo arregles: preguntá si el cambio era
   intencional.** Los dos existen para detectar exactamente un cambio —que alguien wiree `users.roles`
   al middleware de autenticación— que **parece una mejora**. Volver a CA-16 es una decisión de
   producto, no un fix de test.

7. **La revocación de un rol es eventualmente consistente en el plano del bus y no en el HTTP.** Es la
   asimetría que S-017 introduce y conviene saberla al leer un incidente: revocar en Zitadel tiene
   efecto **inmediato** por HTTP —el claim del próximo token ya no lo trae— y **diferido** por el bus,
   porque la fila de `users` conserva los roles anteriores hasta la próxima autenticación y las
   conexiones ya establecidas no se invalidan. Es la garantía que REQ-005 acepta explícitamente.
