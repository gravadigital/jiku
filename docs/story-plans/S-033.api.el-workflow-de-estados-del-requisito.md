- **Service:** `api`
- **Summary:** La api **elimina** la regla propia de tipo+conclusión de

## Hallazgos que hay que leer antes de escribir código

### H-1 · `core` ya no acota C-17 a `incidencia`: la regla que se elimina y la que la reemplaza no son iguales

El código actual de la api (`requirements-id-patch.ts:43`) solo exige tipo+conclusión cuando
`requirement.type === RequirementType.Incidencia`. **La regla nueva de `core` no tiene esa
condición.** `core/src/commands/requirements/requirements-edit.ts:97-108`:

```ts
if (payload.state === RequirementState.Resuelto) {
  // C-17: tipo y conclusión son obligatorios al resolver, venga del camino que venga
  // (CA-10) — sin acotarlo a `incidencia`, a diferencia de la regla que reemplaza.
  const resolutionType = payload.resolutionType ?? requirement.resolutionType;
  const resolutionConclusion = payload.resolutionConclusion ?? requirement.resolutionConclusion;
  if (!resolutionType || !resolutionConclusion) {
    return failure(ErrorCode.RESOLUTION_REQUIRED, 'Se requiere tipo y conclusión para resolver un requisito');
  }
}
```

Y el comentario del propio archivo lo dice explícito: *"sin acotarlo a `incidencia`, a diferencia
de la regla que reemplaza"*. `docs/apis/core.yaml` (`requirements.{id}.resolve`) lo confirma:
**"C-17 applies to every type, not just `incidencia`"**.

**Consecuencia para los tests de la api:** el test existente `TS-8: should resolve non-incidencia
requirement without type nor conclusion` (línea ~563 de
`tests/routes/requirements-id-patch.test.ts`), que hoy verifica `funcionalidad` resolviéndose
**sin** tipo ni conclusión y esperando **200**, queda **falso** después de esta story: `core` va a
rechazarlo con `resolution_required` → 400. Esta story **corrige ese test** (Tarea 2) para afirmar
el comportamiento nuevo, no lo elimina en silencio — sería dejar en verde una aserción que ya no
es cierta sobre el sistema.

### H-2 · El mensaje de error cambia de texto, aunque el código y el status no

El mensaje que la api devolvía era *"Se requiere tipo y conclusión para resolver una incidencia"*.
El mensaje que `core` devuelve por `.edit` es *"Se requiere tipo y conclusión para resolver un
requisito"* (sin acotarlo a incidencia, coherente con H-1). El `code` (`resolution_required`) y el
`status` (400) **no cambian** (CA-13) — es el único texto que un test que compare `message` de
forma literal necesita actualizar. Los tests de la api en general afirman `response.body.code`, no
`message` (ver testing.md — las aserciones son sobre `code`), así que el impacto real es bajo, pero
hay que revisarlo caso por caso al tocar cada test.

### H-3 · Dos imports quedan huérfanos al borrar la función, y el lint corta el build si no se limpian

`requirements-id-patch.ts` importa hoy `NextFunction` (`express`) y `RequirementType`
(`@jiku/models`) **solo** para la firma y el cuerpo de `validateResolutionRules`
(líneas 1, 3, 39, 43). Ninguna otra función del archivo los usa:

```ts
import { Request, Response, NextFunction, Router } from 'express';                                    // NextFunction: solo en validateResolutionRules
import { Person, Project, RequirementResolution, RequirementState, RequirementType, RequirementVisibilityLevel } from '@jiku/models';  // RequirementType: solo en validateResolutionRules
```

`RequirementState` **se queda** — lo sigue usando el schema de Joi (`patchSchema.state`, línea 18).
`Request`, `Response`, `Router` se quedan — los usa `patchRequirement`. Al borrar la función, borrar
también `NextFunction` y `RequirementType` de sus imports respectivos, o
`npm run lint --workspace @jiku/api` falla (regla del `_base.md`: *"Lint antes de dar por
terminado"*).

### H-4 · El middleware sale de la cadena del router, no solo se borra su definición

`validateResolutionRules` aparece en **dos** lugares del archivo: la definición (líneas 33-57) y su
uso en la cadena de `router.patch(...)` (línea 101, entre `validateRequirement` y
`patchRequirement`). Los dos tienen que salir juntos — dejar la referencia sin la función definida
es un error de compilación, no un olvido silencioso, así que TypeScript lo va a marcar solo. Se
cita igual porque el orden de la cadena (`hasAnyRole` → `validateBodyFields` → `validateRequirement`
→ `patchRequirement`) es el que queda después, y conviene verificar que sigue el orden canónico de
`http-server.md` (rol → forma del input → entidad → permiso → negocio → handler): sin
`validateResolutionRules`, no queda ningún paso de "reglas de negocio" en esta cadena — la regla se
mudó entera a `core`, no quedó ninguna mitad acá.

### H-5 · La api conserva `resolutionType` / `resolutionConclusion` / `resolutionComment` en su schema Joi — no se tocan

CA-12 elimina la **regla de validación** (la función), no los **campos**. `patchSchema` sigue
aceptando `resolutionType`, `resolutionConclusion`, `resolutionComment` (líneas 19-21): la api los
sigue reenviando en el payload del comando `requirements.{id}.edit`, y `core` los sigue
persistiendo. Esto ya lo confirma `docs/apis/api.yaml` (la request body del PATCH no cambió sus
propiedades). **No hay tarea que toque el schema Joi.**

## Architectural Context

### Tech Stack

- **Lenguaje:** TypeScript (`strict` desactivado — `_base.md`), Node.js
- **Framework HTTP:** Express 5
- **Validación:** Joi (inline en el archivo de ruta)
- **ORM:** Sequelize, **solo lectura** (`lib/models/index.ts:19-31`)
- **Bus:** NATS request/reply (`nats` 2.29), `@jiku/nats-protocol` para subjects y el envelope

- **Testing:** Mocha 11.7 + `should` 13.2 + `sinon` 21, PostgreSQL real en Docker, `FakeBus` que
  ejecuta `core`

`{recurso}-{path}-{método}`. `requirements-id-patch.ts` es el archivo de
`PATCH /api/requirements/:reqid`.

```

├── lib/
│   ├── routes/
│   │   ├── requirements-id-patch.ts   A MODIFICAR (Tarea 1) — eliminar validateResolutionRules

│   │   │   └── protocol.ts            STATUS_BY_ERROR_CODE — YA mapea los 2 códigos, sin cambios
│   │   └── middlewares/

├── tests/
│   └── routes/
```

**El comando NO abre transacción en la api** — la api publica y espera, `core` decide y escribe. La
api solo relee después con Sequelize de solo lectura (`bus-commands.md`).

`invalid_state_transition`: **ya están en `STATUS_BY_ERROR_CODE`**, mapeados a 400 los dos.

### El middleware que se elimina (código actual, íntegro)

`api/lib/routes/requirements-id-patch.ts:33-57`, con su comentario:

```ts
/**
 * Regla heredada: una incidencia no se resuelve sin tipo y conclusión.
 *
 * Se queda en la api porque combina el estado que llega con el que ya tiene el requisito,
 * y devuelve un código propio que no está en el protocolo.
 */
function validateResolutionRules(req: Request, res: Response, next: NextFunction) {
  const requirement = req.requirement;
  const { resolutionType, resolutionConclusion, state } = req.body;

  if (state === RequirementState.Resuelto && requirement.type === RequirementType.Incidencia) {
    const finalType = resolutionType !== undefined ? resolutionType : requirement.resolutionType;
    const finalConclusion = resolutionConclusion !== undefined
      ? resolutionConclusion
      : requirement.resolutionConclusion;
    if (!finalType || !finalConclusion) {
      return res.status(400).json({
        code: 'resolution_required',
        message: 'Se requiere tipo y conclusión para resolver una incidencia',
      });
    }
  }

  return next();
}
```

Y su lugar en la cadena, que también sale:

```ts
// líneas 97-103 — ANTES
router.patch('/requirements/:reqid',
  hasAnyRole(['user', 'admin']),
  validateBodyFields(patchSchema),
  validateRequirement,
  validateResolutionRules,      // <- ELIMINAR esta línea
  patchRequirement
);
```

```ts
// DESPUÉS

  hasAnyRole(['user', 'admin']),
  validateBodyFields(patchSchema),

  patchRequirement
```

### El comando de `core` que reemplaza la regla (ya implementado — Completed, referencia)

`core/src/commands/requirements/requirements-edit.ts:87-109`, la regla que reemplaza a la de la
api, con la tabla de transiciones (C-15) y la obligatoriedad de tipo+conclusión (C-17):

```ts
// LA TABLA DE TRANSICIONES (C-15, S-033): `edit` es el canal por el que REALMENTE llega la
// resolución (H-2 del Story Plan de core — `resolve` no tiene ruta HTTP que lo publique), así
// que el validador va acá y no solo en `resolve`. `type` se lee de LA FILA
// (`requirement.type`), nunca de `payload.type`.
if (payload.state !== undefined && payload.state !== requirement.state) {
  if (!isTransitionAllowed(requirement.state, payload.state, requirement.type)) {
    return failure(ErrorCode.INVALID_STATE_TRANSITION, 'Transición de estado no permitida');
  }
  if (payload.state === RequirementState.Resuelto) {
    // C-17: tipo y conclusión son obligatorios al resolver, venga del camino que venga
    // (CA-10) — sin acotarlo a `incidencia`, a diferencia de la regla que reemplaza.
    const resolutionType = payload.resolutionType ?? requirement.resolutionType;
    const resolutionConclusion = payload.resolutionConclusion ?? requirement.resolutionConclusion;
    if (!resolutionType || !resolutionConclusion) {
      return failure(
        ErrorCode.RESOLUTION_REQUIRED,
        'Se requiere tipo y conclusión para resolver un requisito'
      );
    }
  }
}
```

**Puntos clave para escribir los tests de la api (Tarea 2):**
- El chequeo de `core` solo dispara cuando `payload.state !== undefined && payload.state !==
  requirement.state` — es decir, cuando el PATCH **trae** `state` y ese `state` es distinto al
  actual. Un PATCH que edita `resolutionComment` sin tocar `state` en un requisito ya `resuelto`
  **no** dispara el chequeo (mismo comportamiento que la regla vieja de la api, que también estaba
  condicionada a `state === RequirementState.Resuelto` en el payload).
- `resolutionType` / `resolutionConclusion` finales se resuelven con `??` entre lo que llega en el
  payload y lo que ya tiene la fila — mismo criterio de "campo ya cargado + campo en el mismo PATCH"
  que tenía la regla vieja (con `!==  undefined` en vez de `??`, pero el resultado observable es el
  mismo: si cualquiera de los dos lados aporta el valor, alcanza).
- **La condición de tipo desaparece.** La regla vieja exigía `requirement.type ===
  RequirementType.Incidencia`; la nueva no tiene esa cláusula. Aplica a `funcionalidad`, `mejora`,
  `otro` e `incidencia` por igual.

## Tasks

### Task 1: Eliminar `validateResolutionRules` y sus dos imports huérfanos

**Status:** Completed

#### Description

Eliminar la función `validateResolutionRules` de `requirements-id-patch.ts` (definición y su
posición en la cadena del router), y limpiar los imports que quedan sin uso. Es la única regla
propia que le quedaba a este endpoint (CA-12): después de esta tarea, la api no vuelve a decidir si
un requisito puede resolverse — solo publica el comando y traduce lo que `core` responde.

- Qué se implementa: borrado de código, sin lógica nueva.
- Por qué es necesaria: `core` ya aplica la misma regla —ampliada a todo `type`, no solo
  `incidencia`— desde el plan `S-033 (core)` (Completed). Dejar la regla vieja en la api la
  duplicaría con un criterio **más estricto** (`core`) conviviendo con uno **más laxo** (api, solo
  `incidencia`), que es peor que no tener ninguna: la api aceptaría en el schema un caso que
  después el bus rechaza, y el usuario vería el error un paso más tarde de lo necesario, pero
  **igual lo vería** — no es un hueco de seguridad, es una regla redundante y desactualizada.
- Contexto importante: ver H-1 a H-4 arriba. La eliminación es mecánica pero tiene dos imports
  huérfanos (H-3) que rompen el lint si no se limpian.

#### Acceptance Criteria

1. La función `validateResolutionRules` (líneas 33-57 del archivo original, con su comentario) ya
   no existe en `requirements-id-patch.ts`.
2. La cadena de `router.patch('/requirements/:reqid', ...)` ya no incluye
   `validateResolutionRules` — queda `hasAnyRole` → `validateBodyFields` → `validateRequirement` →
   `patchRequirement`, sin ningún middleware de "reglas de negocio" entre `validateRequirement` y
   `patchRequirement`.
3. El import de `express` ya no incluye `NextFunction` (era usado solo por la función eliminada).
4. El import de `@jiku/models` ya no incluye `RequirementType` (era usado solo por la función
