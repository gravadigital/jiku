# Story Plan: S-013 (core) - `jiku-queries` registrado y descubrible, con su conexión de solo lectura

## Status

**Status:** Completed

**Progress:** 7/7 tareas completadas

## Story Reference

- **Story:** [S-013](../stories/S-013.jiku-queries-registrado-y-descubrible.md)
- **Service:** `core`
- **Summary:** Montar `jiku-queries` como **segundo servicio micro del mismo proceso** de `core`:
  una conexión nueva de **solo lectura** a Postgres (`src/models/read.ts`, **sin `models`**), un
  módulo nuevo `src/queries/` (registry + dispatcher **sin transacción** + los 6 endpoints que
  contestan un `failure` bien formado), y un elemento más en la llamada a `BusHost` de
  `src/index.ts`. `bus/dispatcher.ts`, `bus/service.ts`, `bus/host.ts`, `commands/registry.ts`,
  los 20 comandos y `models/index.ts` **no se tocan**, y por eso los tests existentes pasan sin una
  sola aserción modificada.

> **El riesgo real de esta story no es el bus: es la base.** Registrar el segundo servicio es
> sumar un objeto literal a una llamada que ya recibe varargs (S-012 lo dejó así a propósito). Lo
> que introduce riesgo nuevo es la **segunda instancia de Sequelize en un mismo proceso**: si
> `read.ts` recibiera `models`, **reasignaría** las clases de `@jiku/models` y —en el sentido
> peligroso— las consultas saldrían por el usuario dueño, con ADR-001 roto **y sin un solo
> síntoma**. CA-7 (verificar que `read.ts` no recibe `models`) y CA-6 (un alta que funciona
> después de que la lectura usó su conexión) son las dos redes, y hay que escribirlas aunque hoy
> parezcan triviales.

> **Sin contrato de consultas (RF-10).** Los 6 endpoints existen, aparecen en `nats micro info`,
> tienen queue group y contadores propios, y **contestan un `failure` bien formado a cualquier
> request**. **Qué** contesta cada uno lo define un requerimiento posterior, cuyo insumo
> (`bus-api-consultas.md`, sin trackear en la raíz del monorepo) **no debe borrarse**. El riesgo de
> alcance más probable de esta story es "aprovechar" para escribir el contrato: seis endpoints que
> devuelven `failure` se sienten incompletos. **No lo son:** CA-10 define "listo" como *el endpoint
> contesta*, no *qué* contesta.

> **Este plan no toca `packages/nats-protocol`, `api`, `deploy`, `web` ni `opus-web`.** La story
> los marca `Ninguno` y está verificado en el árbol: `QUERY_SERVICE`, `querySubject()`,
> `groupSubject()`, `endpointName()`, `endpointSubject()` y `methodFromSubject()` ya existen
> (S-011); las variables `POSTGRESQL_READ_USER/_PASSWORD/_POOL_MAX`,
> `POSTGRESQL_STATEMENT_TIMEOUT_MS`, `NATS_QUERY_SERVICE` y `NATS_QUERY_TIMEOUT_MS` ya están en
> `deploy/.env.dist` y en los tres compose; y el auth-callout ya autoriza
> `{instance}.*.jiku-queries.v1.>` y `$SRV.>` en `deploy/nats/auth-callout/templates/core.yaml`.

**Las tres piezas que este plan usa tal cual, sin modificarlas:**

1. **`BusHost` recibe los specs por varargs** (`constructor(...specs: ServiceSpec[])`) y los
   registra **en serie**, sin `try/catch`, propagando el error: *"un `Promise.all` acá podría dejar
   el proceso arriba con un servicio registrado y el otro caído"*. **CA-12 sale de eso, no de
   código nuevo.**
2. **`stop()` para todos los servicios antes de drenar**
   (`await Promise.all(this.services.map((s) => s.stop()))` → `drain()` → `close()`). **CA-13 sale
   de que la lista tenga dos elementos.**
3. **`registerService(nc, spec)` es genérico**: arma el grupo con `groupSubject(spec.name)`, deriva
   `endpointName`/`endpointSubject` de cada patrón, verifica duplicados con un `Set` y falla el
   registro si hay solapamiento. El `handle()` que garantiza que **ninguna request queda sin
   contestar** (cuerpo vacío → `{}`, no-JSON → `invalid_fields`, excepción → `internal_error`)
   **es el mismo para los dos servicios**: eso es CA-14, y no requiere código nuevo.

**Firma exacta del spec, que este plan tiene que llenar por segunda vez:**

```ts
// core/src/bus/service.ts
export interface ServiceSpec {
  /** Nombre en el bus, queue group, y token `{svc}` del subject. */
  name: string;
  description: string;
  /** Patrones de método: `tasks.{id}.edit`, `clients.new`, … Salen del registry. */
  patterns: string[];
  /** Resuelve la request. Nunca lanza: siempre devuelve un `Reply`. */
  handle: (subject: string, payload: unknown) => Promise<Reply>;
}
```

**`src/index.ts` hoy, completo** (es el archivo que la Tarea 5 modifica):

```ts
import * as dotenv from 'dotenv';
dotenv.config();

import { COMMAND_SERVICE } from '@jiku/nats-protocol';
import logger from './logger';
import initializeDb from './models';
import { loadConfig } from './config';
import { BusHost } from './bus/host';
import { Dispatcher } from './bus/dispatcher';
import { registry } from './commands';

const dispatcher = new Dispatcher(registry);

// Un spec por servicio del bus. Hoy hay uno; el segundo es un elemento más en esta misma
// llamada, sobre la misma conexión.
const host = new BusHost({
  name: COMMAND_SERVICE,
  description: 'Comandos de dominio de Jiku: la única vía de escritura a la base',
  patterns: registry.patterns(),
  handle: (subject, payload) => dispatcher.dispatch(subject, payload),
});

async function main(): Promise<void> {
  // Antes que nada: si falta configuración obligatoria, el proceso tiene que morir acá y no
  // atender el primer comando con una identidad mal resuelta.
  loadConfig();

  await initializeDb();
  logger.info(`[core] ${registry.patterns().length} registered commands`);
  await host.start();
}

/** Para los servicios y drena el bus antes de salir, para no cortar mensajes en vuelo. */
function shutdown(signal: string): void {
  logger.info(`[core] ${signal} recibido, cerrando`);
  host
    .stop()
    .then(() => process.exit(0))
    .catch(() => process.exit(1));
}

process.on('SIGTERM', () => shutdown('SIGTERM'));
process.on('SIGINT', () => shutdown('SIGINT'));

main().catch((error: Error) => {
  logger.error(`[core] no pudo arrancar: ${error.message}`);
  logger.error(error.stack);
  process.exit(1);
});
```

### Convenciones activas y qué exige cada una acá

Del `manifest.yaml` de `core` (`type: worker`, `language: node`), **las 12 son custom** y viven en
`docs/architectures/core/conventions/`. Las que gobiernan este plan:

**`_base`**
- TypeScript obligatorio, `strict: true` **no se apaga**. Más `noUnusedLocals`,
  `noUnusedParameters`, `noImplicitReturns`.
- Archivos en `kebab-case.ts`; clases en `PascalCase` (`QueryRegistry`, `QueryDispatcher`);
  constantes de módulo en `SCREAMING_SNAKE_CASE`.
- **Imports relativos** (`../logger`, `./registry`), sin alias. Los paquetes del workspace por
  nombre. Orden: librerías → `@jiku/*` → relativos.
- **Un archivo por unidad de trabajo.** La regla de comandos (`{entidad}-{acción}.ts`) se traslada
  literal a las consultas: `projects-list.ts`, `tasks-get.ts`, …
- Cada archivo exporta la unidad **nombrada y también como `default`**; el `index.ts` importa el
  default.
- **Comentarios en español**, y explican **el por qué**. Lo que amerita comentario: *una decisión
  que parece un error y no lo es*. Este plan tiene tres de ésas, y las tres hay que comentarlas:
  el `read.ts` sin `models`, el dispatcher que no abre transacción, y el `failure` de los seis
  stubs.
- Un comentario que marca algo transitorio **dice cuándo desaparece**. Los seis stubs son
  transitorios: el comentario tiene que nombrar al REQ del contrato.

**`orm`** (la que este plan estira, sin romper)
- La conexión de comandos usa el **usuario dueño**, y es la única que registra `allModels`.
- Los modelos se importan de `@jiku/models`; **no se define un modelo en core**.
- **Toda operación de Sequelize de un comando lleva `{ transaction: ctx.transaction }`**,
  incluidas las lecturas. **Esto NO aplica a las consultas**, que no tienen transacción (RF-9): es
  la primera vez que el servicio tiene acceso a datos fuera de esa regla, y por eso vive en un
  módulo aparte y no en `commands/`.
- No se agrega capa de repositorio ni de servicio. Una consulta, como un comando, **es** la unidad
  completa.
- Core no ejecuta migraciones. **Este plan no agrega ninguna** (sin DDL).

**`bus-consumer`** — la convención que RF-24 reescribe entera (se tramita por
`/product-change-technical-definition`, **no por esta story**). Su texto vigente describe el
`consumer.ts` que S-012 ya eliminó, así que **hay que leerla por sus reglas, no por su código**.
Lo que este plan tiene que respetar, porque no cambia:
- Los helpers de subject se usan de `@jiku/nats-protocol`. **No se arma un subject a mano ni se
  parsea con `split` fuera del paquete.** En este plan eso significa `methodFromSubject()` y
  `callerFromSubject()` en el dispatcher de consultas, y `groupSubject(QUERY_SERVICE)` (que ya usa
  `registerService`).
- **Todo mensaje recibido se responde**: éxito, falla o error interno. Nunca se descarta en
  silencio. **Es CA-10 y CA-14.**
- La suscripción siempre lleva queue group propio. Sin él, el balanceo se comparte.
- `stop()` drena antes de cerrar. **No agregues un `process.exit()` que se saltee el drain.**
- Core **no publica** en el bus: solo responde. Vale igual para los dos servicios.
- No se agrega JetStream (ADR-002).

**`error-handling`**
- El `Reply` se construye **siempre** con `success()` / `failure()` de `@jiku/nats-protocol`,
  nunca a mano.
- Se usa la **constante** `ErrorCode.X`, **no el literal**.
- **Un código nuevo se agrega en tres lugares**: el paquete, `docs/apis/core.yaml` y el mapa a HTTP
  de la api. **Los tres, o el usuario ve un 500.** Es la razón por la que este plan **no inventa un
  código nuevo** para el `failure` de los stubs (ver "Decisiones que este plan toma").
- El detalle de un error inesperado va **al log**; el mensaje que cruza el bus es genérico.
- Los mensajes nuevos van en **español** y **no llevan datos internos** (ids de otras entidades,
  nombres de columna, detalle de excepción).
- **El despachador nunca lanza**: todo error se traduce a un `Reply` de falla.

**`logging`**
- Un solo logger, importado de `../logger`. **Nunca `console.log`.**
- Prefijos de origen: `[core]` arranque y señales · `[bus]` conexión/registro/estado del bus ·
  `[dispatch]` el despachador de comandos · `[cmd]` la traza de `LOG_COMMANDS` · `[DB]` Sequelize.
  **Este plan agrega uno: `[query]`**, para el despachador de consultas. Es el mínimo cambio que
  hace distinguible en el log una falla de lectura de una de escritura.
- Niveles: `error` lo inesperado · `warn` entrada inválida que el servicio maneja bien · `info`
  hitos de ciclo de vida · `debug` diagnóstico.

**`env-config`**
- `dotenv.config()` en las **dos primeras líneas** de `src/index.ts`, antes de cualquier otro
  import. `read.ts` va a leer `process.env` **al importarse**, así que ese orden ahora también lo
  protege a él.
- **Los defaults van donde se lee la variable, con `||`.** No se duplica un default en dos
  archivos. `POSTGRESQL_READ_POOL_MAX` → `|| 10`; `POSTGRESQL_STATEMENT_TIMEOUT_MS` → `|| 8000`.
- **Un comando nunca lee `process.env`.** Vale igual para una consulta: lo que necesite viene por
  el contexto.
- **Una variable nueva se documenta en tres lugares:** la convención, `core/README.md` y
  `deploy/.env.dist`. Las cuatro de este plan **ya están en `.env.dist` y en los tres compose**
  (S-011); la convención la actualiza RF-24 por otra vía; **le toca `core/README.md`** (Tarea 6).
- El patrón general es `process.env.X || 'default'`. La única excepción con assert es
  `CORE_TRUSTED_PUBLISHER_ID`. **Este plan no agrega asserts**: la conexión de lectura mal
  configurada falla **ruidosamente al primer `SELECT`**, que es el modo de falla que la story
  quiere.

**`testing`**
- Los tests de comandos entran por `dispatch()`, **nunca** llamando a `execute()` directamente.
- **No se mockea Sequelize ni la base.** En este plan la regla es **el punto entero**: CA-5 es una
  garantía de Postgres, y contra un mock no se puede verificar.
- Un archivo de test por módulo; los fixtures se crean en el `before` del propio archivo, con los
  modelos directamente. No hay factories compartidas.
- `TZ=UTC` está fijado en `tests/setup-env.ts`.
- `core/.mocharc.json` tiene `recursive: true`, así que **`tests/queries/*.test.ts` y
  `tests/models/*.test.ts` se recogen solos**; y su `require` incluye `setup-env.ts` +
  `global-setup.ts`, así que **cualquier** archivo de test levanta el PostgreSQL efímero.
- `timeout: 60000` por test: alcanza de sobra para los `pg_sleep` de este plan.

**`contract-translation`** — no se ejercita en este plan (no hay contrato), pero **sí fija dónde
va**: la traducción `task → objectives`, `comments → objective_activity`/`requirement_activity`,
y `priority` enum ↔ entero vive **dentro** del módulo de consultas, igual que en los comandos
(ADR-004). Los seis stubs dejan el comentario que lo dice, para que el REQ del contrato no la
ponga en otro lado.

**`validation`** — sin contrato no hay esquema Joi. **No agregues uno "por si acaso"**: un esquema
sin contrato inventa exactamente lo que RF-10 declara fuera de alcance.

### ADRs relevantes

#### ADR-001: Separación lectura/escritura por credenciales de base de datos

**Decisión:** la separación **la impone PostgreSQL por permisos**, no una convención de código.
`api` conecta con un rol sin `INSERT`/`UPDATE`/`DELETE`; `core` con el **usuario dueño**.

**Implementation Rules (verbatim):**
- Toda escritura de dominio nueva **DEBE** implementarse como comando en `core`. **NO SE DEBE**
  agregar escritura con el ORM en `api`.
- La conexión de `api` **DEBE** usar credenciales sin `INSERT`/`UPDATE`/`DELETE`. Si un endpoint
  nuevo requiere escribir, la respuesta correcta es un comando, no ampliar los permisos del rol.
- La conexión de `core` **DEBE** usar el usuario dueño de la base.
- Las migraciones **DEBEN** correr desde `api` con `POSTGRESQL_MIGRATION_USER`, nunca desde `core`.
- Después de publicar un comando de creación, la api **DEBE** releer la base para armar la
  respuesta: core devuelve solo `{ id }` y el contrato con los frontends es el recurso completo
  con sus relaciones.
- Un endpoint que lee **NO DEBE** pasar por el bus: la lectura va directo a PostgreSQL desde la api.
  **Excepción declarada desde REQ-001 (S-005): la lectura de archivos.**

**Cómo aplica acá — es el ADR que sostiene el diseño de `read.ts`:**
- La regla *"la conexión de core DEBE usar el usuario dueño"* sigue valiendo **para los comandos**.
  Este plan agrega una **segunda** conexión de `core`, de solo lectura, y la garantía de ADR-001
  pasa a depender de que esa segunda conexión **no** sea la del dueño (CA-5).
- El riesgo que el ADR ya registra **sin mitigación** —*"el rol de solo lectura se configura mal en
  una instalación nueva y la garantía desaparece en silencio"*— ahora tiene **un segundo lugar**
  donde puede pasar. La mitigación de este plan es verificar CA-5 **contra el rol real**, no contra
  un mock.
- **`POSTGRESQL_READ_USER` puede ser el mismo rol que usa la api** —es de solo lectura y no hay
  razón para crear otro—. **Lo único que no puede ser es el usuario dueño.**

#### ADR-005: Modelos compartidos en `@jiku/models`, sin abrir la conexión

**Decisión:** los modelos viven en un paquete que **no abre la conexión**; cada servicio registra
las clases en **su propio** `Sequelize`, con sus credenciales.

**Implementation Rules (verbatim):**
- Los modelos Sequelize **DEBEN** vivir en `@jiku/models`. **NO SE DEBE** definir un modelo dentro
  de `api/` o de `core/`.
- `@jiku/models` **NO DEBE** abrir una conexión ni leer variables de entorno de base de datos.
  Exporta clases; la instancia la crea cada servicio.
- Cada servicio **DEBE** registrar las clases en su propio `Sequelize` con sus credenciales.
- Un cambio de esquema **DEBE** hacerse en dos lugares en el mismo cambio: la migración en
  `api/db-upgrade/migrations/` y el modelo en `@jiku/models`.
- Los hooks que van en el modelo son los que pertenecen **al dato**. Los que dependen del caso de
  uso o del rol **DEBEN** ir en el comando de core o en la api.
- Los nombres en `@jiku/models` **DEBEN** ser los reales de la base. La traducción de vocabulario
  es responsabilidad de core.
- Al agregar un modelo, **DEBE** registrarse en el índice del paquete.

**Cómo aplica acá — es el ADR decisivo del riesgo central.** La tercera regla dice que **cada
servicio** registra las clases en su propio Sequelize, y funciona *"porque son procesos
distintos"*. Con **dos instancias en un proceso**, la segunda que registre `allModels`
**reasigna** las clases:

| Reasignación | Síntoma |
|---|---|
| Los comandos salen por el rol de solo lectura | Falla **ruidosa**: Postgres rechaza la escritura. Se detecta al instante |
| Las consultas salen por el usuario dueño | Falla **silenciosa**: funciona perfecto, y **ADR-001 dejó de valer** sin que nada lo diga |

Por eso `read.ts` se crea **sin `models`** (CA-7) y las consultas usan **SQL explícito**. El
"servicio" de la regla es el proceso, y en un proceso con dos perfiles de acceso solo uno puede
ser el dueño de las clases: **el de comandos, que ya lo es.**

#### ADR-003: La transacción es del despachador, nunca del comando

**Decisión:** el despachador de comandos abre y cierra la transacción; commit si el reply es
`success`, rollback en cualquier otro caso.

**Implementation Rules (verbatim):**
- Un comando **DEBE** recibir la transacción por su contexto y usarla en todas sus operaciones de
  base de datos. **NO DEBE** abrir una transacción propia.
- Un comando **NO DEBE** llamar a `commit()` ni a `rollback()`. Si el código de un comando los
  invoca, está mal escrito.
- Un comando **DEBE** señalar el fallo devolviendo un `Reply` con `status: 'failure'` y su
  `errorCode`. **NO DEBE** lanzar una excepción para señalar un fallo de negocio esperado.
- El despachador **DEBE** hacer commit **solo** si el reply es `success`, y rollback en todos los
  demás casos, incluidas las excepciones inesperadas.
- El despachador **NO DEBE** lanzar nunca: todo error se traduce a un `Reply` de falla.
- Los tests de comandos **DEBEN** entrar por el despachador (helper `dispatch()`), no llamando a
  `execute()` directamente.

**Cómo aplica acá:** es **la razón por la que el despachador de consultas es un objeto distinto y
no una rama del mismo** (RF-9, CA-11). Cuatro de las seis reglas hablan de la transacción y no
tienen contraparte en consultas; **la quinta sí se traslada literal**: `QueryDispatcher` **no
lanza nunca**. Y `bus/dispatcher.ts` **no entra en el diff**: agregarle un `if (esConsulta)`
sería exactamente lo que este ADR desaconseja.

#### ADR-013: Tests contra base de datos real

**Implementation Rules (verbatim):**
- Los tests de `api` y `core` **DEBEN** correr contra PostgreSQL real. **NO SE DEBEN** mockear los
  modelos de Sequelize.
- Los tests de comandos de `core` **DEBEN** entrar por el despachador (`dispatch()`), **NO** por
  `execute()` directamente.
- Un test de escritura de la api **DEBE** verificar las tres capas: comando publicado, traducción de
  la respuesta a HTTP, y que la fila quedó escrita. **NO SE DEBE** asertar solo el status HTTP.
- `reply()` / `failWith()` **DEBEN** usarse solo para cubrir caminos de error. El camino feliz
  **DEBE** ejecutar core de verdad.
- Cada archivo de test **DEBE** poder correr solo: el esquema y el mock de auth se preparan en
  fixtures globales de Mocha.
- `TZ=UTC` **DEBE** estar fijado en la configuración de test de todo servicio.
- La limpieza entre corridas **DEBE** ser `TRUNCATE ... RESTART IDENTITY CASCADE`, para que los ids
  autoincrementales sean predecibles.
- **NO SE DEBE** depender del orden de ejecución entre archivos de test.

**Cómo aplica acá:** CA-5 y CA-6 **solo existen** por esta decisión. Un mock del ORM confirmaría la
expectativa en vez de verificar el permiso; la única forma honesta de probar que *Postgres rechaza
la escritura* es tener el rol de verdad. El ADR también explica **por qué el setup vive en
`setup-env.ts` y no en un `mochaGlobalSetup`**: `src/models/index.ts` construye el Sequelize al
importarse, y `read.ts` va a hacer lo mismo (CA-15).

- **ADR-002:** request/reply sin JetStream. El envelope viaja **en el cuerpo**, también en los
  errores. **Nada de esto cambia**, y vale igual para el servicio de consultas. Ojo con el texto
  del ADR: dice `gestion` y "17 comandos", desfase que **RF-23 corrige por otra vía** — la regla de

- **ADR-012:** monorepo con contexto en la raíz. **No se agrega ningún deployable** (RF-6): los dos

### API Context — el contrato del bus

Fuente: `docs/apis/core.yaml` (AsyncAPI 2.6). **Este plan NO lo modifica**, y está verificado: su
`info.description` ya declara el estado final —dos servicios micro en un proceso y *"the contract
of `jiku-queries` is OUT OF SCOPE of this spec"*—. Lo que sigue es lo que el implementador necesita
a mano.

**Gramática de subjects (no cambia):**

```
{instance}.{user-id}.{svc}.{version}.{método}

dev.323332022539911171.jiku-commands.v1.clients.new      <- escritura (20 endpoints)
dev.323332022539911171.jiku-queries.v1.tasks.list        <- lectura   (6 endpoints, NUEVO)
```

| Segmento | Valor | Variable |
|---|---|---|
| `instance` | `dev` / `prod` | `NATS_INSTANCE` |
| `user-id` | el `sub` del token de quien publica, **crudo** | — |
| `svc` | `jiku-commands` / **`jiku-queries`** | `NATS_COMMAND_SERVICE` / `NATS_QUERY_SERVICE` |
| `version` | `v1` | `NATS_PROTOCOL_VERSION` |
| `método` | `clients.new`, `tasks.list`, … | — |

**Por qué la separación vive en `{svc}` y no anidada** (copiado del paquete, porque es la decisión
que este plan materializa): la suscripción de comandos termina en `>`, y ese `>` se comería también
las consultas si compartieran el token. Dos queue groups sobre subjects solapados entregan el
mensaje a **las dos** suscripciones y llegan **dos respuestas al mismo inbox**; un `request()`
pelado devuelve la primera y **descarta la segunda en silencio**. Con un `{svc}` distinto el
problema no puede pasar, porque **los tokens de subject se comparan enteros**.

**Los 6 endpoints de `jiku-queries` — la tabla del contrato.** Es la fuente para las aserciones de
los tests (copiarla, no recalcularla con `endpointName`/`endpointSubject`: recalcular verifica que
el paquete es consistente consigo mismo, copiar verifica que el servicio expone lo que el contrato
promete):

| Patrón (`registry`) | `endpointName` | `endpointSubject` | Qué devolverá (**fuera de alcance**) |
|---|---|---|---|
| `projects.list` | `projects-list` | `projects.list` | Colección paginada |
| `projects.get` | `projects-get` | `projects.get` | Un recurso |
| `tasks.list` | `tasks-list` | `tasks.list` | Colección paginada |
| `tasks.get` | `tasks-get` | `tasks.get` | Un recurso |
| `comments.list` | `comments-list` | `comments.list` | Colección paginada |
| `comments.get` | `comments-get` | `comments.get` | Un recurso |

- **Subject completo del endpoint:** `dev.*.jiku-queries.v1.{patrón}` (el grupo aporta el prefijo).
- **Grupo micro:** `groupSubject(QUERY_SERVICE)` → `dev.*.jiku-queries.v1` (**sin** el `.>` final:
  micro arma el subject de cada endpoint por su cuenta).
- **Queue group:** `jiku-queries`, en la config del **servicio** (grupo y endpoints lo heredan en
  cascada). Sin esa línea quedaría el default `q` de micro y **nada lo delataría**.
- **Ningún patrón lleva `{param}`**, así que `endpointName` y `endpointSubject` coinciden en forma y
  **no hay `*` en los subjects de consulta**. **Es una decisión de performance, no un olvido:** el
  server matchea con un trie más un **cache de subjects de 1024 entradas**, y el tráfico de lectura
  es el de mayor volumen — un subject nuevo por cada id consultado volvería el cache inútil. **El id
  del recurso viaja en el payload, y el REQ del contrato tiene que respetarlo.**

**Helpers del paquete que este plan usa** (`packages/nats-protocol/src/index.ts`, verificados):

```ts
export const COMMAND_SERVICE = process.env.NATS_COMMAND_SERVICE || 'jiku-commands';
export const QUERY_SERVICE   = process.env.NATS_QUERY_SERVICE   || 'jiku-queries';
export const PROTOCOL_VERSION = process.env.NATS_PROTOCOL_VERSION || 'v1';
export const INSTANCE = process.env.NATS_INSTANCE || 'dev';

export function querySubject(query: string, userId: string): string;   // caller (S-014)
export function groupSubject(service: string): string;                 // `{instance}.*.{svc}.{version}`
export function endpointName(pattern: string): string;                 // `tasks.{id}.edit` -> `tasks-edit`
export function endpointSubject(pattern: string): string;              // `tasks.{id}.edit` -> `tasks.*.edit`
export function methodFromSubject(subject: string): string;            // subject completo -> `tasks.list`
export const commandFromSubject = methodFromSubject;                   // @deprecated, MISMO símbolo
export function callerFromSubject(subject: string): string;            // el user id del caller
```

> **Usá `methodFromSubject`, no `commandFromSubject`.** Son el mismo símbolo, pero el segundo está
> `@deprecated` justamente porque *"con dos servicios en el bus, el quinto segmento es un método
> (comando o consulta), no siempre un comando"*. El despachador de comandos lo sigue usando y
> **no se toca**; el de consultas nace con el nombre correcto.

**El envelope, idéntico para los dos servicios:**

```ts
export interface Reply<T = unknown> {
  status: 'success' | 'failure';
  errorCode?: string;
  errorMessage?: string;
  data?: T;
}
export function success<T>(data?: T): Reply<T>;
export function failure(errorCode: string, errorMessage: string): Reply<never>;
```

```json
{ "status": "success", "data": { "id": 7 } }
{ "status": "failure", "errorCode": "project_not_found", "errorMessage": "Project not found" }
```

**Cómo responde el servicio** (`bus/service.ts`, **sin cambios**): un `success` va por
`msg.respond(...)`; un `failure` va por `msg.respondError(500, reply.errorCode ?? 'error',
<cuerpo>)` — **el cuerpo completo, nunca `Empty`**. Los headers `Nats-Service-Error` /
`Nats-Service-Error-Code` son un **agregado**, y el `500` de ese header es del transporte micro,
**no** el status HTTP (ese lo decide `httpStatusFor` de la api sobre el `errorCode` **del cuerpo**).

**Códigos de error disponibles** (`ErrorCode` de `@jiku/nats-protocol`, 26 miembros; los tres que
importan acá):

| Constante | Valor | HTTP en la api | Cuándo |
|---|---|---|---|
| `ErrorCode.INVALID_FIELDS` | `invalid_fields` | 400 | Cuerpo que no es JSON (lo emite `handle()`) |
| `ErrorCode.INTERNAL_ERROR` | `internal_error` | 500 | Excepción no capturada |
| `ErrorCode.UNKNOWN_COMMAND` | `unknown_command` | 500 | El registry no resuelve el método |

**Contadores por servicio (CA-4).** `nc.services.add()` **no tiene singleton**: cada llamada crea
un servicio con su propio `id`, sus endpoints y **sus contadores**. Dos llamadas sobre la **misma**
conexión dan dos servicios que se anuncian por separado en `$SRV`, con `num_requests`,
`processing_time` y `average_processing_time` propios por endpoint. **CA-4 sale de eso**, no de
código nuevo.

Dos limitaciones ya verificadas contra un bus real en S-012, que valen igual para `jiku-queries` y
que **no hay que "arreglar" en esta story**:

- **`num_errors` queda en 0.** `respondError()` no lo incrementa. Las fallas se miden por logs y por
  `errorCode`. **No armes alertas sobre esa métrica** — y ojo: con seis endpoints que **solo**
  devuelven `failure`, `num_errors: 0` va a ser especialmente contraintuitivo.
- **`processing_time` no mide la latencia del handler.** Micro muestrea sincrónicamente, justo
  después de entregar el mensaje, y el handler retorna enseguida (`void handle(...)`). Se espera
  latencia ~0.

### Flow Context

**Ninguno, y es una decisión de la story, no un olvido.**

Un flujo de `docs/flows/` documenta una interacción cross-service de punta a punta con **field names
exactos** como contrato. `jiku-queries` no tiene todavía ni payload de request ni envelope de
respuesta ni campos por recurso: **RF-10 los deja fuera de alcance**. Un flujo escrito ahora tendría
que **inventar exactamente lo que el REQ declaró no definir**.

El arranque y el apagado del proceso tampoco son flujos: no son interacciones cross-service
disparadas por una acción de usuario, son **ciclo de vida de un servicio**. Su lugar es la
convención `bus-consumer` reescrita (RF-24, por otra vía).

**Los cuatro escenarios de la story están transcriptos abajo, en "El diseño que este plan
implementa", que es donde el implementador los necesita.**

### Integration Points

#### NATS micro (`nats@2.29.3`) — lo que este plan usa, verificado en S-012 contra el código instalado

- **`nc.services.add(config)`** crea un servicio nuevo **en cada llamada**, con su propio `id`,
  endpoints y contadores. **No hay singleton.** Dos llamadas sobre la misma conexión dan dos
  servicios que se anuncian por separado en `$SRV`. **Es lo que hace posible un proceso con dos.**
- **`queue` va en la config del servicio**; el grupo y los endpoints lo heredan en cascada.
- **`service.addGroup(subject)`** acepta un `*` en el medio del prefijo: su validación rechaza
  vacío, espacios y `>` interno, **no `*`**.
- **`group.addEndpoint(name, { subject, handler })`**: el `name` se valida contra `/^[-\w]+$/`
  (ADR-32 de NATS), de ahí que `endpointName` una con guiones.
- **`service.stop()`** deja de aceptar requests nuevas; es idempotente.
- Cada servicio se suscribe además a `$SRV.PING` / `INFO` / `STATS` (y a `.<name>` y
  `.<name>.<id>`), que es lo que lo hace aparecer en `nats micro ls`.
- **Costo del segundo servicio:** 6 suscripciones de endpoint más las de `$SRV`. Despreciable.

#### PostgreSQL — la conexión de solo lectura

- **Driver:** `pg@8.16.3` vía `sequelize@6.37.7`. `dialectOptions` se pasa **tal cual** al cliente
  `pg`, así que `statement_timeout` (en ms) es una opción del driver, no de Sequelize.
- **Una sentencia abortada por `statement_timeout`** llega como error de Postgres con
  `code === '57014'` y mensaje *"canceling statement due to statement timeout"*. En Sequelize el
  error viene envuelto: el código está en `error.original.code` / `error.parent.code`.
- **Un `INSERT`/`UPDATE`/`DELETE` sin permiso** llega con `code === '42501'` y mensaje
  *"permission denied for table X"*. **Ése es el mensaje que prueba CA-5**, y viene de Postgres, no
  del código.
- **Sequelize conecta perezosamente**: construir el `Sequelize` no abre socket. La conexión de
  lectura se abre **en el primer query**, y una credencial mal configurada falla **ahí**. **Es la
  falla ruidosa que la story quiere** — no agregues un `authenticate()` al arranque.
- **El pool es por instancia de Sequelize.** `pool.max` de una no afecta a la otra: eso es CA-9.

#### Zitadel y el bus — sin cambios

- **Sin rol ni service user nuevo** (RF-20): los dos servicios micro **comparten la identidad de
  `core`**, una sola conexión, un solo token con auto-refresh, un solo inbox hasheado.
- **Ningún permiso nuevo.** `deploy/nats/auth-callout/templates/core.yaml` ya enumera
  `{instance}.*.jiku-commands.v1.>` **y** `{instance}.*.jiku-queries.v1.>` más `$SRV.>` (S-011).
  Autorizarlos antes de que el servicio existiera fue inocuo: un permiso sobre un subject sin
  suscriptores no hace nada.
- **`core` sigue sin publicar nada** más que sus respuestas, y eso ahora **vale para los dos
  servicios**.

#### Referencias externas

`docs/references/` **está vacío** en este producto. Las referencias del REQ (ADR-32 y ADR-6 de
NATS) son documentación de una **dependencia ya instalada**, y lo que importa de ellas está
transcripto arriba en "NATS micro".

### El diseño que este plan implementa

#### 1. `core/src/models/read.ts` — la segunda conexión

```ts
import { Sequelize } from 'sequelize-typescript';

/**
 * Conexión de SOLO LECTURA del servicio de consultas.
 *
 * SIN `models` A PROPÓSITO, y es la decisión más importante del módulo: `@jiku/models` exporta
 * clases que se registran en UN Sequelize (ADR-005), y hasta hoy eso funcionaba porque api y
 * core son procesos distintos. Dos instancias en el MISMO proceso se pelean las clases: la
 * segunda que registre `allModels` las REASIGNA, y `Objective.findAll()` empieza a salir por la
 * conexión equivocada. En el sentido malo —consultas por el usuario dueño— rompe ADR-001 SIN UN
 * SOLO SÍNTOMA. Por eso acá no hay `models` y las consultas usan SQL explícito.
 *
 * Se construye AL IMPORTARSE, igual que `models/index.ts`: las variables tienen que estar
 * puestas antes (dotenv en `src/index.ts`, `setup-env.ts` en los tests).
 *
 * NO conecta acá: Sequelize abre el socket en el primer query. Una credencial mal configurada
 * falla ahí, ruidosamente, que es el modo de falla que se quiere.
 */
export const readDb = new Sequelize({
  database: process.env.POSTGRESQL_DB,
  username: process.env.POSTGRESQL_READ_USER,
  password: process.env.POSTGRESQL_READ_PASSWORD,
  port: Number(process.env.POSTGRESQL_PORT) || 5432,
  host: process.env.POSTGRESQL_HOST,
  dialect: 'postgres',
  logging: false,
  // Pool PROPIO: el de lectura no le come conexiones al de escritura.
  pool: { max: Number(process.env.POSTGRESQL_READ_POOL_MAX) || 10 },
  dialectOptions: {
    // ESTRICTAMENTE MENOR que NATS_QUERY_TIMEOUT_MS del caller: la base tiene que cortar antes
    // que el bus, o el caller espera un timeout que no explica nada.
    statement_timeout: Number(process.env.POSTGRESQL_STATEMENT_TIMEOUT_MS) || 8000,
  },
});

export default readDb;
```

- **No lleva `omitNull: false`**: esa opción existe para que un `null` explícito de una edición
  llegue como `NULL`. Una conexión que no escribe no la necesita, y copiarla sugeriría que sí.
- **No lleva reintento de arranque.** Los 5 intentos de `models/index.ts` son para el arranque en
  Docker, donde el contenedor de la base puede no estar listo; la conexión de lectura no se usa en
  el arranque.

**`types.ts`:**

```ts
import { Sequelize } from 'sequelize-typescript';
import { Reply } from '@jiku/nats-protocol';

/**
 * Contexto de una consulta.
 *
 * NO tiene `transaction`, y la ausencia es el contrato: el despachador de consultas no abre
 * ninguna (RF-9). Una consulta que necesite consistencia entre varias lecturas abre una
 * transacción `READ ONLY` explícita DENTRO de sí misma.
 *
 * NO tiene `params`: los patrones de consulta no llevan `{param}` —el id del recurso viaja en el
 * payload, por el cache de subjects del server— así que un `params` acá estaría siempre vacío y
 * sugeriría que se puede agregar un `{id}` al patrón. No se puede.
 */
export interface QueryContext {
  /** Servicio que publicó el mensaje, leído del subject. */
  caller: string;
  /** Conexión de SOLO LECTURA. Se inyecta para que el módulo no importe `models/read`. */
  db: Sequelize;
}

/**
 * Una consulta: lee y devuelve.
 *
 * No hay `validate()` todavía: sin contrato (RF-10) un esquema Joi inventaría exactamente lo que
 * el REQ declaró fuera de alcance. El REQ del contrato lo agrega, y ahí la forma es la misma que
 * en `Command`.
 */
export interface Query<TData = unknown> {
  /** Patrón del método, SIN `{param}`: `projects.list`, `tasks.get`. */
  readonly pattern: string;
  execute(payload: unknown, ctx: QueryContext): Promise<Reply<TData>>;
}
```

**`registry.ts`** — no reusa `CommandRegistry`, y el motivo va en un comentario: el matching por
segmentos de aquél existe para extraer `{param}` de subjects con ids embebidos, y **los patrones de
consulta no tienen params**. Un `resolve()` por `Map` es exacto, más corto y —lo importante— no
sugiere que un patrón de consulta pueda llevar `{id}`.

```ts
export class QueryRegistry {
  private entries = new Map<string, Query>();

  register(query: Query): this;
  registerAll(queries: Query[]): this;
  /** La consulta que atiende `method`, o `null`. Match EXACTO: no hay params que extraer. */
  resolve(method: string): Query | null;
  /** Patrones registrados, en orden de registro. Los usa el spec del servicio micro. */
  patterns(): string[];
}
```

- **`register` de un patrón repetido tiene que fallar ruidosamente** (`throw`), no sobreescribir en
  silencio: es el mismo espíritu que la verificación de duplicados de `registerService`. Con un
  `Map` la sobreescritura silenciosa es el default, así que hay que impedirla a mano.

**`dispatcher.ts`:**

```ts
export class QueryDispatcher {
  constructor(private registry: QueryRegistry, private db: Sequelize) {}

  async dispatch(subject: string, raw: unknown): Promise<Reply> {
    const method = methodFromSubject(subject);
    const query = this.registry.resolve(method);

    if (!query) {
      logger.warn(`[query] consulta desconocida: ${method}`);
      return failure(ErrorCode.UNKNOWN_COMMAND, `Unknown query: ${method}`);
    }

    // SIN TRANSACCIÓN, y la ausencia es deliberada (RF-9): una lectura no necesita atomicidad y
    // una transacción por request tomaría y sostendría un snapshot por cada consulta. Si alguna
    // necesita consistencia entre varias lecturas, abre una READ ONLY explícita adentro.
    try {
      return await query.execute(raw, { caller: callerFromSubject(subject), db: this.db });
    } catch (error: any) {
      // Igual que el despachador de comandos: NUNCA LANZA. `handle()` es la última red, pero el
      // detalle del error se loguea acá, donde se sabe qué consulta falló.
      logger.error(`[query] ${method}: ${error.message}`);
      return failure(ErrorCode.INTERNAL_ERROR, 'Internal error');
    }
  }
}
```

#### 4. Los cuatro escenarios de la story, en orden de ejecución

**Escenario 1 — Arranque (CA-1, CA-2, CA-3, CA-12).**
`src/index.ts` corre `loadConfig()` → `initializeDb()` (la conexión del **dueño**, 5 reintentos) →
`host.start()`. Al importarse, `models/read.ts` construye su Sequelize **sin `models`**. `BusHost`
abre **UNA** conexión con `inboxPrefix(userId)` y registra los servicios **en serie**:
`jiku-commands` con 20 endpoints, después `jiku-queries` con 6, cada uno con su queue group y su
grupo. Cada servicio se suscribe a `$SRV.*` → los **dos** aparecen en `nats micro ls` con ids
distintos.
**Outcome:** un proceso, **una** conexión NATS, **dos** conexiones a Postgres (una perezosa), dos
servicios micro anunciados por separado.
**Errores:** falla el registro de **cualquiera** de los dos → el arranque falla **entero**
(registro en serie + error propagado + `main().catch()` con `process.exit(1)`). `SERVICE_VERSION`
que no es SemVer estricto → micro rechaza el registro (cubierto por S-012).

**Escenario 2 — Una consulta (CA-2, CA-10, CA-11, CA-14).**
Un caller publica `dev.{uid}.jiku-queries.v1.tasks.list`. NATS matchea el grupo de consultas y
**no** el de comandos (tokens `{svc}` distintos, comparados enteros: una sola respuesta, un solo
inbox). El endpoint `tasks-list` entra por el **mismo `handle()`** de los comandos (cuerpo vacío →
`{}`, no-JSON → `invalid_fields`, excepción → `internal_error`), que llama al `QueryDispatcher`:
**sin transacción**, resuelve el patrón y ejecuta. El stub devuelve el `failure` de CA-10, y
`respond()` lo manda **en el cuerpo**.
**Errores:** una consulta que intenta escribir → **Postgres la rechaza por permisos** (CA-5); SQL
que supera `POSTGRESQL_STATEMENT_TIMEOUT_MS` → Postgres la aborta y el servicio contesta **antes**
del timeout del caller (CA-8).
**Nota:** un `jiku-queries` sin contrato **no puede degradar nada**, porque no devuelve páginas. El
techo de `limit` y el presupuesto de bytes son del REQ del contrato.

**Escenario 3 — Un alta después de que la lectura usó su conexión (CA-6, CA-7).**
`models/index.ts` registró `allModels` en la conexión del **dueño**; `read.ts` abrió la suya **sin
registrar nada**. Llega `requirements.new` a su endpoint, `bus/dispatcher.ts` (**sin cambios**)
abre transacción, `Requirement.create(..., { transaction })` **sale por la conexión del usuario
dueño** porque nadie reasignó la clase, commit, `success({ id })`.
**Es la única verificación de que los modelos no se reasignaron**, y hay que escribirla aunque hoy
parezca trivial: **no protege contra un bug de hoy, protege contra el refactor de mañana que
"unifica las dos conexiones"**.

**Escenario 4 — Apagado (CA-13).**
`SIGTERM` → `host.stop()`: corta el auto-refresh del token → `Promise.all(services.map(s =>
s.stop()))` (**los DOS**, dejan de aceptar requests nuevas) → `connection.drain()` →
`connection.close()`. **El orden es la garantía**; al revés, una request nueva podría entrar durante
el drain. **No agregues un `process.exit()` que se saltee el drain.**

### Decisiones que este plan toma (y por qué)

Son cinco puntos donde la story deja la elección abierta o el diseño admite dos caminos. **Están
decididos acá para que no se improvisen en implementación.**

**1. El código del `failure` de los seis stubs: `unknown_command`.**
La story dice que *"el código concreto de ese `failure` es decisión de esta story"*. Un código
nuevo (`not_implemented`) obligaría a tocar `packages/nats-protocol`, `docs/apis/core.yaml` **y** el
mapa a HTTP de la api —los tres marcados `Ninguno` en la story, y la convención `error-handling`
exige los tres o el usuario ve un 500 genérico—. `unknown_command` ya existe, ya mapea a **500** en
`api/lib/utils/bus/protocol.ts`, y significa exactamente *"no hay implementación para este
método"*. El mensaje (`La consulta X todavía no tiene contrato definido`) lo distingue del otro
emisor del mismo código. **Hoy no hay ningún caller que lo reciba** (`query()` es de S-014).

**2. La asimetría de pools: se documenta, no se declara el de escritura.**
La story pide decidirlo *"a conciencia: o se declara también el pool de escritura, o se documenta
por qué el de lectura necesita más"*. **Se documenta**, por dos razones. Una, dura: la story declara
`models/index.ts` **intacto**, y declarar su pool sería tocarlo. Dos, de fondo: la forma asimétrica
es la correcta, no un accidente — una lectura toma una conexión por **una sentencia** y la
devuelve, una escritura la sostiene por **toda la transacción**, y el tráfico de lectura es el de
mayor volumen. Techo de 10 para lecturas y 5 (implícito) para escrituras es la proporción que se
quiere. **Lo que no puede quedar es implícito**, así que va a `core/README.md` (Tarea 6) con el
total por réplica y el recordatorio de verificar `max_connections`.

> **Hallazgo relacionado, para no perderlo:** `core/.env.test` declara `POSTGRESQL_POOL_MAX=5`,
> `POSTGRESQL_POOL_MIN=0` y `POSTGRESQL_POOL_IDLE=10000`, y **ningún código del monorepo las lee**
> (`grep -rn 'POSTGRESQL_POOL' --include='*.ts' core api packages` no devuelve nada). Son variables
> muertas heredadas. **No las borres en esta story** —no es su alcance— pero tampoco te apoyes en
> ellas creyendo que configuran el pool de escritura.

**3. `QueryDispatcher` sí captura sus excepciones.**
CA-14 dice que las excepciones se contestan *"por el mismo `handle()`"*, y es cierto: `handle()` es
la última red y ya lo verifica S-012 (TS-3, TS-4). Pero la convención `error-handling` es explícita
—*"el despachador nunca lanza"*— y ADR-003 la repite como regla. Un `queries/dispatcher.ts` sin
`try/catch` al lado de un `bus/dispatcher.ts` con uno es una asimetría que el próximo lector va a
leer como olvido. Cuestan cuatro líneas y agregan lo único que `handle()` no puede dar: **el log
dice qué consulta falló**, no solo qué subject. **La aserción de CA-14 vale igual en los dos
diseños** (el cuerpo es el mismo `internal_error`), así que la decisión no cambia ningún test:
cambia dónde queda el diagnóstico.

**4. La conexión de lectura se inyecta, no se importa dentro de `queries/`.**
`QueryDispatcher` la recibe por constructor y la pasa en `QueryContext.db`. Tres consecuencias, las
tres buenas: el módulo de consultas se testea contra una conexión de test (con
`statement_timeout` chico, o con pool de 1) sin recargar módulos; el import de `read.ts` vive en
`src/index.ts`, **después de `dotenv.config()`**, que es lo que CA-15 protege; y ningún archivo de
`queries/` importa `models/`, lo que hace que el grep de CA-7 sea una verificación real y no un
acuerdo de caballeros.

**5. El rol de test: las variables las pone `setup-env.ts`, el rol y los `GRANT` los hace
`global-setup.ts`.**
CA-15 pide las dos cosas. La parte que **no puede** ir a otro lado son las variables: `read.ts` lee
`process.env` **al importarse**, así que tienen que estar antes de que un test importe `src/`, y
`setup-env.ts` es el único punto que corre antes. El rol es distinto: **`GRANT SELECT ON ALL TABLES`
necesita que las tablas existan**, y las crea `sequelize.sync()` dentro de `global-setup.ts`. Además
`setup-env.ts` es **sincrónico por construcción** (`execFileSync`), mientras `global-setup.ts` es
`async` y ya tiene la conexión del dueño abierta: ahí el rol son seis líneas de `sequelize.query()`
sin ninguna gimnasia. **El resultado cumple CA-15 en lo que importa**: cuando corre el primer test,
el rol existe y las variables están puestas desde antes del primer import de `src/`. **No lo
"arregles" moviendo el rol a `setup-env.ts`**: los `GRANT` fallarían porque las tablas todavía no
están.

### Deuda heredada que hay que conocer antes de empezar

**1. Las requests en vuelo se pierden en el apagado — preexistente, verificada, y NO es una
regresión de esta story.** La verificación de cierre de S-012 (su TS-41) encontró que con 30
requests publicadas y un `SIGTERM` en el medio, **29 expiraron por timeout**: el handler corre con
`void handle(...)` —sin `await`, que es lo que preserva el no-bloqueo entre mensajes— así que
`service.stop()` drena las suscripciones pero **nadie espera las promesas de `handle()` en curso**.
Se verificó contra el `consumer.ts` anterior, que perdía **30 de 30**. **Qué significa para CA-13:**
lo que esta story agrega y puede verificar es que **los dos** servicios se paran **antes** del
drain, en ese orden (automatizado). La parte de *"las que ya estaban en curso se responden"* es esa
deuda preexistente, y cerrarla requiere rastrear las promesas en vuelo y esperarlas entre
`service.stop()` y `connection.drain()`: **funcionalidad nueva, otro REQ**. **No la arregles acá**:
esta story ya es la única del REQ con riesgo nuevo.

**2. `core/tests/commands/storage-signer.test.ts` está SIN TRACKEAR y tiene 2 fallas
preexistentes** (checksum CRC32 del SDK de AWS en URLs prefirmadas, workstream de REQ-001). Es
ajeno a esta story. **Cuando corras la suite para CA-16, esas dos fallas son el punto de partida,
no una regresión tuya.** Anotá el número exacto de tests en verde **antes** de empezar.

**3. `docs/architectures/core/overview.md` y la convención `bus-consumer` describen el
`consumer.ts` que ya no existe.** RF-23/RF-24 los corrigen por `/product-change-technical-definition`,
**no por esta story**. Leelos por sus reglas, no por su código.

### Task 1: El entorno de tests aprende el rol de solo lectura

**Status:** Completed

#### Description

Preparar el entorno de test para que exista **un rol de PostgreSQL que solo puede leer**, y para que
las variables de la conexión de lectura estén puestas **antes** de que cualquier test importe
`src/`. Sin esto, CA-5 (Postgres rechaza la escritura) no se puede verificar: contra el usuario
`test` —que es el dueño de la base efímera— cualquier `INSERT` funciona, y el test que "prueba" la
garantía pasaría sin probar nada.

Son tres archivos y ninguno tiene lógica de negocio, pero **el orden entre ellos es todo el
contenido de la tarea**:

- **`core/.env.test`** declara las cuatro variables (son las que usa CI, donde la base la provee el
  pipeline).
- **`core/tests/setup-env.ts`** las pone en `process.env` **antes que nada** —es el único punto que
  corre antes de que Mocha cargue los tests— y en local usa el host y el puerto del contenedor
  efímero, igual que ya hace con las de escritura.
- **`core/tests/global-setup.ts`** crea el rol y le da `SELECT`, **después** de que
  `sequelize.sync()` creó las tablas. Los `GRANT` no pueden ir antes: no habría a qué dárselos.

Ese último punto es la parte que se presta a "arreglarse" mal. Está decidido y argumentado en
"Decisiones que este plan toma" (punto 5): **no muevas la creación del rol a `setup-env.ts`**.

#### Acceptance Criteria

1. `core/.env.test` declara `POSTGRESQL_READ_USER`, `POSTGRESQL_READ_PASSWORD`,
   `POSTGRESQL_READ_POOL_MAX` y `POSTGRESQL_STATEMENT_TIMEOUT_MS`, con un comentario que diga que
   el rol lo crea `global-setup.ts` y **por qué** no puede ser el usuario dueño.
2. El valor de `POSTGRESQL_READ_USER` **no** es el de `POSTGRESQL_USER` (`test`). Nombre sugerido:
   `jiku_test_readonly`.
3. `POSTGRESQL_STATEMENT_TIMEOUT_MS` de `.env.test` es un valor **holgado** (8000, el mismo del
   despliegue): los tests que necesitan uno chico recargan el módulo. Un valor chico global haría
   fallar tests de comandos lentos por una razón que no tiene nada que ver.
4. `core/tests/setup-env.ts` exporta las cuatro variables en `process.env` en **las dos ramas**
   (local y `CI=true`), sin pisar un valor que ya venga del entorno.
5. `core/tests/global-setup.ts` crea el rol **de forma idempotente** (sobrevive a `KEEP_DB=true`) y
   le concede `CONNECT` a la base, `USAGE` en el esquema `public` y `SELECT ON ALL TABLES`.
   **No** le concede `INSERT`, `UPDATE`, `DELETE` ni pertenencia a ningún rol.
6. La creación del rol corre **después** de `initializeDb()` (que hace el `sync()`).
7. TS-32 y TS-33 pasan.
8. La suite existente sigue en verde: `npm test -w @jiku/core` sin fallas nuevas.

En `core/tests/global-setup.ts`, dentro de `mochaGlobalSetup()`, **después** del `await
initializeDb()` y del `TRUNCATE`:

```ts
  // El rol de SOLO LECTURA de las consultas. Va acá y no en `setup-env.ts` porque
  // `GRANT SELECT ON ALL TABLES` necesita que las tablas EXISTAN, y las crea el `sync()` de
  // arriba. Idempotente: con KEEP_DB=true el contenedor sobrevive entre corridas.
  const readUser = process.env.POSTGRESQL_READ_USER as string;
  const readPassword = process.env.POSTGRESQL_READ_PASSWORD as string;
  const database = process.env.POSTGRESQL_DB as string;

  await sequelize.query(`
    DO $$ BEGIN
      IF NOT EXISTS (SELECT FROM pg_roles WHERE rolname = '${readUser}') THEN
        CREATE ROLE "${readUser}" LOGIN PASSWORD '${readPassword}';
      END IF;
    END $$;
  `);
  // SELECT y nada más. Un GRANT de más acá convierte CA-5 en un test que no prueba nada.
  await sequelize.query(`GRANT CONNECT ON DATABASE "${database}" TO "${readUser}"`);
  await sequelize.query(`GRANT USAGE ON SCHEMA public TO "${readUser}"`);
  await sequelize.query(`GRANT SELECT ON ALL TABLES IN SCHEMA public TO "${readUser}"`);
```

- **El nombre de la base va entre comillas dobles**: es `gestionTest`, con mayúscula, y sin
  comillas Postgres lo pasa a minúsculas y el `GRANT` falla con *"database gestiontest does not
  exist"*.
- **La interpolación es aceptable acá y solo acá**: los valores vienen de `.env.test`, no de
  entrada de usuario, y `CREATE ROLE` no acepta parámetros. En el código de `src/` la regla es la
  opuesta (listas blancas para nombres, parámetros para valores).
- **No hace falta `ALTER DEFAULT PRIVILEGES`**: el `sync()` ya creó todas las tablas y no se crean
  más durante la corrida.
- En CI el usuario `test` es superusuario del contenedor de servicio, así que puede crear roles.
  **Si algún día el pipeline usa un usuario sin ese permiso**, el síntoma es un `permission denied
  to create role` en `global-setup`, no un test rojo confuso.

**Dependencies:**
- Ninguna nueva. `sequelize` ya se importa en `global-setup.ts`.

 * cambiarlas después. Devuelve una conexión NUEVA — hay que cerrarla en el test, o el pool queda

function reloadRead(overrides: Record<string, string | undefined>): Sequelize {
  const saved: Record<string, string | undefined> = {};
  for (const [key, value] of Object.entries(overrides)) {
    saved[key] = process.env[key];
    if (value === undefined) delete process.env[key];
    else process.env[key] = value;
  }

  delete require.cache[modulePath];
  const { readDb } = require('../../src/models/read') as typeof import('../../src/models/read');

  for (const [key, value] of Object.entries(saved)) {
    if (value === undefined) delete process.env[key];
    else process.env[key] = value;

      `[core] no pudo arrancar: 'latest' is not a semver value` (con el stack en
      `registerService` → `ServicesFactory.add` → `parseSemVer`) y el proceso muere. **En ningún
      momento apareció un solo servicio en `nats micro ls`** (`no service instances found`): falla en
      el **primer** spec, así que ninguno de los dos se registra. **CA-12 confirmada contra el bus**

### Hallazgos nuevos

1. **Las consultas sobreviven al apagado y los comandos no, y el motivo es transitorio.** En TS-40
   las 15 consultas contestaron y los 15 comandos se perdieron. No es que el apagado trate distinto
   a los dos servicios: es que el stub de consulta resuelve **sincrónicamente** y el comando hace
   E/S a la base. **Es una lectura que va a envejecer mal**: quien vea estas notas después del REQ
   del contrato podría concluir que las consultas son inmunes al apagado, y no lo son. Anotado acá
   para que ese REQ lo revise.
2. **`BusHost.stop()` no loguea nada por servicio**, y eso deja TS-40 sin forma de verificarse por
   observación externa (ver arriba). No es un bug —el orden está implementado y testeado—, pero es
   la razón por la que un escenario de este plan queda sin marcar. Un `logger.info` por servicio
   parado costaría una línea y haría auditable el apagado en producción.
3. **El CLI `nats micro ls` elide la versión repetida en la tabla** (TS-34): la segunda fila aparece
   con `Version` en blanco. Con dos servicios de la misma versión en el mismo proceso, eso se lee
   como "el segundo no declara versión", que es falso. Vale saberlo antes de diagnosticar nada.
