## Referencia de la Story

Cerrar el barrel de `shared/components/ui/` con los 21 componentes normativos del Design System
`web` v2.4.0, aportando los seis de feedback y contenido: `EmptyState`, `Dropzone`, `Accordion`,
`Tooltip`, `ConfirmDialog`, `ToggleGroup`.

**Dependencias:** S-053 (Completed) y S-054 (Completed). Ambas satisfechas.

### El estado real del código — esto no es "crear seis componentes"

El relevamiento del árbol muestra que **tres de los seis ya existen** en
`web/src/shared/components/ui/`, escritos antes del Design System:

| Componente | Existe hoy | Naturaleza del trabajo |
|---|---|---|
| `EmptyState` | **No** | Crear desde cero |
| `Dropzone` | **No** | Crear desde cero |
| `Accordion` | **No** | Crear desde cero |
| `Tooltip` | **Sí** (8 archivos consumidores) | **Migrar** — le falta foco de teclado, `role="tooltip"`, `Esc`, `placement`, `delay`, y usa el gris `#625F5F` fuera de paleta |
| `ConfirmDialog` | **Sí** (2 consumidores + Button) | **Migrar** — confirma con botón primario (el spec exige `secondary-dismiss` en **ambas** acciones), y su SCSS usa tokens del sistema viejo |
| `ToggleGroup` | **Sí** (3 consumidores) | **Migrar** — usa `aria-pressed` sobre botones sueltos (el spec exige `role="radiogroup"`), sin las 4 variants ni `label` |

**Consecuencia para la implementación:** los tres que existen tienen consumidores en producción.
Cambiar su API es un cambio con onda expansiva, y las tareas de abajo lo tratan explícitamente
(cada migración incluye la actualización de sus consumidores). Los tres nuevos no tienen ese
problema y son puramente aditivos.

**Un matiz sobre CA-1:** la story afirma que "hoy existen ~10" de los 21. El barrel real ya exporta
31 nombres, de los cuales los normativos del DS están casi todos presentes tras S-053 y S-054. Lo
que esta story cierra son los seis últimos — tres creándolos y tres alineándolos al spec.

### Convención `styling` (custom — reemplaza la del catálogo)

Sass + CSS Modules + custom properties. **No hay Tailwind, no hay `clsx`, no hay `cva`.**

- Un módulo `.scss` por componente, junto al `.tsx`. Nombre del módulo = nombre del componente.
- **Clases en `camelCase`**, no `kebab-case`: CSS Modules las expone como propiedades de objeto y
  `styles.buttonContainer` es válido mientras `styles.button-container` no.
- El módulo empieza con `@use '@/styles' as *;` cuando necesita mixins (o `@use '@/styles/mixins'
  as *;` como hace `ConfirmDialog` hoy). Sin eso los `@include` no resuelven.
- **Clases condicionales con `cn()`**, nunca template strings:

  ```ts
  // src/shared/utils/cn.ts
  type ClassValue = string | undefined | null | false | Record<string, boolean>;
  export const cn = (...classes: ClassValue[]): string => /* ... */;
  ```

  ```tsx
  className={cn(styles.option, { [styles.active]: value === option.key })}
  ```

  El patrón `` `${styles.a} ${cond && styles.b}` `` escribe el string `"false"` en el `class`
  cuando la condición falla. Es un bug latente que ya existe en tres archivos, **no el patrón**.
- **Usar el token, nunca el hex literal.**
- **No `@media` cruda: usar los mixins.** (Irrelevante para esta story: viewport único.)

Mixins disponibles en `_mixins.scss` (los relevantes acá): `flex-center`, `flex-between`,
`flex-column`, `flex-column-center`, `truncate`, `visually-hidden`, `sr-only`, `button-reset`,
`focus-ring`, `card-base`, `no-select`.

> **Cuidado con `focus-ring`:** el mixin `@include focus-ring` de `_mixins.scss:347` es del sistema
> **anterior** (usa `--color-highlighted`, violeta). Los barridos transversales de S-054 lo prohíben
> explícitamente en componentes nuevos. El foco del DS se aplica como
> `box-shadow: var(--focus-ring)` sobre `:focus-visible`, con `outline: none` en el mismo selector.

### Convención `testing-unit` (custom — reemplaza la del catálogo)

- **Tests junto al código**, como `{Nombre}.test.tsx`. No hay carpeta `__tests__/`.
- **`TZ: 'UTC'` no se toca** en `vitest.config.mts`.
- **Nombres de test en español**, describiendo comportamiento observable, no implementación.
- **`getByRole` con nombre accesible** antes que clase o `data-testid`.
- **`userEvent` antes que `fireEvent`.**
- **`queryBy*` para aserciones de ausencia**; `getBy*` tira si no encuentra.
- **No mockear `fetch` ni `apiClient`.** Se mockea la capa de hooks o de servicios.
- Los polyfills van en `tests/setup.ts` con guarda de existencia, no en el archivo de test.

### Accesibilidad (guidelines, transversal — WCAG 2.2 AA)

- Texto body (≥16pt) contraste ≥4.5:1; texto grande ≥3:1; componentes interactivos ≥3:1.
- **NO comunicar estado solo con color.**
- Todo elemento interactivo accesible por teclado; foco visible con contraste ≥3:1; orden de tab

- Cada componente declara su rol ARIA correcto. Iconos decorativos `aria-hidden="true"`; iconos

- Respetar `prefers-reduced-motion: reduce`.
- Targets táctiles mínimo 44×44 px; spacing entre targets ≥8 px.

### Spec: `EmptyState` v1.0.0 (normativo)

**Propósito.** Comunica que una consulta terminó y **no hay datos**, sin que el usuario dude de si
algo falló.

**Cuándo NO usar:** consulta en curso → `Loader`. Error de sistema → mensaje de error. *«Estamos
buscando» no es «no hay nada», y confundirlos hace que el usuario espere datos que no van a llegar.*

**Anatomía.** (1) Container — superficie de apoyo en niebla, radio 14 px. (2) Mensaje —
`text.body-default` en `text.secondary`. (3) Acción opcional — botón primario, solo si hay algo que
crear. **Sin ilustración**: la personalidad de marca es sobria y sin adorno.

**Variants:**

| Variant | Propósito | Ejemplo del manual |
|---|---|---|
| `list` | Listado o grilla sin elementos | «No hay etapas activas» |
| `filtered` | Filtro sin resultados | «No se encontraron requisitos» |
| `scoped` | Sin datos para un recorte temporal | «No hay cargas para este día» |

> La diferencia importa: `list` invita a crear el primer elemento; `filtered` invita a **cambiar el
> filtro**, no a crear. Ofrecer «Nuevo requisito» cuando el usuario acaba de filtrar es una respuesta
> a una pregunta que no hizo.

**Sizes:** sin sizes. Ancho del contenedor, padding vertical `space.8` (32 px).
**States:** estado único.

**API:**

| Prop | Tipo | Default | Descripción |
|---|---|---|---|
| `variant` | `"list" \| "filtered" \| "scoped"` | `"list"` | Tipo de vacío |
| `message` | `string` | — | Texto visible, requerido |
| `action` | Button props | — | Acción de alta, **solo en `list`** |

**Accesibilidad:**
- **DEBE** vivir en una región con `aria-live="polite"` cuando aparece como resultado de un filtro.
- **NO DEBE** usar `role="alert"`: la ausencia de datos no es un error.
- El mensaje **DEBE** ser texto real, no una imagen con texto.
- Si hay acción, es un botón con su foco y su label propios.

**Microcopy** — negativa neutra, en presente, sin disculpas ni exclamaciones:
- ✓ «No hay etapas activas» · ✓ «No se encontraron requisitos» · ✓ «No hay cargas para este día»
- ✗ «¡Ups! No encontramos nada» — el tono de marca es sereno
- ✗ «Error: sin resultados» — no es un error
- ✗ «Todavía no cargaste nada» — culpa al usuario

**Tokens:** radio 14 px (`radius.surface`); fondo `bg.surface.sunken`; padding `space.8` vertical /
`space.4` horizontal; gap mensaje–acción `space.4`; texto centrado; `text.body-default` en
`text.secondary`.

**Don't:** no usar un loader para decir que no hay datos · no agregar ilustración ni emoji · no
ofrecer «crear» cuando el usuario está filtrando · no dejar el área en blanco sin mensaje.

### Spec: `Dropzone` v1.0.0 (normativo)

**Propósito.** Permite adjuntar archivos, por arrastre o por selección.

**Anatomía.** (1) Container — radio 14 px, borde claro **punteado**, fondo niebla. (2) Icono
`upload`, 24 px. (3) Instrucción — «Arrastrá archivos aquí o hacé click para seleccionar».
(4) Restricción — «Máximo 10 MB por archivo. No se permiten ejecutables ni scripts.»

> **La restricción va dentro del control, siempre visible.** No en un tooltip ni en un mensaje de
> error posterior: el usuario tiene que saber el límite **antes** de elegir un archivo de 40 MB.

**Variants:** una sola. **Sizes:** sin sizes; ancho del panel contenedor, alto mínimo suficiente
para las dos líneas de texto más el icono.

**States:**

| State | Descripción | Tokens |
|---|---|---|
| `default` | En reposo | `dropzone.border` punteado, `dropzone.bg` |
| `hover` | Puntero encima | `dropzone.hover.border` → verde agua |
| `focus` | Foco por teclado | `focus.ring` |
| `dragover` | Archivo arrastrado encima | Borde verde agua + fondo `bg.active.subtle` (8 %) |
| `uploading` | Subida en curso | `Loader` `inline` + «Subiendo archivo…» |
| `error` | Archivo rechazado | Borde y mensaje en `state.urgent` |

**API:**

| Prop | Tipo | Default | Descripción |
|---|---|---|---|
| `accept` | `string` | — | Tipos admitidos |
| `maxSize` | `number` | `10485760` | Límite por archivo, en bytes |
| `multiple` | `boolean` | `true` | Varios archivos a la vez |
| `onFiles` | `(files) => void` | — | Callback de selección |
| `error` | `string` | — | Mensaje de rechazo |

**Accesibilidad:**
- **El arrastre NUNCA es el único mecanismo.** Toda la zona **DEBE** ser accionable por click y por
  teclado, con un `<input type="file">` real detrás. Un dropzone solo-arrastre excluye a quien
  navega con teclado o usa un lector de pantalla.
- **DEBE** exponer el `<label>` asociado al input, con la instrucción como nombre accesible.
- La restricción **DEBE** estar asociada con `aria-describedby`.
- **`dragover` DEBE** tener un cambio visible que no sea solo color (el borde pasa de punteado a
  sólido).
- El rechazo **DEBE** anunciarse en una región `aria-live` y decir **por qué** («supera 10 MB»,
  «tipo no permitido»), no solo que falló.
- **Teclado:** `Enter` / `Space` abren el selector de archivos.

**Microcopy:** instrucción con las dos vías; restricción concreta y completa; error específico («El
archivo supera 10 MB», no «Archivo inválido»); voseo; estado `uploading`: «Subiendo archivo…».

**Tokens:** radio 14 px; borde 1 px punteado `#DFE1E7` (vía `--dropzone-border`), verde agua en
`dragover`; padding `space.8` vertical; gap icono–texto `space.2`; gap instrucción–restricción
`space.1`. Familias: `dropzone.border`, `dropzone.bg`, `dropzone.hover.border`, `focus.ring`,
`bg.active.subtle`, `state.urgent`.

**Don't:** no confiar solo en el arrastre · no esconder la restricción en un tooltip · no usar verde
agua pleno como fondo del `dragover` (es el tinte al 8 %) · no aceptar el archivo y fallar después
en el servidor sin explicar.

### Spec: `Accordion` v1.0.0 (normativo)

**Propósito.** Agrupa el contenido de una etapa en una sección plegable, mostrando de un vistazo si
está completa.

**Cuándo NO usar:** contenido que hay que ver siempre → `Card` `panel`. Recorrido de estados de un
requisito → `Stepper`.

**Anatomía.** (1) Container — radio 14 px, borde claro. (2) Marca de completitud — `!` (pendiente) o
`✓` (completo), a la izquierda. (3) Título — `text.card-title` (16/700). (4) Chevron `›` a la
derecha, rota al abrir. (5) Contenido — visible al expandir.

**Variant:** una sola. Lo que cambia es la marca:

| Marca | Significado | Token |
|---|---|---|
| `!` | Etapa **pendiente** — falta información | `accordion.pending.mark` → ámbar `#FEA82F` |
| `✓` | Etapa **completa** | `accordion.done.mark` → `#1B998B` |

> La marca usa colores de sistema porque **informa estado**, y distingue **por glifo además de por
> color** (`!` vs `✓`), no solo por el matiz.

**States:**

| State | Descripción | Tokens |
|---|---|---|
| `collapsed` | Plegado | Chevron `›` a la derecha |
| `expanded` | Desplegado | Chevron rotado, contenido visible |
| `hover` | Cabecera bajo el puntero | `bg.surface.sunken` |
| `focus` | Foco por teclado | `focus.ring` |

La transición usa **`motion.slow` (300 ms)** — es el caso de mayor recorrido del sistema.

**API:**

| Prop | Tipo | Default | Descripción |
|---|---|---|---|
| `title` | `string` | — | Nombre de la etapa |
| `status` | `"pending" \| "done"` | `"pending"` | Marca de completitud |
| `defaultExpanded` | `boolean` | `false` | Estado inicial |
| `onToggle` | `(expanded) => void` | — | Callback |

**Slots:** `children` (contenido del panel).

**Accesibilidad:**
- La cabecera **DEBE** ser un `<button>` dentro de un encabezado del nivel que corresponda, con
  `aria-expanded` y `aria-controls` apuntando al panel.
- El panel **DEBE** llevar `role="region"` con `aria-labelledby` hacia su cabecera.
- La marca de completitud **DEBE** anunciarse en texto: «Alcance, pendiente» / «Cierre estimado,
  completo». **El `!` y el `✓` son visuales.**
- **Teclado:** `Enter` / `Space` alternan; `Tab` recorre las cabeceras.
- **`prefers-reduced-motion`:** la apertura es instantánea.
- El contenido plegado **DEBE** estar fuera del orden de foco (`hidden`), no solo con altura 0.

**Microcopy:** el nombre de la etapa con el término de dominio. **Sin indicar en el título que está
pendiente: eso lo dice la marca.** Ejemplos: «Alcance», «Cierre estimado».

**Tokens:** radio 14 px; borde 1 px `#DFE1E7`; padding de cabecera `space.4`; gap marca–título
`space.2`; gap entre acordeones `space.2`. Familias: `accordion.pending.mark`,
`accordion.done.mark`, `bg.surface.sunken`, `focus.ring`, `motion.slow`, `text.card-title`.

**Don't:** no marcar la completitud solo con color · no anidar acordeones · no plegar contenido que
el usuario necesita ver siempre · no abrir todos los paneles a la vez por defecto si son muchos.

### Spec: `Tooltip` v1.0.0 (normativo en presentación)

**Propósito.** Muestra información breve y complementaria al pasar el puntero o al recibir foco.

**Cuándo NO usar:** información necesaria para completar la tarea → visible en la pantalla. *Un
tooltip es complementario por definición: lo que solo aparece al pasar el puntero no existe para
quien usa un teclado o una pantalla táctil.* Restricciones de un campo → dentro del control, como en
`Dropzone`. Mensajes de error → en el campo, con `aria-describedby`.

**Anatomía.** (1) Container — fondo azul oscuro, radio 8 px. (2) Texto — `text.field-label` (13/400)
en niebla. (3) Puntero opcional hacia el elemento que lo dispara.

**Variants:** una sola. **Sizes:** sin sizes; ancho máximo recomendado **240 px**, para que el texto
no forme una línea larga.

**States:** `hidden` (en reposo) · `visible` (por hover o foco). Aparece con **`motion.fast`
(150 ms)** y un retardo breve, para no dispararse al pasar de largo.

**API:**

| Prop | Tipo | Default | Descripción |
|---|---|---|---|
| `content` | `string` | — | Texto, requerido |
| `placement` | `"top" \| "bottom" \| "left" \| "right"` | `"top"` | Posición preferida |
| `delay` | `number` | `300` | Retardo de aparición, en ms |

**Slots:** `children` (el elemento disparador).

**Accesibilidad:**
- **DEBE** aparecer también con **foco de teclado**, no solo con hover.
- El disparador **DEBE** referenciarlo con `aria-describedby`; el tooltip lleva `role="tooltip"`.
- **DEBE** poder cerrarse con `Esc` sin mover el foco.
- **NO DEBE** contener controles interactivos: si hace falta un enlace o un botón adentro, es un
  popover, no un tooltip.
- **NO DEBE** desaparecer mientras el puntero se mueve hacia él, ni antes de que se pueda leer.
- **Contraste:** niebla sobre azul oscuro **14.6:1**.
- **En pantallas táctiles no hay hover:** la información **DEBE** estar disponible por otra vía.

**Microcopy:** una frase corta, sin punto final. Aclara, no repite: si el label ya dice «Guardar», el
tooltip no dice «Guardar». Sentence case, voseo cuando hay imperativo.

**Tokens:** radio 8 px (`radius.action`); fondo `tooltip.bg` → azul oscuro `#0B1934`; texto
`tooltip.text` → niebla `#F6F6F9`; padding `space.1` vertical / `space.2` horizontal; separación del
elemento `space.1`; **z-index `z.tooltip`, el nivel más alto del sistema**; tipografía
`text.field-label`; motion `motion.fast`.

**Migración declarada por el spec** — el componente actual tiene 10 usos:

| Hoy | Pasa a |
|---|---|
| Fondo `#625F5F` (gris fuera de paleta) | **Azul oscuro `#0B1934`** |
| Sin foco de teclado verificado | Hover **y** foco, con `Esc` para cerrar |

**Don't:** no poner información necesaria solo en un tooltip · no poner controles adentro · no usar
para textos largos (eso es un panel) · no usar color de sistema como fondo.

### Spec: `ConfirmDialog` v1.1.0 (normativo)

**Propósito.** Pide confirmación explícita antes de una acción irreversible.

**Cuándo NO usar:** acciones reversibles (se ejecutan y se ofrece deshacer) · avance de estado de un
requisito → `Stepper` / `Badge` editable.

**Anatomía.** (1) Overlay que cubre la vista y atenúa el fondo. (2) Container — superficie blanca,
radio 14 px, `elevation.raised`. (3) Título — `text.card-title` (16/700). (4) Cuerpo —
`text.body-default`, dice **qué** se va a borrar y que no se puede deshacer. (5) Acciones —
confirmar y cancelar, **ambas como secundario de borde claro**.

**Variants:** una sola. **No hay variant destructiva:** la diferencia entre confirmar un borrado y
confirmar cualquier otra cosa **la hace el texto**, no el color.

**Presentación de la acción destructiva — decisión del 2026-09-02 (la que exige CA-3):**

| Elemento | Tratamiento |
|---|---|
| **Confirmar** («Eliminar») | Button `secondary-dismiss` — **borde claro** |
| **Cancelar** | Button `secondary-dismiss` — **borde claro** |
| **La advertencia** | **El texto**: título con el verbo, cuerpo con la entidad y la irreversibilidad |

**Dos razones, y la segunda es la que decide:**
1. **Coherencia de paleta.** No se introduce un segundo significado para el rojo, que en este
   sistema quiere decir «vencido».
2. **Ningún botón compite por el clic.** El verde agua pleno atrae la mirada y el clic; en un
   borrado eso es exactamente lo que **no** se quiere. Con las dos acciones al mismo peso visual,
   **el usuario tiene que leer** — y lo que lee nombra qué se borra y que no hay vuelta atrás.

> **El corolario:** si el texto no advierte, nada advierte. Por eso el microcopy de este componente
> no es una recomendación de estilo sino **parte del mecanismo de seguridad**.

**Sizes:** ancho máximo recomendado **480 px**. Alto según contenido.

**States:** `open` (visible, foco atrapado dentro) · `closed` (no renderizado) · `pending`
(confirmación en curso — el botón de confirmar en `loading`).

**API:**

| Prop | Tipo | Default | Descripción |
|---|---|---|---|
| `title` | `string` | — | Acción a confirmar |
| `body` | `string` | — | Qué se afecta y su irreversibilidad |
| `confirmLabel` | `string` | — | Verbo de la acción |
| `onConfirm` | `() => void` | — | Callback de confirmación |
| `onCancel` | `() => void` | — | Callback de cancelación |
| `pending` | `boolean` | `false` | Confirmación en curso |

**Accesibilidad (obligatoria, no depende del manual):**
- **DEBE** llevar `role="dialog"` con `aria-modal="true"` y `aria-labelledby` hacia su título.
- **El foco DEBE atraparse dentro del diálogo** mientras está abierto, y **volver al elemento que lo
  abrió** al cerrarse.
- **`Esc` DEBE cerrar** el diálogo cancelando la acción.
- **El foco inicial va en la acción menos destructiva (cancelar)**, no en confirmar.
- El cuerpo **DEBE** nombrar qué se afecta: «Se va a eliminar el requisito #151. Esta acción no se
  puede deshacer.» — no «¿Estás seguro?».
- El fondo **DEBE** quedar inerte (`aria-hidden` o `inert`), no solo visualmente atenuado.
- **NO SE DEBE** confiar en el color para señalar el peligro: lo dice el texto.

**Microcopy:**
- **Título:** la acción — «Eliminar requisito».
- **Cuerpo:** qué se afecta **y** que es irreversible.
- **Botón de confirmar: el verbo de la acción**, no «Sí» — «Eliminar». **Cancelar:** «Cancelar».
- ✗ «¿Estás seguro?» — no dice qué pasa · ✗ «Sí / No» — obliga a releer el título.

**Tokens:** radio 14 px; sombra `elevation.raised`; padding `space.4`; gap entre acciones `space.2`;
z-index `z.modal` (por debajo de `z.tooltip` y por encima de `z.navbar`); `text.card-title`,
`text.body-default`; variant de botón `secondary-dismiss`.

**Migración declarada por el spec** — el componente tiene 3 usos:

| Hoy | Pasa a |
|---|---|
| Borrado con `--color-button-delete` `#FB033F` aplicado por el consumidor | **`secondary-dismiss`** de borde claro; el rojo desaparece de la acción |
| Advertencia apoyada en el color | Advertencia en el **texto**: entidad nombrada + irreversibilidad |
| Foco inicial no verificado | Foco inicial en **cancelar** |

> **Al migrar hay que revisar el microcopy de los usos, no solo el color:** si el cuerpo decía
> «¿Estás seguro?», con este tratamiento el diálogo se queda sin nada que advierta.

**Don't:** no usar un diálogo para una acción reversible · no dejar el foco fuera del diálogo · **no
usar rojo en el botón de confirmar** · **no usar el primario verde agua para confirmar un borrado**
· no dejar el cuerpo sin nombrar la entidad.

### Spec: `ToggleGroup` v1.0.0 (normativo)

**Propósito.** Elegir una opción entre pocas, con todas las opciones visibles.

**Cuándo NO usar:** muchas opciones → `Select`. Filtrar un listado por estado con contadores →
`Tabs`. Disparar una acción → `Button`.

**Variants:**

| Variant | Presentación | Ejemplo |
|---|---|---|
| `segmented` | Segmentos unidos en un contenedor de tinte grafito | «Presente / Ausente» |
| `range-pill` | Pills independientes con borde claro | «Esta semana / Semana pasada / Este mes» |
| `stepper-value` | Valores cortos + escape a valor libre | «0 / 1 / 2 / Otro» |
| `day-chip` | Chips de día | «Vie 21 / Lun 24» |

> **`stepper-value` incluye «Otro» a propósito:** una escala corta cubre el caso frecuente sin
> encerrar al usuario. Al elegir «Otro» se abre un `Input`.

**Sizes:** sin sizes. El alto lo da el `text.body-default` más el padding; **la zona clickeable
nunca baja de 32 px de alto**.

**States:**

| State | Descripción | Tokens |
|---|---|---|
| `default` | Opción no elegida, texto secundario | `toggle.item.text` |
| `hover` | Bajo el puntero | `motion.base` |
| `focus` | Foco por teclado | `focus.ring` |
| `selected` | Opción elegida | **Fondo verde agua + texto azul oscuro** — `toggle.item.active.*` |
| `disabled` | No disponible | `text.disabled` |

**API:**

| Prop | Tipo | Default | Descripción |
|---|---|---|---|
| `variant` | `"segmented" \| "range-pill" \| "stepper-value" \| "day-chip"` | `"segmented"` | Presentación |
| `label` | `string` | — | Nombre accesible del grupo, **requerido** |
| `options` | `{ value, label }[]` | — | Opciones visibles |
| `value` | `string` | — | Opción elegida |
| `onChange` | `(value) => void` | — | Callback |
| `allowOther` | `boolean` | `false` | Solo `stepper-value`: habilita «Otro» |

**Accesibilidad:**
- **DEBE** implementarse como grupo de radios (`role="radiogroup"` con `role="radio"` y
  `aria-checked`), **no como botones sueltos**: la exclusividad tiene que ser evidente para el lector
  de pantalla.
- **Teclado:** flechas mueven la selección dentro del grupo; `Tab` entra y sale del grupo. **Es el
  patrón de radios, no el de botones.**
- El grupo **DEBE** tener nombre accesible (`aria-label` o `<legend>`).
- La selección **NO SE COMUNICA solo con color:** el fondo pleno cambia la forma percibida del ítem,
  y `aria-checked` lo declara.
- **Contraste:** azul oscuro sobre verde agua **9.8:1**.

**Microcopy:** labels cortos (una o dos palabras); **paralelismo** — todas del mismo tipo gramatical
(«Presente / Ausente», no «Presente / No vino»); sentence case; fechas abreviadas en `day-chip`.

**Tokens:** radio 999 px (`radius.pill`) **en las cuatro variants**; fondo del contenedor
(`segmented`) `bg.tint.neutral`; padding del ítem `space.1` vertical / `space.2` horizontal; gap
entre pills (`range-pill`, `day-chip`) `space.1`; **los segmentos de `segmented` no llevan gap**.

**Don't:** no usar para más de cuatro o cinco opciones · no permitir selección múltiple · **no
implementar como botones sueltos sin `radiogroup`** · no dejar el grupo sin ninguna opción elegida
cuando el valor es obligatorio.

## Notas de implementación

1. **Tres de los seis ya existen y tienen consumidores.** Las tareas T-5, T-6 y T-7 no son «crear un
   componente» sino «cambiar la API de algo que 13 archivos importan». Cada una incluye la
   actualización de sus consumidores, y esa es la parte que puede sorprender en tiempo.

2. **El test de conteo del barrel es un cepo conocido.** `index.test.ts` afirma «tiene exactamente 31
   exports». Si T-8 no lo actualiza, la suite rompe con un mensaje que no dice qué pasó.

3. **El microcopy de `ConfirmDialog` es parte del mecanismo de seguridad, no estilo.** Con las dos
   acciones al mismo peso visual, si el cuerpo no nombra qué se borra y que es irreversible, el
   diálogo se queda sin nada que advierta. Revisar los textos de los dos consumidores es obligatorio,
   no opcional.

4. **`EmptyState` no se cablea.** Es lo que CA-2 y la Revisión UX de REQ-013 dicen con todas las
   letras. Un `EmptyState` instalado en una pantalla que hoy no tiene estado vacío es alcance de otro
   requerimiento.

5. **Viewport único.** No hay layout responsive que implementar ni testear en esta superficie.

6. **Los cuatro DS Gaps aceptados (`alert`, `toast`, `progress-bar` de subida, `chart`) no afectan a
   esta story.** Están registrados arriba para que el implementador sepa que son decisiones tomadas
   y no omisiones — y para que las stories de migración los tengan a mano.
