## Story Reference

- **Story:** [S-044](../stories/S-044.totalminutes-opt-in-en-el-listado-de-requisitos.md)
- **Service:** `api`
- **Summary:** `GET /requirements` gana un query param `include` con una lista blanca cerrada de un
  solo valor (`totalMinutes`). Sin él, el SQL es exactamente el de hoy; con él, cada fila de la
  página trae `totalMinutes` calculado con las dos subconsultas correlacionadas del patrón de
  `requirements-report-get.ts`. `count=true` corta antes y nunca arrastra las subconsultas.

### Service Architecture

`api` es la única puerta HTTP de Jiku: autentica contra Zitadel, autoriza por rol y por entidad,
**lee la base directamente** y convierte toda mutación en un comando NATS hacia `core`. Esta story es
**100% lectura**: no toca el bus, no toca `core`, no toca el esquema, no crea migraciones.

**Estructura relevante (sin `src/`, el código vive en `lib/`):**

```
api/
├── app.ts                    Express, middleware global, montaje automático de rutas
├── lib/
│   ├── routes/               un archivo por endpoint + index.ts (barrel)
│   │   ├── requirements-get.ts              <- el archivo de esta story
│   │   ├── requirements-report-get.ts       <- el patrón de las subconsultas a copiar
│   │   ├── requirements-id-worked-hours-get.ts  <- el endpoint de referencia de CA-2 (S-043)
│   │   └── index.ts                         <- barrel; NO cambia (la ruta ya está exportada)
│   ├── models/index.ts       el Sequelize de SOLO LECTURA
│   ├── logger.ts             Winston
│   └── utils/
│       ├── middlewares/      has-any-role, validate-requirement, ...
│       ├── validate-query-params.ts
│       └── *.ts
└── tests/
    ├── routes/               un archivo de test por archivo de ruta
    └── mocks/                app.ts, bus.ts, jsonwebtoken-mock.ts
```

**Patrones clave del servicio:**

- **Un archivo por endpoint.** Validación, permisos y handler colocados juntos. No hay controllers,
  services ni repositorios.
- **Montaje automático:** `app.ts:35-37` itera los exports del barrel y hace `app.use('/api', router)`.
  El path en el archivo de ruta va **sin** el prefijo `/api`. **No se toca `app.ts`.**
- **El esquema Joi vive en el mismo archivo de ruta**, como constante nombrada arriba cuando es
  largo (que es el caso de `requirements-get.ts`).
- **La query vive en el handler**, con los `include` que la respuesta necesita. Sin capa de acceso a
  datos.
- **Manejo de errores inline:** `res.status(n).json({ code, message })`. Sin clases de error, sin
  `throw`, sin handler global de traducción.
- **Logging:** `import logger from '../logger'` (desde `lib/routes/`). Nunca `console`.
- **Comentarios en español, explicando el porqué**, no el qué. `requirements-get.ts` ya tiene tres
  comentarios de ese estilo (el CSV de `state`, el `buildWhere` único, el `String(count) !== 'true'`)
  y el código nuevo tiene que sostener el mismo registro.

**Orden canónico de la cadena de middlewares** (convención `http-server`):

1. Rol — `hasAnyRole([...])`
2. Forma del input — `validateBodyFields` / `validateQueryParams`
3. Existencia de la entidad del path — `validateRequirement` / `validateProject`
4. Permiso sobre esa entidad — `validateProjectPermissions`
5. Reglas de negocio — validadores locales
6. Handler

Esta ruta usa 1, 2 y 6 (más el middleware local `getRequirementsCount`, que corta si `count=true`).
**La cadena no cambia con esta story.**

### Relevant ADRs

#### ADR-001: Separación lectura/escritura por credenciales de base de datos

**Decisión:** la `api` conecta con un rol de PostgreSQL **sin `INSERT`/`UPDATE`/`DELETE`**; `core` es
el único que escribe; toda mutación viaja como comando por el bus.

**Implementation Rules (verbatim):**

- Toda escritura de dominio nueva **DEBE** implementarse como comando en `core`. **NO SE DEBE**
  agregar escritura con el ORM en `api`.
- La conexión de `api` **DEBE** usar credenciales sin `INSERT`/`UPDATE`/`DELETE`. Si un endpoint
  nuevo requiere escribir, la respuesta correcta es un comando, no ampliar los permisos del rol.
- La conexión de `core` **DEBE** usar el usuario dueño de la base.
- Las migraciones **DEBEN** correr desde `api` con `POSTGRESQL_MIGRATION_USER`, nunca desde `core`.
- Después de publicar un comando de creación, la api **DEBE** releer la base para armar la
  respuesta: core devuelve solo `{ id }` y el contrato con los frontends es el recurso completo
  con sus relaciones.
- Un endpoint que lee **NO DEBE** pasar por el bus: la lectura va directo a PostgreSQL desde la api.
  **Excepción declarada desde REQ-001 (S-005): la lectura de archivos.**

**Aplicación a esta story:** el endpoint es de lectura pura → **no pasa por el bus**, consulta
PostgreSQL directamente desde el handler. No hay escritura de ningún tipo, ni migración.

#### ADR-008: Autorización deny-by-default

**Decisión:** `validateToken` se instala globalmente en `app.ts` para todo path salvo las exenciones
de `config/public.ts`; el rol se declara por ruta.

**Implementation Rules (verbatim):**

- `validateToken` **DEBE** instalarse globalmente en `app.ts`. **NO SE DEBE** declarar
  autenticación ruta por ruta.
- Un endpoint público **DEBE** agregarse explícitamente a `api/lib/config/public.ts`. Cualquier
  cambio en ese archivo es un **cambio de seguridad** y debe revisarse como tal.
- Un endpoint público **DEBE** validar por su cuenta lo que corresponda. El caso vigente
  (`GET /api/opus/attachments/:id/public`) verifica que el adjunto esté marcado público, responde
  403 en cualquier otro caso, y manda `X-Content-Type-Options: nosniff` con CSP de sandbox.
- Un endpoint que requiere rol **DEBE** declarar `hasAnyRole([...])` explícitamente. La
  autenticación global no implica autorización.
- Un endpoint accesible a `external-user` **DEBE** además verificar permiso de proyecto: el rol
  solo no alcanza (ADR-006).
- Un tipo de entidad nuevo con adjuntos **DEBE** agregarse a la resolución de proyecto de
  `attachments-access.ts`. Un tipo no contemplado **no se autoriza**, que es el comportamiento
  correcto.
- Al leer un archivo de ruta, **NO SE DEBE** concluir que está desprotegido por no ver el
  middleware: la protección es global.

**Aplicación a esta story:** el `hasAnyRole(['user', 'admin'])` existente de `requirements-get.ts`
**se conserva tal cual** (CA-5). No se agrega ni se quita nada de `config/public.ts`. Al no ser
alcanzable por `external-user`, `validateProjectPermissions` (que **solo** restringe a ese rol) sigue
siendo innecesario en esta ruta. **CA-7 se satisface sin cambio de código** — ver "El recorte externo
es estructural" en API Context.

#### ADR-013: Tests contra base de datos real, con un doble de bus que ejecuta `core`

**Decisión:** los tests corren contra PostgreSQL real, sin mocks de Sequelize. El `FakeBus` ejecuta
`core` de verdad contra la misma base.

**Implementation Rules (verbatim):**

- Los tests de `api` y `core` **DEBEN** correr contra PostgreSQL real. **NO SE DEBEN** mockear los
  modelos de Sequelize.
- Los tests de comandos de `core` **DEBEN** entrar por el despachador (`dispatch()`), **NO** por
  `execute()` directamente.
- Un test de escritura de la api **DEBE** verificar las tres capas: comando publicado, traducción de
  la respuesta a HTTP, y que la fila quedó escrita. **NO SE DEBE** asertar solo el status HTTP.
- `reply()` / `failWith()` **DEBEN** usarse solo para cubrir caminos de error. El camino feliz
  **DEBE** ejecutar core de verdad.
- Cada archivo de test **DEBE** poder correr solo: el esquema y el mock de auth se preparan en
  fixtures globales de Mocha.
- `TZ=UTC` **DEBE** estar fijado en la configuración de test de todo servicio.
- La limpieza entre corridas **DEBE** ser `TRUNCATE ... RESTART IDENTITY CASCADE`, para que los ids
  autoincrementales sean predecibles.
- **NO SE DEBE** depender del orden de ejecución entre archivos de test.

**Aplicación a esta story:** los tests preparan su propio estado con `Model.create()` y lo limpian en
`after` con `Model.destroy({ where: {} })`, como ya hace `tests/routes/requirements-get.test.ts`.
**No hay escritura**, así que el `FakeBus` no interviene: no hay comando que asertar. `sinon` sí se
usa, para el caso de error 500 (ya hay precedente en el archivo: `sinon.stub(Requirement, 'count')`).

#### Contrato nuevo (esta story)

**Nuevo query param `include`**, que se inserta después de `count` en la lista de `parameters`:

```yaml
        - name: include
          in: query
          description: |
            Lista de campos calculados adicionales, separados por coma. Único valor aceptado:
            `totalMinutes`. Ausente, la respuesta no lo trae y las subconsultas no se ejecutan.
            Un valor fuera de la lista responde 400 `invalid_fields`.

            **`count=true` lo ignora:** el conteo devuelve un entero y no hay dónde poner el
            campo, así que las subconsultas no se arrastran a un `COUNT`.
          schema: { type: string }
          example: totalMinutes
```

**Nuevo campo opcional en `RequirementWithRelations`** (`docs/apis/api.yaml:3095` en adelante). El
schema hoy es:

```yaml
    RequirementWithRelations:
      description: |
        ... (descripción existente, se conserva) ...
      allOf:
        - $ref: '#/components/schemas/Requirement'
        - type: object
          properties:
            project: { $ref: '#/components/schemas/ProjectSummary' }
            creator: { $ref: '#/components/schemas/AuthorUser' }
            activity: ...
            responsiblePeople: ...
```

Se agrega dentro de ese `properties`:

```yaml
            totalMinutes:
              type: integer
              description: |
                Minutos imputados al requisito más los de sus tareas. **Solo presente con
                `include=totalMinutes` en `GET /requirements`**: son dos subconsultas
                correlacionadas por fila y no se pagan si no se piden. Misma gradación que el
                incluible homónimo de `core-queries.yaml`. Mismo valor que devuelve
                `GET /requirements/{reqid}/worked-hours`.
```

> **Ojo con la deriva ya declarada del schema.** La `description` de `RequirementWithRelations` ya
> advierte que el schema **sobredeclara** para tres de las cinco respuestas que lo referencian
> (`GET /requirements`, `POST /requirements`, `PATCH /requirements/{reqid}` no devuelven `creator`).
> `totalMinutes` **agranda esa deriva de forma controlada y consciente**: solo un endpoint y solo
> bajo `include`. Por eso la `description` del campo dice explícitamente en qué endpoint y bajo qué
> condición aparece. **No arregles la deriva preexistente de `creator` en esta story** — su arreglo
> va por `/product-change-technical-definition`, según la nota del propio schema.

#### La forma del opt-in: por qué `include` y no un booleano

Del diseño técnico de la story, verbatim:

> **La forma del opt-in es `include=totalMinutes`** — mismo nombre y semántica que el mecanismo
> del contrato de consultas del bus (`core-queries.yaml`, "Deny-by-default, as five whitelists
> per resource"): lista de nombres cerrada, un nombre no declarado es `invalid_fields`. Alinear
> los dos nombres deja preparada una futura migración de esta ruta al plano de consultas como
> traducción, no como rediseño.

Consecuencia para el implementor: **no lo simplifiques a `withTotalMinutes=true`**. Que hoy la lista
blanca tenga un solo miembro no es motivo para colapsar el mecanismo — la lista es el contrato.

#### Implementación actual completa (`api/lib/routes/requirements-get.ts`)

```ts
import { NextFunction, Request, Response, Router } from 'express';
import { sequelize } from '../models';
import { Person, Project, Requirement, RequirementState, RequirementType } from '@jiku/models';
import logger from '../logger';
import hasAnyRole from '../utils/middlewares/has-any-role';
import validateQueryParams from '../utils/validate-query-params';
import joi from 'joi';
import { Op } from 'sequelize';

const router: Router = Router();

// `state` acepta un CSV de uno o varios valores. Se valida como una lista (separador ',') en la
// que cada miembro tiene que pertenecer al enum: un unico miembro invalido invalida el parametro
// completo con 400, igual que hoy, y no lo convierte en un filtro parcial silencioso (a
// diferencia de `objectives-get.ts`, que no valida sus miembros contra el enum).
const querySchema = joi.object({
  projectId: joi.number().integer().optional(),
  state: joi
    .string()
    .custom((value, helpers) => {
      const members = String(value).split(',').map((s) => s.trim());
      const validValues = Object.values(RequirementState) as string[];
      const isValid = members.every((member) => validValues.includes(member));
      if (!isValid) return helpers.error('any.only');
      return value;
    }, 'CSV of RequirementState')
    .messages({ 'any.only': `"state" must be one of [${Object.values(RequirementState).join(', ')}]` })
    .optional(),
  type: joi.string().valid(...Object.values(RequirementType)).optional(),
  priority: joi.string().optional(),
  createdBy: joi.string().optional(),
  estimatedFinishDate: joi.date().optional(),
  tag: joi.string().optional(),
  search: joi.string().optional(),
  page: joi.number().integer().min(1).default(1),
  limit: joi.number().integer().min(1).max(100).default(20),
  sort: joi.string().optional(),
  count: joi.boolean().optional(),
});

// Un solo constructor del `where` para listado y conteo: si cada uno armara el suyo, un filtro
// nuevo agregado a uno y no al otro los haria divergir sin que ningun test lo note.
function buildWhere(query: any) {
  const { projectId, state, type, priority, createdBy, estimatedFinishDate, tag, search } = query;

  const where: any = {};
  if (projectId) where.projectId = Number(projectId);
  if (state) where.state = { [Op.or]: String(state).split(',').map((s) => s.trim()) };
  if (type) where.type = type;
  if (priority) where.priority = priority;
  if (createdBy) where.createdBy = createdBy;
  if (estimatedFinishDate) where.estimatedFinishDate = estimatedFinishDate;
  if (search) where.title = { [Op.iLike]: '%' + search + '%' };
  if (tag) {
    const [key, value] = String(tag).split(':');
    where.tags = sequelize.literal(
      `tags @> '[{"key": ${JSON.stringify(key)}, "value": ${JSON.stringify(value)}}]'::jsonb`
    );
  }

  return where;
}

function getRequirementsCount(req: Request, res: Response, next: NextFunction) {
  // `count` llega como string: Express 5 no coerciona req.query, y validateQueryParams descarta
  // el value que Joi devuelve ya coercido (solo usa `error`). Por eso se compara contra 'true' en
  // vez de evaluar la verdad del valor: el string 'false' es truthy y devolveria el conteo a quien
  // pidio el listado.
  if (String(req.query.count) !== 'true') {
    return next();
  }

  // Sin `include`: ningun filtro depende de las relaciones -`project` y `responsiblePeople` se
  // incluyen solo para armar el cuerpo del listado-, asi que no hay filas duplicadas que obliguen
  // al `distinct` que si necesita el conteo de objectives.
  return Requirement.count({ where: buildWhere(req.query) })
    .then((count) => {
      return res.status(200).json(count);
    })
    .catch((error) => {
      logger.error(`[GET /requirements] getRequirementsCount error: ${error.message}`);
      return res.status(500).json({ code: 'internal_error', message: 'Internal error' });
    });
}

function getRequirements(req: Request, res: Response) {
  const { page = 1, limit = 20 } = req.query as any;
  const offset = (Number(page) - 1) * Number(limit);

  const where = buildWhere(req.query);

  return Requirement.findAll({
    where,
    include: [
      { model: Project, as: 'project', attributes: ['id', 'name'] },
      {
        model: Person,
        as: 'responsiblePeople',
        attributes: ['id', 'firstName', 'lastName'],
        through: { attributes: ['isLeader'] },
      },
    ],
    limit: Number(limit),
    offset,
    order: [['createdAt', 'DESC']],
  })
    .then((requirements) => {
      const response = requirements.map((requirement) => {
        const json = requirement.toJSON() as any;
        json.responsiblePeople = (json.responsiblePeople || []).map((person: any) => ({
          id: person.id,
          firstName: person.firstName,
          lastName: person.lastName,
          isLeader: person.PersonRequirement?.isLeader ?? null,
        }));
        return json;
      });
      return res.status(200).json(response);
    })
    .catch((error) => {
      logger.error(`[GET /requirements] error: ${error.message}`);
      return res.status(500).json({ code: 'internal_error', message: 'Internal error' });
    });
}

router.get('/requirements',
  hasAnyRole(['user', 'admin']),
  validateQueryParams(querySchema),
  getRequirementsCount,
  getRequirements
);

export default router;
```

> **Dos detalles del archivo que condicionan la implementación:**
>
> 1. **`validateQueryParams` descarta el `value` coercido de Joi** (`api/lib/utils/validate-query-params.ts`
>    solo usa `error`). Por eso `req.query` sigue trayendo **strings crudos** dentro del handler. El
>    comentario existente sobre `String(req.query.count) !== 'true'` documenta exactamente esta
>    trampa. El `include` se lee igual: como string, y se parsea a mano.
> 2. **`getRequirementsCount` corta con `res.status(200).json(count)`** antes de llegar a
>    `getRequirements`. Eso es lo que ya hace que **CA-4 sea casi gratis**: el `include` se aplica en
>    `getRequirements`, que nunca se ejecuta con `count=true`. Lo que hay que garantizar es que
>    **no se toque `getRequirementsCount`** para hacerlo consciente de `include`.

#### El patrón de las subconsultas a copiar (`api/lib/routes/requirements-report-get.ts:56-69`)

```ts
import { Op, literal } from 'sequelize';

return Requirement.findAll({
  where: whereClause,
  include: [{ model: Project, as: 'project', attributes: ['id', 'name'] }],
  attributes: {
    include: [
      [literal(`(
        SELECT COALESCE(SUM(wt.minutes), 0)
        FROM worked_times wt
        WHERE wt.requirement_id = "Requirement"."id"
      )`), 'directMinutes'],
      [literal(`(
        SELECT COALESCE(SUM(wt.minutes), 0)
        FROM worked_times wt
        INNER JOIN objectives o ON o.id = wt.objective_id
        WHERE o.requirement_id = "Requirement"."id"
      )`), 'objectiveMinutes'],
    ],
  },
})
```

y el armado de la respuesta (`requirements-report-get.ts:81`):

```ts
totalMinutes: Number(raw.directMinutes) + Number(raw.objectiveMinutes),
```

> **`attributes: { include: [...] }` (con la clave `include` **adentro** de `attributes`) suma
> columnas calculadas SIN reemplazar la lista de atributos del modelo.** Es distinto del `include:`
> de nivel superior, que declara asociaciones. `requirements-get.ts` tiene el segundo y **no** tiene
> el primero: hay que agregar `attributes` como clave hermana de `include`, no dentro de él.

> **`COALESCE(SUM(...), 0)` es obligatorio:** sin él, un requisito sin horas devuelve `NULL` y
> `Number(null)` da `0` por casualidad, pero `Number(undefined)` daría `NaN`. El `COALESCE` hace que
> el cero sea del SQL y no del casteo.

> **`Number(...)` en los dos lados es obligatorio:** `SUM` de PostgreSQL es `bigint` y el driver `pg`
> lo entrega como **string** para no perder precisión. Sin el casteo, `"120" + "60"` da `"12060"`.
> Es exactamente el mismo motivo por el que `requirements-id-worked-hours-get.ts` castea sus filas.

#### El endpoint de referencia de CA-2 (`api/lib/routes/requirements-id-worked-hours-get.ts`, dejado por S-043)

```
GET /api/requirements/:reqid/worked-hours
x-roles: [user, admin]
```

Su SQL, verbatim:

```sql
SELECT p.id AS "personId", p.first_name AS "firstName", p.last_name AS "lastName",
       SUM(src.minutes)::bigint AS minutes
  FROM (
    SELECT wt.person_id, wt.minutes FROM worked_times wt WHERE wt.requirement_id = :reqId
    UNION ALL
    SELECT wt.person_id, wt.minutes FROM worked_times wt
      INNER JOIN objectives o ON o.id = wt.objective_id WHERE o.requirement_id = :reqId
  ) AS src
  INNER JOIN people p ON p.id = src.person_id
 GROUP BY p.id, p.first_name, p.last_name
 ORDER BY minutes DESC, p.id ASC
```

Respuesta: `{ requirementId, totalMinutes, byPerson[] }`, con
`totalMinutes = byPerson.reduce((acc, p) => acc + p.minutes, 0)`.

> **La equivalencia que CA-2 exige, y su única diferencia real.** Los dos conjuntos de filas son los
> mismos: horas directas al requisito (`wt.requirement_id`) más horas de sus tareas
> (`o.requirement_id` vía `objectives`). La diferencia es que `worked-hours` hace
> `INNER JOIN people`, así que **una hora imputada a un `person_id` que no existe en `people` se
> perdería ahí y no acá**. En la práctica `worked_times.person_id` es FK a `people.id`, así que el
> conjunto es idéntico. **No repliques el `INNER JOIN people`**: acá no se necesita ninguna columna
> de la persona, y agregarlo sería pagar un join por fila para nada.

### Code Conventions

**Validación (convención `validation`):**

- El esquema Joi vive **en el mismo archivo de ruta**. `requirements-get.ts` ya lo tiene como
  constante nombrada `querySchema` arriba del archivo: ahí va el campo nuevo.
- Contrato de error inamovible: `400` con `{ code: 'invalid_fields', message: 'Invalid field - ...' }`.
- Se devuelve **un** error, no la lista. No lo cambies a un array.
- Los enums salen de los modelos (`...Object.values(...)`). **`include` es la excepción legítima:**
  su lista blanca no es un enum de `@jiku/models`, es un contrato de la API. Va como constante de

> **Nota sobre `literal` en esta story.** La convención dice que los reportes con agregación usan

> expresión en `fn`/`col`. La regla que **sí** sigue vigente y es no negociable: **en ese `literal`

> interpolan nada de `req.query`. El único input que toca esta story (`include`) se compara contra

### Task 1: Agregar el query param `include` y el `totalMinutes` opcional en `requirements-get.ts`

**Status:** Completed

#### Description

Es la tarea central. `GET /api/requirements` gana un query param `include` con una lista blanca

solo miembro.
