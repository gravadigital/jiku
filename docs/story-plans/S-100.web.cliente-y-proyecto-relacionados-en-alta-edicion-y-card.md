# Story Plan: S-100 (web) - Cliente y Proyecto relacionados en alta, edición y "+"

## Status

**Status:** Completed

**Progress:** 4/4 tareas completadas

## Story Reference

- **Story:** [S-100](../stories/S-100.web-cliente-y-proyecto-relacionados-en-alta-edicion-y-card.md)
- **Service:** `web`
- **Origen:** [REQ-022](../requests/REQ-022.arreglos-e2e-documentacion-sin-carpetas.md)
- **Summary:** la web lee el cliente de cada proyecto de `GET /api/projects` con un helper único
  `projectClientId(p) = p.client?.id ?? p.clientId ?? null` y lo usa en `ProjectPicker` (filtro,
  etiqueta y `onChange`), `ClientProjectFields.projectClientOf` y el efecto `clientPending` de
  `NewDocumentDialog`. Con eso el selector de Proyecto ofrece los proyectos del cliente elegido,
  elegir un proyecto completa el cliente, reelegir el mismo cliente conserva el proyecto, y lo
  precargado desde la ficha del proyecto (o del documento en edición) se ve en los selectores.

> **Alcance de este plan:** solo el servicio `web` (CA-1 a CA-5, y la no regresión de CA-7). El
> cambio de `GET /api/projects` (CA-6) es del plan `api`
> ([S-100.api](./S-100.api.cliente-y-proyecto-relacionados-en-alta-edicion-y-card.md), **Completed**).
> El respaldo en `clientId` hace que la web funcione aunque una lista venga sin `client`.

> **Causa del defecto (verificada sobre el árbol, rama `feature/S-100_…`, `e2bbe57`):**
> - `ProjectPicker.tsx` filtra con `p.client?.id === clientId` y arma `clientId: p.client?.id ?? null`.
> - `ClientProjectFields.tsx` arma `projectClientOf` con `p.client?.id ?? null`.
> - `NewDocumentDialog.tsx` (efecto `clientPending`) completa el cliente con `project?.client?.id`.
> - Antes del plan `api`, `GET /api/projects` no traía `client`: los tres leían `undefined`. Con un
>   cliente elegido el selector de Proyecto quedaba solo con "Sin proyecto", elegir un proyecto no
>   completaba el cliente, reelegir el mismo cliente vaciaba el proyecto, y el "+" mostraba
>   "EXO / Sin proyecto".
> - Los tests existentes no lo detectaron porque los mocks de `useProjects` traen `client` (forma del
>   **detalle**) y nunca `clientId` (forma real del **listado** previo). Los tests nuevos usan la forma
>   de la api: `clientId` + `client`, y también `clientId` solo (respaldo).
> - `features/projects/types/project.types.ts` → `Project` declara `client?: Client` y **no** declara
>   `clientId`.
> - `relationFields.ts` (`setPrincipal`, `chooseProject`, `chooseClient`): la lógica es correcta, **no se toca**.
> - `ClientProjectLabel`: sin cambios (CA-7 es no regresión).

### API Context

**`GET /api/projects`** (contrato `docs/apis/api.yaml`, `/projects` → `get`, ya actualizado por el plan `api`):

- Descripción: "Incluye el creador y el cliente. Los `null` de `keyValuePairs` se devuelven como string vacío, porque es lo que espera la web."
- Cada ítem: `allOf: [Project, { creator: User, client: { id: integer, name: string } | null }]`.
- `Project.clientId`: `{ type: integer, nullable: true }` (siempre presente).
- `client`: `type: object`, `nullable: true`, `required: [id, name]`, "El cliente del proyecto; `null` sin cliente".
- Sin `limit`, `parseGetParams` usa 200 (preexistente; con más de 200 proyectos alguno no aparece en el selector — fuera de alcance).

Ejemplo de respuesta (de la story):

```json
[{ "id": 43, "name": "EXO - Videoconferencia", "clientId": 1, "client": { "id": 1, "name": "EXO" }, "...": "..." }]
```

**`GET /api/projects/:id`** (detalle, sin cambios): trae `client` con la fila completa del cliente. Lo
usa `app/(loggedin)/projects/[id]/page.tsx` para `DocsPanel context={{ clientId: project.client?.id }}`.

**Alta (sin cambios):** `POST /api/docs/documents { id, content }`. La web arma el frontmatter con
`jiku: { clients, projects, requirements?, tasks? }` vía `buildNewDocumentContent`. Con cliente 1 y
proyecto 43 el contenido incluye exactamente `  clients: [1]\n  projects: [43]\n`.

### Flow Context

**documentos-desde-la-web — Paso 2b: alta sin carpeta (web)** (extracto):

> `POST /api/docs/documents { id?, folderId?, fileName?, content, message? }`. **Lo que manda la web
> (REQ-021):** solo `id` y `content`. La web arma el frontmatter del contenido (`title`, `visibility`,
> `topics` y `jiku: { clients, projects, requirements?, tasks? }`, con el cuerpo inicial `# {título}`)
> y **no manda `folderId` ni `fileName`**.
>
> **Selectores Cliente / Proyecto (REQ-022, S-100):** la web lee el cliente de cada proyecto de
> `GET /api/projects` (`client.id`, con respaldo en `clientId`): el selector de Proyecto ofrece los del
> cliente elegido y elegir un proyecto completa su cliente.

**Interacción (de la story):**

1. **[web]** `useProjects()` → `GET /api/projects`.
2. **[api]** `200 [{ id: 43, name: "EXO - Videoconferencia", clientId: 1, client: { id: 1, name: "EXO" }, ... }]`.
3. **[web]** `ProjectPicker` con `clientId=1` filtra `projectClientId(p) === 1`: opciones "Sin proyecto" + proyectos de EXO. ← **este plan**
4. **[web]** elegir el proyecto 43 → `chooseProject` → `{ clients: [1], projects: [43] }`. Reelegir EXO conserva el proyecto; otro cliente lo vacía; "Sin cliente" lo vacía siempre. ← **este plan**

"+" de la card de proyecto: `DocsPanel` del proyecto 43 → `NewDocumentDialog initial={{ projectId: 43, clientId: 1 }}`;
estado `{ clients: [1], projects: [43] }`; el `Select` muestra "EXO - Videoconferencia · EXO". Si
`initial` trae solo `projectId`, el efecto `clientPending` completa el cliente con `projectClientId`.
