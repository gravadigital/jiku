## Story Reference

- **Story:** [S-100](../stories/S-100.web-cliente-y-proyecto-relacionados-en-alta-edicion-y-card.md)
- **Service:** `api`
- **Origen:** [REQ-022](../requests/REQ-022.arreglos-e2e-documentacion-sin-carpetas.md)
- **Summary:** `GET /api/projects` agrega a cada proyecto el objeto `client` (`{ id, name }`, o `null`
  si el proyecto no tiene cliente), con un `include` acotado de `Client`. Es un cambio **aditivo**:
  todos los campos previos (incluido `clientId`) se conservan. Se actualiza el contrato `/projects`
  de `docs/apis/api.yaml`. Con esto la web puede leer `p.client?.id` (hoy siempre `undefined`).

> **Alcance de este plan:** solo el servicio `api` (CA-6, y la parte de datos que habilita CA-1 a
> CA-5 y CA-7). Los selectores, el helper `projectClientId`, `ProjectPicker`, `ClientProjectFields`,
> `NewDocumentDialog` y la no regresión de `ClientProjectLabel` son del servicio `web` y van en su
> propio plan. El respaldo en `clientId` de la web permite implementar ambos en paralelo.

> **Contexto UX / Design System:** la story tiene `affects_ui: true` por el lado `web`. Este plan es
> del servicio `api` (`type: api` en su `manifest.yaml`), que no tiene UI: no se copia contexto de
> pantallas ni de Design System. La revisión UX de REQ-022 registra **0 gaps** de DS (verificado
> contra `web` v4.3.0), así que no hay componentes `pendiente-DS` que bloqueen.

> **Precondición verificada sobre el árbol (2026-10-26, rama `feat/jiku-docs`, `a11259d`):**
> - `api/lib/routes/projects-get.ts:27-32` hace `Project.findAll({ ..., include: { model: User, as: 'creator', attributes: ['id', 'name', 'email'] } })` — sin `Client`.
> - `api/lib/routes/projects-id-get.ts:10-13` ya incluye `{ model: Client, as: 'client' }` (sin `attributes`, trae la fila completa). Este plan **no** lo toca.
> - `packages/models/src/project.model.ts:126-134` declara `@ForeignKey(() => Client) clientId` y `@BelongsTo(() => Client) client`. La asociación existe; **no hace falta tocar modelos ni migraciones**.
> - `docs/apis/api.yaml` (`/projects` → `get` → `200`) declara los ítems como `allOf: [Project, { creator: User }]`, sin `client`.
> - `api/tests/routes/projects-get.test.ts` crea 4 proyectos **sin** `clientId` y no crea clientes.

## Architectural Context

### Tech Stack

- Node.js + TypeScript (`strict` apagado, a propósito — ver `_base`).
- Express 5.2, un archivo por endpoint, montado bajo `/api` por el barrel `lib/routes/index.ts`.
- Sequelize 6.37 + `sequelize-typescript` 2.1, conexión **de solo lectura**; modelos en `@jiku/models`.
- Joi para validar query params (`validateQueryParams`).
- Tests: Mocha 11.7 + `should` 13.2 + `supertest` 7.1, contra PostgreSQL real (esquema creado una vez
  por `sequelize.sync()` en el fixture global), app levantada con `start()` de `tests/mocks/app.ts`,
  JWT mockeado (`Bearer token_01_user`).

### Service Architecture

**Estructura relevante:**

```

│   ├── routes/
```

**Convención `_base` (extracto aplicable):**
- No hay `src/`; el código vive en `lib/`. Imports relativos; paquetes del monorepo por nombre (`@jiku/models`).
- El orden habitual en un archivo de ruta: express, paquetes externos, `@jiku/*`, y después los relativos del servicio.
- Comentá en español, y comentá **el por qué**, no el qué.
- Lint antes de dar por terminado: `npm run lint --workspace @jiku/api` (cubre solo `./lib`).

**Convención `orm` (extracto aplicable, verbatim de las reglas):**
- No escribas con el modelo.
- Los modelos se modifican en `packages/models/src/`, nunca localmente en la api. El cambio afecta también a core.
- `attributes` explícito en los `include`. No traigas relaciones completas.
- `as` explícito cuando la asociación tiene alias.
- Búsqueda de texto con `Op.iLike`, nunca `Op.like`.
- Filtros condicionales con el patrón `reduce`.

Ejemplo canónico de `include` múltiple con `attributes` (convención `orm`):

```ts
// lib/routes/requirements-get.ts:47-62
return Requirement.findAll({
  where,
  include: [
    { model: Project, as: 'project', attributes: ['id', 'name'] },
    {
      model: Person,
      as: 'responsiblePeople',
      attributes: ['id', 'firstName', 'lastName'],
      through: { attributes: ['isLeader'] },
    },
  ],
  limit: Number(limit),
  offset,
  order: [['createdAt', 'DESC']],
});
```

**Convención `error-handling`:** errores como `res.status(<n>).json({ code, message })`. El handler
de `projects-get.ts` ya responde `500 { code: 'internal_error', message: 'Internal error' }` en su
`catch`; no cambia.

**Convención `authorization` (extracto):** `GET /api/projects` **no** tiene `hasAnyRole`: es alcanzable
por cualquier usuario autenticado. Es deuda preexistente documentada, **fuera del alcance** de esta
story (la story declara "Sin cambios de autenticación ni de `getRolesFromToken`"). El campo nuevo
`client` expone solo `id` y `name`, que ya son visibles para los mismos roles en `GET /projects/{id}`.

**Convención `testing` (reglas aplicables, verbatim):**
- No mockees Sequelize ni la base. Los tests corren contra PostgreSQL real.
- No prepares el esquema en un archivo de test: lo hacen los fixtures globales.
- Limpiá los datos que creaste en `after` / `afterEach` con `Model.destroy({ where: {} })`. Un test que deja filas contamina al siguiente.
- Aserciones con `should`. No mezcles `assert` ni `expect`.
- Un test no depende del orden de ejecución ni del estado que dejó otro.

### Relevant ADRs

- **ADR-001: Separación lectura/escritura por credenciales de base de datos**
  - Decision: la api lee directo de PostgreSQL con credenciales de solo lectura; toda escritura es un comando a core.
  - Implementation Rules (verbatim):
    - Toda escritura de dominio nueva **DEBE** implementarse como comando en `core`. **NO SE DEBE** agregar escritura con el ORM en `api`.
    - La conexión de `api` **DEBE** usar credenciales sin `INSERT`/`UPDATE`/`DELETE`. Si un endpoint nuevo requiere escribir, la respuesta correcta es un comando, no ampliar los permisos del rol.
    - La conexión de `core` **DEBE** usar el usuario dueño de la base.
    - Las migraciones **DEBEN** correr desde `api` con `POSTGRESQL_MIGRATION_USER`, nunca desde `core`.
    - Después de publicar un comando de creación, la api **DEBE** releer la base para armar la respuesta: core devuelve solo `{ id }` y el contrato con los frontends es el recurso completo con sus relaciones.
    - Un endpoint que lee **NO DEBE** pasar por el bus: la lectura va directo a PostgreSQL desde la api. **Excepción declarada desde REQ-001 (S-005): la lectura de archivos.** Los cinco caminos de lectura de adjuntos publican `files.{fileId}.request-download` para obtener la URL prefirmada, porque el storage tiene un solo dueño y es `core`. Ver "Revisión: la lectura de archivos".
  - Aplicación: `GET /api/projects` es lectura → `Project.findAll` con `include`, sin bus.

- **ADR-005: Modelos compartidos en `@jiku/models`, sin abrir la conexión**
  - Decision: una sola definición de modelos para api y core.
  - Implementation Rules (verbatim):
    - Los modelos Sequelize **DEBEN** vivir en `@jiku/models`. **NO SE DEBE** definir un modelo dentro de `api/` o de `core/`.
    - `@jiku/models` **NO DEBE** abrir una conexión ni leer variables de entorno de base de datos. Exporta clases; la instancia la crea cada servicio.
    - Cada servicio **DEBE** registrar las clases en su propio `Sequelize` con sus credenciales.
    - Un cambio de esquema **DEBE** hacerse en dos lugares en el mismo cambio: la migración en `api/db-upgrade/migrations/` y el modelo en `@jiku/models`. Uno sin el otro deja el código y la base desalineados.
    - Los hooks que van en el modelo son los que pertenecen **al dato** (mantener `finishedAt` consistente con `state`). Los que dependen del caso de uso o del rol **DEBEN** ir en el comando de core o en la api.
    - Los nombres en `@jiku/models` **DEBEN** ser los reales de la base. La traducción de vocabulario es responsabilidad de core.
    - Al agregar un modelo, **DEBE** registrarse en el índice del paquete: los dos servicios lo importan desde ahí.
  - Aplicación: `Client` se importa de `@jiku/models`; la asociación `Project.client` ya existe. Sin cambio de esquema.

- **ADR-013: Tests contra base de datos real, con un doble de bus que ejecuta `core`**
  - Implementation Rules (verbatim, las aplicables a una lectura):
    - Los tests de `api` y `core` **DEBEN** correr contra PostgreSQL real. **NO SE DEBEN** mockear los modelos de Sequelize.
    - Cada archivo de test **DEBE** poder correr solo: el esquema y el mock de auth se preparan en fixtures globales de Mocha.
    - `TZ=UTC` **DEBE** estar fijado en la configuración de test de todo servicio.
    - **NO SE DEBE** depender del orden de ejecución entre archivos de test.

**Cambio de diseño (de la story, verbatim):**
- **Cambio:** el ítem agrega `client` (objeto `{ id: integer, name: string }`, `nullable`, `required: [id, name]`), "El cliente del proyecto; `null` sin cliente". `include: [{ model: User, as: 'creator', attributes: ['id','name','email'] }, { model: Client, as: 'client', attributes: ['id','name'] }]`. Mismo patrón que `projects-id-get.ts:11-14`, acotado a `id`/`name`.
- **Compatibilidad:** aditivo. Todos los campos previos (incluido `clientId`) se conservan; la descripción del endpoint pasa a "Incluye el creador y el cliente". `BelongsTo` no multiplica filas: `limit`/`offset` siguen correctos.
- **Justificación:** hoy el JSON trae `clientId` pero no el objeto `client`; la web lee `p.client?.id` y siempre obtiene `undefined`.

**Query params (sin cambios):** `sort` (por defecto `-createdAt`; `-campo` → `DESC`), `page` (≥ 1,
por defecto 1), `limit` (Joi `min(1).max(30)`; si no viene, `parseGetParams` usa 200), `search`
(`name ILIKE '%…%'`), `type` (`interno | comercial | investigacion | propuesta`), `state` (lista por coma).

**Autenticación:** `validateToken` global (sin token → `401 { code: 'unauthorized', message: 'Unauthorized' }`).
Sin `hasAnyRole` (ver Convención `authorization`).

**Errores:** `400 { code: 'invalid_fields', message: 'Invalid field - "limit" must be greater than or equal to 1' }`
(validación Joi), `500 { code: 'internal_error', message: 'Internal error' }`.

### Database Context

Sin cambios de esquema ni migraciones.

- `projects.client_id` — `INTEGER`, NULL → `clients.id`. Índice en `20260724_01`.
- `clients` — `id` (PK), `name`, `description` (nullable), `created_at`, `updated_at`.
- Modelo (`packages/models/src/project.model.ts:126-134`):
  ```ts
  @ForeignKey(() => Client)
  @Column(...)
    clientId!: number;

  @BelongsTo(() => Client)
    client!: Client;
  ```
  Alias de la asociación: `'client'`.
- `BelongsTo` → `LEFT OUTER JOIN clients` sobre `client_id`: un proyecto sin cliente sale igual, con
  `client: null`. No multiplica filas, así que `limit`/`offset` no necesitan subquery.

## Tasks

### Task 1: `GET /api/projects` incluye el cliente de cada proyecto

**Status:** Completed

#### Description

Agregar a la consulta de `projects-get.ts` el `include` de `Client` con alias `'client'` y
`attributes: ['id', 'name']`, junto al `include` existente de `creator`. Así cada ítem de la
respuesta trae `client: { id, name }` o `client: null`. Es lo que la web necesita para relacionar
Cliente y Proyecto en el alta, la edición y el "+" de la card (CA-1 a CA-5), y lo que CA-6 exige
como cambio compatible.

#### Acceptance Criteria

1. `Project.findAll` recibe `include: [{ model: User, as: 'creator', attributes: ['id', 'name', 'email'] }, { model: Client, as: 'client', attributes: ['id', 'name'] }]`.
2. Un proyecto con `client_id` devuelve `client: { id, name }` con exactamente esas dos claves.
3. Un proyecto sin `client_id` devuelve `client: null` (propiedad presente).
4. Todos los campos previos se conservan, incluidos `clientId`, `creator` (con exactamente `id`, `name`, `email`) y el reemplazo de `null` por `''` en `keyValuePairs`.
5. `limit`, `page`, `sort`, `search`, `type` y `state` se comportan igual que antes (sin errores de columna ambigua por el join).
6. El JSDoc del router documenta `@responsebody {object|null} [projects[].client] Client of the project (id, name), null without client` y la descripción menciona el cliente.
7. Un comentario en español junto al `include` explica por qué `attributes` va acotado a `id`/`name` (el listado no debe traer la fila completa del cliente; el detalle `GET /projects/:id` sí la trae).
8. `npm run lint --workspace @jiku/api` y `npx mocha tests/routes/projects-get.test.ts` pasan.

#### Technical Details

**Architectural Context References:**
- ADR-001: lectura directa, sin bus.
- ADR-005: `Client` desde `@jiku/models`; sin cambios de modelo.
- Convención `orm`: `attributes` explícito y `as` explícito en el `include`; patrón `reduce` del `where` intacto.
