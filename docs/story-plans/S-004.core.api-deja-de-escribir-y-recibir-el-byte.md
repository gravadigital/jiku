# Story Plan: S-004 (core) - La `api` deja de escribir y de recibir el byte

## Status

**Status:** Completed

## Story Reference

- **Story:** [S-004](../stories/S-004.api-deja-de-escribir-y-recibir-el-byte.md)
- **Service:** `core`
- **Summary:** `core` suma el comando `attachments.{id}.delete` — la **desvinculación** de un archivo
  de una entidad. Borra la fila de `attachments` y **no toca `files` ni el bucket** (D-04), que es lo
  que permite a la `api` dejar de borrar filas por su cuenta y cierra la última puerta abierta de la
  excepción 2 de ADR-001.

> **El alcance de `core` en esta story es UN comando.** El grueso de S-004 (contrato HTTP de subida,
> eliminación de `multer` y de `Attachment.create()`, mapeo de los cinco códigos nuevos a HTTP) es
> de la `api` y se planifica aparte, en `S-004.api.*`. Este plan **no** toca ninguno de esos puntos.

### Service Architecture

**La decisión que define el servicio:** la lectura y la escritura están separadas **por credenciales**.
`api` conecta con un rol sin `INSERT`/`UPDATE`/`DELETE`; `core` conecta con el usuario dueño
(`core/src/models/index.ts:11-16`). No hay forma de que la api escriba por accidente.

```
NATS ──> Consumer ──> Dispatcher ──> Command ──> base de datos
         (conexión)   (transacción)  (valida y escribe)
```

```
core/
├── src/
│   ├── index.ts              # arranque: conecta la base, arranca el consumer, maneja señales
│   ├── logger.ts             # Winston
│   ├── config.ts             # loadConfig() / getTrustedPublisherId()
│   ├── bus/
│   │   ├── consumer.ts       # conexión, suscripción con queue group, drain al cerrar
│   │   └── dispatcher.ts     # resuelve el comando, abre la transacción, responde
│   ├── commands/
│   │   ├── index.ts          # el registro único: agregar un comando es sumarlo a esta lista
│   │   ├── registry.ts       # matching por segmentos, extracción de params
│   │   ├── types.ts          # la interfaz Command y su contexto
│   │   ├── validate.ts       # validateWith (Joi) y pickPresent (edición parcial)
│   │   ├── link-files.ts     # linkFiles / syncFileLinks (S-003)
│   │   ├── resolve-actor.ts  # resolveActor (S-002, movido acá en S-003)
│   │   └── clients/ projects/ tasks/ requirements/ times/ files/
│   └── models/index.ts       # registra los modelos de @jiku/models con las credenciales del dueño
└── tests/
    ├── setup-env.ts          # levanta el PostgreSQL efímero ANTES de que Mocha cargue los tests
    ├── global-setup.ts       # crea el esquema y trunca; apaga el contenedor al final
    ├── helpers/dispatch.ts   # despacha un comando como si viniera del bus
    └── commands/             # un archivo por módulo de dominio
```

**Estructura de un archivo de comando — cinco partes, siempre en este orden:**
imports → interfaz del payload → esquema Joi → el objeto `Command` → `export default`.

Orden de imports: `joi` → `sequelize` si hace falta → `@jiku/models` → `@jiku/nats-protocol` → relativos.

**Naming:** archivos `kebab-case.ts`, con el patrón `{entidad}-{acción}.ts`. Comandos exportados en
`camelCase` que coincide con el `pattern`. Interfaces de payload: `{Comando}Payload`. Cada archivo de
comando exporta el comando **nombrado y también como `default`**; `index.ts` importa el default.

**Imports:** relativos, sin alias ni paths de `tsconfig` (`../types`, `./priority`). Los paquetes del
workspace por nombre (`@jiku/models`, `@jiku/nats-protocol`).

**Comentarios:** en **español**. Explican **el por qué**, no el qué. Lo que amerita comentario: una
decisión que parece un error y no lo es, una diferencia deliberada con lo que hacía la api, una
traducción entre contrato y base, un escape transitorio. Un comentario que marca deuda dice **cuándo
desaparece**.

**Sin capa de repositorio ni de servicio.** Un comando habla directo con los modelos y **es** la unidad
completa: valida, consulta y escribe.

**Core no sabe de roles, permisos ni usuarios finales.** El usuario que actúa viaja en el cuerpo
(`creator` / `author` / `editor`), no en el subject: el subject identifica al **service user de la
api**, no a la persona.

**Módulos actuales** (carpetas bajo `src/commands/`): `clients`, `projects`, `tasks`, `requirements`,
`times`, `files`. Esta story **crea el séptimo: `attachments`**.

**Orden dentro de `execute` — consistente en los 19 comandos:**
1. Buscar la entidad del `params` y responder `*_not_found` si no está.
2. Validar las referencias del payload y responder su código.
3. Validar las reglas de negocio.
4. Calcular lo que necesita el estado anterior.
5. **Escribir**, siempre con `{ transaction: ctx.transaction }`.
6. `success()` o `success({ id })`.

**Qué devuelve un comando:**
```ts
success({ id: client.id })   // creaciones: SOLO el id
success()                    // ediciones y borrados: nada
```

**Un comando sin payload** (los borrados no llevan cuerpo — el id viene en el subject):
```ts
validate(payload: unknown) {
  return validateWith<Record<string, never>>(
    joi.object({}).unknown(false).default({}),
    payload ?? {}
  );
}
```
`unknown(false)` rechaza cualquier campo: mandar datos a un borrado es un error del cliente, no algo
a ignorar.

### Relevant ADRs

#### ADR-003: La transacción es del despachador, nunca del comando

**Decisión:** invertir la propiedad de la transacción. La abre y la cierra el **despachador**
(`core/src/bus/dispatcher.ts:42-54`): abre, ejecuta el comando pasándole la transacción en su
contexto, hace **commit si el reply es `success`** y **rollback en cualquier otro caso**. Los comandos
reciben la transacción pero **no tienen acceso a `commit` ni a `rollback`**.

**Implementation Rules (verbatim):**

- Un comando **DEBE** recibir la transacción por su contexto y usarla en todas sus operaciones de
  base de datos. **NO DEBE** abrir una transacción propia.
- Un comando **NO DEBE** llamar a `commit()` ni a `rollback()`. Si el código de un comando los
  invoca, está mal escrito.
- Un comando **DEBE** señalar el fallo devolviendo un `Reply` con `status: 'failure'` y su
  `errorCode`. **NO DEBE** lanzar una excepción para señalar un fallo de negocio esperado.
- El despachador **DEBE** hacer commit **solo** si el reply es `success`, y rollback en todos los
  demás casos, incluidas las excepciones inesperadas.
- El despachador **NO DEBE** lanzar nunca: todo error se traduce a un `Reply` de falla.
- Los tests de comandos **DEBEN** entrar por el despachador (helper `dispatch()`), no llamando a
  `execute()` directamente: es lo único que verifica el comportamiento transaccional, incluido el
  rollback.

#### ADR-013: Tests contra base real

**Decisión:** los tests de `api` y `core` corren contra un PostgreSQL de verdad, con el esquema real.
No hay dobles de la base.

**Implementation Rules (verbatim):**

- Los tests de `api` y `core` **DEBEN** correr contra PostgreSQL real. **NO SE DEBEN** mockear los
  modelos de Sequelize.
- Los tests de comandos de `core` **DEBEN** entrar por el despachador (`dispatch()`), **NO** por
  `execute()` directamente.
- Un test de escritura de la api **DEBE** verificar las tres capas: comando publicado, traducción de
  la respuesta a HTTP, y que la fila quedó escrita. **NO SE DEBE** asertar solo el status HTTP.
- `reply()` / `failWith()` **DEBEN** usarse solo para cubrir caminos de error. El camino feliz
  **DEBE** ejecutar core de verdad.
- Cada archivo de test **DEBE** poder correr solo: el esquema y el mock de auth se preparan en
  fixtures globales de Mocha.
- `TZ=UTC` **DEBE** estar fijado en la configuración de test de todo servicio.
- La limpieza entre corridas **DEBE** ser `TRUNCATE ... RESTART IDENTITY CASCADE`, para que los ids
  autoincrementales sean predecibles.
- **NO SE DEBE** depender del orden de ejecución entre archivos de test.

#### ADR-001: Separación lectura/escritura (contexto)

La excepción 2 de ADR-001 es *la fila de `attachments` que la `api` escribe sin pasar por el bus*.
Este comando es la pieza de `core` que permite cerrarla: sin él, la `api` no tendría a quién delegar
el borrado del vínculo y seguiría escribiendo por esa puerta.

#### ADR-002: Comandos NATS sin JetStream (contexto)

Request/reply sin cola ni reintento. El timeout de la `api` es `NATS_REQUEST_TIMEOUT_MS` = **5000 ms**.
Consecuencia para este comando: **no metas llamadas de red dentro del `execute`** — la transacción del
despachador vive mientras dura el comando, y una llamada externa arriesgaría el timeout. Este comando
no las necesita: es un `DELETE` sobre una fila.

### API Context (AsyncAPI — `docs/apis/core.yaml`)

> **El contrato ya está declarado en el spec.** El canal `attachments.{id}.delete`, su mensaje y su
> reply existen en `docs/apis/core.yaml` desde el diseño del REQ. Esta story **implementa** ese
> contrato; **no** hay que redactarlo.

**Canal `attachments.{id}.delete`** (`docs/apis/core.yaml:467-497`), verbatim:

```yaml
  # -------------------------------------------------------------------------
  # attachments  (REQ-001 — S-004)
  # -------------------------------------------------------------------------

  attachments.{id}.delete:
    description: |
      Unlinks a file from an entity. **Deletes only the `attachments` row: the file is retained**
      (D-04), and so is the object in the bucket.

      With 0..N links per file, deleting the object would break the other links. Unlinking **is**
      deleting the `Attachment`.

      **Why it is a command and not a direct write.** It was the third implicit write of the api
      (row + object). If the link becomes a domain row, deleting it MUST go through core, or it
      would reopen through another door the ADR-001 exception this redesign closes.

      **The parameter is the id of `attachments`** — the link — which is the opposite of
      `files.{fileId}.request-download`. The name says so on purpose: `attachments.{id}.delete`
      is more honest than `files.{id}.unlink`.
    parameters:
      id:
        description: Link id (`attachments.id`).
        schema:
          type: string
    publish:
      operationId: attachmentsDelete
      summary: Unlink a file from an entity
      tags:
        - name: attachments
      message:
        $ref: '#/components/messages/AttachmentsDelete'
```

**Mensaje `AttachmentsDelete`** (`docs/apis/core.yaml:744-750`), verbatim:

```yaml
    AttachmentsDelete:
      name: AttachmentsDelete
      title: attachments.{id}.delete
      contentType: application/json
      payload:
        $ref: '#/components/schemas/EmptyPayload'
      x-reply:
        $ref: '#/components/schemas/ReplyEmpty'
      x-error-codes: [invalid_fields, internal_error]
```

**Formato de `Reply` (idéntico para los 19 comandos):**

```ts
export interface Reply<T = unknown> {
  status: 'success' | 'failure';
  errorCode?: string;
  errorMessage?: string;
  data?: T;
}
export function success<T>(data?: T): Reply<T>;
export function failure(errorCode: string, errorMessage: string): Reply<never>;
```

```json
{ "status": "success" }
{ "status": "failure", "errorCode": "invalid_fields", "errorMessage": "..." }
```

**`ReplyEmpty`** (`docs/apis/core.yaml`), verbatim:

```yaml
    ReplyEmpty:
      allOf:
        - $ref: '#/components/schemas/Reply'
        - type: object
          description: 'Reply with no content: the `status` is the whole reply.'
          example:
            status: success
```

**`EmptyBody` — la nota del contrato sobre los comandos sin cuerpo**, verbatim:

> The delete commands and the unsubscribe carry no body. They are validated all the same,
> with `joi.object({}).unknown(false)`, so **a payload with any field is rejected** with
> `invalid_fields`. An absent or empty body is normalized to `{}`.

**Subject completo:** `{instance}.{user-id}.gestion.v1.attachments.{id}.delete`

> #### ⚠ Discrepancia detectada entre la story y el contrato — **resuelta a favor del contrato**
>
> El texto de la story (sección "Nuevos Endpoints") dice **`Response: success({ id })`**. El spec
> `docs/apis/core.yaml` declara **`x-reply: ReplyEmpty`** (`status` y nada más).
>
> **Manda el contrato.** Lo dice la convención `commands` de este servicio, dos veces: *"El `pattern`
> de un comando tiene que coincidir con el subject de `docs/apis/core.yaml`. Ante una discrepancia,
> **manda el documento**"*. Y coincide con la regla general del servicio —*"Las creaciones devuelven
> solo `{ id }`. Las ediciones y borrados, nada"*— y con los tres borrados que ya existen
> (`requirements.{id}.subscriptors.{userId}.delete`, `worked-times.{id}.delete`,
> `unworked-times.{id}.delete`), los tres con `success()` a secas.
>
> **Se implementa `success()` sin `data`.** La `api` no necesita el id de vuelta: ya lo tiene, es el
> `{id}` de su propia URL. **Anotalo para la planificación de `S-004.api`**: el lado api no debe
> esperar `data.id` en el reply.

| Columna | Tipo | Restricciones |
|---|---|---|
| `id` | `INTEGER` | PK, autoincremental. **Preservado a través de la migración** |
| `entity_type` | `VARCHAR` | NOT NULL |

Valores de `entity_type`, **de 10 a 5**: `project`, `requirement`, `objective`,

- `paranoid: false` con `deleted_at` propio se conserva. **El borrado del vínculo es real**; el ciclo

- Las 9 columnas del archivo migraron a `files`.

#### `files` — el archivo (la tabla que este comando **NO** toca)

```
Table files {
```

> **`retention_status` vive en `files` y no en el vínculo** (D-04): con 0..N vínculos, marcar el
> archivo al desvincular rompería los otros. **Desvincular es borrar la fila de `attachments`.**

#### Migraciones

**Ninguna.** El esquema lo dejó listo S-001 (las cinco migraciones `20260819_01..05` viven en
`api/db-upgrade/migrations/`, la `api` es la dueña del esquema por ADR-001). **`core` no ejecuta
migraciones.** Esta story no agrega columnas.

#### El modelo `Attachment` (`packages/models/src/attachment.model.ts`) — dos trampas

**1. El hook `@BeforeDestroy` lanza si no le pasás `force: true`:**

```ts
@BeforeDestroy
static softDeleteHook(_attachment: Attachment, options: any) {
  if (!options.force) {
    throw new Error(
      'Physical deletion is not allowed. Use attachment.softDelete() instead.'
    );
  }
}
```

Sin `force: true` el `destroy` lanza, el despachador lo captura y responde **`internal_error`** — un
síntoma que no apunta a la causa.

**2. `softDelete()` NO sirve para este comando:**

```ts
async softDelete(deletedByUserId?, options?) {
  await this.update({
    retentionStatus: RetentionStatus.ScheduledForDeletion,
    deletedAt: new Date(),
    deletedBy: deletedByUserId || null,
  }, options);
}
```

Escribe `retention_status` sobre `attachments`, columna que **la migración `20260819_05` ya dropeó**.
Funcionaría en los tests —donde `sequelize.sync()` recrea la columna desde el modelo (ADR-013)— y
**fallaría en producción**. `syncFileLinks` (S-003) ya documenta exactamente esta trampa y usa
`destroy({ force: true })`. **Hacé lo mismo.**

**3. `@DefaultScope` excluye `checksum`.** Irrelevante para un `destroy`, pero relevante si hacés un
`findByPk` previo: los atributos vienen sin `checksum`.

### Flow Context

Flujo afectado: **`vinculacion-de-archivos`** (`docs/flows/vinculacion-de-archivos.md`), **Paso 6**,
hoy marcado explícitamente como PENDIENTE (S-004). Esta story lo implementa del lado `core`.

**Paso 6 del flujo, verbatim:**

> ### Paso 6: Desvinculación — PENDIENTE (S-004)
>
> > **Todavía no implementado.** El comando `attachments.{id}.delete` **no existe** al cerrar S-003:
> > lo crea **S-004**, que es la story a la que la tabla "Servicios Afectados" se lo asigna. Lo que
> > sigue es el diseño acordado, no una descripción de lo que ya corre.
> >
> > Hasta que S-004 lo implemente, la única forma de desvincular es mandando el conjunto completo
> > por `requirements.{id}.edit` o `tasks.{id}.edit` sin el `fileId` que se quiere sacar — eso sí
> > funciona hoy, y borra la fila de `attachments` sin tocar el `File`.
>
> **Origen:** navegador → `api` → `core`
> **Tipo:** REST + Evento
>
> 1. **[navegador]** `DELETE /api/attachments/{id}` — el id es el del **vínculo**
> 2. **[`api`]** Autoriza sobre la **entidad** del vínculo. Si falla, **403 sin publicar**
> 3. **[`api`]** Publica `{instance}.{api-service-user}.gestion.v1.attachments.{id}.delete`
>    - **Parámetro `{id}`:** el id de **`attachments`** — el vínculo, no el archivo. El nombre es
>      deliberado: `attachments.{id}.delete` es más honesto que `files.{id}.unlink`, porque su
>      parámetro es el id del vínculo, **al revés que el comando de descarga**
>    - **Request:** sin payload propio más allá de los campos de auditoría del comando
> 4. **[`core`]** Borra la fila de `attachments`. **No toca `files` ni el bucket**
>    - **Reply:** `success({ id })`
>    - **Errores:** `invalid_fields` (vínculo inexistente), `internal_error`
> 5. **[`api`]** Traduce el reply y responde
>
> > **Es un cambio de comportamiento observable.** Hoy `DELETE /api/attachments/{id}` *"borra la fila
> > y el objeto del bucket"*. Ahora **borra solo el vínculo; el archivo se retiene** (D-04, CA-9). Con
> > 0..N vínculos, borrar el objeto rompería los otros.
>
> > **Es la tercera escritura implícita de la `api`, y también se convierte en comando.** Dejarla
> > afuera dejaría a la `api` escribiendo `attachments` por otra puerta, reabriendo la excepción que
> > este rediseño cierra.

**Diagrama del tramo de desvinculación, verbatim del flujo:**

```mermaid
    Note over B,DB: --- desvinculación ---
    B->>A: DELETE /api/attachments/{id}
    A->>A: autoriza sobre la entidad del vínculo
    A->>N: publica attachments.{id}.delete
    N->>C: entrega el comando
    C->>DB: DELETE de la fila de attachments (NO toca files ni el bucket)
    C-->>N: success { id }
    N-->>A: reply
    A-->>B: respuesta
```

**Qué modifica esta story en el flujo:** implementa el punto 4 (lado `core`). El punto 2 (autorización
sobre la entidad) y el 5 (traducción a HTTP) son de `S-004.api`. Una vez cerrados los dos lados, el
flujo puede pasar de `Draft` a `Active`.

> **Nota de mantenimiento del doc de flujo (fuera del código):** el Paso 6 declara `success({ id })`,
> igual que la story. Ver la discrepancia resuelta en *API Context*: el contrato manda y el reply es
> vacío. Cuando `S-004.api` cierre, conviene actualizar el flujo (vía
> `/product-change-technical-definition`) para que diga `success()`.

### Integration Points

- **NATS** — único canal de entrada. `core` se suscribe a `{instance}.*.{svc}.{version}.>` con queue
  group `gestion`. **No publica nada.** Este comando no agrega integraciones nuevas.
- **S3 / storage** — **NO se toca en este comando.** Es la garantía central de CA-8/CA-9: el objeto
  del bucket se conserva. No importes `getStorageSigner()` ni nada de `commands/files/storage.ts`.
- **PostgreSQL** — un solo `DELETE`, dentro de la transacción del despachador.

### Reusable Code

Del catálogo `docs/reusable-code/core/`, lo relevante para esta story:

#### `validateWith` — `core/src/commands/validate.ts`

Valida el payload contra un esquema Joi con `{ convert: true, abortEarly: true }` y devuelve
`{ value }` o `{ error: Reply }` con `invalid_fields`.

```ts
export function validateWith<T>(
  schema: joi.Schema,
  payload: unknown
): { value: T } | { error: Reply<never> }
```

#### `dispatch()` — `core/tests/helpers/dispatch.ts` (test helper)

Despacha un comando como si hubiera llegado por el bus, armando el subject completo. **Es la única
forma permitida de invocar un comando desde un test** (ADR-013).

```ts
export function dispatch<T = unknown>(
  command: string,
  payload: unknown,
  caller = 'api'
): Promise<Reply<T>>
```

```ts
const reply = await dispatch(`attachments.${link.id}.delete`, {});
```

## Tasks

### Task 1: Comando `attachments.{id}.delete` — el módulo `attachments` de `core`

**Status:** Completed

#### Description

Crear el séptimo módulo de dominio de `core` (`src/commands/attachments/`) con su único comando: la
desvinculación de un archivo de una entidad.

El comando recibe el id de **`attachments`** (el vínculo) en el subject, sin cuerpo, y borra esa fila.
**No toca `files` ni el bucket.** Es lo que permite a la `api` dejar de borrar la fila y el objeto por
su cuenta, cerrando la última puerta abierta de la excepción 2 de ADR-001 (CA-9).

El contrato ya está declarado en `docs/apis/core.yaml` (canal `attachments.{id}.delete`, mensaje
`AttachmentsDelete`, reply `ReplyEmpty`, códigos `[invalid_fields, internal_error]`): esta tarea lo
implementa, no lo redacta.

**Por qué el archivo se conserva:** un `File` tiene 0..N vínculos (D-04). Borrar el objeto del bucket
al desvincular rompería los otros vínculos que apunten al mismo archivo. El ciclo de retención del
archivo vive en `files.retention_status`, no en el vínculo.

#### Acceptance Criteria

1. Existe `core/src/commands/attachments/attachments-delete.ts` que exporta `attachmentsDelete`
   nombrado **y** como `default`.
2. `attachmentsDelete.pattern === 'attachments.{id}.delete'`, idéntico al subject de
   `docs/apis/core.yaml`.
3. El comando está registrado en `core/src/commands/index.ts` — despachar
   `attachments.{id}.delete` no responde `unknown_command`.
4. `validate` usa `validateWith<Record<string, never>>(joi.object({}).unknown(false).default({}), payload ?? {})`:
   un payload ausente o `{}` se acepta; un payload **con cualquier campo** se rechaza con
   `invalid_fields`.
5. `execute` valida que `ctx.params.id` sea un **entero positivo** antes de consultar; si no lo es,
   responde `failure(ErrorCode.INVALID_FIELDS, ...)` — **nunca** `internal_error`.
6. `execute` borra la fila con `Attachment.destroy({ where: { id }, force: true, transaction: ctx.transaction })`.
   El `force: true` es obligatorio (hook `@BeforeDestroy`) y `softDelete()` **no** se usa.
7. Si el `destroy` afectó 0 filas, responde `failure(ErrorCode.INVALID_FIELDS, ...)` con mensaje en
   español que **no incluye el id** ni ningún dato interno.
8. En el camino feliz responde `success()` **sin `data`**, conforme a `ReplyEmpty` del contrato.
9. El comando **no escribe ni lee** `files`: no importa el modelo `File`, ni `getStorageSigner`, ni
   nada de `commands/files/`.
10. El comando **no abre ni cierra transacción**, no llama a `commit()` ni `rollback()`, y no lanza
    para señalar un fallo esperado (ADR-003).
11. Compila con `strict: true` sin warnings de `noUnusedLocals` / `noUnusedParameters` /
    `noImplicitReturns`.

#### Technical Details

**Architectural Context References:**

- **ADR-003** (Architectural Context → Relevant ADRs): la transacción es del despachador. Toda
  operación lleva `{ transaction: ctx.transaction }`; el comando no la abre ni la cierra y señala el
  fallo con `Reply`, nunca lanzando.
- **Convención `commands`** (Service Architecture): anatomía de cinco partes, el patrón de "comando sin

- **Convención `validation`**: `validateWith` con `unknown(false)`; `validate` **no toca la base**.
- **Convención `error-handling`**: `failure(ErrorCode.X, 'mensaje')` con la **constante**; mensajes

- **Convención `orm`**: `{ transaction: ctx.transaction }` sin excepción; sin capa de repositorio.

**Implementation Notes:**

**Forma esperada del archivo** (cinco partes, en orden):

```ts
import joi from 'joi';
import { Attachment } from '@jiku/models';
import { ErrorCode, Reply, failure, success } from '@jiku/nats-protocol';
import { Command, CommandContext } from '../types';
import { validateWith } from '../validate';

/**
 * Desvincula un archivo de una entidad: borra la fila de `attachments`.
 *
 * NO TOCA `files` NI EL BUCKET (D-04, CA-8). Un `File` tiene 0..N vínculos, así que borrar el
 * objeto al desvincular rompería los otros. El ciclo de retención del ARCHIVO vive en
 * `files.retention_status`; el del VÍNCULO no existe: desvincular es borrar la fila.
 *
 * ES UN COMANDO Y NO UNA ESCRITURA DIRECTA DE LA API porque era su tercera escritura implícita
 * (fila + objeto). Dejarla afuera reabriría por otra puerta la excepción 2 de ADR-001 que este
 * rediseño cierra (CA-9).
 *
 * EL PARÁMETRO ES EL ID DE `attachments` —el vínculo—, al revés que
 * `files.{fileId}.request-download`, cuyo parámetro es el id del archivo. El nombre del comando
 * lo dice a propósito: `attachments.{id}.delete` es más honesto que `files.{id}.unlink`.
 */
export const attachmentsDelete: Command<Record<string, never>, void> = {
  pattern: 'attachments.{id}.delete',

  validate(payload: unknown) {
    // Un borrado no lleva cuerpo: el id viene en el subject. `unknown(false)` rechaza cualquier
    // campo —mandar datos a un borrado es un error del cliente, no algo a ignorar—.
    return validateWith<Record<string, never>>(
      joi.object({}).unknown(false).default({}),
      payload ?? {}
    );
  },

  async execute(_payload, ctx: CommandContext): Promise<Reply<void>> {
    // `ctx.params.id` llega SIEMPRE como string: el registry extrae segmentos del subject. Se
    // valida que sea entero ANTES de consultar porque un valor no numérico haría que PostgreSQL
    // lance por tipo inválido, y el despachador lo traduciría a `internal_error` — que es
    // justo lo que este comando no debe responder ante un id mal formado.
    const id = Number(ctx.params.id);
    if (!Number.isInteger(id) || id <= 0) {
      return failure(ErrorCode.INVALID_FIELDS, 'El identificador del vínculo no es válido');
    }

    // DELETE REAL, no `softDelete()`. `softDelete()` escribe `retentionStatus` y `deletedAt`
    // sobre `attachments`, columnas que la migración 20260819_05 YA DROPEÓ: el ciclo de
    // retención vive ahora en `files.retention_status`. Usarlo funcionaría en los tests —donde
    // `sequelize.sync()` recrea las columnas desde el modelo (ADR-013)— y fallaría en
    // producción. Es la misma trampa que `link-files.ts` ya documenta.
    //
    // `force: true` es obligatorio: el hook `@BeforeDestroy` del modelo lanza sin él.
    const deleted = await Attachment.destroy({
      where: { id },
      force: true,
      transaction: ctx.transaction,
    });

    if (deleted === 0) {
      // `invalid_fields` y no un `*_not_found` propio: es el código que el contrato declara
      // para este comando (`x-error-codes: [invalid_fields, internal_error]`). Agregar
      // `attachment_not_found` obligaría a tocar el paquete, el YAML y el mapa a HTTP de la
      // api — los tres, o el usuario ve un 500 (convención `error-handling`).
      //
      // El mensaje NO lleva el id: la convención prohíbe datos internos en el texto de error.
      return failure(ErrorCode.INVALID_FIELDS, 'El vínculo no existe');
    }

    // SIN `data`. El contrato declara `ReplyEmpty` y la convención `commands` lo dice para todo
    // borrado: "las ediciones y borrados, nada". La api ya tiene el id — es el de su propia URL.
    return success();
  },
};

export default attachmentsDelete;
```

**Cuatro decisiones que hay que respetar, con su por qué:**

1. **`invalid_fields` y no un código nuevo `attachment_not_found`.** El contrato ya cerró la lista en
   `[invalid_fields, internal_error]`. Un código nuevo exige tres cambios sincronizados (el paquete
   `@jiku/nats-protocol`, `docs/apis/core.yaml`, y el mapa a HTTP de `api/lib/utils/bus/protocol.ts`),
   y si alguno falta el usuario ve un **500 genérico**. No es una mejora que quepa en esta story.
2. **`success()` sin `data`.** Ver *API Context → Discrepancia resuelta*. Manda el contrato.
3. **No se resuelve actor.** `resolveActor` existe para poblar `uploaded_by` (subida) y para validar
   titularidad (vinculación). Acá **no hay a quién atribuirle nada**: la fila se borra de verdad, no se
   marca con `deletedBy`, y la titularidad de la desvinculación es una regla de la `api` (autoriza
   sobre la **entidad** del vínculo, no sobre quién subió el archivo). Importar `resolveActor` acá
   confundiría dos reglas distintas.
4. **No se valida `entity_type` ni existencia de la entidad.** El vínculo se borra por su id; si
   existe, se borra. `core` no conoce las cinco tablas polimórficas y la FK hacia la entidad es
   imposible por diseño (D-05).

**Qué NO hacer:**

- **No borres ni marques el `File`.** Ni `File.destroy`, ni `retentionStatus`, ni `byteStatus`. Es la
  garantía central de CA-8.
- **No llames al firmador de S3.** El objeto del bucket se conserva. No importes nada de
  `commands/files/storage.ts`.
- **No uses `attachment.softDelete()`.** Ver el comentario del código.
- **No hagas un `findByPk` previo "para validar que existe"** y después el `destroy`. El `destroy`
  devuelve la cantidad de filas afectadas: dos queries donde alcanza una, dentro de una transacción
  que el timeout de 5 s de ADR-002 acota. Es el patrón que ya usan los tres borrados existentes.
- **No refactorices `link-files.ts`** para compartir el `destroy`. Ver *Reusable Code → syncFileLinks*.

**Fuera del alcance de esta tarea (y por qué):**

- **El bloque transitorio de `link-files.ts`** (`markUploadedAndLink`, las siete columnas copiadas del
  `File`) dice *"TRANSITORIO HASTA S-004/S-005 — ESTE BLOQUE SE BORRA ENTERO CUANDO LLEGUEN"*.
  **No se borra en esta story.** Su condición real es que ninguna ruta de la `api` lea esas columnas,
  y `attachments-preview` / `attachments-download` las siguen leyendo hasta **S-005**. Borrarlo ahora
  rompería `api` en producción. La misma lógica aplica a aflojar las columnas del modelo `Attachment`
  en `@jiku/models`, que además es compartido (ADR-005).

### Task 2: Tests del comando `attachments.{id}.delete`

**Status:** Completed

#### Description

Cubrir el comando nuevo con los 15 test scenarios de este plan, en un archivo propio del módulo
(`core/tests/commands/attachments.test.ts`), entrando siempre por `dispatch()`.

La convención del servicio es explícita: *"Un comando nuevo son tres pasos: el archivo, el registro en
`commands/index.ts`, y sus tests. **Los tres o ninguno**"*. Esta tarea es el tercer paso.

El foco de la cobertura no es el `DELETE` en sí —que es trivial— sino **las tres garantías que hacen
al CA**: que el archivo sobreviva, que los otros vínculos del mismo archivo sobrevivan, y que el
borrado sea **duro** (no un soft delete disfrazado), porque de eso depende que una lectura posterior

**Puntos donde el test se puede escribir mal y pasar igual:**

- **TS-4 debe leer con `{ paranoid: false }`.** El modelo es `paranoid: false`, así que un
  `findByPk` normal ya no filtra nada — pero si alguien "arregla" el comando usando `softDelete()`,
  un `findByPk` a secas seguiría devolviendo la fila y el test fallaría correctamente, mientras que
  un test que solo asertara el `status: 'success'` pasaría. **Aserta sobre la fila, no sobre el reply.**
- **TS-3 necesita dos vínculos sobre el MISMO `File`.** Con `makeLink` copiando `storageKey` del
  archivo, y como S-003 le quitó el `unique: true` a `attachments.storage_key` justamente por esto,
  los dos vínculos conviven. Si el `create` del segundo falla por unicidad, el modelo se desincronizó:
  revisá `packages/models/src/attachment.model.ts` antes de tocar el test.
- **TS-11 debe asertar `count()` sobre las dos tablas**, no solo que el reply falló. El punto del
  escenario es el rollback del despachador, no el código de error.
- **TS-14: `installS3Double()` en `beforeEach` y `uninstallS3Double()` en `afterEach`.** Sin el
  uninstall, el doble se filtra a los archivos de test que corran después.
- **TS-15 usa el tercer parámetro de `dispatch()`** (`caller`). El default es `'api'`, que **no**
  coincide con `CORE_TRUSTED_PUBLISHER_ID` de `.env.test` (`'api-service-user-sub'`) — es deliberado
  en este codebase. Como este comando no resuelve actor, los dos callers dan el mismo resultado, y
