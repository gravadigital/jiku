# Story Plan: S-095 (web) - web: buscador de Documentación sin carpetas

## Status

**Status:** Completed

## Story Reference

- **Story:** [S-095](../stories/S-095.web-buscador-de-documentacion-sin-carpetas.md)
- **Service:** `web`
- **Origen:** [REQ-021](../requests/REQ-021.documentacion-sin-carpetas-en-la-web.md)
- **Summary:** `/docs` deja de navegar por carpetas y pasa a ser **una sola pantalla con estados**
  (inicio, sugerencias abiertas, resultados, filtrado desde una ficha, sin proyecto) gobernada por la
  URL: un buscador con tokens (proyecto, cliente, tema, persona, requisito, tarea, texto, "Sin
  proyecto/cliente/tema") con sugerencias agrupadas y teclado, `ToggleGroup` "Todos / Visibles para el
  cliente", orden, resultados con conteo y paginado, y "Asignar proyecto" / "Asignar sugerido" en la
  vista "Sin proyecto". Se da de baja la navegación por carpetas (`DocsBrowser`, `FolderBreadcrumb`,
  hooks y servicios de carpetas).

> **Precondición verificada sobre el árbol (2026-10-26, rama `feature/S-094_rutas-docs-jiku-docs-1-3-0`):**
> - **S-094 (prerrequisito) está `Completed`** y mergeado: la api ya expone `GET /docs/documents` con

### Fuera de alcance (declarado, para no improvisarlo)

- **`access.changed` / tiempo real:** la web no recibe eventos de docs; no se agrega canal.
- **⌘K, vistas guardadas, sidebar, barra superior:** no se tocan (decisiones 1 a 3 del dueño).
- **"Ver todos" en los grupos de inicio:** descartado por la UX (no hay token que los represente).
- **Precargar relaciones en "Nuevo documento"** cuando el diálogo de S-097 todavía no existe (Task 8).
- **Búsqueda de temas por subcadena:** el contrato solo ofrece prefijo; se anota en
  `documentation/known-limitations.md` (Task 9).

### Convenciones activas que aplican (extracto)

**`_base` (Next.js):** TypeScript strict, sin `any` salvo bordes; Server Components por defecto (los
componentes con estado llevan `'use client'`); el token nunca en el cliente; imports absolutos `@/…`;
comentarios solo del **porqué**.

**`data-fetching` (custom):**
- Tres capas: componente cliente → hook `useQuery` → Server Action `'use server'` → `apiClient`.
  "Ninguna capa se saltea desde un componente cliente."
- Server Action con tipo de retorno explícito; devuelve `response.data`, nunca la respuesta de axios.
- **`features/docs/` usa `DocsResult`**: sus Server Actions no lanzan, devuelven
  `{ ok: true; data } | { ok: false; error }` (`toResult`) y los hooks re-lanzan con `unwrap`.
- Hooks: un objeto `options` con defaults, `enabled` siempre expuesto, el hook no transforma datos.
- Query keys: plural para colección, filtros como segundo elemento. La story fija las keys del
  módulo con prefijo `['docs', …]`: `['docs','documents',params]`, `['docs','search',…]`,
  `['docs','suggestions',q,clientId]`, `['docs','suggested-relations',id]`.
- Cache global: `staleTime: 30_000`, `retry: 1`; mutations `retry: 0`. "No poner `staleTime` por query
  sin motivo escrito" → el `staleTime` de 5 min de `suggested-relations` lleva su motivo (REQ-021
  Riesgos: N consultas por página).

**`state-management` (custom):**
- "Los filtros, el orden, la página y el tamaño de página van en la URL." Partir de los params
  actuales; **al cambiar cualquier filtro, resetear la página a 1**.
- No copiar datos de query a `useState`. Estado local solo para lo efímero (texto del campo, lista
  abierta, índice activo, fila en "asignando").
- La story fija `router.replace(...)` para escribir la URL del buscador (Flujo de Interacción, paso 2).

**`mutations` (custom):** invalidar en `onSuccess` **del hook**; el hook no navega ni muestra toasts
(eso es del componente); `retry: 0`; `isPending` alimenta `loading`/`disabled`. En `features/docs/`,
`module_unavailable` invalida `['modules']` (`withModuleInvalidation`).

**`styling` (custom, ADR-010):** Sass + CSS Modules por componente (`{Nombre}.module.scss`,
`@use '@/styles' as *;`), custom properties del DS (`var(--space-*)`, `var(--space-grid-gap)`), sin
librería de componentes. Viewport único desktop: grilla de 12 columnas **sin `@media`** (mismo patrón
que `DocsBrowser.module.scss`: `.header { display: grid; grid-template-columns: repeat(12, minmax(0, 1fr)); gap: var(--space-grid-gap); }`).

**`error-handling` (custom):** avisos inline de docs con `DocsNotice` (gap `alert` aceptado), toasts
con `react-toastify` (`toast.success/warning/error`), mensaje por `code` en un util del módulo.

**`testing-unit` (custom):** tests junto al archivo (`{Nombre}.test.tsx`, se pueden partir por tema:
`DocsSearchBar.keyboard.test.tsx`); mockear **hooks** al testear componentes y **services** al testear
hooks; `vi.mock('@/lib/axios')` al testear Server Actions (patrón de `docsApi.test.ts`); mockear
`next/navigation` (`useRouter`, `useSearchParams`) cuando el componente navega; nombres en español;
`getByRole` antes que `data-testid`; `userEvent`; `queryBy*` para ausencia; `vi.useFakeTimers()` +
`advanceTimersByTime(200)` para el debounce. Comandos: `npm test --workspace web`,
`npm run lint --workspace web`, `npm run build --workspace web`.

### Relevant ADRs

- **ADR-009: Token confinado al servidor.** El navegador nunca llama a la api: todo pasa por Server
  Actions (`'use server'`) con `apiClient`. Ningún hook nuevo importa `apiClient`.
- **ADR-010: Sass + CSS Modules sin librería.** Estilos por CSS Modules sobre tokens del DS; nada de
  librerías de UI ni de combobox (el `DocsSearchBar` se arma a mano).
- **ADR-011: TanStack Query.** Único cache de datos de servidor; invalidación por query key.
- **ADR-015: Módulos opcionales del bus** (DD-2: la api no autoriza el dominio; DD-7: el `code` de
  jiku-docs llega sin traducir). La web decide textos por `code` y el servicio sigue siendo la
  autoridad. Con `not_installed` la ruta hace `notFound()`; con `unavailable` se muestra el aviso y se
  re-sondea `GET /modules` cada 60 s.

### API Context

Todas las rutas son de la api (`{API_URL}/api`), las llama una Server Action con el Bearer de la
sesión. Cadena en la api: `requireModule('docs') → hasAnyRole(['admin','user']) → Joi`. Un parámetro
no declarado → `400 invalid_fields` (por eso `definedOnly`). Errores comunes:
`404 module_not_installed`, `503 module_unavailable`, `504 gateway_timeout`, `400 invalid_fields`.
Cuerpo de error: `{ code, message, details? }` → normalizado por el interceptor a
`ApiError { code, message, status, details? }` y por `toResult` a `DocsError`.

**`GET /docs/documents`** — query:

| Param | Tipo | Nota |
|---|---|---|
| `projectId` | entero, repetido (≤ 20) | O dentro del tipo; excluyente con `myActiveProjects` (400) |
| `requirementId` / `taskId` | entero | uno solo |
| `clientId` | entero, repetido (≤ 20) | |
| `topic` | string, repetido (≤ 20) | |
| `hasProject` / `hasClient` / `hasTopic` | boolean | `false` = sin proyecto/cliente/tema |
| `person` | string `sub`, repetido (≤ 10) | "creado por o último editor" |
| `visibility` | `internal` \| `public` \| `restricted` | el toggle manda `public` |
| `myActiveProjects` | boolean | sin proyectos → `{ items: [], page: { limit, returned: 0 } }` sin bus |
| `count` | boolean | `true` → `page.total` |
| `sort` | `updatedAt`,`-updatedAt`,`createdAt`,`-createdAt`,`title`,`-title`,`path`,`-path` | default `-updatedAt` |
| `limit` | 1..200 (default 50) | la web usa 20 (y 5 para "mis proyectos activos") |
| `cursor` | string ≤ 500 | `page.cursor` anterior; su ausencia es el fin |

Response `200 DocsDocumentPage`:
```json
{
  "items": [{
    "id": "01J9Z3K8M2Q4R6T8V0W2Y4A6C8", "title": "Arquitectura de videoconferencia", "version": 6,
    "visibility": "internal", "updatedAt": "2026-10-24T14:30:00.000Z",
    "updatedBy": "sub-ana", "updatedByName": "Ana Pérez",
    "createdBy": "sub-ana", "createdByName": "Ana Pérez",
    "clients": [4], "projects": [12], "projectMatch": "direct",
    "clientRefs": [{ "id": 4, "name": "EXO" }],
    "projectRefs": [{ "id": 12, "name": "Videoconferencia", "code": "VID", "clientId": 4 }],
    "topics": ["video", "arquitectura"],
    "lock": null
  }],
  "page": { "limit": 20, "returned": 1, "cursor": "c1", "total": 45 }
}
```
`lock` (con `include: ['lock','topics']`, que fija la api): `{ sessionId, holder, holderName: string|null, via: 'human'|'agent', expiresAt }`.
`DocsClientRef { id: integer; name: string|null }`, `DocsProjectRef { id; name|null; code|null; clientId|null }`
(un id desconocido llega con `name` `null` → la web muestra `#id`; el orden es el de `clients`/`projects`,
el primero es el principal). `projectMatch: 'direct'|'indirect'` solo con `projectId` en el filtro.

**`GET /docs/search`** — `q` (2..1000, requerido), `projectId`/`clientId`/`topic` (listas),
`requirementId`, `taskId`, `hasProject`/`hasClient`/`hasTopic`, `person`, `visibility`, `limit` (1..50,
default 20). **Sin `cursor`, `count`, `sort` ni `myActiveProjects`.** Response `200 { items: DocsSearchHit[] }`:
```json
{ "items": [{
  "documentId": "01J9Z3K8M2Q4R6T8V0W2Y4A6C8", "version": 6, "title": "Arquitectura de videoconferencia",
  "path": "/clientes/exo/videoconferencia/arquitectura.md", "headingPath": ["Contexto"],
  "snippet": "…la <b>arquitectura</b> del servicio de video…", "score": 0.91,
  "updatedAt": "2026-10-24T14:30:00.000Z", "updatedBy": "sub-ana", "updatedByName": "Ana Pérez",
  "createdBy": "sub-ana", "createdByName": "Ana Pérez", "visibility": "internal",
  "clients": [4], "projects": [12], "projectMatch": "direct",
  "clientRefs": [{ "id": 4, "name": "EXO" }],
  "projectRefs": [{ "id": 12, "name": "Videoconferencia", "code": "VID", "clientId": 4 }]
}] }
```
(El hit **no trae `topics` ni `lock`**. `path` llega pero la web **no lo muestra**.)

**`GET /docs/suggestions`** — `q` (1..100, requerido; la api hace trim), `clientId` (entero, limita solo
proyectos), `limit` (1..10 por grupo, default 5). Response `200 DocsSearchSuggestions`:
```json
{
  "projects": [{ "id": 12, "name": "Videoconferencia", "code": "VID", "clientId": 4, "clientName": "EXO", "mine": true }],
  "clients":  [{ "id": 4, "name": "EXO" }],
  "persons":  [{ "userId": "sub-ana", "name": "Ana Pérez" }],
  "topics":   [{ "topic": "video", "documents": 7 }]
}
```
Proyectos: los míos (`mine: true`) primero, después `activo`, después el resto. Temas solo por
**prefijo**. "Buscar «q»" y "Sin proyecto / Sin cliente / Sin tema" los arma la web. Si `topics.list`
falla, responde el error del módulo (sin sugerencias parciales).

**`GET /docs/documents/{id}/suggested-relations`** — sin query. Response `200 DocsRelationSuggestions`:
```json
{ "items": [{ "projectId": 12, "clientId": 4, "score": 0.82, "reason": "Menciona «Videoconferencia» 4 veces",
              "projectName": "Videoconferencia", "projectCode": "VID", "clientName": "EXO" }] }
```
`projectId` puede ser `null` (candidato solo de cliente). Id mal formado → 404 sin bus.

**`POST /docs/documents/{id}/relations`** — body (`additionalProperties: false`, `required: [baseVersion]`,
al menos `add` o `remove`):
```json
{ "baseVersion": 3, "add": { "projects": [12] } }
```
`DocsRelationSet { clients?, projects?, requirements?, tasks?: integer[] (≤ 100, ≥ 1) }`; `sessionId`
opcional (ULID, solo si quien asigna tiene el lock — la web no lo manda). Response
`200 DocsRelationsResult { id, version, relations: { clients, projects, requirements, tasks }, warnings? }`.
Errores: `409 version_conflict` (`details.currentVersion`), `409 document_locked`
(`details.holder`, `holderName`, `via`, `expiresAt`), `400 invalid_relation` / `invalid_fields` /
`frontmatter_invalid`, `403 permission_denied`, `404 document_not_found`. jiku-docs reescribe **solo
el bloque `jiku:`** del frontmatter, agrega el cliente del proyecto y crea una versión con mensaje
automático (el contenido no cambia fuera de `jiku:`).

**Lecturas existentes para nombres de tokens (CA-11)** — ya consumidas por la web, sin cambios:
`GET /projects/{id}` (`useProject` → `Project.name`), `GET /clients/{id}` (`useClient` → `name`),
`GET /persons` (`usePersons` → `{ userId, firstName, lastName }[]`), `GET /requirements/{reqid}`
(`useRequirement(reqid)` → `title`), `GET /objectives/{id}` (`useObjective` → `title`),
`GET /projects` (`useProjects()` → `Project[]` con `id`, `code`, `name`, `client?: { id, name }`) para
`ProjectPicker`, `GET /modules` (`useModule('docs')`).

### Database Context

Sin cambios de base de datos (la web no tiene base). Los nombres de cliente/proyecto que muestra la
pantalla los resuelve la api desde `clients`/`projects` (S-094); "mis proyectos activos" sale de
`projects_persons` ⋈ `people.user_id = sub` con `projects.status = 'activo'`.

### Flow Context

**`buscador-de-documentacion`** (flujo nuevo; esta story es su lado web). Pasos, verbatim:

1. **Sugerencias mientras se escribe** — `GET /api/docs/suggestions?q=vid&clientId=4&limit=5`. "Primero la
   base, después el bus." Response `200 { projects, clients, persons, topics }`.
2. **Resultados filtrados** — `GET /api/docs/documents` con `projectId`/`clientId`/`topic` (listas),
   `hasProject`, `hasClient`, `hasTopic`, `person`, `visibility`, `myActiveProjects`, `count`. "Mismo tipo
   repetido = O, tipos distintos = Y." `GET /api/docs/search` acepta los mismos filtros.
3. **Asignar un proyecto** — `GET .../suggested-relations` trae los candidatos con nombres; "Asignar" hace
   `POST .../relations` con `baseVersion: item.version`. jiku-docs agrega el cliente del proyecto y crea
   una versión.

Manejo de errores del flujo (verbatim): módulo no instalado 404 → "La web oculta la documentación";
503 → "Reconsulta"; 504 → "En 'Asignar' pudo haberse aplicado: se refresca"; 409 `version_conflict` →
"Se refresca el documento"; 409 `document_locked` → "Muestra quién lo edita"; 400 `invalid_relation` →
"Mensaje en la fila"; 403 `permission_denied` → "Aviso".

Escenario web de la story (verbatim):
1. **[web — `DocsSearchBar`]** Server Action `getDocsSuggestions`, debounce 200 ms, key
   `['docs','suggestions',q,clientId]` → `GET /api/docs/suggestions?q=vid&clientId=4`.
2. **[web]** muestra "Buscar «vid»…" y los grupos con resaltado; Enter sobre un proyecto →
   `router.replace('/docs?cliente=4&proyecto=12')`.
3. **[web → api]** `GET /api/docs/documents?clientId=4&projectId=12&sort=-updatedAt&limit=20&count=true`.
- "Asignar": `GET /api/docs/documents?hasProject=false&limit=20&count=true` y, por fila,
  `GET .../suggested-relations` → `POST /api/docs/documents/{id}/relations { baseVersion: item.version, add: { projects: [12] } }`
  → invalida `['docs','documents',…]`; el documento sale de la lista. 409 `version_conflict` → toast
  "El documento cambió; se actualizó la fila" y refetch; 409 `document_locked` → toast con
  `details.holderName`; 400 `invalid_relation` → toast de proyecto inválido.

**`documentos-desde-la-web`** (modificado por REQ-021): el panel de carpetas de `/docs` se reemplaza por
el buscador; la web deja de usar `GET /docs/folders`, `GET /docs/folders/{id}`, `folderId` y `pathPrefix`
(se conservan en la api "sin uso en la interfaz"). El resto del flujo (visor, edición, adjuntos) es de
S-096/S-097.

### Diseño del estado en la URL (decisiones de este plan sobre la story)

**Params** (story): `proyecto`, `cliente`, `tema`, `persona`, `q`, `requisito`, `tarea` (repetibles),
`sinProyecto=1`, `sinCliente=1`, `sinTema=1`, `publico=1`, `orden`, `pagina`, `origen=proyecto|requisito|tarea`.

```ts
// utils/docsSearchParams.ts
export type DocsToken =
  | { kind: 'proyecto'; id: number }
  | { kind: 'cliente'; id: number }
  | { kind: 'tema'; value: string }
  | { kind: 'persona'; sub: string }
  | { kind: 'requisito'; id: number }
  | { kind: 'tarea'; id: number }
  | { kind: 'texto'; value: string }
  | { kind: 'sinProyecto' } | { kind: 'sinCliente' } | { kind: 'sinTema' };

export type DocsOrder = 'recientes' | 'az' | 'relevancia';
export type DocsOrigin = 'proyecto' | 'requisito' | 'tarea';

export interface DocsSearchState {
  tokens: DocsToken[];          // en el orden de la URL (Backspace quita el último)
  publico: boolean;
  orden: DocsOrder;             // ya normalizado al modo (ver abajo)
  pagina: number;               // >= 1
  origen: DocsOrigin | null;
}

export function parseDocsSearch(params: URLSearchParams): DocsSearchState;
export function serializeDocsSearch(state: DocsSearchState): string;   // sin '?' ; '' si vacío
export function addToken(state: DocsSearchState, token: DocsToken): DocsSearchState;
export function removeTokenAt(state: DocsSearchState, index: number): DocsSearchState;
export function viewOf(state: DocsSearchState): {
  mode: 'inicio' | 'listado' | 'texto';
  sinProyecto: boolean;
  origin: { kind: DocsOrigin; id: number; href: string } | null;
};
export function toListFilters(state: DocsSearchState): DocumentsFilters;   // sin cursor
export function toSearchQuery(state: DocsSearchState): SearchDocumentsParams;
```

Reglas (cada una con test en Task 2):
- **Orden de tokens:** se recorre `params.entries()` en orden y se agrega un token por entrada válida.
  `serializeDocsSearch` escribe los tokens en ese orden y después `publico`, `orden`, `pagina`, `origen`.
- **Validación:** `proyecto`/`cliente`/`requisito`/`tarea` enteros ≥ 1 (si no, se ignoran); `tema` y
  `persona` no vacíos (≤ 500 / ≤ 200); `q` recortado con trim, ≥ 2 caracteres; `sinX`/`publico` solo
  con valor `1`; `pagina` entero ≥ 1 (si no, 1); `origen` solo `proyecto|requisito|tarea`; **cualquier
  otro param se descarta** al reescribir la URL (nada de URL de vuelta: sin redirect abierto).
- **Topes del contrato:** `proyecto`, `cliente`, `tema` hasta 20; `persona` hasta 10; los excedentes se
  ignoran. `requisito` y `tarea`: la api acepta uno → se toma **el primero** de cada uno.
- **Exclusividad:** "Sin proyecto" y un token `proyecto` no conviven (agregar uno quita los otros); lo
  mismo `sinCliente`/`cliente` y `sinTema`/`tema`. Un token idéntico no se duplica.
- **Cualquier cambio** (token, publico, orden) **borra `pagina`** (vuelve a 1). Quitar el token de la
  entidad de `origen` borra `origen`.
- **Modo:** sin tokens y sin `publico` → `inicio`; con algún token `texto` → `texto`; si no → `listado`.
- **Orden por modo:** listado/inicio admiten `recientes` (default) y `az`; texto admite `relevancia`
  (default) y `recientes`. Un `orden` inválido para el modo se trata como el default y **no** se escribe
  (el default nunca va a la URL).
- **Origen:** `origen=proyecto` + token `proyecto` → `href: '/projects/{id}'` (primer proyecto);
  `origen=requisito` + token `requisito` → `'/requirements/{id}'`; `origen=tarea` + token `tarea` →
  **`'/objectives/{id}'`** (ruta real de la tarea). Sin el token de esa entidad, `origin: null`.
- **Filtros** (story, "Filtros"): proyecto → `projectId`; cliente → `clientId`; tema → `topic`;
  persona → `person`; requisito → `requirementId`; tarea → `taskId`; "Sin…" → `hasX: false`;
  `publico` → `visibility: 'public'`; listado: `sort` (`recientes` → `-updatedAt`, `az` → `title`),
  `limit: 20`, `count: true`. Texto: `q` = los tokens de texto unidos con un espacio, `limit: 50`.
- **Escritura:** `router.replace(`/docs${qs ? `?${qs}` : ''}`, { scroll: false })`.

### Paginado (decisión de este plan)

- **Listados:** `useInfiniteQuery` sobre `listDocuments` (`limit: 20`, `count: true`): `pages[]` **es**
  la pila de cursores en memoria. La página visible es `pages[pagina - 1]`. Si la URL pide una página
  todavía no cargada (recarga con `pagina=3`, o clic en "Página 3"), el hook encadena `fetchNextPage()`
  hasta tenerla. Si se acaba el cursor antes, la pantalla corrige la URL a la última página existente
  (`router.replace`). Total de páginas: `ceil(page.total / 20)` (mínimo 1).
- **Texto:** una sola consulta (`limit: 50`), orden y paginado **en memoria** (20 por página).
  "Relevancia" = orden del servicio; "Más recientes" = `updatedAt` descendente. Total mostrado =
  `items.length`, o `"50+"` si llegó a 50.
- **Componente:** `Pagination` del DS en modo **controlado** (`currentPage`, `onPageChange`,
  `totalItems`, `limit: 20`), sin selector de cantidad. `onPageChange` escribe `pagina` en la URL.

**Estados (verbatim, resumidos por bloque):**
- *default* (inicio): sin filtros; tabla agrupada; paginación oculta.
- *empty*: `"Todavía no hay documentos."`; tabla oculta, vacio-inicio visible.
- *loading*: `"Cargando documentación…"`; loader en el lugar de la tabla; buscador y tokens operables.
- *error de sistema / sin conexión*: aviso-error visible, tabla oculta.
- *success* (asignación): toast success; la fila sale de la lista.
- *not found*: no aplica — un id inexistente muestra `#id` y lista vacía; `not_installed` → 404 de la ruta.
- *sugerencias abiertas*: lista visible bajo el buscador, se superpone al contenido.
- *resultados*: tokens visibles; tabla sin grupos con conteo; fragmento si hay texto; orden Relevancia/Más recientes con texto; paginación visible.
- *sin resultados*: vacio-busqueda; tabla y paginación ocultas.
- *filtrado desde una ficha*: título `"Documentos · {nombre}"`; volver visible; columna `"Temas"` (con proyecto); nuevo documento precarga relaciones.
- *sin proyecto*: título `"Sin proyecto"`, subtítulo; columnas Documento · Cliente · Actualizado · acción; sugerido/asignar.
- *asignando*: botones de esa fila `disabled` con `Loader` `inline`; ante `version_conflict` toast warning y la fila se recarga.
- *módulo no disponible*: aviso visible; buscador, filtro-visible-cliente y nuevo documento `disabled`; tabla oculta.

**Interacciones (verbatim):** input ≥ 1 carácter (debounce 200 ms) → sugerencias (con el cliente
elegido, si lo hay); flechas mueven la marcada; Enter / click → suma el token, limpia el texto y
actualiza la URL; Enter sin marcada → token de texto; Backspace vacío → quita el último; Esc → cierra;
× → quita ese token (sin tokens vuelve a *inicio*); toggle → suma o quita `publico=1`; orden → reordena
(vuelve a la página 1); fila → `/docs/{id}`; volver → ficha; nuevo → O-11; asignar sugerido →
*asignando* → *success*; asignar proyecto → selector → *asignando* → *success*; paginación → página en
la URL. **Validación:** el token de texto pide 2 caracteres o más; con 1, Enter no suma nada y la lista
sigue abierta. **Feedback:** `module_unavailable` en cualquier consulta lleva a *módulo no disponible*
sin esperar el sondeo; el cambio de lista se anuncia en una región live: `"{n} documentos"` / `"Sin resultados"`.

**Accesibilidad (verbatim):**
- Orden de foco: boton-volver-origen → boton-nuevo-documento → buscador (tokens antes del campo, cada × enfocable) → filtro-visible-cliente → orden-documentos → filas (y su acción en sin proyecto) → paginación.
- `main` con un único h1; los grupos de *inicio* son encabezados de fila de la tabla (`th scope="rowgroup"`), no h2 (ver Hallazgos: `Table` no lo soporta).
- Buscador: `combobox` con `aria-expanded`, `aria-controls` hacia la lista (`listbox` con grupos `group` + `aria-label`) y `aria-activedescendant` en la sugerencia marcada; el foco **no** sale del campo al recorrer sugerencias. Al quitar un token con su ×, el foco vuelve al campo.
- El resaltado no puede ser solo color: va en `<mark>`. Sumar o quitar un token se anuncia (`"Filtro {etiqueta} agregado"` / `"quitado"`).

**Decisiones (verbatim, REQ-021):** una ruta con estados, no cinco pantallas; sin carpetas, sin ruta,
sin vistas guardadas, sin ⌘K; el buscador con tokens se arma en la feature, no en el DS; "Solo visibles
para el cliente" es un `ToggleGroup` y no una casilla; "Asignar proyecto" se resuelve en la fila, con el
`Select` searchable, sin overlay propio; la sugerencia se pide por fila visible, como mucho 20 por
página; "Persona" es "creado o editado por última vez por"; "Editado por" con el nombre del servicio.
**Descartes:** fila "Vistas:" y botón "Vistas"; "Ver todos" en los grupos de inicio; lista controlada de
temas y "Proponer tema nuevo". **Pregunta abierta:** ¿"En mis proyectos activos" debería poder abrirse
como lista completa? (no se resuelve acá).

**Navegación de la superficie (product-map, extracto aplicable):** sidebar fija con el ítem
"Documentación" (solo con el módulo instalado); la navegación secundaria de `documentacion` vive en la
URL (los filtros). Overlays disparados desde esta pantalla: **O-11 Nuevo documento** (dialog; ver Task 8)
y **O-07 Menú de selección** (el menú del `Select` en `selector-proyecto-fila`).

**User flow aplicable (Flujo 5, camino alternativo "clasificar Sin proyecto"):** la persona escribe
"sin", elige "Sin proyecto", ve los documentos sin proyecto con su sugerencia, asigna con "Asignar
sugerido" o elige un proyecto con "Asignar proyecto"; error: si otra persona editó el documento, ve
"El documento cambió; se actualizó la fila" y vuelve a intentar sobre la fila recargada.
**Cross-surface:** ninguno aplica (la vista es solo de `web`).

### Design System Context — `web`

- **Versión fijada:** `4.3.0` (`docs/design-system/web/README.md`).
- **Accent de la superficie:** verde agua `#61CCB9` (`color.brand.primary`) — acento, nunca fondo.
- **Grid:** `desktop` 1440 px, único, 12 columnas; layout con `display: grid` de 12 columnas y
  `gap: var(--space-grid-gap)`, sin `@media`.
- **Tipografía/color/espaciado:** se reutilizan los tokens que ya consume `DocsBrowser.module.scss`
  (`--space-2/4/6`, `--space-grid-gap`) y los de cada componente del DS; la fecha va en mono
  (`font-family` mono de la tipografía del DS, igual que las fechas de tablas existentes).

**Componentes usados (extractos normativos verbatim de cada spec):**

- **ToggleGroup** (`segmented`) — "DEBE implementarse como grupo de radios (`role="radiogroup"` con
  `role="radio"` y `aria-checked`)". "Teclado: flechas mueven la selección dentro del grupo; `Tab` entra
  y sale del grupo." "El grupo DEBE tener nombre accesible (`aria-label` o `<legend>`): «Ordenar por»,
  «Vista»." "NO SE DEBE dejar el grupo sin ninguna opción elegida cuando el valor es obligatorio."
  "Labels cortos… Sentence case." API real: `label`, `options: { value, label, disabled? }[]`, `value`,
  `onChange`, `variant`. **No tiene `disabled` de grupo**: para *módulo no disponible* se pasa
  `disabled: true` en cada opción.
- **Select** (`single` + `searchable`) — "Dinámico — mapeado de datos de la api (proyectos…) →
  `searchable` Sí, siempre." "Placeholder «Buscar...»"; búsqueda "insensible a acentos y a caja";
  "Sin coincidencias: Fila «Sin resultados»". "Al abrir, el foco pasa al buscador…" "↑ ↓ recorren las
  visibles; `Enter` elige la resaltada; `Esc` cierra y devuelve el foco al control." ARIA: `<label for>`
  siempre; rol `combobox` con `aria-expanded`/`aria-controls`; opciones `option`/`aria-selected`. API
  real: `label`, `options: { value, label }[]`, `value`, `onChange`, `placeholder`, `disabled`,
  `searchable`. **No expone `defaultOpen` ni `onClose`** (ver Task 7).
- **Table** (`light`) — "**Todos los listados y reportes**". "DEBE usarse `<table>` real con
  `<th scope="col">`." Fila 48 px; celda de texto `nowrap` + elipsis con tope 420 px; celda con badge no
  recorta. "Una celda recortada con elipsis DEBE conservar su texto completo en el DOM." "Celda sin
  dato: «N/D» o «0 h», nunca vacía" (acá la UX fija `"—"`). API real: `variant`, `columns:
  { key, label, sortable?, scope? }[]`, `rows: Record<string, ReactNode>[]`, `ariaLabel`, `loading`,
  `emptyState`. **Sin grupos de filas ni click de fila** (ver Hallazgos).
- **Pagination** — "DEBE ser un `<nav>` con `aria-label="Paginación"`"; `aria-current="page"`; `‹`/`›`
  con nombre «Página anterior»/«Página siguiente»; extremos `disabled` de verdad; "El cambio de página
  DEBE anunciarse en una región `aria-live`" (el componente ya lo hace: "Página {n} de {total}"). "NO SE
  DEBE reimplementar la paginación inline en una pantalla." "NO SE DEBE ocultar la paginación cuando hay
  una sola página" — **en esta pantalla la UX la oculta en inicio/loading/empty/sin resultados**, que no
  son "una sola página" sino ausencia de lista. Modo controlado: `currentPage`, `onPageChange`,
  `totalItems`, `limit`.
- **Input** (`search`) — base visual del campo del buscador: alto 44 px, radio 10 px, anillo de foco 3 px
  al 22 %, "Todo campo DEBE tener `<label for>`" (el combobox lleva label oculto "Buscar en la
  documentación"), "el placeholder nunca porta información necesaria".
- **Badge** (`outline`, familia `neutral`) — pills de temas, visibilidad y "En edición". "El estado
  NUNCA se comunica sólo con color: … texto siempre."
- **Button** — `primary` ("Nuevo documento"), `secondary-nav` (volver, con `href`), `secondary-dismiss`
  (acciones de fila "Asignar sugerido"/"Asignar proyecto": no hay variant terciaria, gap aceptado).
  `loading` → spinner + `aria-busy`.
- **ViewHeader** (`list`) — `<h1>` de la vista, sin divisor.
- **EmptyState** (`list` / `filtered`) — `filtered` lleva `aria-live="polite"`; nunca `role="alert"`.
- **Loader** (`block` / `inline`) — `role="status"`.
- **Card** (`panel`) — contenedor de `contenido`.

**Accesibilidad (guideline `web`, extracto aplicable):** WCAG 2.2 AA. "NO comunicar estado solo con
color." "Todo elemento interactivo es accesible vía teclado. Foco visible. ESC cierra modales /
popovers. Enter / Space activan controles. Sin keyboard traps." "Cada componente declara su rol ARIA
correcto. Iconos puramente decorativos: `aria-hidden="true"`. Live regions para feedback dinámico
(`aria-live="polite"`)." "Cada input tiene un `<label>` asociado."

**DS Gaps — `web`:**
- *Aceptados* (REQ-021 → "Dejar anotado" / "Reemplazar"):
  - `filtro-visible-cliente` (`checkbox`) → **Reemplazar** por `ToggleGroup` segmentado "Todos / Visibles

### Code Conventions

- Componentes en carpeta propia `components/{Nombre}/{Nombre}.tsx` + `{Nombre}.module.scss` +
  `index.ts` (`export { X } from './X'`) + tests al lado.
- Hooks `hooks/use{Algo}.ts` con `'use client'`; Server Actions en `services/docsApi.ts` (`'use server'`).
- Utils puras en `utils/{nombre}.ts` (camelCase, como el resto de `features/docs/utils`).
- Textos de interfaz como constantes al tope del componente o en el util de mensajes (no inline
  repetidos); exactamente los de la sección Contenido.
- Props `readonly`; tipos en `types/docs.types.ts`.

## Hallazgos y decisiones de este plan

1. **Ruta de la tarea:** `screen.md` (`boton-volver-origen`) dice `/tasks/{id}`, pero la ruta real de la
   web es `/objectives/[id]`. El plan usa **`/objectives/{id}`**. Conviene corregir `screen.md` en el
   próximo pase de UX.
2. **axios serializa arrays como `key[]=`**: se fija `paramsSerializer: { indexes: null }` para mandar el
   parámetro repetido del contrato (la api lo aceptaría igual por `qs` extendido, pero el contrato es
   `style: form, explode: true`).
3. **`Table` del DS no tiene grupos de filas (`th scope="rowgroup"`) ni fila clickeable** → dos tablas
   apiladas con rótulo y *stretched link* en la feature (DS gaps nuevos, no bloquean).
4. **`Pagination` exige `totalItems`**: los listados siempre piden `count=true`, así que hay total; los
   saltos a páginas no adyacentes se resuelven encadenando cursores (`useInfiniteQuery`), lo que además
   hace que una URL con `pagina=N` se reconstruya al recargar (CA-11).
5. **`Select` no expone `defaultOpen`/`onClose`** → apertura y cierre programáticos en
   `AssignProjectAction` (sin tocar el DS).
6. **Convivencia con S-097:** el botón "Nuevo documento" de `/docs` no está en ningún CA de S-095 ni de
   S-097; lo cablea este plan con la regla condicional de Task 8 para que no quede huérfano.
7. **`useFolderTrail`/`foldersApi` siguen en uso por `DocumentBreadcrumb`** (S-096): baja condicional.
8. **Los hits de búsqueda no traen `topics` ni `lock`**: en texto no hay pills de temas ni "En edición",
   y la columna "Temas" del filtrado por proyecto se mantiene como "Cliente · Proyecto" cuando hay texto.
9. **Query keys:** la story fija el prefijo `['docs', …]`; el panel actual (`DocsPanel`, S-098) usa
   `['docs-documents']`. La asignación invalida ambos hasta que S-098 migre el panel.
10. **`requisito`/`tarea`** se declaran repetibles en la URL, pero la api acepta uno: se toma el primero.
11. **Exclusividad** "Sin X" ↔ token X: decisión de este plan para no producir combinaciones vacías por
    construcción (la story no la fija).
12. **`router.replace`** (story) en lugar de `router.push` (convención): el botón "atrás" del navegador
    no recorre cada filtro agregado; se respeta lo que fija la story.
13. **`EmptyState` recibe un solo `message`**: las dos líneas de `vacio-inicio`/`vacio-busqueda` se
    unen con un espacio.
