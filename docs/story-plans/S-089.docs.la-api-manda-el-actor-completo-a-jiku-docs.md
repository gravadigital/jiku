#### Lo implementado — `api/lib/modules/client.ts` (commit `6ae6803`)

```ts
 * DD-1 (revisado por REQ-019): se llama SIEMPRE en nombre de la persona con el `actor` de
 * `buildActor(res.req)` sin transformar —`{ id, roles, name?, username?, email? }`, el mismo sobre que
 * recibe core—, para que jiku-docs clasifique con los roles del token verificado (D-11) y no con la
 * fila de `users`. Un llamado sin `actor` lo trata jiku-docs como el propio servicio (clase `service`,
 * lee todo), así que acá se FALLA CERRADO: sin identidad verificada y sin `anonymous` → 401 sin
 * publicar. Por eso no se reusa `withActor`, que sin identidad devuelve el payload sin `actor` (falla
 * abierto, correcto para core).
 *
 * El `actor` lo inyecta el embudo después del spread: gana el del token.
...
  } else {
    const actor = buildActor(res.req);
    if (!actor) {
      res.status(401).json({ code: 'unauthorized', message: 'Unauthorized' });
      return null;
    }
    body = { ...payload, actor };
  }
```

#### D-11 de jiku-docs (fuente externa, solo lectura: `conectores/jiku-docs/docs/decisiones-integracion.md:143`)

> La api manda a jiku-docs el mismo `actor` que manda a core (`buildActor`): `{ id, roles, name?,
> username?, email? }`, con `roles` tomados del token web ya verificado. Solo la api puede mandar
> `actor` (se identifica por `JIKU_API_USER_ID`). jiku-docs, cuando el caller es la api y el `actor`
> trae `roles`, clasifica a la persona con esos roles (`admin`/`user` → `person-internal`,
> `external-user` → `person-external`, otro → sin acceso) y no consulta `users.list` para ese dato.
> Los `project-permissions` del externo se siguen consultando a core. Contrato: el esquema `Actor` de
> los tres contratos de jiku-docs pasa a `{ id (req), roles (req, array de string), name?, username?,
> email? }`, `additionalProperties: false`.

**Requisito de versión (riesgo principal de REQ-019):** mientras jiku-docs tenga `Actor` con
`additionalProperties: false` y solo `id`, **toda** llamada de la api con `roles` responde
`invalid_fields` (400) y la documentación deja de funcionar en web y opus-web. La api con este cambio
**requiere la versión de jiku-docs que implementa D-11**; se actualiza jiku-docs antes o junto con la
api. Sin compatibilidad hacia atrás. El número de versión de jiku-docs que implementa D-11 **NOT
DOCUMENTED - needs verification**: se escribe por la decisión (D-11), no por número.

**Texto de la revisión (fuente: DD-1 a DD-5 de REQ-019, `client.ts` de `6ae6803`, D-11):**

```markdown
## Revisión: el `actor` completo hacia jiku-docs (REQ-019 / S-089, 2026-10-25)

**El embudo ya no manda `actor: { id }`.** `call()` de `api/lib/modules/client.ts` publica
`{ ...payload, actor }` con `actor = buildActor(res.req)` sin transformar:
`{ id, roles, name?, username?, email? }`, **el mismo sobre que recibe core** (`withActor`). Hay una
sola fuente de identidad para los dos destinos: el claim ya verificado (ADR-007); `roles` sale de
`req.decodedTokenRoles` y sin claim es `[]`, que no autoriza nada (ADR-008).

**Por qué.** Core actualiza los roles de una persona en `users` solo cuando ejecuta un comando de core
o se conecta directo a NATS. Una persona que solo lee documentación quedaba con roles viejos o sin
fila, y jiku-docs —que la clasificaba consultando `users`— le respondía `caller_not_authorized`. Con
D-11, jiku-docs clasifica con los `roles` del `actor` que manda la api (`admin`/`user` →
`person-internal`, `external-user` → `person-external`, otro → sin acceso).

**Lo que no cambia:** la falla cerrada (sin identidad, 401 sin publicar); gana el `actor` del token,
entero; `shares.resolve` y `shares.attachment` siguen sin `actor`; la opción `anonymous`;
`getRolesFromToken` (la api no acepta tokens de machine users ni lee claims de roles por proyecto); el
contrato HTTP.

**Sigue sin reusarse `withActor`**, pero la razón cambia: ya no es que su sobre sea `invalid_fields`
para jiku-docs, sino que **sin identidad publica sin `actor`** (falla abierto, correcto para core), y
para jiku-docs un llamado sin `actor` es el propio servicio, que lee todo.

**Requisito de versión:** la api requiere la versión de jiku-docs que implementa D-11 (riesgo R-9).
`name`, `username` y `email` viajan ahora también a jiku-docs; ya viajaban a core por el mismo bus,
jiku-docs solo los acepta del publicador de confianza (`JIKU_API_USER_ID`) y el embudo sigue sin
loguear el `payload`.
```
