### Service Architecture

**La regla central:** el access token se queda en el servidor. Los `services/*Api.ts` llevan
`'use server'` y el interceptor de `apiClient` llama a `auth()`, que solo corre ahí. **Ningún
componente que esta story toque debe hacer fetch propio.**

Estructura relevante:

```
web/src/
├── app/
│   ├── layout.tsx          root: fuente, <Providers>, metadata (título real de la pestaña)
│   ├── page.tsx            home — <h1>Home</h1>
│   ├── globals.scss        reset + tokens en :root
│   ├── (loggedin)/         grupo protegido: auth() + redirect + Navbar + ToastContainer
│   │   ├── layout.tsx      EL SHELL — objeto de la CA-5

│   │   ├── worked-times/   page.tsx + report/page.tsx
│   │   └── time-allocation/page.tsx

│   └── unauthorized/       page.tsx — ÚNICA pantalla sin módulo SCSS
├── features/
│   ├── worked-times/       11 componentes
│   └── time-allocation/    3 componentes

```

**El guard vive en el layout, no en un middleware** (`(loggedin)/layout.tsx:10-21`):

```tsx
export const dynamic = 'force-dynamic';
const session = await auth();
if (!session) redirect('/login');
if (session.user?.roles?.includes('external-user')) redirect('/unauthorized');
```

Tres páginas repiten un chequeo propio porque el rol del grupo no basta: `time-allocation`,
`worked-times` y `worked-times/report` redirigen `external-user` a `/projects`. **Esta story no
toca esa lógica**, solo su presentación.

### Convención de estilado (`conventions/styling.md`) — normativa para esta story

- **Un módulo por componente**, junto al `.tsx`. Las páginas usan `styles.module.scss` (sin prefijo).
- **Clases en `camelCase`**, no `kebab-case`.
- El módulo empieza con `@use '@/styles' as *;` cuando necesita mixins.
- **`cn()` para clases condicionales**, nunca template strings: `` `${styles.a} ${cond && styles.b}` ``
  escribe el string `"false"` en el `class`. Es un bug latente presente en `NavItem.tsx:48-51` y
  `NavSubItem.tsx:49-52` — dos archivos que esta story elimina.
- **Usar el token, nunca el hex literal.**
- **No `@media` cruda:** usar los mixins de `_mixins.scss`.
- **No estilos inline** salvo valores calculados en runtime (una barra de progreso).
  `unauthorized/page.tsx` está todo inline y es **la excepción, no el modelo** — la CA-2 la elimina.

### Convención de testing (`conventions/testing-unit.md`) — normativa para esta story

- Tests **junto al archivo** que testean, como `{Nombre}.test.tsx`. No hay carpeta `__tests__/`.
- **Nombres de test en español**, describiendo comportamiento observable.
- `getByRole` con nombre accesible antes que clase o `data-testid`.
- `userEvent` antes que `fireEvent`; `queryBy*` para ausencias.
- **Se mockea la capa de hooks o de servicios**, nunca `fetch` ni `apiClient`.
- `next/navigation` (`useRouter`, `useSearchParams`) se mockea cuando el componente navega.
- **Las páginas de servidor async SÍ se testean**, invocándolas como función y renderizando el retorno.
- `TZ: 'UTC'` no se toca.
- Comando: `npm test --workspace web` · `npm run lint --workspace web`

### Cambios de API y de Base de Datos

**Ninguno.** Esta story no toca contratos HTTP, entidades ni reglas de negocio. No hay endpoints
nuevos ni modificados, y ningún componente introduce fetch propio.

## Design System Context — superficie `web`

**Versión pineada para esta story: `2.4.1`** (`docs/design-system/web/README.md:14`).

**Accent de la superficie:** `color.brand.primary` = **`#61CCB9`** (verde agua). Es la única fuente;
si alguna ficha de pantalla trae `accent_color` propio, se ignora.

### Los cuatro principios de aplicación

1. El verde agua es **acento, nunca fondo de página**.
2. El azul oscuro carga el texto y la jerarquía.
3. Los colores de sistema informan estado; **no son marca**.
4. Una sola familia de radios y una sola sombra por nivel.

**Proporción de uso:** 60 % niebla · 24 % azul oscuro · 10 % grafito · 6 % verde agua.

#### EmptyState

| Variant | Propósito | Ejemplo del manual |
|---|---|---|
| `list` | Listado o grilla sin elementos | «No hay etapas activas» |
| `filtered` | Filtro sin resultados | «No se encontraron requisitos» |
| `scoped` | Sin datos para un recorte temporal | **«No hay cargas para este día»** |

> La diferencia importa: `list` invita a crear el primer elemento; `filtered` invita a **cambiar el
> filtro**, no a crear.

**Cuándo NO usar:** la consulta está en curso → Loader. **No son lo mismo:** «estamos buscando» no es
«no hay nada».

**Sin ilustración.** La personalidad de marca es sobria; un estado vacío no es una oportunidad
decorativa.

**Accesibilidad:** DEBE vivir en una región con `aria-live="polite"` **cuando aparece como resultado
de un filtro** · **NO DEBE usar `role="alert"`**: la ausencia de datos no es un error.

**Contenido:** negativa neutra, en presente, sin disculpas ni exclamaciones.
✓ «No hay cargas para este día» · ✗ «¡Ups! No encontramos nada» · ✗ «Todavía no cargaste nada»
(culpa al usuario).

**API:** `variant` (`"list" | "filtered" | "scoped"`, default `"list"`) · `message` (string,
**requerido**) · `action` (Button props, **sólo en `list`**).

**Implementación real:** `action` se renderiza sólo en `list`, `aria-live="polite"` sólo en
`filtered`, nunca `role="alert"`.

### Guidelines de accesibilidad

> ⚠️ `guidelines/accessibility.md` está en `status: placeholder` (v0.1.0, agosto 2026) y el propio
> README del DS lo reconoce: «Las reglas de accesibilidad **por componente** ya están en cada spec».

Reglas transversales aplicables (target **WCAG 2.2 AA**):

- Texto body ≥ 4.5:1 · texto grande ≥ 3:1 · componentes interactivos (bordes, iconos) ≥ 3:1.

- Live regions para feedback dinámico (`aria-live="polite"`).
- Respetar `prefers-reduced-motion: reduce`.

## Decisiones tomadas al planificar

Cinco cuestiones que el relevamiento del código dejó abiertas y que este plan resuelve, para que el
implementador no las improvise.

### D-1: `logoLayout.png` ya no existe — la CA-3 parte de una premisa vencida

La CA-3 pide «reemplazar `logoLayout.png` en `Navbar.tsx:16`». **Ese archivo no existe en el
repositorio:** `grep -rn "logoLayout" web/src` no devuelve nada y `find web -iname "*logoLayout*"`
tampoco. **S-052 ya lo eliminó**, y el `Navbar` actual importa `jikuLogo.svg`
(`Navbar.tsx:16`), renderizado en `Navbar.tsx:191`.

Más aún: existe un guardia que lo prohíbe, en `web/tests/tokens.test.ts:298-301`:

```ts
it('TS-23: logoLayout ya no se referencia en ningún lado', () => {
  const hits = grep('logoLayout');
  expect(hits).toBe('');
});
```

**Resolución:** el trabajo real de la CA-3 **no es reemplazar un PNG** (ya está hecho) sino lo que la
CA también pide y todavía no está: **seleccionar el SVG correcto según el modo** (claro/oscuro) y
**respetar el área de resguardo `1x`**. `SidebarNav` hoy tiene `jikuLogo.svg` hardcodeado sin
selección por modo. La tarea T4 lo resuelve. **No se reintroduce `logoLayout.png` bajo ninguna
circunstancia** — rompería TS-23 de `tokens.test.ts`.

### D-2: `ViewHeader` se adopta sólo en las 3 páginas del alcance; `PageLayout` sobrevive

**El contexto:** `PageLayout` lo importan **19 archivos**, de los cuales **13 son páginas fuera del
alcance de esta story** (clients ×3, projects ×2, objectives ×6, requirements ×2). Además
`web/src/shared/components/ui/index.test.ts:168` afirma explícitamente que sigue exportado:

```ts
it.each(['Navbar','NavItem','NavSubItem','PageLayout'])('sigue exportando %s', ...)
```

**La preocupación sobre los metadatos, resuelta:** `PageLayout` renderiza un bloque `<Head>` con
`<title>`, `<link rel="icon">` y `<meta name="robots">`. Pero **usa `next/head`, que es un no-op en
el App Router** — está documentado como limitación conocida en el overview de arquitectura
(«`PageLayout` usa `next/head`, que no tiene efecto en el App Router (`PageLayout.tsx:17-21`). El
`<title>` real lo pone `metadata` en `layout.tsx`»). La ficha de `home-vacia` lo confirma desde el
otro lado: «el `<title>` del documento viene de `metadata` en el layout raíz».

**Consecuencia: no hay metadatos que reubicar.** El `<title>`, el favicon y `robots` que `PageLayout`
declara **no llegan al documento hoy**. Sustituirlo por `ViewHeader` en las 3 páginas del alcance no
pierde nada, porque no había nada que perder. **Lo que sí aporta `PageLayout` y hay que preservar es
el contenedor** (`.generalContainer` + `.headerContainer`), y eso se resuelve en el `<main>` del
shell, no en el componente.

**Resolución:**

- Las **3 páginas del alcance** (`worked-times`, `worked-times/report`, `time-allocation`) pasan a
  `ViewHeader` variant `list`.
- **`PageLayout` NO se elimina ni se saca del barrel**: sigue sirviendo a las 13 páginas restantes, y
  `index.test.ts:168` seguiría pasando. Su baja pertenece a **S-060** («baja de InputSelect y cierre
  de la migración»), que es la story que cierra la migración.
- El límite de `action` singular de `ViewHeader` **no molesta acá**: ninguna de las 3 páginas tiene
  una acción primaria en la cabecera. Sus controles (filtros de período, toggle de vista, filtro de
  tipo) **van debajo del header**, tal como el layout declarado en las fichas los ubica hoy (en
  `controles`, no en la cabecera).

### D-3: El bloque de enlaces externos se conserva, renderizado fuera de `SidebarNav`

`SidebarNav` **no tiene concepto de enlaces externos**: su `items` es
`{ key, label, icon, href, children? }[]`, sin target ni sección separada, y el spec del DS no los
menciona. Pero el `Navbar` actual sí los tiene: `EXTERNAL_LINKS` es una variable de entorno con un
JSON (`[{"tool":"github","href":"...","label":"..."}]`) que se mapea a iconos, y el product-map los
declara como parte de la navegación de la superficie («Más un bloque de enlaces externos
configurable (variable `EXTERNAL_LINKS`; vacío = bloque oculto)»).

**Resolución: se conservan, renderizados en el shell junto a `SidebarNav`, no dentro de él.**
Quitarlos sería una regresión funcional que ninguna CA pide, y meterlos a la fuerza en `items` los
haría pasar por secciones del producto, que es justo lo que el spec prohíbe («labels: el término de
dominio en plural»). El DS además manda que los logos de terceros **conserven su color original y no
se re-dibujen** (`foundations/logo.md` § Coexistencia), lo que refuerza que no son ítems de
navegación. Se deja registrado como observación para el DS.

### D-4: El `z-index` invertido no se corrige en esta story

`foundations/spacing.md` marca que `z.navbar` (400) > `z.modal` (200) y `z.tooltip` (300), y que el
orden correcto sería `dropdown < navbar < modal < tooltip`. **El propio DS declara que corregirlo
cambia el contrato y se versiona como breaking.**

**Resolución: fuera de alcance.** El bug está **neutralizado** en el código actual porque el sidebar
usa `z-index: 10` literal, y esta story conserva ese valor. Corregir el orden de tokens es un cambio
de DS (MAJOR) que afecta a las 25 pantallas, no sólo a las 7 de esta story. Se deja registrado.

### D-5: La deuda de S-056 se cierra en esta story

La deuda registrada son **14 incumplimientos** de TS-36/TS-37 en el alcance de S-056:

- **1** uso de `--color-text-muted` — en `features/clients/components/ClientProjects/ClientProjects.module.scss:14`.
  (Nota: el componente vive en `features/clients`, **no** en `features/projects`.)
- **13** `font-weight` numéricos en `features/objectives/`, en 7 archivos:
  `ObjectiveDetails.module.scss:22,48,101` · `ObjectiveHistoryList.module.scss:6` ·
  `ObjectivesGroup.module.scss:7,43,66` · `ObjectiveCard.module.scss:35,56` ·
  `ObjectivesTable.module.scss:3` · `AreaTag.module.scss:16` · `ObjectiveComment.module.scss:38,83`.

**Resolución: se cierran acá (tarea T9), no se difieren a S-060.** El motivo es de coherencia del
guardia: esta story amplía TS-36/TS-37 desde «sólo requirements» a un alcance nuevo. Dejar 14
incumplimientos conocidos en carpetas que el guardia ya recorre para otros checks obliga a mantener
la restricción artificial de alcance por directorio, que es exactamente la deuda que el comentario
del guardia describe. Cerrarlos permite que **TS-36 y TS-37 pasen a cubrir los 12 directorios de
`SCOPE_DIRS`**, no una sublista.
