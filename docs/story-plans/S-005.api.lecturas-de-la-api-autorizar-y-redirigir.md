# Story Plan: S-005 (api) - Lecturas de la `api`: autorizar y redirigir

## Status

**Status:** Completed

## Story Reference

- **Story:** [S-005](../stories/S-005.lecturas-de-la-api-autorizar-y-redirigir.md)
- **Service:** `api`
- **Summary:** Las cuatro rutas de la `api` que hoy sirven bytes pasan a autorizar, resolver el
  `file_id` del vínculo, publicar `files.{fileId}.request-download` y responder **302** a la
  prefirmada que firmó `core`. Se agrega el camino de lectura por `fileId` para el archivo sin
  vínculo, las dos rutas de metadatos pasan a leer los campos del archivo por `include` a `files`,
  y **la `api` pierde el cliente de S3 y sus credenciales**.

### Service Architecture

**No hay `src/`.** El código vive en `lib/`, y el dominio **no está en carpetas: está en el prefijo
del nombre del archivo de ruta**.

```
api/
├── app.ts                    Express, middleware global, montaje automático de rutas
├── bin/index.ts              entry point: assertAuthConfig → initializeDb → initialize → listen
├── config/public.ts          exenciones de autenticación (regex de lookahead negativo)
├── lib/
│   ├── routes/               61 archivos, uno por endpoint, + index.ts (barrel)
│   ├── models/index.ts       Sequelize de SOLO LECTURA; registra los modelos compartidos
│   ├── interfaces/           augmentación de Express.Request (user, project, transaction…)
│   ├── logger.ts             Winston
│   └── utils/
│       ├── bus/              cliente NATS, sendCommand/runCommand, protocolo, traductores
│       ├── middlewares/      7 compartidos: auth, roles, entidades del path, fechas
│       └── *.ts              validación, storage, permisos de adjuntos, helpers
├── db-upgrade/migrations/    95 migraciones .js, corren al arrancar
├── tests/                    61 archivos de rutas + utils + configuraciones
└── types/
```

**El montaje es automático** (`app.ts:35-37`):

```ts
for (const key of Object.keys(routes)) {
  app.use('/api', routes[key as keyof typeof routes]);
}
```

Agregar un endpoint son **dos pasos**: crear el archivo en `lib/routes/` y exportarlo en
`lib/routes/index.ts`. **`app.ts` no se toca.** El prefijo `/api` lo pone el montaje: en el archivo
de ruta el path va **sin** él.

| Elemento | Convención | Ejemplo |
|---|---|---|
| Archivos | `kebab-case` | `validate-token.ts`, `send-command.ts` |

**Imports relativos.** No hay paths de `tsconfig` en el código fuente. Los `_moduleAliases`
(`@models`, `@logger`, `@utils`) aplican al JavaScript compilado, **no** al TypeScript: no los uses.
Los paquetes del monorepo se importan por nombre (`@jiku/models`, `@jiku/nats-protocol`).

**Comentarios en español, y comentan el POR QUÉ, no el qué.** Cuando toques algo con una razón no
obvia, dejala escrita: es la única documentación de la decisión que viaja con el código.

**Lint antes de dar por terminado:** `npm run lint --workspace @jiku/api` (cubre solo `./lib`).

#### Convención `http-server` — anatomía de un archivo de ruta

```ts
import { Request, Response, Router } from 'express';
import { Attachment, File } from '@jiku/models';
import logger from '../logger';
import validateToken from '../utils/middlewares/validate-token';
import { sendCommand } from '../utils/bus/send-command';

const router: Router = Router();

async function previewAttachment(req: Request, res: Response) { /* ... */ }

router.get('/attachments/:id/preview', validateToken, previewAttachment);

export default router;
```

**Orden de la cadena de middlewares** (importa y es siempre el mismo):

1. **Rol** — `hasAnyRole([...])`, si el endpoint lo acota
2. **Forma del input** — `validateBodyFields(schema)` / `validateQueryParams(schema)`
3. **Existencia de la entidad del path**
4. **Permiso sobre esa entidad**
5. **Reglas de negocio** — validadores locales del endpoint
6. **Handler**

**Reglas:**
- Método y path en la **misma línea** del `router.{verb}(`.
- Un middleware que corta la request **responde y NO llama a `next()`**.
- No agregues un router con su propio prefijo. El montaje bajo `/api` es uniforme.
- **Todo endpoint nuevo lleva su archivo de test en `tests/routes/{mismo-nombre}.test.ts`.**
- Para código nuevo, usá el estilo directo (`router.get('/path', mw, handler)`): es el mayoritario
  y el que hace grepeable la ruta.

**Tabla de status por situación:**

| Situación | Status |
|---|---|
| Lectura correcta | 200 |
| Alta correcta | 201 |
| Input inválido | 400 `invalid_fields` |
| Sin token o token inválido | 401 |
| Rol o permiso insuficiente | 403 `access_denied` |
| Entidad del path que no existe | 404 |
| Bus caído o timeout | 503 `service_unavailable` |

#### Convención `error-handling` — forma del error

Un objeto de **dos claves, siempre**: `{ "code": "access_denied", "message": "Access denied" }`.

- **Sin `throw`, sin clases de error, sin handler global que traduzca.** Se responde con
  `res.status(n).json({ code, message })` y se corta.
- `code` es `snake_case` y **estable**: los fronts hacen `switch` sobre él.
- `message` es **texto de interfaz**: los frontends lo muestran tal cual al usuario. Los mensajes
  nuevos van **en español**.
- **Nunca devuelvas el detalle de un error interno.** Va al log con endpoint y función; la
  respuesta sale como `internal_error`.
- Usá `logger`, **nunca** `console`.

**Códigos por situación relevantes a esta story:**

| Status | Código | Cuándo |
|---|---|---|
| 400 | `invalid_id` | el id del path no es entero (patrón vigente de estas rutas) |
| 401 | `unauthorized` / `user_not_found` | sin token, token inválido, o `sub` no está en `users` |
| 403 | `access_denied` | autenticado pero rol/permiso de proyecto no alcanzan |
| 404 | `not_found` | el vínculo no existe o fue borrado |
| 404 | `file_not_found` | el archivo fue borrado (`retention_status` ≠ `active`) |
| 404 | `file_not_available` | el byte nunca llegó (`byte_status: 'pending'`) |
| 500 | `internal_error` | error inesperado |
| 503 | `service_unavailable` | el bus no responde |

#### Convención `logging`

Winston vía `lib/logger.ts`. Cada denegación se loguea con `logger.warn` y contexto
(`attachmentId`, `userId`), cada error inesperado con `logger.error`. **Nunca logs del contenido de
un archivo**; la clave y el tamaño, sí.

### Relevant ADRs

#### ADR-001: Separación lectura/escritura por credenciales de base de datos

**Decisión:** la `api` conecta con un rol de PostgreSQL **sin `INSERT`/`UPDATE`/`DELETE`**; `core`
conecta con el usuario dueño y es el único que escribe. Toda mutación viaja como comando por el bus.

**Implementation Rules (verbatim):**

- Toda escritura de dominio nueva **DEBE** implementarse como comando en `core`. **NO SE DEBE**
  agregar escritura con el ORM en `api`.
- La conexión de `api` **DEBE** usar credenciales sin `INSERT`/`UPDATE`/`DELETE`. Si un endpoint
  nuevo requiere escribir, la respuesta correcta es un comando, no ampliar los permisos del rol.
- La conexión de `core` **DEBE** usar el usuario dueño de la base.
- Las migraciones **DEBEN** correr desde `api` con `POSTGRESQL_MIGRATION_USER`, nunca desde `core`.
- Después de publicar un comando de creación, la api **DEBE** releer la base para armar la
  respuesta: core devuelve solo `{ id }` y el contrato con los frontends es el recurso completo
  con sus relaciones.
- Un endpoint que lee **NO DEBE** pasar por el bus: la lectura va directo a PostgreSQL desde la api.

> **Revisión obligada por esta story, y hay que dejarla escrita.** La última regla **deja de valer
> para los adjuntos**: los cinco caminos de lectura publican un comando. ADR-001 declara como
> ventaja explícita que *"si core está caído, el producto sigue siendo consultable: solo se pierde
> la escritura"*; con el storage centralizado **eso deja de ser cierto para los adjuntos** (CA-15).
> Es la **consecuencia aceptada** de que el único control del storage sea `core`. Si más adelante
> molesta, la salida **NO** es devolverle credenciales a la `api` —eso deshace la garantía— sino
> subir la disponibilidad de `core`, que ya se reparte por queue group.

#### ADR-002: Toda mutación es un comando NATS request/reply, sin JetStream

**Gramática del subject:**
```
{instance}.{user-id}.{svc}.{version}.{comando}
dev.323332022539911171.gestion.v1.files.42.request-download
```

**Formato de respuesta**, igual para todos los comandos:
```json
{ "status": "success", "data": { "id": 7 } }
{ "status": "failure", "errorCode": "file_not_found", "errorMessage": "Archivo no encontrado" }
```

**Implementation Rules (verbatim):**

- Todo comando **DEBE** publicarse con el subject `{instance}.{user-id}.gestion.v1.{comando}`,
  usando la gramática de `@jiku/nats-protocol`. **NO SE DEBE** construir el subject a mano.
- El cliente NATS **DEBE** fijar `inboxPrefix` explícitamente al conectar, con el hash del user id
  que calcula `@jiku/nats-protocol`. Sin esto las respuestas no llegan.
- El `userId` con el que publica la api **DEBE** salir de la key del service user, **NO** de una
  variable de entorno: tiene que coincidir exactamente con el `sub` que el auth-callout lee del
  token para autorizar el subject.
- Toda respuesta **DEBE** tener el formato `{ status: 'success', data }` o
  `{ status: 'failure', errorCode, errorMessage }`. **NO SE DEBEN** inventar otros formatos.
- Los comandos de creación **DEBEN** devolver únicamente `{ id }`. Las ediciones y borrados, nada.
- **Todo `errorCode` nuevo DEBE agregarse al mapa de `api/lib/utils/bus/protocol.ts` con su status
  HTTP. Un código sin mapeo cae en un 500 genérico.**
- El timeout de la request es `NATS_REQUEST_TIMEOUT_MS` (default **5000 ms**); al expirar la api
  **DEBE** responder **503**.
- **NO SE DEBE** transportar datos estructurados dentro de `errorMessage`.
- Core **NO DEBE** publicar mensajes: solo responde el `Reply` de la request que recibe.

> **La regla del mapa de errores es la que más fácil se olvida en esta story.** `file_not_found` y
> `file_not_available` **no están** hoy en `STATUS_BY_ERROR_CODE` (verificado en
> `lib/utils/bus/protocol.ts`): sin agregarlos, CA-7 y CA-8 salen **500** en lugar de 404.

#### ADR-007: Identidad Zitadel + auth-callout

**Implementation Rules (verbatim):**

- Todo servicio que se conecte al bus **DEBE** autenticarse con el token de un service user
  obtenido vía `@jiku/zitadel-auth`, con auto-refresh. **NO SE DEBE** usar un token de larga
  duración por variable de entorno.
- El `userId` para publicar **DEBE** derivarse de la key del service user, **NO** de una variable
  de entorno.
- El cliente NATS **DEBE** fijar `inboxPrefix` con el hash de `@jiku/nats-protocol`.
- La api **DEBE** validar los tokens de usuario contra el JWKS de Zitadel, con resincronización
  ante `kid` desconocido (`KEY_SYNC_ATTEMPS` reintentos).
- Los roles **DEBEN** leerse del claim `urn:zitadel:iam:org:project:{PROJECT_ID}:roles`.
  **NO SE DEBEN** almacenar roles en la base ni derivarlos de otra fuente.
- `AUTH_BYPASS=true` **DEBE** seguir siendo opt-in explícito, **prohibido con
  `NODE_ENV=production`** y exigir `DEV_USER_ID`.
- El producto **NO DEBE** escribir la tabla `users` para modificar identidad.
- Un cambio en `rules.yaml` del auth-callout **DEBE** tratarse como cambio de seguridad.

> **Consecuencia a registrar (revisión de ADR-007 por esta story).** El comando recibe un
> **`fileId`**, así que **quien pueda publicar en el bus puede pedir la URL de cualquier archivo del
> catálogo por su id**, salteando la autorización de la `api`. Es el mismo modelo de confianza que
> ADR-007 ya declara para toda la escritura, con dos diferencias: **ahora cubre la lectura**, y **la
> superficie es el catálogo de archivos, no el de vínculos autorizables**. Se evaluó un
> `attachmentId` opcional que `core` validara y **se descartó** por simetría con
> `files.request-upload`; queda como mitigación aditiva disponible. **No lo implementes en esta
> story.**

#### ADR-008: Autorización deny-by-default

**Implementation Rules (verbatim):**

- `validateToken` **DEBE** instalarse globalmente en `app.ts`. **NO SE DEBE** declarar
  autenticación ruta por ruta.
- Un endpoint público **DEBE** agregarse explícitamente a `api/lib/config/public.ts`. Cualquier
  cambio en ese archivo es un **cambio de seguridad** y debe revisarse como tal.
- Un endpoint público **DEBE** validar por su cuenta lo que corresponda. El caso vigente
  (`GET /api/opus/attachments/:id/public`) verifica que el adjunto esté marcado público, responde
  403 en cualquier otro caso, y manda `X-Content-Type-Options: nosniff` con CSP de sandbox.
- Un endpoint que requiere rol **DEBE** declarar `hasAnyRole([...])` explícitamente. La
  autenticación global no implica autorización.
- Un endpoint accesible a `external-user` **DEBE** además verificar permiso de proyecto: el rol
  solo no alcanza.
- Un tipo de entidad nuevo con adjuntos **DEBE** agregarse a la resolución de proyecto de
  `attachments-access.ts`. Un tipo no contemplado **no se autoriza**, que es el comportamiento
  correcto.
- Al leer un archivo de ruta, **NO SE DEBE** concluir que está desprotegido por no ver el
  middleware: la protección es global.

> **Nota real sobre el archivo de configuración.** ADR-008 dice `api/lib/config/public.ts`, pero el
> archivo vive en **`api/config/public.ts`** (verificado). Esta story **no lo modifica**: la
> exención de `api/opus/attachments/\d+/public` se mantiene tal cual.

#### ADR-009: El token confinado al servidor

**Implementation Rules relevantes (verbatim):**

- El access token **NO DEBE** llegar al navegador por ningún camino.
- La URL de la api **DEBE** leerse de `API_URL` **en el servidor, en runtime**.
- Todo route handler que reenvíe a la api **DEBE** exigir sesión y responder
  `401 {"error":"Unauthorized"}` si no hay `accessToken`. La única excepción vigente es
  `GET /attachments/[id]/[fileName]` de `opus-web`, cuya autorización la decide la api.
- Al reenviar respuestas binarias, **DEBEN** propagarse `Content-Type`, `Content-Disposition` y
  `Content-Length`.
- **NO SE DEBE** agregar `NEXT_PUBLIC_*` funcional.

> **Excepción a declarar (fuera del código de la `api`, pero la origina esta story).** Con el 302 el
> navegador conoce el endpoint del bucket en **cada lectura**, no solo al subir, lo que amplía la
> excepción ya declarada en ADR-009. Sigue sin ser el token, y las URLs van **por respuesta de la
> api** (`Location` del 302), **no por `NEXT_PUBLIC_*`**, así que ADR-009 se mantiene en lo que más
> importa. **La excepción hay que declararla en ADR-009**, no dejarla implícita — es trabajo de
> documentación de producto, no código de la `api`.

#### ADR-013: Tests contra base real

**Implementation Rules (verbatim):**

- Los tests de `api` y `core` **DEBEN** correr contra PostgreSQL real. **NO SE DEBEN** mockear los
  modelos de Sequelize.
- Los tests de comandos de `core` **DEBEN** entrar por el despachador (`dispatch()`), **NO** por
  `execute()` directamente.
- Un test de escritura de la api **DEBE** verificar las tres capas: comando publicado, traducción de
  la respuesta a HTTP, y que la fila quedó escrita. **NO SE DEBE** asertar solo el status HTTP.
- `reply()` / `failWith()` **DEBEN** usarse solo para cubrir caminos de error. El camino feliz
  **DEBE** ejecutar core de verdad.
- Cada archivo de test **DEBE** poder correr solo: el esquema y el mock de auth se preparan en
  fixtures globales de Mocha.
- `TZ=UTC` **DEBE** estar fijado en la configuración de test de todo servicio.
- La limpieza entre corridas **DEBE** ser `TRUNCATE ... RESTART IDENTITY CASCADE`.
- **NO SE DEBE** depender del orden de ejecución entre archivos de test.

### API Context

#### Endpoints a modificar (contrato objetivo, ya documentado en `docs/apis/api.yaml`)

**`GET /api/attachments/{id}/download`**

```yaml
responses:
  '302':
    description: |
      Redirección a la URL pre-firmada que firmó `core`. **Es el camino normal**, no una
      rama para archivos grandes. Los metadatos (`fileName`, `mimeType`, `fileSize`) viajan
      en los headers de esta respuesta, así que el `HEAD` que los frontends usan para
      resolver nombre y tamaño sigue funcionando.
    headers:
      Location:
        schema: { type: string }
        description: URL pre-firmada de `GetObject`, con el `Content-Disposition` firmado.
  # '200' con application/octet-stream - ELIMINADO: el byte no pasa por la api
  '401': { $ref: '#/components/responses/Unauthorized' }
  '403': { $ref: '#/components/responses/AccessDenied' }
  '404': { $ref: '#/components/responses/AttachmentNotAvailable' }
  '500': { $ref: '#/components/responses/InternalError' }
  '503': { $ref: '#/components/responses/BusUnavailable' }
```

Publica el comando con `disposition: attachment`.

**`GET /api/attachments/{id}/preview`** — idéntico, salvo que publica con `disposition: inline` y
autoriza con `canUserViewEntity`.

**`GET /api/opus/attachments/{id}/preview`** — idéntico al preview interno, con
`hasAnyRole(['user', 'external-user'])`. El portal **solo previsualiza**: no tiene camino de
descarga propio.

**`GET /api/opus/attachments/{id}/public`** — `deprecated: true`, `security: []`. Publica con
`disposition: attachment`. Mantiene la validación de `visibilityLevel === 'public'` por `entityType`
con **403 por default**, más `nosniff` y la CSP de sandbox. Responde 302 en lugar del stream.

**`GET /api/files/{id}/preview`** — **NUEVO** (camino de lectura por `fileId`, CA-12):

```yaml
parameters:
  - name: id
    in: path
    required: true
    description: '`files.id` — el id del **archivo**, no el del vínculo.'
    schema: { type: integer }
responses:
  '302': { headers: { Location: { schema: { type: string } } } }
  '401': { $ref: '#/components/responses/Unauthorized' }
  '404': { $ref: '#/components/responses/AttachmentNotAvailable' }
  '500': { $ref: '#/components/responses/InternalError' }
  '503': { $ref: '#/components/responses/BusUnavailable' }
```

> **Autorización: solo el JWT.** Sin vínculo no hay entidad contra la que validar permiso de
> proyecto, igual que en la subida. **No lleva `hasAnyRole`** ni `403` en su contrato.
>
> **El spec ya declara `GET /api/files/{id}/preview` como ruta propia y trae una nota
> "A definir al implementar (S-005)".** Esta story **decide: ruta propia**, no parámetro sobre la
> ruta existente — la ruta existente entra por `attachments.id` y sobrecargarla con un segundo
> espacio de ids sobre el mismo path es exactamente la confusión que D-16 evita. La tarea 6 borra
> esa nota del spec y deja la decisión escrita.

**`GET /api/attachments` y `GET /api/attachments/{id}`** — **contrato sin cambios**; cambia la
implementación: el `WHERE entity_type/entity_id` sigue sobre `attachments` y los campos del archivo
salen de un **`include` a `files`**. La respuesta sigue **aplanada** para no romper a los frontends.

#### Response `AttachmentNotAvailable` (verbatim del spec)

```yaml
AttachmentNotAvailable:
  description: |
    No existe o no está disponible (REQ-001, S-005). Tres causas distinguibles por el `code`:
    - **el vínculo no existe** o fue eliminado — lo resuelve la api, **sin publicar** ningún comando
    - `file_not_found` — el archivo fue borrado (`retention_status` distinto de `active`)
    - `file_not_available` — **el byte nunca llegó al storage** (`byte_status: 'pending'`)
  content:
    application/json:
      schema: { $ref: '#/components/schemas/Error' }
      examples:
        notFound:         { value: { code: not_found, message: Not found } }
        fileNotFound:     { value: { code: file_not_found, message: File not found } }
        fileNotAvailable: { value: { code: file_not_available, message: El archivo no está disponible } }
```

#### Schema `Attachment` — los 9 campos del archivo se mantienen APLANADOS

```yaml
Attachment:
  properties:
    id:            { type: integer }   # id del VÍNCULO, preservado a través de la migración (D-06)
    entityType:    { $ref: AttachmentEntityType }
    entityId:      { type: integer }   # ya NO es nullable (D-01)
    fileId:        { type: integer }   # FK a files
    fileName:      { type: string }
    fileSize:      { type: integer }
    mimeType:      { type: string }
    storageKey:    { type: string }
    storageBucket: { type: string }
    storageRegion: { type: string }
    uploadedBy:    { type: string }
    byteStatus:    { type: string, enum: [pending, uploaded] }
    checksum:      { type: string }
    createdAt:     { type: string, format: date-time }
```

> **Se mantienen aplanados A PROPÓSITO** (spec, verbatim): *"se leen de `files` por un `include`,
> pero conservar la forma deja intacto el contrato con los dos frontends, cuyos tipos están escritos
> a mano y **no fallan en compilación si divergen**. Anidar el archivo obligaría a tocar todos los

### Bus Context — el comando que esta story publica

**Subject:** `{instance}.{api-service-user}.gestion.v1.files.{file_id}.request-download`

> **El subject lleva el id del ARCHIVO, no el del vínculo.** El parámetro se llama `fileId` a
> propósito, para que no se confunda con el id de `attachments` que sí viaja en el contrato HTTP.

**Nombre del comando a pasar a `sendCommand`:** `files.${fileId}.request-download`

**Payload (`FilesRequestDownloadPayload`):**
```json
{ "disposition": "string — enum [inline, attachment], default inline" }
```

`inline` para vista previa, `attachment` para descarga con nombre. Determina el
`response-content-disposition` de la prefirmada, **así el nombre original viaja en la URL firmada y
S3 lo devuelve sin que nadie proxee el byte**.

> **NO lleva `requester`: la titularidad NO aplica a la lectura.** Un archivo se lee por el permiso
> sobre la entidad del vínculo, no por quién lo subió. Un requisito puede tener adjuntos de varias
> personas y todo el equipo del proyecto tiene que poder verlos. **RF-12 habla de *vincular*, no de
> *leer*** — confundir las dos reglas rompería el producto. **No agregues `requester` al payload.**

**Reply de éxito (`ReplyWithDownloadTicket`)** — campos exactos:

```json
{
  "status": "success",
  "data": {
    "downloadUrl": "https://bucket.example/grava-gestion/f/9c1e....pdf?X-Amz-...",
    "expiresIn": 300,
    "fileName": "informe.pdf",
    "mimeType": "application/pdf",
    "fileSize": 4194304
  }
}
```

> *"Los tres campos de metadatos van en el reply **a propósito**: la `api` los necesita para armar
> los headers de su respuesta sin volver a consultar la base, y el `HEAD` al preview que los
> frontends ya usan para resolver nombre y tamaño sigue funcionando."*

**Códigos de error del comando** (`x-error-codes`): `file_not_found`, `file_not_available`,
`internal_error`.

**Timeout:** 5000 ms (`NATS_REQUEST_TIMEOUT_MS`, ADR-002). Al vencer → **503
`service_unavailable`**, ya resuelto por `sendCommand`.

**Implementación de `core` (`core/src/commands/files/files-request-download.ts`) — el orden que la
`api` puede asumir:**

1. `fileId` no entero o ≤ 0 → `failure(FILE_NOT_FOUND)`
2. `File` inexistente o `retentionStatus !== 'active'` → `failure(FILE_NOT_FOUND)`
3. `byteStatus === 'pending'` → `failure(FILE_NOT_AVAILABLE)` — **sin tocar S3**
4. Lee `download-url-ttl-seconds` de `system_settings` (default 300)
5. Firma `GetObject` sobre `storage_key`, **firma local, sin red**
6. `success({ downloadUrl, expiresIn, fileName, mimeType, fileSize })`

> **`core` NO valida el permiso sobre la entidad, y eso es correcto.** `core` es dueño **del
> storage**; la `api` es dueña **de la autorización**. `core` firma sobre un archivo y **no sabe por
> qué se autorizó esa descarga**.

#### `sendCommand` — la API que el handler usa (verbatim de `lib/utils/bus/send-command.ts`)

```ts
export async function sendCommand<T = any>(
  res: Response, command: string, payload: unknown
): Promise<T | null>
```

Devuelve el `data` de la respuesta si salió bien, o **`null` si ya se respondió con un error** — en
ese caso el llamador **tiene que cortar**:

```ts
const data = await sendCommand<DownloadTicket>(res, `files.${fileId}.request-download`, { disposition: 'inline' });
if (!data) return;
```

Ya resuelve por sí solo: el **503** del bus caído/timeout, y el `res.status(httpStatusFor(errorCode)).json(errorBody(reply))`
para cualquier `failure`. **El handler no arma esos errores.**

### Flow Context — `lectura-de-archivos`, verbatim en lo que toca a la `api`

#### Los cinco caminos de lectura

| # | Camino | Sesión | Id que recibe | Autorización de la `api` |
|---|---|---|---|---|
| A | `web` → `GET /api/attachments/{id}/preview` | **Sí** | Vínculo | `canUserViewEntity` sobre la entidad del vínculo |
| B | `web` → `GET /api/attachments/{id}/download` | **Sí** | Vínculo | `canUserAccessEntity` sobre la entidad del vínculo |
| C | `opus-web` → `GET /api/opus/attachments/{id}/preview` | **Sí** | Vínculo | Igual, más permiso de proyecto |
| D | `opus-web` → `GET /api/opus/attachments/{id}/public` | **NO** | Vínculo | Solo `visibilityLevel === 'public'` de la entidad. **DEPRECADO** |
| E | **Archivo sin vínculo, por `fileId`** | **Sí** | **Archivo** | **Solo el JWT** |

**Todos terminan igual:** publican `files.{fileId}.request-download` y responden **302**.

> **DISCREPANCIA REAL ENTRE EL FLUJO Y EL CÓDIGO — resolverla explícitamente.** El flujo y la story
> declaran que `/download` autoriza con **`canUserAccessEntity`**; el código vigente
> (`lib/routes/attachments-download.ts:26`) usa **`canUserViewEntity`**, igual que el preview.
>
> **Decisión de esta story: se mantiene `canUserViewEntity` en `/download`.** Razones:
> 1. `canUserAccessEntity` es la función de **adjuntar**, con reglas más finas sobre objetivos
>    (creador / asignado), y aplicarla a la descarga **restringiría** el acceso de usuarios que hoy
>    descargan sin problema. Sería un cambio de comportamiento observable **no pedido por ningún
>    CA**, y esta story fue separada de la S-004 justamente para que su cambio observable sea uno
>    solo: el 302.
> 2. CA-4 pide que *"la autorización se mantiene y ocurre antes de publicar"* — **se mantiene**, no
>    se endurece.
>
> La tarea 7 anota la discrepancia en el flujo de producto para que la documentación deje de
> declarar algo que el código nunca hizo.

#### Paso 3: La api autoriza y resuelve el `file_id` (verbatim)

Busca el `Attachment` por `id` con `include` a `files` — **para autorizar y para resolver el
`file_id` en una sola consulta**.

**Autoriza:** `canUserViewEntity` / `canUserAccessEntity` resuelve el proyecto **desde la entidad del
vínculo** y verifica `user_project_permissions`.

- Si falla → **403 y no publica nada**
- Si el vínculo no existe → **404 sin publicar**

**La traducción vínculo → archivo no cuesta nada:** la `api` ya estaba leyendo la fila para
autorizar, así que tiene el `file_id` en la mano. **No hay consulta extra.**

#### Paso 6: La api redirige (verbatim)

**Response (éxito):** Status **302**, headers `Location: {downloadUrl}` y
`X-Content-Type-Options: nosniff`.

**No toca el byte.** Se elimina `getFileStream` de este camino.

> **El 302 es el ÚNICO mecanismo.** La rama *"alt archivo grande / 302 a URL pre-firmada"* **deja de
> ser una rama**: ahora es el camino normal para todos los tamaños y todos los caminos.

#### Manejo de errores del flujo (verbatim)

| Paso | Condición | Reply de core | HTTP | Criterio |
|---|---|---|---|---|
| 3 | Sin permiso sobre el proyecto de la entidad | *(la `api` corta antes de publicar)* | 403 | CA-4 |
| 3 | Entidad `visibilityLevel: 'internal'` y usuario `external-user` | *(idem)* | 403 | CA-5 |
| 3 | Vínculo inexistente o borrado | *(idem)* | 404 | CA-6 |
| D3 | La entidad del vínculo no es `public` | *(idem)* | 403 | Sin cambios |
| D3 | Archivo **sin ningún vínculo** por la vía pública | *(idem)* | 404 — inalcanzable | CA-14 |
| 5 | Archivo borrado (`retention_status` ≠ `active`) | `file_not_found` | 404 | CA-8 |
| 5 | **`byte_status: 'pending'`** | `file_not_available` | **404** con mensaje entendible | CA-7 |
| 4 | Timeout del bus | — | **503** | CA-15 |
| 7 | Objeto borrado del bucket por fuera del producto | *(el 302 lleva a un `NoSuchKey` de S3)* | 403/404 de S3 | Residual |

#### Flujo `adjuntos` — qué cambia

Su **paso 6** (acceso, tres caminos) **cambia de mecanismo**: los tres siguen entrando por id de
vínculo, pero **ninguno sirve el byte**. La rama *"alt archivo grande / 302 a URL pre-firmada"*
**deja de ser una rama**. El **paso 7** (renderizado embebido) conserva los placeholders pero el
`HEAD` resuelve nombre y tamaño **por otro mecanismo** (los metadatos del reply, no el stream).

### Task 2: `GET /api/attachments/{id}/preview` y `/download` — autorizar, resolver `file_id`, redirigir

**Status:** Completed

#### Description

Las dos rutas internas dejan de leer del storage. El handler pasa a: buscar el `Attachment` **con
`include` a `files`** (una sola consulta que sirve para autorizar **y** para resolver el `file_id`),
autorizar con `canUserViewEntity`, publicar `files.{fileId}.request-download` con el `disposition`
que corresponda, y responder **302** a `downloadUrl`.

**Es el corazón de la story y donde está el riesgo real.** No es "cambiar un stream por un redirect":
el orden de las operaciones **es** el criterio de aceptación. CA-4 y CA-6 exigen que un 403 o un 404
ocurran **antes de publicar nada** — un handler que publique primero y autorice después pasaría los
tests de status y violaría el diseño, porque le habría pedido a `core` una URL firmada para un
archivo que el usuario no puede ver.

También desaparece la rama por tamaño: `MAX_STREAMING_SIZE` y `PRESIGNED_URL_EXPIRY` dejan de existir
en estos archivos. **El 302 es el único camino, para todos los tamaños.**

#### Acceptance Criteria

1. `GET /api/attachments/:id/preview` responde **302** con `Location` = el `downloadUrl` del reply de
   `core`, para archivos de cualquier tamaño.
2. `GET /api/attachments/:id/download` responde **302** de la misma forma.
3. El preview publica `files.{fileId}.request-download` con payload `{ disposition: 'inline' }`; la
   descarga, con `{ disposition: 'attachment' }`.
4. El `fileId` del comando es `attachment.fileId` — **el id de `files`**, no el del vínculo.
5. La consulta del `Attachment` usa `include` con el alias `'file'` del modelo `File`, y **no hay una
   segunda consulta** para resolver el archivo.
6. Un usuario sin permiso sobre la entidad del vínculo recibe **403 `access_denied`** y
   **no se publica ningún comando**.
7. Un vínculo inexistente o con `deleted_at` no nulo recibe **404 `not_found`** y
   **no se publica ningún comando**.
8. Un id de path no entero recibe **400 `invalid_id`** y no se publica ningún comando.
9. La respuesta 302 lleva `X-Content-Type-Options: nosniff` y los headers de metadatos
   `Content-Type` (= `mimeType` del reply) y `Content-Disposition` (con el `fileName` del reply).
   El `Content-Length` (= `fileSize` del reply) va **solo en el `HEAD`**.

   > **CORREGIDO AL IMPLEMENTAR (S-005).** Este AC pedía `Content-Length` también en el `GET`, y
   > **así no funciona**: un `Content-Length` distinto de cero en una respuesta sin body deja al
   > cliente esperando bytes que nunca llegan y la conexión termina **abortada** (se reprodujo con
   > `supertest`). Un `HEAD` no lleva body, así que ahí el header describe el recurso y es
   > correcto — y es el único lugar donde los frontends lo leen
   > (`useAttachmentMeta.ts`, `RichContentRenderer.tsx`), así que CA-10 se cumple igual.
   >
   > Por la misma razón **no se usa `res.redirect()`**: internamente hace `format()` + `send(body)`,
   > que pisan el `Content-Type` con `text/html` y el `Content-Length` con el largo de su cuerpo de
   > cortesía. El 302 se arma con `res.setHeader('Location', …)` + `res.status(302).end()`.
10. Ni `attachments-preview.ts` ni `attachments-download.ts` importan `storage-service`, y no queda
    ninguna referencia a `getFileStream`, `getPresignedUrl`, `MAX_STREAMING_SIZE` ni
    `PRESIGNED_URL_EXPIRY` en esos archivos.
11. El payload del comando **no contiene `requester`** ni ningún dato de titularidad.
12. `/download` **conserva** `canUserViewEntity` como autorización (ver la nota de discrepancia en
    Flow Context): no se introduce `canUserAccessEntity` en la lectura.

#### Technical Details

**Architectural Context References:**
- **Flow Context → Paso 3 y Paso 6** de `lectura-de-archivos`: el orden autorizar → resolver →
  publicar → redirigir, verbatim.
- **Bus Context**: nombre del comando, payload, campos exactos del reply, y `sendCommand` con su

  línea, el handler responde con `res.status().json()`.
- **Convención `error-handling`**: `{ code, message }`, mensajes nuevos en español, `logger` nunca
  `console`.

**Implementation Notes:**

- **El orden es el criterio, no un detalle de estilo.** La secuencia obligatoria:

  ```

    ▼
  Attachment.scope('active').findByPk(id, { include: [{ model: File, as: 'file' }] })
    ▼

    ▼

  ```

- **`attachments-download.ts` está escrito con `.then()` anidados de cuatro niveles.** Reescribilo

- **`res.redirect(302, url)` de Express ya emite `Location`**, pero setea los headers **antes** de

  ```ts

  res.setHeader('Content-Disposition', `${disposition}; filename="${encodeURIComponent(data.fileName)}"`);
  ```

### Task 4: `GET /api/files/{id}/preview` — leer un archivo sin vínculo, autorizado solo por el JWT

**Status:** Completed

#### Description

Endpoint **nuevo**, y es lo que hace coherente al modelo consigo mismo. Un archivo **sin ningún
vínculo es un estado válido**: el usuario que subió tres archivos y todavía no guardó el requisito
tiene que poder previsualizar lo que acaba de subir, y los dos frontends ya muestran preview antes de
guardar. Sin vínculo no hay id de `attachments` con el que pedirlo, así que este camino recibe el
**`fileId`**.

**Su autorización es solo el JWT**, y eso es una decisión, no un descuido: sin vínculo no hay entidad

### Task 6: Metadatos de adjuntos desde el `include` a `files`, y cierre del spec

**Status:** Completed

#### Description

`GET /api/attachments` y `GET /api/attachments/{id}` **no cambian su contrato** —los frontends no se
tocan— pero hoy leen los campos del archivo de las columnas duplicadas de `attachments`. Después del
backfill de la S-001 esas columnas son un espejo que puede divergir del `File` real: el `byte_status`
ni siquiera existe en `attachments`, y es un campo que el contrato declara.

Esta tarea hace que los campos del archivo salgan de un **`include` a `files`**, manteniendo la
respuesta **aplanada** exactamente como está.

**La respuesta se mantiene aplanada a propósito, y esto no es negociable:** los tipos de los dos
frontends están escritos a mano y **no fallan en compilación si divergen**. Anidar el archivo
obligaría a tocar todos los consumidores por un beneficio de forma. Si el `include` devuelve
`attachment.file`, el handler tiene que **aplanarlo antes de responder**.

La tarea cierra además la nota abierta del spec sobre la forma del camino por `fileId` (tarea 4).

#### Acceptance Criteria

1. `GET /api/attachments?entityType=X&entityId=N` mantiene el `WHERE` sobre `attachments` y agrega el
   `include` del modelo `File` con alias `'file'`.
2. `GET /api/attachments/{id}` hace lo mismo sobre la consulta por PK.
3. Los campos `fileName`, `fileSize`, `mimeType`, `storageKey`, `storageBucket`, `storageRegion`,
   `uploadedBy`, `checksum` y `byteStatus` de la respuesta salen **de la fila de `files`**, no de las
   columnas homónimas de `attachments`.
4. La respuesta sigue **aplanada**: no aparece un objeto `file` anidado, y `id` sigue siendo el id
   **del vínculo**.
5. `fileId` aparece en la respuesta.
6. El `include` del `uploader` (`User`, alias `'uploader'`) se mantiene, y ahora resuelve contra
   `files.uploaded_by`.
7. La autorización de las dos rutas (`canUserViewEntity`) **no cambia**.
8. `checksum` sigue **excluido** del listado por el `attributes: { exclude: ['checksum'] }` vigente,
   o su equivalente sobre el `include` — el comportamiento observable no cambia.
9. El spec `docs/apis/api.yaml` ya no contiene la nota *"A definir al implementar (S-005)"* en
   `/files/{id}/preview`, y en su lugar declara que la decisión fue **ruta propia**, con su razón.

#### Technical Details

**Architectural Context References:**
- **API Context → Schema `Attachment`**: la lista exacta de los campos aplanados y la justificación
  verbatim de por qué se mantienen así.
- **Database Context**: la consulta `attachments JOIN files`, y el detalle de que
  `Attachment.file` es el alias de la asociación.
- **Convención `orm`**: Sequelize en solo lectura; esta tarea **solo lee**.
- **ADR-005 (modelos compartidos)**: `@jiku/models` lo usan la `api` y `core`. **No modifiques el
  modelo `Attachment` en esta tarea** — ver la nota del Database Context.

**Files to Create/Modify:**
- `lib/routes/attachments-get.ts` (modificar las dos consultas y el armado de la respuesta)
- `tests/routes/attachments-get.test.ts` (ampliar)

**Implementation Notes:**

- El `include` a agregar en ambas consultas:

  ```ts

    { model: File, as: 'file' },

  ```

- **El aplanado.** Sequelize devuelve el `File` anidado bajo `file`; el contrato lo quiere plano. El
  handler tiene que armar el objeto de respuesta explícitamente:

  ```ts

  // escritos a mano y no fallan en compilación si divergen. Anidar el archivo obligaría a
  // tocar todos los consumidores por un beneficio de forma.
  function flatten(attachment: any) {

      entityType: attachment.entityType,
      entityId: attachment.entityId,
      fileId: attachment.fileId,

      byteStatus: file?.byteStatus,

      createdAt: attachment.createdAt,
    };
  }
  ```

  la tarea.** Un campo que hoy sale y mañana no —o que cambia de tipo— rompe un frontend **en
  runtime**, sin error de compilación que lo delate. Es el modo de fallo específico de este servicio
  y está registrado como limitación conocida.
