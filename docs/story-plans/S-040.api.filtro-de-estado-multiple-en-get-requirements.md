### Service Architecture

**No hay `src/`.** El código vive en `lib/`, y el dominio está en el **prefijo del nombre del
archivo de ruta**, no en carpetas.

```
api/
├── app.ts                    Express, middleware global, montaje automático del barrel
├── lib/
│   ├── routes/               61 archivos, uno por endpoint, + index.ts (barrel)
│   │   ├── requirements-get.ts       ← el archivo de esta story
│   │   └── objectives-get.ts         ← el precedente del [Op.or]
│   ├── models/index.ts       Sequelize de SOLO LECTURA
│   ├── utils/
│   │   ├── validate-query-params.ts  ← el middleware que produce el 400
│   │   └── middlewares/has-any-role.ts
│   └── logger.ts             Winston
└── tests/routes/             un archivo de test por archivo de ruta
```

**Patrón clave del servicio:** un archivo por endpoint, con la validación, los permisos y el
handler colocados juntos. El esquema Joi se declara **en el mismo archivo de ruta**, nunca en un
módulo compartido.

**Cadena de middlewares de esta ruta** (`requirements-get.ts:112-117`):

```ts
router.get('/requirements',
  hasAnyRole(['user', 'admin']),      // 1. autorización por rol
  validateQueryParams(querySchema),   // 2. validación de forma (Joi)
  getRequirementsCount,               // 3. si count=true responde y corta
  getRequirements                     // 4. el listado
);
```

**Manejo de errores:** sin clases de error, sin `throw`, sin handler global que traduzca. Cada
punto responde directo con `res.status(n).json({ code, message })` y corta. Un middleware que
responde **no** llama a `next()`.

**Logging:** Winston vía `logger`, nunca `console`. El log lleva endpoint y función; la respuesta
**no** lleva el detalle del error interno.

### Relevant ADRs

**ADR-008 — Autorización deny-by-default**

- **Decisión:** la autenticación se instala globalmente por método HTTP con exenciones explícitas
  en `config/public.ts` (regex de lookahead negativo); la autorización por rol es explícita en
  cada ruta con `hasAnyRole([...])`.
- **Regla aplicable a esta story:** `hasAnyRole(['user', 'admin'])` de
  `requirements-get.ts:113` **no se toca**. El filtro múltiple no puede abrir una vía de lectura
  nueva: cualquier caller sin `user` ni `admin` sigue recibiendo 403 antes de que la validación
  de query se ejecute siquiera (el orden de la cadena garantiza que el 403 precede al 400).

### API Context

**`GET /requirements`** — `docs/apis/api.yaml:468`, `x-roles: [user, admin]`

> **El spec YA está actualizado.** `docs/apis/api.yaml` fue modificado durante el diseño de
> REQ-009 y hoy declara el parámetro en su forma nueva. Según la convención del repositorio,
> **el documento es la fuente de verdad y el código es el que se tiene que alinear**. Esta story
> NO modifica `docs/apis/api.yaml`.

Forma declarada hoy en el spec (la que el código debe cumplir):

```yaml
- name: state
  in: query
  description: |
    Uno o varios estados separados por coma. Devuelve los requisitos que estén en
    **cualquiera** de ellos (OR). Un valor fuera del enum `RequirementState` invalida el
    parámetro completo y responde 400 `invalid_fields`.
  schema: { type: string }
  example: planificacion,en_cola,desarrollo,revision
```

Los demás parámetros **no cambian**: `projectId` (integer), `type` (`RequirementType`),
`priority` (string), `createdBy` (string, id de Zitadel), `estimatedFinishDate` (date), `tag`
(`clave:valor`), `search` (ILIKE sobre título), `page`, `limit` (1..100, default 20), `sort`
(aceptado pero no usado), `count` (boolean).

**Respuestas declaradas:**

| Status | Cuerpo |
|---|---|
| 200 | `oneOf`: `array<RequirementWithRelations>` — o `integer` si `count=true` |
| 400 | `{ code: 'invalid_fields', message: 'Invalid field - {primer error de Joi}' }` |
| 401 | `{ code: 'unauthorized' \| 'user_not_found', ... }` |
| 403 | `{ code: 'access_denied', message: 'Access denied' }` |
| 500 | `{ code: 'internal_error', message: 'Internal error' }` |

**Enum `RequirementState`** (`api.yaml:2689-2695`, derivado de
`packages/models/src/requirement.model.ts:30-38`):

```
analisis, planificacion, en_cola, desarrollo, revision, resuelto, cancelado
```

**Cómo se produce el 400** — `api/lib/utils/validate-query-params.ts` responde con el **primer**
error de Joi, no con la lista:

```ts
const { error } = validationSchema.validate(req.query);
if (error) {
  const firstError = error.details[0].message;
  return res.status(400).json({
    code: 'invalid_fields',
    message: `Invalid field - ${firstError}`,
  });
}
return next();
```

> Devuelve **un** error, no un array. Es el contrato que los fronts ya manejan; no lo cambies.
> Nótese además que **descarta el `value` coercido por Joi**: solo usa `error`. Por eso el handler
> lee de `req.query` crudo y por eso `count` se compara contra el string `'true'`
> (`requirements-get.ts:55`).

### Database Context

**Tabla `requirements`** (`docs/db-schemas/jiku.md:667`) — extracto relevante:

```dbml

  id integer [pk, increment]
  title varchar(255) [not null]
  type requirement_type
  priority requirement_priority [not null, default: 'sin_prioridad']
  state requirement_state [not null, default: 'analisis']

  visibility_level visibility_level [not null, default: 'public']

  ...

    (project_id, created_at, id) [name: 'idx_requirements_project_created_id']

  }
}
```

```dbml
Enum requirement_state { analisis planificacion en_cola desarrollo revision resuelto cancelado }
```

**No hay migración en esta story.** El cambio es de forma de consulta, no de esquema. El índice
`idx_requirements_state_created_id` sobre `(state, created_at, id)` sirve igual a un `IN (...)`:
PostgreSQL lo resuelve como bitmap/index scan por cada valor del `IN` sobre el mismo índice. El
peor caso (los 7 estados) equivale al plan de hoy sin filtro de estado.

### Flow Context

**Ninguno.** La story declara explícitamente que ninguno de los 11 flujos de `docs/flows/` cubre
la lectura del listado de requisitos por HTTP — todos cubren interacciones cross-servicio (bus,
adjuntos, autenticación, asignación semanal).

**Flujo local del endpoint, tal como queda:**

1. `hasAnyRole(['user', 'admin'])` → 403 si no. **Sin cambios.**
2. `validateQueryParams(querySchema)` valida **cada miembro** del CSV contra el enum → 400
   `invalid_fields` si alguno no pertenece.
3. `buildWhere` arma `where.state = { [Op.or]: ['desarrollo', 'revision'] }`.
4. `getRequirementsCount` (si `count=true`) o `getRequirements` ejecutan con ese `where`
   compartido.

- **Errores:** `res.status(n).json({ code, message })`. `code` en `snake_case` y estable —

- **`message` es texto de interfaz.** Los fronts lo muestran tal cual. Mensajes nuevos, en

## Tasks

### Task 1: Aceptar CSV de estados en `GET /requirements` (validación + `where`)

**Status:** Completed

#### Description

Modificar `api/lib/routes/requirements-get.ts` para que el query param `state` acepte uno o varios
valores separados por coma:

1. El esquema Joi valida **cada miembro** del CSV contra el enum `RequirementState`, de modo que un
   solo valor fuera del enum invalide el parámetro completo con 400 `invalid_fields` (CA-3), y un
   valor único inválido siga rechazando exactamente como hoy (CA-4).
2. `buildWhere` pasa de la igualdad `where.state = state` al `[Op.or]` sobre los miembros del CSV,
   copiando el patrón que la ruta hermana `objectives-get.ts:36-40` ya usa.

Es necesaria porque S-041 (multi-select de estados en `web`) depende de este endpoint desplegado:
hoy cualquier CSV que mande `web` recibe 400. La story es autocontenida y verificable sola.

**Por construcción el cambio cubre listado y conteo:** `buildWhere` es el constructor único que
introdujo S-036 y que consumen `getRequirementsCount` (línea 62) y `getRequirements` (línea 76).
No hay que tocar ninguno de los dos handlers (CA-7).

#### Acceptance Criteria

1. `GET /requirements?state=analisis,desarrollo` responde 200 y devuelve únicamente requisitos en
   `analisis` o `desarrollo` (unión, no intersección).
2. `GET /requirements?state=analisis` produce exactamente el mismo `where` y el mismo resultado que
   antes del cambio.
3. Cualquier miembro del CSV fuera del enum `RequirementState` produce 400 con
   `{ code: 'invalid_fields', message: 'Invalid field - ...' }`, **sin** filtrar por los miembros
   válidos y **sin** devolver ningún requisito.
4. Un miembro vacío (`state=analisis,` o `state=,analisis`) también produce 400 — no llega a la
   consulta un `IN` con cadena vacía.
5. Los espacios alrededor de las comas se toleran: `state=analisis, desarrollo` es válido y filtra
   por los dos estados.
6. Los valores de enum se derivan con `...Object.values(RequirementState)`; **no** se listan a mano.
7. `hasAnyRole(['user', 'admin'])` en la línea 113 queda intacto: la firma y el orden de la cadena
   de middlewares no cambian.
8. `buildWhere` sigue siendo el único constructor del `where`, consumido por los dos handlers sin
   código adicional en ninguno.
9. Los demás filtros (`projectId`, `type`, `priority`, `createdBy`, `estimatedFinishDate`, `tag`,
   `search`) siguen funcionando y se combinan con el filtro de estado en el mismo `where`.
10. `docs/apis/api.yaml` **no** se modifica: ya declara la forma nueva del parámetro.
11. `api/lib/routes/objectives-get.ts` **no** se modifica.
12. `npm run lint` y `npm run build` pasan sin errores nuevos.

#### Technical Details

**Architectural Context References:**

- **ADR-008 (Autorización deny-by-default)** — del Architectural Context: `hasAnyRole(['user',
  'admin'])` no se toca. El 403 precede al 400 porque el middleware de rol está **antes** de
  `validateQueryParams` en la cadena; ese orden es parte del contrato y no se altera.
- **Convención `validation`** — el esquema Joi se declara como constante nombrada arriba del archivo
  (ya lo es: `querySchema`, línea 12). No lo muevas a un módulo compartido. **Los valores de enum se
  derivan con `...Object.values(RequirementState)`, nunca a mano.**
- **Convención `error-handling`** — el contrato de error no cambia:
  `400 { code: 'invalid_fields', message: 'Invalid field - {primer error}' }`, producido por
  `validateQueryParams`. No introduzcas un mensaje nuevo ni un código nuevo.
- **Convención `orm`** — Sequelize en solo lectura. El `[Op.or]` sobre una columna se traduce a
  `IN (...)`, que parametriza los valores (sin interpolación de entrada de usuario en SQL) y colapsa
  duplicados.
- **API Context** — el spec ya declara `schema: { type: string }` con la descripción del CSV. El
  código se alinea al documento, no al revés.
- **Reusable Code** — `Op` ya está importado (`requirements-get.ts:8`, para el `Op.iLike` de
  `search`); `RequirementState` ya está importado (línea 3). **No agregues imports nuevos.**
- **Patrón a copiar** — `lib/routes/objectives-get.ts:36-40`. Se copia el `[Op.or]`, **no** su
  validación laxa (`objectives` no valida contra el enum y devuelve 200 con lista vacía ante un

**Implementation Notes:**

- **Estructura actual del esquema** (línea 14):

  ```ts

  ```

  Tiene que pasar a validar cada miembro del CSV contra el mismo enum. La forma idiomática en Joi 18
  para "CSV cerrado a un enum" es un `joi.string()` con un `.custom()` que parte por coma, hace
  `trim` de cada miembro y verifica pertenencia, o equivalentemente un `.pattern()` construido a
  partir de `Object.values(RequirementState)`. **Cualquiera de las dos sirve mientras cumpla los
  criterios de aceptación**; lo que no sirve es dejar `joi.string()` libre (perdería el 400 de CA-3
  y CA-4). El enum se sigue derivando con `Object.values(RequirementState)` en ambos casos.

- **Estructura actual de `buildWhere`** (línea 34):

  ```ts
  if (state) where.state = state;
  ```

  → pasa al patrón de la ruta hermana:

  ```ts
  if (state) where.state = { [Op.or]: String(state).split(',').map((s) => s.trim()) };
  ```

  El `String(...)` es defensivo: Express 5 no coerciona `req.query`, y un `?state=a&state=b`
  repetido llega como array. `buildWhere` recibe `req.query` crudo (los dos handlers le pasan
  `req.query`), no el value coercido de Joi — `validateQueryParams` lo descarta.

- **Compatibilidad hacia atrás:** un CSV de un elemento produce `{ [Op.or]: ['analisis'] }`, que
  Sequelize traduce a `IN ('analisis')` — semánticamente idéntico a `state = 'analisis'`. Por eso la
  card del detalle de proyecto (S-038, 7 tabs de un estado + `count=true`) y `opus-web` no cambian
  (CA-2, CA-8).
