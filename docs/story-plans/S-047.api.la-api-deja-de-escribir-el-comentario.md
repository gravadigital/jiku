# Story Plan: S-047 (api) - La api deja de escribir el comentario

## Status

**Status:** Completed

## Story Reference

- **Story:** [S-047](../stories/S-047.la-api-deja-de-escribir-el-comentario.md)
- **Service:** `api`
- **Summary:** La `api` deja de escribir `objective_activity` con el ORM y pasa a publicar los
  comandos de edición de comentario de `core`; suma la ruta equivalente para requisitos, expone

### Estado del árbol al planificar (leer primero)

Cuatro cosas **ya están hechas** y el plan las da por sentadas en lugar de rehacerlas. Verificarlas,
no reimplementarlas:

1. **Los dos comandos de `core` existen y están implementados.**
   `core/src/commands/tasks/tasks-comment-edit.ts` (`pattern: 'tasks.{id}.comment.{cid}.edit'`) y
   `core/src/commands/requirements/requirements-comment-edit.ts`
   (`pattern: 'requirements.{id}.comment.{cid}.edit'`). Vienen de S-046, que está **Completed**.
   Consecuencia directa para los tests: **el FakeBus los ejecuta de verdad** contra la misma base.
2. **Los dos `errorCode` ya están en `@jiku/nats-protocol`**
   (`packages/nats-protocol/src/index.ts:365-366`: `COMMENT_NOT_OWNED: 'comment_not_owned'`,
   `ACTIVITY_NOT_EDITABLE: 'activity_not_editable'`) y en `docs/apis/core.yaml`. Lo único que falta
   es agregarlos a `STATUS_BY_ERROR_CODE` en `api/lib/utils/bus/protocol.ts`.
3. **`editedAt` / `editedBy` ya existen en los dos modelos** de `@jiku/models`
   (`packages/models/src/objective-activity.model.ts:81,88` y
   `packages/models/src/requirement-activity.model.ts:76,83`), como `Date | null` y `string | null`
   (este último con `@ForeignKey(() => User)`). **No hay migración que escribir en esta story.**
4. **`docs/apis/api.yaml` ya documenta los dos endpoints** (líneas 1056-1149) con `x-roles`,
   `x-bus-command`, `fileIds: $ref '#/components/schemas/FileIds'` y 400/401/403/500/503/504,
   incluida la ruta nueva. **El spec ya describe el estado final; el código todavía no lo cumple.**
   Regla del `CLAUDE.md`: *"`docs/apis/*.yaml` son la fuente de verdad de los contratos: donde el
   código y el documento discrepan, gana el documento"*. Esta story hace que el código alcance al
   contrato — no se reescribe el yaml.

**Corolario:** el trabajo real de esta story es de código y de tests, no de documentación de contrato.

### Service Architecture

No es MVC ni Clean Architecture: es **un archivo por endpoint**, con la validación, los permisos y el
handler colocados juntos.

```
api/
├── app.ts                    Express, middleware global, montaje de rutas
├── bin/index.ts              entry point
├── config/public.ts          exenciones de autenticación
├── lib/
│   ├── routes/               61 archivos, uno por endpoint, + index.ts (barrel)
│   ├── models/index.ts       Sequelize de solo lectura
│   ├── interfaces/           augmentación de Express.Request
│   ├── logger.ts             Winston
│   └── utils/
│       ├── bus/              cliente NATS, sendCommand/runCommand, protocolo, traductores
│       ├── middlewares/      7 compartidos: auth, roles, entidades del path, fechas
│       └── *.ts              validación, storage, permisos de adjuntos, helpers
├── db-upgrade/migrations/
└── tests/                    61 archivos de rutas + utils + configuraciones
```

**El montaje es automático.** `app.ts:35-37` itera los exports del barrel:

```ts
for (const key of Object.keys(routes)) {
  app.use('/api', routes[key as keyof typeof routes]);
}
```

Agregar un endpoint son **dos pasos**: crear el archivo y exportarlo en `lib/routes/index.ts`.
`app.ts` no se toca. **El prefijo `/api` lo pone el montaje**: en el archivo de ruta el path va sin él.

### API Context

#### Forma canónica de un archivo de ruta (verbatim de `http-server`)

```ts
import { Request, Response, NextFunction, Router } from 'express';
import joi from 'joi';
import { Requirement, RequirementState } from '@jiku/models';
import logger from '../logger';
import hasAnyRole from '../utils/middlewares/has-any-role';
import validateBodyFields from '../utils/validate-body-fields';
import { sendCommand } from '../utils/bus/send-command';

const router: Router = Router();

const createSchema = joi.object({
  title: joi.string().required(),
  projectId: joi.number().integer().required(),
});

async function createRequirement(req: Request, res: Response) { /* ... */ }

router.post('/requirements',
  hasAnyRole(['user', 'admin']),
  validateBodyFields(createSchema),
  validateProject,
  createRequirement
);

export default router;
```

Y el barrel: `export { default as RequirementsPost } from './requirements-post';`

#### Orden de la cadena (verbatim) — importa y es siempre el mismo

1. **Rol** — `hasAnyRole([...])`, si el endpoint lo acota
2. **Forma del input** — `validateBodyFields(schema)`
3. **Existencia de la entidad del path** — `validateRequirement`, `validateObjective`
4. **Permiso sobre esa entidad** — `validateProjectPermissions`
5. **Reglas de negocio** — validadores locales
6. **Handler**

> `opus-requirements-id-patch.ts:29-33` invierte 2 y 3. **No lo tomes como modelo:** validar el cuerpo
> antes de buscar la entidad evita una query para una request que ya era inválida.

#### Reglas de `http-server` (verbatim)

- Un endpoint es un archivo en `lib/routes/`, exportado en el barrel. No modifiques `app.ts`.
- El path en el archivo va sin el prefijo `/api`.
- Método y path en la misma línea del `router.{verb}(`.
- Respetá el orden de la cadena.
- Reusá los middlewares de `lib/utils/middlewares/`. Duplicá solo con una razón, y comentala.
- Un middleware que corta la request **responde y no llama a `next()`**.
- No agregues un router de Express con su propio prefijo.
- **Toda mutación va por el bus, no por el modelo.**
- Todo endpoint nuevo lleva su archivo de test en `tests/routes/{mismo-nombre}.test.ts`.

#### Middlewares compartidos disponibles

| Middleware | Qué hace |
|---|---|
| `validate-token` | autentica; lo instala `app.ts` globalmente, **no las rutas** |

| `validate-objective` | carga `req.objective` y `req.project` desde `:objid`, o 404 |

### Integration Points — el bus (`bus-commands`)

#### El flujo completo de una mutación (diagrama verbatim)

```
handler
  │  sendCommand(res, 'requirements.new', payload)
  ▼
bus().request(command, payload)                       lib/utils/bus/index.ts
  │  subject: {instance}.{user-id}.gestion.v1.requirements.new
  ▼
NATS  ──request/reply, timeout NATS_REQUEST_TIMEOUT_MS──▶  core  ──escribe──▶  PostgreSQL
  │
  ▼
Reply { status, errorCode?, errorMessage?, data? }
  │  success → devuelve data          failure → res.status(httpStatusFor(errorCode))
  ▼
handler relee la base con Sequelize y arma la respuesta completa
```

#### Firmas reales (`api/lib/utils/bus/send-command.ts`, verbatim del código)

```ts
export async function sendCommand<T = any>(
  res: Response,
  command: string,
  payload: unknown
): Promise<T | null>

export async function runCommand(
  res: Response,
  command: string,
  payload: unknown
): Promise<boolean>

export function actorId(req: Request): string {
  return req.user.id;
}
```

`runCommand` es literalmente:

```ts
export async function runCommand(res, command, payload): Promise<boolean> {
  await sendCommand(res, command, payload);
  return !res.headersSent;
}
```

#### `runCommand` es el que va en esta story

Los dos comandos `*.comment.{cid}.edit` devuelven `success()` **sin `data`** (verificado en el código
de core), y ADR-002 lo normaliza: *"Los comandos de creación **DEBEN** devolver únicamente `{ id }`.
Las ediciones y borrados, nada."* Un comando exitoso sin `data` haría que `sendCommand` devuelva
`null`, indistinguible de un error — por eso existe `runCommand`.

El precedente exacto es `clients-patch.ts:14-22`:

```ts
const ok = await runCommand(res, `clients.${req.params.id}.edit`, req.body);
if (!ok) {
  return;
}
return res.status(200).json({ code: 'client_updated', message: 'Client Updated' });
```

**No hay relectura post-comando en esta story**: la regla de ADR-001 sobre releer la base aplica a las
**creaciones** (core devuelve solo `{ id }`), y una edición que responde `Acknowledgement` no tiene
recurso que devolver.

#### El nombre del comando

**La ruta NO arma el subject.** Pasa solo el nombre del comando; el subject lo arma `commandSubject`
de `@jiku/nats-protocol` (`{instance}.{user-id}.gestion.v1.{comando}`).

Los dos comandos de esta story, con los patterns verificados en core:
- `` `tasks.${req.params.id}.comment.${req.params.cid}.edit` ``
- `` `requirements.${req.requirement.id}.comment.${req.params.cid}.edit` ``

#### El sobre de identidad — lo inyecta `sendCommand`, no el handler

`withActor` (`lib/utils/bus/send-command.ts`) agrega una clave reservada `actor` a **todo** comando
publicado, armada por `buildActor` **desde el claim verificado** (`req.decodedToken.sub` + los roles
del token), nunca desde `req.user`:

```ts
return { ...payload, actor };   // el sobre va DESPUÉS del spread: gana el del token
```

**Una ruta nueva nace con sobre**: no hay nada que recordar en el handler.

Comentario verbatim de `api/lib/utils/bus/actor.ts`:

> *"El sobre de identidad, armado CON EL CLAIM YA VERIFICADO contra Zitadel. NO LEE `req.user`, Y NO ES
> UN DESCUIDO. […] Usarla es un cambio de una línea que PARECE una mejora […] y que introduce DOS
> FUENTES DE IDENTIDAD para lo mismo, con la peor de las dos decidiendo. ADR-007 lo prohíbe con todas
> las letras […]"*
>
> ```ts
> const actor: Actor = { id, roles: req?.decodedTokenRoles ?? [] };
> ```
>
> *"`roles` es OBLIGATORIO en el contrato: sin claim va `[]`, nunca `undefined`."*

**Esto es lo que hace funcionar la excepción de admin en core sin una línea en la api**:
`ctx.roles.includes('admin')`.

Los campos de dominio (`creator` / `author` / `editor`) siguen existiendo pero **ya no son la fuente de
identidad**: son datos del recurso, y se llenan con `actorId(req)`. El schema de core acepta
`editor?: string` **opcional** y `resolveActor(ctx, payload.editor, COMPONENT)` **prioriza el sobre**,
así que el sobre alcanza. Este plan manda `editor: actorId(req)` por consistencia con las rutas de
comentario hermanas (`requirements-id-activity-post.ts:29` manda `author: req.user.id`).

#### Campos opcionales: el spread condicional

```ts
...(description !== undefined ? { description } : {}),
```

> **Para `fileIds` el chequeo tiene que ser de PRESENCIA (`!== undefined`), NO de longitud.** Lo dice el
> propio código de core: *"El chequeo es de PRESENCIA (`!== undefined`) y no de longitud: un
> `fileIds: []` explícito significa 'que no quede ninguno vinculado' y tiene que desvincular, a
> diferencia del alta donde no hay vínculos previos que borrar."*
>
> Usá el patrón de `requirements-id-activity-post.ts:32`
> (`...(req.body.fileIds !== undefined ? { fileIds: req.body.fileIds } : {})`), **no** el de
> `objectives-id-comments-post.ts` (`req.body.fileIds?.length`), que descartaría el array vacío.

#### Bus caído / timeout — el código real, más fino que la convención

```ts
  } catch (error: any) {
    logger.error(`[bus] ${command}: ${error.message}`);

    if (error instanceof NatsError && error.code === ErrorCode.Timeout) {
      res.status(504).json({ code: 'gateway_timeout', message: 'La operación tardó demasiado' });
      return null;
    }

    res.status(503).json({
      code: 'service_unavailable',
      message: 'El servicio no está disponible en este momento',
    });
    return null;
  }

  if (reply.status !== 'success') {
    res.status(httpStatusFor(reply.errorCode)).json(errorBody(reply));
    return null;
  }

  return (reply.data ?? null) as T | null;
```

Comentario verbatim de ese archivo, clave para los tests:

> *"con 503 la operación NO ocurrió y reintentar es seguro; con 504 PUDO haber ocurrido y reintentar a
> ciegas puede duplicar, porque los comandos no son idempotentes. […] La rama se elige por LA SEÑAL del
> cliente NATS, no por el tiempo transcurrido ni por el texto del mensaje […] Ninguno de estos dos
> `code` va a STATUS_BY_ERROR_CODE: ese mapa traduce el `errorCode` de un reply de core, y acá no hubo
> reply — los genera la api."*

#### Reglas de `bus-commands` (verbatim)

- Ninguna mutación nueva usa el modelo: publicá un comando. Las dos escrituras que quedan
  (`Attachment.create()` y `PUT /api/week-assigned-times`) son deuda, no precedente.
- Después de `sendCommand`, chequeá `if (!data) return;`. Después de `runCommand`, `if (!ok) return;`.
  Sin eso se responde dos veces.
- Usá `runCommand` cuando el comando no devuelve datos, y `sendCommand` cuando sí.
- **La identidad viaja en el sobre**, y lo inyecta `sendCommand`: no la agregues a mano.
- Un `errorCode` nuevo en core se agrega a `STATUS_BY_ERROR_CODE`, o sale 500.
- Los campos opcionales van con spread condicional, no con `undefined` explícito.
- Las traducciones de nombres o formatos van en `lib/utils/bus/`, no en el handler.
- **Si el comando necesita el rol, el usuario final o la fecha de hoy para validarse, ESO YA NO LO DEJA
  EN LA API.** El criterio es **de quién es la regla**: si decide si la operación puede ocurrir sobre
  estos datos y tiene que dar el mismo resultado por HTTP y por el bus, **va al comando de `core`**; si
  es del transporte HTTP —la forma del input, la traducción de nombres, el 404 de la entidad del path,
  un código que el protocolo del bus no tiene— se queda acá.
- No agregues reintento automático: los comandos no son idempotentes.
- En los tests, usá el `FakeBus`.

> **Esa penúltima regla en negrita es la justificación textual de sacar el chequeo de autoría de la
> api** (Task 2).

#### El snippet de `fileIds` — copiarlo textual, con su comentario

**No hay esquema Joi compartido**, y la convención lo prohíbe: *"El esquema vive en el mismo archivo
que la ruta. No lo muevas a un módulo compartido, salvo que dos rutas usen literalmente el mismo."* Lo
que hay es este snippet repetido verbatim en 6 rutas (`requirements-post.ts:23`,
`requirements-id-patch.ts:29`, `objectives-id-comments-post.ts:52`,
`requirements-id-activity-post.ts:16`, `opus-requirements-post.ts:79`):

```ts

  // guardar la entidad. El `max(10)` es el `maxItems` que declara el spec — se valida acá para
  // que un lote de más no cueste un round-trip del bus antes de que core lo rechace igual.
  fileIds: joi.array().items(joi.number().integer().positive()).max(10).optional(),
```

#### Por qué `visibilityLevel` no se declara (CA-4)

Comentario verbatim del comando de core:

> *"`additionalProperties: false` del contrato lo cumple Joi POR DEFECTO: `joi.object()` sin
> `.unknown(true)` rechaza cualquier campo no declarado, `visibilityLevel` incluido. No hace falta un
> `.forbidden()` explícito: la ausencia de la propiedad ES la regla."*

**Consecuencia práctica:** un `joi.object()` sin `.unknown(true)` en la api ya rechaza
`visibilityLevel` con 400 `invalid_fields`, ahorrando el round-trip. No agregues `.forbidden()`.

#### Reglas de `validation` (verbatim, las aplicables)

- Todo endpoint con cuerpo lleva `validateBodyFields`.
- La validación de forma va **antes** de buscar entidades en la base.
- El esquema vive en el mismo archivo que la ruta.
- Esquema largo → constante nombrada arriba del archivo. Corto → inline en la cadena.
- No cambies el contrato de error: `400` con `{ code: 'invalid_fields', message: 'Invalid field - ...' }`.
- Los ids de usuario son `joi.string()`; los de entidad, `joi.number().integer()`.

### Error Handling Context

#### La forma del cuerpo (verbatim)

```json
{ "code": "access_denied", "message": "Access denied" }
```

> **`message` es texto de interfaz.** Los frontends lo muestran tal cual al usuario. Para mensajes
> nuevos que el usuario va a leer, escribilos en **español**.

En esta story **el `message` de los errores del bus lo escribe `core`, no la api**: para
`comment_not_owned` es `'Solo el autor del comentario puede editarlo'`; para `activity_not_editable`,
`'La actividad no es un comentario editable'`. `api.yaml` pone
`example: { code: comment_not_owned, message: Access denied }` — es un *example*, y el mensaje real
será el de core. No fuerces el del ejemplo.

`errorBody` (verbatim del código):


#### Reglas de `error-handling` (verbatim)

- Respondé con `res.status(n).json({ code, message })`. No introduzcas clases de error ni `throw`.
- `code` es `snake_case` y estable: los fronts hacen `switch` sobre él. **No lo renombres sin revisar
  `web` y `opus-web`.**
- `message` es texto de interfaz. Nuevos mensajes de usuario, en español.
- Nunca devuelvas el detalle de un error interno.
- Un middleware que responde **no** llama a `next()`.
- Después de `sendCommand` / `runCommand`, cortá con `if (!data) return;` / `if (!ok) return;`.
- Un `errorCode` nuevo de core se agrega a `STATUS_BY_ERROR_CODE`, o sale 500.
- Usá `logger`, nunca `console`.

### Authorization Context

#### Las tres capas (verbatim)

```
        ▼
```

`hasAnyRole` (implementación real, `lib/utils/middlewares/has-any-role.ts`):

```ts
export default function hasAnyRole(roles: Array<string>) {
  return function(req: Request, res: Response, next: NextFunction) {
    const validRole = req.decodedTokenRoles.find((role) => roles.includes(role));
    if (!validRole) {
      return res.status(403).json({ code: 'access_denied', message: 'Access denied' });
    }
    return next();
  };
}
```

> **Un endpoint sin `hasAnyRole` es alcanzable por cualquier usuario autenticado**, incluido un
> `external-user`. Para un endpoint nuevo, declará el rol explícitamente. **La ausencia no es una
> convención, es deuda.**

**Para esta story:** `api.yaml` declara `x-roles: [user, admin]` para **los dos** endpoints. La ruta
actual `objectives-id-comments-cid-patch.ts` **NO tiene `hasAnyRole`** — hay que agregarlo (deuda que
esta story cierra), y la ruta nueva nace con él.

### Relevant ADRs

#### ADR-001 — Separación lectura/escritura

**Decisión:** la `api` lee la base directamente y convierte toda mutación en un comando publicado en
NATS que atiende `core`.

**Excepciones vigentes (verbatim):** las migraciones (deliberada), la fila de `attachments` (deuda) y
`PUT /api/week-assigned-times` (deuda).

> **Excepción cerrada por REQ-011 (2026-09-01): una cuarta, no declarada.**
> `PATCH /api/objectives/{id}/comment/{cid}` escribía con `ObjectiveActivity.update(...)` directo, sin
> publicar comando, y la propia `api.yaml` lo documentaba así ("No pasa por el bus") sin que esta
> sección la enumerara — ni `NFR-S09` (`docs/prd/requirements.md`), que solo contaba dos. REQ-011
> migró ese endpoint a publicar `tasks.{id}.comment.{cid}.edit`, cerrando la excepción en vez de
> duplicarla al agregar la edición de comentarios de requisito. Las excepciones vigentes vuelven a ser
> las tres de arriba.

> **El ADR ya está escrito en tiempo pasado ("REQ-011 migró"), pero el código de la api todavía no lo
> cumple. S-047 es lo que lo vuelve verdadero.** Es literalmente la razón de ser de la story.

**Implementation Rules (verbatim, completas):**

- Toda escritura de dominio nueva **DEBE** implementarse como comando en `core`. **NO SE DEBE**
  agregar escritura con el ORM en `api`.
- La conexión de `api` **DEBE** usar credenciales sin `INSERT`/`UPDATE`/`DELETE`. Si un endpoint nuevo
  requiere escribir, la respuesta correcta es un comando, no ampliar los permisos del rol.
- La conexión de `core` **DEBE** usar el usuario dueño de la base.
- Las migraciones **DEBEN** correr desde `api` con `POSTGRESQL_MIGRATION_USER`, nunca desde `core`.
- Después de publicar un comando de creación, la api **DEBE** releer la base para armar la respuesta:
  core devuelve solo `{ id }` y el contrato con los frontends es el recurso completo con sus
  relaciones.
- Un endpoint que lee **NO DEBE** pasar por el bus: la lectura va directo a PostgreSQL desde la api.
  **Excepción declarada desde REQ-001 (S-005): la lectura de archivos.**

> **La lectura de `editedAt`/`editedBy` (CA-7) va directo a PostgreSQL desde la api, sin bus**, por la
> última regla.

#### ADR-002 — Comandos NATS sin JetStream

**Implementation Rules (verbatim, completas):**

- Todo comando **DEBE** publicarse con el subject `{instance}.{user-id}.gestion.v1.{comando}`, usando
  la gramática de `@jiku/nats-protocol`. **NO SE DEBE** construir el subject a mano.
- El cliente NATS **DEBE** fijar `inboxPrefix` explícitamente al conectar.
- El `userId` con el que publica la api **DEBE** salir de la key del service user, **NO** de una
  variable de entorno.
- Toda respuesta **DEBE** tener el formato `{ status: 'success', data }` o
  `{ status: 'failure', errorCode, errorMessage }`. **NO SE DEBEN** inventar otros formatos.
- **Los comandos de creación DEBEN devolver únicamente `{ id }`. Las ediciones y borrados, nada.**
- Todo `errorCode` nuevo **DEBE** agregarse al mapa de `api/lib/utils/bus/protocol.ts` con su status
  HTTP. Un código sin mapeo cae en un 500 genérico.
- El timeout de la request es `NATS_REQUEST_TIMEOUT_MS` (default **5000 ms**); al expirar la api
  **DEBE** responder **503**.
- **NO SE DEBE** transportar datos estructurados dentro de `errorMessage`.
- Core **NO DEBE** publicar mensajes: solo responde el `Reply` de la request que recibe.

> **Desactualización conocida del ADR:** la penúltima regla dice **503** al expirar el timeout; el
> código actual devuelve **504 `gateway_timeout`** para el timeout y reserva el 503 para *no
> responders*. `api.yaml` documenta ambos. **Seguí el código y `api.yaml`** (503 no-responders / 504
> timeout).
>
> Y la regla en negrita es la confirmación normativa de que esta story usa **`runCommand`**.

**Riesgo asumido (verbatim):** *"si core escribe y la respuesta se pierde, el cliente ve un error de
algo que sí ocurrió. Los comandos no son idempotentes, así que reintentar a ciegas puede duplicar. No
agregues reintento automático sin resolver la idempotencia primero."*

#### ADR-004 — Vocabulario `objectives` ↔ `tasks`

**Decisión (verbatim):** *"**El nombre nuevo es del contrato, no del almacenamiento.**"*

**Implementation Rules (verbatim, completas):**

- Un comando nuevo **DEBE** usar el vocabulario del producto en su contrato (`task`, no `objective`).
  La traducción a nombres de tabla vive **dentro** del comando.
- **NO SE DEBE** renombrar una tabla ni una columna existente para alinearla con el contrato.
- Toda traducción contrato ↔ base **DEBE** vivir en `core`. **NO DEBE** filtrarse a `@jiku/models`.
- El contrato HTTP de la api **NO DEBE** cambiar de vocabulario sin coordinarlo con los dos frontends:
  es el contrato público del producto.
- `priorityValue` es un escape transitorio: **NO SE DEBE** replicar el patrón.
- Al agregar un valor a un enum del bus, **DEBE** verificarse que la traducción a la base sea biyectiva.

**Consecuencia directa para esta story:**
- El **path HTTP sigue diciendo `objectives`**: `PATCH /api/objectives/:id/comment/:cid`. **No se
  renombra** (regla 4), y `/comment/{cid}` queda en singular pese a la asimetría con `/comments` del
  alta: renombrarlo rompería `web` sin beneficio y no es parte del pedido.
- El **comando dice `tasks`**: `tasks.${id}.comment.${cid}.edit` (regla 1).
- El path nuevo dice `requirements` y el comando también: no hay traducción, se llama igual en los tres
  vocabularios.

**Flujo afectado:** `docs/flows/consulta-por-el-bus.md`.

#### El `FakeBus`

Registra qué comandos publicó la api y, **por default, los ejecuta contra core con la misma base de
datos** (`tests/mocks/bus.ts`). Un solo test verifica tres cosas: qué comando se publicó y con qué
payload, que la api traduce la respuesta al HTTP esperado, y que la escritura ocurrió.

El doble **ya está instalado** para toda la corrida (`tests/setup-env.ts:31` hace `setBus(fakeBus)`), y
un root hook le hace `reset()` antes de cada test. **No llames a `setBus` en un archivo de test.**

```ts
import { fakeBus } from '../mocks/bus';

it('publica clients.new y devuelve el cliente creado', async () => {
  const res = await request(app).post('/api/clients')
    .set('Authorization', `Bearer ${token}`)
    .send({ name: 'Acme' });

  res.status.should.equal(201);
  fakeBus.last!.command.should.equal('clients.new');       // 1. el comando
  fakeBus.last!.payload.name.should.equal('Acme');
  res.body.name.should.equal('Acme');                       // 2. la traducción
  // 3. core ya escribió: el cliente existe en la base
});
```

**API completa del `FakeBus`:**

```ts
reply(command: string, reply: Reply): this        // respuesta fija para un comando
replyDefault(reply: Reply): this                  // respuesta fija para cualquiera
failWith(error: Error): this                      // falla cualquiera
failWithNoResponders(): this                      // → 503 service_unavailable
failWithTimeout(): this                           // → 504 gateway_timeout
reset(): this
get last(): SentCommand | undefined               // { command, payload }
readonly sent: SentCommand[]
```

Comentarios verbatim de los dos helpers de falla, importantes para no escribir mal el test:

> `failWithNoResponders()`: *"Simula que NO HAY NINGÚN SUSCRIPTOR del subject: el server contesta `no
> responders` en milisegundos, no al vencer el timeout. Es la señal de un problema de DESPLIEGUE, y la
> api la traduce a 503 `service_unavailable`. […] un test no puede simular la falla con un `Error`
> pelado que el `catch` de la api ya no lee como esta causa."*
>
> `failWithTimeout()`: *"Simula que LA RESPUESTA NO LLEGÓ A TIEMPO. Es un problema de PERFORMANCE, y la
> api lo traduce a 504 `gateway_timeout`. Es la única señal que toma esa rama: un `new Error('timeout')`
> NO es un timeout para el `catch` de `sendCommand`."*

## Decisiones y riesgos a resolver en implementación

Tres puntos que el implementador **tiene que ver antes de escribir código**, porque cambian el
comportamiento observable y no son evidentes desde los criterios de aceptación.

### D-1 · `comment_not_found` no está en `STATUS_BY_ERROR_CODE` — hay que agregarlo

La story pide dos entradas nuevas (CA-6). **Hacen falta tres.**

Hoy `findObjectiveActivity` resuelve el comentario inexistente localmente y responde **400
`comment_not_found`**, y el test existente lo afirma. Cuando la ruta pase a publicar el comando, ese
caso lo responde `core` con `failure(ErrorCode.COMMENT_NOT_FOUND, ...)` — y **`comment_not_found` NO
está en el mapa**, así que `httpStatusFor` cae en `|| 500`.

Sin la tercera entrada, un comentario inexistente pasa de **400 a 500**, rompiendo el contrato
documentado (`api.yaml`: *"Validación fallida, la tarea o el comentario no existen…"* bajo `'400'`) y
el comportamiento que `web` ya maneja.

**Decisión tomada:** agregar `comment_not_found: 400`, alineado con `api.yaml` y con el comportamiento
actual. (El comentario del protocolo de core menciona un mapeo previsto de 404 para los códigos de
consulta, y `core.yaml:1610` afirma que ya tiene mapeo desde `comments.get` — **eso es falso en el
árbol actual**. Se resuelve por lo que dice `api.yaml`, que es la fuente de verdad del contrato HTTP.)

### D-2 · `previousValue` deja de escribirse — cambio de comportamiento observable

La api vieja copiaba el texto anterior a `previousValue` (`objectives-id-comments-cid-patch.ts:68`).
**El comando de core NO escribe `previousValue`** — comentario verbatim: *"`previousValue` no aparece
(CA-11)"*, porque ahora la marca de edición son `editedAt`/`editedBy`.

El test existente afirma `previousValue: 'New Comment'` después de editar
(`tests/routes/objectives-id-comments-cid-patch.test.ts:144`). **Ese assert va a fallar, y es correcto
que falle**: se actualiza al comportamiento nuevo (`previousValue` queda como estaba, `editedAt` no es
null). No es un test a "arreglar" en silencio — va al changelog de publicación.

### D-3 · El `code` del 403 cambia: `forbidden` → `comment_not_owned`

Hoy el no-autor recibe `403 { code: 'forbidden', message: 'You do not have permission to edit this
comment' }`, generado por la api. Después de la migración recibe
`403 { code: 'comment_not_owned', message: 'Solo el autor del comentario puede editarlo' }`, generado
por core.

El status no cambia, pero **el `code` sí**, y la regla de `error-handling` es explícita: *"`code` es
`snake_case` y estable: los fronts hacen `switch` sobre él. No lo renombres sin revisar `web` y
`opus-web`"*. La Task 6 incluye la verificación de que ningún front hace `switch` sobre `'forbidden'`
en este flujo. Va al changelog junto con el cambio de permisos del admin (CA-5), que es el otro cambio
observable: hoy recibe 403 y pasa a poder editar.

### Task 1: Mapear los códigos de error nuevos en `STATUS_BY_ERROR_CODE`

#### Description

Agregar al mapa `STATUS_BY_ERROR_CODE` de `api/lib/utils/bus/protocol.ts` los códigos que los comandos
de edición de comentario emiten desde `core`. Sin estas entradas, `httpStatusFor` cae en `|| 500` y el
front trata un permiso o una validación como error de servidor.

Va **primera** porque las tasks 2 y 3 dependen de ella para que sus tests de error den el status
correcto: sin el mapa, TS-28 a TS-32 devuelven 500.

**Son tres entradas, no dos.** La story pide dos (CA-6), pero `comment_not_found` tampoco está en el
mapa y hoy lo resuelve la api localmente con 400. Cuando la ruta pase a publicar el comando, ese caso
pasa a venir de core y sin entrada saldría 500. Ver la decisión **D-1** en la sección de decisiones.

#### Acceptance Criteria

1. `STATUS_BY_ERROR_CODE` contiene `comment_not_owned: 403`.
2. `STATUS_BY_ERROR_CODE` contiene `activity_not_editable: 400`.
3. `STATUS_BY_ERROR_CODE` contiene `comment_not_found: 400`.
4. Cada entrada nueva lleva un comentario en español que explica **por qué** ese status, siguiendo el
   estilo denso del archivo (el modelo es la entrada de `file_not_owned`).
5. `httpStatusFor('comment_not_owned')` devuelve `403`, `httpStatusFor('activity_not_editable')`
   devuelve `400` y `httpStatusFor('comment_not_found')` devuelve `400`.
6. Ninguna entrada existente cambia de valor.

#### Technical Details

**Architectural Context References:**
- **ADR-002, Implementation Rule:** *"Todo `errorCode` nuevo **DEBE** agregarse al mapa de
  `api/lib/utils/bus/protocol.ts` con su status HTTP. Un código sin mapeo cae en un 500 genérico."*
- **Error Handling Context** → `STATUS_BY_ERROR_CODE`, estado actual del archivo copiado verbatim.
- **Decisión D-1** — la tercera entrada y su justificación.
- Los códigos ya existen en `@jiku/nats-protocol`
  (`packages/nats-protocol/src/index.ts:365-366`): `COMMENT_NOT_OWNED: 'comment_not_owned'`,
  `ACTIVITY_NOT_EDITABLE: 'activity_not_editable'`. **No hay que agregarlos al paquete.**

**Files to Create/Modify:**
- `lib/utils/bus/protocol.ts` — agregar las tres entradas al mapa.
- `tests/utils/bus/protocol.test.ts` — si existe, sumar los casos; si no, crearlo siguiendo el patrón
  de `tests/utils/`.

**Implementation Notes:**
- El mapa usa **literales string** como claves, no las constantes del enum. Seguí el estilo del archivo.
- `comment_not_owned` es **403 y no 400** por la misma razón que `file_not_owned`: describe un
  **permiso** (el comentario existe y está bien formado, pero lo escribió otra persona), no una entrada
  inválida. Ese es el argumento a escribir en el comentario.
- `activity_not_editable` es **400**: la actividad existe pero no es de un tipo editable — es una
  precondición sobre el dato, no un permiso.
- `comment_not_found` es **400 y no 404** por coherencia con `requirement_not_found`, que ya está en
  400 en el mapa, y con lo que declara `api.yaml` para estos endpoints.
- El mapa es **del servicio, no del endpoint**: una vez agregada, la entrada aplica a cualquier ruta que
  reciba ese código.

**Dependencies:**
- Ninguna externa. `@jiku/nats-protocol` ya está en el `package.json` del servicio.

### Task 2: Migrar `PATCH /api/objectives/{id}/comment/{cid}` a publicar el comando

#### Description

Reescribir `lib/routes/objectives-id-comments-cid-patch.ts` para que publique
`tasks.{id}.comment.{cid}.edit` en vez de escribir con `ObjectiveActivity.update(...)`. Esto cierra la
cuarta excepción no declarada a ADR-001: es la razón de ser de la story.

La ruta pierde la escritura con el ORM, la transacción, el chequeo de autoría y la copia a
`previousValue`; y gana `hasAnyRole`, `fileIds` y las respuestas 503/504 que hereda toda ruta que
publica comandos. **La URL no cambia** (`/comment/{cid}` en singular): renombrarla rompería `web` sin
beneficio y no es parte del pedido (ADR-004, regla 4).

Tres cambios de comportamiento observables, todos deliberados: el admin pasa de 403 a poder editar
(CA-5), el `code` del 403 del no-autor cambia de `forbidden` a `comment_not_owned` (**D-3**), y
`previousValue` deja de escribirse (**D-2**).

#### Acceptance Criteria

1. El handler usa `runCommand(res, \`tasks.${req.params.id}.comment.${req.params.cid}.edit\`, payload)`
   y corta con `if (!ok) { return; }`.
2. La respuesta de éxito sigue siendo exactamente
   `200 { code: 'comment_updated', message: 'Comment Updated' }`.
3. El archivo **no importa ni usa** `ObjectiveActivity` para escribir, ni `transactionStart`, ni
   `transactionCommit`. La función `saveNewValue` se elimina.
4. El chequeo `objectiveActivity.changedBy !== req.user.id` que respondía `403 forbidden` se elimina:
   la autoría la valida `core`.
5. La cadena declara `hasAnyRole(['user', 'admin'])` como primer middleware, según `x-roles` de
   `api.yaml`.
6. El esquema Joi acepta `comment` (string, requerido) y `fileIds` (array de enteros positivos, máx.
   10, opcional). **No declara `visibilityLevel`** y el objeto no lleva `.unknown(true)`.
7. `fileIds` se reenvía con **spread condicional por presencia**
   (`...(req.body.fileIds !== undefined ? { fileIds: req.body.fileIds } : {})`), de modo que un `[]`
   explícito viaja y un campo ausente no.
8. El payload lleva `editor: actorId(req)` como campo de dominio. **No** arma el sobre a mano.
9. Se elimina el middleware `findObjectiveActivity` (core responde `comment_not_found` y
