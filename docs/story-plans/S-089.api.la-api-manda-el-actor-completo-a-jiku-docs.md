# Story Plan: S-089 (api) - La api manda el actor completo a jiku-docs

## Status

**Status:** Completed

**Progress:** 3/3 tareas completadas

## Story Reference

- **Story:** [S-089](../stories/S-089.api-manda-el-actor-completo-a-jiku-docs.md)
- **Service:** `api`
- **Origen:** [REQ-019](../requests/REQ-019.actor-completo-hacia-jiku-docs-y-ajustes-del-portal-de-documentos.md)
  (DD-1 a DD-5, RF-1 a RF-5)
- **Summary:** El embudo `call()` de `api/lib/modules/client.ts` deja de publicar `actor: { id }` y
  publica el `actor` **entero** que devuelve `buildActor(res.req)` — `{ id, roles, name?, username?,
  email? }`, el mismo sobre que recibe core —, inyectado después del spread (gana el del token) y
  fallando cerrado (401 sin publicar) sin identidad verificada. Las rutas públicas `/p/docs/*`
  (`shares.resolve` / `shares.attachment` vía `sendToModule`) siguen sin `actor`. Se actualizan el
  JSDoc, los tests unitarios del embudo y las ~34 aserciones de `actor` de `tests/routes/docs-*` y
  `opus-docs-*` (con un helper `expectedActor(token)`).

> **Precondición verificada sobre el árbol (2026-10-25, rama `feat/jiku-docs`, `13b798e`):**
> - `api/lib/modules/client.ts:72-79` arma `const id = buildActor(res.req)?.id; ... body = { ...payload, actor: { id } };`.
> - `api/lib/utils/bus/actor.ts` exporta `buildActor(req)` (named y default) y devuelve
>   `{ id, roles, name?, username?, email? }` o `undefined` sin `sub` no vacío. **No se toca.**
> - `lib/utils/middlewares/validate-token.ts:113` llena `req.decodedTokenRoles = getRolesFromToken(...)`
>   y arma `req.user` del claim sin consultar `users` (S-034): un `sub` sin fila opera igual.
> - `actor` aparece en 23 archivos de `tests/routes/docs-*` / `opus-docs-*` (34 líneas, 12 de ellas
>   como `const ACTOR = { actor: { id: 'zitadel-sub-01' } };`) y en `tests/utils/module-client.test.ts`
>   (TS-22, TS-25, TS-26, TS-27 de S-077).
> - Ningún token del mock salvo `token_05_user_profile` trae `name` / `preferred_username` / `email`.

### Fuera de alcance (declarado, para no improvisarlo)

- **`getRolesFromToken` (`lib/utils/auth-helper.ts:94`) no se toca** (DD-5, CA-6). La api no acepta
  tokens de machine users ni lee claims de roles por proyecto.
- **`buildActor` (`lib/utils/bus/actor.ts`) no se toca**: se reusa tal cual. No se agrega
  `identityType` ni ningún campo.
- **No se reusa `withActor`** (`lib/utils/bus/send-command.ts`): sin identidad devuelve el payload sin
  `actor` (falla abierto), y para jiku-docs un llamado sin `actor` es el propio servicio. La razón
  cambia (ya no es `invalid_fields`), la conclusión no (DD-1).
- **`sendToModule`, `public-share.ts` y la opción `anonymous`** no cambian (DD-4).
- **Contrato HTTP sin cambios**: `docs/apis/api.yaml` no se toca; rutas, status y cuerpos iguales.
- **Sin cambios de base de datos, variables de entorno, dependencias npm ni `@jiku/nats-protocol`.**
- **La documentación (`docs/`)** es del plan `S-089.docs`. Este plan solo cambia código y tests de
  `api/`.

### Convenciones aplicables (extracto)

**`_base`:**
- TypeScript obligatorio, `strict` apagado; `any` permitido en los bordes con payloads del bus.
- Imports relativos (`../utils/bus/actor`), sin extensión, sin alias de `module-alias`.
- Comentá en español, y comentá el **por qué**.
- Lint antes de dar por terminado: `npm run lint --workspace @jiku/api` (cubre solo `./lib`).

**`bus-modules` (reglas vigentes que se mantienen):**
- Usá `moduleQuery` / `moduleCommand` / `runModuleCommand`. Después de la llamada, `if (!data) return;`.
- **Nunca** armes el `actor` a mano ni lo tomes del cuerpo: lo inyecta el embudo.
- **Nunca** llames a un módulo sin identidad verificada: el embudo responde 401 y no publica.
- **Nunca** loguees `payload`, `options`, el token de un link ni el contenido de un documento. El error
  de bus se loguea como `[modules] {module} {method}: {error.message}`.
- Una ruta que responde HTML (pública) usa `sendToModule`, no `moduleQuery`.
- La regla "inyecta el embudo, **solo con `id`**" es la que **cambia** con esta story: pasa a ser
  "inyecta el embudo **el `actor` de `buildActor(res.req)` entero**". La convención escrita la
  actualiza el plan `S-089.docs`; el código de este plan manda.

**`testing`:**
- Toda ruta de un módulo opcional usa `itRespectsModuleState` y verifica el `actor` publicado
  (hoy "`{ id }` y nada más"; con esta story, **exactamente** `buildActor` del token — `deepEqual`,
  sin campos extra).
- `fakeBus.moduleSent` (`{ kind, method, subject, payload }`) y `fakeBus.lastModule` son lo publicado.
- `itRespectsModuleState(getApp, url, token)` agrega el 404/503 sin publicar.
- Aserciones con `should`. No mezcles `assert` ni `expect`. Un test no depende del orden ni del estado
  que dejó otro.
- `tests/register-jwt-mock.ts` instala el mock de `jsonwebtoken`; los tokens son claves de
  `tests/mocks/jsonwebtoken-mock.ts`.

### ADRs relevantes

**ADR-007: Identidad con Zitadel y auth callout** — *Implementation Rules* (extracto aplicable, verbatim):
- La api **DEBE** validar los tokens de usuario contra el JWKS de Zitadel, con resincronización
  ante `kid` desconocido (`KEY_SYNC_ATTEMPS` reintentos).
- Los roles **DEBEN** leerse del claim `urn:zitadel:iam:org:project:{PROJECT_ID}:roles`.
  **NO SE DEBEN** almacenar roles en la base ni derivarlos de otra fuente.

→ `actor.roles` sale de `req.decodedTokenRoles` vía `buildActor`; **nunca** de `req.user` ni de `users`.

**ADR-008: Autorización deny-by-default** — *Implementation Rules* (extracto aplicable, verbatim):
- `validateToken` **DEBE** instalarse globalmente en `app.ts`. **NO SE DEBE** declarar
  autenticación ruta por ruta.
- Un endpoint que requiere rol **DEBE** declarar `hasAnyRole([...])` explícitamente. La
  autenticación global no implica autorización.
- Un endpoint accesible a `external-user` **DEBE** además verificar permiso de proyecto: el rol
  solo no alcanza ([ADR-006](ADR-006-dos-frontends-una-api.md)).

→ `roles: []` no autoriza nada; es el valor correcto sin claim.

**ADR-015: Módulos opcionales del bus** — *Implementation Rules* (verbatim, estado actual del árbol):
- Toda llamada a un módulo **DEBE** pasar por `api/lib/modules/client.ts`
  (`moduleQuery`/`moduleCommand`/`runModuleCommand`, o `sendToModule` en las rutas que responden
  HTML). **NO SE DEBE** hablar con un módulo desde un handler con `bus()` directo.
- **NO SE DEBE** usar `sendCommand` ni `withActor` con un módulo: su sobre (`roles`, `name`…) es
  `invalid_fields` para jiku-docs.
- El `actor` **DEBE** ser solo `{ id }` y **DEBE** inyectarlo el embudo, después del spread del
  payload. Sin identidad verificada el embudo **DEBE** fallar cerrado (401 sin publicar). **NO SE
  DEBE** llamar a un módulo sin `actor` salvo en una ruta pública deliberada
  (`shares.resolve`/`shares.attachment`).
- Toda ruta de módulo **DEBE** llevar `requireModule('<módulo>')` **antes** de `hasAnyRole`.
- El mapa de errores **DEBE** ser **por módulo** (`docs/errors.ts`); **NO SE DEBE** mezclar con
  `STATUS_BY_ERROR_CODE` de core. El cuerpo **DEBE** ser `{ code, message, details? }` con `code`
  sin traducir y `details` verbatim.
- **NADA se compila con el nombre del servicio**: el `serviceName` sale del registro. El
  `serviceName` **DEBE** validarse (`^[a-z][a-z0-9-]{1,40}$`) antes de armar un subject.
- Agregar un módulo o cambiar su `serviceName` **DEBE** acompañarse de la edición de las plantillas
  del callout (`deploy/nats/auth-callout/templates/`): es un cambio de seguridad y se revisa como tal.
- El cliente del KV **DEBE** abrirse con `bindOnly: true` **y** `allow_direct: true`.
- El estado del módulo **NO DEBE** persistirse ni compartirse entre réplicas.
- La api **NO DEBE** autorizar el dominio de un módulo (ACL, visibilidad): solo autentica, rutea
  por superficie y traduce errores.
- `/p/docs/*` **NO DEBE** loguearse con el token en la URL (`ignoreRoute` en el logger de requests;
  línea propia con `jds_…` enmascarado). **NO DEBE** loguearse la `downloadUrl` ni el `htmlUrl`.
- El host público **NO DEBE** servir nada más que `GET`/`HEAD` de `/p/docs/*`
  (`publicHostOnly` va primero en `app.ts`). La comparación **DEBE** hacerse contra el `Host` crudo,
  nunca contra `X-Forwarded-Host`.
- Toda respuesta de `/p/docs/*` **DEBE** llevar las cinco cabeceras de `PUBLIC_DOCS_HEADERS` y el
  404 **DEBE** ser el mismo para cualquier link inválido.
- Cualquier cambio en `api/config/public.ts` es un **cambio de seguridad** (ADR-008).

> **Reglas 2 y 3 revisadas por REQ-019 (DD-1).** Con esta story pasan a leerse así (el texto del ADR
> lo reescribe el plan `S-089.docs` como revisión fechada):
> - **NO SE DEBE** usar `sendCommand` ni `withActor` con un módulo: `withActor` falla **abierto** sin
>   identidad, y un llamado a jiku-docs sin `actor` es el propio servicio.
> - El `actor` **DEBE** ser `buildActor(res.req)` **sin transformar** (`{ id, roles, name?, username?,
>   email? }`) y **DEBE** inyectarlo el embudo, después del spread del payload. El resto de la regla
>   (falla cerrado, sin `actor` solo en `shares.resolve`/`shares.attachment`) no cambia.

### API Context

**Contrato HTTP:** sin cambios. Las rutas afectadas (solo por el payload del bus) son las 20
`/api/docs/*`, las 3 `/api/opus/docs/*` (todas pasan por `moduleQuery` / `moduleCommand` /
`runModuleCommand`). Error local del embudo sin identidad (sin cambios):

```
401 { "code": "unauthorized", "message": "Unauthorized" }
```

**Payload del bus hacia jiku-docs** (toda consulta o comando de `call()`):

```
actor: { id }                                         - ELIMINADO
actor: { id, roles, name?, username?, email? }        + NUEVO (= buildActor(res.req))
```

Ejemplo (`documents.list` con `token_01_user` del mock):

```
antes:  { filter: {...}, sort, page, include: ['lock'], actor: { id: 'zitadel-sub-01' } }
ahora:  { filter: {...}, sort, page, include: ['lock'], actor: { id: 'zitadel-sub-01', roles: ['user'] } }
```

`shares.resolve` / `shares.attachment` (`public-share.ts`, vía `sendToModule`): sin cambios, sin
`actor`, con `client: { ip, userAgent }`.

**Tipo `Actor`** (`@jiku/nats-protocol`, verbatim resumido de `packages/nats-protocol/src/index.ts:701`):

```ts
export interface Actor {
  id: string;        // el `sub` de Zitadel, PK de `users` (NO es personId)
  roles: string[];   // del claim ya verificado; obligatorio; sin claim va []
  name?: string;
  username?: string; // del claim `preferred_username`
  email?: string;
}
```

**`buildActor`** (`api/lib/utils/bus/actor.ts`, sin cambios): `sub` vacío o ausente → `undefined`;
`roles = req.decodedTokenRoles ?? []`; `name`, `username` (de `preferred_username`), `email` solo si son
strings no vacíos (la ausencia se propaga como **ausencia de la clave**, no `undefined` presente). No
agrega `identityType`. No lee `req.user`.

### Flow Context

**`documentos-desde-la-web`** (párrafo de identidad, verbatim del estado actual):

> Todas las llamadas se hacen **en nombre de la persona**, con `actor: { id }` (solo el `id`), por el
> embudo `api/lib/modules/client.ts`. La api **no autoriza el dominio**: el ACL de carpetas lo
> resuelve jiku-docs con ese `actor`.

| Servicio | Rol | Tipo de Participación |
|---|---|---|
| `api` (`lib/routes/docs-*.ts`, `opus-docs-*.ts`, `lib/modules/`) | Valida rol y forma, firma como la persona (`actor: { id }`), traduce el sobre `Reply` a HTTP | Procesador |
| jiku-docs (externo) | Dueño de documentos, carpetas, versiones, reservas y adjuntos; resuelve permisos | Procesador |

**Lo que cambia en el flujo** (escenario de la story, un externo abre el tablero del portal):

1. **opus-web** — `DocsSection` → `useDocuments` → `GET /api/opus/docs/documents?projectId={id}`.
2. **api** — `requireModule` → `hasAnyRole(['external-user','admin','user'])` → forma →
   `loadDocsScope` → `validateProjectPermissions` → handler con `filter.visibility: 'public'` forzado;
   `moduleQuery(res, 'docs', 'documents.list', {...})`.
3. **api / `call()`** — `respondIfModuleNotReady`; `actor = buildActor(res.req)`; sin `actor` → 401 sin
   publicar; si no, publica `{ ...payload, actor }` con
   `actor = { id, roles: ['external-user'], name?, username?, email? }`. **← paso modificado**
4. **jiku-docs** — clasifica con `actor.roles` (`external-user` → `person-external`) sin depender de la
   fila de `users`; consulta `project-permissions` a core.
5. **api** — `success` → 200; `failure` → mapa de `docs/errors.ts` (`caller_not_authorized` → 403).

Errores: sin identidad → 401 sin publicar; no instalado → 404 `module_not_installed`; caído → 503
`module_unavailable`; timeout → 504 `gateway_timeout`. **Sin cambios.**

**`lectura-por-link-compartido`**: `shares.new` (alta de link, `POST /api/docs/documents/:id/shares`)
pasa al `actor` completo por el mismo embudo; `shares.resolve` / `shares.attachment` **sin cambios**.

### Integration Points

- **jiku-docs (externo)** por NATS: subjects `{env}.{userId}.jiku-docs-queries.v1.{method}` y
  `{env}.{userId}.jiku-docs-commands.v1.{method}` (el `serviceName` sale del registro `JIKU_MODULES`).
  Contrato `Actor` de jiku-docs con D-11: `{ id, roles, name?, username?, email? }`. Clasificación:
  `admin`/`user` → `person-internal`, `external-user` → `person-external`, otro → sin acceso.
- **Riesgo de despliegue (no es código de este plan):** con un jiku-docs anterior a D-11 (`Actor` con
  `additionalProperties: false` y solo `id`), toda llamada responde `invalid_fields` (400). Sin
  compatibilidad hacia atrás. Lo documenta el plan `S-089.docs` (ADR-015) y la release (CHANGELOG,
  *Notes for existing installations*).
- **Datos personales en el bus:** `name`, `username`, `email` viajan ahora a jiku-docs. El embudo
  **sigue sin loguear `payload`** (TS-17 lo blinda).
