**Patrones arquitectónicos que aplican a esta story:**

- **Datos en tres capas:** componente cliente → hook de TanStack Query → Server Action
  (`'use server'`) → `apiClient` (axios de servidor, interceptor que agrega el `Bearer`).
  **El token nunca llega al navegador.**
- **Excepción del BFF:** `PATCH /api/requirements/[reqid]` es un route handler y no una Server
  Action, **porque el update optimista de TanStack Query necesita rollback en el cliente**. Es uno
  de los tres casos justificados por escrito en la convención `api-routes`.
- **Estilos:** Sass + CSS Modules, sin librería de componentes. Los botones de la card de
  resolución son `<button>` nativos con clases del módulo, no el componente `<Button>` compartido.
- **Error handling:** tres niveles — `ApiError` normalizado en el interceptor de axios,
  `toast.error(...)` en el `onError` del `mutate` para errores de acción, y `error.tsx` por ruta
  para excepciones de render. Esta story opera en el nivel 2 (toast).

### Convenciones activas (todas custom, en `docs/architectures/web/conventions/`)

**`data-fetching` — query keys que importan acá:**

| Key | Dónde |
|---|---|
| `['requirements', filters]` | `useRequirements` |
| `['requirement', reqid]` | `useRequirement` |

Regla: el singular es el ítem y el plural la colección. Invalidar `['requirements']` invalida todos
los listados filtrados, porque TanStack Query hace match por prefijo.

Configuración del cache (`src/lib/queryClient.ts`):
```ts
queries:   { staleTime: 30_000, gcTime: 300_000, retry: 1,
             refetchOnReconnect: true, refetchOnWindowFocus: true }
mutations: { retry: 0 }
```
**`retry: 0` en mutations es deliberado:** reintentar una escritura que ya pudo aplicarse duplica
registros.

**`mutations` — update optimista:**

`useUpdateRequirement` es el único caso del servicio con update optimista, y es el que justifica el
BFF de escritura. El trío va completo:

```ts
onMutate: async ({ reqid, payload }) => {
  await queryClient.cancelQueries({ queryKey: ['requirement', reqid] });
  const previousRequirement = queryClient.getQueryData<Requirement>(['requirement', reqid]);
  if (previousRequirement) {
    queryClient.setQueryData(['requirement', reqid], { ...previousRequirement, ...payload });
  }
  return { previousRequirement };
},
onError: (_error, { reqid }, context) => {
  if (context?.previousRequirement) {
    queryClient.setQueryData(['requirement', reqid], context.previousRequirement);
  }
},
onSuccess: (_data, { reqid }) => {
  queryClient.invalidateQueries({ queryKey: ['requirements'] });
  queryClient.invalidateQueries({ queryKey: ['requirement', reqid] });
},
```

**Regla:** si se agrega otro update optimista, el trío `onMutate` / `onError` / `onSuccess` va
completo. Un `onMutate` sin rollback en `onError` deja la UI mintiendo.

Feedback en el componente: un toast de éxito y uno de error por acción del usuario; el mensaje
prioriza `err.message` de la api y cae a un texto propio. El hook **no** navega ni muestra toasts.

**`state-management` — árbol de decisión:**

```
¿De dónde viene el dato?
├── De la api ────────────> TanStack Query. NUNCA copiarlo a useState
├── Define qué se ve y
│   querés que sea
│   compartible ─────────> searchParams (router.push)
├── Sesión ──────────────> useSession() / auth()
└── Solo le importa a este
    componente ──────────> useState / useReducer
```

**Regla dura: no copiar datos de query a `useState`.** *La excepción legítima son los borradores de
formulario* — un formulario de edición sí copia el valor de la query a estado local, porque el
usuario lo está modificando y el cache no debe seguirlo. En ese caso el patrón es inicializar con
un initializer de `useState`, no con un efecto:

```tsx
// SÍ — RequirementStatusCard.tsx:231
const [drafts, setDrafts] = useState<FieldDrafts>(() => draftsFromRequirement(requirement));
```

**Esta excepción es exactamente el caso de los tres campos de resolución de esta story.**

**`styling`:** Sass + CSS Modules + custom properties. El accent de la superficie es
`--color-button` (`#DA2C6A`). No agregar un sexto valor de breakpoint (los 6 que existen ya son
deuda documentada).

**`testing-unit`:**

```ts
// vitest.config.mts
test: {
  environment: 'jsdom',
  globals: true,
  setupFiles: ['./tests/setup.ts'],
  env: { TZ: 'UTC' },
}
```

- **`TZ: 'UTC'` no se toca.** Un literal `'2026-08-01'` se parsea como medianoche UTC, que al oeste
  de Greenwich es el día anterior: sin esto los tests pasan en Argentina y fallan en CI.
- Los tests viven **junto al archivo que testean**, como `{Nombre}.test.tsx`.
- `globals: true`: `describe`, `it`, `expect` y `vi` sin importar. Los tests existentes de este
  módulo igualmente importan explícitamente de `vitest`; seguir el estilo del archivo que se toca.
- Los nombres de los `it` van **en español**, como el resto del módulo.

**`error-handling`:** el error que llega a un componente es siempre un `ApiError`
(`{ code, message, status }`) cuando pasa por `apiClient`. Los errores del BFF (fetch contra
`/api/...`) no pasan por el interceptor: `patchRequirement` lanza un `Error` con
`err?.message ?? 'Error al actualizar el requisito'`.

### API Context

**Endpoint que esta story consume (sin modificarlo):**

`PATCH /requirements/{reqid}` — *Edita un requisito*. Publica `requirements.{id}.edit` y rearma la
respuesta. Roles: `[user, admin]`.

> **REQ-012 — la secuencia de estados (C-15) se deroga; C-17 se acota de nuevo a `incidencia`.**
>
> - **C-15** (la secuencia de estados): `core` deja de validar secuencia: un requisito alcanza
>   cualquier estado desde cualquier otro, hacia adelante o atrás, incluidos `resuelto` y
>   `cancelado` (dejan de ser terminales). `invalid_state_transition` **deja de emitirse** para
>   requisitos — ya no aparece entre los códigos que este endpoint puede devolver.
> - **C-17** (tipo + conclusión al resolver) la sigue aplicando `core` en `requirements.{id}.edit`
>   **y** en `.resolve`, con el mismo validador, pero **solo cuando `type === 'incidencia'`**. Para
>   `funcionalidad`, `mejora` y `otro` ambos campos son siempre opcionales. Devuelve
>   `resolution_required` cuando falta, con el mismo status **400**.

**Request body (campos relevantes para esta story):**

```yaml
type: object
properties:
  title: { type: string }
  description: { type: string }
  type: { $ref: RequirementType, nullable: true }
  priority: { $ref: RequirementPriority }
  estimatedFinishDate: { type: string, format: date }
  state: { $ref: RequirementState }
  resolutionType: { $ref: RequirementResolution, nullable: true }
  resolutionConclusion: { type: string, nullable: true }
  resolutionComment: { type: string, nullable: true }
  visibilityLevel: { $ref: VisibilityLevel }
  responsiblePersonIds: { type: array, nullable: true, items: integer }
  scope: { type: string, nullable: true }
  technicalSolution: { type: string, nullable: true }
  acceptanceCriteria: { type: string, nullable: true }
  tags: { type: array, nullable: true, items: Tag }
  fileIds: { $ref: FileIds }
```

**Responses:**

| Status | Contenido |
|---|---|
| `200` | `RequirementWithRelations` |
| `400` | Validación fallida, `resolution_required`, o un código de core traducido a 400. Ejemplo: `{ code: "resolution_required", message: "Se requiere tipo y conclusión para resolver una incidencia" }` |
| `401` | Unauthorized |
| `403` | AccessDenied |
| `404` | RequirementNotFound |
| `500` | InternalError |
| `503` | BusUnavailable — `"El servicio no está disponible en este momento"` |
| `504` | GatewayTimeout — `"La operación tardó demasiado"` |

**`invalid_state_transition` ya no es un código posible de esta respuesta.** Esta story no debe
manejarlo ni mencionarlo.

**El camino real desde el navegador** — no es el endpoint de `api` directo, sino el BFF:

```ts
// web/src/app/api/requirements/[reqid]/route.ts
export const PATCH = async (request, { params }) => {
  const token = await decodedToken();
  if (!token?.accessToken) return NextResponse.json({ error: 'Unauthorized' }, { status: 401 });
  const { reqid } = await params;
  const body = await request.json();
  const response = await fetch(`${process.env.API_URL}api/requirements/${reqid}`, {
    method: 'PATCH',
    headers: { Authorization: `Bearer ${token.accessToken}`, 'Content-Type': 'application/json' },
    body: JSON.stringify(body),
  });
  const data = await response.json().catch(() => ({}));
  return NextResponse.json(data, { status: response.status });
};
```

El handler **propaga status y body sin transformarlos**: el `code`/`message` de la api llega tal
cual al cliente.

### Flow Context

**Flujo afectado:** `escritura-por-el-bus` — sin cambios adicionales a los descritos en S-049. Esta
story no toca el bus: consume la api HTTP, que ya publica `requirements.{id}.edit`.

**Cadena completa de una transición de estado desde esta pantalla:**

```
RequirementHeader / RequirementStatusCard / RequirementResolutionCard
   │  onUpdate(payload)
   ▼
RequirementDetail.handleUpdate  → mezcla basePayload + payload
   │
   ▼
useUpdateRequirement.mutate({ reqid, payload })
   │  onMutate: setQueryData(['requirement', reqid], {...previous, ...payload})   ← optimista
   ▼
fetch PATCH /api/requirements/{reqid}          (BFF de web)
   ▼
PATCH {API_URL}api/requirements/{reqid}        (api, con Bearer)
   ▼
requirements.{id}.edit                          (bus → core)
   │  core: valida resolution_required SOLO si type === 'incidencia'
   │  core: si sale de `resuelto` hacia un estado no terminal → limpia los 3 campos de resolución
   ▼
200 RequirementWithRelations
   │  onSuccess: invalidate ['requirements'] y ['requirement', reqid]
```

**`basePayload` de `RequirementDetail` (se mezcla en TODA mutación de esta pantalla):**

```ts
const basePayload: UpdateRequirementPayload = {
  title: requirement.title,
  description: requirement.description,
  type: requirement.type,
  priority: requirement.priority,
  state: requirement.state,
  tags: localTags,
  ...(requirement.estimatedFinishDate && { estimatedFinishDate: requirement.estimatedFinishDate }),
};
```

**Dato que importa para "Reabrir":** `basePayload` **no incluye** `resolutionType`,
`resolutionConclusion` ni `resolutionComment`. Por lo tanto un `onUpdate({ state: 'desarrollo' })`
NO reenvía esos campos, y la limpieza del servidor (S-049) opera sin interferencia. Esto es
correcto y **no debe cambiarse**: `core` aplica `changes.resolutionX = payload.resolutionX ?? null`
al reabrir, así que un valor explícito en el payload **ganaría** sobre la limpieza.

**Comportamiento de `core` al reabrir (S-049, ya implementado — para entender el contrato, no para
modificarlo):**

```ts
const leavesResolved = requirement.state === RequirementState.Resuelto
  && payload.state !== undefined
  && payload.state !== RequirementState.Resuelto
  && payload.state !== RequirementState.Cancelado;

if (leavesResolved) {
  changes.resolutionType = payload.resolutionType ?? null;
  changes.resolutionConclusion = payload.resolutionConclusion ?? null;
  changes.resolutionComment = payload.resolutionComment ?? null;
}
```

**La limpieza solo se dispara saliendo de `resuelto`.** Un requisito en `cancelado` que se reabre
**no** limpia nada (nunca tuvo datos de resolución que limpiar por esa vía).

### Microcopy real de los bloques afectados

**pill-estado**
- Texto/label: el estado actual · opciones `"Análisis"` · `"Planificación"` · `"En cola"` ·
  `"Desarrollo"` · `"Revisión"` · `"Resuelto"` · `"Cancelado"`
- Annotation: **el update es optimista** (`useUpdateRequirement.ts:36-43`), así que el valor cambia
  en pantalla antes de la confirmación de la api, con rollback ante error. **Desde REQ-012 la lista
  es siempre la misma: los siete estados, sin recorte y sin excepción por tipo.** El descarte de
  `"En cola"` para `type: 'incidencia'` (`RequirementHeader.tsx:161-166`, `:23-30`) **se elimina**:
  era el reflejo en la UI de la secuencia que `core` dejó de validar, y sostenerlo dejaría a la
  pantalla impidiendo algo que el servidor ya acepta. La pill tampoco se deshabilita en `resuelto`
  ni en `cancelado`: son estados de los que ahora se sale [REQ-012 RF-1, RF-2, RF-12, CA-6]

**stepper-workflow**
- Texto/label: sin texto propio — contiene los 5 nodos
- Annotation: **Flujo de trabajo** (`NEXT_WORK_STEP`): `analisis → planificacion → en_cola →
  desarrollo → revision`. Para incidencias (`NEXT_WORK_STEP_INCIDENCIA`):
  `analisis → planificacion → desarrollo → revision`, salteando `en_cola`. **Desde REQ-012 esa
  secuencia describe el recorrido habitual, no lo permitido**: el stepper sigue mostrando los cinco
  pasos de trabajo en su orden —es cómo el equipo lee dónde está un requisito— pero ya **no recorta
  a dónde se puede ir**. Cualquier estado se alcanza desde la pill; **el stepper informa, la pill
  decide** [REQ-012 RF-1, RF-12]

**boton-transicion**
- Annotation: con siguiente paso disponible convive con `"Guardar"` y hace las dos cosas en una
  acción. **Desde REQ-012 el botón es un atajo al paso siguiente, no la única salida.** En
  `Revisión` sigue sin haber paso siguiente dentro del recorrido de trabajo, así que `"Guardar"`
  queda solo; en `Resuelto` y `Cancelado` el destino es **volver al trabajo**, y esa acción vive en
  `boton-reabrir-requisito`, no acá. Que el botón no aparezca en un estado ya **no significa que no
  haya transición posible**: significa que no hay una *sugerida*, y la pill las ofrece todas
  [REQ-012 RF-2, RF-12]

**campo-tipo-resolucion**
- Texto/label: `"Tipo de resolución"` · opción vacía `"Seleccioná una opción"`
- Annotation: `<select id="resolution-type">` nativo, solo para `type: 'incidencia'`. **Desde
  REQ-012 el servidor exige este campo solo para `incidencia`**, que es exactamente lo que esta
  pantalla ya hacía: el cambio **confirma** el comportamiento actual en vez de modificarlo, y
  cierra el callejón sin salida en que resolver una `funcionalidad` desde acá terminaba en
  `400 resolution_required` sin que la UI hubiera ofrecido nunca el campo [REQ-012 RF-5, RF-6,
  CA-8]. **Al reresolver un requisito que ya tuvo resolución previa, el campo llega precargado con
  el valor anterior**, editable antes de guardar [REQ-012 RF-11, CA-13]

**campo-conclusion**
- Texto/label: `"Conclusión interna"` · placeholder `"Describí la conclusión interna de esta incidencia..."`
- Annotation: `<textarea id="resolution-conclusion">`, solo para incidencias. **Precargado con la
  conclusión de la resolución anterior al reresolver**, editable antes de guardar [REQ-012 RF-11, CA-13]

**campo-nota-cliente**
- Texto/label: `"Nota para cliente"` · placeholder `"Describí la resolución de esta incidencia..."`
- Annotation: `<textarea id="resolution-comment">`, solo para incidencias

**boton-cancelar-requisito**
- Texto/label: `"Cancelar"`
- Annotation: **acá `"Cancelar"` cancela el requisito, no la acción.** Está al lado de `"Resolver"`
  y ambos son transiciones de estado terminales; en el resto del producto `"Cancelar"` significa
  descartar

**boton-resolver-requisito**
- Texto/label: `"Resolver"`

**badge-resultado**
- Texto/label: `"Resuelto"` / `"Cancelado"`

**boton-reabrir-requisito** *(nuevo)*
- Texto/label: **`"Reabrir"`**
- Icono: nada · Asset: nada
- Annotation: aparece **solo** en `resuelto` y `cancelado`, al lado de badge-resultado, y devuelve
  el requisito a `desarrollo`. Es el par simétrico de boton-resolver-requisito y
  boton-cancelar-requisito: los tres son transiciones de la card de resolución, y desde REQ-012 las
  tres son reversibles. **`"Reabrir"` y no `"Volver a abrir"` ni `"Retomar"`**: es la palabra que el
  equipo ya usa para esto y la que no se confunde con `"Cancelar"`, que en esta card cancela el
  requisito y no la acción. **Al confirmarse limpia los tres campos de resolución** —tipo,
  conclusión y nota para cliente—, así que el aviso de esa pérdida es parte de la acción y no de un
  estado posterior [REQ-012 RF-2, RF-10, CA-3, CA-4, CA-12]

### Estados aplicables

**estado terminal / readonly**
- Mensajes: `"Fecha de finalización"` (resuelto) · badge `"Resuelto"` / `"Cancelado"`
- Cambios:
  - **Resuelto** (`state === 'resuelto'`): card-resolucion muestra `"Fecha de finalización"` en vez
    de los botones; campo-tipo-resolucion, campo-conclusion y campo-nota-cliente quedan `disabled`
    (`isClosed`); boton-cancelar-requisito y boton-resolver-requisito ocultos
  - **Cancelado** (`state === 'cancelado'`): badge-resultado `"Cancelado"` en vez de los botones;
    campos deshabilitados; el stepper marca los pasos no recorridos con `"×"`
- **Desde REQ-012 el estado terminal deja de ser terminal.** Sigue siendo un estado *de cierre* —la
  card muestra la fecha de finalización o el badge del resultado, y los tres campos de resolución
  quedan `disabled` mientras el requisito está cerrado— pero ya no es una salida sin retorno:
  `boton-reabrir-requisito` aparece junto a badge-resultado y `pill-estado` deja de deshabilitarse,
  así que el requisito puede volver al trabajo desde cualquiera de los dos [REQ-012 RF-2, CA-3, CA-4].
- **Al reabrir, los datos de resolución se pierden**: tipo, conclusión y nota para cliente vuelven a
  vacío al guardar. El usuario ve la card volver a su forma editable y **sin** lo que había
  cargado. Cuando vuelva a resolver, el formulario **sugiere esos mismos valores** para que no
  tenga que reescribirlos [REQ-012 RF-10, RF-11, CA-12, CA-13].
- **El readonly no alcanza al resto de la pantalla:** las pills de estado, tipo y prioridad, el
  acordeón y las acciones de tarea siguen disponibles.

**error de sistema / sin conexión**
- Mensajes: `error.message` o `"Error al actualizar el requisito"` (actualización).
- **REQ-004:** la api separa `503 service_unavailable` (`"El servicio no está disponible en este
  momento"`) de `504 gateway_timeout` (`"La operación tardó demasiado"`). Los dos salen por los
  toasts que ya existen: **la pantalla no se modifica**.
- **El error al refrescar el requisito no se maneja:** `RequirementDetailContainer` hace
  `requirement ?? initialRequirement`, así que si el refetch falla **se sigue mostrando el dato del
  render inicial sin ningún aviso**.

**confirmación al resolver, cancelar o borrar etiqueta**
- Aplica: **No — no implementado** (ver `gaps-as-is.md`). `"Resolver"` y `"Cancelar"` disparan la
  transición terminal **directo, sin `ConfirmDialog`**.
- **REQ-012 cambia el argumento sin cerrar el gap.** Resolver y cancelar **dejan de ser las
  acciones menos reversibles**: ahora se deshacen con `"Reabrir"`. A cambio, `"Reabrir"` estrena la
  pérdida de datos que ninguna de las dos tenía —limpia tipo, conclusión y nota para cliente
  (RF-10)— y es la acción de la pantalla que más pide una confirmación. **No se diseña acá:** el
  requerimiento no lo pide y la pantalla no tiene `ConfirmDialog` para ninguna de sus tres
  transiciones, así que sumarlo a una sola dejaría la card confirmando lo reversible y no lo
  destructivo. Queda anotado como el gap que ahora **más conviene cerrar** de los tres, y con el
  mismo alcance: las tres acciones de la card, juntas.
  → **Decisión para esta story: NO se implementa `ConfirmDialog` en "Reabrir".** Ver D-4.

### Flujo de usuario relevante — Flujo 2: Avanzar un requisito por su workflow

**JTBD:** *"Cuando el trabajo sobre un pedido avanza, quiero reflejarlo para que el cliente y el
equipo vean el mismo estado sin que yo tenga que avisarles."*
**Audiencia:** equipo-interno.
**Trigger:** el usuario abre un requisito desde el listado o desde el detalle de su proyecto.

**Happy path (pasos que esta story toca):**

2. El **stepper de workflow** muestra dónde está: `analisis → planificacion → en_cola →
   desarrollo → revision`. **Desde REQ-012 el stepper ubica pero no restringe**: el recorrido que
   dibuja es el habitual, no el único posible (RF-1, RF-12)
4. Avanza el estado — con el **botón de transición**, que guarda los campos y va al paso siguiente
   en una sola acción, o con la **pill del header**, que desde REQ-012 lleva a cualquiera de los
   siete estados sin pasar por los intermedios (RF-12, CA-6)
5. El cambio se registra como **actividad pública** automáticamente y aparece en el feed

**Caminos alternativos nuevos o modificados:**

- **Ir a cualquier estado, en cualquier orden** — Camino **nuevo desde REQ-012**, y el que cambia la
  naturaleza del flujo: la secuencia dejó de ser una regla. Desde la **pill de estado** del header
  se llega a cualquiera de los siete estados desde cualquier otro, hacia adelante o hacia atrás, sin
  validación de secuencia ni en la pantalla ni en el servidor (RF-1, CA-1, CA-2, CA-6). El
  **stepper sigue mostrando el recorrido de trabajo** porque es cómo el equipo lee dónde está un
  requisito, pero ya no recorta a dónde puede ir: **informa, no decide**.
- **Es una incidencia** — El recorrido habitual **saltea `en_cola`**. **Desde REQ-012 es una
  costumbre, no una restricción**: `"En cola"` vuelve a estar entre las opciones de la pill para las
  incidencias, porque el servidor ya no distingue por tipo al cambiar de estado (RF-1, RF-12).
- **Reabrir un requisito cerrado** — Camino **nuevo desde REQ-012**. `resuelto` y `cancelado` dejan
  de ser terminales: desde la card de resolución, el botón **"Reabrir"** devuelve el requisito a
  `desarrollo` (RF-2, CA-3, CA-4). **Reabrir borra los datos de resolución** en la misma escritura
  que cambia el estado (RF-10, CA-12); cuando el requisito se vuelva a resolver, el formulario
  **sugiere esos mismos valores** para que nadie tenga que reescribirlos (RF-11, CA-13). La fecha de
  finalización **se conserva** hasta que haya una nueva resolución.
- **Cerrar el requisito** — **Tipo y conclusión se exigen solo si el requisito es de tipo
  `incidencia`** — para `funcionalidad`, `mejora` y `otro` son siempre opcionales y el formulario no
  los pide (RF-5, RF-6, CA-7, CA-8). Hasta REQ-012 el servidor los reclamaba para todos los tipos
  mientras la pantalla los ofrecía solo para incidencias: resolver una `funcionalidad` desde acá
  **era imposible**, y ese callejón es lo que el requerimiento cierra.

**Flujo 2 (Del avance del equipo a la vista del cliente):** el paso 1 contempla la pill libre, y se

### Accessibility guidelines (de `docs/design-system/web/guidelines/accessibility.md`)

Aplicables a lo que esta story construye:

- Todo control interactivo es un elemento nativo (`<button>`, `<select>`, `<textarea>`) o declara
  su rol. El botón "Reabrir" es un `<button type="button">`: rol, foco y activación por teclado
  vienen dados.
- El foco visible no se suprime.
- El estado deshabilitado se expresa con el atributo nativo `disabled`, no solo con color.
- Un control que cambia de significado según el contexto necesita un nombre accesible que lo
  desambigüe (relevante acá: `"Cancelar"` cancela **el requisito**, no la acción).

## Hallazgo bloqueante para CA-6 y la decisión tomada

> **Esto es el hallazgo más importante de esta planificación. Leerlo antes de la Tarea 4.**

**La story propone una fuente de datos que no existe.** El "Flujo de Interacción · Escenario 4" de
S-050 dice que el formulario precargue los valores *"leídos de la actividad de tipo `resolution`
más reciente en el feed"*. **Esa actividad no se escribe nunca.** Verificado en el código:

1. **`core/src/commands/requirements/requirements-edit.ts:57-61`** — el mapa que traduce un campo
   cambiado a un tipo de actividad cubre **tres campos**, y ninguno es de resolución:
   ```ts
   const ACTIVITY_TYPE_BY_FIELD: Record<FieldActivityChange['type'], RequirementActivityType> = {
     title: RequirementActivityType.Title,
     description: RequirementActivityType.Description,
     state: RequirementActivityType.State,
   };
   ```
2. **`packages/models/src/requirement.model.ts:200-231`** — el hook `@BeforeUpdate` que produce el
   `activityLog` solo observa esos mismos tres campos. El tipo lo hace explícito:
   `type: 'title' | 'description' | 'state'`.
3. **`core/src/commands/requirements/requirements-resolve.ts:80-92`** — el comando dedicado de
   resolución escribe **una sola** entrada, y es de tipo `state`, no `resolution`.
4. **`packages/models/src/requirement-activity.model.ts:14`** — el valor
   `RequirementActivityType.Resolution = 'resolution'` **existe en el enum** pero es código muerto
   en escritura: ningún productor lo emite. Las filas históricas con ese tipo se volcaron a la
   columna `resolution_comment` en la migración
   `api/db-upgrade/migrations/20260721_01_requirements_split_resolution_fields.js`, y ahí
   `new_value` era **solo el comentario**, no un JSON con los tres campos.
5. **La limpieza de S-049 es silenciosa:** los tres campos se limpian dentro del mismo `changes` que
   va a `requirement.update(...)`, y el hook no los mira, así que el `activityLog` resultante
   contiene **solo** la entrada `state` (`resuelto` → `desarrollo`).

**Esto ya estaba anticipado.** El REQ-012 lo dejó como riesgo R2 (*"Conviene verificar al planificar
que el hook efectivamente registre esa actividad al limpiar los campos: si no lo hace, el dato se
pierde de verdad y hay que agregarlo"*), y el Story Plan de S-049 lo repitió como verificación
pendiente, aclarando que **agregar un tipo de actividad nuevo estaba fuera del alcance de esa
story**.

**Consecuencia:** una vez que el servidor limpió los campos, los valores anteriores **no son
recuperables desde ninguna respuesta de la api**.

### D-1 · Decisión: la sugerencia se captura en el cliente, antes de que el servidor limpie

CA-6 se cumple **capturando los tres valores en el momento en que el usuario reabre**, que es el
único instante en que todavía están en el cache de TanStack Query, y conservándolos como sugerencia
en el estado del componente.

**Por qué esta opción y no las alternativas:**

| Opción | Por qué no |
|---|---|
| Leer la actividad `resolution` del feed | **No existe.** Es la que la story asumía. |
| Agregar la escritura de esa actividad en `core` | Cambia otro servicio: fuera del alcance de esta story, que declara `web` como único servicio afectado. Es el camino correcto si el equipo quiere que la sugerencia sobreviva a un reload, y queda registrado como seguimiento. |
| No implementar CA-6 | Es un criterio de aceptación de la story. |

**Alcance honesto de lo que se implementa — decir esto explícitamente evita una falsa expectativa:**
la sugerencia vive en el estado del componente, así que cubre el recorrido que la story describe
(reabrir → volver a resolver, en la misma sesión de pantalla) y **se pierde con un reload o al
navegar fuera y volver**. En ese caso el formulario aparece vacío, que es exactamente lo que hace
hoy. No se degrada nada: se agrega una comodidad donde antes no había ninguna.

**Un caso que sí queda cubierto sin ningún truco:** un requisito **`cancelado`** que se reabre
**conserva** sus tres campos en la fila (la limpieza de `core` solo se dispara saliendo de
`resuelto`). Ahí la precarga funciona por la vía normal de `draftsFromRequirement`, y con reload
incluido.

### D-2 · Seguimiento a registrar (no se implementa acá)

Para que la sugerencia sobreviva a un reload hace falta que `core` preserve los valores al
limpiarlos —emitiendo la actividad `resolution` que el enum ya contempla, o de otra forma—. Es un
cambio de otro servicio y **no entra en esta story**. Debe quedar anotado al reportar la
implementación para que el equipo decida si abre un REQ.

### D-3 · Los botones de la card siguen siendo `<button>` nativos

El DS especifica el componente `<Button>`, pero **la card de resolución no lo usa**: `"Resolver"` y
`"Cancelar"` son `<button>` nativos con `.resolveButton` / `.cancelButton` del módulo SCSS.
`"Reabrir"` **sigue ese patrón**, reutilizando el estilo secundario que ya existe. Introducir
`<Button>` para un solo botón dejaría dos sistemas conviviendo dentro de la misma card, que es peor
que la inconsistencia actual —uniforme dentro de su alcance—. La migración completa de la card a
`<Button>` es un trabajo propio, no un efecto colateral de esta story.

### D-4 · "Reabrir" no lleva `ConfirmDialog`

El screen.md lo argumenta y esta story lo respeta: la pantalla no confirma **ninguna** de sus tres
transiciones de la card, y sumarle confirmación solo a "Reabrir" dejaría la card confirmando lo
reversible y no lo destructivo. El gap queda abierto y anotado en `gaps-as-is.md`, con el alcance
correcto: las tres acciones juntas.

### D-5 · Validación de cliente para incidencias: no se agrega

La story menciona en Consideraciones Técnicas (R5) que *"conviene decidir si se agrega validación de
cliente para incidencias"*. **Decisión: no se agrega.** Ningún CA la pide, el screen.md declara el
`"Resolver"` deshabilitado únicamente por `isPending`, y el rechazo del servidor
(`400 resolution_required`) ya llega como toast con mensaje en español. Agregarla ahora sumaría una
regla de UI que la pantalla tendría que mantener sincronizada con `core` — exactamente la clase de
duplicación que este REQ vino a eliminar. **Queda anotado como decisión consciente**, no como
olvido.

### Task 4: El formulario sugiere los valores de la resolución anterior al reresolver

#### Description

Cuando un requisito `resuelto` se reabre, `core` limpia `resolutionType`, `resolutionConclusion` y
`resolutionComment` en la misma escritura (S-049, RF-10). Al volver a resolverlo, el usuario tiene
que reescribir todo. Esta tarea hace que el formulario **sugiera** los valores anteriores,
editables antes de guardar.

**Leer el "Hallazgo bloqueante" de este plan antes de empezar.** La story propone leer esos valores
de una actividad de tipo `resolution` en el feed: **esa actividad no existe** —ningún productor la
escribe, verificado en `core` y en `packages/models`—. La fuente real es el propio cliente: los
valores están en el cache de TanStack Query **hasta el instante en que el usuario hace click en
"Reabrir"**, y ahí se capturan.

**Alcance honesto:** la sugerencia vive en el estado del componente y cubre el recorrido de la story
(reabrir → volver a resolver en la misma pantalla). **Se pierde con un reload o al navegar fuera y
volver**, y en ese caso el formulario aparece vacío, exactamente como hoy. No se degrada nada.

Un caso queda cubierto sin ningún mecanismo extra: un requisito **`cancelado`** que se reabre
conserva sus tres campos en la fila (la limpieza solo se dispara saliendo de `resuelto`), así que la
precarga funciona por la vía normal de `draftsFromRequirement`.

Cubre CA-6 y CA-7.

#### Acceptance Criteria

1. Al hacer click en `"Reabrir"`, el componente captura los valores actuales de `resolutionType`,
   `resolutionConclusion` y `resolutionComment` del `requirement` **antes** de invocar `onUpdate`.
2. Cuando el componente recibe un `requirement` con los tres campos en `null`/vacío **y** existe una
   sugerencia capturada, los drafts se inicializan con la sugerencia y los campos se ven
   precargados.
3. Cuando el `requirement` **sí** trae valores, los drafts se alinean con el `requirement` — la
   sugerencia **nunca** pisa un valor real.
4. Si el requisito nunca tuvo resolución (los tres capturados vacíos), los campos quedan vacíos: no
   se sugiere `""` como si fuera un valor.
5. Los campos sugeridos son **editables**: `fireEvent.change` los modifica y el valor editado es el
   que viaja en el payload.
6. Al hacer click en `"Resolver"` tras editar, se envían los **valores editados**, nunca los
   sugeridos originales.
7. Al hacer click en `"Resolver"` sin editar, se envían los valores sugeridos tal cual.
8. El efecto que realinea los drafts con el `requirement` **no pisa lo que el usuario está
   escribiendo** por un re-render con objeto de nueva referencia y mismos valores.

#### Technical Details

**Architectural Context References:**

- **Convención `state-management` — la excepción legítima:** *"un formulario de edición sí copia el
  valor de la query a estado local, porque el usuario lo está modificando y el cache no debe
  seguirlo. En ese caso el patrón es inicializar con un initializer de `useState`, no con un
  efecto"*. Es exactamente este caso.
- **Precedente directo en el módulo — `RequirementStatusCard.tsx:243-251`:** el efecto que realinea
  drafts usa **deps por valor**, no el objeto `requirement`, con este comentario:
  > *Deps por VALOR (no `[requirement]`): un rollback de `useUpdateRequirement` puede re-renderizar
  > con un objeto `requirement` de nueva referencia pero mismos valores — si las deps fueran el
  > objeto completo, esto pisaría con el valor persistido cualquier draft de texto que el usuario
  > todavía no guardó, perdiendo lo que estaba escribiendo.*

  **`RequirementResolutionCard` tiene hoy justamente el bug que ese comentario describe**
  (`RequirementResolutionCard.tsx:62-64`):
  ```tsx
  useEffect(() => {
    setDrafts(draftsFromRequirement(requirement));
  }, [requirement]);
  ```
  Deps por **objeto**. Esta tarea lo corrige a deps por valor, que es además lo que hace posible el
  AC-8.
- **UX · campo-tipo-resolucion / campo-conclusion:** *"Al reresolver un requisito que ya tuvo
  resolución previa, el campo llega precargado con el valor anterior, editable antes de guardar"*.
- **Reusable Code:** `RESOLUTION_TYPE_OPTIONS` para el select; `draftsFromRequirement` local para el
  mapeo `requirement → drafts`.

**Files to Create/Modify:**

- `src/features/requirements/components/RequirementResolutionCard/RequirementResolutionCard.tsx`
- `src/features/requirements/components/RequirementResolutionCard/RequirementResolutionCard.test.tsx`

**Implementation Notes:**

- **Dónde vive la sugerencia:** un `useState` en `RequirementResolutionCard`, del mismo tipo que
  `ResolutionDrafts`, inicializado en `null`. Se escribe en `handleReopen` (Tarea 3), **antes** del
  `onUpdate`:
  ```tsx
  const handleReopen = () => {
    const previous = draftsFromRequirement(requirement);
    const hasSomething = Object.values(previous).some((v) => v !== '');
    if (hasSomething) setSuggestion(previous);
    onUpdate({ state: 'desarrollo' });
  };
  ```
  El `hasSomething` cubre AC-4: no se guarda una sugerencia toda vacía.
- **Cómo se aplica:** en el efecto de realineación, la sugerencia solo entra cuando el requirement
  no trae valores propios:
  ```tsx
  useEffect(() => {
    const fromRequirement = draftsFromRequirement(requirement);
    const isEmpty = Object.values(fromRequirement).every((v) => v === '');
    setDrafts(isEmpty && suggestion ? suggestion : fromRequirement);
    // eslint-disable-next-line react-hooks/exhaustive-deps
  }, [
    requirement.resolutionType,
    requirement.resolutionConclusion,
    requirement.resolutionComment,
  ]);
  ```
  **Las deps son por valor** —los tres campos— y **no incluyen `suggestion`**: si la incluyeran, el
  `setSuggestion` del click volvería a disparar el efecto y pisaría cualquier edición en curso.
  Dejar el `eslint-disable` con el mismo comentario explicativo que usa `RequirementStatusCard`.
- **AC-3 sale gratis** con la guarda `isEmpty`: si el requirement trae valores, ganan siempre.
- **No** persistir la sugerencia en `localStorage` ni en el cache de queries: sería estado nuevo con
  reglas de invalidación propias, y la convención `state-management` es explícita sobre no agregar
  categorías de estado sin decisión previa.
- **No** tocar `saveChangedFields()`: sigue comparando drafts contra `draftsFromRequirement
  (requirement)` y emitiendo un `onUpdate` por campo cambiado. Con la sugerencia aplicada y el
  requirement en `null`, los tres campos figuran como "cambiados" y se envían — que es exactamente
  lo que AC-7 pide.
- **Verificar el orden en `handleResolve`:** hoy hace `saveChangedFields()` y después
  `onUpdate({ state: 'resuelto' })`. Ese orden importa: `core` valida `resolution_required` contra
  el payload **y** la fila, y si el estado llegara antes que los campos, una incidencia podría ser
  rechazada. **No alterarlo.**

**Dependencies:**

- Ninguna librería nueva.
