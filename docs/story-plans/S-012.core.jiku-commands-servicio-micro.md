## Status

**Status:** Completed

## Story Reference

- **Story:** [S-012](../stories/S-012.jiku-commands-servicio-micro.md)
- **Service:** `core`
- **Summary:** Reemplazar la capa de conexión al bus de `core` —`src/bus/consumer.ts`, 126 líneas—
  por un **host de servicios micro**: `src/bus/host.ts` (una conexión NATS, N servicios, apagado
  ordenado) y `src/bus/service.ts` (`registerService()` desde un spec, con los 20 endpoints
  derivados del registry y la verificación de subjects duplicados que **falla el arranque**).
  `dispatcher.ts`, `registry.ts`, `commands/` y los 20 comandos **no se tocan**, y por eso los
  tests existentes pasan sin una sola aserción modificada.

> **Este plan NO cubre `packages/nats-protocol`.** El borrado de `subscriptionSubject()` y
> `SERVICE_NAME` (CA-15) es la **contracción** del expand/contract que abrió S-011, y va en el plan
> `S-012.nats-protocol.*`, que **tiene que implementarse después de este**: hasta que
> `consumer.ts` no muera y el helper de tests no se repunte, el paquete no puede perder esos dos
> símbolos sin romper el build de `core`. Este plan **deja a cero los callers**; el otro borra los
> símbolos.

> **Este plan no toca `api`, `deploy`, `web` ni `opus-web`.** La story los marca `Ninguno`: la api
> publica en el mismo subject desde S-011, y el callout, `SERVICE_VERSION` y el permiso `$SRV.>`
> ya quedaron declarados en `S-011.deploy.*`.

```ts
let userId = process.env.NATS_USER_ID || SERVICE_NAME;

// :59-67  — la conexión
this.connection = await connect({
  servers,
  inboxPrefix: inboxPrefix(userId),
  ...(authenticators.length ? { authenticator: authenticators } : {}),
  name: 'jiku-core',
});

// :69-70  — UNA suscripción wildcard con queue group
const subject = subscriptionSubject();            // dev.*.jiku-commands.v1.>
this.subscription = this.connection.subscribe(subject, { queue: SERVICE_NAME });

// :84-106 — el loop de consumo
for await (const message of this.subscription!) {
  let payload: unknown;
  try {
    payload = message.data.length ? JSON.parse(new TextDecoder().decode(message.data)) : {};
  } catch {
    logger.warn(`[bus] invalid payload on ${message.subject}`);
    message.respond(encode(failure(ErrorCode.INVALID_FIELDS, 'Malformed JSON payload')));
    continue;
  }
  // Cada mensaje se procesa sin bloquear la llegada de los siguientes.
  void this.dispatcher
    .dispatch(message.subject, payload)
    .then((reply) => message.respond(encode(reply)))
    .catch((error: Error) => {
      logger.error(`[bus] ${message.subject}: ${error.message}`);
      message.respond(encode(failure(ErrorCode.INTERNAL_ERROR, 'Internal error')));
    });
}

// :110-121 — el apagado
async stop(): Promise<void> {
  this.stopTokenRefresh?.();
  this.stopTokenRefresh = null;
  if (this.subscription) await this.subscription.drain();
  if (this.connection) { await this.connection.drain(); await this.connection.close(); }
  logger.info('[bus] desconectado');
}
```

### Convenciones activas y qué exige cada una acá

Del `manifest.yaml` de `core` (`type: worker`, `language: node`), **todas custom** en
`docs/architectures/core/conventions/`. Las que gobiernan este plan:

**`_base`**
- TypeScript obligatorio, `strict: true` **no se apaga**.
- Archivos en `kebab-case.ts`; clases en `PascalCase` (`BusHost`); constantes de módulo en
  `SCREAMING_SNAKE_CASE` (`SERVICE_VERSION`).
- **Imports relativos** (`../logger`, `./service`), sin alias ni paths de `tsconfig`. Los paquetes
  del workspace por nombre (`@jiku/nats-protocol`).
- Orden de imports: librerías → `@jiku/*` → relativos.
- **Comentarios en español**, y explican **el por qué**, no el qué. Lo que amerita comentario: una
  decisión que parece un error y no lo es. Este plan tiene tres de ésas (el `Set` de duplicados, el
  handler que nunca lanza, el seam de conexión).
- `any` se tolera solo en dos bordes: los payloads del bus antes de validar y el acceso dinámico a
  campos del modelo.

**`bus-consumer`** — es la convención que este REQ **reescribe entera** (RF-24), y se tramita
aparte por `/product-change-technical-definition`. Lo que este plan **tiene que respetar de ella**,
porque no cambia:
- Los helpers de subject se usan de `@jiku/nats-protocol`. **No se arma un subject a mano ni se
  parsea con `split` fuera del paquete.**
- `inboxPrefix` **siempre** se fija al conectar, con el user id del service user.
- La suscripción siempre lleva queue group. Sin él, N réplicas escriben N veces.
- **Todo mensaje recibido se responde**: éxito, falla o error interno. Nunca se descarta en
  silencio.
- El `dispatch` **no se `await`ea** en el camino de recepción.
- `stop()` drena antes de cerrar. **No agregues un `process.exit()` que se saltee el drain.**
- Core **no publica** en el bus.
- No se agrega JetStream (ADR-002).

**`error-handling`**
- El `Reply` se construye **siempre** con los helpers `success()` / `failure()`, nunca a mano.
- Se usa la **constante** `ErrorCode.X`, no el literal.
- Los tres errores que no vienen de un comando, con sus códigos exactos:

  | Situación | Código | Mensaje |
  |---|---|---|
  | Cuerpo que no es JSON | `invalid_fields` | `'Malformed JSON payload'` |
  | Comando no registrado | `unknown_command` | `Unknown command: ${name}` (lo emite el despachador) |
  | Excepción no capturada | `internal_error` | `'Internal error'` |

- El detalle del error va **al log**; el mensaje que cruza el bus es genérico.
- Un `failure` esperado **no** se loguea como `error`.

**`logging`**
- Un solo logger, importado de `../logger`. **Nunca `console.log`.**
- Prefijos de origen: `[core]` arranque y señales, `[bus]` conexión/registro/estado del bus,
  `[dispatch]` el despachador, `[cmd]` la traza con `LOG_COMMANDS`, `[DB]` Sequelize.
- Niveles: `error` lo inesperado · `warn` entrada inválida que el servicio maneja bien (payload
  no-JSON) · `info` hitos de ciclo de vida (arranque, conexión, registro) · `debug` diagnóstico.
- Mensajes cortos, con el dato variable al final.

**`env-config`**
- `dotenv.config()` en las dos primeras líneas de `src/index.ts`.
- **Los defaults van donde se lee la variable, con `||`.** No se duplica un default en dos
  archivos.
- **Una variable nueva se documenta en tres lugares:** la convención, `core/README.md` y
  `deploy/.env.dist`. `SERVICE_VERSION` ya está en `.env.dist` (S-011) y en los tres compose; este
  plan la lee por primera vez desde el código, así que le toca `core/README.md` (Tarea 8). La
  convención la actualiza `/product-change-technical-definition` (RF-24).
- El patrón general del servicio es `process.env.X || 'default'`. La **única** excepción es
  `CORE_TRUSTED_PUBLISHER_ID`, que tiene assert de arranque.

**`testing`**
- Los tests entran por `dispatch()`, **nunca** llamando a `execute()` directamente.
- **No se mockea Sequelize ni la base.** (Esta regla es sobre la base: los dobles de este plan son
  del cliente NATS, que no está presente en el entorno de test.)
- Un archivo de test por módulo; los fixtures se crean en el `before` del propio archivo.
- `TZ=UTC` está fijado en `tests/setup-env.ts`.
- `core/.mocharc.json` tiene `recursive: true`, así que **`tests/bus/*.test.ts` se recoge solo**;
  y `require` incluye `setup-env.ts` + `global-setup.ts`, así que **cualquier** archivo de test
  levanta el PostgreSQL efímero. Los tests de este plan no usan la base, pero pagan ese arranque.

### ADRs relevantes

#### ADR-002: Toda mutación es un comando NATS request/reply, sin JetStream

**Decisión:** NATS en modo request/reply, **sin JetStream**. La api publica un comando y espera la
respuesta con timeout; `core` valida, escribe en una transacción y responde.

**Implementation Rules (verbatim):**
- Todo comando **DEBE** publicarse con el subject `{instance}.{user-id}.gestion.v1.{comando}`,
  usando la gramática de `@jiku/nats-protocol`. **NO SE DEBE** construir el subject a mano.
- El cliente NATS **DEBE** fijar `inboxPrefix` explícitamente al conectar, con el hash del user id
  que calcula `@jiku/nats-protocol`. Sin esto las respuestas no llegan.
- El `userId` con el que publica la api **DEBE** salir de la key del service user, **NO** de una
  variable de entorno: tiene que coincidir exactamente con el `sub` que el auth-callout lee del
  token para autorizar el subject.
- Toda respuesta **DEBE** tener el formato `{ status: 'success', data }` o
  `{ status: 'failure', errorCode, errorMessage }`. **NO SE DEBEN** inventar otros formatos.
- Los comandos de creación **DEBEN** devolver únicamente `{ id }`. Las ediciones y borrados, nada.
- Todo `errorCode` nuevo **DEBE** agregarse al mapa de `api/lib/utils/bus/protocol.ts` con su
  status HTTP. Un código sin mapeo cae en un 500 genérico.
- El timeout de la request es `NATS_REQUEST_TIMEOUT_MS` (default **5000 ms**); al expirar la api
  **DEBE** responder **503**.
- **NO SE DEBE** transportar datos estructurados dentro de `errorMessage`.
- Core **NO DEBE** publicar mensajes: solo responde el `Reply` de la request que recibe.

> **Nota de vigencia:** el `gestion` de la primera regla y el "17 comandos" del cuerpo del ADR son
> texto **desactualizado** que S-011 dejó pendiente de corregir (RF-23, vía
> `/product-change-technical-definition`). El token vigente es `jiku-commands` y son **20**
> comandos. La regla de fondo —no construir el subject a mano— es la que manda, y es exactamente
> CA-16.

#### ADR-003: La transacción es del despachador, nunca del comando

**Decisión:** el despachador abre y cierra la transacción; commit si el reply es `success`,
rollback en cualquier otro caso. Los comandos reciben la transacción pero no pueden cerrarla.

**Implementation Rules (verbatim):**
- Un comando **DEBE** recibir la transacción por su contexto y usarla en todas sus operaciones de
  base de datos. **NO DEBE** abrir una transacción propia.
- Un comando **NO DEBE** llamar a `commit()` ni a `rollback()`. Si el código de un comando los
  invoca, está mal escrito.
- Un comando **DEBE** señalar el fallo devolviendo un `Reply` con `status: 'failure'` y su
  `errorCode`. **NO DEBE** lanzar una excepción para señalar un fallo de negocio esperado.
- El despachador **DEBE** hacer commit **solo** si el reply es `success`, y rollback en todos los
  demás casos, incluidas las excepciones inesperadas.
- El despachador **NO DEBE** lanzar nunca: todo error se traduce a un `Reply` de falla.
- Los tests de comandos **DEBEN** entrar por el despachador (helper `dispatch()`), no llamando a
  `execute()` directamente: es lo único que verifica el comportamiento transaccional, incluido el
  rollback.

> **Cómo aplica acá:** el despachador **no se toca**, así que estas seis reglas se cumplen por
> construcción. La única que este plan tiene que sostener activamente es la quinta, un nivel más
> arriba: **`handle()` tampoco lanza nunca**. Y el ADR cita `consumer.ts:101-105` como "la última
> red por si el despachador fallara al fallar" — esa red se muda a `handle()`.

#### ADR-001: Separación lectura/escritura (contexto, no cambia)

`api` conecta con un rol sin `INSERT`/`UPDATE`/`DELETE`; `core` con el usuario **dueño**. Este plan
**no abre ninguna conexión nueva a la base**: `core/src/models/index.ts` queda exactamente como
está. La segunda conexión —la de solo lectura— es de S-013.

#### ADR-012: Monorepo con contexto en la raíz (contexto, no cambia)

`npm workspaces`. **No se agrega ningún deployable** (RF-6): el servicio micro vive en la imagen de
`core`, que no cambia. El `Dockerfile` de `core` **no entra en este plan**.

Dos reglas de forma que la derivación respeta, y por qué:
- **El nombre no lleva puntos.** Micro valida el nombre contra `/^[-\w]+$/`; el subject, con sus
  puntos y sus `*`, viaja aparte en `opts.subject`.
- **`{param}` se convierte en `*` en el subject y se ELIMINA del nombre.** Un token de subject no
  puede llevar llaves, y el despachador ya extrae los params del subject completo con el registry
  por segmentos: no los necesita del nombre.

**El envelope de respuesta (no cambia):**

```json
{ "status": "success", "data": { "id": 7 } }
{ "status": "failure", "errorCode": "project_not_found", "errorMessage": "Project not found" }
```

**En un `failure` el envelope viaja EN EL CUERPO**, y los headers `Nats-Service-Error` /
`Nats-Service-Error-Code` son un **agregado**, nunca un reemplazo. El `500` de `respondError` es el
status del **transporte micro**, no el HTTP: el que ve la persona lo decide `httpStatusFor` de la
api sobre el `errorCode` **del cuerpo**. Confundir los dos es el error fácil de esta story.

**El inbox va hasheado.** El user id viaja crudo en el subject de comandos, pero el inbox usa
`_INBOX.<sha256 → base32 sin padding → 16 chars en minúscula>`. **Hay que fijarlo al conectar**: por
defecto nats.js genera un `_INBOX.<aleatorio>` que ningún permiso acotado autoriza, y el síntoma es
un **timeout**, no un error de permisos.

**Qué hace exactamente `respondError`** (`service.js`:68-75), porque es fácil invertirlo:

```ts
respondError(code, description, data, opts) {
  opts.headers = opts.headers || headers();
  opts.headers.set('Nats-Service-Error-Code', `${code}`);        // <- el 500
  opts.headers.set('Nats-Service-Error', description);           // <- el errorCode
  return this.msg.respond(data, opts);                           // <- EL CUERPO VIAJA IGUAL
}
```

`Nats-Service-Error-Code` lleva el **500** (transporte micro) y `Nats-Service-Error` lleva el
**`errorCode`** del protocolo (`project_not_found`). El `data` es el envelope completo: **el cuerpo
no se pierde**. Eso es CA-5.

**Descubrimiento y métricas.** Al registrarse, el servicio se suscribe solo a `$SRV.PING` / `INFO` /
`STATS`, más `$SRV.<VERB>.<NAME>` y `$SRV.<VERB>.<NAME>.<ID>` (el nombre y el id van en
**mayúsculas** en el subject de control). Por eso aparece en `nats micro ls`. El permiso `$SRV.>` ya
lo concedió S-011: **si faltara, el servicio levantaría y atendería igual, pero sería invisible, sin
ningún error**.

**Hallazgo — `processing_time` va a reportar ~0 y hay que saberlo antes de armar un dashboard.**
`setupHandler` mide la latencia en un `finally` **inmediatamente después de la llamada sincrónica**
al handler (`service.js`:238-252):

```js
const start = Date.now();
try { handler(err, new ServiceMsgImpl(msg)); }
catch (err) { sv.stats.countError(err); msg?.respond(Empty, { headers: this.errorToHeader(err) }); }
finally { sv.stats.countLatency(start); }   // <- corre ANTES de que el await del handler resuelva
```

Como el handler devuelve enseguida (`void handle(spec, msg)`, que es lo que preserva la no-bloqueo
del consumer actual), `countLatency` corre con un elapsed de ~0-1 ms. Entonces:

- **`num_requests` es exacto** — `countLatency` lo incrementa por mensaje. CA-11 se cumple.
- **`processing_time` y `average_processing_time` existen y son por endpoint**, pero **no miden lo
  que tarda el comando**: miden lo que tarda en encolarse.
- No hay forma de arreglarlo desde el handler: micro ignora el valor de retorno, así que devolver
  una promesa tampoco corre el `finally`. La salida, si algún día hace falta latencia real, es el
  `statsHandler` de `ServiceConfig` con medición propia. **Fuera de alcance de esta story.**

Es el mismo tipo de limitación que `num_errors` y se documenta igual: **la latencia por operación
se mide por logs, no por esta métrica**.

### El diseño que este plan implementa

#### `src/bus/service.ts` — un servicio micro desde un spec

```
ServiceSpec
  name: string            // nombre en el bus, queue group y token {svc} del subject
  description: string
  patterns: string[]      // los patrones del registry: 'tasks.{id}.edit', ...
  handle: (subject, payload) => Promise<Reply>    // NUNCA lanza

registerService(nc, spec) -> Promise<Service>
  1. nc.services.add({ name, version: SERVICE_VERSION, description,
                       queue: spec.name, metadata: { instance, protocol } })
  2. service.addGroup(groupSubject(spec.name))          // dev.*.jiku-commands.v1
  3. para cada patrón:
       subject = endpointSubject(patrón)
       si subject ya está en el Set -> throw (nombra SERVICIO y SUBJECT)
       group.addEndpoint(endpointName(patrón), { subject, handler })
  4. log '[bus] {name} v{version}: {n} endpoints'
  5. devuelve el Service

handle(spec, msg)                                       // nunca lanza
  payload = cuerpo vacío ? {} : msg.json()              // fallo -> failure('invalid_fields')
  reply   = await spec.handle(msg.subject, payload)      // fallo -> failure('internal_error')
  respond(msg, reply)

respond(msg, reply)
  success -> msg.respond(encode(reply))
  failure -> msg.respondError(500, reply.errorCode ?? 'error', encode(reply))
```

**Las cuatro decisiones que parecen detalles y no lo son:**

1. **El `Set` de subjects que falla el arranque no es opcional (CA-6).** Dos endpoints que matcheen
   el mismo subject entregan el mensaje a las dos suscripciones y ponen **dos respuestas en el mismo
   inbox**; el caller devuelve la primera y **descarta la otra en silencio**. Respuestas correctas la
   mitad de las veces, sin ningún error en ningún log. Los 20 de hoy no se solapan —el registry
   matchea por cantidad de segmentos y los que comparten longitud difieren en el primer o el último
   token literal— pero **verificarlo a mano hoy no protege del comando 21**.
2. **El handler nunca lanza (CA-10).** Es la contracara del hallazgo #6 de la tabla de la librería:
   si lanzara, micro responde `Empty` con headers y **el cuerpo se pierde**, o sea el envelope, que
   es el contrato. Con handlers `async` una excepción rechaza la promesa y ni entra a ese `catch`, así
   que el `try/catch` tiene que estar **dentro** de `handle()`.
3. **`void handle(spec, msg)` desde el handler de micro, sin `await`.** Es lo que preserva el
   comportamiento actual: un mensaje no bloquea la llegada del siguiente. La concurrencia real la
   acota el pool de Sequelize, igual que hoy.
4. **`queue: spec.name` en la config del servicio, no en cada endpoint.** El queue group cae en
   cascada al grupo y a los 20 endpoints (hallazgo #5). Sin esa línea quedaría el default `q` de
   micro y **CA-2 fallaría en silencio**: el servicio funcionaría igual, con el nombre de balanceo
   equivocado.

#### `src/bus/host.ts` — una conexión, N servicios

```
class BusHost
  constructor(...specs: ServiceSpec[])
  start(): abre UNA conexión y registra los servicios EN SERIE
  stop():  corta el auto-refresh -> para los servicios -> drena -> cierra
  protected openConnection(options): Promise<NatsConnection>   // el único punto que toca la red
```

- **Una sola conexión NATS para todos los servicios** (RF-6). `nc.services.add()` **no tiene
  singleton**: cada llamada crea un servicio con su propio id, endpoints y contadores. Es lo que
  hace posible un proceso con dos servicios.
- **`inboxPrefix` es obligatorio al conectar** (CA-14). Sin él la librería genera un
  `_INBOX.<aleatorio>` que ningún permiso acotado autoriza, y el síntoma es un **timeout**, no un
  error de permisos — que es lo que hace caro el diagnóstico.
- **Registro en serie, y el error se propaga** (CA-7). Es la razón por la que no hay `Promise.all`
  acá: uno que deje un servicio arriba y el otro caído es exactamente lo que CA-7 prohíbe.
- **`stop()` tiene un orden y el orden es la garantía** (CA-13): auto-refresh → servicios → drain →
  close. Al revés, una request nueva podría entrar durante el drain. `Promise.all` **sí** es correcto
  para parar servicios: es idempotente y no tiene orden entre sí.
- **`...specs` desde el día uno, aunque hoy sea uno solo.** No es sobre-ingeniería: es exactamente
  lo que S-013 necesita, y hace que registrar `jiku-queries` sea **sumar un elemento**.
- **`openConnection()` es un seam de test declarado, no un accidente.** `connect` se exporta de
  `nats` con un getter no configurable (`lib/src/mod.js`:55), así que **no se puede stubbear con
  sinon**: sin el seam, `host.ts` sería intesteable sin un bus real. Un método `protected` de una
  línea es el precio más bajo que paga eso.

#### Lo que NO entra en el diff

`src/bus/dispatcher.ts` · `src/commands/**` (registry, types, validate y los 20 comandos) ·
`src/models/**` · `src/config.ts` · `src/logger.ts` · `tests/commands/**` · `Dockerfile` ·
`package.json` · `core/.env.test`.

### Task 3: `bus/service.ts` — `handle()` y `respond()`: el handler nunca lanza

**Status:** Completed

#### Description

Crear `core/src/bus/service.ts` con la mitad que atiende mensajes: `ServiceSpec`, `handle()` y
`respond()`. Es el reemplazo directo del `for await` de `consumer.ts`:84-106, con el mismo
comportamiento observable y **una regla más fuerte**: el handler nunca lanza.

Va antes del registro (Tarea 4) porque no depende de él: `handle()` recibe un `spec` y un `msg`, y
se puede ejercitar entero con los dobles de la Tarea 2. Al revés no: `registerService()` necesita un
`handler` que ya exista.

**Lo que está en juego en las tres ramas:**

| Rama | Hoy (`consumer.ts`) | Ahora | Por qué importa |
|---|---|---|---|
| Cuerpo vacío | `{}` (`:88`) | `{}` | Los comandos de borrado no llevan payload. Tratarlo como error rompería 4 comandos |
| Cuerpo no-JSON | `respond(failure(INVALID_FIELDS))` + `continue` (`:93`) | `respond(msg, failure(INVALID_FIELDS, 'Malformed JSON payload'))` | La request **nunca** queda sin contestar |
| Excepción | `.catch()` → `failure(INTERNAL_ERROR)` (`:101-105`) | `try/catch` en `handle()` | Si dejáramos que la excepción llegara a micro, micro responde `Empty` con headers y **el cuerpo se pierde** |

#### Acceptance Criteria

1. Existe `core/src/bus/service.ts` y exporta `ServiceSpec` con exactamente cuatro miembros:
   `name: string`, `description: string`, `patterns: string[]`,
   `handle: (subject: string, payload: unknown) => Promise<Reply>`.
2. `SERVICE_VERSION` es una constante de módulo: `process.env.SERVICE_VERSION || '1.0.0'`.
3. `handle()` trata un cuerpo de longitud 0 como `{}` y **no** invoca `spec.handle` cuando el cuerpo
   no es JSON.
4. Un cuerpo no-JSON responde `{status:'failure', errorCode:'invalid_fields', errorMessage:'Malformed JSON payload'}`
   **en el cuerpo**, construido con `failure(ErrorCode.INVALID_FIELDS, ...)`.
5. Una excepción de `spec.handle` —sincrónica o asincrónica— responde
   `{status:'failure', errorCode:'internal_error', errorMessage:'Internal error'}` **en el cuerpo**,
   y la promesa de `handle()` **resuelve**: no rechaza.
6. `respond()` usa `msg.respond(encode(reply))` para `success` y
   `msg.respondError(500, reply.errorCode ?? 'error', encode(reply))` para `failure`.
7. Ningún camino de `handle()` responde cero veces ni dos veces.
8. El payload inválido se loguea con `logger.warn` y prefijo `[bus]`; la excepción con
   `logger.error` y prefijo `[bus]`. Un `failure` de negocio **no se loguea**.
9. Hay un comentario en español que explica **por qué** el handler no puede lanzar, citando que
   micro perdería el cuerpo, y otro que documenta que **`num_errors` queda en 0** como consecuencia
   asumida (CA-12).

#### Technical Details

**Architectural Context References:**
- **Integration Points → hallazgo #6:** `respondError()` no incrementa `num_errors`; el `catch` de
  micro responde `Empty` **con headers y sin cuerpo**. Es toda la justificación de esta tarea.
- **Integration Points → qué hace exactamente `respondError`:** `Nats-Service-Error-Code` = `500`,
  `Nats-Service-Error` = el `errorCode`. El `500` es transporte micro, **no HTTP**.
- **ADR-002:** el envelope tiene que ser `{status:'success', data}` o
  `{status:'failure', errorCode, errorMessage}`. **No se inventan otros formatos.**
- **ADR-003 → quinta regla:** *"El despachador **NO DEBE** lanzar nunca"*. `handle()` es el nivel de
  arriba de la misma regla.
- **Convención `error-handling`:** los tres códigos exactos y sus mensajes; se usa la **constante**
  `ErrorCode.X`, nunca el literal; el detalle va al log y el mensaje del bus es genérico.
- **Convención `logging`:** prefijo `[bus]`; `warn` para entrada inválida que el servicio maneja
  bien; un `failure` esperado **no** es un `error`.
- **Reusable Code:** `failure()`, `ErrorCode`, `Reply` de `@jiku/nats-protocol`.

**Files to Create/Modify:**

```ts
import { ServiceMsg } from 'nats';
import { ErrorCode, Reply, failure } from '@jiku/nats-protocol';
import logger from '../logger';

/**
 * Versión que el servicio anuncia en el bus. Micro la valida como SemVer ESTRICTO y rechaza el
 * registro con cualquier otra cosa: un `latest` acá no degrada, tira el arranque. Es deliberado.
 */
const SERVICE_VERSION = process.env.SERVICE_VERSION || '1.0.0';

const encode = (reply: Reply): Uint8Array => new TextEncoder().encode(JSON.stringify(reply));

export interface ServiceSpec {
  /** Nombre en el bus, queue group, y token `{svc}` del subject. */
  name: string;
  description: string;
  /** Patrones de método: `tasks.{id}.edit`, `clients.new`, … Salen del registry. */
  patterns: string[];
  /** Resuelve la request. Nunca lanza: siempre devuelve un `Reply`. */
  handle: (subject: string, payload: unknown) => Promise<Reply>;
}

/**
 * Atiende un mensaje. NUNCA LANZA, y no es una precaución: es el contrato.
 *
 * Si una excepción escapara hasta micro, micro responde `Empty` con headers de error y EL CUERPO
 * SE PIERDE — o sea el envelope, que es lo único que la api parsea (ADR-002). A cambio se ganaría
 * un `num_errors` distinto de cero. Cambiar el contrato por una métrica es un mal negocio, así
 * que el try/catch vive acá y la consecuencia asumida es que `num_errors` queda en 0: las fallas
 * se miden por logs y por `errorCode`. No armes alertas sobre esa métrica.
 */
async function handle(spec: ServiceSpec, msg: ServiceMsg): Promise<void> {
  let payload: unknown;
  try {
    // Un cuerpo vacío es `{}`, no un error: los comandos de borrado no llevan payload.
    payload = msg.data.length ? msg.json() : {};
  } catch {
    logger.warn(`[bus] payload inválido en ${msg.subject}`);
    respond(msg, failure(ErrorCode.INVALID_FIELDS, 'Malformed JSON payload'));
    return;
  }

  try {
    respond(msg, await spec.handle(msg.subject, payload));
  } catch (error: any) {
    // El despachador ya captura sus errores; esto es la última red, la que `consumer.ts`
    // tenía en su `.catch()`.
    logger.error(`[bus] ${msg.subject}: ${error.message}`);
    respond(msg, failure(ErrorCode.INTERNAL_ERROR, 'Internal error'));
  }
}

/**
 * El envelope viaja SIEMPRE en el cuerpo, también en los errores: es el contrato y la api lo
 * parsea siempre. En un `failure` se agregan además los headers de micro
 * (`Nats-Service-Error` con el `errorCode`, `Nats-Service-Error-Code` con el 500 del TRANSPORTE
 * micro, que no es el status HTTP). Son un agregado, nunca un reemplazo del cuerpo.
 */
function respond(msg: ServiceMsg, reply: Reply): void {
  if (reply.status === 'success') {
    msg.respond(encode(reply));
    return;
  }
  msg.respondError(500, reply.errorCode ?? 'error', encode(reply));
}
```

- **`error: any` es uno de los dos bordes que `_base` tolera** (es el mismo patrón de
  `dispatcher.ts`:89).
- **`msg.json()` y no `JSON.parse(new TextDecoder().decode(...))`.** Hace lo mismo y es la API de la
  librería; el `data.length` sigue haciendo falta porque `json()` de un cuerpo vacío lanza.
- **No agregues un log por mensaje atendido.** La traza de comandos ya existe y está detrás de
  `LOG_COMMANDS`; un `info` por mensaje inundaría el log de producción.

### Task 4: `bus/service.ts` — `registerService()` y la verificación de duplicados

```ts
import { NatsConnection, Service } from 'nats';
import {
  INSTANCE,
  PROTOCOL_VERSION,
  endpointName,
  endpointSubject,
  groupSubject,
} from '@jiku/nats-protocol';

/**
 * Registra un servicio micro sobre una conexión existente.
 *
 * Micro no ata un servicio a un proceso: `nc.services.add()` crea uno nuevo en cada llamada, con
 * su propio id, sus endpoints y sus contadores. Dos llamadas sobre la MISMA conexión dan dos
 * servicios que se anuncian por separado en `$SRV`. Es lo que hace posible un proceso con dos.
 */
export async function registerService(nc: NatsConnection, spec: ServiceSpec): Promise<Service> {
  const service = await nc.services.add({
    name: spec.name,
    version: SERVICE_VERSION,
    description: spec.description,
    // Queue group propio, y en la config del SERVICIO: el grupo y los endpoints lo heredan en
    // cascada. Sin esta línea quedaría el default `q` de micro, el balanceo entre réplicas
    // pasaría a compartirse con cualquier otro servicio y nada lo delataría.
    queue: spec.name,
    metadata: { instance: INSTANCE, protocol: PROTOCOL_VERSION },
  });

  // El `*` del user id cubre a cualquier caller. Micro lo acepta en el medio del prefijo: su
  // validación de grupo rechaza vacío, espacios y `>` interno, no `*`.
  const group = service.addGroup(groupSubject(spec.name));

  const subjects = new Set<string>();
  for (const pattern of spec.patterns) {
    const subject = endpointSubject(pattern);

    // Dos endpoints que matcheen el mismo subject entregan el mensaje a las DOS suscripciones y
    // ponen dos respuestas en el mismo inbox: el caller devuelve la primera y DESCARTA LA OTRA EN
    // SILENCIO. Respuestas correctas la mitad de las veces, sin un solo error en el log. Se falla
    // al arrancar. Los 20 de hoy no se solapan, pero verificarlo a mano no protege del comando 21.
    if (subjects.has(subject)) {
      throw new Error(`[bus] ${spec.name}: subject de endpoint duplicado: ${subject}`);
    }
    subjects.add(subject);

    group.addEndpoint(endpointName(pattern), {
      subject,
      handler: (err, msg) => {
        if (err) {
          logger.error(`[bus] ${spec.name} ${subject}: ${err.message}`);
          return;
        }
        // Sin await: un mensaje no bloquea la llegada del siguiente. La concurrencia real la
        // acota el pool de Sequelize, igual que en el consumer que esto reemplaza.
        void handle(spec, msg);
      },
    });
  }

  logger.info(`[bus] ${spec.name} v${SERVICE_VERSION}: ${subjects.size} endpoints`);
  return service;
}
```

  muere con el proceso. **No agregues un `try/catch` que limpie y se coma el error** — el arranque
  tiene que fallar (CA-6, CA-7).
- **No verifiques también los nombres duplicados.** Micro indexa por nombre y dos nombres iguales se
  pisarían, pero `endpointName` y `endpointSubject` derivan del mismo patrón: dos nombres iguales
  implican dos subjects iguales, y el `Set` de subjects ya los atrapa. El paquete además ya lo cubre
  con su TS-25.
- **El orden de los endpoints es el orden de `spec.patterns`**, que es el orden de
  `commands/index.ts`:28-49. TS-12 lo compara contra la tabla del contrato en ese orden, así que no
  reordenes ni ordenes alfabéticamente.
- Para TS-17 y TS-18 hace falta reimportar el módulo con otro `SERVICE_VERSION`, porque se lee **al

### Task 5: `bus/host.ts` — una conexión, N servicios, apagado ordenado

**Status:** Completed

#### Description

Crear `core/src/bus/host.ts` con `BusHost`: abre **una** conexión NATS, registra los servicios **en
serie**, y los apaga en el orden que garantiza que ninguna request quede sin respuesta.

Es la pieza que hace posible S-013: registrar `jiku-queries` va a ser **sumar un elemento** al
`new BusHost(...)`. Por eso el constructor toma `...specs` desde el día uno aunque hoy reciba uno
solo — no es sobre-ingeniería, es la forma que la story siguiente necesita.

**Las dos garantías que dependen del orden, y no del código:**

- **Registro en serie** (CA-7). Un `Promise.all` acá dejaría el proceso arriba con un servicio
  registrado y el otro caído, que es exactamente lo que CA-7 prohíbe. El `for` con `await` adentro
  hace que el primer error corte la secuencia y se propague.
- **Apagado: servicios → drain → close** (CA-13). Al revés, una request nueva podría entrar durante
  el drain. Acá `Promise.all` **sí** es correcto: parar servicios es idempotente y no tiene orden
  entre sí.

#### Acceptance Criteria

1. Existe `core/src/bus/host.ts` y exporta `class BusHost` con `constructor(...specs: ServiceSpec[])`.
2. `start()`:
   - lee `NATS_URL` con default `'nats://localhost:4222'`, y `NATS_CREDS`;
   - resuelve el `userId` como `process.env.NATS_USER_ID || COMMAND_SERVICE`, y lo **reemplaza** por
     `serviceUser.userId` cuando `serviceUserFromEnv()` devuelve un service user;
   - pide el primer token y arranca el auto-refresh, logueando el error de renovación;
   - conecta **una** vez con `{ servers, inboxPrefix: inboxPrefix(userId), authenticator?, name: 'jiku-core' }`;
   - registra los specs **en serie**, guardando los `Service` devueltos;
   - arranca el loop de estado de la conexión (`for await (const status of connection.status())`)
     con `void`, sin bloquear.
3. `inboxPrefix` se pasa **siempre**, en los dos caminos (con y sin service user).
4. Si el registro de un spec falla, `start()` **rechaza** con ese error y **no** intenta el
   siguiente.
5. `stop()` ejecuta, en este orden: cortar el auto-refresh → `Promise.all(services.map(s => s.stop()))`
   → `connection.drain()` → `connection.close()`, y loguea `'[bus] desconectado'`.
6. `stop()` sin `start()` previo no lanza.
7. `openConnection(options: ConnectionOptions): Promise<NatsConnection>` es un método `protected` de
   una línea que llama a `connect(options)`, con un comentario que explica que es el seam de test y
   por qué `connect` no se puede stubbear.
8. `core` sigue sin publicar nada en el bus.

#### Technical Details

**Architectural Context References:**
- **ADR-002, segunda y tercera regla:** el cliente **DEBE** fijar `inboxPrefix` con el hash del user
  id; el `userId` **DEBE** salir de la key del service user, **no** de una variable de entorno.
- **Convención `bus-consumer` → Autenticación:** las creds del sentinel no conceden permisos por sí
  solas; es el token de Zitadel el que dispara el auth-callout. `tokenAuthenticator` espera una

- **Convención `bus-consumer` → El inbox va hasheado:** va bajo el **user id propio**, no bajo el

  roban las respuestas.
- **Convención `bus-consumer` → Reglas:** *"`stop()` drena antes de cerrar. No agregues un

- **Integration Points → Zitadel:** `serviceUserFromEnv()` devuelve `null` sin key o sin issuer, y

```ts
import {
  ConnectionOptions,
  NatsConnection,
  Service,
  connect,
  credsAuthenticator,
  tokenAuthenticator,
} from 'nats';
import { readFileSync } from 'fs';
import { serviceUserFromEnv } from '@jiku/zitadel-auth';
import { COMMAND_SERVICE, inboxPrefix } from '@jiku/nats-protocol';
import logger from '../logger';
import { ServiceSpec, registerService } from './service';

/**
 * Una conexión NATS, N servicios micro.
 *
 * Recibe los specs por varargs desde el día uno aunque hoy le pasen uno: `nc.services.add()` no
 * tiene singleton, así que montar el segundo servicio (S-013) es sumar un elemento acá y nada más.
 */
export class BusHost {
  private connection: NatsConnection | null = null;
  private services: Service[] = [];
  private stopTokenRefresh: (() => void) | null = null;
  private specs: ServiceSpec[];

  constructor(...specs: ServiceSpec[]) {
    this.specs = specs;
  }

  async start(): Promise<void> {
    const servers = process.env.NATS_URL || 'nats://localhost:4222';
    const credsPath = process.env.NATS_CREDS;
    // Fallback solo para arrancar sin service user (tests); en un deploy real lo pisa el `sub` de
    // la key, que es el que el callout usa para mintear el permiso de inbox.
    let userId = process.env.NATS_USER_ID || COMMAND_SERVICE;

    const serviceUser = serviceUserFromEnv();
    if (serviceUser) {
      // El inbox va bajo el hash del user id PROPIO, no del nombre del servicio: es por réplica.
      userId = serviceUser.userId;
      await serviceUser.token();
      this.stopTokenRefresh = serviceUser.startAutoRefresh((error) => {
        logger.error(`[bus] no se pudo renovar el token de Zitadel: ${error.message}`);
      });
    }

    const authenticators = [
      ...(credsPath ? [credsAuthenticator(readFileSync(credsPath))] : []),
      ...(serviceUser ? [tokenAuthenticator(() => serviceUser.currentToken())] : []),
    ];

    this.connection = await this.openConnection({
      servers,
      // Sin este prefijo la librería genera un `_INBOX.<aleatorio>` que ningún permiso acotado
      // autoriza, y el síntoma es un TIMEOUT, no un error de permisos: el diagnóstico más caro
      // que este servicio puede tener.
      inboxPrefix: inboxPrefix(userId),
      ...(authenticators.length ? { authenticator: authenticators } : {}),
      name: 'jiku-core',
    });

    // EN SERIE, y el error se propaga: un `Promise.all` acá podría dejar el proceso arriba con un
    // servicio registrado y el otro caído, que es justo lo que no puede pasar.
    for (const spec of this.specs) {
      this.services.push(await registerService(this.connection, spec));
    }

    void (async () => {
      for await (const status of this.connection!.status()) {
        logger.info(`[bus] ${status.type}: ${JSON.stringify(status.data ?? '')}`);
      }
    })();
  }

  /** Para los servicios y drena para que los mensajes en vuelo terminen antes de cerrar. */
  async stop(): Promise<void> {
    this.stopTokenRefresh?.();
    this.stopTokenRefresh = null;

    // LOS SERVICIOS PRIMERO: dejan de aceptar requests nuevas. Al revés, una request nueva podría
    // entrar durante el drain y quedarse sin respuesta.
    await Promise.all(this.services.map((service) => service.stop()));
    this.services = [];

    if (this.connection) {
      await this.connection.drain();
      await this.connection.close();
      this.connection = null;
    }
    logger.info('[bus] desconectado');
  }

  /**
   * El único punto que toca la red, aislado a propósito: `connect` se exporta de `nats` con un
   * getter no configurable, así que no se puede sustituir con sinon. Sin este método, `host.ts`
   * solo se podría testear con un bus real.
   */
  protected openConnection(options: ConnectionOptions): Promise<NatsConnection> {
    return connect(options);
  }
}
```
