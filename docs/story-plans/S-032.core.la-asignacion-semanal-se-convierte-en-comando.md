### H-5 · La regla del lunes va en Joi; C-36 NO PUEDE ir en Joi

Es una consecuencia mecánica de `validateWith`, y decide dónde vive cada regla:

```ts
// core/src/commands/validate.ts — TODO fallo de esquema es invalid_fields, sin excepción
if (result.error) {
  return { error: failure(ErrorCode.INVALID_FIELDS, result.error.message) };
}
```

| Regla | Código que pide la story | Dónde va | Por qué |
|---|---|---|---|
| `dateFrom` es lunes (CA-5) | **`invalid_fields`** | **esquema Joi**, con `.custom()` | Depende SOLO del payload, y `invalid_fields` es exactamente lo que `validateWith` produce |
| Semana no pasada, C-36 (CA-4) | **`invalid_date_range`** | **`execute`** | Joi **no puede** devolver ese código. Meterla en el esquema la convierte en `invalid_fields` y rompe CA-4 |

La convención `validation` ya lo dice de otra forma: *"Las reglas que relacionan campos del payload
entre sí van en el esquema; las que dependen del estado de la base van en `execute`"*. C-36 no
depende de la base, pero **sí depende del código de error**, y eso la manda a `execute` igual.

### H-6 · `date_from` y `date_to` son TIMESTAMP, no DATE

`docs/db-schemas/jiku.md` y `packages/models/src/week-assigned-time.model.ts` coinciden:

```
| `date_from` | `TIMESTAMP` | Lunes de la semana |
| `date_to`   | `TIMESTAMP` | Lunes + 4 días (viernes) |
```

Es la misma rareza que `worked_times.date`, y tiene dos consecuencias:

1. **Escribir el string `'YYYY-MM-DD'` está bien**: `pg` lo coerciona a medianoche. Es lo que la api
   ya hace hoy con `weekEnd`. **No conviertas a `Date` en el comando**: `new Date('2026-08-24')` es
   medianoche UTC pero `new Date('2026-08-24T00:00:00')` es medianoche LOCAL, y esa diferencia es
   justo el bug de borde que `window.ts` documenta.
2. **Leer devuelve un `Date`**, no un string. Solo importa si algún test relee la fila para comparar
   la fecha: usá `toDayUTC()` de `times/window.ts`, que acepta las dos representaciones.

#### La transacción es del despachador, nunca del comando

`core/src/bus/dispatcher.ts`. Abre la transacción, ejecuta el comando y hace **commit si el reply es
`success`, rollback en cualquier otro caso**. El comando recibe la transacción en su contexto pero
**no tiene acceso a `commit` ni `rollback`**.

**Es la propiedad que hace segura esta story entera**: un `destroy` ya ejecutado seguido de un
`failure` **se pierde solo**, sin que el comando haga nada. Una semana a medio reemplazar es
estructuralmente imposible.

#### El despachador nunca lanza

Todo error inesperado se traduce a `failure(ErrorCode.INTERNAL_ERROR, 'Internal error')`. Del otro
lado hay una request esperando: quedarse sin contestar dejaría a la api colgada hasta
`NATS_REQUEST_TIMEOUT_MS` (5000 ms) y el usuario vería un 503 en vez del error real.

#### Las dos compuertas del despachador, en orden

```ts
// 1. EL SOBRE, antes que todo: comparación de strings sobre el cuerpo, sin base ni transacción
const extracted = extractActor(caller, raw);
const { actor, payload } = extracted;

// 2. El espejo de identidad, en SU PROPIA transacción, que commitea antes
if (actor) { await mirrorActor(actor); }

// 3. Los roles: del sobre si hay, de `users` si no, `[]` en el canal exento
const exemptDirect = !actor && caller === getTrustedPublisherId();
roles = actor ? actor.roles : exemptDirect ? [] : await readCallerRoles(caller);
const channel: Channel = actor ? 'envelope' : 'direct';

// 4. COMPUERTA 1 — "¿su rol habilita este método?"  ← ACÁ SE RESUELVE C-38
const denied = authorizeWithRoles(actorIdentity, roles, name, 'commands', channel);
if (denied) return denied;                       // -> caller_not_authorized

// 5. COMPUERTA 2 — la clase de caller (connector | internal | external)
const resolved = resolveCallerClass(roles);

// 6. registry.resolve(name)                       -> unknown_command
// 7. command.validate(payload)                    -> invalid_fields   ← ACÁ VA LA REGLA DEL LUNES
// 8. authorizeEntityAccess(...)  SOLO si callerClass === 'external'  -> access_denied
// 9. sequelize.transaction()  +  command.execute(...)  ← ACÁ VA C-36 Y LA ESCRITURA
```

**Todo lo que decide C-38 ocurre en el paso 4, antes de resolver el método y antes de abrir la
transacción.** Un `user` no llega ni a enterarse de que el comando existe.

### Relevant ADRs

#### ADR-003: La transacción es del despachador, nunca del comando

**Decisión:** invertir la propiedad de la transacción. La abre y la cierra el **despachador**. Los
comandos la reciben en su contexto pero **no tienen acceso a `commit` ni a `rollback`**.

**Implementation Rules (verbatim):**

- Un comando **DEBE** recibir la transacción por su contexto y usarla en todas sus operaciones de
  base de datos. **NO DEBE** abrir una transacción propia.
- Un comando **NO DEBE** llamar a `commit()` ni a `rollback()`. Si el código de un comando los
  invoca, está mal escrito.
- Un comando **DEBE** señalar el fallo devolviendo un `Reply` con `status: 'failure'` y su
  `errorCode`. **NO DEBE** lanzar una excepción para señalar un fallo de negocio esperado.
- El despachador **DEBE** hacer commit **solo** si el reply es `success`, y rollback en todos los
  demás casos, incluidas las excepciones inesperadas.
- El despachador **NO DEBE** lanzar nunca: todo error se traduce a un `Reply` de falla.
- Los tests de comandos **DEBEN** entrar por el despachador (helper `dispatch()`), no llamando a
  `execute()` directamente: es lo único que verifica el comportamiento transaccional, incluido el
  rollback.

> **Es el ADR que esta story ejercita más que ninguna otra.** `destroy` + `bulkCreate` es la
> operación con más ventana de escritura parcial de todo el producto, y el riesgo que la story marca
> como medio —*"una semana a medio reemplazar es el peor resultado posible"*— **lo cierra ADR-003
> solo**, sin una línea del comando. El test de TS-14 es lo que lo demuestra.

#### ADR-001: Separación lectura / escritura por credenciales

**Decisión:** `api` conecta con un rol **sin `INSERT`/`UPDATE`/`DELETE`**; `core` conecta con el
**usuario dueño** de la base (`core/src/models/index.ts:11-16`). Es una decisión de infraestructura,
no de estilo: no hay forma de que la api escriba por accidente.

**Lo que esta story cierra:** `week_assigned_times` era **la única excepción viva** — la api la
escribía con el ORM y funcionaba *"porque el rol de la instalación se lo permite"*. Con el comando,
la escritura pasa al usuario dueño (CA-13). Después de esta entrega el rol de PostgreSQL de la api
**puede endurecerse a `SELECT` puro** para la escritura de dominio; **no se endurece acá**.

#### ADR-002: Comandos NATS sin JetStream

**Decisión:** request/reply sin cola, sin reintento, sin persistencia, sin idempotencia.

**Consecuencia para esta story:** la ruta hereda **503** (`core` caído, la operación NO ocurrió) y
**504** (respuesta perdida, **PUDO haber ocurrido**), **dos desenlaces que nunca tuvo**. Son de la
api; para `core` la regla operativa es la otra: **core no publica nada**, y esto no cambia.

#### ADR-008: Autorización deny-by-default

**Decisión:** sin coincidencia, no se autoriza. Aplica al mapa rol → método, al `COMMAND_ENTITY` y a
`CLASS_BY_ROLE`.

**Consecuencia para esta story:** el comando 21 **nace sin permisos**. Registrarlo en
`commands/index.ts` **no lo autoriza para nadie** salvo `internal-app`, que lleva el sentinela `'*'`.
`admin` lo alcanza **solo** si se agrega su entrada al mapa (CA-12).

#### El código que se está migrando (`api/lib/routes/week-assigned-times-put.ts:39-78`)

```ts
// Calcular weekEnd (viernes, +4 días)
const weekStartDate = new Date(weekStart);
const weekEndDate = new Date(weekStart);
weekEndDate.setDate(weekStartDate.getDate() + 4);
const weekEnd = weekEndDate.toISOString().split('T')[0];

// 1. Eliminar asignaciones existentes de la semana
await WeekAssignedTime.destroy({ where: { dateFrom: weekStart, dateTo: weekEnd }, transaction });

// 2. Preparar nuevas asignaciones
for (const alloc of allocations) {
  if (alloc.minutes === 0) { continue; }                                  // descarte
  const project = await Project.findByPk(alloc.projectId, { transaction }); // N consultas
  if (!project) { throw new Error(`Project ${alloc.projectId} not found`); }
  const internal = project.type === 'interno';                            // derivación
  allocationsToCreate.push({
    personId: alloc.personId, projectId: alloc.projectId, minutes: alloc.minutes,
    internal, dateFrom: weekStart, dateTo: weekEnd,
  });
}

// 3. Crear asignaciones
await WeekAssignedTime.bulkCreate(allocationsToCreate, { transaction });
```

**Tres cosas que el comando hace DISTINTO, y las tres a propósito:**

1. **Una consulta de proyectos, no N.** El bucle hace `findByPk` por asignación. El comando usa un
   solo `findAll({ where: { id: { [Op.in]: ids } } })` y arma un `Map`. Es el patrón que la
   convención `orm` documenta (*"Un `count` contra el largo de la lista"*), y sobre una grilla de
   ~20 personas × ~10 proyectos la diferencia es real.
2. **`person_not_found` en vez de una violación de FK.** La api no valida personas: una `personId`
   inexistente rompe por foreign key y sale **500**. El contrato del bus declara `person_not_found`,
   así que el comando lo valida y responde **400**. Es la única diferencia de comportamiento
   observable, y está **declarada en el contrato**.
3. **`project_not_found` en vez de un `throw`.** La api lanza y traduce a 500. Un comando **NO
   LANZA** (ADR-003): devuelve `failure(ErrorCode.PROJECT_NOT_FOUND, …)`.

#### El `validateWeekNotPast` que se está migrando (`api/lib/utils/middlewares/validate-week-not-past.ts`)

```ts
const weekStart = new Date(req.body.weekStart);
const today = new Date();
const dayOfWeek = today.getDay();                            // 0=domingo, 1=lunes
const diff = dayOfWeek === 0 ? -6 : 1 - dayOfWeek;           // lunes de la semana actual
const mondayOfCurrentWeek = new Date(today);
mondayOfCurrentWeek.setDate(today.getDate() + diff);
mondayOfCurrentWeek.setHours(0, 0, 0, 0);
weekStart.setHours(0, 0, 0, 0);
if (weekStart < mondayOfCurrentWeek) {
  return res.status(400).json({ code: 'invalid_week', message: 'No se pueden modificar semanas pasadas' });
}
```

**La regla:** `dateFrom >= lunes de la semana actual`. La semana **actual** se acepta; la **anterior**
se rechaza; la **siguiente** se acepta.

> **La api la calcula en hora LOCAL** (`getDay`, `setHours`). **El comando la calcula en UTC**, igual
> que `window.ts`, y eso es una mejora deliberada (D-3): *"un bug de zona horaria acá aparece SOLO EN
> EL BORDE y SOLO ALGUNAS HORAS DEL DÍA, que es la peor forma que puede tener un bug"*. Con
> `TZ=UTC` fijado en el contenedor y en los tests, las dos dan el mismo resultado hoy.

> **El `errorCode` NO se conserva.** La api responde `invalid_week`; el comando responde
> **`invalid_date_range`**, porque es lo que el contrato del bus declara (CA-4) y lo que la api
> mapeará a 400. **El texto sí se conserva** (`'No se pueden modificar semanas pasadas'`): cruza el
> bus y llega al usuario final.

### Code Conventions

| Aspecto | Regla |
|---|---|
| Archivos | `kebab-case.ts`. **Un archivo por comando**: `{entidad}-{acción}.ts`. Los que comparten payload y helpers pueden compartir archivo si son la misma operación en dos direcciones |
| Comandos exportados | `camelCase` que coincide con el `pattern`: `weekAssignedTimesReplace` → `week-assigned-times.replace` |
| Export | **nombrado Y también `default`**. `commands/index.ts` importa el default |
| Interfaces de payload | `{Comando}Payload` → `WeekAssignedTimesReplacePayload`. **Escrita a mano**, no inferida del esquema |
| Constantes de módulo | `SCREAMING_SNAKE_CASE` |
| Imports | **Relativos**, sin alias. Orden: `joi` → `sequelize` → `@jiku/models` → `@jiku/nats-protocol` → relativos |
| Comentarios | **En español**, y explican **el por qué**, no el qué |
| `strict: true` | No se apaga. Tampoco `noUnusedLocals` / `noUnusedParameters` / `noImplicitReturns` |

**Las cinco partes de un archivo de comando, siempre en este orden:**

```
imports → interfaz del payload → esquema Joi (`const schema`) → el objeto `Command` → `export default`
```

**El orden dentro de `execute`, según la convención `commands`:**

1. Buscar la entidad del `params` → `*_not_found` *(este comando no tiene params)*
2. Validar las referencias del payload → su código
3. Validar las reglas de negocio
4. Calcular lo que necesita el estado anterior *(no aplica: no hay historial)*
5. **Escribir**, siempre con `{ transaction: ctx.transaction }`
6. `success()` o `success({ id })`

> **Este comando invierte 2 y 3, igual que `worked-times.new` invirtió el suyo (D-2).** Ver la
> Tarea 2.

**Lo que un comando NO hace:**

- **No abre ni cierra transacciones.**
- **No lanza.** Un error esperado es un `Reply` de falla.
- **No lee `process.env`.** Las constantes de negocio son constantes de módulo.
- **No loguea el flujo normal.** El despachador ya traza con `LOG_COMMANDS`.
- **No decide si un rol habilita un método.** Eso es de la compuerta.

**La regla que más cuesta cuando algo falla:**

> **Toda escritura pasa `{ transaction: ctx.transaction }`. Sin excepción, incluidas las lecturas.**
> Una que se olvide corre **fuera de la transacción y sobrevive al rollback**. Es el error más fácil
> de cometer en este codebase y el más difícil de ver: el test pasa.

**Implementation Notes:**

- **El chequeo del lunes, en UTC y sin construir un instante ambiguo:**

  ```ts
  // `T00:00:00Z` EXPLÍCITO: `new Date('2026-08-24')` ya es UTC, pero la forma sin sufijo es la que
  // un lector futuro va a "corregir" a `new Date(v + 'T00:00:00')`, que es medianoche LOCAL. El
  // mismo bug de borde que `window.ts` documenta.
  const MONDAY = 1;
  dateFrom: joi.string().pattern(/^\d{4}-\d{2}-\d{2}$/).required().custom((value, helpers) => {
    if (new Date(`${value}T00:00:00Z`).getUTCDay() !== MONDAY) {
      return helpers.error('any.invalid');
    }
    return value;
  }),
  ```

  **`getUTCDay()`, nunca `getDay()`.** `getDay()` es hora local y en una TZ negativa un lunes UTC se
  lee como domingo: el comando rechazaría lunes válidos algunas horas del día. Es el mismo bug que
  `window.ts` describe como *"la peor forma que puede tener un bug"*.

- **`.custom()` y no `.valid()` ni una expresión regular:** el día de la semana no es una propiedad
  del texto, hay que calcularlo.
- **`.pattern()` y no `joi.date()`** (convención `validation`): *"Cuando la columna es string y el
  contrato también, se valida con patrón y no con `joi.date()`"*. Además `joi.date()` con

- **`min(0)` y no `min(1)`**: es la diferencia deliberada con `worked-times.new`. Ver el bloque de
  `WeekAssignedTimesReplacePayload` en API Context.
- **Nombre del archivo:** `week-assigned-times.ts`, sin sufijo de acción. Es un solo comando hoy,

  (`worked-times.ts`, `unworked-times.ts`) y el comando futuro de la grilla iría al mismo archivo.

### Task 2: El `execute` — C-36, la derivación de `internal` y el reemplazo total

**Status:** Completed

#### Description

El corazón de la story: el objeto `Command` con su `execute`, que aplica **C-36**, valida las
referencias, deriva `internal` de `projects.type`, descarta las asignaciones con `minutes: 0` y
**borra y recrea la semana entera** dentro de la transacción del despachador.

Es una **mudanza de servicio, no un rediseño**: la semántica de reemplazo total ya es la de la
entidad. Lo que cambia es quién escribe y con qué credencial.

#### Acceptance Criteria

1. El archivo exporta `weekAssignedTimesReplace` **nombrado y como `default`**, con
   `pattern: 'week-assigned-times.replace'`.
2. `execute` aplica **C-36** —`dateFrom` no puede ser anterior al lunes de la semana actual, en
   UTC— y responde `failure(ErrorCode.INVALID_DATE_RANGE, 'No se pueden modificar semanas
   pasadas')`.
3. Un proyecto inexistente responde `failure(ErrorCode.PROJECT_NOT_FOUND, ...)`; una persona
   inexistente, `failure(ErrorCode.PERSON_NOT_FOUND, ...)`.
4. Las asignaciones con `minutes: 0` **no se insertan** y **no producen error**.
5. `internal` se deriva de `projects.type === 'interno'` y **nunca** se lee del payload.
6. `dateTo` se calcula como `dateFrom + 4 días` (viernes), en UTC.
7. La semana se borra **entera** por `date_from` y se recrea con `bulkCreate`.
8. **Todas** las operaciones —`findAll`, `destroy`, `bulkCreate`— llevan
   `{ transaction: ctx.transaction }`.
9. El comando **no llama** a `commit()` ni a `rollback()`, y **no lanza** para señalar errores
   esperados.
10. El reply exitoso es **`success()` sin argumento**.

#### Technical Details

**Architectural Context References:**

- **ADR-003** — Implementation Rules completas en Architectural Context. Es lo que hace que TS-14
  (rollback a mitad de reemplazo) pase **sin escribir una línea de manejo de errores**.
- **ADR-001** — la escritura por la conexión del dueño. `core` **solo tiene** esa conexión para
  comandos, así que CA-13 se cumple estructuralmente.
- Convención **`commands`** — el orden dentro de `execute`, `success()` para ediciones/borrados, y

- Convención **`orm`** — el patrón de existencia en bloque (un `count`/`findAll` contra el largo de

- Convención **`error-handling`** — se usa la **constante** `ErrorCode.X`, nunca el literal; los

**Implementation Notes:**

- **D-2 · El orden de `execute`, y por qué no es el literal de la convención:**

  ```
  1. C-36: la semana no puede ser pasada        -> invalid_date_range
  2. derivar dateTo                              (puro)
  3. filtrar las asignaciones con minutes: 0     (puro)
  4. validar proyectos en UNA consulta           -> project_not_found
  5. validar personas en UNA consulta            -> person_not_found
  6. DELETE de la semana                         (transacción del despachador)
  7. bulkCreate                                  -> success()
  ```

  **C-36 va PRIMERO, contra el orden literal de la convención (referencias antes que reglas), y es
  a propósito:** es pura, no cuesta una sola consulta, y rechazar una semana pasada **antes** de
  preguntar por proyectos y personas es el mismo criterio con que el despachador corre Joi antes de
  abrir la transacción. Es el mismo tipo de desvío que `worked-times.new` documentó en su D-7.

  **El filtro de `minutes: 0` va antes de validar referencias (paso 3), y también importa:** una
  celda vacía con un `projectId` que ya no existe **no debe** hacer fallar el guardado. La api hace
  lo mismo (el `continue` está antes del `findByPk`).

- **C-36, el cálculo:**

  ```ts
  /** Lunes de la semana de `today`, `YYYY-MM-DD` en UTC. */
  function mondayOfWeekUTC(today: Date): string {
    const day = today.getUTCDay();                 // 0 = domingo
    // EL DOMINGO RESTA 6, NO 1: `1 - 0` daría el lunes SIGUIENTE y aceptaría toda la semana
    // pasada durante 24 h por semana. Es el mismo ajuste que hace `validateWeekNotPast`.
    const diff = day === 0 ? -6 : 1 - day;
    const monday = new Date(Date.UTC(
      today.getUTCFullYear(), today.getUTCMonth(), today.getUTCDate() + diff
    ));
    return toDayUTC(monday);
  }
  ```

  y la comparación, **entre strings `'YYYY-MM-DD'`**, que ordenan lexicográficamente igual que
  cronológicamente:

  ```ts
  if (payload.dateFrom < mondayOfWeekUTC(new Date())) {
    return failure(ErrorCode.INVALID_DATE_RANGE, 'No se pueden modificar semanas pasadas');
  }
  ```

  **No compares `Date`s:** cualquier componente de hora vuelve a meter la zona horaria en la
  decisión. Es la misma razón que `window.ts` escribe para su comparación.

  **El texto se conserva de la api** (`validate-week-not-past.ts`): cruza el bus y llega al usuario
  final, así que la paridad se sostiene hasta en la redacción. **El `errorCode` NO se conserva** —
  `invalid_week` era de HTTP, el contrato del bus dice `invalid_date_range`.

- **`dateTo`, en UTC y sin mutar nada:**

  ```ts
  const from = new Date(`${payload.dateFrom}T00:00:00Z`);
  const dateTo = toDayUTC(new Date(Date.UTC(
    from.getUTCFullYear(), from.getUTCMonth(), from.getUTCDate() + 4
  )));
  ```

  `Date.UTC` **normaliza el desborde** de mes y de año sin que haya que pensarlo, que es exactamente
  el argumento que `window.ts` ya escribió para su borde inferior.

- **Las dos validaciones de referencias, una consulta cada una:**

  ```ts
  const projectIds = [...new Set(rows.map((a) => a.projectId))];
  const projects = await Project.findAll({
    where: { id: { [Op.in]: projectIds } },
    transaction: ctx.transaction,
  });
  if (projects.length !== projectIds.length) {
    return failure(ErrorCode.PROJECT_NOT_FOUND, 'Proyecto no encontrado');
  }
  // El Map es lo que hace que la derivación de `internal` NO cueste una consulta por asignación.
  const isInternal = new Map(projects.map((p) => [p.id, p.type === 'interno']));

  const personIds = [...new Set(rows.map((a) => a.personId))];
  const personCount = await Person.count({
    where: { id: { [Op.in]: personIds } },
    transaction: ctx.transaction,
  });
  if (personCount !== personIds.length) {
    return failure(ErrorCode.PERSON_NOT_FOUND, 'Persona no encontrada');
  }
  ```

  **`findAll` para proyectos y `count` para personas, y la asimetría es deliberada:** de los
  proyectos hace falta el `type` para derivar `internal`; de las personas solo hace falta saber que
  existen. Traer las filas de personas sería traer datos que nadie mira.

  **El `[...new Set(...)]` no es cosmético:** la grilla manda la misma `personId` una vez por
  proyecto, y sin deduplicar la comparación `length !== length` fallaría con datos perfectamente
  válidos.

  **Ninguna de las dos informa CUÁL falta**, y es el patrón que la convención `orm` ya declara para
  la validación en bloque: *"No informa cuál falta — está documentado así en el contrato"*.

- **D-5 · El `DELETE` va por `date_from` SOLO, no por el par `(date_from, date_to)`:**

  ```ts
  await WeekAssignedTime.destroy({
    where: { dateFrom: payload.dateFrom },
    transaction: ctx.transaction,
  });
  ```

  La api hoy borra por los dos (`where: { dateFrom: weekStart, dateTo: weekEnd }`). **Borrar por
  `date_from` solo es más correcto**, y es lo que dicen el flujo (`DELETE FROM week_assigned_times
  WHERE date_from = '2026-08-17'`) y CA-2 (*"borra y recrea la semana entera"*): una fila legada con
  un `date_to` que no sea `date_from + 4` sobreviviría al reemplazo y quedaría huérfana en una semana
  que el usuario cree haber vaciado. Con el `date_to` derivado deterministicamente, en datos sanos
  las dos formas borran exactamente lo mismo.

- **El `bulkCreate`, con la transacción:**

  ```ts

    rows.map((a) => ({

    const reply = await dispatch('week-assigned-times.replace', { dateFrom: LUNES, assignments: [
      { projectId: PROJ_COM, personId: P_ANA,  minutes: 60 },
      { projectId: 999999,   personId: P_BETO, minutes: 60 },   // no existe
    ]});

    reply.status.should.equal('failure');
    reply.errorCode!.should.equal(ErrorCode.PROJECT_NOT_FOUND);

    // LA MITAD QUE IMPORTA: la semana quedó ENTERA, no vacía y no a medias.
    const filas = await WeekAssignedTime.findAll({ where: { dateFrom: LUNES }, order: [['minutes','DESC']] });
    filas.length.should.equal(2);
    filas.map((f) => f.minutes).should.deepEqual([480, 240]);
  });
  ```

  **Agregá además el caso simétrico con un `personId` inexistente**, que es el que fallaría si
  alguien reordenara las validaciones y dejara la de personas después del `destroy`. Es el test que
  convierte la garantía de ADR-003 en una regresión detectable en vez de una promesa.

- **La forma de los tres canales:**

  ```ts
  // E (sobre) — el actor viaja DENTRO del payload; el despachador lo extrae antes de validar
  await dispatch('week-assigned-times.replace',
    { actor: { id: BETO, roles: ['admin'] }, dateFrom: LUNES, assignments: [] });

  // D (directo) — la identidad sale del subject; BETO necesita fila en `users` con sus roles
  await dispatch('week-assigned-times.replace', { dateFrom: LUNES, assignments: [] }, BETO);

  // X (exento) — el default: publicador de confianza SIN sobre, roles []. La compuerta lo deja pasar
  await dispatch('week-assigned-times.replace', { dateFrom: LUNES, assignments: [] });
  ```

  **Ojo con el default:** un test de C-38 que **olvide** el sobre o el caller cae en el canal
  **exento** y responde `success`, que es lo contrario de lo que afirma. Los tests de TS-28 a TS-32
  tienen que pasar identidad **explícitamente, siempre**.

- **La matriz de paridad (TS-33, TS-34)** usa el mismo reductor que `times-parity.test.ts`:

  ```ts
  type Decision = [string, string | null];
  const decision = (r: Reply<unknown>): Decision => [r.status, r.errorCode ?? null];
  ```

  Compara **la decisión, no la redacción**. El criterio de comparabilidad es que el `sub` sea **el
  mismo** y los roles sean **los mismos** de los dos lados: con sobre mandan `actor.roles` y no se
  lee la base; sin sobre salen de `users.roles`.

- **Fixtures y limpieza:** `Project` (uno `comercial`, uno `interno`), `Person` (dos), y para el
  archivo de auth también `User` con roles. `WeekAssignedTime.destroy({ where: {} })` en el
  `afterEach` — el reemplazo total hace que los tests se pisen entre sí si no.
- **`TZ=UTC` está fijado** en `tests/setup-env.ts`. No dependas de la zona local en ningún cálculo.

## Decisiones de diseño registradas

| # | Decisión | Por qué |
|---|---|---|
| **D-1** | El comando 21 va en una constante **propia de `admin`** (`ADMIN_COMMANDS`), no en `INTERNAL_COMMANDS` | `admin` y `user` **comparten** esa constante a propósito. Meterlo ahí se lo daría a `user` y rompería CA-3 y CA-12 |
| **D-2** | En `execute`, **C-36 va primero** y el filtro de `minutes: 0` va **antes** de validar referencias | C-36 es pura y cuesta cero consultas: rechazar una semana pasada antes de preguntar por proyectos es el mismo criterio con que Joi corre antes de la transacción. Y una celda **vacía** con un proyecto borrado no debe hacer fallar el guardado — es lo que hace la api hoy |
| **D-3** | Todo el cálculo de fechas en **UTC** (`getUTCDay`, `Date.UTC`), y la comparación entre **strings** `'YYYY-MM-DD'` | La api lo hace en hora local. Un bug de zona horaria acá *"aparece SOLO EN EL BORDE y SOLO ALGUNAS HORAS DEL DÍA"* — la peor forma que puede tener un bug. Con `TZ=UTC` fijado, las dos dan lo mismo hoy |
| **D-4** | `COMMAND_ENTITY['week-assigned-times.replace'] = null` | La regla del mapa es *"qué ruta aplica hoy la capa 3"*, y `week-assigned-times-put.ts` no la aplica. Un descriptor sería **endurecer**, y esta story migra reglas |
| **D-5** | El `DELETE` va por **`date_from` solo**, no por el par `(date_from, date_to)` | Es lo que dicen CA-2 (*"la semana entera"*) y el flujo. Con el par, una fila legada con `date_to` distinto sobreviviría a un reemplazo que el usuario cree total. En datos sanos borran lo mismo |
| **D-6** | `overview.md` se edita **mínimamente** (20→21); el resto del corpus queda para `/product-change-technical-definition` | TS-102 ata el documento al registry en un solo test y **no hay forma de dejarlo verde sin tocarlo** (H-2). La story excluye el barrido, no esta línea |
| **D-7** | El canal 21 **gana `access_denied`** en su `x-error-codes` | El spec lo declara **uniformemente en los 20 canales**, incluidos los 12 que tampoco pueden emitirlo. Es política del plano, no derivación por comando — y el único motivo de la excepción (*"su comando no existe todavía"*) deja de ser cierto acá |
