**Las tres capas de obtención de datos** (convención `data-fetching`, custom de este servicio).
Ninguna capa se saltea desde un componente cliente:

```
componente cliente
      │   useRequirements({ filters })            features/{m}/hooks/useRequirements.ts
      ▼
  useQuery({ queryKey: ['requirements', filters] })   ← cache
      │   queryFn
      ▼
  getRequirements(filters)                       features/{m}/services/requirementsApi.ts
      │   'use server'
      ▼
  apiClient.get('/requirements?...')             lib/axios.ts (interceptor → Bearer)
      ▼
  api
```

**La regla central del servicio: el token nunca sale del servidor.** Los `services/*Api.ts` llevan
`'use server'` y el interceptor de `apiClient` llama a `auth()`, que solo corre en el servidor. El
`baseURL` ya incluye `/api`, así que las rutas que se pasan a `apiClient` empiezan en `/`.

**Manejo de errores** (convención `error-handling`): `error.tsx` por ruta, `ApiError` normalizado,
toasts. **En esta pantalla el error del listado hoy no se maneja** (`useRequirements` se
desestructura sin `isError`), y un fallo se ve como `"No se encontraron requisitos"`. Esta story
**no** arregla eso para el listado —no hay CA que lo pida— pero sí exige aislamiento explícito para
los conteos (CA-8).

**Estrategia de testing:** Vitest + Testing Library, tests junto al código como `{Nombre}.test.tsx`.
No hay carpeta `__tests__/`.

### Relevant ADRs

**ADR-011 — Cache de servidor con TanStack Query.** La configuración global ya provee el
`staleTime` de 30 s que la story cita; **no hace falta declararlo por hook**.

`src/lib/queryClient.ts` (verbatim):

```ts
const STALE_TIME = 30 * 1000;
const GC_TIME = 5 * 60 * 1000;

export const makeQueryClient = () => new QueryClient({
  defaultOptions: {
    mutations: { retry: 0 },
    queries: {
      gcTime: GC_TIME,
      refetchOnReconnect: true,
      refetchOnWindowFocus: true,
      retry: 1,
      staleTime: STALE_TIME,
    },
  },

```

**Reglas aplicables a esta story:**

- Los 7 conteos se cachean 30 s por defecto: ir y volver entre tabs dentro de esa ventana **no**
  repite las llamadas. No agregar `staleTime` por query.
- `retry: 1` es el default: un conteo que falla reintenta una vez antes de quedar en error. El
  aislamiento de CA-8 se resuelve **por query**, no desactivando el retry.

**Hechos del contrato que importan al implementar:**

1. **La respuesta de conteo es el número crudo**, no un sobre: `12`, no `{ count: 12 }`. Verificado
   contra la implementación entregada por S-036 en `api/lib/routes/requirements-get.ts`:
   `res.status(200).json(count)`.
2. `page` y `limit` **se ignoran** cuando `count=true`. No hace falta —ni conviene— mandarlos.
3. La api compara `String(req.query.count) !== 'true'`: el string `'false'` es truthy y devolvería
   el conteo a quien pidió el listado. Por eso **nunca** se manda `count=false`; se omite.
4. `limit` tiene máximo 100 y default 20. El listado de la card usa 5 o 10.
5. El orden es siempre `createdAt DESC` — `sort` se acepta y se ignora.
6. Autorización: `hasAnyRole(['user', 'admin'])`. Sin cambios desde esta story.
7. `401` lo maneja el interceptor de axios existente; comportamiento actual sin cambios.

**Ejemplos concretos de las dos llamadas de esta story:**

```
GET /requirements?projectId=1&state=desarrollo&count=true    → 200  12
GET /requirements?projectId=1&state=desarrollo&page=1&limit=5 → 200  [ {...}, {...}, {...}, {...}, {...} ]
```

**`Pagination`** — `web/src/shared/components/ui/Pagination/Pagination.tsx`. El paginador único del

Contrato público exacto (unión discriminada; `PaginationProps` **no** se exporta, solo el

```ts
interface PaginationBaseProps {
  readonly totalItems: number;
  readonly limit: number;
}

type PaginationUrlProps = PaginationBaseProps & {
  /** Ruta base a la que navegar; el resto de los searchParams se preservan. */
  readonly basePath: string;
  readonly currentPage?: never;
  readonly onPageChange?: never;
};

type PaginationControlledProps = PaginationBaseProps & {
  readonly currentPage: number;
  readonly onPageChange: (page: number) => void;
  readonly basePath?: never;
};

type PaginationProps = PaginationUrlProps | PaginationControlledProps;
```

Implementación entregada (verbatim, 113 líneas):

```tsx
'use client';
import React, { useCallback } from 'react';
import { useRouter, useSearchParams } from 'next/navigation';
import { getPageWindow } from './getPageWindow';
import styles from './Pagination.module.scss';

// ... (tipos de arriba) ...

export function Pagination(props: PaginationProps) {
  const { totalItems, limit } = props;
  const controlled = isControlled(props);
  const basePath = controlled ? undefined : props.basePath;
  const onPageChange = controlled ? props.onPageChange : undefined;

  const router = useRouter();
  const searchParams = useSearchParams();

  const createQueryString = useCallback(
    (name: string, value: string) => {
      const params = new URLSearchParams(searchParams?.toString());
      params.set(name, value);
      return params.toString();
    },
    [searchParams],
  );

  const derivedPage = (() => {
    const pageParam = searchParams?.get('page');
    const parsed = Number(pageParam);
    return Number.isFinite(parsed) && parsed >= 1 ? Math.floor(parsed) : 1;
  })();

  const currentPage = controlled ? props.currentPage : derivedPage;
  const totalPages = Math.ceil(totalItems / limit);

  const handlePageChange = useCallback(
    (newPage: number) => {
      if (onPageChange) {
        onPageChange(newPage);
        return;
      }
      router.push(`${basePath}?${createQueryString('page', String(newPage))}`);
    },
    [onPageChange, router, basePath, createQueryString],
  );

  if (totalItems === 0) {
    return null;
  }

  const pageNumbers = getPageWindow({ currentPage, totalPages });

  return (
    <nav className={styles.pagination} aria-label="Paginación" role="navigation">
      <button
        type="button"
        onClick={() => handlePageChange(currentPage - 1)}
        disabled={currentPage === 1}
        aria-label="Página anterior"
      >
        {'<'}
      </button>
      {pageNumbers.map((pageNumber) => {
        const isCurrentPage = currentPage === pageNumber;
        return (
          <button
            type="button"
            key={pageNumber}
            onClick={() => handlePageChange(pageNumber)}
            disabled={isCurrentPage}
            data-active={isCurrentPage || undefined}
            aria-label={`Página ${pageNumber}`}
            aria-current={isCurrentPage ? 'page' : undefined}
          >
            {pageNumber}
          </button>
        );
      })}
      <button
        type="button"
        onClick={() => handlePageChange(currentPage + 1)}
        disabled={currentPage === totalPages}
        aria-label="Página siguiente"
      >
        {'>'}
      </button>
    </nav>
  );
}
```

> ### Cuatro hechos del componente entregado que contradicen supuestos de la story
>
> La sección "Consideraciones Técnicas" de S-038 se escribió antes de que S-037 se implementara.
> Estos cuatro puntos son lo que **realmente** se entregó, verificado contra el código:
>
> 1. **`hideWhenEmpty` NO existe.** La story dice que S-037 "expone el comportamiento de lista
>    vacía como decisión del consumidor (prop explícita, ej. `hideWhenEmpty`)". No se entregó: el
>    componente hace `if (totalItems === 0) return null;` incondicionalmente. **Da igual para esta
>    story**: ese es exactamente el comportamiento que piden CA-5 y CA-7. **No agregar la prop** —
>    sería superficie de API sin ningún CA que la pida.
> 2. **La prop se llama `limit`, no `pageSize`.** El contrato es `totalItems` + `limit`; S-037
>    rechazó explícitamente exponer `totalPages`. El estado local de la card puede seguir
>    llamándose `pageSize`, pero lo que se le pasa al componente es `limit={pageSize}`.
> 3. **`Pagination` no renderiza `<select>` de tamaño de página.** El selector 5/10 de la card
>    **sigue siendo de la card**, y ahora queda **fuera** del `<nav>` que renderiza el componente
>    compartido (antes estaba adentro). Es un cambio de estructura del DOM a tener en cuenta en los
>    tests.
> 4. **`useSearchParams()` se llama incluso en modo controlado.** El componente lo invoca antes de
>    ramificar. En tests, mockear solo `useRouter` **hace explotar el render**: el mock de
>    `next/navigation` tiene que incluir `useSearchParams`.

**`getPageWindow`** — `web/src/shared/components/ui/Pagination/getPageWindow.ts`. Función pura, sin
dependencia de React, que calcula la ventana de páginas. Ya catalogada en `docs/reusable-code/web/`.
La usa `Pagination` internamente; **esta story no la llama directamente**.

```ts
const PAGE_WINDOW_SIZE = 10;

export function getPageWindow({ currentPage, totalPages }: GetPageWindowParams): number[] {
  if (totalPages <= 0) return [];
  if (totalPages <= PAGE_WINDOW_SIZE) {
    return Array.from({ length: totalPages }, (__, index) => index + 1);
  }
  const idealStart = currentPage - Math.floor(PAGE_WINDOW_SIZE / 2);
  const maxStart = totalPages - PAGE_WINDOW_SIZE + 1;
  const start = Math.min(Math.max(idealStart, 1), maxStart);
  const end = start + PAGE_WINDOW_SIZE - 1;
  return Array.from({ length: end - start + 1 }, (__, index) => start + index);
}
```

#### Servicios

**`getRequirements`** — `web/src/features/requirements/services/requirementsApi.ts`. El listado.
**Ya soporta todo lo que la card necesita**: `state`, `page` y `limit` viajan dentro del objeto de
filtros. No requiere cambios.

```ts
'use server';
const cleanFilters = (filters: object): Record<string, string> => {
  return Object.fromEntries(
    Object.entries(filters).filter(([, value]) => value && value !== 'all')
  ) as Record<string, string>;
};

export const getRequirements = async (filters: RequirementFilters = {}): Promise<Requirement[]> => {
  const nonEmptyFilters = cleanFilters(filters);
  const queryParams = new URLSearchParams(nonEmptyFilters).toString();
  const response = await apiClient.get(`/requirements?${queryParams}`);
  return response.data;
};
```

**`cleanFilters`** es un `const` privado de ese módulo (hay una copia distinta, tipada como
`ObjectiveFilters`, en `objectivesApi.ts`). Descarta las entradas cuyo valor es falsy o `'all'`.
**Esto es lo que hace correcto el patrón de `count`:** `cleanFilters({ count: true })` conserva la
entrada y `URLSearchParams` la serializa como `count=true`; un `count: false` es falsy y se cae solo
— que es exactamente lo que se quiere, dado el punto 3 del API Context.

**`getObjectivesCount`** — `web/src/features/objectives/services/objectivesApi.ts:23-28`. **El
antipatrón que la story prohíbe copiar:**

```ts
export const getObjectivesCount = async (filters: ObjectiveFilters = {}): Promise<number> => {
  const nonEmptyFilters = cleanFilters(filters);
  const queryParams = new URLSearchParams(nonEmptyFilters).toString();
  const response = await apiClient.get(`/objectives?${queryParams}&count=true`);  // ← línea 26
  return response.data;
};
```

Concatena `&count=true` a mano sobre la query string ya serializada. Además de saltearse
`cleanFilters`, produce `/objectives?&count=true` cuando no hay filtros. **El equivalente de
requisitos pasa `count` dentro del objeto de filtros.**

#### El patrón de clamp: `RequirementDetail`

`web/src/features/requirements/components/RequirementDetail/RequirementDetail.tsx:180-183`
(verbatim) — el patrón que la story cita para CA-9:

```tsx
const filtered = objectives.filter((o) => o.state === activeObjTab);
const totalPages = Math.max(1, Math.ceil(filtered.length / objPageSize));
const page = Math.min(objPage, totalPages);
const pageItems = filtered.slice((page - 1) * objPageSize, page * objPageSize);
```

**Lo importante del patrón: el clamp es derivado en el render, no un `setState`.** `objPage`
conserva su valor viejo en el estado mientras `page` es el valor efectivamente usado. Para S-038 el
equivalente se calcula sobre el **conteo del tab activo**, y el valor clampeado alimenta tanto la
query key del listado (para que el refetch de la página válida se dispare) como el `currentPage` que
se le pasa a `<Pagination>`.

**`tabla-requisitos`:**
- Columnas: `"ID"` · `"Título"` · `"Responsable"` · `"Tipo"` · `"Prioridad"` · `"Creación"`.

**`paginacion-requisitos`:**
- `<select>` de tamaño de página con `"5 por página"` / `"10 por página"`; números de página.
- Tamaño de página **5 por defecto**.
- **REQ-008:** deja de ser una reimplementación inline y pasa a ser el **paginador único del
  producto, en modo controlado** — el bloque no navega por URL, avisa el cambio de página al
  contenedor y la card conserva su estado local. Muestra **como máximo 10 números** en una ventana

#### Estados aplicables

**`empty`:**
- Mensaje: `"No se encontraron requisitos"`.
- `tabla-requisitos`: el cuerpo se reemplaza por una celda con `colSpan` y el mensaje.
- **REQ-008 · `tabs-estado-requisito` y `paginacion-requisitos`:** un estado sin requisitos muestra
  el tab con el total `0` —**dato real de la api, no ausencia de datos**— y **el paginador no se
  renderiza**: no hay páginas navegables. Con el proyecto entero vacío los 7 tabs muestran `0`. El
  vacío ahora es un hecho verificado del proyecto y no el efecto de una página fuera de rango.

**`loading`:**
- Mensaje por sección: `"Cargando requisitos..."`; solo el cuerpo de la tabla se reemplaza por una
  celda con `colSpan`; tabs y encabezados quedan.
- **REQ-008 · la sección de requisitos carga en dos pistas independientes.** El listado del estado
  activo y los 7 contadores son consultas separadas: el cuerpo de la tabla puede estar cargando
  mientras los tabs ya muestran sus totales, y al revés. Cambiar de tab o de tamaño de página vuelve
  a poner en carga el cuerpo de la tabla —**nunca la pantalla completa**—, y al cambiar de tab **los
  7 contadores también se refrescan**. Los tabs, el `<select>` y el paginador siguen visibles y
  operables durante la carga.

**`error de sistema / sin conexión`:**
- **REQ-008 · el fallo de un contador queda aislado.** Los 7 conteos son consultas independientes:
  si uno falla, **ese tab muestra un placeholder neutro en lugar del número y nada más se ve
  afectado** — ni la tabla del tab activo, ni los otros seis contadores. Es consecuencia directa de
  pedir cada total por separado: antes había un solo cálculo en memoria y cualquier fallo se llevaba
  puesta la sección entera.
- Contexto preexistente **que esta story no arregla**: el error al cargar el proyecto no se maneja
  (loader infinito), y los errores del listado de requisitos y tareas tampoco (`useRequirements` sin
  `isError`, así que un fallo se ve como `"No se encontraron requisitos"`).

- `tabs-estado-requisito` · **on click** → cambia `activeState` en estado local y resetea la página

- `<select>` de tamaño de página · **on change** → cambia `pageSize` y resetea la página. **REQ-008:**

#### Accesibilidad de la pantalla (lo que afecta a esta story)

- **Orden de foco:** … → `tabs-estado-requisito` → filas de `tabla-requisitos` (**no enfocables**) →
  `paginacion-requisitos` → `tabs-estado-tarea` → …
- **Las tabs no se anuncian como tabs:** son `<nav aria-label="Filtro por estado">` con `<button>`,
  **sin `role="tablist"`/`role="tab"`**, así que no responden a flechas. **Gap preexistente; esta
  story no lo cierra** (ningún CA lo pide).
- **El cambio de tab no se anuncia:** sin `aria-live`. Gap preexistente.
- **Las dos paginaciones de la pantalla tienen distinta calidad:** la de requisitos es
  `<nav aria-label="Paginación">` con `aria-current="page"`; la de tareas es un `<div>` sin `<nav>`
  ni label. **REQ-008 cierra la mitad de esa brecha:** la de requisitos pasa al componente único,
  que conserva `<nav aria-label="Paginación">` y `aria-current="page"`. **La de tareas queda como
  está** — el requerimiento nombra dos paginadores y este no es ninguno de los dos, así que la
  asimetría persiste dentro de la misma pantalla, ahora con motivo registrado.
- **REQ-008 · el paginador nunca muestra más de 10 números**, lo que acota el recorrido por teclado
  a un tramo constante: hoy un estado con muchas páginas obliga a tabular por todas ellas para
  llegar al bloque siguiente.

#### Decisiones y descartes (REQ-008, 2026-08-31)

Copiadas de `docs/ux/surfaces/web/screens/detalle-proyecto.md`. **Son el "por qué"; no reabrirlas
durante la implementación:**

- **Los contadores de los tabs pasan a ser un dato pedido, no un cálculo derivado.** Se descartó el
  paliativo de pedir 100 filas para contar mejor: mueve el techo sin sacarlo, y deja a la pantalla
  mintiendo en silencio a partir del requisito 101.
- **No se agrega un aviso de "datos posiblemente incompletos".** Con totales reales y paginación por
  estado el truncado desaparece por construcción, así que el aviso avisaría de algo que ya no pasa:
  una advertencia permanente que nunca se cumple enseña a ignorar las advertencias.
- **La card sigue sin llevar su paginación a la URL.** Se usa el modo controlado. Pasar a URL
  acoplaría el `?page` entre las dos tablas de la pantalla y cambiaría el comportamiento de
  navegación, que el requerimiento pide conservar.
- **La ventana es de 10 números centrada, y no una elipsis con primera y última.** El recorte
  anterior nunca muestra dónde está parado el usuario: en la página 15 de 30, las vecinas —las
  únicas a las que se salta de verdad— no están.
- **La entrada de la card no cambia:** arranca en `Desarrollo`, con selector 5/10 y default 5.
- **Un contador que falla degrada solo su tab.** Se descartó mostrar `0` ante un fallo: **`0` es un
  dato, y confundirlo con "no se pudo saber" es peor que no mostrar nada.**

### Task 4: Aislar el fallo de conteo y reajustar la página fuera de rango

**Status:** Completed

#### Description

Los dos criterios de robustez, que comparten el hecho de operar sobre el resultado de los conteos:

**CA-8 — fallo aislado.** Con 7 queries independientes, una puede fallar sin las otras. El tab de
ese estado muestra **un placeholder neutro** y nada más se degrada: ni la tabla del tab activo, ni
los otros seis contadores, ni el paginador. La decisión de UX registrada es explícita sobre por qué
no se muestra `0`: *"`0` es un dato, y confundirlo con 'no se pudo saber' es peor que no mostrar
nada"*.

**CA-9 — página que deja de existir.** Si un requisito cambia de estado, el total del tab baja y la
página en la que está el usuario puede desaparecer. Sin clamp, la card queda en una página vacía sin
salida.

#### Acceptance Criteria

1. El contador de cada tab se resuelve por query, de forma independiente: `data` si resolvió,
   placeholder neutro (`'—'`) si esa query está en error.
2. **No** existe en el componente ninguna expresión del tipo `results.some((r) => r.isError)` que
   degrade la sección entera.
3. Un conteo en error **no** muestra `0`.
4. Un conteo en error no afecta la tabla del tab activo, los otros seis contadores ni el paginador.
5. La página efectiva se deriva en el render:
   `const page = Math.min(currentPage, Math.max(1, totalPages))`, con
   `totalPages = Math.ceil(totalDelTabActivo / pageSize)`.
6. La página clampeada alimenta **tanto** la query key del listado (para que se dispare el refetch de
   la página válida) **como** el `currentPage` que recibe `<Pagination>`.
7. El clamp es derivado en el render, **no** un `setState` en un `useEffect`.
8. El clamp nunca produce `0` ni un valor negativo: el piso es `1`.

#### Technical Details

**Architectural Context References:**
- **Reusable Code → El patrón de clamp:** `RequirementDetail.tsx:180-183`, verbatim, con la nota de
  por qué es derivado y no `setState`.
- **Reusable Code → El precedente a copiar:** la advertencia explícita de **no** copiar

- **ADR-011:** `retry: 1` es el default; el aislamiento se resuelve por query, **no** desactivando el
  retry.
- **Wireframes → Estados → error de sistema:** el texto de la decisión de UX sobre el placeholder
  neutro.
- **Wireframes → Decisiones y descartes:** *"`0` es un dato…"*.

**Implementation Notes:**

Render del contador, por tab:


- Distinguir con cuidado los tres casos: **resuelto** (muestra el número, incluido `0`), **en error**
