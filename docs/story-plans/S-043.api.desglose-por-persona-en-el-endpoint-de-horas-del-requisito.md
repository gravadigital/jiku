# Story Plan: S-043 (api) - Desglose por persona en el endpoint de horas del requisito

## Status

**Status:** Completed

## Story Reference

- **Story:** [S-043](../stories/S-043.desglose-por-persona-en-el-endpoint-de-horas-del-requisito.md)
- **Service:** `api`
- **Summary:** `GET /requirements/{reqid}/worked-hours` pasa de devolver `{ requirementId, totalMinutes }`
  a devolver además `byPerson`, el desglose de minutos por persona ordenado de mayor a menor. Las dos
  consultas actuales (`Promise.all`) se reemplazan por un único `SELECT` agrupado con `UNION ALL`, de
  modo que la suma de `byPerson` da `totalMinutes` por construcción y no por coincidencia.

### Service Architecture

`api` es la única puerta HTTP de Jiku: autentica contra Zitadel, autoriza por rol y por entidad,
**lee la base directamente** y convierte toda mutación en un comando NATS hacia `core`. Esta story es
**100% lectura**: no toca el bus, no toca `core`, no toca el esquema.

**Estructura relevante (sin `src/`, el código vive en `lib/`):**

```
api/
├── app.ts                    Express, middleware global, montaje automático de rutas
├── lib/
│   ├── routes/               un archivo por endpoint + index.ts (barrel)
│   │   ├── requirements-id-worked-hours-get.ts   <- el archivo de esta story
│   │   └── index.ts
│   ├── models/index.ts       el Sequelize de SOLO LECTURA
│   ├── logger.ts             Winston
│   └── utils/
│       ├── middlewares/      has-any-role, validate-requirement, ...
│       └── *.ts
└── tests/
    ├── routes/               un archivo de test por archivo de ruta
    └── mocks/                app.ts, bus.ts, jsonwebtoken-mock.ts
```

**Patrones clave del servicio:**

- **Un archivo por endpoint.** Validación, permisos y handler colocados juntos. No hay controllers,
  services ni repositorios.
- **Montaje automático:** `app.ts:35-37` itera los exports del barrel y hace `app.use('/api', router)`.
  El path en el archivo de ruta va **sin** el prefijo `/api`. **No se toca `app.ts`.**
- **La query vive en el handler**, con los `include` que la respuesta necesita. Sin capa de acceso a
  datos.
- **Manejo de errores inline:** `res.status(n).json({ code, message })`. Sin clases de error, sin
  `throw`, sin handler global de traducción.
- **Logging:** `import logger from '../logger'` (desde `lib/routes/`). Nunca `console`.
- **Comentarios en español, explicando el porqué**, no el qué.

**Orden canónico de la cadena de middlewares** (`http-server`):

1. Rol — `hasAnyRole([...])`
2. Forma del input — `validateBodyFields` / `validateQueryParams`
3. Existencia de la entidad del path — `validateRequirement`
4. Permiso sobre esa entidad — `validateProjectPermissions`
5. Reglas de negocio — validadores locales
6. Handler

Este endpoint usa 1, 3 y 6. **No cambia.**

### Relevant ADRs

#### ADR-001: Separación lectura/escritura por credenciales de base de datos

**Decisión:** la `api` conecta con un rol de PostgreSQL **sin `INSERT`/`UPDATE`/`DELETE`**; `core` es
el único que escribe; toda mutación viaja como comando por el bus.

**Implementation Rules (verbatim):**

- Toda escritura de dominio nueva **DEBE** implementarse como comando en `core`. **NO SE DEBE**
  agregar escritura con el ORM en `api`.
- La conexión de `api` **DEBE** usar credenciales sin `INSERT`/`UPDATE`/`DELETE`. Si un endpoint
  nuevo requiere escribir, la respuesta correcta es un comando, no ampliar los permisos del rol.
- La conexión de `core` **DEBE** usar el usuario dueño de la base.
- Las migraciones **DEBEN** correr desde `api` con `POSTGRESQL_MIGRATION_USER`, nunca desde `core`.
- Después de publicar un comando de creación, la api **DEBE** releer la base para armar la
  respuesta: core devuelve solo `{ id }` y el contrato con los frontends es el recurso completo
  con sus relaciones.
- Un endpoint que lee **NO DEBE** pasar por el bus: la lectura va directo a PostgreSQL desde la api.
  **Excepción declarada desde REQ-001 (S-005): la lectura de archivos.**

**Aplicación a esta story:** el endpoint es de lectura pura → **no pasa por el bus**, consulta
PostgreSQL directamente desde el handler. No hay escritura de ningún tipo.

#### ADR-008: Autorización deny-by-default

**Decisión:** `validateToken` se instala globalmente en `app.ts` para todo path salvo las exenciones
de `config/public.ts`; el rol se declara por ruta.

**Implementation Rules (verbatim):**

- `validateToken` **DEBE** instalarse globalmente en `app.ts`. **NO SE DEBE** declarar
  autenticación ruta por ruta.
- Un endpoint público **DEBE** agregarse explícitamente a `api/lib/config/public.ts`. Cualquier
  cambio en ese archivo es un **cambio de seguridad** y debe revisarse como tal.
- Un endpoint público **DEBE** validar por su cuenta lo que corresponda. El caso vigente
  (`GET /api/opus/attachments/:id/public`) verifica que el adjunto esté marcado público, responde
  403 en cualquier otro caso, y manda `X-Content-Type-Options: nosniff` con CSP de sandbox.
- Un endpoint que requiere rol **DEBE** declarar `hasAnyRole([...])` explícitamente. La
  autenticación global no implica autorización.
- Un endpoint accesible a `external-user` **DEBE** además verificar permiso de proyecto: el rol
  solo no alcanza (ADR-006).
- Un tipo de entidad nuevo con adjuntos **DEBE** agregarse a la resolución de proyecto de
  `attachments-access.ts`. Un tipo no contemplado **no se autoriza**, que es el comportamiento
  correcto.
- Al leer un archivo de ruta, **NO SE DEBE** concluir que está desprotegido por no ver el
  middleware: la protección es global.

**Aplicación a esta story:** el `hasAnyRole(['user', 'admin'])` existente **se conserva tal cual**
(CA-5). No se agrega ni se quita nada de `config/public.ts`. Al no ser alcanzable por
`external-user`, `validateProjectPermissions` (que solo restringe a ese rol) sigue siendo innecesario
en esta ruta — CA-7 se satisface **sin cambio de código**.

#### ADR-013: Tests contra base de datos real, con un doble de bus que ejecuta `core`

**Decisión:** los tests corren contra PostgreSQL real, sin mocks de Sequelize. El `FakeBus` ejecuta
`core` de verdad contra la misma base.

**Implementation Rules (verbatim):**

- Los tests de `api` y `core` **DEBEN** correr contra PostgreSQL real. **NO SE DEBEN** mockear los
  modelos de Sequelize.
- Los tests de comandos de `core` **DEBEN** entrar por el despachador (`dispatch()`), **NO** por
  `execute()` directamente.
- Un test de escritura de la api **DEBE** verificar las tres capas: comando publicado, traducción de
  la respuesta a HTTP, y que la fila quedó escrita. **NO SE DEBE** asertar solo el status HTTP.
- `reply()` / `failWith()` **DEBEN** usarse solo para cubrir caminos de error. El camino feliz
  **DEBE** ejecutar core de verdad.
- Cada archivo de test **DEBE** poder correr solo: el esquema y el mock de auth se preparan en
  fixtures globales de Mocha.
- `TZ=UTC` **DEBE** estar fijado en la configuración de test de todo servicio.
- La limpieza entre corridas **DEBE** ser `TRUNCATE ... RESTART IDENTITY CASCADE`, para que los ids
  autoincrementales sean predecibles.
- **NO SE DEBE** depender del orden de ejecución entre archivos de test.

**Aplicación a esta story:** los tests preparan su propio estado con `Model.create()` y lo limpian en
`after` con `Model.destroy({ where: {} })`. **No hay escritura**, así que el `FakeBus` no interviene:
no hay comando que asertar ni `reply()`/`failWith()` que usar.

#### Implementación actual completa (`api/lib/routes/requirements-id-worked-hours-get.ts`)

```ts
import { Request, Response, Router } from 'express';
import { fn, col, literal } from 'sequelize';
import { Objective, WorkedTime } from '@jiku/models';
import logger from '../logger';
import hasAnyRole from '../utils/middlewares/has-any-role';
import validateRequirement from '../utils/middlewares/validate-requirement';

const router: Router = Router();

function getWorkedHours(req: Request, res: Response) {
  const requirementId = req.requirement.id;

  // Horas directas: worked_times imputados directamente al requisito.
  const directPromise = WorkedTime.sum('minutes', { where: { requirementId } });

  // Horas de objetivos vinculados: worked_times de objetivos con objectives.requirement_id = R.
  // La regla de exclusión (objective_id ↔ requirement_id) garantiza que no haya doble conteo.
  const objectivesPromise = WorkedTime.findOne({
    attributes: [[fn('COALESCE', fn('SUM', col('WorkedTime.minutes')), literal('0')), 'totalMinutes']],
    include: [{
      model: Objective,
      as: 'objective',
      where: { requirementId },
      attributes: [],
      required: true,
    }],
    raw: true,
  });

  return Promise.all([directPromise, objectivesPromise])
    .then(([directSum, objResult]: [number | null, any]) => {
      const direct = directSum || 0;
      const fromObjectives = objResult ? Number(objResult.totalMinutes) : 0;
      return res.status(200).json({
        requirementId,
        totalMinutes: direct + fromObjectives,
      });
    })
    .catch((error: Error) => {
      logger.error(`GET /requirements/:reqid/worked-hours error: ${error.message}`);
      return res.status(500).json({ code: 'internal_error', message: 'Internal error' });
    });
}

router.get('/requirements/:reqid/worked-hours',
  hasAnyRole(['user', 'admin']),
  validateRequirement,
  getWorkedHours
);

export default router;
```

#### Middleware `validateRequirement` (`api/lib/utils/middlewares/validate-requirement.ts`)

Carga `req.requirement` y `req.project` desde `:reqid`, o responde **404 `requirement_not_found`**.
Es la fuente del CA-6 y **no se toca**:

```ts
function validateRequirement(req: Request, res: Response, next: NextFunction) {
  const reqId = req.params.reqid;

  return Requirement.findOne({
    where: { id: reqId },
    include: [
      { model: Project, as: 'project', attributes: ['id', 'name', 'keyValuePairs'] },
      { model: User, as: 'creator', attributes: ['id', 'name', 'email', 'identityType'] },
    ],
  })
    .then((requirement) => {
      if (!requirement) {
        return res.status(404).json({
          code: 'requirement_not_found',
          message: 'Requirement not found',
        });
      }
      req.requirement = requirement;
      req.project = requirement.project;
      return next();
    })
    .catch((error: Error) => {
      logger.error(`[middleware] validateRequirement error: ${error.message}`);
      return res.status(500).json({ code: 'internal_error', message: 'Internal error' });
    });
}
```

### Flow Context

**Ninguno.** La story declara explícitamente "Flujos Afectados: Ninguno". `docs/flows/` documenta
interacciones **entre servicios**; esta story es `api → PostgreSQL` dentro de un único servicio de

#### Escenario del diseño técnico (de la story, para referencia del implementor)

**Trigger:** el usuario abre el detalle de un requisito y se dispara la consulta de horas trabajadas
(consumida por S-045 en `web`, **fuera del alcance de esta story**).

1. `hasAnyRole(['user','admin'])` → 403 `access_denied` si no (CA-5)
2. `validateRequirement` → 404 `requirement_not_found` si no existe (CA-6)
3. Ejecuta el `SELECT` agrupado con `UNION ALL`
4. `totalMinutes` = suma de los `minutes` del resultado agrupado
5. `Number()` sobre cada `minutes` antes de responder (CA-10)
6. Response `200 { requirementId, totalMinutes, byPerson[] }`

**Precedente de SQL cruda parametrizada — el único del servicio**
(`api/lib/routes/requirements-tags-suggestions-get.ts:19-30`). Es el modelo a copiar:

```ts
import { QueryTypes } from 'sequelize';
import { sequelize } from '../models';

return sequelize.query<{ key: string; value: string }>(
  `SELECT DISTINCT
    jsonb_array_elements(tags)->>'key' AS key,
    jsonb_array_elements(tags)->>'value' AS value
  FROM requirements
  WHERE project_id = :projectId
  AND tags IS NOT NULL`,
  {
    replacements: { projectId: Number(projectId) },
    type: QueryTypes.SELECT,
  }
)
```

> **Nota sobre la convención `orm`.** La convención dice que "los reportes con agregación usan
> `sequelize.fn` / `sequelize.col`" y que `sequelize.literal` es la última opción. Esta story usa
> `sequelize.query` con `replacements` — el mismo mecanismo que el precedente de arriba — porque el
> `UNION ALL` de la subconsulta **no tiene expresión equivalente en el query builder de Sequelize**.

### Task 1: Reescribir el handler con un único `SELECT` agrupado y agregar `byPerson`

#### Description

Reemplazar el `Promise.all` de dos consultas independientes de
`api/lib/routes/requirements-id-worked-hours-get.ts` por un **único `SELECT` agrupado con

**Implementation Notes:**

La SQL, verbatim del diseño técnico de la story:

```sql
SELECT p.id AS "personId", p.first_name AS "firstName", p.last_name AS "lastName",
       SUM(src.minutes)::bigint AS minutes
  FROM (
    SELECT wt.person_id, wt.minutes FROM worked_times wt WHERE wt.requirement_id = :reqId
    UNION ALL
    SELECT wt.person_id, wt.minutes FROM worked_times wt
      INNER JOIN objectives o ON o.id = wt.objective_id WHERE o.requirement_id = :reqId
  ) AS src
  INNER JOIN people p ON p.id = src.person_id
 GROUP BY p.id, p.first_name, p.last_name
 ORDER BY minutes DESC, p.id ASC
```

Puntos que hay que entender antes de tocar el SQL, porque cada uno responde a un CA:

- **`UNION ALL`, no `UNION`.** Los dos conjuntos son disjuntos por la exclusión mutua
  `objective_id ↔ requirement_id` de `worked_times`, así que no hay nada que deduplicar. Y si se
  usara `UNION`, dos filas idénticas `(person_id, minutes)` — dos imputaciones legítimas de igual
  monto de la misma persona — colapsarían en una y el total quedaría corto (CA-8, TS-26).
- **El `INNER JOIN people` va sin predicado** sobre `enabled`, `end_date` ni `user_id`. Filtrar por
  `enabled` rompería CA-4 y la invariante `sum(byPerson) === totalMinutes`; joinear contra `users`
  rompería CA-9, porque `people.user_id` es nullable. La FK
  `worked_times.person_id → people.id` garantiza que el join no pierda filas.
- **El `ORDER BY` usa el alias `minutes`**, que en PostgreSQL es válido en `ORDER BY` (no en
  `WHERE` ni en `GROUP BY`). El desempate `p.id ASC` es lo que hace el orden determinista y testeable
  (CA-1, TS-22).
- **`SUM(...)::bigint` vuelve como string** por el driver `pg` — no es un bug del código, es cómo
  `pg` entrega `int8` para no perder precisión. **De ahí el `Number()` obligatorio** (CA-10, TS-29).

Forma sugerida del handler (respetando el estilo `.then()/.catch()` del archivo actual y del resto
del servicio):

```ts
import { Request, Response, Router } from 'express';
import { QueryTypes } from 'sequelize';
import { sequelize } from '../models';
import logger from '../logger';
import hasAnyRole from '../utils/middlewares/has-any-role';
import validateRequirement from '../utils/middlewares/validate-requirement';

const router: Router = Router();

// La fila cruda: `minutes` llega como string porque el SUM de PostgreSQL es bigint y `pg`
// lo entrega así para no perder precisión.
type PersonMinutesRow = {
  personId: number;
  firstName: string;
  lastName: string;
  minutes: string;
};

function getWorkedHours(req: Request, res: Response) {
  const requirementId = req.requirement.id;

  // Una sola consulta agrupada, no dos independientes: `totalMinutes` es la suma de las filas
  // de `byPerson`, así que la invariante total = desglose es estructural y no depende de que
  // dos consultas separadas coincidan.
  //
  // UNION ALL y no UNION: los dos conjuntos son disjuntos por la exclusión mutua
  // objective_id ↔ requirement_id de worked_times, y deduplicar borraría dos imputaciones
  // legítimas de igual monto de la misma persona.
  //
  // El INNER JOIN a people va sin predicado sobre enabled / end_date / user_id: una persona
  // deshabilitada, con baja, o sin Usuario vinculado igual trabajó esas horas, y si se la
  // filtrara la suma del desglose dejaría de dar el total.
  return sequelize.query<PersonMinutesRow>(
    `SELECT p.id AS "personId", p.first_name AS "firstName", p.last_name AS "lastName",
            SUM(src.minutes)::bigint AS minutes
       FROM (
         SELECT wt.person_id, wt.minutes FROM worked_times wt WHERE wt.requirement_id = :reqId
         UNION ALL
         SELECT wt.person_id, wt.minutes FROM worked_times wt
           INNER JOIN objectives o ON o.id = wt.objective_id WHERE o.requirement_id = :reqId
       ) AS src
       INNER JOIN people p ON p.id = src.person_id
      GROUP BY p.id, p.first_name, p.last_name
      ORDER BY minutes DESC, p.id ASC`,
    {
      replacements: { reqId: requirementId },
      type: QueryTypes.SELECT,
    }
  )
    .then((rows) => {
      const byPerson = rows.map((row) => ({
        personId: Number(row.personId),
        firstName: row.firstName,
        lastName: row.lastName,
        minutes: Number(row.minutes),
      }));
      const totalMinutes = byPerson.reduce((acc, person) => acc + person.minutes, 0);

      return res.status(200).json({ requirementId, totalMinutes, byPerson });
    })
    .catch((error: Error) => {
      logger.error(`GET /requirements/:reqid/worked-hours error: ${error.message}`);
      return res.status(500).json({ code: 'internal_error', message: 'Internal error' });
    });
}

router.get('/requirements/:reqid/worked-hours',
  hasAnyRole(['user', 'admin']),
  validateRequirement,
  getWorkedHours
);

export default router;
```

### Task 2: Documentar `byPerson` en la spec OpenAPI

#### Description

verdad** de los contratos, y donde el código y el documento discrepan, gana el documento. Si el
schema queda sin desarrollar, el próximo que planifique contra este endpoint no tiene contrato que

#### Acceptance Criteria
