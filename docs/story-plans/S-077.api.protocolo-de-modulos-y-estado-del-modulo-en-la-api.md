### Fuera de alcance (declarado, para no improvisarlo)

- **Ninguna ruta `/docs/*`, `/opus/docs/*` ni `/p/docs/*`.** Son S-078 (lectura), S-079
  (escritura) y S-080 (pública). CA-3 y CA-5 hablan de `GET /docs/documents`: esa ruta **no existe
  en esta story**. Este plan verifica el comportamiento que esas rutas van a heredar —el
  `requireModule('docs')` que les responde 404/503— montándolo sobre una app Express mínima en el
  test. Cuando S-078 cree `docs-documents-get.ts`, su test repite CA-3/CA-5 contra la ruta real.
- **`JIKU_PUBLIC_URL` no se declara acá** (ni en `api/.env.dist`, ni en `.env.defaults`, ni en
  `deploy/`). Es de S-080, que la introduce con `API_TRUST_PROXY` y `DOCS_PUBLIC_DOMAIN`. Este plan
  solo la **lee** en el punto de uso para `features.sharing` (CA-S2, DD-13); ausente o vacía →
  `sharing: false`, que es el comportamiento correcto de una instalación sin links públicos.
- **`errorBody` / `STATUS_BY_ERROR_CODE` de `lib/utils/bus/protocol.ts` NO se tocan.** El mapa de
  docs es **propio del módulo** y no se mezcla con el de core (story: *"no se mezcla con
  `STATUS_BY_ERROR_CODE` de core"*): los códigos se superponen (`invalid_fields`, `access_denied`
  no existe en docs, `caller_not_authorized` sí) y la regla de traducción es por servicio. Las 61
  rutas existentes siguen respondiendo `{ code, message }` sin `details`.
- **`sendCommand` / `withActor` no se reusan para docs** (story, *Seguridad*): el sobre de core
  (`{ id, roles, name?, username?, email? }`) es `invalid_fields` para jiku-docs, cuyo `Actor` es
  `additionalProperties: false` con solo `id` (DD-1).
- **Nada de `put` en `config/public.ts`** (H-3): es de la story que agrega el primer `PUT` de docs
  (S-079).
- **`docs/architectures/api/*`, ADR-015 y los flujos `descubrimiento-de-modulos`,
  `consulta-por-el-bus`, `escritura-por-el-bus`** se escriben en S-085. Este plan solo actualiza
  `docs/apis/api.yaml` (la fuente de verdad del contrato HTTP: las dos rutas nuevas tienen que
  estar declaradas) y el catálogo `docs/reusable-code/api/`.
- **Ningún cambio de base de datos ni migración** (story: *Cambios de Base de Datos: Ninguno*).
- **Ninguna dependencia de npm nueva.** `nats` 2.29.3 ya trae JetStream, KV y watch.

**`lib/modules/` es una carpeta nueva y es deliberado.** `_base` dice que el dominio vive en el
prefijo del archivo de ruta; eso sigue valiendo para las **rutas** (`modules-get.ts`,
`opus-modules-get.ts`, y las `docs-*` de S-078). Lo que va en `lib/modules/` no es una ruta: es el
estado del módulo, su cliente y su mapa de errores, que la story nombra con esas rutas exactas
(`lib/modules/registry.ts`, `lib/modules/docs/errors.ts`). El middleware **sí** va en
`lib/utils/middlewares/` porque la convención `http-server` pone ahí todo middleware compartido
entre rutas, y `requireModule` lo van a compartir 25 rutas.

### Relevant ADRs

**ADR-002: Toda mutación es un comando NATS request/reply, sin JetStream**
- Decision: request/reply sincrónico, gramática fija de subjects desde `@jiku/nats-protocol`.
- Implementation Rules (verbatim):
  - Todo comando **DEBE** publicarse con el subject `{instance}.{user-id}.gestion.v1.{comando}`,
    usando la gramática de `@jiku/nats-protocol`. **NO SE DEBE** construir el subject a mano.
  - El cliente NATS **DEBE** fijar `inboxPrefix` explícitamente al conectar, con el hash del user id
    que calcula `@jiku/nats-protocol`. Sin esto las respuestas no llegan.
  - El `userId` con el que publica la api **DEBE** salir de la key del service user, **NO** de una
    variable de entorno.
  - Toda respuesta **DEBE** tener el formato `{ status: 'success', data }` o
    `{ status: 'failure', errorCode, errorMessage }`. **NO SE DEBEN** inventar otros formatos.
  - Los comandos de creación **DEBEN** devolver únicamente `{ id }`. Las ediciones y borrados, nada.
  - Todo `errorCode` nuevo **DEBE** agregarse al mapa de `api/lib/utils/bus/protocol.ts` con su
    status HTTP.
  - Un bus caído **DEBE** responder **503**.
  - **NO SE DEBE** transportar datos estructurados dentro de `errorMessage`.
- Aplicación: los subjects de módulo salen **solo** de `moduleQuerySubject` / `moduleCommandSubject`
  / `modulePingSubject`, con el `userId` del service user (`this.userId` de `NatsBus`) y el mismo
  `inboxPrefix`. La regla *"Todo `errorCode` nuevo DEBE agregarse al mapa de `protocol.ts`"* es de
  los códigos **de core**; los de jiku-docs van a su propio mapa por decisión explícita de la story
  (ver *Fuera de alcance*). `errorDetails` es el canal estructurado que la regla de `errorMessage`
  pide, y DD-7 lo pasa al cliente como `details`.

**ADR-008: Autorización deny-by-default**
- Implementation Rules (verbatim):
  - `validateToken` **DEBE** instalarse globalmente en `app.ts`. **NO SE DEBE** declarar
    autenticación ruta por ruta.
  - Un endpoint público **DEBE** agregarse explícitamente a `api/lib/config/public.ts`. Cualquier
    cambio en ese archivo es un **cambio de seguridad** y debe revisarse como tal.
  - Un endpoint público **DEBE** validar por su cuenta lo que corresponda. […]
  - Un endpoint que requiere rol **DEBE** declarar `hasAnyRole([...])` explícitamente. La
    autenticación global no implica autorización.
  - Un endpoint accesible a `external-user` **DEBE** además verificar permiso de proyecto: el rol
    solo no alcanza ([ADR-006](ADR-006-dos-frontends-una-api.md)).
  - Un tipo de entidad nuevo con adjuntos **DEBE** agregarse a la resolución de proyecto de
    `attachments-access.ts`. […]
  - Al leer un archivo de ruta, **NO SE DEBE** concluir que está desprotegido por no ver el
    middleware: la protección es global.
- Aplicación:
  - Las dos rutas nuevas **no** se agregan a `config/public.ts`: quedan autenticadas por la
    cobertura global de `GET`.
  - "Cualquiera autenticado" (story) se traduce a **`hasAnyRole(['admin', 'user', 'external-user'])`**
    explícito: los tres roles del producto, y un token sin ninguno de ellos recibe 403. Es la regla
    *"la autenticación global no implica autorización"* aplicada literalmente.
  - **Excepción a "external-user DEBE verificar permiso de proyecto", anotada:** el estado de un
    módulo no pertenece a ningún proyecto (no hay entidad contra la que verificar). Es el mismo caso
    que `GET /opus/projects`, que lista sin un proyecto en el path. Se comenta en el archivo.
  - H-2: la política del bus autoriza `jiku-docs` **literal**. El cliente arma el subject correcto
    para cualquier `serviceName` (CA-8) y **no** intenta compensar el rechazo del bus real.

**ADR-001: Separación lectura/escritura** — regla relevante (verbatim): *"Un endpoint que lee **NO
DEBE** pasar por el bus: la lectura va directo a PostgreSQL desde la api."* El cliente de módulo es
la **primera excepción** (la api lee documentación por el bus, porque no está en su base). REQ-016
la documenta como ADR-015 (DD-17, S-085). Este plan no la usa todavía para ninguna ruta, pero el
cliente existe para eso: dejarlo dicho en el JSDoc de `lib/modules/client.ts`.

### API Context

#### Endpoints nuevos (verbatim de la story)

**`GET /modules`** y **`GET /opus/modules`**
- **Descripción:** estado de los módulos opcionales (`opus/modules` existe porque el catch-all de
  opus-web solo reenvía `/api/opus/*`).
- **Roles:** cualquiera autenticado → `hasAnyRole(['admin', 'user', 'external-user'])`.
- **Response 200:**
  ```json
  [{ "module": "docs", "status": "not_installed | unavailable | available", "features": { "sharing": true } }]
  ```
  `incompatible` se informa como `not_installed`; `features` se omite con `not_installed`.
- Marcados `x-jiku-module: docs` en `api.yaml`.

Respuesta exacta por estado interno (decisión de este plan derivada de lo anterior, sin agregar
nada):

| Estado interno del registro | Cuerpo de `GET /modules` y `GET /opus/modules` |
|---|---|
| `not_installed` | `[{ "module": "docs", "status": "not_installed" }]` (sin clave `features`) |
| `incompatible` | `[{ "module": "docs", "status": "not_installed" }]` (sin clave `features`) |
| `unavailable` | `[{ "module": "docs", "status": "unavailable", "features": { "sharing": <bool> } }]` |
| `available` | `[{ "module": "docs", "status": "available", "features": { "sharing": <bool> } }]` |

`sharing` es `true` **solo** si `process.env.JIKU_PUBLIC_URL` existe y no es vacía tras `trim()`.
Se lee en cada request (convención `env-config`: *"Leé `process.env` en el punto de uso"*), no al
importar.

Contrato del registro para los frontends (`docs/apis/jiku-modules.yaml`, verbatim):

```yaml
ModulesHttpResponse:
  description: Respuesta de `GET /modules` en la api de Jiku (HTTP, autenticado). Referencia para los frontends.
  type: array
  items:
    type: object
    required: [module, status]
    properties:
      module: { type: string }
      status: { type: string, enum: [not_installed, unavailable, available] }
```

`features` es aditivo (DD-13: *"el contrato tolera campos nuevos"*).

#### Middleware `requireModule('docs')` (verbatim de la story)

`not_installed`/`incompatible` → 404 `module_not_installed`; `unavailable` → 503
`module_unavailable`.

Cuerpos exactos (mensajes nuevos de interfaz, en español — convención `error-handling`):

| Estado | Status | Cuerpo |
|---|---|---|
| `not_installed`, `incompatible` | 404 | `{ "code": "module_not_installed", "message": "El módulo docs no está instalado" }` |
| `unavailable` | 503 | `{ "code": "module_unavailable", "message": "El módulo docs no está disponible en este momento" }` |
| `available` | — | `next()` |

#### Mapa de errores de docs (verbatim de la story)

`lib/modules/docs/errors.ts`, propio del módulo (no se mezcla con `STATUS_BY_ERROR_CODE` de core):

| Status | Códigos |
|---|---|
| 400 | `invalid_fields`, `invalid_cursor`, `file_name_invalid`, `frontmatter_invalid`, `invalid_relation`, `content_too_large`, `checksum_mismatch`, `upload_not_found`, `attachment_type_not_allowed`, `attachment_too_large`, `share_expiry_invalid`, `secret_warning_not_acknowledged`, `semantic_search_not_configured` |
| 403 | `permission_denied`, `sharing_blocked`, `unknown_caller`, `caller_not_authorized` |
| 404 | `document_not_found`, `folder_not_found`, `attachment_not_found`, `share_not_found` |
| 409 | `version_conflict`, `document_locked`, `lock_not_held`, `already_exists`, `folder_not_empty` |
| 503 | `upstream_unavailable`, `attachments_not_configured` |
| 504 | `query_timeout` |
| 500 | `internal_error` y cualquier código desconocido |

**30 códigos** explícitos (13 + 4 + 4 + 5 + 2 + 1 + 1).

Cuerpo de error (verbatim): *"`{ code, message, details? }` donde `code` es el `errorCode` de
jiku-docs sin traducir y `details` su `errorDetails` verbatim (DD-7; `errorBody` de `protocol.ts`
hoy descarta `errorDetails`). Sin reply: timeout → `504 gateway_timeout`; `no responders` → `503
module_unavailable` y re-ping inmediato. `upstream_unavailable` no marca al módulo como
`unavailable`."*

Precisiones de forma (decisión de este plan):
- `details` **solo aparece si** el reply trae `errorDetails`. Sin él, la clave no está (no
  `details: undefined`, mismo criterio que `Reply.errorDetails` del paquete).
- Código desconocido → **500 con el `code` original sin traducir** (`code: "brand_new_code"`): el
  catálogo de jiku-docs puede crecer dentro de v1 (*"un código desconocido se trata como error
  genérico"*) y el `code` le sirve al front y al log.
- Reply sin `errorCode`/`errorMessage` → `{ code: 'internal_error', message: 'Internal error' }`,
  como el `errorBody` de core.

Cuerpos de los errores sin reply:

| Señal del cliente NATS | Status | Cuerpo | Efecto en el registro |
|---|---|---|---|
| `NatsError` con `code === ErrorCode.Timeout` | 504 | `{ "code": "gateway_timeout", "message": "La operación tardó demasiado" }` | Ninguno |
| `NatsError` con `code === ErrorCode.NoResponders` | 503 | `{ "code": "module_unavailable", "message": "El módulo docs no está disponible en este momento" }` | `markUnavailable()`: pasa a `unavailable` **ya** y re-ping inmediato |
| Cualquier otro error (p. ej. `Bus no conectado`) | 503 | `{ "code": "module_unavailable", "message": "El módulo docs no está disponible en este momento" }` | Ninguno (no hay evidencia sobre el módulo) |

> `ErrorCode.NoResponders` es el string `'503'` y colisiona con `JetStreamNotEnabled`. En un
> `request()` plano (no JetStream) `'503'` **es** no-responders; por eso el cliente de módulo
> discrimina así y `send-command.ts` documenta la misma colisión.

#### Contrato de jiku-docs que consume este plan (copiado de la especificación v1, §5)

Formato de respuesta:

```jsonc
{ "status": "success", "data": { ... } }
{ "status": "failure", "errorCode": "version_conflict", "errorMessage": "...", "errorDetails": { "currentVersion": 8 } }
```

*"Se decide siempre por `errorCode`; `errorMessage` es texto en español para la interfaz."*

`Reply<T>` de `@jiku/nats-protocol` ya declara `errorDetails?: Record<string, unknown>`.

Subjects (`jiku-modules.yaml` + paquete):

| Uso | Helper | Ejemplo con el service user de tests (`000000000000000001`) |
|---|---|---|
| Consulta | `moduleQuerySubject(serviceName, protocol, method, userId)` | `dev.000000000000000001.jiku-docs-queries.v1.documents.list` |
| Comando | `moduleCommandSubject(serviceName, protocol, method, userId)` | `dev.000000000000000001.jiku-docs-commands.v1.documents.new` |
| Ping | `modulePingSubject(serviceName)` | `$SRV.PING.jiku-docs-queries` (sin instancia) |

Los tres helpers **lanzan** si `serviceName` no matchea `^[a-z][a-z0-9-]{1,40}$` (segunda línea de
defensa; la primera es la validación del registro de este plan).

Actor (DD-1, verbatim): *"La api llama a jiku-docs **siempre** en nombre de la persona con `actor: {
id }` — **solo `id`** —, salvo `shares.resolve` / `shares.attachment` (sin `actor`)"*. Y del
catálogo de jiku-docs: `invalid_fields` incluye *"`actor` enviado por un caller que no es la
`api`"*. **Corolario de seguridad:** un llamado de la api **sin** `actor` es tratado por jiku-docs
como el propio servicio (clase `service`, lee toda la documentación). Por eso el cliente **nunca**
publica sin `actor` salvo opt-in explícito (`anonymous: true`, que usará S-080).

Timeouts recomendados por jiku-docs (§5): comandos 5 s, consultas 10 s (*"la base corta a 8 s con
`query_timeout`"*). Coinciden con `REQUEST_TIMEOUT_MS` (5000) y `QUERY_TIMEOUT_MS` (10000) de
`lib/utils/bus/index.ts`: **se reusan**, sin variable nueva.

#### Decisiones de forma del cliente (este plan; anotadas para S-078/S-079/S-080)

S-078 escribe el llamado abreviado como `moduleQuery('docs', 'documents.list', { actor: { id }, … })`.
Este plan fija la firma completa, alineada con `sendCommand` (convención `bus-commands`):

```ts
// lib/modules/client.ts
export type ModuleName = 'docs';
export interface ModuleCallOptions {
  /** Sin `actor`: SOLO para `shares.resolve` / `shares.attachment` (S-080). Quita cualquier `actor` del payload. */
  anonymous?: boolean;
}
export function moduleQuery<T = any>(res: Response, module: ModuleName, method: string, payload: Record<string, unknown>, options?: ModuleCallOptions): Promise<T | null>;
export function moduleCommand<T = any>(res: Response, module: ModuleName, method: string, payload: Record<string, unknown>, options?: ModuleCallOptions): Promise<T | null>;
export function runModuleCommand(res: Response, module: ModuleName, method: string, payload: Record<string, unknown>, options?: ModuleCallOptions): Promise<boolean>;
```

- **Recibe `res` y responde el error**, devuelve `null` si ya respondió: mismo contrato que
  `sendCommand` (`if (!data) return;`). `runModuleCommand` existe por la misma razón que
  `runCommand`: un comando exitoso sin `data` (p. ej. `documents.{id}.unlock`) no se distinguiría de
  un error.
- **El `actor` lo inyecta el embudo, no la ruta** (convención `bus-commands`: *"una ruta nueva nace
  con sobre"*): `{ ...payload, actor: { id } }` con `id = buildActor(res.req)?.id` — el `sub` del
  claim ya verificado, que es el mismo valor que `req.user.id` (`validate-token.ts:118-119`: `req.user`
  se arma del claim desde S-034). **Va después del spread: gana el del token.** Lo que S-078 escriba
  como `actor: { id }` en el payload queda pisado por el mismo valor: inofensivo, pero
  innecesario.
- **Sin identidad verificada y sin `anonymous` → 401 `{ code: 'unauthorized', message:
  'Unauthorized' }` sin publicar.** Hoy inalcanzable (no hay rutas públicas), pero acá **fallar
  cerrado** es obligatorio, al revés que `withActor` de core: omitir el `actor` ante jiku-docs no
  deja "el comportamiento de hoy", **amplía** a clase `service`.
- **`payload` y `options` nunca se loguean** (contenido de documentos, tokens de links): el log
  lleva módulo, método y `error.message`.

### Flow Context

El flujo **descubrimiento-de-modulos** todavía no existe como documento (lo escribe S-085). Se
copia el escenario de la story, que es lo que este plan implementa:

> **Trigger:** arranque de la api; cambio de la clave `docs`; temporizador de 30 s.
>
> 1. **[api — registry, al arrancar]** `kv = js.views.kv('JIKU_MODULES', { bindOnly: true })`;
>    `kv.get('docs')`. Sin entrada → `not_installed`. Bucket inexistente o bus caído →
>    `not_installed` + log de error + reintento a los 30 s (DD-6: no tumba la api).
> 2. **[api]** Con entrada: valida contra `ModuleRecord`; `protocol !== 'v1'` → `incompatible` +
>    `logger.error('[modules] docs: protocolo v2 no soportado (soportado: v1)')`. JSON inválido →
>    `incompatible` + log, el watch sigue.
> 3. **[api → NATS]** `request('$SRV.PING.jiku-docs-queries', '', { timeout: 2000 })`: respuesta →
>    `available`; `no responders`/timeout → `unavailable`.
> 4. **[api]** `kv.watch({ key: 'docs' })`: `PUT` vuelve al paso 2; `DEL`/`PURGE` → `not_installed`.
> 5. **[api, cada 30 s]** repite el ping con registro `v1`.
> 6. **[cualquier ruta de docs]** `no responders` → `unavailable` inmediato + re-ping.
>
> **Outcome:** `GET /modules` refleja el estado sin reinicios.
>
> **Manejo de errores:** el estado vive en memoria por réplica (DD-5), dos réplicas pueden
> discrepar hasta 30 s.

Decisiones de este plan sobre el flujo (las que la story deja abiertas):

| Punto | Decisión | Por qué |
|---|---|---|
| Paso 1, `bindOnly` | `js.views.kv(MODULES_BUCKET, { bindOnly: true, allow_direct: true })` | **Hallazgo verificado en `node_modules/nats/lib/jetstream/kv.js:160-178`:** con `bindOnly`, nats.js 2.29 **no consulta el stream** y deja `bucket.direct = opts.allow_direct ?? false`. Sin `allow_direct: true`, `kv.get()` usa `$JS.API.STREAM.MSG.GET.KV_JIKU_MODULES`, que la plantilla `connector.yaml` (S-075) **no autoriza** — autoriza `$JS.API.DIRECT.GET.KV_JIKU_MODULES.>`. El síntoma sería un registro siempre ilegible, con la violación de permisos solo en el log del servidor NATS. El bucket se crea con `allow_direct: true` (RF-1, `create-modules-kv.sh`) |
| Paso 1, "bucket inexistente" | Se detecta en el **primer `get()`**, no en el bind | Por lo mismo: `bindOnly` no verifica que el stream exista. El error del `get()` cae en la rama DD-6 |
| Paso 1, entrada borrada | `kv.get()` que devuelve una entrada con `operation` `DEL` o `PURGE` → `not_installed` | `RoKV.get` lo documenta: *"the entry returned could be marked with a "DEL" or "PURGE" operation"* |
| Paso 2, validación | JSON parseable + los cuatro campos `string` + `module === 'docs'` + `serviceName` contra `^[a-z][a-z0-9-]{1,40}$` + `protocol` contra `^v[0-9]+$`. Falla → `incompatible` + `logger.error('[modules] docs: registro inválido (<motivo>)')`. Campos extra se **toleran** | `jiku-modules.yaml`: *"Campos nuevos dentro de v1 son opcionales y no rompen compatibilidad: los lectores deben tolerarlos"*. Validar `serviceName` acá es la primera línea de defensa; el `throw` del paquete es la segunda |
| Paso 2, protocolo | Patrón válido pero `!== 'v1'` → `incompatible` + **exactamente** `` logger.error(`[modules] docs: protocolo ${protocol} no soportado (soportado: v1)`) `` | Para `v2` produce el texto literal de la story |
| Paso 3, ping | `pingModule(serviceName, 2000)`; cualquier reply → `true`; `NoResponders`/`Timeout` → `false` | Story: `{ timeout: 2000 }` |
| Paso 4, watch | `kv.watch({ key: 'docs' })` con el `include` **por default** (último valor + cambios) | Entre el `get()` y el arranque del watch puede haber una escritura: con el default el watch re-entrega el valor vigente y la re-evaluación es idempotente; con `UpdatesOnly` ese cambio se perdería |
| Paso 4, watch que termina | Si el iterador del watch termina (reset de conexión, error), el registro suelta el handle del KV y el **siguiente tick de 30 s** lo reabre (get + watch) | Mismo mecanismo que DD-6; sin esto, un watch muerto dejaría el estado congelado para siempre |
| Paso 5, temporizador | Un único `setInterval(30000)` con `unref()`: si el KV no está abierto → reintenta abrir (get + watch); si hay registro `v1` → ping; si no hay registro → nada | Un solo temporizador cubre DD-6 y CA-7 |
| Pings superpuestos y obsoletos | Contador de **generación** que se incrementa con cada entrada aplicada y con `stop()`; el resultado de un ping solo se aplica si la generación no cambió. Si hay un ping en vuelo, no se lanza otro | Sin esto: ping en vuelo → se borra la clave → el ping vuelve OK → el estado queda `available` con el módulo desinstalado |
| Logs | `logger.info('[modules] docs: <anterior> -> <nuevo>')` **solo en cada cambio de estado**; `logger.error` en cada intento fallido de abrir el registro (`'[modules] docs: no se pudo leer el registro (<error.message>); reintento en 30 s'`) | Un ping exitoso cada 30 s no tiene que llenar el log |
| Arranque | `afterInitialize()` en `app.ts`: `connectBus().catch(log).then(() => docsModule.start()).then(() => synchronizeIdentityKeys())`. `start()` **nunca rechaza** | DD-6: no tumba la api. Se espera (acotado por los timeouts del bus) para que los primeros requests vean el estado real y no un `not_installed` transitorio |

Dónde entra cada símbolo del paquete:

| Paso | Símbolo |
|---|---|
| 1 | `MODULES_BUCKET` (no el literal `'JIKU_MODULES'`) |
| 2 | `ModuleRecord` (tipo del valor validado) |
| 3, 5, 6 | `modulePingSubject(record.serviceName)` dentro de `NatsBus.pingModule` |
| cliente | `moduleQuerySubject` / `moduleCommandSubject(record.serviceName, record.protocol, método, this.userId)` dentro de `NatsBus` — **CA-8** |

### Code Conventions

- **Un archivo por endpoint** (`modules-get.ts` → `ModulesGet`, `opus-modules-get.ts` →
  `OpusModulesGet` en el barrel); método y path en la misma línea; path **sin** `/api`.
- **Errores inline**: `res.status(n).json({ code, message })`; sin clases de error ni `throw` en
  handlers; un middleware que responde **no** llama a `next()`.
- **Imports relativos** (`../utils/bus`, `../../logger`); paquetes por nombre (`@jiku/nats-protocol`).
  Sin alias de `module-alias` en TS.
- **Comentarios en español, el porqué**, con referencias a REQ-016 / DD-x / CA-x, en el estilo de
  `send-command.ts` (mayúsculas para la regla que no hay que romper).
- **Constantes de módulo en `SCREAMING_SNAKE_CASE`**: `SUPPORTED_PROTOCOL`, `MODULE_CHECK_INTERVAL_MS`,
  `MODULE_PING_TIMEOUT_MS`, `DOCS_STATUS_BY_ERROR_CODE`.
- **Logging**: `logger` de `lib/logger.ts`, prefijo `[modules]`; `error.message`, nunca el error
  completo; **nunca** payloads, tokens ni contenido.
- **Tests**: `should`; sin `assert`/`expect`; `tests/utils/` no usa base; `tests/routes/` sí. No
  llamar a `setBus`. Prefijo de los títulos: `it('S-077 · TS-n: …')`.

### Reusable Code

- **`bus()` / `setBus` / `REQUEST_TIMEOUT_MS` / `QUERY_TIMEOUT_MS`** (`lib/utils/bus/index.ts`) —
  la interfaz `Bus` hoy:
  ```ts
  export interface Bus {
    request<T = any>(command: string, payload: unknown): Promise<Reply<T>>;
    query<T = any>(query: string, payload: unknown): Promise<Reply<T>>;
  }
  ```
  `NatsBus` guarda `connection: NatsConnection | null` y `userId` (del service user). Los métodos
  nuevos usan **la misma conexión, el mismo `inboxPrefix` y el mismo `userId`** (mismo argumento
  que `query()`: una segunda conexión pediría otra identidad al auth-callout).
- **`buildActor(req)`** (`lib/utils/bus/actor.ts`) — devuelve `{ id, roles, … }` armado del claim
  verificado, o `undefined` sin token. El cliente de módulo toma **solo** `.id`.
- **Patrón del `catch` de `sendCommand`** (`lib/utils/bus/send-command.ts`) — discriminar por
  `error instanceof NatsError && error.code === ErrorCode.Timeout` (seguro: una sola copia de `nats`
  hoisteada). El cliente de módulo agrega la rama `ErrorCode.NoResponders`.
- **`hasAnyRole(roles)`** (`lib/utils/middlewares/has-any-role.ts`) — 403 `access_denied`.
- **`FakeBus`** (`tests/mocks/bus.ts`) — instalado por `tests/setup-env.ts` y reseteado por root
  hook. Ya tiene `failWithNoResponders()` / `failWithTimeout()` (construyen el `NatsError` con
  `NatsError.errorForCode(...)`); los equivalentes de módulo reusan esa forma.
  `TEST_USER_ID = '000000000000000001'` es el `userId` con el que el doble arma subjects.
- **`start()`** (`tests/mocks/app.ts`) — devuelve el `Application` con `initialize()`, **sin**
  `afterInitialize()`: en los tests el registro **no** arranca solo; cada test lo controla.
- **Tokens del mock** (`tests/mocks/jsonwebtoken-mock.ts`): `token_01_user` (`sub: 'zitadel-sub-01'`,
  rol `user`), `token_03_admin`, `token_04_external_user`. **No hay ninguno sin roles**: se agrega
  `token_08_no_roles`. Desde S-034 `req.user` sale del claim: **no hace falta fila en `users`**.
- **`tests/utils/api-contract.test.ts`** — patrón de test documental sin parser de YAML
  (`readFileSync` + regex).
- **`MODULES_BUCKET`, `ModuleRecord`, `moduleQuerySubject`, `moduleCommandSubject`,
  `modulePingSubject`** (`@jiku/nats-protocol`, re-exportados por `lib/utils/bus/protocol.ts` vía
  `export * from '@jiku/nats-protocol'`).

### Task 6: Cliente de módulo `lib/modules/client.ts`

**Status:** Completed

#### Description
El embudo por el que las rutas de documentación van a hablar con jiku-docs: chequea el estado,
inyecta `actor: { id }`, arma el subject desde el registro (CA-8), traduce errores con el mapa de

   `moduleCommand`, `runModuleCommand`, `ModuleCallOptions`; `ModuleName` re-exportado del registro).
2. Orden de cada llamada:
   1. `registryFor(module)`: `not_installed`/`incompatible` → 404 `module_not_installed`;
      `unavailable` → 503 `module_unavailable` (mismos cuerpos que `requireModule`, desde una
      función compartida); devuelve `null` **sin publicar**.
   2. Identidad: sin `anonymous`, `id = buildActor(res.req)?.id`; sin `id` → 401
      `{ code: 'unauthorized', message: 'Unauthorized' }` sin publicar. Payload enviado:
      `{ ...payload, actor: { id } }`. Con `anonymous: true`: payload **sin** clave `actor` (se
      quita si venía).
   3. `bus().queryModule(record, method, body)` / `commandModule(...)`.
   4. Sin reply: tabla *Cuerpos de los errores sin reply* (Timeout → 504; NoResponders → 503 +
      `registry.markUnavailable()` sin esperarlo; otro → 503). Log antes de responder:
      `` logger.error(`[modules] ${module} ${method}: ${error.message}`) ``.
   5. Reply `failure` → `res.status(docsHttpStatusFor(code)).json(docsErrorBody(reply))`, `null`.
   6. Éxito → `reply.data ?? null`.
3. `runModuleCommand` → `await moduleCommand(...)` y `return !res.headersSent`.
4. JSDoc de cabecera: excepción a ADR-001 (ADR-015, S-085), DD-1 y el corolario de seguridad
   (sin `actor` = clase `service`), por qué no reusa `sendCommand`/`withActor`, y que el payload no
   se loguea.
5. TS-22 a TS-39 verdes.

#### Technical Details

**Architectural Context References:** *API Context* (completo); DD-1, DD-7; *Reusable Code →
