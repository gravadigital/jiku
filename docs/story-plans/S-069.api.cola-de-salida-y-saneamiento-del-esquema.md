### Service Architecture

`api` es la única puerta HTTP del producto. **Lee la base directamente y no escribe**: conecta con
un rol de PostgreSQL de solo lectura. Toda mutación se publica como comando en NATS y la atiende
`core`.

**Esta story toca la única excepción deliberada a eso: las migraciones.** Corren al arrancar la api
con credenciales propias (`POSTGRESQL_MIGRATION_USER` / `_PASSWORD`, con fallback a las de la api si
no están definidas), y son la vía por la que **la api es la dueña del esquema**. No hay ningún
handler, ninguna ruta, ningún middleware ni ningún comando del bus involucrado en este plan.

**Estructura relevante:**

```
api/
├── db-upgrade/
│   ├── config.js                  credenciales de migración (POSTGRESQL_MIGRATION_USER)
│   └── migrations/                105 archivos .js → 106 con esta story
│       └── 20260901_01_activity_edited_at_edited_by.js    ← la última hoy
├── lib/
│   └── models/index.ts            el Sequelize de SOLO LECTURA; registra allModels
└── tests/
    ├── mocks/app.ts               initDb()
    ├── global-setup.ts            crea el esquema con sequelize.sync() una vez por corrida
    └── 00-configurations/         tests de modelo y de migración (corren primero por el nombre)
        ├── query-indexes-migration.test.ts       ← EL precedente de test de migración
        ├── external-integration-removal.test.ts
        ├── notification-outbox-model.test.ts     ← creado por el plan de models (S-069)
        └── mail-threads-removal.test.ts          ← creado por el plan de models (S-069)
```

**Comandos:**

```sh
npm run build:packages                      # desde la raíz: models + nats-protocol + zitadel-auth
npm run upgrade-db --workspace @jiku/api    # corre las migraciones solas
npm start --workspace @jiku/api             # las corre y después sirve
npm test --workspace @jiku/api              # la suite completa
npx mocha api/tests/00-configurations/notification-outbox-migration.test.ts   # un archivo
KEEP_DB=true npx mocha ...                  # deja el contenedor vivo para inspeccionar
```

**Convención de migraciones (convención `orm` de `api`, sección "Migraciones"):**

- Van en `db-upgrade/migrations/`, en **JavaScript** (requisito de `sequelize-cli`).
- Nombre: `YYYYMMDD_NN_descripcion.js` — fecha de 8 dígitos, secuencia de 2 dentro del día,
  `snake_case`.
- CommonJS con `module.exports = { up, down }`.
- Se esperan **aditivas**: el esquema no está versionado aparte del producto.
- Tabla de control: `sequelize_meta`.

> **Las 105 migraciones actuales no construyen el esquema desde cero**: todas asumen uno existente y
> ninguna crea `objectives`. Una instalación nueva necesita un dump previo. No asumas que
> `upgrade-db` sobre una base vacía funciona.

En `testing` y `development` el arranque hace `sequelize.sync()` **además** de las migraciones
(`api/lib/models/index.ts:63-70`). En producción, no. **Esa dualidad es el eje de CA-7 y de todo el
riesgo de esta story.**

### Relevant ADRs

#### ADR-001: Separación lectura/escritura por credenciales de base de datos

**Decisión:** separar lectura y escritura en dos servicios, y hacer que la separación **la imponga
PostgreSQL por permisos**, no una convención de código. La `api` conecta con un rol sin
`INSERT`/`UPDATE`/`DELETE`; `core` conecta con el usuario dueño; toda mutación viaja como comando.

**Implementation Rules (verbatim):**

- La `api` **NO DEBE** escribir en la base con el ORM. Toda mutación **DEBE** publicarse como
  comando.
- `core` **DEBE** ser el único servicio que escribe.
- Las migraciones **DEBEN** correr con credenciales propias (`POSTGRESQL_MIGRATION_USER`), no con
  las de la api.
- Las dos escrituras que quedan en la api (`Attachment.create()` y `PUT /api/week-assigned-times`)
  son **deuda reconocida**, no precedente para código nuevo.

**Por qué aplica acá:** esta story es exactamente la excepción deliberada. La migración escribe DDL
y hace un `bulkInsert` en `system_settings`, y eso es correcto **porque corre con
`POSTGRESQL_MIGRATION_USER`**. Ninguna línea de `api/lib/` cambia en este plan. Si alguna tarea te
lleva a tocar un archivo de ruta, algo se entendió mal.

#### ADR-005: Modelos compartidos en `@jiku/models`, sin abrir la conexión

**Decisión:** los modelos viven en un paquete del workspace que exporta las clases pero
deliberadamente no abre la conexión. Cada servicio las registra en su propio `Sequelize`.

**Implementation Rules (verbatim):**

- Los modelos Sequelize **DEBEN** vivir en `@jiku/models`. **NO SE DEBE** definir un modelo dentro
  de `api/` o de `core/`.
- `@jiku/models` **NO DEBE** abrir una conexión ni leer variables de entorno de base de datos.
  Exporta clases; la instancia la crea cada servicio.
- Cada servicio **DEBE** registrar las clases en su propio `Sequelize` con sus credenciales.
- **Un cambio de esquema DEBE hacerse en dos lugares en el mismo cambio: la migración en
  `api/db-upgrade/migrations/` y el modelo en `@jiku/models`. Uno sin el otro deja el código y la
  base desalineados.**
- Los hooks que van en el modelo son los que pertenecen **al dato**. Los que dependen del caso de
  uso o del rol **DEBEN** ir en el comando de core o en la api.
- Los nombres en `@jiku/models` **DEBEN** ser los reales de la base. La traducción de vocabulario es
  responsabilidad de core.

**Por qué aplica acá, y es la regla central de este plan:** la cuarta regla es literalmente el
motivo de que esta story tenga dos planes. El de `models` ya puso el modelo; **este pone la
migración, y los dos se despliegan juntos.** Un despliegue del modelo sin esta migración deja
`NotificationOutbox` declarando una tabla que producción no tiene —donde `sync()` no corre—, y el
primer insert de S-071 falla con `relation "notification_outbox" does not exist`.

#### ADR-012: Monorepo con contexto en la raíz

**Decisión:** un solo repositorio con npm workspaces; el contexto de build de los Dockerfiles es la
raíz del monorepo, no el directorio del servicio.

**Regla que importa acá:** los consumidores importan `@jiku/models` **compilado** (`main` apunta a
`dist/`). Un cambio en `packages/models/src/` **no llega** a `api` sin `npm run build:packages`.
En esta story el modelo ya está implementado y commiteado, pero **el `dist/` de tu working copy
puede estar rancio**: ver *Hallazgos* §4 del plan de `models`, y el paso 1 del Manual Testing de la
Tarea 3 de este plan.

#### ADR-013: Tests contra base de datos real, con un doble de bus que ejecuta `core`

**Decisión:** los tests corren contra PostgreSQL real, sin mocks de Sequelize. El esquema se
construye con `sequelize.sync()` y se limpia con `TRUNCATE ... RESTART IDENTITY CASCADE` una vez por
corrida. En CI (`CI=true`) se usa la base del pipeline. `KEEP_DB=true` deja el contenedor vivo.

**Su límite declarado, y es el que condiciona la Tarea 3:** *"el esquema de la suite lo construye
`sync()`, no las migraciones, y son dos fuentes de verdad"*. Contra esa base, afirmar "la tabla no
existe" pasa **por construcción** apenas se borra el modelo, y "la tabla existe" pasa por
construcción apenas se agrega. Por eso el test de esta story **aplica la migración a mano**
(`migration.up(...)`) sobre una base auxiliar, en vez de asumir que el esquema de la suite es el
migrado. El precedente exacto es `api/tests/00-configurations/query-indexes-migration.test.ts`
(S-021), que documenta en su cabecera por qué un test de migración se puede escribir en este
servicio y bajo qué condiciones.

**Implementation Rules relevantes:**

- Los tests **DEBEN** correr contra PostgreSQL real; **NO SE DEBE** mockear Sequelize.
- Cada archivo **DEBE** poder correr aislado: el esquema y el mock de auth se preparan en fixtures
  globales.
- Un archivo **NO DEBE** dejar estado que contamine a los que corren después.
- **NO SE DEBE** depender del orden de ejecución entre archivos.

### Database Context

#### La tabla a crear: `notification_outbox`

Forma completa exigida por CA-1, tal como la declara la story:

| Columna | Tipo | Restricciones | Para qué |
|---|---|---|---|
| `id` | `BIGSERIAL` | PK | `BIGINT`, no `INTEGER`: es una tabla de flujo que crece con cada hecho notificado |
| `type` | `VARCHAR(100)` | NOT NULL | Clave del registro de tipos (S-071). Nunca texto libre |
| `channel` | `VARCHAR(20)` | NOT NULL, default `'email'` | Única concesión al multicanal |
| `recipient_user_id` | `VARCHAR(100)` | NOT NULL → `users.id` | Mismo tipo y FK que `requirement_subscriptors.user_id` |
| `recipient_email` | `VARCHAR(255)` | NOT NULL | Congelado al encolar |
| `payload` | `JSONB` | NOT NULL | Datos del mail, congelados |
| `status` | `VARCHAR(20)` | NOT NULL, default `'pending'` | `pending` / `sent`. No hay `failed` |
| `attempts` | `INTEGER` | NOT NULL, default `0` | |
| `next_attempt_at` | `TIMESTAMP` | NOT NULL, default `NOW()` | Backoff |
| `last_error` | `TEXT` | NULL | Causa del último fallo |
| `created_at` | `TIMESTAMP` | NOT NULL, default `NOW()` | |
| `sent_at` | `TIMESTAMP` | NULL | `NULL` mientras `status = 'pending'` |

**No hay `updated_at`.** El modelo la excluye explícitamente (`updatedAt: false`) y la migración
tampoco la crea. Con `timestamps: true` a secas, `sync()` agregaría una columna que la migración no
tiene y las dos fuentes del esquema divergirían.

**El índice, uno solo:**

```sql
CREATE INDEX idx_notification_outbox_pending
  ON notification_outbox (next_attempt_at, id)
  WHERE status = 'pending';
```

**Dos notas del plan de `models` que son decisiones de implementación de ESTA migración:**

1. **`TIMESTAMPTZ`, no `TIMESTAMP` a secas.** Sequelize traduce `DataType.DATE` a
   `timestamp with time zone`, y es el tipo que ya usan las demás columnas de fecha del esquema. La
   story escribe "`TIMESTAMP`" en su tabla de CA-1 hablando del concepto, no del tipo SQL literal:
   si la migración usara `TIMESTAMP` sin zona, la base migrada y la de `sync()` divergirían en el
   tipo de tres columnas. **Usar `TIMESTAMPTZ` en `next_attempt_at`, `sent_at` y `created_at`.**
2. **`next_attempt_at` sí lleva `DEFAULT NOW()` en la base.** En la captura de `sync()` no aparece
   porque Sequelize aplica `DataType.NOW` en la capa de aplicación. CA-1 pide explícitamente
   `NOT NULL DEFAULT NOW()`, y el plan de `models` deja las dos opciones como compatibles. **Se
   elige poner el `DEFAULT` en la base**: es lo que CA-1 dice, y es una red real para cualquier
   `INSERT` que no pase por el modelo (el proceso de S-073, un reencolado manual por SQL). El modelo
   nunca inserta sin fijar el valor, así que no hay conflicto.

#### Estrategia de migración

- Una sola migración, `up` y `down`, envuelta en `queryInterface.sequelize.transaction(...)` como
  las demás del producto. PostgreSQL soporta DDL transaccional: si algo falla, no queda medio
  aplicada.
- **El orden del `up` no es cosmético:** primero se crea `notification_outbox` (aditivo, sin riesgo),
  después se siembran las claves, y **al final** los tres `DROP TABLE`. Si un `DROP` falla por una
  dependencia que nadie relevó, la transacción revierte todo y la base queda intacta.
- **`DROP TABLE IF EXISTS`, sin `CASCADE`.** El `IF EXISTS` hace la migración idempotente contra una
  instalación donde alguien ya las hubiera borrado a mano. La ausencia de `CASCADE` es deliberada, y
  el precedente es explícito: `20260820_01_drop_external_integration.js` documenta que *"si quedara
  una dependencia que nadie relevó, la migración falla y no borra nada, en lugar de arrastrarla en
  silencio"*. Las FK que desaparecen son las **salientes** de las tres tablas borradas; nada apunta
  hacia ellas.
- **Los dos índices de `inbound_mail_threads` caen con la tabla**: PostgreSQL los borra en cascada.
  No hay que `DROP INDEX` por separado, y hacerlo antes tampoco está mal.
- **El `down` es reversible en estructura, no en datos.** Recrea las tres tablas **vacías**, con un
  comentario explícito de que el contenido no se recupera (CA-8). Precedente literal: el `down` de
  `20260820_01`.
- **La verificación de que las tres tablas están vacías es operativa y va FUERA de la migración.**
  La story es explícita: *"No es una condición dentro de la migración — una migración que se saltea a
  sí misma según los datos deja dos esquemas distintos en dos instalaciones."* No agregar una guarda
  como la de `20260819_05`: ahí la guarda protegía de aplicar sobre datos irresueltos; acá el borrado
  es la decisión tomada.

### Flow Context

La story no referencia ningún documento de `docs/flows/`, y es correcto: no hay comando ni endpoint.
El único "flujo" es el de la migración, y está en el cuerpo de la story:

1. **[migración `up`]** — crea `notification_outbox` con su índice parcial, dropea las tres tablas
   muertas, siembra las tres claves de `system_settings`.
2. **[código, ya hecho]** — el modelo `NotificationOutbox` en `packages/models` y la baja de los tres
   modelos muertos. **Commit `ca8bd7b`, plan de `models` Completed.**
3. **[migración `down`]** — dropea `notification_outbox`, recrea las tres tablas vacías.

**El orden entre los dos planes es parte del contrato de la story**, no una preferencia:
`packages/models` primero, `api` después. Lo dice CA-7 con su razón operativa — si el modelo siguiera
registrado, `sync()` en `development`/`testing` recrearía la tabla que la migración acaba de borrar.
**Esa precondición ya está cumplida** (los tres modelos están fuera del barrel desde `ca8bd7b`).

### Integration Points

- **Ninguna integración externa.** Ni Zitadel, ni S3, ni SMTP (eso es S-073), ni NATS.
- **`packages/models`**: la relación es de contrato de esquema, no de código. Esta migración tiene
  que producir la misma forma que el modelo declara. El DDL de arriba es la herramienta para
  verificarlo.
- **Bus / colas de mensajes**: ninguna. Ningún comando nuevo, ningún evento nuevo.

### Code Conventions

De `_base` y `orm` de `api`:

- **Las migraciones son el único JavaScript nuevo aceptado en el servicio** (requisito de
  `sequelize-cli`). El resto es TypeScript obligatorio.
- `'use strict';` en la primera línea, `module.exports = { up, down }`.
- Nombre `YYYYMMDD_NN_snake_case.js`.
- **Los comentarios explican el porqué, en español.** Las migraciones del producto llevan un bloque
  de cabecera con: qué hace, qué **no** hace, por qué el orden es el que es, y si es reversible.
  Comparar `20260819_01_create_files_table.js` y `20260820_01_drop_external_integration.js`: los dos
  son ejemplares y valen como plantilla.
- Archivos de test: `kebab-case`, sufijo `.test.ts`, en `tests/00-configurations/` para los de
  esquema y modelo.
- Cada escenario del test lleva un comentario con su ID `TS-N`.
- Los modelos se modifican en `packages/models/src/`, **nunca** localmente en la api.

### Reusable Code

Del catálogo de `api` (`docs/reusable-code/api/index.md`) y del código existente:

**Patrón de migración con transacción** — `20260819_01_create_files_table.js`:

```js
module.exports = {
  up: (queryInterface, Sequelize) => {
    return queryInterface.sequelize.transaction(async (transaction) => {
      await queryInterface.createTable('files', { /* columnas */ }, { transaction });
      await queryInterface.addIndex('files', ['uploaded_by', 'byte_status'], {
        name: 'idx_files_uploader_byte_status',
        transaction,
      });
    });
  },
  down: (queryInterface) => {
    return queryInterface.sequelize.transaction(async (transaction) => {
      await queryInterface.dropTable('files', { transaction });
    });
  },
};
```

**Patrón de migración destructiva con `down` que recrea vacío** —
`20260820_01_drop_external_integration.js`. Su cabecera es el modelo a seguir para CA-8:

```
 * NO ES REVERSIBLE EN CUANTO A DATOS. El `down` recrea la estructura VACÍA para poder volver
 * atrás el esquema, pero los valores que se hayan cargado a mano no se recuperan. No hay
```

## Hallazgos de la planificación

### 1. CA-9 no tiene, en este plan, más entregable que el `INSERT`

CA-9 dice que sin fila cargada el código devuelve `60`, `50` y `5` *"siguiendo el mismo patrón sin
caché que `core/src/commands/files/settings.ts`"*. Ese archivo es de **`core`**, y la tabla de
Servicios Afectados de la story asigna a `api` solo *"la siembra de las 3 claves"*.

El lector con los defaults en código pertenece a **S-073**, que lo declara en su CA-5. La propia
story lo dice: *"Estas tres claves no se leen todavía en ningún código de esta story."*

**Consecuencia:** CA-9 queda cubierto entre la siembra (Tarea 1, verificada por TS-21) y el lector
(S-073). No hay más tarea acá. Vale dejarlo escrito porque un CA que parece medio cubierto se lee
como un olvido, y no lo es. El mismo hallazgo está en el plan de `models`, §1.

### 2. `sync()` crea `notification_outbox` en la base de la suite, y eso complica el test

Es el punto que más cuidado pide en la Tarea 3. Desde `ca8bd7b`, el modelo está registrado, así que
el fixture global de la suite (`sequelize.sync()`) **ya crea la tabla**. Cuando el test aplique
`migration.up(...)`, el `createTable` va a chocar con una tabla existente.

Esto no le pasó a S-021 —su migración solo creaba índices— ni a `mail-threads-removal.test.ts` —que
asierta ausencia, no aplicación—. Es específico de este archivo, y la salida elegida (dropear antes,
recrear con `sync()` después) tiene una consecuencia que hay que verificar: **`notification-outbox-model.test.ts`
corre después por orden alfabético y necesita la tabla**. De ahí el paso 4 del Manual Testing de la
Tarea 3, y TS-23, que corre la suite entera y no solo el archivo.

### 3. La story dice `TIMESTAMP` y la implementación tiene que ser `TIMESTAMPTZ`

CA-1 enumera `next_attempt_at TIMESTAMP NOT NULL DEFAULT NOW()`, `created_at TIMESTAMP` y
`sent_at TIMESTAMP`. Tomado literalmente, la migración usaría `timestamp without time zone`.

**Sería una divergencia con el modelo ya implementado**, que produce `timestamp with time zone`
(Sequelize traduce así `DataType.DATE`), y con el resto del esquema, que usa `timestamptz` en todas
sus columnas de fecha. La nota está en el propio plan de `models`, al pie del DDL capturado.

**Resolución:** la migración usa `TIMESTAMPTZ`. La story escribe "`TIMESTAMP`" hablando del concepto
—una marca temporal, no una fecha— y no del tipo SQL literal; TS-4 fija la decisión como aserción
para que no se pierda. No es una desviación del criterio de aceptación: es lo que hace que la base
migrada y la de `sync()` coincidan, que es lo que CA-1 busca.

### 4. `next_attempt_at` lleva `DEFAULT NOW()` en la base aunque `sync()` no lo ponga

El DDL capturado no muestra default a nivel de columna, porque Sequelize aplica `DataType.NOW` en la
capa de aplicación. CA-1 pide `NOT NULL DEFAULT NOW()` explícitamente.

**Resolución:** la migración pone el `DEFAULT` en la base. Es lo que CA-1 dice, y es una red real
para cualquier `INSERT` que no pase por el modelo — el reencolado manual por SQL de un operador, por
ejemplo. El modelo nunca inserta sin fijar el valor, así que las dos capas no se contradicen. **Es
la única diferencia esperada entre la base migrada y la de `sync()`**, y está anotada como tal en la
Tarea 4 para que no se lea como un error en la comparación.

### 5. La verificación de "las tablas están vacías" no tiene dueño automático

La story es explícita en que es una **verificación operativa previa al deploy**, fuera de la
migración, y da la razón: una migración que se saltea a sí misma según los datos deja dos esquemas
distintos en dos instalaciones.

El riesgo es que una instrucción que no vive en el código no vive en ningún lado. **Por eso la Tarea
5 la pone en `### Notes for existing installations` del `CHANGELOG.md`**, que es el documento que un
operador lee antes de actualizar, y no solo en el comentario de la migración, que lee quien la
escribe. Sin ese paso, CA-6 se cumple técnicamente y la instalación pierde datos sin aviso.
