# Story Plan: S-032 (api) - La asignación semanal se convierte en comando

## Status

**Status:** Completed

**Progress:** 2/2 tareas completadas

## Story Reference

- **Story:** [S-032](../stories/S-032.la-asignacion-semanal-se-convierte-en-comando.md)
- **Service:** `api`
- **Summary:** `PUT /api/week-assigned-times` deja de escribir con el ORM (`destroy` + `bulkCreate`
  en una transacción propia) y pasa al patrón **comando + relectura**: publica
  `week-assigned-times.replace` —el comando 21, ya implementado en `core` por el plan S-032
  (core)— y relee la base con Sequelize para responder. Se eliminan `hasAnyRole(['admin'])`,
  `validateWeekNotPast` y el uso de los middlewares de transacción (`startTransaction` /
  `commitTransaction`) en esta ruta. **El contrato HTTP no cambia:** mismo verbo, mismo cuerpo
  (`weekStart`/`allocations`), mismos status para los casos ya cubiertos. Gana dos desenlaces
  nuevos: `503` (bus caído) y `504` (timeout).

## ⚠️ Cuatro hallazgos que hay que leer ANTES de escribir código

### H-1 (IMPORTANTE — corrige la CA-10 de la story) · Los middlewares de transacción NO quedan sin consumidor

La CA-10 de la story y `api/overview.md` afirman que `week-assigned-times-put.ts` es *"la única
ruta que usa los middlewares de transacción"* y que al quitarlos **"quedan sin ningún
consumidor"**. **Es falso hoy.** `api/lib/routes/objectives-id-comments-cid-patch.ts:6-7,128,130`
importa y usa `transactionStart` / `transactionCommit` para su propio `PATCH` (edición de un
comentario de tarea, con su propia escritura ORM no documentada como excepción de ADR-001).

**Consecuencia para esta tarea:** el diff de esta story elimina el *uso* de
`startTransaction`/`commitTransaction` en `week-assigned-times-put.ts`, tal como pide CA-10 —eso
sigue siendo correcto—, pero **no hay que tocar ni borrar los archivos
`api/lib/utils/transaction-start.ts` / `transaction-commit.ts`**: `objectives-id-comments-cid-patch.ts`
los sigue necesitando. La entrega no incluye "dejarlos sin consumidor" como hecho verificable,
porque no es cierto. Se documenta acá para que quien lea `api/overview.md` no encuentre la
promesa incumplida: la corrección de esa frase es un `/product-change-technical-definition`
posterior, fuera de esta story.

### H-2 (BLOQUEANTE) · Traducción de nombres de campos: HTTP y bus NO comparten vocabulario

El contrato HTTP (`docs/apis/api.yaml`, y el código actual) usa `weekStart` / `allocations`. El
contrato del comando (`docs/apis/core.yaml`, `WeekAssignedTimesReplacePayload`, y
`core/src/commands/times/week-assigned-times.ts`) usa `dateFrom` / `assignments`. **No es un
error de documentación**: el propio comando lo dice explícitamente en un comentario —*"Los dos
documentos son correctos y dicen cosas distintas; la traducción la hace la api. Un esquema
escrito con los nombres de HTTP compila, pasa el lint y rechaza TODO lo que la api mande, con
`invalid_fields`"*.

**El handler tiene que traducir explícitamente:**

```ts
await sendCommand(res, 'week-assigned-times.replace', {
  dateFrom: req.body.weekStart,
  assignments: req.body.allocations,
});
```

`docs/flows/asignacion-semanal.md` (Paso 3) muestra un payload de ejemplo con `dateFrom` /
`assignments` **en el cuerpo HTTP**, lo cual es inconsistente con `docs/apis/api.yaml` (que usa
`weekStart`/`allocations`) y con el código actual. **`docs/apis/api.yaml` es la fuente de verdad
del contrato HTTP** (regla del repositorio: donde el código y el documento no coinciden, el
documento de contrato gana, y una discrepancia se reporta, no se "arregla" a mano). Se deja
anotado como hallazgo de documentación, no se corrige en esta story — no es un archivo de
contrato (`docs/apis/*.yaml`) sino un flujo narrativo.

### H-3 (IMPORTANTE) · La api hoy no valida `personId`; después de esta story sí, y es una mejora de contrato observable

El comentario del comando en `core` es explícito: *"La api NO valida personas —una `personId`
inexistente le rompe por foreign key y sale 500— así que ésta es la ÚNICA diferencia de
comportamiento observable de la mudanza, y está DECLARADA en el contrato del bus como
`person_not_found` → 400"*. Hoy, un `personId` inexistente en `allocations` revienta el
`bulkCreate` de la api con un error de foreign key no capturado específicamente, y cae en el
`catch` genérico → **500**. Después de esta story, el mismo caso vuelve **400**
`person_not_found` (ya mapeado en `STATUS_BY_ERROR_CODE`, ver Architectural Context). Es una
mejora, y hay que agregar un test scenario nuevo para cubrirla (TS-9 en este plan) — la story no
lo pide explícitamente, pero es observable y el comando lo declara como su única diferencia de
comportamiento.

### H-4 (INFORMATIVO) · `project_not_found` para un proyecto inexistente también cambia de status

Hoy, un `projectId` inexistente en `allocations` hace que la api busque el proyecto con
`Project.findByPk`, no lo encuentre, y haga `throw new Error(...)` → **500** genérico (sin
`code`). Después de esta story, el comando responde `project_not_found` → **400**, ya mapeado.
Mismo tipo de mejora que H-3; se agrega como test scenario (TS-10).

## Architectural Context

### Tech Stack

- **Lenguaje:** TypeScript, Node.js. `tsconfig strict: true`.
- **Framework HTTP:** Express 5, un archivo por endpoint, montaje automático desde el barrel
  `lib/routes/index.ts`.
- **Validación:** Joi 18, esquema inline o como constante nombrada en el mismo archivo de ruta.
- **Acceso a datos:** Sequelize 6 + `sequelize-typescript`, con modelos de `@jiku/models`
  (compartidos con `core`). Conexión **de solo lectura** (`lib/models/index.ts:19-31`).
- **Bus:** `nats` 2.29 + `@jiku/nats-protocol`, request/reply síncrono, sin JetStream.
- **Testing:** Mocha 11 + `should` + `sinon` + `supertest`, PostgreSQL real en Docker, `FakeBus`
  que ejecuta `core` real.

### Relevant ADRs

**ADR-001: Separación lectura/escritura por credenciales de base de datos**

- Decisión: la api conecta a PostgreSQL con un rol sin `INSERT`/`UPDATE`/`DELETE`; `core` conecta
  con el usuario dueño y es el único que escribe. Toda mutación viaja como comando por el bus.
- Implementation Rules (verbatim):
  - Toda escritura de dominio nueva **DEBE** implementarse como comando en `core`. **NO SE DEBE**
    agregar escritura con el ORM en `api`.
  - La conexión de `api` **DEBE** usar credenciales sin `INSERT`/`UPDATE`/`DELETE`. Si un
    endpoint nuevo requiere escribir, la respuesta correcta es un comando, no ampliar los
    permisos del rol.
  - Las migraciones **DEBEN** correr desde `api` con `POSTGRESQL_MIGRATION_USER`, nunca desde
    `core`.
  - Después de publicar un comando de creación, la api **DEBE** releer la base para armar la
    respuesta completa.
- **Consecuencia directa para esta story:** `PUT /api/week-assigned-times` era la última excepción
  viva de escritura ORM sobre `week_assigned_times` (junto con la fila de `attachments`, que
  queda igual). Esta story la cierra.

**ADR-002: Toda mutación es un comando NATS request/reply, sin JetStream**

- Decisión: NATS en modo request/reply con timeout (`NATS_REQUEST_TIMEOUT_MS`, 5000 ms). Sin
  JetStream: un comando perdido es un comando perdido, no hay reintento automático.
- Consecuencia directa: `sendCommand` devuelve **503** `service_unavailable` si nadie responde
  (bus caído) y **504** `gateway_timeout` si la respuesta no llega a tiempo. Los dos son
  desenlaces **nuevos** para esta ruta — hoy la escritura es local y no puede fallar por el bus.
  Un 504 significa "pudo haberse guardado" y no se debe reintentar a ciegas (los comandos no son
  idempotentes).

**ADR-003: La transacción es del despachador, nunca del comando**

- Decisión: el despachador de `core` abre la transacción, ejecuta el comando, y hace commit si el
  reply es `success` o rollback en cualquier otro caso. El comando no tiene acceso a `commit` ni
  `rollback`.
- Consecuencia directa: la atomicidad del reemplazo (`destroy` + `bulkCreate`) ya no depende de la
  transacción de la api (que se elimina) sino de la del despachador de `core`, que **ya está
  implementada** en el comando (S-032 core, completado). Esta story del lado `api` no gestiona
  ninguna transacción.

### API Context

**`PUT /api/week-assigned-times`** (`docs/apis/api.yaml`) — contrato HTTP, **sin cambios**:

```yaml
requestBody:
  required: true
  schema:
    type: object
    required: [weekStart, allocations]
    properties:
      weekStart: { type: string, format: date }
      allocations:
        type: array
        items:
          type: object
          required: [personId, projectId, minutes]
          properties:
            personId: { type: integer }
            projectId: { type: integer }
            minutes: { type: integer, minimum: 0 }
responses:
  '200':
    schema:
      type: object
      properties:
        weekStart: { type: string, format: date }
        weekEnd: { type: string, format: date }
        allocations:
          type: array
          items: { $ref: '#/components/schemas/WeekAssignedTime' }
  '400':
    example: { code: invalid_week, message: No se pueden modificar semanas pasadas }
  '401': Unauthorized
  '403': AccessDenied
  '500': InternalError
x-roles: [admin]              # documenta qué rol autoriza CORE, no lo que la api verifica
x-bus-command: week-assigned-times.replace
```

> **Sobre el código `invalid_week` del ejemplo 400 de `api.yaml`:** es el código legado que
> emitía `validateWeekNotPast` en la api. El comando de `core` devuelve **`invalid_date_range`**
> para el mismo caso (C-36), ya mapeado a 400 en `STATUS_BY_ERROR_CODE`. El status HTTP (400) no
> cambia; el `code` del cuerpo de la respuesta sí: pasa de `invalid_week` a `invalid_date_range`.
> Los tests existentes que aserten `response.body.code.should.equal('invalid_week')` para este
> caso **tienen que actualizarse** a `invalid_date_range` (ver Tarea 2). Esto es coherente con
> "el contrato HTTP no cambia" en el sentido que importa —status, verbo, forma del cuerpo— pero
> el valor exacto del `code` de este caso puntual sí cambia, porque `core` no conserva
> `errorCode`s de HTTP (solo conservó el texto del `message`, ver comando: *"EL TEXTO SE
> CONSERVA... EL `errorCode` NO SE CONSERVA"*).

### Integration Points

**Bus (NATS) — cómo publicar el comando:**

```ts
import { sendCommand } from '../utils/bus/send-command';

const ok = await runCommand(res, 'week-assigned-times.replace', {
  dateFrom: req.body.weekStart,
  assignments: req.body.allocations,
});
if (!ok) {
  return;
}
// relectura con Sequelize
```

- `runCommand`, no `sendCommand`: el reply es `ReplyEmpty` (sin `data`), así que `sendCommand`
  devolvería `null` incluso en éxito. `runCommand` devuelve `true`/`false` sin esa ambigüedad.
- **El sobre de identidad (`actor`) lo inyecta `sendCommand`/`runCommand` automáticamente** vía
  `withActor`, armado desde el claim verificado del token (`req.decodedToken`). El handler
  **no** arma el `actor` a mano. C-38 (solo `admin`) la resuelve el mapa rol → comando de `core`
  a partir de este sobre — no hace falta `hasAnyRole` en la ruta.
- Traducción de errores a HTTP: `httpStatusFor` ya mapea `invalid_date_range`, `invalid_fields`,
  `project_not_found`, `person_not_found`, `caller_not_authorized` (403) — **ninguna entrada
  nueva que agregar a `STATUS_BY_ERROR_CODE`**, los cuatro ya están.

### Code Conventions

- Un archivo de ruta por endpoint; el handler, el esquema Joi y los middlewares locales
  colocados juntos en `week-assigned-times-put.ts`.
- Orden de la cadena de middlewares: rol → forma del input → entidad → permiso → negocio →
  handler. **En esta ruta, después de esta story, la cadena queda reducida a:** forma del input
  (`validateBodyFields`) → handler. No hay rol (lo resuelve `core`), no hay entidad de path (no
  hay `:id`), no hay regla de negocio local (se mudó a `core`).
- Método y path en la misma línea del `router.put(...)`.
- `code` de error en `snake_case`, estable. `message` en español para mensajes que ve el usuario.
- No `console`, siempre `logger`.

### Reusable Code

De `docs/reusable-code/api/index.md` (parcial, sembrado por S-005 y S-031), lo relevante para
esta story:

- **`sendCommand` / `runCommand`** (`api/lib/utils/bus/send-command.ts`) — el helper que publica
  el comando, inyecta el sobre de identidad, y traduce la respuesta a HTTP. **Usar `runCommand`**
  en esta tarea (el comando no devuelve `data`).
- **`httpStatusFor` / `errorBody`** (`api/lib/utils/bus/protocol.ts`) — ya traducen los cuatro
  `errorCode`s que este comando puede emitir. No hay que tocar este archivo.
- **`dayOffset` / `HOY` / `HOY_M10` / `HOY_M11` / `MANANA`** (`api/tests/helpers/dates.ts`) —
  fechas relativas a hoy, nunca literales, para tests que dependen del calendario. Usar en vez de
  construir fechas a mano con `setDate` como hace el test actual (ver Tarea 2) — es el patrón que
  ya usó S-031 para su test de paridad.
- **`fakeBus.failWithNoResponders()` / `fakeBus.failWithTimeout()`** (`api/tests/mocks/bus.ts`) —
  simulan el bus caído y el timeout sin construir el `NatsError` a mano. Usar para los casos 503 y
  504 (Tarea 2).
- **`fakeBus.reply(command, replyObj)` / `fakeBus.replyDefault(...)`** (`FakeBus`, convención
  `testing`) — para forzar caminos de error específicos (`project_not_found`,
  `person_not_found`, `caller_not_authorized`) sin tener que fabricar el estado que los provoca.

No hay componentes, hooks, ni estilos que aplican (servicio backend).

### Task 1: Reescribir `PUT /api/week-assigned-times` a comando + relectura

**Status:** Completed

### Description

Reemplazar la escritura directa con el ORM (`destroy` + `bulkCreate` en una transacción propia)
por la publicación del comando `week-assigned-times.replace` y la relectura de la base con
Sequelize para armar la respuesta. Es el corazón de la story: cierra la última escritura de
dominio que no pasaba por `core` (ADR-001).

### Acceptance Criteria

1. El archivo `api/lib/routes/week-assigned-times-put.ts` ya no importa ni usa: `hasAnyRole`,
   `validateWeekNotPast`, `startTransaction`, `commitTransaction`, ni los modelos `Project` /
   `WeekAssignedTime` para escribir (siguen pudiendo usarse para **leer**, en la relectura).
2. El handler publica `week-assigned-times.replace` vía `runCommand`, traduciendo
   `weekStart → dateFrom` y `allocations → assignments` en el payload (H-2). No arma el `actor` a
   mano.
3. Tras un `runCommand` exitoso, el handler relee `WeekAssignedTime.findAll` filtrando por
   `dateFrom`/`dateTo` derivados de `weekStart`, y responde `200` con
   `{ weekStart, weekEnd, allocations }`, igual forma que hoy.
4. `weekEnd` se sigue derivando como `weekStart + 4 días` (lunes a viernes), en el handler de la
   api (esto es transporte HTTP, no una regla de dominio — se queda acá).
5. El esquema Joi de validación de forma (`weekStart` requerido tipo fecha ISO, `allocations`
   array con `personId`/`projectId`/`minutes` requeridos, `minutes >= 0`) se conserva sin
   cambios: sigue siendo la validación de forma HTTP, independiente de la validación de `core`.
6. La cadena de middlewares del router queda: `validateBodyFields(schema)` → handler. Ningún
   `hasAnyRole`, ninguna validación de semana, ninguna transacción.
7. `x-roles: [admin]` en `docs/apis/api.yaml` **no se toca** (ya documenta correctamente que es
   `core` quien autoriza, no la api).

### Technical Details

**Architectural Context References:**
- ADR-001 (Implementation Rules): toda escritura de dominio nueva va como comando; la api no
  escribe con el ORM.

  errores vía `httpStatusFor`.
