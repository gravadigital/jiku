# Story Plan: S-101 (web) - La persona se reconoce en la documentación

## Status

**Status:** Completed

## Story Reference

- **Story:** [S-101](../stories/S-101.web-reconocer-a-la-persona-y-contrato-api-1-3-0.md)
- **Service:** `web`
- **Origen:** [REQ-022](../requests/REQ-022.arreglos-e2e-documentacion-sin-carpetas.md)
- **Summary:** `useCurrentUser` expone `zitadelId` (el `sub` de Zitadel) y todo `features/docs` compara
  `lock.holder`, `updatedBy` y `author` contra ese `sub` en lugar del uuid de Jiku. Con eso la persona
  ve "Lo estás editando en otra pestaña o ventana." con su propia reserva, "Lo estás editando" en la
  fila del listado y "vos" como autora en la cabecera, en "Editado por" y en el historial. Sin
  `zitadelId` en la sesión no se reconoce nada como propio (falla cerrado).

> **Alcance de este plan:** solo el servicio `web` (CA-1, CA-2, CA-3). CA-4 y CA-5 (esquemas de
> `docs/apis/api.yaml`) son del plan `api` (solo contrato, sin código). La nota del flujo
> `documentos-desde-la-web` ya está escrita (sección "Identidad en la documentación (REQ-022, S-101)").

> **Causa del defecto (verificada sobre el árbol, rama `feat/jiku-docs`, `ac42eaf`):**
> - `web/src/hooks/use-current-user.ts` devuelve `{ id, name }`, con `id = session.user.id` (uuid de Jiku).
> - jiku-docs guarda en `lock.holder`, `createdBy`, `updatedBy` y `author` el `sub` de Zitadel
>   (`DocsLock.holder` ya está tipado como "sub de Zitadel" en `features/docs/types/docs.types.ts`).
> - Todas las comparaciones de `features/docs` usan `currentUser?.id`:
>   - `DocumentView.tsx:270` (`editorLabel` del aviso de versión vieja), `:282` y `:287` (`lockedMessage`), `:323` (`metaVersionLabel`).
>   - `DocumentEditor.tsx:298` (`lockedMessage(session.blockedBy, …)`).
>   - `VersionHistoryPanel.tsx:194` (`editorLabel` del autor).
>   - `DocsResults.tsx:88` (`RowContext.currentUserId` → `editorLabel` en "Editado por" de `DocumentRow.tsx:133-137`).
> - `DocumentRow.tsx` (`DocumentTitleCell`, líneas ~94-111) **nunca** reconoce el lock propio: el nombre
>   accesible es siempre `"{holderName} lo está editando"` / `"Otra persona lo está editando"`.
> - Los tests no lo detectaron porque mockean `useCurrentUser: () => ({ id: 'sub-yo', … })`: el `id`
>   del mock coincide con el `sub` de los fixtures, cosa que en producción nunca pasa.
> - `lockState.ts` y `editorLabel.ts` ya fallan cerrado con `null`/`undefined`: la lógica no cambia.
> - `DocumentRowCompact` **no muestra lock** (grep sin coincidencias en el `.tsx`): sin cambios.
> - Fuera de alcance: `RequirementActivityFeed` y `ObjectiveComment` siguen comparando con
>   `session.user.id` (su autor es el uuid de Jiku); `ObjectiveCard` usa el tipo `TCurrentUser` y el
>   cambio es aditivo.

### Relevant ADRs

- **ADR-007: Identidad Zitadel + auth-callout**
  - Decision: Zitadel es la fuente de verdad de identidad para todo el producto. El `sub` es la identidad
    que viaja como `actor` al bus y la que jiku-docs guarda en `lock.holder`, `createdBy`, `updatedBy`
    y `author`. La tabla `users` es un espejo del proveedor.
  - Implementation Rules (verbatim):
    - Todo servicio que se conecte al bus **DEBE** autenticarse con el token de un service user
      obtenido vía `@jiku/zitadel-auth`, con auto-refresh. **NO SE DEBE** usar un token de larga
      duración por variable de entorno.
    - El `userId` para publicar **DEBE** derivarse de la key del service user, **NO** de una variable
      de entorno.
    - El cliente NATS **DEBE** fijar `inboxPrefix` con el hash de `@jiku/nats-protocol`.
    - La api **DEBE** validar los tokens de usuario contra el JWKS de Zitadel, con resincronización
      ante `kid` desconocido (`KEY_SYNC_ATTEMPS` reintentos).
    - Los roles **DEBEN** leerse del claim `urn:zitadel:iam:org:project:{PROJECT_ID}:roles`.
      **NO SE DEBEN** almacenar roles en la base ni derivarlos de otra fuente.
    - `AUTH_BYPASS=true` **DEBE** seguir siendo opt-in explícito, **prohibido con
      `NODE_ENV=production`** (el arranque debe fallar) y exigir `DEV_USER_ID`. **NO SE DEBE**
      activar por ausencia de otra variable.
    - El producto **NO DEBE** escribir la tabla `users` para modificar identidad: es espejo del
      proveedor. (El alta de la fila local es otro asunto — ver FG-1.)
    - Un cambio en `rules.yaml` del auth-callout **DEBE** tratarse como cambio de seguridad: es lo que
      define quién puede escribir en el producto.
  - Aplicación en este plan: ninguna regla se toca; el plan solo **lee** el `sub` que la sesión ya
    trae (`session.user.zitadelId`) y lo compara con lo que jiku-docs guarda.
- **ADR-015: Módulos opcionales del bus** — `features/docs` es opcional (condicionado por `GET /modules`). Sin cambios.

### API Context

Sin cambios de llamadas ni payloads. Formas que la web compara (tipos ya existentes en
`features/docs/types/docs.types.ts`):

```ts
export interface DocsLock {
  sessionId: string;
  /** sub de Zitadel */
  holder: string;
  /** Nombre de quien tiene el lock; `null` si el servicio no lo resuelve. */
  holderName?: string | null;
  via: 'human' | 'agent';
  expiresAt: string;
}
```

- `GET /api/docs/documents/{id}` → `DocsDocument` con `lock`, `updatedBy` (sub), `updatedByName`.
- `GET /api/docs/documents` / `GET /api/docs/search` → ítems con `lock` (listado), `updatedBy`, `updatedByName`.
- Historial → `DocsVersion` con `author` (sub), `authorName`.
- `POST /api/docs/documents/{id}/lock` con `409 { code: "document_locked", details: { holder, holderName, via, expiresAt } }` → `useEditSession` expone `session.blockedBy` (misma forma `LockHolder`).

Contrato (lo que documenta el plan `api` para CA-5): `lock.holder`, `createdBy`, `updatedBy` y
`author` son "El `sub` de Zitadel (no el uuid de Jiku)".

### Flow Context

**documentos-desde-la-web** (`docs/flows/documentos-desde-la-web.md`), extracto:

> **Identidad en la documentación (REQ-022, S-101):** la web reconoce la reserva y las versiones propias
> comparando `lock.holder`, `createdBy`, `updatedBy` y `author` con `session.user.zitadelId` (el `sub`),
> nunca con `session.user.id` (uuid de Jiku). Sin `zitadelId` no se reconoce nada como propio.

> **Paso 3: tomar la reserva de edición (web).** Al entrar en edición la web genera un `sessionId`
> (ULID) **nuevo** y toma la reserva. Endpoint `/api/docs/documents/{id}/lock`. Comando al bus:
> `documents.{id}.lock { sessionId, ttlSeconds?, via: 'human', actor }`. Response (éxito): `200` con el
> `data` de jiku-docs. La reserva dura **120 s** en jiku-docs.
>
> **Paso 4: renovar la reserva mientras se edita (web).** Cada **60 s** (`RENEW_INTERVAL_MS = 60_000`)
> la web repite el mismo `POST .../lock` con el mismo `sessionId`. Si el error es `document_locked`, se
> muestra quién tiene la reserva (`details.holder`, `details.holderName`, …).
>
> Errores: 409 `{ "code": "document_locked", "details": { "holder", "holderName", "via", "expiresAt" } }` →
> la web muestra quién tiene la reserva; no se pierde el texto.

**Interacción (de la story):**

1. **[web A]** `POST /api/docs/documents/{id}/lock` → jiku-docs guarda `holder = actor.sub`.
2. **[web B]** `GET /api/docs/documents/{id}` → `lock: { sessionId, holder: "<sub>", holderName, via: "human", expiresAt }`; `sessionId` distinto → lock activo.
3. **[web B]** `lockedMessage(doc.lock, currentUser.zitadelId)` → `holder === zitadelId` → "Lo estás editando en otra pestaña o ventana."; en la fila del listado: "Lo estás editando". ← **este plan**
4. Cabecera (`metaVersionLabel`), "Editado por" (`editorLabel` con `updatedBy`) e historial (`author`) → "vos". ← **este plan**

Manejo de errores: sin `zitadelId` en la sesión → `currentUserSub = null` → nunca "vos" ni "Lo estás
editando…"; se muestra `holderName`/nombre o el texto genérico.
