## Story Reference

- **Service:** `web`
- **Summary:** Del lado de `web` esta story **no cambia código de producto ni ninguna pantalla**: la

**Patrón dominante:** el guard de acceso está en el **layout** del grupo de rutas, no en un
middleware. Todo lo que está dentro de `(loggedin)/` queda protegido por el solo hecho de estar
ahí. Fuera del grupo (`/`, `/login`, `/login/enter`, `/unauthorized`) no hay guard estructural.

**Convención de testing:** Vitest + Testing Library, tests junto al código (`page.test.tsx` al
lado de `page.tsx`), no en una carpeta `__tests__/` separada. `TZ=UTC` fijo. Se testean también
páginas de servidor `async` — patrón: `render(await Component({ ...props }))`. `getByRole` /
`getByText`, no `getByTestId` cuando hay rol o texto accesible.

### Relevant ADRs

**Ninguno aplica de forma directa.** Esta story no toca auth, no toca el proxy, no agrega
estilos. Contexto relevante (no normativo para este alcance):

- **ADR-007** — los roles se leen del claim del token, nunca de la base ni de otra fuente. Es la
  decisión que S-034(api) aplica del lado de `validateToken`; en `web` no cambia nada porque `web`
  ya lee `session.user.roles` del claim vía NextAuth (`(loggedin)/layout.tsx:19`), no de un
  `findByPk`.
- **ADR-002** — degradación ante `core` caído: `503` inmediato o `504` a los 5000 ms. Relevante
  para `asignacion-tiempo` (ver Flow Context abajo), donde `PUT /api/week-assigned-times` empieza
  a poder devolver esos dos códigos por primera vez, aunque el manejo en pantalla no cambia en
  esta story (gap ya registrado en la revisión UX del REQ, fuera de alcance).

### API Context

**Ningún endpoint nuevo ni modificado desde `web`.** El cambio de contrato ocurre enteramente del
lado de la api (S-034 servicio `api`) y es compatible hacia atrás para el cliente:

- **Las 61 rutas** pierden el `401 user_not_found` como respuesta posible. El único 401 que
  sobrevive es `unauthorized` (sin token / token inválido) — **sin cambios de forma**.
- **`PUT /api/week-assigned-times`** — mismo verbo, mismo body, mismos status documentados
  (`200`, `400`, `401`, `403`, `500`), más los dos nuevos de ADR-002 (`503`, `504`) que ya
  aplicaban al resto de las escrituras del producto desde REQ-004 y que esta escritura no tenía
  por ser la única que usaba el ORM directo. El contrato HTTP no cambia (CA-8 de la story): mismo
  cuerpo de request, misma forma de response.

**Lo que `web` tiene que verificar, no implementar:** que ningún código lea `error.code ===
'user_not_found'` (o cualquier variante) para decidir una navegación o un render. La búsqueda ya
se hizo como parte de este planeamiento (ver Task 1) y no encontró ningún uso — se deja como test
de regresión, no como fix.

### Database Context

**Ninguno.** `web` no tiene acceso directo a base de datos.

### Flow Context

**Flujo `autenticacion-y-entrada`** (ref: `docs/flows/autenticacion-y-entrada.md`), pasos
relevantes para `web`:

- **Paso 3** ("el paso que no hace nada"): `POST /api/auth/present` sigue siendo un no-op del
  lado de la api — la ruta no cambia. **Lo que cambia es su razón de ser**: hasta esta story
  existía para intentar crear la fila de `users` antes de que el 401 `user_not_found` bloqueara al
  usuario. Esa fila ya no hace falta para operar (S-029 la crea con el primer comando), así que el
  paso queda como no-op **sin nada que evitar**.
- **Paso 4** ("Primera request de datos — donde el problema aparece"): la rama `alt sin fila en
  users → 401 user_not_found` se elimina del diagrama en la actualización de flujos que corre por
  fuera de esta story de servicio (documentación, no código). Desde el punto de vista de `web`, el
  efecto observable es que la primera request de datos después de `login-entrada` **ya no puede
  fallar con ese 401** — puede seguir fallando con `unauthorized` si el token es inválido, igual
  que hoy.

**Consecuencia para `login-entrada` (`web/src/app/login/enter/page.tsx`):** la página sigue
llamando a `presentInApi()` y redirigiendo a `/`, sin cambio de código. Lo que deja de ocurrir es
el bucle documentado en `docs/ux/surfaces/web/screens/login-entrada.md` (estado *"fallo de `POST
/auth/present`"*): antes, una persona nueva sin fila en `users` entraba, la primera request de
datos fallaba con 401 `user_not_found`, y `web/src/lib/axios.ts` la mandaba de vuelta a
`/login` — sin saber por qué. Ahora esa request no falla por esa razón.

**No hay flujo `alta-requisito-desde-portal`, `vinculacion-de-archivos` ni `subida-de-archivos`
relevante para `web`** — esos flujos son de `opus-web` y de la api, no de este servicio.

### Integration Points

**Ninguno nuevo.** El único punto de integración relevante para esta story es el interceptor de
axios existente:

```ts
// web/src/lib/axios.ts (existente, SIN cambios de código en esta story)
apiClient.interceptors.response.use(
  (response) => response,
  (error: AxiosError<ApiErrorResponse>) => {
    const apiError: ApiError = {
      code: error.response?.data?.code ?? 'internal_error',
      message: error.response?.data?.message ?? 'Internal error',
      status: error.response?.status ?? 500,
    };
    if (error.response?.status === 401) {
      console.error('Unauthorized request detected - token may be expired');
      if (typeof window !== 'undefined') window.location.href = '/login';
    }
    return Promise.reject(apiError);
  }
);
```

**Punto crítico para el CA-16:** el chequeo es `error.response?.status === 401` — **por status
HTTP, no por `code`**. Nunca distinguió `user_not_found` de `unauthorized`: los dos eran (y
`unauthorized` sigue siendo) 401. Esto es exactamente lo que hace que CA-16 se cumpla sin tocar
código: el interceptor jamás miró el `code`, así que no hay nada que dependiera de la variante
que desaparece.

## Tasks

### Task 1: Auditoría de dependencia del 401 `user_not_found` en `web`

**Status:** Completed

#### Description

Confirmar, con evidencia verificable (no asumida), que ningún código de `web` usa el 401
`user_not_found` como señal de navegación o de estado — es lo que pide CA-16 de la story
("verificado, no asumido"). Esta tarea es de auditoría: su resultado esperado es "no se encontró
nada", y el hallazgo (o su ausencia) queda documentado en el propio código vía el test de Task 2,
no en un documento aparte.

Esta auditoría ya se ejecutó una vez durante la planificación de esta story (ver Architectural
Context → API Context) y no encontró ningún uso. La tarea es dejarla repetible y a prueba de
regresión.

#### Acceptance Criteria

1. Se ejecuta una búsqueda exhaustiva en `web/src/` de: `user_not_found`, `userNotFound`, y de
   cualquier `error.code === '...'` que compare contra alguna variante del 401 distinta de la
   redirección genérica ya existente en `web/src/lib/axios.ts`.
2. El resultado (positivo o negativo) queda registrado como comentario en el test de TS-1 (Task
   2), citando el comando ejecutado.
3. Si la búsqueda encuentra **algo** (contradiciendo lo ya relevado en este plan), la tarea se
   detiene y se reporta como hallazgo bloqueante antes de continuar con Task 2 — no se "arregla"
   silenciosamente, porque cambiaría el alcance de una story que el REQ declaró "Nulo -
   verificación" para este servicio.

#### Technical Details

**Architectural Context References:**
- Ver "API Context" arriba — el hallazgo esperado (negativo) y por qué el interceptor de axios
  nunca miró `code` para el 401.
- Ver "Integration Points" — el snippet completo de `web/src/lib/axios.ts`, que es el único lugar

**Files to Create/Modify:**

### Task 2: Tests de regresión para CA-16 y CA-17

**Status:** Completed

la suite lo señale.
