# Story Plan: S-036 (api) - Conteo de requisitos en la api

## Status

**Status:** Completed

## Story Reference

- **Story:** [S-036](../stories/S-036.conteo-de-requisitos-en-la-api.md)
- **Service:** `api`
- **Summary:** `GET /requirements` acepta un query param opcional `count` (boolean). Con
  `count=true` devuelve el número crudo de requisitos que satisfacen **los mismos filtros** que el
  listado, en vez del array; sin el parámetro, la respuesta no cambia para ningún consumidor
  existente. Un solo archivo de ruta (`api/lib/routes/requirements-get.ts`) más su test. El spec
  OpenAPI ya fue actualizado en la fase de diseño — esta story alinea el código con él.

## Architectural Context

### Tech Stack

- **Lenguaje:** TypeScript (sin `strict`), Node.js.
- **Framework HTTP:** Express 5.2, un archivo por endpoint bajo `api/lib/routes/`, montaje
  automático vía barrel (`api/lib/routes/index.ts` + `app.ts:35-37`).
- **ORM:** Sequelize, conectado con un rol de PostgreSQL de **solo lectura**
  (`api/lib/models/index.ts:19-31`). Esta story es puramente de lectura: no toca esa restricción.
- **Validación:** Joi 18, esquema declarado inline en el archivo de la ruta.
- **Logging:** Winston (`api/lib/logger.ts`).
- **Testing:** Mocha 11.7 + `should` + `sinon` + `supertest`, PostgreSQL real efímero levantado por
  los fixtures globales, `FakeBus` que ejecuta `core` real por default.

### Service Architecture

```
api/
├── app.ts                    Express, middleware global (incluye validateToken), montaje de rutas
├── lib/
│   ├── routes/               61 archivos de endpoint + index.ts (barrel)
│   │   ├── requirements-get.ts     <- EL ÚNICO ARCHIVO DE PRODUCCIÓN QUE CAMBIA
│   │   └── objectives-get.ts       <- el espejo a imitar (count ya implementado)
│   ├── models/index.ts       Sequelize de solo lectura
│   ├── logger.ts             Winston
│   └── utils/
│       ├── validate-query-params.ts   valida req.query con Joi -> 400 invalid_fields
│       ├── parse-query-params.ts      NO lo usa requirements-get (ver más abajo)
│       └── middlewares/has-any-role.ts
└── tests/routes/requirements-get.test.ts   <- el test que se extiende
```

No hay `src/`; el dominio vive en el **prefijo del nombre del archivo de ruta**. Imports relativos,
sin paths de `tsconfig`. **No se agregan archivos nuevos** en esta story: el middleware de conteo es
local al archivo de ruta existente, como manda `http-server`.

**Errores:** sin clases, `res.status(n).json({ code, message })` directo en cada punto. `code` es
`snake_case` estable (los fronts hacen `switch`). Nunca se devuelve el detalle de un error interno:
va al log con endpoint y función, y la respuesta sale como `internal_error`.

**Logging:** `logger.error(...)` con el endpoint y la función. Nunca `console`.

### Convenciones activas relevantes

Del manifest de `api` (`docs/architectures/api/manifest.yaml`), las que gobiernan esta story:

#### `_base` — reglas que aplican

- TypeScript obligatorio. `strict` **no** está activo y no se activa.
- `any` se usa en los bordes con Sequelize; la regla de ESLint está apagada a propósito.
- Imports **relativos**. No usar los alias de `module-alias` (`@models`, `@utils`) en TypeScript.
- Comentarios **en español**, y comentan **el por qué, no el qué**.
- Un endpoint es un archivo en `lib/routes/` más una línea en el barrel. Acá el endpoint ya existe:
  no se toca ni `app.ts` ni `index.ts`.
- Lint antes de dar por terminado: `npm run lint --workspace @jiku/api`.

#### `http-server` — reglas que aplican

- **Orden de la cadena de middlewares, siempre el mismo:**
  1. Rol — `hasAnyRole([...])`
  2. Forma del input — `validateQueryParams(schema)`
  3. Existencia de la entidad del path — n/a acá
  4. Permiso sobre la entidad — n/a acá
  5. Reglas de negocio / middlewares locales — **acá entra `getRequirementsCount`**
  6. Handler — `getRequirements`
- **Un middleware que corta la request responde y NO llama a `next()`. Uno que sigue, llama a
  `next()` y no responde.** Es la regla que define la forma de `getRequirementsCount`.
- Método y path en la misma línea del `router.get(`.
- Estilo de declaración: el **directo** (`router.get('/requirements', mw1, mw2, handler)`), que es
  el que ya usa este archivo.
- Los datos intermedios de un endpoint van en `res.locals`; los compartidos, en `req`.
- Respuesta de lectura correcta: **200**.
- Todo endpoint lleva su archivo de test en `tests/routes/{mismo-nombre}.test.ts`.

> **Nota de la convención sobre paginación, directamente relevante:** conviven dos mecanismos —
> `parseGetParams()` (compartido, deja `req.parsedParams`) y **query params leídos a mano en el
> handler**. `requirements-get` usa el segundo. La convención advierte explícitamente sobre
> `parseLimit` (`parse-query-params.ts:41-43`), que valida `limit <= 30` y si no se cumple devuelve
> **200** en silencio: *"si tocás paginación, no la repliques"*. **Esta story NO migra
> `requirements-get` a `parseGetParams`** — sería un cambio de comportamiento fuera de alcance
> (el `limit` de requirements es `.max(100)`, incompatible con el `<= 30` de `parseLimit`).

#### `validation` — reglas que aplican

- El esquema Joi vive **en el mismo archivo que la ruta**. No se mueve a un módulo compartido.
- Esquema largo → constante nombrada arriba del archivo. El de `requirements-get` ya lo es
  (`querySchema`, líneas 12-24): el campo nuevo se agrega ahí.
- `validateQueryParams` responde 400 con el **primer** error:
  `{ code: 'invalid_fields', message: 'Invalid field - {mensaje de Joi}' }`. **No se cambia ese
  contrato.**
- Los valores de enum se derivan con `...Object.values(EnumDelModelo)`, no se listan a mano
  (ya cumplido en este archivo para `state` y `type`).
- La validación de forma va **antes** de buscar entidades en la base.

#### `error-handling` — reglas que aplican

- `res.status(n).json({ code, message })`. Sin `throw`, sin clases de error.
- 500 `internal_error` para cualquier error inesperado, con el detalle **solo en el log**.
- `logger.error` con endpoint y función, nunca `console`.

#### `authorization` / `auth-jwt` — reglas que aplican

- **Capa 1 (global, automática):** `app.ts` instala `validateToken` para todo path excepto las
  exenciones de `config/public.ts`. `/api/requirements` **no** está exento → sin token válido es
  401 antes de llegar al archivo de ruta. **No se agrega `validateToken` a la ruta.**
- **Capa 2 (por rol):** `hasAnyRole(['user','admin'])`, ya declarado en la cadena. Responde 403
  `access_denied` a `external-user`.
- **Capa 3 (por entidad):** no aplica a este endpoint (no hay entidad en el path).
- Consecuencia para esta story: el conteo entra **detrás** de las capas 1 y 2, en el mismo orden
  que el listado. No es una superficie más permisiva (CA-5 y CA-6) y no hay que escribir código
  nuevo para conseguirlo — basta con insertar el middleware **después** de `hasAnyRole` y de
  `validateQueryParams`.

#### `orm` — reglas que aplican

- Sequelize en **solo lectura**. `Requirement.count()` es una lectura: cumple.
- Los modelos vienen del paquete compartido `@jiku/models` (ya importado en el archivo).

#### `testing` — reglas que aplican

- Un archivo de ruta lleva su test en `tests/routes/{mismo-nombre}.test.ts` (ya existe:
  `api/tests/routes/requirements-get.test.ts`, 276 líneas).
- **No se mockea Sequelize ni la base:** los tests corren contra un PostgreSQL real.
- **No se prepara el esquema en el archivo de test:** lo hacen los fixtures globales.
- **No se llama a `setBus`:** el doble ya está instalado y se resetea por root hook.
- Limpiar los datos creados en `after` con `Model.destroy({ where: {} })`.
- Todo endpoint con `hasAnyRole` lleva un test por rol rechazado.
- Toda regla de negocio se testea **en su límite**, no en el centro del rango válido.
- Aserciones con `should`. No mezclar `assert` ni `expect`.
- Un test no depende del orden de ejecución ni del estado que dejó otro.

### Relevant ADRs

**ADR-006** (referenciado por la story): el portal externo (`opus-web`) lee por `/opus/*`, no por
las rutas internas. Consecuencia para esta story: `GET /requirements` **no es alcanzable desde el
portal externo**, así que el conteo no expone requisitos `internal` a un cliente aunque no filtre
por `visibilityLevel`. Es lo que hace aceptable heredar el comportamiento del listado sin cambiarlo.

No hay otros ADRs que condicionen esta story (no hay bus, no hay escritura, no hay storage).

### Código actual — el punto de partida exacto

#### `api/lib/routes/requirements-get.ts` (85 líneas, completo)

```ts
import { Request, Response, Router } from 'express';
import { sequelize } from '../models';
import { Person, Project, Requirement, RequirementState, RequirementType } from '@jiku/models';
import logger from '../logger';
import hasAnyRole from '../utils/middlewares/has-any-role';
import validateQueryParams from '../utils/validate-query-params';
import joi from 'joi';
import { Op } from 'sequelize';

const router: Router = Router();

const querySchema = joi.object({
  projectId: joi.number().integer().optional(),
  state: joi.string().valid(...Object.values(RequirementState)).optional(),
  type: joi.string().valid(...Object.values(RequirementType)).optional(),
  priority: joi.string().optional(),
  createdBy: joi.string().optional(),
  estimatedFinishDate: joi.date().optional(),
  tag: joi.string().optional(),
  search: joi.string().optional(),
  page: joi.number().integer().min(1).default(1),
  limit: joi.number().integer().min(1).max(100).default(20),
  sort: joi.string().optional(),
});

function getRequirements(req: Request, res: Response) {
  const { projectId, state, type, priority, createdBy, estimatedFinishDate, tag, search, page = 1, limit = 20 } = req.query as any;
  const offset = (Number(page) - 1) * Number(limit);

  const where: any = {};
  if (projectId) where.projectId = Number(projectId);
  if (state) where.state = state;
  if (type) where.type = type;
  if (priority) where.priority = priority;
  if (createdBy) where.createdBy = createdBy;
  if (estimatedFinishDate) where.estimatedFinishDate = estimatedFinishDate;
  if (search) where.title = { [Op.iLike]: '%' + search + '%' };
  if (tag) {
    const [key, value] = String(tag).split(':');
    where.tags = sequelize.literal(
      `tags @> '[{"key": ${JSON.stringify(key)}, "value": ${JSON.stringify(value)}}]'::jsonb`
    );
  }

  return Requirement.findAll({
    where,
    include: [
      { model: Project, as: 'project', attributes: ['id', 'name'] },
      {
        model: Person,
        as: 'responsiblePeople',
        attributes: ['id', 'firstName', 'lastName'],
        through: { attributes: ['isLeader'] },
      },
    ],
    limit: Number(limit),
    offset,
    order: [['createdAt', 'DESC']],
  })
    .then((requirements) => {
      const response = requirements.map((requirement) => {
        const json = requirement.toJSON() as any;
        json.responsiblePeople = (json.responsiblePeople || []).map((person: any) => ({
          id: person.id,
          firstName: person.firstName,
          lastName: person.lastName,
          isLeader: person.PersonRequirement?.isLeader ?? null,
        }));
        return json;
      });
      return res.status(200).json(response);
    })
    .catch((error) => {
      logger.error(`[GET /requirements] error: ${error.message}`);
      return res.status(500).json({ code: 'internal_error', message: 'Internal error' });
    });
}

router.get('/requirements',
  hasAnyRole(['user', 'admin']),
  validateQueryParams(querySchema),
  getRequirements
);

export default router;
```

**Dos diferencias que el implementador NO debe copiar sin pensar:**

1. `objectives-get` lee de `req.parsedParams` (poblado por `parseGetParams()`).
   `requirements-get` **no usa `parseGetParams`** y lee `req.query` directo. El middleware nuevo
   lee de `req.query`.
2. `objectives-get` usa `distinct: true, col: 'id'` porque cuenta con `include` de `Person`
   (una relación N:M que multiplica filas). **El conteo de requirements va SIN `include`**, porque
   ninguno de sus filtros depende de las relaciones (`project` y `responsiblePeople` se incluyen
   solo para armar el cuerpo del listado). Sin `include` no hay filas duplicadas, así que no hace
   falta `distinct`.

### ⚠ Punto crítico verificado en el código: `count` llega como STRING, no como boolean

Es la trampa de esta story y hay que resolverla explícitamente. Cadena de hechos, todos verificados:

1. **Express 5** entrega `req.query` con los valores **como strings** (`'true'`, `'false'`,
   `'quizas'`). No hay coerción de tipos en el framework.
2. **`validateQueryParams` descarta el valor coercido por Joi.** Su implementación
   (`api/lib/utils/validate-query-params.ts:5`) es:

   ```ts
   const {error} = validationSchema.validate(req.query);
   ```

   Destructura **solo `error`**. El `value` coercido que Joi devuelve —donde `'true'` ya sería el
   boolean `true`— se descarta, y `req.query` **nunca se reasigna**. (En Express 5 `req.query` es
   además un getter, así que reasignarlo no es una opción sin romper otras rutas: **no lo hagas**.)
3. Por lo tanto, dentro del handler `count` vale el **string** `'true'` o el string `'false'`.

**Consecuencia directa:** un `if (!count) return next();` copiado de objectives es **incorrecto**
para requirements, porque el string `'false'` es *truthy* en JavaScript y `count=false` devolvería
un número en vez del listado.

> Aclaración sobre por qué en `objectives` "funciona": `parseGetParams` hace
> `count: queryParams.count || false` (`parse-query-params.ts:50`), que propaga el string tal cual.
> `GET /objectives?count=false` tiene **el mismo defecto**: devuelve el conteo. Nadie lo llama así,
> por eso nunca se notó. **No se arregla en esta story** (`objectives` está fuera de alcance y
> tocarlo cambiaría un comportamiento que la web ya consume), pero **no se replica**: el conteo de
> requirements compara contra el string `'true'`.

**La comparación correcta**, que hay que escribir tal cual:

```ts
// `count` llega como string desde req.query: Express 5 no coerciona y validateQueryParams
// descarta el value que Joi devuelve coercido (solo usa `error`). Por eso se compara contra
// 'true' y no se evalúa la verdad del valor: el string 'false' es truthy y devolvería el
// conteo cuando el consumidor pidió el listado.
if (String(req.query.count) !== 'true') {
  return next();
}
```

Joi sigue siendo el que rechaza `count=quizas` con 400 (valida el string contra `joi.boolean()`,
que acepta `'true'`/`'false'` por su coerción interna y rechaza cualquier otra cosa) — la
comparación de arriba solo decide la rama, no valida.

**Status:** Completed

### Descripción

2. **Extraer** la construcción del objeto `where` (hoy embebida en `getRequirements`, líneas 30-43)

3. Agregar el middleware local `getRequirementsCount`, insertado en la cadena del router.

**Por qué se extrae `buildWhere` y no se duplica la lógica:** es la garantía estructural del CA-1.

uno y no al otro los haría divergir en silencio — exactamente el problema que la convención
`validation` describe para las reglas con dos definiciones. Con un solo constructor, los filtros son
idénticos **por construcción**, no por disciplina. Es además el mismo patrón que ya usa
`objectives-get.ts` con `buildWhereClauses` (líneas 19-52).

**Forma esperada del resultado:**

```ts
const querySchema = joi.object({
  // ... los 11 campos actuales, sin cambios ...
  sort: joi.string().optional(),
  count: joi.boolean().optional(),
});

// Un solo constructor del `where` para listado y conteo: si cada uno armara el suyo, un filtro
// nuevo agregado a uno y no al otro los haría divergir sin que ningún test lo note.
function buildWhere(query: any) {
  const { projectId, state, type, priority, createdBy, estimatedFinishDate, tag, search } = query;

  const where: any = {};
  if (projectId) where.projectId = Number(projectId);
  if (state) where.state = state;
  if (type) where.type = type;
  if (priority) where.priority = priority;
  if (createdBy) where.createdBy = createdBy;
  if (estimatedFinishDate) where.estimatedFinishDate = estimatedFinishDate;
  if (search) where.title = { [Op.iLike]: '%' + search + '%' };
  if (tag) {
    const [key, value] = String(tag).split(':');
    where.tags = sequelize.literal(
      `tags @> '[{"key": ${JSON.stringify(key)}, "value": ${JSON.stringify(value)}}]'::jsonb`
    );
  }

  return where;
}

function getRequirementsCount(req: Request, res: Response, next: NextFunction) {
  // `count` llega como string: Express 5 no coerciona req.query, y validateQueryParams descarta
  // el value que Joi devuelve ya coercido (solo usa `error`). Por eso se compara contra 'true' en
  // vez de evaluar la verdad del valor: el string 'false' es truthy y devolvería el conteo a quien
  // pidió el listado.
  if (String(req.query.count) !== 'true') {
    return next();
  }

  // Sin `include`: ningún filtro depende de las relaciones —`project` y `responsiblePeople` se
  // incluyen solo para armar el cuerpo del listado—, así que no hay filas duplicadas que obliguen
  // al `distinct` que sí necesita el conteo de objectives.
  return Requirement.count({ where: buildWhere(req.query) })
    .then((count) => {
      return res.status(200).json(count);
    })
    .catch((error) => {
      logger.error(`[GET /requirements] getRequirementsCount error: ${error.message}`);
      return res.status(500).json({ code: 'internal_error', message: 'Internal error' });
    });
}

function getRequirements(req: Request, res: Response) {
  const { page = 1, limit = 20 } = req.query as any;
  const offset = (Number(page) - 1) * Number(limit);

  const where = buildWhere(req.query);

  return Requirement.findAll({
    where,
    // ... el resto EXACTAMENTE como está hoy ...
  });
}

router.get('/requirements',
  hasAnyRole(['user', 'admin']),
  validateQueryParams(querySchema),
  getRequirementsCount,
  getRequirements
);
```

**Contexto arquitectónico que aplica:**
- `http-server` → orden de la cadena (el conteo es paso 5, middleware local, después de rol y
  forma del input); un middleware que corta responde y no llama a `next()`, uno que sigue llama a
  `next()` y no responde.
- `validation` → el esquema se queda en el archivo; el contrato de error 400 no se toca.
- `error-handling` → `res.status().json({code, message})`, `logger.error` con contexto, sin filtrar
  `error.message` al cliente.
- `orm` → `Requirement.count()` es lectura; compatible con el rol de solo lectura.
- `authorization` → el conteo hereda las capas 1 y 2 por posición en la cadena; no se agrega
  ninguna verificación nueva.
- `_base` → comentarios en español explicando el por qué; imports relativos; sin `strict`.

**Trampas a evitar (todas verificadas en el código):**
1. **No** copiar `if (!req.parsedParams.count)` de objectives: este endpoint no tiene
   `parsedParams`, y la verdad del valor es la comparación equivocada (TS-7).
2. **No** reasignar `req.query` para "arreglar" la coerción: en Express 5 es un getter.
3. **No** agregar `distinct: true` / `col: 'id'`: sin `include` no hay duplicados, y `distinct`

4. **No** agregar `include` al `count`: multiplicaría filas por `responsiblePeople` y devolvería

5. **No** pasar `limit`/`offset` al `count` (TS-9: el conteo es del total filtrado).
6. **No** migrar a `parseGetParams()` (su `parseLimit` tope 30 es incompatible con el `.max(100)`
