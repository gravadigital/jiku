## Status

**Status:** Ready

## Story Reference

- **Story:** [S-037](../stories/S-037.paginador-unico-con-ventana-deslizante.md)
- **Service:** `web`
- **Summary:** Reescribir el componente compartido `Pagination` para que dibuje **como máximo 10
  números** en una ventana deslizante centrada en la página actual y ajustada a los extremos, y para
  que soporte **dos modos de operación** —modo URL (navega con `router.push` a una ruta base
  parametrizable) y modo controlado (invoca un callback, sin tocar la URL)—. El único consumidor
  actual, `ObjectivesTable`, sigue en modo URL contra `/objectives` **sin ningún cambio observable de
  navegación**. La story habilita a S-038 (card de requisitos en modo controlado).

#### `state-management` — reglas duras que aplican a esta story

Árbol de decisión del servicio:

```
¿De dónde viene el dato?
├── De la api  ─────────────────> TanStack Query.  NUNCA copiarlo a useState
├── Define qué se ve en la
│   pantalla y querés que sea
│   compartible / navegable  ───> searchParams (router.push)
├── Sesión ─────────────────────> useSession() / auth()
└── Solo le importa a este
    componente y a sus hijos ───> useState / useReducer
```

- **"Los filtros, el orden, la página y el tamaño de página van en la URL."** No hay librería: se usa
  `useSearchParams` para leer y `router.push` para escribir.
- **Regla dura: no copiar datos de query a `useState`.** El `useEffect` + `useState` que hoy tiene
  `Pagination` (líneas 14-26) es exactamente ese antipatrón aplicado a `searchParams`: una segunda
  fuente de verdad para la página.
- Patrón de escritura de searchParams, verbatim de la convención:

```tsx
const createQueryString = useCallback((name: string, value: string) => {
  const params = new URLSearchParams(searchParams?.toString());
  if (!value || value === 'all') params.delete(name);
  else params.set(name, value);
  return params.toString();
}, [searchParams]);
```

  **Regla:** partir de los params actuales, no de vacío — cambiar la página no debe borrar los filtros.
- **`useCallback`** en los handlers que se pasan a hijos memoizados o que entran en deps de efectos.
  No en todos por reflejo.
- **`useMemo`** para derivaciones caras sobre listas. El cálculo de la ventana es O(1); un `useMemo`
  acá es opcional y no obligatorio por convención.

#### `styling`

- **Un módulo por componente**, junto al `.tsx`. Nombre del módulo = nombre del componente.
- **Clases en `camelCase`**, no `kebab-case`.
- El módulo empieza con `@use '@/styles' as *;` (o `@use '@/styles/mixins' as *;`, que es lo que hoy
  usa `Pagination.module.scss`) cuando necesita mixins.
- **Usar `cn()` para clases condicionales**, nunca template strings:
  ```tsx
  className={cn(styles.option, { [styles.active]: value === option.key })}
  ```
  El patrón `` `${styles.a} ${cond && styles.b}` `` escribe el string `"false"` en el `class`. Es un
  bug latente que ya existe en el código, **no** el patrón a seguir.
- **Usar el token, nunca el hex literal.** Tokens relevantes ya usados por el módulo actual:
  `--color-general-background`, `--color-general-text`, `--color-general-disabled`, `--color-button`,
  `--color-background`, `--color-text-light`, `--font-primary`.
- **No `@media` cruda:** usar los mixins de `_mixins.scss`. *(No se espera necesitar media queries en
  esta story: la superficie `web` es de un solo viewport.)*
- Mixin de foco disponible y ya usado por el componente:
  ```scss
  @mixin focus-ring($color: var(--color-highlighted), $offset: 2px) {
    &:focus { outline: none; }
    &:focus-visible { outline: 2px solid $color; outline-offset: $offset; }
  }
  ```

### Estado actual del código (el punto de partida exacto)

`web/src/shared/components/ui/Pagination/Pagination.tsx` — **completo, tal como está hoy**:

```tsx
'use client';
import React, { useEffect, useState } from 'react';
import { useRouter, useSearchParams } from 'next/navigation';
import styles from './Pagination.module.scss';

interface PaginationProps {
  readonly totalItems: number;
  readonly limit: number;
}

export function Pagination({ totalItems, limit }: PaginationProps) {
  const router = useRouter();
  const searchParams = useSearchParams();
  const [currentPage, setCurrentPage] = useState(1);
  const [totalPages, setTotalPages] = useState<number | null>(null);

  useEffect(() => {
    const page = searchParams?.get('page');
    const calculatedTotalPages = Math.ceil(totalItems / limit);
    setTotalPages(calculatedTotalPages);
    if (!page || page === '1') {
      setCurrentPage(1);
    } else {
      setCurrentPage(Number(page));
    }
  }, [searchParams, totalItems, limit]);

  const createQueryString = (field: string, value: string) => {
    const params = new URLSearchParams(searchParams?.toString());
    params.set(field, value);
    return params.toString();
  };

  const handlePageChange = (newPage: number) => {
    router.push(`/objectives?${createQueryString('page', newPage.toString())}`);
  };

  if (totalItems === 0) {
    return null;
  }

  return (
    <nav className={styles.pagination} aria-label="Paginación" role="navigation">
      <button
        type="button"
        onClick={() => handlePageChange(currentPage - 1)}
        disabled={currentPage === 1}
        aria-label="Página anterior"
      >
        {'<'}
      </button>
      {Array.from({ length: totalPages || 0 }, (__, index) => {
        const pageNumber = index + 1;
        const isCurrentPage = currentPage === pageNumber;
        return (
          <button
            type="button"
            key={index}
            onClick={() => handlePageChange(pageNumber)}
            disabled={isCurrentPage}
            data-active={isCurrentPage || undefined}
            aria-label={`Página ${pageNumber}`}
            aria-current={isCurrentPage ? 'page' : undefined}
          >
            {pageNumber}
          </button>
        );
      })}
      <button
        type="button"
        onClick={() => handlePageChange(currentPage + 1)}
        disabled={currentPage === totalPages}
        aria-label="Página siguiente"
      >
        {'>'}
      </button>
    </nav>
  );
}
```

#### Accesibilidad de la pantalla — lo que toca al paginador

- **Orden de foco:** … filtro-orden → pill-estado de cada fila → **paginacion**. El paginador es el
  último en el orden de foco de la pantalla.
- El paginador actual **ya cumple** lo esencial: es un `<nav aria-label="Paginación">`, cada número es
  un `<button type="button">` con `aria-label={`Página ${n}`}`, la página activa lleva
  `aria-current="page"` y está `disabled`, y las flechas llevan `aria-label="Página anterior"` /
  `"Página siguiente"`. **Todo esto se preserva en la reescritura.**
- El resto de los hallazgos de accesibilidad de la pantalla (filas de tabla no navegables por teclado,
  `vacio-tareas` como `<h3>` huérfano, el área comunicada solo por color) son **preexistentes y fuera
  de alcance**.

#### Decisiones y descartes ya tomadas en UX (no re-litigar)

Verbatim del screen.md, sección "REQ-008":

- **Esta pantalla no cambia de comportamiento: cambia cuántos números ve el usuario.** Con 30 páginas
  dibujaba 30 botones, una fila de números que no cabe y en la que ninguno destaca. La ventana de 10
  centrada en la página actual mantiene siempre visibles las páginas vecinas —las únicas a las que se
  salta de verdad— y acota el recorrido por teclado a un tramo constante.
- **Se descartó la elipsis con primera y última** (el patrón `1 … 14 15 16 … 30`) que usaban los
  paginadores inline del producto. Muestra menos contexto alrededor de la posición actual y agrega dos
  elementos no interactivos al recorrido; la ventana corrida da lo mismo sin huecos.
  → **Consecuencia dura para la implementación: NO implementar elipsis. Sin `…`, sin botones de
  "primera"/"última".**
- **El total sigue sin mostrarse.** Fuera del alcance de este requerimiento. Queda registrado como gap.
  → **No agregar un "mostrando X de Y".**
- **El paginador pierde la ruta hardcodeada, y esta pantalla no se entera.**
- **No se agregó componente al Design System.**

## Tarea 1: Extraer y testear la función de ventana deslizante

**Status:** Completed
**Categoría:** Logic
**Dependencias:** Ninguna

### Descripción

Implementar el cálculo de la ventana como una **función pura exportada**, separada del componente.
Es el corazón de CA-1 a CA-4 y la parte que conviene testear sin render: 10 escenarios de tabla que
como tests de componente serían 10 renders innecesarios.

Ubicación sugerida, coherente con la estructura del servicio: `web/src/shared/components/ui/Pagination/getPageWindow.ts`
(junto al componente, que es donde vive todo lo suyo), o `web/src/shared/utils/` si se prefiere
tratarla como utilidad general. **La primera es la recomendada:** hoy tiene un solo consumidor y el
catálogo de `shared/utils/` no gana nada con ella.

### Criterios de Aceptación

- [ ] Existe una función pura exportada que, dados `currentPage` y `totalPages`, devuelve el array de
      números de página a renderizar.
- [ ] El tamaño máximo de ventana es **10** y está declarado como una constante nombrada (no un `10`
      suelto repartido por el cuerpo).
- [ ] `totalPages <= 10` ⇒ devuelve `[1..totalPages]`, sin relleno ni huecos (CA-4).
- [ ] `totalPages > 10` ⇒ devuelve exactamente 10 números, siempre dentro de `[1, totalPages]`.
- [ ] La ventana se centra en `currentPage` y **se ajusta a los extremos** cuando la ideal se saldría
      del rango (CA-1, CA-3).
- [ ] `totalPages` 0 o negativo ⇒ array vacío, sin arrojar (TS-8).
- [ ] La función **no** produce elipsis, ni sentinels, ni huecos: solo números contiguos.

### Detalles Técnicos

**El algoritmo, fijado por los casos de la story:**

```
WINDOW = 10
if (totalPages <= 0) return []
if (totalPages <= WINDOW) return [1..totalPages]

start = clamp(currentPage - Math.floor(WINDOW / 2), 1, totalPages - WINDOW + 1)
end   = start + WINDOW - 1
return [start..end]
```

**Verificación contra los cuatro CA** (hacer esta cuenta antes de escribir el código):

| CA | `currentPage` | `totalPages` | `currentPage - 5` | clamp a `[1, 21]` | Rango | ¿Coincide con la story? |
|---|---|---|---|---|---|---|
| CA-1 | 1 | 30 | -4 | **1** | `1-10` | Sí |
| CA-2 | 15 | 30 | 10 | **10** | `10-19` | **Sí** — la story dice `10-19` |
| CA-3 | 30 | 30 | 25 | **21** | `21-30` | Sí |
| CA-4 | 2 | 4 | — | atajo `totalPages <= 10` | `1-4` | Sí |

> **El detalle que decide la implementación:** `Math.floor(10 / 2) = 5`, y `15 - 5 = 10`. Eso deja la
> página actual en la **sexta** posición de la ventana. Es lo que piden la story (CA-2), el REQ-008 y
> el `screen.md`, los tres con el mismo texto: *"página 15 → `10-19`"*. Un `- 4` en vez de `- 5`
> produciría `11-20` y **falla CA-2**.

**Convenciones aplicables:**
- TypeScript `strict`: tipar la firma explícitamente. Nada de `any`.
- Sin dependencias de React: es una función pura, testeable sin `jsdom`.

## Tarea 2: Reescribir el componente `Pagination` con dos modos de operación

**Status:** Completed
**Categoría:** Logic
**Dependencias:** Tarea 1

### Descripción

Reescribir `web/src/shared/components/ui/Pagination/Pagination.tsx` para que:

1. use la función de la Tarea 1 en vez de `Array.from({ length: totalPages })`;
2. soporte **modo URL** (ruta parametrizable, navegación con `router.push`) y **modo controlado**
   (callback, sin tocar la URL);
3. **elimine el `useState` + `useEffect`** que hoy copian la página de `searchParams` — la página se
   deriva o la provee el contenedor.

Es el núcleo de la story. Cubre CA-1 a CA-6.

### Criterios de Aceptación

- [ ] El componente ya **no** contiene `useEffect`, y no guarda la página ni el total de páginas en
      `useState`. Grep de control: `useEffect` y `useState` no aparecen en `Pagination.tsx`.
- [ ] **Modo URL:** recibe la ruta base por prop (ej. `basePath`) y, al hacer click, ejecuta
      `router.push(`${basePath}?${params}`)` con el `page` actualizado. La ruta `/objectives` **no**
      está hardcodeada en ninguna línea del componente.
- [ ] En modo URL la página se **deriva** de `searchParams.get('page')`, con `1` como fallback cuando
      falta, está vacío, o no es un número válido.
- [ ] La navegación **parte de los searchParams actuales** y solo reemplaza `page`: ningún otro filtro
      se pierde (TS-17).
- [ ] **Modo controlado:** recibe `currentPage` y `onPageChange`; al hacer click invoca
      `onPageChange(nuevaPagina)` con el número, y **no** ejecuta ninguna navegación (CA-6).
- [ ] Los dos modos son **mutuamente excluyentes y evidentes en el tipo**: la unión discriminada debe
      hacer que pasar `onPageChange` junto a `basePath` sea un error de tipos, o que falte uno de los
      dos también lo sea.
- [ ] Se preserva `if (totalItems === 0) return null` (o el equivalente sobre `totalPages`), porque
      **S-038 depende de este comportamiento** para su CA-19.
- [ ] Se preserva **toda** la accesibilidad actual: `<nav aria-label="Paginación">`, un `<button
      type="button">` por número con `aria-label={'Página N'}`, `aria-current="page"` + `disabled` en
      la actual, flechas con `aria-label` `"Página anterior"` / `"Página siguiente"` y deshabilitadas
      en los extremos.
- [ ] El aspecto visual no cambia: mismos tokens, mismo `gap`, mismas flechas `<` y `>`.
- [ ] **Sin elipsis, sin botones de "primera"/"última", sin "mostrando X de Y".** UX los descartó
      explícitamente.

### Detalles Técnicos

**Forma sugerida de las props** (unión discriminada; el implementador puede ajustar los nombres
mientras el contrato se mantenga):

```ts
type PaginationBaseProps = {
  readonly totalItems: number;
  readonly limit: number;
};

type PaginationUrlProps = PaginationBaseProps & {
  /** Ruta base a la que navegar; el resto de los searchParams se preservan. */
  readonly basePath: string;
  readonly currentPage?: never;
  readonly onPageChange?: never;
};

type PaginationControlledProps = PaginationBaseProps & {
  readonly currentPage: number;
  readonly onPageChange: (page: number) => void;
  readonly basePath?: never;
};

type PaginationProps = PaginationUrlProps | PaginationControlledProps;
```

> **Alternativa admisible:** exponer `totalPages` directamente en vez de `totalItems` + `limit` para el
> modo controlado. **No hacerlo en esta story.** El consumidor actual pasa `totalItems`/`limit`, S-038
> tiene su propio total por estado y va a poder derivar su `limit`, y cambiar el contrato de conteo
> ahora agrega superficie sin CA que lo pida. Mantener `totalItems` + `limit` en los dos modos.

**Cálculo de la página en modo URL** (deriva, no estado):

```tsx
const searchParams = useSearchParams();
const pageParam = searchParams?.get('page');
const parsed = Number(pageParam);
const derivedPage = Number.isFinite(parsed) && parsed >= 1 ? Math.floor(parsed) : 1;
```

**Escritura de la URL**, siguiendo la convención `state-management` verbatim:

```tsx
const createQueryString = useCallback((name: string, value: string) => {
  const params = new URLSearchParams(searchParams?.toString());
  params.set(name, value);
  return params.toString();
}, [searchParams]);
```

> Nota: la convención documenta que el valor `'all'` **borra** el parámetro. Ese sentinel es de los
> filtros, no de `page` — acá `page` siempre se escribe. No portar esa rama.

**Handler unificado:**

```tsx
const handlePageChange = useCallback((newPage: number) => {
  if (onPageChange) { onPageChange(newPage); return; }
  router.push(`${basePath}?${createQueryString('page', String(newPage))}`);
}, [onPageChange, router, basePath, createQueryString]);
```

**Hooks y el modo controlado:** `useSearchParams()` y `useRouter()` son hooks — se llaman siempre,
también en modo controlado, porque las reglas de hooks no admiten llamadas condicionales. Lo que
cambia es **si se usan**. En modo controlado se llaman y se ignoran; eso es correcto y es lo que
verifica TS-21 (que `push` no se ejecute), no que el hook no se invoque.

> **Requisito de contexto:** `useSearchParams()` exige que el componente esté bajo un `<Suspense>` en
> Next 15+ o produce un warning de bailout en build. `ObjectivesTable` ya lo cumple (la página lo
> envuelve en dos `<Suspense>` anidados). **S-038 tendrá que cumplirlo también** — anotarlo si la
> implementación revela fricción, pero no resolverlo acá.

**Convenciones aplicables:**
- `'use client'` en la primera línea: el componente usa hooks de navegación y handlers.
- `cn()` para clases condicionales, **nunca** template strings (`styling`).
- Tokens de código para colores, nunca hex literal.
- `useCallback` en los handlers que entran en deps — acá aplica genuinamente.

**Estilos:** `Pagination.module.scss` se conserva. Si la implementación cambia el orden o la
estructura de los hijos del `<nav>`, revisar que `button:first-of-type` / `button:last-of-type` sigan
apuntando a las flechas; si no, reemplazar esos selectores por clases explícitas (`.arrow`) **sin
cambiar el resultado visual**.
