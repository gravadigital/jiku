## ⚠️ Tres hallazgos que hay que resolver ANTES de escribir código

Los tres salieron de contrastar la story contra el código y la base **reales**. Ninguno es una
opinión de estilo: los tres cambian lo que se implementa. Están al principio del plan a propósito.

### H-1 · La clave de `hours-per-day` en la base es `hours_per_day`, con guiones BAJOS

**NO DOCUMENTADO — needs verification.**

La story (CA-8), el REQ-006 (RF-28, CA-22) y `bus-api-consultas-ref.md:474` dicen que la lista blanca
de `settings` es **`hours-per-day`** y las cinco de archivos. Pero la clave que **existe en la base**
se llama `hours_per_day`:

```js
// api/db-upgrade/migrations/20260206_01_system_settings.js:39
[{ key: 'hours_per_day', value: '6', created_at: new Date(), updated_at: new Date() }],
```

```
// local/dump.sql:569307
1	hours_per_day	6	2026-02-13 00:51:53.786+00	2026-02-13 00:51:53.786+00
```

Y la api la lee con ese nombre: `api/lib/routes/settings-get.ts:9` hace
`SystemSetting.findOne({ where: { key: 'hours_per_day' } })`.

Las **cinco de archivos SÍ usan guiones medios** y existen así en la base
(`core/src/commands/files/settings.ts:62-68`): `upload-url-ttl-seconds`,
`download-url-ttl-seconds`, `file-max-size-bytes`, `file-allowed-extensions`,
`file-allowed-mime-types`. La única disidente es la vieja, de febrero.

**Si la lista blanca se escribe literal como dice el documento, `settings.list` devuelve CINCO
claves y `hours-per-day` no aparece nunca** — que es exactamente el bug que CA-8 describe al revés.
Y es un bug silencioso: `items: []` para esa clave es indistinguible de "no está declarada".

**Resolución adoptada en este plan (Tarea 3), y hay que confirmarla:** el contrato publica
`hours-per-day` y la ficha traduce a la columna `hours_per_day`. Es exactamente ADR-004 —"el
vocabulario del producto vive en el contrato, la base no se toca"— y la convención
`contract-translation` es el lugar donde se registra (CA-19 ya obliga a tocarla). La alternativa
—publicar `hours_per_day` crudo— rompería el documento del REQ y dejaría al contrato de consultas
hablando en nombres de columna, que es lo que ADR-004 prohíbe.

**Consecuencia técnica:** `settings` NO puede resolver su lista blanca con un `resource.where`
literal sobre `key`, porque el valor del contrato y el de la columna difieren en una de las seis
entradas. Ver el diseño de la Tarea 3.

### H-3 · La ficha NO puede llevar etiquetas de enum todavía

`ResourceSpec.enums` es hoy `Readonly<Record<string, readonly string[]>>`
(`core/src/queries/types.ts:640`): **solo valores, sin etiquetas**. Pero CA-10 exige "los enums **con
etiquetas**" y CA-13 exige que `meta.describe` de `unworked-times` traiga los nueve valores de
`reason` **con sus etiquetas**, para reemplazar funcionalmente a `GET /unworked-times/reasons`.

Las etiquetas existen hoy en **un solo lugar y es la api**:

```ts
// api/lib/routes/unworked-times-reasons-get.ts:6-16
const UNWORKED_REASONS = [
  { value: 'tramite', label: 'Trámite' },
  { value: 'corte_servicios', label: 'Cortes de servicios' },
  { value: 'vacaciones', label: 'Vacaciones' },
  { value: 'dia_no_laborable', label: 'Día no laborable' },
  { value: 'personal', label: 'Personal' },
  { value: 'medico', label: 'Médico' },
  { value: 'estudio', label: 'Estudio' },
  { value: 'enfermedad', label: 'Enfermedad' },
  { value: 'otro', label: 'Otro' },
];
```

**`meta.describe` no puede leerlas de ahí**: `core` no importa nada de `api`, y hacerlo invertiría la
dirección de la dependencia del producto. **Las etiquetas tienen que entrar en la ficha**, y eso es
un cambio de tipo en `types.ts` más un cambio en las cinco fichas con enums de valores reales. Es la
**Tarea 1** y va primero por eso.

> **La ficha es el único lugar donde pueden vivir sin romper CA-12.** Si las etiquetas se mantuvieran
> en un mapa aparte —"total son pocos enums"— sería exactamente la estructura paralela que el riesgo
> principal de la story describe: se desincroniza y `meta.describe` pasa a mentir.

## Architectural Context

### Tech Stack

| Pieza | Versión / detalle |
|---|---|
| Lenguaje | TypeScript con `strict: true` — **único entre los backends**. Suma `noUnusedLocals`, `noUnusedParameters`, `noImplicitReturns` (`core/tsconfig.json:22-26`) |
| Runtime | Node.js |
| ORM | Sequelize + `sequelize-typescript`, modelos en `@jiku/models` |
| Base | PostgreSQL `jiku`. `core` escribe con el usuario **dueño**; el plano de consultas lee por una conexión **de solo lectura** (`core/src/models/read.ts`) |
| Bus | NATS request/reply, **sin JetStream**. `nats.js` micro services |
| Validación | **Joi** (no Zod: el catálogo recomienda Zod, este servicio es anterior) |
| Logging | Winston (`core/src/logger.ts`) |
| Tests | **Mocha + `should` + `sinon`**, contra PostgreSQL real efímero. `npm test` = `mocha "tests/**/*.test.ts"` |
| Config | `dotenv` + `process.env`, sin asserts |

### Service Architecture

`core` es un **worker**: no expone HTTP, no tiene puerto, ni endpoints, ni verbos, ni framework web.
Su único contrato es el bus. Un proceso registra **dos micro servicios sobre una sola conexión**:
`jiku-commands` (20 comandos de escritura) y `jiku-queries` (las consultas de esta story).

```
core/
├── src/
│   ├── index.ts                    # arranque: registra los DOS servicios sobre una conexión
│   ├── logger.ts
│   ├── config.ts
│   ├── authorize-caller.ts         # la compuerta compartida por los dos planos
│   ├── bus/
│   │   ├── consumer.ts
│   │   ├── host.ts                 # una conexión, N micro servicios
│   │   ├── service.ts              # registerService: un endpoint por patrón
│   │   └── dispatcher.ts           # despachador de COMANDOS (con transacción)
│   ├── commands/                   # los 20 comandos
│   ├── queries/                    # ← EL MÓDULO DE ESTA STORY
│   │   ├── index.ts                # el registro único de consultas
│   │   ├── registry.ts             # Map exacto: los patrones NO llevan {param}
│   │   ├── dispatcher.ts           # despachador de CONSULTAS (SIN transacción)
│   │   ├── caller-class.ts         # rol → clase (external/internal/connector)
│   │   ├── entity-type.ts          # la traducción de entityType, en UN lugar
│   │   ├── types.ts                # ResourceSpec y toda la gramática de la ficha
│   │   ├── pending.ts              # ← SE ELIMINA EN ESTA STORY
│   │   ├── engine/                 # el motor genérico: NO conoce ningún recurso
│   │   └── {recurso}/              # una carpeta por recurso: {r}-spec.ts + {r}-list.ts / {r}-get.ts
│   └── models/
│       ├── index.ts                # conexión del DUEÑO (escritura)
│       └── read.ts                 # conexión de SOLO LECTURA (consultas)
└── tests/
    ├── setup-env.ts                # levanta el PostgreSQL efímero ANTES de que Mocha cargue
    ├── global-setup.ts             # crea el esquema, trunca, apaga el contenedor al final
    ├── helpers/dispatch.ts         # dispatch() y dispatchQuery()
    ├── commands/
    └── queries/
```

**Las tres capas del plano de consultas:**

```
NATS ──> service.ts ──> QueryDispatcher ──> Query.validate ──> Query.execute ──> engine ──> readDb
                        (2 compuertas,       (nunca toca         (delega en
                         1 SELECT)            la base)            el motor)
```

**El despachador de consultas NO abre transacción**, y la ausencia es el contrato (RF-9). Contraste
deliberado con el de comandos (ADR-003).

**El despachador nunca lanza.** Todo error inesperado se traduce a un `Reply` de falla
(`core/src/queries/dispatcher.ts:164-171`). Del otro lado hay una request esperando.

#### Agregar una consulta son tres pasos

1. La ficha y el archivo del recurso bajo `src/queries/<recurso>/`
2. El registro en `src/queries/index.ts` (`registerAll([...])`)
3. Los tests en `tests/queries/`

**No hay que tocar `bus/`**: `registerService` crea un endpoint por patrón desde
`queryRegistry.patterns()`, así que sumar una línea al registro alcanza para que aparezca en
`nats micro info` con queue group y contadores propios.

### Relevant ADRs

#### ADR-001: Separación lectura / escritura

**Decisión:** la lectura y la escritura están separadas **por servicio y por credenciales**. `api`
conecta con un rol sin `INSERT`/`UPDATE`/`DELETE`; `core` conecta con el usuario dueño. El plano de
consultas usa `readDb`, una conexión **de solo lectura** con su propio pool y su propio
`statement_timeout`.

**Consecuencia para esta story:** los tres endpoints nuevos son **lecturas puras**. Ninguno escribe,
ninguno abre transacción, y `settings.list` **no vuelve administrable** a `system_settings`: la
escritura sigue siendo solo por SQL.

> `models/read.ts` **no registra los modelos a propósito**: dos instancias de Sequelize en el mismo
> proceso se pelean las clases de `@jiku/models` y la segunda las reasigna. Por eso el plano de
> consultas arma **SQL explícito** contra `ctx.db` y no usa el ORM.

#### ADR-004: El vocabulario del producto vive en el contrato

**Decisión:** el contrato del bus usa el vocabulario del **producto**; la base usa el que tiene;
`core` traduce en el borde.

**Implementation Rules (verbatim):**

- Un comando nuevo **DEBE** usar el vocabulario del producto en su contrato (`task`, no
  `objective`). La traducción a nombres de tabla vive **dentro** del comando.
- **NO SE DEBE** renombrar una tabla ni una columna existente para alinearla con el contrato. La
  base se cambia solo cuando hay una razón propia, no por vocabulario.
- Toda traducción contrato ↔ base **DEBE** vivir en `core`, en el comando o en un helper del
  módulo. **NO DEBE** filtrarse a `@jiku/models`, que describe la base tal como es.
- El contrato HTTP de la api **NO DEBE** cambiar de vocabulario sin coordinarlo con los dos
  frontends: es el contrato público del producto.
- `priorityValue` es un escape transitorio: **NO SE DEBE** replicar el patrón de mandar un campo
  paralelo para esquivar una traducción con pérdida. Cuando la web mande nombres de prioridad,
  el campo se elimina.
- Al agregar un valor a un enum del bus, **DEBE** verificarse que la traducción a la base sea
  biyectiva. Si no lo es, la traducción es el problema, no el enum.

**Es el ADR que decide H-1**: `hours-per-day` es el nombre del contrato, `hours_per_day` el de la
columna, y la traducción vive en la ficha de `settings`.

#### ADR-008: Autorización deny-by-default

**Decisión:** todo se deniega salvo lo declarado explícitamente. En el plano de consultas se
manifiesta en tres lugares: el mapa `ROLE_METHODS`, el mapa `CLASS_BY_ROLE`, y **las listas blancas
de cada ficha** (un nombre no declarado no existe).

**Implementation Rules (verbatim, del ADR — están escritas para la api pero el criterio es el que
gobierna esta story):**

- `validateToken` **DEBE** instalarse globalmente en `app.ts`. **NO SE DEBE** declarar
  autenticación ruta por ruta.
- Un endpoint público **DEBE** agregarse explícitamente a `api/lib/config/public.ts`. Cualquier
  cambio en ese archivo es un **cambio de seguridad** y debe revisarse como tal.
- Un endpoint público **DEBE** validar por su cuenta lo que corresponda. El caso vigente
  (`GET /api/opus/attachments/:id/public`) verifica que el adjunto esté marcado público, responde
  403 en cualquier otro caso, y manda `X-Content-Type-Options: nosniff` con CSP de sandbox.
- Un endpoint que requiere rol **DEBE** declarar `hasAnyRole([...])` explícitamente. La
  autenticación global no implica autorización.
- Un endpoint accesible a `external-user` **DEBE** además verificar permiso de proyecto: el rol
  solo no alcanza (ADR-006).
- Un tipo de entidad nuevo con adjuntos **DEBE** agregarse a la resolución de proyecto de
  `attachments-access.ts`. Un tipo no contemplado **no se autoriza**, que es el comportamiento
  correcto.
- Al leer un archivo de ruta, **NO SE DEBE** concluir que está desprotegido por no ver el
  middleware: la protección es global.

**Aplicación literal en esta story (CA-8, CA-9):** la lista blanca de `settings` es **cerrada**. Una
clave que exista en `system_settings` y no esté declarada **no existe para esta API**, y pedirla
explícitamente devuelve `items: []`, no un error. Es deny-by-default aplicado a datos de
configuración.

#### ADR-013: Tests contra base real

**Implementation Rules (verbatim):**

- Los tests de `api` y `core` **DEBEN** correr contra PostgreSQL real. **NO SE DEBEN** mockear los
  modelos de Sequelize.
- Los tests de comandos de `core` **DEBEN** entrar por el despachador (`dispatch()`), **NO** por
  `execute()` directamente.
- Un test de escritura de la api **DEBE** verificar las tres capas: comando publicado, traducción de
  la respuesta a HTTP, y que la fila quedó escrita. **NO SE DEBE** asertar solo el status HTTP.
- `reply()` / `failWith()` **DEBEN** usarse solo para cubrir caminos de error. El camino feliz
  **DEBE** ejecutar core de verdad.
- Cada archivo de test **DEBE** poder correr solo: el esquema y el mock de auth se preparan en
  fixtures globales de Mocha.
- `TZ=UTC` **DEBE** estar fijado en la configuración de test de todo servicio.
- La limpieza entre corridas **DEBE** ser `TRUNCATE ... RESTART IDENTITY CASCADE`, para que los ids
  autoincrementales sean predecibles.
- **NO SE DEBE** depender del orden de ejecución entre archivos de test.

**Para el plano de consultas el equivalente de `dispatch()` es `dispatchQuery()`** — CA-21 lo exige
literalmente: "los 23 endpoints tienen cobertura entrando **por el despachador**".

#### ADR-002: Comandos NATS sin JetStream — la regla del mapa de errores

**Lo que aplica acá** es la excepción ya declarada: los cinco códigos de REQ-006
(`unknown_caller`, `query_timeout`, `invalid_cursor`, `comment_not_found`, `task_not_found`) **no se
agregan** a `api/lib/utils/bus/protocol.ts`, porque al cerrar REQ-006 `bus.query()` sigue sin caller
y el mapa sería código muerto. Está escrito en
`packages/nats-protocol/src/index.ts:333-338`. **Esta story no cambia eso** y **no agrega ningún
código de error nuevo** (CA-20: los tres endpoints responden `invalid_fields`, que ya existe).

### API Context

#### El subject y el envelope

Patrón del subject de una consulta:

```
{instance}.{user-id}.jiku-queries.v1.{recurso}.{operación}
```

`methodFromSubject()` (`packages/nats-protocol/src/index.ts:152-154`) hace `slice(4)`, así que
`dev.api.jiku-queries.v1.tasks.list` resuelve al método `tasks.list`. El **caller sale del segundo
token del subject y solo de ahí** (RF-19).

Envelope de respuesta (compartido con los comandos, `Reply` de `@jiku/nats-protocol`):

```jsonc
// éxito
{ "status": "success", "data": { ... } }
// falla
{ "status": "failure", "errorCode": "invalid_fields", "errorMessage": "...", "errorDetails": { ... } }
```

#### La gramática del payload de `list` (la que los tres nuevos NO siguen del todo)

Palancas de primer nivel de un `list` (`core/src/queries/engine/validate-query.ts:34`):

```ts
const LIST_KEYS = ['filter', 'sort', 'page', 'fields', 'include', 'count'];
```

Palancas de un `get` (`:43`), más el discriminador si el recurso lo declara:

```ts
const GET_KEYS = ['id', 'fields', 'include'];
```

Límites de la gramática (`core/src/queries/engine/validate-query.ts:30-32`, `cursor.ts`,
`dispatcher.ts:20`):

| Constante | Valor | Nota |
|---|---|---|
| `DEFAULT_PAGE_LIMIT` | `50` | |
| `MAX_PAGE_LIMIT` | `200` | Un pedido mayor **se recorta sin avisar**: es `success`, no `failure` |
| `CURSOR_VERSION` | `1` | |
| `DEFAULT_PAYLOAD_BUDGET_BYTES` | `524288` | `floor(max_payload * 0.5)`, con 1 MiB por defecto |
| Tope de colecciones de `include` | `10` | Con `<relación>Truncated` como clave hermana |

**Los nombres de identidad están prohibidos en el payload** (`validate-query.ts:60-72`), lista
cerrada: `userId`, `user_id`, `user`, `caller`, `callerId`, `caller_id`, `sub`, `identity`, `actor`,
`principal`, `onBehalfOf`. Cualquiera de ellos es `invalid_fields`.

#### La forma de un error de validación

```ts
// core/src/queries/engine/validate-query.ts:81-83
function invalid(message: string, details: Record<string, unknown>): Invalid {
  return { error: failure(ErrorCode.INVALID_FIELDS, message, details) };
}
```

`errorDetails` lleva `{ field, value, allowed? }`, y **`allowed` es la lista de la ficha POR
REFERENCIA**, no una copia. Es la propiedad que hace que CA-12 sea verificable.

#### Las dos compuertas del despachador (S-017 + S-023)

`core/src/queries/dispatcher.ts:76-140`. Un solo `SELECT` sobre `users` alimenta a las dos:

1. **`authorizeWithRoles(caller, roles, method, 'queries')`** → "¿puede ejecutar este método?".
   Rechazo: `caller_not_authorized`.
2. **`resolveCallerClass(roles)`** → "¿qué le recorto?". Rechazo: `unknown_caller`.

**Los tres endpoints nuevos quedan autorizados sin tocar `ROLE_METHODS`**, y es intencional:
`admin`, `user` y `external-user` tienen `queries: ALL` (el sentinela `'*'`), y
`core/src/authorize-caller.ts` lo documenta explícitamente:

> *"`queries: ALL` PARA LOS TRES ROLES DE PRODUCTO, y lo autoriza el contrato: `docs/apis/core.yaml`
> dice 'the product roles get EVERY QUERY and no command'. La consecuencia —una consulta futura queda
> autorizada para esos tres sin tocar este mapa— ES la intención de 'todas las consultas'."*

**No hay que tocar `caller-class.ts` ni `authorize-caller.ts` en esta story.**

#### `docs/apis/core.yaml` — la nota que hay que actualizar (CA-16)

Texto vigente, en el `info.description` (líneas ~26-35):

> *"**One process, two logical services on the bus.** Since REQ-004 the `core` process registers
> **two NATS micro services over a single connection**: `jiku-commands`, the 20 write commands this
> spec describes, and `jiku-queries`, the read endpoints, with their own queue group and their own
> read-only connection to PostgreSQL. **The contract of `jiku-queries` is OUT OF SCOPE of this spec,
> and that is permanent** — this file stays the contract of the commands.*
>
> ***REQ-006 defines that contract: 23 endpoints over 18 resources**, and it gets **its own spec**,
> `docs/apis/core-queries.yaml` (AsyncAPI 2.6, same format, same "the document wins" rule), written
> by the last story of that requirement. **Until that story lands, the endpoints that have no
> resource sheet yet are registered and discoverable and answer a well-formed `failure`
> (`unknown_command`, "todavía no tiene contrato definido"); when it lands,
> `core/src/queries/pending.ts` is deleted and `nats micro info jiku-queries` lists 23 endpoints with
> contract.**"*

### Code Conventions

De `docs/architectures/core/conventions/` (todas **custom**, ninguna del catálogo):

#### `_base`
- `strict: true`, más `noUnusedLocals`, `noUnusedParameters`, `noImplicitReturns`.
- **Un archivo por comando** (y, por extensión, por consulta).
- **Imports relativos** dentro del servicio.
- **Los comentarios explican el POR QUÉ**, no el qué. El codebase de `queries/` lo lleva al extremo:
  cada decisión no obvia tiene un comentario que la justifica y dice qué pasaría si se hiciera al
  revés. **Seguir ese estilo**: es lo que hace legible una ficha de 300 líneas.

#### `bus-consumer`
- NATS request/reply con queue group; inbox hasheado; drain al cerrar.
- **No tocar en esta story.**

#### `validation`
- **Joi por comando, un esquema por archivo.**
- La validación corre **antes** de tocar la base. En el plano de consultas eso lo garantiza el
  despachador: `query.validate(raw)` va antes de `query.execute(...)`.
- **Un enum literal se desincroniza en silencio**: derivar de una constante compartida cuando exista
  (así lo hace `tasks-spec.ts:55` con `TASK_PRIORITY_VALUES`).

#### `error-handling`
- `Reply` de falla, catálogo de códigos compartido, **el despachador nunca lanza**.
- Un timeout de base es un **valor de retorno**, no una excepción.

#### `orm`
- Sequelize con el usuario dueño; modelos en el paquete compartido.
- **Excepción vigente del plano de consultas:** no usa el ORM; arma SQL explícito contra `ctx.db`.

#### `contract-translation` (la que CA-19 obliga a modificar)

Las **cuatro traducciones de escritura** que ya declara:

| Contrato / bus | Base de datos | Dónde traduce |
|---|---|---|
| `task`, `taskId` | `objectives`, `objective_id` | en cada comando de `tasks` y `times` |
| `properties: [{code, value}]` | `key_value_pairs: {code: value}` | `projects/properties.ts:51` |
| `priority: 'alta'` (enum) | `priority: 3` (integer) | `tasks/priority.ts:43` |
| `responsiblePersonIds` | `personIds` | en cada comando de `tasks` y `requirements` |

**Reglas (verbatim):**

- La base no se toca para acomodar un nombre del contrato. Core traduce.
- Una traducción vive en un helper del módulo, no repetida en cada comando.
- Los helpers de traducción devuelven `undefined` para un campo ausente, nunca un valor vacío.
- Un campo cuyo nombre difiere entre el bus y la base **no puede ir por `pickPresent`**: se agrega a
  mano al objeto de cambios, con `hasOwnProperty`.
- No renombres los modelos de `@jiku/models`: los comparte `api`.
- Toda traducción está documentada en `docs/apis/core.yaml`.
- No construyas nada nuevo sobre `priorityValue`: es un escape con fecha de vencimiento.
- Un campo nuevo usa el mismo nombre en las dos puntas salvo que haya una razón que se pueda
  escribir en una línea.

**Las traducciones de SOLO LECTURA que la Tarea 7 tiene que agregar** (CA-19), todas ya existentes

#### `testing`

**Reglas (verbatim):**

- Un comando nuevo lleva sus tests en el mismo cambio.
- Los tests entran por `dispatch()`, **nunca** llamando a `execute` directamente.
- No mockees Sequelize ni la base. La base real es el punto.
- Un archivo de test por módulo de dominio, en `tests/commands/{módulo}.test.ts`.
- Los fixtures se crean en el `before` del propio archivo.
- Todo comando cubre: camino feliz, cada campo requerido faltante, un campo desconocido, y la
  entidad del subject inexistente.
- Todo comando de edición cubre la semántica parcial completa: ausente, con valor, `null`, y `null`
  en obligatorio.
- Toda regla de negocio tiene un test con su código de error.
- Si un comando puede fallar después de escribir, hay un test que verifica que **no quedó nada**.
- No dependas de la zona horaria local: `TZ=UTC` está fijado.
- No dejes datos entre archivos: el truncado es al arrancar la corrida, no entre tests.

**Las tres formas del conjunto base** (`BaseSpec`):

```ts
export type BaseSpec = BaseFieldSpec | BaseConstantSpec | RelationSpec;
// BaseFieldSpec   -> { column, from?, transform? }
// BaseConstantSpec-> { constant }
// RelationSpec    -> OneRelationSpec | ManyRelationSpec, ambas con kind: 'relation'
```

**Las tres formas de incluible** (`IncludableSpec`):

```ts
export type IncludableSpec = IncludableFieldSpec | IncludableComputedSpec | RelationSpec;
// IncludableFieldSpec    -> { kind: 'field', column, ... }
// IncludableComputedSpec -> { kind: 'computed', expr, transform? }
// RelationSpec           -> { kind: 'relation', cardinality: 'one' | 'many', ... }
```

**`ManyRelationSpec` lleva el tope de la colección**, que CA-10 exige exponer:

```ts
readonly cap?: number;             // tope por item. Con más elementos, se marca truncatedFlag
readonly truncatedFlag?: string;   // clave HERMANA: 'commentsTruncated', no un campo anidado
```

Hoy solo dos fichas lo declaran, las dos con `cap: 10`:
- `tasks-spec.ts:155-156` → `cap: 10`, `truncatedFlag: 'commentsTruncated'`
- `requirements-spec.ts:159-160` → `cap: 10`, `truncatedFlag: 'commentsTruncated'`

**`ExternalScopeSpec` — las seis formas del recorte**, todas relevantes para lo que `meta.describe`
podría (o no) exponer:

```ts
export type ExternalScopeSpec =
  | ColumnExternalScope        // la fila LLEVA el proyecto
  | ExistsExternalScope        // la fila es ALCANZABLE desde una tabla que lo lleva
  | OwnerExternalScope         // la fila ES del caller
  | NoneExternalScope          // SIN ACCESO: vacía el conjunto, cero SQL
  | PolymorphicExternalScope   // el tipo de la fila decide qué tabla mirar
  | BridgeExternalScope;       // visible por sus filas puente vivas
```

> **`externalScope` NO se expone en `meta.describe`.** Todos sus nombres son **columnas de la base**
> (`project_id`, `visibility_level`, `user_id`), y publicarlos filtraría el esquema por un endpoint
> que describe el contrato. CA-10 enumera qué devuelve —`base`, `includable`, `filterable`,
> `sortable`, `defaults` y los enums— y `externalScope` **no está en la lista**. Ver la Tarea 4.

### Task 2: `requirements.tags` — el agregado con forma propia

**Status:** Completed

#### Description

El endpoint 21 del contrato: los pares `{key, values[]}` que **ya existen** en los requisitos de un
proyecto, agrupados por clave, para el selector de tags de la pantalla de requisitos.

**Es el único agregado del contrato** y una excepción declarada a "las agregaciones quedan fuera de
la v1" (RF-37): existe porque no hay forma de derivarlo desde `requirements.list` sin traer **todos**
los requisitos del proyecto.

**No entra en el molde del motor.** `runList` devuelve filas proyectadas con keyset y cursor; esto
**colapsa filas** y devuelve una lista sin paginar. Arma su propio SQL — pero **sobre las mismas
piezas**: el recorte externo de la ficha de `requirements`, la constante `PERMITTED_PROJECTS`, y
`selectRows` para que el `statement_timeout` siga siendo `query_timeout`.

#### Acceptance Criteria

1. `requirements.tags` está registrado y responde por el bus.
2. `filter.projectId` es **obligatorio**; su ausencia es `invalid_fields` con
   `errorDetails.field = 'filter.projectId'`.
3. `filter.key` es **opcional** y filtra por **coincidencia parcial**, case-insensitive.
4. La respuesta es `{ items: [{ key, values }] }`, agrupada por clave, **sin valores duplicados**.
5. El recorte del modo externo se aplica **antes** del filtro y usa el recorte **completo** de la
   ficha de `requirements` (proyectos permitidos **y** `visibility_level = 'public'`).
6. Un caller externo sin permiso recibe `items: []`, **no un error**.
7. Un proyecto sin tags recibe `items: []`, **no un `*_not_found`**.
8. Una palanca o un nombre no declarados son `invalid_fields` con `errorDetails`.
9. Un `statement_timeout` responde `query_timeout`.
10. Ningún nombre del payload llega concatenado al SQL.
11. El endpoint **no** emite ningún `*_not_found` (CA-20).

#### Technical Details

**Architectural Context References:**
- **ADR-001** — lectura pura sobre `readDb`, sin transacción, sin ORM.
- **ADR-008** — deny-by-default: `filter` acepta **exactamente** `projectId` y `key`.
- **ADR-013** — tests contra base real, entrando por `dispatchQuery()`.
- **Database Context → `requirements.tags`**: la columna `jsonb` NULL-able y el índice
  `idx_requirements_tags_gin` de S-021.
- **Database Context → el recorte externo de `requirements`**: `ColumnExternalScope` con
  `projectColumn: 'project_id'` y `visibility: { column: 'visibility_level', value: 'public' }`.
- **Reusable Code → el motor:** `selectRows` (**obligatorio**), `PERMITTED_PROJECTS`,
  `deniesAllRows` (no aplica: `requirements` no es `none`), el tipo `Query`.

**Files to Create/Modify:**
- `src/queries/requirements/requirements-tags.ts` — **nuevo**: `validate` + `execute`
- `src/queries/requirements/requirements-tags-sql.ts` — **nuevo** (opcional): el armado del SQL, si
  el archivo del recurso queda largo
- `src/queries/index.ts` — registrar `requirementsTags` **después** de `requirementsGet`
- `tests/queries/requirements-tags.test.ts` — **nuevo**: TS-8..TS-30
- `tests/queries/domain-fixtures.ts` — extender con requisitos de tags variados si hace falta

**Implementation Notes:**

- **La forma del SQL.** Desanidar el `jsonb` y agrupar:

  ```sql
  SELECT tag->>'key' AS key, ARRAY_AGG(DISTINCT tag->>'value') AS values
  FROM requirements t
  CROSS JOIN LATERAL jsonb_array_elements(t.tags) AS tag
  WHERE t.project_id = :projectId
    AND jsonb_typeof(t.tags) = 'array'
    -- + el recorte externo, cuando la clase es external
    -- + AND tag->>'key' ILIKE :keyPattern, cuando vino filter.key
  GROUP BY tag->>'key'
  ORDER BY tag->>'key'
  ```

- **`jsonb_typeof(t.tags) = 'array'` NO es defensivo de más.** `jsonb_array_elements` **lanza** sobre
  un `jsonb` que no sea array, y la columna no tiene CHECK. Un `{}` escrito a mano por SQL —el mismo
  camino por el que se administran los `system_settings`— haría fallar el endpoint entero con
  `internal_error` para **todo** el proyecto. `NULL` no necesita guarda (`LATERAL` sobre `NULL` no
  produce filas), pero un objeto sí.

- **El recorte externo va en el `WHERE`, junto al `project_id`, y solo para `ctx.callerClass ===
  'external'`.** La forma exacta, tomada de la ficha:

  ```sql
  AND t.project_id IN (SELECT project_id FROM user_project_permissions WHERE user_id = :caller)
  AND t.visibility_level = 'public'
  ```

  > **No reimplementar `PERMITTED_PROJECTS` a mano**: importarla de `engine/build-sql.ts` o exportarla
  > desde ahí. Dos copias de la subconsulta de permisos es exactamente el tipo de divergencia que se
  > descubre en producción.

  > **La visibilidad va aunque CA-6 no la nombre.** Ver la nota de "Database Context → El recorte
  > externo de `requirements`": sin ella, los tags de un requisito interno se filtran por un endpoint
  > que "solo devuelve claves y valores".

- **El recorte se aplica ANTES del filtro** en el sentido que importa: van los dos en el mismo
  `WHERE` con `AND`, y **el del payload no puede desactivar al del recorte**. `filter.key` es un
  `ILIKE` sobre `tag->>'key'`, que se aplica a lo que quedó.

- **`filter.projectId` obligatorio es lo que evita el barrido.** Validarlo en `validate`, **antes** de
  tocar la base, con el mismo `invalid()` del resto del motor —`ErrorCode.INVALID_FIELDS` con
  `errorDetails: { field: 'filter.projectId', ... }`.

- **La coincidencia parcial:** `tag->>'key' ILIKE :keyPattern` con
  `replacements: { keyPattern: '%' + key + '%' }`. **El `%` se arma en JS, no en el SQL**, y el valor
  viaja por `replacements`. Escapar `%` y `_` del texto del usuario si se quiere que sean literales
  —decisión menor, pero hay que tomarla y comentarla.

- **`ARRAY_AGG(DISTINCT ...)` resuelve TS-14** sin código. El orden dentro de `values` conviene
  fijarlo (`ORDER BY` dentro del agregado) para que el test sea determinista.

- **La forma de la respuesta NO lleva `page`.** No es un `list` paginado: `{ items: [...] }` y nada
  más, tal como lo escribe la story y `bus-api-consultas-ref.md:456-461`. **No agregar `page` "por
  simetría"**: prometería un cursor que no existe.

- **La validación acepta exactamente una palanca de primer nivel: `filter`.** `sort`, `page`,
  `fields`, `include` y `count` son `invalid_fields`. **Y las claves de identidad también** — reusar
  la lista `IDENTITY_PAYLOAD_FIELDS` de `engine/validate-query.ts`, no reescribirla.

- **Ejecutar con `selectRows(ctx, plan, 'requirements.tags')`.** Es lo que traduce el código PG
  `57014` a `query_timeout`.

El endpoint 22: una lista blanca **cerrada** de claves de `system_settings`, no la tabla. Una clave

**Architectural Context References:**

**Files to Create/Modify:**

**Implementation Notes:**

- **La lista blanca se declara con `ResourceSpec.where`**, que es exactamente el mecanismo que el
  tipo describe: *"EL PREDICADO FIJO DEL RECURSO. Sale de la ficha, JAMÁS del payload… Se emite en

  > escaparse — la misma regla que ya gobierna `ManyRelationSpec.where` e

  ```ts
  const KEY_TO_CONTRACT: Record<string, string> = { hours_per_day: 'hours-per-day' };
  const KEY_TO_DB: Record<string, string> = { 'hours-per-day': 'hours_per_day' };

  base: {
    id:    { column: 'id' },
    key:   { column: 'key', transform: (raw) => KEY_TO_CONTRACT[raw] ?? raw },
    value: { column: 'value' },
  },
  ```

     `readonly values?: Readonly<Record<string, readonly unknown[]>>`, "los valores que acepta y a
     qué se traducen". **Verificar en `engine/validate-query.ts` cómo lo consume**: si mapea valor
     del contrato → valores de la base, resuelve H-1 sin tocar el motor y es la opción correcta.
  2. Si `values` no sirve para esto, **agregar un `transform` de entrada a `FilterableSpec`**, con la
     misma forma que el de `BaseFieldSpec`. Es un cambio del motor, chico y genérico, y **no** puede
     nombrar `settings` (TS-87).

  > **Lo que NO hay que hacer:** resolver la traducción en `settings-list.ts` reescribiendo el
  > payload antes de `validateList`. Sacaría la traducción de la ficha —o sea, fuera de lo que
  > `meta.describe` proyecta— y CA-12 dejaría de ser verificable para este recurso.

- **`value` siempre string:** la columna es `TEXT` y el driver la devuelve como string. **No agregar
  un `transform` que parsee números**: la ficha declara `value` como string y `file-allowed-mime-types`
  es una lista separada por comas, no un número. TS-43 lo fija.

- **El recorte:**

  ```ts
  const EXTERNAL_SCOPE: ExternalScopeSpec = { kind: 'none' };
  ```

- **`sortable` y el keyset.** El default es `["key"]`. El motor agrega `id` como último criterio de
  desempate; la tabla tiene `id`, así que funciona. **Declarar `id` en `sortable`** si se quiere que
  el desempate no se agregue dos veces — mirar cómo lo resolvió `requirements-spec.ts:262-263`, que

- **`includable` vacío es el contrato** (CA-7: "include · ninguno"). `includableNames: []` y

- **`truncatable: []`** — `value` puede ser largo (`file-allowed-mime-types` supera 255 caracteres),

- **Sin `notFoundCode` ni `notFoundMessage`**: `settings` no tiene `get` (CA-20, TS-47).

### Task 4: `meta.describe` — la descripción derivada

**Status:** Completed

#### Description

El endpoint 23 y el que le da sentido a la decisión de S-022 —la ficha como **dato**—: devuelve **el
contrato en datos**, proyectando las mismas estructuras que el validador usa para rechazar nombres.

**Derivado, no mantenido** (CA-12). Es la diferencia entre una descripción que puede mentir y una que
no: si `meta.describe` declara un `sortable`, ordenar por él **no** puede responder `invalid_fields`;
y un nombre que no declara **sí** tiene que responderlo. Es una **propiedad**, y se testea recorriendo
la descripción entera (TS-62..TS-68).

**No toca la base.** Es la consulta más barata del contrato y la única que no depende de PostgreSQL.

**Es igual para todos los callers** (CA-14) y eso es correcto: describe el **contrato**, no los datos.

#### Acceptance Criteria

1. `meta.describe` está registrado y responde por el bus.
2. `resources` es **opcional**; cada nombre tiene que ser uno de los recursos con ficha.
3. Sin `resources`, describe **todos** los recursos con ficha (16 — ver H-2).
4. Por recurso devuelve `base`, `includable`, `filterable`, `sortable`, `defaults` y `enums`.
5. Cada incluible declara `kind` (`field` / `relation` / `computed`) y, si es colección con tope, el
   `cap` y su `truncatedFlag`.
6. Los enums vienen **con etiquetas**; los nueve de `unworked-times.reason` coinciden con los de
   `GET /unworked-times/reasons`.
7. **CA-12 verificado como propiedad**: todo nombre declarado en `sortable` / `filterable` /
   `includable` funciona, y uno no declarado responde `invalid_fields`.
8. La respuesta es **byte a byte idéntica** para un caller externo y uno interno.
9. **No expone** `externalScope`, `where`, `table` ni `joins`, ni ningún nombre de columna.
10. **Cero** consultas a la base.
11. Un recurso inexistente es `invalid_fields`; nunca un `*_not_found`.
12. La respuesta completa entra en el presupuesto de bytes.

#### Technical Details

**Architectural Context References:**
- **ADR-004** — la descripción habla en vocabulario del **contrato**. Un nombre de columna en la
  respuesta es un bug (TS-73).
- **ADR-008** — lo que la descripción declara es exactamente lo que las listas blancas permiten.

  `isRelation`.
- **API Context → los límites de la gramática:** `DEFAULT_PAGE_LIMIT` (50) y `MAX_PAGE_LIMIT` (200)
  para `defaults`.

**Implementation Notes:**

- **`src/queries/resources.ts` es la pieza estructural de la tarea.** Hoy no hay ningún lugar que

  > **Ojo con el gate de genericidad (TS-87/TS-88):** `resources.ts` vive en `src/queries/`, **no**
  > en `src/queries/engine/`. El gate prohíbe que el **motor** nombre recursos; el registro de
  > recursos es exactamente el archivo cuyo trabajo es nombrarlos, igual que `index.ts`.

- **La proyección va en su propio archivo y NO conoce ningún recurso.** `describe-spec.ts` recibe una
  `ResourceSpec` y devuelve la descripción. Es el mismo criterio con que `engine/spec.ts` no nombra
  recursos, y es lo que hace que agregar el recurso 17 no toque esta tarea.

- **La forma de la respuesta**, derivada de CA-10:

  ```jsonc
  {
    "status": "success",
    "data": {
      "resources": {
        "tasks": {
          "base":       { "id": { "kind": "field" }, "title": { "kind": "field" }, ... },
          "includable": { "description": { "kind": "field" },
                          "comments": { "kind": "relation", "cardinality": "many",
                                        "cap": 10, "truncatedFlag": "commentsTruncated" } },
          "filterable": { "state": { "kind": "enum", "enum": "state" }, ... },
          "sortable":   ["title", "createdAt", ...],
          "defaults":   { "sort": ["-createdAt"], "limit": 50 },
          "enums":      { "state": [ { "value": "backlog", "label": "backlog" }, ... ] }
        }
      }
    }
  }
  ```

  **El orden de las claves importa** y sale de `Object.keys` de la ficha: es el mismo orden que viaja
  en `errorDetails.allowed`, y TS-63/TS-65 comparan **listas**, no conjuntos.

- **Qué se proyecta y qué NO, de cada forma de spec:**

  | Origen | Se expone | **No** se expone |
  |---|---|---|
  | `BaseFieldSpec` | el nombre, `kind: 'field'` | `column`, `from`, `transform` |
  | `BaseConstantSpec` | el nombre, `kind: 'field'` (o `'constant'`) | el valor de `constant` si revela algo del esquema — decidir y comentar |
  | `IncludableComputedSpec` | el nombre, `kind: 'computed'` | **`expr`** (es SQL crudo) |
  | `OneRelationSpec` | `kind: 'relation'`, `cardinality: 'one'`, los **nombres** de `fields` | `table`, `localKey`, `targetKey` |
  | `ManyRelationSpec` | `kind: 'relation'`, `cardinality: 'many'`, nombres de `fields`, **`cap`**, **`truncatedFlag`** | `table`, `parentKey`, `join`, `where`, `order`, `scalar` |
  | `FilterableSpec` | el nombre, `kind`, el nombre del `enum`, si admite `search` / `contains` | `column`, `from`, `via`, las columnas de `search`, `searchNumericColumn`, la `column` de `contains` |
  | `SortableSpec` | el nombre | `column`, `nullable` |
  | `ExternalScopeSpec` | **nada** | **todo** |
  | `ResourceSpec.where` / `.table` / `.joins` | **nada** | **todo** |

  > **TS-73 es el test que hace cumplir esta tabla**, y es más confiable que revisarla a mano:
  > serializa la respuesta entera y busca los nombres de tabla y columna reales.

- **El recurso con discriminador (`comments`, `activity`, `subscriptions`).** Su ficha **no está
  completa** hasta que se resuelve la variante: `activity.enums.type` se pisa por variante
  (`activity-spec.ts:113`) y `filterable.entityId` apunta a una columna distinta en cada una.
  **Describir la unión sería mentir** — declararía un `type` que en la mitad de las variantes es
  `invalid_fields`, que es exactamente lo que CA-12 prohíbe.

  **Forma recomendada:** declarar el discriminador y describir **por variante**:

  ```jsonc
  "activity": {
    "discriminator": { "field": "entityType", "values": ["task", "requirement"] },
    "variants": {
      "task":        { "base": {...}, "filterable": {...}, "enums": { "type": [...] }, ... },
      "requirement": { ... }
    },
    "sortable": [...], "defaults": {...}      // los que NO dependen de la variante
  }
  ```

  Usar `resolveVariant(spec, value)` para armar cada una: es la función que ya produce la ficha
  **efectiva**, y hace que la descripción y el validador vuelvan a leer literalmente lo mismo.
  `sortable`, `defaults`, `truncatable` y el par `notFound*` **no** se pueden pisar por variante
  (`ResourceVariant` no los declara), así que van al nivel del recurso.

- **`defaults.limit`** es `DEFAULT_PAGE_LIMIT` (50), y conviene exponer también el tope
  `MAX_PAGE_LIMIT` (200) — es información del contrato que hoy no está en ninguna respuesta y que un
  consumidor necesita para no pedir 500 y recibir 200 en silencio. **Decidir y documentarlo en
  `core-queries.yaml`.**

- **Las etiquetas con fallback:** `label = value` cuando la ficha no la declara (TS-5). Un `label:
  undefined` en la respuesta sería peor que el valor crudo: obligaría a cada consumidor a manejar el
  caso.

- **La validación de `meta.describe` es propia y corta:** una sola palanca de primer nivel
  (`resources`), array de strings, opcional. Reusar `IDENTITY_PAYLOAD_FIELDS`. `resources: []` es
  `invalid_fields` (TS-60): un array vacío no es "todos", y aceptarlo silenciosamente devolvería 16
  recursos a quien pidió cero.

- **CA-12 se testea recorriendo, no enumerando** (TS-62..TS-68). Es un test que **crece solo** con
  cada recurso nuevo, y es el más valioso del REQ entero. Necesita, por recurso, saber cuáles son las
  palancas obligatorias (`entityType` en los tres de S-025, `projectId` en `requirements.tags`); un
  mapa chico de payloads mínimos por recurso, como el que ya usa `pending.test.ts:70-76`, alcanza.

- **`meta.describe` no pasa por `deniesAllRows` ni por ningún recorte.** No lee filas. CA-14 sale
  gratis si `execute` **ignora `ctx.callerClass`** — y TS-70 lo verifica comparando dos respuestas
