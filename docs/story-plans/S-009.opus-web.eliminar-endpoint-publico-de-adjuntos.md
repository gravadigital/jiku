# Story Plan: S-009 (opus-web) - Eliminar el endpoint público de adjuntos

## Status

**Status:** Completed

## Story Reference

- **Story:** [S-009](../stories/S-009.eliminar-endpoint-publico-de-adjuntos.md)
- **Service:** `opus-web`
- **Summary:** `opus-web` elimina la ruta `GET /attachments/{id}/{fileName}` —el único route handler
  sin sesión del producto y el único constructor de la URL del endpoint público de la `api`— borrando
  el árbol `src/app/attachments/` completo, y saca `attachments` del matcher del middleware. Los dos
  cambios son **un solo cambio atómico**: con la ruta borrada y la excepción viva, `/attachments/*`
  quedaría fuera del guard sirviendo el 404 de Next sin sesión; con la excepción cerrada y la ruta
  viva, el handler exigiría sesión para llamar a un endpoint público. El camino autenticado de
  lectura de adjuntos —`/api/attachments/{id}/preview`, `/api/files/{id}/preview` y el proxy
  catch-all— **no se toca ni una línea**.

> **Esta story tiene dos Story Plans y este es el de `opus-web`.** El lado de la `api` —borrar el
> handler `publicPreviewOpusAttachment` y vaciar `config/public.ts`— vive en
> [`S-009.api.eliminar-endpoint-publico-de-adjuntos.md`](S-009.api.eliminar-endpoint-publico-de-adjuntos.md)
> y **ya está `Completed`** (verificado contra el código: `api/config/public.ts` tiene las cuatro
> listas vacías y `api/lib/routes/opus-attachments-preview.ts` declara solo `router.get('/opus/attachments/:id/preview', ...)`).
>
> **Qué implica para este plan:** la `api` ya devuelve **401** a `GET /api/opus/attachments/{id}/public`
> sin token. O sea que **hoy mismo, antes de implementar esto, el handler de `opus-web` que vamos a
> borrar ya está roto**: llama a un endpoint que responde 401 y devuelve una página en blanco. Es
> exactamente la ventana de deploy que la story describe como aceptable ("desplegar `api` primero o
> junto. Nunca `opus-web` primero"), y el estado actual del repo está del lado correcto de esa
> ventana. **No hay que apurar nada, pero tampoco hay razón para no cerrarlo:** RF-5 ya se cumple,
> y lo que falta es CA-1 (el redirect a `/login`) y CA-2 (el 404 con sesión).

**Patrón de guard:** la protección es **por defecto y por exclusión**. Una página nueva queda
protegida sin registrarla en ningún lado; lo que hay que registrar es lo que queda **fuera**, y eso
es un regex. Es lo contrario de `web`, donde el guard está en el layout de `(loggedin)/`.

**Estrategia de errores:** `ApiError` normalizado por el interceptor de `lib/axios.ts`; los route
handlers responden `{code, message}`. **Ninguno de los dos aplica a esta story**: no se toca ningún
handler que quede.

#### Convención `auth` — el guard y su matcher

```ts
// src/middleware.ts:25-47 — ESTADO ACTUAL, verbatim del código
export default async function middleware(request: NextRequest) {
  // `auth` está sobrecargada en v5: sirve como wrapper de middleware y como getter de
  // sesión. Acá se usa la segunda forma, así que se acota el tipo.
  const session = (await (auth as unknown as () => Promise<Session | null>)()) ?? null;
  const isValid = isSessionValid(session);
  const isLoginPage = request.nextUrl.pathname === '/login';

  // Autenticado en /login → redirigir a inicio
  if (isValid && isLoginPage) {
    return NextResponse.redirect(new URL('/', request.url));
  }

  // No autenticado fuera de /login → redirigir a login
  if (!isValid && !isLoginPage) {
    return NextResponse.redirect(new URL('/login', request.url));
  }

  return NextResponse.next();
}

export const config = {
  matcher: '/((?!api|attachments|_next/static|_next/image|favicon.ico).*)',
};
```

```ts
// src/middleware.ts:14-23 — la validación NO es solo "hay cookie", verbatim
function isSessionValid(session: Session | null): boolean {
  if (!session?.user?.id) {
    return false;
  }
  const expiresAt = (session as { expiresAt?: number }).expiresAt;
  if (typeof expiresAt === 'number' && expiresAt > 0 && expiresAt <= Date.now()) {
    return false;
  }
  return true;
}
```

Lo excluido del matcher **hoy**, y por qué (tabla de la convención `auth`):

| Exclusión | Motivo |
|---|---|
| `api` | Los route handlers manejan su propia auth. Si pasaran por el middleware, un 401 se convertiría en un redirect a `/login` — inútil para una llamada de axios |
| `attachments` | El handler de descarga pública es intencionalmente sin sesión. **Es lo que esta story elimina** |
| `_next/static`, `_next/image`, `favicon.ico` | Estáticos |

**Reglas enforceables de la convención `auth` que aplican directo a esta story:**

- *"Agregar una ruta pública implica editar ese regex. Y **sacar algo del matcher significa que no
  tiene sesión**, no solo que no redirige."* — leída al revés, es la regla de esta story: **meter algo
  de vuelta al matcher significa que sí exige sesión.**
- *"**No sacar una ruta del matcher** sin entender que queda sin sesión."*
- *"No usar `getToken()` de `next-auth/jwt`: en v5 está explícitamente desaconsejado."*
- *"No agregar un guard por rol en un layout sin decidir antes si el portal debe cortar navegación —
  hoy, a propósito, no lo hace."* — **esta story no cambia eso.** El guard sigue siendo binario
  (sesión / no sesión), sin corte por rol.
- El cast de `auth` en `middleware.ts:26-28` **no es un cast al azar: es acotar una sobrecarga de
  v5**, y está comentado en el código. **No tocarlo.**

#### Convención `api-routes` — qué handler se borra y qué handlers quedan

El criterio del servicio es **un catch-all cubre toda la api**, y los handlers específicos son la
excepción. Los cuatro que existen hoy:

| Handler | Sesión | Estado tras esta story |
|---|---|---|
| `GET\|POST\|PATCH\|PUT\|DELETE /api/opus/[...path]` (catch-all) | **sí** | **Sin cambios** |
| `GET /api/attachments/[id]/preview` | **sí** | **Sin cambios** — es el camino de CA-5 y CA-6 |
| `GET\|HEAD /api/files/[id]/preview` | **sí** | **Sin cambios** — camino E, lectura por `fileId` |
| `GET\|POST /api/auth/[...nextauth]` | n/a | **Sin cambios** |
| `GET /attachments/[id]/[fileName]` | **NO** | **ELIMINADO** |

El handler a borrar, verbatim y completo (`src/app/attachments/[id]/[fileName]/route.ts`, 50 líneas —
**es el único archivo del árbol**):

```ts
import { NextRequest, NextResponse } from 'next/server';

/**
 * Camino público de descarga, sin sesión. DEPRECADO: sobrevive para los ids ya emitidos.
 *
 * Es la única ruta exenta de autenticación: la autorización la decide la api, que valida
 * `visibilityLevel === 'public'`. Está fuera del matcher del middleware a propósito.
 *
 * Desde S-005 la api responde 302 a una URL prefirmada: este handler devuelve esa
 * redirección en vez de proxear el binario.
 */
const API_URL = () => process.env.API_URL ?? '';

export async function GET(
  _req: NextRequest,
  { params }: { params: Promise<{ id: string; fileName: string }> }
) {
  // El `fileName` de la URL es cosmético: la api resuelve el objeto por el id.
  const { id } = await params;

  const base = API_URL();
  if (!base) {
    return NextResponse.json(
      { code: 'server_misconfigured', message: 'API_URL is not set' },
      { status: 500 }
    );
  }

  const target = new URL(
    `api/opus/attachments/${id}/public`,
    base.endsWith('/') ? base : `${base}/`
  );

  // `redirect: 'manual'` por el mismo motivo que el handler autenticado: sin esto el byte
  // volvería a pasar por el proceso de Next.
  const response = await fetch(target, { redirect: 'manual' });

  if (response.status >= 300 && response.status < 400) {
    const headers: Record<string, string> = {
      Location: response.headers.get('Location') ?? '',
    };
    const contentType = response.headers.get('Content-Type');
    if (contentType) headers['Content-Type'] = contentType;
    const disposition = response.headers.get('Content-Disposition');
    if (disposition) headers['Content-Disposition'] = disposition;
    return new NextResponse(null, { status: response.status, headers });
  }

  return new NextResponse(null, { status: response.status });
}
```

**Es el único constructor de la URL del endpoint público en todo el producto** (`route.ts:29-32`).
Verificado por búsqueda: `attachments/${id}/public` aparece **solo acá** en `opus-web/src`.

**Reglas enforceables de la convención `api-routes` que aplican:**

- *"En `opus-web`, toda llamada **DEBE** ir por el proxy `/api/opus/[...path]`."* El handler que se
  borra era la excepción; al borrarlo, la regla queda sin excepciones.
- *"**No sacar una ruta del matcher del middleware** sin entender que queda sin sesión."*
- *"No inventar un formato de error nuevo: `{code, message}`."* — no aplica a código nuevo acá (esta
  story no crea handlers), pero sí a no romper los que quedan.

### Relevant ADRs

#### ADR-009: El token confinado al servidor

**Decisión:** el access token nunca llega al navegador. En `opus-web` el axios es de navegador y lo
que se queda en el servidor es el destino: el cliente pide a su propio origen y un route handler
catch-all reenvía agregando el token.

**Implementation Rules (copia completa, verbatim):**

- El access token **NO DEBE** llegar al navegador por ningún camino: ni en el bundle, ni en una
  respuesta, ni en una cookie legible por JS.
- La URL de la api **DEBE** leerse de `API_URL` **en el servidor, en runtime**. **NO SE DEBE** usar
  `NEXT_PUBLIC_API_URL` ni ninguna variable horneada en build.
- En `web`, toda llamada de dominio **DEBE** ir por un Server Action (`'use server'`) con `apiClient`.
  Un route handler en `app/api/` **DEBE** justificarse por una capacidad que el Server Action no tenga
  (streaming, headers de respuesta, llamada desde componente cliente).
- En `opus-web`, toda llamada **DEBE** ir por el proxy `/api/opus/[...path]`. **NO SE DEBE** agregar un
  cliente axios que apunte directo a `API_URL` desde el navegador.
- Todo route handler que reenvíe a la api **DEBE** exigir sesión y responder
  `401 {"error":"Unauthorized"}` si no hay `accessToken`. **La única excepción vigente es
  `GET /attachments/[id]/[fileName]` de `opus-web`, cuya autorización la decide la api.**
- Al reenviar respuestas binarias, **DEBEN** propagarse `Content-Type`, `Content-Disposition` y
  `Content-Length`.
- Al reenviar uploads **DEBE** usarse streaming con `duplex: 'half'`, no bufferizar el archivo entero
  en memoria.
- Un 401 de la api **DEBE** redirigir el navegador a `/login`.
- **NO SE DEBE** agregar `NEXT_PUBLIC_*` funcional: rompería la premisa de una imagen por todos los
  entornos.

> **La quinta regla es la que esta story hace verdadera sin excepción.** Al borrar el handler, *"la
> única excepción vigente"* deja de existir y la regla queda absoluta: **todo route handler exige
> sesión**. El ADR sigue diciendo que hay una excepción y **eso queda desactualizado a propósito**:
> corregirlo se tramita por `/product-change-technical-definition` (ver *Cambios de definiciones
> técnicas que NO van en esta story* en la story). **No editar el ADR desde este plan.**

#### ADR-008: Autorización deny-by-default por path, no por ruta

**Decisión:** en la `api`, `validateToken` se instala globalmente para todo path y las excepciones son
una lista explícita (`api/config/public.ts`). Resultado: deny-by-default.

**Relevancia para `opus-web`:** el matcher del middleware es **la misma idea aplicada al frontend** —
protección global por exclusión, con las excepciones enumeradas en un regex. Y hay una regla del ADR
que esta story satisface del lado de `opus-web`:

- *"Un endpoint público **DEBE** validar por su cuenta lo que corresponda. El caso vigente
  (`GET /api/opus/attachments/:id/public`) verifica que el adjunto esté marcado público..."* — ese
  caso **ya no existe** (la `api` lo borró en el plan hermano). El handler de `opus-web` que lo
  llamaba es lo último que queda de él.

**El riesgo que el ADR registra y esta story cierra en su mitad del producto:**

> **La lista de exenciones es una regex de lookahead negativo**, que es difícil de leer y fácil de
> romper. Un error ahí puede exponer más de lo previsto sin que nada falle.
>
> **Mitigación:** ninguna automática hoy. **Un test que verifique que exactamente los paths esperados
> quedan exentos sería la verificación correcta, y es barato de escribir.**

→ **La Tarea 2 de este plan es exactamente esa mitigación, para el matcher de `opus-web`.** No es un
test de conveniencia: es la mitigación que un ADR aceptado declara faltante. Vale escribirlo con ese
encuadre, porque es lo que impide que un "limpiemos el matcher" futuro se lleve el prefijo `api`.

#### ADR-006: Dos frontends, una api

**Relevancia:** las reglas del ADR viven en la `api`, no acá. La que importa como contexto:

- *"**NO SE DEBE** confiar en el frontend para el aislamiento. `opus-web` no corta navegación por rol
  a propósito: el filtro es de datos."*

→ **El guard de `opus-web` es binario: sesión o no sesión.** El redirect a `/login` de CA-1 **no es
autorización**, es autenticación. Quién puede ver *qué* adjunto lo sigue decidiendo la `api` con
`canUserViewEntity` + permiso de proyecto. **No agregar ninguna lógica de rol ni de visibilidad al
middleware:** no es su trabajo y sería la clase de segunda barrera que el ADR desaconseja.

#### ADR-010 y ADR-011

**No aplican.** Esta story no toca estilos (ADR-010: Sass + CSS Modules sin librería) ni la capa de
datos (ADR-011: TanStack Query). Se listan para que quede explícito que se revisaron y se descartaron,
no por omisión.

### API Context

**No hay cambio de contrato HTTP en este servicio.** No se crea ni se modifica ningún endpoint: se
**elimina** una ruta de Next y se cierra una excepción del guard.

#### La ruta eliminada

**`GET /attachments/{id}/{fileName}`** — ELIMINADA
(ref: `docs/architectures/opus-web/overview.md`:78; `docs/architectures/opus-web/index.md`:74)

**No está en ningún OpenAPI**: es un route handler de Next, no un endpoint de la `api`. No hay spec que
editar en este servicio.

- **Justificación:** RF-1. Es el único constructor de la URL del endpoint público en todo el producto.
- **Efecto sobre el guard (RF-2), el diff exacto:**

```diff
- matcher: '/((?!api|attachments|_next/static|_next/image|favicon.ico).*)',
+ matcher: '/((?!api|_next/static|_next/image|favicon.ico).*)',
```

**Los dos cambios son inseparables.** Borrar solo la ruta dejaría `/attachments/*` fuera del guard
sirviendo el 404 de Next **sin sesión**: no filtra nada, pero deja viva la excepción que RF-2 pide
cerrar. Sacar solo la excepción sin borrar la ruta haría que el handler exigiera sesión para después
llamar a un endpoint público — un estado sin sentido.

- **Lo que se va con el handler:** nada compartido. El archivo no exporta nada más que `GET`, no lo
  importa ningún otro módulo (verificado: cero referencias a `@/app/attachments` fuera de su propio
  test), y su `const API_URL` es local al archivo.

**`GET /api/opus/attachments/{id}/public`** — ya no existe (plan hermano, `Completed`). Estado
verificado en el código:

#### Los endpoints que NO cambian — el camino autenticado

RF-6 lo exige explícitamente. **Estos quedan byte por byte iguales**, y son las rutas de CA-5 y CA-6:

| Handler de `opus-web` | Reenvía a | Autorización de la `api` | Payload del comando |
|---|---|---|---|
| `GET /api/attachments/[id]/preview` | `GET /api/opus/attachments/{id}/preview` (`api.yaml`:2033) | `hasAnyRole(['user','external-user'])` + `canUserViewEntity` | `{ "disposition": "inline" }` |
| `GET\|HEAD /api/files/[id]/preview` | `GET /api/files/{id}/preview` (`api.yaml`:1637) | Solo el JWT | `{ "disposition": "inline" }` |
| `GET\|POST\|PATCH\|PUT\|DELETE /api/opus/[...path]` | `/api/opus/*` | por endpoint | — |

**Por qué el diff del matcher no los alcanza, y hay que poder afirmarlo y no solo creerlo:** el regex
excluye por el **prefijo `api`**, y las tres rutas viven bajo `src/app/api/`. Verificado ejecutando el
regex nuevo (no razonado sobre él):

> ### Camino D: ELIMINADO — el link público sin sesión
>
> **Eliminado por REQ-002 / S-009 (2026-08-20).** Existió `GET /attachments/{id}/{fileName}` en
> `opus-web` —fuera del matcher del middleware, a propósito— que llamaba a
> `GET /api/opus/attachments/{id}/public`, el único endpoint exento de `validateToken`. La `api`
> validaba `visibilityLevel === 'public'` sobre la entidad del vínculo y redirigía a la prefirmada
> que firmaba `core`.
>
> **Hoy no existe ninguno de los dos.** Un `GET /attachments/123/informe.pdf` sin sesión recibe un
> **307 a `/login`** del middleware, sin ejecutar ningún route handler y **sin publicar nada en el
> bus**; con sesión válida recibe el **404** de Next. Una llamada a
> `GET /api/opus/attachments/123/public` recibe **401** sin token —`validateToken` corre antes del
> router, así que no toca la base ni revela si el id existe— y **404** con token válido.

**El 307 no es una elección: es lo que devuelve `NextResponse.redirect()`.** Su default es 307
(Temporary Redirect), que preserva el método. No hay que pasar el status a mano y no hay que cambiarlo.

#### Los pasos del flujo que este servicio ejecuta, después del cambio

**Escenario 1 — link público viejo, sin sesión (CA-1, CA-8, CA-12).** Es el corte:

1. **[navegador → `opus-web`]** `GET /attachments/123/informe.pdf`, **sin cookie de sesión**
   → el path ahora **matchea** `'/((?!api|_next/static|_next/image|favicon.ico).*)'`, así que el
   middleware corre
2. **[`opus-web` — `src/middleware.ts`]** `auth()` devuelve `null` → `isSessionValid(null)` es `false`;
   `isLoginPage` es `false` → `NextResponse.redirect(new URL('/login', request.url))` = **307** con
   `Location: /login`
   → **No se ejecuta ningún route handler.** El middleware corre antes del App Router
3. **[nada más ocurre]** No hay `fetch` a la `api`, no se publica `files.{fileId}.request-download`,
   `core` no recibe nada y no firma nada

**Outcome:** el usuario ve la pantalla de login del portal. **Cero bytes servidos, cero comandos en el
bus.**

> **CA-12 se cumple por construcción:** con `core` caído la respuesta es idéntica, **porque `core` ya
> no participa**. La aserción que lo prueba es que `global.fetch` no se llamó (TS-6). No hay forma de
> "testear core caído" acá y no hace falta: lo que hay que probar es que no hay ninguna llamada.
>
> **CA-8 sale del mismo paso:** `visibilityLevel: 'public'` sobre la entidad ya no habilita nada sin
> sesión. La validación de visibilidad no se relaja: **deja de existir en este camino, porque no hay
> camino.**

**Escenario 2 — la misma URL, con sesión válida (CA-2):**

1. **[navegador → `opus-web`]** `GET /attachments/123/informe.pdf` con cookie de sesión válida
2. **[`middleware.ts`]** `isValid` es `true`, `isLoginPage` es `false` → `NextResponse.next()`. El
   guard lo deja pasar
3. **[App Router]** No hay segmento `attachments/`: el árbol se borró completo. Next resuelve la ruta a
   **404**

**Outcome:** 404 del portal. **No es un 500** — y es la razón por la que hay que borrar el **árbol
entero** y no solo el cuerpo de la función `GET`:

| Qué se borra | Qué responde Next |
|---|---|
| Solo el cuerpo de `GET`, dejando el `route.ts` | **405** Method Not Allowed (el archivo existe y no exporta `GET`) |
| El `route.ts` vaciado a cero bytes | **rompe el build** |
| **El árbol entero `src/app/attachments/`** | **404 limpio** ← es lo que pide CA-2 |

> **Consecuencia práctica para la implementación:** hay que borrar **directorios**, no solo el archivo.
> Un `src/app/attachments/[id]/[fileName]/` que quede vacío no rompe nada en Next (los segmentos sin
> `route.ts`/`page.tsx` se ignoran), pero deja basura en el árbol y contradice el "borrar el árbol
> entero" que la story pide. `rm -rf src/app/attachments` y listo. **git no versiona directorios
> vacíos**, así que después de borrar el único archivo el commit queda correcto igual — pero el working
> tree local no, y el implementador va a ver carpetas fantasma si borra con el editor.

**Escenario 5 — el camino autenticado, intacto (CA-5, CA-6, CA-11).** Lo que **no** hay que tocar:

1. **[navegador → `opus-web`]** `GET /api/attachments/45/preview` (la URL va en un `src`/`href`, sin
   `Authorization` — ADR-009) → path bajo `api`, **excluido del matcher**: el middleware no corre,
   igual que antes del cambio
2. **[`src/app/api/attachments/[id]/preview/route.ts`]** Chequea sesión con `auth()` y reenvía con el
   Bearer a `{API_URL}/api/opus/attachments/45/preview`, con `redirect: 'manual'`
3. **[`api`]** `hasAnyRole(['user','external-user')` + `canUserViewEntity` → publica
   `files.{fileId}.request-download` con `{ "disposition": "inline" }` → **302** a la prefirmada
4. **[`opus-web` → navegador]** Propaga el 302; el navegador baja de S3 directo

**Ni una línea de este camino se toca.**

> - **La pantalla no cambia: ni un bloque, ni un estado, ni un layout.** El camino autenticado de
>   lectura de adjuntos —el `HEAD` de metadatos y el preview embebido de `RichContentRenderer`, que
>   entran por `/api/attachments/{N}/preview`— queda **byte por byte igual** (RF-6, CA-5, CA-6). El
>   diff del matcher excluye por el prefijo `api`, así que esas URLs siguen fuera del guard y las
>   imágenes embebidas en markdown se renderizan como antes. Se verificó explícitamente en el diseño
>   técnico en lugar de asumirlo, porque es la única forma de saber que un borrado de rutas no arrastra
>   el camino que sí importa.
> - **Lo que cambia es el peso de este bloque, no su forma: es el único acceso a un archivo que queda
>   en el producto.** Antes había dos caminos —este y el link público sin sesión— y el segundo se
>   eliminó. Abrir un adjunto **exige sesión en todos los casos**, y `visibilityLevel: 'public'` sobre
>   el requisito dejó de habilitar acceso anónimo (RF-8, CA-8). Para un `external-user`, el
>   `PermisoDeProyecto` pasa a ser la **única** puerta a un adjunto, sin alternativa (CA-11).
> - **No se agrega ningún control de compartir, y es el descarte central del REQ.** Ni botón, ni copia
>   de URL, ni link con vencimiento: RF-8 lo deja fuera de alcance de forma explícita. Es la decisión
>   que más se nota desde esta pantalla, porque es acá donde un cliente tendría el impulso de mandarle
>   un entregable a alguien de su organización que no entra al portal. **La pantalla no anticipa nada:
>   agregar un affordance de compartir que no existe sería peor que su ausencia.**
> - **No se avisa que el link viejo dejó de funcionar.** El usuario de esta pantalla ya está
>   autenticado y para él nada cambió, así que el mensaje le hablaría de un problema que no tiene.
> - **Sin cambios en el Design System.**

> **Traducción a instrucción:** en `detalle-requisito` **no se toca un archivo tampoco.** Su relación
> con esta story es de **regresión**: los tests que ya existen del preview autenticado tienen que
> seguir verdes sin modificarse (TS-14).

#### Estados globales de la superficie que esta story cambia (de `product-map.md`, verbatim)

> - **Autenticado vs no autenticado** — Todo está protegido salvo `/login`, por `middleware.ts` con
>   matcher **por exclusión**: una ruta nueva queda protegida sola. El guard además rechaza sesiones
>   con el access token vencido, no solo la ausencia de cookie. **Con REQ-002 la afirmación pasa a ser
>   literal.** Antes el matcher excluía `attachments` además de `api` y los estáticos, así que había
>   **una** ruta de pantalla fuera del guard; hoy las únicas exclusiones son `api`, `_next/static`,
>   `_next/image` y `favicon.ico`, que no son navegación [REQ-002 RF-2, CA-1]. Consecuencia observable:
>   **cualquier `GET /attachments/...` sin sesión redirige a `/login`.**
> - **Ruta inexistente, con sesión** — Devuelve el 404 por defecto de Next, sin chrome del portal ni
>   forma de volver. **REQ-002 le agrega un vector de llegada nuevo:** un cliente logueado que pegue la
>   URL vieja de un adjunto (`/attachments/123/informe.pdf`) pasa el guard y cae en ese 404, porque el
>   segmento ya no existe [REQ-002 CA-2]. El REQ exige explícitamente que sea **404 y no 500**, y por
>   eso se borra el árbol entero y no solo el cuerpo del handler. **No se agrega `not-found.tsx` en
>   este REQ:** sigue siendo el gap de severidad Alta de `gaps-as-is.md`, ahora más alcanzable.

#### Flujos de usuario relevantes

**Flujo 1: Consultar el avance de mis proyectos** — *JTBD: "Cuando quiero saber en qué está lo que
pedí, quiero verlo yo mismo, para no tener que escribirle a alguien y esperar."* · Audiencia: cliente ·
Trigger: el cliente entra al portal, típicamente después de bastante tiempo sin entrar.

**Happy path:** login → login-entrada → proyectos-redireccion (redirige al primer proyecto por orden
alfabético) → tablero-requisitos (agrupado por estado, `resuelto` y `cancelado` colapsados) → abre uno
→ detalle-requisito.

**Camino alternativo nuevo de esta story (verbatim):**

> - **Entrar desde un link viejo de adjunto** — Camino de entrada **nuevo desde REQ-002**. Alguien abre
>   `/attachments/123/informe.pdf` desde un correo de hace meses: la ruta ya no existe y `attachments`
>   salió del matcher, así que el guard lo alcanza y lo manda a **login** (RF-1, RF-2, CA-1). Si tiene
>   cuenta, entra y sigue el happy path hasta el requisito que tiene el adjunto y lo abre por el camino
>   autenticado. **Es el único camino del flujo que empieza sin intención de entrar al portal:** el
>   usuario venía a abrir un archivo. La pantalla de login no se lo dice —no hay mensaje contextual, es
>   un descarte explícito del REQ— así que la orientación depende de que reconozca el portal.

**Errores y recuperación nuevos (verbatim):**

> - **Link viejo de adjunto, ya con sesión** — Un cliente logueado que pegue `/attachments/123/informe.pdf`
>   pasa el guard y cae en el **404 por defecto de Next**, sin chrome ni forma de volver [REQ-002
>   CA-2]. **No hay recuperación guiada:** tiene que volver atrás en el navegador o reescribir la URL
>   del portal. El adjunto sigue estando —dentro del requisito que lo tiene— pero nada en esa página lo
>   lleva ahí.
> - **Sin cuenta en el portal** — Quien abra un link viejo y **no tenga usuario** queda en login sin
>   poder pasar. **Es el resultado buscado, no una falla:** el REQ decide que el acceso a un archivo
>   exige sesión sin excepciones (RF-8) y acepta que los links en circulación rompan sin transición ni
>   aviso (RF-7). Lo que el flujo no ofrece es una salida: no hay texto que explique por qué no puede
>   entrar ni a quién pedirle acceso.

**Flujo 3: Conversar sobre un requisito** — el camino modificado (verbatim):

> - **Abrir un adjunto** — Preview embebido para imágenes, descarga para el resto. Si el contenido del
>   archivo nunca llegó al sistema, dice *"El archivo no está disponible"* en lugar de fallar de forma
>   opaca (REQ-001 RF-21, CA-15). **Desde REQ-002 este es el único camino a un archivo:** abrir un
>   adjunto **exige sesión en todos los casos** y `visibilityLevel: 'public'` sobre el requisito ya no
>   habilita acceso anónimo — pasa a significar solo *"visible para usuarios externos autenticados"*,
>   que es lo que ya significaba en el resto del producto (RF-8, CA-8).
> - **Compartir un adjunto hacia afuera** — **No existe, y su ausencia es deliberada.** Hasta REQ-002
>   el cliente podía copiar la URL de un adjunto y mandársela a alguien de su organización que no
>   tuviera cuenta; ese camino se eliminó y **no se reemplazó por nada** (RF-8). No hay botón de
>   compartir, ni link con vencimiento, ni copia de URL: para que un tercero vea el archivo hay que
>   darle acceso al proyecto.

**Flujo cross-surface 3: Conversación sobre un requisito** — la tabla que resume el delta (verbatim de
`docs/ux/cross-surface-flows.md`):

> **Y desde REQ-002 el archivo cruza entre las dos superficies, pero no sale del producto** [REQ-002
> RF-8, CA-8]. Había un tercer cruce, y era el único que salía hacia afuera: un link
> `/attachments/{id}/{fileName}` servía el adjunto **sin sesión**, así que un tercero sin cuenta —el
> gerente del cliente, un proveedor suyo— podía abrir el archivo con solo tener la URL. Ese camino se
> eliminó y **no se reemplazó**.
>
> | Cruce | Antes | Ahora |
> |---|---|---|
> | `opus-web` ↔ `web`, ver un adjunto | Con sesión y permiso | **Sin cambios** |
> | `opus-web` ↔ `web`, reusar un adjunto ajeno | Rechazado (REQ-001) | **Sin cambios** |
> | Hacia afuera del producto, sin cuenta | Link público, sin sesión | **No existe** |
>
> Los links que ya circulan en correos y documentos **dejan de abrir el día del deploy**, sin
> transición ni aviso: quien los abra cae en el login de `opus-web`. **No es un flujo que se degrada,
> es un flujo que se cierra.**
