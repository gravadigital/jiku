## Story Reference

- **Origen:** [REQ-017](../requests/REQ-017.roles-de-usuarios-para-conectores-y-cierre-de-brechas-de-docs.md)
- **Summary:** La api ya reemplazó `GET /api/opus/docs/attachments/{id}` por
  `GET /api/opus/docs/documents/{documentId}/attachments/{id}` (S-087/api, completada). opus-web

> ya la documenta; la ruta vieja de la api **ya no existe**, así que hoy los adjuntos del portal

### Fuera de alcance (declarado, para no improvisarlo)

- **Tratamiento visible del enlace al adjunto de otro documento (R-3).** El enlace se renderiza
  igual y al abrirlo el proxy responde 404 (imagen rota / enlace que no descarga). La UX lo descartó
  explícitamente: *"Detectar en el visor los enlaces a adjuntos que no están en la lista del
  documento y mostrarlos como texto sin enlace … agrega lógica al renderizador de markdown para un
  caso marginal"*. **No** agregar esa lógica.
- **`HEAD` en el handler.** El handler viejo solo respondía `GET` (P-11 de S-084); el nuevo
  conserva eso, aunque la api acepte `HEAD`.
- **Unificar el 401 con ADR-009** (`{error}` vs `{code, message}`): discrepancia conocida, no se
  resuelve acá. El handler nuevo usa `{code, message}` como el viejo.

### Convenciones activas que aplican (extracto)

**api-routes (custom de opus-web):**

- Un handler propio se justifica cuando *"La URL va en un `src`/`href`/`download`"* (el navegador
  no puede mandar el token) y cuando *"La api responde una redirección (302) que no debe seguirse —
  el catch-all la sigue; usar `redirect: 'manual'`"*. Ambas aplican.
- `/api/*` está **fuera del matcher del middleware** (`matcher: '/((?!api|_next/static|_next/image|favicon.ico).*)'`):
  el handler valida la sesión por sí mismo.
- `API_URL` es una **función** (`const API_URL = () => process.env.API_URL ?? ''`), se lee en cada
  request; `API_URL` vacío → `500 { code: 'server_misconfigured', message: 'API_URL is not set' }`.
- La base se normaliza con `new URL(path, base.endsWith('/') ? base : `${base}/`)`. **No**
  interpolar `${process.env.API_URL}` directo.
- *"Un handler nuevo usa el formato `{code, message}` del catch-all"*: 401 =
  `{ code: 'unauthorized', message: 'Unauthorized' }`.
- *"Siempre `await params`"*. El tipo se declara explícito.
- *"No inventar un formato de error nuevo"*.

**testing-unit (custom de opus-web):**

- Tests nuevos de componentes/utils **junto al código**; los de route handler en `__tests__/`
  (*"No agregar a `__tests__/` salvo que sea un test de un route handler"*).
- Mockear hooks/servicios, no `fetch` ni axios — **excepción de hecho:** los tests de route handler
  mockean `global.fetch` (el handler llama a `fetch` directo), como el test actual.
- No mockear `react-markdown` (ya aliaseado globalmente). No mockear la zona horaria.
- Aserciones por rol y texto (`getByRole`, `getByText`).

**styling:** sin cambios visuales en esta story; no se tocan `.module.scss`.

### Relevant ADRs

- **ADR-009: Token confinado al servidor**
  - Decision: el access token nunca llega al navegador; en `opus-web` toda llamada sale por route
    handlers del propio origen.
  - Implementation Rules (verbatim):
    - El access token **NO DEBE** llegar al navegador por ningún camino: ni en el bundle, ni en una
      respuesta, ni en una cookie legible por JS.
    - La URL de la api **DEBE** leerse de `API_URL` **en el servidor, en runtime**. **NO SE DEBE**
      usar `NEXT_PUBLIC_API_URL` ni ninguna variable horneada en build.
    - En `web`, toda llamada de dominio **DEBE** ir por un Server Action (`'use server'`) con
      `apiClient`. Un route handler en `app/api/` **DEBE** justificarse por una capacidad que el Server
      Action no tenga (streaming, headers de respuesta, llamada desde componente cliente).
    - En `opus-web`, toda llamada **DEBE** ir por el proxy `/api/opus/[...path]`. **NO SE DEBE**
      agregar un cliente axios que apunte directo a `API_URL` desde el navegador.
    - Todo route handler que reenvíe a la api **DEBE** exigir sesión y responder
      `401 {"error":"Unauthorized"}` si no hay `accessToken`. La única excepción vigente es
      `GET /attachments/[id]/[fileName]` de `opus-web`, cuya autorización la decide la api.
    - Al reenviar respuestas binarias, **DEBEN** propagarse `Content-Type`, `Content-Disposition` y
      `Content-Length`.
    - Al reenviar uploads **DEBE** usarse streaming con `duplex: 'half'`, no bufferizar el archivo
      entero en memoria.
    - Un 401 de la api **DEBE** redirigir el navegador a `/login`.
    - **NO SE DEBE** agregar `NEXT_PUBLIC_*` funcional: rompería la premisa de una imagen por todos los
      entornos.
  - Nota: el cuerpo del 401 es la discrepancia F-20 documentada en `api-routes` (opus-web usa
    `{code, message}`); se mantiene. No hay binario reenviado: el handler propaga un 302 sin cuerpo.

- **ADR-015: Módulos opcionales del bus** — DD-15 (reescritura por path):
  *"Los visores de `web` y `opus-web` reescriben **por path y sin mirar el host** todo enlace cuyo
  path sea `/docs/attachments/{ULID}` hacia su propio proxy. No hace falta una variable nueva por
  frontend, y es seguro: el proxy solo le pide a jiku-docs ese id con la identidad de quien mira."*
  Esta story mantiene la detección por path; solo cambia el destino (ahora incluye el id del
  documento abierto). F-13 (*"un usuario interno que use el portal recibe el adjunto de un documento
  `internal` si conoce el id"*) queda cerrado por la api; actualizar el ADR es del servicio `docs`.

### API Context

**Ruta que consume el handler** (de `docs/apis/api.yaml`, verbatim):

```yaml
/opus/docs/documents/{documentId}/attachments/{id}:
  get:
    tags: [opus]
    summary: Descarga un adjunto de un documento público (portal)
    x-jiku-module: docs
    x-roles: [external-user, admin, user]
    description: |
      Lee el documento con `documents.get { id: documentId, include: ['attachments'] }`. Si `visibility` no es
      `public` (o falta) responde **404** `document_not_found` para todo rol; si el adjunto no está en
      `attachments` del documento, **404** `attachment_not_found`. Recién entonces
      `attachments.{id}.request-download` y **302** a la `downloadUrl`. Nunca 403 por visibilidad: el portal
      no revela que existe un documento interno. Mantiene la excepción DD-4 a ADR-006. Un id con forma
      inválida es 404 sin llamar al módulo.
    parameters:
      - { name: documentId, in: path, required: true, description: "Id del documento (ULID)", schema: { type: string, pattern: '^[0-9A-HJKMNP-TV-Z]{26}$' } }
      - { name: id, in: path, required: true, description: "Id del adjunto (ULID)", schema: { type: string, pattern: '^[0-9A-HJKMNP-TV-Z]{26}$' } }
    responses:
      '302':
        description: |
          Redirección a la `downloadUrl` de jiku-docs, sin cuerpo y sin `Content-Type` ni
          `Content-Disposition` (el reply de jiku-docs no trae metadatos de archivo). La URL
          nunca se loguea. `HEAD` responde igual.
        headers:
          Location: { schema: { type: string }, description: '`downloadUrl` prefirmada' }
          X-Content-Type-Options: { schema: { type: string, enum: [nosniff] } }
      '401': { $ref: '#/components/responses/Unauthorized' }
      '403': { $ref: '#/components/responses/ModuleForbidden' }
      '404': { $ref: '#/components/responses/ModuleNotFound' }
      '500': { $ref: '#/components/responses/InternalError' }
      '503': { $ref: '#/components/responses/ModuleUnavailable' }
      '504': { $ref: '#/components/responses/ModuleGatewayTimeout' }
```

**Cuerpos 404 relevantes** (`ModuleNotFound`, ejemplos verbatim):

```yaml
moduleNotInstalled:  { code: module_not_installed, message: El módulo docs no está instalado }
documentNotFound:    { code: document_not_found, message: Documento no encontrado }
attachmentNotFound:  { code: attachment_not_found, message: Adjunto no encontrado }
```

**Schema de adjunto** (`DocsAttachment`, verbatim):

```yaml
DocsAttachment:
  type: object
  properties:
    id: { type: string }
    documentId: { type: string }
    fileName: { type: string }
    mimeType: { type: string }
    sizeBytes: { type: integer }
    link: { type: string, description: "`{JIKU_WEB_URL}/docs/attachments/{id}`" }
    uploadedBy: { type: string }
    createdAt: { type: string, format: date-time }
```

En opus-web el tipo es `DocsAttachment` de `src/features/docs/types/docs.types.ts`
(`documentId?: string` es **opcional** por fidelidad): por eso `DocumentAttachments` cae al id del
documento abierto si falta.

**Contrato del handler de opus-web** (no es API pública; es lo que este plan implementa):

| Caso | Respuesta del handler |
|---|---|
| Sin sesión (`!session?.accessToken`) | `401 { code: 'unauthorized', message: 'Unauthorized' }`, sin `fetch` |
| `documentId` no cumple `ULID_PATTERN` | `404 { code: 'document_not_found', message: 'Documento no encontrado' }`, sin `fetch` |
| `id` no cumple `ULID_PATTERN` | `404 { code: 'attachment_not_found', message: 'Adjunto no encontrado' }`, sin `fetch` |
| `API_URL` vacío | `500 { code: 'server_misconfigured', message: 'API_URL is not set' }`, sin `fetch` |
| api responde 3xx | mismo status, sin cuerpo, headers `Location` (el de la api) y `X-Content-Type-Options: nosniff` |
| api responde no-3xx con JSON | mismo status y mismo cuerpo (el `code` sobrevive) |
| api responde no-3xx sin JSON | mismo status, sin cuerpo |

`fetch(new URL(`api/opus/docs/documents/${documentId}/attachments/${id}`, base normalizada), { headers: { Authorization: `Bearer ${session.accessToken}` }, redirect: 'manual' })`.

Orden de validación: sesión → `documentId` → `id` → `API_URL` (el mismo del handler actual, con el
chequeo de `documentId` antes del de `id`, en el orden del path y como la api).

### Flow Context

**`documentos-desde-la-web`, Paso 9 — estado actual del documento (verbatim, pendiente de
actualizar por el servicio `docs`):**

| Operación | Endpoint | Detalle |
|---|---|---|
| Listar | `GET /api/opus/docs/documents` | Query `projectId` **o** `requirementId` (uno solo); `limit`, `cursor`. … **`filter.visibility: 'public'` lo fuerza el handler**; la query no puede pisarlo |
| Detalle | `GET /api/opus/docs/documents/{id}` | `documents.get { id, include: ['content','attachments'] }`; **404 `document_not_found` si `visibility !== 'public'`** (falla cerrado) |
| Adjunto | `GET /api/opus/docs/attachments/{id}` | 302 a la URL prefirmada |

> Los adjuntos se enlazan por el handler propio `opus-web/src/app/api/docs/attachments/[id]/route.ts`:
> el navegador no puede mandar el token en un `src`/`href` y el catch-all sigue las redirecciones
> (convertiría el 302 en un proxy del binario). El handler valida la sesión, valida el ULID, llama a
> `api/opus/docs/attachments/{id}` con **`redirect: 'manual'`** y propaga el 302 (solo `GET`). Un 401
> responde `{ "code": "unauthorized", "message": "Unauthorized" }`.

**Qué cambia en este paso (según la story):**

1. **[opus-web — visor]** `docsUrlTransform(doc.id)` reescribe el enlace → `/api/docs/documents/{docId}/attachments/{attId}`
2. **[opus-web — route handler]** valida sesión y los dos ULID → `GET {API_URL}/api/opus/docs/documents/{docId}/attachments/{attId}` con `Authorization: Bearer <token>` y `redirect: 'manual'`
3. **[api]** `requireModule('docs')` → `hasAnyRole` → `documents.get { id: docId, include: ['attachments'] }` → `visibility !== 'public'` → 404 `document_not_found`; `attId` ausente en `attachments[].id` → 404 `attachment_not_found`; OK → `request-download` → 302 `Location`
4. **[opus-web — route handler]** propaga el 302; el navegador baja del storage

Errores del paso 9 que el handler propaga tal cual: `404 module_not_installed`, `503 module_unavailable`,
`504 gateway_timeout`, `404 document_not_found`, `404 attachment_not_found`; su propio
`401 { "code": "unauthorized", "message": "Unauthorized" }`.

### Integration Points

- **api** (interno): solo la ruta de arriba, vía `fetch` desde el servidor de Next con el Bearer de
  la sesión. Sin bus, sin servicios externos.
- El navegador sigue el 302 hacia el storage de jiku-docs (URL prefirmada); opus-web no la toca ni la
  loguea.

**Decisiones REQ-017 (verbatim del screen.md):**
- **El adjunto se pide bajo su documento.** El proxy pasa de `/api/docs/attachments/{id}` a
  `/api/docs/documents/{documentId}/attachments/{id}`, y la api verifica que el documento sea `public`
  y que el adjunto le pertenezca antes de generar la descarga. … **Para el cliente no cambia nada
  visible**: los adjuntos del propio documento se ven y se descargan como antes [CA-9, CA-11].
- **Un enlace al adjunto de otro documento deja de abrir, y no se le da tratamiento visible.** …
  Queda registrado en `known-limitations.md`.
- **Alternativa descartada:** detectar en el visor los enlaces a adjuntos que no están en la lista
  del documento y mostrarlos como texto sin enlace (o con un aviso "Adjunto no disponible").

**Flujo 4 "Leer la documentación de mi proyecto" — Errores y recuperación (caso nuevo, verbatim):**
- **Adjunto ajeno al documento** — Si el contenido enlaza el adjunto de **otro** documento (o el de
  uno interno, conociendo su id), el enlace no abre: el proxy responde 404 y no se genera ninguna
  descarga. Los adjuntos del propio documento se abren como siempre [REQ-017 CA-8, CA-9, R-3].

**Cross-surface Flujo 4 (fila nueva, verbatim):** *"Enlace al adjunto de **otro** documento | ❌ No —
en la web abre; en el portal el proxy responde 404, aunque el otro documento también sea `public`
[REQ-017 DD-2, R-3]"*

**Navegación / overlays:** sin cambios. El proxy es una *ruta sin pantalla* del product-map
(`/api/docs/documents/[documentId]/attachments/[id]`, *"el proxy de adjuntos con la sesión del
cliente (la ruta la fija REQ-017; nació como `/api/docs/attachments/[id]`)"*).

## Hallazgos y decisiones de este plan

- **Ventana rota entre api y opus-web.** La api ya no expone `GET /opus/docs/attachments/{id}`; hasta
  que este plan se implemente, el portal muestra imágenes rotas y adjuntos que no descargan. Conviene
  liberar los dos servicios juntos (misma release del monorepo).
- **Nombre de la fábrica:** se eligió `createDocsUrlTransform(documentId)` entre las dos opciones de la
  story (`docsUrlTransform(documentId)(url)` o `createDocsUrlTransform`), porque el nombre deja claro
  que devuelve una función y el archivo conserva su nombre.
- **`documentId` inválido en la fábrica → `''` para adjuntos.** No lo pide la story; se agrega por
  coherencia con "falla cerrado" del handler. En la práctica `doc.id` viene de la api y es ULID.
- **Orden de chequeo de ids en el handler:** primero `documentId` (`document_not_found`), después `id`
  (`attachment_not_found`), igual que la api.
- **Catálogo `docs/reusable-code/opus-web/`:** la story no lo lista en "Documentación a actualizar",
  pero es el catálogo del propio servicio y quedaría describiendo una firma que ya no existe; se
  actualiza en Task 4. Las arquitecturas de opus-web quedan para el servicio `docs`.
