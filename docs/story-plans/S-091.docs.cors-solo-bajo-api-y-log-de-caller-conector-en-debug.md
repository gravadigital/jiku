### Lo implementado (1): CORS solo bajo `/api` (commit `57f1e2b`)

```ts
  // DD-10: PRIMER middleware. En el host público la api no sirve nada que no sea /p/docs/*; va antes
  // de validateToken y del logger para que esos 404 no revelen la api ni ensucien el log.
  app.use(publicHostOnly);
  // F-18 (REQ-020): CORS solo bajo /api. El HTML de un link compartido (/p/docs/*) no tiene que ser
  // legible por JavaScript de otro origen aunque se conozca el token. Va en esta posición, antes de
  // validateToken, para que el preflight de /api lo siga respondiendo cors() con 204 y los 401 lleven
  // Access-Control-Allow-Origin como hasta ahora.
  app.use('/api', cors());
```

**Orden de `api/app.ts` después del cambio:** `trust proxy` (si `API_TRUST_PROXY`) →
`publicHostOnly` (primer middleware) → **`cors()` montado en `/api`** → `docsWriteJson` (768kb, bajo
`/api/docs`) → `express.json()` → `express.urlencoded` → `express.static` → logger de requests
(`ignoreRoute` para `/p/docs/*`) → `validateToken` global (`get`, `patch`, `post`, `put`, `delete`;
**no** `options`) → `publicRoutes` en la raíz → barrel de `lib/routes` bajo `/api` → fallback 404 →
`payloadTooLargeHandler`.

**Comportamiento observable (lo afirma `cors.test.ts`):**

| Request | Resultado |
|---|---|
| `GET /p/docs/{token}` con `Origin` | Sin `Access-Control-Allow-Origin` (CA-1) |
| `OPTIONS /p/docs/{token}` con `Origin` y `Access-Control-Request-Method` | Sin `Access-Control-Allow-Origin`, `-Methods` ni `-Headers` (CA-2); en el host público, el 404 de `publicHostOnly`; fuera, el manejo por defecto de Express |
| `GET /api/...` con `Origin` | `Access-Control-Allow-Origin: *`, también en los 401 de `validateToken` (CA-3) |
| `OPTIONS /api/...` (preflight) | 204 de `cors()` con `Access-Control-Allow-Origin: *` y `Access-Control-Allow-Methods: GET,HEAD,PUT,PATCH,POST,DELETE`, antes de `validateToken` (CA-3) |

Sin cambio en `validateToken`, `config/public.ts`, `getRolesFromToken` ni en la cadena de
`lib/public-routes/index.ts` (`publicDocsHeaders → publicDocsAccessLog → requirePublicHost →
publicDocsRateLimit → handler → publicDocsNotFound`). Web y opus-web no usan el CORS de `/api`: llaman
desde el servidor de Next.js (ADR-009); se conserva igual por el supuesto de REQ-020.

### Lo implementado (2): `callerClass` y el nivel del log (commit `4ee2e71`)

`CommandContext` real (`core/src/commands/types.ts`), en orden:

```ts
export interface CommandContext {
  caller: string;                      // servicio que publicó, del subject
  params: Record<string, string>;      // `clients.{id}.edit` deja { id: '7' }
  transaction: Transaction;            // abierta por el despachador
  actor?: Actor;                       // sobre de identidad, si el publicador de confianza lo declaró
  roles: readonly string[];            // roles de quien actúa (S-031)
  callerClass: CallerClass;            // 'connector' | 'internal' | 'external' (S-091)
  actorName?: string;                  // nombre humano para los eventos (S-070)
}
```

JSDoc de `callerClass` (texto a reflejar): *"La clase del caller, la MISMA que la compuerta del
despachador ya calculó con `resolveCallerClass` (S-030), pasada sin ninguna consulta nueva. De dónde
sale en cada canal: SOBRE: la clase de `actor.roles`. DIRECTO: la clase de `users.roles` del caller.
EXENTO (`CORE_TRUSTED_PUBLISHER_ID` sin sobre): `'connector'`. EXISTE PARA QUE `resolveActor` ELIJA EL
NIVEL DEL LOG de su rama externa (S-091), no para autorizar. NO ES OPCIONAL, igual que `roles`."*

Despachador, los dos puntos:

```ts
const reply = await command.execute(validated.value, {
  caller, params, transaction, actor, roles, actorName, callerClass,
});
// ...
await writeNotifications(reply.notifications, {
  caller, params, transaction, actor, roles, actorName, callerClass,
});
```

`resolveActor`, rama externa:

```ts
  const message =
    `[${component}] comando publicado por un caller externo: ${ctx.caller}. ` +
    'El actor se resuelve del subject y se ignora lo declarado en el cuerpo.';
  if (ctx.callerClass === 'connector') {
    logger.debug(message);
  } else {
    logger.warn(message);
  }

  return ctx.caller;
```

| Canal | Clase | Rama de `resolveActor` | Log |
|---|---|---|---|
| Con sobre (la api en nombre de una persona) | la de `actor.roles` | sobre → `actor.id` | **ninguno** (CA-6) |
| `CORE_TRUSTED_PUBLISHER_ID` sin sobre | `connector` | api → campo declarado | **ninguno** (CA-6) |
| Directo, rol `internal-app` (jiku-docs `['internal-app','docs']`, cualquier servicio externo) | `connector` | externa → `ctx.caller` | **`debug`** (CA-4) |
| Directo, rol `user` / `admin` (persona publicando al bus) | `internal` | externa → `ctx.caller` | **`warn`** (CA-5) |
| Directo, rol `external-user` | `external` | externa → `ctx.caller` | **`warn`** (CA-5) |

Mismo texto, mismo valor devuelto, sin payload. En producción la consola de core loguea desde `info`
(`core/src/logger.ts`), así que la línea de jiku-docs deja de verse sin configuración extra.

### Discrepancia D-1: el `warn` ya no señala un `CORE_TRUSTED_PUBLISHER_ID` mal configurado

DD-4 de la story y el comentario de `resolveActor` dicen que el `warn` "queda como señal de un
`CORE_TRUSTED_PUBLISHER_ID` mal configurado o de una persona publicando directo". **La primera mitad
no se cumple con lo implementado:** el service user de la api tiene rol `internal-app` (su plantilla
es la `connector`, `deploy/nats/auth-callout/README.md`; `core/overview.md:258`), así que si
`CORE_TRUSTED_PUBLISHER_ID` no coincide con su `sub`, un comando de la api **sin sobre** cae en la rama
externa como canal directo de clase `connector` → **`debug`**, no `warn`. El `warn` queda solo para
callers directos de clase `internal` o `external` (personas).

Atenuante, también verificado: desde S-029 la api publica con sobre siempre que hay identidad, y con
sobre gana la rama del sobre aunque la variable esté mal; la rama externa solo la alcanza un llamado
de la api **sin** identidad. Y `loadConfig` corta el arranque si la variable falta o está vacía.

**Cómo se documenta (DP-4):** los documentos dicen lo implementado —`debug` para clase `connector`,
`warn` para el resto— y **no** repiten la afirmación de la señal de mala configuración. Donde un
documento usaba el `warn` como mitigación (`subida-de-archivos.md:455-456`), se corrige. El comentario
del código no se toca en esta fila (no toca código); queda reportado.

### Flow Context

Escenarios de la story, verbatim:

**Lectura de un link compartido desde otro origen (CA-1, CA-2).** Trigger:
`fetch('{JIKU_PUBLIC_URL}/p/docs/{token}')` con `Origin: https://otro`. **[api]** `publicHostOnly` →
(sin CORS) → `express.json()` → logger → `validateToken` (exento) → `publicRoutes` → `shares.resolve`.
Output: 200 HTML sin `Access-Control-Allow-Origin`. **Outcome:** el script del tercero no puede leer
la respuesta; abrir el link en una pestaña sigue igual.

**Llamada a `/api` (CA-3).** `OPTIONS /api/...` con `Origin` → `cors()` responde 204;
`GET /api/...` → `cors()` agrega `Access-Control-Allow-Origin: *` → `validateToken` → ruta. Igual que
hoy.

**jiku-docs pide una subida (CA-4 a CA-6).** **[core / despachador]** `resolveCallerClass(['internal-app'])`
→ `connector`; arma el contexto con `callerClass`. **[core / `resolveActor`]** sin sobre y caller ≠
`CORE_TRUSTED_PUBLISHER_ID` → rama externa → `debug` si `connector`, `warn` si no; devuelve
`ctx.caller`. Sobre o api sin sobre → sin log.
