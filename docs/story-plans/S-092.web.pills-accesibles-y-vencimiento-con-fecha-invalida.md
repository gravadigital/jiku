### Diseño del helper `parseFinishDate` (DD-6, verbatim de la story + decisiones de este plan)

De la story (DD-6):
- Helper nuevo en `web/src/shared/utils/`:
  `parseFinishDate(value: Date | string | null | undefined): Date | null`.
- Devuelve `null` si el valor es nulo, vacío, un `Date` inválido, o un string que no empieza con
  `YYYY-MM-DD`.
- Un `YYYY-MM-DD` se construye como fecha local (`new Date(y, m - 1, d)`), no con
  `new Date('YYYY-MM-DD')` (UTC; en UTC-3 cae el día anterior).
- `ObjectivesTable` lo usa en `getFinishDateText` (inválida → "No definida"), `getDaysLeftText`
  (inválida → `''`) e `isCloseToDeadline` (inválida → `false`). `isOverdue` y `ObjectiveCard` usan el
  mismo helper.
- `calculateDaysLeft` no cambia de firma ni semántica: cuenta días hábiles.

Decisiones de este plan (no contradicen DD-6; la completan en bordes que DD-6 no nombra):
- **Un string ISO con hora** (`'2026-10-23T23:30:00-03:00'`, `'2026-10-23T03:00:00.000Z'`) toma solo
  sus primeros 10 caracteres: "empieza con `YYYY-MM-DD`" → esa es la fecha. Es el mismo criterio que
  ya usa `RequirementStatusCard.tsx:106` (`estimatedFinishDate?.slice(0, 10)`).
- **Un `Date` válido** se devuelve tal cual (no se renormaliza: `calculateDaysLeft` ya normaliza con
  getters locales).
- **Un `YYYY-MM-DD` con mes/día fuera de rango** (`'2026-13-45'`) devuelve `null`: tras construir la
  fecha local se verifica que año, mes y día coincidan (si no, `new Date(2026, 12, 45)` "rueda" a
  febrero de 2027 y aparecería un vencimiento inventado).
- La regex de forma es `/^(\d{4})-(\d{2})-(\d{2})/` (anclada al inicio, sin anclar al final).

Firma de referencia:

```ts
// web/src/shared/utils/parse-finish-date.ts
const ISO_DATE_PREFIX = /^(\d{4})-(\d{2})-(\d{2})/;

export const parseFinishDate = (value: Date | string | null | undefined): Date | null => {
  if (value instanceof Date) return isNaN(value.getTime()) ? null : value;
  if (!value) return null;
  const match = ISO_DATE_PREFIX.exec(value);
  if (!match) return null;
  const [, y, m, d] = match.map(Number);
  const date = new Date(y, m - 1, d);
  // descarta 2026-13-45 y similares, que Date "rueda" a otro día
  if (date.getFullYear() !== y || date.getMonth() !== m - 1 || date.getDate() !== d) return null;
  return date;
};
```

(Con `noUncheckedIndexedAccess`, la desestructuración de `match` necesita el manejo de `undefined`
que el compilador pida; el snippet es orientativo.)

## Hallazgos y decisiones de este plan

1. **El "32666" casi con seguridad es un dato válido por contrato** (`1901-08-09T04:16:48.000Z`,
   objective 2738, `activo`, en `local/dump.sql`): 32 666 días hábiles exactos al 2026-10-26. Por DD-6
   **no se esconde**; TS-27 lo fija y Task 4 lo verifica contra el e2e. Implica que, tras esta story,
   esa fila del listado **seguirá** mostrando "Vencido hace: 32666 día(s)" hasta que alguien corrija
   el dato. Conviene que el dueño del producto lo sepa: el síntoma reportado en REQ-020 no desaparece
   con este cambio, porque no era una fecha inválida.
2. **Bug latente que sí se corrige:** con un string no parseable (`'abc'`), el listado hoy muestra
   "Vence hoy" en rojo (`calculateDaysLeft(Invalid Date) === 0`). TS-18 lo cubre.
3. **Bordes que DD-6 no nombraba, decididos acá:** ISO con hora → se toman los 10 primeros
   caracteres; `YYYY-MM-DD` fuera de rango → `null`; `Date` válido → se devuelve tal cual.
4. **Bajo `TZ: 'UTC'` "local" y "UTC" coinciden;** la construcción local se prueba con
   `'2026-10-23T23:30:00-03:00'` (TS-9) en vez de tocar `TZ`.
5. **`FinishDateLabel` queda fuera** (no está en la story): con fecha inválida su texto sigue su propia
   lógica, aunque el `cardClass` que recibe pase a `'default'`.
