# Story Plan: S-048 (web) - Editar un comentario desde el feed

## Status

**Status:** Ready

## Story Reference

- **Story:** [S-048](../stories/S-048.editar-un-comentario-desde-el-feed.md)
- **Service:** `web`
- **Summary:** Dar al feed de actividad del **requisito** la capacidad de editar un comentario
  in-place —que hoy no tiene— y ampliar la que **detalle-tarea** ya tenía: texto y adjuntos en una
  sola escritura, botón visible solo para el autor o un `admin`, y la marca "(editado)" derivada del
  dato real `editedAt` en vez del heurístico `previousValue`. Sin toggle de visibilidad en edición.

---

## Architectural Context

### Tech Stack

- **Lenguaje:** TypeScript 5.9.3 (`strict`, target ES2017, JSX `react-jsx`)
- **Framework:** Next.js 16.1.1 (App Router) + React 19.2.3
- **Runtime:** Node.js >= 24
- **Path en el monorepo:** `web/` (workspace npm `@jiku/web`)
- **Datos:** axios (cliente de **servidor**, `src/lib/axios.ts`) + TanStack Query (único cache)
- **Estilos:** Sass + CSS Modules + custom properties (sin librería de componentes)
- **Tests:** Vitest + Testing Library, jsdom, `TZ=UTC`, tests junto al código
- **Markdown:** `react-markdown` + `remark-gfm` + `remark-breaks` (vía `MarkdownViewer`)

`web` **no consume ningún paquete del monorepo** (`@jiku/models` incluido): sus tipos de dominio
están escritos a mano en `src/features/*/types/`. **Consecuencia directa para esta story:** la api
**ya devuelve** `editedAt` y `editedBy` en cada entrada de actividad (S-047 los escribe y el GET del
requisito hace `toJSON()` del modelo completo), pero **ningún tipo de `web` los declara**, así que
hoy el dato llega y se descarta silenciosamente. Declararlos es la Tarea 1 y es prerrequisito de
todo lo demás.

**Patrón central (data-fetching):** tres capas, ninguna se saltea desde un componente cliente.

```
componente cliente
      │   useRequirement(reqid)                      features/requirements/hooks/
      ▼
  useQuery({ queryKey: ['requirement', reqid] })     ← cache
      │   queryFn
      ▼
  getRequirementById(reqid)                          features/requirements/services/requirementsApi.ts
      │   'use server'
      ▼
  apiClient.patch('/requirements/1/comments/7')      lib/axios.ts (interceptor → Bearer)
      ▼
  api
```

**Reglas de la convención `data-fetching` que aplican acá:**

- Tipo de retorno explícito en cada Server Action. Es el único contrato con la api que el
  compilador conoce.
- Devolver `response.data`, nunca la respuesta de axios: no es serializable a través del límite
  servidor/cliente.
- El `baseURL` ya incluye `/api`. Las rutas empiezan en `/`: `apiClient.patch('/requirements/...')`,
  **no** `/api/requirements/...`.
- **Nunca importar `apiClient` desde un componente cliente.** `auth()` no corre ahí.
- Query keys: `['requirement', reqid]` para el ítem, `['attachments', entityType, entityId]` para
  los adjuntos de una entidad.

**Reglas de la convención `mutations` que aplican acá:**

- **El default es Server Action.** El BFF (`src/app/api/`) se justifica por escrito y solo para lo
  que el navegador tiene que iniciar. **Esta story NO necesita BFF**: no hay progreso de subida que
  atraviese Next (el byte va directo a S3), no hay archivo que recibir y no hay update optimista.
- `PATCH` para modificación parcial.
- **Invalidar en `onSuccess` del hook, no en el componente.** El hook sabe qué keys tocó.
- El hook **no** navega ni muestra toasts. Eso es del componente, que tiene el contexto de la
  pantalla.
- `retry: 0` en mutaciones es el default y es deliberado: reintentar una escritura que ya pudo
  aplicarse duplica registros.
- Un toast de éxito y uno de error por acción del usuario. El mensaje de error prioriza el de la
  api (`err.message`) y cae a un texto propio en español. Nunca se muestra un error crudo de axios.
- `isPending` del hook alimenta el `loading`/`disabled` del botón.

**Manejo de errores (convención `error-handling`), tres niveles:**

| Nivel | Mecanismo | Para qué |
|---|---|---|
| Transporte | Interceptor de respuesta de axios → `ApiError` | Normalizar cualquier fallo de la api |
| Acción del usuario | `toast.error(...)` en el `onError` del `mutate` | Errores recuperables |
| Render | `error.tsx` de la ruta | Excepciones no atrapadas en el render de servidor |

```ts
// src/lib/axios.ts — el contrato que llega a los hooks
export interface ApiError { code: string; message: string; status: number; }
```

El error que llega a un hook o componente es **siempre** un `ApiError` con `code` — eso es lo que
permite discriminar `comment_not_owned` de `activity_not_editable` en el `onError`. El `401` lo
maneja el interceptor en un solo lugar (redirige a `/login`); **no** repetir ese chequeo.

**Testing (convención `testing-unit`):** Vitest + Testing Library, archivos `*.test.tsx` junto al
código, `TZ=UTC` fijado en `vitest.config.mts`, aliases `@/` → `web/src/`, `@root/` → `web/src/`.

### Relevant ADRs

**ADR-001: Separación lectura/escritura.** No impone trabajo a `web` en esta story, pero explica por
qué la escritura va por `PATCH` a la api y no por otro camino: la api publica el comando al bus y
`core` escribe. `web` solo consume HTTP. **La cuarta excepción no declarada (la ruta de tarea que
escribía con el ORM) ya la cerró S-047**: desde el punto de vista de `web` el contrato HTTP de esa
ruta **no cambió** —mismo método, misma URL, mismo status— salvo que ahora acepta `fileIds` y suma
`503`/`504`.

### API Context

**Las dos rutas ya existen y están desplegadas (S-047). Esta story NO cambia la api.**

#### `PATCH /api/requirements/{reqid}/comments/{cid}` — comentario de requisito

Nota: la ruta del requisito es **`/comments/` en plural**; la de tarea es **`/comment/` en
singular**. La asimetría es real y deliberada (renombrar rompería `web` sin beneficio). Copiarlas
tal cual.

```yaml
x-roles: [user, admin]
x-bus-command: requirements.{id}.comment.{cid}.edit
parameters:
  - reqid (path, integer)
  - cid   (path, integer)   # Id de la actividad (comentario)
requestBody:
  required: true
  schema:
    type: object
    required: [comment]
    properties:
      comment: { type: string }
      fileIds: { $ref: '#/components/schemas/FileIds' }
responses:
  '200': Acknowledgement   → { code: 'comment_updated', message: 'Comment Updated' }
  '400': Error — validación fallida, el requisito o el comentario no existen, o la actividad no es
         un comentario editable
  '401': Unauthorized
  '403': Error — no es el autor ni tiene rol admin, o algún fileId no le pertenece
         example: { code: comment_not_owned, message: Access denied }
  '500': InternalError
  '503': BusUnavailable
  '504': GatewayTimeout
```

#### `PATCH /api/objectives/{id}/comment/{cid}` — comentario de tarea

Idéntico en cuerpo y respuestas; cambia la URL y el comando (`tasks.{id}.comment.{cid}.edit`).
**Novedad de S-047 para `web`:** ahora acepta `fileIds` (antes solo `comment`) y suma `503`/`504`.

#### `FileIds` — el esquema compartido

```yaml
FileIds:
  type: array
  maxItems: 10
  items: { type: integer, minimum: 1 }
```

Ids de `files` a vincular (REQ-001, S-003). **Reemplaza a `attachmentIds`.** Cada uno tiene que
existir, estar vivo, y **haber sido subido por el actor de este comando**: si alguno no cumple, la
respuesta es **403 `file_not_owned`** y se descarta toda la escritura — ni la entidad ni un solo
vínculo. Los `files` sí sobreviven, sin vínculo, que es un estado válido. **La titularidad no tiene
excepción por rol:** un administrador tampoco puede vincular un archivo que no subió. El tope de
**10 es regla fija, no configurable**.

> **`visibilityLevel` NO se declara en el requestBody de ninguna de las dos rutas.** El joi de la
> api es `joi.object()` sin `.unknown(true)`, así que **rechaza cualquier campo no declarado**.
> Mandarlo produce un 400. Es inmutable después de creado (RF-8, CA-8).

#### Códigos de error → status (de `api/lib/utils/bus/protocol.ts`)

| `code` | Status | Significado |
|---|---|---|
| `comment_not_owned` | **403** | No es el autor ni tiene rol `admin` |
| `file_not_owned` | **403** | Algún `fileId` lo subió otra persona |
| `activity_not_editable` | **400** | La actividad existe pero no es de un tipo editable |
| `comment_not_found` | **400** | El comentario no existe o fue borrado |
| `requirement_not_found` | **400** | El requisito no existe |
| `service_unavailable` | 503 | El bus no está disponible — **nada ocurrió**, reintentar es seguro |
| `gateway_timeout` | 504 | **Pudo haber ocurrido** — reintentar a ciegas es caro |

#### `GET /api/requirements/{reqid}` — la lectura que alimenta el feed

Devuelve `RequirementWithRelations`. La actividad viaja en `response.activity` (la ruta renombra
`requirementActivities` → `activity`), con `changedByUser` incluido:

```ts
// forma real de cada entrada, tal como llega hoy (api/lib/routes/requirements-id-get.ts)
{
  id: number,
  typeOfActivity: 'state' | 'comment' | 'type' | 'priority' | ... ,
  previousValue: string | null,
  newValue: string,
  visibilityLevel: 'public' | 'internal',
  changedBy: string,                   // el userId del autor
  changedByUser: { id, name, email, identityType },
  editedAt: string | null,             // ← YA VIAJA (S-047). web no lo declara todavía
  editedBy: string | null,             // ← YA VIAJA (S-047). web no lo declara todavía
  createdAt: string
}
```

> **`editedBy` es un id, no un nombre.** La api **no** incluye un `editedByUser`. Para mostrar
> `"(editado por X)"` hay que resolver el nombre desde los datos que la pantalla ya tiene — ver
> "Implementation Notes" de la Tarea 3.

#### `GET /api/attachments?entityType=&entityId=` — los adjuntos de un comentario

Es la única forma de saber qué adjuntos tiene un comentario ya guardado: **el GET del requisito
NO trae los adjuntos de cada entrada del feed**. Devuelve `Attachment[]`:

```ts
interface Attachment {
  id: number;          // id del VÍNCULO (attachments.id)
  fileId: number;      // FK a files — ESTO es lo que va en fileIds
  entityType: EntityType;
  entityId: number;
  fileName: string;
  fileSize: number;
  mimeType: string;
  storageKey: string;
  uploadedBy: string;
  description: string | null;
  createdAt: string;
  uploader: { id: string; name: string; email: string | null };
}
```

`entityType` para los comentarios: `'requirement_comment'` y `'objective_comment'`.

### Flow Context

La story no modifica ningún flujo de sistema: consume las rutas HTTP ya publicadas. El recorrido
completo, para que el implementor sepa dónde termina cada llamada:

**Escenario A — el autor edita su comentario en un requisito (CA-1):**

1. **[`web`]** El feed entra en modo edición inline reutilizando el editor existente. Sin toggle de
   visibilidad (CA-8). Server Action `updateRequirementComment(reqid, cid, payload)`.
   - Payload: `{ comment: "texto nuevo", fileIds: [7, 12] }` — **el conjunto completo que debe
     quedar**, no un delta.
2. **[`api`]** `PATCH /api/requirements/{reqid}/comments/{cid}` → publica
   `requirements.{id}.comment.{cid}.edit` al bus.
3. **[`core`]** valida autoría (o rol `admin`), que la actividad sea un comentario, que
   `visibilityLevel` no venga, y sincroniza los vínculos de archivo. Escribe `newValue`, `editedAt`
   y `editedBy`.
4. **[`web`]** Invalida `['requirement', reqid]`; el feed muestra el texto nuevo con "(editado)"
   derivado de `editedAt`.

**Manejo de errores en `web`:**

| Situación | Comportamiento |
|---|---|
| `comment_not_owned` (403) | Mensaje de error, comentario original se mantiene visible (CA-10) |
| `activity_not_editable` (400) | Mensaje de error — no debería alcanzarse desde la UI porque el botón solo aparece sobre comentarios |
| `comment_not_found` (400) | `"El comentario ya no existe"` — fue borrado mientras estaba en edición |
| `file_not_owned` (403) | Mensaje indicando el adjunto rechazado, la edición no se guarda |
| 503 | `"El servicio no está disponible en este momento"` — nada ocurrió, reintentar es seguro |
| 504 | `"La operación tardó demasiado"` — **pudo haber ocurrido**, reintentar a ciegas es caro |

**Escenario B — el admin edita un comentario ajeno (CA-5):** igual al A. La lectura trae `editedBy`
distinto de `changedBy`; `web` muestra `"(editado por X)"` en vez de solo `"(editado)"`.

### Database Context

**Ninguno.** `web` no toca la base. Las dos columnas (`edited_at`, `edited_by`) las agregó S-046 en
`requirement_activity` y `objective_activity`; son nullable y **solo se completan en actividades de
tipo `comment`**.

### Integration Points

- **`api`** vía `apiClient` (axios de servidor). Único punto de contacto. Auth: `Bearer` del
  `accessToken` de Zitadel, inyectado por el interceptor. **El token nunca llega al navegador.**
- **Storage S3** vía `uploadFile` (subida directa desde el navegador con URL prefirmada). Ya
  implementado; esta story lo reutiliza sin cambios.
- **Sin cola de mensajes, sin webhooks, sin referencias externas** (`docs/references/` no existe).

### Code Conventions

- **Un archivo por hook**, en `features/{módulo}/hooks/use{Verbo}{Recurso}.ts`, con `'use client'`.
- **Un archivo por recurso** en `features/{módulo}/services/{recurso}Api.ts`, con `'use server'` en
  la primera línea.
- Componentes en `features/{módulo}/components/{Nombre}/{Nombre}.tsx` + `{Nombre}.module.scss` +
  `index.ts` (barrel de un solo export).
- El barrel `index.ts` de cada módulo es la superficie pública. **`features/objectives/index.ts`
  re-exporta explícitamente, uno por uno** (línea 36: `export { createComment, updateComment } from

- Props de componente: `readonly` en cada campo de la interfaz.
- Tests junto al código, nombres en español, a menudo prefijados `TS-N (AC-M):`.

#### User flow relevante (superficie `web`, verbatim)

**Editar un comentario ya publicado** — Camino **nuevo desde REQ-011**, y el primero que escribe
sobre una entrada del feed que ya existe. El autor de un comentario —o un `admin`, sobre
cualquiera— entra en edición desde la propia entrada, corrige el texto y agrega o quita adjuntos, y
guarda. **La visibilidad no se puede cambiar**: quedó fijada al publicarlo, porque el comentario ya
pudo haber sido leído por el cliente en el portal (RF-8, CA-8). El feed **no gana una entrada nueva**
—el comentario cambia en su lugar— y la edición **no notifica** (RF-10). Lo que queda visible es una
marca `"(editado)"` junto a la fecha, que dice `"(editado por X)"` cuando quien editó no fue el
autor. **Las entradas de cambio de campo no son editables**: la asimetría es deliberada y es lo que
mantiene confiable el registro (RF-12, CA-12). Se puede editar **cuantas veces se quiera y sin
ventana de tiempo**; solo se conserva la última edición, no un historial (RF-9, CA-7).

**Error — Editar un comentario que ya no se puede editar** — Falla con *"No podés editar un
comentario que no es tuyo"* si la autoría cambió de criterio desde que se cargó la pantalla, o con
*"El comentario ya no existe"* si fue borrado mientras estaba abierto en edición (CA-10, CA-16).
**Ninguno de los dos debería alcanzarse desde esta pantalla.** La recuperación es refrescar.

**Nota de lectura de identidades de servicio:** desde REQ-011 **el comentario de un servicio es
editable por un `admin`**, como cualquier comentario ajeno: la excepción por rol **no distingue** si
el autor es una persona o una identidad de servicio. Para un `user` que no lo escribió sigue sin
haber acción.

## Tasks

### Task 1: Declarar `editedAt` / `editedBy` en los tipos de actividad

#### Description

La api **ya devuelve** `editedAt` y `editedBy` en cada entrada de actividad —S-047 los escribe y los
GET de detalle hacen `toJSON()` del modelo completo—, pero ningún tipo de `web` los declara, así que
hoy el dato llega y se descarta en silencio. Esta tarea los pone en el contrato de TypeScript de los
dos módulos, y separa el payload de edición del de alta.

Es prerrequisito de todo lo demás: sin estos campos declarados, las tareas 3 y 6 no pueden derivar la
marca "(editado)" del dato real, y la 2 no puede tipar el payload sin `visibilityLevel`.

#### Acceptance Criteria

1. `RequirementActivity` declara `editedAt: string | null` y `editedBy: string | null`.
2. `ObjectiveActivity` declara `editedAt: string | null` y `editedBy: string | null`.
3. Existe un tipo `UpdateCommentPayload` con exactamente `{ comment: string; fileIds?: number[] }`

### Task 6: Alinear `ObjectiveComment` (detalle de tarea)

#### Description

Poner el comentario de tarea al mismo nivel que el del requisito: la marca "(editado)" deja de
inferirse de `previousValue` y pasa a `editedAt` con la variante "editado por X", el botón "Editar"
suma la excepción del `admin`, el modo edición gana adjuntos y deja de ofrecer visibilidad, y los
errores se traducen por código.

Es la pantalla que **ya tenía** edición, así que aquí el trabajo es de alineación, no de alta: hay
comportamiento existente que cambia, y ese es el riesgo de regresión de la story.

#### Acceptance Criteria

1. `"(editado)"` se deriva de `editedAt`; `previousValue` **deja de usarse** para ese fin.
2. Un comentario con `previousValue` pero sin `editedAt` **no** muestra la marca (decisión de CA-7,
   documentada en Test Scenarios).
3. Con `editedBy` distinto del autor, muestra `"(editado por {nombre})"`.
4. El botón `"Editar comentario"` aparece para el autor **o** para un `admin`; para el resto no se
   renderiza.
5. El modo edición muestra los adjuntos actuales del comentario, permite quitarlos y sumar propios,
   y manda el conjunto completo de `fileIds`.
6. El modo edición **no** ofrece el checkbox de comentario público.
7. `"Cancelar"` restaura el contenido original sin llamar a la api.
8. Los errores se traducen con `commentErrorMessage`; en particular `comment_not_owned` muestra
   `"No podés editar un comentario que no es tuyo"`.
9. El tooltip de la fecha puede mostrar la fecha de última edición junto a la de creación.
