## Architectural Context

### Frontera: qué toca este plan y qué no

La story declara tres filas en *Servicios Afectados*. Este plan cubre **solo la primera**.

| Fila de la story | Impacto | Quién la resuelve |
|---|---|---|
| `packages/nats-protocol` | Bajo | **Este plan.** Helpers de subjects por `serviceName`, `MODULES_BUCKET`, `ModuleRecord`, `generateUlid` (movido de core) |
| `api` | Alto | Plan `S-077.api.*`: extensión del `Bus` (KV `bindOnly` + watch, ping, request a un servicio de módulo), `lib/modules/registry.ts`, `requireModule`, `GET /modules`, `GET /opus/modules`, `lib/modules/docs/errors.ts`, cuerpo `{code, message, details?}`, doble de test |
| `core` | Bajo | Plan `S-077.core.*`: solo re-apunta el import de `generateUlid` (y retira su copia local) |

### Fuera de alcance (declarado, para no improvisarlo)

- **NINGÚN cliente NATS, ningún KV, ningún watch, ningún ping real.** El paquete arma **strings**.
  `js.views.kv('JIKU_MODULES', { bindOnly: true })`, el `kv.watch({ key: 'docs' })`, el
  `request('$SRV.PING.jiku-docs-queries', '', { timeout: 2000 })` y el temporizador de 30 s son
  del plan de la **api**. `MODULES_BUCKET` existe para que esa llamada no escriba el literal.
- **NINGÚN cálculo de estado del módulo.** `not_installed` / `incompatible` / `unavailable` /
  `available` es lógica de `api/lib/modules/registry.ts`. El paquete **no** exporta un tipo
  `ModuleStatus`, ni un `SUPPORTED_PROTOCOL = 'v1'`, ni una función `isCompatible()`: la story
  enumera los símbolos exactos del paquete (ver *API Context*) y ninguno de esos está.
- **NINGUNA validación de `ModuleRecord` completo.** Validar el JSON leído del KV (campos
  requeridos, `protocol` contra `^v[0-9]+$`, JSON inválido → `incompatible`) es de la api (paso 2
  del flujo). El paquete declara la **interfaz** y valida **únicamente** `serviceName`, y solo
  dentro de los helpers de subject — es la defensa que impide inyectar tokens NATS, no un
  validador del registro. Misma regla que `Actor` y `AuthEvent` (`src/index.ts:617-619`): *"ACÁ NO
  HAY VALIDACIÓN NI FUNCIONES […] este paquete es el contrato del cable"* — con la única excepción
  que la story pide explícitamente.
- **NINGÚN código de error de docs.** El mapa `lib/modules/docs/errors.ts` (400/403/404/409/503/504)
  es de la api y **NO se mezcla** con `ErrorCode` de este paquete ni con `STATUS_BY_ERROR_CODE` de
  core (story, *Mapa de errores de docs*). `ErrorCode` **no gana miembros** en este plan: TS-49 sigue
  diciendo 35.
- **NINGUNA variable de entorno nueva.** `{version}` de un módulo es el `protocol` del registro,
  **no** `PROTOCOL_VERSION` ni una `NATS_MODULE_PROTOCOL`. `deploy/.env.dist` no se toca, y
  `tests/helpers/reload.ts` tampoco (sigue reseteando cinco variables).
- **NINGUNA dependencia de npm.** `generateUlid` usa `randomBytes` de `node:crypto`, el mismo módulo
  builtin que el paquete ya importa para `hashUserId()`. **No agregar `ulid`, `nanoid` ni nada** al
  `package.json` (D-2 de la planificación de REQ-014, conservada por REQ-016).
- **`docs/apis/jiku-modules.yaml` NO se edita.** Ya existe y es la fuente de verdad del registro
  (verificado sobre el árbol). Este plan lo **lee** en un test de paridad (Task 4). Si algo
  discrepa, manda el yaml y es un bug del paquete.
- **`deploy/nats/auth-callout/templates/*` NO se tocan.** Los permisos (`$KV.JIKU_MODULES.docs`,
  `$SRV.PING.jiku-docs-queries`, etc.) son S-075, ya completada.
- **Los flujos `docs/flows/descubrimiento-de-modulos.md`, `consulta-por-el-bus`,
  `escritura-por-el-bus`** se escriben en S-085, no acá.

### Relevant ADRs

**ADR-005: Modelos compartidos en `@jiku/models`, sin abrir la conexión** — el catálogo de
reusable-code lo invoca para este paquete por su principio: un paquete compartido es contrato, no
lógica, y **no gana dependencias**. Sus reglas literales son de `@jiku/models` y no aplican
textualmente acá; el principio sí: `generateUlid` entra **sin dependencia**, con `node:crypto`.

**ADR-012: Monorepo npm con contexto de build en la raíz**
- Decision: npm workspaces; los paquetes se consumen compilados.
- Implementation Rules (verbatim):
  - Todo servicio y paquete **DEBE** ser un workspace declarado en el `package.json` de la raíz.
  - Un Dockerfile **DEBE** construirse con contexto en la **raíz del monorepo**, no en la carpeta del
    servicio. **NO SE DEBE** usar `docker build .` desde la carpeta del servicio: falla al no
    alcanzar `packages/`.
  - Los Dockerfiles **DEBEN** copiar los manifiestos antes del código fuente, para preservar el cacheo
    de `npm ci`.
  - Los frontends **DEBEN** instalar con `--ignore-scripts`: no consumen `packages/*` compilados.
  - El gestor de paquetes **DEBE** ser **npm** con workspaces. **NO SE DEBEN** usar yarn, pnpm ni bun.
  - Un cambio en `packages/*` **DEBE** ejecutarse con los tests de **todos** los servicios que lo
    consumen antes de mergear.
  - Los cuatro servicios **DEBEN** correr sobre `node:24.12-alpine3.23` con usuario no-root, y usar
    build multi-stage.
  - Una imagen **NO DEBE** hornear configuración: sin `ARG` de entorno ni `NEXT_PUBLIC_*` funcional
    ([ADR-009](../adrs/ADR-009-token-confinado-al-servidor.md)).
- Aplicación: la regla *"Un cambio en `packages/*` DEBE ejecutarse con los tests de todos los
  servicios que lo consumen"* es la Task 6 (api + core).

**ADR-002: Toda mutación es un comando NATS request/reply, sin JetStream**
- Implementation Rules relevantes (verbatim):
  - Todo comando **DEBE** publicarse con el subject `{instance}.{user-id}.gestion.v1.{comando}`,
    usando la gramática de `@jiku/nats-protocol`. **NO SE DEBE** construir el subject a mano.
  - El cliente NATS **DEBE** fijar `inboxPrefix` explícitamente al conectar, con el hash del user id
    que calcula `@jiku/nats-protocol`. Sin esto las respuestas no llegan.
  - Toda respuesta **DEBE** tener el formato `{ status: 'success', data }` o
    `{ status: 'failure', errorCode, errorMessage }`. **NO SE DEBEN** inventar otros formatos.
- Aplicación: *"NO SE DEBE construir el subject a mano"* es **la razón de existir** de
  `moduleCommandSubject`/`moduleQuerySubject`/`modulePingSubject`: la api llama a jiku-docs con la
  misma gramática `{instance}.{user-id}.{svc}.{version}.{método}` y tiene que hacerlo desde este
  paquete, no concatenando en `api/`.

**ADR-008: Autorización deny-by-default** — aplica por H-2 de REQ-016: la política del bus
autoriza subjects **literales** (`{instance}.*.jiku-docs-commands.v1.>`). El paquete arma el
subject correcto para **cualquier** `serviceName` válido (CA-8 con `otro-docs`); que el bus real lo
acepte exige un cambio deliberado de política. **El paquete no debe intentar "compensar" eso** (por
ejemplo, forzando `jiku-docs`): CA-8 se verifica con el subject armado.

### API Context

#### Símbolos que la story fija (verbatim de la story, *Paquete `@jiku/nats-protocol`*)

```ts
export const MODULES_BUCKET = 'JIKU_MODULES';   // stream subyacente KV_JIKU_MODULES
export interface ModuleRecord { module: string; serviceName: string; protocol: string; registeredAt: string; }
export function moduleCommandSubject(serviceName: string, protocol: string, method: string, userId: string): string;
export function moduleQuerySubject(serviceName: string, protocol: string, method: string, userId: string): string;
export function modulePingSubject(serviceName: string): string;   // `$SRV.PING.${serviceName}-queries`
export function generateUlid(): string;                            // movido desde core/src/ulid.ts
```

Reglas (verbatim de la story y de REQ-016):

- *"`{version}` es el `protocol` del módulo, no `PROTOCOL_VERSION` de core."* REQ-016 agrega: *"son
  contratos independientes (mismo argumento por el que `EVENTS_VERSION` no comparte variable)"*.
- *"`serviceName` se valida contra `^[a-z][a-z0-9-]{1,40}$` antes de armar el subject (sin
  inyección de tokens por `.`, `*`, `>`)."*
- *"`generateUlid` se mueve sin cambiar la implementación; core re-apunta su import."* REQ-016:
  *"D-2 de la planificación de REQ-014 se conserva: implementación propia, sin dependencia"*.
- REQ-016, comentario del bloque: *"Subjects de un módulo: misma gramática
  `{instance}.{user-id}.{svc}.{version}.{método}`, con `{svc}` = `${serviceName}-commands` |
  `${serviceName}-queries` y `{version}` = protocolo del módulo"*.

#### Gramática resultante (derivada de lo anterior, sin agregar nada)

| Helper | Forma | Ejemplo (`NATS_INSTANCE` sin definir → `dev`) |
|---|---|---|
| `moduleCommandSubject('jiku-docs', 'v1', 'documents.new', '323332022539911171')` | `${INSTANCE}.${userId}.${serviceName}-commands.${protocol}.${method}` | `dev.323332022539911171.jiku-docs-commands.v1.documents.new` |
| `moduleQuerySubject('jiku-docs', 'v1', 'documents.list', '323332022539911171')` | `${INSTANCE}.${userId}.${serviceName}-queries.${protocol}.${method}` | `dev.323332022539911171.jiku-docs-queries.v1.documents.list` |
| `modulePingSubject('jiku-docs')` | `$SRV.PING.${serviceName}-queries` | `$SRV.PING.jiku-docs-queries` |

- **`INSTANCE` sí entra** en comandos y consultas (es el primer token de la gramática del bus);
  **`COMMAND_SERVICE`, `QUERY_SERVICE` y `PROTOCOL_VERSION` NO entran** — son de core.
- **`modulePingSubject` no lleva `INSTANCE`**: `$SRV.PING.{name}` es el subject de descubrimiento
  del framework micro de NATS, que no conoce la gramática de Jiku. Es literalmente lo que fija la
  story y `jiku-modules.yaml` (`pub $SRV.PING.{serviceName}-queries`).
- **El orden de parámetros es el de la story**: `(serviceName, protocol, method, userId)`. Es
  distinto de `commandSubject(command, userId)`, y los cuatro son `string`: invertir dos es un bug
  que el compilador **no** atrapa. Los tests fijan cada posición con valores distinguibles.
- `methodFromSubject()` y `callerFromSubject()` existentes **siguen funcionando** sobre un subject
  de módulo sin cambios (el `{svc}` `jiku-docs-queries` es un solo token por llevar guiones):
  `methodFromSubject('dev.u1.jiku-docs-queries.v1.documents.list') === 'documents.list'`.

#### Validación de `serviceName` (decisión de este plan sobre la forma, no sobre la regla)

La story fija **la regla** (patrón y momento: "antes de armar el subject"); no fija **cómo falla**.
Este plan decide:

- Una constante **privada del módulo** (no exportada — la story no la lista):
  `const MODULE_SERVICE_NAME_PATTERN = /^[a-z][a-z0-9-]{1,40}$/;` — verbatim de
  `jiku-modules.yaml` (`ModuleRecord.serviceName.pattern`).
- Una función **privada** `assertModuleServiceName(serviceName: string): void` que, si no matchea,
  **lanza** `new Error(\`[nats-protocol] serviceName de módulo inválido: ${JSON.stringify(serviceName)}\`)`.
- Los **tres** helpers la llaman como **primera línea**, antes de cualquier interpolación.
- **Se lanza, no se sanea ni se devuelve `''`**: un subject saneado (`jikudocs`) iría a otro
  servicio, y uno vacío produce un error de NATS lejos del origen. Un `serviceName` inválido es un
  registro corrupto o malicioso, y la api ya lo habrá clasificado `incompatible` al validar el
  `ModuleRecord` (paso 2 del flujo); el `throw` es la segunda línea de defensa, no la primera.
- **`protocol` y `method` NO se validan** en el paquete: la story pide validar solo `serviceName`.
  `protocol` llega a un subject únicamente cuando la api ya verificó `protocol === 'v1'`; `method`
  lo escribe el código de la api, igual que el `command` de `commandSubject()`, que tampoco se
  valida. **Anotado, no resuelto.**

Casos del patrón (`^[a-z][a-z0-9-]{1,40}$` → 2 a 41 caracteres, primera letra minúscula):

| Valor | ¿Válido? | Por qué |
|---|---|---|
| `jiku-docs` | Sí | el caso real |
| `otro-docs` | Sí | CA-8 |
| `ab` | Sí | mínimo: 1 + 1 |
| `a` + 40 × `b` (41 chars) | Sí | máximo: 1 + 40 |
| `a` | **No** | 1 char, el cuantificador exige al menos 1 más |
| `a` + 41 × `b` (42 chars) | **No** | excede 41 |
| `jiku.docs` | **No** | `.` inyectaría un token |
| `jiku-docs.>` | **No** | `.` y `>` |
| `*` | **No** | wildcard |
| `>` | **No** | wildcard |
| `` (vacío) | **No** | token vacío |
| `Jiku-docs` | **No** | mayúscula |
| `1docs` | **No** | empieza con dígito |
| `-docs` | **No** | empieza con guion |
| `jiku_docs` | **No** | `_` fuera del patrón |
| `jiku docs` | **No** | espacio |

#### `ModuleRecord` (fuente de verdad: `docs/apis/jiku-modules.yaml`, copiado verbatim)

```yaml
ModuleRecord:
  type: object
  required: [module, serviceName, protocol, registeredAt]
  properties:
    module: { type: string, pattern: '^[a-z][a-z0-9-]{1,30}$', description: Igual a la clave del KV. }
    serviceName: { type: string, pattern: '^[a-z][a-z0-9-]{1,40}$', description: 'Prefijo de los servicios micro {serviceName}-commands y {serviceName}-queries (y de sus subjects). No afecta los subjects de eventos ni notificaciones.' }
    protocol: { type: string, pattern: '^v[0-9]+$', description: Versión de los contratos del módulo. }
    registeredAt: { type: string, format: date-time, description: Informativo. }
```

Ejemplo del contrato:

```json
{ "module": "docs", "serviceName": "jiku-docs", "protocol": "v1", "registeredAt": "2026-10-24T12:00:00.000Z" }
```

Reglas del registro (verbatim de la `description` de `jiku-modules.yaml`, las que tocan al paquete):

- *"Bucket KV de JetStream `JIKU_MODULES` (stream subyacente `KV_JIKU_MODULES`)."*
- *"Convención: un módulo con `serviceName: X` atiende los servicios NATS micro `X-commands` y
  `X-queries`."*
- *"Campos nuevos dentro de v1 son opcionales y no rompen compatibilidad: los lectores deben
  tolerarlos."* → por eso la interfaz declara **exactamente los cuatro** campos y **no** se marca
  cerrada de ninguna forma: un campo extra en el JSON no es un error de tipos para quien lo lea.
- *"`serviceName` solo nombra los servicios micro […]. Los subjects de eventos y notificaciones de
  cada módulo son fijos y los define su propio contrato (para docs: `{instance}.docs-events.v1.>` y
  `{instance}.{userId}.docs-notify.v1.>`)."* → **no** se agrega ningún helper de eventos ni de
  notificaciones de módulo.

La interfaz va con `registeredAt: string` (ISO 8601, *informativo*), **no** `Date`: es el cable,
mismo criterio que `occurredAt` en `DomainEvent`.

### Flow Context

El flujo **descubrimiento-de-modulos** todavía no existe como documento (se escribe en S-085). Se
copia el escenario de la story porque es lo que consume los símbolos de este plan:

> **Trigger:** arranque de la api; cambio de la clave `docs`; temporizador de 30 s.
>
> 1. **[api — registry, al arrancar]** `kv = js.views.kv('JIKU_MODULES', { bindOnly: true })`;
>    `kv.get('docs')`. Sin entrada → `not_installed`. Bucket inexistente o bus caído →
>    `not_installed` + log de error + reintento a los 30 s (DD-6: no tumba la api).
> 2. **[api]** Con entrada: valida contra `ModuleRecord`; `protocol !== 'v1'` → `incompatible` +
>    `logger.error('[modules] docs: protocolo v2 no soportado (soportado: v1)')`. JSON inválido →
>    `incompatible` + log, el watch sigue.
> 3. **[api → NATS]** `request('$SRV.PING.jiku-docs-queries', '', { timeout: 2000 })`: respuesta →
>    `available`; `no responders`/timeout → `unavailable`.
> 4. **[api]** `kv.watch({ key: 'docs' })`: `PUT` vuelve al paso 2; `DEL`/`PURGE` → `not_installed`.
> 5. **[api, cada 30 s]** repite el ping con registro `v1`.
> 6. **[cualquier ruta de docs]** `no responders` → `unavailable` inmediato + re-ping.

Dónde entra este paquete en cada paso:

| Paso | Símbolo del paquete |
|---|---|
| 1 | `MODULES_BUCKET` (en lugar del literal `'JIKU_MODULES'`) |
| 2 | `ModuleRecord` (tipo del valor leído) |
| 3, 5, 6 | `modulePingSubject(record.serviceName)` |
| consultas/comandos de docs (S-078/S-079) | `moduleQuerySubject(record.serviceName, record.protocol, método, apiUserId)` / `moduleCommandSubject(...)` — CA-8 |
| altas con id (DD-8, S-079) | `generateUlid()` — la api genera los ULID de `documents.new`, `attachments.request-upload`, `shares.new` si el cliente no manda `id`. **Esta es la razón por la que el ULID se muda de core al paquete**: ahora lo necesitan dos servicios |

```ts
const CROCKFORD_ALPHABET = '0123456789ABCDEFGHJKMNPQRSTVWXYZ';

const TIME_CHARS = 10;
const RANDOM_CHARS = 16;
/** 16 caracteres base32 de 5 bits = 80 bits, la parte aleatoria del ULID. */
const RANDOM_BYTES = 10;

/** Codifica `value` (hasta 48 bits) en `length` caracteres Crockford base32, con ceros a la izquierda. */
function encodeTime(value: number, length: number): string {
  let output = '';
  let remaining = value;
  for (let i = 0; i < length; i++) {
    output = CROCKFORD_ALPHABET[remaining % 32] + output;
    remaining = Math.floor(remaining / 32);
  }
  return output;
}

/** Codifica los bytes aleatorios en Crockford base32, a `length` caracteres. */
function encodeRandom(bytes: Buffer, length: number): string {
  let bits = 0;
  let value = 0;
  let output = '';
  for (const byte of bytes) {
    value = (value << 8) | byte;
    bits += 8;
    while (bits >= 5 && output.length < length) {
      output += CROCKFORD_ALPHABET[(value >>> (bits - 5)) & 31];
      bits -= 5;
    }
  }
  if (output.length < length && bits > 0) {
    output += CROCKFORD_ALPHABET[(value << (5 - bits)) & 31];
  }
  return output.slice(0, length);
}

export function generateUlid(now: number = Date.now()): string {
  return encodeTime(now, TIME_CHARS) + encodeRandom(randomBytes(RANDOM_BYTES), RANDOM_CHARS);
}
```
