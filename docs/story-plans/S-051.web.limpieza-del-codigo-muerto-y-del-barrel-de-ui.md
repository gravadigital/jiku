# Story Plan: S-051 (web) - Limpieza del código muerto y del barrel de UI

**Status:** Completed

## Referencia de la Story

- **Story:** [S-051](../stories/S-051.limpieza-del-codigo-muerto-y-del-barrel-de-ui.md)
- **Servicio:** `web`
- **Resumen:** Eliminar del árbol de archivos y del barrel `shared/components/ui/index.ts` los
  siete componentes muertos (`Card`, `Header`, `Input`, `Textarea`, `MarkdownEditor`,
  `MultiSelect`, `AttachmentDownload`), para que cuando S-053 en adelante creen los componentes
  nuevos del Design System no exista ningún nombre previo al que un import pueda resolver en
  silencio.

### Los dos tests de CA-3 — qué dicen realmente

CA-3 nombra `Pagination.test.tsx:205` y `RequirementDetail.test.tsx:573` como tests que leen el
código fuente como string y hay que **actualizar, no borrar**. Al leerlos, lo que verifican es:

**`src/shared/components/ui/Pagination/Pagination.test.tsx` — TS-26:**

```tsx
it('TS-26: el barrel público sigue exportando el componente', async () => {
  const fs = await import('node:fs/promises');
  const path = await import('node:path');
  const barrelSource = await fs.readFile(path.resolve(__dirname, '../index.ts'), 'utf-8');
  expect(barrelSource).toContain("export { Pagination } from './Pagination';");

  const { Pagination: PaginationFromLocalIndex } = await import('./index');
  expect(typeof PaginationFromLocalIndex).toBe('function');
});
```

Y un segundo `describe` ("grep de control") que lee `Pagination.tsx` y verifica que no contiene
`/objectives`, `useEffect`, `useState`, `…` ni `ellipsis`.

**`.../RequirementDetail/RequirementDetail.test.tsx` — TS-12:** lee
`RequirementDetail.module.scss` y verifica que **no** existan `.objPagination`, `.pageBtn`,
`.pageBtnActive` ni `.objPaginationEllipsis` (las clases del paginador inline eliminado).

**Consecuencia para esta story — importante:** ninguno de los dos test se rompe al eliminar los
siete componentes. TS-26 afirma la presencia del export de `Pagination`, que **sobrevive**; TS-12
lee un SCSS que no se toca. La restricción arquitectónica que verifican se conserva sin editar
una línea.

Por eso la tarea sobre estos tests es **verificar que siguen en verde y dejar constancia**, no
reescribirlos preventivamente. Reescribirlos "para reflejar el barrel nuevo" sería debilitar dos
aserciones que hoy son correctas. Si al correr la suite alguno falla, ahí sí se actualiza
conservando la restricción — que es exactamente lo que CA-3 pide.

### Convenciones activas (de `docs/architectures/web/manifest.yaml`)

Todas las convenciones de `web` son **custom** (viven en
`docs/architectures/web/conventions/`), no del catálogo de Next.js. Las relevantes acá:

**`styling` — Sass + CSS Modules:**

- Un módulo `.scss` por componente, junto al `.tsx`, en la misma carpeta.
- Nombre del módulo = nombre del componente.
- Clases en `camelCase`.
- **Consecuencia para esta story:** eliminar un componente implica eliminar su `.module.scss`
  hermano. No hay estilos globales que limpiar por separado — ningún token ni clase de estos
  siete vive en `globals.scss` ni en `_variables.scss` (verificado: `globals.scss` no referencia
  `easymde`).

**`testing-unit` — Vitest + Testing Library:**

- Tests **junto al código**, como `{Nombre}.test.tsx`. No hay carpeta `__tests__/`. `tests/` en la
  raíz tiene **solo** el setup.
- `TZ: 'UTC'` fijado en `vitest.config.mts` — no se toca.
- Alias declarados a mano en `vitest.config.mts` (`@`, `@root`, `@public`).
- Nombres de test en **español**, describiendo comportamiento observable.
- `getByRole` antes que `data-testid`; `userEvent` antes que `fireEvent`; `queryBy*` para
  aserciones de ausencia.
- Estado actual de la suite: **73 archivos de test, 644 casos, 109 bloques `describe`**.
- Comandos: `npm test --workspace web` (vitest run) y `npm run lint --workspace web`.

**Convención de módulos de dominio:** el barrel `index.ts` de cada módulo es la superficie
pública; las rutas importan de ahí, no de rutas profundas. Por eso el barrel es el punto de
control de esta story: sacar el export es lo que hace inalcanzable al componente.

### Código reutilizable relevante

Del catálogo `docs/reusable-code/web/`, lo que importa acá es **qué sobrevive**, porque son los
componentes contra los que S-053+ crearán los nuevos y los que no hay que tocar por error:

| Componente vivo | Por qué no se toca |
|---|---|
| `Button`, `AddButton` | En uso; `Button` es el destino de la migración de S-053 |
| `InputText`, `InputTextarea`, `InputDate` | En uso — **son los que están vivos**, a diferencia de `Input`/`Textarea` que son los muertos. Los nombres se parecen: no confundirlos |
| `InputSelect`, `InputMultipleSelect`, `InputMultiplePersons`, `Select` | En uso (react-select); `InputSelect` se da de baja recién en S-060 |
| `SectionCard` | En uso — es la card viva, `Card` es la muerta |
| `MarkdownEditorWithPreview`, `CommentEditor`, `InlineCommentEditor`, `RichTextEditor` | En uso — son los editores vivos; `MarkdownEditor` es el muerto. `MarkdownEditorWithPreview` **no** depende de `MarkdownEditor` (usa `MarkdownViewer` + `ToggleGroup`) |
| `AttachFileButton`, `AttachmentPreview`, `AttachmentSkeleton` | En uso — `AttachmentDownload` es el muerto |
| `Pagination`, `Loader`, `Spinner`, `Tooltip`, `ToggleGroup`, `ConfirmDialog`, `DatePicker`, `DateLabel`, `FinishDateLabel`, `AutomatedIdentityBadge`, `TintedIcon` | En uso |

**El riesgo real de esta story es borrar el vecino equivocado.** Cuatro de los siete muertos
tienen un homónimo vivo con nombre casi idéntico (`Input` vs `InputText`, `Textarea` vs
`InputTextarea`, `Card` vs `SectionCard`, `MarkdownEditor` vs `MarkdownEditorWithPreview`). Las
tareas usan rutas de carpeta completas por eso.

## Contexto de Design System

**Superficie:** `web` · **DS versión:** `2.4.0` (normativo, pendiente de implementación) ·
**Accent de la superficie:** `#61CCB9` (`color.brand.primary`, Manual de marca Jiku v1.0). El
magenta `#DA2C6A` que sirve hoy el código queda descontinuado por REQ-013.

**Viewport:** `desktop` (único). El shell impone un solo viewport — la sidebar mide 290 px fijos y
el layout de `(loggedin)` no tiene ningún media query. **No hay segundo layout que testear**, así
que esta story no lleva escenarios de viewport ni de breakpoint.

### Por qué esta story es de DS aunque no cree ninguna UI

No renderiza nada nuevo: **habilita** que lo nuevo se pueda crear. Tres nombres del catálogo del
DS colisionan exactamente con tres componentes muertos:

| Spec del DS que S-053+ va a implementar | Componente muerto homónimo | Riesgo si no se borra primero |
|---|---|---|
| `docs/design-system/web/components/card.md` | `ui/Card/` | `import { Card } from '@/shared/components/ui'` resuelve al muerto |
| `docs/design-system/web/components/input.md` | `ui/Input/` | ídem |
| — (sin spec `textarea.md`) | `ui/Textarea/` | Sin colisión directa de spec, pero el nombre queda ocupado |

REQ-013 lo declara como su riesgo principal: *"Si se crea `Card` antes de borrar el muerto, el
import resuelve al muerto y el error es silencioso: compila y se ve mal."* De ahí que S-051 vaya
primera y bloquee S-052 a S-060.

Nota: el catálogo del DS `web` tiene 21 componentes normativos + 1 deprecado (`input-select.md`).
**No existe `textarea.md`** — el DS resuelve el texto multilínea dentro de `input.md`. Es
información para S-053, no una tarea de esta story.

### Gaps del Design System — superficie `web`

**Aceptados** (resueltos como "Dejar anotado" en la `## Revisión UX` de REQ-013 — son decisiones
tomadas, no hallazgos):

| Bloque | Decisión registrada |
|---|---|
| `alert` (13 usos) | Sin componente propio. El DS resuelve el error *dentro* del control (`Input.error`, `Select.error`) y el de pantalla con `EmptyState`; no especifica banner de página |
| `toast` (5 usos) | Sin componente. Coherente con el alcance: REQ-013 excluye el microcopy de los 52 toasts, que es donde el toast se define. Especificarlo adelantaría una decisión de FG-5 |
| `progress-bar` (4 usos) | 3 son barras de subida de adjunto: uso puntual, se resuelven inline. El cuarto es `stepper-workflow`, que se implementa con el componente `Stepper` (que sí existe) |

**Nuevos:** ninguno. La revisión UX de REQ-013 cruzó los 29 tipos de bloque en uso contra el
catálogo y **no dejó ningún `pendiente-DS`**: no hay componente por crear que bloquee esta
planificación.

**Ninguno de los tres gaps aceptados afecta a S-051**, que no renderiza UI. Se documentan acá
porque el Story Plan debe ser autocontenido y el implementador de las stories siguientes los va a
necesitar.
