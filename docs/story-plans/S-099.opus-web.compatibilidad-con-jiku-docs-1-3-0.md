# Story Plan: S-099 (opus-web) - opus-web: compatibilidad con jiku-docs 1.3.0

## Status

**Status:** Completed

## Story Reference

- **Story:** [S-099](../stories/S-099.opus-web-compatibilidad-con-jiku-docs-1-3-0.md)
- **Service:** `opus-web`
- **Origen:** [REQ-021](../requests/REQ-021.documentacion-sin-carpetas-en-la-web.md) (decisión 12, RF-19, CA-25, CA-26)
- **Summary:** La api ya pide a jiku-docs `fields` explícitos sin ruta para el portal (S-094,
  completada). opus-web acompaña: los tipos de `features/docs` pasan a describir **lo que
  `/api/opus/docs/*` devuelve con el contrato 1.3.0** (sin `path`, `folderId` ni `fileName`;
  `visibility` con `restricted`), `stripFrontmatter` queda como defensa documentada y se agregan
  tests de no regresión del portal (lista, documento y avisos de módulo). Ninguna pantalla cambia.

> **Precondición verificada sobre el árbol (2026-10-26):** S-094 está `Completed`. La api define
> `PORTAL_DOC_FIELDS = ['id', 'title', 'version', 'visibility', 'createdAt', 'updatedAt']`
> (`api/lib/modules/docs/query.ts:41`) y lo usan `api/lib/routes/opus-docs-documents-get.ts` y
> `api/lib/routes/opus-docs-documents-id-get.ts` (este último con `include: ['content', 'attachments']`).
> En opus-web, `src/features/docs/types/docs.types.ts` todavía declara `path?`, `folderId?`,
> `fileName?` en `DocsDocument` (sin usos en componentes: la UI usa `id`, `title`, `updatedAt`,
> `content`/`contentUrl` y `attachments[].id/documentId/fileName`). `stripFrontmatter` ya existe y
> `DocumentMarkdown` ya lo aplica.

### Fuera de alcance (declarado, para no improvisarlo)

- **Rediseñar el portal.** La revisión UX de REQ-021 dejó `opus-web` *"verificada sin cambios de
  interfaz: su pantalla `documento` nunca mostró ruta ni carpeta y ya quita el frontmatter; el ajuste
  de la decisión 12 es de tipos y de los campos que recibe"*.
- **Mostrar `version`, `visibility` o `createdAt`.** Llegan, pero la pantalla dice *"sin autor ni
  versión: al cliente le sirve saber si es reciente"*. Se declaran en el tipo; no se renderizan.
- **Quitar `stripFrontmatter`.** CA-3: queda como defensa aunque jiku-docs 1.3.0 ya no mande
  frontmatter a un externo.
- **Chequeo de versión de jiku-docs en runtime.** Riesgo de REQ-021: el registro no publica la versión
  menor; se cubre con las notas del CHANGELOG, no en opus-web.

### Convenciones activas que aplican (extracto)

**testing-unit (custom de opus-web):**
- Tests de componentes/utils/tipos **junto al código**; `__tests__/` solo para route handlers.
- Mockear hooks/servicios (`vi.mock('../../hooks/useDocuments')`), no `fetch` ni axios — excepción
  ya justificada en `docsApi.test.ts` (*"es el test del propio servicio"*).
- No mockear `react-markdown` (aliaseado globalmente). No mockear la zona horaria (TZ fijada).
- Aserciones por rol y texto (`getByRole`, `getByText`). IDs de escenario en el nombre del `it`.

**data-fetching:** `docsApi.list(scope, cursor?)` → `GET /api/opus/docs/documents` con
`params: { ...scope, limit: DOCS_PAGE_SIZE (5), cursor? }`; `docsApi.getById(id)` →
`GET /api/opus/docs/documents/{id}` y, si viene `contentUrl` sin `content`, descarga el texto con
`fetch` nativo. **No cambia en esta story.**

**error-handling:** `ApiError { code, message, status }`. `DocsSection`: `module_not_installed` →
nada; 403 o `caller_not_authorized` → `MSG_DOCS_FORBIDDEN`; resto → `MSG_DOCS_UNAVAILABLE`.
`DocumentView`: `classifyDocumentError` → not found / unavailable / sistema. **No cambia.**

**styling:** sin cambios; no se tocan `.module.scss`.

### Relevant ADRs

- **ADR-015: Módulos opcionales del bus** — el módulo `docs` es opcional: `not_installed` oculta la
  sección (y el documento responde como no encontrado), `unavailable` muestra el aviso. CA-4 de la
  story exige que eso no regrese. DD-3: el portal solo muestra `public`, falla cerrado (lo hace la api).
- **ADR-009: Token confinado al servidor** — en opus-web toda llamada va por el proxy
  `/api/opus/[...path]`; no se agrega ningún cliente. Esta story no toca llamadas.

### API Context

**Rutas que consume el portal** (`docs/apis/api.yaml`, verbatim de las descripciones):

`GET /opus/docs/documents` — *"Llama a `documents.list` con `filter: { projectId | requirementId,
visibility: 'public' }`: **`visibility: public` lo fuerza la api** y la query no lo acepta (400).
Exige exactamente uno de `projectId` o `requirementId`. Orden `-updatedAt`, sin `include`. Pide
`fields: [id, title, version, visibility, createdAt, updatedAt]`: **sin `path`, `folderId` ni
`fileName`** (el portal no recibe la ruta)."* Query: `projectId` | `requirementId`, `limit`
(1..200), `cursor`. 200 → `DocsDocumentPage`.

`GET /opus/docs/documents/{id}` — *"Llama a `documents.get` con `include: ['content', 'attachments']`
y los mismos `fields` sin ruta que el listado (`visibility` tiene que estar: sin ella el chequeo de
abajo fallaría cerrado). Si `visibility` no es `public` (o falta), responde 404 `document_not_found`,
idéntico al de un id inexistente (DD-3). No compone `folder` ni devuelve `path`."* 200 →
`DocsDocument`.

**Lo que efectivamente llega al portal con 1.3.0** (de `PORTAL_DOC_FIELDS` + `include`):

| Campo | Listado | Detalle | Tipo (1.3.0) |
|---|---|---|---|
| `id` | sí | sí | `string` (ULID) |
| `title` | sí | sí | `string` |
| `version` | sí | sí | `integer` |
| `visibility` | sí (`public`) | sí (`public`) | `internal \| public \| restricted` |
| `createdAt` | sí | sí | `string` date-time |
| `updatedAt` | sí | sí | `string` date-time |
| `content` | — | ≤ 256 KiB | `string` |
| `contentUrl` | — | > 256 KiB (vence a los 300 s) | `string` |
| `attachments` | — | sí | `DocsAttachment[]` |

**`DocsAttachment`** (verbatim, sin cambios):
```yaml
DocsAttachment:
  type: object
  properties:
    id: { type: string }
    documentId: { type: string }
    fileName: { type: string }
    mimeType: { type: string }
    sizeBytes: { type: integer }
    link: { type: string, description: "`{JIKU_WEB_URL}/docs/attachments/{id}`" }
    uploadedBy: { type: string }
    createdAt: { type: string, format: date-time }
```

**`DocsPageInfo`** (verbatim): `required: [limit, returned]`; `cursor` (*"Su ausencia es la única
señal de fin"*); `total` (*"Solo con `count`"*).

**`visibility` en 1.3.0:** `enum: [internal, public, restricted]` (`DocsDocument.visibility` en
`api.yaml`). El portal solo recibe `public`, pero el tipo sigue el contrato.

**Errores relevantes (sin cambios):** `404 module_not_installed`, `503 module_unavailable`,
`504 gateway_timeout`, `404 document_not_found`, `403 access_denied` / `permission_denied`,
`caller_not_authorized`.

### Flow Context

**`documentos-desde-la-web`, Paso 9: lectura desde el portal (opus-web)** — verbatim del flujo ya
actualizado por S-094:

| Operación | Endpoint | Detalle |
|---|---|---|
| Listar | `GET /api/opus/docs/documents` | Query `projectId` **o** `requirementId` (uno solo); `limit`, `cursor`. Cadena: `requireModule` → `hasAnyRole(['external-user','admin','user'])` → forma → `loadDocsScope` → `validateProjectPermissions` → `validateRequirementIsPublic` (solo si filtra por requisito) → handler. **`filter.visibility: 'public'` lo fuerza el handler**; la query no puede pisarlo. Lista y detalle piden `fields: ['id','title','version','visibility','createdAt','updatedAt']`: **sin `path`, `folderId` ni `fileName`** (`visibility` tiene que estar, o DD-3 respondería 404 siempre) |
| Detalle | `GET /api/opus/docs/documents/{id}` | `documents.get { id, include: ['content','attachments'], fields }`; **404 `document_not_found` si `visibility !== 'public'`** (falla cerrado) |
| Adjunto | `GET /api/opus/docs/documents/{documentId}/attachments/{id}` | `documents.get { id: documentId, include: ['attachments'] }`; **404 `document_not_found` si `visibility !== 'public'`**; **404 `attachment_not_found` si `id` no está en `attachments[].id`**; recién entonces `attachments.{id}.request-download` → 302 a la URL prefirmada |

*"Si `GET /api/opus/docs/documents` falla, `DocsSection` decide: `module_not_installed` → no muestra
nada; **403** (p. ej. `access_denied` de `validateProjectPermissions`, `permission_denied` de
jiku-docs) o `caller_not_authorized` → "No tenés acceso a la documentación de este proyecto."
(`MSG_DOCS_FORBIDDEN`), sin lista ni reintento; cualquier otro → aviso de no disponible. El visor del
documento no distingue: 403 sigue siendo "no existe o no compartido" (DD-9; DD-3 de REQ-016)."*

**Qué cambia en este paso con esta story:** nada en el flujo (ya lo cambió S-094). opus-web solo
ajusta los tipos a lo que el paso 9 entrega.

## Hallazgos y decisiones de este plan

- **Tipo acotado a la proyección del portal, no al `DocsDocument` completo.** La story pide "los tipos
  siguen el contrato 1.3.0" y "no declaran `path`/`folderId`/`fileName`". Como la api pide `fields`
  explícitos, el portal recibe exactamente `PORTAL_DOC_FIELDS` + `content`/`contentUrl` +
  `attachments`; declarar el resto (`relations`, `lock`, `topics`…) "por fidelidad", como hacía el
  tipo 1.1.0, describiría campos que nunca llegan. Se elige la proyección.
- **`DocsAttachment.fileName` se conserva.** Es el nombre del adjunto que muestra `lista-adjuntos`;
  la decisión 12 habla del `fileName` **del documento** (parte de su ruta de almacenamiento).
- **Discrepancia anotada, no corregida:** `docs/apis/api.yaml` sigue declarando `path`, `folderId` y
  `fileName` en el schema compartido `DocsDocument`, que también referencian las respuestas 200 de
  `/opus/docs/documents` y `/opus/docs/documents/{id}`; solo la descripción textual de esas rutas
  dice "sin `path`, `folderId` ni `fileName`". Para web interna puede ser correcto (otro consumidor
  del mismo schema); para el portal, el schema de la respuesta es más ancho que lo que se devuelve.
  Se reporta; no se toca el yaml en esta story (es el servicio `docs`/api quien decide si separa un
  `DocsPortalDocument`).
- **Sin cambios de UI** en ningún viewport: confirmado por la revisión UX de REQ-021.
