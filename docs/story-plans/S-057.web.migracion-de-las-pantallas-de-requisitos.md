### Convenciones activas relevantes

#### `styling` — Sass + CSS Modules + custom properties

- **Un módulo por componente.** Nombre del módulo = nombre del componente. Las páginas usan
  `styles.module.scss` (sin prefijo) porque el archivo ya es `page.tsx`.
- **Clases en `camelCase`**, no `kebab-case`.
- El módulo empieza con `@use '@/styles' as *;` cuando necesita mixins.
- **Composición de clases con `cn()`** (`src/shared/utils/cn.ts`), nunca template strings: el patrón
  `` `${styles.a} ${cond && styles.b}` `` escribe el string `"false"` en el `class` cuando la
  condición no se cumple. Acepta `{ clase: condición }`.
- **No hex literales: usar tokens.** No estilos inline salvo valores calculados en runtime.
- Los overrides de terceros van en `globals.scss`, no en un módulo.

> **La convención `styling.md` describe todavía la capa de tokens vieja** (`--color-button`
> `#DA2C6A`, `--radius-items`, tipografía Archivo). **S-052 ya la reemplazó en código** por la capa
> de tres tiers. Al migrar se consume el tier semántico; corregir el documento es trabajo de
> `/product-change-technical-definition`, fuera de esta story.

#### `testing-unit` — Vitest + Testing Library

- Tests **junto al archivo que testean**, como `{Nombre}.test.tsx`. `tests/` en la raíz tiene solo
  el setup.
- **Nombres de test en español**, describiendo comportamiento observable.
- **`getByRole` con nombre accesible antes que clase o `data-testid`.** `userEvent` antes que
  `fireEvent`. `queryBy*` para aserciones de ausencia.
- Se mockea la **capa de servicios o de hooks**, nunca `fetch` ni `apiClient`.
- `next/navigation` (`useRouter`, `useSearchParams`) se mockea cuando el componente navega.
- Las páginas de servidor async se testean invocando el componente como función async.
- **`TZ: 'UTC'` no se toca.**
- Comandos: `npm test --workspace web`, `npm run lint --workspace web`.
- Config real: `web/vitest.config.mts` — `jsdom`, `globals: true`, `setupFiles: ['./tests/setup.ts']`,
  alias `@` → `src`, `@root` → `src`, `@public` → `public`.

> **Cobertura previa en el alcance.** El módulo `requirements` sí tiene tests, y **varios van a
> romperse con la migración**: `CreateRequirementForm.test.tsx` (dos tests con comentarios sobre
> `react-select` y estilos calculados que jsdom no resuelve), `RequirementDetail.test.tsx` y
> `RequirementDetail.markdown.test.tsx`, `RequirementHeader.test.tsx`,
> `requirements/page.test.tsx`, más los tests de hooks y utils que **no** cambian.
> Actualizarlos es parte del trabajo, no daño colateral.

#### `data-fetching` / `mutations` / `state-management` / `forms`

**No cambian.** La story es visual: Server Action → axios → TanStack Query queda intacto, y la
mecánica de submit de cada formulario se preserva tal cual está. El REQ deja explícitamente fuera de
alcance la decisión de unificar los tres enfoques de formulario.

**Una excepción que sí toca datos, y hay que respetarla:** el BFF
`PATCH /api/requirements/[reqid]` existe porque el update optimista de TanStack Query necesita
rollback en el cliente. La migración **no lo toca**.

**Clasificación por intención — es CA-4 y está escrita en el propio `Button.tsx`:**

| Intención del uso | Variant | Señal para reconocerlo |
|---|---|---|
| Acción principal de la vista, cambia estado del sistema | `primary` | «Guardar», «Crear», «Agregar», «Nuevo …». Uno solo por vista |

- **No hay variant destructiva.** El rojo se reserva a vencimiento. `boton-cancelar-requisito` de la

- `session` cubre exactamente dos labels, ninguno de este módulo.

> 1. **`Button` renderiza `type="button"` fijo y no tiene prop `type`: no puede ser el submit nativo

>    revisar uso por uso antes de migrarlo (o disparar el submit por `onClick`, conservando la
>    mecánica actual).
> 2. **No tiene prop `size`.** Los `!important` de `requirements.module.scss` nacieron de eso. Se
>    resuelven usando el botón como es.

##### `Stepper` — el control que muestra dónde está

```ts
export interface StepperStep { readonly key: string; readonly label: string; }

export interface StepperProps {
  readonly steps: readonly StepperStep[];
  readonly currentKey: string;
  /** Marca pasos como recorridos aun cuando `currentKey` no es uno de los `steps`
   *  (p. ej. un estado terminal como resuelto/cancelado, que no es nodo del stepper
   *  pero implica que se recorrió todo el flujo). */
  readonly doneKeys?: readonly string[];
  /** De los recorridos, cuáles no tuvieron actividad real — se dibujan con `×` en vez
   *  de `✓`, para no sugerir que se completaron (caso "cancelado" de S-050). */
  readonly skippedKeys?: readonly string[];
  /** Default `false`: informativo, no focusable, no ofrece cambio de estado. */
  readonly interactive?: boolean;
  readonly onStepChange?: (key: string) => void;
}
```

Resolución del estado de cada nodo (`doneKeys` gana sobre el cálculo posicional):

```ts
if (doneKeys?.includes(step.key)) return 'done';
if (currentIndex !== -1) {
  if (stepIndex === currentIndex) return 'current';
  if (stepIndex < currentIndex) return 'done';
}
return 'pending';
```

Glifos: `skipped` → `×`; `done` → `✓`; `pending` → el índice 1-based; `current` → sin glifo (lo
carga el anillo). Texto para lector de pantalla: `` `${step.label}, ${stateLabel}` `` con
`etapa actual` / `omitida` / `completada` / `pendiente`.

**Los cinco pasos son fijos:** Análisis, Planificación, En cola, Desarrollo, Revisión.
**`resuelto` y `cancelado` NO son nodos del stepper**: son estados de cierre, se ven en el badge y
se alcanzan desde la card de resolución.

**Cómo se representa un estado terminal:** `currentKey="resuelto"` (que no está en `steps`, así que
`currentIndex === -1`), más `doneKeys` con las cinco claves, más `skippedKeys` con las que nunca se
trabajaron de verdad.

##### `Table`

```ts
export type TableVariant = 'light' | 'dense' | 'matrix';

export interface TableColumn {
  readonly key: string;
  readonly label: string;
  readonly sortable?: boolean;
  readonly scope?: 'row';   // solo tiene sentido en variant `matrix`
}

export interface TableSort { readonly key: string; readonly direction: 'asc' | 'desc'; }

export interface TableRow {
  readonly [key: string]: React.ReactNode;
  /** Claves de columna cuyo valor está vencido en esta fila. La celda se marca con
   *  texto (nunca sólo color) vía la clase `overdue`. */
  readonly _overdue?: readonly string[];
}

export interface TableProps {
  readonly variant?: TableVariant;
  readonly columns: readonly TableColumn[];
  readonly rows: readonly TableRow[];
  readonly sort?: TableSort;
  readonly onSortChange?: (sort: TableSort) => void;
  readonly emptyState?: React.ReactNode;
  readonly loading?: boolean;
  readonly ariaLabel?: string;
}
```

Mecánica que hay que conocer para migrar las tres tablas:
- **`emptyState`** se renderiza **fuera** del `<table>`, solo cuando `!loading && rows.length === 0`.
  El `<tbody>` no se renderiza; el `<thead>` sí. Se le pasa típicamente un `<EmptyState>`.
- **`loading`** tiene precedencia sobre `emptyState` y emite
  `<span role="status">Cargando…</span>`. El literal está hardcodeado ahí; **no usa `Loader`**.
- **El orden es totalmente controlado.** `Table` nunca ordena `rows`: marca la columna
  `sortable: true`, recibe `sort` y llama `onSortChange({key, direction})`. `nextDirection` alterna
  asc↔desc y **nunca limpia** el orden. Pone `aria-sort` en las columnas ordenables.
- La `key` de fila es el índice del array. `_overdue` es una clave mágica de la fila, no una columna.
- Todo va envuelto en `<div role="region" aria-label={ariaLabel} tabIndex={0}>` (default
  `'Tabla de datos'`).

Variants: `light` (cabecera niebla, listados navegables), `dense` (cabecera azul oscuro, tablas de
consulta densa), `matrix` (cabecera niebla + agrupadores de fila). **Una sola altura de fila: 48 px.**
**Nunca mezclar las dos cabeceras en una misma vista.**

#### Accesibilidad — normativa para toda la story

- **Contraste:** texto normal ≥ 4.5:1, texto grande ≥ 3:1. **El verde agua `#61CCB9` sobre blanco da
  1.9:1 y no se usa nunca para texto** — el verde de texto sobre fondo claro es `#12897A`.
- **El color nunca es el único portador de información.** Los estados llevan además texto o glifo:
  el stepper distingue `✓` / `×` / número; el acordeón `!` / `✓`; las celdas vencidas de `Table` se
  marcan con texto vía la clase `overdue`, no solo con color.
- **Foco visible siempre**, con el anillo único del sistema (`--focus-ring`,
  `0 0 0 3px rgba(97,204,185,.22)`). No se suprime `outline` sin reemplazo.
- **Todo control interactivo tiene nombre accesible.** El FAB requiere `aria-label` por tipo.
- **Labels visibles en los campos**: `Input` exige `label` y el placeholder no lo reemplaza.
- Navegación por teclado completa en los controles compuestos (`Tabs` con roving tabindex, `Select`
  con Enter/Space/flechas/Escape, `Badge` editable con `aria-haspopup="listbox"`).

> ⚠️ **Dos carencias de accesibilidad conocidas en componentes del DS**, que esta story **no
> arregla** pero cuyo efecto hay que conocer al migrar:
> 1. El `Badge` editable **no cierra con click afuera ni con Escape**, y no tiene navegación por
>    teclado dentro del listbox. Su `aria-selected` compara contra `label`, no contra `value`.
> 2. `Select` tampoco cierra con click afuera.
> Ambas son deuda del componente compartido: se arreglan en el componente, no en `requirements`.

### Contexto de flujos

Los cuatro flujos de `surfaces/web/user-flows.md` **no cambian**. El REQ-013 lo registró
explícitamente: *«el requerimiento cambia con qué está construido cada paso, no cuáles son los
pasos»*.

De los tres flujos cross-surface, ninguno cambia. Quedó registrada la consecuencia visual
deliberada: **a partir de REQ-013 las dos superficies se ven abiertamente distintas** (`web` es
Jiku, `opus-web` es Opus), y esa divergencia es la decisión de ADR-006, no un descuido.

**Lo que sí importa de los flujos para esta story** es el flujo de trabajo del requisito, porque es
lo que CA-3 protege. El reparto vigente tras S-050 / REQ-012:

| Control | Rol | Qué NO hace |
|---|---|---|
| **Badge editable** (cabecera) | Decide **a dónde va** — ofrece los **siete** estados, hacia adelante y hacia atrás | No se deshabilita en estado terminal |
| **Stepper** (card de estado) | Muestra **dónde está** — los **cinco** pasos de trabajo | No es un menú de destinos; no restringe transiciones |
| **Card de resolución** | **Cierra y reabre** — resuelve, cancela, reabre | No valida secuencia |

`core` eliminó la tabla de transiciones y `resuelto`/`cancelado` dejaron de ser terminales. **Esa
libertad no vive en el stepper: vive en el badge.**

### Navegación de la superficie

`web` tiene navegación principal por **sidebar fija de 290 px** con el ítem «Requisitos», más
`selector-tema` al pie (que llega en S-059). No hay navegación secundaria propia del módulo. El
chrome —sidebar, `PageLayout`, `ToastContainer`— **es compartido y esta story no lo toca**.

**Overlays disparados desde las pantallas de este módulo:** los popovers de los selects (que pasan
al `Select` único) y el `ConfirmDialog` de borrado. Ninguno se agrega, modifica ni elimina.

### Viewport

**La superficie `web` declara un solo viewport: `desktop`.** El shell lo impone: la sidebar mide
290 px fijos y el layout de `(loggedin)` no tiene ningún media query, así que bajo ~1000 px no hay
navegación posible. Tablet se comporta como desktop.

**Consecuencia directa para los test scenarios:** no hay un segundo layout que testear. **No se
inventan escenarios de viewport**, y no se duplica ningún escenario por ancho. Los breakpoints que
existen en el módulo están **fuera** de los viewports declarados, y el criterio que S-056 dejó
establecido es preservarlos con un comentario que justifique por qué siguen ahí.

**El par 1023/1024 px — el objeto de CA-2:**

| Archivo:línea | Query | Rol |
|---|---|---|
| `RequirementDetail.module.scss:12` | `@media (max-width: 1023px)` | colapsa el grid de dos columnas |
| `RequirementHeader.module.scss:10` | `@media (max-width: 1023px)` | apila el encabezado |
| `CreateRequirementForm.module.scss:96` | `@media (max-width: 1024px)` | **desalineado** — colapsa los paneles |
| `EditRequirementForm.module.scss:96` | `@media (max-width: 1024px)` | **desalineado** |

**A exactamente 1024 px de viewport el detalle todavía muestra dos columnas mientras los
formularios ya colapsaron.** Ese es el error puntual que el CHANGELOG v2.4.0 marcó y que CA-2 manda
unificar.

Los otros tres cortes del módulo son de 640 px, solo en los formularios
(`CreateRequirementForm.module.scss:324` y `:481`, `EditRequirementForm.module.scss:418`), y ajustan
los bloques de etiquetas. **CA-2 dice explícitamente que el resto de la deuda de breakpoints queda
intacta, fuera de esta story: los 640 px no se tocan.**

> **Los dos breakpoints de 1023 px están fijados por tests que leen el SCSS como texto**
> (`RequirementHeader.test.tsx:62,64`, `RequirementDetail.test.tsx:136,137,157`). Si la unificación
> se resuelve moviendo el 1023 al 1024, **esos tests rompen y hay que actualizarlos**. Si se
> resuelve moviendo el 1024 al 1023, siguen pasando. Ver la decisión más abajo.

### Decisiones tomadas en la planificación

Cuatro puntos donde el material dejaba margen y esta planificación elige, para que no se improvise
durante la implementación:

**1. La unificación de CA-2 se resuelve en 1023 px, moviendo los dos formularios.**
El criterio no es estético: **1023 es el valor que ya está fijado por tests** en dos archivos, y
`max-width: 1023px` es el complemento exacto de un `min-width: 1024px`, que es el corte limpio.
Mover el 1024 → 1023 toca dos archivos y no rompe ningún test; mover el 1023 → 1024 toca dos
archivos **y** obliga a reescribir cinco aserciones. Se elige el que no rompe.

**2. Los campos de fecha NO migran a `Input variant="date"` en esta story.**
`Input variant="date"` es un `<input type="text">` con un icono: no abre calendario y no parsea. Los
campos actuales usan `<input type="date">`, que sí lo hace. Migrarlos sería una **regresión
funcional** disfrazada de migración visual, y esta story es explícitamente «solo cambia la
presentación». Se migran sus **estilos** a tokens (que es lo que CA-1 pide) y se deja anotado el
gap. Cerrar la diferencia es trabajo de `/product-design-system-update`.

**3. `InputMultipleSelect` no se migra a `Select variant="multiple"` en esta story.**
Es un componente **compartido** (`shared/components/ui/`), no de `requirements`. Cambiarlo alcanza a
todo consumidor, y su único uso en el alcance (`RequirementFilters.tsx:150`) usa la prop `compact`,
que `Select` no tiene. Lo que sí entra: **quitarle a `RequirementFilters` su `selectStyles` propio y
sus dos `react-select` directos**, que es lo que TS-22 exige. La baja de `InputMultipleSelect` es de
S-060.

**4. El typeahead de los selects de proyecto y responsables se verifica antes de darlo por bueno.**
`Select` no tiene búsqueda. Si la lista de proyectos es larga, perder el filtrado por escritura es
una regresión de uso real. La tarea de formularios incluye verificarlo explícitamente; si resulta
inaceptable, **la salida es escalar a `/product-design-system-update`, no improvisar un buscador**.

```
acordeón:  .accItem:125 .accHead:142 .accChevron:158 .accChevronOpen:165 .accBody:173
```

**Los cinco pasos, fijos:**

```ts
const STEPS: readonly StepperStep[] = [
  { key: 'analisis',      label: 'Análisis' },
  { key: 'planificacion', label: 'Planificación' },
  { key: 'en_cola',       label: 'En cola' },
  { key: 'desarrollo',    label: 'Desarrollo' },
  { key: 'revision',      label: 'Revisión' },
```

**Cómo `Stepper` resuelve cada nodo** (`doneKeys` gana sobre el cálculo posicional):

```ts
if (doneKeys?.includes(step.key)) return 'done';
if (currentIndex !== -1) {
  if (stepIndex === currentIndex) return 'current';
  if (stepIndex < currentIndex)  return 'done';
}
return 'pending';
```

En un estado terminal `currentKey` no está en `steps`, así que `currentIndex === -1` y **sin

mostrar. Por eso `doneKeys` es obligatorio en ese caso, no opcional.

el anillo). El texto para lector de pantalla es `` `${step.label}, ${stateLabel}` `` con
`etapa actual` / `omitida` / `completada` / `pendiente` — es lo que hace que el estado **no dependa
solo del color**.

`pending`, `✓` verde para `done`. Su `title` lleva el término de dominio y **no** indica ahí que
está pendiente — eso lo dice `status`.
