# S-101: web + contrato: la persona se reconoce en la documentación y api.yaml al contrato 1.3.0

**Status:** Ready
**Created:** 2026-10-26
**Source:** REQ-022

## Historia de Usuario

**Como** persona que edita documentos desde la web,
**quiero** que la documentación me reconozca como autora de mi propia reserva y de mis versiones,
**para** ver "vos" y "Lo estás editando en otra pestaña o ventana." en lugar de "Otra persona", y para que el contrato de la api describa lo que realmente devuelve.

## Criterios de Aceptación

### CA-1: Reserva propia en otra pestaña

**DADO** un documento con el lock de la persona actual (humano)
**CUANDO** lo abre en otra pestaña
**ENTONCES** ve "Lo estás editando en otra pestaña o ventana.", no "Otra persona lo está editando…"; en la fila del listado ve "Lo estás editando"

### CA-2: "vos" como autor

**DADO** un documento cuya última versión guardó la persona actual
**CUANDO** ve la cabecera, la fila del listado ("Editado por") o el historial
**ENTONCES** ve "vos" como autor

### CA-3: Sin `zitadelId` falla cerrado

**DADO** una sesión sin `zitadelId`
**CUANDO** se muestra un lock o un autor
**ENTONCES** no se muestra "vos" ni "Lo estás editando…" por error

### CA-4: Contrato del portal

**DADO** `docs/apis/api.yaml`
**CUANDO** se leen los schemas de documentos del portal (`/opus/docs/documents*`)
**ENTONCES** no declaran `path`, `folderId` ni `fileName` y sí los campos del contrato 1.3.0

### CA-5: Contrato de la web alineado a 1.3.0

**DADO** `docs/apis/api.yaml`
**CUANDO** se leen los schemas de documentos de la web (`DocsDocument`, `DocsVersion`, `DocsSearchHit`, `DocsWriteResult`)
**ENTONCES** describen la respuesta de jiku-docs 1.3.0 tal como la devuelven las rutas: `path`, `folderId` y `fileName` se conservan marcados como pass-through de jiku-docs que la UI no usa, y `lock.holder`, `createdBy`, `updatedBy` y `author` se documentan como el `sub` de Zitadel

> Reformulación del AC-11 del REQ-022 (ver Consideraciones Técnicas, "Desvío respecto del AC-11").

### Cambios de API

#### Endpoints Existentes a Modificar (solo contrato, sin cambio de código)

**`GET /opus/docs/documents`** (ref: `docs/apis/api.yaml:3386-3419`)
- **Cambio:** `$ref DocsDocumentPage` pasa a `$ref DocsPortalDocumentPage`.

**`GET /opus/docs/documents/{id}`** (ref: `docs/apis/api.yaml:3421-3448`)
- **Cambio:** `$ref DocsDocument` pasa a `$ref DocsPortalDocument`.

**`GET /docs/documents`, `GET /docs/documents/{id}`, `GET /docs/search`, `POST /docs/documents`**
- **Cambio:** solo descripciones: la respuesta es el `data` de jiku-docs 1.3.0 verbatim (más los `*Refs` de la api); el listado trae por defecto `id, title, path, folderId, version, visibility, updatedAt, updatedBy, updatedByName, clients, projects` (+ `lock`/`topics` por el `include`).

### Diseño de la web

- `web/src/hooks/use-current-user.ts`: `TCurrentUser` gana `zitadelId: string | null` (de `session.user.zitadelId`, `null` si falta). `id` y `name` no cambian: `RequirementActivityFeed` y `ObjectiveComment` siguen comparando con `id` (fuera de alcance).
- `features/docs`: cada llamada pasa `currentUser?.zitadelId ?? null` en lugar de `currentUser?.id`: `DocumentView.tsx` (aviso de versión vieja, lock, cabecera `metaVersionLabel`), `DocumentEditor.tsx` (`lockedMessage`), `DocsResults.tsx` (contexto de fila → `editorLabel` en "Editado por"), `VersionHistoryPanel.tsx` (autor). El parámetro de `lockedMessage`/`editorLabel`/`metaVersionLabel` se renombra `currentUserSub`. Revisar cualquier otro lugar de `features/docs` que compare con el usuario actual.
- `DocumentRow.tsx` (líneas ~94-111): si el lock activo es `via: 'human'` y `holder === currentUserSub`, dice "Lo estás editando" en lugar de "Otra persona lo está editando". Mismo criterio en `DocumentRowCompact` si muestra lock.
- `lockState.ts` / `editorLabel.ts`: la lógica no cambia (ya fallan cerrado sin id). Test nuevo: con `currentUserSub` igual al `id` de Jiku y distinto del `sub`, no reconoce.
- No se agrega lógica para resolver nombres en null (`updatedByName`, `authorName`, `lock.holderName`): se arregla en jiku-docs.

### Flujo de Interacción

#### Escenario: reconocer el lock propio (CA-1, CA-2, CA-3)

**Trigger:** la persona edita en la pestaña A y abre el mismo documento en la pestaña B.

1. **[web A]** `POST /api/docs/documents/{id}/lock` → jiku-docs guarda `holder = actor.sub`.
2. **[web B]** `GET /api/docs/documents/{id}` → `lock: { sessionId, holder: "<sub>", holderName, via: "human", expiresAt }`; `sessionId` distinto → lock activo.
3. **[web B]** `lockedMessage(doc.lock, currentUser.zitadelId)` → `holder === zitadelId` → "Lo estás editando en otra pestaña o ventana."; en la fila del listado: "Lo estás editando".
4. Cabecera (`metaVersionLabel`), "Editado por" (`editorLabel` con `updatedBy`) e historial (`author`) → "vos".

**Outcome:** la persona se reconoce a sí misma.

**Manejo de errores:**
- Sin `zitadelId` en la sesión → `currentUserSub = null` → nunca "vos" ni "Lo estás editando…"; se muestra `holderName`/nombre o el texto genérico.

### Flujos Afectados

- **documentos-desde-la-web** (ref: docs/flows/documentos-desde-la-web.md) — Pasos 3 y 4 (reserva): la web reconoce la reserva propia comparando `lock.holder` con `session.user.zitadelId` (el `sub`), nunca con `session.user.id`.

### Consideraciones Técnicas

**Seguridad:**
- Sin cambios de autenticación ni de `getRolesFromToken`. El cambio de `useCurrentUser` es aditivo.

**Performance:**
- Sin cambios.

**Desvío respecto del AC-11 del REQ-022:**
- El portal cumple (esquema propio sin `path`/`folderId`/`fileName`). Para la web no se eliminan a propósito: las rutas los devuelven (jiku-docs 1.3.0 los conserva para el CLI y el sync) y el REQ prohíbe cambiar la api para ajustarse al yaml; el yaml es la fuente de verdad. Si se prefiere que la web no los reciba, es un cambio de comportamiento aparte (pedir `fields` explícitos).

**Dependencias:**
- Independiente de S-100; puede ir en paralelo. Toca otros archivos de `features/docs` y el contrato, salvo el bloque `/projects` de `api.yaml`, que es de S-100.
