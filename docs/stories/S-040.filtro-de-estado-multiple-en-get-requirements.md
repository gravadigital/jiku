# S-040: Filtro de estado múltiple en GET /requirements

**Status:** Completed
**Created:** 2026-09-01
**Source:** REQ-009

## Historia de Usuario

**Como** cliente HTTP de la api (el listado global de requisitos de `web`, la card de requisitos
del detalle de proyecto, y `opus-web`),
**quiero** que `GET /requirements` acepte uno o varios valores de `state` separados por coma,
**para** poder filtrar por varios estados a la vez sin romper el contrato actual de un único
valor.

## Criterios de Aceptación

### CA-1: Múltiples estados válidos devuelven la unión

**DADO** un caller autenticado con rol `user` o `admin`
**CUANDO** pide `GET /requirements?state=desarrollo,revision`
**ENTONCES** la respuesta es 200 y contiene únicamente requisitos en `desarrollo` o `revision`
(OR entre los estados)

### CA-2: Un solo estado mantiene el comportamiento actual

**DADO** la card de requisitos del detalle de proyecto, que pide un estado por tab
**CUANDO** pide `GET /requirements?state=desarrollo&count=true`
**ENTONCES** el comportamiento y la respuesta son idénticos a los actuales — un CSV de un
elemento produce el mismo `where` que la igualdad de hoy, sin cambios para ningún caller
existente

### CA-3: Un valor fuera del enum rechaza toda la request

**DADO** un caller autenticado
**CUANDO** pide `GET /requirements?state=desarrollo,inventado`
**ENTONCES** la respuesta es 400 con `code: 'invalid_fields'` y **ningún** requisito — el valor
inválido invalida el parámetro completo, no se filtra por los válidos

### CA-4: Un único valor inválido sigue rechazando como hoy

**DADO** un caller autenticado
**CUANDO** pide `GET /requirements?state=inventado`
**ENTONCES** la respuesta es 400 con `code: 'invalid_fields'` — el comportamiento actual ante un
único valor inválido no cambia

### CA-5: La autorización no cambia

**DADO** un caller **sin** los roles `user` ni `admin`
**CUANDO** pide `GET /requirements?state=desarrollo,revision`
**ENTONCES** la respuesta es 403 — el filtro múltiple no abre una vía de lectura nueva
(`hasAnyRole(['user', 'admin'])` en `requirements-get.ts:113`)

### CA-6: Valores repetidos no duplican resultados

**DADO** una request con `state` que repite un valor (ej. `state=desarrollo,desarrollo`)
**CUANDO** se ejecuta la consulta
**ENTONCES** el resultado es el mismo que con `state=desarrollo`: sin filas duplicadas y con el
total correcto (Sequelize traduce `[Op.or]` sobre una columna a `IN (...)`, que colapsa
duplicados)

### CA-7: El cambio vale igual para el listado y para el conteo

**DADO** que `buildWhere` es el constructor único que consumen `getRequirements` y
`getRequirementsCount`
**CUANDO** se pide `GET /requirements?state=planificacion,en_cola,desarrollo,revision&count=true`
**ENTONCES** el conteo devuelto corresponde exactamente al conjunto filtrado por esos cuatro
estados, sin código adicional más allá del cambio en `buildWhere`

### CA-8: `opus-web` no sufre regresión

**DADO** un `external-user` autenticado en `opus-web` consultando requisitos como hoy (un valor o
ninguno en `state`)
**CUANDO** consulta requisitos
**ENTONCES** el comportamiento no cambia: sigue viendo solo los proyectos con
`PermisoDeProyecto` y solo los requisitos con `visibilityLevel: 'public'`, y el filtro múltiple no
altera ese recorte

## Diseño Técnico

### Servicios Afectados

| Servicio | Impacto | Cambios Necesarios | Estado |
|----------|---------|---------------------|--------|
| `api` | Bajo | `GET /requirements`: `state` acepta CSV validado contra el enum; `buildWhere` pasa de igualdad a `[Op.or]` | Done |

### Cambios de API

#### Endpoints Existentes a Modificar

**`GET /requirements`** (ref: `docs/apis/api.yaml:468`, implementación
`api/lib/routes/requirements-get.ts`)

Estructura actual del parámetro `state`:

```yaml
- name: state
  in: query
  schema: { $ref: '#/components/schemas/RequirementState' }
```

→ **MODIFICADO** a la forma que `GET /objectives` ya usa (`api.yaml:821-824`):

```yaml
- name: state
  in: query
  description: |
    Uno o varios estados separados por coma. Devuelve los requisitos que estén en
    **cualquiera** de ellos (OR). Un valor fuera del enum `RequirementState` invalida el
    parámetro completo y responde 400 `invalid_fields`.
  schema: { type: string }
  example: planificacion,en_cola,desarrollo,revision
```

- **Justificación:** la forma `{ type: string }` con validación de cada miembro contra el enum es
  la única que expresa "CSV cerrado al enum": un `$ref` al enum no admite CSV, y un
  `type: string` libre —como el de `objectives`— perdería el 400 ante un valor inválido.
- **Compatibilidad:** un `state` de un solo valor sigue siendo un CSV de un elemento y produce
  exactamente el mismo `where`. **Sin cambio** para la card del detalle de proyecto (S-038, 7 tabs
  de un estado + `count=true`) ni para `opus-web` (CA-2, CA-8).
- Los demás parámetros (`projectId`, `type`, `priority`, `createdBy`, `estimatedFinishDate`,
  `tag`, `search`, `page`, `limit`, `sort`, `count`) **no cambian**.
- El response **no cambia**: sigue siendo el `oneOf` de `array<RequirementWithRelations>` o
  `integer` con `count=true`.

Cambios en la implementación:

1. **Schema Joi** (`requirements-get.ts:14`). Estructura actual:

   ```ts
   state: joi.string().valid(...Object.values(RequirementState)).optional(),
   ```

   → **MODIFICADO**: validar cada miembro del CSV contra el enum, de modo que un solo valor
   inválido invalide todo el parámetro (CA-3, CA-4) y un valor único siga comportándose igual
   (CA-4 devuelve 400 como hoy). El mensaje sigue saliendo por `validateQueryParams` como
   `{ code: 'invalid_fields', message: 'Invalid field - ...' }` — contrato intacto según
   `docs/architectures/api/conventions/validation.md`.

   > **Divergencia deliberada respecto del precedente.** `objectives-get.ts` declara `state`
   > como `joi.string()` **sin** validar contra el enum, así que un estado inventado en tareas
   > devuelve 200 con lista vacía. Acá **no** se copia esa parte: se pide 400 explícito. Se copia
   > el `[Op.or]`, no la validación laxa.

2. **`buildWhere`** (`requirements-get.ts:34`). Estructura actual:

   ```ts
   if (state) where.state = state;
   ```

   → **MODIFICADO** al patrón ya presente en la ruta hermana
   (`api/lib/routes/objectives-get.ts:36-40`):

   ```ts
   if (state) where.state = { [Op.or]: String(state).split(',').map((s) => s.trim()) };
   ```

   `Op` ya está importado en el archivo (`requirements-get.ts:8`, se usa para el `Op.iLike` de
   `search`). Sequelize traduce `[Op.or]` sobre una columna a `IN (...)`, que colapsa duplicados
   (CA-6) y usa `idx_requirements_state_created_id`.

   **Por construcción, el cambio vale para el listado y para el conteo**: `buildWhere` es el
   constructor único que introdujo S-036 y que consumen `getRequirements` (línea 76) y
   `getRequirementsCount` (línea 62) (CA-7).

### Flujo de Interacción

#### Escenario: caller pide múltiples estados

**Trigger:** un cliente HTTP pide `GET /requirements?state=desarrollo,revision`.

**Flujo:**

1. **[api]**
   - Acción: `hasAnyRole(['user', 'admin'])` (`requirements-get.ts:113`) — sin cambios.
   - Acción: `validateQueryParams(querySchema)` valida cada miembro del CSV contra el enum de
     `RequirementState`.
   - Input/Output: si algún miembro no pertenece al enum → 400 `invalid_fields`. Si todos son
     válidos → continúa.

2. **[api — buildWhere]**
   - Acción: `where.state = { [Op.or]: ['desarrollo', 'revision'] }`.
   - Output: consulta Sequelize con `state IN ('desarrollo', 'revision')`.

3. **[api — getRequirements / getRequirementsCount]**
   - Acción: ejecuta la consulta con el `where` compartido.
   - Output: 200 con el array filtrado, o el entero si `count=true`.

**Outcome:** el caller recibe únicamente requisitos en los estados pedidos, o el conteo
correspondiente.

**Manejo de errores:**
- Estado fuera del enum (en cualquier posición del CSV) → 400 `invalid_fields`, sin filtrar por
  los válidos.
- Caller sin `user` ni `admin` → 403.

### Flujos Afectados

Ninguno. Los 11 flujos documentados en `docs/flows/` cubren interacciones cross-servicio (bus,
adjuntos, autenticación, asignación semanal); ninguno cubre la lectura del listado de requisitos
por HTTP.

### Consideraciones Técnicas

**Seguridad:**
- Sin cambios. `hasAnyRole(['user', 'admin'])` sigue igual y el filtro no abre una vía de lectura
  nueva (CA-5), conforme a `ADR-008-autorizacion-deny-by-default.md`.
- El CSV se valida contra el enum **antes** de llegar al `where`; no hay interpolación de entrada
  del usuario en SQL (el `[Op.or]` parametriza los valores).

**Performance:**
- El `IN (...)` sobre `idx_requirements_state_created_id` no degrada respecto de la igualdad
  actual. El peor caso (los 7 estados seleccionados) equivale al plan de hoy sin filtro de estado.

**Dependencias:**
- Esta story es la dependencia dura de S-041: sin ella, cualquier CSV que mande `web` recibe 400.
  Es autocontenida y verificable sola (CA-1 a CA-8 se cubren enteros acá).
- Divergencia deliberada respecto de `objectives-get.ts`: tras este cambio, `requirements` valida
  el CSV contra el enum y `objectives` no. Es intencional (se pide 400 explícito) y no se toca
  `objectives-get.ts` en esta story.
