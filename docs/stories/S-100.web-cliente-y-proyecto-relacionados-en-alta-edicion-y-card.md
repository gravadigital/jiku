# S-100: api + web: Cliente y Proyecto relacionados en alta, edición y "+"

**Status:** Completed
**Created:** 2026-10-26
**Source:** REQ-022

## Historia de Usuario

**Como** persona que crea o edita documentos de un cliente o proyecto,
**quiero** que los selectores de Cliente y Proyecto se relacionen entre sí y respeten lo precargado desde la ficha del proyecto,
**para** que mis documentos queden vinculados al cliente y al proyecto correctos sin completar datos a mano.

## Criterios de Aceptación

### CA-1: Proyectos del cliente elegido

**DADO** "Nuevo documento" abierto
**CUANDO** la persona elige el cliente EXO y abre Proyecto
**ENTONCES** ve los proyectos de EXO (además de "Sin proyecto")

### CA-2: Elegir el proyecto completa el cliente

**DADO** "Nuevo documento" sin cliente elegido
**CUANDO** la persona elige el proyecto "EXO - Videoconferencia"
**ENTONCES** el selector de Cliente muestra EXO

### CA-3: Conservar o vaciar el proyecto al cambiar de cliente

**DADO** un proyecto de EXO elegido
**CUANDO** la persona elige el cliente EXO
**ENTONCES** el proyecto se conserva; si elige otro cliente, el proyecto se vacía

### CA-4: "+" de la card de proyecto

**DADO** el detalle de un proyecto de EXO
**CUANDO** la persona toca "+" en la card de Documentación
**ENTONCES** el alta muestra EXO / {proyecto} precargados y al guardar manda ambos

### CA-5: Edición de un documento existente

**DADO** un documento existente con proyecto y cliente
**CUANDO** la persona lo edita
**ENTONCES** los selectores muestran su cliente y su proyecto

### CA-6: `GET /api/projects` compatible

**DADO** un consumidor existente de `GET /api/projects`
**CUANDO** pide la lista
**ENTONCES** recibe los mismos campos que antes más el cliente de cada proyecto (`client: { id, name }`, o `null` sin cliente)

### CA-7: Listado muestra el cliente del documento

**DADO** un documento con cliente y proyecto
**CUANDO** aparece en un listado
**ENTONCES** la columna Cliente · Proyecto muestra el nombre del cliente, no "Sin cliente"

## Technical Design

### Servicios Afectados

| Servicio | Impacto | Cambios Necesarios | Estado |
|----------|---------|-------------------|--------|
| api | Bajo | `GET /api/projects` incluye `client` (`id`, `name`), aditivo; test de ruta; contrato `/projects` en `api.yaml` | Done |
| web | Medio | Tipo `Project.client`; helper `projectClientId`; `ProjectPicker`, `ClientProjectFields` y `NewDocumentDialog` leen el cliente con respaldo en `clientId`; tests de CA-1 a CA-5 y no regresión de `ClientProjectLabel` (CA-7) | Done |

### Cambios de API

#### Endpoints Existentes a Modificar

**`GET /projects`** (ref: `docs/apis/api.yaml:301-346`, código `api/lib/routes/projects-get.ts:27-32`)

- **Cambio:** el ítem agrega `client` (objeto `{ id: integer, name: string }`, `nullable`, `required: [id, name]`), "El cliente del proyecto; `null` sin cliente". `include: [{ model: User, as: 'creator', attributes: ['id','name','email'] }, { model: Client, as: 'client', attributes: ['id','name'] }]`. Mismo patrón que `projects-id-get.ts:11-14`, acotado a `id`/`name`.
- **Compatibilidad:** aditivo. Todos los campos previos (incluido `clientId`) se conservan; la descripción del endpoint pasa a "Incluye el creador y el cliente". `BelongsTo` no multiplica filas: `limit`/`offset` siguen correctos.
- **Justificación:** hoy el JSON trae `clientId` pero no el objeto `client`; la web lee `p.client?.id` y siempre obtiene `undefined`.

#### Nuevos Endpoints

Ninguno.

### Cambios de Base de Datos

Ninguno. `projects.client_id` (ref: `docs/db-schemas/jiku.md:226`) y la asociación `Project.client` ya existen. Sin migraciones.

### Diseño de la web

- `features/projects/types/project.types.ts`: `client?: Client | null` (el listado trae solo `id`/`name`; el detalle, el `Client` completo).
- Helper único `projectClientId(p) = p.client?.id ?? p.clientId ?? null` en `features/docs/utils/relationFields.ts`, usado por `ProjectPicker` (filtro y `onChange`), `ClientProjectFields.projectClientOf` y `NewDocumentDialog` (efecto `clientPending`). El respaldo en `clientId` hace a la web robusta aunque una lista venga sin `client`.
- Etiqueta de opción en `ProjectPicker`: `client?.name` si viene; si no, el nombre desde `useClients()` por `clientId`; si tampoco, solo el nombre del proyecto.
- `relationFields.ts` (`chooseProject`, `chooseClient`): la lógica es correcta, no se toca.
- `ClientProjectLabel`: sin cambios; test de no regresión con `clientRefs` (CA-7). El caso de la e2e ("Sin cliente · EXO - Videoconferencia") fue un documento sin cliente, consecuencia de este defecto, no un error de la etiqueta.

### Flujo de Interacción

#### Escenario: elegir cliente y luego proyecto (CA-1, CA-3)

**Trigger:** la persona abre "Nuevo documento" (o "Editar") y elige el cliente EXO.

1. **[web]** `useProjects()` → `GET /api/projects`.
2. **[api]** `200 [{ id: 43, name: "EXO - Videoconferencia", clientId: 1, client: { id: 1, name: "EXO" }, ... }]`.
3. **[web]** `ProjectPicker` con `clientId=1` filtra `projectClientId(p) === 1`: opciones "Sin proyecto" + proyectos de EXO.
4. **[web]** elegir el proyecto 43 → `chooseProject` → `{ clients: [1], projects: [43] }`. Reelegir EXO conserva el proyecto; otro cliente lo vacía; "Sin cliente" lo vacía siempre.

**Outcome:** al guardar, `POST /api/docs/documents` manda `relations: { clients: [1], projects: [43] }` (sin cambios).

#### Escenario: proyecto primero (CA-2)

Elegir "EXO - Videoconferencia" sin cliente → el selector de Cliente muestra EXO.

#### Escenario: "+" de la card de proyecto y edición (CA-4, CA-5)

**Trigger:** `DocsPanel` del proyecto 43 → `NewDocumentDialog initial={{ projectId: 43, clientId: 1 }}` (o el editor con las relaciones del documento).

1. **[web]** estado `{ clients: [1], projects: [43] }`; el proyecto 43 está entre las opciones filtradas, el `Select` muestra "EXO - Videoconferencia · EXO". Si `initial` trae solo `projectId`, el efecto `clientPending` completa el cliente con `projectClientId`.

**Outcome:** el alta muestra EXO / proyecto y guarda ambos.

### Flujos Afectados

- **documentos-desde-la-web** (ref: docs/flows/documentos-desde-la-web.md) — Paso 2b (alta): los selectores de Cliente/Proyecto leen el cliente de cada proyecto de `GET /api/projects` (`client.id`, con respaldo en `clientId`).

### Consideraciones Técnicas

**Seguridad:**
- `client` expone solo `id` y `name`, ya visibles para los mismos roles en `GET /projects/{id}`. Sin cambios de autenticación ni de `getRolesFromToken`.

**Performance:**
- Un `LEFT JOIN clients` por consulta, sobre `client_id` indexado. Despreciable.
- `useProjects()` sin filtros usa el límite por defecto (200); con más proyectos alguno no aparecería en el selector. Preexistente, no se cambia.

**Dependencias:**
- Independiente de S-101. El respaldo `clientId` permite implementar web y api en paralelo; la e2e necesita ambas.
- El bloque `/projects` de `api.yaml` es de esta story; el resto del contrato es de S-101.
