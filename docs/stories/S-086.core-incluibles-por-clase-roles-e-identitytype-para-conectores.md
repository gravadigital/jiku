# S-086: Incluibles por clase y roles/identityType para conectores

**Status:** Ready
**Created:** 2026-10-24
**Source:** REQ-017

## Historia de Usuario

**Como** conector del bus (jiku-docs, con roles `[internal-app, docs]`),
**quiero** pedir `roles` e `identityType` de `users` en `users.list`,
**para** clasificar a quien me llama sin responder `upstream_unavailable`, sin que esos campos existan para personas internas ni externas.

## Criterios de Aceptación

### CA-1: Conector con `[internal-app, docs]`

**DADO** un caller de clase `connector` (roles `[internal-app, docs]`)
**CUANDO** pide `users.list {filter:{id:[<id de una persona>]}, include:["roles","identityType"]}`
**ENTONCES** recibe al usuario con `roles` (lista) e `identityType` (`person`/`service`)

### CA-2: Conector con solo `internal-app`

**DADO** un caller de clase `connector` con solo `internal-app`
**CUANDO** pide los mismos incluibles
**ENTONCES** también los recibe

### CA-3: Persona interna

**DADO** un caller `person-internal` (rol `admin` o `user`)
**CUANDO** pide `users.list` con `include:["roles"]` o `include:["identityType"]`
**ENTONCES** recibe `invalid_fields`, igual que con un nombre inexistente

### CA-4: Persona externa

**DADO** un caller `person-external`
**CUANDO** pide `users.list` con `include:["roles","identityType"]`
**ENTONCES** recibe `invalid_fields`

### CA-5: Ni filtrables ni ordenables

**DADO** cualquier caller, incluido un `connector`
**CUANDO** pide `users.list` con `filter:{roles:...}`, `filter:{identityType:...}` o `sort:["roles"]`
**ENTONCES** recibe `invalid_fields`

### CA-6: `meta.describe` para conector

**DADO** un caller `connector`
**CUANDO** pide `meta.describe` de `users`
**ENTONCES** ve `roles` e `identityType` entre los incluibles

### CA-7: `meta.describe` para personas

**DADO** un caller `person-internal` o `person-external`
**CUANDO** pide `meta.describe` de `users`
**ENTONCES** no ve `roles` ni `identityType` en ninguna lista (byte a byte igual que hoy)

### CA-8: La restricción vive en la ficha

**DADO** el motor de consultas de core
**CUANDO** se revisa `users-list.ts` y las demás consultas
**ENTONCES** ningún handler decide por clase: la restricción es un dato declarado en la ficha (ADR-008) y las otras quince fichas no cambian

## Diseño Técnico

| Servicio | Impacto | Cambios Necesarios | Estado |

### Cambios de API

#### Contrato del bus de core (`docs/apis/core-queries.yaml`)

**`users.list`** (ref: `docs/apis/core-queries.yaml`:línea 480)
- **Cambio:** la descripción deja de decir que `roles` "is not exposed at all" y documenta los dos incluibles restringidos a la clase `connector`:
  ```jsonc
  { "filter": { "id": ["<sub>"] }, "include": ["roles", "identityType"] }
  // -> items[i] suma:
  //   "roles": ["admin"]         // lista de strings tal como está en users.roles (incluye roles desconocidos, p. ej. "docs")
  //   "identityType": "person"   // "person" | "service"
  ```
  Para `person-internal` y `person-external`, pedirlos en `include` o `fields` responde `invalid_fields`; para cualquier clase, en `filter` o `sort` también.
- **Justificación:** RF-1 a RF-4 y RF-6.

**`x-resources.users`** (ref: `docs/apis/core-queries.yaml`:línea 1406)
- **Cambio:** `includable: [email, person]` queda igual; se agrega `includableByClass: { connector: [roles, identityType] }`. La `note` reemplaza "`roles` NO SE EXPONE en absoluto" por la regla por clase y su motivo.
- **Test de paridad:** `core/tests/queries/contract-spec.test.ts` (TS-95) suma una aserción que compare `includableByClass` del documento con `usersSpec.includableByClass`.

**`meta.describe`** (ref: `docs/apis/core-queries.yaml`:líneas 128 y 712)
- **Cambio:** "identical for every caller" pasa a "identical for every person caller (internal and external); a `connector` also sees what a sheet declares for its class". No se agrega ninguna clave a la respuesta.

#### Nuevos Endpoints

Ninguno. No se agrega ni quita ningún canal del bus.

### Cambios de Base de Datos

Ninguno. `users.roles` (`jsonb`, lista de strings) y `users.identity_type` (enum `person`/`service`) existen desde S-015 (ref: `docs/db-schemas/jiku.md`:líneas 659-660). No son filtrables ni ordenables, no hace falta índice.

### Cambios en core (detalle)

```ts
// core/src/queries/types.ts — ResourceSpec
readonly includableByClass?: Readonly<Partial<Record<CallerClass, Readonly<Record<string, IncludableSpec>>>>>;

// core/src/queries/users/users-spec.ts
includableByClass: {
  connector: {
    roles: { kind: 'field', column: 'roles' },
    identityType: { kind: 'field', column: 'identity_type' },
  },
},
```

- `resolveForClass(resource, callerClass)` fusiona `includable` con lo declarado para la clase y deriva `includableNames` y `fieldNames` (nunca copiados). Sin `includableByClass` o sin entrada para la clase devuelve la misma referencia.
- Solo incluibles, por tipo: filtros y orden por clase no son representables. Tampoco entran en `q`.
- Se aplica antes que `resolveVariant` en `validateList`, `validateGet`, `runList` y `runGet`.
- `Query.validate(payload, callerClass)`; `validateList`/`validateGet` reciben `callerClass` como tercer parámetro opcional (ausente: no suma nada, falla cerrado). Todas las consultas `list`/`get` registradas lo reenvían (cambio mecánico de una línea por archivo).
- `describeResource(resource, callerClass)` aplica `resolveForClass`; `meta-describe.ts` deja de ignorar `ctx.callerClass`.
- Sin `enums.identityType`: `enums` es del recurso y `meta.describe` lo publica para todas las clases.
- Se reescribe el comentario de cabecera de `users-spec.ts` y el de `run.ts` ("la gramática es la MISMA para las tres clases").
- Alternativa descartada: chequear la clase dentro de `users-list.ts` (código en el handler, segunda copia de la regla en `meta.describe`).

### Flujo de Interacción

#### Escenario: jiku-docs clasifica a quien lo llama (CA-1, CA-2, CA-5, CA-6)

**Trigger:** una persona llama a jiku-docs; jiku-docs necesita sus roles.

**Flujo:**

1. **[jiku-docs]**
   - Acción: publica `{instance}.{jiku-docs-sub}.jiku-queries.v1.users.list`
   - Payload: `{ "filter": { "id": ["<sub>"] }, "include": ["roles", "identityType"] }`

2. **[core — despachador]**
   - Acción: compuerta 1 `authorizeWithRoles(..., 'queries')`; compuerta 2 `resolveCallerClass` -> `connector`; `usersList.validate(raw, 'connector')` -> `resolveForClass` suma los dos campos

3. **[core — motor]**
   - Acción: `runList` resuelve la ficha para `ctx.callerClass`; SQL con `t.roles, t.identity_type`
   - Output: `{ success: true, data: { items: [{ ..., roles: ["user"], identityType: "person" }], page } }`

**Outcome:** jiku-docs clasifica a la persona con esos roles.

**Manejo de errores:**
- `filter: { roles }`, `filter: { identityType }` o `sort: ["roles"]` para cualquier clase -> `invalid_fields`
- Fila del caller ausente -> `unknown_caller` (sin cambio)

#### Escenario: una persona pide los incluibles (CA-3, CA-4, CA-7)

**Trigger:** `admin`, `user` o `external-user` publica `users.list` con `include: ["roles"]`.

**Flujo:**

1. **[core]**
   - Acción: compuerta 2 -> `internal` o `external`; `validateList` con `resolveForClass` sin cambios
   - Output: `invalid_fields`, `details.field: "include"`, `allowed: ["email","person"]`, idéntico a un nombre inexistente

2. **[core]**
   - Acción: `meta.describe { resources: ["users"] }`
   - Output: `includable: { email, person }`, byte a byte como hoy

**Outcome:** para personas, los campos no existen.

### Tests

- TS-31 a TS-33 (CA-7 de S-023) se conservan para `internal` y `external`; se suman los casos `connector` para `filter` y `sort` (CA-5).
- Nuevos: CA-1 (`[internal-app, docs]`), CA-2 (`[internal-app]`), CA-3 (`admin`, `user`), CA-4 (externo), CA-6 y CA-7 (describe por clase).

- TS-70 (describe idéntico externo/interno) se conserva sin cambios; se agrega su par: un conector ve dos incluibles más en `users` y nada más distinto.

### Flujos Afectados

- **consulta-por-el-bus** (ref: docs/flows/consulta-por-el-bus.md) — líneas 97 y 404: `meta.describe` "idéntica para todos los callers" pasa a idéntica para las personas, el conector ve además lo declarado para su clase; el paso de validación recibe la clase del caller (`resolveForClass` antes de la variante).

### Consideraciones Técnicas

**Seguridad:**
- R-1: si una consulta no reenviara la clase a `validate`, el parámetro ausente falla cerrado. El riesgo inverso (que `runList` use la ficha de otra clase) se mitiga resolviendo ambas con la clase del despachador y con un test que pide `roles` como persona y verifica `invalid_fields` y que el SQL no nombra la columna.
- R-2: cualquier identidad `internal-app` ve los roles de todos (consecuencia de D-10); se documenta en `documentation/known-limitations.md` junto a "Every connector can read all documentation".
- CA-7 de S-023 se mantiene para personas.

**Performance:**
- `resolveForClass` es una fusión de objetos por request solo para fichas con `includableByClass` (hoy, una).

**Dependencias:**
- Independiente de S-087 y S-088. Desbloquea la integración de jiku-docs una vez desplegada.
