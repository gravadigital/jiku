# S-051: Limpieza del código muerto y del barrel de UI

**Status:** Completed
**Created:** 2026-09-02
**Source:** REQ-013

## Historia de Usuario

**Como** desarrollador que va a crear los componentes nuevos del Design System,
**quiero** que el código muerto que colisiona con esos nombres esté eliminado del árbol y del
barrel de `web/src/shared/components/ui/` antes de empezar,
**para** que el import de cada componente nuevo resuelva siempre al componente correcto y nunca
al muerto.

## Criterios de Aceptación

### CA-1: Los siete componentes muertos están eliminados

**DADO** que `Card`, `Header`, `Input`, `Textarea`, `MarkdownEditor`, `MultiSelect` y
`AttachmentDownload` son código muerto exportado desde el barrel de
`shared/components/ui/index.ts`
**CUANDO** se completa esta story
**ENTONCES** los siete componentes fueron eliminados del árbol de archivos y de su export en el
barrel, sin dejar ninguna referencia residual

### CA-2: Ningún import resuelve al componente muerto

**DADO** que `Card`, `Input` y `Textarea` colisionan con nombres de specs nuevos del DS
(`components/card.md`, `components/input.md`, `components/textarea.md`)
**CUANDO** se crean esos componentes en las stories siguientes (S-053 en adelante)
**ENTONCES** no existe ningún archivo ni export previo con esos nombres que pueda producir una
resolución de import silenciosa al código muerto

### CA-3: Los tests que verifican el barrel leyendo el archivo se actualizan, no se borran

**DADO** que `Pagination.test.tsx:205` y `RequirementDetail.test.tsx:573` verifican estructura
(presencia de export en el barrel, ausencia de clases SCSS duplicadas) leyendo el código fuente
como string, no renderizando
**CUANDO** se reorganiza el barrel al eliminar los siete componentes
**ENTONCES** ambos tests se actualizan para reflejar el barrel nuevo, conservando la restricción
arquitectónica que verifican (siguen siendo válidos, no se eliminan)

### CA-4: El build y la suite de tests pasan sin referencias rotas

**DADO** que hasta 227 archivos `.tsx` podrían importar del barrel de `ui/`
**CUANDO** se eliminan los siete componentes y se ejecuta el build
**ENTONCES** no hay ningún import roto a `Card`, `Header`, `Input`, `Textarea`,
`MarkdownEditor`, `MultiSelect` ni `AttachmentDownload` en ningún archivo de la superficie —
si alguno los usaba, ese uso se resuelve antes de fusionar (nota: el relevamiento del REQ los
declara sin usos; si el build encuentra alguno, se documenta como discrepancia con el relevamiento
antes de decidir cómo resolverlo)

### Flujo de Interacción

#### Escenario: Eliminación de código muerto sin romper el resto de la superficie

**Trigger:** Se ejecuta esta story antes de crear ningún componente nuevo del DS.

**Flujo:**

1. **[web · relevamiento]**
   - Acción: Confirmar con un grep del código fuente que `Card`, `Header`, `Input`, `Textarea`,
     `MarkdownEditor`, `MultiSelect` y `AttachmentDownload` no tienen usos reales fuera del
     propio barrel (el REQ los declara "código muerto exportado desde el barrel").
   - Output: Lista confirmada de archivos a eliminar.

2. **[web · `shared/components/ui/index.ts`]**
   - Acción: Quitar las siete líneas de export correspondientes a estos componentes.
   - Output: Barrel sin esos siete nombres.

3. **[web · árbol de archivos]**
   - Acción: Eliminar las carpetas/archivos de cada uno de los siete componentes (componente,
     estilos `.module.scss`, y sus tests si los hay).
   - Output: Árbol sin esos archivos.

4. **[web · `Pagination.test.tsx` y `RequirementDetail.test.tsx`]**
   - Acción: Actualizar las aserciones que leen el barrel como string, para que reflejen el
     contenido nuevo del archivo sin perder la restricción que verifican (export presente para
     lo que sigue vivo, ausencia de clases SCSS duplicadas).
   - Output: Tests actualizados y en verde.

5. **[web · build]**
   - Acción: Ejecutar build y suite de tests completa.
   - Output: Sin errores de import roto, sin regresiones.

**Outcome:** El barrel queda limpio de código muerto, sin colisión de nombres pendiente para las
stories que crean `Card`, `Input` y `Textarea` nuevos.

**Manejo de errores:**
- Si el grep encuentra un uso real de alguno de los siete componentes en una pantalla, no se
  elimina a ciegas: se documenta el uso encontrado y se decide si migra a un componente existente
  o si el relevamiento del REQ necesita corrección antes de continuar.

### Consideraciones Técnicas

**Seguridad:**
- No aplica; es limpieza de código de presentación sin lógica de negocio.

**Performance:**
- Reducir el barrel disminuye levemente el bundle de UI; no es el objetivo de la story pero es
  un efecto colateral positivo.

**Dependencias:**
- **Bloqueante duro para toda la migración.** El REQ-013 lo marca como el riesgo principal: "Si
  se crea `Card` antes de borrar el muerto, el import resuelve al muerto y el error es
  silencioso: compila y se ve mal." Por eso esta story va primera y bloquea a todas las demás
  del split (S-052 a S-060).
- No depende de ninguna story previa.
