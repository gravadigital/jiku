# S-038: Card de requisitos con totales reales y paginación por estado

**Status:** Ready
**Created:** 2026-08-31
**Source:** REQ-008

## Historia de Usuario

**Como** usuario que mira la pantalla de detalle de un proyecto,
**quiero** que los 7 tabs de estado de la card de requisitos muestren el total real de
requisitos de ese estado y que cada tab pagine su propio listado desde la api,
**para** dejar de ver totales calculados sobre datos parciales que esconden requisitos —
especialmente los más nuevos.

## Criterios de Aceptación

### CA-1: Totales reales por tab, no calculados sobre datos parciales

**DADO** un proyecto con 45 requisitos repartidos entre los 7 estados
**CUANDO** el usuario abre la pantalla de detalle del proyecto
**ENTONCES** cada uno de los 7 tabs muestra el total real de requisitos de ese estado en el
proyecto, obtenido de la api con `count=true`, y la suma de los 7 es 45 — no 20

### CA-2: Carga inicial del tab por defecto

**DADO** un proyecto con 45 requisitos y el tab activo por defecto `Desarrollo` con 12
requisitos, y `limit` 5
**CUANDO** se carga la card
**ENTONCES** la tabla muestra los primeros 5 requisitos en estado `desarrollo` traídos de la api
con `state=desarrollo`, `page=1`, `limit=5`, y el paginador informa 3 páginas

### CA-3: Navegación de página pide a la api, no recorta en memoria

**DADO** el tab `Desarrollo` activo en la página 1 con 12 requisitos
**CUANDO** el usuario navega a la página 3
**ENTONCES** se pide a la api `state=desarrollo`, `page=3`, `limit=5` y la tabla muestra los 2
requisitos restantes — no un recorte en memoria del subconjunto ya traído

### CA-4: Cambio de tab resetea página y refresca totales

**DADO** el tab `Desarrollo` activo en la página 3
**CUANDO** el usuario cambia al tab `Análisis`
**ENTONCES** la página vuelve a 1, se pide el listado de `analisis` y se refrescan también los 7
totales

### CA-5: Tab sin requisitos

**DADO** un tab con 0 requisitos en ese estado
**CUANDO** el usuario lo selecciona
**ENTONCES** el tab muestra el total `0`, la tabla muestra "No se encontraron requisitos" y el
paginador no ofrece páginas navegables

### CA-6: Cambio de tamaño de página resetea página y mantiene tab

**DADO** la card con `limit` 5 en el tab `Desarrollo`
**CUANDO** el usuario cambia el selector a 10 por página
**ENTONCES** la página vuelve a 1 y se pide el listado con `limit=10`, manteniendo el estado del
tab activo

### CA-7: Proyecto sin requisitos

**DADO** un proyecto sin ningún requisito
**CUANDO** el usuario abre la card
**ENTONCES** los 7 tabs muestran `0`, la tabla muestra el estado vacío y el paginador no se
renderiza

### CA-8: Fallo aislado de un conteo

**DADO** que la llamada de conteo de un estado falla
**CUANDO** se renderiza la card
**ENTONCES** el fallo no rompe la pantalla ni el listado del tab activo — la tabla sigue
mostrando sus datos

### CA-9: Página que deja de existir se reajusta

**DADO** el usuario en la última página de un tab y el requisito de esa página cambia de estado
(deja de pertenecer al tab)
**CUANDO** se refrescan los datos y esa página deja de existir
**ENTONCES** la card no queda en una página vacía sin salida: la paginación se reajusta al total
vigente

#### Endpoints Reutilizados sin Cambios

- `GET /requirements` con `state`, `projectId`, `page` y `limit` — ya soporta todo lo que la
  card necesita para paginar del lado del servidor (código existente). El front simplemente deja
  de recortar en memoria.
- `GET /requirements?count=true` — entregado por S-036; esta story es su primer consumidor.

### Cambios de Base de Datos

### Flujo de Interacción

#### Escenario A: carga inicial de la card de requisitos (CA-1, CA-2, CA-7)

**Trigger:** el usuario abre la pantalla de detalle de un proyecto.

**Flujo:**

1. **[web — `ProjectRequirementsSection`]** (client component)
   - Estado inicial: `activeState = 'desarrollo'`, `currentPage = 1`, `pageSize = 5`.
   - Dispara **8 queries en paralelo** vía TanStack Query:
     - 7 conteos, uno por estado: `useRequirementsCount({ projectId, state })` con query key
       `['requirements-count', { projectId, state }]`.
     - 1 listado: `useRequirements({ filters: { projectId, state: 'desarrollo', page: 1, limit: 5 } })`
       con key `['requirements', filters]`.

2. **[api]** `GET /requirements?projectId={id}&state={estado}&count=true` (×7)
   - Responde `200` con el número crudo, ej. `12`.

3. **[api]** `GET /requirements?projectId={id}&state=desarrollo&page=1&limit=5`
   - Responde `200` con el array de hasta 5 requisitos.

4. **[web — render]**
   - Cada tab muestra su conteo real; el activo (`Desarrollo`) muestra 12.
   - La tabla muestra 5 filas; el paginador calcula `Math.ceil(12 / 5) = 3` páginas.

**Outcome:** los 7 tabs suman el total real del proyecto (45, no 20) y la tabla muestra la
primera página real del estado activo. Con proyecto vacío, los 7 tabs muestran `0`, la tabla
muestra el estado vacío y el paginador no se renderiza (CA-7).

**Manejo de errores:**
- Si falla el conteo de un estado → esa query queda en error de forma **aislada**; el tab
  muestra un placeholder neutro y ni la tabla ni el resto de los tabs se ven afectados (CA-8). Es
  consecuencia directa de que sean 7 queries independientes en vez de una sola.
- Si falla el listado → error boundary de la card; los conteos siguen visibles.
- `401` → el interceptor de axios ya maneja la sesión caída, comportamiento actual sin cambios.

#### Escenario B: cambio de tab (CA-4)

**Trigger:** el usuario hace clic en el tab `Análisis`.

**Flujo:**

1. **[web]** `setActiveState('analisis')` y `setCurrentPage(1)`.
2. La key del listado pasa a `['requirements', { projectId, state:'analisis', page:1, limit:5 }]`
   → TanStack Query dispara `GET /requirements?projectId={id}&state=analisis&page=1&limit=5`.
3. Los 7 conteos se **invalidan**
   (`invalidateQueries({ queryKey: ['requirements-count'] })`) y se refetchean.
4. Render con los datos del nuevo tab.

**Outcome:** página 1 del nuevo estado, con los 7 totales frescos.

#### Escenario C: navegación de página y cambio de tamaño (CA-3, CA-6)

**Flujo:**

1. Clic en la página 3 → el `Pagination` (de S-037) en **modo controlado** invoca
   `onPageChange(3)`; el contenedor hace `setCurrentPage(3)`; nueva key →
   `GET ...&page=3&limit=5`. No hay navegación de URL.
2. Cambio del selector a 10 → `setPageSize(10)` + `setCurrentPage(1)` →
   `GET ...&page=1&limit=10`, manteniendo `activeState`.

#### Escenario D: página que deja de existir (CA-9)

**Trigger:** el usuario está en la última página de un tab y un requisito cambia de estado, con
lo que el total del tab baja y esa página desaparece.

**Flujo:**

1. Al refrescarse el conteo, el contenedor detecta `currentPage > totalPages` y **clampea** a
   `Math.max(1, totalPages)` antes de renderizar, disparando el refetch de la página válida. El
   patrón ya existe en el producto: `RequirementDetail.tsx`:182 hace
   `const page = Math.min(objPage, totalPages)`.

**Outcome:** la card nunca queda en una página vacía sin salida.

### Consideraciones Técnicas

**Riesgos identificados en el request y su mitigación en esta story:**

1. **Los tests existentes de la card colisionan con el `Pagination` compartido.**
   `ProjectRequirementsSection.test.tsx`:117 y :132 exigen que el
   `<nav aria-label="Paginación">` esté **siempre** presente, mientras el compartido (reescrito
   en S-037) hace `if (totalItems === 0) return null`. El CA-7 pide que con 0 requisitos "el
   paginador no se renderice" y el CA-5 que "no ofrezca páginas navegables".
   **Mitigación:** el componente unificado (S-037) expone el comportamiento de lista vacía como
   decisión del consumidor (prop explícita, ej. `hideWhenEmpty`), preservando el `return null` de
   tareas y permitiendo a esta card cumplir el CA-7. Los dos tests de la card se actualizan en
   **esta misma story**, que es la que hace la migración.

2. **De 1 request a 8 en la carga de la card.** Ocho llamadas HTTP donde antes había una.
   **Mitigación:** los 7 conteos son consultas indexadas triviales que corren en paralelo;
   TanStack Query las cachea con `staleTime` 30 s (ADR-011), así que un ida y vuelta entre tabs no
   las repite. Si más adelante molestara, la evolución natural es un endpoint de conteo agrupado
   por estado — **fuera de alcance de esta story**, que fija explícitamente "cada total por
   separado".

3. **`getObjectivesCount` concatena `&count=true` a mano** sobre la query string
   (`objectivesApi.ts`:23-28). El equivalente para requisitos debe evitar ese patrón y pasar
   `count` dentro del objeto de filtros, porque `cleanFilters` descarta falsy — un `count: false`
   se cae solo, que es exactamente lo que se quiere.

**Seguridad:**
- El conteo entra detrás de `hasAnyRole(['user','admin'])`, heredado de S-036; sin cambios desde
  esta story.

**Performance:**
- El listado por tab pasa de traer hasta 20 filas con dos `include` a traer 5 o 10: **menos**
  datos por request que hoy.
- Los 7 conteos van en paralelo y se cachean 30 s (ADR-011).

**Dependencias:**
- **S-036** (api): dependencia dura. Sin `count` en `GET /requirements`, esta story no tiene de
  dónde sacar los totales reales.
- **S-037** (web — paginador unificado): dependencia dura. Esta story adopta el componente en
  modo controlado; sin él, seguiría con la reimplementación inline del paginador de la card.
