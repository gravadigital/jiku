# S-042: Total real y paginador unificado en el listado de requisitos

**Status:** Completed
**Created:** 2026-09-01
**Source:** REQ-009

## Historia de Usuario

**Como** usuario interno que navega el listado global de requisitos (`/requirements`),
**quiero** que el paginador me informe el total real y la cantidad exacta de páginas del conjunto
filtrado,
**para** poder navegar el listado con confianza, igual que ya puedo hacerlo en el listado de
tareas y en la card de requisitos del detalle de proyecto.

## Criterios de Aceptación

### CA-1: El total y las páginas corresponden al conjunto filtrado

**DADO** 60 requisitos, de los cuales 32 están en `planificacion`, `en_cola`, `desarrollo` o
`revision`, con `limit` 15
**CUANDO** el usuario abre `/requirements` con el default
**ENTONCES** el total informado es 32 y el paginador ofrece 3 páginas — no 60 ni 4

### CA-2: Combinación sin resultados no ofrece páginas navegables

**DADO** una combinación de estados seleccionados sin ningún requisito que la satisfaga
**CUANDO** se carga el listado
**ENTONCES** la tabla muestra el empty state de requisitos, el total informado es 0 y el
paginador no ofrece páginas navegables

### Flujo de Interacción

#### Escenario: carga del listado con el paginador unificado (CA-1, CA-2)

**Trigger:** el usuario navega a `/requirements` (con o sin filtros de estado).

**Flujo:**

1. **[web — RequirementList]**
   - Estado actual: `RequirementList.tsx:196-246` reimplementa un paginador inline que adivina si
     hay página siguiente con `requirements.length >= limit` (líneas 218 y 231): no sabe cuántas
     páginas hay en total.
   - → **MODIFICADO**: reemplazar ese bloque por el componente `Pagination`
     (`web/src/shared/components/ui/Pagination/Pagination.tsx`), el mismo que ya usan
     `ObjectivesTable.tsx:131` (modo URL, `basePath`), `ProjectRequirementsSection.tsx:165` y
     `RequirementDetail.tsx:230` (modo controlado).

2. **[web — useRequirementsCount]**
   - Invocar el hook ya existente desde S-036 (`useRequirementsCount(filters)`), que este listado
     hoy no usa.
   - Llama: `GET /requirements?state=...&count=true` con los mismos filtros que la consulta del
     listado.

3. **[api]** Responde con el entero del conjunto filtrado (contrato ya cubierto por S-040 y
   S-036; sin cambios de este lado).

4. **[web — Pagination]**
   - Recibe `totalItems={count}` y `limit`, y calcula `totalPages = Math.ceil(totalItems / limit)`
     → `ceil(32/15) = 3` páginas (CA-1).
   - Con `count = 0`, no ofrece páginas navegables (CA-2).

**Outcome:** el paginador informa el total y la cantidad de páginas real del conjunto filtrado,
consistente entre el listado y el conteo.

**Manejo de errores:**
- Conjunto vacío → 200 con `[]` y `count` 0: empty state y paginador sin páginas navegables
  (CA-2).

### Flujos Afectados

Ninguno. No cruza el bus ni a `core`; la interacción es `web → api → PostgreSQL` dentro de un
único servicio de lectura.

### Consideraciones Técnicas

**Seguridad:**
- Sin cambios.

**Performance:**
- El listado pasa de una request a dos por render (agrega el `count`). Es exactamente el patrón
  que ya usan `ObjectivesTable` y la card de S-038; el `count` no lleva `include`
  (`requirements-get.ts:59-61`) y se apoya en el mismo índice
  (`idx_requirements_state_created_id`). No se introduce un patrón nuevo en el producto.

**Dependencias:**
- **Requiere S-040 desplegada**, porque `useRequirementsCount` con filtro multi-estado depende
  del `buildWhere` con `[Op.or]`.
- `Pagination` (S-037, Completed) y `useRequirementsCount` / `count=true` (S-036, Completed) ya
  están en el árbol; no hay dependencia pendiente fuera de este split.
- Corrige deuda preexistente al paginador (no introducida por REQ-009): el paginador inline ya
  adivinaba páginas antes de este requerimiento; CA-1 lo vuelve exigible. Se separa de S-041 por
  tener una causa distinta — S-041 implementa lo que el request pide, esta story corrige un
  paginador que ya estaba incompleto. Fundirlas escondería una corrección de deuda dentro de una
  feature.

**Nota de secuenciación con S-041:** ambas stories tocan `RequirementList.tsx` (S-041, la zona de
filtros; esta, la zona de paginación). Podrían implementarse en paralelo, pero se recomienda
secuenciar (S-041 antes que esta) para evitar un conflicto de merge.
