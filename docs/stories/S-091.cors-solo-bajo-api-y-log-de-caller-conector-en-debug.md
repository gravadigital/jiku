# S-091: CORS solo bajo /api y log de caller conector en debug

**Status:** Completed
**Created:** 2026-10-26
**Source:** REQ-020

## Historia de Usuario

**Como** dueño de la instalación de Jiku,
**quiero** que los links compartidos `/p/docs/*` no emitan cabeceras CORS y que core no llene el log de warnings por el camino normal de jiku-docs,
**para** que el HTML de un link compartido no sea legible por JavaScript de otro origen y para que un `warn` signifique algo realmente anómalo.

## Criterios de Aceptación

### CA-1: Sin CORS en el link compartido

**DADO** un request a una ruta pública `/p/docs/{token}` con cabecera `Origin`
**CUANDO** la api responde
**ENTONCES** la respuesta no lleva `Access-Control-Allow-Origin`

### CA-2: Preflight sin CORS en el link compartido

**DADO** un preflight `OPTIONS` a `/p/docs/{token}`
**CUANDO** la api responde
**ENTONCES** no lleva cabeceras CORS

### CA-3: CORS bajo /api sin cambios

**DADO** un request a una ruta bajo `/api` con cabecera `Origin`
**CUANDO** la api responde
**ENTONCES** lleva las mismas cabeceras CORS que hoy (incluido el preflight)

### CA-4: Caller conector en debug

**DADO** un comando `files.request-upload` publicado por un caller de clase `connector` (jiku-docs)
**CUANDO** core resuelve el actor
**ENTONCES** el mensaje de caller externo se registra en `debug` y no en `warn`

### CA-5: Otro caller externo sigue en warn

**DADO** un comando publicado por un caller externo que no es de clase `connector`
**CUANDO** core resuelve el actor
**ENTONCES** el mensaje se sigue registrando en `warn`

### CA-6: Actor verificado o api sin logs

**DADO** un comando con `actor` verificado o publicado por la api
**CUANDO** core resuelve el actor
**ENTONCES** no se registra ningún log (sin cambios)

## Technical Design

### Servicios Afectados

| Servicio | Impacto | Cambios Necesarios | Estado |
|----------|---------|-------------------|--------|
| api | Bajo | `app.use(cors())` → `app.use('/api', cors())` en la misma posición; test de cabeceras CORS en `/p/docs/*` y `/api/*` | Done |
| core | Bajo | `callerClass` pasa al `CommandContext`; la rama externa de `resolveActor` loguea `debug` si es `connector`, `warn` si no; TS-26 se ajusta y se agrega el caso no-`connector` | Done |
| docs | Bajo | `http-server.md`, `api/overview.md`, `api/index.md`, ADR-015 (revisión fechada: F-18 resuelto), `commands.md`, flujos `lectura-por-link-compartido` y `escritura-por-el-bus` | Done |
| jiku-docs | Ninguno | No se modifica | - |

### Cambios de API

Ninguno en rutas, status ni cuerpos. Solo cambian cabeceras de transporte:

```
/p/docs/{token} (GET, HEAD, OPTIONS)
  Access-Control-Allow-Origin: *                       - ELIMINADO
  (preflight) Access-Control-Allow-Methods / -Headers  - ELIMINADO
/api/** (todas)
  Access-Control-Allow-Origin: *                       sin cambios
```

No se toca la autenticación ni `getRolesFromToken` (la api no acepta tokens de machine users).

### Cambios de Base de Datos

Ninguno.

### Decisiones de diseño

- **DD-1 — CORS montado en `/api`, misma configuración.** En `api/app.ts` pasa a `app.use('/api', cors())`, **en la misma posición** (después de `publicHostOnly`, antes de `validateToken`), así el preflight bajo `/api` lo sigue respondiendo `cors()` con 204 antes de `validateToken`. Fuera de `/api` no hay middleware CORS. No se toca `validateToken`, `config/public.ts` ni `getRolesFromToken`.
- **DD-2 — Test con la app real.** Test nuevo en `api/tests/routes/` (supertest contra `initialize()`, patrón de `public-share`): `GET /p/docs/{token}` con `Origin` → sin `access-control-allow-origin`; `OPTIONS /p/docs/{token}` con `Access-Control-Request-Method` → sin cabeceras CORS; `GET` y `OPTIONS` bajo `/api` → `access-control-allow-origin: *` y, en el preflight, `access-control-allow-methods`.
- **DD-3 — `callerClass` en el `CommandContext`.** Se agrega `callerClass: CallerClass` (no opcional, como `roles`) a `CommandContext` y a los dos puntos donde el despachador arma el contexto (`dispatcher.ts:272`, `:367-373`). Es la misma clasificación de S-030 (`resolveCallerClass`); no se duplica lógica. Los tests que arman el contexto a mano (p. ej. `notifications.test.ts`) agregan el campo.
- **DD-4 — Nivel por clase en la rama externa.** `ctx.callerClass === 'connector'` → `logger.debug(...)`; cualquier otra → `logger.warn(...)`. Mismo texto, mismo valor devuelto (`ctx.caller`), sin payload. La rama del sobre y la de la api no loguean. El comentario de la función explica que para jiku-docs es el camino normal (D-3) y que el `warn` queda como señal de un `CORE_TRUSTED_PUBLISHER_ID` mal configurado o de una persona publicando directo.
  - **Tests:** TS-26 (`files.test.ts:504`, rol `internal-app` → `connector`) afirma `debug` una vez con `[files.request-upload]` y el caller, y `warn` no llamado. Caso nuevo con caller directo de rol `user` (clase `internal`) → `warn` una vez. TS-27 y `attachments.test.ts:311-318` se mantienen. Revisar el `sinon.stub(logger, 'warn')` de `files.test.ts:1013`.

### Flujo de Interacción

#### Escenario: lectura de un link compartido desde otro origen (CA-1, CA-2)

**Trigger:** `fetch('{JIKU_PUBLIC_URL}/p/docs/{token}')` con `Origin: https://otro`.

**Flujo:**

1. **[api]**
   - Acción: `publicHostOnly` → (sin CORS) → `express.json()` → logger → `validateToken` (exento) → `publicRoutes` → `shares.resolve`
   - Output: 200 HTML sin `Access-Control-Allow-Origin`

**Outcome:** el script del tercero no puede leer la respuesta; abrir el link en una pestaña sigue igual.

#### Escenario: llamada a /api (CA-3)

**Flujo:**

1. **[api]**
   - Acción: `OPTIONS /api/...` con `Origin` → `cors()` responde 204; `GET /api/...` → `cors()` agrega `Access-Control-Allow-Origin: *` → `validateToken` → ruta
   - Output: igual que hoy

#### Escenario: jiku-docs pide una subida (CA-4 a CA-6)

**Flujo:**

1. **[core / despachador]**
   - Acción: `resolveCallerClass(['internal-app'])` → `connector`; arma el contexto con `callerClass`
2. **[core / `resolveActor`]**
   - Acción: sin sobre y caller ≠ `CORE_TRUSTED_PUBLISHER_ID` → rama externa → `debug` si `connector`, `warn` si no; devuelve `ctx.caller`
   - Output: actor resuelto; sobre o api sin sobre → sin log

### Flujos Afectados

- **lectura-por-link-compartido** (ref: docs/flows/lectura-por-link-compartido.md) — nota de CORS (línea 301-302): "sin cabeceras CORS; `cors()` está montado solo en `/api`"
- **escritura-por-el-bus** (ref: docs/flows/escritura-por-el-bus.md) — paso 2, `resolveActor` (línea 279-285): la rama externa loguea `debug` para clase `connector` y `warn` para el resto

### Consideraciones Técnicas

**Seguridad:**
- Cierra F-18: el HTML de un link compartido ya no es legible por JavaScript de otro origen aunque se conozca el token
- La autenticación no cambia (ADR-007, ADR-009)

**Performance:**
- Sin impacto

**Dependencias:**
- `callerClass` obligatorio en `CommandContext` rompe la compilación de tests que arman el contexto a mano; se arregla en esta story
- Nota de release (patch): un tercero que leyera `/p/docs/*` por JavaScript deja de poder hacerlo
