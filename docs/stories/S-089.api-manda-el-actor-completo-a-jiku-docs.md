# S-089: La api manda el actor completo a jiku-docs

**Status:** Completed
**Created:** 2026-10-25
**Source:** REQ-019

## Historia de Usuario

**Como** usuario web (interno o externo) que lee documentación de un proyecto,
**quiero** que la api identifique ante jiku-docs a quien llama con el mismo `actor` completo que le manda a core (`id`, `roles`, `name?`, `username?`, `email?`),
**para** que jiku-docs me clasifique con los roles de mi token verificado y no me responda `caller_not_authorized` por tener roles viejos o ninguna fila en `users`.

## Criterios de Aceptación

### CA-1: El `actor` publicado es el mismo que recibe core

**DADO** un usuario web autenticado con roles en su token
**CUANDO** la api llama a jiku-docs en su nombre (por ejemplo `documents.list`)
**ENTONCES** el payload publicado lleva `actor` = `{ id, roles, name?, username?, email? }`, igual al que la api manda a core para ese mismo request

### CA-2: Token sin claim de roles

**DADO** un token sin claim de roles
**CUANDO** la api llama a jiku-docs en nombre de esa persona
**ENTONCES** el `actor` lleva `roles: []`

### CA-3: Gana el `actor` del token, entero

**DADO** un handler que arma un payload con su propio `actor`
**CUANDO** se publica la llamada al módulo
**ENTONCES** el `actor` publicado es exactamente el del token, sin campos del original

### CA-4: Sin identidad verificada falla cerrado

**DADO** un request sin identidad verificada
**CUANDO** un handler intenta llamar a jiku-docs en nombre de una persona
**ENTONCES** no se publica nada en el bus y la api responde el error de autenticación actual (401 `{ code: 'unauthorized', message: 'Unauthorized' }`)

### CA-5: Las rutas públicas siguen sin `actor`

**DADO** un visitante de un link compartido `/p/docs/{token}`
**CUANDO** la api llama a `shares.resolve` o `shares.attachment`
**ENTONCES** el payload no lleva `actor`

### CA-6: Identidad y contrato HTTP sin cambios

**DADO** la api con este cambio
**CUANDO** se revisa la autenticación y el contrato HTTP
**ENTONCES** `getRolesFromToken` no cambia, la api no acepta tokens de machine users ni lee claims de roles por proyecto, y rutas, status y cuerpos HTTP son los mismos

### CA-7: Documentación al día

**DADO** la story terminada
**CUANDO** se revisan ADR-015, DD-1 de REQ-016, las convenciones y el índice de api, `prd/architecture.md`, `reusable-code/api/utils.md` y los flujos afectados
**ENTONCES** describen el `actor` completo (`buildActor(res.req)`), conservan la historia como revisión fechada (REQ-019) y dejan escrito el requisito de versión de jiku-docs con D-11

## Technical Design

### Servicios Afectados

| Servicio | Impacto | Cambios Necesarios | Estado |
|----------|---------|-------------------|--------|
| api | Medio | `call()` de `lib/modules/client.ts` inyecta `buildActor(res.req)` entero en vez de `{ id }`; JSDoc; tests unitarios del embudo (TS-22, TS-25 y CA-1 a CA-5) y ~43 aserciones de `actor` en `tests/routes/*` (conviene un helper `expectedActor(token)`) | Done |
| docs | Bajo | ADR-015, nota en DD-1 de REQ-016, convenciones `bus-modules`, `testing`, `authorization`, `index.md` y `overview.md` de api, `prd/architecture.md`, `reusable-code/api/utils.md`, flujos `documentos-desde-la-web` y `lectura-por-link-compartido` | Done |
| core | Ninguno | `buildActor` ya existe y no se toca | - |
| jiku-docs (externo) | Externo | Ya acepta el `actor` completo (D-11); lo cambia otra sesión en su repo. **No se modifica acá** | - |

### Cambios de API

#### Contrato HTTP (`docs/apis/api.yaml`)

Ninguno. Mismas rutas, mismos status, mismos cuerpos.

#### Payload del bus hacia jiku-docs

Toda consulta o comando publicado por `moduleQuery` / `moduleCommand` / `runModuleCommand`:

```
actor: { id }                                         - ELIMINADO
actor: { id, roles, name?, username?, email? }        + NUEVO (= buildActor(res.req))
```

Ejemplo (`documents.list` con `token_01_user` del mock):

```
antes:  { filter: {...}, sort, page, include: ['lock'], actor: { id: 'zitadel-sub-01' } }
ahora:  { filter: {...}, sort, page, include: ['lock'], actor: { id: 'zitadel-sub-01', roles: ['user'] } }
```

`shares.resolve` / `shares.attachment` (`public-share.ts`): sin cambios, sin `actor`, con `client`.

El esquema `Actor` del contrato de jiku-docs lo actualiza la otra sesión en ese repo. En este repo no hay copia de ese contrato (`docs/apis/jiku-modules.yaml` no describe el `actor`).

### Cambios de Base de Datos

Ninguno.

### Decisiones de diseño

- **DD-1 — `actor` = `buildActor(res.req)` sin transformar.** El embudo reemplaza `body = { ...payload, actor: { id } }` por `body = { ...payload, actor }`. Es el mismo sobre que recibe core (`withActor`), así que hay una sola fuente de identidad. No se agregan campos (ni `identityType`). Se sigue sin reusar `withActor`: sin identidad devuelve el payload sin `actor` (falla abierto, correcto para core), y para jiku-docs un llamado sin `actor` es el propio servicio.
- **DD-2 — Falla cerrado, igual que hoy.** Sin `buildActor(res.req)` → 401 sin publicar (ADR-015, DD-9).
- **DD-3 — Gana el del token, entero.** El `actor` va después del spread; sin mezcla campo a campo.
- **DD-4 — Sin cambios en rutas públicas ni en `anonymous`.** `public-share.ts` usa `sendToModule` sin `actor`; la opción `anonymous` sigue quitando el `actor` (TS-26 de S-077).
- **DD-5 — Sin cambios de identidad.** `getRolesFromToken` no se toca; los roles salen de `req.decodedTokenRoles`.

### Flujo de Interacción

#### Escenario: un externo abre el tablero del portal (CA-1, CA-2)

**Trigger:** el externo entra a `/projects/{id}` en opus-web.

**Flujo:**

1. **[opus-web]**
   - Acción: `DocsSection` → `useDocuments`
   - Output: `GET /api/opus/docs/documents?projectId={id}`

2. **[api]**
   - Acción: cadena actual (`requireModule` → `hasAnyRole(['external-user','admin','user'])` → forma → `loadDocsScope` → `validateProjectPermissions` → handler con `filter.visibility: 'public'` forzado); el handler llama `moduleQuery(res, 'docs', 'documents.list', {...})`
   - Output: llamada al embudo `call()`

3. **[api / `call()`]**
   - Acción: `respondIfModuleNotReady`; `actor = buildActor(res.req)`; sin `actor` → 401 sin publicar; si no, publica `{ ...payload, actor }`
   - Output: `actor = { id, roles: ['external-user'], name?, username?, email? }`

4. **[jiku-docs]**
   - Acción: clasifica con `actor.roles` (`external-user` → `person-external`) sin depender de la fila de `users`; consulta `project-permissions` a core
   - Output: `success` o `failure`

5. **[api]**
   - Acción: `success` → 200 con la página; `failure` → mapa de `docs/errors.ts` (`caller_not_authorized` → 403)

**Outcome:** el externo con acceso ve la documentación de su proyecto.

**Manejo de errores:**
- Sin identidad → 401, sin publicar
- Módulo no instalado → 404 `module_not_installed`
- Módulo caído → 503 `module_unavailable`
- Timeout → 504 `gateway_timeout`

### Flujos Afectados

- **documentos-desde-la-web** (ref: docs/flows/documentos-desde-la-web.md) — párrafo de identidad y tabla de participantes, diagramas y payloads: `actor: { id }` → `actor` completo de `buildActor`
- **lectura-por-link-compartido** (ref: docs/flows/lectura-por-link-compartido.md) — `shares.new` y alta de link: `actor` completo; `shares.resolve` / `shares.attachment` sin cambios

### Consideraciones Técnicas

**Seguridad:**
- La identidad sale solo del claim verificado (ADR-007); `roles: []` no autoriza nada (ADR-008); falla cerrado sin identidad
- `name`, `username` y `email` viajan ahora a jiku-docs; ya viajan a core por el mismo bus y jiku-docs los recibe solo del publicador de confianza (la api, por `JIKU_API_USER_ID`). El embudo sigue sin loguear `payload`

**Performance:**
- Sin impacto: unos bytes más por mensaje

**Dependencias:**
- **Orden de despliegue con jiku-docs (riesgo principal).** Mientras jiku-docs tenga `Actor` con `additionalProperties: false` y solo `id`, toda llamada de la api con `roles` responde `invalid_fields` (400) y la documentación deja de funcionar en web y opus-web. Esta story requiere la versión de jiku-docs con D-11. Dejarlo escrito en ADR-015 y, en la release, en *Notes for existing installations* del CHANGELOG ("actualizar jiku-docs antes o junto con la api"). Sin compatibilidad hacia atrás
- Las aserciones de `tests/routes/*` pasan de `{ id }` a `{ id, roles: [...] }` según el token del mock
