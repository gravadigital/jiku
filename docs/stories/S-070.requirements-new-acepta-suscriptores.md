# S-070: `requirements.new` acepta suscriptores

**Status:** Ready
**Created:** 2026-09-17
**Source:** REQ-015

## Historia de Usuario

**Como** desarrollador de `core` y de `api`,
**quiero** que `requirements.new` acepte un campo opcional `subscriberUserIds` y cree las
suscripciones en la misma transacción que el requisito, y que ambas rutas HTTP lo aprovechen,
**para** que el alta de un requisito con suscriptores deje de depender de una carrera entre el
comando de creación y N comandos de suscripción posteriores.

Esta es la **única modificación de contrato de todo el REQ**, y es aditiva: un cliente que hoy
publica `requirements.new` sin el campo sigue funcionando exactamente igual. Se corta como story
propia — independiente de la cola de salida y del registro de notificaciones — porque aislada es
revisable y reversible por sí sola.

## Criterios de Aceptación

### CA-1: Alta con suscriptores crea requisito y suscripciones en una transacción

**DADO** un requisito de proyecto creado como `public` desde el portal, con
`subscriberUserIds = [U2, U3]` y creador U1
**CUANDO** se ejecuta `requirements.new` con esos suscriptores
**ENTONCES** en la misma transacción se crean el requisito y las tres suscripciones (U1 incluido,
porque el portal lo auto-suscribe; U2 y U3 explícitos)

### CA-2: Un cliente que no manda el campo sigue funcionando igual

**DADO** un cliente que hoy publica `requirements.new` **sin** suscriptores
**CUANDO** se despliega la versión que acepta el campo nuevo
**ENTONCES** el comando **sigue funcionando igual**: el campo es opcional y su ausencia no cambia
nada

### CA-3: Deduplicación de `subscriberUserIds` en el comando

**DADO** `subscriberUserIds` con un id repetido
**CUANDO** se ejecuta `requirements.new`
**ENTONCES** el id repetido **no** es un error: se colapsa antes de insertar, con la misma
semántica que `already_subscribed` valida en `requirements.{id}.subscriptors.new`

### CA-4: `userId` inexistente falla y hace rollback completo

**DADO** `subscriberUserIds` con un id que no existe en `users`
**CUANDO** se ejecuta `requirements.new`
**ENTONCES** el comando responde `failure` con el código `user_not_found` y hace **rollback**: no
queda ni el requisito ni ninguna suscripción

### CA-5: `POST /requirements` (ruta interna) gana el campo

**DADO** un request a `POST /requirements` con `subscriberUserIds` en el body
**CUANDO** la api lo recibe
**ENTONCES** lo pasa sin transformar al comando `requirements.new` — el campo es opcional y
aditivo al contrato HTTP existente

### CA-6: `POST /opus/requirements` pasa de N+1 comandos a uno

**DADO** un alta desde el portal con `subscriberUserIds: [U2, U3]` y creador U1
**CUANDO** `POST /opus/requirements` procesa el request
**ENTONCES** publica **un solo** comando `requirements.new` con
`subscriberUserIds = [...new Set([req.user.id, U2, U3])]` — ya no publica un
`requirements.{id}.subscriptors.new` por cada suscriptor

### CA-7: El auto-suscribir al creador no se toca

**DADO** el comportamiento actual del portal de auto-suscribir siempre al creador
**CUANDO** se aplica esta story
**ENTONCES** ese comportamiento **sigue igual**: la api arma el set incluyendo a `req.user.id`
antes de publicar el comando único

## Diseño Técnico

### Servicios Afectados

| Servicio | Impacto | Cambios Necesarios | Estado |
|----------|---------|-------------------|--------|
| `core` | Medio | `requirements.new` valida `subscriberUserIds` contra `users`, deduplica, inserta en `requirement_subscriptors` dentro de la misma transacción; nuevo código de error `user_not_found` en su lista | Done |
| `api` | Bajo | `POST /requirements` pasa el campo nuevo sin transformar; `POST /opus/requirements` arma el set con el creador y publica un solo comando en lugar de N+1 | Pending |

### Cambios de API

#### Endpoints Existentes a Modificar

**`requirements.new`** (ref: `docs/apis/core.yaml:561`, payload en `:2181-2237`)

Estructura actual (`RequirementsNewPayload`), con el único agregado:

```yaml
RequirementsNewPayload:
  type: object
  required: [title, description, projectId]
  properties:
    # ... campos existentes sin cambios ...
+   subscriberUserIds:    # NUEVO — array de IdentityUserId, opcional
```

- **Cambio:** campo nuevo `subscriberUserIds: string[]`, opcional, ids de usuario de Zitadel. Se
  crean las filas de `requirement_subscriptors` **en la misma transacción** que el requisito.
- **Justificación:** sin él, el alta con suscriptores tiene una carrera entre la creación del
  requisito y la suscripción posterior, y la lista de destinatarios de un evento `requirement.created`
  sale vacía (`docs/apis/core-events.yaml:203` ya documenta que hoy están *"always empty at
  creation"*).
- **Compatibilidad: aditiva.** CA-2: un cliente que hoy publica sin el campo sigue funcionando
  igual.
- **Deduplicación al crear:** `subscriberUserIds` se deduplica **en el comando** antes de insertar,
  aunque el portal ya mande un `Set`. El comando no puede confiar en eso.
- **Error nuevo posible:** un `userId` que no existe en `users`. Se reusa **`user_not_found`**, el
  código que `requirements.{id}.subscriptors.new` ya declara (`docs/apis/core.yaml:717-733`), y se
  agrega a la lista `x-error-codes` de `RequirementsNew`.

**`POST /requirements`** (ref: `docs/apis/api.yaml:550-580`)

- **Cambio:** campo opcional nuevo en el request body:
  ```yaml
  subscriberUserIds:
    type: array
    items: { type: string }
    description: Ids de usuario de Zitadel
  ```
- **Justificación:** sin esto, la ruta interna nunca puede disparar el alta con suscriptores.

**`POST /opus/requirements`** (ref: `docs/apis/api.yaml:2166-2218`)

- **Cambio:** no cambia su contrato HTTP — ya acepta `subscriberUserIds`. Cambia su
  **implementación**: de N+1 comandos (un `requirements.new` más un
  `requirements.{id}.subscriptors.new` por suscriptor) a **un solo** `requirements.new` con
  `subscriberUserIds`.
- **Descripción de la spec a actualizar:** eliminar la frase *"Las suscripciones son comandos
  aparte: se publica un `requirements.{id}.subscriptors.new` por cada usuario"*.
- **Justificación:** además de la unificación pedida, un beneficio de corrección: hoy, si el
  requisito se crea y una suscripción posterior falla, el requisito queda sin sus suscriptores.
  Con un solo comando, la atomicidad la da la transacción.

**Nota fuera de alcance de esta story:** la descripción de `requirements.{id}.comment`,
`requirements.{id}.comment.{cid}.edit`, `requirements.{id}.resolve` y `requirements.{id}.edit`
también mencionan "no notifica" — esas actualizaciones de contrato/descripción son de las stories
3 y 4 (registro de tipos y comandos que declaran), no de esta.

### Cambios de Base de Datos

Ninguno. `requirement_subscriptors` se usa tal como está — sin agregar el unique compuesto que le
falta (eso es deuda de FG-6, no de este REQ).

### Flujo de Interacción

#### Escenario: alta de un requisito público con suscriptores (CA-1, CA-6, CA-7)

**Trigger:** un `external-user` crea un requisito desde el portal con
`subscriberUserIds: [U2, U3]`, siendo U1 el creador.

**Flujo:**

1. **[opus-web]** → `POST /api/requirements` → proxy catch-all → `POST /opus/requirements` de la
   api. Payload: `{ title, description, projectId, subscriberUserIds: [U2, U3], ... }`

2. **[api]**
   - Autoriza por rol y por permiso de proyecto.
   - **`→ MODIFICADO`:** arma `subscriberUserIds = [...new Set([req.user.id, ...subscriberUserIds])]`
     — el auto-suscribir al creador no se toca — y publica **un solo** comando `requirements.new`.

3. **[core · dispatcher]** — compuerta de autorización, `sequelize.transaction()`. →
   `requirements-new.execute(payload, ctx)`

4. **[core · requirements-new]** — dentro de la transacción:
   - `INSERT INTO requirements (...)` → id 412
   - `INSERT INTO people_requirements (...)` (el primero es líder)
   - Flujo de archivos sin cambios
   - **`+ NUEVO`:** valida que cada `subscriberUserIds` exista en `users` → `user_not_found` si
     no; deduplica; `INSERT INTO requirement_subscriptors (requirement_id, user_id) VALUES (412,
     U1), (412, U2), (412, U3)`
   - `reply.events = [requirementCreated({...})]` sin cambios
   - → `success({ id: 412 })`

**Outcome:** el requisito y sus tres suscripciones existen atómicamente. (La declaración de
notificación sobre este mismo comando es de S-071/S-072, no de esta story: acá el foco es que el
campo exista, valide y persista correctamente.)

**Manejo de errores:**
- `user_not_found` en un suscriptor → el comando responde `failure`, **rollback**: no queda ni el
  requisito ni ninguna suscripción.
- `POST /requirements` sin el campo → comportamiento idéntico al actual.

### Consideraciones Técnicas

**Seguridad:**
- Ninguna consideración nueva de autorización: el filtrado de destinatarios de notificación es de
  otra story. Esta solo valida existencia de usuario.

**Performance:**
- Una consulta adicional por comando cuando llega `subscriberUserIds` (`SELECT` de existencia,
  posiblemente en lote), despreciable para listas de suscriptores chicas.

**Dependencias:**
- **Orden de despliegue:** `core` primero. Si se desplegara `api` primero con el campo nuevo pero
  `core` sin soporte, el campo se ignoraría silenciosamente y las suscripciones se perderían. Como
  el campo es aditivo y el despliegue del monorepo es conjunto, no hay ventana de incompatibilidad
  si se respeta ese orden.
- Independiente de S-069 (no toca `notification_outbox`) y de S-071/S-072 (el `Reply` de este
  comando no declara notificaciones todavía — eso lo agrega S-072). Puede implementarse en
  paralelo con S-069.
