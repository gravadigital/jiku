# S-004: La `api` deja de escribir y de recibir el byte

**Status:** Ready
**Created:** 2026-08-19
**Source:** REQ-001

## Historia de Usuario

**Como** equipo que mantiene la `api`,
**quiero** que los endpoints de subida y de baja de adjuntos dejen de escribir la base y de recibir el binario, y pasen a publicar comandos de `core`,
**para** cerrar la excepción 2 de ADR-001 y eliminar el costo de bufferizar 10 MB × 10 archivos en memoria.

> **Es la story más riesgosa del split.** Concentra el cambio de contrato HTTP, la eliminación de la
> escritura directa, la reescritura completa de los tests de adjuntos de la api, y el comando de
> desvinculación. Si al planificarla el volumen lo pide, **el corte natural es separar el comando de
> desvinculación (`DELETE`) del cambio de subida (`POST`)**.

## Criterios de Aceptación

### CA-1: `POST /api/attachments` acepta JSON y devuelve un ticket

**DADO** un usuario autenticado
**CUANDO** hace `POST /api/attachments` con `{ fileName, mimeType, fileSize, checksum? }` en JSON
**ENTONCES** recibe `201` con `{ fileId, uploadUrl, expiresIn }`, y el endpoint **no aceptó ningún
binario ni ningún `entityType`**

### CA-2: La `api` deja de escribir la fila

**DADO** el código de `attachments-post.ts` después de esta story
**CUANDO** se revisa
**ENTONCES** **no existe ninguna llamada a `Attachment.create()`** ni ninguna otra escritura directa
sobre la base desde el módulo de adjuntos — la excepción 2 de ADR-001 queda cerrada

### CA-3: `multer` desaparece del camino

**DADO** el endpoint de subida después de esta story
**CUANDO** se revisa
**ENTONCES** no usa `multer` ni `memoryStorage`, y el proceso de la `api` deja de tener un pico de
memoria de 10 MB × 10 por subida

### CA-4: Un archivo por request

**DADO** un usuario que quiere subir tres archivos
**CUANDO** los sube
**ENTONCES** hace **tres requests independientes**, y el fallo de uno no afecta a los otros dos (D-07)

### CA-5: La autorización de subida queda en el JWT

**DADO** un usuario autenticado sin permiso sobre ningún proyecto en particular
**CUANDO** pide permiso de subida
**ENTONCES** la solicitud se acepta — no hay entidad contra la que validar `canUserAccessEntity`, y el
control de entidad se corre al momento de vincular

### CA-6: `POST /api/opus/attachments` cambia igual

**DADO** el portal
**CUANDO** pide permiso de subida
**ENTONCES** el endpoint se comporta igual que el interno, mantiene `x-roles: [user, external-user]`
y **pierde su validación propia de `entityType`**, porque ya no recibe `entityType`

### CA-7: Los códigos de error nuevos se mapean a HTTP

**DADO** un reply de `core` con `file_type_not_allowed`, `file_too_large`, `file_not_owned`,
`file_not_found` o `file_not_available`
**CUANDO** la `api` lo traduce
**ENTONCES** responde 400, 400, **403**, 404 y 404 respectivamente — **ninguno cae en el 500 genérico**
(ADR-002 lo exige)

### CA-8: `DELETE /api/attachments/{id}` borra solo el vínculo

**DADO** un archivo con dos vínculos
**CUANDO** un usuario elimina uno de los dos
**ENTONCES** se elimina **solo ese vínculo**, el archivo se conserva en el bucket y en `files`, y el
otro vínculo sigue funcionando

### CA-9: La desvinculación es un comando de `core`

**DADO** el código de `DELETE /api/attachments/{id}` después de esta story
**CUANDO** se revisa
**ENTONCES** la `api` **autoriza y publica un comando**; no borra la fila por su cuenta ni toca el
bucket — de lo contrario reabriría por otra puerta la excepción que este REQ cierra

### CA-10: El vínculo eliminado deja de dar acceso

**DADO** un vínculo eliminado
**CUANDO** se intenta acceder al archivo por ese vínculo
**ENTONCES** el acceso falla con 404, aunque el archivo siga existiendo por otro vínculo

### CA-11: Los frontends siguen recibiendo el `Attachment` aplanado

**DADO** un `GET /api/attachments` o `GET /api/attachments/{id}` después de esta story
**CUANDO** el frontend lee la respuesta
**ENTONCES** encuentra los mismos campos de archivo que hoy (`fileName`, `fileSize`, `mimeType`,
`storageKey`, ...) más `fileId` y `byteStatus`, y sin `description`

### CA-12: El enum de tipos de entidad se reduce a cinco

**DADO** `AttachmentEntityType` en `docs/apis/api.yaml`
**CUANDO** se revisa después de esta story
**ENTONCES** tiene exactamente `project`, `requirement`, `objective`, `requirement_comment` y
`objective_comment` — sin `comment`, `comment_draft`, `requirement_draft`, `objective_draft` ni `stage`

### CA-13: El timeout del bus se traduce a 503

**DADO** `core` caído o el bus saturado
**CUANDO** un usuario pide permiso de subida
**ENTONCES** la `api` responde 503 al vencer los 5000 ms de `NATS_REQUEST_TIMEOUT_MS` (ADR-002)

## Diseño Técnico

### Servicios Afectados

| Servicio | Impacto | Cambios Necesarios | Estado |
|----------|---------|-------------------|--------|
| **`api`** | Alto | `POST /api/attachments` y `POST /api/opus/attachments` pasan de multipart a JSON y publican `files.request-upload`. Se elimina `Attachment.create()` y `multer`. `DELETE /api/attachments/{id}` pasa a publicar un comando. Mapeo de los 5 códigos nuevos en `lib/utils/bus/protocol.ts`. Schemas `UploadTicket`, `Attachment` y `AttachmentEntityType` en `docs/apis/api.yaml` | Pending |
| **`core`** | Medio | Comando nuevo `attachments.{id}.delete` — la desvinculación | Done |

### Cambios de API

#### Endpoints Existentes a Modificar

**`POST /api/attachments`** (ref: `docs/apis/api.yaml`:1437-1499)

Estructura actual, verbatim del spec:

```yaml
requestBody:
  content:
    multipart/form-data:
      schema:
        required: [files, entityType]
        properties:
          files: { type: array, maxItems: 10, items: {type: string, format: binary} }
          entityType: { $ref: AttachmentEntityType }
          entityId: { type: integer }
          description: { type: string }
responses:
  '201': { schema: { type: array, items: { $ref: Attachment } } }
```

Estructura nueva:

```yaml
requestBody:
  content:
    application/json:                                   # -> MODIFICADO (era multipart/form-data)
      schema:
        required: [fileName, mimeType, fileSize]        # -> MODIFICADO
        properties:
          fileName: { type: string }                    # + NUEVO
          mimeType: { type: string }                    # + NUEVO
          fileSize: { type: integer }                   # + NUEVO
          checksum: { type: string, nullable: true }    # + NUEVO
          # files       - ELIMINADO: el byte no pasa por acá (D-09)
          # entityType  - ELIMINADO: subir no menciona la entidad (D-12)
          # entityId    - ELIMINADO: idem
          # description - ELIMINADO: columna muerta confirmada
responses:
  '201':
    schema: { $ref: '#/components/schemas/UploadTicket' }   # -> MODIFICADO (era array<Attachment>)
```

- **Cambio:** de multipart a JSON; de un lote de hasta 10 a **un archivo por request** (D-07); la
  respuesta pasa de `array<Attachment>` a un objeto nuevo. **Ya no escribe la base**: publica
  `files.request-upload`.
- **Justificación:** RF-5, RF-6, RF-7, D-07, D-08, D-09, D-12. Cierra la excepción 2 de ADR-001.
- **Autorización:** hoy usa `canUserAccessEntity` sobre la entidad declarada. **Deja de aplicar**: no
  hay entidad. Queda solo el JWT. El control de entidad se corre al momento de vincular.

> **Los frontends no pierden nada.** Hoy leen `fileName`, `fileSize` y `mimeType` de la respuesta para
> el preview embebido; ahora **los tienen antes de llamar** — salen del `File` del input del navegador.
> El único dato que necesitan de vuelta es el `fileId` y la URL.

**`POST /api/opus/attachments`** (ref: `docs/apis/api.yaml`:1877-1911) — mismo cambio, misma forma.
Sigue con `x-roles: [user, external-user]`. Pierde la validación de `entityType` propia del portal.

**`DELETE /api/attachments/{id}`** (ref: `:1519-1532`) — hoy *"Borra la fila y el objeto del bucket"*.
Ahora **borra solo el vínculo; el archivo se retiene** (D-04). Es un cambio de comportamiento
observable: con 0..N vínculos, borrar el objeto rompería los otros.

- **Y es la única escritura de adjuntos que quedaba fuera del bus.** Si el vínculo pasa a ser una fila
  de dominio, borrarlo **debe** ser un comando de `core` para no reabrir la excepción que este REQ
  cierra. **Se incluye en el alcance.**

**`GET /api/attachments/{id}`** (ref: `:1502-1518`) — el schema `Attachment` cambia de forma (abajo).
Sigue recibiendo el id **del vínculo** (D-16). El `include` a `files` que lo alimenta llega con la
Story 5.

#### Nuevos Endpoints

**`attachments.{id}.delete`** — comando de bus (la desvinculación)

- **Servicio:** `core`
- **Subject:** `{instance}.{user-id}.gestion.v1.attachments.{id}.delete`
- **Parámetro `{id}`:** el id de **`attachments`** — el vínculo, no el archivo. El nombre es
  deliberado: `attachments.{id}.delete` es más honesto que `files.{id}.unlink`, porque su parámetro es
  el id del vínculo, **al revés que el comando de descarga**.
- **Descripción:** borra la fila de `attachments`. **No toca `files` ni el bucket.**
- **Request:** sin payload propio más allá de los campos de auditoría del comando.
- **Response:** `success({ id })`
- **Errores:** `invalid_fields` (vínculo inexistente), `internal_error`

**Schema nuevo — `UploadTicket`:**

```yaml
UploadTicket:
  type: object
  required: [fileId, uploadUrl, expiresIn]
  properties:
    fileId: { type: integer, description: Id de `files`. Es lo que viaja en `fileIds` al guardar la entidad }
    uploadUrl:
      type: string
      description: |
        URL prefirmada de **PUT**, de un solo objeto y TTL corto (D-10). El navegador la
        usa directo contra el storage: no pasa por la api ni por el bus.
    expiresIn: { type: integer, description: Segundos de validez. Sale de `system_settings` }
```

> **El campo se llama `id` en el bus y `fileId` en HTTP.** No es un descuido: en el bus `id` es la
> convención de todas las creaciones, y en HTTP `fileId` dice de qué id se trata, que importa porque
> el contrato HTTP de adjuntos maneja **dos** espacios de ids (el del vínculo y el del archivo). La
> `api` traduce, que es lo que ya hace en las cinco traducciones de contrato que documenta su `overview.md`.

**Schema `Attachment` modificado** (ref: `docs/apis/api.yaml`:2578-2604):

```yaml
Attachment:
  properties:
    id: { type: integer }                                # sin cambios — es el id del VÍNCULO, preservado (D-06)
    entityType: { $ref: AttachmentEntityType }           # -> MODIFICADO: el enum pierde 5 valores
    entityId:
      type: integer
      # nullable: true          - ELIMINADO -> ahora NOT NULL (D-01)
    fileId: { type: integer }                            # + NUEVO — FK a `files`
    # --- los 9 campos de abajo siguen en la RESPUESTA (contrato intacto para los fronts),
    #     pero se leen de `files` por el include, no de `attachments`
    fileName: { type: string }
    fileSize: { type: integer }
    mimeType: { type: string }
    storageKey: { type: string }                         # -> MODIFICADO: el patrón ya no incluye entityType/entityId (D-02)
    storageBucket: { type: string }
    storageRegion: { type: string }
    uploadedBy: { type: string }
    checksum: { type: string }
    byteStatus: { type: string, enum: [pending, uploaded] }   # + NUEVO — estado del byte (D-03)
    # description  - ELIMINADO (columna muerta confirmada)
    createdAt: { type: string, format: date-time }
```

> **Los 9 campos del archivo se mantienen en la respuesta HTTP a propósito.** Aplanar `files` sobre el
> vínculo mantiene intacto el contrato con los dos frontends, cuyos tipos están escritos a mano y **no
> fallan en compilación si divergen**. Un `Attachment` con el archivo anidado obligaría a tocar todos
> los consumidores por un beneficio de forma.

**`AttachmentEntityType` modificado** (ref: `docs/apis/api.yaml`:2255-2275). De 10 valores a **5**:

```yaml
enum:
  - project
  - requirement
  - objective
  - requirement_comment
  - objective_comment
  # - comment            - ELIMINADO (legado, resuelto en el backfill)
  # - comment_draft      - ELIMINADO (D-01: no hay draft)
  # - requirement_draft  - ELIMINADO (D-01)
  # - objective_draft    - ELIMINADO (D-01)
  # - stage              - ELIMINADO (resuelto en el backfill)
```

**Mapeo de códigos en `api/lib/utils/bus/protocol.ts`** (ADR-002 lo exige, o caen en 500 genérico):

| `errorCode` | HTTP |
|---|---|
| `file_type_not_allowed` | 400 |
| `file_too_large` | 400 |
| `file_not_owned` | **403** |
| `file_not_found` | 404 |
| `file_not_available` | 404 |

### Cambios de Base de Datos

Ninguno. El esquema lo dejó listo la Story 1. Lo que cambia es **quién escribe**: la `api` deja de
hacerlo por completo en el módulo de adjuntos.

### Flujo de Interacción

#### Escenario: pedido de permiso de subida desde la web (CA-1 a CA-5)

**Trigger:** El usuario selecciona un PDF de 4 MB en un formulario.

**Flujo:**

1. **[navegador]**
   - Acción: `POST /api/attachments` contra la api
   - Payload: `{ "fileName": "informe.pdf", "mimeType": "application/pdf", "fileSize": 4194304, "checksum": "9c1e..." }`
   - → Un request por archivo (D-07)

2. **[`api` — `attachments-post.ts`]**
   - Acción: valida el JWT (capa 1) y la forma con Joi. **No valida tipo ni tamaño** — eso es de
     `core` ahora (D-08). **No toca la base**
   - Output: publica `{instance}.{api-service-user}.gestion.v1.files.request-upload` con
     `{ uploader: <zitadel-sub>, fileName, mimeType, fileSize, checksum }`
   - → Espera respuesta, timeout 5000 ms (ADR-002)

3. **[`core`]**
   - Acción: la de la Story 2 — política, clave, fila de `files`, firma del PUT
   - Output: `{ status: 'success', data: { id, uploadUrl, expiresIn } }`

4. **[`api`]**
   - Acción: traduce el reply. **No relee la base**: la URL prefirmada no está en la base y no es
     reconstruible desde afuera de `core`
   - Output: `201 { "fileId": 1234, "uploadUrl": "https://...", "expiresIn": 300 }`

**Outcome:** El navegador tiene el `fileId` y la URL para subir directo a S3 (Story 6/7). La `api` no
tocó el byte ni la base.

**Manejo de errores:**

| Condición | Reply de core | HTTP |
|---|---|---|
| Extensión o MIME fuera de lista | `file_type_not_allowed` | 400 |
| Supera el máximo configurado | `file_too_large` | 400 |
| Forma del payload inválida | *(Joi en la api, sin publicar)* | 400 |
| Timeout del bus | — | 503 |

#### Escenario: desvincular un archivo de una entidad (CA-8 a CA-10)

**Trigger:** El usuario elimina un adjunto de un requisito.

**Flujo:**

1. **[navegador → `api`]** `DELETE /api/attachments/{id}`
2. **[`api`]** Autoriza sobre la entidad del vínculo (`canUserAccessEntity`). Si falla, **403 sin publicar**
3. **[`api`]** Publica `attachments.{id}.delete`
4. **[`core`]** Borra la fila de `attachments`. **No toca `files` ni el bucket** — con 0..N vínculos,
   borrar el objeto rompería los otros
5. **[`api`]** Traduce el reply y responde

**Outcome:** El vínculo desaparece; el archivo se conserva y sus otros vínculos siguen funcionando.

**Manejo de errores:**
- Vínculo inexistente → `invalid_fields` → 404/400 según el mapeo vigente
- Sin permiso sobre la entidad → 403, sin publicar

### Flujos Afectados

- **`subida-de-archivos`** (ref: `docs/flows/subida-de-archivos.md`) — esta story agrega el canal HTTP
  al flujo que la Story 2 creó: la `api` como traductora entre el contrato HTTP y el comando del bus.
- **`vinculacion-de-archivos`** (ref: `docs/flows/vinculacion-de-archivos.md`) — se suma la
  **desvinculación** (`attachments.{id}.delete`), que cierra el ciclo de vida del vínculo.
- **`adjuntos`** (ref: `docs/flows/adjuntos.md`) — sus pasos 2, 3 y 4 (subida multipart, validación y
  rollback en la api, escritura de la fila sin pasar por core) quedan **eliminados** por esta story.
- **`alta-requisito-desde-portal`** (ref: `docs/flows/alta-requisito-desde-portal.md`) — el paso 3
  (`POST /api/opus/attachments` multipart) pasa a JSON, un archivo por request, con `UploadTicket`.
- **`asignacion-semanal`** (ref: `docs/flows/asignacion-semanal.md`:164) — **sin cambios funcionales**.
  Solo la mención *"las dos excepciones vivas del producto, junto con la fila de `attachments`"* queda
  desactualizada: al cerrarse la excepción 2, `PUT /api/week-assigned-times` queda como **la única**
  excepción viva. Corrección de una línea.

### Consideraciones Técnicas

**Seguridad:**
- **Cierra la excepción 2 de ADR-001**: la `api` deja de escribir la base en el módulo de adjuntos.
- **La autorización de subida se relaja, y es correcto.** Al desaparecer la entidad (D-12), queda solo
  el JWT. **No es una pérdida de control real:** lo que protege el permiso de proyecto es la entidad, y
  el control se corre al momento de vincular. Lo que un usuario gana es poder crear `File` sin vínculo
  — que es exactamente RF-1, y cuyo costo es **acumulación de basura, no acceso indebido**. Sin barrido
  ese costo no tiene techo (riesgo asumido del REQ).
- **Todo `errorCode` nuevo tiene que estar en el mapa de `protocol.ts`** o cae en 500 genérico
  (ADR-002). Los cinco entran en esta story.

**Performance:**
- **El beneficio principal:** la `api` deja de bufferizar hasta 10 MB × 10 archivos. Con
  `multer.memoryStorage()` ese es su pico de memoria hoy.
- **Un request por archivo sube el número de round-trips**: 3 archivos son 3 requests + 3 comandos,
  donde antes era 1 multipart. Cada uno es chico y sin binario, y el fallo de uno es independiente del
  resto — que es el punto de D-07. El tiempo total lo domina el PUT a S3, que ahora es paralelo desde
  el navegador en lugar de secuencial en la api.

**Riesgos:**
- **El rollback de S3 desaparece y nadie lo nota.** Hoy la `api` borra del bucket lo ya subido si un
  lote falla a mitad (`attachments-post.ts:124-134`), y `conventions/storage.md` lo declara *"el modelo
  para cualquier operación futura que toque un sistema externo antes de poder fallar"*. Con el byte
  directo a S3 **ese rollback ya no existe ni puede existir**: quien escribe el objeto es el navegador.
  **Mitigación: ninguna**, es consecuencia aceptada — pero `conventions/storage.md` tiene que
  actualizarse para no seguir presentando como modelo un patrón que el flujo principal ya no usa (va
  por `/product-change-technical-definition`).

**Tests:**
- **Los tests de `attachments-post.ts` se reescriben, no se ajustan.** Hoy verifican multipart,
  `multer`, el rollback de S3 y el `Attachment.create()`. **Nada de eso queda.** Los nuevos verifican
  que se publica `files.request-upload` con el payload correcto y que el ticket se traduce a 201.
- **Los tests que cubren la ruta completa siguen pasando por `core` sin cambios de setup**, porque el
  `FakeBus` lo ejecuta de verdad (ADR-013) — es lo que hace que el corrimiento de la validación de la
  `api` a `core` quede cubierto de punta a punta con los tests que ya existen.
- **El comando de desvinculación necesita su propio test de que no toca `files` ni el bucket.**

**Dependencias:**
- **S-003** debe estar completa: `core` tiene que aceptar `fileIds` antes de que la `api` cambie el
  contrato de subida.
- **Habilita las stories 6 y 7** (los dos frontends), que dependen de este contrato ya cerrado.
- **No depende de la Story 5 (las lecturas)**, y a propósito: los dos cortes se despliegan y se
  verifican por separado.
