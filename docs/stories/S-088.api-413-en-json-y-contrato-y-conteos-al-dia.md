# S-088: 413 en JSON y contrato y conteos al día

**Status:** Ready
**Created:** 2026-10-24
**Source:** REQ-017

## Historia de Usuario

**Como** persona que integra o mantiene la api de Jiku,
**quiero** que `docs/apis/api.yaml` y los documentos públicos declaren lo que la api realmente hace (413, sin 400 espurio, conteo real),
**para** poder confiar en el contrato y en los números que citan el README y `documentation/`.

## Criterios de Aceptación

### CA-1: Conteo coherente

**DADO** `docs/apis/api.yaml`
**CUANDO** se cuentan sus operaciones
**ENTONCES** el número coincide con el del encabezado y con los citados en `README.md`, `documentation/api-reference.md` y `docs/prd/architecture.md`

### CA-2: 413 declarado y real

**DADO** un `POST`/`PUT` de `/api/docs` con un cuerpo mayor a 768 KiB
**CUANDO** llega a la api
**ENTONCES** responde 413 `{ "code": "payload_too_large", "message": "El cuerpo de la solicitud supera el límite permitido" }` tal como lo declara el contrato, sin llegar a la ruta ni al bus

### CA-3: Otros errores sin cambio

**DADO** cualquier error que no sea `entity.too.large`
**CUANDO** pasa por la cadena de errores de `app.ts`
**ENTONCES** sigue con `next(err)`, sin cambio de comportamiento

### CA-4: `DELETE /docs/shares/{id}` sin 400

**DADO** `DELETE /docs/shares/{id}` en el contrato
**CUANDO** se revisan sus respuestas
**ENTONCES** no declara `400` (declara `200, 401, 403, 404, 500, 503, 504`)

### CA-5: `api-reference.md` verificable

**DADO** `documentation/api-reference.md`
**CUANDO** se corre la receta de `grep` de su sección "Regenerating this list"
**ENTONCES** el conteo del documento coincide con las filas listadas (se agregan las 27 filas de documentación que faltan) y "Errors" cita `payload_too_large`

### CA-6: ADR-015 al día

**DADO** `docs/adrs/ADR-015-modulos-opcionales-del-bus.md`
**CUANDO** se revisa
**ENTONCES** registra F-12 y B-1 a B-4 como resueltos por REQ-017 y deja anotado el pendiente de que el resto de las rutas no declara `413`

### CA-7: Suite verde

**DADO** el monorepo con los cambios de las tres stories
**CUANDO** se corre `npm run build && npm run lint && npm test`
**ENTONCES** todo pasa

### Cambios de API

#### Endpoints Existentes a Modificar

**`DELETE /docs/shares/{id}`** (ref: `docs/apis/api.yaml`:línea 2737)
- **Cambio:** se quita `'400': { $ref: '#/components/responses/ModuleBadRequest' }`. El handler no tiene más input que el path (un id malformado es 404 `share_not_found` sin bus) y el payload a `shares.{id}.revoke` es `{}`.
- **Justificación:** se corrige el contrato, no el handler (DD-4).

**Escrituras de `/docs/*`** (ref: `docs/apis/api.yaml`:líneas 2127, 2201, 2460, 2498, 2534, 2571, 2606, 2646, 2670)
- `POST /docs/documents`, `PUT /docs/documents/{id}`, `POST /docs/documents/{id}/move`, `/restore`, `/lock`, `/unlock`, `POST /docs/attachments`, `POST /docs/attachments/{id}/confirm`, `POST /docs/documents/{id}/shares`.
- **Cambio:** `'413': { $ref: '#/components/responses/PayloadTooLarge' }` en las nueve. Respuesta nueva en `components/responses`:
  ```yaml
  PayloadTooLarge:
    description: El cuerpo JSON supera el límite de la ruta (768 KiB en las escrituras de /docs). Lo
      responde body-parser antes de llegar a la ruta; no llama al bus.
    content:
      application/json:
        schema: { code: payload_too_large, message: string }   # con el esquema de error del archivo
  ```
- **Justificación:** RF-13, CA-2.

**Encabezado de `docs/apis/api.yaml`** (línea 3)
- **Cambio:** "los 88 endpoints" -> "las 89 operaciones" (72 internas, 15 del portal, 2 públicas). El conteo se verifica contando operaciones después de S-087 (una ruta del portal se reemplaza por otra, el total no cambia).

### Flujo de Interacción

#### Escenario: escritura de docs con cuerpo grande (CA-2)

**Trigger:** `PUT /api/docs/documents/{id}` con más de 768 KiB.

**Flujo:**

1. **[web]**
   - Acción: envía el `PUT`
   - Output: cuerpo mayor al límite

2. **[api]**
   - Acción: `docsWriteJson` (body-parser, `limit: '768kb'`) lanza `PayloadTooLargeError` (`type: 'entity.too.large'`); el manejador nuevo, al final de la cadena de `app.ts`, lo atiende
   - Output: `413 { "code": "payload_too_large", "message": "El cuerpo de la solicitud supera el límite permitido" }`

**Outcome:** el cliente recibe un 413 JSON con la forma del resto de la api, en lugar del HTML de `finalhandler`.

**Manejo de errores:**
- Cualquier otro error -> `next(err)` (sin cambio)

### Flujos Afectados

- **documentos-desde-la-web** (ref: docs/flows/documentos-desde-la-web.md) — manejo de errores: 413 `payload_too_large` en las escrituras (pasos de edición).

### Consideraciones Técnicas

**Seguridad:**
- El 413 JSON no expone el stack que el `finalhandler` mostraba fuera de producción.

**Performance:**
- Sin impacto.

**Dependencias:**
- Depende de S-087: el conteo final y las filas de `api-reference.md` reflejan la ruta definitiva del adjunto.
- El manejador aplica a toda la api (body-parser corre en todas las rutas), pero el contrato lo declara solo en las nueve escrituras de docs; el resto es un desfase previo anotado en ADR-015 (R-5). El fallback 404 de `app.ts` (un solo argumento) es un defecto previo fuera de alcance.
- R-4: si jiku-docs respondiera `invalid_fields` a `shares.{id}.revoke`, el mapa produciría un 400 no declarado; improbable, se mantiene la decisión.
