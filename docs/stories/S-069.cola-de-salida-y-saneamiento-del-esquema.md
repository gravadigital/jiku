# S-069: Cola de salida y saneamiento del esquema

**Status:** Ready
**Created:** 2026-09-17
**Source:** REQ-015

## Historia de Usuario

**Como** desarrollador de `core`,
**quiero** una tabla `notification_outbox` con su índice parcial y su modelo Sequelize, y la baja
de las tres tablas muertas de la funcionalidad de mail eliminada (`objective_mail_threads`,
`requirement_mail_threads`, `inbound_mail_threads`) con sus tres modelos,
**para** tener dónde escribir la cola de notificaciones y dejar el esquema sin los restos de una
funcionalidad que ya no existe, antes de que ninguna story de lógica dependa de la tabla.

Esta story no escribe ni lee ninguna fila desde un comando: es exclusivamente esquema, modelo y
las tres claves de configuración con sus defaults en código. El saneamiento va en la misma story
porque comparte el mismo archivo de migración: separarlo produciría dos migraciones consecutivas
sobre el mismo tema.

## Criterios de Aceptación

### CA-1: La tabla `notification_outbox` existe con su forma completa

**DADO** que se aplica la migración de esta story
**CUANDO** se inspecciona el esquema
**ENTONCES** existe `notification_outbox` con columnas `id BIGSERIAL PK`, `type VARCHAR(100) NOT
NULL`, `channel VARCHAR(20) NOT NULL DEFAULT 'email'`, `recipient_user_id VARCHAR(100) NOT NULL
REFERENCES users(id)`, `recipient_email VARCHAR(255) NOT NULL`, `payload JSONB NOT NULL`, `status
VARCHAR(20) NOT NULL DEFAULT 'pending'`, `attempts INTEGER NOT NULL DEFAULT 0`, `next_attempt_at
TIMESTAMP NOT NULL DEFAULT NOW()`, `last_error TEXT NULL`, `created_at TIMESTAMP NOT NULL DEFAULT
NOW()`, `sent_at TIMESTAMP NULL`

### CA-2: El índice es parcial y cubre exactamente la consulta del proceso de envío

**DADO** la tabla creada
**CUANDO** se inspecciona el índice
**ENTONCES** existe `idx_notification_outbox_pending` sobre `(next_attempt_at, id)` con
`WHERE status = 'pending'`, sin cubrir las filas ya enviadas

### CA-3: `type` y `status` son `VARCHAR`, no ENUM nativo

**DADO** la tabla creada
**CUANDO** se inspecciona el tipo de las columnas `type` y `status`
**ENTONCES** ambas son `VARCHAR`, no un tipo ENUM de PostgreSQL — para que agregar un tipo de
notificación futuro sea sumar una fila al registro de código, no un `ALTER TYPE`

### CA-4: No hay unique de idempotencia sobre la tabla

**DADO** la tabla creada
**CUANDO** se inspeccionan sus constraints
**ENTONCES** no existe ningún `UNIQUE` sobre `(type, recipient_user_id, ...)` — la entrega es
at-least-once por decisión (RF-25) y un unique de ese tipo rompería el caso legítimo de dos
comentarios seguidos del mismo autor en el mismo requisito

### CA-5: El modelo `NotificationOutbox` existe en `packages/models`

**DADO** el paquete `packages/models`
**CUANDO** se importa su barrel
**ENTONCES** exporta un modelo Sequelize `NotificationOutbox` mapeado 1:1 a la tabla, con
`recipient_user_id` tipado como `VARCHAR(100)` y sin alterar ningún otro modelo existente

### CA-6: Las tres tablas muertas ya no existen

**DADO** que se aplica la migración
**CUANDO** se inspecciona el esquema
**ENTONCES** `objective_mail_threads`, `requirement_mail_threads` e `inbound_mail_threads` **no
existen**, junto con sus índices (`uk_inbound_mail_threads_message_id`,
`idx_inbound_mail_threads_requirement_id`), y ninguna funcionalidad del producto se degrada

### CA-7: Los tres modelos Sequelize de las tablas muertas ya no existen

**DADO** `packages/models`
**CUANDO** se inspecciona su código fuente
**ENTONCES** los tres modelos (`objective-mail-thread.model.ts`,
`requirement-mail-thread.model.ts`, `inbound-mail-thread.model.ts`) fueron eliminados **antes** de
aplicar el `DROP` en la migración — el orden importa: si el modelo sigue registrado, `sync()` en
`development`/`testing` recrea la tabla que la migración acaba de borrar

### CA-8: El `down` de la migración es honesto sobre lo que recupera

**DADO** la migración de esta story
**CUANDO** se revierte con `down`
**ENTONCES** recrea las tres tablas **vacías** (reversible en estructura) y dicho contenido
**no** se recupera (no reversible en datos), con un comentario en el código que lo deja explícito

### CA-9: Las tres claves nuevas de `system_settings` funcionan con default en código

**DADO** una base sin fila cargada para `notification-dispatch-interval-seconds`,
`notification-batch-size` o `notification-max-attempts`
**CUANDO** el código las lee
**ENTONCES** devuelve `60`, `50` y `5` respectivamente, siguiendo el mismo patrón sin caché que
`core/src/commands/files/settings.ts` ya usa para las claves de archivos

### CA-10: La migración se aplica sin romper la suite existente

**DADO** la suite completa de tests de `core` y `api`
**CUANDO** se aplica esta migración y se corren los tests
**ENTONCES** ningún test que dependía de las tres tablas eliminadas queda roto sin resolver —
se verificó previamente que ningún código fuera de `packages/models` las referencia
(`core/src`, `api/lib`, `web/`, `opus-web/`)

### Cambios de Base de Datos

#### Nuevas Tablas

**`notification_outbox`**

| Columna | Tipo | Restricciones | Para qué |
|---|---|---|---|
| `id` | `BIGSERIAL` | PK | `BIGINT`, no `INTEGER`: es una tabla de flujo que crece con cada hecho notificado |
| `type` | `VARCHAR(100)` | NOT NULL | Clave del registro de tipos (S-071). Nunca texto libre |
| `channel` | `VARCHAR(20)` | NOT NULL, default `'email'` | Única concesión al multicanal |
| `recipient_user_id` | `VARCHAR(100)` | NOT NULL → `users.id` | Mismo tipo y FK que `requirement_subscriptors.user_id` |
| `recipient_email` | `VARCHAR(255)` | NOT NULL | Congelado al encolar. Un destinatario sin correo no llega a escribirse |
| `payload` | `JSONB` | NOT NULL | Datos del mail, congelados |
| `status` | `VARCHAR(20)` | NOT NULL, default `'pending'` | `pending` / `sent`. No hay `failed`: tras el máximo de intentos la fila se borra |
| `attempts` | `INTEGER` | NOT NULL, default `0` | |
| `next_attempt_at` | `TIMESTAMP` | NOT NULL, default `NOW()` | Backoff |
| `last_error` | `TEXT` | NULL | Causa del último fallo |
| `created_at` | `TIMESTAMP` | NOT NULL, default `NOW()` | |
| `sent_at` | `TIMESTAMP` | NULL | `NULL` mientras `status = 'pending'` |

**Índice, uno solo:**

```sql
CREATE INDEX idx_notification_outbox_pending
  ON notification_outbox (next_attempt_at, id)
  WHERE status = 'pending';
```

**Por qué `type` y `status` son `VARCHAR`:** el esquema ya documenta la fricción de los ENUM entre
`sync()` y las migraciones (`identity_type` se declara `DataType.STRING` por eso). Obligar a un
`ALTER TYPE ... ADD VALUE` (no reversible dentro de una transacción en PostgreSQL) contradiría que
"agregar un tipo es sumar una entrada y su plantilla".

**Por qué no hay unique de idempotencia:** la entrega es at-least-once (RF-25). La ventana de
duplicado está entre el `send` y el `UPDATE`, no en el `INSERT`; un unique sobre
`(type, recipient_user_id, entity, ...)` prometería exactly-once sin darlo, y rompería el caso
legítimo de dos comentarios seguidos del mismo autor.

#### Tablas Existentes a Modificar

Ninguna.

#### Tablas Eliminadas

```sql
DROP TABLE IF EXISTS objective_mail_threads;
DROP TABLE IF EXISTS requirement_mail_threads;
DROP TABLE IF EXISTS inbound_mail_threads;
```

- Ref: `docs/db-schemas/jiku.md:621-634` ("Tablas sin uso").
- Se dan de baja también los tres modelos Sequelize de `packages/models`, **antes** del `DROP` en
  el orden de ejecución del código (aunque vivan en el mismo commit): si el modelo sigue
  registrado, `sync()` en `development`/`testing` recrea la tabla (`core/src/models/index.ts:56-62`).
- `inbound_mail_threads` tiene dos índices (`uk_inbound_mail_threads_message_id`,
  `idx_inbound_mail_threads_requirement_id`) que caen con la tabla.
- El `down` de la migración recrea las tres tablas vacías: reversible en estructura, no en datos.
  Comentario explícito en el código.
- **Verificación de operación previa al deploy** (fuera de la migración): confirmar que las tres
  tablas no tienen filas con valor antes de aplicar. No es una condición dentro de la migración —
  una migración que se saltea a sí misma según los datos deja dos esquemas distintos en dos
  instalaciones.

#### Claves nuevas de `system_settings`

Sin cambio de esquema (la tabla ya existe con `value TEXT`). Siguiendo el precedente de las cinco
claves de archivos: defaults en el código, sembradas por la migración por conveniencia, leídas
**sin caché**.

| `key` | Default | Qué controla |
|---|---|---|
| `notification-dispatch-interval-seconds` | `60` | Cada cuánto corre el proceso (S-073) |
| `notification-batch-size` | `50` | Filas por lote (S-073) |
| `notification-max-attempts` | `5` | Máximo de intentos antes del descarte (S-073) |

Estas tres claves no se leen todavía en ningún código de esta story — se siembran ahora porque
comparten la migración con la tabla, y las lee S-073 (proceso de envío).

### Flujo de Interacción

Esta story no introduce ningún flujo de interacción de comando: no hay comando que escriba en
`notification_outbox` todavía (eso empieza en S-071). El único "flujo" es el de migración:

1. **[migración `up`]** — crea `notification_outbox` con su índice parcial, dropea las tres tablas
   muertas, siembra las tres claves de `system_settings` con sus valores default (por
   conveniencia operativa, no porque el código las requiera cargadas).
2. **[código]** — se agrega el modelo `NotificationOutbox` a `packages/models` y se eliminan los
   tres modelos de las tablas muertas del mismo paquete.
3. **[migración `down`]** — dropea `notification_outbox`, recrea las tres tablas vacías.

**Manejo de errores:**
- Una base con filas en las tres tablas muertas al momento de aplicar: no es un caso que la
  migración maneje — es una verificación operativa previa al deploy, documentada como tal.

### Consideraciones Técnicas

**Seguridad:**
- Ninguna consideración nueva: la tabla no se expone por HTTP ni por el bus en esta story.

**Performance:**
- El índice parcial mantiene su tamaño acotado al de la cola pendiente, no al histórico — decisión
  central de esta story, no un detalle de implementación.

**Dependencias:**
- Ninguna con otra story de este REQ para poder aplicarse: es la base de S-071 (que escribe en la
  tabla) y de S-073 (que lee las tres claves de `system_settings`).
- Orden de migraciones: esta es la primera del REQ; toda story posterior que toque
  `notification_outbox` asume que esta ya corrió.
