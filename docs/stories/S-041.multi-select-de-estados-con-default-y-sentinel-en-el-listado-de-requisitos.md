# S-041: Multi-select de estados con default y sentinel en el listado de requisitos

**Status:** Ready
**Created:** 2026-09-01
**Source:** REQ-009

## Historia de Usuario

**Como** usuario interno que trabaja el listado global de requisitos (`/requirements`),
**quiero** filtrar por varios estados a la vez, con un default razonable al entrar y la
posibilidad de ver todos los estados deseleccionando todo,
**para** enfocarme en el trabajo en curso sin perder la capacidad de ver el panorama completo,
igual que ya puedo hacerlo en el listado de tareas.

## Criterios de Aceptación

### CA-1: Default de cuatro estados al entrar sin `state` en la URL

**DADO** un usuario interno que abre `/requirements` sin parámetro `state` en la URL
**CUANDO** se carga la pantalla
**ENTONCES** el filtro de estado muestra seleccionados `Planificación`, `En cola`, `Desarrollo` y
`Revisión`, y la tabla lista solo requisitos en esos cuatro estados — ninguno en `analisis`,
`resuelto` ni `cancelado`

### CA-2: Agregar un estado a la selección

**DADO** el filtro con los cuatro estados por default
**CUANDO** el usuario agrega `Análisis` a la selección
**ENTONCES** la URL pasa a `state=planificacion,en_cola,desarrollo,revision,analisis`, se pide a
la api con esos cinco valores, la página vuelve a 1 y la tabla lista requisitos de los cinco
estados

### CA-3: Quitar un estado de la selección

**DADO** el filtro con `planificacion,en_cola,desarrollo,revision` seleccionados
**CUANDO** el usuario deselecciona `Revisión`
**ENTONCES** la URL pasa a `state=planificacion,en_cola,desarrollo`, la página vuelve a 1 y ningún
requisito en `revision` aparece en la tabla

### CA-4: Deseleccionar todos los estados muestra todos los requisitos

**DADO** el filtro con al menos un estado seleccionado
**CUANDO** el usuario deselecciona todos los estados
**ENTONCES** la URL pasa a `state=all`, la api se llama sin filtro de estado, y la tabla lista
requisitos de los siete estados — no una lista vacía y no un retorno al default de cuatro

### CA-5: La selección se persiste en la URL

**DADO** un usuario con `state=desarrollo,revision` en la URL
**CUANDO** recarga la página o abre el link compartido
**ENTONCES** el filtro de estado muestra seleccionados exactamente `Desarrollo` y `Revisión`, y la
tabla lista solo esos dos estados

### CA-6: El filtro de estado se combina en conjunción con los demás filtros

**DADO** `state=desarrollo,revision` seleccionado
**CUANDO** el usuario además filtra por proyecto y por texto de búsqueda
**ENTONCES** los tres filtros se aplican en conjunto: AND entre filtros, OR entre los estados

### CA-7: Combinación sin resultados

**DADO** una combinación de estados seleccionados sin ningún requisito que la satisfaga
**CUANDO** se carga el listado
**ENTONCES** la tabla muestra el empty state de requisitos

### Flujo de Interacción

#### Escenario A: carga inicial del listado sin `state` en la URL (CA-1)

**Trigger:** el usuario navega a `/requirements`.

**Flujo:**

1. **[web — Server Component]** `web/src/app/(loggedin)/requirements/page.tsx:18`
   - Actual: `state: resolvedSearchParams.state || null` — sin default.
   - → **MODIFICADO**: `state: resolvedSearchParams.state || 'planificacion,en_cola,desarrollo,revision'`,
     replicando el mecanismo de tareas (`objectives/page.tsx:25`,
     `state: resolvedSearchParams.state || 'activo'`).
   - El default vive en el servidor de la página, no en el componente de filtros: así el primer
     render ya trae el recorte correcto y no hay parpadeo de "todos y después cuatro".

2. **[web — RequirementList / TanStack Query]**
   - `useRequirements({ filters })` serializa los filtros con `cleanFilters`
     (`requirementsApi.ts:15-19`), que descarta valores vacíos **y el literal `'all'`** — el
     sentinel ya está contemplado en el serializador, no hay que tocarlo.
   - Llama: `GET /requirements?state=planificacion,en_cola,desarrollo,revision&page=1&limit=15`

3. **[api]** Responde según el contrato de S-040: 200 con los requisitos en esos cuatro estados.

**Outcome:** la tabla muestra solo los cuatro estados por default.

**Manejo de errores:**
- Estado fuera del enum → 400 `invalid_fields` (no alcanzable desde la UI con los `STATE_OPTIONS`
  cerrados al enum).

#### Escenario B: el usuario cambia la selección de estados (CA-2, CA-3)

**Trigger:** el usuario agrega o quita un estado en el multi-select.

**Flujo:**

1. **[web — RequirementFilters]**
   - Reemplazar el `ReactSelect` sin `isMulti` (`RequirementFilters.tsx:143-150`) por
     `InputMultipleSelect`, el mismo componente que usa
     `ObjectiveSearchFilters.tsx:122-145`.
   - Quitar de `STATE_OPTIONS` la opción `"Todos los estados"` de valor `''`: el sentinel `all` la
     reemplaza (ver Escenario C).
   - El `onChange` del multi-select serializa la selección a CSV y la entrega como un único
     string: `onChange('state', 'planificacion,en_cola,desarrollo,revision,analisis')`.

2. **[web — RequirementList.updateFilter]** (`RequirementList.tsx:79-91`) ya hace
   `params.set('state', value)` + `params.delete('page')` + `router.push`. **`params.delete('page')`
   es exactamente CA-2/CA-3 y ya está implementado** — no requiere cambio.

3. **[web]** Next.js re-renderiza el Server Component con los nuevos `searchParams`, TanStack
   Query re-pide con la nueva key (`docs/adrs/ADR-011-tanstack-query.md`), y el flujo sigue como
   el Escenario A desde el paso 2.

**Outcome:** URL, request y tabla quedan sincronizados en página 1.

#### Escenario C: deseleccionar todos los estados (CA-4)

**Trigger:** el usuario quita el último estado del multi-select.

**Flujo:**

1. **[web — RequirementFilters]** con la lista vacía emite el sentinel: `onChange('state', 'all')`,
   igual que tareas (`ObjectiveSearchFilters.tsx:69`,
   `formattedValue = value.length === 0 ? 'all' : ...`).

2. **[web — RequirementList.updateFilter]** (`RequirementList.tsx:82-86`) hoy hace
   `if (!value || value === 'all') params.delete(key)` — **borra el parámetro de la URL**.

   > **Punto de atención — riesgo real de esta story.** Ese borrado colisiona con el default
   > nuevo del paso 1 del Escenario A: una URL sin `state` volvería a significar "los cuatro por
   > default", que es precisamente lo que CA-4 prohíbe. → **MODIFICADO**: tratar `state` como
   > excepción y **conservar `state=all` en la URL** (dejar de tratar `'all'` como "borrar" para
   > este parámetro específico), tal como hace tareas, que sí escribe `state=all`. El resto de los
   > filtros mantiene el borrado actual.

3. **[web — requirementsApi.cleanFilters]** descarta `'all'` al serializar
   (`requirementsApi.ts:17`), así que la llamada sale **sin** `state`:
   `GET /requirements?page=1&limit=15`. No requiere cambio: el sentinel ya está contemplado.

4. **[api]** `buildWhere` no agrega condición de estado → devuelve los siete estados.

**Outcome:** todos los requisitos, sin filtro de estado. No lista vacía y no retorno al default.

**Test obligatorio:** abrir el listado, deseleccionar todo, y verificar que la URL queda en
`state=all` y la tabla trae los siete estados.

#### Escenario D: entrada por link compartido con `state` explícito (CA-5)

**Trigger:** el usuario abre `/requirements?state=desarrollo,revision`.

**Flujo:** `page.tsx` toma el valor de la URL (no aplica el default), el filtro deriva su valor
seleccionado del propio `state` de los filtros —parseando el CSV a la lista de opciones, como
`ObjectiveSearchFilters.tsx:126-135`— y la api recibe los dos estados.

**Outcome:** el filtro muestra exactamente `Desarrollo` y `Revisión`, y la tabla lista solo esos.

### Consideraciones Técnicas

**Seguridad:**
- Sin cambios. El filtro es un recorte de lectura sobre un endpoint ya autorizado.

**Performance:**
- El default de cuatro estados **reduce** el conjunto respecto del comportamiento actual (que no
  filtra nada al entrar), así que la carga inicial pasa a ser más barata, no más cara.

**Dependencias:**
- **Requiere S-040 desplegada.** Un CSV contra la api actual (sin S-040) devuelve 400. El orden de
  implementación lo refleja.
- Reutiliza `InputMultipleSelect`, componente ya en producción en
  `ObjectiveSearchFilters.tsx:122-145`. No se crea un componente nuevo (ver Design System, más
  abajo).
- Deuda de DS anotada, no resuelta en esta story: el catálogo de `web` tiene tres formas
  conviviendo de hacer un select (`InputSelect`, `Select` y `react-select` directo con su
  `selectStyles` duplicado en 5 archivos). Esta story reutiliza la que ya usa la pantalla hermana;
  unificarlas queda registrado en `docs/ux/gaps-as-is.md`.

**Accesibilidad (gaps que esta story roza y no cierra, ya anotados en la pantalla):**
- El label del filtro sigue sin `htmlFor` que lo asocie al control, y ahora el control tiene más
  estado que comunicar (una lista de chips en vez de un valor).
- El resultado del filtrado no se anuncia (sin `aria-live`).
