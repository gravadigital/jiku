## Clarificaciones

### Supuestos (modo automático)

El dueño del producto delegó las decisiones de detalle; no se hicieron preguntas. Cada ambigüedad se resolvió así:

- **[Cliente de cada proyecto]:** → **Supuesto tomado:** `GET /api/projects` agrega el cliente del proyecto como objeto
  `client` (`id`, `name`) además de lo que ya devuelve; es un cambio aditivo y no rompe a los otros consumidores. Si el
  diseño encuentra que el cliente ya llega por otra vía, la web se corrige para leerlo de ahí. Un proyecto sin cliente
  devuelve `client: null`.
- **[Relación Cliente → Proyecto]:** → **Supuesto tomado:** se conserva la regla de REQ-021: con un cliente elegido, el
  selector de Proyecto ofrece solo los proyectos de ese cliente (más "Sin proyecto"); elegir un proyecto completa su
  cliente; cambiar el cliente vacía el proyecto solo si no es de ese cliente; "Sin cliente" lo vacía siempre.
- **["+" de la card de proyecto]:** → **Supuesto tomado:** el diálogo abre con el cliente y el proyecto visibles en los
  selectores (no solo en el payload). Lo mismo aplica al editor de un documento existente que ya tiene proyecto.
- **[Listado "Sin cliente · Proyecto"]:** → **Supuesto tomado:** la etiqueta muestra el cliente del documento cuando el
  ítem lo trae en `clients`. Si el documento no tiene cliente propio pero sí un proyecto, se muestra "Sin cliente" (no se
  infiere el cliente del proyecto en la etiqueta), porque refleja las relaciones reales del documento. El diseño
  confirma si el caso de la e2e era un documento sin cliente (consecuencia de JIKU-WEB-3) o un error de la etiqueta, y
  corrige la etiqueta solo si es lo segundo.
- **[Identidad del usuario actual en docs]:** → **Supuesto tomado:** en el módulo de documentación, "yo" es
  `session.user.zitadelId` (el `sub` que jiku-docs guarda en `lock.holder`, `createdBy`, `updatedBy` y `author`). No se
  cambia el criterio de otros módulos (comentarios de requisitos y objetivos siguen con `session.user.id`). Si
  `zitadelId` no está en la sesión, nada se reconoce como propio (se muestra el nombre o "—", nunca "vos" por error).
- **[Alcance de la revisión]:** → **Supuesto tomado:** se revisan todos los componentes y utilidades de
  `web/src/features/docs` que comparan con el usuario actual (lock en lectura, editor y filas; cabecera "Versión N ·
  actualizado …"; "Editado por" en listados; autor en el historial).
- **[Contrato `api.yaml`]:** → **Supuesto tomado:** se alinean los schemas de respuesta de documentos de la web y del
  portal con lo que devuelven las rutas hoy (contrato 1.3.0): sin `path`, `folderId` ni `fileName` en el documento;
  con `clients`, `projects`, `topics`, `visibility` (`internal | public | restricted`), `createdByName`,
  `updatedByName`, `authorName` donde corresponda, `lock` con `holderName`. Los parámetros y cuerpos de rutas que ya no
  usa la web (filtro `folderId`, `move`, carpetas) se documentan tal como están implementados en la api; si una ruta
  sigue existiendo, no se borra del contrato. No se cambia comportamiento de la api para ajustarse al yaml.
- **[Tamaño]:** → **Supuesto tomado:** una o dos stories (api + web para JIKU-WEB-3, web para JIKU-WEB-4 y contrato).

## Requerimientos Funcionales

1. En "Nuevo documento", en la edición y en el "+" de la card de proyecto, el selector de Proyecto ofrece los proyectos
   del cliente elegido.
2. Elegir un proyecto completa su cliente en el selector de Cliente.
3. Elegir un cliente después de un proyecto de ese cliente conserva el proyecto.
4. El "+" de la card de proyecto abre el alta con el cliente y el proyecto visibles en los selectores.
5. `GET /api/projects` informa el cliente de cada proyecto sin romper a sus otros consumidores.
6. El listado de documentos muestra el cliente del documento cuando lo tiene.
7. La web de documentación reconoce a la persona actual por su id de Zitadel: lock propio en otra pestaña, "vos" en la
   cabecera, en "Editado por" y en el historial.
8. `docs/apis/api.yaml` describe los documentos tal como los devuelven las rutas después de REQ-021 (contrato 1.3.0).
9. Cada punto queda cubierto por tests.

## Criterios de Aceptación

1. DADO "Nuevo documento" abierto
   CUANDO la persona elige el cliente EXO y abre Proyecto
   ENTONCES ve los proyectos de EXO (además de "Sin proyecto").

2. DADO "Nuevo documento" sin cliente elegido
   CUANDO la persona elige el proyecto "EXO - Videoconferencia"
   ENTONCES el selector de Cliente muestra EXO.

3. DADO un proyecto de EXO elegido
   CUANDO la persona elige el cliente EXO
   ENTONCES el proyecto se conserva; si elige otro cliente, el proyecto se vacía.

4. DADO el detalle de un proyecto de EXO
   CUANDO la persona toca "+" en la card de Documentación
   ENTONCES el alta muestra EXO / {proyecto} precargados y al guardar manda ambos.

5. DADO un documento existente con proyecto y cliente
   CUANDO la persona lo edita
   ENTONCES los selectores muestran su cliente y su proyecto.

6. DADO un consumidor existente de `GET /api/projects`
   CUANDO pide la lista
   ENTONCES recibe los mismos campos que antes más el cliente de cada proyecto.

7. DADO un documento con cliente y proyecto
   CUANDO aparece en un listado
   ENTONCES la columna Cliente · Proyecto muestra el nombre del cliente, no "Sin cliente".

8. DADO un documento con el lock de la persona actual (humano)
   CUANDO lo abre en otra pestaña
   ENTONCES ve "Lo estás editando en otra pestaña o ventana.", no "Otra persona lo está editando…".

9. DADO un documento cuya última versión guardó la persona actual
   CUANDO ve la cabecera, la fila del listado o el historial
   ENTONCES ve "vos" como autor.

10. DADO una sesión sin `zitadelId`
    CUANDO se muestra un lock o un autor
    ENTONCES no se muestra "vos" ni "Lo estás editando…" por error.

11. DADO `docs/apis/api.yaml`
    CUANDO se leen los schemas de documentos de la web y del portal
    ENTONCES no declaran `path`, `folderId` ni `fileName` en el documento y sí los campos del contrato 1.3.0.
