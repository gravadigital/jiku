# REQ-004: El bus en dos servicios micro — `jiku-commands` y `jiku-queries`

> **Documento autocontenido.** El requerimiento llegó como un documento de análisis interno que
> **ya fue eliminado**: todo su contenido relevante está transcripto acá. No hay ninguna otra
> fuente que consultar.

## Requerimiento Original

**Fuente:** Documento de análisis interno (`bus-micro-dos-servicios.md`, estado "Propuesta — listo
para desarrollo"), eliminado tras la captura.
**Fecha de recepción:** 2026-08-23

> ### 1. Qué resuelve
>
> Hoy el bus tiene **un solo servicio lógico** (`gestion`, servido por `core`) que atiende
> mutaciones, con **una suscripción wildcard** y **cero introspección**: no hay forma de
> preguntarle al bus qué servicios hay, qué endpoints exponen ni cuántas requests atendieron.
>
> Tres problemas concretos:
>
> 1. **El nombre `gestion` quedó viejo.** El producto se llama **Jiku**; el paquete es
>    `@jiku/models`, el contrato es `Jiku core — NATS command contract`, pero el token del subject
>    dice `gestion`.
> 2. **No hay lugar para las lecturas.** Servir consultas por el bus dentro del mismo servicio
>    mezcla dos perfiles opuestos: escrituras cortas y transaccionales contra lecturas largas con
>    joins, compitiendo por el mismo queue group, el mismo pool de base y el mismo timeout.
> 3. **No hay observabilidad del bus.** Para saber si `core` está vivo hay que mandarle un comando
>    real. No hay latencia por operación ni conteo de requests.
>
> ### 2. Alcance y no-objetivos
>
> **Entra:**
> - Renombrar el servicio de escrituras a `jiku-commands` y migrarlo al framework **micro**.
> - Crear el servicio de lecturas `jiku-queries` **dentro del mismo proceso de `core`**, con su
>   propio nombre en el bus, su propio queue group y **su propia conexión de solo lectura** a la
>   base.
> - Registrar los 20 comandos existentes como endpoints micro, sin tocar su lógica.
> - Permisos del auth-callout, variables de entorno y compose.
>
> **No entra:**
> - El contrato de consultas (filtros, paginación, payloads).
> - JetStream, colas o persistencia. Se mantiene **request/reply puro** (ADR-002).
> - Cambiar el formato de `Reply`, los códigos de error o la semántica de los comandos.
> - Migrar los endpoints HTTP de lectura de la api al bus. La api sigue leyendo Postgres directo
>   (ADR-001); `jiku-queries` nace para servir a **otros** consumidores.
>
> **Servicios afectados:** `api`, `core`, `packages/nats-protocol`, `deploy/` (compose y
> auth-callout). **No se agrega ningún deployable**: los dos servicios micro viven en la misma
> imagen de `core`.
>
> ### 3. Contexto: el bus hoy
>
> #### 3.1 El patrón
>
> **NATS core en request/reply, sin JetStream.** La api publica un comando y **espera la
> respuesta** con timeout; `core` valida, escribe en una transacción y responde. No hay cola, ni
> reintento, ni persistencia: si `core` está caído, la request expira y la operación no ocurrió.
> El motivo de fondo es de producto: un `POST /api/requirements` tiene que devolver el recurso
> creado o un error accionable, no un "encolado, vuelva más tarde".
>
> #### 3.2 La gramática de subjects
>
> ```
> {instance}.{user-id}.{svc}.{version}.{método}
>
> dev.323332022539911171.gestion.v1.clients.new
> ```
>
> | Segmento | Qué es | Origen |
> |---|---|---|
> | `instance` | Despliegue: `dev` / `prod` | `NATS_INSTANCE` |
> | `user-id` | **Quién publica**: el `sub` del token de Zitadel, **crudo** | key del service user |
> | `svc` | **A quién le habla**: hoy `gestion` | `NATS_SERVICE_NAME` |
> | `version` | Versión del protocolo: `v1` | `NATS_PROTOCOL_VERSION` |
> | `método` | `clients.new`, `requirements.{id}.edit`, … | el comando |
>
> El user id va crudo **a propósito**: el auth-callout fija el permiso de publicación, así que un
> cliente no puede publicar bajo el id de otro. Eso hace que `core` sepa quién lo llamó **leyendo
> el subject**, no el cuerpo.
>
> `core` se suscribe a `{instance}.*.gestion.v1.>` con queue group `gestion`. El `*` cubre a
> cualquier caller; el queue group hace que N réplicas se repartan los mensajes en vez de procesar
> cada una lo mismo.
>
> #### 3.3 Autenticación e inbox
>
> - Las **creds del sentinel** no conceden permisos por sí solas.
> - El **token de Zitadel** dispara el **auth-callout**, que lee el rol del token y mintea los
>   permisos de subject para esa conexión. El token se renueva solo (caduca en ~1h).
>
> **El inbox va hasheado.** El user id viaja crudo en el subject, pero el inbox usa
> `_INBOX.<sha256(user-id) → base32 sin padding → 16 chars en minúscula>`. **Hay que fijarlo al
> conectar** (`inboxPrefix` en nats.js): por defecto la librería genera un `_INBOX.<aleatorio>` que
> ningún permiso acotado autoriza, y **las respuestas nunca llegan**.
>
> Las personas **no conectan al bus**: hablan HTTP con la api, y la api publica con su propio
> service user. Por eso el usuario final viaja en el cuerpo (`creator` / `author` / `editor`).
>
> #### 3.4 El formato de respuesta
>
> ```json
> { "status": "success", "data": { "id": 7 } }
> { "status": "failure", "errorCode": "project_not_found", "errorMessage": "Project not found" }
> ```
>
> El `status` **decide la transacción**: el despachador commitea si es `success` y hace rollback en
> cualquier otro caso (ADR-003). La api traduce `errorCode` a status HTTP con un mapa explícito.
>
> #### 3.5 Lo que este documento NO cambia
>
> - El envelope `Reply` y el catálogo de `errorCode`.
> - La gramática de subjects (solo cambian los **valores** del token `{svc}`).
> - El inbox hasheado y el flujo de token del service user.
> - La lógica de los 20 comandos, el registry y el despachador.
> - El nombre del **operador NATS** (`NATS_OPERATOR_NAME`, default `gestion`, en
>   `deploy/nats/bootstrap.sh`). Es el operador del árbol de cuentas, **no** el token `{svc}`.
>   **No se toca**: renombrarlo obliga a regenerar el árbol de creds.
>
> ### 4. Decisión
>
> **Dos servicios micro con nombre propio, en un solo deployable: la imagen de `core`.**
>
> **Comparten:** la imagen y el deployable (`core/`), el proceso, la conexión NATS, el service user
> y el rol `core` del auth-callout.
>
> **No comparten:**
>
> | | Escrituras | Lecturas |
> |---|---|---|
> | **Nombre en el bus** | `jiku-commands` | `jiku-queries` |
> | **Qué sirve** | Los 20 comandos de dominio | Consultas: `list` / `get` |
> | **Módulo** | `core/src/commands/` | `core/src/queries/` |
> | **Conexión a Postgres** | Usuario **dueño** de la base | Rol de **solo lectura** |
> | **Queue group** | `jiku-commands` | `jiku-queries` |
> | **Timeout del caller** | `NATS_REQUEST_TIMEOUT_MS` (5000) | `NATS_QUERY_TIMEOUT_MS` (10000) |
> | **Stats de micro** | Propias | Propias |
>
> Los nombres respetan la regla de ADR-32 de NATS: solo `A-Z a-z 0-9 - _`, y son tokens válidos de
> subject.
>
> #### 4.1 Un proceso, dos servicios micro
>
> **Micro no ata un servicio a un proceso.** `nc.services.add()` crea un servicio nuevo en cada
> llamada —sin singleton ni registro compartido— y le asigna su propio `id`, sus propios endpoints
> y sus propios contadores. Dos llamadas sobre la misma conexión dan dos servicios independientes
> que se anuncian por separado en `$SRV`. Verificado en `nats@2.29.3`
> (`lib/nats-base-client/nats.js:501-513`, `service.js:190`).
>
> Desde afuera se ven como dos servicios de verdad:
>
> ```
> $ nats micro ls
> jiku-commands   1.0.0   IcXY…
> jiku-queries    1.0.0   Kd7Q…
> ```
>
> **Lo que la separación en el bus sigue dando, aunque compartan proceso:**
>
> - Permisos distintos por caller: se puede dar `jiku-queries.v1.>` sin dar las escrituras.
> - Queue groups distintos, y por lo tanto balanceo independiente entre réplicas.
> - Stats y latencia por servicio y por endpoint, separadas.
> - **La opción de separarlos después sin tocar el contrato.** El día que las lecturas necesiten
>   escalar aparte, se levanta la misma imagen con un flag que registra solo uno de los dos
>   servicios. Ningún caller se entera: el subject no cambia.
>
> **Lo que sí se comparte, y hay que asumirlo:**
>
> - **El escalado.** Escalar lecturas escala también escrituras, y al revés.
> - **El proceso.** Un OOM o un crash se lleva los dos servicios. La mitigación real es el
>   presupuesto de bytes de las consultas, que es lo que evita que una respuesta grande infle la
>   memoria del proceso.
> - **El event loop.** Node es de un solo hilo: la espera de Postgres no lo bloquea, pero
>   serializar una página grande a JSON sí. El techo de `limit` (200) y el presupuesto de bytes
>   acotan cuánto.
>
> **Lo que NO se comparte, y es lo que más importa:** la conexión a la base. El proceso abre **dos**
> conexiones Sequelize con credenciales distintas —la del dueño para los comandos, la de solo
> lectura para las consultas—, así que la garantía de ADR-001 **la sigue imponiendo Postgres**:
> contra un rol estrictamente `SELECT`, un `Model.update()` desde una consulta falla en runtime
> aunque el código lo intente. Compartir proceso no afloja esa barrera.
>
> **Por qué `commands` y no `actions`:** "comando" ya es el vocabulario de todo el repo —
> `CommandRegistry`, `sendCommand`, `docs/apis/core.yaml` ("NATS command contract"), ADR-002. El
> nombre del servicio coincide con lo que sirve y no se introduce una segunda palabra para la misma
> cosa, que es el espíritu de ADR-004.
>
> ### 5. La gramática nueva
>
> ```
> {instance}.{user-id}.{svc}.{version}.{método}
>
> dev.<uid>.jiku-commands.v1.tasks.new          ← escritura
> dev.<uid>.jiku-commands.v1.tasks.88.edit      ← escritura
> dev.<uid>.jiku-queries.v1.tasks.list          ← lectura
> dev.<uid>.jiku-queries.v1.tasks.get           ← lectura
> ```
>
> Suscripciones:
>
> ```
> {instance}.*.jiku-commands.v1.>   queue group: jiku-commands
> {instance}.*.jiku-queries.v1.>    queue group: jiku-queries
> ```
>
> Reglas de forma que hay que respetar (documentación de NATS):
>
> - El subject **es routing, no datos**. Nada de filtros, correlation ids ni valores por-request
>   adentro: van en el payload o en headers.
> - De lo **general a lo específico** de izquierda a derecha, ≤16 tokens y ≤256 caracteres.
> - `lowercase-con-guiones`, consistente. Los subjects son **case-sensitive**.
> - `*` = un token, `>` = el resto y **solo al final**; ambos solo en suscripciones.
> - Prefijos reservados: `$` (interno del server, incluido `$SRV`) y `_INBOX.`.
>
> ### 6. Por qué la separación va en el token `{svc}`
>
> Es la decisión menos obvia del documento y la que evita un bug caro.
>
> La alternativa natural sería anidar las lecturas bajo el servicio actual:
> `…gestion.v1.query.projects.list`. **No hacerlo.** `core` se suscribe hoy a
> `{instance}.*.gestion.v1.>`, y ese `>` se come también las consultas. Entonces:
>
> - **Hoy**, con los dos servicios en el mismo proceso: la suscripción wildcard de los comandos y
>   la de las consultas se solapan. El mensaje se entrega a **las dos**, porque son queue groups
>   distintos, y salen **dos respuestas al mismo inbox**. Y ahí aplica el pitfall que la doc de
>   NATS marca explícito: *"A plain `request()` returns the first reply and discards the rest… the
>   second answer is lost silently"*. El síntoma sería respuestas correctas la mitad de las veces,
>   sin ningún error. Compartir proceso **no** evita esto: el solapamiento es del subject, no del
>   deployable.
> - **Mañana**, si las lecturas se separan a un proceso propio: el mismo problema, más difícil de
>   ver porque el tráfico se reparte entre dos deployments.
>
> No hay "deny" en suscripciones para arreglarlo: habría que enumerar recursos o migrar los
> comandos a `gestion.v1.command.>`, que es igual de breaking.
>
> Con `{svc}` distinto el problema no existe: `gestion.v1.>` **no matchea** `jiku-queries.v1.…`
> porque los tokens se comparan enteros. Además habilita lo que queremos:
>
> - **Permisos:** `publish: ["{inst}.{uid}.jiku-queries.v1.>"]` para un consumidor de solo lectura,
>   sin darle acceso a las escrituras. Alineado con ADR-008 (deny-by-default).
> - **Queue groups y stats separados** aunque compartan proceso, y la posibilidad de separar el
>   deployable después **sin cambiar el contrato**.
> - **Credenciales de base distintas**, que es exactamente lo que sostiene ADR-001: las consultas
>   usan la conexión de solo lectura, así que **no pueden escribir aunque el código lo intente**.
>
> ### 7. Qué aporta el framework micro
>
> Micro es parte del cliente `nats` que ya está instalado (`nats@2.29.3`, `nc.services`): **no hay
> dependencia nueva**. Formaliza un responder de request/reply en *"a named, versioned handler that
> the server can discover, that reports its own stats, and that load-balances across as many copies
> as you start"*.
>
> | Qué da | Detalle |
> |---|---|
> | **Discovery** | `$SRV.PING`, `$SRV.INFO`, `$SRV.STATS`; también `.<name>` y `.<name>.<id>`. El servicio responde a los tres niveles. Sin registry externo. |
> | **Stats por endpoint** | `num_requests`, `num_errors`, `processing_time`, `average_processing_time`, `last_error`, `queue_group`. |
> | **Queue group** | Default `q`; se puede fijar por servicio, grupo o endpoint. Nosotros lo fijamos por servicio. |
> | **Versión y metadata** | `version` en SemVer estricto; `metadata` como `Record<string,string>`, inmutable una vez seteada. |
> | **Herramientas** | `nats micro ls`, `nats micro info <name>`, `nats micro stats <name>`. |
>
> Lo que **no** da y hay que seguir haciendo a mano: nada de persistencia (*"A service stores
> nothing; it answers a request and retains no record of it"*), ni reintento, ni idempotencia.
>
> ### 8. Verificaciones hechas sobre `nats@2.29.3`
>
> Cuatro cosas que no están en la documentación y que condicionan el diseño. Todas verificadas en
> el código instalado en `node_modules/nats`:
>
> **1. Un grupo micro acepta `*` en el prefijo.** Era la duda razonable, porque nuestra gramática
> tiene el user id con wildcard **en el medio** del subject. Son dos validaciones distintas y
> ninguna prohíbe `*`:
>
> | Qué se valida | Función | Qué rechaza |
> |---|---|---|
> | Nombre del **grupo** | `validInternalToken` (`service.js:147-157`) | Espacios y cualquier token `>` |
> | **Subject** del endpoint | `validSubjectName` (`service.js:133-146`) | Vacío, espacios y `>` **interno** (o sea, permite `>` final) |
>
> ADR-32 de NATS tampoco prohíbe `*` (solo `>`). Entonces `addGroup('dev.*.jiku-commands.v1')` es
> válido y los endpoints cuelgan de ahí.
>
> **2. El nombre de un endpoint debe matchear `/^[-\w]+$/`** — letras, dígitos, `_` y `-`, **sin
> puntos** (`validateName` en `lib/jetstream/jsutil.js:67-82`). El subject con puntos va en
> `opts.subject`, que sí acepta `*`.
>
> **3. `respondError()` NO incrementa `num_errors`.** Setea los headers `Nats-Service-Error` y
> `Nats-Service-Error-Code` (`service.js:68-75`), pero el contador solo sube cuando el handler
> **lanza de forma sincrónica** (`service.js:261-270`). Con handlers `async`, una excepción adentro
> rechaza la promesa y ni siquiera entra a ese `catch`.
>
> **4. `nc.info.max_payload`** está disponible después de conectar (`core.d.ts:213`). Lo usa el
> servicio de consultas para presupuestar el tamaño de las páginas.
>
> ### 9. Los dos servicios
>
> #### 9.1 `jiku-commands` — endpoints
>
> Los 20 comandos del registry, uno a uno. El `{id}` del patrón se convierte en `*` en el subject
> del endpoint, y el nombre sale de sacar los segmentos variables y unir con guiones:
>
> ```
> pattern  tasks.{id}.edit
> subject  tasks.*.edit
> name     tasks-edit
> ```
>
> | # | Patrón del comando | Subject del endpoint | Nombre |
> |---|---|---|---|
> | 1 | `clients.new` | `clients.new` | `clients-new` |
> | 2 | `clients.{id}.edit` | `clients.*.edit` | `clients-edit` |
> | 3 | `projects.new` | `projects.new` | `projects-new` |
> | 4 | `projects.{id}.edit` | `projects.*.edit` | `projects-edit` |
> | 5 | `tasks.new` | `tasks.new` | `tasks-new` |
> | 6 | `tasks.{id}.edit` | `tasks.*.edit` | `tasks-edit` |
> | 7 | `tasks.{id}.comment` | `tasks.*.comment` | `tasks-comment` |
> | 8 | `requirements.new` | `requirements.new` | `requirements-new` |
> | 9 | `requirements.{id}.edit` | `requirements.*.edit` | `requirements-edit` |
> | 10 | `requirements.{id}.resolve` | `requirements.*.resolve` | `requirements-resolve` |
> | 11 | `requirements.{id}.comment` | `requirements.*.comment` | `requirements-comment` |
> | 12 | `requirements.{id}.subscriptors.new` | `requirements.*.subscriptors.new` | `requirements-subscriptors-new` |
> | 13 | `requirements.{id}.subscriptors.{userId}.delete` | `requirements.*.subscriptors.*.delete` | `requirements-subscriptors-delete` |
> | 14 | `attachments.{id}.delete` | `attachments.*.delete` | `attachments-delete` |
> | 15 | `files.request-upload` | `files.request-upload` | `files-request-upload` |
> | 16 | `files.{fileId}.request-download` | `files.*.request-download` | `files-request-download` |
> | 17 | `worked-times.new` | `worked-times.new` | `worked-times-new` |
> | 18 | `worked-times.{id}.delete` | `worked-times.*.delete` | `worked-times-delete` |
> | 19 | `unworked-times.new` | `unworked-times.new` | `unworked-times-new` |
> | 20 | `unworked-times.{id}.delete` | `unworked-times.*.delete` | `unworked-times-delete` |
>
> **Son 20, no 17.** ADR-002 y la cabecera de `docs/apis/core.yaml` dicen 17: quedaron atrás de los
> comandos que sumó REQ-001. La lista de arriba sale del registry real
> (`core/src/commands/index.ts`) y es la que manda; los dos documentos se corrigen en el mismo PR.
>
> **Regla dura: dos endpoints no pueden matchear el mismo subject.** Si dos wildcards se solapan,
> el mensaje se entrega a las dos suscripciones y salen **dos respuestas**, con el mismo síntoma
> silencioso de §6. Los 20 de arriba no se solapan (verificado: los que comparten cantidad de
> tokens difieren en el primero o el último), pero **hay que dejar la verificación en el arranque**.
>
> #### 9.2 `jiku-queries` — endpoints
>
> La forma; el contenido se define aparte.
>
> | Subject del endpoint | Nombre | Qué devuelve |
> |---|---|---|
> | `projects.list` | `projects-list` | Colección paginada |
> | `projects.get` | `projects-get` | Un recurso |
> | `tasks.list` | `tasks-list` | Colección paginada |
> | `tasks.get` | `tasks-get` | Un recurso |
> | `comments.list` | `comments-list` | Colección paginada |
> | `comments.get` | `comments-get` | Un recurso |
>
> **Sin `*` en los subjects de consulta**: el id del recurso va en el payload, no en el subject. El
> motivo es de cardinalidad — el server matchea con un trie más un cache de subjects **de 1024
> entradas**, y el tráfico de lectura es el de mayor volumen; un subject nuevo por cada id
> consultado lo vuelve inútil.
>
> #### 9.3 Queue groups
>
> Cada servicio fija el suyo a nivel de servicio (`ServiceConfig.queue`), y lo heredan todos sus
> endpoints. **No usar el default `q`**: dos servicios distintos con el mismo queue group en
> subjects distintos no colisionan, pero el nombre explícito es lo que se ve en `nats micro info` y
> en `queue_group` de las stats.
>
> Aunque los dos servicios vivan en el mismo proceso, **los queue groups siguen siendo dos**: con
> tres réplicas de `core` arriba, un comando lo atiende una sola de las tres y una consulta también,
> pero **la elección es independiente**. No hay ninguna coordinación entre los dos grupos.
>
> ### 10. Cambios por componente
>
> #### 10.1 `packages/nats-protocol` — el contrato en código
>
> Es la única definición de subjects, compartida por todos. **Nadie arma un subject a mano.**
>
> ```ts
> // packages/nats-protocol/src/index.ts
>
> /** Despliegue: dev / prod. */
> export const INSTANCE = process.env.NATS_INSTANCE || 'dev';
> /** Versión del protocolo. Cambia solo en un breaking change del contrato. */
> export const PROTOCOL_VERSION = process.env.NATS_PROTOCOL_VERSION || 'v1';
>
> /**
>  * Los dos servicios del bus.
>  *
>  * Son tokens del subject Y nombres de servicio micro, así que valen las dos reglas:
>  * ADR-32 de NATS (solo A-Z a-z 0-9 - _) y token de subject sin puntos ni wildcards.
>  */
> export const COMMAND_SERVICE = process.env.NATS_COMMAND_SERVICE || 'jiku-commands';
> export const QUERY_SERVICE = process.env.NATS_QUERY_SERVICE || 'jiku-queries';
>
> /** Subject de un comando saliente. `userId` es el `sub` de quien publica. */
> export function commandSubject(command: string, userId: string): string {
>   return `${INSTANCE}.${userId}.${COMMAND_SERVICE}.${PROTOCOL_VERSION}.${command}`;
> }
>
> /** Subject de una consulta saliente. Misma gramática, otro servicio. */
> export function querySubject(query: string, userId: string): string {
>   return `${INSTANCE}.${userId}.${QUERY_SERVICE}.${PROTOCOL_VERSION}.${query}`;
> }
>
> /**
>  * Prefijo del grupo micro: `{instance}.*.{svc}.{version}`.
>  *
>  * El `*` cubre el user id de cualquier caller. Verificado que micro lo acepta:
>  * la validación de grupo solo rechaza vacío, espacios y `>` interno.
>  */
> export function groupSubject(service: string): string {
>   return `${INSTANCE}.*.${service}.${PROTOCOL_VERSION}`;
> }
>
> /**
>  * El método pedido, leído del subject completo.
>  * `dev.<uid>.jiku-commands.v1.clients.7.edit` -> `clients.7.edit`
>  */
> export function methodFromSubject(subject: string): string {
>   return subject.split('.').slice(4).join('.');
> }
>
> /** Alias histórico. Se mantiene para no tocar el despachador. */
> export const commandFromSubject = methodFromSubject;
>
> /** Quién publicó, leído del subject: el user id de Zitadel del caller. */
> export function callerFromSubject(subject: string): string {
>   return subject.split('.')[1] || '';
> }
>
> /** Nombre del endpoint micro a partir del patrón: `tasks.{id}.edit` -> `tasks-edit`. */
> export function endpointName(pattern: string): string {
>   return pattern
>     .split('.')
>     .filter((segment) => !segment.startsWith('{'))
>     .join('-');
> }
>
> /** Subject del endpoint micro: `tasks.{id}.edit` -> `tasks.*.edit`. */
> export function endpointSubject(pattern: string): string {
>   return pattern.replace(/\{[^}]+\}/g, '*');
> }
> ```
>
> **Se elimina** `SERVICE_NAME` y `subscriptionSubject()`. `inboxPrefix()`, `hashUserId()`,
> `Reply`, `success()`, `failure()` y `ErrorCode` **quedan igual**.
>
> Si algún consumidor externo importa `SERVICE_NAME`, exportarlo como alias de `COMMAND_SERVICE`
> marcado `@deprecated` en vez de romper el build.
>
> #### 10.2 `core` — un proceso, dos servicios
>
> Se reemplaza `core/src/bus/consumer.ts` por un **host** que abre la conexión una sola vez y
> registra los dos servicios micro contra ella. **El despachador de comandos, el registry y los 20
> comandos no se tocan**: `dispatcher.dispatch(subject, payload)` sigue recibiendo el subject
> completo y resolviendo el comando con `methodFromSubject`.
>
> ```
> core/src/
> ├── index.ts              # arranque: BusHost.start() / stop()
> ├── bus/
> │   ├── host.ts           # NUEVO — la conexión y el registro de los dos servicios
> │   ├── service.ts        # NUEVO — registra UN servicio micro a partir de un spec
> │   └── dispatcher.ts     # el de comandos, con transacción — SIN CAMBIOS
> ├── commands/             # SIN CAMBIOS: registry + los 20 comandos
> ├── queries/              # NUEVO
> │   ├── index.ts          # registry de consultas
> │   ├── registry.ts
> │   ├── dispatcher.ts     # sin transacción: las consultas no escriben
> │   ├── projects/
> │   ├── tasks/
> │   └── comments/
> └── models/
>     ├── index.ts          # conexión del DUEÑO de la base — SIN CAMBIOS
>     └── read.ts           # NUEVO — conexión de SOLO LECTURA
> ```
>
> **Un spec por servicio.** Lo único que cambia entre los dos es el nombre, los subjects y quién
> resuelve la request:
>
> ```ts
> // core/src/bus/service.ts
> import { NatsConnection, Service, ServiceMsg } from 'nats';
> import {
>   ErrorCode, INSTANCE, PROTOCOL_VERSION, Reply,
>   endpointName, endpointSubject, failure, groupSubject,
> } from '@jiku/nats-protocol';
> import logger from '../logger';
>
> const SERVICE_VERSION = process.env.SERVICE_VERSION || '1.0.0';
> const encode = (reply: Reply) => new TextEncoder().encode(JSON.stringify(reply));
>
> export interface ServiceSpec {
>   /** Nombre en el bus y token `{svc}` del subject. */
>   name: string;
>   description: string;
>   /** Patrones de método: `tasks.{id}.edit`, `tasks.list`, … */
>   patterns: string[];
>   /** Resuelve la request. Nunca lanza: siempre devuelve un `Reply`. */
>   handle: (subject: string, payload: unknown) => Promise<Reply>;
> }
>
> /**
>  * Registra un servicio micro sobre una conexión existente.
>  *
>  * Micro no ata un servicio a un proceso: `nc.services.add()` crea uno nuevo en cada
>  * llamada, con su propio id, sus endpoints y sus contadores. Dos llamadas sobre la misma
>  * conexión dan dos servicios que se anuncian por separado en `$SRV`.
>  */
> export async function registerService(nc: NatsConnection, spec: ServiceSpec): Promise<Service> {
>   const service = await nc.services.add({
>     name: spec.name,
>     version: SERVICE_VERSION,
>     description: spec.description,
>     // Queue group propio: el balanceo entre réplicas es independiente del otro servicio.
>     queue: spec.name,
>     metadata: { instance: INSTANCE, protocol: PROTOCOL_VERSION },
>   });
>
>   // El `*` del grupo cubre el user id de cualquier caller.
>   const group = service.addGroup(groupSubject(spec.name));
>
>   const subjects = new Set<string>();
>   for (const pattern of spec.patterns) {
>     const subject = endpointSubject(pattern);
>     // Dos endpoints que matcheen el mismo subject producen DOS respuestas al mismo inbox,
>     // y el caller descarta una en silencio. Se falla al arrancar, no en runtime.
>     if (subjects.has(subject)) {
>       throw new Error(`[bus] ${spec.name}: subject de endpoint duplicado: ${subject}`);
>     }
>     subjects.add(subject);
>
>     group.addEndpoint(endpointName(pattern), {
>       subject,
>       handler: (err, msg) => {
>         if (err) {
>           logger.error(`[bus] ${spec.name} ${subject}: ${err.message}`);
>           return;
>         }
>         void handle(spec, msg);
>       },
>     });
>   }
>
>   logger.info(`[bus] ${spec.name} v${SERVICE_VERSION}: ${subjects.size} endpoints`);
>   return service;
> }
>
> /**
>  * Nunca lanza. Del otro lado hay una request esperando: quedarse sin contestar deja al
>  * caller esperando hasta su timeout, que es el peor de los desenlaces.
>  */
> async function handle(spec: ServiceSpec, msg: ServiceMsg): Promise<void> {
>   let payload: unknown;
>   try {
>     payload = msg.data.length ? msg.json() : {};
>   } catch {
>     logger.warn(`[bus] payload inválido en ${msg.subject}`);
>     return respond(msg, failure(ErrorCode.INVALID_FIELDS, 'Malformed JSON payload'));
>   }
>
>   try {
>     respond(msg, await spec.handle(msg.subject, payload));
>   } catch (error: any) {
>     logger.error(`[bus] ${msg.subject}: ${error.message}`);
>     respond(msg, failure(ErrorCode.INTERNAL_ERROR, 'Internal error'));
>   }
> }
>
> /**
>  * El envelope SIEMPRE viaja en el cuerpo, también en los errores: es el contrato
>  * (ADR-002) y la api lo parsea siempre.
>  *
>  * En un `failure` se agregan además los headers de micro. No cambian el contrato: son
>  * para las herramientas (`nats micro stats`) y para cualquier cliente que quiera
>  * distinguir error de éxito sin parsear el cuerpo.
>  */
> function respond(msg: ServiceMsg, reply: Reply): void {
>   if (reply.status === 'success') {
>     msg.respond(encode(reply));
>     return;
>   }
>   msg.respondError(500, reply.errorCode ?? 'error', encode(reply));
> }
> ```
>
> **El host: una conexión, dos servicios.**
>
> ```ts
> // core/src/bus/host.ts
> import { NatsConnection, Service, connect, credsAuthenticator, tokenAuthenticator } from 'nats';
> import { readFileSync } from 'fs';
> import { serviceUserFromEnv } from '@jiku/zitadel-auth';
> import { COMMAND_SERVICE, QUERY_SERVICE, inboxPrefix } from '@jiku/nats-protocol';
> import logger from '../logger';
> import { registerService } from './service';
> import { Dispatcher } from './dispatcher';
> import commandRegistry from '../commands';
> import { QueryDispatcher } from '../queries/dispatcher';
> import queryRegistry from '../queries';
>
> export class BusHost {
>   private connection: NatsConnection | null = null;
>   private services: Service[] = [];
>   private stopTokenRefresh: (() => void) | null = null;
>
>   constructor(
>     private commands: Dispatcher,
>     private queries: QueryDispatcher
>   ) {}
>
>   async start(): Promise<void> {
>     const servers = process.env.NATS_URL || 'nats://localhost:4222';
>     const credsPath = process.env.NATS_CREDS;
>     let userId = process.env.NATS_USER_ID || COMMAND_SERVICE;
>
>     // Las creds del sentinel no conceden permisos por sí solas: es el token de Zitadel el
>     // que dispara el auth-callout, que lee el rol y mintea los permisos de subject.
>     const serviceUser = serviceUserFromEnv();
>     if (serviceUser) {
>       userId = serviceUser.userId;
>       await serviceUser.token();
>       this.stopTokenRefresh = serviceUser.startAutoRefresh((error) => {
>         logger.error(`[bus] no se pudo renovar el token de Zitadel: ${error.message}`);
>       });
>     }
>
>     const authenticators = [
>       ...(credsPath ? [credsAuthenticator(readFileSync(credsPath))] : []),
>       ...(serviceUser ? [tokenAuthenticator(() => serviceUser.currentToken())] : []),
>     ];
>
>     // UNA conexión para los dos servicios: comparten identidad, token e inbox.
>     this.connection = await connect({
>       servers,
>       // Sin este prefijo la librería genera un _INBOX aleatorio que ningún permiso
>       // autoriza, y las respuestas de los servicios que core llame no llegarían.
>       inboxPrefix: inboxPrefix(userId),
>       ...(authenticators.length ? { authenticator: authenticators } : {}),
>       name: 'jiku-core',
>     });
>
>     this.services = [
>       await registerService(this.connection, {
>         name: COMMAND_SERVICE,
>         description: 'Comandos de dominio de Jiku: la única vía de escritura a la base',
>         patterns: commandRegistry.patterns(),
>         handle: (subject, payload) => this.commands.dispatch(subject, payload),
>       }),
>       await registerService(this.connection, {
>         name: QUERY_SERVICE,
>         description: 'Consultas de lectura de Jiku: proyectos, tareas y comentarios',
>         patterns: queryRegistry.patterns(),
>         handle: (subject, payload) => this.queries.dispatch(subject, payload),
>       }),
>     ];
>
>     void (async () => {
>       for await (const status of this.connection!.status()) {
>         logger.info(`[bus] ${status.type}: ${JSON.stringify(status.data ?? '')}`);
>       }
>     })();
>   }
>
>   /** Drena para que los mensajes en vuelo terminen antes de cerrar. */
>   async stop(): Promise<void> {
>     this.stopTokenRefresh?.();
>     this.stopTokenRefresh = null;
>     // Los dos servicios primero: dejan de aceptar requests nuevas.
>     await Promise.all(this.services.map((service) => service.stop()));
>     this.services = [];
>     if (this.connection) {
>       await this.connection.drain();
>       await this.connection.close();
>     }
>     logger.info('[bus] desconectado');
>   }
> }
> ```
>
> **Un flag para separarlos el día que haga falta.** Si en el futuro las lecturas necesitan escalar
> aparte, alcanza con que `BusHost` lea un `BUS_SERVICES=commands,queries` y registre solo los que
> le pidan. La misma imagen se despliega dos veces con valores distintos, y **ningún caller se
> entera**: el subject no cambia. Es la razón por la que la separación vive en el token `{svc}`
> desde el día uno.
>
> `CommandRegistry` necesita un método nuevo, de dos líneas:
>
> ```ts
> // core/src/commands/registry.ts
> /** Los patrones registrados. Lo usa el servicio para armar los endpoints micro. */
> patterns(): string[] {
>   return this.entries.map((entry) => entry.command.pattern);
> }
> ```
>
> #### 10.3 `core/src/queries/` y la conexión de solo lectura
>
> El módulo de consultas es hermano de `commands/` y tiene la misma forma: un registry de patrones,
> un despachador que resuelve el patrón y una carpeta por recurso. Dos diferencias, y las dos
> importan.
>
> **1. No hay transacción por request.** El despachador de comandos abre una transacción y decide
> commit o rollback según el `status` (ADR-003); el de consultas no abre nada. Si una consulta
> necesita consistencia entre varias lecturas, usa una transacción `READ ONLY` explícita **dentro**
> de la consulta.
>
> **2. Usa una conexión propia, con el rol de solo lectura.** Es lo que preserva la garantía de
> ADR-001 dentro de un proceso compartido: contra un rol estrictamente `SELECT`, una escritura falla
> en runtime aunque el código la intente.
>
> ```ts
> // core/src/models/read.ts
> import { Sequelize } from 'sequelize-typescript';
>
> /**
>  * Conexión de SOLO LECTURA del servicio de consultas.
>  *
>  * SIN `models` A PROPÓSITO — registrar `allModels` acá reasignaría las clases del ORM a
>  * esta conexión y los comandos escribirían por el rol equivocado.
>  * Las consultas usan SQL explícito con `readDb.query(...)`.
>  */
> export const readDb = new Sequelize({
>   database: process.env.POSTGRESQL_DB,
>   username: process.env.POSTGRESQL_READ_USER,
>   password: process.env.POSTGRESQL_READ_PASSWORD,
>   port: Number(process.env.POSTGRESQL_PORT) || 5432,
>   host: process.env.POSTGRESQL_HOST,
>   dialect: 'postgres',
>   logging: false,
>   pool: { max: Number(process.env.POSTGRESQL_READ_POOL_MAX) || 10 },
>   dialectOptions: {
>     // Estrictamente por debajo del timeout de la request: así una consulta lenta
>     // vuelve como `query_timeout` en vez de dejar al caller esperando sin saber por qué.
>     statement_timeout: Number(process.env.POSTGRESQL_STATEMENT_TIMEOUT_MS) || 8000,
>   },
> });
> ```
>
> ⚠️ **Dos instancias de Sequelize NO pueden compartir las clases de `@jiku/models`.** Hoy `api` y
> `core` hacen `new Sequelize({ models: allModels })` cada uno, y funciona porque son **procesos
> distintos**. En un solo proceso, la segunda instancia que registre `allModels` **reasigna** esas
> clases: `Objective.findAll()` pasaría a salir por la conexión equivocada. Y el sentido del error
> es el peligroso — los comandos escribiendo por el rol de solo lectura sería un fallo ruidoso, pero
> las consultas corriendo con el usuario dueño rompen ADR-001 **en silencio**.
>
> Por eso `read.ts` se crea **sin `models`** y las consultas no usan el ORM.
>
> **Las consultas se escriben en SQL explícito**, y no es solo por esa restricción: es lo que
> conviene igual para este servicio.
>
> - Los filtros dinámicos, el `ORDER BY` variable y sobre todo el keyset
>   (`WHERE (created_at, id) < ($1, $2)`) se expresan directo en SQL; a través del ORM son un armado
>   indirecto y frágil.
> - `fields` es literalmente la lista del `SELECT`. Con el ORM habría que traer la fila entera y
>   descartar campos después, justo lo que el presupuesto de bytes quiere evitar.
> - Instanciar 200 modelos por página para serializarlos a JSON acto seguido es trabajo puro de más.
>
> **La regla de seguridad que lo acompaña:** los **nombres** de tabla, columna y dirección de orden
> salen **siempre** de las listas blancas declaradas por cada recurso, nunca de la entrada del
> usuario; los **valores** van siempre como parámetros (`replacements` / `$1`), nunca interpolados.
> Con las dos cosas, el SQL explícito no agrega superficie de inyección.
>
> ```ts
> // core/src/queries/tasks/tasks-list.ts (forma)
> const rows = await readDb.query<TaskRow>(sql, {
>   type: QueryTypes.SELECT,
>   replacements: { projectId, limit: limit + 1, cursorCreatedAt, cursorId },
> });
> ```
>
> La traducción contrato ↔ base (`task` → `objectives`, `priority` enum ↔ entero, `body` →
> `new_value`) vive **dentro** del módulo de consultas, igual que en los comandos (ADR-004).
>
> #### 10.4 `api` — el cliente
>
> La api mantiene **una sola conexión** y suma un método. El inbox, el service user y el token no
> cambian.
>
> ```ts
> // api/lib/utils/bus/index.ts
> const REQUEST_TIMEOUT_MS = Number(process.env.NATS_REQUEST_TIMEOUT_MS) || 5000;
> const QUERY_TIMEOUT_MS = Number(process.env.NATS_QUERY_TIMEOUT_MS) || 10000;
>
> export interface Bus {
>   request<T = any>(command: string, payload: unknown): Promise<Reply<T>>;
>   query<T = any>(query: string, payload: unknown): Promise<Reply<T>>;
> }
>
> async request<T>(command: string, payload: unknown): Promise<Reply<T>> {
>   return this.roundtrip<T>(commandSubject(command, this.userId), payload, REQUEST_TIMEOUT_MS);
> }
>
> async query<T>(query: string, payload: unknown): Promise<Reply<T>> {
>   return this.roundtrip<T>(querySubject(query, this.userId), payload, QUERY_TIMEOUT_MS);
> }
> ```
>
> **Distinguir "no hay nadie" de "tardó demasiado".** Hoy los dos casos caen en el mismo `catch` de
> `send-command.ts` y salen 503. Cuando no hay ningún suscriptor, el server contesta **al instante**
> con un status `503` —*"within milliseconds, not after the full timeout. This distinguishes
> deployment problems from performance issues"*—, mientras que un timeout es una respuesta que no
> llegó a tiempo. Vale separarlos:
>
> ```ts
> catch (error: any) {
>   const noResponders = error?.code === ErrorCode.NoResponders || error?.code === '503';
>   res.status(noResponders ? 503 : 504).json({
>     code: noResponders ? 'service_unavailable' : 'gateway_timeout',
>     message: noResponders
>       ? 'El servicio no está disponible en este momento'
>       : 'La operación tardó demasiado',
>   });
> }
> ```
>
> #### 10.5 `deploy/nats/auth-callout` — permisos
>
> Cuatro archivos. El callout evalúa las reglas **en orden** y gana la primera que coincida con
> algún rol del token; **sin coincidencia la conexión se rechaza**.
>
> Como los dos servicios comparten proceso, **comparten también el service user y el rol**: no hace
> falta ningún rol nuevo en Zitadel. Lo único que cambia es que la plantilla de `core` ahora tiene
> que autorizar **dos** prefijos de suscripción.
>
> **`rules.yaml`** — solo cambia el `service` de las reglas existentes:
>
> ```yaml
>   # Publicador externo: enumera sus comandos, por eso va arriba de internal-app.
>   - match: external-publisher
>     type: service
>     service: external-publisher
>     template: templates/external-publisher.yaml
>
>   # La api. Único emisor de comandos, y ahora también de consultas.
>   - match: internal-app
>     type: service
>     service: api
>     template: templates/api.yaml
>
>   # Core: atiende los DOS endpoints, `jiku-commands` y `jiku-queries`, desde el mismo
>   # proceso. `service` nombra uno solo, así que la plantilla enumera los dos prefijos.
>   - match: core
>     type: service
>     service: jiku-commands
>     template: templates/core.yaml
>
>   # Diagnóstico local. Ve los dos servicios, por eso su `service` ya no alcanza:
>   # la plantilla enumera los dos prefijos.
>   - match: bus-observer
>     type: service
>     service: jiku-commands
>     template: templates/observer.yaml
> ```
>
> **`templates/api.yaml`** — dos líneas de publicación:
>
> ```yaml
> pub:
>   allow:
>     - "{{instance}}.{{user_id}}.jiku-commands.v1.>"
>     - "{{instance}}.{{user_id}}.jiku-queries.v1.>"
> sub:
>   allow:
>     - "_INBOX.{{user_id_hash}}.>"
> response:
>   max: 1
>   ttl: 45s
> ```
>
> **`templates/core.yaml`** — el cambio central: **dos** prefijos de suscripción, porque el proceso
> atiende los dos endpoints con una sola conexión.
>
> ```yaml
> # SERVICE USER de core.
> #
> # Un solo proceso, DOS servicios micro:
> #   jiku-commands  las escrituras
> #   jiku-queries   las lecturas
> # `{{service}}` nombra uno solo, así que los dos prefijos van enumerados.
> pub:
>   allow:
>     # Requests salientes bajo su propia identidad. Hoy core no llama a nadie;
>     # queda declarado porque es la forma del permiso en un despliegue real.
>     - "{{instance}}.{{user_id}}.>"
>
> sub:
>   allow:
>     # Los comandos dirigidos a su endpoint, de cualquier caller.
>     - "{{instance}}.*.jiku-commands.v1.>"
>     # Las consultas, ídem.
>     - "{{instance}}.*.jiku-queries.v1.>"
>     # Discovery de micro. Sin esto los servicios levantan pero son invisibles.
>     - "$SRV.>"
>     # Inbox propio, bajo el hash de su user id. Es POR RÉPLICA, no por endpoint.
>     - "_INBOX.{{user_id_hash}}.>"
>
> response:
>   # allow_responses: contesta al inbox del caller sin permiso de pub explícito.
>   max: 1
>   ttl: 45s
> ```
>
> **`$SRV.>` es obligatorio.** Micro se suscribe a los subjects de control al arrancar; sin ese
> permiso los servicios levantan pero son invisibles para `nats micro ls`.
>
> Si algún día las lecturas se separan a un deployable propio, este es el único archivo que cambia
> además del compose: se parte en dos plantillas, cada una con su prefijo, y se suma una regla con
> un rol nuevo. El contrato del bus no se toca.
>
> **`templates/external-publisher.yaml`** — reemplazar `gestion` por `jiku-commands` en las 8 líneas
> de `pub.allow`. La lista enumerada **no se abre a `>`**: es la plantilla más restrictiva a
> propósito. Las 8 líneas son:
>
> ```
> {{instance}}.{{user_id}}.jiku-commands.v1.files.request-upload
> {{instance}}.{{user_id}}.jiku-commands.v1.files.*.request-download
> {{instance}}.{{user_id}}.jiku-commands.v1.requirements.new
> {{instance}}.{{user_id}}.jiku-commands.v1.requirements.*.edit
> {{instance}}.{{user_id}}.jiku-commands.v1.requirements.*.comment
> {{instance}}.{{user_id}}.jiku-commands.v1.tasks.new
> {{instance}}.{{user_id}}.jiku-commands.v1.tasks.*.edit
> {{instance}}.{{user_id}}.jiku-commands.v1.tasks.*.comment
> {{instance}}.{{user_id}}.jiku-commands.v1.attachments.*.delete
> ```
>
> **`templates/observer.yaml`** — enumerar los dos prefijos, ya que `{{service}}` es un solo valor:
>
> ```yaml
> sub:
>   allow:
>     - "{{instance}}.*.jiku-commands.>"
>     - "{{instance}}.*.jiku-queries.>"
>     - "$SRV.>"
>     - "_INBOX.>"
> ```
>
> **En Zitadel no hay nada que hacer:** los dos servicios usan el service user y el rol `core` que
> ya existen.

> ### 11. Errores y estadísticas
>
> **El envelope siempre viaja en el cuerpo, también en los errores.** Es el contrato de ADR-002 y la
> api lo parsea siempre. Los headers de micro se agregan **además**, nunca en lugar del cuerpo.
>
> Consecuencia de la verificación §8.3, que hay que asumir de forma consciente:
>
> - `respondError()` no incrementa `num_errors`. El contador solo sube si el handler **lanza
>   sincrónicamente**, y ahí micro responde `Empty` con headers — **perdiendo el cuerpo**, o sea el
>   envelope. Por eso la regla es **nunca dejar que el handler lance**.
> - Resultado: **`num_errors` queda en 0** en `nats micro stats`. No es una pérdida grave — un
>   `project_not_found` es una respuesta correcta del servicio, no una falla suya — pero hay que
>   saberlo antes de armar una alerta sobre esa métrica.
> - Las fallas se miden con los logs y las métricas propias del servicio: contar por `errorCode` al
>   responder.
>
> ### 13. Observabilidad y operación
>
> ```bash
> nats micro ls                       # qué servicios hay y en qué versión
> nats micro info jiku-queries        # endpoints, subjects, queue groups, metadata
> nats micro stats jiku-commands      # requests, latencia media, último error, por endpoint
> nats micro ping                     # instancias vivas, con su id
> ```
>
> - **Healthcheck de deploy:** un `$SRV.PING.<name>` con timeout corto es mejor readiness probe que
>   un puerto abierto — comprueba que el servicio está **conectado al bus y atendiendo**.
> - **Una instancia por réplica:** cada réplica se anuncia con su propio `id`, así que
>   `nats micro ping` sirve para ver cuántas hay arriba y si alguna quedó vieja tras un deploy.
> - **El observer no va a producción.** Su plantilla escucha todo el protocolo, incluidos los datos
>   de negocio de cada comando.
>
> ### 14. Reglas de implementación
>
> - Todo subject **DEBE** salir de `@jiku/nats-protocol` (`commandSubject`, `querySubject`,
>   `groupSubject`, `endpointSubject`). **NO SE DEBE** concatenar un subject a mano.
> - El cliente **DEBE** fijar `inboxPrefix` con el hash del user id propio al conectar. Sin eso las
>   respuestas no llegan.
> - El `userId` con el que se publica **DEBE** salir de la key del service user, **NO** de una
>   variable de entorno: tiene que coincidir con el `sub` que el callout lee del token.
> - Un handler de endpoint **NUNCA DEBE** lanzar: siempre responde un `Reply`. Del otro lado hay una
>   request esperando.
> - Toda respuesta **DEBE** tener el formato `{ status: 'success', data }` o
>   `{ status: 'failure', errorCode, errorMessage }`, en el **cuerpo**. Los headers de micro son un
>   agregado, no un reemplazo.
> - Dos endpoints **NO DEBEN** poder matchear el mismo subject. La verificación **DEBE** correr al
>   arrancar y hacer fallar el arranque.
> - Las consultas **DEBEN** usar la conexión de solo lectura (`core/src/models/read.ts`).
>   **NO SE DEBE** agregarles escrituras: para eso está `jiku-commands`.
> - La conexión de lectura **NO DEBE** registrar los modelos de `@jiku/models`. Registrar
>   `allModels` en dos instancias de Sequelize dentro del mismo proceso **reasigna** las clases del
>   ORM y rompe ADR-001 en silencio. Las consultas usan SQL explícito.
> - En el SQL de una consulta, los **nombres** de tabla, columna y dirección de orden **DEBEN**
>   salir de las listas blancas del recurso; los **valores** **DEBEN** ir como parámetros.
>   **NO SE DEBE** interpolar entrada del usuario en el SQL.
> - Los dos servicios **DEBEN** registrarse en el arranque del proceso, y `stop()` **DEBE** parar
>   los dos antes de drenar la conexión.
> - Un servicio **NO DEBE** publicar mensajes que no sean la respuesta a una request que recibió,
>   salvo que se le agregue el permiso de `pub` explícito y acotado.
> - El `version` del servicio micro **DEBE** ser SemVer estricto: micro valida con la regex oficial
>   de semver.org y rechaza cualquier otra cosa.
> - **NO SE DEBEN** transportar datos estructurados dentro de `errorMessage`.
>
> ### 16. Riesgos
>
> | Riesgo | Mitigación |
> |---|---|
> | **Endpoints con subjects solapados** | Verificación al arrancar. Es un bug silencioso si se escapa |
> | **Se olvida `$SRV.>` en una plantilla** | El servicio levanta pero es invisible para `nats micro ls` |
> | **`num_errors` siempre en 0** | Documentado. No armar alertas sobre esa métrica |
> | **Escalado acoplado**: escalar lecturas escala también escrituras | Asumido. Cuando deje de alcanzar, se separa el deployable con un flag, **sin tocar el contrato** |
> | **Una consulta pesada degrada las escrituras del mismo proceso** | El techo de `limit` (200) y el presupuesto de bytes acotan el trabajo por request; el pool de lectura es propio y no le come conexiones al de escritura |
> | **Los modelos del ORM reasignados a la conexión de lectura** | La conexión de lectura se crea **sin `models`**. Es el riesgo más silencioso del diseño co-locado |

## Contexto del Producto

**Feature groups relacionados:**
- **Feature Group 3: Durabilidad y Observabilidad de la Escritura** — Relación parcial y
  complementaria. FG-3 plantea dos mitades: (a) la garantía de durabilidad de la escritura
  (JetStream, reintento, idempotencia) y (b) la observabilidad (healthchecks, logs, métricas de
  latencia y de comandos fallidos). Este requerimiento **no toca la mitad (a)** —mantiene
  request/reply puro sin JetStream, explícitamente— y **cubre parte de la mitad (b)**: aporta
  discovery (`$SRV.PING/INFO/STATS`), latencia y conteo de requests por endpoint, y una base de
  readiness probe (`$SRV.PING.<name>`). Lo que **no** aporta de FG-3: métrica confiable de comandos
  fallidos, porque `num_errors` de micro queda en 0 por diseño de la librería (ver §11 del
  requerimiento original).
- **Feature Group 6: Saneamiento del Modelo de Datos** — Sin solapamiento. Este requerimiento no
  toca esquema ni entidades.

**Stories relacionadas:**
- **S-010: Dar de baja la integración con sistemas externos (Jira)** — Sin conflicto. S-010 eliminó
  las tablas `external_*` y sus columnas; el rol `external-publisher` del auth-callout es otra cosa
  (un servicio externo que sube archivos por el bus con permiso acotado a 9 subjects) y **sigue
  vigente**: su plantilla se actualiza al nombre nuevo, no se elimina.
- **S-001 a S-008 (REQ-001, rediseño de archivos y adjuntos)** — Aportaron los 3 comandos que
  llevan el registry de 17 a 20 (`files.request-upload`, `files.{fileId}.request-download`,
  `attachments.{id}.delete`, sumados a los ya existentes). Es la causa de que ADR-002 y
  `docs/apis/core.yaml` digan 17 y haya que corregirlos.
- **S-009: Eliminar el endpoint público de adjuntos (REQ-002)** — Sin solapamiento técnico.

**Servicios involucrados:**
- **`core`** (worker): impacto alto. Reemplaza el consumer del bus por un host con dos servicios
  micro, gana el módulo `queries/` y una segunda conexión Sequelize de solo lectura.
- **`api`**: impacto medio. Publica en el subject nuevo, suma el método `query()` al cliente del bus
  y separa 503 de 504.
- **`packages/nats-protocol`**: impacto alto. Es la definición del contrato de subjects: cambia su
  superficie pública.
- **`deploy/`**: impacto medio. Cuatro archivos del auth-callout, tres compose y `bus-inspect.sh`.
- **`web` / `opus-web`**: sin cambios. Las personas no conectan al bus y los frontends muestran el
  mensaje que viene en el cuerpo del error.

**Flujos del sistema relacionados:** todos los flujos que escriben pasan por el bus y por lo tanto
por el subject que se renombra — `alta-requisito-desde-portal`, `asignacion-semanal`,
`carga-de-horas`, `subida-de-archivos`, `vinculacion-de-archivos`, `lectura-de-archivos`,
`adjuntos`. Ninguno cambia su comportamiento observable: cambia el token `{svc}` del subject, no la
semántica del comando.

## Clarificaciones

### Alcance

- **P:** El documento declara no-objetivo el contrato de consultas (filtros, paginación, payloads)
  y lo deja en un documento hermano, pero sí define la infraestructura de `jiku-queries`: registro
  del servicio, 6 endpoints, módulo `core/src/queries/`, conexión de solo lectura y permisos.
  ¿Qué entrega este requerimiento?
- **R:** Todo el documento tal cual: rename a `jiku-commands` + framework micro + `jiku-queries`
  levantado y descubrible con sus 6 endpoints registrados, **pero sin el contrato de qué contesta
  cada uno**. El contenido de las consultas queda para un requerimiento posterior.

- **P:** El plan de migración del documento (paso 0 a paso 5: credenciales, callout permisivo, corte
  coordinado de api y core, verificación, cierre del permiso viejo, release de `jiku-queries`),
  junto con la ventana de indisponibilidad de escrituras y el rollback, ¿entra en el alcance?
- **R:** **No.** El plan de corte queda fuera: este requerimiento implementa **solo lo nuevo**. Sí
  entra la **configuración final** del auth-callout (los nombres nuevos, los dos prefijos de
  suscripción, `$SRV.>`), porque es parte del estado final del sistema y no del procedimiento de
  migración.

- **P:** El paso 2 de la migración reinicia api y core juntos y toda escritura del producto falla
  con 503 durante la ventana. ¿Alcanza con eso o hace falta modo mantenimiento en los frontends?
- **R:** Alcanza con el 503 actual y coordinación fuera de horario. No se agrega nada al producto.
  *(Pregunta resuelta antes de acotar el alcance; queda registrada, pero la migración quedó fuera
  del requerimiento.)*

### Funcionales

- **P:** Hoy un timeout del bus y un `core` caído devuelven ambos `503 service_unavailable`. El
  cambio los separa en `503 service_unavailable` (no hay nadie escuchando) y `504 gateway_timeout`
  (tardó demasiado). Es un cambio del contrato HTTP que ven `web` y `opus-web`.
- **R:** Entra en el alcance, **sin tocar los frontends**. La api separa los dos casos; `web` y
  `opus-web` muestran el mensaje que viene en el cuerpo, como ya hacen con cualquier error.

### Negocio

- **P:** El documento dice que la api sigue leyendo Postgres directo (ADR-001) y que `jiku-queries`
  "nace para servir a otros consumidores", pero a la vez agrega `bus.query()` al cliente de la api.
  Hoy no hay ningún consumidor identificado. ¿Hay uno previsto?
- **R:** No hay consumidor hoy. Se construye por adelantado: `jiku-queries` y `bus.query()` quedan
  disponibles sin uso, listos para cuando aparezca.

## Requerimientos Funcionales

**Renombrar y formalizar el servicio de escrituras**

1. El servicio lógico de escrituras del bus pasa a llamarse `jiku-commands`, reemplazando a
   `gestion` en el token `{svc}` del subject. La gramática
   `{instance}.{user-id}.{svc}.{version}.{método}` no cambia.
2. Los 20 comandos del registry de `core` se registran como endpoints del framework micro de NATS,
   uno por comando, con el subject y el nombre derivados del patrón (`tasks.{id}.edit` →
   subject `tasks.*.edit`, nombre `tasks-edit`). **La lógica de los comandos no se toca.**
3. El servicio queda descubrible por el bus (`$SRV.PING` / `INFO` / `STATS`) y reporta, por
   endpoint, cantidad de requests, latencia media y último error.
4. El queue group del servicio es `jiku-commands` (no el default `q` de micro).

**Crear el servicio de lecturas**

5. Se crea un segundo servicio lógico, `jiku-queries`, con nombre propio en el bus, queue group
   propio y sus 6 endpoints registrados: `projects.list`, `projects.get`, `tasks.list`,
   `tasks.get`, `comments.list`, `comments.get`. Sin `*` en sus subjects: el id del recurso viaja
   en el payload.
6. Los dos servicios viven en **el mismo proceso y el mismo deployable** (la imagen de `core`),
   sobre **una sola conexión NATS**. No se agrega ningún deployable nuevo.
7. Los dos servicios se registran en el arranque del proceso, y el apagado los detiene a **ambos**
   —dejan de aceptar requests nuevas— antes de drenar y cerrar la conexión NATS, de modo que
   ninguna request en vuelo quede sin respuesta.
8. `jiku-queries` usa una **conexión propia a Postgres con un rol de solo lectura**, distinta de la
   del usuario dueño que usan los comandos. Esa conexión **no registra los modelos de
   `@jiku/models`** y las consultas se escriben en SQL explícito.
9. El módulo de consultas **no abre transacción por request**. Si una consulta necesita
   consistencia entre varias lecturas, usa una transacción `READ ONLY` explícita dentro de sí misma.
10. **El contrato de cada endpoint de consulta (filtros, paginación, campos, payloads de respuesta)
   queda fuera de alcance.** Este requerimiento entrega los endpoints registrados y descubribles.

**Contrato del bus (sin cambios de semántica)**

11. El envelope de respuesta (`{status:'success', data}` / `{status:'failure', errorCode,
    errorMessage}`), el catálogo de `errorCode` y la semántica de los comandos **no cambian**.
12. En un `failure`, el envelope viaja **en el cuerpo** y además se agregan los headers
    `Nats-Service-Error` / `Nats-Service-Error-Code`. Los headers son un agregado, nunca un
    reemplazo del cuerpo.
13. Se mantiene request/reply puro: **no se introduce JetStream, cola ni persistencia** (ADR-002).
14. Los endpoints HTTP de lectura de la api **no** migran al bus: la api sigue leyendo Postgres
    directo (ADR-001).

**Cliente de la api**

15. La api suma un método `query()` a su cliente del bus, con su propio timeout
    (`NATS_QUERY_TIMEOUT_MS`, 10000) separado del de comandos (`NATS_REQUEST_TIMEOUT_MS`, 5000).
    Queda disponible sin consumidor: no hay ningún caso de uso que lo ejercite hoy.
16. La api distingue dos fallas que hoy colapsan en una: `503 service_unavailable` cuando no hay
    ningún suscriptor del subject, y `504 gateway_timeout` cuando la respuesta no llegó a tiempo.
    `web` y `opus-web` no se modifican: siguen mostrando el mensaje del cuerpo.

**Contrato de subjects en código**

17. `@jiku/nats-protocol` es la **única** fuente de subjects. Expone `COMMAND_SERVICE`,
    `QUERY_SERVICE`, `commandSubject()`, `querySubject()`, `groupSubject()`, `endpointName()` y
    `endpointSubject()`; elimina `SERVICE_NAME` y `subscriptionSubject()`. `inboxPrefix()`,
    `hashUserId()`, `Reply`, `success()`, `failure()` y `ErrorCode` quedan igual.
18. Ningún componente arma un subject concatenando strings a mano.

**Permisos y configuración**

19. El auth-callout autoriza el estado final: la api publica en los dos prefijos nuevos, `core`
    se suscribe a **los dos** (`{instance}.*.jiku-commands.v1.>` y `{instance}.*.jiku-queries.v1.>`)
    más `$SRV.>` y su inbox, el publicador externo mantiene su lista **enumerada** de 9 subjects
    con el nombre nuevo, y el observer enumera los dos prefijos.
20. No se crea ningún rol ni service user nuevo en Zitadel: los dos servicios comparten el service
    user y el rol `core` existentes.
21. Se elimina la variable `NATS_SERVICE_NAME` de los compose y de `deploy/bus-inspect.sh`, y se
    agregan `NATS_COMMAND_SERVICE`, `NATS_QUERY_SERVICE`, `NATS_QUERY_TIMEOUT_MS`,
    `SERVICE_VERSION`, `POSTGRESQL_READ_USER`, `POSTGRESQL_READ_PASSWORD`,
    `POSTGRESQL_READ_POOL_MAX` y `POSTGRESQL_STATEMENT_TIMEOUT_MS`.
22. **No se toca `NATS_OPERATOR_NAME`** (default `gestion`): es el operador del árbol de cuentas
    NATS, no el token `{svc}`. Cambiarlo obliga a regenerar el árbol de creds.

**Documentación**

23. Se corrigen ADR-002 y la cabecera de `docs/apis/core.yaml`, que dicen 17 comandos cuando el
    registry tiene 20, y se actualizan con la gramática y el nombre de servicio nuevos.
24. Se actualizan las convenciones `docs/architectures/api/conventions/bus-commands.md` y
    `docs/architectures/core/conventions/bus-consumer.md` — esta última pasa a describir un servicio
    micro, no un `subscribe` a pelo.
25. Se escribe un ADR nuevo, *"El bus se sirve como dos servicios micro en un mismo proceso"*, con
    las dos decisiones que un lector futuro no podría reconstruir solo: por qué la separación va en
    el token `{svc}` y por qué los dos servicios comparten deployable pero **no** conexión a la base.

## Criterios de Aceptación

### Registro y descubrimiento

1. **DADO** el proceso de `core` desplegado con el cambio aplicado
   **CUANDO** se ejecuta `nats micro ls`
   **ENTONCES** aparecen dos servicios, `jiku-commands` y `jiku-queries`, ambos en la versión de
   `SERVICE_VERSION` y servidos por el **mismo** proceso

2. **DADO** `jiku-commands` registrado
   **CUANDO** se ejecuta `nats micro info jiku-commands`
   **ENTONCES** lista exactamente **20** endpoints, cada uno con subject
   `{instance}.*.jiku-commands.v1.{método}` —los segmentos variables como `*`—, nombre sin puntos
   (`tasks-edit`, `requirements-subscriptors-delete`) y queue group `jiku-commands`

3. **DADO** `jiku-queries` registrado
   **CUANDO** se ejecuta `nats micro info jiku-queries`
   **ENTONCES** lista 6 endpoints — `projects-list`, `projects-get`, `tasks-list`, `tasks-get`,
   `comments-list`, `comments-get` — **sin `*`** en sus subjects y con queue group `jiku-queries`

4. **DADO** tres réplicas de `core` arriba
   **CUANDO** se ejecuta `nats micro ping`
   **ENTONCES** devuelve 3 instancias de `jiku-commands` y 3 de `jiku-queries`, cada una con su
   propio `id`

5. **DADO** un comando atendido por `jiku-commands`
   **CUANDO** se ejecuta `nats micro stats jiku-commands`
   **ENTONCES** el endpoint correspondiente reporta `num_requests`, `processing_time` y
   `average_processing_time` propios, separados de los de `jiku-queries`

### Comportamiento del contrato (sin cambios)

6. **DADO** un usuario de `web` que crea un actor
   **CUANDO** la api publica `{instance}.{uid}.jiku-commands.v1.clients.new`
   **ENTONCES** `core` responde `{status:'success', data:{id}}` en el cuerpo y el actor queda
   creado — comportamiento idéntico al de antes del rename, con los tests existentes de `core` en
   verde y **sin cambios en sus aserciones**

7. **DADO** un comando que falla por regla de negocio (por ejemplo `project_not_found`)
   **CUANDO** `core` responde
   **ENTONCES** el envelope `{status:'failure', errorCode, errorMessage}` viaja **en el cuerpo** y
   además llegan los headers `Nats-Service-Error` y `Nats-Service-Error-Code`

8. **DADO** un `POST /api/requirements` y ningún suscriptor de `jiku-commands`
   **CUANDO** la api publica el comando
   **ENTONCES** el server contesta "no responders" en milisegundos y la api devuelve
   `503 service_unavailable` con el cuerpo `{code:'service_unavailable', message:'El servicio no
   está disponible en este momento'}`

9. **DADO** un `POST /api/requirements` cuyo comando no recibe respuesta dentro de
   `NATS_REQUEST_TIMEOUT_MS`
   **CUANDO** vence el timeout
   **ENTONCES** la api devuelve `504 gateway_timeout` con el cuerpo `{code:'gateway_timeout',
   message:'La operación tardó demasiado'}`, y `web` / `opus-web` muestran ese mensaje sin
   modificarse

### Separación lectura/escritura en un proceso compartido

10. **DADO** el módulo de consultas con su conexión de solo lectura abierta
    **CUANDO** una consulta intenta escribir en la base
    **ENTONCES** Postgres la rechaza por permisos del rol — no una validación de código

11. **DADO** el proceso de `core` arrancado **después** de que el módulo de consultas abrió su
    conexión
    **CUANDO** un usuario da de alta un requisito
    **ENTONCES** el alta funciona: los comandos siguen escribiendo por la conexión del usuario
    dueño de la base (es la regresión que causaría reasignar los modelos del ORM)

### Apagado ordenado

12. **DADO** el proceso de `core` con requests en vuelo en los dos servicios
    **CUANDO** se apaga el proceso
    **ENTONCES** los dos servicios dejan de aceptar requests nuevas, las que ya estaban en curso se
    responden, y recién después se drena y cierra la conexión NATS — ninguna queda sin respuesta

### Permisos

13. **DADO** un consumidor al que se le concede `{instance}.{uid}.jiku-queries.v1.>`
    **CUANDO** intenta publicar en `{instance}.{uid}.jiku-commands.v1.clients.new`
    **ENTONCES** el bus rechaza la publicación por falta de permiso

14. **DADO** el publicador externo con rol `external-publisher`
    **CUANDO** publica `{instance}.{uid}.jiku-commands.v1.files.request-upload`
    **ENTONCES** `core` responde normalmente, y los 9 subjects enumerados en su plantilla siguen
    siendo los únicos que puede publicar — un comando fuera de la lista es rechazado por el bus

### Casos de error

15. **DADO** un servicio cuyos patrones producen dos endpoints que matchean el mismo subject
    **CUANDO** arranca el proceso de `core`
    **ENTONCES** el arranque **falla** con un mensaje que nombra el servicio y el subject duplicado
    — nunca se llega a runtime con dos respuestas al mismo inbox

16. **DADO** que el registro de uno de los dos servicios micro falla
    **CUANDO** arranca el proceso de `core`
    **ENTONCES** el arranque falla entero: no queda el proceso arriba con un solo servicio
    registrado

17. **DADO** un mensaje cuyo payload no es JSON válido
    **CUANDO** llega a un endpoint de cualquiera de los dos servicios
    **ENTONCES** el servicio responde `{status:'failure', errorCode:'invalid_fields'}` en el cuerpo
    — la request nunca queda sin contestar

18. **DADO** un handler que lanza una excepción inesperada
    **CUANDO** se procesa la request
    **ENTONCES** el servicio responde `{status:'failure', errorCode:'internal_error'}` en el cuerpo
    y el caller obtiene una respuesta en vez de esperar hasta su timeout

19. **DADO** `SERVICE_VERSION` con un valor que no es SemVer estricto
    **CUANDO** arranca `core`
    **ENTONCES** micro rechaza el registro y el arranque falla con un error claro

20. **DADO** una consulta cuyo SQL supera `POSTGRESQL_STATEMENT_TIMEOUT_MS`
    **CUANDO** se ejecuta
    **ENTONCES** Postgres la aborta y el servicio responde un `failure` **antes** de que expire
    `NATS_QUERY_TIMEOUT_MS` del caller

21. **DADO** un cliente que conecta sin fijar `inboxPrefix` con el hash de su propio user id
    **CUANDO** publica una request
    **ENTONCES** la respuesta no llega y la request expira por timeout — no por un error de
    permisos, que es lo que hace caro el diagnóstico

22. **DADO** una plantilla del auth-callout a la que le falta `$SRV.>`
    **CUANDO** arranca `core`
    **ENTONCES** los dos servicios levantan y atienden requests, pero **no aparecen** en
    `nats micro ls` — el síntoma que la configuración final debe evitar

23. **DADO** un comando que responde `failure`
    **CUANDO** se consulta `nats micro stats jiku-commands`
    **ENTONCES** `num_errors` sigue en **0** — es una limitación conocida de la librería
    (`respondError()` no lo incrementa) y las fallas se miden por logs y por `errorCode`, no por esa
    métrica

## Clasificación

- **Complejidad:** alta
- **Justificación:**
  - Toca cuatro componentes (`core`, `api`, `packages/nats-protocol`, `deploy/`) y el contrato que
    los une
  - Reemplaza la capa de conexión al bus de `core` completa (`consumer.ts` → host + service)
  - Introduce un módulo nuevo (`core/src/queries/`) y una segunda conexión a la base dentro del
    mismo proceso, con una trampa silenciosa documentada (la reasignación de modelos del ORM)
  - Cambia la superficie pública de un paquete compartido y un contrato de subject que rompe a
    todos los callers a la vez
  - En contrapartida, **no toca la lógica de los 20 comandos ni el esquema de la base**, y el plan
    de migración quedó fuera de alcance
- **Prioridad:** alta

### Cambios de API

`core` no expone HTTP: su contrato es AsyncAPI (`docs/apis/core.yaml`). Los cambios de "API" de este REQ son de tres clases distintas y conviene no mezclarlas: **la gramática del bus**, **la superficie del paquete que la implementa** y **el contrato HTTP de la api**.

#### 1. El contrato del bus — la gramática

**Actual** (copiado verbatim de `docs/apis/core.yaml`:99-112):

```
{instance}.{user-id}.{svc}.{version}.{command}
dev.323332022539911171.gestion.v1.clients.new

instance   deployment: dev / prod              (NATS_INSTANCE)
user-id    WHO publishes: the token's `sub`, RAW
svc        who it talks to: `gestion`          (NATS_SERVICE_NAME)
version    protocol version: `v1`              (NATS_PROTOCOL_VERSION)
command    clients.new, requirements.{id}.edit, ...
```

**Nueva** — la gramática **no cambia**; cambia el conjunto de valores del token `{svc}`, que pasa de uno a dos:

```
{instance}.{user-id}.{svc}.{version}.{método}

dev.<uid>.jiku-commands.v1.tasks.new          -> MODIFICADO  (era gestion)
dev.<uid>.jiku-commands.v1.tasks.88.edit      -> MODIFICADO  (era gestion)
dev.<uid>.jiku-queries.v1.tasks.list          + NUEVO
dev.<uid>.jiku-queries.v1.tasks.get           + NUEVO

svc   jiku-commands  (NATS_COMMAND_SERVICE)   -> MODIFICADO
      jiku-queries   (NATS_QUERY_SERVICE)     + NUEVO
```

Suscripciones:

```
{instance}.*.gestion.v1.>        queue group: gestion         - ELIMINADO
{instance}.*.jiku-commands.v1.>  queue group: jiku-commands   + NUEVO
{instance}.*.jiku-queries.v1.>   queue group: jiku-queries    + NUEVO
```

**Por qué la separación va en `{svc}` y no anidada bajo el servicio actual** — es la decisión menos obvia del REQ y la que evita un bug silencioso. La suscripción de comandos es `{instance}.*.{svc}.v1.>`, y ese `>` **se come también las consultas** si comparten el token `{svc}`. Con dos queue groups distintos sobre subjects solapados el mensaje se entrega a **las dos** suscripciones y salen **dos respuestas al mismo inbox**; un `request()` devuelve la primera y **descarta la segunda en silencio**. El síntoma sería respuestas correctas la mitad de las veces, sin ningún error. Compartir proceso no lo evita: el solapamiento es del subject. Con `{svc}` distinto el problema no existe porque los tokens se comparan enteros. Justificación: RF-1, RF-5, §6 del requerimiento original.

**Lo que NO cambia del contrato:** el envelope `Reply`, el catálogo de `ErrorCode`, la semántica de los 20 comandos, el inbox hasheado, el flujo del token del service user, `v1` (RF-11, RF-13).

#### 2. Canales existentes: el prefijo cambia, el canal no

Los **20 canales** de `docs/apis/core.yaml`:130-569 **no cambian de nombre, ni de payload, ni de respuesta**. Los canales están nombrados por el **comando**, no por el subject completo — el spec lo dice explícito (`:115-116`: *"The `channels` below are named after the COMMAND, not the full subject"*), así que el rename **no toca ni una línea de `channels`**.

Lo que cambia es la **prosa** del spec (RF-23):

| Ubicación en `docs/apis/core.yaml` | Actual | Nuevo |

Las dos reglas de forma que la derivación respeta, y por qué:

- **El nombre no lleva puntos.** Micro valida el nombre del endpoint contra `/^[-\w]+$/`; el subject con puntos y `*` va aparte, en `opts.subject`.
- **El `{param}` se vuelve `*`.** Un token de subject no puede llevar llaves, y el despachador ya extrae los params del subject completo con el registry por segmentos — **no los necesita del endpoint**.

**Verificación de no-solapamiento (CA-15).** Dos endpoints que matcheen el mismo subject producen dos respuestas al mismo inbox. Los 20 de arriba no se solapan, y la razón es estructural, no suerte: el registry matchea **por cantidad de segmentos** (`core/conventions/commands.md`: *"un patrón solo matchea si tiene la misma cantidad de segmentos"*), y entre los que comparten longitud difieren en el primer o el último token literal. Pero **el diseño no se apoya en esa verificación manual**: `registerService()` mantiene un `Set` de subjects y **falla el arranque** ante un duplicado. Se verifica al arrancar, no en revisión.

#### 3. Nuevo servicio lógico en el bus: `jiku-queries`

Seis endpoints **registrados y descubribles**, con el contenido de cada uno **fuera de alcance** (RF-10):

| Subject del endpoint | Nombre | Qué devuelve |
|---|---|---|
| `projects.list` | `projects-list` | Colección paginada |
| `projects.get` | `projects-get` | Un recurso |
| `tasks.list` | `tasks-list` | Colección paginada |
| `tasks.get` | `tasks-get` | Un recurso |
| `comments.list` | `comments-list` | Colección paginada |
| `comments.get` | `comments-get` | Un recurso |

**Sin `*` en los subjects de consulta.** El id del recurso viaja en el payload. El motivo es de cardinalidad: el server matchea con un trie más un **cache de subjects de 1024 entradas**, y el tráfico de lectura es el de mayor volumen — un subject nuevo por cada id consultado vuelve inútil el cache. Justificación: RF-5, §9.2 del requerimiento original.

**Qué significa "registrado sin contrato".** Un endpoint que existe, aparece en `nats micro info`, tiene queue group y contadores, y **responde un `failure` bien formado** a cualquier request. No queda sin contestar (esa es la regla dura) ni responde datos inventados. El código concreto de ese `failure` es decisión de la story; lo que el diseño fija es que **el endpoint contesta**.

**Traducción de vocabulario, ya ubicada.** `comments` no es una tabla: son las filas de `objective_activity` y `requirement_activity` con `type_of_activity = 'comment'` (`docs/db-schemas/jiku.md`:278-299). Y `tasks` es la tabla `objectives`. Las dos traducciones viven **dentro** del módulo de consultas, igual que en los comandos (ADR-004). No es trabajo de este REQ resolverlas, pero sí dejar dicho **dónde** van, para que el REQ del contrato no las ponga en otro lado.

#### 4. Superficie pública de `@jiku/nats-protocol`

Es el cambio de API **real** del REQ: lo consumen los dos backends y define el contrato.

| Símbolo | Estado | Detalle |
|---|---|---|
| `INSTANCE`, `PROTOCOL_VERSION` | Sin cambios | `NATS_INSTANCE` / `NATS_PROTOCOL_VERSION`, leídos **al importar** |
| `COMMAND_SERVICE` | **+ NUEVO** | `NATS_COMMAND_SERVICE \|\| 'jiku-commands'` |
| `QUERY_SERVICE` | **+ NUEVO** | `NATS_QUERY_SERVICE \|\| 'jiku-queries'` |
| `SERVICE_NAME` | **-> DEPRECADO** | Alias de `COMMAND_SERVICE`, marcado `@deprecated`. **No se borra de golpe**: es el símbolo que un consumidor externo podría importar, y romperle el build no aporta nada |
| `commandSubject(command, userId)` | **Firma igual, valor distinto** | Usa `COMMAND_SERVICE` en vez de `SERVICE_NAME`. **Ningún caller cambia** |
| `querySubject(query, userId)` | **+ NUEVO** | Misma gramática, `QUERY_SERVICE` |
| `groupSubject(service)` | **+ NUEVO** | `{instance}.*.{svc}.{version}` — el prefijo del grupo micro. El `*` cubre al caller |
| `endpointName(pattern)` | **+ NUEVO** | `tasks.{id}.edit` -> `tasks-edit` |
| `endpointSubject(pattern)` | **+ NUEVO** | `tasks.{id}.edit` -> `tasks.*.edit` |

| `subscriptionSubject()` | **- ELIMINADO** | Su único caller es `consumer.ts`, que desaparece. Lo reemplaza `groupSubject()` |
| `callerFromSubject`, `inboxPrefix`, `hashUserId`, `Reply`, `success`, `failure`, `ErrorCode` | **Sin cambios** | RF-17 explícito. `inboxPrefix`/`hashUserId` **no se tocan**: tienen que seguir dando exactamente lo mismo que el auth-callout |

**La regla que hace que esto funcione:** ningún componente concatena un subject a mano (RF-18). Es lo que permite que el rename sea un cambio de **un** archivo y no una búsqueda de strings por cuatro servicios.

#### 5. Contrato HTTP de la api — un status nuevo

**Actual** (verbatim de `api/lib/utils/bus/send-command.ts:29-38`, citado en `api/conventions/bus-commands.md`):

```ts
} catch (error: any) {
  logger.error(`[bus] ${command}: ${error.message}`);
  res.status(503).json({ code: 'service_unavailable', message: 'El servicio no está disponible en este momento' });
  return null;
}
```

**Nuevo** — se separan dos fallas que hoy colapsan en una:

| Causa | Actual | Nuevo | Cuerpo nuevo |
|---|---|---|---|
| No hay **ningún suscriptor** del subject | 503 `service_unavailable` | **503 `service_unavailable`** (sin cambio) | `{code:'service_unavailable', message:'El servicio no está disponible en este momento'}` |
| La respuesta **no llegó a tiempo** | 503 `service_unavailable` | **504 `gateway_timeout`** -> MODIFICADO | `{code:'gateway_timeout', message:'La operación tardó demasiado'}` |

**Por qué vale la pena separarlos.** No son el mismo problema y hoy son indistinguibles. Cuando no hay suscriptores el server contesta **en milisegundos**, no al vencer el timeout: es la señal de un problema de **despliegue**. Un timeout es un problema de **performance**. Con un solo status, el operador no puede distinguir "no desplegué core" de "core está lento" sin mirar los logs.

**Lo que hay que respetar al agregarlo** (`api/conventions/error-handling.md`): `code` es `snake_case` y estable, y **un `errorCode` sin entrada en el mapa sale 500**. `gateway_timeout` no es un `errorCode` de core —no viene en un `Reply`, lo genera la api en el `catch`— así que **no va en `STATUS_BY_ERROR_CODE`**; es un `code` de respuesta HTTP directa, como `service_unavailable`. Confundir los dos mapas es el error fácil acá.

**Y lo que confirma que los frontends no cambian** (RF-16): ninguno enumera códigos en su capa de red. `web/src/lib/axios.ts:41-49` y `opus-web/src/lib/axios.ts:26-30` normalizan cualquier `{code,message}` a `ApiError` con un default y **propagan `message` tal cual**; solo el 401 tiene rama propia. Un 504 con código nuevo se muestra sin tocar una línea.

#### 6. `docs/apis/api.yaml` — el 504 es un cambio de spec de 27 lugares

El REQ no lo menciona y es el cambio de documentación de API con más superficie del REQ. El spec de la api **ya declara el 503 del bus como un contrato explícito y compartido**:

- **`components/responses/BusUnavailable`** (`:2277-2286`) — la respuesta compartida, con `example: {code: service_unavailable, message: El servicio no está disponible en este momento}`. Su `description` actual **conflaciona las dos causas** exactamente como el código: *"El bus no respondió dentro de `NATS_REQUEST_TIMEOUT_MS` (default 5000 ms), **o no está disponible**"*
- **26 referencias** `'503': { $ref: '#/components/responses/BusUnavailable' }` repartidas por las operaciones que publican
- **20 anotaciones `x-bus-command`** que marcan qué comando publica cada operación
- **La cabecera** (`:32-36`): *"Eso agrega dos modos de falla a todos ellos: `503` (`service_unavailable`) si el bus no responde dentro de `NATS_REQUEST_TIMEOUT_MS`..."*

El cambio, entonces:

| Qué | Cambio |
|---|---|
| `components/responses/BusUnavailable` | **Se acota** a su causa real: *no hay ningún suscriptor del subject; el server lo contesta en milisegundos*. Deja de mencionar el timeout |
| `components/responses/GatewayTimeout` | **+ NUEVO**, con `example: {code: gateway_timeout, message: La operación tardó demasiado}` y la nota de que **la operación pudo haber ocurrido** — es el modo de falla más confuso del sistema (ADR-002) y el spec es el lugar donde decirlo |
| Las **26** operaciones con `'503'` | Suman `'504': { $ref: '#/components/responses/GatewayTimeout' }`. **Ninguna pierde el 503**: las dos son alcanzables |
| Cabecera (`:32-36`) | *"dos modos de falla"* -> **tres**, con la distinción despliegue / performance explicada |

**Que las 26 referencias apunten a un componente compartido es lo que hace este cambio mecánico en vez de riesgoso:** el texto se escribe una vez y las operaciones solo suman una línea. Es también la razón de que valga hacerlo completo en la misma story y no dejarlo para después: un spec que documenta 503 donde el servicio devuelve 504 es peor que uno que no documenta nada.

Los **61 endpoints HTTP** de `docs/apis/api.yaml` **no cambian de forma**: mismo path, mismo método, mismo request, misma respuesta de éxito. Los que publican comandos ganan un status de error posible (504) que antes salía como 503. Los **endpoints HTTP de lectura no migran al bus** (RF-14): la api sigue leyendo PostgreSQL directo (ADR-001).

### Cambios de Base de Datos

#### Tablas Existentes a Modificar

**Ninguna.** Este REQ no toca el esquema: ni una tabla, ni una columna, ni un índice, ni un enum, ni una migración. `docs/db-schemas/jiku.md` no cambia en su sección de entidades ni en el DBML.

#### Nuevas Tablas

**Ninguna.**

#### Lo que sí cambia: un tercer par credencial/rol

No es DDL de esquema, pero es infraestructura de base y es **la pieza que sostiene la garantía de ADR-001 dentro de un proceso compartido**. Hoy `docs/db-schemas/jiku.md`:8-14 declara dos accesos; pasan a ser tres:

| Servicio / módulo | Acceso | Variables | Detalle |
|---|---|---|---|
| `core` — comandos | **lectura y escritura** | `POSTGRESQL_USER` / `_PASSWORD` | El usuario **dueño**. Sin cambios (`core/src/models/index.ts`) |
| `core` — consultas | **solo lectura** | `POSTGRESQL_READ_USER` / `_PASSWORD` + NUEVO | Rol estrictamente `SELECT`. Conexión nueva (`core/src/models/read.ts`) |
| `api` | **solo lectura** | `POSTGRESQL_USER` / `_PASSWORD` | Sin cambios |

**`POSTGRESQL_READ_USER` puede ser el rol que ya usa la api.** Es de solo lectura y no hay razón para crear otro. Lo único que **no** puede ser es el usuario dueño — si lo fuera, la garantía desaparece en silencio y CA-10 no se cumple.

**La conexión de lectura se crea SIN `models`.** Es la decisión más importante de esta sección y la más fácil de romper. `ADR-005` dice que cada servicio registra las clases de `@jiku/models` en su propio Sequelize, y que eso funciona **porque son procesos distintos**. En un solo proceso, la **segunda** instancia que registre `allModels` **reasigna** esas clases: `Objective.findAll()` empezaría a salir por la conexión equivocada. Y el sentido del error es el peligroso:

| Reasignación | Síntoma |
|---|---|
| Los comandos salen por el rol de solo lectura | Falla **ruidosa**: Postgres rechaza la escritura. Se detecta al instante |
| Las consultas salen por el usuario dueño | Falla **silenciosa**: funciona perfecto, y **ADR-001 dejó de valer** sin que nada lo diga |

Por eso `read.ts` se crea sin `models` y **las consultas usan SQL explícito** (`readDb.query(...)`), no el ORM. Es la única forma de que las dos conexiones coexistan en un proceso sin que una pise a la otra. CA-11 es exactamente la regresión que esto previene.

**Y no es solo una restricción: para este servicio el SQL explícito conviene igual.** Los filtros dinámicos, el `ORDER BY` variable y el keyset (`WHERE (created_at, id) < ($1, $2)`) se expresan directo; `fields` es literalmente la lista del `SELECT`, mientras que con el ORM habría que traer la fila entera y descartar campos después; e instanciar 200 modelos para serializarlos a JSON acto seguido es trabajo puro de más.

**La regla de seguridad que lo acompaña, y que hay que fijar ahora aunque el contrato venga después:** los **nombres** de tabla, columna y dirección de orden salen **siempre** de listas blancas declaradas por cada recurso, nunca de la entrada del usuario; los **valores** van siempre como parámetros (`replacements` / `$1`), nunca interpolados. Con las dos cosas, el SQL explícito no agrega superficie de inyección. Sin ellas, este REQ habría cambiado la postura de seguridad del producto de pasada.

**`statement_timeout` en la conexión de lectura.** `POSTGRESQL_STATEMENT_TIMEOUT_MS` (8000) va **estrictamente por debajo** de `NATS_QUERY_TIMEOUT_MS` (10000). Así una consulta lenta vuelve como un `failure` explicable en vez de dejar al caller esperando sin saber por qué (CA-20). El orden entre las dos variables es una **invariante**, no una coincidencia de defaults.

**Pool separado, y una asimetría a decidir.** `POSTGRESQL_READ_POOL_MAX` (10) es propio: el pool de lectura no le come conexiones al de escritura. Es la mitigación concreta de "una consulta pesada degrada las escrituras del mismo proceso". **Pero hoy la conexión de escritura no declara pool en absoluto** (`core/src/models/index.ts:17-27` no pasa `pool`, así que corre con los defaults de Sequelize — `max: 5`). El resultado es que el pool **nuevo** queda con techo explícito y **el doble** del viejo, que quedó implícito. No es un error, pero es una asimetría que conviene resolver a conciencia: o se declara también el de escritura, o se documenta por qué el de lectura necesita más. Es la clase de detalle que, sin decirlo, se descubre cuando `max_connections` de la instalación se queda corto.

### Flujo de Interacción

#### Escenario 1: Arranque del proceso — los dos servicios se registran (CA-1, CA-2, CA-3, CA-15, CA-16, CA-19)

**Trigger:** arranca el contenedor de `core`.

**Flujo:**

1. **[`core/src/index.ts`]**
   - Conecta la base del **dueño** con 5 reintentos de 1s (`models/index.ts`, sin cambios)
   - Construye `Dispatcher` (comandos) y `QueryDispatcher` (consultas)
   - -> `new BusHost(commands, queries).start()`

2. **[`core/src/bus/host.ts`]**
   - Pide el token del service user a `@jiku/zitadel-auth` y arranca el auto-refresh
   - Abre **UNA** conexión: `connect({ servers, inboxPrefix: inboxPrefix(userId), authenticator: [...], name: 'jiku-core' })`
   - **`inboxPrefix` es obligatorio.** Sin él la librería genera un `_INBOX.<aleatorio>` que ningún permiso acotado autoriza (CA-21)
   - -> registra los servicios, **en serie**

3. **[`bus/service.ts` — `registerService(nc, spec)` para `jiku-commands`]**
   - `nc.services.add({ name: 'jiku-commands', version: SERVICE_VERSION, queue: 'jiku-commands', metadata: {instance, protocol} })`
   - **`version` debe ser SemVer estricto** o micro rechaza el registro (CA-19)
   - `service.addGroup(groupSubject('jiku-commands'))` -> `{instance}.*.jiku-commands.v1`
   - Para cada uno de los **20** patrones de `commandRegistry.patterns()`: deriva `endpointSubject` + `endpointName`, **verifica que el subject no esté ya en el `Set`** y hace `group.addEndpoint(name, { subject, handler })`
   - Si hay duplicado -> **`throw`**, y el arranque falla nombrando servicio y subject (CA-15)
   - -> devuelve el `Service`

4. **[`bus/service.ts` — `registerService(nc, spec)` para `jiku-queries`]**
   - Ídem con `queue: 'jiku-queries'`, grupo `{instance}.*.jiku-queries.v1` y los **6** patrones de `queryRegistry.patterns()`
   - -> devuelve el `Service`

5. **[NATS]**
   - Cada servicio se suscribe a `$SRV.PING` / `INFO` / `STATS`, y a `.<name>` y `.<name>.<id>`
   - -> los dos aparecen en `nats micro ls` con ids distintos (CA-1, CA-4)

**Outcome:** un proceso, una conexión, **dos** servicios micro anunciados por separado en `$SRV`, con 20 y 6 endpoints y queue groups propios.

**Manejo de errores:**
- Falla el registro de **cualquiera** de los dos -> el arranque falla **entero**. No queda el proceso arriba con un solo servicio (CA-16). Es la razón por la que se registran en serie y el error se propaga
- `SERVICE_VERSION` no es SemVer estricto -> micro rechaza el registro -> arranque falla (CA-19)
- Dos endpoints con el mismo subject -> `throw` con el nombre del servicio y el subject (CA-15)
- Falta `$SRV.>` en la plantilla del callout -> **los servicios levantan y atienden, pero son invisibles** para `nats micro ls`. No hay error: es el modo de falla que la configuración final tiene que evitar (CA-22)

**Notas:**
- `nc.services.add()` **no** tiene singleton: cada llamada crea un servicio con su propio id, endpoints y contadores. Es lo que hace posible un proceso con dos servicios
- El `*` del grupo cubre el user id de cualquier caller. Micro lo acepta: la validación del **grupo** solo rechaza vacío, espacios y `>` interno

#### Escenario 2: Un comando de escritura, después del rename (CA-6, CA-7)

**Trigger:** un usuario de `web` crea un actor.

**Flujo:**

1. **[`web`]** `POST /api/clients` con `{name, description}` -> **api**. **Sin cambios**

2. **[`api` — `lib/routes/clients-post.ts`]**
   - `sendCommand(res, 'clients.new', {...})` -> `bus().request('clients.new', payload)`
   - Subject: `commandSubject('clients.new', userId)` -> `{instance}.{uid}.jiku-commands.v1.clients.new` -> **MODIFICADO** (era `gestion`)
   - **El archivo de ruta no cambia**: el subject sale del paquete
   - Timeout: `NATS_REQUEST_TIMEOUT_MS` (5000)
   - -> publica y espera en `_INBOX.<hash(uid)>`

3. **[NATS]** Matchea `{instance}.*.jiku-commands.v1.>`; el endpoint `clients-new` (subject `clients.new`) lo recibe. Queue group `jiku-commands`: **una** réplica lo atiende

4. **[`core` — `bus/service.ts` `handle()`]**
   - Parsea el cuerpo. **Vacío es `{}`**, no un error (los borrados no llevan payload)
   - `await spec.handle(msg.subject, payload)` -> `dispatcher.dispatch(subject, payload)` — **el despachador recibe el subject completo y resuelve el comando con `methodFromSubject`: SIN CAMBIOS**
   - -> `Reply`

5. **[`core` — `bus/dispatcher.ts`, SIN CAMBIOS]**
   - `validate` **antes** de abrir la transacción
   - Abre transacción, `execute`, **commit si `success`** / rollback en cualquier otro caso (ADR-003)
   - `Client.create(..., { transaction })` por la conexión del **dueño** (CA-11)
   - -> `success({ id })`

6. **[`core` — `respond()`]**
   - `success` -> `msg.respond(encode(reply))`. El envelope va **en el cuerpo**
   - -> al inbox del caller

7. **[`api`]** Recibe `{status:'success', data:{id}}`, **relee la base** con Sequelize y responde `201` con el actor completo (ADR-001)

**Outcome:** el actor queda creado. **Comportamiento idéntico al de antes del rename**, y los tests existentes de `core` pasan **sin cambios en sus aserciones** (CA-6) — porque entran por el despachador (`tests/helpers/dispatch.ts`) y el despachador no cambió.

**Manejo de errores:**
- Falla de negocio (`project_not_found`) -> `respondError(500, errorCode, encode(reply))`: el envelope `{status:'failure', errorCode, errorMessage}` viaja **en el cuerpo** y **además** llegan los headers `Nats-Service-Error` y `Nats-Service-Error-Code` (CA-7). Los headers son un **agregado**, nunca un reemplazo (RF-12)
- Payload que no es JSON -> `{status:'failure', errorCode:'invalid_fields'}` en el cuerpo. **Nunca queda sin contestar** (CA-17)
- El handler lanza algo inesperado -> `{status:'failure', errorCode:'internal_error'}` en el cuerpo (CA-18)
- La api traduce el `errorCode` a HTTP con `httpStatusFor` — **mapa sin cambios**

**Notas:**
- **La regla dura: el handler nunca lanza.** Micro solo incrementa `num_errors` si el handler lanza **sincrónicamente**, y en ese caso responde `Empty` con headers, **perdiendo el cuerpo** — o sea el envelope, que es el contrato. Con handlers `async` una excepción rechaza la promesa y ni entra a ese `catch`. Consecuencia asumida: **`num_errors` queda en 0** (CA-23)
- `respondError` con status `500` es el status **del transporte micro**, no el HTTP. El que ve el usuario lo decide `httpStatusFor` sobre el `errorCode` del cuerpo

#### Escenario 3: Una consulta por `jiku-queries` (CA-3, CA-10, CA-20)

**Trigger:** un consumidor publica `{instance}.{uid}.jiku-queries.v1.tasks.list`. **Hoy no hay ninguno**: se construye por adelantado (Clarificaciones › Negocio).

**Flujo:**

1. **[caller]** `querySubject('tasks.list', userId)`, timeout `NATS_QUERY_TIMEOUT_MS` (10000)
2. **[NATS]** Matchea `{instance}.*.jiku-queries.v1.>`. **No matchea la suscripción de comandos** — tokens distintos, comparados enteros. **Una sola respuesta, un solo inbox**
3. **[`core` — endpoint `tasks-list`]** Queue group `jiku-queries`: el balanceo es **independiente** del de comandos
4. **[`core` — `queries/dispatcher.ts`]**
   - **No abre transacción** (RF-9). Si una consulta necesitara consistencia entre varias lecturas, usa una transacción `READ ONLY` explícita **dentro** de sí misma
   - -> resuelve el patrón contra el `queryRegistry`
5. **[`core` — `queries/tasks/tasks-list.ts`]**
   - `readDb.query<TaskRow>(sql, { type: QueryTypes.SELECT, replacements: {...} })` — **conexión de solo lectura, SQL explícito, sin ORM**
   - Nombres de tabla/columna/orden desde **listas blancas**; valores como **parámetros**
6. **[`core` — `respond()`]** Envelope en el cuerpo, igual que los comandos

**Outcome:** una respuesta JSON. En este REQ el endpoint existe, es descubrible y **contesta**; **qué** contesta lo define un requerimiento posterior (RF-10).

**Manejo de errores:**
- La consulta intenta **escribir** -> **Postgres la rechaza por permisos del rol**, no una validación de código (CA-10). Es ADR-001 sobreviviendo dentro de un proceso compartido
- El SQL supera `POSTGRESQL_STATEMENT_TIMEOUT_MS` (8000) -> Postgres lo aborta y el servicio responde un `failure` **antes** de que expire el `NATS_QUERY_TIMEOUT_MS` (10000) del caller (CA-20)
- Payload no-JSON / excepción inesperada -> `invalid_fields` / `internal_error` en el cuerpo. Mismo `handle()` que los comandos: **un solo lugar** donde está la regla de nunca dejar sin contestar

#### Escenario 4: No hay nadie vs. tardó demasiado (CA-8, CA-9)

**Trigger:** `POST /api/requirements`.

**Flujo A — ningún suscriptor de `jiku-commands`:**

1. **[`api`]** Publica el comando
2. **[NATS]** Contesta **"no responders"** con status `503` **en milisegundos**, no al vencer el timeout
3. **[`api` — `send-command.ts`]** Reconoce la señal -> **503** `{code:'service_unavailable', message:'El servicio no está disponible en este momento'}`
4. **[`web`/`opus-web`]** `axios.ts` normaliza y muestra `message`. **Sin cambios**

**Flujo B — no llega respuesta dentro de `NATS_REQUEST_TIMEOUT_MS`:**

1-2. **[`api` / NATS]** Vence el timeout de 5000 ms
3. **[`api`]** -> **504** `{code:'gateway_timeout', message:'La operación tardó demasiado'}` -> **MODIFICADO** (antes 503)
4. **[`web`/`opus-web`]** Muestran el mensaje nuevo **sin modificarse** (CA-9), verificado en `web/src/lib/axios.ts:41-49` y `opus-web/src/lib/axios.ts:26-30`

**Outcome:** dos fallas distinguibles. **En los dos casos la operación no ocurrió** — sin JetStream no hay cola ni reintento (ADR-002), y eso **no cambia**.

**Manejo de errores:**
- La distinción se hace sobre la señal del error del cliente NATS, no sobre el tiempo transcurrido
- **Cualquier otra excepción** del `catch` sigue cayendo en 503, que es el comportamiento actual. El cambio **agrega** una rama, no reescribe el `catch`

**Notas:**
- `gateway_timeout` es un `code` de respuesta HTTP de la api, **no un `errorCode` de core**: no entra en `STATUS_BY_ERROR_CODE`
- **El riesgo asumido de ADR-002 no se resuelve y empeora en legibilidad:** si core escribió y la respuesta se perdió, el usuario ahora ve un 504 de una operación que **sí** pasó. El status es más honesto sobre la causa (tardó) pero igual de engañoso sobre el efecto

#### Escenario 5: Apagado ordenado (CA-12)

**Trigger:** `SIGTERM` / `SIGINT` (deploy).

**Flujo:**

1. **[`core/src/index.ts`]** -> `BusHost.stop()`
2. **[`host.ts`]** Corta el auto-refresh del token
3. **[`host.ts`]** `await Promise.all(services.map(s => s.stop()))` — **los DOS servicios primero**: dejan de aceptar requests nuevas
4. **[`host.ts`]** `await connection.drain()` — las requests **en vuelo terminan y se responden**
5. **[`host.ts`]** `await connection.close()`

**Outcome:** ninguna request queda sin respuesta. Es la misma garantía que hoy da el `drain()` del consumer, extendida a dos servicios.

**Manejo de errores:**
- El orden es la garantía: parar los servicios **antes** de drenar. Al revés, una request nueva podría entrar durante el drain
- **No agregar un `process.exit()` que se saltee el drain.** Sin JetStream, una escritura cortada a medio camino se pierde sin rastro

### Consideraciones Técnicas

#### Riesgos

- **Riesgo: dos endpoints con subjects solapados.** El mensaje se entrega a las dos suscripciones y salen dos respuestas al mismo inbox; el caller devuelve la primera y **descarta la otra en silencio**. Respuestas correctas la mitad de las veces, sin ningún error.
  - **Mitigación:** `registerService()` mantiene un `Set` de subjects y **falla el arranque**. Es la mitigación que el REQ exige explícitamente y **no** es opcional: verificar los 20 a mano hoy no protege del comando 21.

- **Riesgo (el más silencioso del diseño): los modelos del ORM reasignados a la conexión de lectura.** `ADR-005` garantiza que api y core no divergen porque comparten `@jiku/models`, y funciona *"porque son procesos distintos"*. Con dos instancias de Sequelize en un proceso, la segunda que registre `allModels` **reasigna** las clases. En el sentido malo —consultas por el usuario dueño— **rompe ADR-001 sin síntoma**.
  - **Mitigación:** `read.ts` se crea **sin `models`** y las consultas usan SQL explícito. CA-11 es el test de regresión: un alta tiene que seguir funcionando **después** de que el módulo de consultas abrió su conexión. Ese test hay que escribirlo aunque hoy parezca trivial: es la única red.

- **Riesgo: se olvida `$SRV.>` en una plantilla del callout.** Los servicios levantan, atienden requests **y son invisibles** para `nats micro ls`. No hay error, y la observabilidad —que es la mitad del valor del REQ— desaparece sin avisar.
  - **Mitigación:** CA-22 lo declara como criterio. Un `$SRV.PING.<name>` como readiness probe lo detecta al deployar en vez de meses después.

- **Riesgo: `num_errors` siempre en 0.** `respondError()` no lo incrementa (solo sube si el handler lanza sincrónicamente, y con handlers `async` eso no pasa). Una alerta sobre esa métrica no se dispararía nunca.
  - **Mitigación:** documentarlo (CA-23) y medir las fallas por logs y por conteo de `errorCode`. **No armar alertas sobre `num_errors`.** No es una pérdida grave —un `project_not_found` es una respuesta correcta, no una falla del servicio— pero hay que saberlo **antes** de construir el dashboard.

- **Riesgo: el rename es un cambio de contrato que rompe a todos los callers a la vez.** No hay convivencia posible entre `gestion` y `jiku-commands` sin doble suscripción.
  - **Mitigación parcial y explícita:** el plan de corte **quedó fuera de alcance** (Clarificaciones › Alcance). Lo que este diseño **sí** aporta es que el estado final del callout autorice los nombres nuevos, y que el orden de stories deje el rename en **una** story acotada. La coordinación del deploy es de operación, no de código.

- **Riesgo: escalado acoplado.** Escalar lecturas escala escrituras y al revés. Un OOM o un crash se lleva los dos servicios.
  - **Mitigación:** **asumido**, y con salida diseñada: el día que las lecturas necesiten escalar aparte, `BusHost` lee un flag (`BUS_SERVICES=commands,queries`) y registra solo los que le pidan; la misma imagen se despliega dos veces con valores distintos y **ningún caller se entera** porque el subject no cambia. **Es la razón por la que la separación vive en `{svc}` desde el día uno**, no una racionalización posterior.

- **Riesgo: una consulta pesada degrada las escrituras del mismo proceso.** Node es de un solo hilo: la espera de Postgres no lo bloquea, pero serializar una página grande a JSON sí.
  - **Mitigación:** pool de lectura propio (`POSTGRESQL_READ_POOL_MAX`) que no le come conexiones al de escritura, `statement_timeout` propio, y el techo de `limit` + presupuesto de bytes del contrato de consultas. **Los dos últimos son del REQ del contrato, no de este** — este REQ deja la infraestructura, y un `jiku-queries` sin contrato no puede degradar nada porque no devuelve páginas.

- **Riesgo: `SERVICE_VERSION` mal configurado tira el arranque.** Micro valida SemVer con la regex oficial y rechaza cualquier otra cosa.
  - **Mitigación:** es el comportamiento **deseado** (CA-19) — falla ruidosa al arrancar, no degradación. Requiere que el default (`1.0.0`) esté en el código y que los compose no lo sobreescriban con algo como `latest`.

- **Riesgo (nuevo, no está en el REQ): `gestion` aparece en el repo en contextos que NO son el token del subject, y un find-and-replace los rompe.** Es el riesgo operativo más probable de este REQ, porque el cambio *se siente* como un rename global y no lo es:

  | Aparición | Qué es | Si se renombra |
  |---|---|---|
  | `deploy/.env.dist`:197 y `:149` — `STORAGE_S3_KEY_PREFIX=grava-gestion` | El **prefijo de claves de S3** | **Los archivos ya subidos se vuelven inalcanzables.** El propio `.env.dist:149` lleva una `ADVERTENCIA` explícita sobre cambiarlo en una instalación existente |
  | `deploy/nats/bootstrap.sh`:28-30 — `NATS_OPERATOR_NAME`, `NATS_APP_ACCOUNT=GESTION`, `NATS_AUTH_ACCOUNT=GESTION_AUTH` | El **operador y las cuentas** del árbol NATS | Obliga a **regenerar el árbol de creds** (RF-22 lo prohíbe explícitamente para el operador; las dos cuentas son igual de intocables y el REQ no las nombra) |
  | `deploy/nats/creds/nats-resolver.conf`:1 — `// Operator "gestion"` | Comentario del resolver generado | Inconsistente con el árbol real |
  | `deploy/.env`:27 — `DATABASE_NETWORK=grava-gestion-dev-database` | Nombre de una **red de Docker** | El contenedor no encuentra la base |
  | `core/tests/setup-env.ts`:65,81 — `POSTGRES_DB=gestionTest` | Nombre de la **base de tests** | Los tests no arrancan |
  | `docs/db-schemas/jiku.md`:213 y `docs/prd/requirements.md`:79 — enum `área`: `diseño / desarrollo / gestion / investigacion` | Un **valor de enum del dominio** | Migración de datos no pedida por nadie |

  - **Mitigación:** el cambio se hace **por símbolo, no por string**. En código el único lugar donde vive el valor es `packages/nats-protocol/src/index.ts`; en `deploy/` la lista de archivos a tocar está enumerada arriba, archivo por archivo y línea por línea. **`grep -r gestion` no es la herramienta correcta acá**, y conviene decirlo en la story.

- **Riesgo (nuevo): `PROTOCOL_VERSION` es variable en el código y literal en las plantillas del callout.** `templates/core.yaml`:29 tiene `{{instance}}.*.{{service}}.v1.>` con el `v1` **hardcodeado**, igual que los 9 subjects del `external-publisher`; y `templates/observer.yaml`:17 **omite el segmento de versión por completo**. Subir `NATS_PROTOCOL_VERSION` a `v2` dejaría al callout autorizando `v1` y todas las conexiones fallarían por permisos.
  - **Mitigación:** **fuera de alcance de este REQ** —no cambia la versión del protocolo (RF-11)— pero es una trampa latente que el REQ no registra, y este es el momento en que alguien está leyendo esas cuatro plantillas. Vale anotarla en el ADR nuevo como consecuencia conocida.

#### Dependencias

- **Orden duro entre stories:** el paquete antes que todo. `groupSubject()`, `endpointName()` y `endpointSubject()` no existen hasta la story 1, y sin ellos no hay servicio micro que registrar.
- **`jiku-queries` depende del host de `jiku-commands`**, no al revés: el host es la pieza que abre la conexión y registra N servicios. Registrar el segundo es sumar un elemento a un array.
- **`deploy` no depende de código pero es precondición de despliegue.** El callout tiene que autorizar el subject nuevo **antes o junto con** el código que lo usa; si no, las conexiones se rechazan y nada funciona. Autorizar `jiku-queries` y `$SRV.>` de entrada es **inocuo** cuando el servicio todavía no existe —un permiso sobre un subject sin suscriptores no hace nada— y evita un segundo cambio de seguridad después.
- **`api` depende solo de la story 1**, no de las de `core`: `query()` compila y publica sin que haya nadie del otro lado (y hasta que lo haya, devuelve el 503 de *no responders*). Es paralelizable.
- **Zitadel: ninguna dependencia** (RF-20). Sin rol ni service user nuevo.
- **Base de datos:** el rol de solo lectura tiene que existir en la instalación antes de que arranque el `core` con el módulo de consultas. Puede ser el de la api.
- **Ninguna dependencia nueva de npm.** Micro es parte de `nats`, que ya está instalado (`nc.services`).

#### Performance

- **Los comandos no cambian de costo.** Un endpoint micro es una suscripción con un handler: el camino es el mismo que el `for await` actual. Micro suma los contadores por endpoint, que es aritmética.
- **Lo que sí cambia, y a favor:** hoy hay **una** suscripción wildcard que recibe todo y el registry resuelve el comando en el proceso. Ahora el **server** matchea el subject contra 20 endpoints y entrega solo al que corresponde. El trabajo de routing se mueve de Node a NATS, que es donde va.
- **El despachador sigue sin `await` en el camino de recepción** (`void handle(...)`): un mensaje no bloquea la llegada del siguiente. La concurrencia real la acota el pool de Sequelize, igual que hoy.
- **Dos pools, no uno más grande.** El de escritura no cambia; el de lectura es nuevo y propio. El total de conexiones a Postgres por réplica de `core` **sube**, y hay que verificarlo contra `max_connections` de la instalación antes de subir `POSTGRESQL_READ_POOL_MAX`.
- **Un token más en el subject: cero.** Los subjects son de longitud similar (`jiku-commands` es más largo que `gestion`), muy por debajo de los 256 caracteres y 16 tokens.
- **El cache de subjects de 1024 entradas del server** es la razón de que las consultas no lleven `*`. Con el id en el subject, el tráfico de mayor volumen —lecturas— generaría un subject nuevo por id y volvería el cache inútil. Es una decisión de performance tomada **antes** de tener el contrato, y por eso hay que dejarla escrita acá: el REQ del contrato tiene que respetarla.

#### Seguridad

- **Un cambio en `rules.yaml` del auth-callout es un cambio de seguridad** (ADR-007, Implementation Rules). Se revisa como tal, no como configuración.
- **Deny-by-default se mantiene, y se refuerza.** Las plantillas **enumeran** los dos prefijos en vez de abrirse a `>` (ADR-008). La de `external-publisher` mantiene sus **9 subjects enumerados** con el nombre nuevo — es la más restrictiva a propósito y **no se abre** (CA-14).
- **La separación en `{svc}` habilita un permiso que hoy no se puede expresar:** `publish: ["{inst}.{uid}.jiku-queries.v1.>"]` da lectura **sin** dar escritura (CA-13). Con las consultas anidadas bajo el servicio de comandos no habría forma de acotarlo sin enumerar recursos.
- **`$SRV.>` es un permiso nuevo y hay que entender qué concede:** discovery y stats de micro. No expone payloads de negocio. **El `observer` sí los expone** —su plantilla escucha todo el protocolo, incluidos los datos de cada comando— y por eso **no va a producción**.
- **El SQL explícito de las consultas es superficie nueva de inyección si se hace mal.** La regla de listas blancas para nombres + parámetros para valores es lo que la cierra, y tiene que quedar en la convención **ahora**, con la infraestructura, no después con el contrato.
- **El rol de solo lectura es la garantía, no el código.** Si en una instalación `POSTGRESQL_READ_USER` apunta al usuario dueño, todo funciona y ADR-001 dejó de valer en silencio. Es el mismo riesgo que ADR-001 ya registra sin mitigación ("el rol de solo lectura se configura mal y la garantía desaparece en silencio"), ahora con un segundo lugar donde puede pasar.
- **El inbox hasheado no se toca.** `inboxPrefix()` y `hashUserId()` tienen que seguir dando exactamente lo mismo que calcula el callout. Un cambio ahí rompe todas las respuestas **por timeout, no por error de permisos**, que es lo que hace caro el diagnóstico (CA-21).
- **`core` sigue sin publicar nada** más que sus respuestas. El `pub.allow` de su plantilla queda declarado por forma, no porque haga falta.

#### Testing

- **Los tests existentes de `core` tienen que pasar sin cambios en sus aserciones** (CA-6). Es el criterio que verifica que el rename y la migración a micro no cambiaron comportamiento, y es posible **porque los tests entran por el despachador** (`tests/helpers/dispatch.ts`), no por el bus. Si un test hubiera que tocarlo, es señal de que se cambió algo que el REQ declara intacto.
- **Pero el helper sí se toca, y no contradice CA-6.** `tests/helpers/dispatch.ts:21` arma el subject a mano con `SERVICE_NAME` en vez de llamar a `commandSubject()`. Hay que repuntarlo — es el único lugar del repo que viola RF-18, y `SERVICE_NAME` queda `@deprecated`. **Un helper no es una aserción:** CA-6 se sigue cumpliendo, y el cambio hace que la gramática deje de estar duplicada donde podía divergir en silencio.
- **`core/.env.test:16` define `NATS_SERVICE_NAME=gestion`.** Si se saca la variable del código sin sacarla de acá queda definida y sin uso; si se saca de acá antes de repuntar el helper, los tests corren con el default. Van en el mismo cambio.
- **Lo nuevo a cubrir es la capa que reemplaza a `consumer.ts`**, y se puede testear sin bus: la derivación patrón -> `endpointName`/`endpointSubject` para los 20 patrones, y **la detección de subjects duplicados** (CA-15), que es una función pura sobre una lista.
- **`packages/nats-protocol` no tiene tests, ni carpeta donde ponerlos.** Es el paquete con más impacto del REQ y su superficie crece de 12 a 18 símbolos sin una sola prueba hoy — tampoco de `hashUserId`/`inboxPrefix`, que son los que **tienen que dar exactamente lo mismo que el auth-callout**. `endpointName()` y `endpointSubject()` son funciones puras: son la oportunidad barata de abrir esa carpeta. No es un requisito del REQ; es la recomendación que sale de mirar el estado real.
- **CA-11 es el test que más importa y el que menos parece necesario:** un alta que funciona **después** de que el módulo de consultas abrió su conexión. Es la única verificación de que los modelos no se reasignaron.
- **CA-10 necesita el rol real**, no un mock: es una garantía de Postgres. Encaja con ADR-013 (tests contra base real) y con el `setup-env.ts` que ya levanta un PostgreSQL efímero (`POSTGRES_DB=gestionTest`) — hay que crear el rol de solo lectura en ese setup.
- **El orden de carga de `.mocharc.json` condiciona el módulo nuevo:** `src/models/index.ts` construye su Sequelize **al importarse** (línea 17, no dentro de una función), y `read.ts` va a hacer lo mismo. `tests/setup-env.ts` tiene que tener las `POSTGRESQL_READ_*` puestas antes de que cualquier test importe `src/`. Es la misma trampa que la convención ya documenta, ahora con un segundo módulo.
- **`FakeBus implements Bus` y no compila al sumar `query()`.** No es una decisión de estilo: `api/tests/mocks/bus.ts:35` declara la implementación explícita, así que ampliar la interfaz **rompe el build de los tests** hasta que lo implemente. Lo bueno: `FakeBus` ya construye el subject con `commandSubject()` (`:93`), así que **sigue el rename sin tocarse**. Lo que hay que decidir es si `query()` despacha contra un `QueryDispatcher` real (como hace hoy con los comandos, cargando `core/src` por `require`) o rechaza explícitamente — **sin contrato de consultas, rechazar explícitamente es lo honesto**; dejarlo sin implementar haría fallar los tests por `TypeError` en vez de por la razón real.
- **Los tests del 503 de la api hay que revisarlos uno por uno.** Hay al menos 8 archivos que afirman 503 sobre un bus caído (`attachments-post`, `attachments-preview`, `attachments-download`, `attachments-delete`, `opus-attachments-post`, `projects-post`, `clients-post`, `clients-patch`). Según cómo el `FakeBus` simule la falla —`failWith(error)` genérico— algunos van a **seguir esperando 503** y otros tendrán que pasar a 504. **Es el único lugar donde este REQ obliga a cambiar aserciones existentes**, y es en la api, no en `core`: CA-6 protege a `core`, no al `api`.

#### Impacto en UX

**`ux_review: required`, por un solo motivo y bien acotado: hay un mensaje nuevo que un usuario va a leer.**

Ningún servicio `type: frontend` está en "Servicios Afectados", no hay pantalla nueva, ni navegación nueva, ni entidad de dominio nueva, ni flujo de usuario alterado. Por casi todos los criterios esto sería `not-applicable`. Lo que lo mueve a `required` es RF-16 / CA-9: **la api empieza a devolver un estado de error que antes no existía**, con copy propio —`La operación tardó demasiado`— en un caso que hasta ahora decía `El servicio no está disponible en este momento`.

Eso es contenido de producto, no plumbing: los dos frontends **muestran el `message` del cuerpo tal cual**, así que el texto que se elija acá es literalmente lo que ve la persona.

**Lo que está verificado y no hace falta revisar:**

- **Ningún frontend necesita cambios de código.** `web/src/lib/axios.ts:41-49` y `opus-web/src/lib/axios.ts:26-30` normalizan cualquier `{code,message}` con un default y propagan `message`; solo el 401 tiene rama propia. No hay `switch` por código en la capa de red que haya que ampliar.
- **No hay pantalla, overlay ni flujo nuevo.** El error aparece donde ya aparecen los errores de mutación de hoy.

**Lo que la revisión UX debería decidir, y es poco:**

1. **El copy de los dos mensajes.** Ahora que son dos casos distinguibles, ¿el texto los distingue de forma útil para quien lo lee? "El servicio no está disponible" y "La operación tardó demasiado" son buenos candidatos, pero conviene confirmar que ninguno sugiera reintentar cuando reintentar puede **duplicar** —los comandos no son idempotentes (ADR-002)— y que el de timeout no afirme que la operación **no** ocurrió, porque puede haber ocurrido.
2. **Si el estado de error del timeout merece tratamiento distinto** en las pantallas donde más va a aparecer: la carga de horas y la creación de requisitos desde el portal.
3. **Una inconsistencia previa que conviene resolver de paso:** los flujos documentan el cuerpo como `{ code: bus_unavailable }` y la api emite `service_unavailable`. Ver "Flujos Afectados".

**Un dato técnico que la revisión UX tiene que conocer:** `opus-web` fija un timeout **propio de 10 s** en su cliente HTTP (`opus-web/src/lib/axios.ts:18,52`). Con `NATS_REQUEST_TIMEOUT_MS`=5000 el 504 llega holgado y se muestra bien. Pero si algún día un endpoint de la api usa `bus.query()` con `NATS_QUERY_TIMEOUT_MS`=10000, los dos timeouts **empatan** y el usuario vería el error genérico de axios en vez del 504 con su mensaje. Hoy no hay ningún consumidor (Clarificaciones › Negocio), así que no es un problema — es una restricción a respetar cuando aparezca.

### Flujos Afectados

#### Flujos Existentes Modificados

Los seis flujos que citan el subject o el queue group **literal**. **Ninguno cambia su comportamiento observable**: cambia el token `{svc}`, no la semántica del comando ni el contrato de la respuesta.

- **`carga-de-horas`** (ref: `docs/flows/carga-de-horas.md`)
  - Línea 54: `entrega el comando (queue group gestion)` -> queue group **`jiku-commands`**
  - Línea 128: `{instance}.{user-id}.gestion.v1.worked-times.new` -> **`jiku-commands`**
  - Línea 216, fila 3 de la tabla de errores: `Timeout del bus (core caído o lento) | 503 | { code: bus_unavailable }` -> **se parte en dos filas**: no-responders -> 503 `service_unavailable`, timeout -> **504 `gateway_timeout`**. **Y de paso se corrige el código**: el flujo dice `bus_unavailable`, la api emite `service_unavailable` (`send-command.ts:29-38`). El flujo está mal hoy
  - Línea 243: la nota "el usuario ve un 503 de una operación que sí ocurrió" -> pasa a **504**

- **`alta-requisito-desde-portal`** (ref: `docs/flows/alta-requisito-desde-portal.md`)
  - Línea 174: subject -> **`jiku-commands`**
  - Línea 270, fila 5: mismo desdoblamiento 503/504 y misma corrección de `bus_unavailable`

- **`subida-de-archivos`** (ref: `docs/flows/subida-de-archivos.md`)
  - Líneas 172 y 202: los dos subjects (canal api y canal externo) -> **`jiku-commands`**

- **`adjuntos`** (`docs/flows/adjuntos.md`) — `status: Deprecated`. Menciona comandos y replies en prosa (`:44`, `:217`, `:222`, `:290`) pero **no cita ningún subject ni el queue group**. Nada que actualizar.

#### Nuevos Flujos

**Ninguno, y es una decisión, no un olvido.**

Un flujo documenta una interacción cross-service de punta a punta con **field names exactos** como contrato (`.claude/templates/flow-tmpl.yaml`, y la regla del rol: *"Field names in flows MUST match exactly with OpenAPI specs and DBML schemas"*). `jiku-queries` no tiene todavía ni payload de request ni envelope de respuesta ni campos por recurso — **RF-10 los deja fuera de alcance**. Un flujo escrito ahora tendría que inventar exactamente lo que el REQ declaró no definir.

**El flujo de consultas se escribe con su contrato**, en el requerimiento que lo defina. Lo que este REQ deja listo para ese momento es el subject, el queue group, la conexión de lectura y los permisos.

**El arranque y el apagado del proceso** (Escenarios 1 y 5) tampoco son flujos de `docs/flows/`: no son interacciones cross-service disparadas por una acción de usuario, son ciclo de vida de un servicio. Su lugar es la convención `bus-consumer` reescrita (RF-24).

El REQ toca cuatro componentes y un contrato que los une. El criterio del split no es el tamaño sino **qué puede verificarse por separado**:

- **La story 1 aísla el cambio de contrato.** Es el único cambio que rompe a todos los callers a la vez, y no tiene lógica: son nombres, helpers y permisos. Aislarla permite verificar `CA-6` (comportamiento idéntico), `CA-13` y `CA-14` (permisos) **sin** que la migración a micro esté de por medio.

  Y es la razón de la decisión de diseño más discutible del split: **la story 1 no borra nada.** Con `SERVICE_NAME` como alias de `COMMAND_SERVICE`, el `consumer.ts` actual **se renombra solo, sin tocar una línea de `core`** — y esto es verificable, no una esperanza: `consumer.ts`:69-70 hace `subscribe(subscriptionSubject(), { queue: SERVICE_NAME })`, así que **el subject y el queue group salen los dos del mismo símbolo**. Aliasarlo mueve las dos cosas a la vez, que es exactamente lo que hace falta. El producto queda funcionando end-to-end al terminar la story.

  Es expand/contract clásico: la story 2 hace la contracción cuando el último caller muere. La alternativa —borrar en la story 1— dejaría el build de `core` roto a mitad del REQ, y RF-17 se cumple igual al final.
- **La story 2 es un reemplazo de la capa de conexión con comportamiento invariante.** Su criterio de éxito es negativo y muy fuerte: **los tests existentes pasan sin cambios en sus aserciones** (CA-6). Eso solo es afirmable si no viene mezclada con funcionalidad nueva. Es también donde entra la verificación de subjects duplicados, que es la mitigación del bug silencioso del REQ.
- **La story 3 es la única que introduce riesgo nuevo**, y conviene que sea la única: la segunda conexión a la base dentro del mismo proceso, con la trampa de la reasignación de modelos. Su test más importante (CA-11: un alta sigue funcionando después de que las consultas abrieron su conexión) **solo tiene sentido si el estado previo ya está verificado** por la story 2. Separarla es lo que hace que, si algo se rompe, se sepa qué lo rompió.
- **La story 4 es del otro servicio y no depende de las de `core`.** `query()` compila y publica sin nadie del otro lado, y la separación 503/504 es una rama en un `catch` de la api. Depende **solo** de la story 1. **Y es la única story que cambia aserciones de tests existentes:** CA-6 protege a `core`, no al `api`, y hay ~8 archivos que hoy afirman 503 sobre un bus caído. Que ese trabajo esté concentrado en una story —y no repartido— es parte del valor del split.

**Lo que el split NO separa, a propósito:** el auth-callout no es una story propia. Es configuración del mismo contrato que define la story 1 —los mismos nombres, escritos en otro archivo— y separarlos produciría una ventana donde el código publica en un subject que el callout no autoriza, o al revés. Van juntos porque **tienen que salir juntos**.

**Orden de implementación sugerido:**

1. **Story 1** — Todo lo demás nombra contra ella. Nada compila con los helpers nuevos hasta que existan, y ningún deploy conecta si el callout no autoriza el subject nuevo. Es la única con orden forzado.
2. **Story 2** — El host es la pieza que abre la conexión y registra servicios; `jiku-queries` no tiene dónde montarse sin él. Va antes que la 3 por dependencia estructural, no por tamaño.
3. **Story 4** — **en paralelo con la 2 y la 3**, por otro desarrollador. Es del `api`, depende solo de la 1, y no comparte ni un archivo con las de `core`. Ponerla tercera en la lista es orden de lectura, no de ejecución.
4. **Story 3** — Última porque es la que más riesgo agrega y la que se verifica contra un estado previo ya sano. Cierra RF-5 a RF-10 y completa CA-1 (los **dos** servicios en `nats micro ls`).

**Planificación, no split.** En monorepo `/service-planify-story` genera un plan por servicio (`docs/story-plans/S-XXX.{service_name}.{title}.md`), así que la story 1 va a producir **dos** planes —`packages/nats-protocol` y `deploy`— y la story 2 otros dos —`core` y `packages/nats-protocol`—, ejecutables en paralelo. Es el mismo patrón que S-004 (`api` + `core`) en REQ-001.

**Precondición de despliegue, no de desarrollo.** El estado final del auth-callout tiene que estar aplicado **antes o junto con** la story 1: es lo que autoriza el subject nuevo. El **plan de corte** —callout permisivo transitorio, reinicio coordinado de `api` y `core`, ventana de indisponibilidad de escrituras, rollback— **quedó explícitamente fuera de alcance** (Clarificaciones › Alcance) y **no está planificado en ninguna story**. Lo que sí queda entregado es la configuración final. La coordinación del corte es trabajo de operación, fuera de horario, y el REQ lo declara así.

**Fuera de alcance de las cuatro stories, de forma explícita:**

- **El contrato de las consultas** (RF-10): filtros, paginación, campos, payloads de request y respuesta, y el contrato campo por campo de los tres recursos. Es un requerimiento posterior — y su documento de análisis (`bus-api-consultas.md`) ya existe sin trackear en la raíz del monorepo.
- **JetStream, colas, persistencia, reintento e idempotencia** (RF-13). Sigue siendo request/reply puro (ADR-002) y sigue siendo el contenido de FG-3.
- **Migrar las lecturas HTTP de la api al bus** (RF-14). La api sigue leyendo Postgres directo (ADR-001).
- **`NATS_OPERATOR_NAME`** (RF-22). Renombrarlo obliga a regenerar el árbol de creds.
- **Los ADRs, las convenciones y el PRD** — se tramitan por `/product-change-technical-definition`, como en REQ-002. La excepción es `docs/apis/core.yaml`, que se actualiza durante la creación de las stories.

## Revisión UX

**Fecha:** 2026-08-23
**Superficies afectadas:** `web`, `opus-web`

**Viewports de las superficies afectadas:** `web`: desktop (único) · `opus-web`: desktop (primario), mobile

**Cómo se acotó el delta.** Este REQ no agrega ni quita ninguna capacidad de usuario: cambia el
token `{svc}` del subject, que no es observable, y **separa una falla en dos** (RF-16, CA-8, CA-9).
Eso último **sí** es observable, y es el único impacto UX del requerimiento. El REQ deja `web` y
`opus-web` sin cambios de código a propósito: los dos mensajes viajan en el cuerpo del error y salen
por los toasts y los `role="alert"` que ya existen. Por eso **no hay ninguna pantalla nueva, ningún
overlay nuevo, ningún bloque nuevo y ninguna transición nueva** — diseñar un `alert` propio para el
timeout habría inventado alcance que el REQ declaró fuera.

Lo que sí cambia, y era invisible en la documentación hasta ahora, es **la recuperación**:

| Falla | Mensaje | Qué pasó | Qué debería hacer el usuario |
|---|---|---|---|
| `503 service_unavailable` | *"El servicio no está disponible en este momento"* | La operación **no ocurrió** | Reintentar es seguro |
| `504 gateway_timeout` | *"La operación tardó demasiado"* | **Pudo haber ocurrido** | Verificar antes de reintentar — el reintento a ciegas duplica |

**El criterio de selección de pantallas es la idempotencia**, no la lista de escrituras. Toda
escritura del producto pasa por el bus (salvo una, ver abajo), pero el desdoblamiento solo cambia lo
que el usuario debería hacer cuando **repetir la acción crea algo nuevo**. En las escrituras
idempotentes —editar una entidad, cambiar estado o prioridad inline, borrar, suscribirse— reintentar
un 504 es inofensivo y no había nada que documentar. Las 8 pantallas modificadas son exactamente las
**no idempotentes**.

### Respuesta a los tres puntos que el diseño técnico dejó para la revisión

El diseño técnico (Consideraciones › Impacto en UX) dejó tres decisiones. Se cierran acá:

1. **El copy de los dos mensajes: se aprueban los dos como están.** `"El servicio no está
   disponible en este momento"` y `"La operación tardó demasiado"` cumplen las dos condiciones que
   el diseño técnico pedía verificar: **ninguno invita a reintentar** (ninguno dice "intentá de
   nuevo", que sería el error grave dado que los comandos no son idempotentes) y **el de timeout no
   afirma que la operación no ocurrió** — dice cuánto tardó, no qué pasó, que es exactamente la
   incertidumbre real. Lo que **no** hacen es guiar la recuperación: ninguno dice "revisá antes de
   repetir". Se descartó agregarlo porque el mensaje del timeout no sabe qué operación falló y un
   texto genérico *"verificá si se guardó"* pegado a cualquier acción envejece mal. La guía queda
   documentada por pantalla (columna "Qué debería hacer el usuario") para el requerimiento que sí
   pueda tocar los frontends.
2. **El estado de error del timeout no recibe tratamiento distinto, y es un descarte explícito.**
   Las dos pantallas que el diseño técnico señalaba —`carga-horas` y el alta desde el portal— son
   efectivamente las dos donde más va a aparecer y donde más cuesta, y las dos están en el delta.
   Pero darles un estado propio significa diseñar UI, y el REQ deja `web` y `opus-web` sin cambios
   (RF-16, CA-9). Se documentó la consecuencia en las dos, con el hallazgo de que en el portal el
   caso es peor de lo que el diseño técnico suponía: **el modal de alta no muestra ningún error**,
   ni el viejo ni el nuevo, así que ahí el desdoblamiento no mejora nada para el cliente.
3. **La inconsistencia `bus_unavailable` / `service_unavailable` queda resuelta del lado UX.** El
   único lugar de la documentación UX que citaba el código era `web/user-flows.md` (flujo 1), y
   decía solo *"503"*, sin código: ahora nombra `service_unavailable` y `gateway_timeout`, los dos
   que la api realmente emite. La corrección en `docs/flows/` es de los flujos de sistema y viaja
   por las stories, como el REQ ya define en "Flujos Afectados".

**Y una restricción del diseño técnico que la UX confirma y hereda:** `opus-web` fija un timeout
propio de 10 s en su cliente HTTP. Con `NATS_REQUEST_TIMEOUT_MS`=5000 el 504 llega holgado y se
muestra. Si algún día un endpoint de la api usa `bus.query()` con `NATS_QUERY_TIMEOUT_MS`=10000, los
dos empatan y el cliente vería el error genérico de axios **en vez** del mensaje del cuerpo — es
decir, el portal perdería justamente el texto que este REQ agrega. Hoy no hay consumidor, así que no
es un problema; queda anotado como condición a respetar en el REQ que defina el contrato de
consultas.

### Hallazgos para las stories

Tres cosas que la revisión encontró y que **no son alcance de este REQ**, anotadas donde
`/service-planify-story` las va a leer:

1. **`alta-proyecto` descarta el `message` de la api** y muestra un literal fijo. Con una falla
   genérica no importaba; con dos mensajes de recuperación opuesta, es pérdida de información. Es
   código de `web`, que el REQ deja sin tocar (RF-16).
2. **Los toasts de `web` cierran en 2 segundos** (`autoClose: 2000`). El mensaje que distingue "no
   ocurrió" de "pudo haber ocurrido" es ahora la única guía de recuperación, y se va antes de que se
   lea.
3. **La story 4 cambia aserciones de tests de la api, no de los frontends.** `web` y `opus-web` no
   tienen ni un test ni una línea que enumere códigos de error (`axios.ts` normaliza cualquier
   `{code,message}`), así que la separación 503/504 no les rompe nada — lo que confirma el
   "**Ninguno**, verificado" de Servicios Afectados desde el lado de la UX.
