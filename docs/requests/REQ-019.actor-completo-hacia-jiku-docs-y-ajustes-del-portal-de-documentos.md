# REQ-019: Actor completo hacia jiku-docs y ajustes del portal de documentos (hallazgos e2e de REQ-016/REQ-017)

## Requerimiento Original

> Hallazgos de la prueba end-to-end en navegador de la documentación (REQ-016/REQ-017). La decisión
> de referencia es D-11 de `conectores/jiku-docs/docs/decisiones-integracion.md`.
>
> 1. **La api manda a jiku-docs el `actor` completo.**
>    - Hoy `api/lib/modules/client.ts` manda `actor: { id }` (DD-1).
>    - Core actualiza los roles en `users` solo con comandos de core o con conexión directa a NATS.
>      Por eso un usuario web que solo lee queda con roles viejos o sin fila, y jiku-docs le responde
>      `caller_not_authorized`. Se reprodujo con un externo real en opus-web.
>    - Pedido: mandar el mismo `actor` que recibe core (`buildActor(req)`:
>      `{ id, roles, name?, username?, email? }`, con roles del token web verificado) en todas las
>      llamadas a módulos que van en nombre de una persona.
>    - Las llamadas sin `actor` (las rutas públicas `/p/docs/*`) no cambian.
>    - Actualizá DD-1/ADR-015 y los tests.
>    - jiku-docs ya acepta ese `actor` (contrato `Actor` = `{ id, roles, name?, username?, email? }`).
>      Lo cambia otra sesión en el repo jiku-docs, así que no toques ese repo.
> 2. **opus-web no enlaza a la web interna.**
>    - `opus-web/src/features/docs/utils/docsUrlTransform.ts` deja pasar cualquier `http(s)`. Por eso
>      un enlace entre documentos (`{JIKU_WEB_URL}/docs/{ULID}` o `/docs/{ULID}`) le muestra al
>      externo un link a `localhost:3000/docs/...`.
>    - Pedido: mostrar esos enlaces como texto, igual que en los links compartidos. Con test.
> 3. **opus-web distingue errores en la sección de documentos.**
>    - Hoy `DocsSection` muestra "no disponible" ante cualquier error.
>    - Pedido: un 403 o `caller_not_authorized` tiene que mostrar un mensaje propio, no el de
>      "módulo caído". Con test.
>
> Restricción explícita: la api **no** debe aceptar tokens de machine users ni leer claims de roles
> específicos de proyecto. Ese cambio fue rechazado por el dueño. No toques `getRolesFromToken`.

## Clarificaciones

### Supuestos (modo automático)

El dueño del producto delegó las decisiones de detalle; no se hicieron preguntas. Cada ambigüedad se
resolvió así:

- **[Qué `actor` se manda]:** → **Supuesto tomado:** exactamente el que devuelve `buildActor(req)`,
  sin campos extra ni transformaciones. `roles` sale de `req.decodedTokenRoles` (token web ya
  verificado); sin claim de roles va `[]`. `getRolesFromToken` no se toca.
- **[Qué pasa si no hay identidad verificada en una llamada "en nombre de una persona"]:** →
  **Supuesto tomado:** se mantiene el comportamiento actual de fallar cerrado (DD-9): sin `id` del
  token no se publica nada. Nunca se cae a la llamada sin `actor`, que jiku-docs trata como el
  propio servicio.
- **[Si el payload del handler trae un `actor`]:** → **Supuesto tomado:** igual que hoy, gana el del
  token (se pisa entero, no se mezcla campo a campo).
- **[Rutas sin `actor`]:** → **Supuesto tomado:** `shares.resolve` y `shares.attachment` (rutas
  públicas `/p/docs/*`) siguen sin `actor`, sin cambios.
- **[Qué es un "enlace entre documentos" en opus-web]:** → **Supuesto tomado:** cualquier URL cuyo
  path sea `/docs/{ULID}` (con o sin `?`/`#` al final), relativa o absoluta con cualquier host
  `http(s)`. No se compara contra `JIKU_WEB_URL`: opus-web no tiene por qué conocer el host de la web
  interna, y el criterio por path es el mismo que ya se usa para adjuntos (DD-15). Los adjuntos
  (`/docs/attachments/{ULID}`) conservan su reescritura actual.
- **[Cómo se muestra "como texto"]:** → **Supuesto tomado:** el texto visible del enlace se conserva
  y no se renderiza ningún `<a>` navegable (ni con `href` vacío): es el mismo resultado que da el
  link compartido, donde jiku-docs deja esos enlaces como texto plano.
- **[Enlaces externos legítimos]:** → **Supuesto tomado:** los demás `http(s)` y `mailto` siguen
  pasando como hoy.
- **[Qué errores cuentan como "sin permiso" en `DocsSection`]:** → **Supuesto tomado:** status HTTP
  403 o `code` `caller_not_authorized`. Muestran un mensaje propio de "sin acceso a la
  documentación de este proyecto", no el aviso de módulo no disponible. `module_not_installed`
  sigue sin renderizar nada; cualquier otro error sigue mostrando "no disponible".
- **[Alcance del mensaje propio]:** → **Supuesto tomado:** aplica a `DocsSection` (tablero y
  detalle de requisito). Si el visor de un documento del portal tiene el mismo tratamiento genérico
  ante 403, se alinea con el mismo mensaje cuando el cambio sea trivial; si no, queda anotado como
  pendiente.
- **[Cambios en web interna]:** → **Supuesto tomado:** ninguno. La web interna sí debe enlazar entre
  documentos.
- **[Contrato HTTP de la api]:** → **Supuesto tomado:** no cambia. El cambio es en el payload del
  bus hacia jiku-docs, cuyo contrato ya lo admite.

## Requerimientos Funcionales

1. Toda llamada de la api a un módulo en nombre de una persona lleva como `actor` el resultado de
   `buildActor(req)`: `{ id, roles, name?, username?, email? }`, con `roles` del token web
   verificado.
2. Si el payload trae un `actor`, el del token lo reemplaza entero.
3. Sin identidad verificada, la api no publica la llamada (falla cerrado, como hoy).
4. `shares.resolve` y `shares.attachment` siguen sin `actor`.
5. La api no acepta tokens de machine users ni lee claims de roles por proyecto; `getRolesFromToken`
   no cambia.
6. DD-1 (REQ-016) y ADR-015 se actualizan al contrato nuevo.
7. En el visor de documentos de opus-web, todo enlace cuyo path sea `/docs/{ULID}` (relativo o con
   cualquier host) se muestra como texto, sin link navegable.
8. Los adjuntos, los demás `http(s)` y `mailto` conservan el comportamiento actual.
9. `DocsSection` muestra un mensaje propio de "sin acceso" ante un 403 o `caller_not_authorized`,
   distinto del de módulo no disponible.

## Criterios de Aceptación

1. DADO un usuario web autenticado con roles en su token
   CUANDO la api llama a jiku-docs en su nombre (por ejemplo `documents.list`)
   ENTONCES el payload publicado lleva `actor` = `{ id, roles, name?, username?, email? }` igual al
   que la api manda a core para ese mismo request.

2. DADO un token sin claim de roles
   CUANDO la api llama a jiku-docs en nombre de esa persona
   ENTONCES el `actor` lleva `roles: []`.

3. DADO un handler que arma un payload con su propio `actor`
   CUANDO se publica la llamada al módulo
   ENTONCES el `actor` publicado es exactamente el del token, sin campos del original.

4. DADO un request sin identidad verificada
   CUANDO un handler intenta llamar a jiku-docs en nombre de una persona
   ENTONCES no se publica nada en el bus y la api responde el error de autenticación actual.

5. DADO un visitante de un link compartido `/p/docs/{token}`
   CUANDO la api llama a `shares.resolve` o `shares.attachment`
   ENTONCES el payload no lleva `actor`.

6. DADO un documento abierto en opus-web con un enlace `http://localhost:3000/docs/{ULID}`
   CUANDO se renderiza
   ENTONCES se ve el texto del enlace y no hay ningún `<a>` navegable hacia esa URL.

7. DADO un documento con un enlace relativo `/docs/{ULID}` o `/docs/{ULID}#seccion`
   CUANDO se renderiza en opus-web
   ENTONCES se muestra como texto.

8. DADO un documento con un adjunto `/docs/attachments/{ULID}`, un enlace `https://ejemplo.com` y un
   `mailto:`
   CUANDO se renderiza en opus-web
   ENTONCES el adjunto sigue reescrito al proxy propio y los otros dos siguen siendo enlaces.

9. DADO un externo sin acceso a la documentación del proyecto
   CUANDO `DocsSection` recibe un 403 o `caller_not_authorized`
   ENTONCES muestra el mensaje propio de "sin acceso" y no el de "no disponible".

10. DADO el módulo caído o un error 5xx/de red
    CUANDO `DocsSection` carga
    ENTONCES sigue mostrando el aviso de "no disponible".

11. DADO `module_not_installed`
    CUANDO `DocsSection` carga
    ENTONCES no renderiza nada (sin cambios).

### Decisiones de diseño

- **DD-1 — `actor` = `buildActor(res.req)` sin transformar.** El embudo reemplaza
  `body = { ...payload, actor: { id } }` por `body = { ...payload, actor }`, donde
  `actor = buildActor(res.req)`. Es el mismo sobre que recibe core (`withActor`,
  `reusable-code/api/utils.md` línea 180-182), así que hay **una sola fuente de identidad** para los dos
  destinos. No se agregan campos (ni `identityType`, ver JSDoc de `buildActor`).
  - **Se sigue sin reusar `withActor`**: `withActor` sin identidad devuelve el payload sin `actor`
    (falla abierto, correcto para core), y para jiku-docs un llamado sin `actor` es el propio
    servicio. La razón cambia (ya no es el `invalid_fields`), pero la conclusión se mantiene.
- **DD-2 — Falla cerrado, igual que hoy.** Sin `buildActor(res.req)` → 401
  `{ code: 'unauthorized', message: 'Unauthorized' }` sin publicar (ADR-015, DD-9).
- **DD-3 — Gana el del token, entero.** El `actor` va después del spread: reemplaza cualquier
  `actor` del payload sin mezcla campo a campo.
- **DD-4 — Sin cambios en las rutas públicas ni en `anonymous`.** `public-share.ts` usa
  `sendToModule` sin `actor`; la opción `anonymous` sigue quitando el `actor` (TS-26 de S-077).
- **DD-5 — Sin cambios de identidad.** `getRolesFromToken` no se toca; los roles salen de
  `req.decodedTokenRoles` (token web verificado). La api no acepta tokens de machine users ni lee
  claims de roles por proyecto.
- **DD-6 — Enlace entre documentos en opus-web = path `/docs/{ULID}`.** Nueva regex en
  `docsUrlTransform`, evaluada **después** de la de adjuntos:
  `/^(?:https?:\/\/[^/?#\s]+)?\/docs\/([0-9A-HJKMNP-TV-Z]{26})(?:[?#].*)?$/` → devuelve `''`.
  No se compara con `JIKU_WEB_URL`. Hoy la variante relativa ya se vacía (falla `new URL`), pero el
  `a` de `DocumentMarkdown` sigue renderizando un `<a target="_blank">` sin `href`.
- **DD-7 — "Como texto" = sin `<a>`.** El override `a` de `DocumentMarkdown` renderiza un
  fragmento con los `children` cuando `href` es vacío. Alcanza también a los demás enlaces vaciados
  (`javascript:`, `data:`, `//host`), que hoy quedan como `<a>` sin `href`: es la misma regla y es más
  seguro. El test existente "mal" (`not.toHaveAttribute('href')`) se ajusta a "no hay `<a>`".
- **DD-8 — "Sin acceso" en `DocsSection`.** Con `query.isError`:
  1. `code === 'module_not_installed'` → no renderiza nada (igual que hoy);
  2. `status === 403` **o** `code === 'caller_not_authorized'` → `DocsAlert` con la constante nueva
     `MSG_DOCS_FORBIDDEN` = *"No tenés acceso a la documentación de este proyecto."*;
  3. cualquier otro → `MSG_DOCS_UNAVAILABLE` (igual que hoy).
  `ApiError` ya trae `code` y `status` (`opus-web/src/lib/axios.ts`). Un 403 local de la api
  (`validateProjectPermissions`) cae también en "sin acceso", que es correcto.
- **DD-9 — El visor del documento no cambia.** `classifyDocumentError` ya trata 403 como
  `not_found` ("no existe o no compartido", DD-3 de REQ-016) a propósito: no es el tratamiento
  genérico que pide el punto 3, así que no se alinea. Queda anotado, sin pendiente.

### Flujo de Interacción

#### Escenario: un externo abre el tablero del portal (CA-1, CA-9)

**Trigger:** el externo entra a `/projects/{id}` en opus-web.

1. **opus-web** — `DocsSection` → `useDocuments` → `GET /api/opus/docs/documents?projectId={id}`.
2. **api** — cadena actual (`requireModule` → `hasAnyRole(['external-user','admin','user'])` →
   forma → `loadDocsScope` → `validateProjectPermissions` → handler, `filter.visibility: 'public'`
   forzado). El handler llama `moduleQuery(res, 'docs', 'documents.list', {...})`.
3. **api / `call()`** — `respondIfModuleNotReady`; `actor = buildActor(res.req)`; sin `actor` → 401
   sin publicar; si no, publica `{ ...payload, actor }` con
   `actor = { id, roles: ['external-user'], name?, username?, email? }`.
4. **jiku-docs** — clasifica con `actor.roles` (`external-user` → `person-external`) sin depender de
   la fila de `users`; consulta `project-permissions` a core.
5. **api** — `success` → 200 con la página; `failure` → mapa de `docs/errors.ts`
   (`caller_not_authorized` → 403 `{ code, message, details? }`).
6. **opus-web** — 200 → lista; 403/`caller_not_authorized` → "No tenés acceso a la documentación de
   este proyecto."; `module_not_installed` → nada; otro → "no disponible".

**Manejo de errores:** sin identidad → 401 (sin publicar); módulo no instalado → 404
`module_not_installed`; caído → 503 `module_unavailable`; timeout → 504 `gateway_timeout`.

#### Escenario: enlace entre documentos en el visor de opus-web (CA-6 a CA-8)

1. `DocumentMarkdown` → `urlTransform(url)`:
   - `/docs/attachments/{ULID}` (con o sin host) → `/api/docs/documents/{documentId}/attachments/{ULID}` (sin cambios);
   - `/docs/{ULID}` (con o sin host, con `?`/`#`) → `''` (**nuevo**);
   - `http(s)`/`mailto` → pasa; resto → `''`.
2. Override `a`: `href` vacío → `<>{children}</>` (**nuevo**); si no, `<a href target=_blank rel>`.

### Consideraciones Técnicas

#### Riesgos
- **Orden de despliegue con jiku-docs (el principal).** Mientras jiku-docs tenga
  `Actor` con `additionalProperties: false` y solo `id`, **toda** llamada de la api con `roles`
  responde `invalid_fields` (400) y la documentación deja de funcionar en web y opus-web. La api con
  este cambio requiere la versión de jiku-docs que implementa D-11. Mitigación: dejarlo escrito en
  ADR-015 y, en la release, en *Notes for existing installations* del CHANGELOG ("actualizar jiku-docs
  antes o junto con la api"). No se agrega compatibilidad hacia atrás: el protocolo de módulos es v1
  y jiku-docs ya acepta el sobre nuevo.
- **Datos personales en el bus.** `name`, `username` y `email` viajan ahora a jiku-docs. Ya viajan a
  core por el mismo bus; jiku-docs los recibe solo del publicador de confianza (la api, por
  `JIKU_API_USER_ID`). El embudo sigue sin loguear `payload`.
- **Tests de rutas.** ~43 aserciones `actor: { id: ... }` en `api/tests/routes/*` cambian a
  `{ id, roles: [...] }` según el token del mock. Conviene un helper (p. ej. `expectedActor(token)`)
  en lugar de literales repetidos.

#### Dependencias
- jiku-docs con D-11 desplegado (externo, otra sesión).
- Las dos stories del split son independientes entre sí.

#### Performance
- Sin impacto: unos bytes más por mensaje.

#### Seguridad
- La identidad sigue saliendo solo del claim verificado (ADR-007); `roles: []` no autoriza nada
  (ADR-008). Falla cerrado sin identidad (DD-2). No cambia `getRolesFromToken`.
- opus-web deja de exponer al externo URLs de la web interna.
