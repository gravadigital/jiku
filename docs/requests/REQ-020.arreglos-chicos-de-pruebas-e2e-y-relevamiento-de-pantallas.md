# REQ-020: Arreglos chicos de las pruebas e2e y del relevamiento de pantallas (CORS, log de core, accesibilidad, vencimientos y acceso en opus-web)

## Requerimiento Original

> Arreglos chicos encontrados en las pruebas end-to-end y en el relevamiento de pantallas. Es el
> grupo P-2 de `/home/lautaro/Documentos/proyectos/interno/gestor/conectores/jiku-docs/docs/backlog-jiku-web.md`,
> ítems 3, 4, 14, 15 y 18.
>
> 1. **CORS solo bajo `/api`.**
>    - Hoy `api/app.ts` aplica `app.use(cors())` a todo, y `/p/docs/*` responde
>      `Access-Control-Allow-Origin: *`. Así, cualquier origen puede leer por JavaScript el HTML de
>      un link compartido si conoce el token.
>    - Pedido: montar CORS solo donde lo necesitan los frontends. Las rutas públicas `/p/docs/*` no
>      emiten cabeceras CORS. Con test.
>    - **No toques la autenticación ni `getRolesFromToken`:** la api no acepta tokens de machine
>      users, por decisión del dueño.
> 2. **Warning en cada adjunto de docs.**
>    - `core/src/commands/resolve-actor.ts` registra con nivel `warn` "comando publicado por un
>      caller externo" en cada `files.request-upload` de jiku-docs, que es el camino normal según
>      D-3.
>    - Pedido: bajarlo a `debug` para callers de clase `connector` y mantener el `warn` donde
>      corresponda.
> 3. **Pills del detalle de requisito.** En la web, las pills de estado, tipo y prioridad se
>    anuncian las tres como "Estado: …" en lectores de pantalla. Cada una tiene que anunciar su
>    propio atributo. Con test.
> 4. **"Vencido hace: 32666 día(s)" en el listado de tareas de la web.** Una fecha nula o inválida
>    produce ese texto. Pedido: no mostrar el vencimiento cuando la fecha es nula o inválida, y
>    revisar el cálculo. Con test.
> 5. **opus-web, externo que abre un requisito interno.** Hoy ve "Error al cargar el requisito"
>    con "Reintentar", sin header ni explicación. Pedido: un estado claro de "no disponible o sin
>    acceso", con navegación de vuelta al tablero, que no ofrezca reintentar algo que nunca va a
>    funcionar. Con test.

## Clarificaciones

### Supuestos (modo automático)

El dueño del producto delegó las decisiones de detalle; no se hicieron preguntas. Cada ambigüedad se
resolvió así:

- **[Dónde se monta CORS]:** → **Supuesto tomado:** solo bajo `/api` (que es donde llaman web y
  opus-web). Ninguna ruta fuera de `/api` (en particular `/p/docs/*`) emite
  `Access-Control-Allow-Origin` ni responde preflight CORS. La configuración de `cors()` no cambia
  (mismo comportamiento que hoy dentro de `/api`).
- **[Autenticación]:** → **Supuesto tomado:** no se toca. La api sigue sin aceptar tokens de machine
  users y `getRolesFromToken` no cambia.
- **[Qué es "clase `connector`" para el log de core]:** → **Supuesto tomado:** la misma clasificación
  de caller que ya usa core (S-030). Para un caller de clase `connector` la rama externa de
  `resolveActor` loguea en `debug`; para cualquier otro caller externo (no clasificado, desconocido)
  se mantiene el `warn`. El texto del mensaje, el valor devuelto y el criterio de no loguear el
  payload no cambian. La rama del `actor` verificado y la de la api siguen sin loguear nada.
- **[Qué anuncia cada pill]:** → **Supuesto tomado:** "Estado: …", "Tipo: …" y "Prioridad: …"
  respectivamente. El `Badge` editable recibe el nombre del atributo como prop con default
  "Estado", así los usos actuales que son de estado no cambian.
- **[Alcance del arreglo de las pills]:** → **Supuesto tomado:** cualquier otro uso del `Badge`
  editable que no sea de estado también pasa el nombre correcto si el cambio es trivial.
- **[Fecha nula o inválida en "Tareas"]:** → **Supuesto tomado:** si la fecha estimada de fin es
  nula, vacía o no parsea a una fecha válida, no se muestra texto de vencimiento ni se marca como
  cercana al vencimiento. Se revisa el cálculo de días para que no dependa de `new Date(null)` ni
  de fechas `Invalid Date`.
- **[Qué cuenta como "no disponible o sin acceso" en opus-web]:** → **Supuesto tomado:** 403, 404 o
  `code` de "sin permiso"/"no encontrado" que devuelva la api al cargar el requisito. Se muestra un
  estado con título y explicación ("El requisito no está disponible o no tenés acceso"), con un
  botón para volver al tablero del proyecto y **sin** "Reintentar". El header/layout del portal se
  mantiene visible.
- **[Otros errores en opus-web]:** → **Supuesto tomado:** errores de red o 5xx siguen ofreciendo
  "Reintentar", porque ahí sí puede funcionar.
- **[Página y modal]:** → **Supuesto tomado:** el tratamiento aplica a la página de detalle y al
  `RequirementDetailModal` de opus-web.

## Requerimientos Funcionales

1. La api aplica CORS solo a las rutas bajo `/api`. Las rutas públicas `/p/docs/*` no emiten
   cabeceras CORS.
2. La autenticación de la api y `getRolesFromToken` no cambian.
3. En core, la rama de caller externo de `resolveActor` loguea en `debug` cuando el caller es de
   clase `connector`, y en `warn` para cualquier otro caller externo.
4. En el detalle de requisito de la web, cada pill (estado, tipo, prioridad) se anuncia en lectores
   de pantalla con el nombre de su propio atributo.
5. En el listado de tareas de la web, una fecha estimada de fin nula o inválida no produce texto de
   vencimiento ni marca de "cerca del vencimiento".
6. En opus-web, un requisito que la api devuelve como no encontrado o sin permiso muestra un estado
   claro de "no disponible o sin acceso", con navegación de vuelta al tablero del proyecto y sin
   "Reintentar".
7. Los demás errores de carga del requisito en opus-web conservan "Reintentar".

## Criterios de Aceptación

1. DADO un request a una ruta pública `/p/docs/{token}` con cabecera `Origin`
   CUANDO la api responde
   ENTONCES la respuesta no lleva `Access-Control-Allow-Origin`.

2. DADO un preflight `OPTIONS` a `/p/docs/{token}`
   CUANDO la api responde
   ENTONCES no lleva cabeceras CORS.

3. DADO un request a una ruta bajo `/api` con cabecera `Origin`
   CUANDO la api responde
   ENTONCES lleva las mismas cabeceras CORS que hoy (incluido el preflight).

4. DADO un comando `files.request-upload` publicado por un caller de clase `connector` (jiku-docs)
   CUANDO core resuelve el actor
   ENTONCES el mensaje de caller externo se registra en `debug` y no en `warn`.

5. DADO un comando publicado por un caller externo que no es de clase `connector`
   CUANDO core resuelve el actor
   ENTONCES el mensaje se sigue registrando en `warn`.

6. DADO un comando con `actor` verificado o publicado por la api
   CUANDO core resuelve el actor
   ENTONCES no se registra ningún log (sin cambios).

7. DADO el detalle de un requisito en la web
   CUANDO un lector de pantalla recorre las pills
   ENTONCES anuncia "Estado: …", "Tipo: …" y "Prioridad: …" respectivamente.

8. DADO una tarea con fecha estimada de fin nula, vacía o inválida
   CUANDO se renderiza el listado de tareas
   ENTONCES no aparece texto "Vencido hace" ni "Falta", ni marca de cercanía al vencimiento.

9. DADO una tarea con fecha estimada de fin válida vencida hace 3 días y no cerrada
   CUANDO se renderiza el listado
   ENTONCES muestra "Vencido hace: 3 día(s)".

10. DADO un externo en opus-web que abre un requisito interno (la api responde 403 o 404)
    CUANDO carga la página o el modal de detalle
    ENTONCES ve un estado de "no disponible o sin acceso" con explicación, un botón para volver al
    tablero del proyecto y ningún botón "Reintentar".

11. DADO un error de red o 5xx al cargar el requisito en opus-web
    CUANDO se muestra el error
    ENTONCES sigue ofreciendo "Reintentar".
