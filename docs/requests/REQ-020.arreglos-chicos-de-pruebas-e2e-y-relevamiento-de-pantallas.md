# REQ-020: Arreglos chicos de las pruebas e2e y del relevamiento de pantallas (CORS, log de core, accesibilidad, vencimientos y acceso en opus-web)

## Requerimiento Original

> Arreglos chicos encontrados en las pruebas end-to-end y en el relevamiento de pantallas. Es el
> grupo P-2 de `/home/lautaro/Documentos/proyectos/interno/gestor/conectores/jiku-docs/docs/backlog-jiku-web.md`,
> ítems 3, 4, 14, 15 y 18.
>
> 1. **CORS solo bajo `/api`.**
>    - Hoy `api/app.ts` aplica `app.use(cors())` a todo, y `/p/docs/*` responde
>      `Access-Control-Allow-Origin: *`. Así, cualquier origen puede leer por JavaScript el HTML de
>      un link compartido si conoce el token.
>    - Pedido: montar CORS solo donde lo necesitan los frontends. Las rutas públicas `/p/docs/*` no
>      emiten cabeceras CORS. Con test.
>    - **No toques la autenticación ni `getRolesFromToken`:** la api no acepta tokens de machine
>      users, por decisión del dueño.
> 2. **Warning en cada adjunto de docs.**
>    - `core/src/commands/resolve-actor.ts` registra con nivel `warn` "comando publicado por un
>      caller externo" en cada `files.request-upload` de jiku-docs, que es el camino normal según
>      D-3.
>    - Pedido: bajarlo a `debug` para callers de clase `connector` y mantener el `warn` donde
>      corresponda.
> 3. **Pills del detalle de requisito.** En la web, las pills de estado, tipo y prioridad se
>    anuncian las tres como "Estado: …" en lectores de pantalla. Cada una tiene que anunciar su
>    propio atributo. Con test.
> 4. **"Vencido hace: 32666 día(s)" en el listado de tareas de la web.** Una fecha nula o inválida
>    produce ese texto. Pedido: no mostrar el vencimiento cuando la fecha es nula o inválida, y
>    revisar el cálculo. Con test.
> 5. **opus-web, externo que abre un requisito interno.** Hoy ve "Error al cargar el requisito"
>    con "Reintentar", sin header ni explicación. Pedido: un estado claro de "no disponible o sin
>    acceso", con navegación de vuelta al tablero, que no ofrezca reintentar algo que nunca va a
>    funcionar. Con test.

## Clarificaciones

### Supuestos (modo automático)

El dueño del producto delegó las decisiones de detalle; no se hicieron preguntas. Cada ambigüedad se
resolvió así:

- **[Dónde se monta CORS]:** → **Supuesto tomado:** solo bajo `/api` (que es donde llaman web y
  opus-web). Ninguna ruta fuera de `/api` (en particular `/p/docs/*`) emite
  `Access-Control-Allow-Origin` ni responde preflight CORS. La configuración de `cors()` no cambia
  (mismo comportamiento que hoy dentro de `/api`).
- **[Autenticación]:** → **Supuesto tomado:** no se toca. La api sigue sin aceptar tokens de machine
  users y `getRolesFromToken` no cambia.
- **[Qué es "clase `connector`" para el log de core]:** → **Supuesto tomado:** la misma clasificación
  de caller que ya usa core (S-030). Para un caller de clase `connector` la rama externa de
  `resolveActor` loguea en `debug`; para cualquier otro caller externo (no clasificado, desconocido)
  se mantiene el `warn`. El texto del mensaje, el valor devuelto y el criterio de no loguear el
  payload no cambian. La rama del `actor` verificado y la de la api siguen sin loguear nada.
- **[Qué anuncia cada pill]:** → **Supuesto tomado:** "Estado: …", "Tipo: …" y "Prioridad: …"
  respectivamente. El `Badge` editable recibe el nombre del atributo como prop con default
  "Estado", así los usos actuales que son de estado no cambian.
- **[Alcance del arreglo de las pills]:** → **Supuesto tomado:** cualquier otro uso del `Badge`
  editable que no sea de estado también pasa el nombre correcto si el cambio es trivial.
- **[Fecha nula o inválida en "Tareas"]:** → **Supuesto tomado:** si la fecha estimada de fin es
  nula, vacía o no parsea a una fecha válida, no se muestra texto de vencimiento ni se marca como
  cercana al vencimiento. Se revisa el cálculo de días para que no dependa de `new Date(null)` ni
  de fechas `Invalid Date`.
- **[Qué cuenta como "no disponible o sin acceso" en opus-web]:** → **Supuesto tomado:** 403, 404 o
  `code` de "sin permiso"/"no encontrado" que devuelva la api al cargar el requisito. Se muestra un
  estado con título y explicación ("El requisito no está disponible o no tenés acceso"), con un
  botón para volver al tablero del proyecto y **sin** "Reintentar". El header/layout del portal se
  mantiene visible.
- **[Otros errores en opus-web]:** → **Supuesto tomado:** errores de red o 5xx siguen ofreciendo
  "Reintentar", porque ahí sí puede funcionar.
- **[Página y modal]:** → **Supuesto tomado:** el tratamiento aplica a la página de detalle y al
  `RequirementDetailModal` de opus-web.

## Requerimientos Funcionales

1. La api aplica CORS solo a las rutas bajo `/api`. Las rutas públicas `/p/docs/*` no emiten
   cabeceras CORS.
2. La autenticación de la api y `getRolesFromToken` no cambian.
3. En core, la rama de caller externo de `resolveActor` loguea en `debug` cuando el caller es de
   clase `connector`, y en `warn` para cualquier otro caller externo.
4. En el detalle de requisito de la web, cada pill (estado, tipo, prioridad) se anuncia en lectores
   de pantalla con el nombre de su propio atributo.
5. En el listado de tareas de la web, una fecha estimada de fin nula o inválida no produce texto de
   vencimiento ni marca de "cerca del vencimiento".
6. En opus-web, un requisito que la api devuelve como no encontrado o sin permiso muestra un estado
   claro de "no disponible o sin acceso", con navegación de vuelta al tablero del proyecto y sin
   "Reintentar".
7. Los demás errores de carga del requisito en opus-web conservan "Reintentar".

## Criterios de Aceptación

1. DADO un request a una ruta pública `/p/docs/{token}` con cabecera `Origin`
   CUANDO la api responde
   ENTONCES la respuesta no lleva `Access-Control-Allow-Origin`.

2. DADO un preflight `OPTIONS` a `/p/docs/{token}`
   CUANDO la api responde
   ENTONCES no lleva cabeceras CORS.

3. DADO un request a una ruta bajo `/api` con cabecera `Origin`
   CUANDO la api responde
   ENTONCES lleva las mismas cabeceras CORS que hoy (incluido el preflight).

4. DADO un comando `files.request-upload` publicado por un caller de clase `connector` (jiku-docs)
   CUANDO core resuelve el actor
   ENTONCES el mensaje de caller externo se registra en `debug` y no en `warn`.

5. DADO un comando publicado por un caller externo que no es de clase `connector`
   CUANDO core resuelve el actor
   ENTONCES el mensaje se sigue registrando en `warn`.

6. DADO un comando con `actor` verificado o publicado por la api
   CUANDO core resuelve el actor
   ENTONCES no se registra ningún log (sin cambios).

7. DADO el detalle de un requisito en la web
   CUANDO un lector de pantalla recorre las pills
   ENTONCES anuncia "Estado: …", "Tipo: …" y "Prioridad: …" respectivamente.

8. DADO una tarea con fecha estimada de fin nula, vacía o inválida
   CUANDO se renderiza el listado de tareas
   ENTONCES no aparece texto "Vencido hace" ni "Falta", ni marca de cercanía al vencimiento.

9. DADO una tarea con fecha estimada de fin válida vencida hace 3 días y no cerrada
   CUANDO se renderiza el listado
   ENTONCES muestra "Vencido hace: 3 día(s)".

10. DADO un externo en opus-web que abre un requisito interno (la api responde 403 o 404)
    CUANDO carga la página o el modal de detalle
    ENTONCES ve un estado de "no disponible o sin acceso" con explicación, un botón para volver al
    tablero del proyecto y ningún botón "Reintentar".

11. DADO un error de red o 5xx al cargar el requisito en opus-web
    CUANDO se muestra el error
    ENTONCES sigue ofreciendo "Reintentar".

### Decisiones de diseño

- **DD-1 — CORS montado en `/api`, misma configuración.** En `api/app.ts` la línea 59 pasa a
  `app.use('/api', cors())`, **en la misma posición** (después de `publicHostOnly`, antes de
  `validateToken`), así el preflight `OPTIONS` bajo `/api` lo sigue respondiendo `cors()` con 204
  antes de que `validateToken` lo vea (CA-3). Fuera de `/api` no hay ningún middleware CORS: `/p/docs/*`
  y el fallback 404 no emiten `Access-Control-*` (CA-1). Un `OPTIONS /p/docs/{token}` cae en
  `publicHostOnly` (404 en el host público, solo pasan `GET`/`HEAD`) o en el manejo por defecto de
  Express, en ninguno de los dos casos con cabeceras CORS (CA-2). No se toca `validateToken`,
  `config/public.ts` ni `getRolesFromToken` (RF-2).
- **DD-2 — Test de CORS con la app real.** Un test nuevo en `api/tests/routes/` (supertest contra
  `initialize()`, mismo patrón que los tests de `public-share`) verifica: `GET /p/docs/{token}` con
  `Origin` → sin `access-control-allow-origin`; `OPTIONS /p/docs/{token}` con
  `Access-Control-Request-Method` → sin cabeceras CORS; `GET` y `OPTIONS` a una ruta bajo `/api` →
  `access-control-allow-origin: *` y, en el preflight, `access-control-allow-methods`.
- **DD-3 — `callerClass` viaja en el `CommandContext`.** El despachador ya calcula `callerClass`
  (`dispatcher.ts:272`, `:367-373`) para la compuerta de entidad, pero no lo pasa al comando. Se
  agrega `callerClass: CallerClass` (no opcional, mismo criterio que `roles`: el despachador siempre
  sabe cuál es) a `CommandContext` y a los dos puntos donde se arma el contexto. Es la **misma**
  clasificación de S-030 (`resolveCallerClass`, una sola tabla); no se duplica la lógica en
  `resolveActor`. Los tests que arman un `CommandContext` a mano (p. ej.
  `tests/commands/notifications.test.ts`) agregan el campo.
- **DD-4 — Nivel por clase en la rama externa.** En `resolveActor`, rama externa:
  `ctx.callerClass === 'connector'` → `logger.debug(...)`; cualquier otra clase → `logger.warn(...)`.
  Mismo texto, mismo valor devuelto (`ctx.caller`), sin payload. La rama del sobre y la de la api no
  loguean nada (CA-6, sin cambios). El comentario de la función explica por qué: para jiku-docs
  (`internal-app` → `connector`) es el camino normal según D-3; el `warn` queda como señal de un
  `CORE_TRUSTED_PUBLISHER_ID` mal configurado (la api con rol `internal-app` sin sobre ya cae en la
  rama de la api, no acá) o de una persona publicando directo.
  - En producción la consola de core loguea desde `info` (`core/src/logger.ts`), así que el mensaje
    deja de verse sin configuración extra; el archivo depende de `LOGGER_INFO_LEVEL`.
  - **Tests:** TS-26 (`files.test.ts:504`) usa `EXTERNAL` con rol `internal-app`, o sea clase
    `connector`: pasa a afirmar `debug` llamado una vez con `[files.request-upload]` y el caller, y
    `warn` no llamado (CA-4). Caso nuevo con un caller directo de rol `user` (clase `internal`, que
    tiene `files.request-upload` en `INTERNAL_COMMANDS`) → `warn` una vez (CA-5). TS-27 y
    `attachments.test.ts:311-318` se mantienen (CA-6). El `sinon.stub(logger, 'warn')` de
    `files.test.ts:1013` se revisa: con caller `connector` ya no hace falta.
- **DD-5 — `Badge` editable con nombre de atributo.** Prop nueva solo en `BadgeEditableProps`:
  `attributeLabel?: string`, default `'Estado'`; `aria-label={`${attributeLabel}: ${label}`}`.
  `RequirementHeader` pasa `attributeLabel="Tipo"` y `attributeLabel="Prioridad"` a los editables de
  tipo y prioridad; el de estado queda con el default. `StateTag` (único otro uso del editable, que es
  de estado) no cambia. Tests: `Badge.test.tsx` (default y prop) y `RequirementHeader.test.tsx` (los
  tres nombres accesibles con `canEdit`) (CA-7). La spec del DS (`badge.md` §Accesibilidad) documenta
  la prop; el bump del DS lo resuelve `/product-ux-request`.
- **DD-6 — "Fecha válida" = la forma del contrato.** Helper nuevo en `web/src/shared/utils/`:
  `parseFinishDate(value: Date | string | null | undefined): Date | null`.
  - Devuelve `null` si el valor es nulo, vacío, un `Date` inválido, o un string que **no empieza con
    `YYYY-MM-DD`** (la forma que declara `core.yaml:2057` y `api.yaml` `format: date`). La columna
    es `VARCHAR` (`jiku.md:307`) y puede traer texto heredado que `new Date()` interpreta a su manera.
  - Un `YYYY-MM-DD` se construye como **fecha local** (`new Date(y, m - 1, d)`), no con
    `new Date('YYYY-MM-DD')`, que lo toma como UTC y en Argentina (UTC-3) cae el día anterior: es un
    corrimiento de un día en el cálculo actual ("revisar el cálculo", RF-5).
  - `ObjectivesTable` usa el helper en `getFinishDateText` (inválida → "No definida", hoy daría
    "Hasta: NaN Invalid Date | "), `getDaysLeftText` (inválida → `''`; hoy `calculateDaysLeft` con
    `Invalid Date` devuelve `0` → "Vence hoy") e `isCloseToDeadline` (inválida → `false`). `isOverdue`
    (`objectiveHelpers.ts`) y `ObjectiveCard` usan el mismo helper (cambio trivial, mismo criterio).
  - `calculateDaysLeft` no cambia de firma ni de semántica: **cuenta días hábiles** (lunes a
    viernes). 32 666 días hábiles son ~125 años, o sea una fecha alrededor de 1900 producida por un
    texto heredado no ISO. La story reproduce el caso con el valor real del entorno e2e y lo fija en
    un test; si ese valor resultara ser un `YYYY-MM-DD` válido, se reporta como dato y no se esconde.
  - Tests (CA-8, CA-9): `parseFinishDate` (null, `''`, `'abc'`, `'31/12/2026'`, `Invalid Date`,
    `'2026-10-23'`, ISO con hora) y `ObjectivesTable` con reloj fijo: fecha vencida hace 3 días
    hábiles y estado abierto → "Vencido hace: 3 día(s)"; fecha nula/inválida → ni "Vencido hace" ni
    "Falta" ni la clase `closeToDeadline`.
- **DD-7 — Clasificación del error del requisito en opus-web.** Helper
  `classifyRequirementError(error): 'not_found' | 'system'` en `features/requirements/utils/`:
  `status` 403 o 404, o `code` `requirement_not_found` / `access_denied` → `not_found`; cualquier
  otro (5xx, red: el interceptor de `lib/axios.ts` deja `status: 500`, `code: 'unknown_error'`) →
  `system`. Mismo criterio que `classifyDocumentError` (DD-3 de REQ-016): no se distingue "no existe"
  de "sin permiso", porque la api ya los iguala a propósito (`api.yaml:2989-2991`).
- **DD-8 — Estado "no disponible o sin acceso".** Componente compartido
  `RequirementUnavailable` (página y modal) con título y explicación: *"El requisito no está

### Flujo de Interacción

#### Escenario: lectura de un link compartido desde otro origen (CA-1, CA-2)

1. **Navegador de un tercero** — `fetch('{JIKU_PUBLIC_URL}/p/docs/{token}')` con `Origin: https://otro`.
2. **api** — `publicHostOnly` → (sin CORS) → `express.json()` → logger (ignora `/p/docs/*`) →
   `validateToken` (exento por `config/public.ts`) → `publicRoutes` → `shares.resolve` → 200 HTML.
3. **Navegador** — la respuesta no trae `Access-Control-Allow-Origin` → el script no puede leerla.
   Abrir el link en una pestaña sigue igual.

#### Escenario: frontend propio o cliente llama a `/api` (CA-3)

1. `OPTIONS /api/...` con `Origin` → `cors()` montado en `/api` responde 204 con las cabeceras de hoy.
2. `GET /api/...` → `cors()` agrega `Access-Control-Allow-Origin: *` → `validateToken` → ruta.

#### Escenario: jiku-docs pide una subida (CA-4 a CA-6)

1. **jiku-docs** publica `files.request-upload` sin sobre; subject con su `sub` (rol `internal-app`).
2. **core / despachador** — compuerta 1 (`internal-app` → `ALL`), compuerta 2
   `resolveCallerClass(['internal-app'])` → `connector`; arma el contexto con `callerClass`.
3. **core / `resolveActor`** — sin sobre, caller ≠ `CORE_TRUSTED_PUBLISHER_ID` → rama externa →
   `logger.debug('[files.request-upload] comando publicado por un caller externo: {sub}. …')` →
   devuelve `ctx.caller`.
4. Persona de rol `user` publicando directo → clase `internal` → mismo mensaje en `warn`.
   Sobre o api sin sobre → sin log.

#### Escenario: externo abre un requisito interno en opus-web (CA-10, CA-11)

1. **opus-web** — página o modal → `useRequirement` → `GET /api/opus/requirements/{id}` (route
   handler same-origin que agrega el token).
2. **api** — requisito `internal` → `404 { code: 'requirement_not_found', message }` (o `403
   access_denied` sin permiso de proyecto).
3. **opus-web** — `classifyRequirementError` → `not_found` → sin reintento de TanStack →
   `RequirementUnavailable` con "Volver al tablero" y sin "Reintentar".
4. Error de red o 5xx → `system` → un reintento automático → "Error al cargar el requisito" +
   "Reintentar".

**Manejo de errores:** 401 sigue redirigiendo a `/login` desde el interceptor de `lib/axios.ts`.

### Consideraciones Técnicas

#### Riesgos
- **Clientes de navegador que dependan de CORS fuera de `/api`.** No hay ninguno propio: web y
  opus-web llaman desde el servidor (overviews de web y opus-web) y `/p/docs/*` se abre como página.
  Un tercero que hiciera `fetch` a un link compartido deja de poder leerlo, que es justamente el
  objetivo. Se anota en la release.
- **`callerClass` obligatorio en `CommandContext`.** Rompe la compilación de los tests que arman el
  contexto a mano; es deseado (mismo criterio que `roles`) y se arregla en la misma story.
- **El valor real del "32666".** Si el dato heredado fuera un `YYYY-MM-DD` válido muy viejo, el
  guard no lo oculta (DD-6); la story lo verifica contra el entorno e2e antes de cerrar.
- **Badge en el DS.** La prop nueva es aditiva; los usos actuales no cambian.

#### Dependencias
- Ninguna entre stories ni con jiku-docs.

#### Performance
- `parseFinishDate` evita que `calculateDaysLeft` recorra ~45 000 días por fila con fechas de 1900
  en un server component. El resto, sin impacto.

#### Seguridad
- Cierra F-18: el HTML de un link compartido ya no es legible por JavaScript de otro origen aunque
  se conozca el token.
- La autenticación no cambia (RF-2, ADR-007/ADR-009); la api sigue sin aceptar tokens de machine users.
- opus-web no distingue "no existe" de "sin permiso", igual que la api.
