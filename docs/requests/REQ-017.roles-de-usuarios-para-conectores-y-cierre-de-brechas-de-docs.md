# REQ-017: Roles de usuarios para conectores y cierre de brechas de docs (seguimiento de REQ-016)

## Requerimiento Original

> Seguimiento de REQ-016, que ya está implementado y mergeado en `feat/jiku-docs`:
>
> 1. **core expone `roles` e `identityType` de `users` solo a la clase `connector`.** Es la decisión
>    D-10 de `conectores/jiku-docs/docs/decisiones-integracion.md`.
>    - jiku-docs clasifica a quien lo llama con
>      `users.list {filter:{id:[...]}, include:["roles","identityType"]}`. Hoy
>      `core/src/queries/users/users-spec.ts` los excluye a propósito (CA-7). Sin ellos, jiku-docs
>      responde `upstream_unavailable` a cualquier persona, y bloquea la integración.
>    - Quedan como incluibles solo para callers de clase `connector` (roles `internal-app`, y por lo
>      tanto `docs`), sin filtro ni orden.
>    - Para personas internas y externas siguen sin existir: responden `invalid_fields` y
>      `meta.describe` no los muestra. Así CA-7 se mantiene para quien importa.
>    - Tests de ambos lados, más la actualización de `docs/apis/core-queries.yaml` y su test de
>      paridad si existe.
>    - Si la ficha no admite "incluible por clase", diseñá el mecanismo mínimo y consistente con
>      ADR-008.
> 2. **Cerrar la brecha de `GET /opus/docs/attachments/{id}`.** Hoy un usuario interno que entra al
>    portal opus-web y conoce el id de un adjunto de un documento `internal` puede descargarlo. Por
>    el portal solo se sirven adjuntos de documentos `public`, sin importar el rol de quien pida.
>    Revisá también las demás rutas `/opus/docs/*` con el mismo criterio.
> 3. **Correcciones en `docs/apis/api.yaml` que quedaron reportadas en ADR-015:**
>    - el conteo de endpoints del encabezado;
>    - el 400 que declara `DELETE /docs/shares/{id}` y que el handler no produce;
>    - el 413 que falta en las escrituras de docs con cuerpo grande.
>
>    Actualizá también los conteos desactualizados en `README.md`,
>    `documentation/api-reference.md`, `docs/architectures/api/conventions/_base.md`,
>    `documentation/installation.md` y `documentation/known-limitations.md`.

## Clarificaciones

### Supuestos (modo automático)

El dueño del producto delegó todas las decisiones; no se hicieron preguntas. Cada ambigüedad se
resolvió así:

- **[Qué significa "incluible por clase"]:** → **Supuesto tomado:** `roles` e `identityType` se
  agregan a la ficha de `users` como campos **incluibles restringidos a la clase `connector`**. Para
  un caller `connector` se comportan como cualquier incluible (se piden en `include`, salen en
  `meta.describe` y se devuelven); para `person-internal` y `person-external` **no existen**: pedirlos
  en `include`, `fields`, `filter` o `sort` responde `invalid_fields` exactamente igual que un nombre
  inexistente, y `meta.describe` no los lista. Si el motor no soporta esa restricción, el diseño agrega
  el mecanismo mínimo **declarativo en la ficha** (un dato, no código en el handler), consistente con
  ADR-008: "no está declarado para tu clase" es la única forma de "no se puede pedir".
- **[Filtro y orden]:** → **Supuesto tomado:** ni filtrables ni ordenables, ni para la clase
  `connector`. Tampoco entran en `q`.
- **[Forma de los valores]:** → **Supuesto tomado:** `roles` sale como lista de strings tal como está
  en la tabla (incluye roles que core no conoce, como `docs`) e `identityType` como string con los
  valores de la columna (`person` / `service`). El diseño fija la forma exacta según el esquema real.
- **[Quién es `connector`]:** → **Supuesto tomado:** la clase que core ya calcula (S-023): un usuario
  con rol `internal-app`, con o sin roles adicionales desconocidos. jiku-docs (`[internal-app, docs]`)
  y la api quedan dentro. Un `admin` o `user` humano **no** es `connector`.
- **[Contrato de core]:** → **Supuesto tomado:** `docs/apis/core-queries.yaml` documenta los dos
  incluibles con su restricción de clase; si existe un test de paridad entre la ficha y el contrato,
  se actualiza para que entienda la restricción.
- **[Cómo se cierra la brecha del portal]:** el reply de `attachments.{id}.request-download` no trae
  la visibilidad del documento (F-13). → **Supuesto tomado:** la api **no sirve un adjunto por el
  portal sin haber verificado que pertenece a un documento `public`**, para cualquier rol. El diseño
  elige el mecanismo con lo que el contrato de jiku-docs ya ofrece (por ejemplo, exigir el id del
  documento y comprobar visibilidad y pertenencia con `documents.get` / `attachments.list`); si eso
  cambia lo que manda opus-web, opus-web se ajusta en la misma entrega. Jiku-docs no se modifica.
- **[Cuando no es `public`]:** → **Supuesto tomado:** 404 `attachment_not_found` (o
  `document_not_found` si el error es del documento), indistinguible de un adjunto inexistente. Nunca
  403: el portal no revela que existe un documento interno.
- **[Las demás rutas `/opus/docs/*`]:** → **Supuesto tomado:** se revisan `GET /opus/docs/documents` y
  `GET /opus/docs/documents/{id}` con el mismo criterio (solo `public`, sin importar el rol). Si
  alguna deja pasar algo no `public` para algún rol, se corrige en la misma entrega; si ya cumplen,
  se agrega el test que lo prueba para usuarios internos.
- **[400 de `DELETE /docs/shares/{id}`]:** → **Supuesto tomado:** se corrige el contrato, no el
  handler: se quita el `400` (el id mal formado responde 404 `share_not_found`). Si jiku-docs llegara
  a responder `invalid_fields`, el mapa de errores lo traduce igual que en el resto de las rutas.
- **[413 en las escrituras de docs]:** → **Supuesto tomado:** se declara `413` en todas las
  operaciones `POST`/`PUT` de `/docs/*` sujetas a `DOCS_WRITE_BODY_LIMIT` (768 KiB). El contrato
  describe el cuerpo **real** que produce body-parser hoy (no es `{code, message}`); el diseño decide si
  conviene además un manejador que lo convierta a `{code, message}`, siempre que el contrato y el
  código queden alineados.
- **[Conteos]:** → **Supuesto tomado:** el conteo correcto se obtiene contando las operaciones de
  `docs/apis/api.yaml` después de los cambios de este REQ (si se agrega o cambia una ruta, cuenta), y
  todos los documentos citados quedan con el mismo número. Si alguno de esos documentos no tiene
  conteo, no se le agrega uno.
- **[Ruta `/docs/documents/{id}` de la web (F-31)]:** D-10 la menciona junto con este cambio, pero el
  pedido no la incluye. → **Supuesto tomado:** **fuera de alcance**; queda como pendiente.
- **[Versión del producto]:** → **Supuesto tomado:** este REQ no versiona; la release es otra
  acción.
- **[Prioridad]:** → **Supuesto tomado:** alta. El punto 1 bloquea la integración de jiku-docs.

## Requerimientos Funcionales

### core: `roles` e `identityType` para conectores
1. Un caller de clase `connector` puede pedir `roles` e `identityType` en el `include` de
   `users.list` y recibirlos en cada usuario.
2. Para un caller `person-internal` o `person-external`, `roles` e `identityType` no existen: pedirlos
   por cualquier palanca (`include`, `fields`, `filter`, `sort`) responde `invalid_fields`.
3. `meta.describe` de `users` lista `roles` e `identityType` como incluibles solo para la clase
   `connector`; para personas no los muestra.
4. Ninguno de los dos es filtrable ni ordenable para ninguna clase.
5. La restricción vive declarada en la ficha del recurso (ADR-008), no en código del handler.
6. `docs/apis/core-queries.yaml` documenta los dos incluibles y su restricción de clase.

### api: portal de documentación
7. `GET /opus/docs/attachments/{id}` (o la ruta que lo reemplace) solo entrega adjuntos de
   documentos `public`, para cualquier rol que use el portal (`external-user`, `admin`, `user`).
8. Un adjunto de un documento no `public` responde 404, indistinguible de uno inexistente.
9. `GET /opus/docs/documents` y `GET /opus/docs/documents/{id}` solo devuelven documentos `public`
   para cualquier rol, con test que lo pruebe para usuarios internos.
10. Si el cambio de la ruta de adjuntos altera lo que manda el portal, opus-web se adapta y los
    adjuntos de documentos `public` se siguen viendo en el visor del portal.

### Contrato y documentación
11. El encabezado de `docs/apis/api.yaml` declara el número real de operaciones.
12. `DELETE /docs/shares/{id}` no declara un `400` que el handler no produce.
13. Las escrituras de `/docs/*` con límite de cuerpo declaran el `413` con el cuerpo que realmente
    se devuelve.
14. `README.md`, `documentation/api-reference.md`, `docs/architectures/api/conventions/_base.md`,
    `documentation/installation.md` y `documentation/known-limitations.md` dicen el mismo conteo que
    `api.yaml` donde citan uno, y `known-limitations.md` deja de declarar la brecha F-13.
15. ADR-015 registra como resueltos F-12, F-13, F-30, B-1, B-2, B-3 y B-4.

## Criterios de Aceptacion

1. DADO un caller de clase `connector` (roles `[internal-app, docs]`)
   CUANDO pide `users.list {filter:{id:[<id de una persona>]}, include:["roles","identityType"]}`
   ENTONCES recibe al usuario con `roles` (lista) e `identityType` (`person`/`service`).

2. DADO un caller de clase `connector` con solo `internal-app`
   CUANDO pide los mismos incluibles
   ENTONCES también los recibe.

3. DADO un caller `person-internal` (rol `admin` o `user`)
   CUANDO pide `users.list` con `include:["roles"]` o `include:["identityType"]`
   ENTONCES recibe `invalid_fields`, igual que con un nombre inexistente.

4. DADO un caller `person-external`
   CUANDO pide `users.list` con `include:["roles","identityType"]`
   ENTONCES recibe `invalid_fields`.

5. DADO cualquier caller, incluido un `connector`
   CUANDO pide `users.list` con `filter:{roles:...}`, `filter:{identityType:...}` o `sort:["roles"]`
   ENTONCES recibe `invalid_fields`.

6. DADO un caller `connector`
   CUANDO pide `meta.describe` de `users`
   ENTONCES ve `roles` e `identityType` entre los incluibles.

7. DADO un caller `person-internal` o `person-external`
   CUANDO pide `meta.describe` de `users`
   ENTONCES no ve `roles` ni `identityType` en ninguna lista.

8. DADO un usuario interno (`admin` o `user`) en el portal opus-web
   CUANDO pide un adjunto de un documento `internal` por la ruta de adjuntos del portal, conociendo
   su id
   ENTONCES recibe 404 y no se genera ninguna URL de descarga.

9. DADO un usuario externo con permiso sobre el proyecto
   CUANDO pide un adjunto de un documento `public` vinculado a su proyecto por el portal
   ENTONCES recibe la redirección 302 a la descarga, como hoy.

10. DADO un usuario interno en el portal
    CUANDO lista documentos o abre un documento `internal` por `/opus/docs/*`
    ENTONCES no lo ve en la lista y la ficha responde 404.

11. DADO el visor del portal con un documento `public` que embebe adjuntos
    CUANDO se renderiza
    ENTONCES los adjuntos se ven (las URLs reescritas apuntan a la ruta del portal vigente).

12. DADO `docs/apis/api.yaml`
    CUANDO se cuentan sus operaciones
    ENTONCES el número coincide con el del encabezado y con los citados en README y `documentation/`.

13. DADO un `POST`/`PUT` de `/api/docs` con un cuerpo mayor a 768 KiB
    CUANDO llega a la api
    ENTONCES responde 413 tal como lo declara el contrato.

14. DADO `DELETE /docs/shares/{id}` en el contrato
    CUANDO se revisan sus respuestas
    ENTONCES no declara `400`.

15. DADO el monorepo con los cambios
    CUANDO se corre `npm run build && npm run lint && npm test`
    ENTONCES todo pasa.
