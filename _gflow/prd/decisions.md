# Decisiones

Lo que se eligió a propósito frente a una alternativa. Un requisito que cambia una decisión la revierte explícitamente.

## Técnicas

| ID | Tema | Decisión | Descartado | Motivo | Afecta | Origen |
|---|---|---|---|---|---|---|
| DEC-T01 | Separación lectura/escritura | La api lee con un rol de PostgreSQL sin escritura y core es el único que escribe, con el rol dueño; la separación la impone la base por permisos | Una capa de servicios dentro de la api; un solo servicio con transacciones explícitas por endpoint; microservicios con una base por servicio | La garantía no puede depender de que cada endpoint recuerde aplicar las reglas: con permisos de la base, la disciplina deja de ser opcional | api, core, GAR-28 | inicial |
| DEC-T02 | Comandos por el bus | Toda escritura viaja de la api a core como comando NATS request/reply, sin JetStream ni broker de colas; la api espera la respuesta con timeout y un comando perdido es un comando perdido | JetStream para comandos; una API HTTP interna en core; escritura directa desde la api | Mantener la respuesta inmediata al usuario: con cola, el frontend tendría que manejar «aceptado pero no aplicado» | api, core, BUS, BUS-09 | inicial |
| DEC-T03 | Transacción del despachador | El despachador de core abre y cierra la transacción de cada comando y es dueño de sus efectos posteriores (notificaciones en la transacción, eventos después del commit); el comando no puede confirmar ni revertir | Que cada comando administre su transacción; un decorador transaccional por comando; escritura sin transacción con compensaciones | Un comando no puede olvidarse de revertir si el rollback no es su responsabilidad | core, BUS-08, GAR-27 | inicial |
| DEC-T04 | Vocabulario del contrato | El bus usa el vocabulario del producto (`task`, `properties`, prioridad como nombre) y core traduce al esquema (`objectives`, `key_value_pairs`, prioridad numérica); el contrato HTTP conserva el vocabulario viejo | Renombrar la base al vocabulario del producto; no traducir; vistas de PostgreSQL con los nombres nuevos | Renombrar la base era caro y de beneficio cosmético | core, api, core.tasks, core.projects | inicial |
| DEC-T05 | Modelos compartidos | Los modelos Sequelize viven en el paquete `models`, que describe la base tal como es y no abre conexión: cada servicio los registra con sus credenciales | Modelos duplicados en cada servicio; un paquete que también abre la conexión; SQL directo sin ORM | La separación de credenciales es la garantía de integridad del producto | models, api, core | inicial |
| DEC-T06 | Dos frontends, una api | `web` y `opus-web` son aplicaciones Next separadas sobre la misma api, con la superficie del portal separada por ruteo (`/api/opus/*`), rol y permiso de proyecto | Una aplicación con secciones por rol; los mismos endpoints con filtrado por rol; un backend separado para el portal | Con superficies separadas, lo que un cliente ve es lo que se le expuso a propósito | web, opus-web, api.opus | inicial |
| DEC-T07 | Identidad | Zitadel es la fuente de identidad de personas, servicios y del bus: OIDC con PKCE en las superficies, service users con key JSON y token renovado solo para api y core, y un auth-callout que valida el token de cada conexión NATS y mintea sus permisos por rol | Autenticación propia con usuarios y contraseñas; NATS con credenciales estáticas por cuenta | La organización ya tenía Zitadel; un secreto estático no alcanza cuando la autorización del bus es la autorización de escritura | ACC, api, core, CRED-04, CRED-06 | inicial |
| DEC-T08 | Autenticación deny-by-default | `validateToken` se instala globalmente en la api y lo público se declara en una única lista de exenciones (`api/config/public.ts`); encima, rol por ruta y permiso por entidad | Middleware de autenticación por ruta; autorización declarativa en el índice de rutas; autorización en el gateway | Un endpoint nuevo queda protegido sin que su autor haga nada | api, ACC-08, GAR-36 | inicial |
| DEC-T09 | Llamadas a la api desde el servidor de Next | Toda llamada a la api sale del servidor de Next con el Bearer de la sesión: Server Actions y route handlers puntuales en `web`, proxy catch-all `/api/opus/[...path]` en `opus-web`; la URL de la api se lee en runtime (`API_URL`) y las imágenes no hornean configuración | SPA con el token en el navegador; cookie httpOnly con llamadas directas del navegador; un BFF completo por frontend | — | web, opus-web | inicial |
| DEC-T10 | Estilos | Sass con CSS Modules y custom properties, con componentes propios en cada frontend; sin librería de componentes | Una librería de componentes (MUI, Chakra, Ant Design); Tailwind CSS; CSS-in-JS | El producto tiene identidad y patrones propios | web, opus-web | inicial |
| DEC-T11 | Estado de servidor en los frontends | TanStack Query es la única capa de datos remotos; mutaciones sin reintento | Redux Toolkit; solo Server Components y `fetch` sin cache de cliente; SWR | Reintentar una escritura sin idempotencia duplicaría datos | web, opus-web | inicial |
| DEC-T12 | Monorepo | Monorepo npm con workspaces (`api`, `core`, `web`, `opus-web`, `packages/*`); los Dockerfiles se construyen con contexto en la raíz | Repositorios separados con paquetes publicados; Nx o Turborepo; código compartido por copia; yarn, pnpm o bun | Compartir modelos y protocolo sin que puedan divergir | api, core, web, opus-web, models, nats-protocol, zitadel-auth | inicial |
| DEC-T13 | Tests contra base real | Los tests de api y core corren contra PostgreSQL real en Docker (o el del CI) con el esquema creado por los modelos, y el doble del bus de la api ejecuta core contra la misma base | Mocks de Sequelize; SQLite en memoria; un doble del bus con respuestas fijas como única opción | Un mock confirma la expectativa en lugar de verificar el comportamiento | api, core | inicial |
| DEC-T14 | Eventos de dominio | JetStream solo para el stream `JIKU_EVENTS` sobre `{instance}.events.v1.>`, con versión propia (`NATS_EVENTS_VERSION`); se publican después del commit, sin outbox: a lo sumo una vez | Outbox transaccional para eventos; un stream por versión; separar por visibilidad en el subject | La ventana entre el commit y la publicación se asume | core.events, BUS-10, BUS-11, GAR-29 | inicial |
| DEC-T15 | Módulos opcionales | Un módulo se anuncia escribiendo su clave en el KV `JIKU_MODULES`; la api calcula su estado en memoria por réplica, con watch y ping periódico; los subjects del módulo salen del registro; los links públicos los sirve la api en la raíz, con host exclusivo | Nombre del servicio fijo o por variable; comodín de servicio en las plantillas del callout; servir la página pública desde la web; estado del módulo compartido entre réplicas | — | DOC, api.docs | inicial |
| DEC-T16 | Lenguaje y runtime | TypeScript estricto sobre Node 24 en los servicios, los frontends y los paquetes; imágenes `node:24.12-alpine3.23` con `TZ=UTC` | — | — | api, core, web, opus-web, models, nats-protocol, zitadel-auth | inicial |
| DEC-T17 | Framework HTTP | Express 5 en la api, una ruta por archivo, validación con Joi | — | — | api | inicial |
| DEC-T18 | Persistencia | PostgreSQL 15.4 con Sequelize 6 y `sequelize-typescript`; las consultas del bus usan SQL explícito sin modelos | — | — | api, core, models | inicial |
| DEC-T19 | Frontends | Next.js 16 con App Router y `output: 'standalone'`, React 19 | — | — | web, opus-web | inicial |
| DEC-T20 | Sesión de los frontends | NextAuth v5 (beta) con el provider de Zitadel y sesión JWT en cookie, sin refresh del access token | — | — | web, opus-web, CRED-01, CRED-02 | inicial |
| DEC-T21 | Frameworks de test | Mocha con should y sinon en api, core y `nats-protocol`; Vitest con Testing Library en web y opus-web | — | — | api, core, web, opus-web, nats-protocol | inicial |
| DEC-T22 | Versión única | Todo el monorepo comparte una versión, que `scripts/set-version.sh` escribe en cada `package.json` y en las versiones de imagen de `deploy/.env.dist`; mayor si rompe el contrato HTTP o el del bus | — | — | api, core, web, opus-web, models, nats-protocol, zitadel-auth | inicial |
| DEC-T23 | Publicación de imágenes | GitHub Actions: CI en cada push y pull request; imágenes `gravadigital/jiku-<servicio>` en Docker Hub con etiqueta `dev` en cada push a `dev` y `X.Y.Z`, `X.Y` y `latest` al empujar un tag `vX.Y.Z` | — | — | api, core, web, opus-web | inicial |
| DEC-T24 | Despliegue | Docker Compose en `deploy/`: producción con imágenes publicadas detrás de un ingress externo, una variante de desarrollo sin dependencias externas y una local completa (`local.sh`) | — | — | api, core, web, opus-web | inicial |
| DEC-T25 | Migraciones | sequelize-cli en `api/db-upgrade/migrations/`; la api, dueña del esquema, las corre al arrancar con un usuario de migración; las migraciones parten de un esquema base de producción y no lo crean desde cero | — | — | api | inicial |
| DEC-T26 | Sin cache | Ni api ni core usan cache: cada lectura va a la base o al bus | — | — | api, core | inicial |
| DEC-T27 | Identificadores | Ids enteros autoincrementales en las entidades; `users.id` es el `sub` de Zitadel; ULID en eventos, correlaciones y documentos; UUID v4 en las claves de almacenamiento | — | — | api, core, models, nats-protocol | inicial |
